Connect to external services and discover their capabilities.

`stigmer connect` lets you connect to MCP servers, discover their tools and
resource templates, and push the results to the Stigmer backend. This is how you
teach Stigmer what an MCP server can do — the discovered capabilities become
available to agents at runtime.

## Usage

```bash
stigmer connect
```

## Subcommands

### stigmer connect mcp-server

connect to an MCP server and discover its tools

```bash
stigmer connect mcp-server <slug-or-id> [flags]
```

| Flag        | Type     | Default | Description                                                                                                                    |
| ----------- | -------- | ------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `--dry-run` | `bool`   |         | discover and display results without pushing to the backend                                                                    |
| `--timeout` | `string` | `30`    | bound the wait for connection and discovery (always bounds --dry-run; bounds the server-side connect only when set explicitly) |

### How connection works

For **stdio-based servers**, the CLI spawns the server process locally.
Environment variables from your shell are passed through, so credentials (e.g.,
`GITHUB_TOKEN`) never leave your machine. Note that stdio servers are
local-runner-only: connecting one while authenticated to Stigmer Cloud is
refused, because cloud compute never spawns stdio subprocesses. Use `--dry-run`
(which runs entirely on your machine) or connect against a local
`stigmer server`.

For **HTTP-based servers**, the CLI connects to the configured URL directly.

### Passing credentials

A connect reads the keys the MCP server declares from your own vault (My vault)
in the organization, never from the command line. Save each key there first,
then connect:

```bash
stigmer vault set-secret PLANTON_API_KEY --mine
stigmer connect mcp-server planton
```

A server that signs in with OAuth uses the sign-in saved for its address, or
runs the sign-in in your browser when there is none. A server that also accepts
a personal token is satisfied by a secret saved under its login key. `--env` is
refused, naming the vault command.

### Environment variable placeholders

A server's command arguments (stdio) and HTTP headers may reference declared
environment variables using `${VAR_NAME}` syntax. For example, the filesystem
server takes its allowed directory as an argument:

```yaml validate-as="McpServer.spec"
stdio:
  command: npx
  args:
    - "-y"
    - "@modelcontextprotocol/server-filesystem"
    - "${FILESYSTEM_ALLOWED_DIR}"
env:
  FILESYSTEM_ALLOWED_DIR:
    description: Root directory the server is allowed to access
```

For `--dry-run`, placeholders are resolved from your shell (the variable must be
declared under the server's `env`); a real connect resolves them from your
vault. Resolution is strict: a missing variable produces a clear error naming
the variable, rather than passing a literal `${VAR}` to the server.

```bash
FILESYSTEM_ALLOWED_DIR="$HOME/projects" \
  stigmer connect mcp-server mcp-server-filesystem --dry-run
```

### Dry run

Use `--dry-run` to preview discovered capabilities without pushing them to the
backend.

```bash
stigmer connect mcp-server github --dry-run
```

### Bound the wait

```bash
stigmer connect mcp-server my-server --timeout 90
```

The value is a number of seconds. `--timeout` always bounds `--dry-run`'s local
discovery; for a real connect it bounds the wait only when set explicitly — the
connect keeps running server-side and persists its result, so a timeout here
means "stop waiting", not "the connect failed". Without an explicit `--timeout`,
a real connect waits for the server to finish (sandbox start and discovery can
take a few minutes).
