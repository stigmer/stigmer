### useCreateRoutine

Behavior hook that wraps `routine.apply()` with loading and error
state.

Creates a routine from a `RoutineInput`. Uses `apply()`
(upsert) rather than `create()` so re-submissions are idempotent —
matching the CLI's `stigmer apply` semantics and the established SDK
mutation hook pattern (`isCreating` flag, `error` state, `clearError`
reset, result returned from the promise, not stored in hook state).

NOTE: this hook is for CREATION. Editing an existing routine must
NOT go through `RoutineInput` — the input type cannot express every
metadata field (tags, description), and the server replaces spec and
mutable metadata wholesale on update, so a down-converting edit would
silently wipe them. Edit flows use the full-proto path instead (see
`useSetRoutineEnabled` for the pattern).

### useFireRoutine

Behavior hook that fires a routine once, immediately, and reports the
run's real outcome.

A fire is a two-level contract, and this hook honors both levels:

- A **gRPC error** means the fire itself was refused — a disabled
  routine answers `FAILED_PRECONDITION` with copy that names the
  remedy ("enable it before firing"). The error toast relays that
  copy verbatim (byte-identical across editions) and the promise
  rejects.
- A **success** means the fire happened. The result's `outcome` then
  says what the RUN did: `STARTED` (a run was created — a
  success toast), or `REFUSED` / `TARGET_MISSING` (a launch gate said
  no — an error toast carrying the gate's `refusalReason` verbatim).
  The promise RESOLVES in every one of these cases: a refused run is a
  successful fire honestly reported, and the caller decides what to
  do with it (navigate to the run, show the reason).

Firing starts a real, billable run — gate the call behind a
confirmation (the detail view uses `ConfirmDialog`).

### useResumeRoutine

Behavior hook that resumes a platform-paused routine.

Resume is the ONE path that clears `status.paused_reason` (and the
failure streak with it) — re-applying the manifest deliberately does
not, so a routine GitOps apply can never silently un-pause a failing
routine. Resuming a routine that is not paused is a server-side
no-op; resuming a disabled routine clears the pause but the routine
stays disabled (the owner's lever is separate — see
[`useSetRoutineEnabled`](#usesetroutineenabled)).

Error toasts relay the server's message verbatim: the copy is

### RoutineApiPanel

How another system starts this routine: the one HTTP call, what it
answers, and, where the edition shares a routine with a service account,
the three steps that set a caller up.

The setup is three existing acts by up to two people, never one wizard:
an organization admin creates the service account and its key (offered
here, with Viewer preset, to someone who may), the routine's creator
grants it Participant (Manage access), and the caller sends the key. The
key's reach beyond this routine is stated, since a key acts with its
account's whole organization role.

What shows follows the server:
- on open source (the server's reported edition), which grants roles on
  organizations only, so only a routine's creator may start it: use the
  creator's key;
- where an edition shares a routine with people and service accounts:
  the setup steps to someone who may grant on it (`can_grant_access`),
  "send your own key" to someone who may start it (`can_fire`), and to
  anyone else that starting it takes Participant from its creator. A
  permission answers for the person, never for the edition, so the
  edition is read from the server, not inferred from a refusal;
- the Authorization line unless the server trusts every request;
- the shared unknown-address notice when the server's public address
  cannot be known.

Zero Console dependencies; all visual properties flow through `--stgm-*`

day-of-week in cron numbering (0 = Sunday). For `custom`, the raw
string is returned as-is — validate it with [`validateCron`](#validatecron).

```tsx
function cadenceToCron(preset: CadencePreset): string
```


### createRoutineColumns

Column set for a routine workbench — shared by every console so the
list renders identically everywhere.

The columns exist because routines are listed via the direct query:
each row is a full `Routine` proto, so the operational fields the
issue calls for (next fire, last run, enabled/paused state) render
straight from the row — no generic `SearchResult` limitations.

Columns are not sortable: the direct query has one fixed server-side
order (newest first), and a sort affordance that silently does
nothing would lie.

```tsx
function createRoutineColumns(options?: RoutineColumnsOptions): WorkbenchColumnDef<Routine>[]
```


### createRoutineListFn

Build a `ResourceWorkbench` data source over the direct routine query.
Consumers type their workbench as `ResourceWorkbench<Routine>` and pass
`getItemId={(s) => s.metadata?.id}`.

`request.query` is ignored: routines have no server-side text search
(render the workbench with `searchable={false}`).

```tsx
function createRoutineListFn(client: RoutineListClient): WorkbenchListFn<Routine>
```


### cronToCadence

Recognize a cron expression as one of the builder's presets.

Only the exact shapes [`cadenceToCron`](#cadencetocron) emits (plus the
calendar shorthands `@hourly`/`@daily`/`@weekly`/`@monthly`) map to a
structured preset. Everything else — ranges, steps, names, `@yearly`
— is a perfectly valid schedule that this UI simply cannot decompose,
so it round-trips as `custom` with the raw string intact.

```tsx
function cronToCadence(cron: string): CadencePreset
```


### deriveRoutineState

Derive a routine's display state from its spec and status.

### describeCadence

Human-readable summary of a cadence, e.g.
`"Every day at 09:00 (Asia/Kolkata)"`.

This is a description of the chosen preset, not a computed fire-time
forecast — the platform's next fire time is published by the server
as `status.next_fire_at` after apply.

```tsx
function describeCadence(preset: CadencePreset, timeZone?: string): string
```


### FIRE_TEXT_MAX_LEN

The contract's bound on a fire's note: io.proto pins
`FireRoutineInput.text` to 65,536 characters. The field stops there; the
server's bound stays the rule and answers in its own words.


### formatNextFire

Compact future-instant formatter for a routine's next fire time:
`now`, `in 5m`, `in 3h`, `in 6d`, then a short date once "days from
now" stops being how people think about it.

The routine-local sibling of the activity module's past-only
`formatRelativeTime` (same compact units, same date tail) — kept
separate because that util's contract is deliberately past-only.
A fire time slightly in the past (a tick mid-flight, clock skew)
renders as `now` rather than a nonsense negative countdown.

`now` is injected, never read from the live clock — required for
deterministic tests and Scenar fixtures.

```tsx
function formatNextFire(date: Date, now: Date): string
```

### validateCron

Validate a cron expression against the platform's lexical grammar.

Returns the user-facing error message (identical wording to the
server's) or `null` when the expression is acceptable. Purely
lexical — it does not evaluate calendar semantics.

```tsx
function validateCron(cron: string): string | null
```


### validateTimeZone

Validate an IANA time zone name using the runtime's own tz database
(`Intl`), mirroring the server's check against the platform tz
database. Returns the user-facing error message or `null`.

`"Local"` is rejected explicitly for the same reason the server
rejects it: it is host-dependent, not a zone.

```tsx
function validateTimeZone(timeZone: string): string | null
```
