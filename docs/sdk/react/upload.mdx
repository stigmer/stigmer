### FileChipList

Renders a horizontal list of upload chips: images as
preview-only thumbnail tiles (the image IS the chip — no filename

the tooltip and the accessible label; clicking an image tile opens

### assessVisionPreflight

Predict which attached images the runner will degrade this turn.

Pure and deterministic — safe to call in render (memoized by callers).
Non-image files never warn. The byte assessment replicates the
runner's sequential admission: an image over the per-image cap is
degraded WITHOUT consuming budget; remaining images are admitted in
order until the count or total-byte budget is exhausted.

### extractClipboardFiles

Extracts files from a paste event, giving clipboard images that carry the
browser's generic `image.png` name a unique, human-readable one
(`pasted-image-<HHMMSS>-<n>.<ext>`).

A message's files mount at `.stigmer/uploads/{filename}`, where the server
renames a clash (`image-2.png`); a name that says what the file is serves
the person reading the conversation's Files and the agent reading its
uploads better. Files with real names (pasted from a file manager) are
returned unchanged.

Returns an empty array for a text-only paste — callers use that to let
the default text insertion proceed untouched.

Must be called synchronously from the paste event handler. Call
`event.preventDefault()` in the same tick when the result is non-empty;
the returned `File` objects remain valid afterwards.

```tsx
function extractClipboardFiles(event: ClipboardFilesSource): File[]
```

```tsx
function handlePaste(e: React.ClipboardEvent<HTMLTextAreaElement>) {
  const files = extractClipboardFiles(e);
  if (files.length === 0) return; // plain text paste — leave it alone
  e.preventDefault();
  uploads.addFiles(files);
}
```

### FileUploadPhase

Lifecycle phase of one file managed by [`useFileUploads`](#usefileuploads).

- `preparing`: client-side image preparation is running (see
  `AddFilesOptions.prepareImages`); the entry exists so the UI can
  show the file from the instant it was added, but no bytes have been
  sent yet. Only entries added with `prepareImages` visit this phase.
- `uploading`: the bytes are on their way to the server.
- `ready`: the File exists; `fileId` names it.
- `error`: the upload failed; `error` says why.


### fitToVisionResolution

The largest size that fits both vision limits while preserving aspect
ratio. Never upscales: dimensions already within the limits come back
unchanged. Mirrors Anthropic's published "max API fit" computation.

Degenerate inputs (zero, negative, or non-finite dimensions) come back
unchanged — the caller's decode has already failed or will fail, and this
module never turns a bad input into a crash.

```tsx

```


### MAX_FILE_BYTES

Maximum size of a file given with a message, in bytes (500 MB).

The server's default File size limit: a file this large is streamed to
an upload URL, so the request cap does not bind it. A file over it is
refused before any bytes move. An operator may set a lower limit, which
the server enforces when the upload URL is requested.


### MAX_MESSAGE_FILES

The most Files one message carries: the server refuses a run naming more
in `file_ids`. [`useFileUploads`](#usefileuploads) holds no more entries than this.


### MAX_VISION_LONG_EDGE_PX

Maximum long-edge length, mirroring Anthropic's standard-tier limit.


### MAX_VISION_PIXELS

Maximum total pixels, mirroring Anthropic's standard-tier visual-token
ceiling (1568 tokens ≈ 1.15 megapixels). For nearly all photos and
screenshots this — not the edge limit — is the binding constraint: a
1920×1080 screenshot fits the edge limit but still resizes to 1456×819.


### prepareImageForVision

Bounds a pasted image to the resolution vision providers actually
process, re-encoding to a format every harness can display inline.

- PNG and JPEG within the resolution limits pass through byte-identical
  (also guards edit-and-resubmit flows against generation loss).
- GIF within the limits passes through untouched — re-encoding would
  silently flatten an animation the agent also receives as a file.
- Oversized images resize to [`fitToVisionResolution`](#fittovisionresolution); other formats
  (WebP, TIFF, BMP…) re-encode even when small, for harness visibility.
- Output format: JPEG stays JPEG; everything else prefers PNG (crisp UI
  text), switching to JPEG only for photographic content — detected by
  PNG byte density, where PNG can exceed the runner's inline byte cap.
- A same-format resize that grew the file returns the original: the
  runner caps bytes, not pixels, so the smaller original is the better
  payload. A cross-format re-encode is kept even when larger, the price
  of being visible to every model.

Never throws; every failure path returns the original file (see module
doc). Non-image files are returned unchanged.

```tsx
function prepareImageForVision(file: File): Promise<File>
```

### uniquifyFilename

Returns `name` unchanged when it is not in `taken`, otherwise the first
free `stem-2.ext`, `stem-3.ext`, … variant.

A conversation's Files are mounted at `.stigmer/uploads/{filename}`, so
duplicate names contend for one path. The server resolves that with this
same rename when it lists a File in the conversation
(backend/services/stigmer-server/src/domain/file/session-resources.ts,
uniquifyMountPath — the packages share no dependency). Renaming
client-side as well keeps the chip, the uploaded File and the mounted
file agreeing on one visible name — strictly better UX than a rename the
user only discovers in the transcript.

```tsx
function uniquifyFilename(name: string, taken: ReadonlySet<string>): string
```

### visionPreflightMessage

One-line human copy for a [`VisionPreflight`](#visionpreflight) — the client-side twin
of the runner's `visionDisclosureLines`, worded for BEFORE the turn
("will arrive as a file") instead of after ("was not viewable").

Returns `null` when there is nothing to warn about. Copy rules:
- a blind model leads with the model, never the files — no smaller
  resend can help, so file-size advice would be dishonest;
- `too_large` names the files (up to two, then a count) and the actual
  cap, so the fix — export smaller — is self-evident;
- `budget_exhausted` explains the per-turn budget, the only fix being
  fewer images this turn.

```tsx
function visionPreflightMessage(preflight: VisionPreflight, options?: VisionPreflightMessageOptions): string | null
```
