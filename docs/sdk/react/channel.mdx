### useCanCreateChannel

Mirrors the server's Channel create bar so create affordances never
appear to a user whose create would be refused. One bar for every
type: the Channels tab asks it for a chat link, Slack and WhatsApp
alike (through [`useAddChannelOptions`](#useaddchanneloptions)).

A channel lives in its agent's organization (to share another
organization's agent, install the plugin that carries it and share the
installed copy), and creating one asks two questions of that
organization, both of which the create handler enforces:

- `can_manage_audience` on the agent — a channel puts the agent in front
  of a wider audience, so it is the owner's decision; an editor, who may
  change the definition, may not publish it.
- `can_create_channel` on the organization (admin by default) — a
  channel spends the organization's own provider keys with people
  outside it, so it is an admin-level decision. The org check uses the
  agent's `metadata.org` as the resource id, which is the
  organization's id.

A viewer from another organization looking at a platform-visible agent
needs no special case: both checks answer false for them, so the
affordance hides on permissions alone.

On the open-source edition the answer follows the server's posture. A
server without sign-in has the permissive single-team authorizer and
answers allowed. A server with sign-in enforces the
same organization roles as the cloud, so `can_create_channel` is
the admin's and a member sees no create affordance.

Pass `null` for `agent` while it loads — `allowed` stays `false` so
no affordance flashes before the gate can be evaluated.

### useChannelTemplateList

Data hook that lists a channel's message templates as the channel's
provider registry reports them (`listTemplates`) — every field
provider-verbatim, including approval `status`, the provider's
`rejectionReason`, and Stigmer's own `unsupportedReason` (why this
platform version cannot send an otherwise-approved template).

The channel is addressed by `slug` + `org` (not id), because that is
the RPC's key — the provider registry is derived from the channel's
phone number, not stored on any Stigmer resource. Pass an empty
`channelSlug` or `org` to skip fetching (stable no-op).

While any entry is PENDING the hook polls every 60 seconds — the
server's registry-cache TTL, so a faster interval would only re-read
a cached answer. There is deliberately no `refetchInterval` option:
the pending-only conditional poll is the hook's policy, and
`approvedOnly` (a wire field) is the only knob exposed.

Results are never cached across mounts: a template's approval status
can change on the provider's side at any time, and rendering a stale
"APPROVED" is exactly what this surface must not do.

### useChannelToolReadiness

Channel-scoped wrapper over [`useToolCredentialsReadiness`](/docs/sdk/react/vault#usetoolcredentialsreadiness):
checks whether a tool-using agent's credentials will work over a
channel — i.e. whether the channel names vaults
(`ChannelSpec.vaults`) and each one is a shared vault.

Channel runs have no person, so they use only the channel's own vaults
— exactly the share contract, without the audience arm (channels have no
audience concept). So a tool-using agent on a channel naming no vault is
guaranteed to refuse every workspace message that needs a tool.

The check runs only when serving is enabled (a paused channel serves
no traffic), the deployment is cloud (the channel runtime is
cloud-only), and the agent dials MCP servers (its own or its plugins', which read keys).

### ChannelsPanel

### ChannelTemplatesDialog

the one place that shows the provider's rejection copy AND Stigmer's

### channelInstallsAvailable

Whether the connected edition can install a channel into a vendor
(Slack, WhatsApp): the facility is the hosted webhook and delivery
runtime that receives the vendor's events and sends the agent's
replies, and only Stigmer Cloud composes one. Every channel surface
asks this one predicate, so the panel and the connect dialogs never
disagree. Channel configuration (create, edit, the on/off switch,
delete) needs no runtime and works in every edition, chat links
included.

```tsx
function channelInstallsAvailable(mode: DeploymentMode): boolean
```


### ChannelTemplateReadiness

Whether a channel can answer a template-registry read
(`listTemplates`), and if not, which precondition fails first.

- `cloud-only` — the deployment is not cloud; the template registry
  is part of the cloud channel runtime.
- `not-installed` — the provider install has not completed (covers
  both pending and revoked; render the per-provider
  `describeChannel` sentence, which already distinguishes them).
- `channel-off` — the owner's serving switch (`spec.enabled`) is off.
- `not-proactive` — `spec.proactive_messaging_enabled` is not set;
  business-initiated messaging (and with it the template surface)
  is not granted on this channel.
- `ready` — the read can be made.

### templateStatusPhase

Map a provider-verbatim template status onto a [`StatusPhase`](/docs/sdk/react/resource-workbench#statusphase)
for `StatusBadge` coloring.

The wire carries the provider's own vocabulary, never a Stigmer enum
— so the caller renders the verbatim status string as the
badge label and uses this phase only for the color. WhatsApp's
observed set exceeds the documented five (IN_APPEAL, LIMIT_EXCEEDED,
PENDING_DELETION, DELETED occur, and Meta can add more), so unknown
statuses deliberately land on `draft` — a neutral tone that renders
the provider's word without claiming to understand it.

```tsx
function templateStatusPhase(status: string): StatusPhase
```
