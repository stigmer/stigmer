### useCreateRun

### FileReviewDock

decision bar, pinned in the fixed strip above the composer.

observational — they show what changed, badged with the live review state —
but the newest turn's open decision must never scroll out of view. An
in-thread card does exactly that on a long conversation. The turn does not
wait on it: its edits are already applied, Undo puts a file back, and the
next message keeps whatever is still undecided. Docking the bar to
the composer keeps the pending decision visible regardless of scroll
position, matching the shape of Cursor's own review bar. Once decided, the
dock empties and the thread's read-only record (and the rows' Kept/Discarded
badges) carry the history.

on their rows (with `ApprovalPeekBar` as the scroll backstop): an approval is

aggregate over many calls, with no single row that owns it.

needs per-file attention starts expanded (see [`FileReviewCard`](#filereviewcard)), and an
unconstrained list in a fixed strip would swallow the viewport.

### deriveRunFileChanges

Collapses the file changes captured across `executions` into one *net*
[`DisplayFileChange`](#displayfilechange) per path, ordered for a file list (modified, then
added/renamed, then deleted; alphabetical within each group).

**Source.** Each run's file record ([`displayFileChangeSets`](#displayfilechangesets): the
change sets it captured, `RunStatus.file_changes`), each captured change
projected via [`toDisplayFileChange`](#todisplayfilechange). A run's record already includes
subagent captures, so one pass per run suffices. What was decided about a
file is the session's events, not this list.

**Net-diff (not latest-wins).** A change is a *delta*: an agent often
rewrites the same file several times, and showing only the last edit's diff
would misrepresent what changed. So changes to the same path are reduced to
a single net change: `before` from the first change, `after` from the last.
Every capture is a complete file snapshot, so `first.before -> last.after`
is exactly the net change. A group with one change (the common case) is
passed through untouched.

**Ordering is a correctness input.** `executions` MUST be chronological:
the net collapse anchors on each path's first and last change, so two
runs touching the same path (a session's follow-up turns) produce a
wrong net diff if visited out of order.

Counts for captures stay derivable by the presentation layer, matching
the contract the SDK `tool-view` established.

```tsx
function deriveRunFileChanges(executions: readonly Run[]): readonly DisplayFileChange[]
```

### FileChangeProgressBar

The live "N files changed so far" strip for a turn that is still running.

WHY IT EXISTS. The transcript streams per-edit tool rows, but a change made by
a shell command (a `sed`, a build step) has no tool row, and there is no
running net-of-many-edits rollup until the turn ends. This bar fills that gap:

the dock shows once AWAITING_REVIEW), so the bar hands off cleanly to the dock.

turn-boundary candidate ([`FileReviewDock`](#filereviewdock) / the stamped transcript rows).

`FileLineStats` renders nothing for it.

A11Y. Only the summary count is an `aria-live` region — the per-file list is
not — so a screen reader hears "3 files changing" as the count moves, not a
per-file barrage on every ~2s refresh.

### FileReviewability

How completely a single file change can be reviewed before it is decided —
the classification that decides whether a file can be kept.

- `{ kind: "reviewable" }` — the full before/after diff is available.
- `{ kind: "binary" }` — a binary file changed: no text diff, but its exact
  bytes are captured, so it can be kept consciously ("Keep anyway").
- `{ kind: "unavailable"; reason }` — the diff is not available to review
  at all; the file can only be discarded.

Mirrors the server, which refuses to keep a set that is not complete
unless every incompleteness is binary and acknowledged.

### FileReviewCard

Renders a turn's file changes (`FileReviewSet`) as a **compact
decision bar**: one line carrying the set summary and the whole-set
decision controls, with the
per-file detail behind an expander. What the expander holds depends on
`FileReviewCardProps.showDiffs`: the diff-rich body (default — for
surfaces where this card is the only review surface) or a compact file list
(the session thread, whose stamped edit rows already show every diff in
place). A set that needs per-file attention (binary acknowledgment, blocked
files, mid-review) starts expanded.

File edits are reviewed as a captured workspace delta, not tool calls, so this
is a dedicated decision surface distinct from the message transcript and the
tool-approval [`ApprovalCard`](#approvalcard). The reviewer can decide each file
individually (Keep / Discard, a `"file"` decision) or act on the whole set
at once (Keep / Discard all, a `"change_set"` decision). Kept bytes stay;
discarded ones are put back, verified against the digest the person saw.

The set stays offered until every file has a verdict, so a partially
decided set stays actionable. A per-file verdict is changeable while the
set is still open: clicking the other option records a new decision (the
last one wins).

A `binary-only` set (binary files are the only blocker) can be kept in one
action: the bulk button reads "Keep all" and carries the acknowledgment.
A `blocked` set (something unavailable to review) cannot be approved
as a whole — the Approve button is disabled with an explanation, and the
per-file path is the escape: keep the reviewable files and discard the rest.

Each non-reviewable file is labeled honestly by [`fileReviewability`](#filereviewability): a
`binary` change has no text diff to review; an `unavailable` change is one
whose diff isn't available at all (a secret path whose bytes were never
captured, or an incomplete diff). Both are discard-only, and their Keep
affordance is disabled with the reason associated via `aria-describedby`.
Files captured outside normal git tracking (gitignored / non-git CAS) carry
a small provenance badge, read from the capture, so the reviewer knows the
change is not part of the repo's tracked history.

Wrapped in `React.memo` — the session fold keeps an unchanged set's
reference, so review cards skip re-renders during unrelated stream updates.

```tsx
const { reviewFileChanges, submittingDecisionKeys } = useReviewFileChanges();
<FileReviewCard
  fileReviewSet={set}
  onSubmit={(action, opts) => reviewFileChanges(sessionId, set.changeSetId, action, opts)}

```

### resolvePathAction

Resolves a tool-call file path to a user action.

Resolution strategy (mirrors the CLI's `buildHyperlinkedPath`):

1. **Platform paths** (`.stigmer/` prefix) → copy raw path.
2. **Workspace paths** → match against the conversation's repositories
   and folders (its Files live under `.stigmer/uploads/`, a platform path):
   - Single entry: treat path as relative to that entry.
   - Multiple entries: scan path segments for an entry name match
     (handles org-prefixed paths like `plantonhq/agent-fleet/...`).
     Unmatched paths fall back to the first entry.
3. **Git source** → construct GitHub blob URL.
4. **Local source** → join with absolute local path for copy.
5. **Fallback** → copy the raw path.

```tsx
function resolvePathAction(path: string, resources: readonly SessionResource[]): ResolvedPathAction
```

### ToolCallGroup

Renders one AI turn's tool activity as a **persistent-row timeline** rather
than a collapsible "Ran N tools" box. Each call stays visible after it
settles, so completed work is never hidden behind a pill — the thread reads
like a virtual human at work.

The turn is segmented by `segmentToolCalls`:
- high-signal calls (edits, shell, MCP, subagents, …) render as persistent
  [`ToolCallItem`](#toolcallitem) rows; a content-bearing call shows its body inline
  (no card chevron), bounded by a single in-place reveal;

  fold into one collapsible `ToolRunGroup` chip — the *only* collapse,

### ToolCallItem

Renders a single tool call as a row in the tool call group.

Four rendering modes, set by one rule — **does the body carry content the
one-line row cannot, and does it stay content once the call settles?**

- **Non-expandable** (completed/skipped Read): a static `<div>` row with a
  clickable [`FilePathLink`](#filepathlink). The path IS the complete information.
- **Preview** (content-bearing: edit / write / fetch / web-search /
  unknown / mcp): a plain (non-button) header above an **always-visible**
  [`ToolCallDetail`](#toolcalldetail) body — Cursor-style "previews aren't collapsible".
  There is no header chevron; each content block self-bounds with its own
  single in-place reveal (`RevealToggle`), so a long diff or output
  never floods the thread. The body is suppressed only for an `empty` result,
  which stays a clean one-line row.
- **Tail** (shell): live like preview — the full terminal session streams in
  view while the command runs or awaits its gate — but a *successful* settle
  collapses the row to a [`TerminalTail`](#terminaltail) teaser (the `$ command` line
  plus a dimmed tail of the last output lines) behind the header chevron.
  A settled failure stays open: error output is content, not context. A
  result that isn't a terminal session (e.g. an offloaded `outputRef`)
  falls back to the preview layout — never hide evidence we cannot condense.
- **Summary / subagent** (read / list / search / delete / think, and
  subagent delegations): a chevron-gated `div[role=button]` header that
  discloses a body hidden by default — [`ToolCallDetail`](#toolcalldetail), a
  [`SubagentSection`](#subagentsection), or, when gated, an inline [`ApprovalCardBody`](#approvalcardbody).
  `useAutoDisclosure` force-opens it while *running* or *awaiting
  approval*, then settles it closed; a manual click always wins thereafter.

The two disclosure axes — the card-level chevron and a block's
content-overflow reveal — never govern the same body, which is what removes
the old "expand, then Show more" double control.

Orthogonal to the layout modes is the **chrome tier** (the density axis,
stigmer#274): metadata-only categories (read / list / search / think)
render as quiet unboxed lines — no card frame — while content-bearing
categories keep their cards. A quiet row escalates to a card while gated
or failed; its disclosed body renders under a light left rail instead of a
border. See `ToolChrome`.

A call that started a command in the background (`toolUse.background`)
is the command's row: a "Background" chip and the command's state beside
the call's own, the running look (shimmer, spinner, forced open) for as
long as the command runs though the call itself returned, its output in
the body, and Stop while a stop handler is wired
([`BackgroundCommandContext`](#backgroundcommandcontext)).

Shows category-aware labels (e.g., "Shell", "Read", "Edit") with
the primary argument as a subtitle, a category-specific icon, and
an inline approval decision badge when applicable. A shell row whose
call carries a model-authored intent phrase is titled with that phrase
instead — the command becomes the subtitle (stigmer#276).

Wrapped in `React.memo` — the session fold keeps an unchanged tool use's
reference, so a settled row skips re-renders while sibling tools stream.

```tsx
<ToolCallItem toolUse={toolUse} />
```

### ToolDisclosure

How much of a settled tool call to reveal inline by default in the thread.

- `"summary"` — a compact one-line row. Used when the label + primary arg +
  result summary already tell the story (`Read foo.ts`, `Edit bar.ts +40 -0`,
  `Search … 2 matches`). The full detail is one click away.
- `"preview"` — the row renders its result body **always** (no card chevron),
  because the one-liner cannot convey what happened so the content itself IS
  the information (an MCP result such as a screenshot, a fetched page, a
  web-search answer, or an unrecognised tool's output). The body's own
  in-place reveal expands it beyond the height budget.
- `"tail"` — live like `"preview"`, settled like a teaser: while the tool
  runs (or awaits approval) the full body streams in view; once it settles
  successfully the row collapses to a dimmed tail of its last output lines —
  at-a-glance evidence that it ran and what it printed last — expanding on
  demand via the header chevron. A settled *failure* stays open: error
  output is content, not context. Shell is the canonical tail category — a
  working session's compile/validate loops would otherwise dominate the
  transcript at full contrast (Cursor's chat is the reference UX).

This is the *disclosure* axis (how much of a result to show); it is
orthogonal to `isRunGroupableCategory` (whether consecutive same-kind
calls fold into one chip). A category can be result-rich but never folded
(`shell`), or foldable but never previewed (`read`).

### writeBackDisplayName
