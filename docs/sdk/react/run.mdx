### useArtifactDownloadUrl

Presigned URLs expire, so the URL is minted at view time from the stable

### useCreateRun

Behavior hook that wraps `run.create()` and `run.sendMessage()` with
loading/error state.

Maps 1:1 to the Run aggregate — a single run of an agent.
Two session strategies are supported, mirroring the RPC contract:

### deriveRunFileChanges

Collapses the file changes captured across `executions` into one *net*
[`DisplayFileChange`](#displayfilechange) per path, ordered for a file list (modified, then
added/renamed, then deleted; alphabetical within each group).

**Source.** Each run's file record ([`displayFileChangeSets`](#displayfilechangesets): the
change sets it captured, `RunStatus.file_changes`), each captured change
projected via [`toDisplayFileChange`](#todisplayfilechange). A run's record already includes
subagent captures, so one pass per run suffices. What was decided about a
file is the session's events, not this list.

**Net-diff (not latest-wins).** A change is a *delta*: an agent often
rewrites the same file several times, and showing only the last edit's diff
would misrepresent what changed. So changes to the same path are reduced to
a single net change: `before` from the first change, `after` from the last.
Every capture is a complete file snapshot, so `first.before -> last.after`
is exactly the net change. A group with one change (the common case) is
passed through untouched.

**Ordering is a correctness input.** `executions` MUST be chronological:
the net collapse anchors on each path's first and last change, so two
runs touching the same path (a session's follow-up turns) produce a
wrong net diff if visited out of order.

Counts for captures stay derivable by the presentation layer, matching
the contract the SDK `tool-view` established.

```tsx
import type { Run } from "@stigmer/apis/ai/stigmer/agentic/run/v1/api_pb";
// ---cut---
function deriveRunFileChanges(executions: readonly Run[]): readonly DisplayFileChange[]
```

### FileChangeProgressBar

The live "Changing 2 files" strip for a turn that is still running.

WHY IT EXISTS. The transcript streams per-edit tool rows, but a change made by
a shell command (a `sed`, a build step) has no tool row, and there is no
running net-of-many-edits rollup until the turn ends. This strip fills that
gap above the composer: the count and line counts so far, opening to each
file in the same words the finished turn's Changed group uses (New,
Deleted, nothing for an edit), so the files read as one thing moving from
changing to changed.

NEVER A DECISION SURFACE. Progress is non-authoritative and carries no file
bodies. A secret-like path is surfaced by name with its counts withheld
(zeroed), so `FileLineStats` renders nothing for it.

A11Y. Only the summary count is an `aria-live` region; the per-file list is
not, so a screen reader hears the count move, not a per-file barrage on
every refresh.

Purely presentational (headless-first): the data lives in
`useSessionConversation().fileChangeProgress`. `SessionViewer` mounts it

### FileReviewability

How completely a single file change can be reviewed before it is decided —
the classification that decides whether a file can be kept.

- `{ kind: "reviewable" }` — the full before/after diff is available.
- `{ kind: "binary" }` — a binary file changed: no text diff, but its exact

  at all; the file can only be discarded.

Mirrors the server, which refuses to keep a set that is not complete
unless every incompleteness is binary and acknowledged.

### resolvePathAction

Resolves a tool-call file path to a user action.

Resolution strategy (mirrors the CLI's `buildHyperlinkedPath`):

1. **Platform paths** (`.stigmer/` prefix) → copy raw path.
2. **Workspace paths** → match against the conversation's repositories
   and folders (its Files live under `.stigmer/uploads/`, a platform path):
   - Single entry: treat path as relative to that entry.
   - Multiple entries: scan path segments for an entry name match

4. **Local source** → join with absolute local path for copy.
5. **Fallback** → copy the raw path.

### ToolCallItem

Renders a single tool call as one step: a line in plain words, closed
until clicked, opening in place to what the step did.

- **The line** says what the call did, in the tense it stands in, from
  `stepPhrase` (`@stigmer/client`): "Editing invoice.ts" while it runs,
  "Edited invoice.ts" once it returned, "Couldn't edit invoice.ts" when it
  failed. A command reads as the agent's own description when it wrote one,
  with the command beside it; a connected app's tool reads as its own name
  with the app beside it. A host's `registerToolPresenter` label wins
  over all of it. Beside the words: how much changed (`+2 −2`), the
  matches or items found, a non-zero exit, and the folder of the file.
- **Closed by default.** A settled step opens on a click to its body: the
  diff, the lines read or written, the matches, the command's output, the
  MCP call's fields and result, a subagent's own steps. A step with
  nothing to show has no chevron and opens to nothing, never to an empty
  box.
- **Open while it matters.** `useAutoDisclosure` opens a step while
  it runs (a command streams its output as it prints), while it waits for
  a person (its decision inline), and, for a command, once it failed; a
  manual click always wins thereafter.
- **Preview** (a memory proposal, or a kind a host asks to preview): the
  body is always in view under a plain line, because it is a decision
  surface.

Inside a list of steps (`bordered={false}`) a step is a divider row; on
its own it is a card, or a quiet unboxed line for the metadata-only kinds
(read, list, search, think) unless it waits or failed. A pending gate
carries a restrained left accent.

A call that started a helper (`toolUse.thread`) draws the helper's header:
its subject as the line, its agent's name as a tag beside it ("Helper"
when it has none), and a pill only once the helper failed or stopped; the
body is the helper's work ([`SubagentSection`](#subagentsection)'s flat form).

A call that started a command in the background (`toolUse.background`)
is the command's row: one line saying how the command stands ("Running in
the background · 12s", or how it ended), the running look (shimmer,
spinner, open) for as long as the command runs though the call itself
returned, its output in the body, and a quiet Stop while a stop handler is
wired ([`BackgroundCommandContext`](#backgroundcommandcontext)).

Wrapped in `React.memo` — the session fold keeps an unchanged tool use's
reference, so a settled row skips re-renders while sibling tools stream.

```tsx
import type { ToolUse } from "@stigmer/client";

function Step({ toolUse }: { toolUse: ToolUse }) {
  return <ToolCallItem toolUse={toolUse} />;
}
```

### ToolDisclosure

How much of a settled tool call to reveal inline by default in the thread.

- `"summary"` — a closed one-line step that opens to its body on a click.
  The line says what the step did (`Read foo.ts`, `Edited bar.ts +40 −0`,
  `Searched for … 2 matches`); the diff, the matches or the output are one
  click away. Every category but a memory proposal and shell.
- `"preview"` — the row renders its result body **always** (no card
  chevron), because the body is a decision surface: a memory proposal's
  fact and its Confirm/Reject actions. A host may ask for it per kind
  ([`registerToolPresenter`](#registertoolpresenter)).
- `"tail"` — a summary step that stays open while it shows a failure: the
  full body streams in view while the tool runs (or awaits approval), it
  closes once it settles successfully, and a settled failure (an error or
  a non-zero exit) stays open, because error output is the content the
  person needs next. Shell is the tail category.

This is the *disclosure* axis (how much of a result to show); it is
orthogonal to `isRunGroupableCategory` (whether consecutive same-kind
calls fold into one chip). A category can be result-rich but never folded
(`shell`), or foldable but never previewed (`read`).
