This is the "Execution" layer in the Template→Instance→Execution pattern. WorkflowExecutionSpec is ephemeral - it defines the inputs for a single runtime invocation.

Following Stigmer proto standards: - Spec contains ONLY user inputs (what the user controls) - Status contains execution state (what the system manages)

The spec is immutable after creation. To retry with different inputs, create a new WorkflowExecution with updated spec values.

Spec vs Status Separation: ✅ Spec: workflow_instance_id, workflow_id, trigger_message, trigger_metadata, runtime_env ✅ Status: phase, tasks, output, error, timestamps

Instance Resolution (matches AgentExecution pattern): - Either workflow_instance_id OR workflow_id must be provided - If workflow_instance_id: Use the specified instance directly - If workflow_id: Resolve to workflow's default instance (auto-create if missing) - Handler enforces: at least one must be provided

Example Use Case 1 (Direct Instance Reference): spec \{ workflow_instance_id: "wfi-customer-onboarding-prod" trigger_message: "New signup: john.doe@example.com" trigger_metadata: \{ "source": "web_signup_form" "ip_address": "203.0.113.42" "referrer": "https://marketing.example.com/campaign" "timestamp": "2025-01-11T14:30:22Z" \} runtime_env: \{ "CUSTOMER_EMAIL": \{ value: "john.doe@example.com" \} "CUSTOMER_PLAN": \{ value: "pro" \} "STRIPE_API_KEY": \{ secret_ref: "sec-stripe-prod" \} \} \}

Example Use Case 2 (Default Instance Resolution): spec \{ workflow_id: "wf-customer-onboarding"  // System resolves to default instance trigger_message: "New signup: john.doe@example.com" runtime_env: \{ "CUSTOMER_EMAIL": \{ value: "john.doe@example.com" \} \} \}

### ApprovalAction

ApprovalAction represents the user's decision on an approval request.

| Value | Description |
|-------|-------------|
| `APPROVAL_ACTION_APPROVE` | Execute the tool normally. |
| `APPROVAL_ACTION_SKIP` | Skip tool execution, continue without it. |
| `APPROVAL_ACTION_REJECT` | Reject tool execution, fail the entire execution. |

### ExecutionPhase

ExecutionPhase defines the lifecycle phase of a workflow execution.

| Value | Description |
|-------|-------------|
| `EXECUTION_PENDING` | Execution created, waiting to start. |
| `EXECUTION_IN_PROGRESS` | Execution is actively running tasks. |
| `EXECUTION_COMPLETED` | Execution completed successfully. |
| `EXECUTION_FAILED` | Execution failed with an error. |
| `EXECUTION_CANCELLED` | Execution was cancelled by user or system. |
| `EXECUTION_TERMINATED` | Execution was force-stopped immediately. |
| `EXECUTION_PAUSED` | Execution was paused by user and can be resumed. |

### WorkflowTaskType

WorkflowTaskType defines the type of workflow task.

| Value | Description |
|-------|-------------|
| `WORKFLOW_TASK_AGENT_INVOCATION` | Invoke an AI agent with a prompt. |
| `WORKFLOW_TASK_APPROVAL` | Wait for human approval before proceeding. |
| `WORKFLOW_TASK_API_CALL` | Make an HTTP or gRPC API call to an external service. |
| `WORKFLOW_TASK_CONDITIONAL` | Evaluate a condition and branch to different paths. |
| `WORKFLOW_TASK_PARALLEL` | Execute multiple sub-tasks concurrently. |
| `WORKFLOW_TASK_TRANSFORM` | Transform data between tasks. |
| `WORKFLOW_TASK_CUSTOM` | Execute custom task logic defined by plugins. |

### WorkflowTaskStatus

WorkflowTaskStatus defines the execution status of a workflow task.

| Value | Description |
|-------|-------------|
| `WORKFLOW_TASK_PENDING` | Task is waiting to execute. |
| `WORKFLOW_TASK_IN_PROGRESS` | Task is currently executing. |
| `WORKFLOW_TASK_COMPLETED` | Task finished successfully. |
| `WORKFLOW_TASK_FAILED` | Task failed during execution. |
| `WORKFLOW_TASK_SKIPPED` | Task was skipped due to conditional logic. |
| `WORKFLOW_TASK_WAITING_APPROVAL` | Task is waiting for approval from child agent (HITL Phase 1). |
