Every Stigmer component reads its colors, radii, fonts, shadows, and motion
from `--stgm-*` CSS custom properties — nothing visual is hardcoded. To make
the components wear your design language, you override tokens; the component
markup never changes.

## Try a look

Pick a preset, light or dark, and a corner radius, and watch the chat take it
on. The code under the chat is what gives your product that look.

## How the scope works

`StigmerProvider` wraps your subtree in a scoping element:

```html
<div class="stgm stgm-theme-corporate" data-stgm-color-mode="dark">
  <!-- your app + Stigmer components -->
</div>
```

Three mechanisms keep Stigmer's styles and your host application's styles
from colliding — in either direction:

- **The `stg:` utility prefix.** Every utility class in the compiled
  stylesheet is namespaced (`.stg\:flex`, never `.flex`), and its Tailwind
  theme variables are namespaced too (`--stg-*`). The stylesheet shares no
  class names and no variable names with your own Tailwind build, so loading
  it cannot change how your classes render — and your build cannot change how
  Stigmer components render. This holds everywhere, including host elements
  inside the provider subtree.
- **The `.stgm` scope.** Styles that cannot be namespaced (the element
  resets) are scoped to the `.stgm` containers, and the utilities only apply
  inside them.
- **The `--stgm-*` namespace** keeps token names from clashing with your own
  custom properties.

### How Stigmer's styles meet yours

Your page's own CSS is usually unlayered (a `create-next-app` stylesheet's
`* { padding: 0 }`, Tailwind 3's preflight, a template's `button { … }`), and
unlayered CSS beats any rule inside a cascade layer, whatever its selector. So
Stigmer's utilities ship unlayered too, and meet your rules by specificity, as
any stylesheet does. From weakest to strongest:

1. **Stigmer's defaults** (the box and border defaults, the button and field
   reset) sit in `@layer base`, where Tailwind keeps its own preflight. Every
   rule and class of yours beats them.
2. **Your bare element rules** (`button { … }`, `* { … }`) do not reach the
   buttons and fields Stigmer draws: one rule hands those back to Stigmer's
   defaults. Your own buttons and fields inside the provider keep them.
3. **Stigmer's utilities** (`.stg\:p-2`) beat your bare element rules.
4. **Anything you aim at Stigmer on purpose** wins: a class you pass through
   `className`, or a rule that names a class or the scope (`.stgm .x`).

Text alignment is inherited, so Stigmer's outermost elements start their text
at the start edge, even inside a page that centers everything (the app
`create-vite` makes does).

The design tokens (`--stgm-*`) stay layered: setting one on `.stgm` from your
CSS is how you theme Stigmer.

Portaled surfaces (dropdowns, dialogs, tooltips) render into a container on
`document.body` that carries the same theme class and color-mode attribute,
so they stay themed even though they render outside your DOM subtree.

The two containers are distinguishable through stable, documented marker
attributes: the in-tree scope carries `data-stgm-root`, the portal
container carries `data-stgm-portal`. You can rely on both in host CSS.

One exception: a popup opened inside an SDK dialog renders inside that
dialog, because a modal dialog sits in the browser's top layer and would
otherwise cover it. Such a popup inherits its theme from the in-tree scope
and is not under `[data-stgm-portal]`.

## Sizing and fixed-height embedding

The in-tree scope ships with **no layout styling** — it sizes to its
content, so mounting the provider in a normally-scrolling page needs
nothing.

Fixed-height embeddings (a docked conversation pane, a split layout, an
IDE-style panel) are different: height-filling components like
`SessionViewer` root at `height: 100%` and need an unbroken
percentage-height chain from your definite-height region down to them.
The scope element sits in that chain, so opt it in from your CSS via the
stable `data-stgm-root` selector:

```css
.stgm[data-stgm-root] {
  height: 100%;
  min-height: 0;
}
```

Then give the provider a definite-height ancestor and the conversation
fills the pane, with the transcript scrolling internally:

```tsx
declare const sessionId: string;
declare const org: string;
// ---cut---
<div style={{ height: 480, overflow: "hidden" }}>
  <StigmerProvider client={client} preset="monochrome" colorMode="dark">
    <SessionViewer sessionId={sessionId} org={org} audience="endUser" />
  </StigmerProvider>
</div>
```

`min-height: 0` matters when the scope is a flex or grid child: without
it the browser refuses to shrink the scope below its content, and
internal scrolling never engages.

Two things to know:

- **This is opt-in by design, not an SDK default.** `height: 100%` is
  not benign in arbitrary layouts — under a flex-item parent (a `flex-1`
  content column, for instance) the browser resolves percentages against
  the flexed size and the scope balloons to it, even in a content-sized
  page. Only you know your layout; scope the rule to the embeddings that
  need it.
- **The provider's `className` prop is the wrong tool for layout.** It is
  a *theming* channel, mirrored onto the portal container on
  `document.body` so token overrides reach portaled surfaces — layout
  styles passed there would also size that off-tree element. Target
  `.stgm[data-stgm-root]` for the in-tree container alone.

## Set the color mode

Pass `colorMode` to `StigmerProvider`:

```tsx
declare function YourApp(): null;
// ---cut---
<StigmerProvider client={client} colorMode="dark">
  <YourApp />
</StigmerProvider>
```

- `"light"` (default) and `"dark"` set the mode explicitly.
- `"system"` follows the OS preference and updates live.

The resolved mode is applied as `data-stgm-color-mode` on the scope, and all
dark token values key off that attribute — no ancestor classes required. If
your app already has a theme state (next-themes, MUI, your own context),
pass its current value straight through:

```tsx
declare function YourApp(): null;
declare function useTheme(): { resolvedTheme?: string };
// ---cut---
const { resolvedTheme } = useTheme(); // next-themes
<StigmerProvider client={client} colorMode={resolvedTheme === "dark" ? "dark" : "light"}>
  <YourApp />
</StigmerProvider>
```

## Start from a preset

Presets are complete design languages — radius, palette, surfaces, sidebar
treatment and, for three of them, a font — shipped as CSS classes. Import the
CSS once and select the preset on the provider:

```tsx
declare function YourApp(): null;
// ---cut---
import "@stigmer/design-tokens/tokens.css";
import "@stigmer/design-tokens/presets/corporate.css";

<StigmerProvider client={client} preset="corporate" colorMode="system">
  <YourApp />
</StigmerProvider>
```

Corporate, Friendly and Fintech name a font (Inter, Nunito and IBM Plex Sans)
and put every piece of text inside the provider in it, your own content and
portaled surfaces included. The preset names the font; your page loads it,
with an `@font-face` rule or a font loader. If the font isn't loaded, that
text falls back to the system font, not to your page's. Default, Startup and
Monochrome name no font, so text inside the provider keeps your page's.

See [Presets](/docs/sdk/theme/presets) for the six built-in design languages
and every token each one overrides.

## Override tokens directly

For a custom brand, define a theme class that overrides the tokens you care
about and pass it via `className`. Anything you do not override falls
through to the [defaults](/docs/sdk/theme/tokens).

```css
.acme-theme {
  --stgm-radius: 0.375rem;
  --stgm-primary: oklch(0.55 0.2 260);
  --stgm-primary-foreground: oklch(0.985 0 0);
  --stgm-ring: oklch(0.55 0.15 260);
}

.acme-theme[data-stgm-color-mode="dark"],
[data-stgm-color-mode="dark"] .acme-theme {
  --stgm-primary: oklch(0.72 0.18 260);
  --stgm-primary-foreground: oklch(0.145 0 0);
}
```

```tsx
declare function YourApp(): null;
// ---cut---
<StigmerProvider client={client} className="acme-theme" colorMode="dark">
  <YourApp />
</StigmerProvider>
```

Two rules keep custom themes correct:

- **Always pair light and dark.** A token defined only in your light block
  outranks Stigmer's default dark value in the cascade, so the light value
  would leak into dark mode. If you override a token, give it a dark value
  too (the dual selector above handles both attribute placements).
- **Mind contrast.** Stigmer's defaults are contrast-audited in CI (WCAG 2.1
  AA for every declared text pairing). When you replace a fill, replace its
  `-foreground` partner so the pair stays readable — dark-mode fills are
  usually lighter, which is why their foregrounds flip to near-black. The
  dark status pill fills (`--stgm-status-*-subtle`) are translucent tints of
  their status colour, so they read on your page, card and dialog surfaces
  without an override. If you replace one, keep it translucent.

### Change the font

Set `--stgm-font-sans` and declare `font-family` from it on the same class:

```css
.acme-theme {
  --stgm-font-sans: "Acme Sans", system-ui, sans-serif;
  font-family: var(--stgm-font-sans);
}
```

Both lines matter. Text takes its font from its parent, and your page works
that font out once, on its root element. The token alone reaches only the few
spots that ask for it by name; the `font-family` line makes every piece of
text inside the provider follow, including portaled surfaces. As with a
preset, your page loads the font.

Without a theme font, text inside the provider already uses your page's font.
To bring the spots that ask for the token by name along too, set
`--stgm-font-sans` to your page's font on `:root`.

## Tailwind hosts

The compiled stylesheet coexists with your own Tailwind build, 3 or 4,
without configuration. Stigmer's semantic color declarations resolve straight through
the `--stgm-*` tokens (a `stg:bg-background` utility paints
`var(--stgm-background)` directly), and Tailwind's own theme variables ship
under the `--stg-*` namespace — so nothing in your `@theme` blocks can
repaint Stigmer components, and nothing Stigmer ships can repaint yours.

Two things remain worth knowing:

- **Overriding component styling via `className` uses *your* utilities.**
  Stigmer components merge your classes with theirs treating the `stg:`
  prefix as transparent for conflict resolution, so a `p-4` you pass
  displaces the component's `stg:p-2` exactly as it would between two of
  your own classes.
- **If your build declares its own `dark` variant** (e.g. next-themes'
  `.dark` class) and your elements render inside Stigmer scopes, declare the
  combined form after your imports so your own utilities also respond to
  `data-stgm-color-mode`:

```css
@custom-variant dark (&:is(.dark *, [data-stgm-color-mode="dark"] *));
```

## The radius scale

Components use a four-step radius scale (`rounded-sm` through `rounded-xl`)
that is *derived* from the single `--stgm-radius` token:

| Step | Value |
|------|-------|
| `sm` | `--stgm-radius` − 4px |
| `md` | `--stgm-radius` − 2px |
| `lg` | `--stgm-radius` |
| `xl` | `--stgm-radius` + 4px |

Override one token and every corner in every component reshapes
proportionally — `0.125rem` gives the sharp Fintech look, `1.25rem` the very
round Friendly look.

## Tool-call output blocks

Every tool-call output the agent produces — the terminal/shell session (the
`$ command` line and its stdout/stderr), code and file blocks, and search
and list results — renders on one shared surface: `--stgm-muted-subtle` with
`--stgm-foreground` text (and `--stgm-destructive` for stderr and non-zero
exit codes). There is no separate "terminal" token, and no block ships a
fixed dark box: they all track the active preset and color mode through the
core tokens, so a themed light surface stays light. Override the core
surface and text tokens and every output block follows — including the
terminal. All of these pairings are covered by the CI contrast audit.

## Beyond tokens: component slots

When your design system needs different *structure* — not just different
colors — the conversation chrome accepts component overrides through the
`slots` prop on `MessageThread` (forwarded as `threadSlots` by `SessionViewer`
and by `AgentChat`, so the chat you embed takes the same overrides). Each slot
replaces one built-in and receives exactly that
built-in's props, so an override can always delegate back to the default
for the cases it does not customize:

```tsx
declare function AcmeCheckIcon(props: { done: boolean }): null;
declare const id: string;
declare const org: string;
// ---cut---
import {
  MessageEntry,
  SessionViewer,
  type MessageEntryProps,
  type MessageThreadSlots,
  type TodoRowProps,
} from "@stigmer/react-sdk";

// Restyle only user bubbles; every other message keeps the built-in.
function BrandedMessageEntry(props: MessageEntryProps) {
  if (props.message.kind !== "user") {
    return <MessageEntry {...props} />;
  }
  return <div className="acme-bubble">{props.message.text}</div>;
}

// Bring your own to-do row (and iconography) inside the built-in card.
function BrandedTodoRow({ item }: TodoRowProps) {
  return (
    <li className="acme-todo-row">
      <AcmeCheckIcon done={item.status === "completed"} /> {item.content}
    </li>
  );
}

// Module level, so thread rows keep their streaming re-render guarantees.
const THREAD_SLOTS: MessageThreadSlots = {
  MessageEntry: BrandedMessageEntry,
  TodoRow: BrandedTodoRow,
};

<SessionViewer sessionId={id} org={org} threadSlots={THREAD_SLOTS} />;
```

On `AgentChat` it is the same prop:
`<AgentChat agent="variance-reporter" org={org} threadSlots={THREAD_SLOTS} />`. To
answer approvals in your own card, pass `ApprovalCard`.

Available slots: `MessageEntry`, `ApprovalCard`, `TodoCard`, `TodoRow`,
`PlanFileCard`, `PlanCompletionCard`, `PlanStreamingCard`, `SetupProgress`
(the pre-first-token "Thinking…" indicator), `RecalledMemoriesCard` (the
"Recalled N of M memories" card), `RunErrorNotice` (the notice when a turn
fails) and `LivenessStatusLine` (the line that shows the agent is still
working between visible steps). Each slot's props type is exported from
`@stigmer/react-sdk` under the built-in's name plus `Props`, beside the
built-in itself, and the light chat entry, `@stigmer/react-sdk/chat`, exports
both too. Handing a case back costs your page nothing up front from the light
entry: its built-ins arrive with the conversation, as they do when nothing is
customized, and draw on its first frame. A page that draws the root's
`SessionViewer`, as above, already holds them. See the
[run reference](/docs/sdk/react/run) for each slot's props.

If a slot throws while it draws, ours draws in its place with the same props
and the chat keeps going; the error reaches your root's caught-error handler
(React's `onCaughtError`, which logs with `console.error` unless you set one).
A slot that draws nothing hides that part. For `ApprovalCard` and
`RunErrorNotice` that hides a decision or a failure the person needs, so always
draw them.

Two more ways add your own parts without replacing ours. When your own tool
runs (a tool of a server you connected, such as `create_invoice` on your
billing server), pass your card for it to `StigmerProvider` as `toolCards`,
keyed by the tool's name as the agent sees it (`mcp__billing__create_invoice`).
The step's line stays ours and still says whether it's running, done or
failed; your card replaces what opens under it and stays in view after the turn
finishes. If your card throws, ours shows
instead. See the [core reference](/docs/sdk/react/core) for `toolCards`, and
the [run reference](/docs/sdk/react/run) for `ToolCardProps`.

To put your own buttons on a message ("Open in Billing" on the agent's answer),
pass `messageActions` to `AgentChat`, `SessionViewer` or `MessageThread`: a
function that gets what the thread knows about each message (whose it is,
whether it's the final answer, its run and session) and returns your actions.
Up to two with an icon show beside Copy, the rest in one "More actions" menu,
all reachable by keyboard. A `MessageEntry` slot receives the same actions as
data (`messageActions`, with `messageInfo`), for a bubble or a right-click menu
of your own. If your function throws, that message shows without your actions.

## Token reference

The complete contract — all tokens with purposes, light/dark values, and
swatches — is in the [Design Tokens](/docs/sdk/theme/tokens) reference. It
is generated from the theme package's source stylesheet, so it always
matches the shipped values.
