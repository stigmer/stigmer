Every Stigmer component reads its colors, radii, fonts, shadows, and motion
from `--stgm-*` CSS custom properties — nothing visual is hardcoded. To make
the components wear your design language, you override tokens; the component
markup never changes.

Try it below: the conversation is rendered by the real `MessageThread`
organism from `@stigmer/react`. Switching preset or color mode changes only
token values.

## How the scope works

`StigmerProvider` wraps your subtree in a scoping element:

```html
<div class="stgm stgm-theme-corporate" data-stgm-color-mode="dark">
  <!-- your app + Stigmer components -->
</div>
```

Three mechanisms keep Stigmer's styles from colliding with your host
application:

- **The `.stgm` class** scopes every Stigmer style rule. Outside the scope,
  Stigmer's CSS does nothing.
- **The `stgm` cascade layer** (`@layer stgm`) gives Stigmer's rules lower
  priority than your unlayered host CSS, so your styles win ties by default.
- **The `--stgm-*` namespace** keeps token names from clashing with your own
  custom properties.

Portaled surfaces (dropdowns, dialogs, tooltips) render into a container on
`document.body` that carries the same theme class and color-mode attribute,
so they stay themed even though they render outside your DOM subtree.

The two containers are distinguishable through stable, documented marker
attributes: the in-tree scope carries `data-stgm-root`, the portal
container carries `data-stgm-portal`. You can rely on both in host CSS.

## Sizing and fixed-height embedding

The in-tree scope ships with **no layout styling** — it sizes to its
content, so mounting the provider in a normally-scrolling page needs
nothing.

Fixed-height embeddings (a docked conversation pane, a split layout, an
IDE-style panel) are different: height-filling components like
`SessionViewer` root at `height: 100%` and need an unbroken
percentage-height chain from your definite-height region down to them.
The scope element sits in that chain, so opt it in from your CSS via the
stable `data-stgm-root` selector:

```css
.stgm[data-stgm-root] {
  height: 100%;
  min-height: 0;
}
```

Then give the provider a definite-height ancestor and the conversation
fills the pane, with the transcript scrolling internally:

```tsx
<div style={{ height: 480, overflow: "hidden" }}>
  <StigmerProvider client={client} preset="monochrome" colorMode="dark">
    <SessionViewer sessionId={sessionId} org={org} audience="endUser" />
  </StigmerProvider>
</div>
```

`min-height: 0` matters when the scope is a flex or grid child: without
it the browser refuses to shrink the scope below its content, and
internal scrolling never engages.

Two things to know:

- **This is opt-in by design, not an SDK default.** `height: 100%` is
  not benign in arbitrary layouts — under a flex-item parent (a `flex-1`
  content column, for instance) the browser resolves percentages against
  the flexed size and the scope balloons to it, even in a content-sized
  page. Only you know your layout; scope the rule to the embeddings that
  need it.
- **The provider's `className` prop is the wrong tool for layout.** It is
  a *theming* channel, mirrored onto the portal container on
  `document.body` so token overrides reach portaled surfaces — layout
  styles passed there would also size that off-tree element. Target
  `.stgm[data-stgm-root]` for the in-tree container alone.

## Set the color mode

Pass `colorMode` to `StigmerProvider`:

```tsx
<StigmerProvider client={client} colorMode="dark">
```

- `"light"` (default) and `"dark"` set the mode explicitly.
- `"system"` follows the OS preference and updates live.

The resolved mode is applied as `data-stgm-color-mode` on the scope, and all
dark token values key off that attribute — no ancestor classes required. If
your app already has a theme state (next-themes, MUI, your own context),
pass its current value straight through:

```tsx
const { resolvedTheme } = useTheme(); // next-themes
<StigmerProvider client={client} colorMode={resolvedTheme === "dark" ? "dark" : "light"}>
```

## Start from a preset

Presets are complete design languages — radius, palette, surfaces, sidebar
treatment — shipped as CSS classes. Import the CSS once and select the
preset on the provider:

```tsx
import "@stigmer/theme/tokens.css";
import "@stigmer/theme/presets/corporate.css";

<StigmerProvider client={client} preset="corporate" colorMode="system">
```

See [Presets](/docs/sdk/theme/presets) for the six built-in design languages
and every token each one overrides.

## Override tokens directly

For a custom brand, define a theme class that overrides the tokens you care
about and pass it via `className`. Anything you do not override falls
through to the [defaults](/docs/sdk/theme/tokens).

```css
.acme-theme {
  --stgm-radius: 0.375rem;
  --stgm-primary: oklch(0.55 0.2 260);
  --stgm-primary-foreground: oklch(0.985 0 0);
  --stgm-ring: oklch(0.55 0.15 260);
}

.acme-theme[data-stgm-color-mode="dark"],
[data-stgm-color-mode="dark"] .acme-theme {
  --stgm-primary: oklch(0.72 0.18 260);
  --stgm-primary-foreground: oklch(0.145 0 0);
}
```

```tsx
<StigmerProvider client={client} className="acme-theme" colorMode="dark">
```

Two rules keep custom themes correct:

- **Always pair light and dark.** A token defined only in your light block
  outranks Stigmer's default dark value in the cascade, so the light value
  would leak into dark mode. If you override a token, give it a dark value
  too (the dual selector above handles both attribute placements).
- **Mind contrast.** Stigmer's defaults are contrast-audited in CI (WCAG 2.1
  AA for every declared text pairing). When you replace a fill, replace its
  `-foreground` partner so the pair stays readable — dark-mode fills are
  usually lighter, which is why their foregrounds flip to near-black.

## Tailwind hosts: avoid theme-key collisions

Stigmer's stylesheet maps its tokens onto Tailwind's standard theme keys
(`--color-background`, `--color-card`, `--color-muted`, …) so components can
use plain utilities like `bg-background`. If your own Tailwind v4 build maps
those same keys to your palette in an `@theme` block, Tailwind resolves each
key once — last definition wins — and Stigmer components will silently paint
with *your* palette, ignoring `data-stgm-color-mode` and presets.

If your app defines those keys, re-point the underlying variables inside the
Stigmer scope so shared utilities resolve through the token contract again:

```css
.stgm {
  --background: var(--stgm-background);
  --foreground: var(--stgm-foreground);
  --card: var(--stgm-card);
  --card-foreground: var(--stgm-card-foreground);
  --muted: var(--stgm-muted);
  --muted-foreground: var(--stgm-muted-foreground);
  --primary: var(--stgm-primary);
  --primary-foreground: var(--stgm-primary-foreground);
  --border: var(--stgm-border);
  /* ...every key both palettes define */
}
```

No light/dark pairing is needed here — the `--stgm-*` values already flip
with `data-stgm-color-mode`. Similarly, if your build declares its own
`dark` variant (e.g. next-themes' `.dark` class), declare the combined form
after your imports so both your app and Stigmer scopes respond correctly:

```css
@custom-variant dark (&:is(.dark *, [data-stgm-color-mode="dark"] *));
```

## The radius scale

Components use a four-step radius scale (`rounded-sm` through `rounded-xl`)
that is *derived* from the single `--stgm-radius` token:

| Step | Value |
|------|-------|
| `sm` | `--stgm-radius` − 4px |
| `md` | `--stgm-radius` − 2px |
| `lg` | `--stgm-radius` |
| `xl` | `--stgm-radius` + 4px |

Override one token and every corner in every component reshapes
proportionally — `0.125rem` gives the sharp Fintech look, `1.25rem` the very
round Friendly look.

## Tool-call output blocks

Every tool-call output the agent produces — the terminal/shell session (the
`$ command` line and its stdout/stderr), code and file blocks, and search
and list results — renders on one shared surface: `--stgm-muted-subtle` with
`--stgm-foreground` text (and `--stgm-destructive` for stderr and non-zero
exit codes). There is no separate "terminal" token, and no block ships a
fixed dark box: they all track the active preset and color mode through the
core tokens, so a themed light surface stays light. Override the core
surface and text tokens and every output block follows — including the
terminal. All of these pairings are covered by the CI contrast audit.

## Beyond tokens: component slots

When your design system needs different *structure* — not just different
colors — the conversation chrome accepts component overrides through the
`slots` prop on `MessageThread` (forwarded as `threadSlots` by
`SessionViewer`). Each slot replaces one built-in and receives exactly that
built-in's props, so an override can always delegate back to the default
for the cases it does not customize:

```tsx
import {
  MessageEntry,
  type MessageEntryProps,
  type MessageThreadSlots,
  type TodoRowProps,
} from "@stigmer/react";
import { MessageType } from "@stigmer/protos/ai/stigmer/agentic/agentexecution/v1/enum_pb";

// Restyle only user bubbles; every other message keeps the built-in.
function BrandedMessageEntry(props: MessageEntryProps) {
  if (props.message.type !== MessageType.MESSAGE_HUMAN) {
    return <MessageEntry {...props} />;
  }
  return <div className="acme-bubble">{props.message.content}</div>;
}

// Bring your own to-do row (and iconography) inside the built-in card.
function BrandedTodoRow({ item }: TodoRowProps) {
  return (
    <li className="acme-todo-row">
      <AcmeCheckIcon done={item.status === 3} /> {item.content}
    </li>
  );
}

// Module level, so thread rows keep their streaming re-render guarantees.
const THREAD_SLOTS: MessageThreadSlots = {
  MessageEntry: BrandedMessageEntry,
  TodoRow: BrandedTodoRow,
};

<SessionViewer sessionId={id} org={org} threadSlots={THREAD_SLOTS} />;
```

Available slots: `MessageEntry`, `ApprovalCard`, `TodoCard`, `TodoRow`,
`PlanArtifactCard`, `PlanCompletionCard`, `PlanStreamingCard`, and
`SetupProgress` (the pre-first-token "Thinking…" indicator). See the
[execution reference](/docs/sdk/react/execution) for each slot's props.
