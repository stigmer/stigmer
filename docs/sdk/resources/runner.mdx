Runner follows the Kubernetes Node pattern: the spec is intentionally thin because the runner is infrastructure that registers itself. The user's intent when creating a runner is minimal — "I want a runner with this name." All operational state (phase, queue, machine info, capacity) is reported by the runner process via heartbeat and lives in RunnerStatus.

For system-managed (ephemeral) runners created by the platform for cloud executions, the spec is typically empty — the platform fills in metadata labels (stigmer.ai/system-managed: "true") and the runner self-reports everything else.

### heartbeat

Report runner liveness and operational state.

Called by the runner process every 30 seconds. Updates status fields (phase, last_heartbeat_at, current_executions, connection_info) without modifying spec or metadata.

If the runner is in PENDING or STOPPED phase, a heartbeat transitions it to the phase reported in the input (typically READY). This enables the "restart and reconnect" flow: a stopped runner resumes heartbeating and goes back to READY with the same identity and task queue.

### RunnerPhase

RunnerPhase tracks the operational state of a runner process.

| Value | Description |
|-------|-------------|
| `RUNNER_PHASE_PENDING` | Resource created but no heartbeat received yet. |
| `RUNNER_PHASE_READY` | Runner is heartbeating and accepting new executions. |
| `RUNNER_PHASE_BUSY` | Runner is heartbeating but at maximum concurrent execution capacity. |
| `RUNNER_PHASE_STOPPED` | Runner has stopped heartbeating (timeout) or was explicitly stopped. |
| `RUNNER_PHASE_FAILED` | Unrecoverable error. |
