# Stigmer Documentation Standards

This document defines the rules, conventions, and quality bar for all Stigmer documentation. Every document — whether authored by a human or generated by AI — must conform to these standards.

For doc-type-specific structure, see the templates in [`templates/`](templates/).

For the canonical terminology dictionary, see [`terminology.json`](terminology.json).

For the navigation hierarchy and URL scheme, see [`information-architecture.md`](information-architecture.md).

---

## Audience & Purpose

### Who the documentation is for

**Primary audience**: Platform builders who want to embed Stigmer's AI agent execution into their products. They are technically skilled, new to Stigmer, evaluating alternatives, and time-constrained. Every page must serve their needs first.

**Secondary audiences**: Individual developers exploring Stigmer for personal projects. Contributors to the OSS project who need to understand the architecture.

The primary audience drives every structural and editorial decision. When in doubt, optimize for the platform builder.

### What the documentation must accomplish

Bridge the gap from **"What is this?"** to **"I have agents running in my platform."** Every page must move the reader closer to that outcome.

### Organizing framework — Diataxis

Stigmer documentation follows the [Diataxis framework](https://diataxis.fr/). Every document belongs to exactly one quadrant:

| Quadrant | Reader need | Our content type | Directory |
|---|---|---|---|
| **Tutorials** | "Help me learn" (learning-oriented) | Quickstarts | `docs/quickstarts/` |
| **How-to Guides** | "Help me solve a problem" (task-oriented) | Guides | `docs/guides/` |
| **Reference** | "Give me the facts" (information-oriented) | CLI Reference, SDK Reference | `docs/cli/`, `docs/sdk/` |
| **Explanation** | "Help me understand" (understanding-oriented) | Concepts | `docs/concepts/` |

Content that mixes quadrants confuses the reader. A concept doc that drifts into step-by-step instructions is neither a good explanation nor a good guide.

### Content validation

Every factual claim must be validated against the current codebase. Stale documentation is worse than no documentation.

- Proto definitions in `apis/ai/stigmer/` are the source of truth for domain concepts.
- CLI examples must be tested — run every command, verify every output.
- YAML examples must be valid and complete enough to use.
- Do not trust legacy documentation or AI-generated content without verification.

## Mandate

These five rules are non-negotiable. They apply to every document in `docs/`.

### 1. Ubiquitous Language Is Sacred

Documentation must mirror the domain model exactly. Proto names are the canonical names.

- If the proto says `AgentExecution`, the docs never say "agent run," "execution instance," or "job."
- If the code uses `McpServer`, the docs never say "tool connector" or "tool server."
- If a domain term changes in the architecture, update every document that references it in the same PR. Stale terminology is a severity-1 bug.

The machine-readable term dictionary in [`terminology.json`](terminology.json) is the source of truth. The terminology linter enforces it automatically.

### 2. Eliminate Assumptions

Never assume "the user just knows."

- State every prerequisite explicitly.
- Define every acronym on first use: MCP (Model Context Protocol), DDD (Domain-Driven Design), HITL (Human-in-the-Loop).
- Every YAML example must be complete enough to `stigmer apply` without guessing.
- Every CLI example must include the expected output or a description of what happens.

### 3. Active Voice and Imperative Clarity

Use direct, active verbs. Be surgical with words.

| Do | Do not |
|---|---|
| "Configure the environment" | "The environment should be configured" |
| "Run the command" | "The command can be run" |
| "Stigmer creates an AgentInstance" | "An AgentInstance is created by Stigmer" |

Remove hedging words: "usually," "sometimes," "might," "should probably," "it is recommended that." If something is conditional, state the condition explicitly.

### 4. Structural Hierarchy

Information must be scannable.

- Use consistent heading levels, bullet points for lists, tables for comparisons, and fenced code blocks for YAML/CLI examples.
- Complex flows must be accompanied by a Mermaid diagram or ASCII-art step-by-step breakdown.
- Follow the established templates for each document type. Do not invent new structures.

### 5. Analogies Ground Understanding

Stigmer uses container/Kubernetes analogies deliberately:

| Stigmer Concept | Analogy |
|---|---|
| Agent | Docker image |
| AgentExecution | `docker run` |
| AgentInstance | Docker Compose service |
| Session | Terminal session |
| Organization | Kubernetes namespace |
| Skill | npm package |

Use these analogies when they clarify. Drop them when they mislead.

## Content Types

Every document in `docs/` belongs to exactly one content type. Each type has a defined purpose, audience, canonical directory, and template.

| Type | Purpose | Audience | Directory | Template |
|---|---|---|---|---|
| **Concept** | Explain what X is and why it exists | All developers | `docs/concepts/` | [`concept.mdx`](templates/concept.mdx) |
| **Quickstart** | Get X running in 5 minutes | New users | `docs/quickstarts/` | [`quickstart.mdx`](templates/quickstart.mdx) |
| **SDK Guide** | How to use X with SDK Y | SDK users | `docs/sdk/{language}/` | [`sdk-guide.mdx`](templates/sdk-guide.mdx) |
| **How-to Guide** | How to accomplish task Z | Practicing developers | `docs/guides/` | [`how-to-guide.mdx`](templates/how-to-guide.mdx) |
| **CLI Reference** | Command reference for `stigmer <cmd>` | CLI users | `docs/cli/` | [`cli-reference.mdx`](templates/cli-reference.mdx) |
| **Architecture** | Why X is designed this way | Contributors, advanced users | `docs/architecture/` | [`architecture.mdx`](templates/architecture.mdx) |
| **ADR** | We decided X because Y | Contributors | `docs/adr/` | [`adr.mdx`](templates/adr.mdx) |

### Choosing the Right Type

- "What is X?" → Concept
- "How do I install and run my first X?" → Quickstart
- "How do I do Y with the Go SDK?" → SDK Guide
- "How do I configure environment variables?" → How-to Guide
- "What does `stigmer apply` do?" → CLI Reference
- "Why does Stigmer use SQLite locally?" → Architecture
- "We switched from BadgerDB to SQLite" → ADR

## Frontmatter Schema

Every MDX file must include YAML frontmatter. The following fields are defined:

### Required Fields

| Field | Type | Description |
|---|---|---|
| `title` | string | Page title. Rendered as the H1 and used in the sidebar. |
| `description` | string | One-sentence summary. Used in meta tags and search results. Max 160 characters. |

### Optional Fields

| Field | Type | Default | Description |
|---|---|---|---|
| `sidebar_label` | string | Value of `title` | Short label for sidebar navigation when the title is too long. |
| `sidebar_position` | number | Alphabetical | Ordering within the parent section. Lower numbers appear first. |
| `tags` | string[] | `[]` | Categorization tags for search and filtering. |
| `last_updated` | date | — | ISO 8601 date of last substantive edit. Updated manually. |

### Example

```yaml
---
title: What is an Agent?
description: An Agent is a portable, versioned, declarative definition of an AI worker.
sidebar_label: Agents
sidebar_position: 2
tags: [concepts, agent, core]
last_updated: 2026-03-21
---
```

## Heading Hierarchy

- **H1** (`#`): Page title. Exactly one per document. Must match the `title` frontmatter field.
- **H2** (`##`): Major sections. These define the document's structural outline.
- **H3** (`###`): Subsections within an H2. Use for logical groupings.
- **H4** (`####`): Permitted only in reference docs (CLI options, API fields) where deep nesting is unavoidable.
- Never skip levels. An H3 must follow an H2, not an H1.

### Heading Content Rules

- Use sentence case: "The problem agents solve," not "The Problem Agents Solve."
  - Exception: the existing `what-is-*.md` files use title case. New documents use sentence case; existing documents retain their style until migrated.
- Do not use code formatting in headings: "Install the CLI," not "Install `stigmer`."
- Headings must be unique within a document to ensure anchor links work.

## Code Blocks

### Language Tags

Every fenced code block must have a language tag.

````markdown
```yaml
apiVersion: agentic.stigmer.ai/v1
kind: Agent
```
````

Supported tags: `yaml`, `bash`, `go`, `python`, `typescript`, `sql`, `json`, `proto`, `mermaid`, `text`.

Use `text` for generic output that has no syntax highlighting.

### Completeness

- YAML examples must be valid YAML. A reader should be able to paste the example into a file and use it.
- Bash examples must include the command and, where practical, the expected output as a comment or separate `text` block.
- Go/Python/TypeScript examples must include import statements when the imports are not obvious.

### Runnable Examples

Quickstart and how-to guide code blocks must be runnable end-to-end. If an example requires setup that is not shown, state the prerequisites explicitly before the code block.

## Writing Style

### Voice and Tense

- Use **second person** ("you") when addressing the reader.
- Use **present tense** for descriptions: "Stigmer creates an AgentInstance."
- Use **imperative mood** for instructions: "Run the command." "Create a file."

### Precision

- One precise sentence beats three vague ones.
- Remove filler words: "basically," "simply," "just," "actually," "in order to."
- Remove hedging: "usually," "sometimes," "might," "it is recommended." If something is conditional, state the condition.
- Avoid marketing language. Documentation is not a press release.

### Terminology

- Always use the canonical term from [`terminology.json`](terminology.json).
- On first use in a document, provide context: "An AgentExecution (a single run of an agent within a session) records every tool call."
- After first use, use the canonical term without explanation.

### Lists

- Use bullet lists for unordered items.
- Use numbered lists only for sequential steps.
- Each list item starts with a capital letter and ends with a period if it is a complete sentence.

---

## Cross-Referencing

- Use **relative links** that survive directory restructuring.
- Link to the canonical document for a concept rather than re-explaining it. Example: "See [What is an Agent?](../concepts/agent.mdx) for the full resource model."
- Never duplicate explanations across documents. If two docs need the same explanation, one of them must link to the other.
- Anchor links must point to actual headings. Verify that the target heading exists.

---

## Diagrams

- Use **Mermaid** fenced code blocks for all diagrams — flowcharts, sequence diagrams, architecture diagrams, resource hierarchies, and pipelines. Mermaid renders natively in Fumadocs.
- Never use `text` code blocks for visual structures like resource trees, architecture flows, or pipelines. If it has a visual structure, it belongs in a Mermaid diagram.
- Every diagram must have surrounding text that conveys the same information. Diagrams supplement text; they do not replace it.

## Quality Checklist

Before merging any documentation change, verify:

- [ ] Frontmatter includes `title` and `description`
- [ ] Exactly one H1 matching the `title` field
- [ ] No skipped heading levels
- [ ] Every code block has a language tag
- [ ] YAML examples are valid YAML
- [ ] No prohibited terminology (run the linter)
- [ ] All relative links resolve to real files
- [ ] No duplicated explanations — linked to canonical docs instead
- [ ] Active voice throughout instructions
- [ ] No hedging words
- [ ] Follows the correct template for its content type
