## What you'll build

An Agent that can **look up real data**, **take actions on your behalf**, and
**ask for human approval** before doing anything risky. You will add an MCP
server, see its tools with the risky ones marked, and wire everything into your
code.

**Time**: ~15 minutes **Prerequisites**: Completed
[Your first Skill](/docs/getting-started/first-skill)

<Callout type="info">
  **Running locally?** Your web console is at
  [`http://localhost:7234`](http://localhost:7234). Wherever these steps say
  `app.stigmer.ai`, use your local address instead. Drop the
  `STIGMER_API_KEY=sk_your_key` prefix from run commands — your local server
  doesn't require it.
</Callout>

Here is where this tutorial ends up: your order management API in a plugin,
signed in, a chat started with it, then the same plugin listed on a Session from
code, an order lookup, and an approval before a return.

## The problem

Your Agent knows your return policy — it answers domain questions accurately.
But ask it to look up order #ORD-4821 or process a return, and it can't help. It
has knowledge but no hands.

MCP servers give your Agent hands. An MCP server is a bridge between your Agent
and an external system — an API, a database, an internal service. Stigmer
connects to any server that speaks the
[Model Context Protocol](https://modelcontextprotocol.io/).

In Stigmer an MCP server reaches an Agent two ways: in a plugin, the package
that can carry Skills and hooks as well, or written in the Agent itself. This
tutorial uses a plugin, which every Agent and chat can share: a server you add
by its address becomes a plugin of its own, holding that one server. To write a
server in one Agent instead, see
[Give an agent its own MCP server](/docs/guides/integrations/connect-an-mcp-server#give-an-agent-its-own-mcp-server).

<Callout type="info">
  Many MCP servers arrive ready-made in plugins: install one from a marketplace
  and its servers come with it (see [Install a plugin from a
  marketplace](/docs/guides/plugins/install-from-a-marketplace)). This tutorial
  adds one server by its address, so you see every step.
</Callout>

## Add an MCP server

Your order management service answers MCP at an address, say
`https://orders.example.com/mcp`.

1. Open [`app.stigmer.ai`](https://app.stigmer.ai) and go to **Library →
   Plugins**.
2. Click **Add MCP server**. The form asks for a name, the server's URL, what it
   is for, and optional headers.
3. Name it `order-management-api`, paste the URL, and click **Add**. Stigmer
   builds a plugin holding that one server, named after it, installs it in your
   Organization, and opens the plugin's page.

Here is what that flow looks like:

<ScenarEmbed
  id="mcp-server-creation-tour"
  title="Add an MCP server walkthrough"
/>

The CLI does the same in one line:

```bash
stigmer mcp add order-management-api https://orders.example.com/mcp
```

A server that takes an API key instead of a sign-in gets it in a header, such as
`Authorization` with the value `Bearer ${ORDER_API_KEY}`. The `${ORDER_API_KEY}`
names a key in your vault; its value is never written into the plugin.

<Callout type="info">
  A server at an address works in local and hosted conversations alike. A server
  that runs as a local program (through `npx`, `uvx` or a binary) is written
  into a plugin folder instead (see [Install a
  plugin](/docs/guides/plugins/install-a-plugin)), and runs only where your own
  runner runs: the desktop app or the CLI.
</Callout>

</Step>

## Sign in and see its tools

The plugin's page shows its one server and what stands before its first tool
call. This server asks you to sign in: when it was added, Stigmer asked its
address once, and it answered with an OAuth challenge.

1. On the server's row, click **Sign in** and finish the login on the provider's
   own page. Stigmer never sees your password: the token it gets back is saved
   in your [My vault](/docs/concepts/vaults), and the row reads **Signed in**.
2. Click **Check tools**. Stigmer asks the server for its tools right now, as
   you, and stores nothing.

<ScenarEmbed
  id="mcp-server-connect-tour"
  title="Sign in and check tools walkthrough"
/>

From the CLI, `stigmer connect plugin order-management-api` signs in when the
server needs it and prints the same list. To try the tools before writing any
code, click **Start a chat** on the plugin's page: it opens a conversation that
uses the plugin whole.

In this example, three tools come back: `get_order`, `list_orders`, and
`process_return`. A tool the server marks destructive (its author set the MCP
annotation `destructiveHint: true`) is shown as **Destructive** and asks for
human approval before it runs. The server marks `process_return` destructive, so
the Agent will pause and present the action details before executing it. The
first two run automatically.

<Callout type="info">
  The server's author decides which tools are destructive, and every Agent that
  uses the server asks before those tools. To keep an Agent away from a tool
  altogether, leave it out of the Agent's `tools` list — see [Approval
  Flows](/docs/concepts/approval-flows).
</Callout>

</Step>

## Handle approvals in your code

Now try a request that needs an approval. Update the message:

```
"Process a return for order #ORD-4821 — the headphones are defective."
```

The run pauses when the Agent calls `process_return`. The call waits for your
answer: the Session's log records a `stigmer.permission.asked` event for it,
naming the call by its `tool_use_id`. Your code answers on the Session with
`confirmToolUse`, and the run resumes. Replace your stream loop:

<Tabs items={["TypeScript", "Go", "Python", "Java"]} groupId="sdk-language" persist>
<Tab value="TypeScript">

`waitForTurn` follows the Session until the run ends or waits for an answer.
Replace the import at the top of `ask-agent.ts` with these:

```typescript
import { create } from "@bufbuild/protobuf";
import { ConfirmToolUseInputSchema } from "@stigmer/protos/ai/stigmer/agentic/session/v1/io_pb";
import { Stigmer, waitForTurn } from "@stigmer/sdk";
```

Then replace the stream loop in `ask-agent.ts`:

```typescript
  const sessionId = session.metadata!.id;
  let outcome = await waitForTurn(stigmer, sessionId, run.metadata!.id);
  while (outcome.phase === "waiting") {
    for (const ask of outcome.asks) {
      console.log(`\nApproval required: ${ask.ask?.message}`);
      console.log(`  Tool use: ${ask.id}`);

      await stigmer.session.confirmToolUse(
        create(ConfirmToolUseInputSchema, { sessionId, toolUseId: ask.id, result: "allow" }),
      );
      console.log("  Approved. Resuming run...\n");
    }
    outcome = await waitForTurn(stigmer, sessionId, outcome.runId, {
      afterSeq: outcome.lastSeq,
    });
  }
  console.log(outcome.answer);
}

main();
```

</Tab>
<Tab value="Go">

Replace the stream loop in `main.go`:

```go
for {
    frame, err := stream.Recv()
    if err == io.EOF {
        break
    }
    if err != nil {
        log.Fatal(err)
    }
    event := frame.GetEvent()
    if event.GetRunId() != run.GetMetadata().GetId() {
        continue
    }

    if asked := event.GetStigmerPermissionAsked(); asked != nil {
        fmt.Printf("\nApproval required: %s\n", asked.GetMessage())
        fmt.Printf("  Tool use: %s\n", asked.GetToolUseId())

        _, err := client.Session.ConfirmToolUse(ctx, &sessionv1.ConfirmToolUseInput{
            SessionId: session.GetMetadata().GetId(),
            ToolUseId: asked.GetToolUseId(),
            Result:    "allow",
        })
        if err != nil {
            log.Fatal(err)
        }
        fmt.Println("  Approved. Resuming run...")
    }

    if msg := event.GetAgentMessage(); msg != nil && event.GetThreadId() == "" {
        for _, block := range msg.GetContent() {
            fmt.Print(block.GetText())
        }
        fmt.Println()
    }

    if status := event.GetStigmerRunStatus(); status != nil {
        switch status.GetPhase() {
        case "completed", "failed", "cancelled", "terminated":
            return
        }
    }
}
```

        print("".join(block.text for block in event.agent_message.content))

    var event = stream.next().getEvent();
    if (!event.getRunId().equals(run.getMetadata().getId())) {
        continue;
    }

    if (event.hasStigmerPermissionAsked()) {
        var asked = event.getStigmerPermissionAsked();
        System.out.printf("%nApproval required: %s%n", asked.getMessage());
        System.out.printf("  Tool use: %s%n", asked.getToolUseId());

        client.session.confirmToolUse(
            ConfirmToolUseInput.newBuilder()
                .setSessionId(session.getMetadata().getId())
                .setToolUseId(asked.getToolUseId())
                .setResult("allow")
                .build()
        );

    }

    if (event.hasAgentMessage() && event.getThreadId().isEmpty()) {
        for (var block : event.getAgentMessage().getContentList()) {
            System.out.print(block.getText());
        }
        System.out.println();
    }
    if (event.hasStigmerRunStatus()
            && ended.contains(event.getStigmerRunStatus().getPhase())) {
        break;
    }
}

## The difference

|                     | Without tools         | With tools + approvals          |
| ------------------- | --------------------- | ------------------------------- |
| **Data access**     | None — can only guess | Calls APIs to get real data     |
| **Actions**         | None — can only talk  | Processes returns, updates      |
| **Human oversight** | Not applicable        | Sensitive actions need approval |
| **Trust**           | Low — no verification | High — grounded in real data    |

## What just happened

You gave your Agent tools by adding an MCP server, which Stigmer installed as a
plugin of one server. The server itself says which of its tools ask for
approval. In your code, two changes made the difference: `plugins` to give the
conversation the server's tools, and `confirmToolUse` to answer the calls that
ask for approval.

Your Agent now knows your domain (Skills), uses your tools (MCP servers), and
asks before risky actions (approvals). But look at your Session creation code —
every time you create a Session, you list every Skill and every plugin. Add a
new feature tomorrow, and you'll copy-paste that list again. A colleague
building the checkout page won't know which references to include. And the Agent
has no personality — it uses a generic prompt for every interaction.

In the next guide, you'll bundle all of this into a reusable Agent with its own
name, role, and instructions — then reference it with a single line.
