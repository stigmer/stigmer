## What you'll build

An Agent that can **look up real data**, **take actions on your behalf**, and
**ask for human approval** before doing anything risky. You will connect an MCP
server, discover its tools, generate approval policies, and see everything
working end-to-end from your code.

**Time**: ~15 minutes **Prerequisites**: Completed
[Your first Skill](/docs/getting-started/first-skill)

<DemoConnectToolsTour />

## The problem

Your Agent knows your return policy — it answers domain questions accurately.
But ask it to look up order #ORD-4821 or process a return, and it can't help. It
has knowledge but no hands.

MCP servers give your Agent hands. An MCP server is a bridge between your Agent
and an external system — an API, a database, an internal service. Stigmer
connects to any server that speaks the
[Model Context Protocol](https://modelcontextprotocol.io/).

## Add an MCP server

1. Open [`app.stigmer.ai`](https://app.stigmer.ai) and go to **Library → MCP
   Servers**.
2. Click **Add MCP Server**. This opens the MCP Server Creator — an Agent that
   builds the server configuration from your description.
3. Tell it about your server: the name, the URL (for HTTP servers), and whether
   it needs authentication.

For an HTTP server, the Agent needs the endpoint URL. For a stdio server (a
command-line tool), it needs the command — `npx` for an npm package or the path
to a Go binary.

Here is what that conversation looks like:

<DemoMcpServerCreationTour />

4. Review the generated configuration and click **Apply** to save it to your
   Organization's library.

<Callout type="info">
  Stigmer supports both **HTTP** servers (REST APIs, webhooks) and **stdio**
  servers (CLI tools via `npx`, `go run`, or local binaries). The Server Creator
  Agent handles either — just describe what you have.
</Callout>

</Step>

## Discover capabilities

Your MCP server is registered, but Stigmer doesn't know what tools it provides
yet. Discovery connects to the server and catalogs every tool.

1. Open the MCP server detail page.
2. If the server requires credentials (API keys, tokens), enter them in the
   Environment variables section.
3. Click **Discover**.

Stigmer connects to the live server, queries its capabilities, and lists every
tool with its name and description:

<DemoDiscoverCapabilities />

In this example, three tools were discovered: `get_order` (read), `list_orders`
(read), and `process_return` (write). Two are safe read operations. One modifies
data — that's where approval policies come in.

</Step>
<Step>

## Generate approval policies

Some tools are safe to call any time — looking up an order is a read operation.
Others, like processing a return and issuing a refund, need a human in the loop.

1. On the same MCP server detail page, click **Generate Policies**.
2. Stigmer's AI reviews each discovered tool. Read-only tools pass through.
   Tools that modify data, move money, or have side effects get flagged for
   approval.
3. Review the generated policies and confirm.

<DemoGeneratePolicies />

In this example, `get_order` and `list_orders` run automatically.
`process_return` requires human approval — the Agent will pause and present the
action details before executing.

<Callout type="info">
  Approval policies are stored on the MCP server resource. Every Agent that uses
  this server inherits the same policies. You can edit or override them at any
  time.
</Callout>

</Step>

## Handle approvals in your code

Now try a request that triggers the approval policy. Update the message:

```
"Process a return for order #ORD-4821 — the headphones are defective."
```

The execution will pause when the Agent tries to call `process_return`. Your
code needs to detect the pending approval and submit a decision. Update your
subscribe loop:

<Tabs items={["TypeScript", "Go", "Python", "Java"]} groupId="sdk-language" persist>
<Tab value="TypeScript">

Replace the subscribe loop in `ask-agent.ts`:

```typescript
for await (const snapshot of stigmer.agentExecution.subscribe(
  execution.metadata!.id,
)) {
  const phase = snapshot.status?.phase;
  const messages = snapshot.status?.messages ?? [];
  const pendingApprovals = snapshot.status?.pendingApprovals ?? [];

  if (pendingApprovals.length > 0) {
    for (const pending of pendingApprovals) {
      console.log(`\nApproval required: ${pending.approvalMessage}`);
      console.log(`  Tool: ${pending.toolCallId}`);

      await stigmer.agentExecution.submitApproval({
        agentExecutionId: snapshot.metadata!.id,
        toolCallId: pending.toolCallId,
        action: "APPROVAL_ACTION_APPROVE",
      });
      console.log("  Approved. Resuming execution...\n");
    }
  }

  if (phase === "EXECUTION_COMPLETED" || phase === "EXECUTION_FAILED") {
    const last = messages[messages.length - 1];
    if (last?.content) console.log(last.content);
    break;
  }
}

main();
```

</Tab>
<Tab value="Go">

Replace the subscribe loop in `main.go`:

```go
for {
    snapshot, err := stream.Recv()
    if err == io.EOF {
        break
    }
    if err != nil {
        log.Fatal(err)
    }

    status := snapshot.GetStatus()
    pending := status.GetPendingApprovals()

    for _, p := range pending {
        fmt.Printf("\nApproval required: %s\n", p.GetApprovalMessage())
        fmt.Printf("  Tool: %s\n", p.GetToolCallId())

        _, err := client.AgentExecution.SubmitApproval(ctx,
            &stigmer.SubmitApprovalInput{
                AgentExecutionId: snapshot.GetMetadata().GetId(),
                ToolCallId:       p.GetToolCallId(),
                Action:           stigmer.ApprovalActionApprove,
            })
        if err != nil {
            log.Fatal(err)
        }
        fmt.Println("  Approved. Resuming execution...\n")
    }

    phase := status.GetPhase()
    if phase == stigmer.ExecutionCompleted || phase == stigmer.ExecutionFailed {
        msgs := status.GetMessages()
        if len(msgs) > 0 {
            fmt.Println(msgs[len(msgs)-1].GetContent())
        }
        break
    }
}
```

while (stream.hasNext()) {
    var snapshot = stream.next();
    var status = snapshot.getStatus();
    var pending = status.getPendingApprovalsList();

    for (var p : pending) {
        System.out.printf("%nApproval required: %s%n", p.getApprovalMessage());
        System.out.printf("  Tool: %s%n", p.getToolCallId());

        client.agentExecutions().submitApproval(
            SubmitApprovalInput.builder()
                .agentExecutionId(snapshot.getMetadata().getId())
                .toolCallId(p.getToolCallId())
                .action(ApprovalAction.APPROVE)
                .build()
        );
        System.out.println("  Approved. Resuming execution...\n");
    }

    var phase = status.getPhase();
    if (phase == ExecutionPhase.COMPLETED || phase == ExecutionPhase.FAILED) {
        var messages = status.getMessagesList();
        if (!messages.isEmpty()) {
            System.out.println(messages.get(messages.size() - 1).getContent());
        }
        break;
    }
}

## The difference

|                     | Without tools         | With tools + approvals          |
| ------------------- | --------------------- | ------------------------------- |
| **Data access**     | None — can only guess | Calls APIs to get real data     |
| **Actions**         | None — can only talk  | Processes returns, updates      |
| **Human oversight** | Not applicable        | Sensitive actions need approval |
| **Trust**           | Low — no verification | High — grounded in real data    |

## What just happened

You connected tools to your Agent through an MCP server, discovered its
capabilities, and generated approval policies — all through the Stigmer web app.
In your code, two changes made the difference: `mcpServerRefs` to give the Agent
access to tools, and `submitApproval` to handle the human-in-the-loop flow.

Your Agent now knows your domain (Skills), uses your tools (MCP servers), and
follows your rules (approval policies). But look at your Session creation code —
every time you create a Session, you list every Skill and every MCP server. Add
a new feature tomorrow, and you'll copy-paste that list again. A colleague
building the checkout page won't know which references to include. And the Agent
has no personality — it uses a generic prompt for every interaction.

In the next guide, you'll bundle all of this into a reusable Agent with its own
name, role, and instructions — then reference it with a single line.
