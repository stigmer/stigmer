---
title: Enable authentication
description:
  Turn on authentication for the Docker Compose stack or the Helm chart. People
  sign in through your OIDC provider, machines use API keys, and the web console
  signs in through the same provider.
---

By default, a self-hosted Stigmer server trusts every request. That is the right
posture for a single-user machine, and the wrong one the moment the port is
reachable by anyone else. This guide turns authentication on for the two shapes
you serve to a team, the [Docker Compose stack](./docker-compose) and the
[Helm chart](./kubernetes): people sign in through your OIDC provider, and
machines (CI jobs, the runner, scripts) use API keys. The
[laptop install](/docs/getting-started/quickstart) and the
[all-in-one container](./all-in-one) are single-user shapes and have no sign-in.

## What you need

- A running stack, reached over TLS on port 443 the way its page's "Reach it
  from outside" section sets up. The console's redirect URI and the CLI's TLS
  rule both assume it. On Kubernetes the chart refuses an Ingress while
  authentication is off, so the Ingress and the values below go into one
  upgrade. For an evaluation on one machine over plain HTTP,
  `http://localhost:7234` works too.
- An OIDC provider you control: Keycloak, Okta, Auth0, Dex, or any server that
  supports OIDC discovery. You need three values from it: the **issuer URL**
  (for example `https://auth.example.com/realms/main`; it must be `https`, since
  the server fetches the provider's signing keys from it, and the server refuses
  a plain-HTTP issuer at boot unless it is on `localhost`), the **audience**
  your provider stamps on access tokens minted for Stigmer (usually configured
  in the provider as an "API" or "resource server" entry), and the **client ID**
  of the console client you register in the first step. For the desktop app, the
  client ID of a second, native client (the last step).

Every setting on this page is one line in the file your shape already uses,
`.env` for Compose and your values file for the chart:

| Setting               | Docker Compose (`.env`)          | Kubernetes (values file)             |
| --------------------- | -------------------------------- | ------------------------------------ |
| Issuer                | `STIGMER_OIDC_ISSUER`            | `server.oidc.issuer`                 |
| Audience              | `STIGMER_OIDC_AUDIENCE`          | `server.oidc.audience`               |
| Console client ID     | `STIGMER_OIDC_CONSOLE_CLIENT_ID` | `server.oidc.consoleClientId`        |
| Desktop app client ID | `STIGMER_OIDC_NATIVE_CLIENT_ID`  | `server.oidc.nativeClientId`         |
| The runner's API key  | `STIGMER_TOKEN`                  | `runner.stigmerToken.existingSecret` |
| Operator email        | `STIGMER_OPERATOR_EMAIL`         | `server.operator.email`              |

On Kubernetes the runner's key lives in a Secret whose key is `STIGMER_TOKEN`,
and the value names that Secret.

## Turn authentication on

<Steps>

### Register the console with your OIDC provider

Create a client (an "app") for the web console. Every provider names these
settings a little differently; this is what each one must be:

- **Client type: public, using PKCE, with no client secret.** The console runs
  in the browser and cannot keep a secret. In Keycloak this is a client with
  "Client authentication" off; in Auth0 a "Single Page Application"; in Okta a
  "Single-Page App"; in Dex a public client.
- **Redirect URI**: `https://stigmer.example.com/auth/callback`, your console's
  address plus `/auth/callback`. For an evaluation over plain HTTP,
  `http://localhost:7234/auth/callback`.
- **Post-logout redirect URI**: `https://stigmer.example.com/login`.
- **Allowed web origins**: `https://stigmer.example.com`. The browser calls your
  provider's token endpoint directly, so your provider must allow that origin.
  Keycloak calls this "Web origins"; Auth0 "Allowed Web Origins"; Okta "Trusted
  Origins"; Dex `allowedOrigins`.
- **Refresh tokens allowed**: the console asks for `offline_access` so it can
  renew your sign-in without asking you again. Without a refresh token the
  console signs you in again when the token expires.
- **The access token carries your audience**: the server checks that the token
  it receives names your audience. Auth0 and Okta do this when you request the
  API you configured; Keycloak needs an **Audience mapper** on the console
  client that adds the audience to the access token. Dex has no audience mapper
  and stamps the token with the client ID, so on a Dex install the audience
  **is** the client ID.

The issuer URL must be one address that both the browser and the server
container resolve. `localhost` is a different machine to each of them, so a
provider on the same host as the stack needs a hostname or the host's address in
its issuer, never `localhost`.

Copy the client ID your provider shows you. It is a public identifier, not a
secret.

### Set the issuer

<Tabs items={["Docker Compose", "Kubernetes"]} groupId="self-hosting-shape" persist>
<Tab value="Docker Compose">

Three lines in `.env`:

```bash
# .env
STIGMER_OIDC_ISSUER=https://auth.example.com/realms/main
STIGMER_OIDC_AUDIENCE=https://stigmer.example.com
STIGMER_OIDC_CONSOLE_CLIENT_ID=stigmer-console
```

```bash
docker compose up -d
```

Compose recreates the services whose settings changed.

</Tab>
<Tab value="Kubernetes">

Add the three values to your values file, with the `ingress` lines from
[Reach it from outside the cluster, signed in](./kubernetes#reach-it-from-outside-the-cluster-signed-in)
if you are adding the Ingress now, and upgrade:

```yaml no-validate="Helm values, not a Stigmer resource"
server:
  oidc:
    issuer: https://auth.example.com/realms/main
    audience: https://stigmer.example.com
    consoleClientId: stigmer-console
```

```bash
helm upgrade stigmer oci://ghcr.io/stigmer/charts/stigmer \
  --namespace stigmer \
  -f values.yaml \
  --wait
```

The pod is recreated with the server alone. The runner needs its own API key,
and only someone signed in can create one, so it starts once you give it that
key below; the upgrade's notes say so. Start your port-forward again afterwards.

</Tab>
</Tabs>

The issuer and the audience go together: the server refuses to boot on one
without the other rather than serve unauthenticated. The client ID is the one
value it tolerates missing: the server boots, logs a warning, and the console
tells anyone who opens it which variable to set.

### Check the server's answer

Before you open a browser, ask the server what the console will read. It
publishes its sign-in settings at `/config.json`, the one file the console
fetches before it renders anything:

```bash
curl -s https://stigmer.example.com/config.json
```

Through a port-forward, the address is `http://localhost:7234/config.json`. With
authentication on, the answer names your provider:

```json
{
  "authMode": "oidc",
  "oidcIssuer": "https://auth.example.com/realms/main",
  "oidcClientId": "stigmer-console",
  "oidcAudience": "https://stigmer.example.com"
}
```

`"authMode": "disabled"` means the values never reached the server: check the
file you edited and that the service was recreated.

### Sign in

Open the console. It sends you to your provider to sign in and brings you back.
The first time, the server creates your Identity Account from the profile your
provider publishes, and you land in the server's one Organization, which it made
at its first start. If your email matches the operator email you set, you own
it; the server trusts that email exactly as your provider asserts it, so use a
provider that verifies email addresses. Sign in as the operator first: the first
person your provider lets in before the operator becomes an administrator, and
everyone else joins as a member. With no operator email set, the first person to
sign in owns the Organization.

### Link people to sign-up

To send newcomers straight to your provider's create-account screen, link them
to `https://stigmer.example.com/login?signup=1`. The console asks your provider
for that screen with the standard `prompt=create` request when the provider's
discovery document lists `create` among its `prompt_values_supported`; any other
provider shows its ordinary sign-in, from which people can still register if it
allows them to. Someone already signed in lands in the console.

A provider that ignores the standard and reads its own hint instead can be given
that hint when you build the console as its own container:
`NEXT_PUBLIC_OIDC_SIGNUP_PARAMS` takes the extra parameters as a query string,
and the console refuses one that names a parameter of the sign-in flow itself,
such as `client_id` or `redirect_uri`.

### Create the keys

Open **Settings → API Keys** and choose **New API key**. Create one named
`runner` with expiration **Never**: it is a long-lived credential, and a key
that expires stops authenticating on that day. Create a second one for your own
CLI. Each key is shown exactly once; the server stores only a hash and cannot
show it again.

Create keys after you sign in. A key created while the server still trusted
everyone is refused once authentication is on, and the refusal says so: the CLI
prints that the key was created before sign-in was turned on, and asks you to
sign in and create a new one.

### Give the runner its key

<Tabs items={["Docker Compose", "Kubernetes"]} groupId="self-hosting-shape" persist>
<Tab value="Docker Compose">

One line in `.env`:

```bash
# .env
STIGMER_TOKEN=stk_...
```

```bash
docker compose up -d
```

Compose recreates the services whose settings changed.

</Tab>
<Tab value="Kubernetes">

Put the key in a Secret:

```bash
kubectl -n stigmer create secret generic stigmer-runner-token \
  --from-literal=STIGMER_TOKEN=stk_...
```

Name it in your values file and upgrade with the same command as before. The pod
is recreated with the runner beside the server:

```yaml no-validate="Helm values, not a Stigmer resource"
runner:
  stigmerToken:
    existingSecret: stigmer-runner-token
```

Start your port-forward again afterwards; it stops with the pod.

</Tab>
</Tabs>

The runner's key is its own credential. It does not decide whose runs the runner
serves or who is recorded as running them; the next section says how a run is
attributed.

### Point the CLI at the stack

Add the stack as a named backend, switch to it, sign in, and point it at your
Organization:

```bash
stigmer config backend add prod --endpoint stigmer.example.com:443
stigmer config backend use prod
stigmer auth login
stigmer config context set --org <your-org-slug>
```

`stigmer auth login` signs you in through your provider, once you have
registered the client for installed apps
([Let the desktop app sign in](#let-the-desktop-app-sign-in)). Until then, or
for a script, give the backend your own key instead: `--api-key stk_...` on
`config backend add`.

Port 443 is the one port the CLI dials with TLS. A named backend keeps its own
sign-in or key, so switching between this stack, your laptop and Stigmer Cloud
stays one command. The context command checks, with your credential, that you
belong to the Organization before it saves it.

</Steps>

## What changes

From the boot that read the issuer, every request needs a credential:

- **People** send an access token from your OIDC provider. The server verifies
  it against the issuer's published keys and checks the audience, then resolves
  the token to that person's Identity Account. The account is created at their
  first sign-in through the console, or the first time they run
  `STIGMER_API_KEY=<oidc-access-token> stigmer auth whoami`; the command says
  when it did.
- **Machines** send an API key (`stk_...`) the same way, as a bearer token.
  Settings → API Keys and `stigmer apikey create` mint them; deleting a key
  revokes it immediately, and a key with an expiration stops working on that
  date.
- **Your product's users** can reach Stigmer through
  [minted user tokens](/docs/guides/authentication/product-users): an admin
  creates an admin service account and its API key and sets the embedding
  settings under Settings → Embedding, and your backend uses the key to mint a
  15-minute token per user. The server signs those tokens with
  `STIGMER_PLATFORM_TOKEN_KEY` when you set it, or with a key it generates into
  its data directory. A server without an issuer refuses to mint them.
- **Roles decide what a signed-in person may do.** Every Organization has four
  roles: owner, admin, member and viewer. Owners and admins manage the
  Organization's Agents, Skills and Plugins and its members. Members start
  conversations with what is shared with the Organization, create Agents while
  the Organization allows it, and keep their own Sessions, vault and API keys;
  shared vaults are the admins' to create. Viewers see what is shared and cannot
  start conversations. An Agent or Skill marked Private shows up in the library
  and opens on its page only for the person who created it and the
  Organization's admins, whether it is opened by ID or by name
  (`stigmer get agent acme/helper` answers the same as the page does). Nobody
  reads another person's conversations, API keys or vault, admins included, and
  no saved key is ever shown again, even to its owner. These are the same rules
  Stigmer Cloud enforces, so an Agent behaves the same way wherever it runs.
- **Nothing is readable outside its Organization.** There is no public
  visibility level: a write that asks for one is refused.
- **Runs belong to the person who started them, whoever's key the runner
  holds.** For each run, the server gives the runner a credential for that run
  alone, and everything the runner does for it, including the Sessions and runs
  it creates, the status it reports and the memories its Agent proposes with
  `remember`, is recorded as that person. Listing a plugin's MCP server tools
  works the same way: the runner reads the server's credentials as the person
  who asked for the listing. A run that was already in flight when you turned
  authentication on belongs to no signed-in person and stops with a message
  saying so; start it again while signed in. A run's credential is written into
  the run's Temporal history and stays valid for ten minutes after the run ends,
  so protect Temporal the way you protect the database. The Helm chart's bundled
  Temporal admits only the Stigmer pod; a Temporal of your own can require TLS,
  mutual TLS or an API key, and both the server and the runner can present them
  ([Bring your own Postgres and Temporal](./kubernetes#bring-your-own-postgres-and-temporal)).
  To end a run's credential, end the run: cancel it and the credential is dead
  ten minutes later. To end every run's credential at once, rotate
  `STIGMER_RUNNER_TOKEN_KEY`; every run in flight stops and must be started
  again.
- Requests without a credential are rejected with
  `authentication token missing`. Requests with a bad credential get a specific
  reason (`token has expired`, `token signature verification failed`, and so
  on).
- Two things stay reachable without a credential on purpose: the public
  `getServerInfo` read your console and CLI use before login, and the standard
  gRPC health service (`grpc.health.v1.Health`), so Kubernetes `grpc:` readiness
  and liveness probes keep working exactly as before.

### What the roles mean day to day

- A member cannot create an Agent or Skill until an owner or admin promotes them
  under **Settings → Members**. New arrivals are members.
- The server does not stop a signed-in person from creating another
  Organization; whoever creates one owns it.
- A script that presents an access token but has never signed in through the
  console or run `stigmer auth whoami` has no Identity Account yet, and cannot
  create anything until it does.
- Routines you created before turning authentication on belong to no signed-in
  person. Each pauses at its next run and says why; recreate it while signed in.
- Memories recorded before you turned authentication on belong to no signed-in
  person either, and stay hidden.
- An admin's lists show the Organization's Agents and Skills, not other members'
  Sessions, vaults or API keys.

## Let the desktop app sign in

The desktop app asks the server it points at how to sign in, before anyone signs
in, and the server answers with your issuer, your audience and the client the
app should use. Nothing about your provider is built into the app: a person
chooses **Use another server**, types your address, and signs in through your
provider in their own browser.

The app needs its own client, separate from the console's. Register a second
client with your provider:

- **Client type: public native app, using PKCE, with no client secret.** In
  Keycloak a client with "Client authentication" off; in Auth0 a "Native"
  application; in Okta a "Native App"; in Dex a public client.
- **Redirect URIs**: `stigmer://auth/callback`, and for the CLI and builds that
  sign in through a local port, `http://127.0.0.1:17234/auth/callback`,
  `http://127.0.0.1:17235/auth/callback` and
  `http://127.0.0.1:17236/auth/callback`.
- **Refresh tokens allowed**, so the app keeps people signed in.
- **The access token carries your audience**, as for the console.

Then set its client ID, `STIGMER_OIDC_NATIVE_CLIENT_ID` in `.env` or
`server.oidc.nativeClientId` in your values file, and restart or upgrade as
before. Until you do, the server logs a warning at start, and the app tells
people this server has not been set up for it.

The app connects only over `https` to another machine, so give people the
address your TLS setup serves, `https://stigmer.example.com`. It keeps sign-in
keys in the system keychain.

### The CLI signs in through the same client

`stigmer auth login` asks the server the same question and signs in through the
same client, returning to the first free of the three `http://127.0.0.1` ports
above. It keeps the sign-in in its config file beside the issuer it came from,
and refreshes it there.

Where no browser can open on the person's machine (an SSH session, a remote
sandbox, a coding agent's container), `stigmer auth login --device` prints an
address and a short code to type on any device, the OAuth device grant. It works
when your provider publishes a `device_authorization_endpoint` in its discovery
document and allows that grant for the native client: in Auth0, the Device Code
grant on the Native application; in Keycloak, "OAuth 2.0 Device Authorization
Grant" on the client; in Okta, the Device Authorization grant type. Without it,
the CLI says so and the person signs in with a browser or a key.

The CLI signs in only at a provider on your server's own site, the same
registrable domain or both on one machine, unless the person passes
`--trust-provider`. A server can name another site's provider to collect tokens
that site's servers accept, so the CLI refuses it, naming both hosts, until the
person runs `stigmer auth login --trust-provider`.

### Where the app's agents run

The app carries a runner of its own, which runs the Agents of the conversations
started in it, on the person's computer. That runner listens only on each
conversation's own queue, so it receives work only when your server routes runs
per conversation, `STIGMER_ACTIVITY_ROUTING=session`.

On the default, `global`, the server puts every run on its one shared queue
([How a run reaches the runner](./runners#how-a-run-reaches-the-runner)), and
your stack's runner answers the app's conversations on the server. They work,
but nothing runs on the person's computer, and the app still shows its own
runner in the sidebar as working. A server with no runner of its own leaves them
unanswered.

`session` sends every conversation's runs to that conversation's own queue,
including the console's. A conversation started in the console then waits for a
runner the server provisions for it
([A runner per Session](./runners#a-runner-per-session)); without a provisioner
it gets none. So keep the default unless everyone works from the desktop app.
The server saying which it does, so the app can say where Agents run, is tracked
as [stigmer#2861](https://github.com/stigmer/stigmer/issues/2861).

## What still needs an API key

The `stigmer` CLI cannot sign in to a self-hosted server through your OIDC
provider yet. Point the CLI at the stack with an API key, as the last step
shows. If you hold an access token from your provider, the CLI accepts it in
place of a key: `STIGMER_API_KEY=<oidc-access-token>` in front of
`stigmer auth whoami` creates your Identity Account if you have never signed in,
and in front of `stigmer apikey create --name ci` mints a key without the
console. How you obtain that token is your provider's business. Sign-in for the
CLI is tracked as
[stigmer#1077](https://github.com/stigmer/stigmer/issues/1077).
