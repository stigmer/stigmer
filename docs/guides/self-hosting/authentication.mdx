---
title: Enable authentication
description:
  Turn on authentication for a self-hosted Stigmer server with your own OIDC
  identity provider and API keys, and let the web console sign in through it.
---

By default, a self-hosted Stigmer server trusts every request. That is the right
posture for a single-user machine, and the wrong one the moment the port is
reachable by anyone else. This guide turns authentication on: people sign in
through your identity provider, and machines (CI jobs, the runner, scripts) use
API keys.

## What you need

- A running self-hosted stack
  ([Docker Compose](/docs/guides/self-hosting/docker-compose)).
- An OIDC identity provider you control — Keycloak, Okta, Auth0, Dex, or any
  server that supports OIDC discovery. You need two values from it:
  - the **issuer URL** (for example `https://auth.example.com/realms/main`)
  - the **audience** your provider stamps on access tokens minted for Stigmer
    (you usually configure this in the provider as an "API" or "resource server"
    entry)

## Mint your API keys first

API keys are created through the server itself, so mint the keys you know you
will need — one for the runner, one for CI — **before** turning authentication
on, while the server still trusts you:

```bash
stigmer apikey create --name runner
stigmer apikey create --name ci
```

Each command prints the key exactly once. Save them somewhere safe — the server
stores only a hash and cannot show them again.

You can also mint keys later with an access token from your identity provider:

```bash
STIGMER_API_KEY=<oidc-access-token> stigmer apikey create --name another
```

## Turn authentication on

Set two environment variables on the server and restart it. In the Docker
Compose stack, add them to the `server` service:

```yaml no-validate="docker-compose service fragment, not a Stigmer resource"
services:
  server:
    environment:
      STIGMER_OIDC_ISSUER: "https://auth.example.com/realms/main"
      STIGMER_OIDC_AUDIENCE: "https://stigmer.example.com/"
```

Both must be set together — the server refuses to boot on a half configuration
rather than silently serving unauthenticated.

Give the runner its API key in the same file:

```yaml no-validate="docker-compose service fragment, not a Stigmer resource"
services:
  runner:
    environment:
      STIGMER_TOKEN: "stk_..." # the key you minted for the runner
```

## What changes

From the next boot, every request needs a credential:

- **People** send an access token from your identity provider. The server
  verifies it against the issuer's published keys and checks the audience, then
  resolves the token to that person's Identity Account. The account is created
  the first time that person runs
  `STIGMER_API_KEY=<oidc-access-token> stigmer auth whoami`; the command says
  when it did.
- **Machines** send an API key (`stk_...`) the same way — as a bearer token.
  `stigmer apikey create` mints them; deleting a key revokes it immediately.
- **Roles decide what a signed-in person may do.** Every Organization has four
  roles: owner, admin, member and viewer. Owners and admins manage the
  organization's Agents, Workflows, Skills and MCP servers and its members.
  Members use what is shared with the organization and create their own
  Sessions, Environments and API keys. Viewers only read what is shared. An
  Agent, Workflow or Skill marked Private shows up in the library and opens on
  its page only for the person who created it and the organization's admins.
  Nobody reads another person's conversations, API keys or Environments — admins
  included. These are the same rules Stigmer Cloud enforces, so an Agent behaves
  the same way wherever it runs.
- **If authentication was already on before this release, roles are assigned at
  the first start.** People who signed in under an earlier release keep what
  they had: whoever created an Organization owns it, whoever created an Agent,
  Workflow, Skill, MCP server, Environment or Schedule in it is an admin there,
  the `STIGMER_OPERATOR_EMAIL` holder is an admin everywhere, and everyone else
  is a member. This happens once; from then on roles change only when an owner
  or admin changes them.
- **Anything marked Public before this release stays readable by every signed-in
  person**, including people outside its Organization. New Public marks are
  refused on a self-hosted server; an admin can set an existing one back to
  Organization from its page.
- Requests without a credential are rejected with
  `authentication token missing`. Requests with a bad credential get a specific
  reason (`token has expired`, `token signature verification failed`, and so
  on).
- Two things stay reachable without a credential on purpose: the public
  `getServerInfo` read your console and CLI use before login, and the standard
  gRPC health service (`grpc.health.v1.Health`), so Kubernetes `grpc:` readiness
  and liveness probes keep working exactly as before.
- **The web console signs in through your provider.** Register it as a client
  and tell the server its ID; see
  [Sign in to the console](#sign-in-to-the-console).

Point your CLI at the stack as a named backend with its key:

```bash
stigmer config backend add prod --endpoint stigmer.example.com:7234 --api-key stk_...
stigmer config backend use prod
```

## Sign in to the console

The web console the server serves signs in through your identity provider, with
the browser's standard Authorization Code flow (PKCE). Two steps: register the
console with your provider, then tell the server which client you registered.

### Register the console with your identity provider

Create a client (an "application") for the console. Every provider names these
settings a little differently; this is what each one must be:

- **Client type: public, using PKCE, with no client secret.** The console runs
  in the browser and cannot keep a secret. In Keycloak this is a client with
  "Client authentication" off; in Auth0 a "Single Page Application"; in Okta a
  "Single-Page App".
- **Redirect URI**: `https://stigmer.example.com/auth/callback` — your console's
  address plus `/auth/callback`. For a laptop evaluation over plain HTTP,
  `http://localhost:7234/auth/callback`.
- **Post-logout redirect URI**: `https://stigmer.example.com/login`.
- **Allowed web origins**: `https://stigmer.example.com`. The browser calls your
  provider's token endpoint directly, so your provider must allow that origin.
  Keycloak calls this "Web origins"; Auth0 "Allowed Web Origins"; Okta "Trusted
  Origins".
- **Refresh tokens allowed**: the console asks for `offline_access` so it can
  renew your sign-in without asking you again. Without a refresh token the
  console signs you in again when the token expires.
- **The access token carries your audience**: the server checks that the token
  it receives names `STIGMER_OIDC_AUDIENCE`. Auth0 and Okta do this when you
  request the API you configured; Keycloak needs an **Audience mapper** on the
  console client that adds the audience to the access token.

Copy the client ID your provider shows you. It is a public identifier, not a
secret.

### Tell the server

Add the client ID beside the two variables you already set:

```yaml no-validate="docker-compose service fragment, not a Stigmer resource"
services:
  server:
    environment:
      STIGMER_OIDC_ISSUER: "https://auth.example.com/realms/main"
      STIGMER_OIDC_AUDIENCE: "https://stigmer.example.com/"
      STIGMER_OIDC_CONSOLE_CLIENT_ID: "stigmer-console"
```

Restart the server. The variable is optional: a server with the issuer set but
no console client still boots, logs a warning, and the console tells anyone who
opens it which variable to set.

### What you see

Open the console. It sends you to your provider to sign in and brings you back.
The first time, the server creates your Identity Account from the profile your
provider publishes, and the console asks you to create your first Organization.
The person who creates an organization is recorded as its owner; people who sign
in afterwards join it as members. Owners and admins change roles under Settings
→ Members. If you set `STIGMER_OPERATOR_EMAIL`, the person whose provider email
matches it becomes an administrator of every Organization the first time they
sign in. The server trusts that email exactly as your provider asserts it, so
use a provider that verifies email addresses. Sign out from the console's
account menu; you land on the console's sign-in page.

What the roles mean day to day:

- A member cannot create an Agent, Workflow or Skill until an owner or admin
  promotes them under Settings → Members. New arrivals are members.
- The server does not stop a signed-in person from creating another
  Organization; whoever creates one owns it.
- A script that presents an access token but has never signed in through the
  console or run `stigmer auth whoami` has no Identity Account yet, and cannot
  create anything until it does.
- Schedules you created before turning authentication on belong to no signed-in
  person. Each pauses at its next run and says why; recreate it while signed in.
- Memories recorded before you turned authentication on belong to no signed-in
  person either, and stay hidden.
- An admin's lists show the organization's Agents, Workflows and Skills, not
  other members' Sessions, Environments or API keys.

### What still needs an API key

The `stigmer` CLI and the desktop app cannot sign in to a self-hosted server
through your identity provider yet. Point the CLI at the stack with an API key
as shown above, or pass an access token from your provider as `STIGMER_API_KEY`.
Console-style sign-in for the CLI and the desktop app is tracked as
[stigmer#1077](https://github.com/stigmer/stigmer/issues/1077) and
[stigmer#1080](https://github.com/stigmer/stigmer/issues/1080).
