  Install the complete Stigmer stack on a Kubernetes cluster with one Helm
  chart, reach the console, run a first Agent, then put an Ingress in front and
  turn authentication on. Every setting is a line in your values file.
---

The Helm chart is the Kubernetes shape from [Self-hosting](./overview): the same
four parts as the [Docker Compose stack](./docker-compose), the server with the
web console and one runner in a single pod, with Postgres and a real Temporal
server bundled for one team or pointed at the ones you already run. One rule
holds for the whole page: every setting you change is a line in your values
file. You never edit the chart, and it refuses a value it does not know.

<Callout type="warn">
  **No sign-in until you turn it on.** A fresh install trusts every caller that
  can reach it, like the compose stack. Keep it behind `kubectl port-forward` or
  a private network until you [turn authentication on](./authentication). stdio
  MCP Servers spawn **inside the runner container**: they can reach its
  filesystem and network, not your nodes'.
</Callout>

## What the chart installs

One Deployment whose pod has two containers: the server, which serves the API,
the web console and the artifact file server, and the runner, which executes
Agents and Workflows and holds your LLM key. They share the pod's network and
one artifact disk, the way the compose stack's two containers share one volume,
which is why the chart needs no shared-filesystem storage class. Postgres runs
as a StatefulSet with its own disk and Temporal as a Deployment, both bundled
unless you point the chart at your own.

For a release named `stigmer`, the chart creates four PersistentVolumeClaims.
Three hold durable state: `data-stigmer-postgres-0` (every resource and
execution record, and Temporal's own tables), `stigmer-artifacts` (files
produced by executions) and `stigmer-server-data` (the Skill content store). The
fourth, `stigmer-runner-data`, holds in-flight Session checkpoints so a paused
run survives a pod restart; losing it abandons runs in flight but loses no
durable data. Those three claims, the Secret you create below, and your values
file are a complete backup. [Back up and upgrade your stack](./operations) has
the procedures.

## What you need

- A Kubernetes cluster, 1.27 or newer, with a default storage class. Any storage
  class works: the server and the runner share one pod, so the chart needs no
  shared-filesystem storage.
- `helm` 3 and `kubectl`, pointed at the cluster.
- The Stigmer CLI on your laptop. The
  [local quickstart](/docs/getting-started/local) has the install commands.
- Laptop ports 7234 and 7235 free for the port-forward. If the laptop stack
  runs, stop it first with `stigmer down`; it uses the same ports.
- An LLM provider key if you want Agents to answer. Workflows without Agent
  tasks run without one.

## Install

<Steps>

### Create the Secrets

The chart refuses to install until you name a Secret with two random keys and
the database password. That's deliberate, the way `docker compose up` refuses
without `.env`: the keys you must back up are never generated somewhere you
can't see.

```bash
kubectl create namespace stigmer
kubectl -n stigmer create secret generic stigmer-secrets \
  --from-literal=STIGMER_ENCRYPTION_KEY=$(openssl rand -base64 32) \
  --from-literal=STIGMER_RUNNER_TOKEN_KEY=$(openssl rand -base64 32) \
  --from-literal=POSTGRES_PASSWORD=$(openssl rand -hex 24)
```

`STIGMER_ENCRYPTION_KEY` encrypts secret values at rest.
`STIGMER_RUNNER_TOKEN_KEY` signs the tokens the runner authenticates with. Keep
this Secret with your backups: without the encryption key, every encrypted value
in the database is unreadable. Once you turn on authentication, the Secret may
also carry `STIGMER_PLATFORM_TOKEN_KEY`, which signs the tokens PlatformClients
mint; it is optional, and the server generates one on its volume without it.

If you have an LLM provider key, put it in a second Secret now, so Agents can
answer from the first run:

```bash
kubectl -n stigmer create secret generic stigmer-llm-keys \
  --from-literal=ANTHROPIC_API_KEY=sk-ant-...
```

Without it the stack still serves the console, the API and LLM-free Workflow
executions; Agent runs fail at the LLM call. You can add the key later: create
this Secret, add its line to your values file, and run the `helm upgrade` shown
further down this page.

### Write your values file and install

Create a file called `values.yaml`. It names the Secrets you just created and
never holds a key itself, so it is safe to keep in version control:

```yaml no-validate="Helm values, not a Stigmer resource"
secrets:
  existingSecret: stigmer-secrets
runner:
  llm:
    existingSecret: stigmer-llm-keys
server:
  operator:
    email: you@example.com
```

Leave the `runner.llm` lines out if you created no LLM Secret. The operator
email is optional too, and worth setting now: it's stamped on what you create,
and when you later turn authentication on, the person who signs in with this
email becomes an administrator of every Organization. Then install:

```bash
helm install stigmer oci://ghcr.io/stigmer/charts/stigmer \
  --namespace stigmer \
  -f values.yaml \
  --wait
```

The first install pulls two images, starts Postgres, lets Temporal create its
schema, and waits for the server to answer. The chart's notes print what to do
next.

<Callout type="info">
  Back up `values.yaml` beside the Secret. Every change on this page is a line
  added to it; with the Secret and the three durable claims, it is everything a
  reinstall needs.
</Callout>

### Open the console

```bash
kubectl -n stigmer port-forward svc/stigmer 7234:7234 7235:7235
```

Open [http://localhost:7234](http://localhost:7234). The console asks you to
create an Organization: a fresh install has none yet. Leave it there; the next
steps bootstrap one from the CLI. Download links the platform mints point at
port 7235, which the same port-forward carries.

Leave the port-forward running in its terminal. It stops whenever the pod is
recreated, which every `helm upgrade` that changes a setting does; start it
again with the same command.

### Connect the CLI

Through the port-forward, the cluster's server answers on your laptop's
port 7234. Tell the CLI where it is, as a named backend, then switch to it:

```bash
stigmer config backend add mycluster --endpoint localhost:7234
stigmer config backend use mycluster
```

A named backend keeps its own address and, later, its own API key, so switching
between this cluster, your laptop and Stigmer Cloud is one command. The
[`stigmer config`](/docs/cli/commands/config) reference lists every backend
command. Every command on this page lands in the Organization the next step
creates, the CLI's default; `--org <slug>` on a command, or `STIGMER_ORG_ID` set
for the process, points it at another Organization.

### Bootstrap the backend

Bootstrap the backend. It creates the `stigmer` Organization and installs the
official marketplace's default Plugins into it — the same bootstrap `stigmer up`
performs on your laptop. Today the default Plugin is the `assistant` Agent.
`stigmer` is also the Organization the CLI uses when you don't name one, so
every `apply`, `run` and `get` on this page lands where the console looks. The
command is safe to run again; a ready backend reports every default as up to
date. The first run for a CLI version fetches the catalogue with `npm`, so run
it from a machine with `npm` installed and the npm registry reachable:

```bash
stigmer bootstrap
```

The command prints what it did: the Organization `created`, then one line per
default Plugin, `assistant` reading `installed`. Reload the console: it opens on
the workbench, with the `assistant` Agent already there. The
[`stigmer bootstrap`](/docs/cli/commands/bootstrap) reference has the flags;
[Organizations](/docs/concepts/organizations) explains how more than one fits
together.

<Callout type="warn">
  **Run this step before you turn authentication on.** The default Plugins are
  platform-managed content (Public, with platform labels), and a self-hosted
  server with authentication on accepts platform-managed content from nobody: a
  cluster that turned authentication on first can't be bootstrapped, and a
  bootstrapped cluster can't take a newer catalogue
  ([stigmer#1192](https://github.com/stigmer/stigmer/issues/1192)). A re-run
  with the same CLI version stays harmless.
</Callout>

### Run your first Agent

Create a file called `agent.yaml`:

```yaml
apiVersion: agentic.stigmer.ai/v1
kind: Agent
metadata:
  name: my-first-agent
spec:
  instructions: |
    You are a helpful assistant. Answer questions clearly
    and concisely. When you don't know something, say so.
```

Apply it and run it:

```bash
stigmer apply -f agent.yaml
stigmer run my-first-agent -m "What can you help me with?"
```

The Agent responds in your terminal. The run traveled from the CLI through the
port-forward to the server, through Temporal, and executed inside the runner
container on your cluster: the whole stack, end to end. `stigmer list agents`
shows both: yours, and the `assistant` Agent the bootstrap installed.

</Steps>

## Reach it from outside the cluster

To serve your team, turn on the Ingress with two hostnames: one for the API and
console, one for artifact downloads. They are separate listeners and cannot
share a host. Add to `values.yaml`:

```yaml no-validate="Helm values, not a Stigmer resource"
ingress:
  enabled: true
  className: nginx
  api:
    host: stigmer.example.com
    tlsSecretName: stigmer-api-tls
    annotations:
      nginx.ingress.kubernetes.io/backend-protocol: "GRPC"
  artifacts:
    host: artifacts.stigmer.example.com
    tlsSecretName: stigmer-artifacts-tls
```

```bash
helm upgrade stigmer oci://ghcr.io/stigmer/charts/stigmer \
  --namespace stigmer \
  -f values.yaml \
  --wait
```

The CLI and SDKs speak gRPC, which needs HTTP/2 all the way to the server. On
ingress-nginx that is the preceding `backend-protocol: "GRPC"` annotation;
without it the console works and the CLI does not. Set `tlsSecretName` on both
hosts: the URLs the server mints for downloads and Skill transfers follow each
host's scheme, and a host without a TLS Secret gets plain-HTTP links.

Point your CLI at the API host on port 443, which is the one port the CLI dials
with TLS:

```bash
stigmer config backend add prod --endpoint stigmer.example.com:443
stigmer config backend use prod
```

The console needs nothing: it reads its own origin. If you front the Service
some other way than the chart's Ingress, `server.publicUrl` and
`server.artifactPublicUrl` are the same two settings the compose page sets in
`.env`.

## Turn authentication on

Authentication is on when the issuer, the audience and the console's client ID
are in your values file:

```yaml no-validate="Helm values, not a Stigmer resource"
server:
  oidc:
    issuer: https://auth.example.com/realms/main
    audience: https://stigmer.example.com
    consoleClientId: stigmer-console
runner:
  stigmerToken:
    existingSecret: stigmer-runner-token
```

The chart asks for one more value beside them,
`runner.stigmerToken.existingSecret`: a Secret holding an API key for the
runner. It refuses the issuer without it, so turning authentication on is an
upgrade you prepare, not a value you flip. The
[authentication guide](./authentication) says where that key comes from, what to
register with your OIDC provider, and the order of the steps; follow it from
here. Once authentication is on, the person whose provider email matches
`server.operator.email` becomes an administrator of every Organization.

## Bring your own Postgres and Temporal

The chart bundles both, on purpose: one cluster, one backup story. If your team
already runs them, point the chart at yours instead:

```yaml no-validate="Helm values, not a Stigmer resource"
postgres:
  enabled: false
externalDatabase:
  host: db.internal.example.com
  user: stigmer
  database: stigmer
  existingSecret: stigmer-db
  passwordKey: password
temporal:
  enabled: false
externalTemporal:
  hostPort: temporal-frontend.temporal.svc.cluster.local:7233
  namespace: default
```

Decide this before your first install: moving data from the bundled Postgres to
yours later is a database restore, not a value change. The database password
never appears in a rendered manifest; the server assembles its connection string
inside the container. If Temporal stays bundled while Postgres is yours,
Temporal creates its two databases on your instance at first start and needs a
user with `CREATE DATABASE`.

## Back up, upgrade, uninstall

A complete backup is the three durable claims, the Secret, and your values file.
`helm upgrade` to a new chart version with the same values file moves the whole
stack to that Stigmer version: the chart version is the Stigmer version, and the
images move with it. The pod is recreated, so there is a short interruption, and
in-flight Agent turns resume from their Temporal checkpoints. `helm uninstall`
removes the workload and **leaves every claim in place**; installing again with
the same release name and values file picks them up.
[Back up and upgrade your stack](./operations) has each procedure in full.

## Every setting

The chart documents every value, with the reason behind it, in its values and
its README. Read both from the registry:

```bash
helm show values oci://ghcr.io/stigmer/charts/stigmer
helm show readme oci://ghcr.io/stigmer/charts/stigmer
```

Your values file holds only the lines you change. The chart refuses a misspelled
or unknown value instead of ignoring it.

## Next step

Your stack is running on the cluster, and right now anyone who can reach its
Service or its Ingress has full control of it. Before your team uses it, turn
authentication on with your OIDC provider.
