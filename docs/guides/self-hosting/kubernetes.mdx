---
title: Self-host on Kubernetes
description:
  Install the Stigmer operator, declare one Stigmer resource, and the operator
  runs the whole stack on your cluster, from the database and Temporal to
  sign-in, backups and a sandbox for each Session. Status says in words what is
  ready.
---

On Kubernetes, Stigmer runs through the Stigmer operator. You install the
operator once per cluster with Helm, then declare what you want in one `Stigmer`
resource: a hostname, the owner's email, a bucket, how Agents run. The operator
runs the rest, the same parts as the [Docker Compose stack](./docker-compose),
and keeps them converged. It mints the server's keys, runs Postgres and
Temporal, brings up the server with the web console and its runner, and, as you
declare them, a front door with its certificate, a bundled sign-in, backups to
your bucket and a sandbox of its own for each Session. `kubectl get stigmer`
says in words what is ready and what it is waiting for.

<Callout type="warn">
  **No sign-in until you give it a front door.** An install without
  `spec.ingress` signs nobody in, and every caller is its owner, which is safe
  only while it is reached from inside the cluster. Keep it behind `kubectl
  port-forward` until you [put it behind a
  hostname](#reach-it-at-a-hostname-signed-in), which brings sign-in with it.
</Callout>

## What you need

- A Kubernetes cluster, 1.30 or newer, with a default storage class. GKE 1.37
  marks none default; mark one yourself, for example
  `kubectl patch storageclass standard-rwo -p '{"metadata":{"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'`.
- `helm` 3 and `kubectl`, pointed at the cluster.
- The Stigmer CLI on your laptop. The
  [quickstart](/docs/getting-started/quickstart) has the install commands.
- Laptop ports 7234 and 7235 free for the port-forward. If the laptop stack
  runs, stop it first with `stigmer down`; it uses the same ports.
- An LLM provider key, so Agents can answer.

Some declarations need more from the cluster, and the status names what is
missing: [cert-manager](https://cert-manager.io) for backups and for a
certificate it issues, a network plugin that enforces NetworkPolicies for the
fences around the database, Temporal and each sandbox, and, for Agent Substrate,
the pod-certificate APIs described [below](#a-sandbox-for-each-session). A
hostname needs an ingress controller, such as Traefik, or a Gateway, and
cert-manager with an issuer for its certificate; the operator installs neither.

## Install

<Steps>

### Install the operator

```bash
helm install stigmer-operator oci://ghcr.io/stigmer/charts/stigmer-operator \
  --namespace stigmer-system --create-namespace
```

The chart installs the operator and the `Stigmer` definition. It holds
cluster-wide rights because it installs what an install needs when the cluster
has none: CloudNativePG for the database, and later its backup plugin,
agent-sandbox or Agent Substrate. It removes only what it installed.
`helm show readme oci://ghcr.io/stigmer/charts/stigmer-operator` lists the
chart's values and the rights it holds.

### Give it your model key

```bash
kubectl create namespace stigmer
kubectl -n stigmer create secret generic anthropic \
  --from-literal=ANTHROPIC_API_KEY=sk-ant-...
```

This Secret is the only one you write. The runner reads the providers' keys from
it (`OPENAI_API_KEY`, `ANTHROPIC_FOUNDRY_API_KEY` and `AWS_BEARER_TOKEN_BEDROCK`
too, when you add them), and the operator mints every key the server needs.

### Declare Stigmer

Create a file called `stigmer.yaml`:

```yaml
apiVersion: stigmer.ai/v1
kind: Stigmer
metadata:
  name: stigmer
  namespace: stigmer
spec:
  owner:
    email: you@example.com
  runner:
    llm:
      secretName: anthropic
```

Apply it and watch the status:

```bash
kubectl apply -f stigmer.yaml
kubectl -n stigmer get stigmer --watch
```

The operator installs CloudNativePG if the cluster has none, creates the
database, brings up Temporal, then the server and its runner, and moves from
`Deploying` to `Ready`. While it works, the message column says what it is
waiting for and names the object; a declaration it cannot carry out is `Refused`
with the field and the next step. `kubectl -n stigmer describe stigmer` shows
every component's standing.

A CloudNativePG someone else installed is used as it is, while its controller
runs. Uninstalling CloudNativePG's Helm chart keeps its definitions, and a
cluster can hold them with nothing running them; the database is then `Refused`
with `PrerequisiteNotRunning`, naming the release that left them. Reinstall
CloudNativePG, or delete its leftover definitions and the operator installs its
own. The backup plugin and agent-sandbox are treated the same way.

The owner is the person who runs this install: everything you create is
attributed to them, and once sign-in is on they own the Organization.

<Callout type="info">
  The operator keeps the server's keys in the Secret `stigmer-keys`. Everything
  Stigmer encrypts is readable only with it, so keep a copy outside the cluster;
  the status says so until you do.
</Callout>

### Open the console

```bash
kubectl -n stigmer port-forward svc/stigmer 7234:7234 7235:7235
```

Open [http://localhost:7234](http://localhost:7234). The console opens straight
into your library. Download links the platform mints point at port 7235, which
the same port-forward carries. Leave the port-forward running in its terminal;
it stops whenever the server's pod is replaced, and the same command starts it
again.

### Connect the CLI

Through the port-forward, the cluster's server answers on your laptop's
port 7234. Tell the CLI where it is, as a named backend, and switch to it:

```bash
stigmer config backend add mycluster --endpoint localhost:7234
stigmer config backend use mycluster
```

Every `apply`, `run` and `get` on this page now lands where the console looks.
The [`stigmer config`](/docs/cli/commands/config) reference lists every backend
and context command.

### Run your first Agent

Create a file called `agent.yaml`:

```yaml
apiVersion: agentic.stigmer.ai/v1
kind: Agent
metadata:
  name: my-first-agent
spec:
  instructions: |
    You are a helpful assistant. Answer questions clearly
    and concisely. When you don't know something, say so.
```

Apply it and run it:

```bash
stigmer apply -f agent.yaml
stigmer run my-first-agent -m "What can you help me with?"
```

The Agent responds in your terminal. The run traveled from the CLI through the
port-forward to the server, through Temporal, and executed in the runner on your
cluster. Reload the console: your Agent is on the workbench.

</Steps>

## Reach it at a hostname, signed in

A front door gives the install one hostname for everything people reach: the
console at `/`, the API at its own paths, sign-in at `/idp`, and files kept on a
volume at `/artifacts`, all on port 443. Declaring one turns sign-in on: by
default through a sign-in the operator runs beside Stigmer.

```yaml
apiVersion: stigmer.ai/v1
kind: Stigmer
metadata:
  name: stigmer
  namespace: stigmer
spec:
  owner:
    email: you@example.com
  runner:
    llm:
      secretName: anthropic
  ingress:
    hostname: stigmer.example.com
    tls:
      issuer:
        name: letsencrypt
        kind: ClusterIssuer
  identity:
    bundled:
      signUp:
        emailDomains: [example.com]
      smtp:
        host: smtp.example.com
        from: stigmer@example.com
        secretName: mail
        starttls: true
```

Point `stigmer.example.com` at your ingress controller. cert-manager issues the
certificate through the issuer you name, and the front door is `Ready` only once
the certificate is; while DNS is missing, the status says what to point where.
An issuance that failed while DNS or the load balancer was still settling is
retried on cert-manager's own backoff, which reaches an hour;
`cmctl renew stigmer-tls -n stigmer` retries it at once. To keep a certificate
yourself, name its Secret in `tls.secretName` instead. On a cluster that runs
Gateway API, `gatewayRef` attaches the routes to your Gateway, whose listener
holds the certificate.

The CLI, the desktop app and the SDKs speak gRPC, which needs HTTP/2 from your
controller to the server. A controller that takes its hint on the Ingress reads
it from `ingress.annotations`; one that reads it from the Service, such as
Traefik, takes it in `ingress.serviceAnnotations`:

```yaml validate-as="Stigmer.ingress"
hostname: stigmer.example.com
className: traefik
serviceAnnotations:
  traefik.ingress.kubernetes.io/service.serversscheme: h2c
tls:
  issuer:
    name: letsencrypt
```

**The owner signs in first.** The bundled sign-in creates the owner's account
with a one-time password; the status names the Secret it is in
(`stigmer-owner-setup`, key `password`). Sign in at
`https://stigmer.example.com` with the owner's email and that password, and set
your own. The Secret goes, and only then does sign-up open, to addresses in the
domains you list, each verified by mail through the SMTP server you name (its
user name and password go in the Secret named by `smtp.secretName`, keys
`username` and `password`). Leave `signUp` out and only the owner signs in.
Whoever signs up joins the owner's Organization and runs Agents on your model
key, which is why sign-up waits for the owner and stays limited to your domains.

The runner starts signed in: the operator provisions its key, so there is no key
to create and no second upgrade. Point your CLI at the hostname on port 443 and
sign in:

```bash
stigmer config backend add prod --endpoint stigmer.example.com:443
stigmer config backend use prod
stigmer auth login
```

The sign-in asks once whether to grant access to the Stigmer desktop app and
CLI; grant it.

**Your own identity provider** replaces the bundled sign-in. Register Stigmer
with it as the [authentication guide](./authentication) describes, then name it:

```yaml validate-as="Stigmer.identity"
oidc:
  issuer: https://auth.example.com/realms/main
  audience: https://stigmer.example.com
  consoleClientId: stigmer-console
  nativeClientId: stigmer-desktop
```

If the server cannot reach the issuer's public address from inside the cluster,
`discoveryUrl` names where it can fetch the issuer's discovery document instead.
If something of yours already authenticates every caller before Stigmer, such as
an authenticating proxy, `server.allowUnauthenticatedExposure: true` exposes the
install with sign-in off, on purpose.

## Bring your own Postgres and Temporal

The operator runs both by default, on purpose: one cluster, one backup story. If
your team already runs them, point the install at yours. The role needs to own
its database, where Stigmer creates its schemas, and its password is read from
the Secret you name:

```yaml validate-as="Stigmer"
database:
  postgresql:
    external:
      host: postgres.databases.svc
      user: stigmer
      database: stigmer
      passwordSecret:
        name: stigmer-db
        key: password
      sslMode: require
temporal:
  external:
    hostPort: temporal-frontend.temporal.svc:7233
    namespace: stigmer
```

Your own Postgres needs your own Temporal: the operator creates Temporal's
databases only on a Postgres it runs. When your Temporal requires authentication
(Temporal Cloud, or a frontend with an authorizer), `temporal.external.tls`
names the Secret with its PEM items and `temporal.external.apiKey` the Secret
with its API key. The bundled sign-in keeps its accounts on the bundled
database, so with your own Postgres people sign in through your own identity
provider. Decide this before the first install: moving data from the bundled
Postgres to yours later is a database restore, not a change to the resource.

## Keep files in a bucket, with backups

Declare a bucket and Stigmer keeps its files there instead of on volumes: what a
run stores beside its record, Files and Skills, each under its own prefix. The
bundled database archives to the same bucket from its first minute, and takes a
full backup on the schedule you set, so the bucket and the keys Secret are a
complete backup.

```bash
kubectl -n stigmer create secret generic bucket \
  --from-literal=ACCESS_KEY_ID=<key id> --from-literal=SECRET_ACCESS_KEY=<secret>
```

```yaml validate-as="Stigmer"
objectStore:
  s3:
    bucket: acme-stigmer
    region: us-east-1
    credentialsSecret:
      name: bucket
database:
  postgresql:
    bundled:
      backup:
        schedule: "0 0 2 * * *"
        retention: 30d
```

Any S3-compatible bucket works for files and backups: AWS S3, Cloudflare R2,
SeaweedFS or MinIO in the cluster, and Google Cloud Storage through its S3 API
with an HMAC key, with `endpoint` naming the service. Agent Substrate's
snapshots are the exception: Cloud Storage's S3 API refuses them, so with that
driver use another store. Only the server and the database hold the bucket's
keys; a runner reads and writes through short-lived URLs the server signs.
Backups need cert-manager on the cluster; the operator installs CloudNativePG's
backup plugin itself. The Backup column of `kubectl get stigmer` shows the last
full backup, and a failing backup never takes the install out of `Ready`: the
`BackupHealthy` condition says so instead.
[Back up and upgrade your stack](./operations) has the restore.

## A sandbox for each Session

By default every Session's Agent runs in the one shared runner beside the
server. With a bucket declared, each Session whose Agent has a computer can run
in a sandbox of its own instead, on one of two drivers. A sandbox sleeps after
`idleSeconds` without activity and wakes, with its files, on the Session's next
message.

An Agent without a computer needs no sandbox: it writes no file and starts no
program. Its Sessions run on one shared runner the operator adds beside the
sandboxes, the Deployment `stigmer-runner`. That runner serves only those
Sessions and holds no Organization's key, so a licensed install runs it too. The
operator mints its key and the key that seals each turn's credential, and hands
them to the server and that runner alone. It runs one replica on purpose: the
runner keeps each Session's checkpoints on its own disk, on the
`stigmer-runner-data` claim, and a second replica would lose them.
`spec.runner.resources`, `storage` and `extraEnv` size and tune it.

**agent-sandbox** runs a pod per Session in the namespace `stigmer-sandboxes`
beside the install, and the operator installs agent-sandbox when the cluster has
none:

```yaml validate-as="Stigmer.sandboxes"
driver: agentSandbox
idleSeconds: 60
agentSandbox:
  egress:
    allowCIDRs: [10.20.0.0/16]
```

Each sandbox is fenced: it reaches the server, the bucket, DNS and the public
internet, and no other private address unless you list its range under
`allowCIDRs`, such as a model gateway or an MCP server on your network. The
fences are NetworkPolicies, so they hold only on a network plugin that enforces
them.

**Agent Substrate** runs each Session as a gVisor actor on a pool of workers. A
sleeping Session is a snapshot in the bucket and wakes on any worker. The
operator installs Agent Substrate when the cluster has none:

```yaml validate-as="Stigmer.sandboxes"
driver: substrate
idleSeconds: 60
substrate:
  workers: 2
  sandbox:
    cpuMillicores: 2000
    memoryMiB: 2048
  egress:
    http: [models.ai.svc.cluster.local:8080]
```

- **The cluster** must serve Kubernetes' pod-certificate APIs: Kubernetes 1.37
  with the `ClusterTrustBundle`, `ClusterTrustBundleProjection` and
  `PodCertificateRequest` feature gates and `certificates.k8s.io/v1beta1`. The
  status says so in words when they are missing.
- **The pool** runs at the size you declare. The operator never sizes it from
  demand; Agent Substrate's own autoscaler is what will grow it. A run that
  finds no room waits for it. Keep the pool to nodes of one CPU architecture
  (`substrate.worker.nodeSelector`): a sleeping Session wakes only on workers of
  the architecture it slept on.
- **The fence** is Agent Substrate's own egress gateway: a sandbox reaches the
  server, the bucket and the public internet over HTTPS, and over plain HTTP
  only the addresses listed under `egress.http`.
- **The install is `Ready`** once the server has prepared the image every new
  sandbox starts from, so the first Session starts without waiting for it.
- **Its certificate authorities**, which the operator generates, are valid for
  10 years, and nothing rotates them yet.
- **On a development cluster** such as kind, a sandbox image built on your
  machine reaches the workers through the cluster's local registry: install the
  operator with `--set localRegistry=kind-registry:5000`.

The sandbox image runs on amd64 and arm64 nodes alike. The
[runners guide](./runners#a-runner-per-session) covers what a sandbox holds, how
a Session moves between them, and
[the shared runner for Agents without a computer](./runners#agents-without-a-computer).

## Stigmer Enterprise

A license Secret switches the server to the Enterprise image. It signs every
caller in through your identity provider, and runs every Session whose Agent has
a computer in a sandbox of its own rather than on a shared runner, so a licensed
install declares a bucket and a sandbox driver:

```bash
kubectl -n stigmer create secret generic stigmer-license \
  --from-literal=STIGMER_LICENSE_KEY=<the key you were sent>
```

```yaml validate-as="Stigmer"
identity:
  oidc:
    issuer: https://login.example.com
    audience: https://stigmer.example.com
    consoleClientId: stigmer-console
    nativeClientId: stigmer-desktop
enterprise:
  license:
    name: stigmer-license
    key: STIGMER_LICENSE_KEY
  accessHistoryRetentionDays: 365
objectStore:
  s3:
    bucket: acme-stigmer
    region: us-east-1
    credentialsSecret:
      name: bucket
sandboxes:
  driver: agentSandbox
```

[Cloud or self-hosted](./cloud-vs-self-hosted) says what the license adds.

## Upgrade

Operator `vX` runs Stigmer `vX`. To move to a release, upgrade the operator:

```bash
helm upgrade stigmer-operator oci://ghcr.io/stigmer/charts/stigmer-operator \
  --namespace stigmer-system --version <X.Y.Z>
```

The upgrade applies the new `Stigmer` definition first, then the new operator,
which upgrades Stigmer. With a bucket, it takes a full backup of the database
and waits for it before the server rolls, and the server's status says which
version it upgraded from after which backup. In-flight Agent turns resume from
their Temporal checkpoints. [Back up and upgrade your stack](./operations) has
the details.

## Change a setting

Edit `stigmer.yaml` and apply it again; the operator converges the install, and
the API server refuses, naming the field, a declaration that contradicts itself.
A server or runner setting the resource does not carry goes in `server.extraEnv`
or `runner.extraEnv`; a name the operator sets itself is refused there. The
[Stigmer resource reference](./kubernetes-reference/stigmer) lists every field,
its default and its rules.

## Delete

```bash
kubectl -n stigmer delete stigmer stigmer
```

Deleting the `Stigmer` removes the install: the server, the runner, the
sandboxes, Temporal, the bundled sign-in and the database with its volumes. Once
no `Stigmer` remains in the cluster, the operator also removes what it installed
at the cluster level: the sandbox namespace, Agent Substrate, agent-sandbox, the
backup plugin and CloudNativePG. Anything someone else installed stays. Three
things outlive the delete, so a restore stays possible: the keys Secret
`stigmer-keys`, your bucket with the database's archive, and a certificate
cert-manager issued. A delete while a backup is running waits for it, up to
about 3 minutes more.

To remove the operator too, delete every `Stigmer` first, so it can clean up,
then:

```bash
helm uninstall stigmer-operator --namespace stigmer-system
```

The `Stigmer` definition stays;
`kubectl delete customresourcedefinition stigmers.stigmer.ai` removes it.
