This page is for the two shapes a team is served from: the
[Docker Compose stack](./docker-compose) and
[Kubernetes with the Stigmer operator](./kubernetes). The laptop stack and the
[all-in-one container](./all-in-one) are single-user shapes; their own pages say
how to stop, start, and upgrade them.

One idea holds for the whole page: a backup is the database, the files and the
keys whichever shape you run. On Docker Compose you take it yourself. On
Kubernetes, an install with a bucket takes it for you, continuously, and you
keep the keys.

## What a complete backup is

The stack keeps its durable state in three places, plus the keys that unlock it:

| What                                                                   | On Docker Compose      | On Kubernetes                                                                            |
| ---------------------------------------------------------------------- | ---------------------- | ---------------------------------------------------------------------------------------- |
| The database: every resource and run record, and Temporal's own tables | `postgres-data` volume | the bundled database, archived to your bucket when you declare one, or your own database |
| File storage: Files and what runs store                                | `artifacts` volume     | your bucket, or the `stigmer-artifacts` claim without one                                |
| The Skill content store                                                | `server-data` volume   | your bucket, or the `stigmer-server-data` claim without one                              |
| The keys that unlock encrypted values                                  | your `.env` file       | the `stigmer-keys` Secret the operator minted, and your `stigmer.yaml`                   |

The database is one Postgres instance holding three databases: `stigmer`, the
platform's own, and `temporal` and `temporal_visibility`, which hold Temporal's
schedules and in-flight histories. A backup that leaves the two Temporal
databases out loses every scheduled run.

<Callout type="error">
  The keys are part of the backup, not just configuration. Losing
  `STIGMER_ENCRYPTION_KEY` strands every encrypted value—vault secrets and
  logins, OAuth tokens—in the database with no recovery path. Store `.env` or
  the exported `stigmer-keys` Secret like a key file. The operator keeps that
  Secret when the `Stigmer` is deleted, for the same reason.
</Callout>

The fourth volume or claim, `runner-data` (`stigmer-runner-data` on Kubernetes),
is lifecycle state, not backup state: it holds in-flight Session checkpoints and
Agent working directories so a paused run survives a restart. Losing it abandons
runs in flight but loses no durable data.

## Back up

The backup is a SQL dump of the three databases, a tarball of each file store,
and the keys as a flat file. Postgres's own dump format restores into a newer
Postgres and onto either shape; a copied data directory does neither.

<Tabs items={["Docker Compose", "Kubernetes"]} groupId="self-hosting-shape" persist>
<Tab value="Docker Compose">

Stop the two Stigmer services first, so nothing writes to the file stores while
you copy them. Postgres and Temporal keep running; `pg_dump` takes a consistent
snapshot of each database on its own.

```bash
mkdir -p backup
docker compose stop stigmer-server stigmer-runner

for db in stigmer temporal temporal_visibility; do
  docker compose exec -T postgres \
    pg_dump -U postgres --create --clean --if-exists "$db"
done > backup/stigmer-db.sql
```

Then copy the two file stores and `.env`, and start the services again:

```bash
for v in artifacts server-data; do
  docker run --rm \
    -v "stigmer_${v}:/source:ro" \
    -v "$PWD/backup:/backup" \
    alpine tar czf "/backup/${v}.tgz" -C /source .
done

cp .env backup/
docker compose start stigmer-server stigmer-runner
```

Docker Compose prefixes the volume names—`stigmer_` when you run from the cloned
`stigmer` directory. Check yours with `docker volume ls`.

</Tab>
<Tab value="Kubernetes">

**With a bucket, the operator backs up for you.** The bundled database streams
its write-ahead log to the bucket from its first minute and takes a full backup
on the schedule in `spec.database.postgresql.bundled.backup` (daily at 02:00 UTC
unless you set one), and Files and Skills already live in the bucket. The Backup
column of `kubectl get stigmer` shows the last full backup, and the
`BackupHealthy` condition says when one is failing. To take one now, outside the
schedule:

```bash
kubectl -n stigmer apply -f - <<'EOF'
apiVersion: postgresql.cnpg.io/v1
kind: Backup
metadata:
  name: stigmer-by-hand
spec:
  cluster:
    name: stigmer-postgres
  method: plugin
  pluginConfiguration:
    name: barman-cloud.cloudnative-pg.io
EOF
```

What you keep yourself is the keys and your declaration. Export the keys Secret
as a flat file, and keep `stigmer.yaml` beside it:

```bash
mkdir -p backup
kubectl -n stigmer get secret stigmer-keys   -o go-template='{{range $k, $v := .data}}{{$k}}={{$v | base64decode}}{{"\n"}}{{end}}'   > backup/stigmer-keys.env
cp stigmer.yaml backup/
```

**Without a bucket, nothing is backed up for you.** Declare one before the
install holds data you would miss. Until then, or to move data to another shape,
dump the three databases through the database's primary pod; `pg_dump` takes a
consistent snapshot of each database on its own, so the stack keeps running:

```bash
PRIMARY=$(kubectl -n stigmer get pod \
  -l cnpg.io/cluster=stigmer-postgres,cnpg.io/instanceRole=primary -o name)
for db in stigmer temporal temporal_visibility; do
  kubectl -n stigmer exec "$PRIMARY" -c postgres -- \
    pg_dump -U postgres --create --clean --if-exists "$db"
done > backup/stigmer-db.sql
```

Copy the two file stores through the server container, in a quiet moment when no
run is in flight:

```bash
kubectl -n stigmer exec deploy/stigmer -c server -- \
  tar czf - --exclude=lost+found -C /data . > backup/server-data.tgz
kubectl -n stigmer exec deploy/stigmer -c server -- \
  tar czf - --exclude=lost+found -C /artifacts . > backup/artifacts.tgz
```

`lost+found` is the root-owned directory an ext4 disk carries at its root; the
server can't read it and doesn't need it.

</Tab>
</Tabs>

## Restore

<Tabs items={["Docker Compose", "Kubernetes"]} groupId="self-hosting-shape" persist>
<Tab value="Docker Compose">

On a fresh machine, clone the repository and put your `backup` directory at its
root. The same `.env` goes back, with the same keys, not new ones. Start
Postgres alone and load the dump before anything else runs:

```bash
git clone https://github.com/stigmer/stigmer.git
cd stigmer
cp backup/.env .env

docker compose up -d --wait postgres
docker compose exec -T postgres \
  psql -U postgres -v ON_ERROR_STOP=1 -f - < backup/stigmer-db.sql
```

Postgres creates an empty `stigmer` database on its first start; the dump drops
it and recreates it with your data. `ON_ERROR_STOP` makes a failed restore stop
and say so instead of continuing past the error.

Seed the two file stores, then start the rest of the stack. It boots on your
restored data:

```bash
for v in artifacts server-data; do
  docker volume create "stigmer_${v}"
  docker run --rm \
    -v "stigmer_${v}:/target" \
    -v "$PWD/backup:/backup:ro" \
    alpine tar xzf "/backup/${v}.tgz" -C /target
done

docker compose up -d
```

</Tab>
<Tab value="Kubernetes">

**From the bucket, to a point in time.** On the new cluster, install the
operator as the [Kubernetes page](./kubernetes) does. Recreate the keys Secret
from the exported file before you declare anything: the operator keeps every key
it finds there, and the restored database is readable only with them.

```bash
kubectl create namespace stigmer
kubectl -n stigmer create secret generic stigmer-keys \
  --from-env-file=backup/stigmer-keys.env
```

Recreate the model key's Secret and the bucket's, then declare the install as it
was, with `recoverFrom` under the bundled database: the archive's name, which is
the old install's `status.backup.serverName`, and the moment to restore to, in
RFC 3339. Leave `targetTime` out to restore to the newest moment the archive
holds.

```yaml validate-as="Stigmer.database"
postgresql:
  bundled:
    recoverFrom:
      serverName: stigmer-postgres
      targetTime: "2026-11-21T09:30:00Z"
    backup:
      schedule: "0 0 2 * * *"
```

```bash
kubectl apply -f stigmer.yaml
kubectl -n stigmer get stigmer --watch
```

The database is created from the archive, Temporal's schedules and histories
with it, and the server boots on it. Files and Skills were never anywhere but
the bucket. `recoverFrom` is honoured only when the database is created; on a
running install it changes nothing, and the status says so.

**From a dump**, onto an install without a bucket: declare the install, wait for
`Ready`, then stop the operator and the two users of the database while you load
the dump over the fresh, empty databases:

```bash
kubectl -n stigmer-system scale deploy/stigmer-operator --replicas=0
kubectl -n stigmer scale deploy/stigmer --replicas=0
kubectl -n stigmer scale deploy -l app.kubernetes.io/name=temporal --replicas=0

PRIMARY=$(kubectl -n stigmer get pod \
  -l cnpg.io/cluster=stigmer-postgres,cnpg.io/instanceRole=primary -o name)
kubectl -n stigmer exec -i "$PRIMARY" -c postgres -- \
  psql -U postgres -v ON_ERROR_STOP=1 -f - < backup/stigmer-db.sql

kubectl -n stigmer-system scale deploy/stigmer-operator --replicas=1
```

A database can't be dropped while something is connected to it, which is why the
server and Temporal go to zero first; the operator, started again, brings them
back. `ON_ERROR_STOP` makes a failed restore stop and say so. Then wait for the
server to be back, fill the two file stores through its container, and restart
it so it reads them fresh:

```bash
kubectl -n stigmer wait --for=jsonpath='{.status.readyReplicas}'=1 \
  deploy/stigmer --timeout=10m
kubectl -n stigmer exec -i deploy/stigmer -c server -- \
  tar xzf - --strip-components=1 -C /data < backup/server-data.tgz
kubectl -n stigmer exec -i deploy/stigmer -c server -- \
  tar xzf - --strip-components=1 -C /artifacts < backup/artifacts.tgz

kubectl -n stigmer rollout restart deploy/stigmer
```

`--strip-components=1` drops the archive's own root entry, which names the mount
point: the server's user can't change the mount point's mode or time, and
without the flag `tar` writes every file and still exits with an error. Start
your port-forward again afterwards; it stops with the pod.

</Tab>
</Tabs>

## Move a stack between shapes

A dump taken on Docker Compose restores onto a Kubernetes install without a
bucket with the Kubernetes steps under [Restore](#restore), and the other way
round. The dump is Postgres's own format, and each tarball is a directory's
contents rather than a path: the compose stack keeps its file storage at
`/data/.stigmer/data/artifacts` and the operator at `/artifacts`, and the
restore step names the target. The database stores a stored file's key, never
its path, so downloads keep working after the move. An install with a bucket
keeps its files in the bucket rather than on a volume, which this procedure does
not fill: move onto an install without one, and know that declaring a bucket
later starts the file store empty in the bucket, leaving what the volume held
behind.

## Upgrade

The two Stigmer images always move together; on Kubernetes the operator's
version is the Stigmer version. The server migrates its database schema forward
on start, and there is no migration back, so a backup comes first: on Docker
Compose [take one](#back-up); on Kubernetes with a bucket the operator takes it
for you.

<Tabs items={["Docker Compose", "Kubernetes"]} groupId="self-hosting-shape" persist>
<Tab value="Docker Compose">

Set the version in `.env`, then pull and restart:

```bash
# .env
STIGMER_VERSION=v0.3.2
```

```bash
docker compose pull
docker compose up -d
```

The compose file's own default moves with each release, so `git pull` gives you
the release's file; your `.env` line wins over its default either way.

</Tab>
<Tab value="Kubernetes">

Upgrade the operator to the version you're moving to:

```bash
helm upgrade stigmer-operator oci://ghcr.io/stigmer/charts/stigmer-operator \
  --version 0.3.2 \
  --namespace stigmer-system
```

The upgrade applies the new `Stigmer` definition, then the new operator, which
upgrades Stigmer. With a bucket it first takes a full backup of the database,
named for the version (`stigmer-before-<version>`), and the server rolls only
once that backup has finished; the server's status then says which version it
upgraded from after which backup. In-flight Agent turns resume from their
Temporal checkpoints. Start your port-forward again afterwards.

</Tab>
</Tabs>

Going back is a restore, not a downgrade: the server refuses to start against a
database a newer release migrated, and its error names both schema versions.
Restore the pre-upgrade backup instead. Releases are listed on the
[GitHub releases page](https://github.com/stigmer/stigmer/releases).

## Change a setting or a secret

The rule from the shape pages holds here: a setting is a line in `.env` or a
field of the `Stigmer` resource, never an edit to the compose file or to what
the operator runs.

<Tabs items={["Docker Compose", "Kubernetes"]} groupId="self-hosting-shape" persist>
<Tab value="Docker Compose">

Change the line, then `docker compose up -d`. Compose recreates the services
whose settings changed and leaves the others running.

The one line that doesn't work this way is `POSTGRES_PASSWORD`. Postgres reads
it once, when it initialises an empty data directory; changing the line later
doesn't change the database's password, and the server can no longer connect.
Leave it as it is.

</Tab>
<Tab value="Kubernetes">

Edit `stigmer.yaml` and apply it; the operator rolls what the change touches. A
server or runner setting the resource has no field for goes in
`spec.server.extraEnv` or `spec.runner.extraEnv`.

A Secret's contents is different: the pod reads its Secrets when it starts, and
nothing restarts it when one changes. Replace the Secret, then restart the pod:

```bash
kubectl -n stigmer create secret generic anthropic \
  --from-literal=ANTHROPIC_API_KEY=sk-ant-... \
  --dry-run=client -o yaml | kubectl apply -f -
kubectl -n stigmer rollout restart deploy/stigmer
```

</Tab>
</Tabs>

### Where your people ask for help

Set where your people ask when they're stuck (your support desk, team chat or a
mail address) and every console screen shows it: at the foot of the sidebar,
under the Sign in button, and under every failure. Every command the server
refuses ends with it too. Unset, nothing shows.

| `.env`               | `Stigmer` resource       | What it holds                                            |
| -------------------- | ------------------------ | -------------------------------------------------------- |
| `STIGMER_HELP_URL`   | `spec.server.help.url`   | An absolute `https:`, `http:` or `mailto:` address.      |
| `STIGMER_HELP_LABEL` | `spec.server.help.label` | Its words, at most 40 characters. `Get help` when unset. |

```bash title=".env"
STIGMER_HELP_URL=https://support.example.com/stigmer
STIGMER_HELP_LABEL=Ask IT on Slack
```

A console shows it as "Stuck? Ask IT on Slack". The server never announces an
address with another scheme: it drops one at start and says so in its log, and
does the same for words over 40 characters, which become `Get help`. Apps your
builders make with the React SDK don't show it to their own users: help there is
the builder's to give.

### Where newcomers stop

The server can tell you how far the organizations made on it got, from a first
agent to their users: how many were made, and how many said what their agent
should do, added a model key, watched it work, made it theirs, put it in their
app and brought others in. It counts the same six steps each admin sees on the
dashboard's first-steps card, from what the server already records, so the card
and the count always agree. A platform operator reads it:

```bash
stigmer usage onboarding --from 2026-11-01 --to 2026-11-07
```

With no dates it counts the last week. It counts only: no names, no addresses.
An organization made inside another (a customer's) isn't a newcomer and isn't
counted.

Leave out your own team's tries by naming their sign-in addresses:

| `.env`                      | `Stigmer` resource             | What it holds                                                              |
| --------------------------- | ------------------------------ | -------------------------------------------------------------------------- |
| `STIGMER_INTERNAL_ACCOUNTS` | `spec.server.internalAccounts` | Addresses, each exact or a pattern with one `*` (`*@example.com`): a list. |

```bash title=".env"
STIGMER_INTERNAL_ACCOUNTS=*@example.com,tester+*@example.org
```

An organization made by a matching address is left out and counted apart. A bad
entry is dropped at start, and the log says which.

### Rotate the runner's key

The runner's API key is the one credential you'll rotate on purpose.

<Tabs items={["Docker Compose", "Kubernetes"]} groupId="self-hosting-shape" persist>
<Tab value="Docker Compose">

Generate a new key, replace the line in `.env`, and recreate the stack:

```bash
echo "stk_$(openssl rand -base64 32 | tr '+/' '-_' | tr -d '=')"
```

```bash
# .env
STIGMER_TOKEN=stk_...
```

```bash
docker compose up -d
```

The server and the runner both read the line. At its start the server deletes
the old key of its `runner` service account and stores the new one, and its log
says "the shared runner's key changed".

</Tab>
<Tab value="Kubernetes">

With sign-in on, the operator mints the runner's key into the Secret
`stigmer-runner-key`. To rotate it, delete the Secret, wait for the operator to
mint a new one, and restart the pod so the server and the runner both read it:

```bash
kubectl -n stigmer delete secret stigmer-runner-key
kubectl -n stigmer wait --for=create secret/stigmer-runner-key --timeout=2m
kubectl -n stigmer rollout restart deploy/stigmer
```

At its start the server deletes the old key of its `runner` service account and
stores the new one, and its log says "the shared runner's key changed". An
install whose Sessions each run in a sandbox has no shared runner and no key to
rotate.

</Tab>
</Tabs>

Your LLM provider key is a new line in `.env`, or a replaced Secret and a
restart ([Change a setting or a secret](#change-a-setting-or-a-secret)).

Two keys are never rotated. `STIGMER_ENCRYPTION_KEY` is the one key every
encrypted value was written under; a different key can't read them, so the key
generated at install is the key for the life of the stack.
`STIGMER_RUNNER_TOKEN_KEY` signs the short-lived credentials the runner
authenticates each run with; leave it alone too.

`STIGMER_PLATFORM_TOKEN_KEY`, when you set it, signs the 15-minute tokens the
server mints for your product's users. It can be replaced at any restart: tokens
minted in the last 15 minutes stop working and your backend mints new ones, as
it does when a token expires.

`STIGMER_DOWNLOAD_URL_KEY` signs the download links the server mints for files
on its own disk (Files, what runs store, and Skill and Plugin archives), so a
link works only until it expires, at most 7 days after it was made. You never
need to set it: without it the server generates one on its first start and keeps
it in its data, as `download-url.key` beside its other key files. It has no
backup story. Replacing or losing it only stops the links already handed out,
and clients request new ones.

## Load test it

Before your team relies on the stack, check what happens when many people start
an Agent at the same moment. `stigmer load-test` does that with the key you
already use: it starts the number of Agents you name at once, each in a new
conversation of its own, and reports how many started, how long each waited for
a sandbox, and which the server refused and why.

```bash
stigmer load-test --agents 25
```

Every run calls your model provider, so it costs money. `--max-usd` is the whole
burst's budget, $1 by default, split evenly across the runs: each stops once its
own estimate reaches its share, and one model call can go past a share. The
report adds up what the runs spent. When the burst is over, the command deletes
every conversation it made and its own Agent, even when you press Ctrl-C.

Only a fleet that can run out of room ever shows a wait. On the Agent Substrate
driver, a run that finds every sandbox busy waits for one
([When every sandbox is busy](./runners#when-every-sandbox-is-busy)), and the
report gives the longest wait each run reported. The other drivers start every
run at once, so the report says no run waited. The wait reaches the command from
the server process that asked the fleet for room; with several server processes
behind one address, a wait can read shorter than it was, while the time to
start, from the server's own stamps, stays exact. The
[command's reference](/docs/cli/commands/load-test) explains each column.

## After an Organization is deleted

A server that holds more than one Organization can delete one (open source holds
one and never deletes it). The delete answers at once, and the server then
removes everything the Organization owned in the background, from the database
and from file storage, and frees its slug last
([Deleting an Organization](/docs/concepts/organizations#deleting-an-organization)).

A server running with a Stigmer Enterprise license keeps one record on purpose:
the Organization's permission history, the
[access history](/docs/guides/authentication/access-history) its admins read
while it exists. Each entry records access granted or removed, saying who made
the change, why it was made, and when. It names the accounts and resources by
ID, and keeps each access row as it stood, including the email and display name
of the person who granted it. The server removes it once it is older than the
access history's window, if you set one: `STIGMER_ACCESS_HISTORY_RETENTION_DAYS`
holds the number of days, and unset keeps every entry for good
([How long it is kept](/docs/guides/authentication/access-history#how-long-it-is-kept)).
To erase a deleted Organization's history sooner, delete its rows from the
`grant_history` table yourself, where `org` is the Organization's ID. Its row in
`grant_history_heads` holds only that ID, the last number it handed out and that
number's time; it is what keeps the Organization's numbers from being reused,
and you may delete it too.

Some copies live outside what the server can reach, and each ages out on its own
schedule:

| Where                      | What may still hold the Organization's data       | When it goes                                                                                                                                                                                                                      |
| -------------------------- | ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Database backups           | Every row the Organization had when it was copied | When you delete the backup. The stack seals secrets with one key, `STIGMER_ENCRYPTION_KEY`, so a backup's secrets stay readable with it                                                                                           |
| Temporal's history         | The histories of the Organization's runs          | When the Temporal namespace's retention ends                                                                                                                                                                                      |
| Logs                       | Ids and messages from the Organization's requests | When your log retention ends                                                                                                                                                                                                      |
| An external storage bucket | Skill and Plugin archive files                    | The server removes the Organization's Files and other files itself; archive files stay until [stigmer#1926](https://github.com/stigmer/stigmer/issues/1926) lands; files written to the bucket some other way are yours to remove |

## Uninstall

<Tabs items={["Docker Compose", "Kubernetes"]} groupId="self-hosting-shape" persist>
<Tab value="Docker Compose">

`docker compose down` stops and removes the containers and keeps every volume;
`docker compose up -d` brings the same data back. To delete the data too:

```bash
docker compose down -v
```

</Tab>
<Tab value="Kubernetes">

Deleting the `Stigmer` removes the install and its data: the server, the
sandboxes, Temporal, the bundled sign-in, and the database with its volumes.
Once no `Stigmer` remains, the operator removes what it installed at the cluster
level too, and nothing someone else installed.

```bash
kubectl -n stigmer delete stigmer stigmer
```

The keys Secret `stigmer-keys`, your bucket with the database's archive, and a
certificate cert-manager issued outlive the delete, so a restore stays possible.
Delete the keys Secret and empty the bucket yourself when you mean the data to
be gone for good. To remove the operator as well, delete every `Stigmer` first,
then `helm uninstall stigmer-operator --namespace stigmer-system`.

</Tab>
</Tabs>
