Embedding puts an Agent's chat link directly on your website. Visitors chat in
place — they don't need a Stigmer account, and they never leave your page.

Before you start,
[create a public chat link](/docs/guides/channels/create-a-chat-link) for the
Agent. Embedding uses the same public chat that powers the hosted link.

## Paste the snippet

Open the chat link's dialog (**Edit** on its card in the Agent's **Channels**
tab) and copy the code from the **Embed** tab:

```html
<script src="https://app.stigmer.ai/embed.js" async></script>
<stigmer-agent channel="chn_01j9z3k8f2q4m6n7p8r9s0t1v2"></stigmer-agent>
```

Paste it where you want the chat to appear. The `<script>` tag loads once per
page, even if you embed several Agents. The `<stigmer-agent>` tag marks the spot
where the chat renders, and its `channel` attribute names the channel by its
permanent ID — so renaming your Organization never breaks the embed. If you
reset the chat link, the snippet also carries a `token` attribute; re-copy it
after every reset.

If you run your own Stigmer server, the dialog fills in your server's address
automatically — the snippet works the same way.

## Size and theme

The widget renders at 400×600 px by default. Set `width` and `height` to change
that — a plain number is px, or use any CSS length with a unit:

```html
<stigmer-agent
  channel="chn_01j9z3k8f2q4m6n7p8r9s0t1v2"
  width="320"
  height="80vh"
  theme="dark"
></stigmer-agent>
```

`theme` accepts `light`, `dark`, or `auto` (match the visitor's system
preference). Without it, the chat uses its own default. The theme is chosen when
the widget loads — it does not switch mid-conversation.

## Control which sites can embed

By default, any site can embed a public chat link — the same "anyone with the
link" deal as the hosted page itself. To restrict embedding to your own sites,
add them under **Allowed embed origins** in the chat link dialog's **Embed** tab
(for example `https://acme.com`).

Once the list has at least one entry:

- The widget works only on the listed sites.
- On any other site, the widget hides itself instead of showing an error.
- Removing a site takes effect on the visitor's next message.

The hosted link keeps working for everyone either way — the list only controls
embedding.

The list is enforced with browser-grade evidence: for direct SDK embeds the
platform checks the request's `Origin` header — which page scripts cannot forge
— so an unlisted site cannot claim a listed one. Sites you list need no changes;
honest embeds pass automatically.

<Callout type="info">
  Visitor chats in the widget run on your Organization's provider keys, with the
  same rate limits and protections as the hosted link. See [who pays for
  chat-link
  conversations](/docs/guides/channels/create-a-chat-link#who-pays-for-chat-link-conversations).
</Callout>

## If your site can't run scripts

Some platforms strip `<script>` tags. The **Embed** tab's **No-JavaScript
alternative** gives you a plain `<iframe>` snippet instead. It shows the same
chat, with one difference: on a site that isn't allowed to embed the Agent, the
iframe shows an empty frame instead of hiding.

## React and custom integrations

The widget also works from a bundler — install `@stigmer/embed` and register the
element. In a TypeScript React project, also import the `jsx` entry once so the
element typechecks in TSX:

```typescript
import "@stigmer/embed/define"; // registers <stigmer-agent>
import "@stigmer/embed/jsx"; // TypeScript: makes it a valid JSX element
```

Then render
`<stigmer-agent channel="chn_01j9z3k8f2q4m6n7p8r9s0t1v2" app-origin="https://app.stigmer.ai" />`
anywhere in your markup. The `app-origin` attribute replaces what the script
tag's URL normally provides.

One caution for React: the element rebuilds its chat — losing the visitor's
conversation — whenever any attribute changes. Pass stable values, and resolve
anything dynamic (like a light or dark theme) once, before the element mounts.

For full control — your own UI, your own users, your own authentication — use
the SDK directly instead of the widget. The
[Put the agent in your app](/docs/getting-started/embed-agent) tutorial walks
through the React components; the chat link dialog's **Developer** tab and the
[Sign your product's users in](/docs/guides/authentication/product-users) guide
cover authentication for your own users.

## The app's own tools

With the React SDK the Agent can also call tools your app answers itself, for
the conversations your chat starts (what they are and how a call waits:
[Your app's own tools](/docs/concepts/sessions#your-apps-own-tools)). Declare
each with `defineCustomTool` and pass them as `customTools`. Register a card
under the tool's name on `StigmerProvider`'s `toolCards`: it draws the call
inside the chat, filled with what the Agent asked, and its `answer` sends your
app's reply to the Agent. Or hear each waiting call with `onCustomToolUse` and
answer from your own panel:

```tsx
import { useState } from "react";
import { defineCustomTool, type Stigmer } from "@stigmer/client";
import {
  AgentChat,
  StigmerProvider,
  type ToolCardProps,
} from "@stigmer/react-sdk/chat";

declare const stigmer: Stigmer;
declare function saveAccount(name: string): Promise<string>;
// ---cut---
const registerAccount = defineCustomTool({
  name: "register_cloud_account",
  description:
    "Show the person the account registration form, filled in from the conversation.",
  inputSchema: {
    type: "object",
    properties: {
      account_name: { type: "string" },
      auth_method: { enum: ["role", "keys"] },
    },
    required: ["account_name"],
  },
});

function RegisterAccountCard({ call, answer }: ToolCardProps) {
  const [name, setName] = useState(String(call.input.account_name ?? ""));
  if (call.state !== "waiting-on-host")
    return <p>{call.result?.text ?? "Not registered."}</p>;
  if (answer === undefined)
    return <p>Waiting for the account form to be sent.</p>;
  return (
    <form
      onSubmit={async (event) => {
        event.preventDefault();
        await answer(`Registered ${name} as ${await saveAccount(name)}`);
      }}
    >
      <input value={name} onChange={(event) => setName(event.target.value)} />
      <button type="submit">Register</button>
      <button
        type="button"
        onClick={() => answer("The person cancelled.", { isError: true })}
      >
        Cancel
      </button>
    </form>
  );
}

export function Assistant() {
  return (
    <StigmerProvider
      client={stigmer}
      toolCards={{ register_cloud_account: RegisterAccountCard }}
    >
      <AgentChat
        agent="acme/cloud-helper"
        customTools={[registerAccount]}
        onCustomToolUse={(call) =>
          console.log("waiting on the app:", call.tool, call.id)
        }
      />
    </StigmerProvider>
  );
}
```

- `answer` exists only while the call waits, and only for the person whose
  conversation it is; someone watching sees the card with no `answer`. `isError`
  tells the Agent the tool failed or the person cancelled.
- `onCustomToolUse` fires once for each waiting call, and again when the
  conversation is opened while the call still waits, so your panel comes back
  after a reload. Two open tabs each hear it: make what it does safe to run
  twice. The same answer sent twice is accepted; a different second one is
  refused.
- An input field named like a secret (`password`, `token`, `secret`, `api_key`,
  `apikey`, `credentials`, `auth`, `authorization`) is refused when the
  conversation is created, because Stigmer hides those values in everything it
  stores; name it for what it holds (`auth_method`).
- The tools are read once, when the conversation starts. Import
  `defineCustomTool` from `@stigmer/client`, as you import the client; the light
  chat entry carries only the types.

## Give the agent standing user context

SDK integrations can hand the agent standing, per-user context — who the caller
is, their experience level, their standing instructions — that the agent
receives on every turn but the conversation never shows. Your agent greets the
user by name and calibrates its depth and defaults from the first message,
without a visible context preamble polluting the chat.

Pass `sessionContext` when you create the session — every session-creating
surface in `@stigmer/react-sdk` accepts it
([`useNewSessionFlow`](/docs/sdk/react/session#usenewsessionflow),
[`useCreateSession`](/docs/sdk/react/session#usecreatesession), and
[`useCreateRun`](/docs/sdk/react/run#usecreaterun)'s bootstrap `sessionSpec`):

```tsx
declare function navigate(path: string): void;
declare const user: { name: string; role: string };
// ---cut---
import { useNewSessionFlow } from "@stigmer/react-sdk/headless";

const flow = useNewSessionFlow({
  org: "acme",
  onSessionCreated: (id) => navigate(`/sessions/${id}`),
  sessionContext:
    `Name: ${user.name}. Role: ${user.role}. ` +
    `Kubernetes experience: beginner. Prefers step-by-step guidance.`,
});
```

The value is stored on the session's spec metadata under
`stigmer.ai/session-context` (exported from `@stigmer/client` as
`SESSION_CONTEXT_METADATA_KEY` for integrations that set the raw `metadata` map
instead).

Two things it is not:

- **Not authorization.** Anyone who can create the session can set it — the same
  trust level as typing the first message. Enforce privileges with the
  credentials bound to the session, never with what the agent reads here.
- **Not a secrets channel.** It is hidden from the conversation thread, not from
  the API — `session.get` returns it. Put secrets in a
  [vault](/docs/concepts/vaults) the session names instead.
