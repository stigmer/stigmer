---
title: Install a plugin
description:
  Install a Cursor, Claude Code, Codex or Agent Plugins folder on Stigmer and
  get an Agent that uses its skills and tools, or the tools for your own Agents.
---

A plugin is a folder of skill files, MCP server entries, and sub-agent prompts
in the layout the Cursor, Claude Code, and Codex communities already publish.
Installing it on Stigmer creates ordinary Skills and MCP Servers in your
Organization, as one unit, and when the plugin carries skills or sub-agents, an
Agent that uses them. A plugin installs as an Agent, as tools for your Agents,
or both: a plugin that is only MCP servers installs its servers, ready to list
on any Agent, and no Agent of its own.

Before you start, [sign in](/docs/guides/authentication) with
`stigmer auth login`. Every command below takes `--org <slug>` if you work in
more than one Organization.

This page installs a plugin from a folder you have. To install one by name from
a catalogue, Stigmer's or your own, see
[Install from a marketplace](/docs/guides/plugins/install-from-a-marketplace);
the plugin lands the same way.

## Check the folder

Point `stigmer validate` at the plugin's directory. It reads the folder offline,
tells you what would install, and refuses anything Stigmer cannot run:

```bash
stigmer validate -f ./thermos
```

```text
✓ Plugin 'thermos' is valid with 1 warning

Plugin
  Name       thermos
  Version    1.2.0
  Format     Cursor plugin
  Manifests  .cursor-plugin/plugin.json, mcp.json
  Files      14 read, 3 excluded by ignore rules

Installs
  Skills       2: code-review, triage
  MCP servers  1: github (http)
  Sub-agents   1: reviewer
  Variables    1: GITHUB_TOKEN

Warnings
  - sub-agent 'reviewer' names model 'sonnet'; it runs on the session's model
```

A refusal lists every problem at once, so one pass fixes them all. The same
sentences come back from the server, so a folder that validates installs.

## Install it

```bash
stigmer push plugin ./thermos
```

```text
✓ Installed plugin 'thermos' (2 skills, 1 MCP server, 1 agent) with 1 warning

Plugin
  ID       plg_01j9...
  Slug     thermos
  Version  1.2.0
  Digest   3f9a2c1e
  Format   Cursor plugin
  Size     12.4 KB

Installed
  Skills       code-review, triage
  MCP servers  github
  Agents       thermos

Next
  - github needs GITHUB_TOKEN; the agent asks at its first session
```

The summary names only the kinds the plugin installed, and `Next` says what each
MCP Server still needs before its first tool call: a variable the Agent asks
for, a sign-in an OAuth server needs (with the command that runs it), or
nothing. A plugin that installed servers and no Agent ends with the one thing
still missing: an Agent that lists them under `mcp_server_usages`.

`stigmer apply` pointed at a plugin directory does the same thing, so a
repository that is a plugin installs with the command you already run.

The Agent it created is `thermos`, named after the plugin. It carries the
plugin's Skills, uses its MCP Server, and has the plugin's sub-agent prompts as
its own. Open it in the console or start a Session:

```bash
stigmer run thermos
```

## Give it its secrets

The MCP server declared a variable, `GITHUB_TOKEN`. The MCP Server was created
with that variable marked secret, and the Agent's Session asks for it the first
time the tool is used, exactly as it would for an MCP Server you added by hand.
Set it once on the [Environment](/docs/concepts/environments) and every Session
has it.

A server that declares no variable and signs in with OAuth instead (Linear,
Notion, and most hosted servers) is recognized as such when it is saved: its
definition is completed with the sign-in, and the server's page, the plugin's
page and the Session composer carry **Sign in** until someone in the
Organization has done it once. The CLI's `Next` line names the command
(`stigmer connect mcp-server <server>`). How the completion works is in
[OAuth for tools](/docs/guides/integrations/oauth-for-tools).

## Upgrade

Edit the folder and push it again. Stigmer compares the new archive with the
installed one: an unchanged folder changes nothing, a changed one becomes the
new version. Skills the new version dropped are removed, and the Agent is
rewritten to match. Every installed version stays in the plugin's history under
its content digest, and the manifest's `version` is recorded as that version's
tag, so `1.2.0` names the archive that carried it.

```bash
stigmer get plugin thermos
```

## What you cannot edit

The Skills, MCP Servers and Agent a plugin installs are the plugin's to define.
Editing one directly is refused with the plugin's name, because the next upgrade
would overwrite your change. Two ways forward:

- **Change the plugin.** Edit the folder and push it again; that is what an
  upgrade is.
- **Compose over it.** Create your own Agent and give it the plugin's Skills and
  MCP Servers. Your Agent is yours to edit and survives every upgrade.

Operational actions still work on the plugin's members: running the Agent,
sharing it, checking a Skill's versions.

## Remove it

```bash
stigmer delete plugin thermos
```

This removes the plugin and everything it installed. It is refused while an
Agent or Workflow of your own still uses one of the plugin's Skills or MCP
Servers; detach them first.

## Stigmer's own overlay

A plugin can carry a folder named `ai.stigmer/` with Stigmer resources the other
tools ignore: an `agent.yaml` to author the Agent yourself instead of taking the
composed one, `workflows/` for Workflows that use the plugin's tools, and
`mcp-servers/` overlays that set OAuth or transport details on a declared
server. Each document names the plugin's own resources and nothing else; a
document that names something outside the plugin is refused.

The manifest may also carry presentation under `extensions["ai.stigmer"]`, the
extension slot the Agent Plugins format reserves for a host: `displayName` (the
name a card and a page show; the plugin's `name` stays its slug), `logo` (a URL
the Marketplace card renders where the format has no logo field) and `category`
(a word the catalogue groups by). A Cursor manifest's own `displayName`, `logo`
and `category` are read the same way; nothing else in the slot is read.
