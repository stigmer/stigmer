---
title: Install a plugin
description:
  Install a Cursor, Claude Code, Codex or Agent Plugins folder on Stigmer and
  use its skills, agents, hooks and MCP servers in your chats and Agents.
---

A plugin is a folder of skill files, MCP server entries, sub-agent prompts and
hooks in the layout the Cursor, Claude Code, and Codex communities already
publish. Installing it on Stigmer stores the plugin in your Organization as one
resource, and its page lists what it holds. A chat or an Agent that lists the
plugin gets all of it: its Skills and hooks, its agents as Sub-Agents, and its
MCP servers. A plugin is also the only home of an MCP server: to use one server
at an address, `stigmer mcp add` installs a plugin holding just that server.

Before you start, [sign in](/docs/guides/authentication) with
`stigmer auth login`. Every command below takes `--org <slug>` if you work in
more than one Organization.

This page installs a plugin from a folder you have. To install one by name from
a catalogue, Stigmer's or your own, see
[Install from a marketplace](/docs/guides/plugins/install-from-a-marketplace);
the plugin lands the same way.

## Check the folder

Point `stigmer validate` at the plugin's directory. It reads the folder offline,
tells you what would install, and refuses anything Stigmer cannot run:

```bash
stigmer validate -f ./thermos
```

```text
✓ Plugin 'thermos' is valid with 1 warning

Plugin
  Name       thermos
  Version    1.2.0
  Format     Cursor plugin
  Manifests  .cursor-plugin/plugin.json, mcp.json
  Files      14 read, 3 excluded by ignore rules

Installs
  Skills       2: code-review, triage
  MCP servers  1: github (http)
  Sub-agents   1: reviewer
  Hooks        none
  Variables    1: GITHUB_TOKEN

Warnings
  - sub-agent 'reviewer' names model 'sonnet'; it runs on the session's model
```

A refusal lists every problem at once, so one pass fixes them all. The same
sentences come back from the server, so a folder that validates installs.

## Install it

```bash
stigmer push plugin ./thermos
```

```text
✓ Installed plugin 'thermos' (2 skills, 1 MCP server, 1 agent) with 1 warning

Plugin
  ID       plg_01j9...
  Slug     thermos
  Version  1.2.0
  Digest   3f9a2c1e
  Format   Cursor plugin
  Size     12.4 KB

Installed
  Skills       code-review, triage
  MCP servers  github (http)
  Agents       reviewer

Next
  - Save GITHUB_TOKEN in your vault:  stigmer vault set-secret GITHUB_TOKEN --mine
  - Use it in a conversation:  stigmer run --plugin thermos
  - Give it to an agent: add '- slug: thermos' under spec.plugins in the agent's YAML, or from the plugin's page in the console
```

The summary names only the kinds the plugin holds, and `Next` says what stands
between the plugin and its first tool call: a key its servers read, a sign-in a
server needs (with the command that runs it), then the two ways to use it.
Install writes the plugin and nothing else, and no other resource appears beside
it, so two plugins that each carry a Skill named `review` both install, and a
turn tells them apart as `thermos:review` and `other:review`.

`stigmer apply` pointed at a plugin directory does the same thing, so a
repository that is a plugin installs with the command you already run.

## Use it

Turn it on for one conversation:

```bash
stigmer run --plugin thermos -m "Review my open pull request"
```

With no Agent named, the built-in assistant runs with everything the plugin
carries. Name an Agent (`stigmer run my-agent --plugin thermos`) and the plugin
joins that Agent's own. In the console, pick the plugin in the chat's plugin
picker, or use **Start a chat** on the plugin's page.

To give it to an Agent for good, list it in the Agent's `plugins`:

```yaml validate-as="Agent"
spec:
  plugins:
    - kind: plugin
      slug: thermos
```

**Add to an agent** on the plugin's page writes the same entry. In a turn, the
plugin's Skills are named `thermos:<skill>`, its agents are Sub-Agents named
`thermos:<agent>`, and its servers' tools are
`mcp__plugin_thermos_<server>__<tool>`, the names an Agent's `tools` and
`disallowed_tools` lists use.

## Give it its secrets

The MCP server reads a variable, `GITHUB_TOKEN`. The plugin declares it as a
secret, and a conversation that uses the plugin finds it by name in its vaults
when a run starts. Save it once in your [vault](/docs/concepts/vaults)
(`stigmer vault set-secret GITHUB_TOKEN --mine`) and every conversation of yours
has it.

A server at an address that names no key and signs in with OAuth instead
(Linear, Notion, and most hosted servers) is recognized as such at install: the
plugin records that it signs in, with a login key and the `Authorization` header
that carries it, and the plugin's page and the chat composer carry **Sign in**
until you have signed in. The sign-in is saved in your own vault, so each person
signs in once for themselves. The CLI's `Next` line names the command
(`stigmer connect plugin <plugin>`), which also lists the server's tools. How
the sign-in works is in
[OAuth for tools](/docs/guides/integrations/oauth-for-tools).

## Upgrade

Edit the folder and push it again. Stigmer compares the new archive with the
installed one: an unchanged folder changes nothing, a changed one becomes the
new version, and every Agent and conversation that lists the plugin without a
version uses it from its next turn. Every installed version stays in the
plugin's history under its content digest, and the manifest's `version` is
recorded as that version's tag, so `1.2.0` names the archive that carried it.

```bash
stigmer get plugin thermos
```

## Change it

Everything a plugin holds lives in its archive. To change one, edit the folder
and push it again; that is what an upgrade is. Your own Agent lists the plugin
and adds its own instructions, Skills and tool lists around it, so it is yours
to edit and survives every upgrade.

## Remove it

```bash
stigmer delete plugin thermos
```

This removes the plugin. It is refused while an Agent of your Organization lists
it, and the refusal names those Agents; take the plugin out of their `plugins`
first. A conversation that listed it fails its next turn, naming the plugin.

## Stigmer settings in the manifest

The manifest may carry presentation under `extensions["ai.stigmer"]`, the
extension slot the Agent Plugins format reserves for a host: `displayName` (the
name a card and a page show; the plugin's `name` stays its slug), `logo` (a URL
the Marketplace card renders where the format has no logo field) and `category`
(a word the catalogue groups by). A Cursor manifest's own `displayName`, `logo`
and `category` are read the same way; nothing else in the slot is read.

A folder named `ai.stigmer/` in the plugin is not read. Install still succeeds,
and reports the folder with a warning (`stigmer-folder-ignored`).
