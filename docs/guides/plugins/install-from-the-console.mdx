---
title: Install from the console
description:
  Find a plugin in the Marketplace or upload one from your computer, read what
  it would install, install it, and start a Session on the Agent it installs.
---

The console installs a plugin the way the CLI does: it reads the plugin's files,
packages them, and pushes one archive to the server. The archive is
byte-for-byte the one `stigmer install` or `stigmer push plugin` would push for
the same files, so a plugin installed from the console and one installed from
the CLI are one plugin with one digest, and the server treats a second install
of the same version as nothing to do.

There are two ways in. The **Marketplace**, in the sidebar, is where you find a
plugin someone else publishes. **Upload plugin**, from the Library's Plugins
page, is how you install a plugin folder you already have. Everything here works
the same in the web console and the desktop app.

## Find a plugin in the Marketplace

Open **Marketplace** in the sidebar. The page lists the plugins on offer in a
section per source, with one search box that filters all of them. Four sources
are built in, in this order: Stigmer's official catalogue, then Cursor's, Claude
Code's and Codex's public catalogues. A card says **Installed** when your
Organization already holds a plugin of that name.

Each section reads its own catalogue. A section that cannot be read right now
says so and the rest of the page stands. On a development server the official
section says the catalogue is not published for that build; the other sections
still work.

Below the sections, **Sources** lists the catalogues the page reads and lets you
add your own: type a public GitHub repository as `owner/repo`, `owner/repo@ref`
or the URL a browser shows, and choose **Add source**. The repository is read
before it is added, and the source takes the name its marketplace file gives
itself unless you type one. The built-in sources cannot be removed; a source you
added can. The list is this browser's, exactly as the CLI's is this machine's
(`marketplaces` in `~/.stigmer/config.yaml`): nothing about a source reaches the
server.

## Upload a plugin from your computer

In the Library, open **Plugins**, then **Upload plugin**. Drop a plugin folder
onto the page, or choose one with **Choose a folder**; a Cursor, Claude Code,
Codex or Agent Plugins folder installs unchanged. A `.zip` of the folder works
too, and a zip that wraps everything in one directory (the shape `zip -r` gives
a folder) is read from inside that directory.

The console rebuilds the archive from the folder's files with the same ignore
rules and the same deterministic packaging `stigmer push plugin` applies, so the
preview's digest is the one the CLI prints for the same folder. If the preview
says no manifest was found, your browser may have left out files whose names
begin with a dot when the folder was picked (a Cursor or Claude Code plugin
keeps its manifest in one): zip the folder and upload the `.zip` instead.

## Read what a plugin would install

Before anything is pushed, the console reads the plugin's files and shows the
same description `stigmer validate -f` prints: the plugin's name, version and
format; the Skills, MCP Servers and Sub-Agents it installs; the variables its
tools need; the reader's warnings; and what is not installed (rules, hooks and
the other components Stigmer does not read). A plugin the reader refuses is
shown with every problem named, the way the CLI prints it.

The preview also states one fact the CLI states only after the act:

- **Already installed**: your Organization holds this exact version. Install is
  not offered; there is nothing to do.
- **Upgrade**: your Organization holds another version, from whichever source it
  came. Installing replaces the plugin's Skills, MCP Servers and Agent with this
  version's. The Agent is re-created, so a Session bound to the previous one
  does not follow it.

## Install and start a Session

Choose **Install** (or **Upgrade**). The console pushes the archive and shows
what landed, in the CLI's words: how many Skills, MCP Servers and Agents. Then
it opens the plugin's page.

The plugin's page lists what the install produced, each a link to its own page,
together with the manifest's version, format and author, and the server's
install warnings. When the plugin carries an Agent, **Start session** is the
page's primary action. The Agent declares the variables its tools need, so the
first Session asks for them and saves them to your personal Environment; from
then on they are supplied to every Session on that Agent without asking.

A Skill, MCP Server or Agent a plugin installed says so at the top of its page
and is not editable there: the plugin's resources are the plugin's to redefine.
To change one, change the plugin and install it again; to customise, compose
your own Agent over the plugin's Skills and MCP Servers.

## Remove

From the plugin's page, **Remove** deletes the plugin and every Skill, MCP
Server and Agent it installed, the same act as `stigmer delete plugin`. The
server refuses when something outside the plugin still references one of them,
and the console shows that refusal as the server phrases it, naming what still
uses the member.

## What the console does and does not do

- It never reads a source through the server. The GitHub trees and the official
  catalogue are fetched by the browser, so the control plane makes no outbound
  request on your behalf.
- It reads a GitHub source at one commit: the tree is listed once and every file
  is read at the commit the listing resolved to, so what you preview is what you
  install.
- It does not record where a plugin came from. As with the CLI, installing
  `thermos` from a second source, or uploading it, upgrades the `thermos` from
  the first.
- Private repositories are not sources, in the console or the CLI.
