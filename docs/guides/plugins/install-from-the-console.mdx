---
title: Install from the console
description:
  Find a plugin in the Marketplace or upload one from your computer, read what
  it would install, install it, sign in to the tools it brought, and use them in
  a Session.
---

The console installs a plugin the way the CLI does: it reads the plugin's files,
packages them, and pushes one archive to the server. The archive is
byte-for-byte the one `stigmer install` or `stigmer push plugin` would push for
the same files, so a plugin installed from the console and one installed from
the CLI are one plugin with one digest, and the server treats a second install
of the same version as nothing to do.

There are two ways in. The **Marketplace**, in the sidebar, is where you find a
plugin someone else publishes, and its first tile is **Upload a plugin** for a
plugin folder you already have. The Library's Plugins page offers the same
upload as **Upload plugin**. Everything here works the same in the web console
and the desktop app.

## Find a plugin in the Marketplace

Open **Marketplace** in the sidebar. The sources come first, one chip each, with
the mark of the account that publishes it, its name, and how many plugins it
offers. One source is built in: Stigmer's official catalogue, published with
each release and curated so that every plugin in it is one Stigmer may ship and
one whose tools Stigmer can connect to. Any catalogue you add follows. **All
sources** is chosen by default; choose a chip to see one source alone.

Below the chips, one search box and one grid of cards across the chosen sources,
24 to a page; **Previous** and **Next** sit under the grid. A card shows the
plugin's own logo where its manifest names one and a monogram where it does not,
the plugin's display name, its author, its description, the source it comes
from, and **Install**. A card says **Installed** when your Organization already
holds a plugin of that name. Searching filters the grid by name and description
and returns to the first page.

Each source is read on its own, so the first cards appear when the first
catalogue arrives. A source that cannot be read right now says so on its chip
and in one line before the grid, with **Retry**; choose its chip to read the
whole sentence. On a development server the official source says the catalogue
is not published for that build; a source you added still works.

**Manage sources**, beside the chips, lists the catalogues the page reads and
says for each how many plugins it offers and how many it lists that cannot be
installed from here (with the reason for each). Under **Add your own catalogue**
it takes a repository you or your company publish with a marketplace file: type
it as `owner/repo`, `owner/repo@ref` or the URL a browser shows, and choose
**Add source**. The repository is read before it is added, and the source takes
the name its marketplace file gives itself unless you type one. The official
catalogue cannot be removed; a source you added can. The list is this browser's,
exactly as the CLI's is this machine's (`marketplaces` in
`~/.stigmer/config.yaml`): nothing about a source reaches the server.

## Upload a plugin from your computer

In the Marketplace, choose the **Upload a plugin** tile; or in the Library, open
**Plugins**, then **Upload plugin**. Drop a plugin folder onto the drop zone, or
choose one with **Choose a folder**; a Cursor, Claude Code, Codex or Agent
Plugins folder installs unchanged. A `.zip` of the folder works too, and a zip
that wraps everything in one directory (the shape `zip -r` gives a folder) is
read from inside that directory.

The console rebuilds the archive from the folder's files with the same ignore
rules and the same deterministic packaging `stigmer push plugin` applies, so the
preview's digest is the one the CLI prints for the same folder. If the preview
says no manifest was found, your browser may have left out files whose names
begin with a dot when the folder was picked (a Cursor or Claude Code plugin
keeps its manifest in one): zip the folder and upload the `.zip` instead.

## Read what a plugin would install

Before anything is pushed, the console reads the plugin's files and shows the
same description `stigmer validate -f` prints: the plugin's name, version and
format; the Skills, MCP servers and Sub-Agents it holds; its hooks, counted per
event; the variables its tools and hooks need; the reader's warnings, which name
every hook the plugin carries that Stigmer does not run; and what is not
installed (rules, commands and the other components Stigmer does not read). A
plugin the reader refuses is shown with every problem named, the way the CLI
prints it.

The preview also states one fact the CLI states only after the act:

- **Already installed**: your Organization holds this exact version. Install is
  not offered; there is nothing to do.
- **Upgrade**: your Organization holds another version, from whichever source it
  came. Installing makes this version the installed one: every Agent and
  conversation that lists the plugin without a version uses it from its next
  turn.

## Install, sign in, and start a chat

Choose **Install** (or **Upgrade**). The console pushes the archive and opens
the plugin's page, which is where the install ends. Install stores the plugin
and nothing beside it, so the page is where everything it holds is listed: its
MCP servers; its Skills and agents, by the names a turn uses
(`<plugin>:<skill>`); its hooks, with every command each runs and, under **Not
run on Stigmer**, the hooks Stigmer leaves out; the keys it reads; the
manifest's version, format and author; and the push's other warnings.

Each MCP server says, on its row, how it is reached and what stands between it
and its first tool call. A server that signs in with OAuth and has no sign-in in
your vault yet carries **Sign in**; choose it, grant access in the window that
opens, and the row reads **Signed in**. The sign-in is saved in your own vault:
it serves your conversations, and each teammate signs in for themselves. A
server that wants an API key names the keys. **Check tools** asks the server for
its tools right now, as you, and lists them, marking the ones the server calls
destructive; nothing is stored, so check again whenever you want the current
list.

Under **Use this plugin**, the page offers the two ways in. **Start a chat**
opens a conversation with the built-in assistant that lists the plugin, so its
Skills, agents, hooks and tools are there from the first message. **Add to an
agent** lists the plugin in one of your Agents' `plugins` in one save; the
dialog tells you when that Agent already has it, and when the Agent's own
`tools` list leaves the plugin's servers out, because the add alone would not
let it call them.
[Guard an agent's tools with hooks](/docs/guides/plugins/use-hooks) covers the
hooks.

A conversation whose plugin's server nobody has signed in to yet asks for the
sign-in before the first message, the way it asks for a missing key.

A plugin's Skills, agents and servers live in its archive and are not edited in
the console. To change one, change the plugin and install it again; to
customise, write your own Agent that lists the plugin and adds its own
instructions and tool lists.

## Remove

From the plugin's page, **Remove** deletes the plugin, the same act as
`stigmer delete plugin`. The server refuses while an Agent of your Organization
lists the plugin, and the console shows that refusal as the server phrases it,
naming the Agents.

## What the console does and does not do

- It never reads a source through the server. The GitHub trees and the official
  catalogue are fetched by the browser, so the control plane makes no outbound
  request on your behalf.
- It reads a GitHub source at one commit: the tree is listed once and every file
  is read at the commit the listing resolved to, so what you preview is what you
  install.
- It does not record where a plugin came from. As with the CLI, installing
  `thermos` from a second source, or uploading it, upgrades the `thermos` from
  the first.
- Private repositories are not sources, in the console or the CLI.
