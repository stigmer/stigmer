---
title: Service accounts
description:
  Give a CI job, a script or an integration an account of its own in your
  Organization, so it keeps working when the person who set it up leaves.
---

A script or a CI job that calls Stigmer with a person's API key stops working
when that person leaves the company, and while they stay, everything it does is
recorded as them. A service account is your Organization's own account for that
automation. It holds one Organization role, it acts only through API keys your
admins create for it, and what it creates says the service account created it.

This guide creates a service account named `ci-deploy`, gives it a key, and uses
the key in a CI job. Service accounts need a server that checks credentials: a
server that trusts every request (no `STIGMER_OIDC_ISSUER`) checks no API keys,
so it refuses to create one.

## What a service account may do

A service account holds exactly one Organization role: **Admin**, **Member** or
**Viewer**. Pick the smallest one the job needs: **Member** to create and run
Agents, **Admin** to install Skills and Plugins for the whole Organization.

Whatever its role, a service account:

- Is never an owner of its Organization
- Is never a member of a team, because a team is a group of people
- Cannot create or change API keys or service accounts, change or delete any
  account (its own included), or create or delete an Organization
- Cannot grant or revoke a role on its Organization, create an invitation, or
  create or change a platform client, an identity provider or a federated
  account, because each of these decides who belongs to the Organization
- Works only in its own Organization: its keys are refused with
  `PERMISSION_DENIED` in every other one

Where your edition shares a single resource with a person, it can share it with
a service account too: the share picker lists them in a **Service accounts**
group.

## Create a service account

Only your Organization's admins create service accounts.

In the Console, open **Settings > Service accounts** and select **New service
account**. Enter a name, `ci-deploy`, and choose its role. **Member** is
preselected. The name is unique among your Organization's service accounts, and
it is the name everything the service account creates shows as its creator.

With the CLI, in the Organization your CLI context names (or the one `--org`
names):

```bash
stigmer service-account create ci-deploy --role member
```

`--role` takes `admin`, `member` or `viewer`, and defaults to `member`.
`stigmer service-account list` lists your Organization's service accounts,
newest first.

The Members page lists service accounts apart from people, in a collapsed
**Service accounts** group, and leaves them out of the member count.

## Create its key

A service account's key speaks for the service account, not for the admin who
creates it. It keeps working when that admin leaves, it is limited to the
service account's Organization, and its raw value is shown once, when it is
created.

In the Console, right after you create the service account, the same form offers
its first key: give the key a name, such as `github-actions`, choose when it
expires, and select **Create key**. Copy the key before you dismiss it. For
another key later, open the service account from **Settings > Service accounts**
and select **New key** under **API keys**.

With the CLI:

```bash
stigmer apikey create --service-account ci-deploy --name github-actions --expires-in 90d
```

The key needs a `--name`, and takes no `--bound-org`: it works only in the
service account's Organization.

## Use the key in CI

Store the key as a secret of your CI system, named `STIGMER_API_KEY`, and pass
it to the job's environment. The CLI reads it from there on every command. Set
`STIGMER_ORG` to your Organization too, so every command names it:

```bash
# Stigmer Cloud; for your own server, register it with
# `stigmer config backend add` and `stigmer config backend use` it instead.
stigmer config backend use cloud
export STIGMER_ORG=acme
stigmer apply -f agents/
```

The SDK clients take the same key: pass `STIGMER_API_KEY` to the client as in
[SDK Overview > Authentication](/docs/sdk/overview#authentication).

Every Agent the job creates names `ci-deploy` as its creator.

## Manage a service account

Open the service account from **Settings > Service accounts**. There an admin
can:

- Rename it.
- Change its role, to any of **Admin**, **Member** or **Viewer**.
- See every key it has, when each expires and when each was last used, create
  another, and revoke one that leaked. A revoked key is refused at once.

With the CLI, an admin lists a service account's keys with
`stigmer service-account keys <name>`, and reads or revokes one by its ID with
`stigmer get apikey` and `stigmer delete apikey`, as any API key.
`stigmer list apikeys` lists only your own keys.

## Delete a service account

Delete the service account from its page, under **Delete service account**, or
with the CLI:

```bash
stigmer service-account delete ci-deploy
```

Both ask first. Deleting a service account ends every key it has at once, and
anything still using them is refused. It loses every role it holds. What it
created stays with the Organization, reachable by its admins as every Agent is.
A service account created again under the same name is a new account that
inherits none of the old one's keys or roles.

Deleting a person's account deletes their API keys the same way, so a person who
signs up again does not get their old keys back.
