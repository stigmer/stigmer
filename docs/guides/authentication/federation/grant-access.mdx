title: Grant access to federated users
description:
  Use Grants to give federated Identity Accounts access to your Organization's
  resources in Stigmer.
---

A federated Identity Account proves _who_ the user is, but not _what_ they can
do. Without a Grant, an authenticated request returns `403 Forbidden`. This page
shows how to grant roles manually so federated users can access your
Organization's resources.

<Callout type="info">
  **Using JIT provisioning?** If your Federation Issuer sets a `signInRole`,
  Stigmer grants that role the first time an account signs in to an
  Organization. You don't need to create Grants for that role. See [Enable JIT
  provisioning](/docs/guides/authentication/federation/register-federation-issuer#enable-jit-provisioning)
  for the automatic setup.
</Callout>

## How authorization works

Stigmer uses fine-grained authorization (FGA) with three elements:

| Element       | Meaning                                                                             |
| ------------- | ----------------------------------------------------------------------------------- |
| **Principal** | Who is requesting access (an Identity Account)                                      |
| **Resource**  | What they want to access (Organization, Vault, Agent, etc.)                         |
| **Relation**  | The role they hold (`owner`, `admin`, `member`, `viewer`, or a resource's own role) |

A Grant binds all three. When Stigmer receives an API call, it checks whether a
grant exists that matches the caller, the target resource, and the required
permission.

## Grant an Organization role

The most common pattern is granting a role on the Organization itself. This
gives the user access to resources within that Organization based on the
relation.

| Relation | Permissions                                                                                                                                                |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `owner`  | Everything, including deleting the Organization and choosing its owners                                                                                    |
| `admin`  | Manage people, settings, billing, and the Organization's Agents and tools; cannot read private conversations, delete the Organization or change its owners |
| `member` | Start conversations with the Agents shared with them, and create Agents when the Organization allows it                                                    |
| `viewer` | See what is shared with the Organization; cannot start conversations                                                                                       |

[Sharing and access](/docs/concepts/sharing-and-access) explains how these roles
combine with the roles on a single resource.

Use the account ID returned from
[`createFederatedAccount`](/docs/guides/authentication/federation/provision-federated-accounts)
as the principal, and the Organization ID as the resource.

<SDKTabs>
<Tab value="TypeScript">

```typescript
declare const accountId: string;
declare const organizationId: string;
// ---cut---
const grant = await stigmer.grant.create({
  principal: {
    kind: "identity_account",
    id: accountId,
  },
  resource: {
    kind: "organization",
    id: organizationId,
  },
  relation: "viewer",
});

console.log(`Granted viewer role: ${grant.metadata?.id}`);
```

</Tab>

## Complete onboarding flow

In practice, you'll provision the account and grant access in a single handler.
Here's the combined pattern:

<SDKTabs>
<Tab value="TypeScript">

```typescript
interface PlatformUser {
  oidcSubject: string;
  email: string;
  firstName: string;
  lastName: string;
  avatarUrl: string;
}
// ---cut---
async function onboardUser(
  user: PlatformUser,
  organizationId: string,
): Promise<void> {
  const issuerRef = {
    org: "acme",
    kind: ApiResourceKind.federation_issuer,
    slug: "acme-cloud-auth",
  };

  let account;
  try {
    account = await stigmer.identityAccount.getByExternalSub({
      org: "acme",
      federationIssuerRef: issuerRef,
      externalSub: user.oidcSubject,
    });
  } catch (err) {
    if (!isNotFound(err)) throw err;
    account = await stigmer.identityAccount.createFederatedAccount({
      org: "acme",
      federationIssuerRef: issuerRef,
      externalSub: user.oidcSubject,
      email: user.email,
      firstName: user.firstName,
      lastName: user.lastName,
      pictureUrl: user.avatarUrl,
    });
  }

  await stigmer.grant.create({
    principal: { kind: "identity_account", id: account.metadata?.id ?? "" },
    resource: { kind: "organization", id: organizationId },
    relation: "viewer",
  });
}
```

</Tab>
<Tab value="Go">

```go
type PlatformUser struct{ OIDCSubject, Email, NewEmail, FirstName, LastName, AvatarURL string }
// ---cut---
func onboardUser(ctx context.Context, client *stigmer.Client, user PlatformUser, organizationID string) error {
	issuerRef := &apiresource.ApiResourceReference{
		Org:  "acme",
		Kind: apiresourcekind.ApiResourceKind_federation_issuer,
		Slug: "acme-cloud-auth",
	}

	account, err := client.IdentityAccount.GetByExternalSub(ctx, &identityaccountv1.ExternalSubLookup{
		Org:                 "acme",
		FederationIssuerRef: issuerRef,
		ExternalSub:         user.OIDCSubject,
	})
	if stigmer.IsNotFound(err) {
		account, err = client.IdentityAccount.CreateFederatedAccount(ctx, &identityaccountv1.CreateFederatedAccountInput{
			Org:                 "acme",
			FederationIssuerRef: issuerRef,
			ExternalSub:         user.OIDCSubject,
			Email:               user.Email,
			FirstName:           user.FirstName,
			LastName:            user.LastName,
			PictureUrl:          user.AvatarURL,
		})
	}
	if err != nil {
		return fmt.Errorf("provision account: %w", err)
	}

	_, err = client.Grant.Create(ctx, &grantv1.GrantSpec{
		Principal: &grantv1.ApiResourceRef{Kind: "identity_account", Id: account.GetMetadata().GetId()},
		Resource:  &grantv1.ApiResourceRef{Kind: "organization", Id: organizationID},
		Relation:  "viewer",
	})
	return err
}
```

```java
interface PlatformUser { String getOidcSubject(); String getEmail(); String getNewEmail(); String getFirstName(); String getLastName(); String getAvatarUrl(); }
// ---cut---
public void onboardUser(StigmerClient client, PlatformUser user, String organizationId) {
    ApiResourceReference issuerRef = ApiResourceReference.newBuilder()
        .setOrg("acme")
        .setKind(ApiResourceKind.federation_issuer)
        .setSlug("acme-cloud-auth")
        .build();

    IdentityAccount account;
    try {
        account = client.identityAccount.getByExternalSub(ExternalSubLookup.newBuilder()
            .setOrg("acme")
            .setFederationIssuerRef(issuerRef)
            .setExternalSub(user.getOidcSubject())
            .build());
    } catch (StigmerException e) {
        if (!e.isNotFound()) throw e;
        account = client.identityAccount.createFederatedAccount(CreateFederatedAccountInput.newBuilder()
            .setOrg("acme")
            .setFederationIssuerRef(issuerRef)
            .setExternalSub(user.getOidcSubject())
            .setEmail(user.getEmail())
            .setFirstName(user.getFirstName())
            .setLastName(user.getLastName())
            .setPictureUrl(user.getAvatarUrl())
            .build());
    }

    client.grant.create(GrantSpec.newBuilder()
        .setPrincipal(ApiResourceRef.newBuilder().setKind("identity_account").setId(account.getMetadata().getId()))
        .setResource(ApiResourceRef.newBuilder().setKind("organization").setId(organizationId))
        .setRelation("viewer")
        .build());
}
```

## Revoking access

When a user leaves your platform, revoke their access. The `revokeOrgAccess`
method removes all Grants for a user across the entire Organization, including
grants on child resources like Vaults and Agents.

<SDKTabs>
<Tab value="TypeScript">

```typescript
declare const accountId: string;
declare const organizationId: string;
// ---cut---
await stigmer.grant.revokeOrgAccess({
  identityAccountId: accountId,
  org: organizationId,
});
```

</Tab>
<Tab value="Go">

```go
var accountID, organizationID string
// ---cut---
err := client.Grant.RevokeOrgAccess(ctx, &grantv1.RevokeOrgAccessInput{
	IdentityAccountId: accountID,
	Org:               organizationID,
})
```

</Tab>

```python
organization_id = ""
# ---cut---
```

</Tab>
<Tab value="Java">

```java

String organizationId;
```

</Tab>
</SDKTabs>

<Callout type="info">
  Revoking access doesn't delete the Identity Account. The user's account still
  exists but can no longer access any resources. If you also want to remove the
  account, call `identityAccount.delete` after revoking access. With a JIT
  Federation Issuer, keep the account instead: a deleted account is created
  again, with the Federation Issuer's sign-in role, at the user's next sign-in.
  A kept account does not get the sign-in role back once it has signed in to the
  Organization.
</Callout>
