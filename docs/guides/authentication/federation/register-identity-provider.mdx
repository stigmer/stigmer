---
title: Register an Identity Provider
description:
  Create an Identity Provider in Stigmer to establish trust with your platform's
  authentication system.
---

An Identity Provider tells Stigmer how to validate JWTs from your authentication
system. Once registered, Stigmer can verify tokens presented by your users and
resolve them to federated Identity Accounts.

## What you'll need

Gather these values from your OIDC provider before starting:

| Value        | Where to find it                                          | Example                                           |
| ------------ | --------------------------------------------------------- | ------------------------------------------------- |
| **JWKS URI** | Your provider's well-known configuration or admin console | `https://acme.us.auth0.com/.well-known/jwks.json` |
| **Issuer**   | The `iss` claim in JWTs your provider issues              | `https://acme.us.auth0.com/`                      |
| **Audience** | The `aud` claim in JWTs intended for Stigmer              | `https://api.acme.com/stigmer`                    |

<Callout type="tip">
  Every OIDC provider publishes a discovery document at `https://
  {provider - base - url}/.well-known/openid-configuration`. Open that URL in
  your browser and look for the `issuer` and `jwks_uri` fields—they give you two
  of the three values you need. Stigmer reads the same document when you save:
  the JWKS URI (and the userinfo endpoint, if you set one) must be the values it
  names, so that only your provider's own keys can sign tokens for its issuer.
</Callout>

<Callout type="info">
  **Use an audience that belongs to your organization.** An Identity Provider is
  identified by its issuer and its audience together, so several Organizations
  can federate with the same provider, such as a shared Auth0 tenant or Google,
  each with its own registration. An audience that another Identity Provider
  already registered at the same issuer is refused, so register one of your own
  for Stigmer (an API identifier or a client ID) instead of a shared value.
</Callout>

## Create the Identity Provider

Use the SDK to register an Identity Provider in your Organization.

<SDKTabs>
<Tab value="TypeScript">

```typescript
const idp = await stigmer.identityProvider.create({
  name: "Acme Cloud Auth",
  org: "acme",
  slug: "acme-cloud-auth",
  displayName: "Acme Cloud Auth",
  jwksUri: "https://acme.us.auth0.com/.well-known/jwks.json",
  allowedIssuers: ["https://acme.us.auth0.com/"],
  expectedAudience: "https://api.acme.com/stigmer",
});

console.log(`Created IdP: ${idp.metadata.id}`);
```

</Tab>
<Tab value="Go">

```go
idp, err := client.IdentityProvider.Create(ctx, &stigmer.IdentityProviderInput{

  AllowedIssuers:   []string{"https://acme.us.auth0.com/"},

if err != nil {
  log.Fatal(err)
}
fmt.Printf("Created IdP: %s\n", idp.Metadata.Id)
```

</Tab>


## Understand the fields

| Field                    | Required | Purpose                                                                                                                                                                                                            |
| ------------------------ | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `name`                   | Yes      | Human-readable name shown in the console                                                                                                                                                                           |
| `org`                    | Yes      | The Organization slug that owns this Identity Provider                                                                                                                                                             |
| `slug`                   | No       | URL-friendly identifier, unique within the Organization. Generated from `name` if omitted                                                                                                                          |
| `jwksUri`                | Yes      | JWKS endpoint URL. Stigmer fetches public keys from here to verify JWT signatures. Must be the `jwks_uri` each issuer's discovery document names                                                                   |
| `allowedIssuers`         | Yes      | List of `iss` values Stigmer accepts, at most 10. Tokens with a different issuer are rejected. Each must publish an OpenID Connect discovery document                                                              |
| `expectedAudience`       | Yes      | The `aud` value Stigmer expects. Tokens without this audience are rejected. With the issuer, it identifies this Identity Provider across the platform                                                              |
| `displayName`            | No       | Display name in the console, and on the sign-in button of an SSO provider. The console's provider list and detail show `name` when it is empty                                                                     |
| `isSsoProvider`          | No       | Set to `true` only when configuring console SSO for your own team. Defaults to `false`                                                                                                                             |
| `oidcClientId`           | No       | OIDC client ID for browser-based SSO. Only required when `isSsoProvider` is `true`                                                                                                                                 |
| `createAccountsOnSignIn` | No       | When `true`, Stigmer creates a federated account the first time a valid token arrives for a subject it has no account for. Defaults to `false`. Required for an SSO provider                                       |
| `signInRole`             | No       | The role an account receives the first time it signs in to an Organization through this provider. Options: `viewer`, `member`, `admin`. Unset grants nothing. Owner is not permitted. Required for an SSO provider |
| `externalIdClaim`        | No       | JWT claim name that names, by its external id, the child organization each token works in. Read on every token. See [Child organizations](/docs/guides/authentication/federation/child-organizations)              |

<Callout type="warn">
  Do not set `isSsoProvider` to `true` for a platform integration. SSO is
  designed for your own team signing in directly via the Stigmer web app. For a
  platform integration, your users authenticate on your platform and call the
  Stigmer API with their JWT.
</Callout>

## Which Organization a token works in

Every token an Identity Provider vouches for is bound to one Organization and
works there only, whatever roles the user holds elsewhere:

- Without `externalIdClaim`, the token is bound to the Identity Provider's own
  Organization (`acme` in the examples on this page).
- With `externalIdClaim`, it is bound to the child organization of `acme` whose
  external id the claim carries. Stigmer reads the claim on every token and
  refuses a token that lacks it or names no child. See
  [Child organizations](/docs/guides/authentication/federation/child-organizations#route-your-customers-sign-ins).

A bound token can still reach what belongs to no Organization, such as the
user's own Identity Account and API keys, and, in a child organization, can read
and run the Agents, Skills, MCP Servers and Plugins its parent shares with its
child organizations. It cannot create an Organization, except a child of its own
Organization, or accept an invitation to another one.

## Enable JIT provisioning

JIT (Just-In-Time) provisioning lets Stigmer create federated accounts and grant
roles automatically when users sign in. Instead of your backend calling
`createFederatedAccount` and `iamPolicy.create` for each user, you set two
fields on the Identity Provider and Stigmer handles the rest:

- `createAccountsOnSignIn` creates the account the first time a valid token
  arrives for an unknown subject.
- `signInRole` grants a role the first time an account signs in to the
  Organization its token is bound to.

With these two fields set, the first time a user signs in with a valid JWT,
Stigmer:

1. Creates a federated Identity Account using the JWT's `sub` claim and its
   `email`, `given_name` and `family_name` (or `name`) and `picture` claims,
   reading the `userinfo_endpoint` only when the token carries no email
2. Grants the **viewer** role on the Organization the token is bound to: the
   Identity Provider's owning Organization here

On later sign-ins, Stigmer finds the existing account and proceeds: it does not
refresh the profile or grant the role again. To change a user's profile, call
`updateFederatedAccount` from your backend (see
[Update a federated account](/docs/guides/authentication/federation/provision-federated-accounts#update-a-federated-account)).

### Choose the sign-in role

Set `signInRole` to the role a user should start with:

| Role     | Access level                                            |
| -------- | ------------------------------------------------------- |
| `viewer` | Read-only access to the Organization and its resources  |
| `member` | Can create and modify resources within the Organization |
| `admin`  | Full access to the Organization and all its resources   |

Stigmer grants the sign-in role once per account and Organization. If an
administrator later removes it, it stays removed, and changing `signInRole` does
not reach accounts that already signed in there. The `owner` role cannot be the
sign-in role: Organization ownership must be assigned explicitly.

### JIT without automatic role grants

If you set `createAccountsOnSignIn` to `true` and leave `signInRole` unset,
Stigmer creates the account but grants no Organization access. The user is
authenticated (Stigmer knows who they are) but not authorized (they can't access
anything). Your backend must still create IAM Policies to grant access.

This suits a platform that decides each user's role itself. A platform with
child organizations can also set `externalIdClaim` without either field: Stigmer
then binds each token to its child organization and grants nothing. See
[Child organizations](/docs/guides/authentication/federation/child-organizations).

<Callout type="warn">
  An SSO provider must set `createAccountsOnSignIn` to `true` and a
  `signInRole`; the console fills in `viewer` for you. SSO signs your own team
  in to your Organization, so routing to child organizations with
  `externalIdClaim` belongs on a non-SSO Identity Provider. See [Set up
  SSO](/docs/guides/authentication/federation/sso-login) for the SSO path.
</Callout>

<Callout type="info">
  **JIT setup is complete.** If you enabled JIT provisioning, your integration
  is ready. Users can call the Stigmer API with JWTs from your auth provider,
  and Stigmer handles account creation and role grants automatically. Skip to
  [Authentication
  flow](/docs/guides/authentication/federation/authentication-flow) to
  understand the runtime path from JWT to authorized response.
</Callout>

After creation, confirm the Identity Provider is registered correctly:

```typescript
const idp = await stigmer.identityProvider.getByReference({
```

## Multiple Identity Providers

An Organization can have multiple Identity Providers. This is useful when your
platform uses different auth providers for different regions or customer
segments. Use `listByOrg` to see all providers for an Organization:

<SDKTabs>
<Tab value="TypeScript">

```typescript
const result = await stigmer.identityProvider.listByOrg({ org: "acme" });

for (const idp of result.entries) {
  console.log(`${idp.metadata.slug}: ${idp.spec.displayName}`);
}
```

</Tab>
<Tab value="Go">

```go
result, err := client.IdentityProvider.ListByOrg(ctx, &stigmer.ListIdentityProvidersByOrgInput{
  Org: "acme",
})
if err != nil {
  log.Fatal(err)
}
for _, idp := range result.Entries {
  fmt.Printf("%s: %s\n", idp.Metadata.Slug, idp.Spec.DisplayName)
}
```

</Tab>
<Tab value="Python">

```python
result = client.identity_providers.list_by_org(ListIdentityProvidersByOrgInput(
    org="acme",
))

for idp in result.entries:
    print(f"{idp.metadata.slug}: {idp.spec.display_name}")
```

</Tab>
<Tab value="Java">

```java
IdentityProviders result = client.identityProviders().listByOrg(ListIdentityProvidersByOrgInput.builder()
    .org("acme")
    .build());

for (IdentityProvider idp : result.getEntries()) {
  System.out.println(idp.getMetadata().getSlug() + ": " + idp.getSpec().getDisplayName());

```

</Tab>

## What's next

Your Identity Provider is registered. Stigmer can now validate JWTs from your
auth system.

**JIT provisioning enabled?** Your setup is complete. Skip to
[Authentication flow](/docs/guides/authentication/federation/authentication-flow)
to understand the runtime path from JWT to authorized response.

**Manual provisioning?** There are no federated accounts yet — tokens from
unknown subjects will be rejected. Next:
[Provision federated accounts](/docs/guides/authentication/federation/provision-federated-accounts)
for your users so Stigmer can resolve their tokens to Identity Accounts.

For the full Identity Provider API reference, see
[IdentityProvider](/docs/sdk/resources/identity-provider).
