Once you've
[registered a Federation Issuer](/docs/guides/authentication/federation/register-federation-issuer),
your users can call the Stigmer API using JWTs from your auth system. With JIT
provisioning, that's all you need — accounts and roles are handled
automatically. With manual provisioning, you'll also
[provision federated accounts](/docs/guides/authentication/federation/provision-federated-accounts)
and [grant access](/docs/guides/authentication/federation/grant-access) before
users authenticate. This page explains what happens at runtime regardless of
provisioning mode.

### Step-by-step breakdown

**Steps 1--3: User authenticates on your platform.** Your app redirects the user
to your auth provider (Auth0, Okta, etc.). The provider authenticates the user
and issues a JWT. This is standard OIDC---Stigmer isn't involved yet.

**Step 4: API call with JWT.** Your app calls the Stigmer API with the JWT in
the `Authorization` header:

```bash
curl -H "Authorization: Bearer eyJhbGciOiJSUzI1NiIs..." \
     https://api.stigmer.ai/...
```

**Step 5: Fetch public keys.** Stigmer finds the one Federation Issuer whose
`allowed_issuers` contains the token's `iss` (issuer) claim and whose
`expected_audience` the token's `aud` (audience) claim carries; the issuer alone
does not pick a Federation Issuer, because several organizations can federate
with one issuer. It then fetches the JWKS from that Federation Issuer's
`jwks_uri`. Keys are cached, so this network call happens on the first request,
after cache expiry, or when a token names a key the cache doesn't hold yet (a
key rotation).

**Step 6: Validate the token.** Stigmer verifies:

- The JWT signature using the JWKS public keys
- The `iss` claim matches one of the Federation Issuer's `allowed_issuers`
- The `aud` claim matches the Federation Issuer's `expected_audience`
- The token hasn't expired (`exp` claim) and, when it carries `nbf`, is already
  valid
- The token carries a `sub` claim

If any check fails, Stigmer returns `401 Unauthorized`.

**Step 7: Resolve the identity.** Stigmer extracts the `sub` claim and looks up
a federated Identity Account matching the Federation Issuer + subject pair. If
the account exists, Stigmer proceeds. If no account exists, what happens depends
on the Federation Issuer's provisioning mode:

- **JIT-enabled Federation Issuer** (`createAccountsOnSignIn: true`) — Stigmer
  creates a federated account automatically using the JWT's `sub` claim and its
  `email`, `given_name` and `family_name` (or `name`) and `picture` claims,
  reading the `userinfo_endpoint` only when the token carries no email. The
  request proceeds.
- **Manual provisioning** (`createAccountsOnSignIn` unset) — The request fails
  with `401 Unauthorized`. Your backend must provision the account first (see
  [Provision federated accounts](/docs/guides/authentication/federation/provision-federated-accounts)).

**Step 7b: Bind the token.** Stigmer binds the token to one Organization: the
child organization its `externalIdClaim` claim names when the Federation Issuer
sets one, otherwise the Federation Issuer's own Organization. With
`externalIdClaim`, Stigmer reads the claim on every token, returning users
included, and refuses a token that lacks it or names no child of the Federation
Issuer's Organization with `401 Unauthorized`. The first time an account signs
in to its bound Organization, Stigmer grants the Federation Issuer's
`signInRole` there, when one is set.

**Step 8--9: Check authorization.** Stigmer checks whether the resolved Identity
Account has a Grant giving it the required permission on the target resource. If
no matching grant exists, the request fails with `403 Forbidden`. A target
outside the token's bound Organization and its child organizations also fails
with `403 Forbidden`, whatever roles the user holds there, unless it belongs to
no Organization (the user's own account and API keys) or is a blueprint the
bound Organization's parent shares with its child organizations, which the
request reads or runs. A token bound to a parent reaches its children as the
user's role allows: an admin of the parent is an admin in each child. With a
`signInRole`, the first sign-in creates the Grant, so step 8 succeeds for the
bound Organization. With manual provisioning, your backend must create Grants
explicitly.

**Step 10: Response.** The request proceeds normally and the response is
returned.

## Token requirements

JWTs presented to Stigmer must contain these standard OIDC claims:

| Claim | Required | Purpose                                                             |
| ----- | -------- | ------------------------------------------------------------------- |
| `iss` | Yes      | Issuer --- must match a Federation Issuer's `allowed_issuers`       |
| `sub` | Yes      | Subject --- mapped to a federated Identity Account's `externalSub`  |
| `aud` | Yes      | Audience --- must match the Federation Issuer's `expected_audience` |
| `exp` | Yes      | Expiration --- token must not be expired                            |
| `nbf` | No       | Not before --- when present, the token must already be valid        |
| `iat` | No       | Issued at --- informational, not validated                          |

## Error responses

When authentication or authorization fails, Stigmer returns specific error codes
so you can diagnose issues:

| Error              | Meaning                                      | Common cause                                                                                                      |
| ------------------ | -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `401 Unauthorized` | Token validation failed                      | Wrong issuer, wrong audience, expired token, unknown `sub`, missing or unknown external id claim                  |
| `403 Forbidden`    | Token is valid but the user lacks permission | No Grant gives the required relation on the resource, or the resource is in another Organization than the token's |

### Distinguishing 401 causes

A `401` can mean different things. Here's how to narrow it down:

| Scenario                                     | What happened                                                                                                                                                      | Fix                                                                                                                                                                               |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No Federation Issuer matches `iss` and `aud` | Stigmer routes a token by its issuer and audience together, and no Federation Issuer registered this pair                                                          | Check that `iss` is one of your Federation Issuer's `allowed_issuers`, and configure your auth provider to put its `expected_audience` in `aud`                                   |
| Signature verification failed                | JWKS keys don't match the signing key                                                                                                                              | Verify `jwks_uri` points to the correct endpoint                                                                                                                                  |
| Token expired                                | The `exp` claim is in the past                                                                                                                                     | Issue a fresh token                                                                                                                                                               |
| No federated account for this `sub`          | Account wasn't provisioned (Federation Issuers that provision manually)                                                                                            | Set `createAccountsOnSignIn` on the Federation Issuer, or call `createFederatedAccount` before the user authenticates. A JIT Federation Issuer provisions accounts automatically. |
| External id claim missing or unknown         | The Federation Issuer sets `externalIdClaim`, and the token lacks the claim, carries a non-string value, or names no child of the Federation Issuer's Organization | Put the claim in every token, and create the child organization with that `externalId`. Stigmer checks it on every sign-in, not only the first                                    |

## Calling the API from your app

Your users authenticate on your platform and get a JWT. Pass that JWT directly
to the Stigmer SDK or API. No token exchange is needed---Stigmer validates your
provider's tokens directly.

<SDKTabs>
<Tab value="TypeScript">

```typescript
import { Stigmer } from "@stigmer/client";

const stigmer = new Stigmer({
  accessToken: userJwt,
});

const session = await stigmer.session.create({
  agentRef: { slug: "support-agent" },
});
```

</Tab>
<Tab value="Go">

```go
client, err := stigmer.NewClient(
  stigmer.WithAccessToken(userJWT),
)
if err != nil {
  log.Fatal(err)
}

session, err := client.Session.Create(ctx, &stigmer.SessionInput{
  AgentRef: &stigmer.ResourceRef{Slug: "support-agent"},
})
```

</Tab>
<Tab value="Python">

```python
from stigmer import Stigmer

client = Stigmer(access_token=user_jwt)

session = client.sessions.create(SessionInput(
    agent_ref=ResourceRef(slug="support-agent"),
))
```

</Tab>
<Tab value="Java">

```java
StigmerClient client = StigmerClient.builder()
    .accessToken(userJwt)
    .build();

Session session = client.sessions().create(SessionInput.builder()
    .agentRef(ResourceRef.builder().slug("support-agent").build())
    .build());
```

</Tab>
</SDKTabs>

## Troubleshooting checklist

If federated authentication isn't working, walk through this list:

<Steps>
<Step>

### Verify the Federation Issuer exists

List your Organization's Federation Issuers and confirm yours is registered. The
CLI applies Federation Issuers from YAML (`stigmer apply`); list them through
the SDK or in the console's Federation Issuers settings.

```typescript
const page = await stigmer.federationIssuer.list({ org: "acme" });
for (const issuer of page.entries) {
  console.log(issuer.metadata?.slug, issuer.spec?.allowedIssuers);
}
```

</Step>
<Step>

### Decode the JWT and check claims

Use [JWT.io](https://jwt.io) or a local tool to inspect the token. Verify:

- `iss` matches one of your Federation Issuer's `allowed_issuers`
- `aud` matches your Federation Issuer's `expected_audience`
- `exp` is in the future
- `sub` is the value you used as `externalSub` when creating the account

</Step>
<Step>

### Confirm the federated account exists

Use `getByExternalSub` with the token's `sub` claim. If this returns
`NOT_FOUND`, the account hasn't been provisioned. For manual provisioning, call
`createFederatedAccount`. For JIT provisioning, verify that
`createAccountsOnSignIn` is `true` on your Federation Issuer.

</Step>
<Step>

### Check grants

If you get `403`, the account exists but lacks permissions. Use
`getPrincipalResourceRoles` to check what roles the account has on the target
resource. If empty, create the missing Grant.

With JIT provisioning, a `403` usually means `signInRole` is unset. The account
was provisioned automatically (identity established) but no role was granted (no
authorization). Either set `signInRole` on the Federation Issuer or create the
Grant manually. Stigmer grants the sign-in role only at an account's first
sign-in to an Organization, so an account that already signed in there gets no
role from setting `signInRole` later; create a Grant for it.

A `403` can also mean the request targets another Organization than the one the
token is bound to. A token works only in the Federation Issuer's Organization,
or in the child organization its `externalIdClaim` claim names. Check the
claim's value against the target child organization's `externalId`.

</Step>
<Step>

### Verify JWKS endpoint accessibility

Stigmer's backend must be able to reach your `jwks_uri` over HTTPS. If you're
running a private auth provider, ensure the endpoint is publicly accessible or
reachable from Stigmer's infrastructure.

</Step>
</Steps>

## Summary

The federation setup you've completed depends on your provisioning mode:

**JIT provisioning:**

| Step | What you did                                                                                                         | API used                  |
| ---- | -------------------------------------------------------------------------------------------------------------------- | ------------------------- |
| 1    | [Registered a Federation Issuer](/docs/guides/authentication/federation/register-federation-issuer) with JIT enabled | `federationIssuer.create` |
| 2    | Understood the runtime authentication flow (this page)                                                               | ---                       |

**Manual provisioning:**

| Step | What you did                                                                                                             | API used                                 |
| ---- | ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------- |
| 1    | [Registered a Federation Issuer](/docs/guides/authentication/federation/register-federation-issuer) for your auth system | `federationIssuer.create`                |
| 2    | [Provisioned federated accounts](/docs/guides/authentication/federation/provision-federated-accounts) for your users     | `identityAccount.createFederatedAccount` |
| 3    | [Granted access](/docs/guides/authentication/federation/grant-access) via Grants                                         | `grant.create`                           |
| 4    | Understood the runtime authentication flow (this page)                                                                   | ---                                      |

Your platform's users can now call the Stigmer API with JWTs from your auth
system. Stigmer validates the token, resolves the identity, checks
authorization, and processes the request.
