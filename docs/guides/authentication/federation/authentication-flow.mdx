Once you've
[registered an Identity Provider](/docs/guides/authentication/federation/register-identity-provider),
your users can call the Stigmer API using JWTs from your auth system. With JIT
provisioning, that's all you need — accounts and roles are handled
automatically. With manual provisioning, you'll also
[provision federated accounts](/docs/guides/authentication/federation/provision-federated-accounts)
and [grant access](/docs/guides/authentication/federation/grant-access) before
users authenticate. This page explains what happens at runtime regardless of
provisioning mode.

### Step-by-step breakdown

**Steps 1--3: User authenticates on your platform.** Your app redirects the user
to your auth provider (Auth0, Okta, etc.). The provider authenticates the user
and issues a JWT. This is standard OIDC---Stigmer isn't involved yet.

**Step 4: API call with JWT.** Your app calls the Stigmer API with the JWT in
the `Authorization` header:

```bash
curl -H "Authorization: Bearer eyJhbGciOiJSUzI1NiIs..." \
     https://api.stigmer.ai/...
```

**Step 5: Fetch public keys.** Stigmer finds the one Identity Provider whose
`allowed_issuers` contains the token's `iss` (issuer) claim and whose
`expected_audience` the token's `aud` (audience) claim carries; the issuer alone
does not pick a provider, because several organizations can federate with one
issuer. It then fetches the JWKS from that provider's `jwks_uri`. Keys are
cached, so this network call happens on the first request, after cache expiry,
or when a token names a key the cache doesn't hold yet (a key rotation).

**Step 6: Validate the token.** Stigmer verifies:

- The JWT signature using the JWKS public keys
- The `iss` claim matches one of the Identity Provider's `allowed_issuers`
- The `aud` claim matches the Identity Provider's `expected_audience`
- The token hasn't expired (`exp` claim) and, when it carries `nbf`, is already
  valid
- The token carries a `sub` claim

If any check fails, Stigmer returns `401 Unauthorized`.

**Step 7: Resolve the identity.** Stigmer extracts the `sub` claim and looks up
a federated Identity Account matching the Identity Provider + subject pair. If
the account exists, Stigmer proceeds. If no account exists, what happens depends
on the Identity Provider's provisioning mode:

- **JIT-enabled Identity Provider** (`createAccountsOnSignIn: true`) — Stigmer
  creates a federated account automatically using the JWT's `sub` claim and its
  `email`, `given_name` and `family_name` (or `name`) and `picture` claims,
  reading the `userinfo_endpoint` only when the token carries no email. The
  request proceeds.
- **SSO-enabled Identity Provider** (`isSsoProvider: true`) — An SSO provider
  always sets `createAccountsOnSignIn`, so Stigmer creates the account the same
  way. See [Set up SSO](/docs/guides/authentication/federation/sso-login) for
  details.
- **Manual provisioning** (`createAccountsOnSignIn` unset) — The request fails
  with `401 Unauthorized`. Your backend must provision the account first (see
  [Provision federated accounts](/docs/guides/authentication/federation/provision-federated-accounts)).

**Step 7b: Bind the token.** Stigmer binds the token to one Organization: the
child organization its `externalIdClaim` claim names when the Identity Provider
sets one, otherwise the Identity Provider's own Organization. With
`externalIdClaim`, Stigmer reads the claim on every token, returning users
included, and refuses a token that lacks it or names no child of the Identity
Provider's Organization with `401 Unauthorized`. The first time an account signs
in to its bound Organization, Stigmer grants the Identity Provider's
`signInRole` there, when one is set.

**Step 8--9: Check authorization.** Stigmer checks whether the resolved Identity
Account has an IAM Policy granting it the required permission on the target
resource. If no matching policy exists, the request fails with `403 Forbidden`.
A target outside the token's bound Organization also fails with `403 Forbidden`,
whatever roles the user holds there, unless it belongs to no Organization (the
user's own account and API keys) or is a blueprint the bound Organization's
parent shares with its child organizations, which the request reads or runs.
With a `signInRole`, the grant at the first sign-in creates the IAM Policy, so
step 8 succeeds for the bound Organization. With manual provisioning, your
backend must create IAM Policies explicitly.

**Step 10: Response.** The request proceeds normally and the response is
returned.

## Token requirements

JWTs presented to Stigmer must contain these standard OIDC claims:

| Claim | Required | Purpose                                                             |
| ----- | -------- | ------------------------------------------------------------------- |
| `iss` | Yes      | Issuer --- must match an Identity Provider's `allowed_issuers`      |
| `sub` | Yes      | Subject --- mapped to a federated Identity Account's `externalSub`  |
| `aud` | Yes      | Audience --- must match the Identity Provider's `expected_audience` |
| `exp` | Yes      | Expiration --- token must not be expired                            |
| `nbf` | No       | Not before --- when present, the token must already be valid        |
| `iat` | No       | Issued at --- informational, not validated                          |

## Error responses

When authentication or authorization fails, Stigmer returns specific error codes
so you can diagnose issues:

| Error              | Meaning                                      | Common cause                                                                                                            |
| ------------------ | -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `401 Unauthorized` | Token validation failed                      | Wrong issuer, wrong audience, expired token, unknown `sub`, missing or unknown external id claim                        |
| `403 Forbidden`    | Token is valid but the user lacks permission | No IAM Policy grants the required relation on the resource, or the resource is in another Organization than the token's |

### Distinguishing 401 causes

A `401` can mean different things. Here's how to narrow it down:

| Scenario                                     | What happened                                                                                                                                             | Fix                                                                                                                                                                       |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No Identity Provider matches `iss` and `aud` | Stigmer routes a token by its issuer and audience together, and no provider registered this pair                                                          | Check that `iss` is one of your Identity Provider's `allowed_issuers`, and configure your auth provider to put its `expected_audience` in `aud`                           |
| Signature verification failed                | JWKS keys don't match the signing key                                                                                                                     | Verify `jwks_uri` points to the correct endpoint                                                                                                                          |
| Token expired                                | The `exp` claim is in the past                                                                                                                            | Issue a fresh token                                                                                                                                                       |
| No federated account for this `sub`          | Account wasn't provisioned (manual provisioning IdPs only)                                                                                                | Set `createAccountsOnSignIn` on the Identity Provider, or call `createFederatedAccount` before the user authenticates. JIT and SSO IdPs provision accounts automatically. |
| External id claim missing or unknown         | The Identity Provider sets `externalIdClaim`, and the token lacks the claim, carries a non-string value, or names no child of the provider's Organization | Put the claim in every token, and create the child organization with that `externalId`. Stigmer checks it on every sign-in, not only the first                            |

## Calling the API from your app

Your users authenticate on your platform and get a JWT. Pass that JWT directly
to the Stigmer SDK or API. No token exchange is needed---Stigmer validates your
provider's tokens directly.

<SDKTabs>
<Tab value="TypeScript">

```typescript
import { Stigmer } from "@stigmer/sdk";

const stigmer = new Stigmer({
  accessToken: userJwt,
});

const session = await stigmer.session.create({
  agentRef: { slug: "support-agent" },
});
```

</Tab>
<Tab value="Go">

```go
client, err := stigmer.NewClient(
  stigmer.WithAccessToken(userJWT),
)
if err != nil {
  log.Fatal(err)
}

session, err := client.Session.Create(ctx, &stigmer.SessionInput{
  AgentRef: &stigmer.ResourceRef{Slug: "support-agent"},
})
```

</Tab>
<Tab value="Python">

```python
from stigmer import Stigmer

client = Stigmer(access_token=user_jwt)

session = client.sessions.create(SessionInput(
    agent_ref=ResourceRef(slug="support-agent"),
))
```

</Tab>
<Tab value="Java">

```java
StigmerClient client = StigmerClient.builder()
    .accessToken(userJwt)
    .build();

Session session = client.sessions().create(SessionInput.builder()
    .agentRef(ResourceRef.builder().slug("support-agent").build())
    .build());
```

</Tab>
</SDKTabs>

## SSO login flow

The flow above describes platform federation, where your app calls the Stigmer
API with a JWT. Console SSO uses a different path: the user signs in to the
Stigmer web console through their Organization's Identity Provider.

**Steps 1--3** discover the SSO provider. The login page calls the
unauthenticated `getSsoProvider` RPC to find the Organization's SSO
configuration (issuer, client ID, display name).

**Steps 4--8** are a standard OIDC authorization code flow between the user's
browser and the Organization's Identity Provider. Stigmer acts as an OIDC
relying party.

**Steps 9--11** follow the same token validation and identity resolution
described above. If this is the user's first login, Stigmer creates a federated
account automatically and grants the Identity Provider's `signInRole` on the
Organization. The token works in that Organization only.

For full setup instructions, see
[Set up SSO](/docs/guides/authentication/federation/sso-login).

## Troubleshooting checklist

If federated authentication isn't working, walk through this list:

<Steps>
<Step>

### Verify the Identity Provider exists

List Identity Providers for your org and confirm yours is registered.

```bash
# Using the Stigmer CLI
stigmer get identity-providers --org acme
```

</Step>
<Step>

### Decode the JWT and check claims

Use [JWT.io](https://jwt.io) or a local tool to inspect the token. Verify:

- `iss` matches one of your Identity Provider's `allowed_issuers`
- `aud` matches your Identity Provider's `expected_audience`
- `exp` is in the future
- `sub` is the value you used as `externalSub` when creating the account

</Step>
<Step>

### Confirm the federated account exists

Use `getByExternalSub` with the token's `sub` claim. If this returns
`NOT_FOUND`, the account hasn't been provisioned. For manual provisioning, call
`createFederatedAccount`. For JIT provisioning, verify that
`createAccountsOnSignIn` is `true` on your Identity Provider.

</Step>
<Step>

### Check IAM Policies

If you get `403`, the account exists but lacks permissions. Use
`getPrincipalResourceRoles` to check what roles the account has on the target
resource. If empty, create the missing IAM Policy.

With JIT provisioning, a `403` usually means `signInRole` is unset. The account
was provisioned automatically (identity established) but no role was granted (no
authorization). Either set `signInRole` on the Identity Provider or create the
IAM Policy manually. Stigmer grants the sign-in role only at an account's first
sign-in to an Organization, so an account that already signed in there gets no
role from setting `signInRole` later; grant it with an IAM Policy.

A `403` can also mean the request targets another Organization than the one the
token is bound to. A token works only in the Identity Provider's Organization,
or in the child organization its `externalIdClaim` claim names. Check the
claim's value against the target child organization's `externalId`.

</Step>
<Step>

### Verify JWKS endpoint accessibility

Stigmer's backend must be able to reach your `jwks_uri` over HTTPS. If you're
running a private auth provider, ensure the endpoint is publicly accessible or
reachable from Stigmer's infrastructure.

</Step>
</Steps>

## Summary

The federation setup you've completed depends on your provisioning mode:

**JIT provisioning:**

| Step | What you did                                                                                                          | API used                  |
| ---- | --------------------------------------------------------------------------------------------------------------------- | ------------------------- |
| 1    | [Registered an Identity Provider](/docs/guides/authentication/federation/register-identity-provider) with JIT enabled | `identityProvider.create` |
| 2    | Understood the runtime authentication flow (this page)                                                                | ---                       |

**Manual provisioning:**

| Step | What you did                                                                                                              | API used                                 |
| ---- | ------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| 1    | [Registered an Identity Provider](/docs/guides/authentication/federation/register-identity-provider) for your auth system | `identityProvider.create`                |
| 2    | [Provisioned federated accounts](/docs/guides/authentication/federation/provision-federated-accounts) for your users      | `identityAccount.createFederatedAccount` |
| 3    | [Granted access](/docs/guides/authentication/federation/grant-access) via IAM Policies                                    | `iamPolicy.create`                       |
| 4    | Understood the runtime authentication flow (this page)                                                                    | ---                                      |

Your platform's users can now call the Stigmer API with JWTs from your auth
system. Stigmer validates the token, resolves the identity, checks
authorization, and processes the request.
