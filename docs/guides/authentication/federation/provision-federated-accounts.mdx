---
title: Provision federated accounts
description:
  Create federated Identity Accounts in Stigmer for your platform's users so
  they can authenticate with your provider's JWTs.
---

For manual provisioning, your backend must explicitly create a federated
Identity Account for each user **before** that user can call the Stigmer API.
This gives you full control over who gets access and when.

<Callout type="info">
  **Using JIT provisioning?** If your Federation Issuer has
  `createAccountsOnSignIn` enabled, Stigmer creates accounts automatically on
  first authentication. You don't need to follow this page. See [Enable JIT
  provisioning](/docs/guides/authentication/federation/register-federation-issuer#enable-jit-provisioning)
  for the automatic setup.
</Callout>

## The provisioning pattern

The standard pattern is check-then-create: first check whether the user already
has a federated account, then create one if they don't. This is typically called
from a signup webhook or user-creation handler on your platform.

## Check for an existing account

Before creating an account, check whether one already exists for this user's
OIDC subject. The `getByExternalSub` method looks up a federated account by
Federation Issuer reference and external subject identifier.

<SDKTabs>
<Tab value="TypeScript">

```typescript
declare const user: {
  oidcSubject: string;
  email: string;
  newEmail: string;
  firstName: string;
  lastName: string;
  avatarUrl: string;
};
// ---cut---
try {
  const existing = await stigmer.identityAccount.getByExternalSub({
    org: "acme",
    federationIssuerRef: {
      org: "acme",
      kind: ApiResourceKind.federation_issuer,
      slug: "acme-cloud-auth",
    },
    externalSub: user.oidcSubject,
  });
  console.log(`Account already exists: ${existing.metadata?.id}`);
} catch (err) {
  if (!isNotFound(err)) throw err;
  // Account doesn't exist yet: create it below
}
```

</Tab>
<Tab value="Go">

```go

	_, err := client.IdentityAccount.GetByExternalSub(ctx, &identityaccountv1.ExternalSubLookup{
		Org:                 "acme",
		FederationIssuerRef: &apiresource.ApiResourceReference{
			Org:  "acme",
			Kind: apiresourcekind.ApiResourceKind_federation_issuer,
			Slug: "acme-cloud-auth",
		},
		ExternalSub:         user.OIDCSubject,
	})
	if stigmer.IsNotFound(err) {
		return false, nil // Account doesn't exist yet: create it below
	}
	if err != nil {
		return false, err
	}
	return true, nil
}
```

If `getByExternalSub` returned `NOT_FOUND`, create the account. The
`createFederatedAccount` method takes the user's OIDC subject, email, and
profile data.

## Understand `externalSub`

The `externalSub` field is the OIDC `sub` (subject) claim from your provider's
tokens. It uniquely identifies a user within your auth system and is the value
Stigmer uses to resolve tokens to accounts at runtime.

<Callout type="warn">
  Use the OIDC `sub` claim, not the email address. Email addresses can change
  and aren't guaranteed to be unique across Federation Issuers. The `sub` claim
  is immutable and unique within a provider.
</Callout>

Common `sub` claim formats by provider:

| Provider    | Typical `sub` format | Example                                |
| ----------- | -------------------- | -------------------------------------- |
| Auth0       | `auth0\|{user-id}`   | `auth0\|507f1f77bcf86cd799439011`      |
| Okta        | UUID                 | `00u1a2b3c4d5e6f7g8h9`                 |
| Entra ID    | UUID                 | `a1b2c3d4-e5f6-7890-abcd-ef1234567890` |
| AWS Cognito | UUID                 | `a1b2c3d4-e5f6-7890-abcd-ef1234567890` |

## Uniqueness constraint

Stigmer enforces a compound uniqueness constraint: **Federation Issuer +
external subject** (the Federation Issuer named by its Organization and slug).
This means:

- The same `sub` can exist in different Federation Issuers (different auth
  systems have independent subject spaces)
- The same `sub` in the same Federation Issuer can't be duplicated
- Attempting to create a duplicate returns `ALREADY_EXISTS`

## Full provisioning handler

Here's a complete example that combines the check-then-create pattern with error
handling:

<SDKTabs>
<Tab value="TypeScript">

```typescript
interface PlatformUser {
  oidcSubject: string;
  email: string;
  firstName: string;
  lastName: string;
  avatarUrl: string;
}
// ---cut---
async function provisionUser(user: PlatformUser): Promise<IdentityAccount> {
  const issuerRef = {
    org: "acme",
    kind: ApiResourceKind.federation_issuer,
    slug: "acme-cloud-auth",
  };

  try {
    return await stigmer.identityAccount.getByExternalSub({
      org: "acme",
      federationIssuerRef: issuerRef,
      externalSub: user.oidcSubject,
    });
  } catch (err) {
    if (!isNotFound(err)) throw err;
  }

  return stigmer.identityAccount.createFederatedAccount({
    org: "acme",
    federationIssuerRef: issuerRef,
    externalSub: user.oidcSubject,
    email: user.email,
    firstName: user.firstName,
    lastName: user.lastName,
    pictureUrl: user.avatarUrl,
  });
}
```

</Tab>
<Tab value="Go">

```go
type PlatformUser struct{ OIDCSubject, Email, NewEmail, FirstName, LastName, AvatarURL string }
// ---cut---
func provisionUser(ctx context.Context, client *stigmer.Client, user PlatformUser) (*identityaccountv1.IdentityAccount, error) {
	issuerRef := &apiresource.ApiResourceReference{
		Org:  "acme",
		Kind: apiresourcekind.ApiResourceKind_federation_issuer,
		Slug: "acme-cloud-auth",
	}

	existing, err := client.IdentityAccount.GetByExternalSub(ctx, &identityaccountv1.ExternalSubLookup{
		Org:                 "acme",
		FederationIssuerRef: issuerRef,
		ExternalSub:         user.OIDCSubject,
	})
	if err == nil {
		return existing, nil
	}
	if !stigmer.IsNotFound(err) {
		return nil, err
	}

	account, err := client.IdentityAccount.CreateFederatedAccount(ctx, &identityaccountv1.CreateFederatedAccountInput{
		Org:                 "acme",
		FederationIssuerRef: issuerRef,
		ExternalSub:         user.OIDCSubject,
		Email:               user.Email,
		FirstName:           user.FirstName,
		LastName:            user.LastName,
		PictureUrl:          user.AvatarURL,
	})
	if err != nil {
		return nil, fmt.Errorf("create federated account: %w", err)
	}
	return account, nil
}
```

## Revoke a federated account

When a user leaves your platform, revoke their Stigmer access with
`deprovisionFederatedAccount`. You choose between two modes:

- **Revoke only** (`deleteAccount: false`) — Removes all Grants for this account
  in the Organization. The account still exists but can't access anything. Use
  this when you might re-enable access later.
- **Revoke and delete** (`deleteAccount: true`) — Removes Grants **and** deletes
  the Identity Account. Use this when the user is permanently leaving and can no
  longer sign in to your auth provider.

<SDKTabs>
<Tab value="TypeScript">

```typescript
declare const user: {
  oidcSubject: string;
  email: string;
  newEmail: string;
  firstName: string;
  lastName: string;
  avatarUrl: string;
};
// ---cut---
const deprovisioned = await stigmer.identityAccount.deprovisionFederatedAccount(
  {
    org: "acme",
    federationIssuerRef: {
      org: "acme",
      kind: ApiResourceKind.federation_issuer,
      slug: "acme-cloud-auth",
    },
    externalSub: user.oidcSubject,
    deleteAccount: false,
  },
);
```

<Callout type="warn">
  If the Federation Issuer has JIT provisioning enabled, deleting the account
  does not keep the user out: their next sign-in with a valid token creates a
  new account and grants it the Federation Issuer's sign-in role. To keep such a
  user out of your Organizations, revoke only (`deleteAccount: false`). Stigmer
  grants the sign-in role once per account and Organization, so a kept account
  can still sign in but holds no role in them. To stop the user signing in at
  all, stop them at your auth provider.
</Callout>

## What's next

You've provisioned a federated account, but the user can't access any resources
yet. An authenticated request without matching Grants returns `403 Forbidden`.

Next: [Grant access](/docs/guides/authentication/federation/grant-access) to
give federated users roles on your Organization.

For the full Identity Account API reference, see
[IdentityAccount](/docs/sdk/resources/identity-account).
