If your platform serves multiple customers and each customer needs their own
isolated set of Agents, Skills, Sessions, and access controls, you create one
**platform-managed Organization** per customer. Each Organization is a full
tenant boundary — resources inside one Organization are invisible to users in
another.

## When you need this

You already have a working
[Identity Provider](/docs/guides/authentication/federation/register-identity-provider)
and understand
[federated accounts](/docs/guides/authentication/federation/provision-federated-accounts).
Now you need to extend that setup for multiple tenants:

- Your platform has multiple customers (tenants)
- Each customer needs their own Agents, Skills, MCP Servers, and Sessions
- You want tenant boundaries on Stigmer to mirror your own platform's tenant
  structure
- You want to provision users and manage resources per tenant through your
  platform's backend

## Prerequisites

Before starting, you need:

- A **Stigmer Organization** that owns your Identity Provider (for example,
  `acme`)
- A **registered Identity Provider** in that Organization (see
  [Register an Identity Provider](/docs/guides/authentication/federation/register-identity-provider))
- An **API key** with admin access to the Organization that owns the Identity
  Provider

The Identity Provider is registered once in your platform's Organization. For
each new customer, your backend creates a platform-managed Organization linked
to that Identity Provider. Each user has one federated account, which belongs to
the Identity Provider; a role on a tenant Organization is what lets that user
into the tenant. Tenants share the same authentication system but have
completely separate resources and access controls.

## Create a platform-managed Organization

When a new customer signs up on your platform, create a platform-managed
Organization for them. Three fields are specific to this pattern:

| Field                 | Purpose                                                                      |
| --------------------- | ---------------------------------------------------------------------------- |
| `managementMode`      | Set to `platform_managed` to indicate an external platform operates this org |
| `identityProviderRef` | Reference to your Identity Provider — links this org to your auth system     |
| `externalOrgId`       | Your platform's own identifier for this tenant, used for reverse lookup      |

## Provision users and place them in tenants

When a user signs up on your platform, provision their federated Identity
Account once, under the Organization that owns your Identity Provider: the `org`
field must be the Identity Provider reference's own `org`, and Stigmer refuses
any other value with `INVALID_ARGUMENT`. The account belongs to your Identity
Provider, not to a tenant. What places the user in a tenant is the role you
grant on that tenant's Organization in the next step.

boundary enforces tenant isolation at the authorization layer.

## JIT provisioning for multi-tenant platforms

With JIT provisioning and `tenantOrgClaim`, you can eliminate per-user
provisioning code entirely. You still create tenant Organizations, but Stigmer
handles account creation and role grants automatically based on a JWT claim.

### How `tenantOrgClaim` works

When you set `tenantOrgClaim` on an Identity Provider, Stigmer reads that claim
from the JWT when it creates the user's account, at their first sign-in, and
uses it to place the user in the correct tenant Organization. The resolution
algorithm:

1. Read the claim value from the JWT (for example, claim `org_id` yields value
   `tenant-123`)
2. Look up the platform-managed Organization where `identityProviderRef` matches
   this Identity Provider and `externalOrgId` matches the claim value
3. Create a federated account if one doesn't exist (because
   `autoProvisionAccounts` is `true`)
4. Grant `autoGrantRole` (default: viewer) on the resolved tenant Organization
   (because `autoGrantOnOrg` is `true`)

<Callout type="warn">
  Stigmer reads the claim only at the sign-in that creates the account. A
  returning user is not placed again: if their token names another tenant,
  Stigmer grants nothing there, so grant that role from your backend with an IAM
  Policy, as in manual setup.
</Callout>

With this configuration, your platform only needs to:

1. Create tenant Organizations with `externalOrgId` set (same as manual setup)
2. Include the tenant identifier as a claim in your JWTs (for example,
   `"org_id": "acme-tenant-alpha-id"`)

When a user authenticates, Stigmer reads the `org_id` claim from the JWT, finds
the Organization with that `externalOrgId`, creates the user's account, and
grants the member role on that Organization. No per-user provisioning code
needed.

### Error handling

If, at a user's first sign-in, the JWT does not contain the `tenantOrgClaim`, or
its value does not match any platform-managed Organization's `externalOrgId`
under this Identity Provider, Stigmer refuses the sign-in with
`401 Unauthenticated` and removes the account it began to create. This is a
fail-closed design: no account remains and no partial access is granted.

The refusal says that provisioning failed and the account was rolled back; it
does not name the tenant. When it happens, check that the token carries the
claim, and that an Organization with that `externalOrgId` exists under this
Identity Provider. When `tenantOrgClaim` is configured, include the claim in
every JWT.

### JIT vs. manual for multi-tenant

|                                | JIT with `tenantOrgClaim`              | Manual per-tenant provisioning                                   |
| ------------------------------ | -------------------------------------- | ---------------------------------------------------------------- |
| **Tenant org creation**        | You create them (same for both)        | You create them (same for both)                                  |
| **Per-user provisioning code** | None — Stigmer handles it              | Your backend calls `createFederatedAccount` + `iamPolicy.create` |
| **JWT requirement**            | Must include a tenant identifier claim | No additional claim needed                                       |
| **Role control**               | Same role for all users (configurable) | Different roles per user possible                                |
| **Tenant resolution**          | Automatic from JWT claim               | Your backend maps tenant to org                                  |

Choose JIT with `tenantOrgClaim` when all users in a tenant should get the same
role and your auth provider can include a tenant identifier in the JWT. Choose
manual provisioning when you need per-user role differences or your JWT doesn't
carry tenant information.

async function onboardTenant(tenant: PlatformTenant): Promise<string> {
  const idpRef = {
    org: "acme",
    kind: "identity_provider",
    slug: "acme-cloud-auth",
  };

  const tenantOrg = await stigmer.organization.create({
    name: tenant.name,
    slug: tenant.slug,

    managementMode: "platform_managed",
    identityProviderRef: idpRef,
    externalOrgId: tenant.id,

}

async function onboardTenantUser(
  tenantExternalId: string,
  user: PlatformUser,
): Promise<void> {
  const idpRef = {
    org: "acme",
    kind: "identity_provider",
    slug: "acme-cloud-auth",

    externalOrgId: tenantExternalId,

  // One account per user, whichever tenants they join.

    principal: { kind: "identity_account", id: accountId },
    resource: { kind: "organization", id: tenantOrg.metadata.id },

  });
}

        .resource(ApiResourceRefInput.builder().kind("organization").id(tenantOrg.getMetadata().getId()).build())
        .relation("viewer")
        .build());
}
