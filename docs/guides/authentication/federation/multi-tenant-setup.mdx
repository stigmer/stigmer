If your platform serves multiple customers and each customer needs their own
isolated set of Agents, Skills, Sessions, and access controls, you create one
**platform-managed Organization** per customer. Each Organization is a full
tenant boundary — resources inside one Organization are invisible to users in
another.

## When you need this

You already have a working
[Identity Provider](/docs/guides/authentication/federation/register-identity-provider)
and understand
[federated accounts](/docs/guides/authentication/federation/provision-federated-accounts).
Now you need to extend that setup for multiple tenants:

- Your platform has multiple customers (tenants)
- Each customer needs their own Agents, Skills, MCP Servers, and Sessions
- You want tenant boundaries on Stigmer to mirror your own platform's tenant
  structure
- You want to provision users and manage resources per tenant through your
  platform's backend

## Prerequisites

Before starting, you need:

- A **Stigmer Organization** that owns your Identity Provider (for example,
  `acme`)
- A **registered Identity Provider** in that Organization (see
  [Register an Identity Provider](/docs/guides/authentication/federation/register-identity-provider))
- An **API key** with admin access to the Organization that owns the Identity
  Provider

The Identity Provider is registered once in your platform's Organization. For
each new customer, your backend creates a platform-managed Organization linked
to that Identity Provider. Each user has one federated account, which belongs to
the Identity Provider; a role on a tenant Organization is what lets that user
into the tenant. Each token your auth provider issues names one tenant in a
claim, and Stigmer lets that token work in that tenant only. Tenants share the
same authentication system but have completely separate resources and access
controls.

## Create a platform-managed Organization

When a new customer signs up on your platform, create a platform-managed
Organization for them. Three fields are specific to this pattern:

| Field                 | Purpose                                                                      |
| --------------------- | ---------------------------------------------------------------------------- |
| `managementMode`      | Set to `platform_managed` to indicate an external platform operates this org |
| `identityProviderRef` | Reference to your Identity Provider — links this org to your auth system     |
| `externalOrgId`       | Your platform's own identifier for this tenant, used for reverse lookup      |

```typescript
const tenantOrg = await stigmer.organization.create({
  name: "Tenant Alpha",
  slug: "tenant-alpha",
  description: "Acme Cloud customer: Tenant Alpha",
  managementMode: "platform_managed",
  identityProviderRef: {
    org: "acme",
    kind: "identity_provider",
    slug: "acme-cloud-auth",
```

## Bind each token to its tenant

Every token an Identity Provider vouches for works in one Organization only.
Without `tenantOrgClaim`, that Organization is the Identity Provider's own
(`acme` here), so your users' tokens would never reach a tenant. Set
`tenantOrgClaim` to the name of the JWT claim that carries your tenant ID, and
put that claim in every token your auth provider issues for Stigmer:

```json
{
  "iss": "https://acme.us.auth0.com/",
  "sub": "auth0|507f1f77bcf86cd799439011",
  "aud": "https://api.acme.com/stigmer",
  "org_id": "acme-tenant-alpha-id"
}
```

On every request, Stigmer:

1. Reads the claim value from the token (here, claim `org_id` yields
   `acme-tenant-alpha-id`)
2. Looks up the platform-managed Organization whose `identityProviderRef` is
   this Identity Provider and whose `externalOrgId` matches the value
3. Binds the token to that Organization: the token works there and nowhere else,
   whatever roles the user holds in other tenants

Stigmer reads the claim on every token, from a user's first sign-in to their
latest. A user who belongs to several tenants signs in to each one with a token
that names it.

<Callout type="info">
  **Example.** Alice is a user at two of your customers, Alpha and Beta, and
  holds a role in both tenant Organizations. Her token that claims Alpha is
  refused in Beta, even though she holds a role there. To work in Beta, she
  signs in with a token that claims Beta. If your Identity Provider sets a
  `signInRole`, the first time she signs in to Beta with a Beta token she
  receives that role in Beta, once.
</Callout>

Set `tenantOrgClaim` when you register the Identity Provider:

`tenantOrgClaim` works on its own: Stigmer binds each token to its tenant and
grants nothing. That suits a platform that creates accounts and grants roles
from its backend, as the next two sections show. To have Stigmer create accounts
and grant a role as well, see
[Create accounts and grant a role at sign-in](#create-accounts-and-grant-a-role-at-sign-in).

### What a bound token can reach

A token bound to a tenant can still reach:

- The tenant Organization's resources, as the user's role there allows
- What belongs to no Organization: the user's own Identity Account and API keys
- Agents, Skills, Workflows, MCP Servers and Plugins shared at Platform
  visibility, to read and to run

It cannot create an Organization or accept an invitation to another
Organization.

### Errors

| Error                       | When                                                                                            | What to do                                                                                     |
| --------------------------- | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `UNAUTHENTICATED` (`401`)   | The token lacks the `tenantOrgClaim` claim, or its value is not a string                        | Put the claim, as a string, in every token your auth provider issues for Stigmer               |
| `UNAUTHENTICATED` (`401`)   | The claim names no platform-managed Organization's `externalOrgId` under this Identity Provider | Create the tenant Organization with that `externalOrgId`, or fix the value your provider sends |
| `PERMISSION_DENIED` (`403`) | The token names one tenant and the request targets another                                      | Sign in with a token that names the tenant the request targets                                 |
| `PERMISSION_DENIED` (`403`) | The token names the right tenant, but the user's role there doesn't allow the request           | Grant a role on the tenant Organization                                                        |

Stigmer refuses a missing or unknown claim on every sign-in, returning users
included, and the refusal does not name the tenant. A first sign-in refused this
way leaves no account behind. This is a fail-closed design: a token that names
no known tenant reaches nothing.

## Provision users and place them in tenants

When a user signs up on your platform, provision their federated Identity
Account once, under the Organization that owns your Identity Provider: the `org`
field must be the Identity Provider reference's own `org`, and Stigmer refuses
any other value with `INVALID_ARGUMENT`. The account belongs to your Identity
Provider, not to a tenant. What places the user in a tenant is the role you
grant on that tenant's Organization in the next step, and what lets their token
reach the tenant is the claim that [binds it](#bind-each-token-to-its-tenant).

on `tenant-alpha` cannot see resources in `tenant-beta`. The token is bound too:
a token that names `tenant-alpha` works in `tenant-alpha` only. The Organization
boundary enforces tenant isolation at the authorization layer.

drop per-user provisioning code. You still create tenant Organizations, but
Stigmer creates each user's account the first time they sign in and grants the
sign-in role the first time they sign in to each tenant.

With this configuration, your platform only needs to:

1. Create tenant Organizations with `externalOrgId` set (same as manual setup)
2. Put the tenant identifier in a claim in every JWT (for example,
   `"org_id": "acme-tenant-alpha-id"`)

The first time a user signs in to a tenant, Stigmer reads the `org_id` claim,
finds the Organization with that `externalOrgId`, creates the user's account if
they have none, and grants `member` on that Organization. When the same user
first signs in to a second tenant, with a token that names it, Stigmer grants
`member` there too. No per-user provisioning code needed.

<Callout type="info">
  Stigmer grants the sign-in role once per account and tenant. If an
  administrator later removes it, it stays removed, and changing `signInRole`
  does not reach users who already signed in to that tenant. To give one user a
  different role, grant it from your backend with an IAM Policy. The `owner`
  role cannot be the sign-in role.
</Callout>

### Automatic vs. manual for multi-tenant

|                                | `createAccountsOnSignIn` and `signInRole`                          | Manual per-tenant provisioning                                   |
| ------------------------------ | ------------------------------------------------------------------ | ---------------------------------------------------------------- |
| **Tenant org creation**        | You create them (same for both)                                    | You create them (same for both)                                  |
| **Per-user provisioning code** | None — Stigmer handles it                                          | Your backend calls `createFederatedAccount` + `iamPolicy.create` |
| **Tenant claim in every JWT**  | Required (same for both)                                           | Required (same for both)                                         |
| **Role control**               | One role for every user, granted at their first sign-in per tenant | Different roles per user possible                                |

Choose automatic account creation when every user in a tenant should start with
the same role. Choose manual provisioning when you need per-user role
differences, or when you want to decide who gets an account before they sign in.

## Complete tenant onboarding flow (manual)

Here's the full pattern that runs when a new customer signs up on your platform.
`onboardTenantUser` reuses `provisionUser`, the check-then-create handler from
[Provision federated accounts](/docs/guides/authentication/federation/provision-federated-accounts#full-provisioning-handler),
so a user who joins a second tenant keeps their one account and gains a role in
the new tenant:

```typescript
async function onboardTenant(tenant: PlatformTenant): Promise<string> {
  const idpRef = {
    org: "acme",
    kind: "identity_provider",
    slug: "acme-cloud-auth",
  };

  const tenantOrg = await stigmer.organization.create({
    name: tenant.name,
    slug: tenant.slug,
    description: `Acme Cloud customer: ${tenant.name}`,
    managementMode: "platform_managed",
    identityProviderRef: idpRef,
    externalOrgId: tenant.id,
  });

  return tenantOrg.metadata.id;
}

async function onboardTenantUser(
  tenantExternalId: string,
  user: PlatformUser,
): Promise<void> {
  const idpRef = {
    org: "acme",
    kind: "identity_provider",
    slug: "acme-cloud-auth",
  };

  const tenantOrg = await stigmer.organization.getByExternalOrgId({
    identityProviderRef: idpRef,
    externalOrgId: tenantExternalId,
  });

  // One account per user, whichever tenants they join.
  const accountId = await provisionUser(user);
```
