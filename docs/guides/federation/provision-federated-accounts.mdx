---
title: Provision federated accounts
description:
  Create federated Identity Accounts in Stigmer for your platform's users so
  they can authenticate with your provider's JWTs.
---

For manual provisioning, your backend must explicitly create a federated
Identity Account for each user **before** that user can call the Stigmer API.
This gives you full control over who gets access and when.

<Callout type="info">
  **Using JIT provisioning?** If your Identity Provider has
  `autoProvisionAccounts` enabled, Stigmer creates accounts automatically on
  first authentication. You don't need to follow this page. See [Enable JIT
  provisioning](/docs/guides/federation/register-identity-provider#enable-jit-provisioning)
  for the automatic setup.
</Callout>

<Callout type="info">
  **Self-managed SSO is different.** If your Identity Provider has SSO enabled,
  Stigmer creates accounts automatically on first login. You don't need to
  provision accounts manually. See [Set up
  SSO](/docs/guides/federation/sso-login) for details.
</Callout>

## The provisioning pattern

The standard pattern is check-then-create: first check whether the user already
has a federated account, then create one if they don't. This is typically called
from a signup webhook or user-creation handler on your platform.

## Check for an existing account

Before creating an account, check whether one already exists for this user's
OIDC subject. The `getByExternalSub` method looks up a federated account by
Identity Provider reference and external subject identifier.

<SDKTabs>
<Tab value="TypeScript">

```typescript
try {
  const existing = await stigmer.identityAccount.getByExternalSub({
    org: "acme",
    identityProviderRef: {
      org: "acme",
      kind: "identity_provider",
      slug: "acme-cloud-auth",
    },
    externalSub: user.oidcSubject,
  });
  console.log(`Account already exists: ${existing.metadata.id}`);
} catch (err) {
  if (err.code === "NOT_FOUND") {
    // Account doesn't exist yet — create it below
  } else {
    throw err;
  }
}
```

</Tab>
<Tab value="Go">


## Create the federated account

If `getByExternalSub` returned `NOT_FOUND`, create the account. The
`createFederatedAccount` method takes the user's OIDC subject, email, and
profile data.

## Understand `externalSub`

The `externalSub` field is the OIDC `sub` (subject) claim from your provider's
tokens. It uniquely identifies a user within your auth system and is the value
Stigmer uses to resolve tokens to accounts at runtime.

<Callout type="warn">
  Use the OIDC `sub` claim, not the email address. Email addresses can change
  and aren't guaranteed to be unique across Identity Providers. The `sub` claim
  is immutable and unique within a provider.
</Callout>

Common `sub` claim formats by provider:

| Provider    | Typical `sub` format | Example                                |
| ----------- | -------------------- | -------------------------------------- |
| Auth0       | `auth0\|{user-id}`   | `auth0\|507f1f77bcf86cd799439011`      |
| Okta        | UUID                 | `00u1a2b3c4d5e6f7g8h9`                 |
| Entra ID    | UUID                 | `a1b2c3d4-e5f6-7890-abcd-ef1234567890` |
| AWS Cognito | UUID                 | `a1b2c3d4-e5f6-7890-abcd-ef1234567890` |

## Uniqueness constraint

Stigmer enforces a compound uniqueness constraint: **Organization + Identity
Provider + external subject**. This means:

- The same `sub` can exist in different Identity Providers (different auth
  systems have independent subject spaces)
- The same `sub` in the same Identity Provider can't be duplicated
- Attempting to create a duplicate returns `ALREADY_EXISTS`

## Full provisioning handler

Here's a complete example that combines the check-then-create pattern with error
handling:

<SDKTabs>
<Tab value="TypeScript">

```typescript
async function provisionUser(user: PlatformUser): Promise<string> {
  const idpRef = {
    org: "acme",
    kind: "identity_provider",
    slug: "acme-cloud-auth",
  };

  try {
    const existing = await stigmer.identityAccount.getByExternalSub({
      org: "acme",
      identityProviderRef: idpRef,
      externalSub: user.oidcSubject,
    });
    return existing.metadata.id;
  } catch (err) {
    if (err.code !== "NOT_FOUND") throw err;
  }

  const account = await stigmer.identityAccount.createFederatedAccount({
    org: "acme",
    identityProviderRef: idpRef,
    externalSub: user.oidcSubject,
    email: user.email,
    firstName: user.firstName,
    lastName: user.lastName,
    pictureUrl: user.avatarUrl,
  });

  return account.metadata.id;
}
```

</Tab>
<Tab value="Go">

```go
func provisionUser(ctx context.Context, client *stigmer.Client, user PlatformUser) (string, error) {
  idpRef := &stigmer.ResourceRef{
    Org:  "acme",
    Kind: "identity_provider",
    Slug: "acme-cloud-auth",
  }

  existing, err := client.IdentityAccount.GetByExternalSub(ctx, &stigmer.ExternalSubLookup{
    Org:                 "acme",
    IdentityProviderRef: idpRef,
    ExternalSub:         user.OIDCSubject,
  })
  if err == nil {
    return existing.Metadata.Id, nil
  }
  if status.Code(err) != codes.NotFound {
    return "", err
  }

  account, err := client.IdentityAccount.CreateFederatedAccount(ctx, &stigmer.CreateFederatedAccountInput{
    Org:                 "acme",
    IdentityProviderRef: idpRef,
    ExternalSub:         user.OIDCSubject,
    Email:               user.Email,
    FirstName:           user.FirstName,
    LastName:            user.LastName,
    PictureUrl:          user.AvatarURL,
  })
  if err != nil {
    return "", fmt.Errorf("create federated account: %w", err)
  }

  return account.Metadata.Id, nil
}
```

## Update a federated account

those changes to Stigmer with `updateFederatedAccount`. The method uses the same
natural-key lookup as provisioning: Identity Provider reference + external
subject.

The update replaces all profile fields at once. Pass the current values for any

`externalSub`) are immutable and used only for lookup.

## Revoke a federated account

When a user leaves your platform, revoke their Stigmer access with
`deprovisionFederatedAccount`. You choose between two modes:

- **Revoke only** (`deleteAccount: false`) — Removes all IAM Policies for this
  account in the Organization. The account still exists but can't access
  anything. Use this when you might re-enable access later.
- **Revoke and delete** (`deleteAccount: true`) — Removes IAM Policies **and**
  deletes the Identity Account. Use this when the user is permanently leaving.

<SDKTabs>
<Tab value="TypeScript">

```typescript
const deprovisioned = await stigmer.identityAccount.deprovisionFederatedAccount(
  {
    org: "acme",
    identityProviderRef: {
      org: "acme",
      kind: "identity_provider",
      slug: "acme-cloud-auth",
    },
    externalSub: user.oidcSubject,
    deleteAccount: false,

);
```

<Callout type="warn">
  If you revoke-only and the Identity Provider has SSO enabled, the user can
  sign in again through SSO and regain viewer access automatically. To
  permanently block an SSO user, use `deleteAccount: true` or disable the
  Identity Provider.
</Callout>

## What's next

You've provisioned a federated account, but the user can't access any resources
yet. An authenticated request without matching IAM Policies returns
`403 Forbidden`.

Next: [Grant access](/docs/guides/federation/grant-access) to give federated
users roles on your Organization.

For the full Identity Account API reference, see
[IdentityAccount](/docs/sdk/resources/identity-account).
