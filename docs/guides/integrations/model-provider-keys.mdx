description:
  Run your Agents on Stigmer Cloud with your Organization's own Anthropic,
  OpenAI and Google keys, on the provider's API or on your own compatible
  endpoint.
---

On Stigmer Cloud every model call an Agent run on the Stigmer harness makes runs
on a key your Organization owns, on every plan. An admin adds an Anthropic key,
an OpenAI key, a Google key, or any of them together, and your Agents run on
them: the provider bills your Organization directly, and Stigmer meters the
calls and charges nothing for them. Stigmer never runs a model call on a key of
its own. Claude-harness runs work the same way, on your Organization's Anthropic
key: a Claude run runs Claude models only, so it always needs that key, whatever
its model.

Stigmer tells you which models can run before you try one. **Models &
providers**, in the console's sidebar, shows each provider, whether it is
connected and by whom, and the models it unlocks on each engine. The model
picker marks a model whose provider is not connected ("Needs an Anthropic key"),
and the new-conversation screen holds **Send** until it is. A run that still
needs a provider your Organization has no key for is refused before it starts:

```
This organization has no Anthropic key for model 'claude-sonnet-4-6', so the run
was not started. An admin can add one in Models & providers.
```

## Add a key

1. Open **Models & providers**. Every member sees which providers are connected;
   adding, replacing and removing a key needs an admin.
2. Choose **Connect Anthropic** (or OpenAI, or Google) on the provider's card
   and paste the key.
3. To use the provider's own API, go on. For your own endpoint, choose **Use
   your own endpoint** and give its **Base URL** (see below).
4. Choose **Connect Anthropic** again to save it.

Stigmer checks the key once with the provider before saving it, and refuses a
key the provider rejects. The card then says **Checked with Anthropic**, or
**Saved, not checked** when the provider did not answer the check; such a key is
saved, and its first run tells you whether it works. A saved key is never shown
again, only its last four characters. **Replace key** saves a new key over it;
**Remove** deletes it, and runs that need that provider are refused until a key
serves your Organization again.

From a terminal, `stigmer provider-key list` shows the same, and an admin saves
and removes keys with `stigmer provider-key set anthropic` and
`stigmer provider-key delete anthropic`; the providers are named `anthropic`,
`openai` and `google`. The key is read from a prompt, or from standard input
with `--key-stdin`, never from the command line.

## Use a Google key

Google's provider runs Gemini models. Create its key in
[Google AI Studio](https://aistudio.google.com/api-keys) and save it under
Google, on the **Google** card's **Connect Google** or with
`stigmer provider-key set google`. A Gemini key is a Google key:
`stigmer provider-key set gemini` is refused with "Gemini keys are saved under
google." Keys AI Studio makes today begin with `AQ.`; older ones begin with
`AIza`. Google bills the calls to you: AI Studio's
[billing page](https://aistudio.google.com/billing) is where you add a payment
method or raise a limit, and its
[status page](https://aistudio.google.com/status) says whether Google is having
trouble.

A Gemini model is named with the `google:` prefix and Google's own name for the
model, such as `google:gemini-4-hydrogen`, the form for a model the catalog does
not list ([below](#run-a-model-your-endpoint-serves)): the Stigmer catalog lists
no Gemini models, so a Gemini model has no catalog price. Stigmer calls Gemini
on Google's own protocol, tool calls included.

## The rules

- **One key per provider.** Your Organization holds at most one Anthropic key,
  one OpenAI key and one Google key. Saving another replaces the one you have.
- **A provider is a protocol.** The Anthropic slot serves Anthropic's API or any
  endpoint that speaks it; the OpenAI slot serves OpenAI's API or any endpoint
  that speaks OpenAI's API (an Azure OpenAI deployment that accepts a bearer
  key, a company gateway such as LiteLLM, a vLLM server you run); the Google
  slot serves Google's Gemini API or a gateway that speaks Gemini's own
  protocol.
- **Base URL is what the provider's SDK takes.** OpenAI's usually ends in `/v1`
  (`https://gateway.example.com/v1`), Anthropic's does not
  (`https://gateway.example.com`), and Google's is the address before Google's
  own `/v1beta/...` path (`https://gateway.example.com/google`). Stigmer appends
  the provider's request path and does not repeat a trailing `/v1`, so
  `https://my-resource.openai.azure.com/openai/v1` serves chat completions at
  `/openai/v1/chat/completions`.
- **Only `https`, only public addresses.** A base URL must be an `https` URL
  with no user name, password, query or fragment, and it must resolve to a
  public address. Stigmer refuses a plain `http` URL, `localhost`, and private
  or link-local addresses, both when you save the key and on every call.
- **The key is sent the provider's way.** Anthropic-compatible endpoints receive
  it as `x-api-key`, OpenAI-compatible ones as `Authorization: Bearer`, and
  Gemini-compatible ones as `x-goog-api-key`. An endpoint that needs another
  header or cloud credentials (Bedrock, Vertex) is not served by a key.
- **A child Organization uses its parent's key.** An Organization created under
  another is served by the parent's key for any provider it holds none of. The
  child sees that key read-only; its own key for a provider always wins.

## Run a model your endpoint serves

A model the Stigmer catalog does not list, served by your own endpoint, is named
with its provider slot as a prefix: `openai:<name>`, `anthropic:<name>` or
`google:<name>`. For example, with the OpenAI slot pointed at your vLLM server,
an Agent whose model is `openai:llama-3.3-70b` runs on it:

```yaml
apiVersion: agentic.stigmer.ai/v1
kind: Agent
metadata:
  name: variance-reporter
spec:
  instructions: Report each account's variance against budget.
  harness: HARNESS_STIGMER
  run_config:
    model_name: openai:llama-3.3-70b
```

Stigmer accepts the form wherever a model on the Stigmer harness is named,
subagents included. Settings that depend on what Stigmer knows about a model,
the fast service tier and explicit thinking, stay limited to the catalog's
models, and a model the catalog does not list has no catalog price.

A Gemini model runs on the Google slot, named `google:<name>` (see
[Use a Google key](#use-a-google-key)). A model family with no slot of its own,
such as Kimi, GLM or Grok, runs on the OpenAI slot: point it at an
OpenAI-compatible endpoint that serves the family, and name the model
`openai:<name>`. Don't reach Gemini that way: Gemini's OpenAI-compatible
endpoint fails a tool call's second step, so an Agent that uses tools stops
there.

## When a call fails on your key

A failure on your key, such as a rejected key or an exhausted provider balance,
is reported as your key's, with the provider's own message, so you know to fix
it in your provider account or replace the key here. Stigmer never retries the
call on another key.

## Visitors of a chat link or channel

Someone chatting with your Agent through a chat link or a channel is not told
about your keys. When your Organization has no key for the Agent's model, they
read: "This agent isn't set up to answer yet. Its owner needs to connect a model
provider." Try your own chat link to see it; the fix is a key in **Models &
providers**.

## Your own machine and self-hosted servers

A self-hosted Stigmer server holds no provider keys: its runners call the
providers with keys from their own environment. On your own machine,
`stigmer setup` saves the Anthropic key the runner uses; an `OPENAI_API_KEY` set
in the shell you start Stigmer from gives it OpenAI, and a `GEMINI_API_KEY` set
there gives it Google. `stigmer up` tells the server which providers the runner
reaches, whether by a key, a cloud backend (Vertex, Bedrock, Foundry) or a
gateway. **Models & providers** then shows them, and a run whose provider the
runner cannot reach is refused before it starts:

```
This server's runners have no Anthropic key for model 'claude-sonnet-4-6', so the
run was not started. On your own machine, run `stigmer setup`, then
`stigmer down && stigmer up`.
```

For an OpenAI model the refusal says to set `OPENAI_API_KEY` instead, and for a
Gemini model `GEMINI_API_KEY`. To give your machine's runner Google, start
Stigmer again from a shell that holds the key:

```bash
export GEMINI_API_KEY=<your key>
stigmer down && stigmer up
```

`stigmer status` then lists `google (key)` among the providers the runner
reaches. `stigmer setup` asks for the Anthropic key only, and the runner never
reads `GOOGLE_API_KEY`.

A Docker Compose or Kubernetes install tells its server the same with
`STIGMER_RUNNER_PROVIDERS`, the providers its runners reach
([What the runner is given](/docs/guides/self-hosting/runners#what-the-runner-is-given)).
Without it the server cannot see the runners' keys, so it refuses nothing and
the runner's own error names a missing key. The `openai:<name>`,
`anthropic:<name>` and `google:<name>` forms work there too. A self-hosted
runner calls Google's own Gemini API with its `GEMINI_API_KEY`; a Google base
URL is a Stigmer Cloud key's setting.
