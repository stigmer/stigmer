An MCP Server definition tells Stigmer where a server is and how to reach it.
Connecting it is how Stigmer learns what the server can do: one action discovers
every tool the server exposes and decides which of them may run without a
human's approval. This guide walks through connecting a server from the web
console and reading what comes back.

<Callout type="info">
  New to tools in Stigmer? Start with the [Tools concept
  page](/docs/concepts/tools) for the foundational model before following this
  guide.
</Callout>

## Find the server in your Library

Open **Library** in the sidebar and choose **MCP Servers**. The page lists every
MCP Server your Organization holds, in a card grid: the servers a plugin
installed and the servers you defined yourself. Each card shows the server's
name, a short description, and the Organization it belongs to; a server that
came from a plugin says so at the top of its page.

If the server you need is not there yet, get it one of two ways. Install a
plugin that carries it, from the Marketplace or from a folder on your computer
([Install from the console](/docs/guides/plugins/install-from-the-console); in
the CLI, [Install a plugin](/docs/guides/plugins/install-a-plugin) or
[Install from a marketplace](/docs/guides/plugins/install-from-a-marketplace)).
Or write the definition by hand, as the
[Connect your tools](/docs/getting-started/connect-tools) tutorial does.

A remote (HTTP) server works on any session, local or cloud-hosted. A stdio
server, a local subprocess launched with `npx`, `uvx` or a binary, runs only on
a local runner; you can still define one for local-runner sessions.

## Connect an MCP Server

When you open a server's detail view and click **Connect**, Stigmer performs
three steps in a single action:

1. **Discovers tools** — Connects to the live server and enumerates every tool
   it exposes, capturing names, descriptions, and input schemas.
2. **Classifies approval policies** — A lightweight model evaluates each tool to
   determine whether it should run automatically or require human approval.
3. **Stores the results** — Discovered tools and their approval classifications
   are saved on the MCP Server's status, ready for any Agent that references it.

The whole process takes a few seconds. When it finishes, the detail view updates
to show the discovered tools and their approval policies.

<Callout type="info">
  **stdio servers are local-runner-only.** In Stigmer Cloud, connecting a stdio
  server (launched via `npx`, `uvx`, or a binary) is refused — cloud compute
  never spawns stdio subprocesses. The server remains fully usable on sessions
  that run on a local runner (the desktop app or `stigmer server`), where its
  tools are discovered automatically when the session starts. If a connect
  fails, the error message names the likely cause for the server's transport.
</Callout>

## What changes after connecting

### Tools tab

The tools tab lists every tool the server exposes. Each entry shows the tool's
name and description — the same information the Agent sees when deciding which
tool to call. In the demo above, Neon exposes five tools: `list_projects`,
`get_database_tables`, `describe_table_schema`, `explain_sql_statement`, and
`run_sql`.

### Policies tab

The policies tab shows the approval classification for each tool. Read-only
tools like `list_projects` and `describe_table_schema` are classified for
automatic approval — the Agent can call them without pausing. Tools with side
effects, like `run_sql`, are flagged for human approval.

These classifications come in two tiers:

- **Pinned approvals** are set by the server author in the MCP Server
  definition. They never change on reconnect.
- **Classified approvals** are generated by the classifier each time you
  connect. New tools are classified automatically.

Pinned policies always take precedence. You can override any classification by
editing the MCP Server definition or adding `tool_approval_overrides` on your
Agent.

## Authentication patterns at a glance

Some servers need credentials to reach the systems behind them. Three patterns
cover the range:

| Pattern                   | When it applies                                                  | What happens on Connect                                        |
| ------------------------- | ---------------------------------------------------------------- | -------------------------------------------------------------- |
| **No credentials**        | The server works without authentication (Context7 without a key) | Connects immediately — no extra steps                          |
| **Environment variables** | The server uses API keys or connection strings (Tavily, Neon)    | You enter the value in the credential form before connecting   |
| **OAuth**                 | The server uses OAuth with a vendor like GitHub, Slack, or Figma | Stigmer redirects you through the OAuth flow to obtain a token |
| **OAuth-only (hosted)**   | The hosted endpoint accepts only OAuth tokens (Notion, Monday)   | Only "Sign in" is offered — manual token entry is hidden       |

<Callout type="info">
  Some hosted endpoints — such as Notion (`mcp.notion.com`) and Monday
  (`mcp.monday.com`) — accept **only** an OAuth-obtained token and reject a
  personal API token or integration secret pasted into the credential form. For
  these servers Stigmer offers just the "Sign in" flow and hides manual token
  entry, so you are never sent down a path that cannot succeed. If you connect
  such a server another way (for example the CLI `--env` flag or `--dry-run`),
  you will get a clear message explaining that OAuth is required.
</Callout>

<Callout type="info">
  OAuth patterns — including automatic discovery (DCR) and vendor-specific flows
  — are covered in depth in the [OAuth for
  tools](/docs/guides/integrations/oauth-for-tools) guide. Organization-level
  credential overrides are in [Bring Your Own OAuth
  App](/docs/guides/integrations/bring-your-own-oauth).
</Callout>

## Wire tools to your Agent

Once an MCP Server is connected, reference it from your Agent definition using
`mcp_server_usages`:

```yaml validate-as="Agent"
spec:
  mcp_server_usages:
    - mcp_server_ref:
        kind: mcp_server
        slug: mcp-server-postgres
      enabled_tools:
        - query
        - list_tables
        - describe_table
```

Each usage entry controls which tools the Agent can call. An empty
`enabled_tools` list means all discovered tools are available. You can also add
`tool_approval_overrides` to customize approval behavior per Agent.

For a hands-on guide to wiring tools to an Agent and running a Session, see the
[Connect your tools](/docs/getting-started/connect-tools) tutorial.
