title: Connect an MCP server
description:
  Add an MCP server by its address as a plugin of its own, sign in to it, see
  its tools and which of them ask for approval, and use it in a chat or an
  Agent; or give one Agent a server of its own in one call.
---

An MCP server reaches an Agent two ways: in a plugin the Agent lists, or written
in the Agent itself under `mcp_servers`. Use a plugin to share a server across
Agents and chats: a plugin from a marketplace may carry the servers you need
already, and to use one server at an address, Stigmer builds a plugin holding
just that server and installs it, the way `claude mcp add` adds a server to
Claude Code. This guide adds a server, signs in to it, reads its tools, and puts
it to work. When one Agent needs a server, or you create Agents from code,
[give the Agent its own MCP server](#give-an-agent-its-own-mcp-server) instead.

<Callout type="info">
  New to tools in Stigmer? Start with the [Tools concept
  page](/docs/concepts/tools) for the foundational model before following this
  guide.
</Callout>

## Connect an MCP server

From the console:

1. Open **Library** in the sidebar and choose **Plugins**.
2. Choose **Add MCP server**. Give it a name (lowercase letters, digits, dots
   and hyphens; the plugin is named after it), the server's URL, an optional
   description, and the headers it is sent with.
3. Choose **Add**. Stigmer installs the plugin in your Organization and opens
   its page.

From the CLI:

```bash
stigmer mcp add linear https://mcp.linear.app/mcp
```

A server that takes a key gets it in a header. Name the key as `${NAME}` and
save its value in your vault; the plugin declares the key, and each conversation
reads it from the vaults it uses, so the value is never written into the plugin:

```bash
stigmer vault set-secret ACME_TOKEN --mine
stigmer mcp add acme https://mcp.acme.example/mcp \
  --header 'Authorization=Bearer ${ACME_TOKEN}'
```

`--dry-run` shows the plugin without installing it. Adding again with the same
name, address and headers changes nothing; a changed address or header upgrades
the plugin. Remove it with `stigmer delete plugin <name>`, or **Remove** on its
page. The [`stigmer mcp`](/docs/cli/commands/mcp) reference has every flag.

A server that runs as a local program (through `npx`, `uvx` or a binary) has no
address to add. Write it into a plugin folder's MCP configuration and install
the folder ([Install a plugin](/docs/guides/plugins/install-a-plugin)). It runs
only where a person's own runner runs, the desktop app or the CLI; a
conversation hosted in a cloud sandbox is refused when one of its plugins
carries a local program.

## Sign in

When you add a server whose headers name no key, Stigmer probes its address. A
server that answers with an OAuth challenge (Linear, Notion, Atlassian, most
hosted vendors) is recorded as one you sign in to: the plugin gets a login key
named `<SERVER>_ACCESS_TOKEN` and the `Authorization` header that carries it.

On the plugin's page the server's row then carries **Sign in**. Choose it, grant
access in the window that opens, and the row reads **Signed in**. From the CLI,
`stigmer connect plugin linear` opens the login page in your browser and waits
until the sign-in is saved. The login is kept in your own
[vault](/docs/concepts/vaults) as a connection at the server's address, so each
person signs in once for themselves, and it is refreshed before each run.

A server recorded this way accepts **only** a sign-in: a personal API token
pasted for it is refused by the vendor, so Stigmer offers only the sign-in. How
the sign-in works, and what a vendor that refuses automatic registration needs
instead, is in [OAuth for tools](/docs/guides/integrations/oauth-for-tools).

## See its tools

Stigmer stores nothing about a server's tools. **Check tools** on the server's
row asks the live server for them now, as you, with the keys and sign-ins in
your vault, and lists each tool with its description. From the CLI:

```bash
stigmer connect plugin linear
stigmer connect plugin acme-tools --server issues
```

`--server` picks one server when a plugin carries several. A key the server
needs and none of your vaults hold fails the listing, naming the key.

### Which tools ask for approval

A tool asks for human approval before it runs when its server marks it
destructive, with the MCP annotation `destructiveHint: true`; the listing marks
those tools. The server's author makes that call, and every Agent that uses the
server follows it. Every other tool runs without asking. The annotation is read
from the server again at the start of every turn, and a server whose tools
cannot be listed then asks before every one of its tools. Hooks can refuse, ask
about or allow any tool
([Guard an agent's tools with hooks](/docs/guides/plugins/use-hooks)), and to
keep an Agent away from a tool such as `run_sql`, leave it out with the Agent's
tool lists, below.

## Use it

For one conversation, turn the plugin on with `--plugin`, or pick it in the
chat's plugin picker in the console:

```bash
stigmer run --plugin linear -m "What's on my plate this week?"
```

With no Agent named, the built-in assistant runs with the server's tools. To
give the server to an Agent, list its plugin in the Agent's `plugins`, or choose
**Add to an agent** on the plugin's page:

```yaml validate-as="Agent"
spec:
  plugins:
    - kind: plugin
      slug: neon
  tools: [Read, mcp__plugin_neon_neon]
  disallowed_tools: [mcp__plugin_neon_neon__run_sql]
```

The Agent gets every tool of every plugin it lists, unless its two lists, in
Claude Code's names, say otherwise: `tools` keeps only the entries listed, and
`disallowed_tools` removes entries first. `mcp__plugin_<plugin>_<server>` names
every tool of one server and `mcp__plugin_<plugin>_<server>__<tool>` one tool; a
server added with `stigmer mcp add` has the plugin's name, so `neon` above is
both. This Agent can read files and use the Neon server, but never `run_sql`,
and cannot run shell commands or write files. See
[Approval Flows](/docs/concepts/approval-flows) for everything the lists cover.

For a first Agent to give these tools to, see
[Your first agent job](/docs/getting-started/quickstart).

## Give an agent its own MCP server

A plugin shares a server with every Agent and chat that lists it. When one Agent
needs a server, or you create Agents from your own code, write the server in the
Agent itself under `mcp_servers`, as an agent in Claude Managed Agents or a
Claude Code subagent lists its own. There is no plugin to package.

- **Who may.** Only your Organization's admins add a server to an Agent or
  change its address or headers. Anyone who may edit the Agent may keep or
  remove its servers.
- **What it can be.** A server reached over HTTP: an `https` address, or `http`
  on your own machine. An Agent lists at most 20.
- **Its name.** 2 to 63 lowercase letters, digits and hyphens, starting with a
  letter and not ending with a hyphen. A name starting with `stigmer` is the
  platform's, and `plugin` is reserved.
- **Its tools.** `mcp__<name>__<tool>` for one tool, and `mcp__<name>` for every
  tool of the server, in the Agent's `tools` and `disallowed_tools`.

### From the console

On the Agent's page, the **MCP servers** section lists the Agent's own servers;
an admin adds one with its name, address and headers. The new-Agent wizard's
**Capabilities** step has the same **MCP servers** list. Both show the section
to admins only; anyone else sees the servers the Agent already has.

### From YAML

```yaml validate-as="Agent"
spec:
  instructions: Answer support tickets. Look a ticket up before you reply.
  mcp_servers:
    - name: tickets
      url: https://tickets.acme-helpdesk.example/mcp
      headers:
        Authorization: Bearer ${TICKETS_API_KEY}
  tools: [Read, mcp__tickets]
```

Save it with the rest of the Agent's manifest and apply it with
`stigmer apply -f support-agent.yaml`.

### From your code

One call creates the Agent with its server, or updates it if it exists: `apply`
finds the Agent by its slug, so your backend can run the same call every time it
starts.

`${TICKETS_API_KEY}` stays as written: it names a key, and each run fills it
from its own vaults. One Agent serves all your customers, because the key comes
from the conversation, not from the Agent. If each customer's server has its own
address, run the same call once per customer, with a name and address each.

### How it logs in

A run finds the server's login the way the contract states it:

- **With an `Authorization` header** that names `${NAME}`, as in the example,
  the login is that key, and the run needs it: a run whose vaults do not hold it
  is refused before it starts, naming the key.
- **With no `Authorization` header**, the run uses the login saved in its vaults
  at the server's address, else a secret named `<NAME>_ACCESS_TOKEN` (here
  `TICKETS_ACCESS_TOKEN`: the server's name upper-cased, each other character
  written as `_`), else it calls the server with no login. For a server that
  asks you to sign in, the server's row on the Agent's page carries **Sign in**,
  which saves the login at the address in your vault.

A `${NAME}` value is sent to that server only, never to the Agent's shell, and a
header's `${NAME}` is a required secret unless the Agent's `env` declares it.
Header values themselves are stored in the Agent and returned to anyone who can
read it, so a key goes in a vault and the header names it.

For a product's customers, each customer's vault holds that customer's key, or
their own sign-in through a Connect link, and you name the vault on each of
their conversations:
[Keep your customers' keys](/docs/guides/authentication/customer-keys).

### What to know

- **No tool listing yet.** **Check tools** and `stigmer connect` list a plugin's
  servers only ([#2325](https://github.com/stigmer/stigmer/issues/2325)). Name
  the whole server as `mcp__tickets` in `tools`, or take the tool names from the
  server's own documentation. Destructive tools still ask first: the annotation
  is read from the live server at the start of every turn.
- **On the Agent only.** A conversation adds plugins, not servers of its own,
  and a local program (stdio) comes in a plugin.
- **One name per turn.** An Agent and a subagent it lists can't both have a
  server of the same name; the turn is refused, naming both.
- **Changes reach new conversations.** A conversation keeps the Agent version it
  started on, so a changed address or header reaches the conversations that
  start after the change.
- **Evals.** An eval's tries leave the Agent's own servers off, as they do its
  plugins' servers, unless the eval runs real servers.
- **The Cursor engine.** It runs the main Agent's own servers. A saved subagent
  that brings servers of its own is refused there, by name; run such an Agent on
  the native engine.
