Some MCP servers connect to services that require OAuth — GitHub, Slack, Figma,
Google Calendar. When a server declares an `auth` section, Stigmer manages the
entire OAuth flow: sign-in popup, token exchange, encrypted storage, and
automatic refresh. You never handle tokens directly.

<Callout type="info">
  This guide assumes you've read the [Connect an MCP
  Server](/docs/guides/integrations/connect-an-mcp-server) guide. The connect
  process (tool discovery) is the same for OAuth and non-OAuth servers — the
  difference is how credentials are obtained.
</Callout>

## How OAuth tools differ

When you open an MCP server that uses API keys (like PostgreSQL), the detail
view shows a credential form where you enter the value before connecting. OAuth
servers skip that form entirely. Instead, the connection section shows a **Sign
in to connect** button.

The difference comes from the `auth` section in the MCP server definition, which
Stigmer fills in for a standard OAuth server from its URL alone (the next
section), or which you write yourself. Here is what it looks like for GitHub's
MCP server:

```yaml validate-as="McpServer"
spec:
  http:
    url: "https://api.githubcopilot.com/mcp"
    headers:
      Authorization: "Bearer ${GITHUB_ACCESS_TOKEN}"
  env:
    GITHUB_ACCESS_TOKEN:
      is_secret: true
      description: "GitHub OAuth token or personal access token"
  auth:
    target_env_var: "GITHUB_ACCESS_TOKEN"
    scope_hints:
      - "repo"
      - "read:user"
```

The `auth` block tells Stigmer two things:

- **That the server signs in at its address** — the sign-in is saved at the
  server's URL, and `target_env_var` names the variable that receives the access
  token. This variable also appears in `env`, so a run resolves it the same way
  it resolves any other credential.
- **What access to expect** — `scope_hints` are shown before you sign in. The
  scopes actually requested are the ones the login server or the login app
  publishes.

The definition names no OAuth app. Which OAuth client signs you in is found from
the address: your Organization's own login app for it, then Stigmer's built-in
app (GitHub's MCP server and `github.com` use Stigmer's GitHub app), then the
server's own login server.
[OAuth architecture](/docs/guides/integrations/oauth-architecture#a-login-is-found-by-its-address)
explains the order.

Only an MCP server reached over HTTP has an `auth` block. A local program (an
MCP server that runs a command) takes its keys as environment variables declared
in `env`, saved as vault secrets; a definition that gives one an `auth` block is
refused.

The **Environment Variables** section in the detail view labels the
OAuth-managed variable with an **OAuth** badge to distinguish it from variables
you enter manually.

## For a standard OAuth server, a URL is enough

Most hosted MCP servers (Linear, Notion, Atlassian, Figma, Stripe and many more)
publish their sign-in the way the MCP specification describes: an
unauthenticated request is answered with a challenge that points at the server's
login metadata. For such a server you write nothing but its address:

```yaml validate-as="McpServer"
spec:
  http:
    url: "https://mcp.linear.app/mcp"
```

When the server is saved, by `stigmer apply`, by a plugin install or by the
console's form, Stigmer asks the endpoint once, under a three-second ceiling. If
it answers with a standard OAuth challenge whose metadata resolves, the
definition is completed on the spot: `auth.target_env_var` becomes
`<NAME>_ACCESS_TOKEN`, that variable is declared secret in `env`, the
`Authorization: Bearer` header that sends it is added, and `auth.oauth_only` is
set because such an endpoint rejects a pasted token. The row is labelled
`stigmer.ai/mcp-auth: endpoint` so Stigmer remembers the completion is its own.
From that moment the server's page, the page of any plugin that installed it,
and the Session composer carry **Sign in**.

Three rules keep this honest:

- **A definition you wrote is never overwritten.** A server that already carries
  `auth`, a header that sends a variable, or declared variables is left exactly
  as written; the probe only completes what is empty.
- **Applying the same definition again changes nothing.** The completion is
  carried across a re-apply, a plugin upgrade and a description edit as long as
  the URL is unchanged and the incoming definition says nothing about auth. A
  changed URL is asked again. An `auth` block you add yourself wins, and the
  label is dropped.
- **Anything but a standard challenge leaves the definition alone.** An open
  server, a server that wants an API key, a server that is down: none is
  changed, and the usual connect runs afterwards.

Signing in to such a server needs no setup: Stigmer becomes a client of the
server's login server on the first sign-in and reuses that client afterwards.
Some vendors publish their login metadata but do not let a client register
itself. Their servers are completed like the others, so the page tells the
truth, but **Sign in** refuses with the reason and the way forward: an admin
adds a login app for the address
([Bring Your Own OAuth App](/docs/guides/integrations/bring-your-own-oauth)), or
you paste a token.

## Connect an OAuth-protected tool

1. Open the server's detail view from the Library's MCP Servers page.
2. Click **Sign in to connect**. A popup opens to the provider's authorization
   page — GitHub, Slack, or whichever service the server integrates with.
3. Review the requested permissions and authorize the application.
4. The popup closes. Stigmer exchanges the authorization code for an access
   token, saves it as a connection in your vault, then connects to the server.
5. Tools are discovered, with the ones the server marks destructive — the same
   process described in
   [Connect an MCP Server](/docs/guides/integrations/connect-an-mcp-server#connect-an-mcp-server).

<Callout type="info">
  You never see or handle the access token. Stigmer keeps it sealed in your own
  vault and hands it to your runs when the Agent calls a tool; a teammate's runs
  never use it.
</Callout>

## Token lifecycle

After you authorize, Stigmer keeps the credential healthy without further
action. The connection section in the detail view shows one of four states:

| State              | What it means                                       | What to do                                     |
| ------------------ | --------------------------------------------------- | ---------------------------------------------- |
| **Connected**      | The access token is valid. Tools work normally.     | Nothing — you're set                           |
| **Token expired**  | The token expired but a refresh token is available. | Stigmer refreshes it automatically on next use |
| **Re-auth needed** | Both the access and refresh tokens have expired.    | Click **Sign in to connect** again             |
| **Not connected**  | No credential exists yet.                           | Click **Sign in to connect**                   |

When the provider supports refresh tokens, Stigmer refreshes the access token
automatically at run time. You don't need to re-authorize unless the refresh
token itself expires.

The detail view also shows a token lifetime hint when the server's definition
gives one (`auth.token_lifetime_hint`), so you know how long a token lasts
before the next automatic refresh.

## Manual override

If you prefer to use a personal access token or a service account key instead of
the OAuth flow, you can enter the value directly:

1. Click **Enter token manually** in the connection section.
2. Type or paste the token into the credential form.
3. Click **Connect**.

The server connects the same way — Stigmer saves the value as a login in your
vault and uses it for tool execution. The difference is that you manage token
rotation yourself instead of relying on the automatic OAuth lifecycle.

To switch back to OAuth, click **Sign in with OAuth instead** in the connection
section.
