Some MCP servers connect to services that require OAuth — GitHub, Slack, Figma,
Linear, Notion. For such a server Stigmer manages the whole sign-in: the login
window, token exchange, sealed storage in your vault, and automatic refresh. You
never handle tokens directly.

<Callout type="info">
  This guide assumes you've read [Connect an MCP
  server](/docs/guides/integrations/connect-an-mcp-server). Adding a server and
  reading its tools work the same for OAuth and non-OAuth servers — the
  difference is how credentials are obtained.
</Callout>

The walkthrough below signs in to the MCP server of a GitHub plugin from the
plugin's page: **Sign in** opens GitHub's authorization page, you approve the
requested permissions, and the login is saved in your vault at the server's
address. **Check tools** then lists what the server offers.

## How a server signs in

A server's login is the variable in its `Authorization: Bearer ${VAR}` header.
At run time that variable is filled by a login saved at the server's address in
your vault, then by a secret with that name. Here is GitHub's server, as
Stigmer's catalogue plugin declares it in its `mcp.json`:

```json
{
  "mcpServers": {
    "github": {
      "type": "http",
      "url": "https://api.githubcopilot.com/mcp/",
      "headers": {
        "Authorization": "Bearer ${GITHUB_PERSONAL_ACCESS_TOKEN}"
      }
    }
  }
}
```

A personal access token saved in your vault as `GITHUB_PERSONAL_ACCESS_TOKEN`
fills it, and so does your GitHub sign-in: the `github.com` login also serves a
tool on GitHub's own API (`api.github.com`, `api.githubcopilot.com`).

The plugin names no OAuth app. Which OAuth client signs you in is found from the
address: your Organization's own login app for it, then Stigmer's built-in app
(GitHub's MCP server and `github.com` use Stigmer's GitHub app), then the
server's own login server.
[OAuth architecture](/docs/guides/integrations/oauth-architecture#a-login-is-found-by-its-address)
explains the order.

Only an MCP server reached over HTTP signs in. A local program (an MCP server
that runs a command) takes its keys as variables, saved as vault secrets.

## For a standard OAuth server, a URL is enough

Most hosted MCP servers (Linear, Notion, Atlassian, Figma, Stripe and many more)
publish their sign-in the way the MCP specification describes: an
unauthenticated request is answered with a challenge that points at the server's
login metadata. For such a server the plugin names nothing but its address,
which is all `stigmer mcp add linear https://mcp.linear.app/mcp` writes:

```json
{
  "mcpServers": {
    "linear": { "type": "http", "url": "https://mcp.linear.app/mcp" }
  }
}
```

When the plugin is installed, Stigmer asks each such address once, with one MCP
`initialize` under a three-second deadline; servers are asked in parallel, and
the install never fails on the answer. If the server answers with an OAuth
challenge, the plugin's entry for it is completed on the spot: it records that
the server signs in and accepts only a sign-in (`sign_in.oauth_only`), gets a
login variable named `<SERVER>_ACCESS_TOKEN` (`LINEAR_ACCESS_TOKEN` here),
declared as a secret, and the `Authorization: Bearer` header that sends it. The
completion lives on the installed plugin; the archive is never rewritten. From
that moment the plugin's page and the chat composer carry **Sign in** for the
server.

Three rules keep this honest:

- **What the author wrote is never overwritten.** Only a server at an address
  with no variables, no `Authorization` header and no `${VAR}` in any header is
  asked. Anything else is the author speaking about authentication, and is left
  as written.
- **Installing the same archive again changes nothing.** A push of the version
  already installed reuses the answers recorded for it and asks nothing.
- **Anything but an OAuth challenge leaves the entry alone.** An open server, a
  server that wants an API key, a server that is down: none is changed.

Signing in to such a server needs no setup: Stigmer becomes a client of the
server's login server on the first sign-in and reuses that client afterwards.
Some vendors publish their login metadata but do not let a client register
itself. Their servers are completed like the others, so the page tells the
truth, but **Sign in** refuses with the reason and the way forward: an admin
adds a login app for the address
([Bring Your Own OAuth App](/docs/guides/integrations/bring-your-own-oauth)).

## Sign in

1. Open the plugin's page from **Library → Plugins**.
2. On the server's row, choose **Sign in**. A window opens to the provider's
   authorization page — GitHub, Linear, or whichever service the server
   integrates with.
3. Review the requested permissions and authorize the application.
4. The window closes. Stigmer exchanges the authorization code for an access
   token and saves it as a connection at the server's address in your vault. The
   row reads **Signed in**.
5. Choose **Check tools** to see the server's tools, with the ones it marks
   destructive, as
   [Connect an MCP server](/docs/guides/integrations/connect-an-mcp-server#see-its-tools)
   describes.

From the CLI, `stigmer connect plugin <plugin>` does the same: it opens the
login page in your browser, waits until the sign-in is saved, then lists the
tools. Off an interactive terminal it stops and names the ways to sign in
instead of waiting for a browser.

<Callout type="info">
  You never see or handle the access token. Stigmer keeps it sealed in your own
  vault and hands it to your runs when the Agent calls a tool; a teammate's runs
  never use it. **Sign out** on the server's row removes it.
</Callout>

## Token lifecycle

After you sign in, Stigmer keeps the credential healthy without further action.
When the provider supports refresh tokens, Stigmer refreshes the access token
automatically before each run. You sign in again, from the plugin's page, only
when the refresh token itself expires or is revoked; a conversation that needs
the sign-in asks for it before the first message.

## Using a key instead

A server that accepts a personal access token or a service account key, and is
not recorded as sign-in only, takes it as a vault secret named after its login
variable:

```bash
stigmer vault set-secret GITHUB_PERSONAL_ACCESS_TOKEN --mine
```

You manage that key's rotation yourself instead of relying on the automatic
OAuth lifecycle. A server recorded as sign-in only refuses a pasted key, so
Stigmer offers only **Sign in** for it.
