---
title: Caller identity for MCP servers
description:
  Receive the platform-verified identity of the person talking to your Agent in
  your own MCP server, without trusting anything the model says.
---

When your Agent serves people over a channel like WhatsApp, your MCP server
often needs to know who is asking. A member should see their own membership, not
someone else's. You cannot trust the model to pass a phone number as a tool
argument — a persuasive user could talk the Agent into passing someone else's.

Stigmer solves this with reserved variables your server's plugin can read in its
headers. The runner fills them with the verified caller identity when it reaches
your server. The value never passes through the model, so the model cannot
change it.

## The reserved keys

| Key                             | Value                                                                                                                                                                                            |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `STIGMER_CALLER_IDENTITY_KIND`  | What kind of identity this is: `whatsapp_phone`, `slack_user_id`, `stigmer_user` (a signed-in person, a routine's owner, or the configured operator of a server without sign-in), or `anonymous` |
| `STIGMER_CALLER_IDENTITY_VALUE` | The identity itself: the WhatsApp `wa_id`, the Slack user ID, the Stigmer user's email, or a service account's ID (`ida_…`) when a service account owns the conversation. Empty for `anonymous`  |
| `STIGMER_SESSION_ID`            | The Session the identity was resolved for. Empty outside a Session                                                                                                                               |

The identity comes from the strongest source available: the channel-verified
sender for channel Sessions, the signed-in person for console and CLI Sessions
on a server with sign-in (stigmer.ai, or a self-hosted server you set sign-in up
on), the routine's owner for a routine's runs, the configured operator identity
on a server without sign-in, and `anonymous` when none exists.

## Routines

A [routine](/docs/concepts/routines)'s run presents its owner: the person or
service account that created the routine. That holds in every edition with
sign-in, on its schedule or started by hand, and whoever started it: a
Participant pressing **Run now**, or an alerting tool calling it with a note,
does not change the identity your server sees. The run is the owner's
conversation, acting with the owner's access, as Claude Code's routines run as
the person who made them.

- **A routine a person created** presents kind `stigmer_user` with that person's
  email, the same value their own console and CLI Sessions present. A grant you
  already hold for that email covers their routines too.
- **A routine a service account created** presents kind `stigmer_user` with the
  service account's ID, such as `ida_01j9z3k8f2q4m6n7p8r9s0t1v2`, because a
  service account has no email. `stigmer service-account list` prints the ID.
  Grant it in your server's access model the way you grant an email.

So a grant decides which people's and which service accounts' routines may call
a privileged tool, routine by owner. A routine meant to keep calling a tool
after a person leaves is created by a service account, and your server grants
that account's ID.

## Servers without sign-in

A server that signs nobody in, such as `stigmer up` on a laptop or the
all-in-one container, cannot resolve a per-caller identity. By default every
Session presents `anonymous`: tools list, identity-gated calls refuse, deny by
default. A self-hosted server with
[sign-in](/docs/guides/self-hosting/authentication) presents each person, as
stigmer.ai does, and this section does not apply to it.

To present a real identity, persist it once with `stigmer setup` — the
recommended path, because it survives shell changes and daemon restarts:

```bash
stigmer setup --operator-email "ada@example.com" --operator-name "Ada Lovelace"
```

The interactive `stigmer setup` asks the same question, and the identity lands
in `~/.stigmer/config.yaml` alongside your API key. An environment value always
wins over the persisted one, and remains the way to configure a bare server
started without the CLI:

```bash
export STIGMER_OPERATOR_EMAIL="ada@example.com" # the identity
export STIGMER_OPERATOR_NAME="Ada Lovelace"     # optional display name
```

Every Session created from then on presents kind `stigmer_user` with that email
as the value — grant it in your server's access model like any other caller,
compared case-insensitively. Sessions created before the identity was configured
keep their original attribution and continue to present `anonymous`.

A server without sign-in is a single-operator trust domain, so the identity
covers everything the server does — console and CLI Sessions and routines alike.
A grant for the operator email therefore also covers your unattended automation;
keep that in mind when gating destructive tools.

A malformed email (no `@`) is refused at `stigmer setup` time, and a malformed
`STIGMER_OPERATOR_EMAIL` fails the server boot rather than silently stamping a
typo: the value feeds your binding sheet, so a typo would mint a wrong grantable
identity.

## Template your headers

Reference the reserved keys in your server's headers, in the plugin's MCP
configuration (its `.mcp.json` or `mcp.json`), or in the Agent's own
`mcp_servers` entry. In a plugin:

```json
{
  "mcpServers": {
    "gym-management": {
      "type": "http",
      "url": "https://gym-mcp.example.com/mcp",
      "headers": {
        "Authorization": "Bearer ${GYM_MCP_SHARED_SECRET}",
        "X-Stigmer-Caller-Kind": "${STIGMER_CALLER_IDENTITY_KIND}",
        "X-Stigmer-Caller-Value": "${STIGMER_CALLER_IDENTITY_VALUE}"
      }
    }
  }
}
```

Written in an Agent instead:

```yaml validate-as="Agent"
spec:
  mcp_servers:
    - name: gym-management
      url: https://gym-mcp.example.com/mcp
      headers:
        Authorization: Bearer ${GYM_MCP_SHARED_SECRET}
        X-Stigmer-Caller-Kind: ${STIGMER_CALLER_IDENTITY_KIND}
        X-Stigmer-Caller-Value: ${STIGMER_CALLER_IDENTITY_VALUE}
```

The plugin or the Agent declares nothing for the reserved keys: Stigmer
recognizes them and records each as an optional variable the platform fills, so
no vault is ever asked for one. A fourth key, `STIGMER_SERVER_ADDRESS`, carries
the address of the Stigmer server the run belongs to, for a server that calls
back. Every other key you template, such as `GYM_MCP_SHARED_SECRET` here, is the
plugin's to declare in its manifest, or the Agent's in its `env`; one it does
not declare is taken as a required secret, which a conversation finds in its
vaults by name.

## Handle the anonymous caller

Listing a server's tools outside a conversation (**Check tools** on the plugin's
page, or `stigmer connect plugin`) has no caller to name. In that context the
reserved keys resolve to the anonymous sentinel: kind `anonymous`, empty value.

Your server must answer `tools/list` for anonymous callers. Gate tool _calls_
instead: resolve the identity to a role on every call, and refuse calls the role
does not permit. Deny by default.

## Trust the header only behind your secret

The identity header is asserted by the runner. It is not a signed token. That
closes the prompt-injection hole — the model cannot influence the value — but
anyone who can reach your endpoint directly can send any header they like.

Always pair the identity headers with a shared secret, as in the preceding
example, and reject requests that fail the secret check before reading anything
else. Use this pattern only for MCP servers you operate yourself.

## Who asserts the email

For a `stigmer_user`, the value is the email the person's sign-in asserted, and
the server takes it as given. On a server where each Organization can bring its
own Federation Issuer, that includes every one of those issuers: an
Organization's Federation Issuer can sign a person in with any email it chooses.

So the email identifies a person only to an MCP server whose operator trusts
every Federation Issuer of every Organization the Stigmer server serves. If you
serve Organizations whose Federation Issuers you do not control, grant by
something those issuers cannot choose, or keep privileged tools out of their
reach.
