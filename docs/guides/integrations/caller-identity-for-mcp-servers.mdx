---
title: Caller identity for MCP servers
description:
  Receive the platform-verified identity of the person talking to your Agent in
  your own MCP server, without trusting anything the model says.
---

When your Agent serves people over a channel like WhatsApp, your MCP server
often needs to know who is asking. A member should see their own membership, not
someone else's. You cannot trust the model to pass a phone number as a tool
argument — a persuasive user could talk the Agent into passing someone else's.

Stigmer solves this with reserved environment variable keys. The runner injects
the verified caller identity into your server's configuration at resolution
time. The value never passes through the model, so the model cannot change it.

## The reserved keys

| Key                             | Value                                                                                                                                                                                                      |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `STIGMER_CALLER_IDENTITY_KIND`  | What kind of identity this is: `whatsapp_phone`, `slack_user_id`, `stigmer_user` (a console or CLI Session, a scheduled run on stigmer.ai, or a self-hosted backend's configured operator), or `anonymous` |
| `STIGMER_CALLER_IDENTITY_VALUE` | The identity itself: the WhatsApp wa_id, the Slack user ID, or the Stigmer user's email. Empty for `anonymous`                                                                                             |
| `STIGMER_SESSION_ID`            | The Session the identity was resolved for. Empty outside a Session                                                                                                                                         |

The identity comes from the strongest source available: the channel-verified
sender for channel Sessions, the logged-in Stigmer user for console and CLI
Sessions on stigmer.ai, the configured operator identity on a self-hosted
backend, and `anonymous` when none exists.

## Scheduled runs

A [Schedule](/docs/cli/commands/schedule) fire carries an identity too — but not
its creator's. A scheduled run is unattended automation: the person who created
the schedule may change roles or leave the Organization while the cron keeps
firing, so the platform attributes every fire to a per-org system account by
design instead of impersonating a person. If your server gates tools on
identity, scheduled runs stay unprivileged until you grant that account —
explicitly, the same way you grant any caller.

On stigmer.ai, a scheduled run presents kind `stigmer_user` with the org's
schedule-account email as the value:

```text
schedule+{org-slug}@schedule.stigmer.internal
```

To let scheduled runs call privileged tools, grant that email in your server's
own access model, compared case-insensitively like any email. The grant covers
the Organization's scheduled automation as a whole: every schedule in the org
presents the same identity, whoever created it.

<Callout type="info">
  The per-org schedule account requires Stigmer Cloud. On a self-hosted backend,
  scheduled runs present the configured operator identity (next section), or
  `anonymous` when none is configured — anonymous runs can list tools but cannot
  pass an identity-gated call.
</Callout>

## Self-hosted backends

A self-hosted server has no login, so it cannot resolve a per-caller identity.
By default every Session presents `anonymous`: tools list, identity-gated calls
refuse, deny by default.

To present a real identity, configure the operator identity before starting the
server (for `stigmer up`, export it in the shell that starts the daemon):

```bash
export STIGMER_OPERATOR_EMAIL="ada@example.com" # the identity
export STIGMER_OPERATOR_NAME="Ada Lovelace"     # optional display name
```

Every Session created from then on presents kind `stigmer_user` with that email
as the value — grant it in your server's access model like any other caller,
compared case-insensitively. Sessions created before the identity was configured
keep their original attribution and continue to present `anonymous`.

A self-hosted install is a single-operator trust domain, so the identity covers
everything the install does — console and CLI Sessions and locally scheduled
runs alike. A grant for the operator email therefore also covers your unattended
automation; keep that in mind when gating destructive tools.

A malformed `STIGMER_OPERATOR_EMAIL` (no `@`) fails the server boot rather than
silently stamping a typo: the value feeds your binding sheet, so a typo would
mint a wrong grantable identity.

## Declare the keys and template your headers

Declare the reserved keys in your server's `env` — marked `optional: true` — and
reference them in your headers:

```yaml
apiVersion: agentic.stigmer.ai/v1
kind: McpServer
metadata:
  name: gym-management
spec:
  description: >
    Membership tools for the gym. Resolves the caller's role from the
    platform-verified identity on every call.
  http:
    url: "https://gym-mcp.example.com/mcp"
    headers:
      Authorization: "Bearer ${GYM_MCP_SHARED_SECRET}"
      X-Stigmer-Caller-Kind: "${STIGMER_CALLER_IDENTITY_KIND}"
      X-Stigmer-Caller-Value: "${STIGMER_CALLER_IDENTITY_VALUE}"
  env:
    GYM_MCP_SHARED_SECRET:
      is_secret: true
      description: Shared secret the MCP server requires on every request
    STIGMER_CALLER_IDENTITY_KIND:
      optional: true
      description: Injected by the platform — the caller identity's kind
    STIGMER_CALLER_IDENTITY_VALUE:
      optional: true
      description: Injected by the platform — the caller identity's value
```

Two rules matter here:

1. **Declare every reserved key you template.** Placeholders resolve against the
   variables your server declares. An undeclared key in a template fails
   resolution.
2. **Mark the reserved keys `optional: true`.** Their values come from the
   runner at execution time, not from an Environment. A required declaration
   fails execution creation with a missing-variable error.

## Handle the anonymous caller

Tool discovery runs when your server connects, before any conversation exists.
In that context the reserved keys resolve to the anonymous sentinel: kind
`anonymous`, empty value.

Your server must answer `tools/list` for anonymous callers. Gate tool _calls_
instead: resolve the identity to a role on every call, and refuse calls the role
does not permit. Deny by default.

## Trust the header only behind your secret

The identity header is asserted by the runner. It is not a signed token. That
closes the prompt-injection hole — the model cannot influence the value — but
anyone who can reach your endpoint directly can send any header they like.

Always pair the identity headers with a shared secret, as in the preceding
example, and reject requests that fail the secret check before reading anything
else. Use this pattern only for MCP servers you operate yourself.
