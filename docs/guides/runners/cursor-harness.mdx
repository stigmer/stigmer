The Cursor [Harness](/docs/concepts/harnesses) uses the Cursor SDK as the
execution engine for your Agent Sessions. This guide covers how to set it up
locally, how it works in Stigmer Cloud, and how to create Sessions that use it.

## Prerequisites

- A working Stigmer setup — complete the
  [quickstart](/docs/getting-started/quickstart) or
  [local setup](/docs/getting-started/local) first.
- A [Cursor API key](https://docs.cursor.com) (for local runners only — cloud
  runners handle this automatically).

## Local setup

<Steps>

<Step>

### Set the Cursor API key

Export your Cursor API key as an Environment variable before starting the
runner:

```bash
export CURSOR_API_KEY=your-cursor-api-key
```

</Step>

<Step>

### Start the runner

Run `stigmer up` as usual. When a Cursor API key is configured, the runner
automatically starts a Cursor worker alongside the native worker:

```bash
stigmer up
```

You will see both workers register in the startup output. The Cursor worker uses
a dedicated task queue derived from the runner's base queue.

</Step>

<Step>

### Verify in the console

Open **Settings > Runners** in the web console. Your runner should show a
**Ready** phase. The runner hosts both the native and Cursor workers — you don't
need separate runner processes.

</Step>

</Steps>

## Cloud setup

On Stigmer Cloud, the Cursor harness works without any API key configuration on
the runner. Stigmer Cloud handles proxy routing automatically — the runner
authenticates with its `STIGMER_TOKEN`, and the platform injects the Cursor
credentials server-side.

If you already have a [cloud runner](/docs/guides/runners/cloud-mode) set up,
the Cursor harness is available with no additional steps.

## Creating a Cursor Session

### Via the SDK

Specify `harness: "HARNESS_CURSOR"` when creating a Session:

<Tabs items={["TypeScript", "Go"]}>
  <Tab value="TypeScript">

```typescript
const session = await client.session.create({
  spec: {
    subject: "Add unit tests for auth module",
    agentInstanceId: "ain-abc123",
    harness: "HARNESS_CURSOR",
  },
});
```

  </Tab>
  <Tab value="Go">

```go
session, err := client.Session.Create(ctx, &sessionv1.CreateInput{
    Spec: &sessionv1.SessionSpec{
        Subject:         "Add unit tests for auth module",
        AgentInstanceId: "ain-abc123",
        Harness:         sessionv1.Harness_HARNESS_CURSOR,
    },
})
```

  </Tab>
</Tabs>

### Via the model picker

In the web console, the unified model picker shows models from both harnesses.
Each model row displays an engine tag — "Stigmer" for native models or "Cursor"
for Cursor-served models. Selecting a Cursor model implicitly sets the Session's
Harness to Cursor.

## Selecting models

The Cursor harness uses its own model catalog. Model identifiers follow the
Cursor platform's naming (for example, `claude-4.6-sonnet`). In the SDK, you can
use compound keys to disambiguate when the same model name exists in both
harnesses:

```typescript
// Compound key: harness/modelId
const compoundKey = "cursor/claude-4.6-sonnet";
```

See the [Models reference](/docs/sdk/react/models) for details on compound keys,
the model registry hook, and the `ModelSelector` component.

## Approval flows

Approval flows work the same way with the Cursor harness. When a tool call
requires approval, the Agent pauses, presents the action for review, and waits
for a human to approve, skip, or reject — just like with the native Harness.

The Cursor harness bridges Cursor's `preToolUse` hooks to Stigmer's approval
pipeline transparently. You configure
[approval flows](/docs/concepts/approval-flows) the same way regardless of
Harness.

## Limitations and differences

The Cursor harness shares most of the native Harness's capabilities through
Stigmer's unified pipeline (streaming, approval flows, usage tracking). A few
areas differ:

| Area                  | Native Harness                       | Cursor Harness                            |
| --------------------- | ------------------------------------ | ----------------------------------------- |
| **Models**            | All supported providers              | Cursor-served models only                 |
| **Checkpoint/resume** | Full Stigmer-managed checkpoints     | Cursor manages its own conversation state |
| **Sandbox**           | Container-based isolation via Docker | Cursor's own sandbox model                |
| **Pricing**           | Per-provider token pricing           | Cursor platform pricing                   |
| **Immutability**      | Cannot change after first execution  | Cannot change after first execution       |

## Troubleshooting

### Cursor worker not starting

If `stigmer up` does not start the Cursor worker, check that `CURSOR_API_KEY` is
set in the Environment. The runner only starts the Cursor worker when a valid
key is available.

On first startup, the runner may bootstrap a Node.js 22 runtime and run
`npm install` for the Cursor worker's dependencies. This one-time step can take
a minute.

### Model not available

If a Cursor model does not appear in the model picker, verify the runner has an
active Cursor worker. Only runners with a Cursor worker advertise Cursor models.

### API key errors

If Cursor executions fail with authentication errors on a local runner, verify
your `CURSOR_API_KEY` is valid and not expired. On Stigmer Cloud, contact
support if Cursor executions fail — the platform manages credentials
server-side.
