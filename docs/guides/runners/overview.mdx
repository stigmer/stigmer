A Runner is the process that executes your users' Agents. If you are building a
desktop application and want your users to run Stigmer agents, you need to
understand how runners work and how to set one up.

These guides walk you through the integration — from bundling the `stigmer` CLI
as a sidecar in your app to choosing the right execution mode for your users'
workloads.

## Three execution modes

Every runner integration starts with a choice: where should agent commands run?

|                     | Local                                    | Sandbox                                               | Cloud (auto)                          |
| ------------------- | ---------------------------------------- | ----------------------------------------------------- | ------------------------------------- |
| **What runs where** | Agent commands run on the user's machine | Agent commands run in a Docker container              | Stigmer provisions compute on demand  |
| **Start command**   | `stigmer-cli --standalone up runner`     | `stigmer-cli --standalone up runner --runtime docker` | No command — automatic                |
| **Isolation**       | None — full host access                  | Container-level                                       | Platform-managed                      |
| **Good for**        | Development, on-premises, data-sensitive | Untrusted workloads, consistent environments          | Zero-setup production, burst capacity |

**Local** is the default. Your app spawns `stigmer-cli --standalone up runner`
and the runner executes agent commands directly on the user's machine. The agent
has full access to the local file system.

**Sandbox** adds isolation. The runner executes agent commands inside a Docker
container, keeping untrusted operations away from the host. Your app spawns
`stigmer-cli --standalone up runner --runtime docker` or configures the
execution mode to `sandbox`.

**Cloud (auto)** requires no local runner at all. When a Session needs compute
and no runner is specified, Stigmer provisions an ephemeral cloud runner on
demand. If your app does not start a runner, this is what happens.

## The sidecar pattern

Your application bundles the `stigmer` CLI binary and spawns it as a child
process. The CLI handles everything — runner registration, heartbeats, the
bidirectional command stream, and the Python runtime. Your app only needs to
start and stop it.

### The `--standalone` flag

Every sidecar invocation uses the `--standalone` flag. This tells the CLI to
ignore the user's `~/.stigmer/config.yaml` file — all configuration must come
from flags or environment variables that your app provides.

Without `--standalone`, the CLI reads the user's config file. If the user has
previously run `stigmer auth login` or `stigmer config set`, those stored
settings could silently override the credentials and endpoint your app passes.
The `--standalone` flag prevents this by isolating your sidecar from any ambient
CLI configuration on the machine.

You will see `--standalone` in every CLI example throughout these guides.

## Who these guides are for

These guides are for **platform builders** who want to integrate Stigmer into
their own desktop applications. The journey assumes you are building an app that
manages runner processes on behalf of your users — using the CLI as a sidecar.

You should already understand what [Runners](/docs/concepts/runners) are and how
they fit the platform. If terms like "runner phase" or "runner lifecycle" are
not familiar yet, start with the [Runners concept page](/docs/concepts/runners).
