In local mode, the runner executes agent commands directly on the host machine.
The agent has full access to the local file system, installed tools, and
network. This is the default when you start a runner with `stigmer up`.

Use local mode when your users need:

- Full access to local files and directories
- Low latency with no container overhead
- Development and testing workflows
- On-premises or data-sensitive workloads where nothing should leave the machine

## Start a runner

One command starts a runner on the user's machine:

```bash
stigmer up
```

The CLI bootstraps a Python virtual environment (first run only), registers the
runner with the server, and begins accepting
[Agent Executions](/docs/concepts/agents#blueprint-vs-runtime). The runner stays
running until you stop it or the process is terminated.

For your sidecar integration, spawn this as a child process with authentication
flags:

```bash
stigmer-cli up runner --token stk_your_api_key --name my-runner
```

## Runner naming

Every runner needs a unique name within the Organization. The name appears in
the web console, CLI output, and the Session composer's runner picker.

By default, `stigmer up` uses the machine's host name, sanitized into a slug:

```bash
stigmer up
# Using "surreshs-macbook" as runner name (sanitized from hostname)
```

To choose a specific name, use `--name`:

```bash
stigmer up --name build-01
```

**Naming rules:**

- Lowercase letters, numbers, and hyphens only
- Cannot start or end with a hyphen
- Maximum 63 characters

If a runner with that name is already running, `stigmer up` reports the conflict
and suggests using a different name.

## What happens behind the scenes

1. The CLI bootstraps a Python virtual environment (first run only — subsequent
   starts reuse it).
2. It registers the runner with the server via `Runner.Apply`.
3. It starts the runner Python process, passing backend credentials and routing
   configuration through environment variables.
4. It saves a state file at `~/.stigmer/runners/<name>.json`.
5. The runner sends its first heartbeat and transitions to the **Ready** phase.

The process runs in the foreground. Output streams to stdout/stderr. Press
`Ctrl+C` to stop it — the CLI sends SIGTERM to the runner and cleans up the
state file.

## Connect to a specific backend

Without any flags, `stigmer up` connects to the backend configured with
`stigmer auth login` (cloud) or `stigmer up server` (local). You can override
this per runner:

```bash
stigmer up --endpoint api.stigmer.ai:443 --token sk-your-api-key
```

This is useful in environments where no config file exists — CI/CD pipelines,
Docker containers, or SSH sessions. The `--endpoint` and `--token` flags take
priority over stored configuration.

<Callout type="tip">
  Running against a local server? If you started it with `stigmer up server`,
  the CLI detects it automatically. No `--endpoint` or `--token` needed.
</Callout>

## Run multiple runners

Each `stigmer up` call with a unique name starts a separate runner process. All
runners connect to the server independently and appear in the runner list.

In your app, spawn one child process per runner:

```bash
# Runner 1
stigmer-cli up runner --token stk_key --name laptop-native

# Runner 2
stigmer-cli up runner --token stk_key --name laptop-build
```

Both runners register with the server and accept executions. In the web
console's Session composer, users can select either runner from the runner
picker.

To see all active runners on this machine:

```bash
stigmer list runners
```

This reads the local state files in `~/.stigmer/runners/` and shows each
runner's name, runtime, backend, and start time. Only runners started from this
machine appear — it does not query the server.

## Execution mode configuration

Local mode is the default execution mode. You can set it explicitly through the
CLI configuration:

```bash
stigmer config set execution.mode local
```

Or through the `STIGMER_EXECUTION_MODE` environment variable:

```bash
STIGMER_EXECUTION_MODE=local
```

When starting the full local development stack, use the `--execution-mode` flag:

```bash
stigmer up server --execution-mode local
```

## Security considerations

In local mode, agent commands have full access to the host machine. The agent
can read and write files, execute commands, and access the network. If your
users run untrusted agents, consider
[sandbox mode](/docs/guides/runners/sandbox-mode) instead.
