One command starts a runner on your machine. The runner registers with the
server, connects over gRPC, and begins accepting
[Agent Executions](/docs/concepts/agents#blueprint-vs-runtime). It stays running
until you stop it or close the terminal.

<DemoLocalRunnerTour />

```bash
stigmer up
```

That's it. The runner uses your machine's host name as its name, starts with the
native Python runtime, and connects to whatever backend you configured with
`stigmer auth login` or `stigmer config`.

The rest of this guide covers naming, runtime options, multiple runners, and
backend configuration — all things you'll need as you move beyond the basics.

## Runner naming

Every runner needs a unique name within your Organization. The name appears in
the web console, the desktop app, CLI output, and the Session composer's runner
picker.

By default, `stigmer up` uses your machine's host name, sanitized into a slug:

```bash
stigmer up
# Using "surreshs-macbook" as runner name (sanitized from hostname "Surresh's-MacBook.local")
```

To choose your own name, use `--name`:

```bash
stigmer up --name build-01
```

**Naming rules:**

- Lowercase letters, numbers, and hyphens only
- Cannot start or end with a hyphen
- Maximum 63 characters

If a runner with that name is already running, `stigmer up` tells you and
suggests using a different name.

## Native runtime (default)

The default runtime starts an embedded Python process directly on your machine.
No Docker required.

```bash
stigmer up --name dev-laptop
```

What happens behind the scenes:

1. The CLI bootstraps a Python virtual environment (first run only — subsequent
   starts reuse it).
2. It registers the runner with the server via `Runner.Apply`.
3. It starts the runner Python process, passing backend credentials and routing
   configuration through Environment variables.
4. It saves a state file at `~/.stigmer/runners/dev-laptop.json`.
5. The runner sends its first heartbeat and transitions to the **Ready** phase.

The process runs in the foreground. Output streams to your terminal. Press
`Ctrl+C` to stop it — the CLI sends SIGTERM to the runner and cleans up the
state file.

## Docker runtime

If you prefer isolation or need a consistent setup across machines, start the
runner inside a Docker container:

```bash
stigmer up --runtime docker --name dev-docker
```

Docker must be running on your machine. The CLI checks for Docker availability
before starting and tells you if it can't connect.

The container is named `stigmer-runner-<name>` (for example,
`stigmer-runner-dev-docker`). It runs in the background — the CLI blocks and
streams output until the container exits or you press `Ctrl+C`.

### Custom images

By default, the CLI uses `ghcr.io/stigmer/agent-runner` tagged with the CLI's
own version. To use a different image:

```bash
stigmer up --runtime docker --image ghcr.io/stigmer/agent-runner:latest
```

This is useful when you need a specific version or a custom image with
additional dependencies.

## Connect to a specific backend

Without any flags, `stigmer up` connects to the backend you configured with
`stigmer auth login` (cloud) or `stigmer up server` (local). You can override
this per runner:

```bash
stigmer up --endpoint api.stigmer.ai:443 --token sk-your-api-key
```

This is useful in Environments where no config file exists — CI/CD pipelines,
Docker containers, or SSH Sessions. The `--endpoint` and `--token` flags take
priority over stored configuration.

<Callout type="tip">
  Running against a local server? If you started it with `stigmer up server`,
  the CLI detects it automatically. No `--endpoint` or `--token` needed.
</Callout>

## Run multiple runners

Each `stigmer up` call with a unique name starts a separate runner process. All
runners connect to the server independently and appear in the runner list.

Open multiple terminal Sessions and start one runner in each:

```bash
# Terminal 1
stigmer up --name laptop-native

# Terminal 2
stigmer up --name laptop-docker --runtime docker
```

Both runners register with the server and accept executions. In the web
console's Session composer, you can select either runner from the runner picker.

To see all active runners:

```bash
stigmer list runners
```

This reads the local state files in `~/.stigmer/runners/` and shows each
runner's name, runtime, backend, and start time. Only runners started from this
machine appear — it does not query the server.

## Check runner status

Two commands give you visibility into runner health:

```bash
# Overview of all running Stigmer components
stigmer status

# Runner-specific logs
stigmer logs --component agent-runner
```

`stigmer status` shows the state of the local server (if running), active
runners, and their phases. `stigmer logs` streams the runner's log output, which
includes execution traces, heartbeat activity, and error details.

## State files

The CLI tracks each runner in a JSON file at `~/.stigmer/runners/<name>.json`.
The state file records the runner ID, backend endpoint, process PID (or Docker
container ID), runtime type, and start time.

These files serve two purposes:

1. `stigmer down runner` reads them to find and stop the right process.
2. `stigmer list runners` reads them to show what's running locally.

If a runner crashes or its process disappears, the state file becomes stale. The
next `stigmer up` automatically detects and removes stale state files before
starting — you don't need to clean them up manually.

## `stigmer up` vs `stigmer up runner`

These two commands are identical. `stigmer up` is the short form.
`stigmer up runner` exists for clarity when used alongside `stigmer up server`
(which starts the full local development stack with Temporal, the Stigmer
server, and an embedded runner).

The embedded runner in `stigmer up server` is daemon-managed — it starts and
stops with the server. Runners started with `stigmer up` / `stigmer up runner`
are standalone — they have their own lifecycle and can connect to any backend.
