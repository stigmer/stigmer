This guide helps you make cost-effective decisions when running Agent Executions
on Stigmer Cloud. It covers when each harness saves money, how prompt caching
reduces repeated-prefix costs, and practical patterns for managing session
economics.

## Harness economics at a glance

The two harnesses have fundamentally different cost profiles:

| Factor              | Native                                     | Cursor                                    |
| ------------------- | ------------------------------------------ | ----------------------------------------- |
| Platform commission | 20% over provider rates                    | 10% over provider rates                   |
| Per-call overhead   | Minimal (~your prompt only)                | ~10,000 tokens of system context per call |
| Latency             | 2–3× faster                                | Structural overhead from agent tooling    |
| Cache control       | Full (explicit breakpoints, TTL selection) | Automatic and opaque                      |
| Multi-turn savings  | Compounds heavily via prompt caching       | Limited — overhead repeated each turn     |

The native harness costs less per token, but the cursor harness provides managed
agent tooling (code search, file edits, terminal, MCP) that would be expensive
to build yourself.

## When native saves money

Choose native when:

- **Multi-turn conversations** — Anthropic prompt caching reduces
  repeated-prefix cost by up to 78% over 10 turns. The stable prefix (tool
  definitions + system prompt) is cached and reused on every subsequent call.
- **Straightforward prompts** — A factual question or summarization task does
  not need cursor's code editing tools. Native avoids the ~10k token overhead
  entirely.
- **High-volume batch work** — Many short tasks sent sequentially benefit from
  native's lower latency and cache amortization.
- **Chat-style sessions** — Interactive sessions where the user asks follow-up
  questions. The growing conversation prefix stays cached.

### Prompt caching economics

On the native harness, Anthropic prompt caching provides significant savings on
repeated content. The cache works over the request prefix in order: `tools` →
`system` → `messages`.

For a typical 10,800-token stable prefix (tool definitions + system prompt)
using Claude Sonnet 4.6:

| Metric                   | Without caching | With caching (10 uses) |
| ------------------------ | --------------- | ---------------------- |
| Cost for repeated prefix | $0.33           | $0.07                  |
| Savings                  | —               | **78%**                |
| Break-even               | —               | After 1 cache read     |

The cache has a 5-minute TTL that refreshes on each hit. Sessions with turns
spaced less than 5 minutes apart keep the cache warm indefinitely. For
long-lived prefixes, a 1-hour TTL is available at a slightly higher write cost.

**What gets cached:** Tool schemas, system prompt, and conversation history (up
to the cache boundary). If your Agent's tool definitions are stable across
calls, the entire tool block stays cached.

**What invalidates the cache:** Changing tool names, descriptions, or parameters
flushes the cache. Keep your tool definitions stable within a Session.

## When cursor is worth the premium

Choose cursor when:

- **Repository-aware coding** — The task needs semantic code search, file edits,
  or understanding of a codebase structure. Cursor clones the repo and indexes
  it.
- **Terminal automation** — The task involves running commands, checking output,
  and iterating based on results.
- **Complex multi-file changes** — Refactoring, migrations, or feature
  implementation across many files benefits from cursor's built-in file editing
  tools.
- **MCP-heavy workflows** — When your agent uses many MCP servers and the cursor
  harness manages their lifecycle.

The ~10,000-token overhead per call is the cost of having the full agent
environment loaded and ready. For tasks that would otherwise require you to
build custom tools for code search, file manipulation, and terminal access, this
overhead is well worth the investment.

## Decision matrix

| Task type               | Recommended | Rationale                          |
| ----------------------- | ----------- | ---------------------------------- |
| Quick factual answer    | Native      | No tools needed; avoid overhead    |
| Multi-turn support chat | Native      | Caching compounds over turns       |
| Code refactoring        | Cursor      | Needs code search + file edits     |
| PR generation           | Cursor      | Full repo awareness required       |
| Data summarization      | Native      | Text-in, text-out workload         |
| Bug investigation       | Cursor      | Terminal + code navigation         |
| Document drafting       | Native      | Text generation, no tools needed   |
| Complex coding session  | Cursor      | Semantic search + edits + terminal |
| Batch classification    | Native      | High volume, low per-call overhead |

## Session length and cost

**Short sessions (1–3 turns):** Native is almost always cheaper. The cache write
on the first call is amortized over subsequent turns, and the token count stays
low.

**Medium sessions (4–10 turns):** Native advantage grows. Each additional turn
benefits from cached prefix at one-tenth the read cost. Cursor's fixed overhead
repeats on every call, so total cost diverges.

**Long coding sessions (10+ turns):** Cursor can be cost-effective here if every
turn uses the coding tools. The fixed overhead is amortized across many
productive tool uses. But if only some turns need tools, consider using native
for the dialogue turns and switching to cursor only when code changes are
needed.

## Practical tips

1. **Match harness to task** — Do not default to cursor for everything. Reserve
   it for tasks that genuinely need its tooling.

2. **Keep tool schemas stable** — On native, changing tool definitions between
   calls invalidates the cache. Define your tools once at session start.

3. **Use session-level harness selection** — The harness is set when you create
   a Session and is immutable for that session's lifetime. Create separate
   sessions for different task types.

4. **Monitor credit consumption** — The billing dashboard shows per-execution
   cost breakdowns. Watch for executions that consume more credits than expected
   — they may be candidates for harness switching.

5. **Leverage prompt caching for prefixes above 1,024 tokens** — Anthropic
   requires a minimum of 1,024 tokens for caching. Most Agent configurations
   exceed this threshold (tool definitions alone are typically 2,000+ tokens).
