In sandbox mode, agent commands run inside a Docker container instead of
directly on the host. This keeps untrusted operations isolated from the user's
machine — the agent cannot access host files or processes outside the container.

Use sandbox mode when your users need:

- Security isolation for untrusted or third-party agents
- A consistent execution environment across different machines
- Protection against agents that modify the file system or install packages

## Two levels of isolation

Sandbox mode offers two approaches depending on how much isolation you need.

### Runner-level isolation

The entire runner process — including the Python runtime and all agent commands
— runs inside a Docker container:

```bash
stigmer-cli --standalone up runner --runtime docker --token stk_key --name my-sandbox
```

Docker must be running on the user's machine. The CLI checks for Docker
availability before starting and reports an error if it cannot connect.

The container is named `stigmer-runner-<name>` (for example,
`stigmer-runner-my-sandbox`). It runs in the background — the CLI blocks and
streams output until the container exits or the process is terminated.

**Custom images.** By default, the CLI uses `ghcr.io/stigmer/agent-runner`
tagged with the CLI's own version. To use a different image:

```bash
stigmer-cli --standalone up runner --runtime docker --image ghcr.io/stigmer/agent-runner:latest --token stk_key --name my-sandbox
```

This is useful when you need a specific version or a custom image with
additional dependencies.

### Command-level isolation

The runner process itself runs natively on the host, but individual agent
commands execute inside a sandbox container. This gives you faster startup while
still isolating the commands that interact with the file system and run external
tools:

```bash
stigmer up server --execution-mode sandbox
```

Or configure it persistently:

```bash
stigmer config set execution.mode sandbox
```

This approach uses a separate sandbox container image
(`ghcr.io/stigmer/agent-sandbox-basic` by default) that the runner spins up for
each execution. The runner manages the container lifecycle automatically.

## Configuration

### CLI flags

These flags apply when starting a runner or the local development server:

| Flag                  | Applies to          | Description                                                 |
| --------------------- | ------------------- | ----------------------------------------------------------- |
| `--runtime docker`    | `stigmer up`        | Run the entire runner inside a Docker container             |
| `--image`             | `stigmer up`        | Docker image for runner-level isolation                     |
| `--execution-mode`    | `stigmer up server` | Set to `sandbox` for command-level isolation                |
| `--sandbox-image`     | `stigmer up server` | Docker image for the sandbox container                      |
| `--sandbox-auto-pull` | `stigmer up server` | Pull sandbox image if missing (default: `true`)             |
| `--sandbox-cleanup`   | `stigmer up server` | Remove sandbox containers after execution (default: `true`) |

### Environment variables

When deploying the runner directly (without the CLI), configure sandbox mode
through environment variables:

| Variable                    | Description                                                   | Default                                      |
| --------------------------- | ------------------------------------------------------------- | -------------------------------------------- |
| `STIGMER_EXECUTION_MODE`    | Set to `sandbox` for command-level isolation                  | `local`                                      |
| `STIGMER_SANDBOX_IMAGE`     | Docker image for sandbox execution                            | `ghcr.io/stigmer/agent-sandbox-basic:latest` |
| `STIGMER_SANDBOX_AUTO_PULL` | Pull sandbox image if missing (`true` or `false`)             | `true`                                       |
| `STIGMER_SANDBOX_CLEANUP`   | Remove sandbox containers after execution (`true` or `false`) | `true`                                       |
| `STIGMER_SANDBOX_TTL`       | Container reuse TTL in seconds                                | `3600`                                       |

These variables are set automatically when you start a runner through the CLI.
Set them yourself only when deploying the runner container directly.

### Persistent configuration

Set the execution mode in the CLI configuration file so it persists across
restarts:

```bash
stigmer config set execution.mode sandbox
stigmer config set execution.sandbox_image ghcr.io/stigmer/agent-sandbox-basic:latest
```

## Custom sandbox images

To add dependencies your agents need (system packages, Python libraries, or
runtime tools), extend the base image:

```dockerfile
FROM ghcr.io/stigmer/agent-sandbox-basic:latest

USER root
RUN apt-get update && apt-get install -y --no-install-recommends \
    ffmpeg \
    && rm -rf /var/lib/apt/lists/*

RUN pip install --no-cache-dir pandas numpy

USER stigmer
```

Build and reference the custom image:

```bash
docker build -t my-sandbox:latest .
stigmer config set execution.sandbox_image my-sandbox:latest
```

## Docker prerequisite

Both levels of isolation require a running Docker daemon on the user's machine.
If your app offers sandbox mode, verify Docker availability before attempting to
start a sandboxed runner. The CLI checks automatically and provides a clear
error if Docker is not available.

## Choosing between the two levels

| Consideration         | Runner-level (`--runtime docker`)     | Command-level (`--execution-mode sandbox`) |
| --------------------- | ------------------------------------- | ------------------------------------------ |
| **What's isolated**   | Everything — runner + agent commands  | Only agent commands                        |
| **Startup speed**     | Slower — pulls and starts a container | Faster — runner starts natively            |
| **Host access**       | None                                  | Runner has host access; commands do not    |
| **Docker dependency** | Required for the runner itself        | Required for sandbox containers only       |
| **Best for**          | Maximum isolation, server deployments | Desktop apps with fast startup needs       |

For desktop app integrations, command-level isolation is usually the better
choice. It starts faster and gives the runner access to host resources (like
configuration files) while keeping agent commands sandboxed.
