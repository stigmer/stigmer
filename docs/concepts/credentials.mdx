  Credentials hold the keys and sign-ins your Agents and MCP Servers need at

[Agents](/docs/concepts/agents) and [MCP Servers](/docs/concepts/tools) need
secrets at runtime: an API key, a sign-in to Linear, a token for GitHub. Those
values never belong in the Agent or MCP Server definition. The same
`order-management-api` MCP Server is used by everyone in your Organization, and
each person may need to reach it with their own key.

A **Credential** is a saved set of values that belongs to someone: "my Linear
sign-in" and "my OpenAI key" belong to you; "the deploy bot's AWS key" and "our
Datadog key" belong to the Organization. When a run starts, Stigmer decides from
one rule which Credential fills each value the run needs.

## Who a Credential belongs to

Every Credential has an owner, fixed when it is created:

- **Yours.** A person's Credential holds their own keys and sign-ins. Only you
  can use it, edit it, and reveal its values. Nobody else in the Organization,
  admins included, can list it.
- **The Organization's.** An Organization's Credential holds a shared key. Only
  admins create and edit it. An admin decides who may use it by giving people or
  Teams the **user** role on it (the `can_use` permission). Its values are
  write-only: they can be replaced, never read back, by anyone.

You create a Credential with its values in the Stigmer Console, under **Settings
→ Accounts and keys**, or with the CLI. There is no manifest for it and no
`stigmer apply`: a secret never belongs in a file you commit.

```bash
# Your own OpenAI key, used by default for the research-agent Agent
stigmer credential create "OpenAI" \
  --from-env OPENAI_API_KEY \
  --serves agent:research-agent

# The Organization's Datadog key for the incident Agent (admins only)
stigmer credential create "Datadog (on-call)" --org-owned \
  --field DD_API_KEY=... \
  --plain DD_SITE=datadoghq.com \
  --serves agent:incident-agent
```

Each field is named after the key it fills. A field is a secret unless you mark
it plain (`--plain`): a secret is encrypted at rest and never returned, while a
plain value such as a URL or a region is stored and shown as it is.

The name is how you tell your Credentials apart ("OpenAI"). Stigmer adds a short
random suffix to the slug, so your "OpenAI" and a teammate's never collide.
[`stigmer credential`](/docs/cli/commands/credential) lists every command;
`stigmer list credentials` shows your own Credentials and the Organization's
ones you may use, and an admin sees all of the Organization's.

## What a Credential serves

A Credential's `serves` list names what it is for by default: an Agent, an MCP
Server, or a git host such as `github.com`. A run uses a Credential that serves
the thing asking for a value without anyone wiring it up.

- Connect Linear once, and every Agent that uses the Linear MCP Server runs with
  _your_ Linear when _you_ start it. A teammate's runs use theirs.
- An admin saves the Datadog key for the incident Agent and lets the on-call
  Team use it. Every on-call member's chat with that Agent then works, and
  nobody else's does.

At most one of your Credentials, and at most one of the Organization's, may
serve the same Agent, MCP Server or git host. Saving a second one is refused and
names the first, so a run never has to choose between two.

## Sign-ins are Credentials

When you sign in to an MCP Server that uses OAuth, Stigmer saves the access
token as your own Credential, serving that server, with one field named by the
server's `auth.target_env_var`. The platform keeps the token fresh; you cannot
edit its fields by hand, only sign out. The refresh token never becomes a field:
it stays sealed with the sign-in, where no run receives it and nobody can reveal
it.

An MCP Server's author decides whose account its runs use with `sign_in`:

| `sign_in`                                   | Whose sign-in a run uses                                                                              |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `mcp_server_sign_in_personal` (the default) | The sign-in of the person who started the run. Each person signs in with their own account.           |
| `mcp_server_sign_in_organization`           | One sign-in for the whole Organization, made once by an admin. Every run in the Organization uses it. |

## Declaring what a run needs

[Agents](/docs/concepts/agents) and [MCP Servers](/docs/concepts/tools) declare
the values they need through the `env` map. Each declared key is a
**requirement**, and the Agent or MCP Server that declares it is its declarer:

```yaml validate-as="McpServer"
# In the McpServer definition
spec:
  env:
    ORDER_API_URL:
      is_secret: false
      description: Base URL of the order management API
    ORDER_API_KEY:
      is_secret: true
      description: API key for the order management service
```

This is a _schema_, not a value. It says "this server needs these values at
runtime". A Workspace that clones a repository from a git host needs one more:
`GITHUB_TOKEN`, declared by the host itself.

Requirements keep their declarer. An Agent's `env` holds what the Agent itself
needs (the keys its shell commands read); each MCP Server's needs stay on the
server, and reach every Agent that uses it.

## How a run gets its values

Every message in a [Session](/docs/concepts/sessions) is one run. When it is
created, Stigmer fills each requirement from the first of these sources that has
a value:

  chart={`
graph TD
  R["Requirement<br/>declarer + key"] --> P{"Passed for<br/>this run?"}
  P -- yes --> V["Value"]
  P -- no --> S{"Assigned on the schedule,<br/>share link, channel or<br/>platform client?"}
  S -- yes --> V
  S -- no --> D{"A Credential that<br/>serves the declarer?"}
  D -- yes --> V
  D -- no --> X["Required: the run is refused<br/>Optional: left absent"]
`}

1. **Values passed for this one run.** The request's `runtime_env`, by key.
2. **The surface that started the run.** A schedule, a share link, a channel or
   a platform client starts runs with no person behind them, so it carries the
   values those runs use as Credential assignments (see
   [below](#assignments-on-unattended-surfaces)).
3. **The default Credential, for a run a person started.**
   - An MCP Server with personal sign-in: your own Credential serving it.
   - An MCP Server with Organization sign-in: the Organization's Credential
     serving it.
   - An Agent or a git host: your own Credential serving it first, then the
     Organization's Credential serving it if you may use that Credential. This
     is how a Team key reaches a member's chat.
4. **Nothing.** A required key refuses the run before it starts, naming the key
   and who must act, for example "Linear: Ben has not signed in". An optional
   key is left absent.

Only Credentials in the run's own Organization are read. A person's Credentials
in another Organization never reach the run, so an admin of a parent
organization acting in a child organization brings none of theirs.

A run has a person only when a person started it directly. A schedule fire, a
channel message, a visitor on a share link, a machine account and a platform
client's users start runs with no person, and those runs take no default: they
use only what is passed and what is assigned. A run records its person when it
is created, so recovering it later uses the same person's Credentials.

<Callout type="warn">
  A Credential's values reach the tools and the shell of the Agent the run uses,
  and those follow the instructions the Agent's author wrote. Your own
  Credential fills an Agent's own keys only when it serves that Agent, so saying
  which Agents a key is for is your consent to send it to them.
</Callout>

Two requirements with the same key must agree. When they would get different
values, for example two MCP Servers that both read `API_KEY` from different
Credentials, the run is refused and names both declarers rather than one value
winning unnoticed. One GitHub sign-in that serves both the GitHub MCP Server and
`github.com` is one value, not a conflict.

## Assignments on unattended surfaces

A schedule's invocation, a share, a channel and a platform client each carry a
`credentials` list. Each entry is a **Credential assignment**: a requirement (a
declarer and a key) and where its value comes from, either a field of a
Credential or a plain literal written on the surface itself.

```yaml
apiVersion: agentic.stigmer.ai/v1
kind: Schedule
metadata:
  name: nightly-returns-report
  org: acme
spec:
  cron: "0 6 * * *"
  time_zone: Europe/Berlin
  enabled: true
  agent:
    agent_ref:
      kind: agent
      org: acme
      slug: support-agent
    message: Summarize yesterday's returns.
    credentials:
      - requirement:
          declarer:
            mcp_server:
              kind: mcp_server
              org: acme
              slug: order-management-api
          key: ORDER_API_KEY
        credential:
          credential:
            kind: credential
            org: acme
            slug: orders-production-3f9a1c7e
      - requirement:
          declarer:
            mcp_server:
              kind: mcp_server
              org: acme
              slug: order-management-api
          key: ORDER_API_URL
        literal: https://api.acme.com/orders
```

A Credential field reference with no `field` takes the field named like the
requirement's key. The same Agent runs against test keys from one schedule and
production keys from another; its definition never changes.

Who may assign what:

- **You assign only Credentials you may use.** Stigmer records you as the
  assignment's writer. When a run starts, it checks again that the writer may
  still use the Credential, and refuses the run, naming the assignment, when
  they no longer can.
- **Your own Credential is assigned only on your own schedule.** A schedule is
  the one surface whose runs are yours, unattended. A share link, a channel and
  a platform client serve other people, so they take only the Organization's
  Credentials, and an edit that keeps your Credential on your schedule is yours
  alone to make.
- **Changing the Agent re-checks every assignment.** Pointing a schedule, share
  or channel at another Agent sends its values to that Agent's tools, so every
  assignment it keeps is checked against the person making the change and
  recorded as theirs.

## Reveal and write-only

You can reveal one field of your own Credential at a time, in the console or
with `stigmer credential reveal <credential> <field>`. An Organization's
Credential is write-only for everyone: an admin replaces a field with
`stigmer credential set-fields`, and nobody reads it back. Every other read,
`stigmer get credential` included, shows secret values redacted.

## Secrets vs. configuration

A declaration's `is_secret` flag and a Credential field's `plain` flag decide
how a value is handled:

|                    | Configuration | Secrets       |
| ------------------ | ------------- | ------------- |
| **Visible in UI**  | Yes           | Masked        |
| **In logs**        | Yes           | Redacted      |
| **In audit trail** | Full value    | Presence only |

Mark anything sensitive (API keys, passwords, tokens) as a secret. Stigmer
handles the masking and redaction automatically.

## What a running Agent sees

Stigmer gathers the values into a single **ExecutionContext** for the run, and
the runner uses that map at execution time. Different surfaces see different
slices of it:

| Surface                                            | What the Agent sees                                                                                                                                                                                                                                                                  |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Shell commands** (native harness `execute` tool) | The runner's own process variables, minus runner-internal credentials, plus only the ExecutionContext values the Agent declares in its `env`, and the `GITHUB_TOKEN` a git clone of the Workspace used. An Agent that declares nothing gets no ExecutionContext values in its shell. |
| **MCP stdio servers**                              | Only variables declared in the MCP server's `env` map, taken from ExecutionContext, plus a minimal base set (`PATH`, `HOME`, and similar). A server that declares nothing gets only that base set — never the runner's own variables.                                                |

Agent shell commands inherit `PATH` and other host settings from the runner so
local CLIs work, while ExecutionContext supplies the API keys and service URLs
your Agent declares. Every surface follows the same declare-to-receive rule: a
key an MCP server declares reaches that server and never the shell, so a shell
command that needs a key (a cloud CLI, `stigmer`, `gh` with its own token) works
only when the Agent declares it. The one exception is the `GITHUB_TOKEN` a git
Workspace was cloned with: the clone already stores it where the shell can read
it, so the shell receives it as well. The built-in assistant has no Agent and so
declares nothing: its shell receives no ExecutionContext values beyond that
token, so a task whose shell needs a key runs on an Agent that declares it.
Secret values are redacted in logs and the UI regardless of which surface
consumes them.
