## Overview

Stigmer Cloud uses a **prepaid credit wallet**. You purchase credits before
running Agents. Each LLM call during an Agent Execution is metered and the cost
is debited from your balance in real time.

- **1 credit = $0.01 USD** (10,000 micro-USD internally)
- Credits are dollar-denominated — no abstract unit conversion
- Self-hosted Stigmer (OSS) has no billing — it runs on your infrastructure

## Credit packs

Credits are sold in fixed packs through Stripe Checkout:

| Pack    | Price | Credits |
| ------- | ----- | ------- |
| Starter | $10   | 1,000   |
| Growth  | $50   | 5,000   |
| Team    | $200  | 20,000  |

New accounts receive a one-time promotional credit grant to explore the
platform. Promotional credits expire after 90 days. Purchased credits expire 12
months from purchase.

## How pricing works

Each LLM call has a cost based on three factors:

1. **Model** — different models have different per-token rates
2. **Token count** — input tokens, output tokens, cache writes, and cache reads
3. **Billing policy** — a markup multiplier applied over the raw provider rate

The formula for a single call:

```
billable_amount = (input_tokens × input_rate / 1M)
                + (output_tokens × output_rate / 1M)
                + (cache_write_tokens × cache_write_rate / 1M)
                + (cache_read_tokens × cache_read_rate / 1M)
```

Rates are per million tokens with the platform markup already included. You can
see current rates on the [pricing page](https://stigmer.ai/pricing) or via the
`getCustomerModelPricing` API.

### Platform commission

Stigmer applies a flat **10% commission** on top of provider rates — the same on
both execution harnesses:

| Harness | Commission | What you pay         |
| ------- | ---------- | -------------------- |
| Native  | 10%        | Provider rate × 1.10 |
| Cursor  | 10%        | Provider rate × 1.10 |

The commission covers the operational stack Stigmer runs around every call: the
LLM proxy, cache-aware metering, cost caps, and execution lifecycle management.
For example, if a model's provider input rate is $3.00 per million tokens, you
pay $3.30 per million input tokens on either harness.

### Cursor Token Rate

Cursor-harness models can carry one cost the native harness does not: the
**Cursor Token Rate**. On Cursor Teams plans, Cursor charges a small per-token
fee on top of the underlying model price for non-Auto requests. Stigmer pays
that fee and folds it into the model's cost base _before_ the 10% commission, so
the price you see already includes it:

```
billable_per_token = (provider_rate + cursor_token_rate) × 1.10
```

The Cursor Token Rate is zero for the native harness and for exempt Cursor
models (Auto and the Composer pool), which are priced as `provider_rate × 1.10`.
For a Cursor model that does carry the rate, the same underlying model costs
slightly more on Cursor than on native — that difference is Cursor's fee, not a
higher Stigmer commission.

Rates on the [pricing page](https://stigmer.ai/pricing) and the
`getCustomerModelPricing` API already include the commission and any Cursor
Token Rate — you always see the final price you pay. Pricing is versioned and
only affects future usage; historical charges are immutable.

### Ledger-verified rates

Stigmer Cloud continuously reconciles its rates against the providers' own
billing ledgers (the Anthropic admin usage/cost reports and Cursor's team
usage-event ledger). When a provider's observed rate drifts from the published
rate, the platform corrects the rate automatically within a small tolerance —
larger changes require an explicit operator sign-off. Corrections apply forward
only: every historical charge keeps the exact rates that were in effect when it
was billed.

## Optimizing your costs

Most of what you spend is provider token cost; Stigmer's commission is a flat
10% on top. The biggest savings come from sending fewer tokens, reusing cached
ones, and matching the model and harness to the job. The levers below are
ordered by impact.

### Reuse the prompt with caching

Anthropic models bill cached prefix tokens at a fraction of the normal rate: a
**cache read costs about one-tenth of the input rate**, and a **cache write
about 1.25× input**. Re-reading a stable prefix (system instructions, Skills,
earlier turns) therefore costs about **90% less** than sending it fresh, and the
advantage compounds as a Session grows.

- **Native** gives you explicit control: the harness sets cache breakpoints on
  the stable prefix, and every follow-up turn re-reads it.
- **Cursor** caches automatically and opaquely — you benefit without configuring
  anything, but with less control over what is cached.

Keep the stable part of your prompt (instructions, Skills) first and the
variable part (the user's message) last, so the cacheable prefix stays constant
across turns.

### Pick the harness for the job

Commission is identical on both harnesses, so harness choice is about
**capability and the Cursor Token Rate**, not commission:

| If you need…                                | Prefer | Why                                                            |
| ------------------------------------------- | ------ | -------------------------------------------------------------- |
| The lowest cost on a given model            | Native | No Cursor Token Rate; direct provider pricing × 1.10           |
| The widest model catalog or a cheaper model | Native | All supported providers; downgrade the model for simple tasks  |
| Built-in coding tools (edit, shell, search) | Cursor | The tooling is worth the added per-call context and token rate |

Reach for Cursor when you want its coding tooling — not as a default, since a
Cursor model that carries the token rate is cheaper to run on native. See
[Harnesses](/docs/concepts/harnesses) for the full capability comparison and the
[measured cost comparison](/docs/concepts/harnesses#measured-cost-comparison)
for real benchmark numbers — same model, same prompt, per task category.

### Match the model to the task

Within a harness, model choice is usually the largest single lever — premium
models can cost an order of magnitude more per token than economy ones. Use a
small, cheap model for routine work (classification, short replies, summaries)
and reserve premium models for genuinely hard reasoning. The
[pricing page](https://stigmer.ai/pricing) and `getCustomerModelPricing` list
the current per-token rate for every model.

### Manage Session and turn length

A Session resends its accumulated context on every turn, so cost grows with
conversation length:

- Start a fresh Session for an unrelated task instead of extending a long one.
- Attach only the Skills and tools a Session needs — every attached Skill is
  tokens on every turn.
- Lean on caching so the growing prefix is re-read cheaply rather than re-billed
  at full rate.

### Set budget guardrails

Stigmer caps spend automatically so a runaway Agent cannot drain your balance:

- Each execution **reserves** budget up front and stops when the balance is
  exhausted — see [Execution billing lifecycle](#execution-billing-lifecycle).
- `low_balance_warning` then `stop_execution` signals tell the Agent to wrap up
  as the balance runs down — see
  [Low balance and stop behavior](#low-balance-and-stop-behavior).
- [Automatic recharge](#automatic-recharge) with a **monthly cap** keeps you
  topped up without unbounded spend.

## Execution billing lifecycle

When an Agent Execution runs on Stigmer Cloud, billing follows a four-phase
lifecycle:

### 1. Authorization

Before the Agent Runner starts, the billing system **reserves** credits from
your available balance. This reservation ensures the execution has budget to
operate.

- Default reservation: $1.00
- Minimum balance to start: $0.05
- If your balance is below $1.00 but above $0.05, a partial reservation is made
  for whatever is available

### 2. Per-call debit

As each LLM call completes, the proxy extracts token usage from the provider's
response and records it. The billing system computes the cost server-side (using
frozen rates from the model registry, not caller-provided data) and debits it
from the reservation.

After each debit, a **billing signal** is returned:

- `continue` — balance is healthy
- `low_balance_warning` — balance is getting low
- `stop_execution` — balance is exhausted; the Agent should wrap up

### 3. Finalization

When the execution completes (success, failure, or cancellation), unused
reservation credits are **released** back to your available balance. A summary
of the execution's total cost is recorded.

### 4. Reservation expiry (safety net)

If an execution never finalizes (crash, network partition), reservations expire
automatically after 1 hour. Expired reservations release unused credits back to
the available balance.

## Balance model

Your billing account tracks credits in two buckets:

- **Available** — credits you can use for new executions
- **Reserved** — credits held by active execution reservations

The invariant is: `total = available + reserved`.

Credits are also categorized by source:

- **Purchased** — from Stripe payments and automatic recharge
- **Promotional** — from free trial grants and campaigns

Promotional credits are consumed first (burn-order priority), so your purchased
credits last longer.

## Automatic recharge

Save a payment method during your first purchase, then configure automatic
recharge in your billing settings:

- **Threshold** — recharge when available balance drops below this amount
- **Recharge amount** — fixed amount to charge per event
- **Monthly cap** — maximum total recharge spend per calendar month

payment method. Credits appear after payment confirmation (typically a few

## Low balance and stop behavior

When your balance gets low during an execution:

1. At the **low balance threshold**, a `low_balance_warning` signal is sent to
   the Runner and automatic recharge is triggered (if configured)
2. At **zero balance**, a `stop_execution` signal tells the Runner to finish the
   current LLM call and stop — the Agent summarizes its progress and exits
3. **New executions** cannot start when the available balance is below $0.05

## Credit ledger

Every balance-affecting operation produces an **immutable ledger entry**:

- `purchase_credit` — Stripe Checkout purchase
- `auto_recharge_credit` — automatic top-up
- `promotional_credit` — trial or campaign grant
- `usage_debit` — LLM call cost deduction
- `reservation_hold` — credits reserved at execution start
- `reservation_release` — unused credits returned after execution
- `adjustment_credit` / `adjustment_debit` — manual admin adjustments
- `refund_reversal` — Stripe refund reversal
- `expiry_debit` — expired credit removal

All entries are append-only and deduplicated by an idempotency key.

## Payment methods

Payment methods are managed through the **Stripe Customer Portal**. You can add,
update, or remove cards without leaving the Stigmer billing flow. Your default
payment method is used for automatic recharge.

## Self-hosting

Stigmer is fully open source under Apache 2.0. When you self-host, there is no
billing — you pay your own LLM provider costs directly. Billing only applies
when using Stigmer Cloud at [`app.stigmer.ai`](https://app.stigmer.ai).
