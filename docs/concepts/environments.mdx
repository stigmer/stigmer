[Agents](/docs/concepts/agents) and [MCP Servers](/docs/concepts/tools) need
configuration at runtime — API keys, service URLs, feature flags. But these
values don't belong in the Agent or MCP Server definition. The same
`order-management-api` MCP Server should point to a test API in development and
a production API in production.

Environments solve this. An Environment is a named, persistent collection of
configuration values and secrets. Agent Instances reference one or more
Environments, and Stigmer resolves the values at runtime.

## What an Environment looks like

```yaml
apiVersion: agentic.stigmer.ai/v1
kind: Environment
metadata:
  name: production-secrets
  org: acme
spec:
  description: Production API keys and service URLs.
  data:
    ORDER_API_URL:
      value: "https://api.acme.com/orders"
      is_secret: false
      description: Base URL for the order management API
    ORDER_API_KEY:
      value: "sk-prod-..."
      is_secret: true
      description: Production API key for the order service
    SUPPORT_EMAIL:
      value: "support@acme.com"
      is_secret: false
      description: Email address for customer support
```

Each variable has:

| Field         | Purpose                                                                          |
| ------------- | -------------------------------------------------------------------------------- |
| `value`       | The actual value                                                                 |
| `is_secret`   | Whether the value should be treated as a secret (redacted in logs, masked in UI) |
| `description` | Human-readable description of what this variable is for                          |

## Environment layering

An Agent Instance can reference multiple Environments. They merge in order —
later Environments override earlier ones for the same variable name:

```yaml
apiVersion: agentic.stigmer.ai/v1
kind: AgentInstance
metadata:
  name: support-agent-production
spec:
  agent_id: agt-abc123
  environment_refs:
    - kind: environment
      slug: shared-config
    - kind: environment
      slug: production-secrets
```

This layering lets you separate concerns:

- **Shared configuration** — URLs, feature flags, non-sensitive settings shared
  across Agents
- **Per-Environment secrets** — API keys, credentials, tokens specific to
  dev/staging/production
- **Per-Agent overrides** — Settings that only one Agent needs

## Declaring required variables

[Agents](/docs/concepts/agents) and [MCP Servers](/docs/concepts/tools) declare
which variables they need at runtime through the `env` map:

```yaml validate-as="McpServer"
# In the McpServer definition
spec:
  env:
    ORDER_API_URL:
      is_secret: false
      description: Base URL of the order management API
    ORDER_API_KEY:
      is_secret: true
      description: API key for the order management service
```

This is a _schema_, not a value assignment. It says "this resource needs these
variables at runtime." The actual values come from the Environments attached to
the Agent Instance.

If a required variable is missing at runtime, the Agent fails fast with a clear
error — not halfway through a tool call.

## Secrets vs. configuration

The `is_secret` flag matters:

|                    | Configuration | Secrets       |
| ------------------ | ------------- | ------------- |
| `is_secret`        | `false`       | `true`        |
| **Visible in UI**  | Yes           | Masked        |
| **In logs**        | Yes           | Redacted      |
| **In audit trail** | Full value    | Presence only |

Mark anything sensitive — API keys, passwords, tokens, credentials — as a
secret. Stigmer handles the masking and redaction automatically.

## Private and shared Environments

An Environment is **private** by default: only you can use it, and only you can
reveal its secret values. On Stigmer Cloud, you can share an Environment with
your Organization by setting its visibility to **Organization**:

- Agents and Workflows run in your Organization can use its values at runtime.
  This includes runs by your teammates and visitor chats on
  [shared Agents](/docs/guides/sharing/share-an-agent).
- Members can see the Environment and its variable names, but secret values stay
  masked. Revealing a secret value remains yours alone, at every visibility
  level.
- Setting it back to **Private** takes effect on the next run.

Environments never go beyond the Organization — there is no public or platform
visibility for secrets.

## How values resolve at runtime

When an Agent runs, Stigmer merges the Environments attached to its Agent
Instance into a single **ExecutionContext**. That merged map is what the runner
uses at execution time. Different surfaces see different slices of it:

| Surface                                            | What the Agent sees                                                                                                                                                      |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Shell commands** (native harness `execute` tool) | The runner's own process variables, minus runner-internal credentials, with ExecutionContext values overlaid on top. Overlay wins when a name exists in both.            |
| **MCP stdio servers**                              | Only variables declared in the MCP server's `env_spec`, taken from ExecutionContext. If the server declares no env, the runner falls back to its full process variables. |

Shell commands inherit `PATH` and other host settings from the runner so local
CLIs work, while ExecutionContext supplies API keys and service URLs your Agent
declares. Secrets marked `is_secret: true` are still redacted in logs and the UI
regardless of which surface consumes them.
