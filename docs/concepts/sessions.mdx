When a user talks to an Agent, the conversation needs memory. The second message
should know about the first. The Agent should remember an order number mentioned
earlier without the user repeating it. That context lives in a Session.

A Session is a conversation context that holds message history and connects a
user to an [Agent](/docs/concepts/agents). When a user sends a message, the
Agent sees the full conversation history from that Session — it knows what was
asked before, what tools were called, and what the outcomes were.

## Sessions in action

The Agent remembers context across messages. When a user mentions an order in
the first message, the Agent recalls the product and order number in the second
— without the user repeating any details.

This works because both messages exist in the same Session. The Agent sees the
complete thread when processing each new message.

## How Sessions fit in the lifecycle

A Session names the Agent it talks to, and each message in it is one run:

[run](/docs/concepts/agents#blueprint-vs-runtime). The run sees all previous
messages from the Session — this is how the Agent remembers context.

## Creating a Session

In the SDK, you create a Session by naming the Agent it talks to:

<Tabs items={["TypeScript", "Go"]}>
  <Tab value="TypeScript">
```typescript
const session = await client.session.create({
  name: "order-inquiry",
  org: "acme",
  subject: "Order inquiry",
  agentRef: { org: "acme", slug: "support-agent" },
});
```
  </Tab>
  <Tab value="Go">

```go
session, err := client.Session.Create(ctx, &stigmer.SessionInput{
    Name:    "order-inquiry",
    Org:     "acme",
    Subject: "Order inquiry",
    AgentRef: stigmer.ResourceRef{Org: "acme", Slug: "support-agent"},
})
```

  </Tab>
</Tabs>

If you name no Agent, the Session runs the
[built-in assistant](/docs/concepts/agents#the-built-in-assistant) — the same
one the [Quickstart](/docs/getting-started/quickstart) talks to. A Session can
later name an Agent, change it, or drop it again through an update.

A Session can name an Agent of another Organization only when that Organization
is its parent and shares the Agent with its child organizations
(`visibility_child_orgs`).

## Which version a Session runs

An Agent keeps a [version](/docs/concepts/agents#versions) for every change to
its definition. A Session runs the version that was current when it started, and
stays on it. When the Agent's author saves a change, conversations already under
way keep the instructions, Skills and tools they started with; the change
reaches them only when someone updates them:

- **In the console**, a conversation on an older version says so and offers to
  update it to the current version.
- **Through the API**, update the Session with the Agent reference's `version`
  set to `latest`:

  ```yaml validate-as="Session"
  spec:
    agent_ref:
      kind: agent
      org: acme
      slug: support-agent
      version: latest
  ```

  An update that sends the reference unchanged, with no version, keeps the
  version the conversation runs.

To start a conversation on a particular version instead of the current one, name
a tag or a version hash in the reference (`version: stable`). Every
[run](/docs/concepts/agents#versions) records the Agent and version it ran.

## Who may send a message

Starting a conversation on an Agent, or switching a Session to another Agent,
needs permission to run that Agent. Every message asks again: if the Agent's
author makes it private, or your access to it is removed, your next message in
an existing conversation is refused. If the Agent is deleted, the next message
fails and the error names the Agent.

The keys an Agent declares in its `env` are filled when each message runs. When
the Agent belongs to the Organization the conversation runs in, the ones nothing
else supplies come from your personal Environment; an Agent another Organization
published reads none of them. Those keys reach the Agent's tools and its shell,
which follow the instructions the Agent's author wrote. An MCP Server's OAuth
variable comes only from the sign-in to that server, never from your personal
Environment. Before your first message in a conversation, the console names the
keys the Agent declares.
[Environments](/docs/concepts/environments#how-a-run-gets-its-values) explains
every source.

## Harness

Every Session runs on a [Harness](/docs/concepts/harnesses) — the execution
engine that processes the Agent's turns. Stigmer supports two: **Native** (the
default) and **Cursor** (for Cursor SDK-powered execution with access to
Cursor-specific models and coding tools).

You set the Harness when creating a Session; when you set none, the Session
starts on the Agent's own `harness`, or native when the Agent names none. Once
the first run starts, the Harness is locked for that Session.

```yaml validate-as="Session"
spec:
  harness: HARNESS_CURSOR
```

See [Harnesses](/docs/concepts/harnesses) for a full comparison.

## Session-level additions

Sessions can customize an Agent's behavior for a specific conversation without
changing the Agent definition. Two key additions:

### Skills

Add domain knowledge for this conversation only:

```yaml validate-as="Session"
spec:
  skill_refs:
    - kind: skill
      slug: seasonal-promotions
```

Session-level Skills merge with the Agent's Skills. If the same Skill appears in
both, the Session-level reference takes precedence.

### Tools

Attach an MCP Server for this conversation only:

```yaml validate-as="Session"
spec:
  mcp_server_usages:
    - mcp_server_ref:
        kind: mcp_server
        slug: inventory-api
```

Session-level servers merge with the Agent's, one entry per server. The Agent's
`tools` and `disallowed_tools` lists govern them like the Agent's own servers:
an Agent whose `tools` list does not name `mcp__inventory-api` cannot use it. To
narrow what an Agent can do, change its lists.

## Session lifecycle

Sessions persist until explicitly deleted. You can:

- **Resume** a Session by sending new messages to the same Session ID
- **List** past Sessions, or every Session on one Agent, and their run history
- **Delete** a Session when the conversation is no longer needed

Each Session maintains its own thread of messages. The Agent sees the complete
history when processing a new message, so context accumulates over the
conversation.

the difference between local and cloud runners, and how Sessions find the right
