A Session is one piece of work an [Agent](/docs/concepts/agents) does for
someone: one customer's quarter reviewed, one month's books closed. Your app
starts it when a customer asks for the work, the way it would put a job on a
queue. It holds the conversation with whoever asked, the computer the Agent
works on, an ordered log of everything that happened, and the files that went in
and came out.

When someone sends a message, the Agent sees the whole conversation so far: what
was asked before, what tools it called, and what came back.

## Sessions in action

The Agent remembers context across messages. When a customer asks for this
quarter's variance report in the first message, and for the flagged accounts
only in the second, the Agent knows which ledger and which quarter they mean,
without the customer naming them again.

This works because both messages exist in the same Session. The Agent sees the
complete thread when processing each new message.

## How Sessions fit in the lifecycle

A Session names the Agent it talks to, and each message in it is one run:

Each request-response cycle within a Session creates an
[run](/docs/concepts/agents#blueprint-vs-runtime). The run sees all previous
messages from the Session — this is how the Agent remembers context.

## What a Session keeps

A Session keeps three things for as long as it exists:

- **The computer its Agent works on.** On Stigmer Cloud, and on a self-hosted
  server that
  [starts a runner per Session](/docs/guides/self-hosting/runners#a-runner-per-session),
  that is a sandbox of its own, which keeps the files the Agent works on between
  turns and goes when the Session does. What survives while it sleeps depends on
  the sandbox
  ([Environments](/docs/concepts/environments#when-packages-install-and-when-a-change-takes-effect)).
  A self-hosted server with one shared runner runs every Session's turns on that
  runner instead.
- **Its events.** Everything the Agent does is written to one ordered log of
  events, in the Claude Managed Agents event format: its messages, its tool uses
  and their results, the calls waiting for an approval, and each run's phase.
  Your app follows the log as it grows ([Streaming](/docs/sdk/streaming)).
- **Its files.** The Files you give it, and what the Agent saves in its outputs
  folder, which come back as Files of the Session
  ([Files](/docs/concepts/files)).

## A job that runs for hours

A turn in a Session is a job, not one request to a model. When a customer
uploads a year of ledgers, the Agent can work through them for two hours in one
turn, and the turn keeps going for as long as the job takes:

- **It stays at work while it waits.** While a tool runs or the model answers,
  the turn is working, and your app sees what it has open and for how long
  (`stigmer.run.liveness` in
  [Stigmer's own events](/docs/sdk/streaming#stigmers-own-events)).
- **It carries on through a restart.** When the server or the runner restarts in
  the middle of a turn, for an upgrade or after a crash, the turn picks up where
  it was. The model is never handed the task a second time.
- **Your app misses nothing.** A dropped event stream picks up after the last
  event your app read
  ([Resume a dropped stream](/docs/sdk/streaming#resume-a-dropped-stream)).
- **You can steer it while it works.** A message sent during the turn waits in
  the Session, and the turn reads it at its next step, without starting over. On
  the [Cursor harness](/docs/concepts/harnesses#cursor-harness), when Cursor
  can't take the message mid-run, the turn reads it as soon as that run ends
  (`user.message` in [Read the events](/docs/sdk/streaming#read-the-events)).
- **It tells its person when it needs them.** When the turn finishes, fails or
  waits for an answer, the person who started the Session is told, in the
  console and the desktop app, and your app can follow the same notices
  ([Know when a conversation needs you](/docs/sdk/streaming#know-when-a-conversation-needs-you)).
- **It keeps its place as the work grows.** When the conversation outgrows the
  model's context, it is summarized and the turn carries on, and each summary is
  an `agent.thread_context_compacted` event in the Session. On the
  [native harness](/docs/concepts/harnesses#native-harness), each summary
  carries the person's request forward, so the Agent keeps to its goal.

## Creating a Session

In the SDK, you create a Session by naming the Agent it talks to:

<Tabs items={["TypeScript", "Go"]}>
  <Tab value="TypeScript">
```typescript
const session = await client.session.create({
  name: "q3-variance-review",
  org: "acme",
  subject: "Q3 variance review",
  agentRef: { org: "acme", slug: "variance-reporter" },
});
```
  </Tab>
  <Tab value="Go">

```go
session, err := client.Session.Create(ctx, &stigmer.SessionInput{
    Name:    "q3-variance-review",
    Org:     "acme",
    Subject: "Q3 variance review",
    AgentRef: stigmer.ResourceRef{Org: "acme", Slug: "variance-reporter"},
})
```

  </Tab>
</Tabs>

If you name no Agent, the Session runs the
[built-in assistant](/docs/concepts/agents#the-built-in-assistant). A Session
can later name an Agent, change it, or drop it again through an update.

A Session can name an Agent of another Organization only when that Organization
is its parent and shares the Agent with its child organizations
(`visibility_child_orgs`).

## Which version a Session runs

An Agent keeps a [version](/docs/concepts/agents#versions) for every change to
its definition. A Session runs the version that was current when it started, and
stays on it. When the Agent's author saves a change, conversations already under
way keep the instructions, Skills and tools they started with; the change
reaches them only when someone updates them:

- **In the console**, a conversation on an older version says so and offers to
  update it to the current version.
- **Through the API**, update the Session with the Agent reference's `version`
  set to `latest`:

  ```yaml validate-as="Session"
  spec:
    agent_ref:
      kind: agent
      org: acme
      slug: variance-reporter
      version: latest
  ```

  An update that sends the reference unchanged, with no version, keeps the
  version the conversation runs.

To start a conversation on a particular version instead of the current one, name
a tag or a version hash in the reference (`version: stable`). Every
[run](/docs/concepts/agents#versions) records the Agent and version it ran, and
the version of every Skill and Plugin each turn loaded.

## Who may send a message

Starting a conversation on an Agent, or switching a Session to another Agent,
needs permission to run that Agent and the Organization's Member role or higher:
an Organization Viewer reads what is shared and starts no conversation. Every
message asks again: if the Agent's author makes it private, or your access to it
is removed, your next message in an existing conversation is refused. If the
Agent is deleted, the next message fails and the error names the Agent.

A conversation is private to the person who started it. In the Enterprise and
Cloud editions its owner may share it with people: a **Participant** reads it
and sends messages, which run in the conversation's Workspace as the person who
started it, and a **Viewer** reads it and sends nothing.
[Sharing and access](/docs/concepts/sharing-and-access#conversations) explains
both.

The keys an Agent declares in its `env` are filled when each message runs, from
the vaults the conversation uses: the My vault of the person sending the
message, when the conversation includes it, then the vaults the conversation
lists. You choose them when you start the conversation, as you choose its Agent,
and only the person who started it may change them. Those keys reach the Agent's
tools and its shell, which follow the instructions the Agent's author wrote.
Before your first message in a conversation, the console names the keys the
Agent declares. [Vaults](/docs/concepts/vaults#which-vaults-a-run-uses) explains
every source.

## Harness

Every Session runs on a [Harness](/docs/concepts/harnesses) — the execution
engine that processes the Agent's turns. Stigmer supports two: **Native** (the
default) and **Cursor** (for Cursor SDK-powered execution with access to
Cursor-specific models and coding tools).

You set the Harness when creating a Session; when you set none, the Session
starts on the Agent's own `harness`, or native when the Agent names none. Once
the first run starts, the Harness is locked for that Session.

```yaml validate-as="Session"
spec:
  harness: HARNESS_CURSOR
```

See [Harnesses](/docs/concepts/harnesses) for a full comparison.

## Session-level additions

Sessions can customize an Agent's behavior for a specific conversation without
changing the Agent definition. Four key additions:

### Skills

Add domain knowledge for this conversation only:

```yaml validate-as="Session"
spec:
  skill_refs:
    - kind: skill
      slug: year-end-adjustments
```

Session-level Skills merge with the Agent's Skills. If the same Skill appears in
both, the Session-level reference takes precedence.

### Tools

Attach a plugin for this conversation only, with its MCP servers, Skills, agents
and hooks:

```yaml validate-as="Session"
spec:
  plugins:
    - kind: plugin
      slug: payroll
```

Session-level plugins join the Agent's, one entry per plugin; from the CLI,
`stigmer run --plugin payroll` does the same. The Agent's `tools` and
`disallowed_tools` lists govern them like the Agent's own: an Agent whose
`tools` list does not name `mcp__plugin_payroll_payroll` cannot use that server.
To narrow what an Agent can do, change its lists. A conversation with no Agent
gets its tools from these plugins alone.

### Environment

Run this conversation's sandbox in an [Environment](/docs/concepts/environments)
other than its Agent's default: the packages installed before its first turn and
the websites it may reach.

```yaml validate-as="Session"
spec:
  environment_ref:
    kind: environment
    slug: data-science
```

From the CLI, `stigmer run --environment data-science` does the same. The
conversation keeps the Environment it started with: naming another after its
first turn is refused.

### Files and repositories

Give this conversation the [Files](/docs/concepts/files) and git repositories it
works on. The Agent finds each File under `.stigmer/uploads/` and each
repository cloned in its workspace, on every turn:

```yaml validate-as="Session"
spec:
  resources:
    - file:
        file_id: file_01j9zq6v8w3x4y5z6a7b8c9d0e
        mount_path: q3/ledger.xlsx
    - name: finance-models
      git_repository:
        url: https://github.com/acme/finance-models
```

A File sent with a message joins this list too, so the Agent still has it on
later turns. What the Agent saves in `.stigmer/outputs/` comes back as Files of
the conversation; [Files](/docs/concepts/files) explains both directions.

## Session lifecycle

Sessions persist until explicitly deleted. You can:

- **Resume** a Session by sending new messages to the same Session ID
- **List** past Sessions, or every Session on one Agent, and their run history
- **Delete** a Session when the conversation is no longer needed

Each Session maintains its own thread of messages. The Agent sees the complete
history when processing a new message, so context accumulates over the
conversation.
