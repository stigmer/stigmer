[Tools](/docs/concepts/tools) give agents the ability to act. Approval flows
make the risky actions pause for a human decision.

This is not a logging feature. When an Agent encounters an action that requires
approval, it stops, presents what it wants to do and why, and waits for a human
to approve, skip, or reject before proceeding. The Agent's execution is durable
— it waits indefinitely without losing state.

## What asks for approval

By default there is nothing to configure. Stigmer asks before:

- shell commands
- file writes and deletes
- any MCP tool whose server marks it destructive, with the MCP annotation
  `destructiveHint: true`

Nothing else asks. Stigmer reads the annotation when you connect the
[MCP Server](/docs/concepts/tools), so the server's author decides which of its
tools are destructive. A server that annotates nothing never asks.

Stigmer records the annotations each time a server connects, and reads them from
that record. Connect a server again after its author changes them. A server
connected before Stigmer recorded annotations asks for nothing until it is
connected again, so connect each existing server once after upgrading.

An Agent's hooks can change that, call by call. A hook is a command in Claude
Code's hooks format, from a plugin or written in the Agent itself, that runs
before a tool call. It can refuse the call, ask you first, or let it run without
the approval it would otherwise need; a call it says nothing about keeps the
default. A hook's refusal holds even when you trust the whole run. To apply a
plugin's hooks, reference the plugin in the Agent's `hooks`:

```yaml validate-as="Agent"
spec:
  hooks:
    - plugin:
        kind: plugin
        slug: safety
```

Stigmer's own engine runs hooks, in the Cloud and on your laptop. The Cursor
engine does not run them yet, and refuses a run of an Agent that has them.

## Keeping an Agent away from a tool

To stop an [Agent](/docs/concepts/agents) from using a tool at all, rather than
asking about it, give the Agent one or both of Claude Code's two lists:

- `tools`: only these tools
- `disallowed_tools`: never these tools

Entries use Claude Code's names: `Read`, `Grep`, `Bash(git push *)`,
`Agent(explore)`, `mcp__<server-slug>` for every tool of one server,
`mcp__<server-slug>__<tool>` for one tool, and `mcp__*` for every MCP tool. The
never-list is applied first. A specifier in parentheses is accepted but governs
the whole tool, as in Claude Code: `tools: [Bash(git status *)]` allows every
shell command, not only `git status`, and `disallowed_tools: [Bash(git push *)]`
removes the shell entirely.

```yaml validate-as="Agent"
spec:
  mcp_server_usages:
    - mcp_server_ref:
        kind: mcp_server
        slug: order-management-api
  tools: [Read, Grep, mcp__order-management-api]
  disallowed_tools: [mcp__order-management-api__cancel_order]
```

This Agent can read files and use the order server's tools, but cannot run shell
commands, write files, or cancel an order. The lists hold on both
[harnesses](/docs/concepts/harnesses), and even when someone chooses to trust
the whole run. A sub-agent can narrow its parent's tools with its own lists but
never widen them. On the Cursor harness a sub-agent cannot carry lists of its
own: Cursor does not say which sub-agent made a call, so a turn whose sub-agent
has lists is refused there, with the sub-agent named, and so is a turn whose
Agent limits `Agent` to types, since Cursor cannot hold back its own built-in
sub-agents. Run such an Agent on the native harness. With `Read` left out, the
Agent still reads its own Skills, inputs and plan. The platform's channel,
conversation and memory tools, and `think`, are outside the lists.

## Approving everything

`auto_approve_all` on an execution skips every approval, which suits automated
processes where a human has already authorized the operation. At an approval,
**Approve all** for one kind of tool (every shell command, or every tool of one
server) stops asking about that kind for the rest of the run. Neither widens the
Agent's tool lists.

Embedding products can also set the _default_ for their interactive Sessions:
`StigmerProvider`'s `approvalDefaults` prop pre-arms the session-scoped
automatic approval preference app-wide — an appropriate product decision when
the host has already judged its whole surface trusted (for example, a desktop
app operating on the user's own files). The user keeps the last word through the
always-visible `Auto-approving tool calls` notice and its `Turn off` control,
and guest Sessions never inherit the host default.

## The approval lifecycle

When a tool call triggers an approval:

1. The Agent runtime detects that the tool requires approval
2. It sets the tool call status to `WAITING_APPROVAL` and pauses
3. Stigmer computes a `PendingApproval` projection with the tool name, message,
   and argument preview
4. The UI or API surfaces the approval request
5. The human submits a decision: **Approve**, **Skip**, or **Reject**
6. The Agent resumes based on the decision

| Decision    | What happens                                                            |
| ----------- | ----------------------------------------------------------------------- |
| **Approve** | The tool call executes with the original arguments                      |
| **Skip**    | The tool call is skipped — the Agent continues without this action      |
| **Reject**  | The tool call is rejected — the Agent receives the rejection and adapts |

The execution is durable throughout this process. If the server restarts while
waiting for approval, the Agent resumes from the same waiting state.

## Designing for approvals

A few principles:

- **Mark destructive tools on the server.** If you write an MCP server, set
  `destructiveHint: true` on every tool that deletes, refunds or changes an
  account, so every Agent that uses it asks first.
- **Leave out what an Agent should never do.** A support Agent that only looks
  things up needs `tools: [Read, Grep, mcp__<server-slug>]`, not an approval on
  every write.
- **Approval is for the person at the conversation.** On a channel or a guest
  share there is no approver, so a tool that asks is skipped there. Keep the
  tools such an Agent needs free of `destructiveHint`, and confirm intent in the
  conversation instead.

The goal is to make the approval decision quick. The human should see the
request and immediately understand what's happening and whether to allow it.
