[Tools](/docs/concepts/tools) give agents the ability to act. Approval flows
give _you_ control over which actions happen automatically and which ones pause
for a human decision.

This is not a logging feature. When an Agent encounters an action that requires
approval, it stops, presents what it wants to do and why, and waits for a human
to approve, skip, or reject before proceeding. The Agent's execution is durable
— it waits indefinitely without losing state.

## Configuring approvals

Approval requirements are configured at three levels. Each level can add or
override the one above it.

### 1. MCP Server defaults

The [MCP Server](/docs/concepts/tools) resource carries approval policies at two
levels. System-generated policies live in `status.tool_approvals` — Stigmer
classifies each tool automatically when you click Connect. Manual overrides live
in `spec.pinned_tool_approvals` — these persist across reconnects and take
precedence over the automatic classifications:

```yaml validate-as="McpServer"
# Auto-classified (status.tool_approvals) — regenerated on each Connect
status:
  tool_approvals:
    - tool_name: process_return
      message: "Process return for order '{{args.order_id}}'"

# Manual overrides (spec.pinned_tool_approvals) — set by the server owner
spec:
  pinned_tool_approvals:
    - tool_name: delete_agent
      message: "Permanently delete agent '{{args.slug}}'"
```

Each `ToolApprovalPolicy` has:

| Field       | Purpose                                                                 |
| ----------- | ----------------------------------------------------------------------- |
| `tool_name` | The exact tool name that requires approval                              |
| `message`   | A human-readable message with `{{args.field}}` placeholders for context |

The `message` template resolves at runtime using the actual tool call arguments,
so the human sees "Process return for order 'ORD-4821'" instead of a generic
prompt.

### 2. Agent overrides

[Agents](/docs/concepts/agents) can override the default policy for each MCP
Server they reference:

```yaml validate-as="Agent"
# In the Agent definition
spec:
  mcp_server_usages:
    - mcp_server_ref:
        kind: mcp_server
        slug: order-management-api
      tool_approval_overrides:
        - tool_name: process_return
          requires_approval: true
          message: "Return requested for order '{{args.order_id}}'"
        - tool_name: get_order
          requires_approval: false
```

A `ToolApprovalOverride` can:

- **Enable** approval for a tool that doesn't require it by default
- **Disable** approval for a tool that does
- **Change** the approval message

An override applies only to the MCP Server referenced by its parent usage — a
same-named tool on another server is unaffected. To override the same tool name
on two servers, add an override under each server's usage.

This lets the same MCP Server behave differently across Agents. A read-only
Agent might disable approvals for query tools, while a full-access Agent keeps
them enabled.

### 3. Session and runtime overrides

[Sessions](/docs/concepts/sessions) can further override approval settings for a
specific conversation. At the execution level, `auto_approve_all` is a bypass
flag that skips all approvals — useful for automated processes where a human has
already authorized the operation.

## The approval lifecycle

When a tool call triggers an approval:

1. The Agent runtime detects that the tool requires approval
2. It sets the tool call status to `WAITING_APPROVAL` and pauses
3. Stigmer computes a `PendingApproval` projection with the tool name, message,
   and argument preview
4. The UI or API surfaces the approval request
5. The human submits a decision: **Approve**, **Skip**, or **Reject**
6. The Agent resumes based on the decision

| Decision    | What happens                                                            |
| ----------- | ----------------------------------------------------------------------- |
| **Approve** | The tool call executes with the original arguments                      |
| **Skip**    | The tool call is skipped — the Agent continues without this action      |
| **Reject**  | The tool call is rejected — the Agent receives the rejection and adapts |

The execution is durable throughout this process. If the server restarts while
waiting for approval, the Agent resumes from the same waiting state.

## Designing approval policies

A few principles for deciding what needs approval:

- **Destructive actions** should always require approval — deletes, refunds,
  account changes
- **Read-only actions** don't need approval — queries, searches, status checks
- **High-value actions** benefit from approval even if they're not destructive —
  sending emails to customers, creating orders
- **Be specific in messages** — "Process return for order 'ORD-4821'" helps the
  human decide faster than an uninformative message that only names the tool
  `process_return` without further context.

The goal is to make the approval decision quick. The human should see the
message and immediately understand what's happening, why, and whether to allow
it.
