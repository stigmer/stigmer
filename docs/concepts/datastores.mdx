---
title: Datastores
description:
  A Datastore gives your Agents durable, structured business records — typed
  collections with constraints and role-based access, declared in YAML and
  enforced by the platform, not the prompt.
---

[Skills](/docs/concepts/skills) give an Agent knowledge and
[Tools](/docs/concepts/tools) let it act on external systems. A Datastore gives
it something neither provides: a safe place to keep _your business records_ —
appointments, orders, sign-ups — that survives across conversations and is
protected by rules the Agent cannot talk its way around.

Without a Datastore, an Agent that needs to remember a booking has to write to
some external database you set up, secure, and wire in yourself. With a
Datastore, you declare the shape of your records in YAML, apply it, and the
Agent gets built-in record tools that are safe by construction.

## What a Datastore looks like

A Datastore declares one or more **collections**. Each collection has typed
**fields**, optional **constraints**, and **grants** that say which roles may do
what:

```yaml
apiVersion: agentic.stigmer.ai/v1
kind: Datastore
metadata:
  name: clinic-records
spec:
  description: Clinic appointment records.
  timezone: Asia/Kolkata
  authorization:
    roles:
      - name: admin
      - name: patient
    bindings:
      - subject:
          channel_sender:
            sender_kind: whatsapp
            value: "+15550100" # the doctor's number
        role: admin
    default_role: patient
  collections:
    - name: bookings
      fields:
        - name: slot_date
          type: date
          required: true
        - name: slot_time
          type: time
          required: true
        - name: patient_phone
          type: string
          required: true
        - name: status
          type: string
          enum_values: [confirmed, cancelled]
      uniques:
        - name: one_confirmed_per_slot
          fields: [slot_date, slot_time]
          where: { field: status, equals: confirmed }
          message: that slot is already booked
      grants:
        - role: admin
          verbs: [read, insert, update, delete]
        - role: patient
          verbs: [read, insert]
          scope: own
```

Three things in this file do the heavy lifting:

- **Typed fields.** `slot_date` is a date, `slot_time` is a time, `status` only
  accepts `confirmed` or `cancelled`. The store rejects anything else — the
  Agent cannot write malformed records.
- **Constraints.** `one_confirmed_per_slot` makes double-booking impossible. The
  rule lives in the store, not the prompt, so no amount of persuasion can break
  it. The `message` is what the Agent relays when the rule fires — you write it
  once and every surface shows the same words.
- **Grants.** The doctor's verified WhatsApp number gets the `admin` role.
  Everyone else gets `patient`, which can only read and insert records they
  created (`scope: own`). A patient asking the Agent to change the schedule gets
  a clean permission error, not a prompt-rule failure.

## Browsing records in the console

Every Datastore appears in the Library beside your Agents, Workflows, Skills,
and MCP Servers. The **Overview** tab shows the declared schema, the
authorization summary, and a sync report confirming your last apply landed. The
**Records** tab is a full browser: filter with schema-aware conditions, page
through results, insert or edit records through a typed form, and read the same
constraint messages your users see.

## How Agents use it

Attach a Datastore to an Agent with `datastore_usages` in the Agent spec:

```yaml
apiVersion: agentic.stigmer.ai/v1
kind: Agent
metadata:
  name: clinic-assistant
spec:
  instructions: You help patients book appointments.
  datastore_usages:
    - datastore_ref:
        slug: clinic-records
```

The Agent automatically gets five record tools — find, insert, update, delete,
and describe — with no extra configuration and no approval prompts. The tools
are safe to run unattended because every call is authorized server-side: the
platform resolves who is really talking (the channel-verified sender identity),
maps them to a role through your bindings, and applies your grants. The Agent
never holds a database credential and never decides who may write what.

## What the record layer enforces

| Rule                   | Where it lives                                                            |
| ---------------------- | ------------------------------------------------------------------------- |
| Field types & required | The store validates every write against the declared schema               |
| Unique constraints     | Substrate indexes — violations return your declared message               |
| Check constraints      | CEL expressions evaluated on every insert and update                      |
| Who can do what        | Role grants resolved from the caller's verified identity, deny-by-default |
| Attribution            | Every record carries `created_by` — who wrote it, stamped by the server   |

Records also carry system fields (`id`, `created_at`, `updated_at`,
`created_by`) that no caller can write, and every record lives in a named
**partition** (`default` unless you choose otherwise) so one datastore can serve
separate data spaces.

## Deleting a Datastore

Deleting a Datastore destroys its records, so it is the most guarded action in
the platform:

1. A Datastore referenced by any Agent's `datastore_usages` cannot be deleted at
   all — detach the Agents first.
2. A Datastore holding records requires you to type its name to confirm, after
   the console shows exactly how many records would be destroyed.

Record tools never delete collections or datastores — structure only changes
through YAML apply, and data only leaves through an explicit, acknowledged
delete.
