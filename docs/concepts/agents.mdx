An Agent is the core resource in Stigmer. It defines _what_ an Agent does — its
role, its instructions, the domain knowledge it can access, and the tools it can
use. Think of it as a job description: it describes the Agent's capabilities and
responsibilities, but it's not a running process.

When someone wants the Agent to handle a request, they start a conversation on
it. Each conversation remembers the version of the Agent it started on, so you
can update an Agent's definition without changing conversations already under
way.

## Anatomy of an Agent

An Agent is defined in YAML with a standard resource structure:

```yaml
apiVersion: agentic.stigmer.ai/v1
kind: Agent
metadata:
  name: support-agent
  visibility: visibility_org
spec:
  description: Handles customer support requests.
  instructions: |
    You are a customer support agent for Acme Corp.

    Use the company knowledge base to answer product questions.
    When customers ask about orders, look up the order details
    using the available tools before responding.

    For returns and refunds, always ask for human approval
    before processing.
  skill_refs:
    - kind: skill
      slug: company-knowledge-base
    - kind: skill
      slug: return-policy
  mcp_server_usages:
    - mcp_server_ref:
        kind: mcp_server
        slug: order-management-api
  tools: [Read, Grep, mcp__order-management-api]
  env:
    ORDER_API_URL:
      is_secret: false
      description: Base URL of the order management API
    ORDER_API_KEY:
      is_secret: true
      description: API key for the order management service
```

its own — each section of the detail page is one of the YAML fields above,
rendered for reading:

Check the frame against the YAML: the description at the top is
`spec.description`, the instructions section carries the system prompt verbatim,
the MCP servers section lists `order-management-api`, the tool list shows
`tools`, and the two `skill_refs` appear under Skills. Each of those fields
serves a purpose:

| Field               | What it does                                                                           |
| ------------------- | -------------------------------------------------------------------------------------- |
| `instructions`      | The Agent's system prompt — defines its personality, behavior rules, and task guidance |
| `skill_refs`        | References to [Skills](/docs/concepts/skills) that give the Agent domain knowledge     |
| `mcp_server_usages` | References to [MCP Servers](/docs/concepts/tools) that give the Agent tool access      |
| `tools`             | Only these tools, in Claude Code's names — here no shell commands and no file writes   |
| `env`               | Environment variables the Agent needs at runtime (API keys, URLs, configuration)       |

Two more fields shape what the Agent's tools may do. `disallowed_tools` lists
tools the Agent may never use, and `hooks` names the plugins whose hooks run
around its tool calls, or carries hooks written in the Agent: commands that can
refuse a call, ask a person first, or let it run.
[Approval Flows](/docs/concepts/approval-flows) explains both.

## Blueprint vs. runtime

An Agent definition is a **blueprint**. It contains zero secrets, zero
Environment-specific values, and zero runtime state. This separation is a hard
architectural invariant — it means the same Agent definition works identically
in development, staging, and production.

The runtime resources that bring an Agent to life form a chain:

| Resource      | What it represents                                                     | Analogy                                    |
| ------------- | ---------------------------------------------------------------------- | ------------------------------------------ |
| **Agent**     | The definition — instructions, Skills, tools                           | A recipe                                   |
| **Session**   | A conversation on one Agent, at the version it started on, with memory | An order cooked from the recipe as written |
| **Agent Run** | One request-response cycle within a Session                            | Preparing one dish for that order          |

A Session names its Agent directly. There is no deployed copy in between: the
person who starts the conversation picks the Agent, and every message in it runs
that Agent.

### Where the secrets come from

The Agent's `env` map declares the keys it needs, never their values. Values
reach a run when it starts: from the [Environments](/docs/concepts/environments)
bound to whatever started it (a Schedule, a PlatformClient), from values the
request passes for that one run, and, for keys still missing, from the personal
Environment of the person sending the message, when the Agent belongs to the
Organization the run is in (an Agent another Organization published reads no
one's personal Environment, and an MCP Server's OAuth variable comes only from
the sign-in to that server). The same Agent runs with test credentials from one
Schedule and production credentials from another, and its definition never
changes.

### Sessions and Agent Runs

A [Session](/docs/concepts/sessions) represents a conversation. It holds message
history and can add Skills and MCP Servers for a specific interaction; the
Agent's tool lists still govern every tool.

An Agent Run is a single request-response cycle within a Session. When a user
sends a message, Stigmer creates an Agent Run that:

1. Loads the Agent's instructions, Skills, and tool configuration
2. Sends the message to the LLM along with conversation history
3. Executes any tool calls the LLM requests
4. Pauses for [approval](/docs/concepts/approval-flows) when required
5. Returns the response

Agent Runs are **durable** — if the process crashes mid-run, Stigmer recovers
and resumes from where it left off.

## Versions

Every change to an Agent's definition is kept. The definition is what the Agent
runs with: its instructions, Skills, tools, Sub-Agents, variables and
[run settings](#run-settings). When you apply an Agent whose definition differs
from every version it has had, Stigmer records a new version under a fingerprint
of its content. Applying it unchanged records nothing, applying an earlier
definition again points the Agent back at that version, and renaming it or
changing its labels or visibility records no version.

You can list an Agent's versions, open any of them, and give one a tag such as
`stable`:

```bash
stigmer get agent code-reviewer --version-history
stigmer get agent code-reviewer --version stable
stigmer tag agent acme-corp/code-reviewer <version-hash> stable
```

Every Agent Run records the Agent version it ran, and runs that version to the
end. If someone changes the Agent while your message is queued or running, your
Agent Run keeps the instructions it started with, and anyone who can view the
Agent can later open that version, for as long as the Agent exists, to see
exactly what it was told. An Agent last saved before versions existed has none
until it is next saved; until then its Agent Runs record only the Agent and run
it as it is.

A [Session](/docs/concepts/sessions#which-version-a-session-runs) runs the
version it started on, so an author's later saves never change a conversation
under the people in it; they reach an open conversation when someone updates it
to the current version. Schedules, channels, and shares start each conversation
on the version their reference names, or on the current version when it names
none.

## Run settings

An Agent can carry the settings its conversations run with: the model, whether
the model thinks before it answers, its speed tier, and limits on what one
message may spend. They live in `run_config`, next to `harness`, the
[Harness](/docs/concepts/harnesses) they were chosen for:

```yaml
apiVersion: agentic.stigmer.ai/v1
kind: Agent
metadata:
  name: pr-reviewer
  visibility: visibility_org
spec:
  description: Reviews pull requests for correctness and risk.
  instructions: |
    You review pull requests. Read the diff and the files it touches, then
    report bugs, risky changes and missing tests, most severe first.
  tools: [Read, Grep, Glob]
  harness: HARNESS_NATIVE
  run_config:
    model_name: claude-sonnet-4.5
    thinking_mode: THINKING_MODE_ENABLED
    max_cost_usd: 2
```

Every message to this Agent runs on Claude Sonnet 4.5 with thinking on, and
stops once its estimated cost reaches $2, keeping the work done so far. The next
message starts a fresh count.

| Field                   | What it sets                                                                                                                                                                              |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `model_name`            | The model, by its name in the model catalog. It must be one the named Harness lists.                                                                                                      |
| `thinking_mode`         | `THINKING_MODE_ENABLED` turns on the model's extended reasoning, so the Agent reasons before it acts. Off unless set, except on a model that always thinks. Needs a model that can think. |
| `service_tier`          | `SERVICE_TIER_FAST` runs at the model's fast tier and bills at its fast rates. Needs a model that offers one.                                                                             |
| `max_cost_usd`          | Stops a message once its estimated cost reaches this many dollars.                                                                                                                        |
| `max_tool_rounds`       | Stops a message after this many rounds of tool calls (native Harness only).                                                                                                               |
| `max_tool_result_chars` | Cuts a single tool result longer than this; 30,000 characters when no one sets it.                                                                                                        |

### Where each setting comes from

A message's settings are worked out once, when it is sent, from three layers,
most specific first:

1. **The message**, or the surface it came through: the saved `run_config` of a
   Schedule, a channel or a share.
2. **The Agent**: its `run_config`.
3. **The operator**: the defaults the operator set for that kind of run.

Two rules combine them:

- **Choices come from the most specific layer that makes one.** That covers the
  model, the tier and thinking. A channel that names a model replaces the
  Agent's; a channel that names none runs the Agent's. A tier or thinking
  setting belongs to its model: it comes from the layer that chose the model or
  a more specific one, never from a layer whose model was replaced. When no
  layer names a model, the Harness picks: native uses its default model, Cursor
  uses Auto.
- **Limits are the tightest any layer sets.** That covers cost, tool rounds and
  result size. A message or a channel can lower this Agent's $2 cap to $0.50,
  but cannot raise it to $5.

The settings a message ran with are recorded on its Agent Run
(`status.run_config`), so its history and its bill read the same answer.

### In the console

The model picker in a conversation opens on **Agent default** and the model the
Agent names. A person can switch any one message to another model, or turn
thinking off for it, without changing the Agent.

### Harnesses and versions

- Run settings are versioned with the Agent. A conversation runs the version it
  started on, so it keeps that version's model after the author picks another.
- A new conversation on the Agent starts on the Agent's `harness`, unless the
  person or the surface starting it names another. A message or a surface that
  names a model but no Harness starts on native, the Harness that model was
  checked against. On the other Harness the Agent's model, tier and thinking are
  left out, since each Harness lists its own models, and only its limits apply.
- Stigmer checks the settings when the Agent is saved: a model needs a
  `harness`, the model must be one that Harness lists, and a fast tier or
  thinking needs a model that supports it there.
- Saved settings stand on their own. An Agent, Schedule, channel or share that
  sets a fast tier or thinking also names the model it is for. Only a message
  may set them alone, to adjust the model it is given.

## The built-in assistant

A Session that names no Agent runs the **built-in assistant**. It is what the
[Quickstart](/docs/getting-started/quickstart) talks to, and what the console
and `stigmer run -m "..."` use when you pick no Agent: a general-purpose
assistant whose instructions are part of Stigmer itself, not a stored Agent.
There is no row to find, no label to configure and nothing to install — a fresh
installation answers its first message at once.

The assistant works with whatever the Session carries: the MCP Servers and
Skills you attach to the conversation are its tools, and the variables those
servers declare are asked for the same way an Agent's are. What it does not have
is anything of its own — no Skills, no MCP Servers, no Sub-Agents. The value of
Stigmer appears when you create Agents tailored to your domain, and a
conversation can pick one up at any point: choosing an Agent binds the Session
to it, and removing the Agent returns the Session to the assistant.

Schedules, channels and shares always name an Agent; they never fall back to the
built-in assistant. The built-in assistant is for a person opening a
conversation.

## Instructions matter

The `instructions` field is the Agent's system prompt. It's the single biggest
factor in how the Agent behaves. Structure it as a brief for a new team member:

- **Be specific about the role.** "You are a customer support Agent for Acme
  Corp" is better than "You are a helpful assistant."
- **Define boundaries.** "For returns and refunds, always ask for human
  approval" tells the Agent what to escalate.
- **Reference available tools by purpose.** "Look up order details using the
  available tools" guides the Agent to apply its tools to each user request.
- **Set the tone.** "Be direct and concise. Act on requests rather than
  explaining steps." shapes conversational style.
