Every API call to Stigmer is made by an **Identity Account**---a principal that
Stigmer can authenticate and authorize. Identity Accounts come in four types,
each suited to a different integration pattern.

## Account types

| Type          | How it's created                                                       | Use case                                                        |
| ------------- | ---------------------------------------------------------------------- | --------------------------------------------------------------- |
| **Direct**    | User signs up on Stigmer or through a Stigmer-hosted login             | Self-managed Organizations using Stigmer's own auth             |
| **Federated** | Created via JIT provisioning or explicit `createFederatedAccount` call | Platform-managed Organizations bringing their own OIDC provider |
| **Platform**  | Created automatically when your backend calls `mintUserToken`          | Embedding Stigmer in your product without OIDC setup            |
| **Machine**   | Created via API with client credentials                                | Service-to-service communication (backend-to-backend)           |

Direct accounts use Stigmer's own authentication tenant. Federated and Platform
accounts both represent your platform's users, but they establish trust
differently---federated accounts authenticate with tokens from an external OIDC
provider, while Platform accounts authenticate with tokens that Stigmer itself
signs. Machine accounts use client credentials and have no interactive login.

## Identity Providers

An Identity Provider represents a **trust relationship** between an external
platform and Stigmer. It is not a user database---it tells Stigmer how to
validate tokens that a platform's users present.

```yaml
apiVersion: iam.stigmer.ai/v1
kind: IdentityProvider
metadata:
  name: Acme Cloud
  slug: acme-cloud
  org: acme
spec:
  display_name: "Acme Cloud"
  jwks_uri: "https://acme.us.auth0.com/.well-known/jwks.json"
  allowed_issuers: ["https://acme.us.auth0.com/"]
  expected_audience: "https://api.stigmer.ai/"
```

When a user presents a JWT issued by `acme.us.auth0.com`, Stigmer fetches the
public keys from `jwks_uri`, verifies the signature, checks the issuer and
audience, and resolves the token's `sub` claim to a federated Identity Account.

Key fields:

| Field               | Purpose                                                                |
| ------------------- | ---------------------------------------------------------------------- |
| `jwks_uri`          | JWKS endpoint where Stigmer fetches public keys for token verification |
| `allowed_issuers`   | JWT `iss` values Stigmer accepts from this provider                    |
| `expected_audience` | JWT `aud` value Stigmer expects                                        |
| `is_sso_provider`   | Marks this IdP as the SSO login provider for its Organization          |

## How federated authentication works

Your backend registers an Identity Provider once. After that, users authenticate
with JWTs from your OIDC provider and Stigmer validates them directly.

Federation supports two provisioning modes:

- **JIT provisioning** --- Stigmer creates accounts and grants roles
  automatically when a user first presents a valid JWT. You only register the
  Identity Provider.
- **Manual provisioning** --- Your backend creates accounts and grants roles via
  the API before users can authenticate. Use this when you need explicit control
  over who gets access.

## How PlatformClient authentication works

PlatformClient uses a different trust model. Instead of validating tokens from
an external OIDC provider, **Stigmer acts as the token issuer**. Your backend
authenticates users with your own auth system, then calls Stigmer's
`mintUserToken` endpoint with the user's identity. Stigmer signs a JWT and
returns it. Your frontend passes this token to the React SDK.

No Identity Provider registration or JWKS endpoint is needed. You create a
PlatformClient in the Stigmer Console, store its credentials in your backend,
and call `mintUserToken` for each user.

Platform accounts are **org-scoped**: the same user ID from any PlatformClient
in your Organization resolves to a single Identity Account. A user who accesses
Stigmer through your dashboard, mobile app, and admin tool shares one identity
and one set of permissions.

For the full setup guide, see
[Embed Stigmer with PlatformClient](/docs/guides/authentication/platform-client/overview).

## Authorization

Having an Identity Account is necessary but not sufficient. The account also
needs **IAM Policies** that grant it access to specific resources. An IAM Policy
binds three things:

- **WHO** --- the Identity Account (principal)
- **WHAT** --- the resource (Organization, Environment, Agent, etc.)
- **HOW** --- the relation (`admin`, `viewer`, `owner`)

```yaml
apiVersion: iam.stigmer.ai/v1
kind: IamPolicy
spec:
  principal:
    kind: identity_account
    id: ida_01abc123
  resource:
    kind: organization
    id: org_acme456
  relation: admin
```

Without a matching IAM Policy, an authenticated user gets `403 Forbidden`.

## What's next

Choose the authentication path that fits your integration:

- **Your users have an OIDC provider** (Auth0, Okta, Entra ID) --- the
  [federation guide](/docs/guides/authentication/federation/overview) walks you
  through registering an Identity Provider, provisioning accounts, and the
  runtime authentication flow.
- **You want to embed Stigmer without OIDC setup** --- the
  [PlatformClient guide](/docs/guides/authentication/platform-client/overview)
  shows how to mint user tokens from your backend.
- **Not sure which to use?** --- the
  [authentication overview](/docs/guides/authentication/overview) compares all
  three authentication paths side by side.
