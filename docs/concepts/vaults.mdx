title: Vaults
description:
  Vaults hold the logins and secrets your runs use. Learn about your own vault
  and shared vaults, how a run finds the keys it needs, and why a saved value is
  never shown again.
---

[Agents](/docs/concepts/agents) and [MCP Servers](/docs/concepts/tools) need
keys at runtime: an OpenAI API key, a sign-in to Linear, a token that lets a
private repository clone. Those keys belong to people and teams, not to the
Agent or MCP Server definition. The same `support-agent` should use Ana's Linear
sign-in when Ana chats with it and Ben's when Ben does.

A **Vault** holds them. It holds two kinds of entry:

- **Secrets**, matched by name: `OPENAI_API_KEY`, `ZENDESK_API_KEY`.
- **Connections** (logins), matched by the address of the tool or Git host they
  are for: `https://mcp.linear.app/mcp`, `github.com`.

Saved values can be replaced but are never shown again, not even to the person
who saved them. Every read shows an entry's name or address, its description,
who saved it and when, never the value.

## Your vault and shared vaults

**My vault** is yours alone. Stigmer creates it the first time you save a key or
sign in to a tool, and a chat you start uses it unless the conversation lists
vaults of its own (below). A teammate's chats never use it, even on the same
Agent, and an Organization's admins cannot see or use it either. When you leave
an Organization, your vault there is deleted with every value in it.

A **shared vault** belongs to the Organization. Its admins create it, for
example "Support tools" holding the team's Zendesk key, and decide who may use
it:

- **Organization** visibility lets every member of the Organization use it.
- On Stigmer Cloud, an admin can also grant **Can use** to a person or a Team.

Using a vault means a run reads its values, so a person's runs use a shared
vault only while that person may use it.

```bash
# Save a key in your own vault (a hidden prompt asks for the value)
stigmer vault set-secret OPENAI_API_KEY --mine

# A shared vault for a team
stigmer vault create "Support tools"
stigmer vault set-secret ZENDESK_API_KEY --vault support-tools
```

A sign-in starts from an address. Signing in to an MCP Server from the console
saves the login as a connection at that server's address in your vault (or a
shared vault you may edit), and it serves every MCP Server reached at that
address, as a login you paste there does. GitHub is one more address: connecting
GitHub signs you in at `github.com` and saves the login there, and the console's
repository picker reads GitHub through the server with it, so the page never
holds the token. Which OAuth app signs you in is found from the address
([OAuth architecture](/docs/guides/integrations/oauth-architecture#a-login-is-found-by-its-address)).

## Declaring what a run needs

[Agents](/docs/concepts/agents) and [MCP Servers](/docs/concepts/tools) declare
the variables they need through the `env` map:

```yaml validate-as="McpServer"
# In the McpServer definition
spec:
  env:
    ZENDESK_SUBDOMAIN:
      description: Your Zendesk subdomain
      value: acme
    ZENDESK_API_KEY:
      is_secret: true
      description: API key for the Zendesk API
```

A declaration describes what the resource needs, never a person's key. A secret
is found by its name in a vault when a run starts. A plain setting that is not a
secret carries its value in the declaration (`value`), and a vault secret with
the same name takes its place. A secret declaration cannot carry a value.

## Which vaults a run uses

Every message in a [Session](/docs/concepts/sessions) is one run. A conversation
uses exactly the vaults it was started with, and nothing else. When a run
starts, Stigmer looks for each key the run needs in these places, in order, and
the first one holding a match wins:

1. **My vault of the person who sent the message**, when the conversation
   includes it (`include_my_vault`). In a conversation shared with teammates,
   each person's message uses their own My vault, never anyone else's.
2. **The vaults the conversation lists**, in order.

The console, the CLI and Stigmer's own MCP tools include My vault in every
conversation they start for a person, and let you leave it out. The API leaves
it out unless the caller sets it, so an integrator calling with an admin's key
never reaches that admin's own keys. An Agent carries no vaults: it is a
blueprint, and a team key reaches a conversation only when someone picks its
vault.

An Agent of another Organization, one shared with yours, reads no My vault at
all: your keys never reach it. A tool of another Organization that your own
Organization's Agent or conversation uses, such as an MCP Server a parent
Organization shares with its child Organizations, still takes keys from your My
vault, but only the keys that tool itself declares.

A run that no person sent uses only the vaults its conversation and the surface
that started it name. The one personal vault such a run can use is a Schedule
owner's own My vault, named on the owner's own Schedule; no other surface can
name a My vault (below):

| Started by                                                                                                   | Uses                                                                             |
| ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| A [Schedule](/docs/sdk/resources/schedule)                                                                   | The vaults on the schedule (the console names its creator's My vault by default) |
| A [public share link](/docs/guides/sharing/share-an-agent)                                                   | The vaults on the share                                                          |
| A [Slack](/docs/guides/channels/connect-slack) or [WhatsApp](/docs/guides/channels/connect-whatsapp) channel | The vaults on the channel                                                        |
| A user signed in through an integrator's app                                                                 | The vaults on the app's PlatformClient                                           |

A visitor on a share link brings no keys of their own: anything a visitor's
request names is dropped, so the share's vaults are what its runs use. Each time
such a run starts, Stigmer checks again that the person who attached each vault
may still use it, so taking away someone's access stops every surface they
attached the vault to.

A My vault can be attached only to its owner's own Schedule, which the owner
sets up for their own work. A conversation, a share, a channel and a
PlatformClient refuse it, because a conversation can have several people and
each person's own vault serves only their own messages: a conversation includes
My vault instead, and each sender then uses their own.

While a Schedule names its owner's My vault, only the owner who created it may
change what it runs, because its runs use that person's credentials. Anyone else
who may edit the Schedule, an Organization admin included, can still switch it
off, rename it, relabel it or delete it, but switching it back on or any other
change to what it runs is refused unless the same update removes that My vault.
The Agent it runs is still its editors' to change: a Schedule that follows the
Agent's latest version fills whatever keys that version declares from the
owner's My vault. Pin the Agent's version on the Schedule when someone else
edits that Agent.

A shared vault a Schedule keeps stays attached in the name of whoever attached
it: an editor's change to the Schedule leaves that record alone, and each fire
checks that this person may still use the vault, so taking away their use stops
the Schedule's fires. A change of the Agent the Schedule runs is the exception:
it checks every vault on the Schedule against the editor making the change, and
records that editor as having attached each one.

### How a key is matched

Each key is matched for the one that declared it, the Agent, a tool or a
repository, and that one alone receives the value. Two tools that declare the
same name each get their own value.

- **A tool's login** (the variable in its `auth.target_env_var`, or in an
  `Authorization: Bearer ${VAR}` header) is filled by a connection at the tool's
  URL, then by a secret with that name. A login saved by signing in and a login
  pasted into a vault serve the same tools: every HTTP tool whose URL is that
  address. A new sign-in at an address replaces whatever login was saved there.
  The `github.com` login also fills the login of a tool on GitHub's own API
  (`api.github.com`, `api.githubcopilot.com`).
- **A local program** (an MCP Server that runs a command) has no address and no
  sign-in: it takes its keys from secrets by name.
- **A tool's other keys** are filled by a secret with their name, then by the
  declaration's own `value`.
- **The Agent's own keys** are filled by a secret with their name, then by the
  declaration's own `value`, never by a login or a repository's token. A key one
  of the run's tools declares is that tool's, so the Agent does not receive it
  even when its own `env` lists it too.
- **A private repository's clone** takes a token only for an `https` repository
  on `github.com`: the repository's own token when the conversation gave one
  ([below](#a-repositorys-own-token)), then the `github.com` login, then a
  `GITHUB_TOKEN` secret. A token given to any other repository is refused.

A tool's address is its full URL with the scheme and host lowercased, a default
port and one trailing slash dropped, and any query or fragment dropped, so
`https://MCP.Linear.app/mcp/` and `https://mcp.linear.app/mcp` are one address,
while two tools on one host under different paths keep separate logins. A Git
host is its bare host name.

### A missing key stops the run before it starts

When a required key is in none of these places, the run is refused before it
starts, naming the key, what needs it, and what the conversation lacks: "linear
needs LINEAR_API_KEY: add LINEAR_API_KEY to My vault" when the conversation
includes My vault; "add LINEAR_API_KEY to one of this conversation's vaults, or
include My vault in this conversation" when it lists vaults but leaves My vault
out; or, for a scheduled run, "linear needs LINEAR_API_KEY: ask the owner of
schedule 'nightly' to attach a vault that holds LINEAR_API_KEY". An optional key
that nobody holds is simply absent.

### When the values are read

A run keeps no copy of its keys. When the run is created, Stigmer records where
each value lives: the run's status lists, for each key and who declared it, the
vault's ID and the entry (a secret's name or a login's address), never a value.
The runner fetches the values from those vaults when the run's work starts, so:

- **A key you rotate reaches the next run**, and a run you recover, without
  anyone sending it again.
- **A key removed after the run was created stops it**, naming the key, who
  needs it and the vault. So does a vault the run may no longer use, a sign-in
  the provider will no longer renew, or a tool whose URL changed since: its
  login was matched for the old address. Fix it, then recover the run, which
  looks at the vaults again.
- **Nothing is left behind** when a run stops, fails or is deleted.

## A repository's own token

A conversation holds no keys of its own, with one exception: a repository entry
may carry a `token` for cloning that repository. It is kept sealed for the
conversation's life, replaceable by an update, never returned by a read, and
destroyed with the conversation. Every other key a conversation needs lives in a
vault: a key you type into the console is saved in My vault, and
`stigmer run --vault` names the vaults a run from a terminal uses.

An integrator that keeps one vault per customer creates a shared vault with an
`external_id`, finds it again with that ID, and names it on each Session.

## Connect links for your customers

A customer of an integrator often needs to sign in to a tool themselves (their
own Slack, their own Linear) without ever having a Stigmer account. A **Connect
link** does that: a one-time page for one shared vault and one address. The
customer opens it, sees "Connect Slack for Acme Helpdesk" with a **Continue**
button, signs in on Slack's own page, and lands back in the integrator's app.
The login is saved into that customer's vault.

A link signs in only through your Organization's own login app for the address
(**Settings → OAuth Apps**, with the address listed), so the vendor's consent
page shows your app's name to your customer. Stigmer's own apps, and the client
Stigmer registers with a tool's login server, are never used for a link: they
would ask your customer to trust Stigmer, not you. For the same reason a login
app whose client ID is one Stigmer signs in with is refused for a link.

From your backend, with a key that may edit the vault, make a link and send the
customer to its `url`:

```bash
stigmer vault connect-link vlt_01hzx9m5k7customervault001 \
  --address https://mcp.slack.com/mcp \
  --return-url https://helpdesk.example.com/settings/integrations
```

The API call is `createConnectLink` on the vault service, with the Organization,
the vault's ID, the address, the return URL and, optionally, how long the link
lives in seconds (30 minutes unless you say, a day at most). When the customer
is done, Stigmer sends them to the return URL with `stigmer_connect=connected`,
or `stigmer_connect=error` and a `reason` (`denied` when they declined,
`provider_error`, `expired`, `failed` or `not_allowed`), so your app can show
what happened.

A Connect link:

- **Works once.** The first sign-in saved through it spends it; a link that is
  used, expired or unknown shows "This link has expired or was already used". A
  sign-in that fails after the vendor's page leaves the link usable until it
  expires.
- **Saves into a shared vault only.** My vault belongs to its person, and a link
  is for someone else.
- **Is checked when you make it.** An address your Organization has no approved
  login app for is refused then, so a customer is never sent to a dead end. The
  return URL must be an `https` address (`http` only for `localhost`,
  `127.0.0.1` or `[::1]`).
- **Acts for you.** The saved login records you as the one who saved it. If you
  lose the right to edit the vault, the customer can still open the link, but
  Continue and the finished sign-in are refused, so nothing is saved.

Only the link's fingerprint is stored, so treat the `url` like a password: send
it to that customer only.

## Where the values reach

Each part of a run receives only the values declared for it:

| Surface                                             | What it receives                                                                                                                                                                                                                                                       |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Shell commands and hooks** (the Agent's own code) | The runner's own process variables, minus runner-internal credentials, plus only the Agent's own keys: secrets by name and plain settings, never a login or a repository's token, and never a key one of its tools declares. An Agent that declares nothing gets none. |
| **MCP stdio servers**                               | Only the keys declared in the MCP server's `env` map, plus a minimal base set (`PATH`, `HOME`, and similar). A server that declares nothing gets only that base set, never the runner's own variables.                                                                 |
| **MCP HTTP servers**                                | Their own keys and login, sent only to the URL whose address the login was matched for. A server whose URL changed since the run was created gets nothing.                                                                                                             |
| **A repository's clone**                            | The token, handed to each git command that talks to GitHub for that command alone. Nothing is written into the clone's `.git` folder or its remote URL, so the shell never finds it there. Cloning a private repository needs git 2.31 or newer on the runner.         |

A shell command that needs a key works only when the Agent declares it, as a
secret by name: an Agent whose shell runs `gh` declares `GITHUB_TOKEN`, and you
save a `GITHUB_TOKEN` secret for it. Your GitHub sign-in fills the clone and
GitHub's tool, never the shell.

<Callout type="warn">
  The keys an Agent declares reach its tools and its shell, and those follow the
  instructions the Agent's author wrote. When you send a message to an Agent a
  teammate wrote, the keys it declares that your vault holds go to that Agent.
  Before your first message in a conversation, the console names the keys the
  Agent declares, so you can decide before anything is sent.
</Callout>
