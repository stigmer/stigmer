Every [Agent](/docs/concepts/agents) needs somewhere to run. An Agent definition
describes _what_ the Agent does — its instructions, Skills, and tools. A Runner
is _where_ it runs. It is the process that picks up work, calls the LLM,
executes tool calls, and reports results back to the server.

Without a runner, an Agent is a blueprint sitting idle. With one, it can handle
requests.

## Runners in the platform

Runners sit at the execution layer of the resource model. When you send a
message to a [Session](/docs/concepts/sessions), Stigmer creates an
[Agent Execution](/docs/concepts/agents#blueprint-vs-runtime) and dispatches it
to a runner. The runner processes the execution — calling the LLM, running
tools, pausing for [approval](/docs/concepts/approval-flows) — and streams the
result back.

Unlike Agents and Skills, you don't write a Runner definition in YAML. Runners
register themselves. You start a runner process, it connects to the server,
heartbeats to stay alive, and picks up executions. The server tracks each runner
as a resource with a thin spec and rich status — similar to how Kubernetes
tracks Nodes.

A single runner can host workers for multiple
[Harnesses](/docs/concepts/harnesses). When you start a runner with
`stigmer up`, it runs the native worker by default. If a Cursor API key is
configured, it also starts a Cursor worker on a dedicated task queue. Both
workers share the same runner identity — you don't need separate runner
processes for each Harness.

## Three execution modes

Runners operate in one of three modes. The mode determines where Agent commands
run and who manages the infrastructure.

|                   | Local                                    | Sandbox                                         | Cloud (auto)                                        |
| ----------------- | ---------------------------------------- | ----------------------------------------------- | --------------------------------------------------- |
| **Who starts it** | You — via `stigmer up`                   | You — via `stigmer up --execution-mode sandbox` | The platform — automatically                        |
| **Where it runs** | Your machine (laptop, server, CI)        | Docker container on your machine                | Stigmer-managed infrastructure                      |
| **Isolation**     | None — full host access                  | Container-level                                 | Platform-managed                                    |
| **Lifecycle**     | Persistent — stays until you stop it     | Persistent — stays until you stop it            | Ephemeral — created per execution, cleaned up after |
| **Good for**      | Development, on-premises, data-sensitive | Untrusted workloads, consistent runtimes        | Zero-setup production, burst capacity               |

**Local** is the default. Start a runner with `stigmer up` and Agent commands
execute directly on the host machine. The Agent has full access to the local
file system.

**Sandbox** adds isolation. Start a runner with
`stigmer up --execution-mode sandbox`. Agent commands run inside a Docker
container, keeping untrusted operations away from the host.

**Cloud (auto)** requires no setup. When a Session needs compute and no runner
is specified, the platform provisions an ephemeral runner on demand. Cloud
runners are labeled `stigmer.ai/system-managed` and cleaned up automatically.

## Runner lifecycle

Every runner moves through a set of phases. These phases appear as status badges
in the web console and reflect what the runner is doing right now.

| Phase       | What it means                                        | What triggers it                              |
| ----------- | ---------------------------------------------------- | --------------------------------------------- |
| **Pending** | Resource exists, runner process hasn't connected yet | Runner created but not yet sending heartbeats |
| **Ready**   | Connected and accepting new executions               | First heartbeat received (or restart)         |
| **Busy**    | Connected but at maximum concurrent capacity         | Runner reports it cannot take more work       |
| **Stopped** | No longer sending heartbeats, resource retained      | Heartbeat timeout, explicit stop, or shutdown |
| **Failed**  | Unrecoverable error                                  | Fatal condition reported by runner or server  |

Two things drive phase transitions:

1. **The runner process** sends a heartbeat every 30 seconds. Each heartbeat
   reports the runner's phase, current execution count, and machine information.
   The first heartbeat moves a runner from Pending to Ready.

2. **The server** monitors heartbeats. If a runner misses its heartbeat window,
   the server marks it Stopped. You can also stop a runner explicitly from the
   web console, the CLI, or the SDK.

A Stopped runner is not gone. If the same runner process restarts and sends
heartbeats again, it transitions back to Ready. The runner's identity persists
across restarts — the CLI stores the runner ID locally and reactivates the same
resource.

## How Sessions find runners

When you start a conversation, Stigmer needs to decide which runner handles the
executions. There are three modes:

**Auto (default)** — You don't pick a runner. Stigmer chooses for you. In cloud
mode, it provisions an ephemeral runner on demand. In local/OSS mode, it routes
to the runner embedded in `stigmer up server`.

**Explicit selection** — You pick a runner from the runner picker in the Session
composer. Only runners in the Ready or Busy phase appear as selectable options.
This is how you direct work to a specific machine — your laptop, a GPU server,
or a build Agent.

**Session binding** — A Session remembers its runner. Once an execution runs on
a runner, subsequent messages in that Session route to the same runner. If the
bound runner is unavailable, the Session falls back to automatic provisioning.

## Runners in the web console

In Settings > Runners, you see every runner in your Organization — local runners
you started, sandboxed runners, and optionally the system-managed ones the
platform created. Each row shows the runner's name, phase badge, machine info,
and an action menu for stop and delete operations.

## What's next

You understand what runners are and how they fit the platform. The next step
depends on what you want to do:

- **Embed the runner in your app** — The
  [embedding guide](/docs/guides/runners/embedding) covers hosting the runner in
  a desktop or web app: local versus cloud execution, the `RunnerAdapter`, and
  the configuration each kind of integrator passes.
- **Drive the manager-mode protocol** — The
  [manager-mode IPC protocol reference](/docs/guides/runners/ipc-protocol)
  specifies the subprocess command and response contract and its versioned
  handshake.
- **Use the Cursor harness** — The
  [Cursor harness guide](/docs/guides/runners/cursor-harness) covers setting up
  the Cursor execution engine for coding-focused capabilities.

The next concept page covers [Harnesses](/docs/concepts/harnesses) — the
execution engines that power your Agent's Sessions. After that,
[Workflows](/docs/concepts/workflows) — multi-step automation sequences that
chain Agent calls, HTTP requests, and approval gates into structured processes.
