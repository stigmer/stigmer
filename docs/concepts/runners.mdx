Every [Agent](/docs/concepts/agents) needs somewhere to run. An Agent definition
describes _what_ the Agent does — its instructions, Skills, and tools. A Runner
is _where_ it runs. It is the process that picks up work, calls the LLM,
executes tool calls, and reports results back to the server.

Without a runner, an Agent is a blueprint sitting idle. With one, it can handle
requests.

## Runners in the platform

Runners sit at the execution layer of the resource model. When you send a
message to a [Session](/docs/concepts/sessions), Stigmer creates an
[Agent Execution](/docs/concepts/agents#blueprint-vs-runtime) and hands it to a
runner. The runner processes the execution — calling the LLM, running tools,
pausing for [approval](/docs/concepts/approval-flows) — and streams the result
back.

| Resource            | What it represents             | Analogy                          |
| ------------------- | ------------------------------ | -------------------------------- |
| **Agent**           | Instructions, Skills, tools    | A recipe                         |
| **Agent Instance**  | Agent bound to Environments    | A kitchen set up for that recipe |
| **Session**         | Conversation with memory       | An ongoing order at that kitchen |
| **Agent Execution** | One request-response cycle     | Preparing one dish               |
| **Runner**          | The process that does the work | The cook                         |

Unlike Agents and Skills, a Runner is not a resource. You don't write one in
YAML, you can't `apply` one, and the server keeps no record of which runners
exist. A runner is a process that connects to the server and to Temporal and
does the work that appears on its queue.

A single runner serves both [Harnesses](/docs/concepts/harnesses). The Harness
is a property of the Session, and it travels with each execution to whichever
runner takes it; there is no separate runner, process, or queue per Harness.

## Where a runner comes from

Every way of running Stigmer starts exactly one runner beside the server, and
the two never meet directly.

- **Your laptop.** `stigmer up` starts the server, a managed Temporal, and a
  runner as its own process. `stigmer up server` starts the server alone,
  without one.
- **The all-in-one container.** The same composition as `stigmer up`, inside one
  container.
- **The Docker Compose stack and the Helm chart.** One runner service beside the
  server, or one runner container in the server's pod. The
  [self-hosting runner page](/docs/guides/self-hosting/runners) explains what it
  is given, what happens when it is gone, and why it is one trust domain.
- **Stigmer Cloud.** The platform provides the runner, in a sandbox it starts
  and cleans up for you. You never see it. The mechanism behind it exists in the
  open source server as a sandbox provisioner that starts a runner per Session;
  the self-hosting runner page says what it does and does not do today.

## How work reaches a runner

The server never picks a runner. It puts each execution on a Temporal task
queue, `stigmer_runner` by default, and whichever runner polls that queue takes
the work. A run carries two things with it: the Session's Harness, and a
credential the server mints for that run alone, so that everything the runner
does for the run is recorded as the person who started it.

A runner that is absent is noticed only when a run has nobody to take it. An
Agent execution waits five minutes for a runner and then fails with a message
that names the runner as the likely cause; a Workflow execution waits until a
runner returns. A runner that stops in the middle of an Agent turn is detected
through the heartbeat it sends Temporal every 30 seconds, and the turn resumes
from the runner's checkpoint once a runner is back.

## What's next

You understand what runners are and how they fit the platform. The next step
depends on what you want to do:

- **Run Stigmer for a team** — the
  [self-hosting runner page](/docs/guides/self-hosting/runners) covers the
  runner on the Docker Compose stack and the Helm chart: its keys and addresses,
  its failure modes, and the per-Session sandbox mechanism.
- **Embed the runner in your app** — The
  [embedding guide](/docs/guides/runners/embedding) covers hosting the runner in
  a desktop or web app: local versus cloud execution, the `RunnerAdapter`, and
  the configuration each kind of integrator passes.
- **Drive the manager-mode protocol** — The
  [manager-mode IPC protocol reference](/docs/guides/runners/ipc-protocol)
  specifies the subprocess command and response contract and its versioned
  handshake.
- **Use the Cursor harness** — The
  [Cursor harness guide](/docs/guides/runners/cursor-harness) covers setting up
  the Cursor execution engine for coding-focused capabilities.

The next concept page covers [Harnesses](/docs/concepts/harnesses) — the
execution engines that power your Agent's Sessions. After that,
[Workflows](/docs/concepts/workflows) — multi-step automation sequences that
chain Agent calls, HTTP requests, and approval gates into structured processes.
