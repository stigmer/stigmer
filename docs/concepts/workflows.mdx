---
title: Workflows
description:
  Workflows are multi-step automation sequences that chain agent calls, LLM
  tasks, HTTP requests, branching logic, and human approvals into durable
  processes defined in YAML.
---

Workflows let you orchestrate multi-step processes that go beyond what a single
Agent can handle in one turn. Where an Agent responds to a message, a Workflow
defines a sequence of **tasks** — LLM calls, HTTP requests, data transforms,
conditional branches, loops, and human approval gates — that execute durably
from start to finish.

Use a Workflow when you need:

- **Deterministic control flow** — branch on structured data, not LLM prose
- **Multiple steps with dependencies** — one task's output feeds the next
- **Human checkpoints** — pause for review or approval mid-process
- **Cost and duration budgets** — enforce limits across all tasks
- **Reliability** — automatic retry and crash recovery

## Anatomy of a Workflow

A Workflow is defined in YAML with the same resource structure as Agents:

```yaml
apiVersion: agentic.stigmer.ai/v1
kind: Workflow
metadata:
  name: content-review-pipeline
spec:
  description: AI-powered content drafting with human review.
  document:
    dsl: "1.0.0"
    namespace: acme
    name: content-review-pipeline
    version: "1.0.0"
  env:
    TOPIC:
      description: "The topic to write about"
  budget:
    max_cost_micros: 2000000
    max_duration_seconds: 600
  tasks:
    - name: draft_content
      kind: llm_call
      task_config:
        model: "claude-sonnet-4-5"
        system_prompt: "You are a professional content writer."
        prompt: "Write content about: ${ $env.TOPIC }"
        temperature: 0.7
        max_tokens: 2000
      export:
        as: "${ . }"
      flow:
        then: review

    - name: review
      kind: human_input
      task_config:
        prompt: "Review the draft:\n${ $context.draft_content.text }"
        outcomes:
          - name: approve
            label: "Approve"
          - name: reject
            label: "Reject"
            then: end
      export:
        as: "${ . }"
```

Each section of the Workflow definition serves a purpose:

| Field      | What it does                                                                                      |
| ---------- | ------------------------------------------------------------------------------------------------- |
| `document` | Workflow metadata — DSL version, namespace, name, and version (semver)                            |
| `env`      | Environment variable declarations the Workflow needs at runtime                                   |
| `budget`   | Cost, token, and duration limits for the entire run                                               |
| `tasks`    | Ordered list of steps — each with a `kind`, `task_config`, optional `export`, and optional `flow` |

## Blueprint vs. runtime

Like Agents, a Workflow definition is a **blueprint**. It contains no secrets,
no environment-specific values, and no runtime state.

You run the Workflow itself. Each run is a **Workflow Run**:

  chart={`

  W["Workflow<br/>(blueprint)"] --> WE["Workflow Run"]
`}
/>

| Resource         | What it represents                                    | Analogy           |
| ---------------- | ----------------------------------------------------- | ----------------- |
| **Workflow**     | The definition — tasks, flow, budgets                 | A recipe          |
| **Workflow Run** | One run of the Workflow, at the version it started on | Cooking one batch |

Start a run from the console, with `stigmer run workflow <name>`, with the MCP
server's `run_workflow` tool, or from an SDK by creating a Workflow Run whose
`spec.workflow_id` names the Workflow. Then
[subscribe](/docs/sdk/streaming#subscribe-to-a-workflow-run) to track progress
task by task.

## Versions

Every change to a Workflow's definition is kept. A version covers the whole
definition: the tasks, each step's Environments, the declared `env`, the budget
and the description. When you save a Workflow whose definition passes validation
and differs from every version it has had, Stigmer records a new version.
Changing who can see its runs records no version.

```bash
stigmer get workflow content-review-pipeline --version-history
```

Every run is pinned to the version the Workflow had when the run started, and
every step reads that version. If someone edits the Workflow while your run is
in progress, the steps still to come run as they were when you started it.

## Where a run gets its values

The `env` map declares the keys a Workflow needs, never their values. When a run
starts, Stigmer fills them in this order:

1. **Values passed with the run.** The `--env` flags, the run form in the
   console, or the request's `runtime_env`.
2. **The Workflow's declarations decide what the run receives.** When the
   Workflow declares any keys, a key it does not declare is dropped.
3. **Your personal Environment, for declared keys still missing.** Every
   declared key nothing passed is read from the
   [personal Environment](/docs/concepts/environments#how-a-run-gets-its-values)
   of the person who started the run, when the Workflow belongs to the
   Organization the run is in. A Workflow of another Organization reads no one's
   personal Environment.

Before you start a run, the console's run form says where each declared key will
come from: what you type, your personal Environment, or nowhere yet.

<Callout type="warn">
  The keys a Workflow declares reach its steps, and those follow what the
  Workflow's author wrote: an `http_call` step can send a value anywhere. When
  you run a Workflow a teammate in your Organization wrote, the keys it declares
  that only your personal Environment holds go to that run. A Workflow from
  another Organization never receives them. The console's run form names each
  key before you start; the CLI, the MCP server and the SDKs fill the same keys
  without asking.
</Callout>

A key the whole team uses, such as a shared webhook URL, cannot yet be bound
once for everyone: each person who runs the Workflow saves it in their own
personal Environment or passes it with the run. An `agent_call` step can still
name Environments of its own in `environment_refs`; they supply the keys its
Agent declares.

## Who can see the runs

Who can see a Workflow and who can see its runs are separate settings. Letting
your Organization see and run a Workflow never shows anyone else's runs. The run
visibility setting does:

| Setting                   | Who sees each run                                           |
| ------------------------- | ----------------------------------------------------------- |
| **Private** (the default) | The person who started it                                   |
| **Organization**          | Every member of the Organization, with its input and output |

The setting covers every run of the Workflow, past runs included. Only the
Workflow's owner can change it, on the Workflow's page in the console or with
the `updateRunVisibility` call on the Workflow. People who can edit the Workflow
cannot change it, and saving or applying the Workflow keeps the stored setting.
When a Workflow's runs are visible to the Organization, the run form says so
before you start a run.

## Tasks

Every step in a Workflow is a **task**. Each task has a `name` (unique within
the workflow), a `kind` (what type of work it does), and a `task_config` (the
kind-specific configuration). An `agent_call` task's name is unique across the
whole Workflow, the tasks inside `for_each`, `fork` and `try_catch` and every
`compensate` list included.

```yaml
- name: classify_ticket
  kind: llm_call
  task_config:
    model: "gpt-4o-mini"
    prompt: "Classify this ticket: ${ $env.TICKET }"
    response_schema:
      type: object
      properties:
        severity: { type: string, enum: [low, medium, high, critical] }
  export:
    as: "${ .structured }"
  flow:
    then: route_by_severity
```

- **`export`** saves the task's output to the workflow context so later tasks
  can reference it with `${ $context.classify_ticket.severity }`.
- **`flow`** controls which task runs next. By default, the next task in the
  list runs. Set `then` to a task name to jump, or `"end"` to terminate.

## Task types at a glance

Stigmer provides 20 task types organized into six categories:

| Category     | Task kinds                                                                            | Purpose                                           |
| ------------ | ------------------------------------------------------------------------------------- | ------------------------------------------------- |
| **AI**       | `llm_call`, `agent_call`, `eval`                                                      | LLM inference, agent invocation, LLM-as-judge     |
| **Control**  | `switch_case`, `for_each`, `fork`, `try_catch`, `wait`, `raise_error`, `run_workflow` | Branching, loops, parallelism, error handling     |
| **Data**     | `set_vars`, `transform`, `validate`                                                   | Variables, JQ transforms, schema validation       |
| **Human**    | `human_input`                                                                         | Approval gates, forms, routing by reviewer choice |
| **External** | `http_call`, `grpc_call`, `activity_call`                                             | HTTP/gRPC requests, Temporal activities           |
| **Events**   | `listen`, `emit_event`, `notification`                                                | Wait for signals, emit CloudEvents, notify humans |

`run_workflow` is not supported yet: a Workflow that contains it is refused when
it is saved, and the error names the task.

For details on each task type, see the
[Task Type Overview](/docs/guides/workflows/task-types). For exhaustive
field-level reference, see the
[Task Type Reference](/docs/guides/workflows/task-types/set-vars).

## How execution works

Tasks execute **sequentially** by default — the first task in the `tasks` list
runs, then the second, then the third. Use `flow.then` to override this with
explicit jumps:

{/* prettier-ignore */}
<Mermaid
  chart={`
graph LR
  A["classify"] -->|"severity == critical"| B["escalation_approval"]
  A -->|"severity == high"| C["senior_queue"]
  A -->|"default"| D["standard_queue"]
  B --> E["escalation_summary"]
`}
/>

Data flows between tasks through **expressions**. When a task exports its output
with `export.as`, later tasks access it via `${ $context.<taskName>.<field> }`.
Environment variables are available as `${ $env.<VAR_NAME> }`.

Execution is **durable**. Stigmer runs workflows on
[Temporal](https://temporal.io/), so if the process crashes mid-task, it
recovers and resumes from the last checkpoint automatically.

## Budgets

Workflows can enforce cost, token, and duration limits:

```yaml validate-as="Workflow.spec"
budget:
  max_cost_micros: 2000000
  max_total_tokens: 200000
  max_duration_seconds: 600
  on_exceeded: budget_exceeded_human_review
```

The `on_exceeded` policy controls what happens when a limit is hit:

| Policy                         | Behavior                                                |
| ------------------------------ | ------------------------------------------------------- |
| `budget_exceeded_terminate`    | Stop the workflow immediately with a failed status      |
| `budget_exceeded_human_review` | Pause and create an approval gate for a human to decide |
| `budget_exceeded_warn`         | Log a warning but continue executing                    |

## Human-in-the-loop

The `human_input` task type pauses the workflow and waits for a human reviewer
to make a decision. Reviewers see a prompt, an optional form, and a set of
**outcomes** — each outcome can route the workflow to a different task:

```yaml
- name: review
  kind: human_input
  task_config:
    prompt: "Approve this content?"
    outcomes:
      - name: approve
        label: "Approve"
      - name: revise
        label: "Request Revisions"
        then: revise_content
      - name: reject
        label: "Reject"
        then: end
    timeout: 86400
    on_timeout: HUMAN_INPUT_TIMEOUT_FAIL
```

This is different from Agent [approval flows](/docs/concepts/approval-flows),
which gate individual tool calls. Workflow `human_input` tasks are
**workflow-level checkpoints** that can include forms, multiple outcomes, and
explicit routing.
