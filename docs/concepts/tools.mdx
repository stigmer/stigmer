[Skills](/docs/concepts/skills) give an Agent domain knowledge. Tools give it
the ability to _act_: the calls it makes into your product's systems, the way
your own backend calls an internal API. An Agent with tool access can read a
customer's ledger, list their accounts, post an adjustment to their books — any
operation your systems support.

Stigmer uses the
[Model Context Protocol (MCP)](https://modelcontextprotocol.io/) to connect
Agents to external tools. MCP is an open standard that defines how AI models
discover and call tools. This means any MCP-compatible tool server works with
Stigmer — you're not locked into a proprietary integration format.

## How tool calls work

When an Agent has tool access and receives a request that requires action, it:

1. Decides which tool to call based on the request and the tool's description
2. Constructs the tool call arguments
3. Stigmer validates the arguments and executes the call in a sandbox
4. The tool returns a result
5. The Agent uses the result to form its response

Say an accounting product's customer asks for this quarter's variance report,
and the Agent calls the `get_ledger` tool to read their ledger. The tool call
appears in the Session with its name and result. The Agent then works from the
customer's real numbers instead of guessing.

## Built-in web fetch

Not every capability needs an MCP server. Every Agent can fetch a public URL out
of the box — the native harness ships a built-in `web_fetch` tool, and the
[Cursor harness](/docs/concepts/harnesses) has its own `WebFetch`. Fetched HTML
is converted to Markdown, large pages are paginated, and the tool is read-only
and asks for no approval unless the Agent's hooks ask about it, so it works in
unattended contexts like shared and embedded Agents. On managed cloud runners,
fetches to private and internal addresses are refused.

Reach for an MCP server when you need more than retrieval of a public page —
authenticated APIs, site-specific extraction, or write operations.

## Where an MCP server comes from

An MCP server reaches an Agent two ways: in a plugin the Agent lists, or written
in the Agent itself under `mcp_servers`. There is no MCP server to create on its
own.

- **In a plugin.** A [plugin](/docs/concepts/plugins)'s MCP configuration (its
  `.mcp.json` or `mcp.json`) names each server and how to reach it, beside the
  plugin's Skills, agents and hooks. A plugin is how a server is packaged and
  shared: every Agent and every chat that lists the plugin gets it, and only a
  plugin can run a local program. Install one from Stigmer's catalogue or one
  you add, or add one server by its address with `stigmer mcp add <name> <url>`
  or **Add MCP server** on the console's **Library → Plugins** page, which
  builds a plugin holding that one server, the way `claude mcp add` adds a
  server to Claude Code.
- **In the Agent itself.** An Agent's `mcp_servers` lists servers of its own,
  each a name, an address and optional headers, as an agent in Claude Managed
  Agents or a Claude Code subagent lists its own. It is for a server one Agent
  needs, or for Agents you create from code in one call. These servers are
  reached over HTTP only, and only the Organization's admins add one or change
  its address or headers; anyone who may edit the Agent may keep or remove them.
  [Give an agent its own MCP server](/docs/guides/integrations/connect-an-mcp-server#give-an-agent-its-own-mcp-server)
  walks through it.

A server another Organization owns is yours to use only through a plugin you
install, or when that Organization is a platform sharing the plugin with the
Organizations it manages.

Here is a plugin's MCP configuration with one server of each kind:

```json
{
  "mcpServers": {
    "ledger": {
      "type": "http",
      "url": "https://ledger.acme.example/mcp",
      "headers": { "Authorization": "Bearer ${LEDGER_API_KEY}" }
    },
    "files": {
      "command": "npx",
      "args": [
        "-y",
        "@modelcontextprotocol/server-filesystem",
        "${PROJECT_DIR}"
      ]
    }
  }
}
```

An Agent's own server is written in its spec:

```yaml validate-as="Agent"
spec:
  mcp_servers:
    - name: ledger
      url: https://ledger.acme.example/mcp
      headers:
        Authorization: Bearer ${LEDGER_API_KEY}
  tools:
    - mcp__ledger
```

### Transport options

| Mode      | When to use                                                                      | Configuration                                                            |
| --------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| **stdio** | The tool must run on your own machine: **conversations on your own runner only** | `command` and `args`: the runner launches it and talks over stdin/stdout |
| **HTTP**  | The tool server is a remote service: works in every conversation, local or cloud | `url` and optional `headers`, with `${VAR}` substitution                 |

An Agent's own server is HTTP only; a local program comes in a plugin.

A local program (stdio) runs where the person's own runner runs: the desktop app
or the CLI. A conversation hosted in a cloud sandbox, whose runner runs in cloud
mode, is refused when it is created if one of its plugins carries a local
program, with an error naming the server.

### Variables

The plugin declares what its servers read at run time in its manifest: API keys,
service URLs, settings. A `${NAME}` in a server's arguments or headers names a
variable, and one the plugin does not declare is taken as a required secret; the
plugin's page lists every variable its servers and hooks read. A secret is found
by its name in a [vault](/docs/concepts/vaults) when a run starts; a plain
setting may carry its value in the plugin's declaration. A required variable no
vault holds refuses the run before it starts, naming the key and who must add
it.

An Agent's own server follows the same rule from the Agent: a `${NAME}` in one
of its headers is a required secret unless the Agent's `env` declares it. Its
value is sent to that server only, never to the Agent's shell. Header values are
stored in the Agent and shown to everyone who can read it, so a secret goes in a
vault and the header names it.

The platform fills four optional variables itself, so a server can know who is
calling without a vault: `STIGMER_CALLER_IDENTITY_KIND`,
`STIGMER_CALLER_IDENTITY_VALUE`, `STIGMER_SESSION_ID` and
`STIGMER_SERVER_ADDRESS`. A server reads them in its headers
([Caller identity for MCP servers](/docs/guides/integrations/caller-identity-for-mcp-servers)).

The plugin stays portable: the same plugin works for every person and team that
uses it, and only the vault values change.

## Using a server's tools

[Agents](/docs/concepts/agents) list the plugins they use in `plugins`. A plugin
is attached whole: its Skills, its agents (as subagents), its hooks and its MCP
servers. The servers in the Agent's own `mcp_servers` join them.

```yaml validate-as="Agent"
spec:
  plugins:
    - kind: plugin
      slug: ledger
  tools:
    - mcp__plugin_ledger_ledger__get_ledger
    - mcp__plugin_ledger_ledger__list_accounts
```

The Agent gets every tool its servers offer. To narrow that, it carries Claude
Code's two lists:

| Field              | Purpose                                                 |
| ------------------ | ------------------------------------------------------- |
| `tools`            | Only these tools (empty means every tool the Agent has) |
| `disallowed_tools` | Never these tools, applied first                        |

Entries use Claude Code's names: built-ins such as `Read`, `Grep` or
`Bash(git push *)`; `mcp__plugin_<plugin>_<server>` for every tool of one
plugin's server; `mcp__plugin_<plugin>_<server>__<tool>` for one tool;
`mcp__<server>` and `mcp__<server>__<tool>` for a server in the Agent's own
`mcp_servers`; and `mcp__*` for every MCP tool. Every character outside letters,
digits, `_` and `-` in a plugin's or its server's name is written as `_`. A
specifier such as `(git push *)` is accepted but governs the whole tool: it
never narrows `Bash` to some commands.

You install the plugin once and list it on as many Agents as you like. Each
Agent can keep a different subset: the read-only Agent above only gets
`get_ledger` and `list_accounts`, while a full-access Agent also gets
`post_adjustment`. [Approval Flows](/docs/concepts/approval-flows) covers what
the lists guarantee, and how hooks decide a call the lists allow.

## Seeing a server's tools

Stigmer stores nothing about a server's tools. To see them, ask the live server:
`stigmer connect plugin <plugin>` (add `--server <name>` when the plugin carries
several), or **Check tools** on the plugin's page in the console. Either reaches
the server as you, with the keys and sign-ins in your own vault, and marks the
tools the server calls destructive.

A server in an Agent's own `mcp_servers` cannot be listed this way yet
([#2325](https://github.com/stigmer/stigmer/issues/2325)). Name the whole server
as `mcp__<server>` in `tools`, or take its tool names from the server's own
documentation.

A tool asks for human approval before it runs when its server marks it
destructive, with the MCP annotation `destructiveHint: true`, and every other
tool runs without asking. The server's author makes that call, not Stigmer:
`post_adjustment` asks if the `ledger` server annotates it, and `get_ledger`
does not. The annotation is read again at the start of every turn, and a server
whose tools cannot be listed then asks before every one of its tools. Hooks can
change that call by call: a hook can refuse a tool, ask about it, or let it run
([Guard an agent's tools with hooks](/docs/guides/plugins/use-hooks)).

## Authentication for tools

Some tools need credentials to access the systems behind them. Stigmer supports
three authentication patterns, each suited to a different type of integration:

| Pattern                    | When it applies                                                     | How it works                                                                                           |
| -------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| **Environment variables**  | The tool uses API keys or tokens                                    | The plugin names the variable in a header or argument, and the value is saved in a vault               |
| **Automatic OAuth**        | The server implements the MCP Authorization spec                    | Stigmer reads the server's login server from its URL, becomes its client once, and handles the sign-in |
| **OAuth with a login app** | The vendor requires an OAuth app registered with it (Slack, GitHub) | Stigmer signs in with the app your Organization or the deployment registered for the server's address  |

A server at an address with no key in its headers is probed when the plugin is
installed. If it answers with an OAuth challenge, the plugin records that the
server signs in, with a login variable named `<SERVER>_ACCESS_TOKEN` and the
`Authorization` header that carries it. A person signs in once, with **Sign in**
on the plugin's page or `stigmer connect plugin`, and the login is kept in their
vault as a connection at the server's address, refreshed automatically before
each run. If it expires and cannot be refreshed, they sign in again from the
plugin's page. A local program has no sign-in: it takes its keys from secrets.

A server in an Agent's own `mcp_servers` is not probed. A run logs in to it with
the connection saved in its vaults at the server's address, else a secret named
`<SERVER>_ACCESS_TOKEN` (the server's name upper-cased, each other character
written as `_`), else it calls the server with no login. A header that names
`Authorization` takes the login from its `${NAME}` instead, and the run then
needs that key. For a server that asks for one, **Sign in** sits beside it on
the Agent's page.

An Organization that needs its own OAuth app for an address — for a vendor
Stigmer cannot sign in to on its own, or for tighter control — adds a login app
listing that address, and every sign-in there uses it.

For a deeper look at OAuth patterns and configuration, see the
[integration guides](/docs/guides/integrations/overview).

## Tool discovery

When a turn starts, Stigmer reaches the Agent's own servers and the servers of
every plugin the Agent and the conversation list, and asks each for its tools.
Each tool has:

- A **name** — used to call it (for example, `get_ledger`)
- A **description** — helps the LLM decide when to use it
- An **input schema** — defines what arguments it accepts

The Agent sees these tool descriptions in its context and decides which tools to
call based on the user's request. You don't need to tell the Agent "when the
customer asks for a variance report, call `get_ledger`" — the LLM figures that
out from the tool's description.

## Sandbox isolation

Tool calls run in a controlled sandbox:

- **Input validation** — Arguments are checked against the tool's input schema
  before execution
- **Isolated execution** — Each tool call runs in its own sandbox
- **Result capture** — Tool outputs are captured and returned to the Agent as
  structured data

HTTP-based MCP servers are isolated by design — Stigmer connects to them as a
network client, so the tool server runs in its own infrastructure. Local
programs run only on a person's own runner, as subprocesses of the runner on
their machine — Stigmer-managed cloud compute never launches them.

This sandboxing means the Agent can't bypass the tool server's logic or directly
access the underlying system. It can only use the tools as the MCP server
exposes them.

## Conversation-level tools

Just as [Skills](/docs/concepts/skills) can be added at the Session level, a
[Session](/docs/concepts/sessions) can list plugins of its own in `plugins`.
They join the Agent's, one entry per plugin. A conversation adds plugins only;
the servers written in an Agent stay the Agent's. A chat with the built-in
assistant, which has no Agent, gets its tools from the plugins its conversation
lists, and runs their hooks.

The Agent's tool lists govern these plugins like its own: an Agent whose `tools`
list does not name a conversation's plugin server cannot use it.
