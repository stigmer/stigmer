[Skills](/docs/concepts/skills) give an Agent domain knowledge. Tools give it
the ability to _act_. An Agent with tool access can query databases, create
tickets, look up orders, send emails — any operation your systems support.

Stigmer uses the
[Model Context Protocol (MCP)](https://modelcontextprotocol.io/) to connect
Agents to external tools. MCP is an open standard that defines how AI models
discover and call tools. This means any MCP-compatible tool server works with
Stigmer — you're not locked into a proprietary integration format.

## How tool calls work

When an Agent has tool access and receives a request that requires action, it:

1. Decides which tool to call based on the request and the tool's description
2. Constructs the tool call arguments
3. Stigmer validates the arguments and executes the call in a sandbox
4. The tool returns a result
5. The Agent uses the result to form its response

## Built-in web fetch

Not every capability needs an MCP server. Every Agent can fetch a public URL out
of the box — the native harness ships a built-in `web_fetch` tool, and the
[Cursor harness](/docs/concepts/harnesses) has its own `WebFetch`. Fetched HTML
is converted to Markdown, large pages are paginated, and the tool is read-only
and asks for no approval unless the Agent's hooks ask about it, so it works in
unattended contexts like shared and embedded Agents. On managed cloud runners,
fetches to private and internal addresses are refused.

Reach for an MCP server when you need more than retrieval of a public page —
authenticated APIs, site-specific extraction, or write operations.

## Where MCP Servers come from

Most MCP Servers arrive as Plugins. A plugin from Stigmer's catalogue, or from a
catalogue you add, declares the servers it needs; installing it creates them in
your Organization, marked as the plugin's, beside the Agent that uses them when
the plugin carries one, and ready to list on your own Agents when it does not.
You connect a server once and Stigmer discovers its tools. A server another
Organization owns is yours to use only through a Plugin, or when that
Organization is a platform sharing it with the Organizations it manages.

A remote (HTTP) server works in any Session, local or cloud-hosted. A stdio
server (a local subprocess launched through `npx` or `uvx`) runs only on a local
runner, so it fits local Sessions and not the hosted product.

You can also define your own MCP Servers for internal or proprietary systems. A
plugin is a starting point, not a constraint: any server that speaks the Model
Context Protocol works with Stigmer, whether a plugin installed it, or you wrote
its definition for your Organization.

## MCP Server resource

An MCP Server is a Stigmer resource that defines a tool connection. It describes
how to reach the tool server and what environment variables it needs:

```yaml
apiVersion: agentic.stigmer.ai/v1
kind: McpServer
metadata:
  name: order-management-api
  visibility: visibility_org
spec:
  description: >
    Connects to the order management system. Provides tools for looking up
    orders, checking inventory, and processing returns.
  stdio:
    command: "npx"
    args: ["@acme/order-mcp-server"]
  env:
    ORDER_API_URL:
      is_secret: false
      description: Base URL of the order management API
    ORDER_API_KEY:
      is_secret: true
      description: API key for authenticating with the service
```

### Transport options

MCP Servers support two transport modes:

| Mode      | When to use                                                                  | Configuration                                                                      |
| --------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| **stdio** | The tool must run on your own machine — **local-runner sessions only**       | `command` and `args` — the local runner launches and communicates via stdin/stdout |
| **HTTP**  | The tool server is a remote service — works on every session, local or cloud | `url`, optional `headers` and `query_params` with `${VAR}` substitution            |

Stdio servers spawn a subprocess on the machine executing the agent, so they are
supported only on sessions that run on a local runner (the desktop app or
`stigmer server`). Sessions on Stigmer-managed cloud compute refuse stdio
servers when a run is created, with a clear error naming the server and the
remediation.

### Variable declarations

The `env` map declares what the MCP Server needs at runtime — API keys, service
URLs, configuration values. A secret is found by its name in a
[vault](/docs/concepts/vaults) when a run starts; a plain setting may carry its
value in the declaration.

Each declaration can be marked as `optional`. By default, every declared
variable is required — a run whose vaults hold no value for it is refused before
it starts, naming the key and who must add it. Optional variables let the MCP
Server operate without that value.

A server's login is matched by its address: signing in to it saves a connection
at that address in your vault, and a run fills that server's login variable from
it (only that server's: a sign-in never serves another server at the same
address). Other keys are matched by name. So a credential on a Schedule's vault
is the one its runs use, and your own vault serves your own chats.
[Vaults](/docs/concepts/vaults#which-vaults-a-run-uses) explains the order in
full.

This separation means the MCP Server definition is portable. The same
`order-management-api` works for every person and team that uses it — only the
vault values change.

## Connecting tools to Agents

[Agents](/docs/concepts/agents) reference MCP Servers through
`mcp_server_usages` in their definition:

```yaml validate-as="Agent"
spec:
  mcp_server_usages:
    - mcp_server_ref:
        kind: mcp_server
        slug: order-management-api
  tools:
    - mcp__order-management-api__get_order
    - mcp__order-management-api__list_orders
```

Each usage entry names one MCP Server by slug, and the Agent gets every tool it
reports. To narrow that, the Agent carries Claude Code's two lists:

| Field              | Purpose                                                 |
| ------------------ | ------------------------------------------------------- |
| `tools`            | Only these tools (empty means every tool the Agent has) |
| `disallowed_tools` | Never these tools, applied first                        |

Entries use Claude Code's names: built-ins such as `Read`, `Grep` or
`Bash(git push *)`, `mcp__<server-slug>` for every tool of one server,
`mcp__<server-slug>__<tool>` for one tool, and `mcp__*` for every MCP tool. A
specifier such as `(git push *)` is accepted but governs the whole tool: it
never narrows `Bash` to some commands.

This design means you define the tool server once and reference it from multiple
Agents. Each Agent can keep a different subset — the read-only Agent above only
gets `get_order` and `list_orders`, while a full-access Agent also gets
`process_return`. [Approval Flows](/docs/concepts/approval-flows) covers what
the lists guarantee, and how an Agent's `hooks` decide a call the lists allow.

## Connecting a tool

An MCP Server definition describes _what_ a tool server is. Connecting it tells
Stigmer _what it can do_.

When you connect an MCP Server, Stigmer performs two steps in a single action:

1. **Discovers tools** — connects to the live server and enumerates every tool
   and resource template it exposes, with each tool's MCP annotations
2. **Stores the results** — discovered tools are saved on the MCP Server's
   status, each marked destructive or not, ready for any Agent that references
   it

By default, a tool asks for human approval before it runs when its server marks
it destructive, with the MCP annotation `destructiveHint: true`, and every other
tool runs without asking. The server's author makes that call, not Stigmer:
`process_return` asks if the order server annotates it, and `get_order` does
not. An Agent's hooks can change that call by call: a hook can refuse a tool,
ask about it, or let it run
([Guard an agent's tools with hooks](/docs/guides/plugins/use-hooks)).

## Authentication for tools

Some tools need credentials to access the systems behind them. Stigmer supports
three authentication patterns, each suited to a different type of integration:

| Pattern                    | When it applies                                                     | How it works                                                                                           |
| -------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| **Environment variables**  | The tool uses API keys or tokens                                    | You declare the variable in `env` and save the value in a vault                                        |
| **Automatic OAuth**        | The server implements the MCP Authorization spec                    | Stigmer reads the server's login server from its URL, becomes its client once, and handles the sign-in |
| **OAuth with a login app** | The vendor requires an OAuth app registered with it (Slack, GitHub) | Stigmer signs in with the app your Organization or the deployment registered for the server's address  |

In every OAuth pattern, the sign-in starts from the server's address, and the
access token is saved as a connection at that address in the signer's vault,
where it serves every HTTP tool at that address and is refreshed automatically
before each run. If a token expires and cannot be refreshed, the user signs in
again from the MCP Server's connect page. A local program (a tool that runs a
command) has no sign-in: it takes its keys from secrets.

An Organization that needs its own OAuth app for an address — for a vendor
Stigmer cannot sign in to on its own, or for tighter control — adds a login app
listing that address, and every sign-in there uses it.

For a deeper look at OAuth patterns and configuration, see the
[integration guides](/docs/guides/integrations/overview).

## Tool discovery

When an Agent runs, Stigmer connects to the referenced MCP Servers and discovers
their available tools. Each tool has:

- A **name** — used to call it (for example, `get_order`)
- A **description** — helps the LLM decide when to use it
- An **input schema** — defines what arguments it accepts

The Agent sees these tool descriptions in its context and decides which tools to
call based on the user's request. You don't need to tell the Agent "when the
user asks about an order, call `get_order`" — the LLM figures that out from the
tool's description.

## Sandbox isolation

Tool calls run in a controlled sandbox:

- **Input validation** — Arguments are checked against the tool's input schema
  before execution
- **Isolated execution** — Each tool call runs in its own sandbox
- **Result capture** — Tool outputs are captured and returned to the Agent as
  structured data

HTTP-based MCP servers are isolated by design — Stigmer connects to them as a
network client, so the tool server runs in its own infrastructure. Stdio-based
MCP servers run only on local runners, as subprocesses of the runner on your own
machine — Stigmer-managed cloud compute never launches them.

This sandboxing means the Agent can't bypass the tool server's logic or directly
access the underlying system. It can only use the tools as the MCP Server
exposes them.

## Session-level tools

Just as [Skills](/docs/concepts/skills) can be added at the Session level, a
[Session](/docs/concepts/sessions) can attach MCP Servers of its own.
Session-level `mcp_server_usages` merge with the Agent's, one entry per server.

The Agent's tool lists govern these servers like its own: an Agent whose `tools`
list does not name a Session's server cannot use it.
