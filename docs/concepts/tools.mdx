[Skills](/docs/concepts/skills) give an Agent domain knowledge. Tools give it
the ability to _act_. An Agent with tool access can query databases, create
tickets, look up orders, send emails — any operation your systems support.

Stigmer uses the
[Model Context Protocol (MCP)](https://modelcontextprotocol.io/) to connect
Agents to external tools. MCP is an open standard that defines how AI models
discover and call tools. This means any MCP-compatible tool server works with
Stigmer — you're not locked into a proprietary integration format.

## How tool calls work

When an Agent has tool access and receives a request that requires action, it:

1. Decides which tool to call based on the request and the tool's description
2. Constructs the tool call arguments
3. Stigmer validates the arguments and executes the call in a sandbox
4. The tool returns a result
5. The Agent uses the result to form its response

## MCP Server resource

An MCP Server is a Stigmer resource that defines a tool connection. It describes
how to reach the tool server and what Environment variables it needs:

```yaml
apiVersion: agentic.stigmer.ai/v1
kind: McpServer
metadata:
  name: order-management-api
  visibility: visibility_public
spec:
  description: >
    Connects to the order management system. Provides tools for looking up
    orders, checking inventory, and processing returns.
  stdio:
    command: "npx"
    args: ["@acme/order-mcp-server"]
  env_spec:
    data:
      ORDER_API_URL:
        is_secret: false
        description: Base URL of the order management API
      ORDER_API_KEY:
        is_secret: true
        description: API key for authenticating with the service
  pinned_tool_approvals:
    - tool_name: process_return
      message: "Process return for order '{{args.order_id}}'"
```

### Transport options

MCP Servers support two transport modes:

| Mode      | When to use                             | Configuration                                                             |
| --------- | --------------------------------------- | ------------------------------------------------------------------------- |
| **stdio** | The tool server runs as a local process | `command` and `args` — Stigmer launches and communicates via stdin/stdout |
| **HTTP**  | The tool server is a remote service     | `url`, optional `headers` and `query_params` with `${VAR}` substitution   |

### Environment variables

The `env_spec` declares what the MCP Server needs at runtime — API keys, service
URLs, configuration values. These are _schemas_, not values. The actual values
come from [Environments](/docs/concepts/environments) attached to the Agent
Instance at deployment time.

This separation means the MCP Server definition is portable. The same
`order-management-api` works in development (pointing to a test API) and
production (pointing to the real one) — only the Environment values change.

## Connecting tools to Agents

[Agents](/docs/concepts/agents) reference MCP Servers through
`mcp_server_usages` in their definition:

```yaml
spec:
  mcp_server_usages:
    - mcp_server_ref:
        kind: mcp_server
        slug: order-management-api
      enabled_tools:
        - get_order
        - list_orders
        - process_return
```

Each usage entry specifies:

| Field                     | Purpose                                                                        |
| ------------------------- | ------------------------------------------------------------------------------ |
| `mcp_server_ref`          | Which MCP Server to connect to (by slug)                                       |
| `enabled_tools`           | Which tools the Agent can use (empty means all tools)                          |
| `tool_approval_overrides` | Per-Agent overrides for [approval requirements](/docs/concepts/approval-flows) |

This design means you define the tool server once and reference it from multiple
Agents. Each Agent can enable a different subset of tools — a read-only Agent
might only get `get_order` and `list_orders`, while a full-access Agent also
gets `process_return`.

## Tool discovery

When an Agent runs, Stigmer connects to the referenced MCP Servers and discovers
their available tools. Each tool has:

- A **name** — used to call it (for example, `get_order`)
- A **description** — helps the LLM decide when to use it
- An **input schema** — defines what arguments it accepts

The Agent sees these tool descriptions in its context and decides which tools to
call based on the user's request. You don't need to tell the Agent "when the
user asks about an order, call `get_order`" — the LLM figures that out from the
tool's description.

## Tool isolation

Tool calls run in a controlled sandbox:

- **Input validation** — Arguments are checked against the tool's input schema
  before execution
- **Isolated execution** — Each tool call runs in its own sandbox
- **Result capture** — Tool outputs are captured and returned to the Agent as
  structured data

This sandboxing means the Agent can't bypass the tool server's logic or directly
access the underlying system. It can only use the tools as the MCP Server
exposes them.

## Session-level tool overrides

Just as [Skills](/docs/concepts/skills) can be added at the Session level, tool
access can be customized per [Session](/docs/concepts/sessions). Session-level
`mcp_server_usages` merge with the Agent's configuration — if the same MCP
Server appears in both, the Session-level entry takes precedence.

This lets you temporarily add or restrict tool access for a specific
conversation without changing the Agent definition.
