Every resource in Stigmer — Agents, Skills, MCP Servers, Sessions, Environments
— belongs to an Organization. An Organization is a tenant boundary that groups
resources and controls who can access them.

### Organizations

An Organization is the top-level boundary. It owns all resources within it and
controls access through identity providers and API keys.

```yaml
apiVersion: tenancy.stigmer.ai/v1
kind: Organization
metadata:
  name: Acme Corp
  slug: acme
spec:
  description: Acme Corp agent platform
```

Key properties:

| Field         | Purpose                                                                                                                                              |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`          | The permanent id Stigmer gives the Organization when it is made (`org_…`). Everything the Organization owns is filed under it                        |
| `slug`        | The name you type in URLs, manifests and `--org`, unique across the platform. An owner can change it                                                 |
| `parent_org`  | Set only on a [child organization](#parent-and-child-organizations): the Organization that manages it. Fixed at create                               |
| `external_id` | Set only on a child organization: the parent's own identifier for it, such as a customer id. Unique among the parent's children, and fixed at create |

### Ids and slugs

Wherever you name an Organization (`org: acme` in a manifest, `--org acme` on
the CLI, a console URL) you can give its slug or its id; Stigmer answers with
the id. Because every resource is filed under the id, an owner can rename an
Organization and nothing moves: its agents, members and secrets stay where they
are. The old slug keeps leading to the Organization for 30 days, and nobody else
can take it meanwhile; after that it is free. A deleted Organization's slug is
free once everything it owned has been removed, and an Organization made later
under the same slug reaches nothing the deleted one owned.

Renaming is its own operation, open to the Organization's owners: in the
console, the Organization's settings; with the CLI, apply the Organization's
manifest with its `id` and the new `slug` (the manifest
`stigmer get organization <slug> -o yaml` prints has both). An ordinary update
never changes the slug.

### Per edition

- **Open source** holds one Organization. Its server makes it the first time it
  starts and fills it into every request that names none, so nobody names it:
  the console has no organization switcher, the CLI never asks for one, and an
  API call leaves `org` empty. Everyone who signs in holds a role on it, so the
  console's create-an-organization screen shows only to someone whose role was
  removed, or on a server whose organization could not be made. The server
  refuses a second Organization (`ORGANIZATION_LIMIT_REACHED`) and refuses to
  delete its one (`ORGANIZATION_IS_SINGLE`). `getServerInfo` answers
  `single_org: true`, which is how a client knows.
- **Enterprise and Stigmer Cloud** hold many. A write or an organization-scoped
  read names its Organization, and one that names none is refused. A
  cross-organization read such as search accepts an empty `org` and spans every
  Organization the caller can see.

### Plugins

A Plugin groups the resources that belong together within an Organization: the
Agent, Skills, MCP Servers and Workflows one folder installs. It is the unit of
install, upgrade and removal: `stigmer push plugin <dir>` installs the folder as
one Plugin, the Marketplace installs one from a catalogue, and removing the
Plugin removes every resource it brought. A Plugin is not written as YAML; it is
read from a folder in the open Agent Plugins format (or the Cursor, Claude Code
or Codex dialect), and the resource the server keeps records what landed:

```yaml
apiVersion: agentic.stigmer.ai/v1
kind: Plugin
metadata:
  name: customer-support
  org: acme
spec:
  name: customer-support
  version: "1.0.0"
  description: "Customer support agents, skills, and tool connections."
```

A resource you author on its own (`stigmer apply -f agent.yaml`) belongs to the
Organization directly and is managed one at a time. See
[Install a plugin](/docs/guides/plugins/install-a-plugin).

## Parent and child organizations

An Organization may have a **parent**: another Organization that created it and
manages it. A platform that builds on Stigmer (Acme Cloud, say) creates one
**child organization** for each of its own customers under its own Organization,
the **parent organization**. A child names its parent in `parent_org`, and may
carry the parent's own identifier for the customer in `external_id`:

```yaml
apiVersion: tenancy.stigmer.ai/v1
kind: Organization
metadata:
  name: Tenant Alpha
  slug: tenant-alpha
spec:
  parent_org: acme-cloud
  external_id: cust-4411
```

Both are fixed when the child is created, and children are one level deep: a
child has no children of its own. An Organization you create for yourself has no
parent; that is the usual case.

A child organization is a full tenant boundary. Its own people work in it as in
any Organization, and nothing it holds is visible to another child.

The parent's admins **manage** every child and read **nothing** a child holds.
They can change a child's settings, rename or delete it, manage its members,
roles and invitations, and see its billing; they cannot see its Agents,
Sessions, Environments or files, its usage reports, or run anything in it. A
parent admin who needs to look inside adds themselves as a member of the child,
through its ordinary members screen; the child's member list and access history
show it, and the child's own admins can remove them. Nobody owns a child when it
is created: the parent's admins grant its first members and owner.

A child's people sign in through the parent's Identity Provider, whose
`external_id_claim` names each token's child by its `external_id`, or with
tokens a PlatformClient of the parent mints for that child. On Stigmer Cloud a
child runs on its parent's plan. An Organization can be deleted once every child
it has is being deleted (see
[Deleting an Organization](#deleting-an-organization)).

## Deleting an Organization

An owner deletes an Organization from the CLI with
`stigmer delete organization <slug>`. Deleting removes everything the
Organization owned, in three steps:

1. **At once.** The delete answers, and from that moment the Organization does
   not exist for anyone. Its members, its API keys, its share links, its
   Schedules and its Channels all get "not found", and nothing new can start
   inside it. Every role anyone held in it is gone.
2. **Within minutes.** In the background, Stigmer stops anything still running
   (Schedules, runs, sandboxes), then removes every Agent, Session, Workflow,
   file, Skill, MCP Server, Plugin, Environment and secret, Channel and its
   conversations, and every permission that named the Organization. Where an
   edition seals secrets with a key per Organization (Stigmer Cloud), that key
   is destroyed too, so a copy of a secret in an old backup can no longer be
   read.
3. **When that finishes.** The Organization's slug is free for someone else, and
   not before.

Some records are kept on purpose, and each edition says which. Stigmer Cloud
keeps billing records, because they are money, and the history of who was
granted what, because it is the audit trail. Open source keeps nothing.

A parent Organization can be deleted once every child it has is being deleted;
its own removal finishes after theirs. While a child is not being deleted, the
parent's delete is refused (`FAILED_PRECONDITION`, `ORGANIZATION_HAS_CHILDREN`).

There is no restore window: once deleted, an Organization and what it owned do
not come back. Open source holds one Organization and never deletes it.

## Cloud vs. local

In **Stigmer Cloud**, you create an Organization through the web console or API.
Your Organization has its own isolated boundary, and you manage resources
through the SDK, CLI, or web console.

In **local mode** (running `stigmer server` on your machine), Stigmer creates an
implicit Organization automatically. You don't need to think about Organizations
at all — resources just work. This implicit Organization ensures that the same
API contracts work identically in both modes.

## Resource visibility

Every resource has a visibility setting that says who inside the platform can
read it:

| Visibility              | Meaning                                                                                                                                 |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `visibility_private`    | The person who created it, and anyone granted access to it directly                                                                     |
| `visibility_org`        | Everyone in the owning Organization (the default for Agents, Skills, MCP Servers, Workflows and Plugins)                                |
| `visibility_child_orgs` | Everyone in every child organization of the owning Organization (see [Parent and child organizations](#parent-and-child-organizations)) |

Nothing an Organization owns is visible outside it unless it is a parent sharing
it with its child organizations. To use another Organization's Agent, Skill or
MCP Server, install the Plugin that carries it: the copy is yours, in your
Organization, and upgrades with the Plugin.

## Resource references

Resources reference each other by `kind` and `slug`. Omit `org` and the
reference points at your own Organization, which is the common case:

```yaml validate-as="Agent.spec"
skill_refs:
  - kind: skill
    slug: return-policy
```

An `org` field is accepted only when that Organization is your parent and shares
the resource with its children at `visibility_child_orgs`:

```yaml validate-as="Agent.spec"
# A Skill the parent organization shares with every child organization
skill_refs:
  - kind: skill
    slug: return-policy
    org: acme-cloud
```

Stigmer checks every reference when you save: the referenced resource must
exist, and an Agent or Workflow may not be more visible than the Skills, MCP
Servers and Agents it references, so what a person can run they can also read. A
reference that fails either check is refused with the field and the reason
named, rather than failing later at run time.

This keeps resource definitions portable — they reference resources by name, not
by internal IDs. Stigmer stores a reference's Organization by id, so a stored
reference keeps pointing at its Organization across a rename.
