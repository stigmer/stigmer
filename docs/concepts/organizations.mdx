Every resource in Stigmer — Agents, Skills, MCP Servers, Sessions, Environments
— belongs to an Organization. An Organization is a tenant boundary that groups
resources and controls who can access them.

### Organizations

An Organization is the top-level boundary. It owns all resources within it and
controls access through identity providers and API keys.

```yaml
apiVersion: tenancy.stigmer.ai/v1
kind: Organization
metadata:
  name: Acme Corp
  slug: acme
spec:
  description: Acme Corp agent platform
  management_mode: self_managed
```

Key properties:

| Field             | Purpose                                                                                                                                          |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `slug`            | URL-friendly identifier, unique across the platform                                                                                              |
| `management_mode` | `self_managed` (you operate the org directly) or `platform_managed` (an external platform creates and operates the org via an Identity Provider) |

### Plugins

A Plugin groups the resources that belong together within an Organization: the
Agent, Skills, MCP Servers and Workflows one folder installs. It is the unit of
install, upgrade and removal: `stigmer push plugin <dir>` installs the folder as
one Plugin, the Marketplace installs one from a catalogue, and removing the
Plugin removes every resource it brought. A Plugin is not written as YAML; it is
read from a folder in the open Agent Plugins format (or the Cursor, Claude Code
or Codex dialect), and the resource the server keeps records what landed:

```yaml
apiVersion: agentic.stigmer.ai/v1
kind: Plugin
metadata:
  name: customer-support
  org: acme
spec:
  name: customer-support
  version: "1.0.0"
  description: "Customer support agents, skills, and tool connections."
```

A resource you author on its own (`stigmer apply -f agent.yaml`) belongs to the
Organization directly and is managed one at a time. See
[Install a plugin](/docs/guides/plugins/install-a-plugin).

## Management modes

Every Organization has a `management_mode` that determines who operates it. The
mode is set at creation and cannot change afterward.

### Self-managed

You create a self-managed Organization when you sign up for Stigmer directly.
You own the Organization and manage its resources, users, and settings through
the Stigmer UI, CLI, or API. Authentication uses Stigmer's own login, or you can
configure an SSO Identity Provider so your team signs in with existing
credentials.

```yaml
apiVersion: tenancy.stigmer.ai/v1
kind: Organization
metadata:
  name: Acme Corp
  slug: acme
spec:
  management_mode: self_managed
```

Self-managed is the default. If you are a team using Stigmer to build and run
Agents, this is the mode you use.

### Platform-managed

A platform-managed Organization is created programmatically by an **external
platform** that builds on Stigmer. The platform registers an Identity Provider,
then creates Organizations on behalf of its own customers. Each Organization is
linked to the platform's Identity Provider via `identity_provider_ref`, and the
platform can store its own tenant identifier in `external_org_id` for reverse
lookup.

```yaml
apiVersion: tenancy.stigmer.ai/v1
kind: Organization
metadata:
  name: Tenant Alpha
  slug: tenant-alpha
spec:
  management_mode: platform_managed
  identity_provider_ref:
    kind: identity_provider
    slug: acme-cloud
    org: acme
  external_org_id: "acme-tenant-alpha-id"
```

Platform-managed Organizations are operated by the platform, not by their end
users. The platform's backend provisions users, grants access, and manages
resources through the Stigmer API. End users authenticate with tokens from the
platform's Identity Provider — they never interact with Stigmer's own login.

## Multi-tenant platforms

When a platform serves multiple customers and each customer needs isolated
Agents, Skills, Sessions, and access controls, the platform creates one
platform-managed Organization per customer. The Organization boundary gives each
tenant full resource isolation — an Agent in one Organization cannot see or
access resources in another.

The pattern works like this:

1. The platform registers a single Identity Provider in its own Organization.
2. For each new customer, the platform creates a platform-managed Organization
   linked to that Identity Provider.
3. When a customer's user signs up, the platform provisions a federated Identity
   Account in the customer's Organization and grants it an appropriate role.
4. The user authenticates with a JWT from the platform's auth system. Stigmer
   validates the token, resolves the user's federated account, and checks IAM
   Policies scoped to the tenant's Organization.

Because every resource — Agents, Skills, MCP Servers, Sessions, IAM Policies —
is scoped to an Organization, tenants cannot see or affect each other's
resources. The Identity Provider is shared (it authenticates all tenants), but
the Organization boundary keeps each tenant's data and access separate.

## Cloud vs. local

In **Stigmer Cloud**, you create an Organization through the web console or API.
Your Organization has its own isolated boundary, and you manage resources
through the SDK, CLI, or web console.

In **local mode** (running `stigmer server` on your machine), Stigmer creates an
implicit Organization automatically. You don't need to think about Organizations
at all — resources just work. This implicit Organization ensures that the same
API contracts work identically in both modes.

## Resource visibility

Every resource has a visibility setting that says who inside the platform can
read it:

| Visibility            | Meaning                                                                                                                                                  |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `visibility_private`  | The person who created it, and anyone granted access to it directly                                                                                      |
| `visibility_org`      | Every member of the owning Organization (the default for Agents, Skills, MCP Servers, Workflows and Plugins)                                             |
| `visibility_platform` | Every member of every Organization the owning Organization manages through its Identity Provider (see [Multi-tenant platforms](#multi-tenant-platforms)) |

Nothing an Organization owns is visible outside it unless that Organization is a
platform sharing it with the Organizations it manages. To use another
Organization's Agent, Skill or MCP Server, install the Plugin that carries it:
the copy is yours, in your Organization, and upgrades with the Plugin.

## Resource references

Resources reference each other by `kind` and `slug`. Omit `org` and the
reference points at your own Organization, which is the common case:

```yaml validate-as="Agent.spec"
skill_refs:
  - kind: skill
    slug: return-policy
```

An `org` field is accepted only when that Organization is a platform that shares
the resource with yours at `visibility_platform`:

```yaml validate-as="Agent.spec"
# A Skill the platform Organization shares with every Organization it manages
skill_refs:
  - kind: skill
    slug: return-policy
    org: acme-cloud
```

Stigmer checks every reference when you save: the referenced resource must
exist, and an Agent or Workflow may not be more visible than the Skills, MCP
Servers and Agents it references, so what a person can run they can also read. A
reference that fails either check is refused with the field and the reason
named, rather than failing later at run time.

This keeps resource definitions portable — they reference resources by name, not
by internal IDs.
