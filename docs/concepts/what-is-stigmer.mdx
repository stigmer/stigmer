## The problem Stigmer solves

You called the ChatGPT or Claude API. The demo worked. Then you tried to ship
it.

The AI doesn't know your business — your return policy, your product catalog,
your escalation process. It can't take actions in your systems. There's no way
to add human oversight. Every call is a one-shot interaction with no memory of
what came before.

Building all of that yourself means assembling orchestration, durability, tool
security, state management, and an API layer — months of infrastructure work
before you ship a single Agent.

Stigmer is the platform that handles that infrastructure so you can focus on
building Agents.

## What Stigmer is

Stigmer is an open-source AI-powered Agent platform. You define Agents, teach
them your domain, connect them to your tools, and set rules for when they need
human approval. Then any application in your stack can call those Agents via a
standard API.

Stigmer provides the runtime layer that makes Agents production-ready:

- **Durable Execution** — Agents survive crashes and resume where they left off
- **Tool sandboxing** — Agents interact with external systems through
  controlled, validated tool calls
- **Human approval flows** — you decide which actions require a human decision
  before proceeding
- **Conversation memory** — Agents remember context across interactions within a
  Session
- **Real API contracts** — gRPC services with public protobuf definitions, so
  you generate type-safe clients in any language

## Who Stigmer is for

**Technical founders and engineering leads** choosing Agent infrastructure for
their product. You build software used by other people — SaaS platforms,
internal tools, customer-facing applications — and you want to add AI-powered
Agent capabilities without building Agent infrastructure from scratch.

**Developers on those teams** who implement the integration. You write the YAML,
use the CLI, call the API, and embed SDK components. You care about developer
experience, type safety, and local development that matches production.

Stigmer is not for hobbyists building personal chat assistants, data scientists
doing model training, or no-code users expecting a visual drag-and-drop builder.
It's a platform for people building products.

## Three capability layers

Stigmer's value builds in layers. Each layer adds a capability that makes Agents
more useful. You adopt them progressively — start with domain knowledge, add
tools when ready, add human oversight when the use case demands it.

### 1. Knows your business

You upload domain knowledge — product docs, process guides, policies,
institutional knowledge — as Skills. The Agent uses that knowledge to answer
questions and make decisions specific to your business.

Without a Skill, the Agent gives generic answers. With a Skill, it gives
domain-expert answers. The difference is visible in one prompt.

### 2. Uses your tools

Your Agent can query databases, create tickets, send emails, update records —
any action your systems support. Tool access uses the
[Model Context Protocol (MCP)](https://modelcontextprotocol.io/), an open
standard for connecting AI models to external tools.

An Agent with tool access can look up an order, check its status, and initiate a
return. An Agent without it can only say "I would be happy to help — please
contact support."

### 3. Asks before acting

You define which actions require human approval. The Agent pauses, presents its
reasoning, and waits for a human to approve or reject before proceeding. This is
a control mechanism, not a logging feature.

Routine questions and queries are handled automatically. Only the actions you
designate require approval.

## How Stigmer is different

### vs. Direct LLM API calls

Calling the OpenAI or Anthropic API gives you a prompt-in, response-out flow.
The LLM doesn't know your business, can't take actions, has no state across
conversations, and offers no approval mechanism. Every call is a one-shot
interaction.

Stigmer adds domain knowledge, tool access, conversation memory, approval flows,
and Durable Execution around the LLM.

### vs. RAG solutions

Retrieval-augmented generation makes an Agent better at answering questions from
documents. It's a read-only capability — the Agent still can't take actions, run
Workflows, or ask for human approval. And you manage embedding pipelines, vector
databases, and retrieval tuning yourself.

Skills provide domain knowledge without embedding pipelines or vector databases.
And knowledge is just the starting point — tool access, approval flows, and
Workflow automation build on top.

### vs. Agent frameworks

Frameworks give you Agent primitives as a library. You still build the
infrastructure: orchestration, durability, state management, API layer, tool
security, deployment. Every app that uses the Agent embeds the framework. Update
the Agent logic and you redeploy every consumer.

Stigmer is a platform, not a framework. Define the Agent once. Run it as a
service. Call it from any app via API. Update the Agent — every consumer
benefits instantly. Stigmer provides the infrastructure layer that frameworks
leave to you.

## Core resource model

Stigmer manages Agents as declarative resources — similar to how a database
manages tables or an auth service manages users. You define resources in YAML,
apply them, and Stigmer handles the rest.

The key resources you'll learn about in the following pages:

| Resource                                     | What it represents                                                                |
| -------------------------------------------- | --------------------------------------------------------------------------------- |
| [Agent](/docs/concepts/agents)               | A blueprint that defines what an Agent does — its instructions, Skills, and tools |
| [Skill](/docs/concepts/skills)               | A piece of domain knowledge that makes an Agent an expert in your business        |
| [MCP Server](/docs/concepts/tools)           | A tool connection that lets an Agent interact with external systems               |
| [Session](/docs/concepts/sessions)           | A conversation context that preserves memory across interactions                  |
| [Environment](/docs/concepts/environments)   | A named set of configuration values and secrets                                   |
| [Organization](/docs/concepts/organizations) | A tenant boundary that groups resources and teams                                 |
