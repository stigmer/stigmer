Stigmer is the open-source backend for the agents in your product. It runs
behind your app, the way your database does.

You already ship a product with customers. You want each of them to get an agent
that does real work inside it: it takes what the customer hands it, works
through it, and hands back the result. Stigmer runs those agents for you, so you
build the feature and not the machinery. Your app calls Stigmer, and Stigmer
runs the agent on your model provider.

## What each customer's agent has

- **Its own computer.** A sandbox that keeps its files between turns: the agent
  reads what the customer gave it there, works there, and saves what it hands
  back. An [Environment](/docs/concepts/environments) says what is installed on
  it and what it may reach, and
  [Sessions](/docs/concepts/sessions#what-a-session-keeps) says where it runs on
  your servers and on ours.
- **It asks before acting** on anything you mark as needing a yes. The agent
  stops, a person approves or declines, and the agent carries on
  ([Approval flows](/docs/concepts/approval-flows)).
- **Each customer's agents, files and keys stay apart** from every other
  customer's. On the editions that include it, each customer gets an
  [Organization](/docs/concepts/organizations) of their own
  ([Give each customer their own organization](/docs/getting-started/one-organization-per-customer)).
  On the open-source server, each customer's keys live in a vault of their own
  ([Keep your customers' keys](/docs/guides/authentication/customer-keys)).
- **Your model keys, on your servers or ours.** Agents run on your own provider
  keys, never on one of Stigmer's
  ([Model provider keys](/docs/guides/integrations/model-provider-keys)). Run it
  yourself under Apache 2.0, or use Stigmer Cloud;
  [Open source, Enterprise and Cloud](/docs/guides/self-hosting/cloud-vs-self-hosted)
  says how the editions differ.

## One job, end to end

The [quickstart](/docs/getting-started/quickstart) runs one job: an accounting
product's customer uploads a ledger and gets a variance report back. Here is the
same job told through Stigmer's pieces.

1. Your app starts a [Session](/docs/concepts/sessions) on the
   `variance-reporter` [Agent](/docs/concepts/agents), in the customer's
   Organization. The Agent is the job description; the Session is this one piece
   of work.
2. The ledger arrives as a [File](/docs/concepts/files), attached to the
   Session's first message.
3. The Agent works in its own sandbox, set up by an
   [Environment](/docs/concepts/environments), and calls the model on your
   Anthropic key.
4. Add the `ledger` plugin to the Agent, and it can read the customer's books
   and post corrections to them as well. It asks before `post_adjustment`
   changes the books, and waits for a person's yes
   ([Approval flows](/docs/concepts/approval-flows)). The quickstart's Agent has
   no plugin; [Tools](/docs/concepts/tools) shows how one is added.
5. The report comes back as a File of the Session, and the Session's events
   stream to your app while the Agent works ([Streaming](/docs/sdk/streaming)).

Your app talks only to Stigmer, and Stigmer talks to your model provider on your
key. Inside Stigmer, the Session runs the Agent in a sandbox of its own, which
holds the ledger that came in and the report that goes back.

## How it differs

### From calling a model API

A model's API answers one request at a time. It has no computer to work on,
keeps no customer's files between turns, never stops to ask a person, and has no
wall between one customer's data and the next. You would build each of those
yourself, along with the queues, retries and tenant checks around them. Stigmer
is those pieces, behind your app.

### From an agent framework

A framework is a library inside your app. It gives you the agent loop, and you
still build the server around it: storage, sandboxes, approvals, an API, and a
redeploy of every app that embeds it when the agent changes. Stigmer is a server
behind your app instead. You define an Agent once, call it from any service, and
change it in one place.

### From Claude Managed Agents

Anthropic describes Claude Managed Agents as a "pre-built, configurable agent
harness that runs in managed infrastructure": Anthropic runs the agents and
their sandboxes, on Claude. Stigmer is open source, runs on your servers or
ours, runs on your own model keys, and gives each of your customers their own
Organization on the editions that include it. Agents, Environments, Sessions and
their events carry the same names in both, and Anthropic's SDK reads a Stigmer
Session's events.
[Coming from Claude Managed Agents](/docs/concepts/coming-from-claude-managed-agents)
maps each idea, and
[Stigmer and Claude Managed Agents](https://stigmer.ai/compare/claude-managed-agents)
sets the two side by side.

## What Stigmer is not for

Stigmer is not a coding agent. Agents that write and review your own code are
the world of Claude Code, Cursor and Codex, and you may well use one already.
Stigmer runs the agents you ship to your customers. The plugins you built for
those tools still work here: Stigmer reads them unchanged
([Plugins](/docs/concepts/plugins)).
