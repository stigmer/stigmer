# Stigmer Sales Website Standards

This document defines the rules, conventions, and quality bar for the Stigmer sales website. Every page, section, component, and line of copy — whether authored by a human or generated by AI — must conform to these standards.

The sales website exists to **convert developer visitors into Stigmer adopters**. It is not the documentation site (which explains *how*) and not the product console (which enables *doing*). It explains *why*.

For page and section templates, see [`templates/`](templates/).

For machine-readable content requirements, see [`content-requirements.json`](content-requirements.json).

For machine-readable copy rules, see [`copy-guidelines.json`](copy-guidelines.json).

For performance budgets, see [`performance-budget.json`](performance-budget.json).

For component naming and quality rules, see [`component-standards.md`](component-standards.md).

For the navigation hierarchy and URL scheme, see [`information-architecture.md`](information-architecture.md).

## Mandates

These seven rules are non-negotiable. They apply to every page, section, and component in `site/`.

### 1. Conversion-First

Every element on the sales website must serve a defined role in the conversion funnel. Content that does not move the visitor toward adoption does not belong.

The funnel has four stages:

| Stage | Visitor Goal | Site's Job | Example Content |
|---|---|---|---|
| **Awareness** | "What is this?" | Hook in 5 seconds | Hero section, headline, badges |
| **Interest** | "What does it do?" | Educate with benefits | Features, How It Works |
| **Evaluation** | "Is it right for me?" | Build trust, address objections | Comparison, Use Cases, Architecture |
| **Action** | "Let me try it" | Remove friction | Quickstart, install command, docs link |

Every page must be tagged to a funnel stage. Every section must have a defined job. A section without a job does not belong on the page. Content that tries to serve all stages serves none.

### 2. Developer Authenticity

The copy must sound like a senior engineer explaining their tool choice at a meetup — confident, specific, honest about tradeoffs. Never like a marketing team writing a press release.

Developers are technically literate, naturally skeptical, and allergic to hype. They detect and punish marketing speak instantly. If the copy would still make sense after replacing "Stigmer" with "Acme AI Platform," it is too generic.

Honest signals: precise technical language, named protocols (MCP, gRPC), named technologies (Temporal, LangGraph), specific formats (YAML, protobuf), acknowledged tradeoffs.

Dishonest signals: vague superlatives, unattributed testimonials, empty comparisons, stock-photo-style language.

### 3. Show, Don't Tell

Code snippets, terminal output, YAML blocks, and architecture diagrams carry more persuasive weight than paragraphs of text. They are copy elements, not illustrations.

- Every claim must be accompanied by proof. "Agents survive crashes" requires a terminal output showing an execution resuming after failure. "5 lines of YAML" requires the actual 5 lines.
- If you cannot show it, do not claim it.
- The homepage must show working code within the first two viewports.
- Sales code examples must be **minimal** (only essential lines), **impressive** (demonstrate a meaningful capability), and **self-explanatory** (readable without surrounding context).

### 4. Specificity Over Superlatives

"5 lines of YAML" is a claim. "Easy to configure" is noise. Every statement must be specific enough to verify.

Numbers are credibility markers: "5 lines of YAML," "zero cloud dependency," "3 commands to your first agent," "Apache 2.0 license." Use them.

If a claim cannot be quantified, it must be demonstrated with a code snippet, terminal output, or architecture diagram. Undemonstrated claims are marketing; demonstrated claims are proof.

### 5. Performance Is Credibility

A slow marketing site tells developers the product is slow. This is not rational, but it is true. Core Web Vitals targets are mandatory, not aspirational. See [Performance Requirements](#performance-requirements) for specific targets.

### 6. Accessibility Is Non-Negotiable

WCAG 2.1 AA compliance is the minimum bar. Accessibility is a design constraint, not an engineering concern to handle later. See [Accessibility Requirements](#accessibility-requirements) for specific requirements.

### 7. Consistency Across Surfaces

The sales website does not exist in isolation. It connects to the GitHub README, the documentation site, the CLI `--help` output, and eventually the Cloud signup flow. Messaging, terminology, and factual claims must be consistent across all surfaces.

- Use the canonical terms from `docs/standards/terminology.json`. The sales website must never introduce terminology that contradicts the domain model.
- If the homepage says "5 lines of YAML," the quickstart must not require 15 lines.
- The sales website says "why." The docs say "how." They complement each other without contradicting or duplicating.

## Page Types

The sales website supports nine page types. Every page belongs to exactly one type. Each type has a defined purpose, audience, funnel stage, and set of required sections.

### Choosing the Right Type

- "What is Stigmer and why should I care?" → Homepage
- "How does Stigmer solve X problem?" → Use-Case Page
- "How does Stigmer compare to Y?" → Comparison Page
- "Tell me more about capability Z" → Feature Page
- "I came from a campaign or launch announcement" → Landing Page
- "What does it cost?" → Pricing Page
- "What changed in the latest release?" → Changelog Page
- "Teach me something useful" → Blog Page
- "How do I get involved?" → Community Page

### Page Type Registry

| Type | Purpose | Audience | Funnel Stage | Required Sections |
|---|---|---|---|---|
| **Homepage** | First impression; hub to all journeys | All personas | Awareness → Action | Hero, Features, How It Works, Quickstart, CTA Band |
| **Use-Case** | Persona-specific problem → solution story | Specific persona | Interest → Evaluation | Hero, Problem, Solution, Proof, CTA Band |
| **Comparison** | Honest "Stigmer vs X" evaluation | Engineering managers, architects | Evaluation | Hero, Comparison Table, When to Use Each, CTA Band |
| **Feature** | Deep-dive on a major capability | All personas | Interest → Evaluation | Hero, Explanation, Code Showcase, Benefits, CTA Band |
| **Landing** | Campaign or launch conversion page | Campaign audience | Awareness → Action | Hero, Key Message, Social Proof, CTA Band |
| **Pricing** | Pricing tiers and feature breakdown | Evaluators, decision-makers | Evaluation → Action | Hero, Tier Comparison, FAQ, CTA Band |
| **Changelog** | Release notes and migration guides | Existing users, evaluators | Interest | Release entries with date, version, changes |
| **Blog** | Technical posts, tutorials, announcements | All personas | Awareness → Interest | Title, Author, Date, Content, Related Posts |
| **Community** | Community resources and contribution paths | Contributors, advocates | Interest → Action | Hero, Contribution Paths, Resources, CTA Band |

Every page must also include: a clear audience (which persona), a clear goal (what the visitor should do next), and a clear success metric (how we know it is working).

For detailed structural requirements, see the templates in [`templates/`](templates/).

## Section Types

Every reusable section has a defined job, required elements, and quality criteria.

### Hero

**Job:** Hook — earn the scroll.

| Requirement | Detail |
|---|---|
| Headline | Max 8 words. Communicates category + value. |
| Subheadline | 1-2 sentences. Expands the headline with specificity. |
| Primary CTA | Dominant visual weight. Specific action text. |
| Secondary CTA | Clearly subordinate. Alternative path. |
| Visual anchor | Code snippet, terminal mockup, or badge cluster. Not a stock image. |
| Above fold | **Yes** — all elements visible without scrolling. |

The hero is scanned, not read. Visitors pattern-match in under 5 seconds: what is this, why does it matter, what do I do next.

### Features

**Job:** Educate — what does it do, and why should I care?

| Requirement | Detail |
|---|---|
| Benefit-first descriptions | Lead with the outcome, not the implementation detail. |
| Icon or visual identifier | One per feature. Consistent style. |
| Proof point | Code snippet, metric, or link to deeper content. Per feature. |
| Hierarchy | 3-6 features per grid. More than 6 requires prioritization. |

### How It Works

**Job:** Build trust — show it is well-built.

| Requirement | Detail |
|---|---|
| Step-by-step flow | 3-5 numbered steps with visual progression. |
| Code or diagram | At least one concrete artifact per step. |
| Progressive disclosure | Overview first, detail on demand. |

### Code Showcase

**Job:** Prove — show it works.

| Requirement | Detail |
|---|---|
| Minimal example | Only essential lines. Self-explanatory without context. |
| Syntax highlighting | Language-tagged. Consistent theme. |
| Copy button | One click to clipboard. |
| Context label | What this code does, in one line above the block. |

### Comparison

**Job:** Handle objections — why this over alternatives?

| Requirement | Detail |
|---|---|
| Honest positioning | Acknowledge what alternatives do well. |
| Specific differences | Technical, not marketing. Name the protocols, features, tradeoffs. |
| "When to use each" | Clear guidance on when Stigmer is and is not the right choice. |
| Fair representation | Never misrepresent competitors. Developers who know those tools will notice. |

### Social Proof

**Job:** Validate — who else uses this?

| Requirement | Detail |
|---|---|
| Real metrics | GitHub stars, contributor count, recent commit activity. |
| Verifiable claims | Every number must be auditable. No vanity metrics. |
| Freshness | Metrics must be current. Stale numbers signal an abandoned project. |

### CTA Band

**Job:** Convert — make the next step obvious.

| Requirement | Detail |
|---|---|
| Headline | Reinforces the page's key message. |
| Supporting copy | 1-2 sentences max. |
| Primary CTA | Dominant. Specific action text ("Install Stigmer," not "Get Started"). |
| Secondary CTA | Subordinate alternative path. |
| Placement | End of every major content section. Repeat at page bottom. |

### FAQ

**Job:** Address remaining objections.

| Requirement | Detail |
|---|---|
| Real questions | Sourced from actual developer objections, not fabricated. |
| Concise answers | 2-3 sentences max per answer. Link to docs for depth. |
| Structured data | JSON-LD `FAQPage` schema for search engine rich results. |

## Copy Rules

Sales copy follows different rules than documentation. The docs are neutral and exhaustive. Sales copy is confident, concise, and benefit-driven.

### Voice and Tone

- **Confident, not arrogant.** State what Stigmer does well. Be transparent about where it is headed.
- **Technical, not academic.** Use precise terms. Avoid jargon that adds no information.
- **Conversational, not casual.** Write as if speaking to a peer at a technical meetup.
- **Second person** ("you") when addressing the visitor.
- **Present tense** for descriptions. **Imperative mood** for instructions.
- **Active voice** always. "Stigmer runs your agent," not "Your agent is run by Stigmer."

### Feature → Benefit → Proof Pattern

Every feature on the site must follow this structure:

1. **Feature:** What it is (technical fact).
2. **Benefit:** Why it matters (outcome for the developer).
3. **Proof:** How to verify (code snippet, terminal output, link).

Lead with the benefit. Support with the feature. Prove with an example. Never lead with the implementation detail.

Example:
- Benefit: "Your agent survives crashes and resumes exactly where it left off"
- Feature: Temporal-backed durable execution with per-tool-call checkpointing
- Proof: Terminal output showing an execution resuming after failure

### Banned Phrases

These phrases are prohibited. They add no information and signal marketing over engineering.

| Banned | Why | Replace With |
|---|---|---|
| "revolutionary" | Hyperbole | State the specific improvement |
| "game-changing" | Hyperbole | State the specific difference |
| "seamless" | Vague | Describe the actual integration steps |
| "best-in-class" | Unverifiable | State the specific metric |
| "enterprise-grade" | Meaningless without proof | State the specific capability (HA, RBAC, audit logs) |
| "next-generation" | Empty | Describe what is actually new |
| "powerful" | Every tool claims this | State the specific capability |
| "easy to use" | Subjective | Show the actual steps ("3 commands") |
| "unlock the potential" | Corporate jargon | State the specific outcome |
| "digital transformation" | Enterprise jargon | Remove entirely |
| "synergy" | Enterprise jargon | Remove entirely |
| "AI-powered" | The entire product is AI-related | Remove — it adds no information |
| "scalable solutions" | Vague | State the specific scaling characteristic |

### Required Patterns

- **Every claim needs proof.** No undemonstrated assertions.
- **Code before paragraph.** When explaining a capability, show the code first, then explain.
- **Specific numbers over adjectives.** "5 lines of YAML" beats "simple configuration."
- **Objection-aware writing.** Anticipate why the visitor might leave and address it directly.
- **Honest comparisons.** When comparing to alternatives, state genuine differences. Acknowledge competitor strengths.

### Terminology

Use the canonical terms from [`docs/standards/terminology.json`](../../docs/standards/terminology.json). The sales website must never introduce terminology that contradicts the domain model.

Key terms: `Agent` (not "bot"), `AgentExecution` (not "agent run" or "job"), `McpServer` (not "tool connector"), `Organization` (not "tenant"), `stigmer apply` (not "deploy"), `stigmer run` (not "execute").

## Design Rules

The sales website has its own design vocabulary, distinct from the product design system. Marketing components serve narrative, persuasion, and conversion — not task efficiency.

### Typography

| Role | Font | Weight | Usage |
|---|---|---|---|
| Body text | Geist Sans | 400 | Paragraphs, descriptions |
| Headings | Geist Sans | 600, 700 | Section titles, headlines |
| Code | Geist Mono | 400 | Code blocks, terminal output, inline code |
| Hero headline | Geist Sans | 700 | Page hero only |

Limit to these two font families. Every additional font weight is a performance cost. Do not use display fonts — they signal "marketing site" rather than "developer tool."

### Color System

Use the established CSS custom properties from `globals.css`. Do not introduce arbitrary color values.

| Token | Role | Value |
|---|---|---|
| `--primary` | Interactive elements, links, primary CTA | Electric blue (217 91% 60%) |
| `--accent` | Highlights, secondary emphasis | Purple (262 83% 58%) |
| `--background` | Page background | Dark theme base |
| `--foreground` | Body text | Light on dark |
| `--muted` | Subdued text, borders | Low-contrast variant |
| `--card` | Card surfaces | Elevated surface |
| `--glass-*` | Glassmorphism effects | Glass background, border, blur |
| `--glow-*` | Glow effects | Small, medium, large glow presets |

Color must serve function, not decoration. Use color to distinguish categories, indicate hierarchy, and guide attention. Gratuitous gradients undermine the technical aesthetic.

Dark theme is the default. If a light theme is added, it must be equally polished — not an afterthought inversion.

### Spacing

Follow the Tailwind spacing scale. Do not use arbitrary values (`w-[347px]`). If a value is not on the scale, the design needs adjustment, not a custom value.

| Context | Minimum | Recommended |
|---|---|---|
| Section padding (vertical) | `py-16` (64px) | `py-24` (96px) |
| Content max-width | — | `max-w-7xl` (80rem) |
| Card gap | `gap-4` (16px) | `gap-6` (24px) |
| Text block max-width | — | `max-w-2xl` (42rem) for readability |

### Animation

Use the centralized variants from `lib/animations.ts`. Do not write inline `animate` props with magic values.

| Variant | Use For |
|---|---|
| `fadeInUp` | Section entrance on scroll |
| `fadeIn` | Subtle content reveals |
| `scaleIn` | Cards, interactive elements |
| `slideInRight` / `slideInLeft` | Slide-in panels, mobile menu |
| `staggerContainer` | Parent of staggered children |

**Rules:**
- GPU-composited properties only (`transform`, `opacity`). No layout-triggering animations (`width`, `height`, `top`, `left`).
- Use `viewportSettings.standard` (`once: true, margin: "-100px"`) for scroll-triggered animations.
- Respect `prefers-reduced-motion`. The `globals.css` already disables transitions and animations when this preference is set. Do not override it.
- Use transition presets from `transitions` (`spring`, `smooth`, `fast`). Do not invent new timing curves.

### Component Conventions

Components follow the atomic design taxonomy:

| Level | Examples | Location |
|---|---|---|
| Atoms | Button, Badge, CodeBlock, Icon | `site/src/components/ui/` |
| Molecules | FeatureCard, CTABand, ComparisonRow | `site/src/components/ui/` or `sections/` |
| Organisms | HeroSection, FeatureGrid, ComparisonTable | `site/src/components/sections/` |
| Pages | HomePage, UseCasePage | `site/src/components/pages/` |

Marketing components live in `site/src/components/`. They are not part of the SDK packages and must not leak into them.

For detailed component quality rules, see [`component-standards.md`](component-standards.md).

### Responsive Breakpoints

Test at four breakpoints. The design must be intentional at each — not fluid-scaled from desktop.

| Breakpoint | Width | Focus |
|---|---|---|
| Mobile | 375px | Touch targets ≥ 44px, thumb-reachable nav, stacked layouts |
| Tablet | 768px | Two-column where appropriate, readable code blocks |
| Laptop | 1024px | Full layout, hover interactions |
| Desktop | 1440px | Maximum content width, generous whitespace |

Code blocks must be horizontally scrollable on narrow viewports, never truncated.

## Performance Requirements

Performance targets are hard limits. Violations must be fixed before merge.

### Core Web Vitals

| Metric | Target | Measurement |
|---|---|---|
| Largest Contentful Paint (LCP) | < 2,500ms | Lighthouse, Chrome UX Report |
| First Input Delay (FID) / Interaction to Next Paint (INP) | < 100ms / < 200ms | Lighthouse, Chrome UX Report |
| Cumulative Layout Shift (CLS) | < 0.1 | Lighthouse, Chrome UX Report |

### Bundle Budget

| Asset | Maximum |
|---|---|
| Total JavaScript (compressed) | 150 KB |
| Total CSS (compressed) | 50 KB |

Static marketing content should ship minimal client-side JavaScript. Interactive elements (code tabs, copy buttons, mobile menu) use progressive enhancement.

### Image Strategy

- SVG for icons and diagrams.
- WebP or AVIF for raster images. Never ship unoptimized PNGs.
- Lazy-load below-the-fold images with `loading="lazy"`.
- Maximum individual image size: 200 KB.

### Font Strategy

- Two font families maximum (Geist Sans + Geist Mono).
- Four font weights maximum across both families.
- Subset fonts to used character ranges.
- Use `font-display: swap` to prevent flash of invisible text.

### Animation Budget

- GPU-composited properties only (`transform`, `opacity`).
- No layout-triggering animations.
- Animations disabled when `prefers-reduced-motion: reduce` is set.
- Total animation JavaScript: included in the bundle budget, not in addition to it.

## Accessibility Requirements

WCAG 2.1 AA compliance is the minimum bar.

### Contrast

| Context | Minimum Ratio |
|---|---|
| Body text | 4.5:1 |
| Large text (≥ 18px bold or ≥ 24px regular) | 3:1 |
| UI components and graphical objects | 3:1 |

Dark themes present unique contrast challenges. Test text on dark backgrounds specifically — do not assume light-theme contrast ratios transfer.

### Keyboard Navigation

- All interactive elements must be reachable via keyboard (`Tab`, `Shift+Tab`, `Enter`, `Escape`).
- Focus order must follow the visual reading order.
- Focus indicators must be visible. Use the existing `:focus-visible` styles. Do not remove outlines.
- Modal dialogs and mobile menus must trap focus and return it on close.

### Screen Reader

- Skip link to main content (already implemented in the site).
- Landmark regions: `<header>`, `<main>`, `<footer>`, `<nav>`.
- Semantic headings: one `<h1>` per page, sequential heading levels, no skips.
- `alt` text for every non-decorative image. Decorative images use `alt=""`.
- `aria-labelledby` on sections (already implemented in the site).
- Live regions (`aria-live`) for dynamic content updates.

### Reduced Motion

- All non-essential animations must be disabled when `prefers-reduced-motion: reduce` is set.
- The `globals.css` media query already handles this. Do not override it.
- Essential animations (e.g., loading indicators) may use reduced-intensity alternatives.

### Touch Targets

- Minimum touch target size: 44 x 44 pixels.
- Adequate spacing between adjacent touch targets to prevent mis-taps.

### Color Independence

- Color must not be the sole channel for conveying information.
- Use text labels, icons, or patterns alongside color to communicate status, categories, or differences.

## SEO Requirements

### Title Tags

- Every page must have a unique `<title>`.
- Maximum 60 characters.
- Include the primary keyword.
- Format: `{Page-Specific Title} | Stigmer` or `Stigmer: {Value Proposition}`.

### Meta Descriptions

- Every page must have a unique `<meta name="description">`.
- Maximum 160 characters.
- Include the primary keyword and a call to action.
- Meta descriptions are ad copy for search results — write them to earn the click.

### Heading Hierarchy

- Exactly one `<h1>` per page.
- `<h2>` for major sections, `<h3>` for subsections.
- Never skip heading levels (`<h3>` must follow `<h2>`, not `<h1>`).
- Include relevant keywords naturally in headings. Do not keyword-stuff.

### Structured Data

Provide JSON-LD structured data where applicable:

| Schema | When |
|---|---|
| `Organization` | Site-wide (in layout) |
| `SoftwareApplication` | Homepage, feature pages |
| `WebSite` | Site-wide (in layout) |
| `FAQPage` | Pages with FAQ sections |
| `Article` / `BlogPosting` | Blog pages |

### Internal Linking

- Every page must link to 2-3 related pages using descriptive anchor text.
- Links must guide visitors through the funnel: Interest page → Evaluation page → Action page.
- No page should be a dead end.
- Use descriptive anchor text. "See how Stigmer compares to LangChain" is useful. "Click here" is not.

### Open Graph and Social

- Every page must include `og:title`, `og:description`, `og:image`, and `og:url`.
- `og:image` dimensions: 1200 x 630 pixels.
- Include `twitter:card` with `summary_large_image` type.

## Quality Checklist

Before merging any sales website change, verify every item. Each is pass/fail.

### Content

- [ ] Page belongs to a defined page type
- [ ] All required sections for that page type are present
- [ ] Every section has a defined job in the conversion funnel
- [ ] Every claim is specific and verifiable
- [ ] Every claim is accompanied by proof (code, metric, or link)
- [ ] No banned phrases (run lint)
- [ ] Copy follows the Feature → Benefit → Proof pattern
- [ ] Terminology matches `terminology.json`
- [ ] Messaging is consistent with the README and docs

### Design

- [ ] Layout follows the Tailwind spacing scale (no arbitrary values)
- [ ] Colors use CSS custom properties (no hardcoded values)
- [ ] Typography uses Geist Sans / Geist Mono only
- [ ] Animations use `lib/animations.ts` variants (no inline `animate` props)
- [ ] Responsive at all four breakpoints (375, 768, 1024, 1440)
- [ ] CTA hierarchy is clear (primary dominant, secondary subordinate)

### Performance

- [ ] Lighthouse score ≥ 90 for Performance
- [ ] LCP < 2,500ms
- [ ] CLS < 0.1
- [ ] Total JS < 150 KB (compressed)
- [ ] Total CSS < 50 KB (compressed)
- [ ] Images are WebP/AVIF or SVG (no unoptimized PNGs)
- [ ] Fonts: 2 families, ≤ 4 weights, `font-display: swap`

### Accessibility

- [ ] Contrast ratios meet WCAG 2.1 AA (4.5:1 body, 3:1 large text)
- [ ] All interactive elements keyboard-accessible
- [ ] Focus indicators visible
- [ ] `prefers-reduced-motion` respected
- [ ] Screen reader tested (headings, landmarks, alt text)
- [ ] Touch targets ≥ 44px

### SEO

- [ ] Unique `<title>` under 60 characters
- [ ] Unique `<meta description>` under 160 characters with CTA
- [ ] One `<h1>` per page, sequential heading levels
- [ ] JSON-LD structured data present where applicable
- [ ] Internal links to 2-3 related pages with descriptive anchor text
