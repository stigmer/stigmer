# Deep Research: Why LangGraph `astream_events(version="v2")` Buffers Anthropic `input_json_delta` Streaming Events

## Research Objective

We are building a platform that uses LangGraph to orchestrate an Anthropic Claude agent. We stream events from the graph to a CLI client in real-time. **Thinking blocks stream perfectly in real-time, but `input_json_delta` blocks (tool call argument tokens) are buffered for ~30 seconds and then released in a ~2-second burst.** We need to understand exactly why this happens and how to fix it.

This is a critical UX problem: when the LLM decides to write a file, the user stares at a static "Write: file.py" indicator for 30 seconds before all the file content appears at once, instead of seeing it stream progressively.

## Our Stack (Exact Versions)

- **LangGraph**: 1.0.8
- **LangChain**: 1.2.10
- **langchain-core**: (bundled with LangChain 1.2.10)
- **langchain-anthropic**: 1.3.3
- **anthropic** (Python SDK): (bundled with langchain-anthropic 1.3.3)

## What We've Already Investigated

### The Evidence (from production logs)

```
12:05:55  [THINK] streaming_started     ← thinking begins streaming
12:05:58  [THINK] streaming_completed   ← 3 seconds of progressive real-time streaming ✓
...
12:06:13  [TOOL_EARLY] tool=write       ← tool_use block arrives immediately ✓
              (events_processed = 358)
          ── 30-second gap: NO on_chat_model_stream events for input_json_delta ──
              (only 9 total events in 30 seconds, counter goes 358 → 367)
12:06:43  [STREAM] burst starts         ← hundreds of events in ~2 seconds
12:06:45  [STREAM_DIAG] block_types=['input_json_delta']  ← all deltas arrive at once
12:06:45  [TOOL_RECONCILE] on_tool_start fires  ← 176ms after last delta
```

**Key observation**: Thinking blocks (type `thinking`) stream in real-time. The `tool_use` block header also arrives immediately. Only `input_json_delta` blocks are buffered. All three block types go through the same `on_chat_model_stream` event path in `astream_events(version="v2")`.

### The Architecture

The graph is built by a library called `deepagents` (v0.4.0) which internally calls `langchain.agents.create_agent()` (from `langchain` 1.2.10). The agent graph is a standard LangGraph `CompiledStateGraph`.

The model node is defined as:
```python
graph.add_node("model", RunnableCallable(model_node, amodel_node, trace=False))
```

The async model node calls:
```python
output = await model_.ainvoke(messages)
```

We stream via:
```python
async for event in agent_graph.astream_events(graph_input, config=config, version="v2"):
    process(event)
```

### What We've Traced Through the Code

We traced the complete streaming pipeline through 8 layers:

1. **`ainvoke()` auto-upgrades to streaming**: `BaseChatModel._agenerate_with_cache()` (langchain-core) checks `_should_stream()`, which detects the `_StreamingCallbackHandler` injected by `astream_events()`. When detected, it calls `_astream()` internally instead of `_agenerate()`. This explains why thinking blocks DO stream even though the node code says `ainvoke()`.

2. **`_agenerate_with_cache()` fires callbacks for ALL chunks** (langchain-core `chat_models.py` lines 1331-1336):
   ```python
   if run_manager:
       await run_manager.on_llm_new_token(
           cast("str", chunk.message.content), chunk=chunk
       )
   ```
   This runs for every chunk from `_astream()`, regardless of content type (thinking, tool_use, input_json_delta, text).

3. **`ChatAnthropic._astream()` yields ALL block types** (langchain-anthropic `chat_models.py`): Each `content_block_delta` event from the Anthropic API (including `input_json_delta`) is converted to an `AIMessageChunk` and yielded individually.

4. **The event handler uses `send_nowait()`** (langchain-core `event_stream.py` line 170): `_AstreamEventsCallbackHandler._send()` immediately queues each event via `send_nowait()` on a `_MemoryStream`. No batching.

5. **The consumer runs as a concurrent asyncio Task** (langchain-core `event_stream.py` line 1062): `asyncio.create_task(consume_astream())` runs the graph execution in a separate task. The main generator reads events from the `_MemoryStream` receive stream.

6. **Each iteration of `_astream()` has async yield points**: Both `async for event in stream` (Anthropic SDK) and `await run_manager.on_llm_new_token(...)` are await points that should allow the event loop to schedule the consumer task.

### The Mystery

Every layer in the pipeline appears to forward events immediately. The code path is identical for thinking blocks and input_json_delta blocks. Yet thinking streams in real-time while input_json_delta buffers for 30 seconds. **We cannot find the buffering mechanism from static code analysis alone.**

## Specific Research Questions

### 1. LangGraph `astream_events` Known Issues with Tool Call Streaming

- Are there any known issues, GitHub issues, or discussions about `astream_events(version="v2")` buffering `input_json_delta` or tool call argument streaming?
- Has anyone reported that tool call arguments don't stream in real-time through `astream_events`?
- Are there any LangGraph version-specific fixes (e.g., in versions after 1.0.8) that address streaming of tool call arguments?

### 2. LangGraph `stream_mode="messages"` as Alternative

- LangGraph 1.0.8 supports `stream_mode="messages"` on `graph.astream()`, with `stream_eager=True` automatically enabled. Does this mode deliver `input_json_delta` tokens in real-time?
- What is the event format for `stream_mode="messages"`? What metadata is included?
- Can `stream_mode=["messages", "updates"]` provide both token-level streaming AND node-level state changes (equivalent to `on_tool_start`/`on_tool_end`)?
- Has anyone successfully used `stream_mode="messages"` to solve the exact buffering problem we're seeing?
- What are the tradeoffs vs `astream_events`?

### 3. `langchain-anthropic` Streaming Behavior

- In `langchain-anthropic` 1.3.3, does `ChatAnthropic._astream()` yield `input_json_delta` chunks one-at-a-time as they arrive from the Anthropic API, or does it batch them?
- Does `_make_message_chunk_from_anthropic_event()` have any special handling for `input_json_delta` that could cause delays?
- Is there a `block_start_event` tracking mechanism that could delay yielding chunks until a block completes?

### 4. LangGraph Model Node Internals

- When `langchain`'s `create_agent()` (factory.py) creates the model node as `RunnableCallable(model_node, amodel_node)`, does LangGraph's runtime replace `ainvoke()` with `astream()` when running under `astream_events()`? We believe yes (via `_should_stream()` detecting `_StreamingCallbackHandler`), but want confirmation.
- Is there any internal buffering in LangGraph's pregel runner that accumulates streaming events from a model node before routing to the next node (tool execution)?
- Does LangGraph need the complete `AIMessage` (with fully-formed tool calls) before it can route to the tool node, and does this requirement cause it to delay emitting streaming events?

### 5. Anthropic Python SDK SSE Streaming

- Does the `anthropic` Python SDK's SSE client (`httpx`-based) have any buffering that could delay `input_json_delta` events?
- Is there a difference in how the Anthropic API server streams thinking tokens vs tool argument tokens? (e.g., different buffering on the API side)
- Are there any known issues with the `anthropic` SDK's streaming when extended thinking is enabled alongside tool use?

### 6. Prior Art and Solutions

- Has anyone built a system that successfully streams tool call arguments in real-time through LangGraph to a CLI/UI?
- What streaming approach did they use (`astream_events`, `astream` with `stream_mode`, direct model streaming, custom callbacks)?
- Are there any LangGraph examples or documentation that specifically address streaming tool call argument generation?
- Are there any known workarounds (e.g., custom callback handlers, model wrappers, or graph modifications) that enable real-time tool call argument streaming?
