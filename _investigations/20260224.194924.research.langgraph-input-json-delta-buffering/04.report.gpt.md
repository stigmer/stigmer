# Why LangGraph `astream_events(version="v2")` Appears to Buffer Anthropic `input_json_delta` Tool-Argument Streams

## What the symptom most strongly indicates

Your timeline (“thinking streams perfectly; tool header arrives immediately; then ~30 seconds of silence; then hundreds of `input_json_delta` events arrive in a burst”) is best explained by **server-side buffering of tool-argument streaming**, not by LangGraph’s event pipeline.

Anthropic’s own documentation for **fine‑grained tool streaming** explicitly describes the behavior you are seeing:

- Tool-argument streaming can be **delayed because parameters are buffered and JSON-validated** before being streamed.
- Fine‑grained tool streaming exists specifically to stream tool parameters **“without buffering or JSON validation,” reducing latency** to begin receiving large parameters. citeturn48view0

The doc’s example is strikingly similar to your “write a long thing into a tool call” workload (writing a long poem into a tool call), and it shows **a multi‑second “delay” before the first tool-parameter chunks begin** in the non‑fine‑grained case. citeturn48view0

This is why your **thinking blocks** are fine: they are not subject to the “buffer until valid JSON” constraint. But when the model starts emitting a **large tool input JSON**, the platform may hold back the incremental deltas until it’s confident it has valid JSON (or until it has assembled a large portion), then flush the deltas quickly—creating exactly the “30‑second gap, then 2‑second burst” UX failure you’re observing. citeturn48view0

### Reports that match your “gap then burst” tool-argument streaming pattern

This is not unique to your LangGraph + CLI setup.

A recent issue in **LangChain.js** describes the same pattern with Anthropic tool calls: initial tool call chunks appear, then a multi‑second pause while the model “generates the whole input json,” and then many deltas arrive “at the same time.” citeturn39view0

Separately, an issue in the **Anthropic TypeScript SDK** describes a **long delay** when using streaming + tools. citeturn3view2

Taken together with Anthropic’s own documentation, these reports strongly suggest the “buffering” is frequently **upstream of LangGraph** (platform/tool-streaming semantics, not LangGraph’s event queue). citeturn48view0turn39view0turn3view2

### Why this can look like LangGraph buffering in production logs

From LangGraph’s perspective, if the upstream (Anthropic API/SDK) is not yielding `input_json_delta` events for 30 seconds, **LangGraph has nothing to emit**, so your `events_processed` counter will barely move—exactly like your logs. Then when the upstream quickly yields the already-buffered deltas, LangGraph will forward them quickly, producing a burst.

This interpretation fits your observation that:
- **`tool_use` header arrives immediately** (block start is available early)
- but **argument deltas** appear later in a burst (arguments were buffered upstream)

## How LangGraph and LangChain streaming modes relate to this issue

### `astream_events(version="v2")` vs `astream(..., stream_mode="messages")`

In the LangGraph docs, **`stream_mode="messages"`** is described as streaming **2‑tuples `(message_chunk, metadata)`** “from any graph nodes where an LLM is invoked.” citeturn37view0

LangChain’s streaming overview also shows that `messages` mode streams **tool call chunks** as incremental pieces (e.g., `tool_call_chunk` with partial JSON). citeturn36view0

This means `stream_mode="messages"` is *a plausible alternative interface* if you want:
- token-level chunks (including tool-call-arg chunks, when the provider emits them)
- plus node metadata (`langgraph_node`, etc.) that helps you route output to the right UI panel citeturn37view0turn36view0

But it does **not** magically fix upstream buffering. If Anthropic delays tool-argument emission, both `astream_events` and `messages` mode will still observe the gap. (The LangChain.js issue reproduces the delay even while using `streamMode: ["updates","messages"]`.) citeturn39view0

### Combining token streaming and step/state streaming

LangGraph explicitly supports streaming multiple modes at once; if you pass a list, you get `(mode, chunk)` tuples. citeturn37view0

LangChain’s streaming overview demonstrates the same idea at the agent level and shows how `messages` gives you token chunks while `updates` yields step-level updates. citeturn36view0

So yes, **`stream_mode=["messages","updates"]`** is the closest built-in analog to:
- token-level chunk streaming (`messages`)
- tool/node lifecycle / “step completed” updates (`updates`) citeturn37view0turn36view0

### Why `ainvoke()` still streams under graph streaming

LangGraph documentation notes that message streaming events can be emitted even when the model call is written using `.invoke()` (and, by extension, many call paths that aren’t explicitly `.stream()`), as long as streaming is enabled around the run. citeturn41view0

That supports your traced observation that your node calling `ainvoke()` can still produce token streaming under the streamed execution context.

### `stream_eager` and “messages/custom are eager”

In LangGraph’s Pregel runtime implementation, the constructor docs describe a `stream_eager` switch and explicitly state it is **“automatically turned on for stream_mode ‘messages’ and ‘custom’.”** citeturn47view0

That is relevant because it reduces a class of “graph step boundary” buffering. However, your symptom is not “events held until step ends”; you are already seeing non-tool streaming blocks in real time. Your symptom matches an upstream “tool args not emitted yet” delay more than a “Pregel step batching” delay.

## The most likely root cause

### Default tool-argument streaming behavior can buffer for JSON validity

Anthropic’s **Fine‑grained tool streaming** doc is explicit:

- Fine‑grained tool streaming “enables streaming of tool use parameter values **without buffering or JSON validation**, reducing the latency to begin receiving large parameters.” citeturn48view0  
- Without it, the doc gives a concrete example of a noticeable delay (“15s delay” in their illustration) before tool chunks arrive. citeturn48view0  
- The tradeoff is that you may receive “invalid or partial JSON inputs,” and you need robust handling. citeturn48view0

Your “writing a file via tool args” case is exactly “large parameters,” so it lands in the doc’s target zone.

### Why the `tool_use` “header” can arrive early

Tool-use streaming is typically block-structured:
- a tool block can “start” (name/id is known)
- then tool input streams

If the platform decides to validate/buffer tool inputs, the block can be announced early but the actual parameter deltas can be delayed. This matches your logs:
- immediate `tool_use`
- delayed deltas
- tool execution starts only after the final deltas arrive (because the tool node needs completed arguments)

### Why LangGraph can’t route to tools until tool args are complete

Even in an ideal world where tool-arg chunks arrive immediately, the tool execution step still requires a **complete** tool call (fully formed arguments). That’s why `on_tool_start` naturally occurs after the last tool-arg chunk in many designs.

LangChain’s streaming docs also highlight a practical distinction:
- stream partial tool-call chunks (token-level)
- separately access completed messages / tool calls (usually via `updates`) citeturn36view0

So the “tool node waits for completed args” behavior is expected—but it does **not** explain a 30‑second silence during argument generation. The silence is better explained by the provider not emitting the deltas until late.

## Concrete fixes and how to apply them in your exact stack

### Enable fine‑grained tool streaming for the `write` tool

Anthropic now documents fine‑grained tool streaming as generally available and says to enable it by setting **`eager_input_streaming: true`** on the relevant tool definition and turning on `stream`. citeturn48view0

This is the single most direct lever that maps to your symptom.

#### How that maps to LangChain `ChatAnthropic`

The LangChain `ChatAnthropic` reference docs state:

- `bind_tools(...)` accepts a sequence of tool definitions that can be **Mappings** (i.e., dict tool schemas), not only Python callables. citeturn35view1  
- Any unsupported model parameter is passed through to the underlying Anthropic API call. citeturn35view2  
- LangChain also exposes a `betas: list[str]` field: “If specified, invocations will be routed through `client.beta.messages.create`.” citeturn35view0

This matters because you have two practical implementation routes:

**Route A: Pass an Anthropic-format tool dict that includes `eager_input_streaming`**

Because `bind_tools` accepts Mapping tool definitions and claims it supports Anthropic-format tool schemas, you can likely supply a tool dict shaped like Anthropic expects, including `eager_input_streaming`. citeturn35view1turn48view0

### Use `stream_mode=["messages","updates"]` to get both progressive args and tool lifecycle

If your primary UI contract is:
- stream tool-arg deltas progressively
- but also show reliable tool start/end and step transitions

Then LangGraph’s own streaming system supports combining modes. citeturn37view0turn36view0

Key points from the docs:

- `messages` yields `(message_chunk, metadata)` and includes node-level metadata like `langgraph_node`, which is useful for routing a delta to “model output” vs “tool output.” citeturn37view0turn36view0  
- When multiple modes are enabled, outputs are `(mode, chunk)` tuples. citeturn37view0turn36view0

This doesn’t fix upstream buffering by itself, but once you enable fine‑grained tool streaming, it gives you the best structure for a CLI:
- show partial tool arg content as it is generated
- show tool execution result via `updates` (or via the tool node output)

### UI/UX tradeoffs you must handle once tool args truly stream

Fine-grained tool streaming comes with a critical tradeoff: you may receive invalid/incomplete JSON during the stream. citeturn48view0

Practically, that means in your CLI renderer you should:

- treat streamed tool args as a **byte/character stream** for UX (write them as they arrive)
- only treat them as “parsed JSON arguments” once you have a completion signal (e.g., final tool call event, or once the tool node starts)  
- avoid letting partial tool call chunks accidentally become “real tool calls” in the agent logic

This mirrors real-world issues seen when streaming tool call chunks:
- In a LangChain issue, streamed tool-call chunks can have missing/empty names/ids while streaming, causing downstream confusion if treated as finalized tool calls. citeturn40view0

So the safest pattern is:
- **render partial args** for UX
- **execute tools only from completed tool_call structures** (step/update pathway)
