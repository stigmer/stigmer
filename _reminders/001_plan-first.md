# Reminder: Plan First

Before writing any code, creating any file, or making any change — **produce a plan**.

## What a Plan Must Include

1. **What** you are going to do — the specific deliverables, not vague intentions.
2. **Why** this approach — what alternatives exist and why this one wins.
3. **Where** it goes — exact file paths, directories, module boundaries.
4. **What it touches** — every file that will be created, modified, or deleted.
5. **What it does NOT touch** — explicit scope boundaries so we agree on what is out of scope.
6. **Open questions** — anything ambiguous, risky, or requiring a decision. Surface these before executing.

## When to Skip Planning

- Single-line fixes where the change is obvious and self-contained.
- Typo corrections, comment updates, and formatting changes.
- When explicitly told "just do it" for a trivial task.

Everything else gets a plan. If in doubt, plan.

## How to Present the Plan

- Use a structured format: numbered deliverables, file paths, and a sequence of execution.
- Call out surprises — anything discovered during research that was not anticipated.
- Wait for explicit approval before executing. "Looks good" or "go ahead" means proceed. Silence does not.
