# T01.2: Add Organization to the Apply Pipeline

## Architectural Decisions

- **Organization is NOT a project member.** The hierarchy is Platform -> Organization -> Project -> Resources. Organization is applied independently and never tracked in `Project.Spec.Members`. No changes to `reconcile/service.go`.
- **Organization tier changes from `TIER_CLOUD_ONLY` to `TIER_OPEN_SOURCE`.** Required for the CLI to recognize Organization. The proto enum is the source of truth.
- **Server-side controller does not exist yet** (that is T01.5). CLI is wired up correctly; gRPC calls will fail with a clear error until T01.5 lands. Acceptable for incremental delivery.
- **Membership filtering is explicit.** A new `IsProjectMemberKind()` function in the types package makes the member/non-member distinction self-documenting. The declarative flow uses it to decide what gets added to `Project.Spec.Members`.

### Layer 3: Organization CLI package (new)

**New files** under `client-apps/cli/internal/cli/organization/`:

- `loader.go` — `LoadFromBytes([]byte) (*LoadResult, error)`, follows [agent/loader.go](client-apps/cli/internal/cli/agent/loader.go) pattern: YAML -> JSON -> protojson unmarshal -> protovalidate
- `applier.go` — `Apply(*ApplyOptions) (*ApplyResult, error)`, follows [agent/applier.go](client-apps/cli/internal/cli/agent/applier.go) pattern: validate opts, set metadata.org, dry-run shortcut, gRPC Apply RPC
- `BUILD.bazel` — deps on Organization proto stubs, apiresource commons, protovalidate, errors, yaml, protojson, grpc
- `loader_test.go` — valid YAML, invalid YAML, empty content, protovalidate enforcement
- `applier_test.go` — nil org, nil conn, dry-run, org metadata population (follows agent test patterns)

Key design note: The Organization applier sets `metadata.org` from CLI context the same way Agent does. Consistency across all appliers; the server handles any Organization-specific metadata semantics.
