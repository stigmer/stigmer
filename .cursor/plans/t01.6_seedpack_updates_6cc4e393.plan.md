# T01.6: Seedpack Updates — Organization Resource, Remove `org: local`

## Design Decision Requiring Confirmation

**The transitional consistency problem**

The original T01 plan has T01.6 removing `org: local` from seedpack YAML and T01.7 changing the CLI default from `"local"` to `"default"`. Between these two tasks, a broken intermediate state exists:

- Seedpack creates an Organization resource with slug `default`
- But the CLI's `resolveApplyOrganization()` ([apply.go:155](client-apps/cli/cmd/stigmer/root/apply.go)) still returns `"local"` for local backends
- Result: agents get `metadata.org = "local"`, Organization exists with slug `"default"` — they are in different namespaces

**Proposed solution: Add `metadata.org: default` to `stigmer.yaml`**

The CLI already reads the project's `metadata.org` and uses it for all resources in the session:

```130:141:client-apps/cli/cmd/stigmer/root/apply.go
func resolveApplyOrganization(cfg *config.Config, proj *projectv1.Project, override string) (string, error) {
	if override != "" {
		// ...
	}
	if proj.Metadata != nil && proj.Metadata.Org != "" {
		fmt.Fprintf(os.Stderr, "Using organization from stigmer.yaml: %s\n", proj.Metadata.Org)
		return proj.Metadata.Org, nil
	}
	// ... falls through to "local"
```

By setting `metadata.org: default` on the Project manifest, the seedpack becomes self-contained: the project declares its org, all child resources inherit it, and the Organization slug matches. No dependency on T01.7. This also sets the correct example for user-authored projects — declare your org in `stigmer.yaml`, not in every resource.

T01.7 then narrows to changing the CLI *fallback* default (when no project/flag/config provides an org), which is a separate concern.

**Need your confirmation on this approach before proceeding.**

## Apply Order Observation

`scanResourceFiles` uses `os.ReadDir` which returns entries in lexical order. The seedpack subdirectories will be scanned as: `agents/` then `mcp-servers/` then `organizations/`. This means agents are applied BEFORE the Organization resource.

This is **not a problem**: `metadata.org` is a string namespace, not a foreign key. The server stores whatever org value is provided. The Organization resource is independently created — no resource depends on it existing first. This is the same model as today (agents reference org `"local"` which has no corresponding Organization resource).
