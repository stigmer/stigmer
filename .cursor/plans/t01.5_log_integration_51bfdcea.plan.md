# T01.5: Log Integration for Native Mode

## Domain Analysis (Architect Review)

### The Surprise: Log Integration Is Already Implemented

After reading every file in the logging pipeline, I must report that **T01.4 proactively completed the core log integration work**. Specifically:

- [agent_runner_native.go](client-apps/cli/internal/cli/daemon/agent_runner_native.go) lines 91-99 redirect both stdout and stderr to `{logDir}/agent-runner.log` (matching the workflow-runner pattern exactly)
- [server_logs.go](client-apps/cli/cmd/stigmer/root/server_logs.go) already uses `IsAgentRunnerDocker()` to branch between Docker and file-based streaming for all three code paths: single-component, `getComponentConfigs`, and `getComponentConfigsWithStreamPreferences`
- [streamer.go](client-apps/cli/internal/cli/logs/streamer.go) and [merger.go](client-apps/cli/internal/cli/logs/merger.go) are fully generic — they handle any component with `LogFile`/`ErrFile` fields

There is **no missing wiring** between the native agent-runner process and the `stigmer server logs` command. The data flows through existing infrastructure.

### The Real Problem: `IsAgentRunnerDocker` Shells Out to Docker in Native Mode

The function that the entire logs command depends on for mode detection has a design flaw:

```go
// daemon.go lines 1481-1491
func IsAgentRunnerDocker(dataDir string) bool {
    containerIDFile := filepath.Join(dataDir, AgentRunnerContainerIDFileName)
    if _, err := os.Stat(containerIDFile); err == nil {
        return true
    }
    containerID := getContainerIDByName(AgentRunnerContainerName) // execs `docker ps`!
    return containerID != ""
}
```

When running in native mode: no container ID file exists, so it **falls through to `getContainerIDByName` which runs `docker ps -aq`**. Three problems:

1. **Contradicts the migration goal**: Every `stigmer server logs` call execs Docker even when the whole point is to not require Docker
2. **Wrong detection order**: `health_integration.go` correctly checks PID file first, then container ID file. `IsAgentRunnerDocker` never checks the PID file at all and jumps straight to Docker
3. **Stale marker file hazard**: If a user switches from Docker to native mode without a clean stop, a leftover `agent-runner-container.id` file causes `IsAgentRunnerDocker` to return `true` incorrectly

### Proposed Fix

Rewrite `IsAgentRunnerDocker` to use the **authoritative source** — `startup-config.json` — which T01.4 already populated with `AgentRunnerMode`. Fall back to marker-file heuristic (PID-first, matching `health_integration.go`). Never exec Docker.

```go
func IsAgentRunnerDocker(dataDir string) bool {
    // Authoritative: startup config records the mode that was actually used
    if cfg, err := loadStartupConfig(dataDir); err == nil && cfg.AgentRunnerMode != "" {
        return cfg.AgentRunnerMode == config.AgentRunnerModeDocker
    }
    // Fallback: marker file heuristic (PID-first, consistent with health_integration.go)
    if _, err := os.Stat(filepath.Join(dataDir, AgentRunnerPIDFileName)); err == nil {
        return false
    }
    if _, err := os.Stat(filepath.Join(dataDir, AgentRunnerContainerIDFileName)); err == nil {
        return true
    }
    // Neither marker exists. Default false — file-based log lookup handles missing files gracefully.
    return false
}
```

This eliminates the `getContainerIDByName` call entirely from the detection path. Zero Docker dependency.

### `.err` File Gap — Intentional, Consistent

Both native agent-runner and workflow-runner consolidate stdout and stderr into a single `.log` file. The `--stderr` flag will show "Log file does not exist" for `agent-runner.err`. This matches workflow-runner behavior exactly (`daemon.go` line 545: "Consolidate stdout and stderr to single .log file for clarity"). No action needed.
