# T01.1: Define Runtime Filesystem Layout

## Domain Analysis

### The Critique

The research report proposes:

```
~/.stigmer/runtimes/agent-runner/<agentRunnerVersion>/<platform>/python/
~/.stigmer/runtimes/agent-runner/<agentRunnerVersion>/<platform>/venv/
~/.stigmer/cache/wheels/<lockHash>/<platform>/
```

Three issues with this proposal:

1. **The version key is ambiguous.** `<agentRunnerVersion>` conflates the agent-runner app version with the runtime environment version. In practice, the Go CLI orchestrates the entire lifecycle — it decides which Python version to install, which wheelhouse to use, and which agent-runner code to run. The CLI build version (injected via `embedded.buildVersion` in [embedded/version.go](client-apps/cli/embedded/version.go)) already pins everything. Using it as the version key gives us a single, unambiguous identifier.
2. `**<lockHash>` for the wheelhouse is over-engineered.** A content-addressable cache sounds elegant but adds complexity for no practical benefit — the lock file is already pinned by the CLI version. Version-based paths are readable, debuggable, and sufficient.
3. **The wheelhouse and runtime are split across two directory trees** (`runtimes/` vs `cache/wheels/`). This means cleanup requires coordinating two locations. A self-contained layout where everything for one version lives under one path makes lifecycle operations trivial (`rm -rf <version>/` cleans everything).

### Existing Conventions (from codebase)

The existing `~/.stigmer/` layout has two tiers:

- **Config root** (`~/.stigmer/`): `config.yaml`, `stigmer.db`, `bin/`, `logs/` (Temporal, Ollama)
- **Data root** (`~/.stigmer/data/`): `bin/`, `logs/`, PID files, `workspace/`, `artifacts/`

Key source: [config/config.go](client-apps/cli/internal/cli/config/config.go) defines `ConfigDir = ".stigmer"` and `DefaultDataDir = "data"`. `GetConfigDir()` returns `~/.stigmer`, `GetDataDir()` returns `~/.stigmer/data`.

There is an existing inconsistency: Temporal/Ollama put files directly under `~/.stigmer/` while daemon components use `~/.stigmer/data/`. The new `runtimes/` directory should not inherit this mess — it should follow a clean convention.

### The Fix — Recommended Layout

```
~/.stigmer/
├── config.yaml                          # (existing) CLI configuration
├── data/                                # (existing) runtime state
│   ├── logs/                            # (existing) component log files
│   ├── daemon.pid                       # (existing) stigmer-server PID
│   ├── workflow-runner.pid              # (existing) workflow-runner PID
│   ├── agent-runner.pid                 # (NEW) native agent-runner PID
│   ├── agent-runner-container.id        # (existing) Docker fallback
│   ├── workspace/                       # (existing) agent workspace
│   └── artifacts/                       # (existing) shared artifacts
├── runtimes/                            # (NEW) runtime environments
│   └── agent-runner/
│       └── <cli-version>/               # e.g., 0.42.0
│           └── <platform>/              # e.g., darwin-arm64
│               ├── python/              # python-build-standalone extracted
│               ├── venv/                # virtual environment with deps
│               ├── wheels/              # cached wheelhouse for reinstall
│               └── manifest.json        # environment metadata
```

**Design principles:**

- `**runtimes/` is a peer of `data/`**, both under `~/.stigmer/`. Runtimes are *tools* (immutable installations), not *state* (mutable data). Analogous to `/usr/local/` vs `/var/`.
- **Self-contained per version.** Python, venv, wheels, and manifest all live together. One `rm -rf` cleans a version completely.
- **Version = CLI build version.** The CLI pins everything: Python version, wheelhouse contents, agent-runner source. One CLI version = one reproducible environment.
- **Platform = `GOOS-GOARCH`.** Natural Go convention (`darwin-arm64`, `darwin-amd64`, `linux-amd64`, `linux-arm64`). The CLI already uses `runtime.GOOS` and `runtime.GOARCH`.
- **Logs and PID files stay in `data/`.** They are runtime *state*, not the runtime *environment*. This preserves the existing log rotation and PID management patterns from [daemon.go](client-apps/cli/internal/cli/daemon/daemon.go).

### manifest.json

Machine-readable metadata for the Go runtime manager to check whether the installed environment is current:

```json
{
  "cli_version": "0.42.0",
  "platform": "darwin-arm64",
  "python_version": "3.11.11",
  "python_build_standalone_tag": "20260115",
  "deps_lock_sha256": "a1b2c3...",
  "installed_at": "2026-03-01T05:00:00Z"
}
```

The Go runtime manager (T01.2) will read `manifest.json` to decide if bootstrapping is needed: if the `cli_version` matches the running CLI and the platform matches, the environment is ready. Otherwise, bootstrap a new one.

### Key Decisions to Confirm


| #   | Decision                     | Recommendation                                   | Rationale                                                                   |
| --- | ---------------------------- | ------------------------------------------------ | --------------------------------------------------------------------------- |
| 1   | Where does `runtimes/` live? | `~/.stigmer/runtimes/` (peer of `data/`)         | Tools vs state separation; clean break from existing inconsistencies        |
| 2   | What is the version key?     | CLI build version (`embedded.GetBuildVersion()`) | CLI orchestrates and pins everything; single source of truth                |
| 3   | Are wheels cached?           | Yes, inside the version directory (`wheels/`)    | Enables reinstall without re-download; self-contained cleanup               |
| 4   | Platform identifier format?  | `GOOS-GOARCH` (e.g., `darwin-arm64`)             | Go convention; CLI already uses `runtime.GOOS`/`runtime.GOARCH`             |
| 5   | Multiple versions on disk?   | Yes, old versions retained until cleanup         | Enables atomic upgrades and rollback; negligible disk cost (~400MB/version) |


### What This Does NOT Change

- Logs stay in `~/.stigmer/data/logs/agent-runner.log` (existing pattern)
- PID files stay in `~/.stigmer/data/` (existing pattern)
- Workspace stays in `~/.stigmer/data/workspace/` (existing pattern)
- Existing Temporal/Ollama paths are left as-is (separate tech debt)
- The naming mismatch between `daemon.go` (`agent-runner-container.id`) and `supervisor.go` (`agent-runner.containerid`) is noted as tech debt, not fixed here

### Surprise Found During Research

The `embedded` package ([embedded/extract.go](client-apps/cli/embedded/extract.go)) has dormant infrastructure for binary extraction that currently does nothing for agent-runner. The function `EnsureBinariesExtracted(dataDir)` is called on every daemon start. This is a natural hook point for T01.2 (runtime bootstrapping), but the decision of whether to repurpose this existing mechanism or create a new one belongs to T01.2, not T01.1. Flagging it here for awareness.
