# T05.22: Manifest Collection - Complete MCP Server Support

**Date**: February 4, 2026

## Summary

Completed Phase 5 Sub-task T05.22 by adding comprehensive MCP Server support to the CLI synthesis package. The synthesis infrastructure now fully supports all four resource types (Skills, MCP Servers, Agents, Workflows) with proper ordering, validation, and visualization. This completes the manifest collection foundation needed for Project Track SDK synthesis workflow.

## Problem Statement

The synthesis package was designed to read and process manifests generated by SDK programs, but it only supported three resource types: Skills, Agents, and Workflows. MCP Servers - a critical resource type for external tool integrations - were missing from the entire synthesis pipeline.

### Pain Points

- **Incomplete Resource Coverage**: MCP Server manifests (mcpserver-*.pb files) were not being read from synthesis output
- **Missing Dependency Support**: Agents depending on MCP Servers couldn't be properly ordered
- **Visualization Gaps**: Dependency graphs didn't show MCP Server resources
- **Inconsistent Architecture**: Only 3 of 4 resource types were supported in the synthesis workflow
- **Documentation Ambiguity**: The `Dependencies` field's purpose (local-only validation) wasn't clearly documented

## Solution

Enhanced the existing `synthesis` package to add first-class MCP Server support across all components:

### 1. Core Data Structures (result.go)
- Added `McpServers` field to `Result` struct
- Implemented `McpServerCount()` method for resource counting
- Updated `TotalResources()` to include MCP Servers
- Enhanced documentation to clarify that `Dependencies` field is for LOCAL CLI validation only (not sent to backend)

### 2. Manifest Reading (reader.go)
- Added reading of `mcpserver-*.pb` files from synthesis output directory
- Implemented `GetResourceID()` support for McpServer type (format: `mcp_server:{slug}`)
- Maintained pattern consistency with existing skill/agent/workflow readers
- Updated documentation to reflect all four resource types

### 3. Dependency Ordering (ordering.go)
- Updated `GetOrderedResources()` to include MCP Servers in topological sort
- Placed MCP Servers after Skills but before Agents (typical dependency order)
- Added MCP Server support to `ValidateDependencies()` for reference checking
- Updated `getResourceType()` to recognize `mcp_server:` prefix
- Implemented diamond shape and purple color (#f3e5f5) for MCP Server visualization

### 4. Visualization Enhancements
- **Mermaid Diagrams**: Added purple styling for MCP Server nodes
- **DOT Diagrams**: Implemented diamond shape for MCP Servers
- Updated both graph formats to properly display MCP Server dependencies

### 5. Build Configuration (BUILD.bazel)
- Added `//apis/stubs/go/ai/stigmer/agentic/mcpserver/v1:mcpserver` dependency to library target
- Added same dependency to test target for comprehensive testing

### Resource ID Format

MCP Servers use the format: `mcp_server:{slug}`

Examples:
- `mcp_server:github-api`
- `mcp_server:slack`
- `mcp_server:jira`

### Dependency Ordering

The topological sort now follows this order:

```
1. Skills (no dependencies)
2. MCP Servers (typically no dependencies)
3. Agents (may depend on Skills + MCP Servers)
4. Workflows (may depend on Agents)
```

Within each category, resources are ordered by their dependencies using Kahn's algorithm.

## Key Architectural Decision

### LOCAL vs BACKEND Dependencies

**CRITICAL DISTINCTION** now clearly documented:

```go
// Dependencies maps resource IDs to their dependencies.
// Format: {"agent:reviewer": ["skill:code-analysis", "mcp_server:github"], ...}
//
// IMPORTANT: This is for LOCAL CLI validation only (dry-run preview, cycle detection).
// Dependencies are NOT sent to the backend - the backend derives the dependency graph
// from ApiResourceReference fields via proto reflection. See Phase 5 architecture docs.
Dependencies map[string][]string
```

**Why this matters:**
- CLI uses dependencies.json for local validation (catch cycles early)
- Backend derives its own graph from proto fields (single source of truth)
- Prevents drift between CLI and backend dependency understanding
- Enables backend to work with manually-created resources (not just SDK-generated)

```go

// Dependencies (from dependencies.json):

```
