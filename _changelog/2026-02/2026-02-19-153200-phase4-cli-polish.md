# CLI Phase 4: Conversational Session Polish

**Date**: February 19, 2026

## Summary

Phase 4 completes the conversational agent UX in the Stigmer CLI. Three targeted improvements address the practical gaps left after Phase 2's conversational follow-up TUI: stream error recovery that doesn't kill the session, full conversation history when re-opening completed sessions, and a `--verbose` flag for execution-level debugging. Together, these make `stigmer run` a first-class conversational experience that handles the real-world rough edges of gRPC streaming and multi-turn sessions.

## Problem Statement

Phase 2 established the core pattern: agent executions belong to sessions, sessions support follow-up messages, and the TUI stays alive across multiple turns. Three gaps remained:

### Pain Points

- **Stream errors were fatal** — A transient gRPC disconnect sent `StreamErrorEvent`, set `m.done = true`, and killed the TUI. The user had to exit and manually run `stigmer run <session-id>` to re-attach. In a live conversational session, this was a jarring interruption even when the backend was perfectly healthy.
- **Re-opening a session lost history** — `stigmer run <session-id>` on a completed session fetched only the latest execution. Since each execution stores only its own turn's messages, only the last turn was visible. The entire prior conversation — every user message and agent response — was invisible.
- **No execution visibility for debugging** — When an agent behaved unexpectedly, there was no way to see execution boundaries, IDs, or phase transitions in the TUI. The `--debug` zerolog output covered CLI internals but not the conversation-level execution flow.

## Solution

Three targeted fixes, each following an existing pattern in the codebase:

1. **Stream error recovery** — Treat stream errors as recoverable terminal events in conversational mode. When `FollowUpFn` is set, both `StreamErrorEvent` and `handleStreamClosed` activate the input composer instead of setting `m.done = true`. The user sees the error and can send a follow-up (creating a new execution) or press Esc to exit. This mirrors the existing `DoneEvent` behavior from Phase 2.

2. **Resumable multi-execution session replay** — When re-opening a completed session, fetch all executions (not just the latest), build blocks from each in chronological order, and open a `NewResumable` TUI pre-populated with the full transcript and the input composer active. The conversation reads as a seamless transcript with no execution boundaries visible — consistent with the design decision to hide execution internals from the user.

3. **`--verbose` flag** — Added to `stigmer run` and `stigmer draft skill`. When enabled, execution IDs and phase transitions appear as system blocks in the TUI transcript. This is an explicit opt-in for debugging; the default remains a clean conversation view.

## Implementation Details

### Stream Error Recovery (`handle_events.go`)

The fix is a three-line conditional in two places — identical pattern to `DoneEvent` from Phase 2:

```go
// Before: always terminal
m.done = true

// After: terminal only in non-conversational mode
if m.cfg.FollowUpFn != nil {
    m.inputActive = true
    m.textarea.Focus()
} else {
    m.done = true
}
```

Applied to both `StreamErrorEvent` and `handleStreamClosed`. The guard `!m.done && !m.inputActive` in `handleStreamClosed` already prevents double-activation, so no additional state management was needed.

### Resumable Session Replay (`replay.go`, `run_session.go`)

Two new constructs in `replay.go`:

**`BuildSessionReplayBlocks`** — Takes a slice of executions in chronological order, calls `BuildReplayBlocks` on each, and concatenates into a single block list. No execution boundary markers; the transcript is seamless.

**`NewResumable`** — Counterpart to `NewReplay`. Creates a `Model` pre-populated with blocks and `inputActive = true`. Key difference from `New`: no `Events` channel, so `Init()` skips starting an event listener and the activity tick. The model is interactive but not streaming — until the user submits a follow-up, at which point `handleFollowUpStarted` wires in a fresh events channel.

`Init()` was updated to check `m.activeEvents == nil` rather than `m.isReplayMode()`. This distinction matters: `NewResumable` models have no events channel but are interactive (not read-only), so the `isReplayMode()` check — which also required `m.done == true` — would have incorrectly allowed `Init()` to try starting an event listener.

In `run_session.go`, `openSession` now fetches all executions with `execution.MaxPageSize`. Completed sessions call the new `resumeSession` function, which reverses the backend's newest-first ordering, builds the combined block list, creates a `NewResumable` model, and runs the program. The post-TUI logic (fetching final execution, displaying exit/detach line) is identical to `streamAgentExecution`.

### `--verbose` Flag (`model.go`, `handle_events.go`, `followup.go`, command layer)

`Config.Verbose bool` was added to the TUI model. Three places emit system blocks when verbose:

- `New()` — emits `"Execution: exec-xxx"` as the first block when the TUI starts
- `PhaseChangeEvent` handler — emits `"Phase: pending → in_progress"` on each transition
- `handleFollowUpStarted` — emits `"Follow-up execution: exec-xxx"` when a new execution starts

The flag is registered as `--verbose` / `-v` on both `stigmer run` and `stigmer draft skill`, and threaded through the full call chain: command → options struct → `routeRun` / `executeRun` → `runAgent` → `streamAgentExecution` → `executiontui.Config`. The `resumeSession` path threads it through `ResumableConfig.Verbose` → `Config.Verbose`.

## Benefits

- **Resilient conversational sessions** — Transient network hiccups no longer kill the TUI. Users can continue working without manual re-attachment.
- **Complete conversation history** — `stigmer run <session-id>` always shows the full conversation, regardless of how many turns it took. The UX matches what users expect from a conversational tool (Claude Code, ChatGPT, etc.).
- **Seamless session resumption** — A completed session re-opens ready for follow-up. No separate "resume" command, no mode switching.
- **Debuggable execution flow** — `stigmer run --verbose` shows which execution is running and how phases are transitioning, without polluting the default clean view.

## Impact

- **All `stigmer run` users** — Stream error recovery improves reliability in unstable network environments.
- **Multi-turn session users** — Full history makes `stigmer run <session-id>` genuinely useful for reviewing and continuing past conversations.
- **Agent developers and power users** — `--verbose` gives visibility into execution boundaries that were previously invisible without grepping server logs.
- **`stigmer draft skill` users** — Inherits the same `--verbose` flag; skill creation sessions can also be resumed with full history.
