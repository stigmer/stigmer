# ISO 8601 Wait Semantics - Structured Duration Support

**Date**: February 13, 2026

## Summary

Replaced the primitive `int32 seconds` field in `WaitTaskConfig` with a structured `Duration` message and absolute timestamp support, enabling human-readable wait specifications like "wait 1 week" or "wait until March 1st 9am". This completes Gap B6 from the durable agentic workflows roadmap and aligns the API with the platform's "weeks/months" positioning.

## Problem Statement

The wait task API forced users to perform mental arithmetic for common durations:
- "Wait 1 week" → calculate 604,800 seconds
- "Wait 2 hours" → calculate 7,200 seconds  
- "Wait until market open" → not possible

This violated **ubiquitous language** principles - users think in days, hours, and minutes, not raw seconds. It also created an architecture mismatch where the proto API was less capable than the underlying execution layer (Serverless Workflow SDK supports rich durations).

### Pain Points

- Mental arithmetic required for every wait specification
- No support for absolute timestamps ("wait until...")
- API surface contradicted the platform's "wait weeks/months" positioning
- Proto bottleneck - execution layer already supported rich durations
- Poor developer experience for a core workflow primitive

## Solution

Introduced a structured `Duration` message with fields for days, hours, minutes, seconds, and milliseconds, plus support for absolute timestamps via `google.protobuf.Timestamp`. Users now choose between:

1. **Relative durations** - wait N days/hours/minutes from now
2. **Absolute timestamps** - wait until a specific point in time

The proto uses a `oneof` to cleanly separate the two semantics, with CEL validation ensuring at least one duration field is non-zero.

## Implementation Details

### Proto Changes

**New Duration message:**
```protobuf
message Duration {
  uint32 days = 1;
  uint32 hours = 2;
  uint32 minutes = 3;
  uint32 seconds = 4;
  uint32 milliseconds = 5;
}
```

**Updated WaitTaskConfig:**
```protobuf
message WaitTaskConfig {
  oneof wait_type {
    Duration duration = 1;                    // Relative
    google.protobuf.Timestamp until = 2;     // Absolute
  }
}
```

**CEL validation:**
```protobuf
option (buf.validate.message).cel = {
  id: "duration.non_zero",
  expression: "this.days > 0 || this.hours > 0 || ..."
};
```

### Go Implementation

**Converter** - Handles both wait types:
```go
func (c *Converter) convertWaitTask(cfg *WaitTaskConfig) map[string]interface{} {
  switch w := cfg.GetWaitType().(type) {
  case *WaitTaskConfig_Duration:
    return map[string]interface{}{"wait": durationMap}
  case *WaitTaskConfig_Until:
    return map[string]interface{}{"wait": w.Until.AsTime().Format(time.RFC3339)}
  }
}
```

**Utility functions:**
- `ProtoToSDKDuration()` - Convert proto Duration to Serverless Workflow SDK Duration
- `ProtoToTimeDuration()` - Convert proto Duration directly to `time.Duration`

## Usage Examples

### Relative Duration - Wait 1 Week
```yaml
- waitForApproval:
    wait:
      duration:
        days: 7
```

### Composite Duration - 2.5 Hours
```yaml
- cooldownPeriod:
    wait:
      duration:
        hours: 2
        minutes: 30
```

### Absolute Timestamp - Market Open
```yaml
- waitUntilMarketOpen:
    wait:
      until: "2026-03-02T09:30:00Z"
```

### Go Usage via Utilities
```go
duration := &tasksv1.Duration{
  Days: 7,
  Hours: 12,
}
timeDuration := utils.ProtoToTimeDuration(duration)
// Result: 7 days + 12 hours = 180 hours
```

## Technical Decisions

### Structured Duration vs ISO 8601 Strings

**Decision**: Structured Duration message

**Rationale**:
- Type safety - proto validation at compile time
- SDK alignment - 1:1 mapping to `model.DurationInline`
- Self-documenting - all fields visible in IDE
- Parsing at edge - CLI/UI can convert ISO 8601 strings to structured form

### oneof for wait_type

**Decision**: Use `oneof` to separate relative and absolute semantics

**Rationale**:
- Clear distinction between "wait for" and "wait until"
- Prevents ambiguous state (both set)
- Follows proto best practices
- Makes validation straightforward

### Breaking Change Acceptable

**Decision**: Remove old `seconds` field completely

**Rationale**:
- No existing users (platform in development)
- Cleaner API for future
- Avoids technical debt of supporting both
- User explicitly approved breaking changes
