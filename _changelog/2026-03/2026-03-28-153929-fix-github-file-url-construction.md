# Fix GitHub File URL Construction in File Path Resolver

**Date**: March 28, 2026

## Summary

Fixed malformed GitHub blob URLs generated by the `@stigmer/react` SDK when rendering tool-call file paths in multi-workspace sessions. The resolver now correctly matches workspace entries even when tool-call paths embed an org prefix (e.g. `plantonhq/agent-fleet/...`), and includes a safety net that strips duplicate `org/repo` prefixes from the final URL.

## Problem Statement

When an agent session has multiple workspace entries (e.g. `mcp-server-planton` and `agent-fleet`), clicking a file path link in the execution thread navigated to a broken GitHub URL:

```
github.com/plantonhq/mcp-server-planton/blob/main/plantonhq/agent-fleet/mcp-servers/mcp-server-planton.yaml
```

The correct URL should have been:

```
github.com/plantonhq/agent-fleet/blob/main/mcp-servers/mcp-server-planton.yaml
```

### Pain Points

- File path links in the Console session view produced 404 pages on GitHub
- The wrong repository was selected for the URL (first entry fallback)
- The relative file path included a redundant org/repo prefix that duplicated what was already in the URL

## Solution

Two-layer defense in `sdk/react/src/execution/file-path-resolver.ts`:

1. **Smarter workspace matching** — `matchWorkspaceEntry` now scans all path segments for an entry name match instead of only checking the first segment. This handles tool-call paths that embed an org prefix before the workspace name.

2. **Duplicate-prefix safety net** — `resolveGitBrowseUrl` detects and strips a `relPath` that accidentally starts with the same `org/repo` already encoded in the git URL, preventing double-path URLs regardless of how the path arrives.

## Implementation Details

### `matchWorkspaceEntry` (Layer 1)

Previously iterated only the first path segment against entry names. Now splits the full path and scans each segment, matching the first entry name found at any depth. Segments before the match are stripped as the org prefix they represent.

### `resolveGitBrowseUrl` (Layer 2)

After computing `repoPath` from the git URL (e.g. `plantonhq/agent-fleet`), checks whether `cleanRelPath` starts with `repoPath + "/"`. If so, strips the redundant prefix before assembling the final URL.

### Test coverage

Added `sdk/react/src/execution/__tests__/file-path-resolver.test.ts` with 21 vitest cases covering:
- `classifyPath` — platform vs. workspace paths, leading-slash stripping
- `resolveGitBrowseUrl` — normal URLs, commit preference, HEAD fallback, non-GitHub hosts, duplicate org/repo stripping, partial-prefix non-stripping
- `resolvePathAction` — single entry, multi-entry first-segment match, multi-entry deep-segment match (the bug case), fallback, local path entries, platform paths, empty inputs

## Benefits

- File path links in the Console now navigate to the correct GitHub blob URL in multi-workspace sessions
- Backward-compatible — single-workspace sessions and first-segment matches continue to work identically
- Defense-in-depth prevents similar URL malformation even if upstream path formats change

## Impact

- **SDK consumers**: Any platform builder rendering `<FilePathLink>` or `<MessageThread>` with multi-workspace sessions will see correct GitHub links
- **Console users**: Clicking file paths in agent execution views now navigates to the right file on GitHub

## Related Work

- CLI equivalent (`buildHyperlinkedPath` in `client-apps/cli/pkg/toolrender/render_compact.go`) uses `file://` URIs and is unaffected
