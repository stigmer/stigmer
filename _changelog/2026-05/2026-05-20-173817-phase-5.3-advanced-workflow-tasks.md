# Phase 5.3: Advanced Workflow Tasks — wait, listen, run, emit_event, human_input

**Date**: May 20, 2026

## Summary

Implemented the remaining 5 advanced task types for the TypeScript workflow engine, completing Phase 5 of the CNCF Serverless Workflow rewrite. The engine now supports 16 executable task types — covering timers, event-driven signal gates, script/shell/child-workflow execution, CloudEvents emission, and human-in-the-loop approval gates — all while preserving the kernel's Temporal-agnostic architecture.

## Problem Statement

The TypeScript workflow engine (Phase 5.2) could execute structural tasks (set, switch, do, for, fork, try, raise) and external calls (http, grpc, llm, agent), but lacked the remaining CNCF DSL primitives needed for production workflows:

### Pain Points

- No timer/delay capability — workflows couldn't pause between steps
- No event-driven waiting — couldn't block on external signals or approvals
- No script execution — inline JS/Python transforms required full activities
- No child workflow composition — sub-workflow invocation was missing
- No HITL approval gates — interactive workflows were impossible

## Solution

Added 5 new task types following the established architectural pattern: kernel-side builders/executors that call opaque callbacks on `TaskExecutionContext`, with Temporal-specific implementations living in dedicated orchestrator files in the `workflows/` layer.

## Implementation Details

### New TaskExecutionContext callbacks

| Callback | Purpose | Temporal Primitive |
|----------|---------|-------------------|
| `sleep(ms)` | Timer delay | `@temporalio/workflow sleep()` |
| `listen(config)` | Signal event gate | `defineSignal` + `setHandler` + `condition` |
| `runCommand(config)` | Script/shell execution | `proxyActivities` → `child_process` |
| `runWorkflow(config)` | Child workflow | `executeChild` + `ParentClosePolicy` |
| `awaitHumanInput(config)` | HITL approval | Signal + timer selector |

### Task dispatch patterns

- `wait` and `run`: standard builder path via `task-factory.ts` → `createTaskBuilder`
- `listen` and `human_input`: special dispatch in `runSingleTask()` (same pattern as for/fork/try)
- `emit_event`: routes through existing `call:function` dispatcher → new case in activity

### Key design decisions

- **Listen: signal-only** — query/update event types deferred to Phase 6 (architecturally distinct, no production usage)
- **Human input reclassified at load time** — `call: "human_input"` → dedicated `HumanInputTaskDef` kind (needs signal handling, not simple activity proxy)
- **Run: all three modes** in one phase — script activity, shell activity, and child workflow orchestrator share validation logic
- **Emit event: envelope only** — CloudEvents 1.0 construction, no delivery (Phase 6)
- **Notification deferred** — needs provider registry infrastructure
