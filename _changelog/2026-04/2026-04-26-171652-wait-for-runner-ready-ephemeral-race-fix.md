# WaitForRunnerReady — Ephemeral Runner Readiness Gate

**Date**: April 26, 2026

## Summary

Added a `WaitForRunnerReady` local activity to the agent execution Temporal workflow that gates Python activity scheduling until the ephemeral runner's agent-runner process has connected to Temporal. This fixes a race condition where `ScheduleToStart` timeouts fired before the Daytona sandbox finished booting, causing execution failures with `RETRY_STATE_NON_RETRYABLE_FAILURE`.

## Problem Statement

Ephemeral runners are provisioned asynchronously via `DaytonaSandboxRunnerLauncher` — the Daytona sandbox is created and the Python worker is started *after* the Temporal workflow has already begun scheduling activities. The workflow's `EnsureThread` activity had a 1-minute `ScheduleToStartTimeout` that fired before any worker polled the per-runner queue, producing:

```
Activity with activityType='EnsureThread' failed: 'Activity task timed out'.
scheduledEventId=5, startedEventId=0,
retryState=RETRY_STATE_NON_RETRYABLE_FAILURE
```

### Pain Points

- Temporal treats `ScheduleToStart` timeouts as non-retryable — the 3-retry policy on `EnsureThread` never engaged
- The workflow had no awareness of the runner provisioning lifecycle
- Error messages pointed to "agent-runner not running" but the actual cause was a timing race
- A secondary Temporal SDK 1.31.0 state machine bug (`MARKER_COMMAND_CREATED->RECORD_MARKER`) was triggered during replay of the failed activity, causing the workflow to get stuck

## Solution

New `WaitForRunnerReady` local activity inserted as Step 0 in `executeGraphtonFlow`, before any Python activities are scheduled. The activity polls the Runner's phase from the store every 5 seconds until the runner reports `READY` via heartbeat.

### Scoping: Ephemeral Runners Only

The gate applies only to ephemeral runners (`stigmer.ai/ephemeral=true`). Persistent (user-managed) runners return immediately — they are validated at dispatch time by `RunnerDispatchService.resolveSessionBoundRunner`, and any subsequent unavailability is handled by the existing `ScheduleToStartTimeout`.

Design principle: the platform should only wait for things it controls. Ephemeral runners are system-managed; persistent runners are user-managed.

## Implementation Details

### Dual-Edition (Go + Java)

**Go (stigmer-server):**
- New file: `backend/services/stigmer-server/pkg/domain/agentexecution/temporal/activities/wait_for_runner_ready.go`
- Polls `store.GetResource` for the Runner, checks `stigmer.ai/ephemeral` label and phase
- Registered as local activity in `WorkerConfig.CreateWorker`
- Called via `workflow.ExecuteLocalActivity` in `executeGraphtonFlow`

**Java (stigmer-cloud):**
- New interface: `WaitForRunnerReadyActivity.java` (`@ActivityInterface`)
- New impl: `WaitForRunnerReadyActivityImpl.java` (polls `RunnerRepo.findById`)
- Registered as local activity in `AgentExecutionTemporalWorkerConfig`
- Called via `Workflow.newLocalActivityStub` in `InvokeAgentExecutionWorkflowImpl`

### Phase Semantics

| Phase | Behavior |
|-------|----------|
| PENDING | Keep polling (sandbox booting) |
| READY / BUSY | Return success |
| FAILED | Fail immediately ("provisioning failed") |
| STOPPED | Fail immediately ("stopped before ready") |

### Timeout

Local activity `StartToCloseTimeout` / `ScheduleToCloseTimeout` is 5 minutes — covers sandbox creation + image pull + Python boot + Temporal connection. The activity polls internally; no Temporal retries needed (`maxAttempts=1`).

### Additional Fix

Fixed misleading comment in `backend/services/agent-runner/worker/config.py` that documented the task queue format as `agent-runner:{runner-id}` — the actual format generated by `RunnerCreateHandler` is `runner:{id}`.

## Benefits

- **No more ScheduleToStart race**: The workflow waits for the runner to be ready before dispatching Python activities
- **Fast failure on provisioning errors**: If the sandbox fails, the workflow detects `FAILED` phase immediately instead of waiting for the full timeout
- **Visibility in workflow history**: "WaitForRunnerReady" appears as an explicit step, making it clear what the workflow is waiting for
- **No impact on persistent runners**: The gate returns immediately for non-ephemeral runners

## Impact

- **Dual-edition**: Changes in both stigmer (Go) and stigmer-cloud (Java), identical behavior
- **Ephemeral-only scope**: Persistent runners are unaffected
- **No proto changes**: `runnerId` was already in the workflow input
- **No agent-runner changes**: Python side is unaffected
- **No launcher changes**: `DaytonaSandboxRunnerLauncher` remains fire-and-forget

### Benchmark Finding

During investigation, benchmarked Daytona sandbox creation using the dev API key:
- `CreateSandboxFromImage` (current path): **1.75s** — Daytona internally resolves images to snapshots
- This confirms sandbox creation is not the bottleneck. The timeout was caused by the workflow scheduling activities before the `@Async` provisioning completed and the Python worker connected.
