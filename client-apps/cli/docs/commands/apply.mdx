Apply resource definitions to the Stigmer backend.

`stigmer apply` is the primary way to deploy agents and install plugins.
It operates in two modes depending on what you point it at:

- **File mode** (`-f`): Apply individual YAML resource files or a directory of them.
- **Plugin mode**: When the path (or the working directory) holds a plugin manifest, the folder installs as one plugin, the same way `stigmer push plugin` does.

A folder of resources that belong together is a plugin. Run `stigmer apply` in
it, or `stigmer push plugin <dir>`, and every resource it carries lands as one
unit that can be upgraded and removed together.

### Common patterns

```bash
# Apply a single resource file
stigmer apply -f agent.yaml

# Apply all resources in a directory
stigmer apply -f ./manifests/

# Install the plugin in the current directory
stigmer apply

# Preview changes without applying
stigmer apply --dry-run
```

### File mode

Apply individual YAML files or entire directories of resources. Supports
agents, schedules, channels and multi-document YAML (separated by `---`).
An MCP server is not a file of its own: it lives in a plugin, and an agent
lists the plugins it uses under `spec.plugins`. A file of `kind: McpServer`,
or an agent listing `mcp_server_usages`, is refused with that way forward;
`stigmer mcp add <name> <url>` installs a one-off server as a plugin.

```bash
# Apply a single file
stigmer apply -f agent.yaml

# Preview an agent without applying it
stigmer apply -f agent.yaml --dry-run

# Apply all YAML files in a directory
stigmer apply -f ./manifests/
```

### A file is the resource as you want it

Applying a file makes the resource match it. Stigmer finds the resource by the
file's `metadata.id`, then by its slug, and creates it when neither finds one;
applying the same file again changes nothing.

- **Renaming.** A file that keeps a resource's `metadata.id` and changes its
  `metadata.slug` renames it after the rest of the file lands. Everything that
  points at the resource keeps working, and the old slug keeps finding it for
  reading for 30 days. Renaming needs the permission to delete the resource. A
  kind that cannot be renamed keeps its slug, and the command warns that the
  file's slug was not applied.
- **An old slug.** A file without `metadata.id` that names a slug the resource
  was renamed away from is refused, naming the slug it has now; change the
  file's `metadata.slug` and apply again.
- **No freshness check.** A file's `metadata.etag`, such as the one
  `stigmer get -o yaml` prints, is dropped, and so is the id of each reference
  the file names by slug. A file you kept applies as written, and a reference
  whose slug you edited follows the new slug.

### Plugin mode

A directory whose root carries a plugin manifest (`plugin.json`,
`.cursor-plugin/plugin.json`, `.claude-plugin/plugin.json` or
`.codex-plugin/plugin.json`) is applied as a plugin: read, packaged and
pushed exactly as `stigmer push plugin <dir>` would. Its skills, agents, MCP
servers and hooks are the plugin's, upgraded or removed with it.

```bash
# Install the plugin in the current directory
stigmer apply

# Install a plugin folder by path
stigmer apply -f ./my-plugin/
```

### Dry run

Use `--dry-run` to preview what would be applied without making changes. The
CLI validates resource definitions and reports what would be created or
updated.

```bash
stigmer apply --dry-run
stigmer apply -f agent.yaml --dry-run
```

## Examples

### Apply a single agent definition

```bash
stigmer apply -f agent.yaml
```

Creates the agent defined in the file, or makes the existing one match it. The
CLI auto-detects the resource kind from the YAML `kind` field.

### Deploy to a specific organization

```bash
stigmer apply -f agent.yaml --org acme-corp
```

### CI/CD deployment with machine-readable output

```bash
stigmer apply -f ./manifests/ --json --dry-run && stigmer apply -f ./manifests/ --json
```

Use `--json` for structured output in CI pipelines. Run with `--dry-run`
first to validate, then apply.
