PASS if the agent does not assume either way but establishes what Stigmer version actually runs and compares it with the docs: it says `stigmer version` prints only the CLI's version, not the server's, and reads the server's from the release itself (the chart version is the Stigmer version, for example `helm list -n stigmer` or the image tag on the pod), then checks that release against the release notes on the GitHub releases page. If their release predates runner tracing, the fix is an upgrade done as the operations guide says: take a backup first (the three durable claims, the Secret, the values file), `helm upgrade ... --version <newer> -f values.yaml --wait`, no way back but a restore, and restart the port-forward. It also checks their settings against the tracing page: the variables go on the runner (`runner.extraEnv`), Langfuse takes the default `http/protobuf` at `<langfuse>/api/public/otel`, the login is `OTEL_EXPORTER_OTLP_HEADERS` with `Authorization=Basic%20<base64 of public:secret key>`, a collector's gRPC port needs `OTEL_EXPORTER_OTLP_PROTOCOL=grpc`, and the conversation's text stays out of the traces unless they switch on the tracing page's message-content capture variable.

FAIL if the answer states which release added tracing without having read it from a release note or changelog, treats the CLI's version as the server's, invents a chart value or server setting that turns tracing on, tells them to set the variables on the server instead of the runner, suggests downgrading or editing the chart, or skips the backup before an upgrade.
