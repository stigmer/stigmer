# LangGraph streamEvents v2 to v3 migration for Stigmer

## Executive Summary

LangGraph’s current JavaScript guidance is clear on the big picture: for new application code, the recommended in-process streaming model is **event streaming** via `streamEvents(..., { version: "v3" })`, which was introduced in **LangGraph v1.2**. The v3 API returns a **run stream object** rather than a flat callback-event iterator, and that run object can be consumed as a raw protocol-event stream or through typed projections such as `messages`, `values`, `output`, `subgraphs`, `lifecycle`, `interrupts`, and product-specific projections like LangChain `toolCalls` and deepagents `subagents`. citeturn34view0turn15view0turn35view5turn35view3turn35view4turn27view0

The most important correction to your current mental model is this: in the current public JavaScript docs and `GraphRunStream` source, **there is no built-in `run.updates` accessor** on the in-process v3 stream. The raw **`updates` channel does exist**, but you access it by iterating the run itself as `ProtocolEvent`s or by adding a custom transformer. Likewise, **`run.subagents` is not a core LangGraph projection**; core LangGraph exposes `run.subgraphs`, while deepagents adds `run.subagents` via its own native `createSubagentTransformer`. citeturn17view0turn35view5turn35view3turn35view4turn27view0turn25view4

For Stigmer specifically, the most robust migration pattern is not “replace one flat loop with several projection loops and hope ordering still works”. It is: **keep one authoritative loop over the raw v3 protocol stream** for Temporal heartbeats, cancellation, stall detection, approval/HITL state, inline artifact publishing, and protobuf status mapping; then separately **await `run.output`** to recover the final merged state, which is the only official v3 surface that can plausibly solve your `structuredResponse` visibility problem. LangGraph documents `run.values` as full state snapshots after each step and `run.output` as the final state; the docs do **not** explicitly mention `UntrackedValue`, so “this definitely includes `structuredResponse`” is still an inference rather than a formal guarantee, but it is the strongest officially-supported path I found. citeturn16view4turn35view5turn35view3

There is also a practical caution for your exact stack. As of May 2026, there are open or recently-closed ecosystem issues in the same version family you are using: one deepagents.js issue reports that v3 can leak tool results into `run.messages`, return serialised `ToolMessage`s rather than raw tool outputs, and trigger `INVALID_TOOL_RESULTS` on fresh threads; another langchainjs issue, filed against `@langchain/core 1.1.47` and `deepagents 1.10.2`, reports a `ChatModelStream` assembly bug where a blank text block followed by a `tool_call_chunk` can drop `AIMessage.tool_calls` and halt tool execution. Those two reports materially increase migration risk for exactly the sort of ReAct-plus-tools platform you are building. citeturn24view0turn42view1turn41view1

My overall recommendation is therefore **yes, migrate to v3**, but **do it in a feature-flagged, protocol-first way**, with v2 fallback preserved until you have passed a regression matrix covering tool calls, subagents, interrupts, reasoning blocks, and structured output extraction. The user-value upside is real: final merged state access, better lifecycle/HITL signals, cleaner subagent streams, explicit content-block semantics, and future-proof extension channels. But a blind swap at your current versions would be harder to justify operationally. citeturn15view0turn15view1turn17view0turn24view0turn41view1

## Detailed Findings

**What v3 actually returns.** Official v3 examples show `graph.streamEvents(input, { version: "v3" })` returning a run object that can be used in several ways at once. The run object itself is an async iterable of raw `ProtocolEvent`s. On top of that raw stream, core LangGraph exposes `messages`, `values`, `output`, `subgraphs`, `lifecycle`, `interrupts`, `interrupted`, `abort(reason)`, `signal`, `messagesFrom(node)`, and `extensions`. In source, `run.values` is a dual interface: it is both an async iterable of state snapshots and a promise-like that resolves to the final state; `run.output` is the final-state promise; `run.subgraphs` filters discovered nested graph handles; `run.messages` lazily wires a messages transformer and replays buffered events so earlier message events are not lost if the getter is accessed late. citeturn15view0turn18view0turn35view5turn35view0turn35view3turn35view1turn35view4

**Important correction.** The current public JS docs/source do **not** show a built-in `run.updates` getter on `GraphRunStream`. What they do show is an `updates` **channel** in the raw protocol, described as “per-node state deltas”. The low-level stream-mode type published by the JS SDK is shaped as `{ event: "updates", data: { [node: string]: UpdateType }, id?: string }`, while the corresponding values stream event is `{ event: "values", data: StateType, id?: string }`. In other words: the `updates` concept exists, but in v3 you should treat it as a raw protocol channel or make your own transformer-backed projection. citeturn17view0turn19search1turn19search0turn35view5

**Deepagents-specific correction.** Core LangGraph gives you `run.subgraphs`; deepagents gives you `run.subagents`. In deepagents.js source, `createDeepAgent` compiles the agent with `createSubagentTransformer([])`, and that transformer is explicitly documented as a **native** projection whose `subagents` handle lands directly on the `GraphRunStream` instance. The same source defines a `SubagentRunStream` with `name`, `taskInput`, `output`, `messages`, `toolCalls`, and nested `subagents`. That means your assumption that “v3 has `run.subagents`” is only true **because deepagents adds it**, not because `GraphRunStream` has that property generically. citeturn25view4turn27view0

**How the v2 callback events map to v3.** The mapping is conceptually straightforward, but it is not one-to-one because v3 is a **channel-and-content-block protocol**, not a runnable-span callback log. Your current `on_chat_model_stream` maps most closely to the v3 `messages` channel, especially `content-block-delta` events with `text-delta` and `reasoning-delta` payloads, or to the typed `run.messages` projection and its `.text` and `.reasoning` iterables. Your `on_chat_model_end` maps to `message-finish`, plus the typed `message.output` and `message.usage` helpers. Your `on_tool_start` maps to the `tools` channel’s `tool-started` event and, in LangChain agent streams, the `run.toolCalls` projection. Your `on_tool_end` maps to `tool-finished` or `tool-error`, again also visible via `run.toolCalls` through `output`, `status`, and `error`. Your ignored `on_chain_start` / `on_chain_end` do not have a single v3 equivalent; the closest replacement is a combination of `lifecycle` events and `values` / `updates` state signals. Your ignored `on_llm_end` is effectively subsumed into `message-finish` and the final `message.output`. citeturn20search3turn17view0turn10view3turn43view0turn15view1turn16view0turn35view3

**What is genuinely new in v3.** Compared with callback-style v2, v3 adds a real protocol envelope with a stable sequence number, namespace path, timestamp, node attribution, channel name, and typed channel payload. It also introduces raw channels for `lifecycle`, `input`, `checkpoints`, `tasks`, `custom`, and named extension channels (`custom:<name>`), plus explicit message/content-block boundaries and optional streaming tool output via `tool-output-delta`. For an agent platform, that is a notable increase in observability surface. citeturn7view1turn17view0turn10view3turn43view0turn43view1turn11view1

**Event shape differences.** The v3 envelope is a `ProtocolEvent` with `type: "event"`, a monotonic `seq`, a `method` channel name, and `params` containing `namespace`, `timestamp`, optional `node`, and channel-specific `data`. On the `messages` channel, `data` is one of `message-start`, `content-block-start`, `content-block-delta`, `content-block-finish`, `message-finish`, or model-call `error`. Token streaming is represented by content-block deltas, not by a generic “stream” callback name. Reasoning is first-class through `reasoning-delta`, and typed message handles also expose `message.reasoning`. Usage is attached to `message-finish` as `usage`, while the typed message projection offers `message.usage` and `message.output`; the docs also note that `message.output` contains the final AI message including provider-specific content blocks. On the `tools` channel, `tool-started` includes a tool call ID, tool name, and optional input; `tool-finished` includes output; `tool-error` includes the failure message; and `tool-output-delta` is available for streaming tools. citeturn7view1turn10view0turn10view3turn43view0turn43view1turn15view1turn16view0

**One subtle ecosystem inconsistency is worth flagging.** The agent-protocol spec documents tool event fields in **camelCase** such as `toolCallId` and `toolName`, but some current JS examples and deepagents source still read or emit snake_case-like names such as `tool_name` and `tool_call_id`. That means your adapter layer should normalise field names defensively rather than assuming a single stable casing pattern everywhere. citeturn43view0turn17view3turn28view5

**Recommended consumption pattern for Stigmer.** Official docs show two idioms: consume typed projections concurrently with `Promise.all`, or iterate the run object itself for raw protocol events. For your architecture, the second pattern is the stronger fit because you already centralise scheduling, heartbeats, cancellation checks, approval pauses, writeback triggers, and protobuf status accumulation in one stream-processing loop. In v3, you can keep that architecture by iterating `for await (const event of run)`, switching on `event.method`, and then awaiting `run.output` once the stream completes. Use typed projections only where they offer real leverage, such as `run.toolCalls` for tool status promises or `run.subagents` to expose deepagents task delegation with less manual namespace parsing. Multiple projections can be read concurrently without consuming each other’s data. citeturn16view4turn18view0turn15view0turn15view1

```ts
const run = await agentGraph.streamEvents(input, {
  version: "v3",
  configurable,
  recursionLimit,
});

const heartbeatTimer = setInterval(() => heartbeat(), 2000);

try {
  for await (const event of run) {
    if (await isCancelledFn()) {
      run.abort(new Error("Cancelled by platform"));
      break;
    }

    touchStallWatchdog();

    switch (event.method) {
      case "messages":
        statusBuilder.onMessageProtocolEvent(event);
        break;
      case "tools":
        statusBuilder.onToolProtocolEvent(event);
        break;
      case "lifecycle":
        statusBuilder.onLifecycleEvent(event);
        break;
      case "input.requested":
        statusBuilder.onInterruptEvent(event);
        break;
      case "updates":
        statusBuilder.onStateUpdateEvent(event);
        break;
      case "custom":
      default:
        statusBuilder.onOtherEvent(event);
        break;
    }

    maybeFlushStatus();
  }

  const finalState = await run.output;
  const structuredResponse = (finalState as any).structuredResponse;
  await finishPostStreamWork(finalState);
} finally {
  clearInterval(heartbeatTimer);
}
```

**Heartbeat and keep-alive implications.** v3 does not remove your ability to heartbeat per event, because the run itself is still an async iterable. What v3 does change is the event model: some information now appears only at node or content-block boundaries, and `tool-output-delta` is explicitly optional. That means a silent long-running tool can still produce long event gaps. I did not find any official maximum-gap or batching guarantee, so for Temporal compatibility you should keep your current independent timer-based heartbeat and stall timeout rather than relying exclusively on event arrival cadence. That is especially important around large tools, synchronous file operations, and HITL pauses. citeturn18view0turn43view0

**Cancellation and interruption semantics.** `GraphRunStream` has a documented `abort(reason?)` method and exposed `signal: AbortSignal`. For HITL, v3 is significantly better than callback v2: the run has `interrupted` and `interrupts`, and the raw protocol includes `input.requested` events with an `interruptId` and opaque payload. The docs show resuming with `new Command({ resume: ... })` and calling `graph.streamEvents(...)` again. In practice, that gives you cleaner modelling for approval-gate UIs than inferring “waiting” from ad hoc tool-start rules alone. citeturn35view1turn18view0turn43view1turn12view5

**Error handling in v3.** The public materials support three layers of failure signalling. Tool-level failures are on the `tools` channel as `tool-error`. Model-call failures can appear as `messages` channel `error` events. Run- or subgraph-level failures appear on the `lifecycle` channel as `failed`, optionally with error text and checkpoint metadata, and `run.output` is documented to reject if the run fails. What I did **not** find was a separate dedicated “error stream”, or an explicit documented guarantee about whether consumers of `for await (const event of run)` will always observe a thrown exception versus graceful stream termination plus rejected projections. Treat that iterable-level behaviour as an implementation detail and test it explicitly in your Temporal worker. citeturn43view0turn43view1turn11view1turn35view3

**Structured output in v3.** The official guarantee is that `run.values` streams **full state snapshots after each step** and `run.output` resolves to the **final state**. The source confirms that `run.output` is simply the final `values` promise. That is enough to say that v3 is fundamentally more suitable than callback-style v2 for retrieving graph state. However, I did **not** find any official documentation that explicitly mentions `UntrackedValue`, `Annotation` without reducers, or `structuredResponse` specifically. So the strongest defensible statement is: if deepagents writes `structuredResponse` into the live in-memory state before the run completes, then `run.output` is the official v3 surface most likely to expose it, whereas `getState()` and checkpoint-derived APIs will not help because they are checkpoint-oriented by construction. That is a strong inference from the documented architecture, not an explicit LangGraph contract. citeturn16view4turn35view5turn35view3

**Alternatives to waiting for `run.output`.** If you want the structured response as soon as it appears, two v3-native patterns are available. The first is to watch `run.values` snapshots and react when the final node has written `structuredResponse`. The second is to add a custom transformer that listens to the `values` channel and emits a named extension event the moment `structuredResponse` becomes non-null, for example `custom:structuredResponseReady`. LangGraph’s transformer system is explicitly designed for this sort of application-specific projection, and named `StreamChannel`s can forward projection events into the main protocol stream while also exposing a local handle under `run.extensions`. citeturn16view4turn17view2turn17view3turn35view4

**Whether `generate_structured_response` node events become visible.** The public docs do not document that node by name, so I cannot state this as a contract. What the docs and source do show is that raw protocol events are node-scoped, that message events can carry `node` attribution, and that `messagesFrom(node)` exists specifically to filter messages from a given graph node. The deepagents native subagent transformer I inspected is additive and returns `true` from `process`, so it does not suppress the original event log. On that basis, I would treat visibility of a `generate_structured_response` model call in v3 as **possible and testable**, but still **not guaranteed by published docs**. citeturn17view0turn35view3turn35view0turn17view1turn30view0

**What else v3 gives you that is worth exposing to users.** First, `lifecycle` gives you a real run/subgraph/subagent state machine (`started`, `running`, `completed`, `failed`, `interrupted`) instead of approximating phases from callback events. Second, lifecycle `cause` can explain why a child scope started; the protocol spec explicitly calls out deepagents’ `SubagentTransformer` as the producer of tool-call-based causation edges, which is exactly what a delegation-aware UI wants. Third, `subgraphs` and deepagents `subagents` let you present nested agent activity as a tree rather than as opaque namespace strings. Fourth, raw `updates` and `values` give you state deltas and snapshots suitable for richer progress panels. Fifth, `checkpoints` and `tasks` channels are available for advanced debugging, time-travel, and low-level execution analysis. Sixth, `custom` and `custom:<name>` give you a principled way to surface retrieval progress, artifact publication, git-writeback milestones, or domain events to both local and remote consumers. citeturn17view0turn11view1turn43view2turn27view0turn29view2turn16view4turn17view2turn17view3

**Subagent streaming specifically.** Deepagents’ current JS source correlates root-level `task` tool calls into `SubagentRunStream` objects, resolves subagent outputs either from task tool completion or, for child namespaces, from the latest `values` snapshot plus terminal `lifecycle`, and routes child `messages` and `tools` events into per-subagent channels. Concretely, that means you can show: which subagent was spawned, the task description used to spawn it, its message stream, its nested tool calls, and its final state. Because message handles expose `usage`, you can also derive **per-subagent token usage** by aggregating `message.usage` inside each subagent stream. citeturn27view0turn29view1turn29view2turn29view3turn29view5turn15view1

**Deepagents stream-transformer behaviour.** The deepagents native transformer I inspected is not a filter in the harmful v2 sense you described. It is an observational transformer that adds a `subagents` projection while returning `true` from `process`, meaning it keeps the original protocol events visible. That matters: it means v3’s deepagents integration is designed to be additive and composable. The broader LangGraph transformer contract does allow transformers to return `false` and suppress original events, but the docs explicitly frame that as something to use sparingly. So the practical advice is to work **with** the v3 transformer system, not around it, and avoid any custom transformer that drops original events unless you have a very specific reason. citeturn17view1turn17view2turn30view0

**Performance and operational characteristics.** I did not find any official benchmark comparing callback-v2 and event-streaming-v3 latency, throughput, or memory use. What the docs and source do show is the mechanism: v3 normalises Pregel stream output into protocol events, routes each event through a transformer pipeline, stores it in the run stream unless suppressed, and can replay buffered events for projections that are attached later. That architecture almost certainly means **more CPU work and some additional buffering** compared with a single flat callback iterator, especially on token-heavy runs and when you attach several projections. The payoff is that you gain typed projections, replay safety for lazily-attached consumers, and much richer structure. In short: expect some overhead, but no published numbers. citeturn15view0turn17view1turn17view2turn35view0

**Mock testing with v3.** Your mock LLM infrastructure does not need to emit “v3-formatted events” itself. ## Migration Risk Assessment

The highest-risk migration issue is **tool-call correctness in your exact version family**. The deepagents.js issue filed on 12 May 2026 reports a v3 path that leaks tool results into `run.messages`, returns serialised `ToolMessage`s from `toolCall.output`, and can end in `INVALID_TOOL_RESULTS`; the langchainjs issue filed on 21 May 2026 reports a `ChatModelStream` bug in `@langchain/core 1.1.47` and `deepagents 1.10.2` where blank text followed by `tool_call_chunk` can erase `AIMessage.tool_calls` and stop tool execution. I would rate this **high likelihood / high impact** for Stigmer because your platform depends on correct tool orchestration, tool timelines, and post-tool writeback hooks. citeturn24view0turn42view1turn41view1

The next risk is **API-surface mismatch**. If you migrate assuming `run.updates` and core `run.subagents` exist as built-ins, you will spend time debugging the wrong abstraction. The present source/docs support `run.subgraphs` in core, `run.subagents` in deepagents, and raw `updates` only. I would rate this **high likelihood / medium impact**: it will not corrupt runs, but it can derail the implementation plan and expand scope. citeturn17view0turn35view5turn27view0turn25view4

A more nuanced risk is **structured-response certainty**. v3 is clearly the right direction because it exposes final state rather than only callback spans, but the public docs do not promise that non-checkpointed `UntrackedValue` fields are always included. I would rate this **medium likelihood / high impact**: the most likely outcome is that your hypothesis is correct, but because the guarantee is inferential rather than explicit, you should verify it on real deepagents runs before declaring the migration complete. citeturn16view4turn35view3turn35view5

There is also **operational risk around heartbeat cadence**. v3 still supports event-driven loops, but the protocol does not guarantee short gaps, and `tool-output-delta` is optional. If you changed Temporal heartbeat policy to be event-only, long silent tools or model pauses could make the worker look unhealthy. I would rate this **medium likelihood / medium impact**, with a straightforward mitigation: keep your independent timer heartbeat. citeturn18view0turn43view0

Finally, there is **documentation and field-shape inconsistency risk**. The current ecosystem shows inconsistencies around feature availability, event field naming, and frontend surfaces. I would rate this **medium likelihood / medium impact**. It will not usually break the backend run, but it can produce brittle adapters and UI regressions unless you normalise protocol fields and pin behaviour with tests. citeturn43view0turn17view3turn28view5turn41view0turn20search16

## Recommended Migration Strategy

Start with a **feature-flagged v3 adapter** rather than a wholesale replacement. The first cohort should be executions that request structured output, because that is where v3’s final-state access has the clearest user-value advantage. Keep the current v2 callback path available as a fallback for ordinary chat/tool runs until you have cleared the known v3 regressions in your environment. This is consistent with the official recommendation to prefer v3 for new app code, while also reflecting the concrete May 2026 workaround guidance from the deepagents.js issue. citeturn34view0turn24view0turn42view1

Rebuild the `StatusBuilder` against **raw `ProtocolEvent` envelopes**, not against the higher-level projection helpers. In Stigmer’s case, the authoritative event loop should remain a single ordered stream so that heartbeats, cancellation checks, stall detection, approval gates, artifact publishing, and writeback hooks all observe the same sequence. Use `event.method === "messages"` to reconstruct assistant text and reasoning blocks, `event.method === "tools"` to drive tool lifecycle, `event.method === "lifecycle"` for run/subgraph status, and `event.method === "input.requested"` for approval/HITL state. Then use `await run.output` only once, at the end, to capture the final merged state and look for `structuredResponse`. That gives you the best of both worlds: strict ordering during execution, plus structured final-state access after completion. citeturn18view0turn17view0turn35view3turn16view4

Preserve your existing **timer-based heartbeat and stall monitors**. V3 does not obsolete those controls. Instead, treat each protocol event as an opportunity to refresh the “last activity” timestamp, while the heartbeat timer continues on its own cadence and `run.abort()` is used for cancellation or STOP requests. The run’s documented `AbortSignal` and `abort(reason)` API make that a clean fit for Temporal cancellation and graceful termination handling. citeturn35view1turn18view0

Add two small **custom transformers** early. The first should watch the `updates` channel and expose a typed `run.extensions.stateUpdates` stream, because core `GraphRunStream` does not give you `run.updates` out of the box. The second should watch `values` and emit a named channel when `structuredResponse` first appears, so your backend can surface structured-output readiness before the whole run completes if needed. LangGraph’s documented transformer contract and named `StreamChannel` mechanism are designed for exactly these platform-specific projections. citeturn17view2turn17view3turn35view4

Treat **subagents as a first-class UI concept** during the migration. Because deepagents 1.10.2 compiles in `createSubagentTransformer([])`, you can consume `run.subagents` to expose delegation trees, per-subagent messages, per-subagent tool calls, and task descriptions without manually parsing every namespace yourself. That is a higher-value evolution of your current timeline UI than simply reproducing the v2 behaviour. citeturn25view4turn27view0turn29view1turn29view5

Before broad rollout, run a **regression matrix** that specifically covers: a normal ReAct tool-call turn; long-running silent tools; Anthropic reasoning blocks; approval/HITL interrupts; structured-output runs; parent-plus-subagent runs; blank leading text followed by tool-call chunks; tool-output streaming; and a fresh-thread tool call with concurrent `run.messages` plus `run.toolCalls`. Those last two are not theoretical edge cases; they are explicitly represented in current ecosystem bug reports. citeturn24view0turn41view1

Once the adapter is stable, roll forward by **user-visible capability**, not by internal purity. In practical terms: structured output first, then lifecycle/HITL improvements, then subagent visibility, then optional state-diff and checkpoint/task panels. That sequence gets the highest user value early while reducing the blast radius of the trickier protocol edges. citeturn17view0turn11view1turn27view0

## Opportunities Inventory

The single highest-value opportunity is **final merged state access**, especially if it solves your structured-output gap. Even if you decide not to surface the entire state object to end users, your backend should start storing the final `run.output` for every v3 execution. That gives you a durable record of the actual completed state rather than only the checkpointed subset and callback-event reconstruction. citeturn16view4turn35view3turn35view5

The next highest-value opportunity is **accurate lifecycle and interrupt modelling**. Today, Stigmer infers phases such as “waiting for approval” largely from tool-based heuristics. V3 gives you explicit `lifecycle` status transitions and `input.requested` interrupt payloads, plus a boolean `interrupted` and collected `interrupts`. That should let you present cleaner waiting/paused/resumed states and better approval UX. citeturn11view1turn18view0turn43view1

Third, you should capture and expose **delegation as a tree**, not just as tool calls. Deepagents’ `run.subagents` projection gives you subagent name, task input, messages, nested tool calls, and output. Combined with lifecycle `cause`, that lets you show which parent tool call spawned which child run, which subagent is currently active, and what work it was assigned. const run = await agentGraph.streamEvents(input, {

```ts
// Wrong for v3 in @langchain/langgraph@1.3.2
agentGraph.streamEvents(input, config, { version: "v3" });
```

## 1.2 Deep Agents additions

For Deep Agents, the v3 run is effectively a `DeepAgentRunStream`: LangChain agents add `run.toolCalls`, and Deep Agents adds `run.subagents`.

Deep Agents docs say `stream.subagents` gives one stream handle per delegated `task` call, with each subagent exposing `.messages`, `.toolCalls`, `.values`, `.subagents`, and `.output`. const run = await agentGraph.streamEvents(input, {

```ts
for await (const event of run) {
```

## 1.3 Raw v3 `ProtocolEvent` shape

The raw stream event envelope is:

```ts
interface ProtocolEvent {
  readonly type: "event";
  readonly seq: number;
  readonly method: string;
  readonly params: {
    readonly namespace: string[];
    readonly timestamp: number;
    readonly node?: string;
    readonly data: unknown;
  };
}
```

LangGraph docs emphasize that `seq` is strictly increasing within a run and should be used for ordering; `timestamp` is wall-clock and can drift. ([LangChain Docs][2])

## 1.4 v3 channels and event families

LangGraph event streaming defines raw channels such as `values`, `updates`, `messages`, `tools`, `lifecycle`, `checkpoints`, `input`, `tasks`, `custom`, and `custom:<name>`. ([LangChain Docs][2]) Source inspection of `@langchain/langgraph@1.3.2` shows the v3 implementation requests these underlying Pregel modes by default: `values`, `updates`, `messages`, `tools`, `custom`, and `tasks`; it synthesizes lifecycle and checkpoint protocol events through transformers/metadata rather than requesting raw `debug`.

### Messages

The v3 `messages` channel is content-block-centric. The event `data.event` is one of:

* `message-start`
* `content-block-start`
* `content-block-delta`
* `content-block-finish`
* `message-finish`

The docs explicitly say this makes token streaming, reasoning blocks, tool-call blocks, and multimodal content explicit; `message-finish` may include token usage. ([LangChain Docs][2])

For raw token handling:

```ts
if (event.method === "messages") {
  const data = event.params.data as any;

  if (data.event === "content-block-delta") {
    const delta = data.delta ?? {};

    if (delta.type === "text-delta") {
      statusBuilder.appendText(delta.text ?? "");
    }

    if (delta.type === "reasoning-delta") {
      statusBuilder.appendThinking(delta.reasoning ?? "");
    }

    if (delta.type === "block-delta") {
      // Tool call args, provider-specific block fields, etc.
      statusBuilder.appendToolCallArgumentDelta(delta.fields);
    }
  }

  if (data.event === "message-finish") {
    statusBuilder.finishMessage({
      usage: data.usage,
      responseMetadata: data.responseMetadata,
    });
  }
}
```

For ergonomic consumption, LangChain agent docs say `stream.messages` yields message streams exposing `.text`, `.reasoning`, `.toolCalls`, `.output`, and `.usage`. ([LangChain Docs][5])

### Tools

The raw `tools` channel uses:

* `tool-started`
* `tool-output-delta`
* `tool-finished`
* `tool-error`

LangGraph docs say tool events are correlated by tool call ID so they can be joined back to originating tool-call content blocks. ([LangChain Docs][2]) Low-level streaming docs also document the underlying tool lifecycle events as `on_tool_start`, `on_tool_event`, `on_tool_end`, and `on_tool_error`. ([LangChain Docs][4])

Mapping from v2 to v3:

| v2 callback event | v3 raw protocol event                                          | Notes for Stigmer                                                                                     |
| ----------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `on_tool_start`   | `event.method === "tools"` and `data.event === "tool-started"` | Create tool record, evaluate approval policy, enter `WAITING_FOR_APPROVAL` if needed.                 |
| `on_tool_event`   | `data.event === "tool-output-delta"`                           | New opportunity: stream progress from async-generator tools.                                          |
| `on_tool_end`     | `data.event === "tool-finished"`                               | Mark complete, persist output, trigger inline artifact publishing/writeback for file-modifying tools. |
| `on_tool_error`   | `data.event === "tool-error"`                                  | Mark failed, preserve error message.                                                                  |

For agent-level ergonomics, LangChain agent docs say `stream.toolCalls` streams tool execution lifecycle, inputs, output deltas, final output, and errors. ([LangChain Docs][5]) Use it for convenience, but keep raw `tools` events for exact ordering and immediate artifact/writeback triggers.

### Values

`values` are full state snapshots. Docs define `values` as “full state after each step” and `stream.values` as state snapshots. ([LangChain Docs][4])

For Stigmer:

* Do not persist every `values` snapshot as a user status update.
* Do use `run.output` for the final state.
* Optionally sample/diff `values` for debugging or developer-mode traces.

### Updates

`updates` are per-node state deltas. Docs say `updates` stream state updates after each step, and multiple updates in the same step are streamed separately. ([LangChain Docs][4])

In source for `@langchain/langgraph@1.3.2`, the v3 converter normalizes updates into:

```ts
{
  node: string,
  values: Record<string, unknown>
}
```

For Stigmer:

* Use `updates` for node progress, graph routing, and structured-output early detection.
* Do not assume `run.updates`; filter raw events.

### Lifecycle

Lifecycle raw events include `started`, `running`, `completed`, `failed`, and `interrupted`, with optional graph name, error, and cause. ([LangChain Docs][2])

Use these to clean up phase heuristics:

* root `running` → `IN_PROGRESS`
* `interrupted` → `WAITING_FOR_APPROVAL` or `PAUSED`, depending on interrupt payload
* `completed` → only after post-stream artifact/writeback completion
* `failed` → `FAILED`
* STOP/cancel path → `TERMINATED`

### Checkpoints

Docs describe a `checkpoints` channel as lightweight checkpoint envelopes for branching and time travel. ([LangChain Docs][2]) In `@langchain/langgraph@1.3.2` source, v3 does not request the raw `checkpoints` stream mode; it emits lightweight checkpoint protocol events adjacent to `values` when checkpoint metadata is present.

For Stigmer, checkpoint envelopes are useful for:

* developer trace UIs,
* reproducing a run segment,
* correlating UI state with resumable LangGraph thread state.

### Tasks

Docs identify `tasks` as Pregel task creation/result events. ([LangChain Docs][2]) In practice, this is a lower-level graph-runtime signal. Capture it in debug traces, not necessarily end-user UI.

### Custom and `custom:<name>`

Docs say `custom` carries user-defined payloads and custom transformers can expose application-specific projections under `stream.extensions`. ([LangChain Docs][2]) This is where Stigmer should eventually put native artifact/writeback/usage projections once v3 parity is proven.

# 2. Migration patterns and best practices

## 2.1 Recommended consumption architecture

Do **not** try to make v3 look exactly like v2. Instead, introduce a v3-normalized internal event model.

Recommended architecture:

```ts
type StigmerRunEvent =
  | { kind: "message_start"; seq: number; namespace: string[]; node?: string; messageId?: string }
  | { kind: "text_delta"; seq: number; namespace: string[]; node?: string; text: string }
  | { kind: "reasoning_delta"; seq: number; namespace: string[]; node?: string; text: string }
  | { kind: "message_finish"; seq: number; namespace: string[]; node?: string; usage?: unknown; responseMetadata?: unknown }
  | { kind: "tool_started"; seq: number; namespace: string[]; callId: string; name: string; input: unknown }
  | { kind: "tool_output_delta"; seq: number; namespace: string[]; callId: string; delta: string }
  | { kind: "tool_finished"; seq: number; namespace: string[]; callId: string; output: unknown }
  | { kind: "tool_error"; seq: number; namespace: string[]; callId: string; message: string }
  | { kind: "state_update"; seq: number; namespace: string[]; node?: string; values: Record<string, unknown> }
  | { kind: "lifecycle"; seq: number; namespace: string[]; event: string; error?: string; cause?: unknown }
  | { kind: "checkpoint"; seq: number; namespace: string[]; checkpoint: unknown }
  | { kind: "custom"; seq: number; namespace: string[]; data: unknown };
```

The raw protocol loop should be canonical:

```ts
const abortController = new AbortController();

const run = await agentGraph.streamEvents(input, {
  ...config,
  version: "v3",
  signal: abortController.signal,
});

let finalState: Record<string, unknown> | undefined;

const rawLoop = async () => {
  for await (const event of run) {
    activity.mark(event);

    if (await isCancelledFn()) {
      abortController.abort(new Error("Stigmer execution cancelled"));
      run.abort?.(new Error("Stigmer execution cancelled"));
      break;
    }

    const normalized = normalizeV3ProtocolEvent(event);
    if (normalized) {
      statusBuilder.ingest(normalized);
      maybeFlushStatus();
    }
  }
};

const finalOutput = run.output.then((state) => {
  finalState = state as Record<string, unknown>;
  const structuredResponse = finalState?.structuredResponse;
  if (structuredResponse !== undefined) {
    statusBuilder.setStructuredOutput(structuredResponse);
  }
});

const subagentLoop = observeSubagentsIfPresent(run, statusBuilder);

const settled = await Promise.allSettled([rawLoop(), finalOutput, subagentLoop]);

// If any branch failed, classify the failure after flushing best-effort status.
for (const result of settled) {
  if (result.status === "rejected") {
    throw result.reason;
  }
}
```

Why raw events first? Deep Agents docs explicitly say that when exact arrival order across coordinator and subagents matters, iterate raw protocol events and use `namespace`. ([LangChain Docs][3]) Stigmer’s UI, artifact publishing, writeback triggers, and Temporal observability all need that exact order.

## 2.2 Should Stigmer use `run.messages`?

Use it selectively.

`run.messages` is excellent for a simple console-style streamer. LangChain docs show iterating `message.text`, awaiting `message.output`, and reading `message.usage`. ([LangChain Docs][5]) But Stigmer already has a rich `StatusBuilder`, tool timeline, approval gates, subagent state, and writeback triggers. Raw `messages` events are better for a single reducer because they preserve exact `seq`, `namespace`, `node`, and interleaving with tools/lifecycle.

Recommended split:

* **Canonical ingestion:** raw `for await (const event of run)`.
* **Final output:** `await run.output`.
* **Subagent user-facing handles:** `run.subagents`.
* **Optional ergonomic usage/token sanity checks:** `run.messages` / `message.usage`.
* **Optional tool-call promise convenience:** `run.toolCalls`, but do not make it the only artifact/writeback trigger.

## 2.3 Heartbeats and keep-alives

Move Temporal heartbeats out of the event loop.

Current v2 approach heartbeats per event. That is fragile under v3 because:

* an LLM/model call may be non-streaming;
* structured-output/internal calls can be tagged `nostream`, which suppresses tokens while still executing; ([LangChain Docs][4])
* long-running tools may emit only start/end unless implemented as async generators; Promise-returning tools emit start/end but no progress events. ([LangChain Docs][4])
* subagents may be active while the top-level projection you are reading is quiet.

Use:

```ts
const heartbeatTimer = setInterval(() => {
  heartbeat({
    executionId,
    lastSeq: activity.lastSeq,
    lastEventAt: activity.lastEventAt,
    phase: statusBuilder.phase,
  });
}, 2_000);

try {
  await consumeV3Run();
} finally {
  clearInterval(heartbeatTimer);
}
```

Stall detection should use `lastActivityAt` updated by any raw protocol event, tool progress event, status mutation, or known long-running post-stream operation—not by heartbeat itself.

## 2.4 Cancellation and STOP

Recommended cancellation stack:

```ts
const abortController = new AbortController();

const run = await agentGraph.streamEvents(input, {
  ...config,
  version: "v3",
  signal: abortController.signal,
});

async function cancel(reason: string) {
  abortController.abort(new Error(reason));
  run.abort?.(new Error(reason));
}
```

Reason: in the exact `@langchain/langgraph@1.3.2` source, `stream()` combines the caller’s `options.signal` into the graph execution config, while `GraphRunStream.abort()` is not enough to rely on as the only cancellation mechanism. Treat caller-provided `AbortController.signal` as authoritative.

STOP flow should be:

1. detect STOP/cancel in independent polling or raw-event loop;
2. abort caller controller;
3. mark phase `TERMINATED`;
4. flush final status;
5. run idempotent post-stream cleanup only for artifacts already known complete;
6. do not wait for `run.output` as if it were normal completion.

## 2.5 HITL interrupt semantics

Docs show the v3 pattern: drain/consume the stream, inspect `stream.interrupted` and `stream.interrupts`, and resume with a `Command` using a graph compiled with a checkpointer and config carrying a thread ID. ([LangChain Docs][2])

Stigmer should classify interrupts by payload:

```ts
if (run.interrupted) {
  const interrupts = run.interrupts;

  if (isToolApprovalInterrupt(interrupts)) {
    statusBuilder.setPhase("WAITING_FOR_APPROVAL");
  } else {
    statusBuilder.setPhase("PAUSED");
  }

  statusBuilder.setInterrupts(interrupts);
  await flushNow();
}
```

Do not assume every interrupt is tool approval. Keep a generic interrupt model and specialize when payload matches Deep Agents HITL approval shape.

## 2.6 Error handling

v3 error behavior should be treated as three layers:

1. **Tool-level recoverable errors:** raw `tools` event with `data.event === "tool-error"`. This should mark the tool call failed but not necessarily fail the whole graph.

2. **Model/message-level failures:** docs say unrecoverable model-call failures can arrive as message error events, and lifecycle can emit `failed`. ([LangChain Docs][2]) Normalize these if present, but also expect the async iterator or `run.output` to reject.

3. **Graph-level failures:** source inspection shows the v3 pump fails the mux when the underlying graph stream throws. That means:

   * raw `for await` may throw,
   * `run.output` rejects,
   * projection streams may reject/fail.

Use `Promise.allSettled`, then classify:

```ts
const results = await Promise.allSettled([
  rawLoop(),
  run.output.then(handleFinalOutput),
  observeSubagents(),
]);

const failures = results.filter((r) => r.status === "rejected");

if (failures.length > 0) {
  const primary = pickPrimaryFailure(failures);
  statusBuilder.setFailure(classifyLangGraphError(primary));
  await flushNow();
  throw primary;
}
```

Special handling:

* `GraphRecursionError` → clear user-facing explanation about recursion limit / loop.
* Tool approval interrupt → not failure.
* STOP/cancel → `TERMINATED`, not `FAILED`.
* Tool error event inside a successful agent run → tool failed, run may still complete.

# 3. Structured output in v3

## 3.1 Confirmed behavior

**Confirmed for normal completion:** `await run.output` is the correct place to read `structuredResponse`.

Why:

* LangChain docs state structured output is captured, validated, and returned in the `structuredResponse` key of the agent’s state. ([LangChain Docs][1])
* LangChain agent streaming docs state `stream.output` is the final agent state. ([LangChain Docs][5])
* LangGraph event streaming docs state `stream.output` awaits the final output and `stream.values` streams full state snapshots. ([LangChain Docs][2])
* Source inspection of the exact LangChain/Deep Agents packages shows `structuredResponse` is defined as an `UntrackedValue` output field when response format is enabled, and the agent node returns it as a plain state update.
* Local probe against `@langchain/langgraph@1.3.2` showed v3 `run.output` includes an `UntrackedValue`, while checkpoint-backed `getState()` omits it.

The probe was equivalent to:

```ts
const State = new StateSchema({
  input: z.string(),
  persisted: z.string().optional(),
  temp: new UntrackedValue(z.object({ ok: z.boolean(), answer: z.number() })),
});

const graph = new StateGraph(State)
  .addNode("n", async (state) => ({
    persisted: `${state.input}-p`,
    temp: { ok: true, answer: 42 },
  }))
  .addEdge(START, "n")
  .addEdge("n", END)
  .compile({ checkpointer: new MemorySaver() });

const run = await graph.streamEvents(
  { input: "hello" },
  { version: "v3", configurable: { thread_id: "t1" } }
);

for await (const _ of run) {}

console.log(await run.output);
// { input: "hello", persisted: "hello-p", temp: { ok: true, answer: 42 } }

console.log((await graph.getState({ configurable: { thread_id: "t1" } })).values);
// { input: "hello", persisted: "hello-p" }
```

This directly matches your structured-output failure mode: checkpoint state strips untracked values; v3 final in-memory output keeps them.

## 3.2 Extraction pattern

```ts
const run = await agentGraph.streamEvents(input, {
  ...config,
  version: "v3",
  signal: abortController.signal,
});

let finalState: any;

try {
  for await (const event of run) {
    statusBuilder.ingest(normalizeV3ProtocolEvent(event));
    maybeFlushStatus();
  }

  finalState = await run.output;

  if (finalState?.structuredResponse !== undefined) {
    statusBuilder.setStructuredResponse(finalState.structuredResponse);
  }

  statusBuilder.setPhase("COMPLETED");
} catch (err) {
  statusBuilder.setFailure(classifyError(err));
  throw err;
} finally {
  await flushNow();
}
```

## 3.3 Edge cases where `structuredResponse` can still be missing

Treat `structuredResponse` as expected but not guaranteed. It can be missing when:

* no `responseFormat` was configured;
* the graph was interrupted before structured response generation;
* the graph failed before the structured-output node/model call completed;
* structured-output validation failed and the configured strategy propagated the error;
* a STOP/cancel aborted the run;
* a custom `outputKeys`/output-channel setting excludes `structuredResponse`;
* a model/tool strategy retries and never reaches a valid structured response;
* Deep Agents or LangChain changes the internal state key in a future version.

LangChain docs also note structured output may use provider-native structured output or a tool-calling strategy, with tool strategy supporting retries on schema/multiple-output errors. ([LangChain Docs][1]) That means your final extraction must distinguish “missing because no schema” from “missing because structured-output generation failed.”

## 3.4 Alternative capture mechanisms

### `run.values`

`run.values` should include `structuredResponse` in the state snapshot after the relevant node updates it, because it streams full state snapshots. ([LangChain Docs][2]) Use it for debug or early detection, but do not make it canonical; `run.output` is simpler and less prone to partial-state interpretation.

### Raw `updates`

Raw `updates` may include the node delta containing `structuredResponse`, for example:

```ts
if (
  event.method === "updates" &&
  (event.params.data as any).values?.structuredResponse !== undefined
) {
  statusBuilder.setStructuredResponsePreview(
    (event.params.data as any).values.structuredResponse
  );
}
```

Use this only as a “preview” or diagnostic. The final canonical value should come from `run.output`.

### Message/tool events from structured-output call

Do not rely on token/tool events for structured-output extraction. Internal structured-output calls can be suppressed from message streaming using `nostream`, which the docs specifically call out for internal processing such as structured output. ([LangChain Docs][4]) This explains why your v2 event search found no usable `extract` events.

## 4.2 Subagent streaming

Deep Agents docs say each delegated `task` call yields a subagent stream handle, and each subagent can expose messages, tool calls, nested subagents, values, and output. ([LangChain Docs][3]) They also say coordinator and subagent output often interleave and concurrent consumers are appropriate for live UI. ([LangChain Docs][3])

Recommended UI model:

```ts
type AgentScope =
  | { kind: "coordinator"; namespace: [] }
  | { kind: "subagent"; name: string; namespacePrefix: string[]; taskInput?: string }
  | { kind: "subgraph"; name: string; namespacePrefix: string[] };
```

Subagent handling should be recursive:

```ts
async function observeSubagents(
  stream: { subagents?: AsyncIterable<any> },
  parentPath: string[] = []
) {
  if (!stream.subagents) return;

  for await (const sub of stream.subagents) {
    statusBuilder.subagentStarted({
      name: sub.name,
      taskInput: await sub.taskInput.catch(() => undefined),
      parentPath,
    });

    void observeSubagentMessages(sub);
    void observeSubagentToolCalls(sub);
    void observeSubagents(sub, [...parentPath, sub.name]);

    sub.output.then(
      (output) => statusBuilder.subagentFinished({ name: sub.name, output }),
      (err) => statusBuilder.subagentFailed({ name: sub.name, error: String(err) })
    );
  }
}
```

Avoid double-counting:

* If raw events already drive the global message/tool timeline, `run.subagents` should create/label subagent containers, not replay all subagent tokens into the same message stream again.
* If subagent projections drive subagent message/tool UI, raw events should still be used for ordering, writeback triggers, and low-level trace, but gated by namespace.

## 4.3 Stream transformers

Official docs describe stream transformers as observational projection builders; they receive protocol events, can push derived values, and should return `false` only when intentionally suppressing the original event. ([LangChain Docs][2]) That is important: v3 transformers are not graph execution logic; they are stream projection logic.

For Stigmer, custom transformers are attractive but should be phase two. First migrate with raw protocol parsing. Then introduce transformers such as:

* `usageTotalsTransformer`
* `artifactActivityTransformer`
* `writebackActivityTransformer`
* `approvalInterruptTransformer`
* `agentExecutionStatusTransformer`

Example:

```ts
import { StreamChannel } from "@langchain/langgraph";

function stigmerArtifactTransformer() {
  const artifacts = StreamChannel.local<{
    toolCallId: string;
    path: string;
    operation: "created" | "modified" | "deleted";
  }>();

  return {
    init: () => ({ artifacts }),
    process(event: any) {
      if (event.method !== "tools") return true;

      const data = event.params.data;
      if (data.event !== "tool-finished") return true;

      const artifact = extractArtifactFromToolOutput(data.output);
      if (artifact) {
        artifacts.push({
          toolCallId: data.tool_call_id,
          path: artifact.path,
          operation: artifact.operation,
        });
      }

      return true;
    },
  };
}
```

Register later:

```ts
const run = await agentGraph.streamEvents(input, {
  ...config,
  version: "v3",
  transformers: [stigmerArtifactTransformer],
});
```

Docs show call-time transformer registration in v3. ([LangChain Docs][2])

# 5. Performance and operational considerations

## 5.1 Memory footprint

v3 is heavier than v2 callback iteration because:

* it normalizes raw Pregel chunks into protocol events;
* it runs transformer pipelines;
* it exposes multiple projections;
* it requests `values` by default in `@langchain/langgraph@1.3.2`;
* `values` are full state snapshots after steps.

Docs define `values` as full state snapshots and `updates` as deltas. ([LangChain Docs][4]) For Stigmer, this means:

* **Do not persist raw `values` snapshots to backend status.**
* **Do not keep every full state snapshot in your own arrays.**
* **Continue truncating tool outputs.**
* **Use `updates` and tool/message events for UI; use only final `run.output` for final state.**
* **Benchmark long file-editing agents with large `files` state**, because Deep Agents may carry file state in snapshots.

## 5.2 Latency

Token latency should remain good when models stream, because v3 `messages` is designed for token-by-token streaming and `message.text` can be iterated live. ([LangChain Docs][2]) But Stigmer must avoid accidentally awaiting whole projections:

Bad for live UI:

```ts
for await (const message of run.messages) {
  const text = await message.text; // waits for complete message
  statusBuilder.appendText(text);
}
```

Good for live UI:

```ts
for await (const message of run.messages) {
  void (async () => {
    for await (const delta of message.text) {
      statusBuilder.appendText(delta);
      maybeFlushStatus();
    }
  })();
}
```

Even better for Stigmer’s ordering contract: parse raw `messages` `content-block-delta` events by `seq`.

## 5.3 CPU overhead

Expected overhead sources:

* protocol conversion;
* stream transformer processing;
* content-block normalization;
* optional subgraph/subagent projections;
* status diffing if you compare full `values`.

Mitigation:

* Single raw reducer for status.
* Avoid expensive JSON serialization on every event.
* Truncate large payloads before storing in `AgentExecutionStatus`.
* Keep artifact/writeback extraction keyed to `tool-finished`, not `values`.
* Sample debug snapshots behind a flag.

## 5.4 Version stability

LangGraph docs say event streaming is the recommended in-process streaming model for new apps and was introduced in LangGraph v1.2. ([LangChain Docs][4]) Deep Agents type declarations in `1.10.2` mark v3 streaming as experimental and state it may change in future releases. Treat the migration as stable enough to adopt, but pin and contract-test exact versions.

Important lockfile issue from a clean install of your stated versions:

* root `@langchain/core@1.1.47`
* `deepagents@1.10.2`
* `@langchain/langgraph@1.3.2`
* Deep Agents pulled `langchain@1.4.2`
* one dependency path resolved `@langchain/core@1.1.48`

That can matter because message/tool classes and `BaseMessage.isInstance` checks can behave badly when multiple copies of `@langchain/core` are present. Add a CI assertion:

```bash
npm ls @langchain/core @langchain/langgraph langchain deepagents
```

And ideally enforce a single `@langchain/core` version through your package manager overrides/resolutions.

## 5.5 Backward compatibility

v2 and v3 can coexist behind a feature flag:

```ts
if (featureFlags.langGraphV3Stream) {
  return runAgentV3(args);
}
return runAgentV2(args);
```

But do not attempt automatic fallback from v3 to v2 after a v3 run has already started. The run may have executed tools, modified files, emitted approvals, or written checkpoints. Fallback is safe only before graph execution starts or in offline tests.

Recommended rollout flags:

* `LANGGRAPH_STREAM_EVENTS_VERSION=v2|v3`
* `LANGGRAPH_V3_CAPTURE_RAW_EVENTS=true`
* `LANGGRAPH_V3_CAPTURE_VALUES=false`
* `LANGGRAPH_V3_CAPTURE_SUBAGENTS=true`
* `LANGGRAPH_V3_STRUCTURED_OUTPUT_REQUIRED=true` for schema runs

## 5.6 Mock testing

Mock LLMs do not need to emit v3 protocol events directly. LangGraph/Core converts model streams, tool events, and graph events into v3 protocol events. But your MockLLM must implement the LangChain chat-model behavior that v3 expects:

Test cases:

1. streaming text deltas;
2. streaming reasoning/thinking deltas;
3. tool call argument streaming;
4. final AI message with `usage_metadata`;
5. tool call start/end/error;
6. async-generator tool progress → `tool-output-delta`;
7. non-streaming fallback message;
8. `nostream` internal structured-output call;
9. structured output via provider strategy;
10. structured output via tool strategy and retry;
11. graph interrupt and resume;
12. cancellation during model call;
13. cancellation during tool call;
14. subagent task call with nested messages/tools.

The key change is not “mock emits v3”; it is “mock emits enough LangChain Core chat model stream events and final messages for v3’s protocol message handler to produce the right protocol stream.”

# 6. Detailed v2 → v3 mapping for Stigmer `StatusBuilder`

## 6.1 Message streaming

| Current v2 behavior                                      | v3 implementation                                                                                                                                                      |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `on_chat_model_stream` appends token text to AI message. | Raw `messages` event where `data.event === "content-block-delta"` and `data.delta.type === "text-delta"`.                                                              |
| Anthropic thinking blocks parsed provider-specifically.  | Raw `messages` event where `data.delta.type === "reasoning-delta"`, or ergonomic `message.reasoning`. LangChain docs expose `message.reasoning`. ([LangChain Docs][5]) |
| `on_chat_model_end` marks message complete.              | `messages` event where `data.event === "message-finish"`.                                                                                                              |
| `usage_metadata` extracted from final message.           | `message-finish.usage` in raw protocol, or `await message.usage`. LangChain docs expose `message.usage`. ([LangChain Docs][5])                                         |

Defensive parser:

```ts
function normalizeMessageEvent(event: ProtocolEvent): StigmerRunEvent[] {
  if (event.method !== "messages") return [];

  const data = event.params.data as any;
  const base = {
    seq: event.seq,
    namespace: event.params.namespace,
    node: event.params.node,
  };

  switch (data.event) {
    case "message-start":
      return [{ kind: "message_start", ...base, messageId: data.id }];

    case "content-block-delta": {
      const delta = data.delta ?? {};
      if (delta.type === "text-delta") {
        return [{ kind: "text_delta", ...base, text: delta.text ?? "" }];
      }
      if (delta.type === "reasoning-delta") {
        return [{ kind: "reasoning_delta", ...base, text: delta.reasoning ?? "" }];
      }
      return [];
    }

    case "message-finish":
      return [{
        kind: "message_finish",
        ...base,
        usage: data.usage,
        responseMetadata: data.responseMetadata,
      }];

    default:
      return [];
  }
}
```

## 6.2 Tool lifecycle

| Current v2 behavior                                            | v3 implementation                  |
| -------------------------------------------------------------- | ---------------------------------- |
| `on_tool_start` creates tool call record and approval state.   | `tools` event `tool-started`.      |
| `on_tool_end` marks completed and triggers artifact/writeback. | `tools` event `tool-finished`.     |
| Tool failure inferred from v2 payload.                         | `tools` event `tool-error`.        |
| No intermediate progress except custom tool output hacks.      | `tools` event `tool-output-delta`. |

Parser:

```ts
function normalizeToolEvent(event: ProtocolEvent): StigmerRunEvent[] {
  if (event.method !== "tools") return [];

  const data = event.params.data as any;
  const base = {
    seq: event.seq,
    namespace: event.params.namespace,
    callId: data.tool_call_id ?? "",
  };

  switch (data.event) {
    case "tool-started":
      return [{
        kind: "tool_started",
        ...base,
        name: data.tool_name ?? "unknown",
        input: parseMaybeJson(data.input),
      }];

    case "tool-output-delta":
      return [{
        kind: "tool_output_delta",
        ...base,
        delta: String(data.delta ?? ""),
      }];

    case "tool-finished":
      return [{
        kind: "tool_finished",
        ...base,
        output: data.output,
      }];

    case "tool-error":
      return [{
        kind: "tool_error",
        ...base,
        message: data.message ?? "unknown error",
      }];

    default:
      return [];
  }
}
```

## 6.3 State updates

```ts
function normalizeUpdateEvent(event: ProtocolEvent): StigmerRunEvent[] {
  if (event.method !== "updates") return [];

  const data = event.params.data as any;

  return [{
    kind: "state_update",
    seq: event.seq,
    namespace: event.params.namespace,
```

* structured-output preview;
* debugging graph routing;

Do not use it as a replacement for final `run.output`.

# 8. Recommended migration strategy

## Phase 0 — Freeze the contract

Create a compatibility spec before writing migration code:

1. Record golden v2 runs for:

   * plain chat;
   * Anthropic thinking;
   * one tool call;
   * tool error;
   * file modification + artifact publish;
   * writeback;
   * approval interrupt;
   * cancellation;
   * subagent delegation;
   * structured output.

2. Save:

   * raw v2 events;
   * resulting `AgentExecutionStatus`;
   * backend persisted statuses;
   * artifacts/writebacks;
   * token usage totals.

3. Add lockfile assertion for dependency versions and duplicate `@langchain/core`.

## Phase 1 — Build v3 event recorder only

Add a flag that runs v3 in a non-production test path and records raw protocol events without changing the UI.

```ts
for await (const event of run) {
  rawRecorder.write(redactAndTruncate(event));
}
```

Validate:

* event ordering by `seq`;
* namespace shape;
* tool event shape;
* message delta shape;
* usage availability;
* `run.output.structuredResponse`.

## Phase 2 — Implement `V3StatusBuilder`

Do not mutate the v2 builder heavily. Create:

```ts
class V3StatusBuilder {
  ingestProtocolEvent(event: ProtocolEvent): void;
  ingestNormalizedEvent(event: StigmerRunEvent): void;
  setFinalOutput(state: unknown): void;
}
```

The reducer should be idempotent by:

* `seq` for raw events;
* `message id` for messages;
* `tool_call_id` for tool calls;
* `namespace + node + step` for updates;
* `subagent name + task call ID` for subagents.

## Phase 3 — Structured-output path first

Enable v3 only when `responseFormat` is present. That gives immediate value with controlled scope.

Completion logic:

```ts
const finalState = await run.output;

if (responseFormat && finalState?.structuredResponse === undefined) {
  throw new StructuredOutputMissingError({
    phase: statusBuilder.phase,
    interrupted: run.interrupted,
    interrupts: run.interrupts,
  });
}

statusBuilder.setStructuredResponse(finalState.structuredResponse);
```

This should solve the current production blocker without changing every streaming feature at once.

## Phase 4 — Full streaming parity

Enable v3 for all runs behind a per-workspace or per-agent flag.

Parity gates:

* text token latency within acceptable delta from v2;
* thinking/reasoning messages match or improve v2;
* tool timeline matches v2;
* approval waits/resumes work;
* artifact publishing is not delayed;
* writeback commits are identical;
* usage totals within provider variance;
* cancellation/STOP classification correct;
* final status exactly one of completed/failed/terminated/paused.

## Phase 5 — Subagent UX upgrade

Add user-facing subagent cards:

* subagent name;
* delegated task prompt;
* active/running/completed/failed state;
* nested tool calls;
* per-subagent usage if message usage is attributable by namespace;
* final subagent output.

Deep Agents docs show `stream.subagents` as the correct user-facing abstraction for delegated work. ([LangChain Docs][3])

## Phase 6 — Stigmer custom transformers

Once raw v3 ingestion is stable, add custom transformers to reduce application-layer complexity:

* `stigmerUsageTransformer`
* `stigmerToolTimelineTransformer`
* `stigmerArtifactTransformer`
* `stigmerWritebackTransformer`
* `stigmerApprovalTransformer`

Do not start here. Transformers are powerful, but using them too early hides migration bugs.

* Deep Agents has dedicated event streaming docs for `stream.subagents`, nested messages, and subagent tool calls. ([LangChain Docs][3])

For Stigmer, the absence of public migration reports increases the importance of your own contract tests and canary rollout.

## Runtime loops

```ts
async function executeAgentV3(args: ExecuteAgentArgs) {
  const abortController = new AbortController();
  const heartbeat = startTemporalHeartbeatLoop(args, statusBuilder);

  const run = await args.agentGraph.streamEvents(args.input, {
    ...args.config,
    version: "v3",
    signal: abortController.signal,
  });

  const observer = new V3RunObserver({
    run,
    abortController,
    statusBuilder,
    isCancelledFn: args.isCancelledFn,
    flushScheduler,
    artifactPublisher,
    writebackManager,
  });

  try {
    await observer.consume();
    await observer.applyFinalOutput();

    if (run.interrupted) {
      observer.applyInterrupts(run.interrupts);
      await flushScheduler.flushNow();
      return;
    }

    await completePostStreamOperations();
    statusBuilder.markCompleted();
    await flushScheduler.flushNow();
  } catch (error) {
    if (isAbortError(error) || await args.isCancelledFn()) {
      statusBuilder.markTerminated();
    } else {
      statusBuilder.markFailed(classifyError(error));
    }
    await flushScheduler.flushNow();
    throw error;
  } finally {
    heartbeat.stop();
  }
}
```

## `V3RunObserver.consume()`

```ts
class V3RunObserver {
  async consume() {
    const branches = [
      this.consumeRawEvents(),
      this.observeSubagents(),
      this.captureFinalOutput(),
    ];

    const results = await Promise.allSettled(branches);
    this.rethrowIfNeeded(results);
  }

  private async consumeRawEvents() {
    for await (const event of this.run) {
      this.activity.record(event);

      if (await this.isCancelledFn()) {
        this.abortController.abort(new Error("cancelled"));
        this.run.abort?.(new Error("cancelled"));
        break;
      }

      const normalized = normalizeV3ProtocolEvent(event);
      for (const item of normalized) {
        this.statusBuilder.ingest(item);

        if (item.kind === "tool_finished") {
          await this.handleToolFinished(item);
        }
      }

      await this.flushScheduler.maybeFlush();
    }
  }

  private async captureFinalOutput() {
    this.finalState = await this.run.output;
  }

  async applyFinalOutput() {
    if (!this.finalState) return;

    this.statusBuilder.setFinalStateSummary(this.finalState);

    if (this.finalState.structuredResponse !== undefined) {
      this.statusBuilder.setStructuredResponse(this.finalState.structuredResponse);
    }
  }
}
```

## Rollback plan

Rollback is not “retry v2 after v3 partially ran.” Rollback is feature-flag-based routing before starting execution:

```ts
const streamingVersion = getStreamingVersionForExecution({
  workspaceId,
  agentId,
  hasResponseFormat,
  featureFlags,
});

if (streamingVersion === "v3") {
  return executeAgentV3(args);
}

return executeAgentV2(args);
```

For structured-output executions, v2 should be considered unsupported unless you add a separate non-streaming final invoke path. The whole problem is that v2 cannot see the untracked final state.
