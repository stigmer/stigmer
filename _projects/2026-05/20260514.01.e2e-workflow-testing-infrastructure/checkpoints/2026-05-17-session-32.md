## Decisions Made

- **Config validation over runtime tests for grpc_call/activity_call**: Positive runtime tests require harness infrastructure (mock gRPC server, registered Temporal activity) not yet built. Validation-level tests provide immediate value.
- **Duration-based budget enforcement tests**: Using `wait` tasks with short `max_duration_seconds` avoids needing LLM API keys for cost-based testing.
- **Documentation-first assertions for ambiguous behaviors**: Tests that exercise budget check timing, switch fall-through, and listen timeout use `t.Logf` to document actual behavior rather than hard assertions, since the exact semantics may depend on runtime implementation details.
- **Timing-strict fork compete test**: Uses `require.Less(elapsed, 10s)` to verify the slow branch (15s wait) is actually cancelled when the fast branch wins.

## Learnings

- The `WorkflowSpec` proto has `Budget` field with `WorkflowBudget` type, but no `Input` field — input schema validation is a CNCF model-level concern handled by the runner, not exposed at the proto API level
- `for_each` concurrency config (`max_parallelism`, `batch_size`, `on_error`) is read from both `task.Metadata` and JSON round-trip of the task's `for` block — the proto `ForTaskConfig` has these as direct fields
- Budget enforcement checks happen between task boundaries, not during task execution — a single long `wait` task may complete before the duration check fires
