## Decisions Made

- **Native gRPC for TypeScript**: `createGrpcTransport` instead of `createGrpcWebTransport` because the Java service speaks standard gRPC and there's no Envoy/proxy in the test harness. The gRPC-Web path requires a separate "production topology" test.
- **SDK types exclusively in Go test**: Imports from `sdk/go/proto/...`, never from `apis/stubs/go/...`. This is the entire point: proving the SDK's codegen output matches the server.
- **Dummy API key for Python**: `"test-api-key"` satisfies the SDK's non-empty validation while the test-mode server ignores it.
- **Subprocess model for TS/Python**: JSON output contract (`{tier1, tier2, errors}`) keeps the Go harness as single orchestrator. Logs go to stderr, structured results to stdout.

## Learnings

1. The Go SDK's proto types are embedded at `sdk/go/proto/...` — a completely separate Go package from `apis/stubs/go/...`. Both are generated from the same `.proto` files but are Go-incompatible (different import paths). This is by design for SDK isolation.
2. The SDK proto uses `GetTaskName()` (not `GetName()`) on `WorkflowTask` — field naming differs from the non-SDK stubs.
3. TypeScript SDK's `createNodeClient` uses `createGrpcWebTransport` by default — NOT `createGrpcTransport`. For talking to a standard gRPC server without a proxy, `customTransport` with `createGrpcTransport` is required.
4. Python SDK's `StigmerClient` constructor requires a non-empty `api_key` (raises `ValueError` otherwise), even though the test-mode server ignores auth headers entirely.
5. Python protos package is at `apis/stubs/python/stigmer/pyproject.toml` (nested one level deeper than expected), uses Poetry build backend.
