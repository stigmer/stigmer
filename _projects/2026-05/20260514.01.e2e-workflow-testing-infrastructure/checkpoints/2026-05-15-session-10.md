# Session Notes: 2026-05-15, Session 10 — Java Signal Routing Fix

## Accomplishments

- Fixed the production signal routing gap in the polyglot Temporal architecture
- Signals sent via gRPC API (`submitWorkflowTaskApproval`, `sendSignal`) were silently dropped because the outer Java workflow had no mechanism to forward them to the inner Go workflow
- Added `relaySignal` `@SignalMethod` to `InvokeWorkflowExecutionWorkflow` — generic signal forwarding via `SignalExternalWorkflow`
- Updated `signalWithStart()` in the creator to route through `relaySignal` instead of sending raw signal names
- Removed the direct-Temporal-SDK bypass from HITL integration tests — now exercise the full gRPC API path

## Decisions Made

- **Option A (relay in outer workflow) over Option B (direct signal to inner workflow)**: The outer workflow's job is orchestration — signal relay is a natural part of that responsibility. Cross-service coupling is contained within the Temporal layer rather than leaking into gRPC handler code.
- **No `Workflow.getVersion()` needed**: Adding a new `@SignalMethod` is additive and doesn't change existing event history replay. The `relaySignal` signal was never sent by old code, so no old event history references it. Unnecessary versioning would be dead code.
- **Single routing change in creator, not handlers**: Both `submitWorkflowTaskApproval` and `sendSignal` handlers call `workflowCreator.signalWithStart()`. Changing the creator to route through `relaySignal` fixes both handlers without modifying either.

## Signal Flow (After Fix)

```
User/API
  → Java Handler (submitWorkflowTaskApproval / sendSignal)
    → SignalWithStart("relaySignal", [signalName, payload]) to outer workflow
      → InvokeWorkflowExecutionWorkflowImpl.relaySignal()
        → Workflow.newUntypedExternalWorkflowStub("workflow-exec-{id}")
          → SignalExternalWorkflow(signalName, payload)
            → ExecuteServerlessWorkflow (Go) → signal channel receives → task resumes
```
