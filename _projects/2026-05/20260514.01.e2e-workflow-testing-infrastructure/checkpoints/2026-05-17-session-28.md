## Key Decisions

1. **Opt-in via `INTEGRATION_TEST_OTEL=true`** — zero overhead for quick local runs; CI always enables
2. **Jaeger all-in-one over OTel Collector** — queryable API enables programmatic trace export on failure; OTel Collector alone has no query API
3. **Standard `OTEL_EXPORTER_OTLP_ENDPOINT`** — same env var convention across all services and environments (test, local dev, production)
4. **No-op when disabled** — workflow-runner's `InitTracing` returns nil when endpoint unset; zero production overhead
5. **No stigmer-cloud changes needed** — Java service's existing `OpenTelemetryConfig` + `application-observability.yaml` handle everything via env vars

## Key Discoveries

1. Java service OTel export was trivial to enable — `OBSERVABILITY_ENABLED=true` + `OTEL_EXPORTER_OTLP_ENDPOINT` is all that's needed; the `OpenTelemetryConfig` Spring bean handles SDK setup, OTLP exporter, W3C propagation, and shutdown
2. Temporal SDK's `opentelemetry.NewTracingInterceptor` is a `client.Interceptor` (goes on `client.Options`), distinct from the existing `interceptor.WorkerInterceptor` instances (progress, counter) — both coexist cleanly
3. The `otelgrpc` package now prefers `grpc.WithStatsHandler(otelgrpc.NewClientHandler())` over the deprecated `UnaryClientInterceptor`/`StreamClientInterceptor`
