## Decisions Made

- **jq-wasm over node-jq**: jq-wasm (WASM, in-process) is the recommended primary engine due to 0.66ms avg latency, no binary dependency, and in-process execution matching Go's gojq. node-jq (100% pass rate) is the fallback for edge cases.
- **CNCF SDK without strict validation**: The SDK's `Workflow.deserialize()` rejects `document.description` via Ajv schema validation. Workaround: use `new Workflow(parsed)` constructor, which mirrors Go's `json.Unmarshal` approach. All model types and task structures are fully accessible through this path.
- **Manual expression detection**: The TS SDK doesn't provide `isStrictExpr`/`sanitizeExpr` equivalents. Implemented manually in 5 lines each — checks for `${ ... }` wrapping with a space after `${`.
- **Custom function pre-processing**: Neither jq library supports custom function registration (Go has `uuid()`). Only one function exists, so pre-processing is the workaround.

## Learnings

- Go's gojq is a pure in-process library, not a subprocess — the original research report's framing of jq as "subprocess overhead" was misleading. jq-wasm brings the same in-process model to TypeScript.
- The CNCF TS SDK (v1.0.1) has stricter schema validation than the Go SDK (v3.2.0). The Go SDK uses plain `json.Unmarshal` without Ajv-style validation. This is a known difference, not a bug.
- Two separate jq evaluation paths exist in Go: runtime expressions (with $context/$data variables, nil root context) and transform/validate (raw input as document, no variables). Both paths validated.
- The zigflow engine is ~12.7K lines (not 9.7K as originally estimated).
- `document.description` is not in the CNCF Serverless Workflow 1.0.0 JSON Schema — it's a Stigmer/Zigflow extension.
