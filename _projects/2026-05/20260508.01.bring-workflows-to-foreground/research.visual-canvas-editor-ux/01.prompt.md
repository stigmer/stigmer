# Deep Research: Visual Workflow Canvas Editor — Node Interaction UX Patterns

## Research Objective

We are building a **visual workflow canvas editor** for an open-source AI agent platform called **Stigmer** (https://stigmer.ai). The editor allows users to visually compose multi-step AI agent workflows by dragging task nodes onto a canvas, connecting them with edges, and configuring each task's properties. Think of it like a visual DAG (Directed Acyclic Graph) editor, similar to tools like n8n, Apache Airflow's DAG view, Retool Workflows, Zapier Canvas, Temporal Cloud's workflow visualizer, or LangGraph Studio.

We need comprehensive research on **best practices for node interaction UX** in visual canvas/flow editors — specifically around **adding, deleting, and manipulating nodes directly on the canvas** — so we can redesign our current implementation to match modern, polished canvas editor standards.

## What Is Stigmer?

Stigmer is an **open-source AI agent platform**. Users define AI agents in YAML and deploy them with a single command. Agents can use MCP servers (Model Context Protocol) for tool access, knowledge skills, and approval flows for human oversight.

**Workflows** are a core Stigmer feature: users define multi-step orchestration pipelines where each step is a "task" — an agent call, an LLM call, a data transformation, an HTTP request, a conditional branch, a human approval gate, etc. Workflows are defined in a YAML DSL and can be run as durable Temporal workflows.

The **visual canvas editor** is a GUI alternative to writing YAML by hand. It renders the workflow as a node-and-edge graph, with a task palette on the left, an interactive canvas in the center, and an inspector panel on the right.

## Our Current Implementation

### Technology Stack
- **React** (Next.js app)
- **@xyflow/react v12** (formerly React Flow) — the core canvas rendering library
- **@dagrejs/dagre** — for automatic graph layout (top-to-bottom DAG)
- **@stigmer/react SDK** — our internal React component library containing the canvas editor
- **Tailwind CSS** + custom CSS variables (`--stgm-*` design tokens)

### Architecture Overview

The canvas editor has these layers:

1. **`WorkflowEditorView`** — Top-level composed component that toggles between "Code" (YAML) and "Visual" (canvas) editing modes. Provides toolbar with validation summary, save, undo/redo, auto-layout, and a "Refine with AI" panel.

2. **`WorkflowCanvasEditor`** — The visual mode container. Composes:
   - **`WorkflowTaskPalette`** (left sidebar) — categorized, searchable list of available task types (Agent Call, LLM Call, HTTP Call, Switch Case, etc.) that users drag onto the canvas
   - **`WorkflowCanvasInner`** (center) — the actual `<ReactFlow>` canvas component, lazy-loaded
   - **`WorkflowInspectorPanel`** (right sidebar) — property editor for the selected node/edge

3. **`useWorkflowCanvas`** hook — orchestrates the graph model through a **command/history pattern** (undo/redo). All structural mutations go through `GraphCommand` objects dispatched to history. React Flow state is derived from the model after each mutation.

4. **`WorkflowGraphModel`** — the source-of-truth data model. Contains `nodes` (task name, kind, category, config, position) and `edges` (source, target, optional source handle for branching). Sentinel nodes `__start__` and `__end__` represent workflow entry/exit points.

### Current Node Types

- **Sentinel nodes** (`Start`, `End`) — rendered as rounded pills, cannot be deleted
- **Task nodes** — rendered as cards with: category-colored left border, task name, kind badge (e.g., "agent call"), connection handles (top=input, bottom=output). Multi-port outputs for `switch_case` and `human_input` tasks.

### Current Node Interactions

Here is where our UX gaps are:

#### Adding Nodes
- **Drag from palette**: Users drag a task kind from the left palette sidebar and drop it onto the canvas. This creates a new node at the drop position.
- **"+" button on edges**: When hovering over an edge, a small "+" button appears at the midpoint. Clicking it inserts a new `agent_call` task between the source and target nodes, splitting the edge. **Problem**: This always inserts `agent_call` — there's no task type picker.

#### Deleting Nodes
- **Keyboard**: Pressing `Backspace` or `Delete` while a node is selected removes it (React Flow's built-in `deleteKeyCode`).
- **Inspector panel "Delete task" button**: At the very bottom of the right inspector panel, after scrolling past all the configuration fields, there's a red "Delete task" button. **This is the only visible UI affordance for deletion, and it requires scrolling to find it.**
- **There is NO delete button on the node card itself** — users must either know the keyboard shortcut or scroll to the bottom of the inspector.

#### Selecting Nodes
- Click a node to select it (opens its details in the inspector panel)
- Click the canvas background to deselect
- Shift+click for multi-selection
- Box selection by dragging on the canvas

### What's Missing / Broken

1. **No delete affordance on the node card** — Modern canvas editors (n8n, Retool, Zapier) show a small trash/delete icon on the card itself, or in a floating toolbar that appears when a node is selected or hovered. Our users have to either discover the keyboard shortcut or scroll through the inspector to find "Delete task". This is a major UX gap.

2. **No inline add-node button** — Beyond the drag-from-palette approach, most modern editors let you click a "+" on a node itself (typically on the output handle/connection point) to quickly add a successor node. We only have the edge "+" which always inserts `agent_call`.

3. **No context menu on right-click** — Right-clicking a node could offer: Delete, Duplicate, Copy, Disconnect, etc. We have nothing.

4. **The edge "+" insert is hardcoded to `agent_call`** — It should open a quick task-type picker (mini-palette or command palette popup) so users can choose which task to insert.

5. **No floating action bar on selection** — When you select a node in editors like Figma, Miro, or n8n, a small floating toolbar appears above/below the node with quick actions (delete, duplicate, copy, etc.). We don't have this.

6. **No visual feedback for drag-to-delete** — Some editors let you drag a node to a trash zone or show a delete affordance when dragging starts.

For each, document:

### 4. Recommended Interaction Model

Based on the research, propose a **concrete interaction model** for our canvas editor that covers:

1. **Node card design** — What controls should appear on each node card? Where should they be placed? What triggers their visibility (always visible, on hover, on select)?

2. **Delete flow** — Primary and secondary ways to delete a node. Confirmation dialog or undo-based? What about batch delete?

3. **Add flow** — Beyond drag-from-palette, how should users quickly add nodes? ("+" on handles, inline search, command palette, right-click > Add)

4. **Edge insert flow** — How should the "+" on edges work? Should it open a picker? What should the picker look like?

5. **Context menu** — What items should appear? Design recommendations.

6. **Floating action bar** — Should we have one? What actions? Where positioned relative to the node?

7. **Selection states** — Visual treatment for: default, hovered, selected, multi-selected, error state, drag-in-progress.

## Known Constraints

- We use **@xyflow/react v12** (latest) — solutions must be compatible
- We use a **command/history pattern** — all mutations must go through commands for undo/redo
- Nodes have a **`WorkflowGraphModel`** as the single source of truth
- We use **CSS variables** (`--stgm-*`) for theming — solutions must be theme-aware
- The canvas is **lazy-loaded** via `React.lazy` + `Suspense` — performance matters
- We need to support **10-50+ nodes** in a single workflow without performance degradation
- The editor runs in both **self-hosted (open-source)** and **cloud** environments
