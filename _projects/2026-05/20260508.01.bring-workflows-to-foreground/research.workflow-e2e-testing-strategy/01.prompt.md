# Deep Research: End-to-End Integration Testing Strategy for AI Workflow Orchestration Platform

## Research Objective

We need a comprehensive strategy for building an end-to-end integration test suite for an AI agent workflow orchestration platform. The platform has a complex architecture with multiple execution engines ("harnesses"), a Temporal-based workflow runner, multiple SDKs, a gRPC API surface, and two distinct agent runners (Python/LangGraph and TypeScript/Cursor SDK). We need to understand industry best practices, tooling choices, test architecture patterns, secrets management for CI, report generation, and how to use AI coding agents (Cursor Runner / `@cursor/sdk`) as the mechanism to trigger and execute integration tests.

## Our Specific Situation

### Platform Overview

**Stigmer** is an open-source infrastructure platform for AI agents and workflows. It uses a monorepo architecture with the following key components:

### Architecture Components

#### 1. Backend Services (4 services)

- **stigmer-server** (Go) — The central API server. gRPC + gRPC-Web. Manages agent/workflow/project resources. Stores state in SQLite (`~/.stigmer/stigmer.db`). Serves as the control plane.
- **workflow-runner** (Go) — A Temporal worker that executes workflow DAGs. Connects to a Temporal server (started automatically by `stigmer server`). Executes tasks defined in CNCF Serverless Workflow DSL (YAML). Task kinds include: `agent_call`, `http_call`, `set`, `emit_event`, `for_each`, `fork`, `switch_case`, `try_catch`, `raise_error`, `sleep`, `listen`, `llm_call`, `extract`, `validate`, `human_input`, `transform`, `notification`, `budget_guard`, and `emit_event`.
- **agent-runner** (Python, LangGraph) — Executes AI agent sessions using LangGraph. Communicates with LLM providers (Anthropic, OpenAI, Ollama) via configurable model registry. Reports back to stigmer-server via gRPC.
- **cursor-runner** (TypeScript, Node.js) — Executes AI agent sessions using the Cursor SDK (`@cursor/sdk`). This is an alternative harness that uses Cursor's agent infrastructure instead of direct LLM calls. Communicates with Cursor's backend, captures usage via `onDelta` callbacks, and reports back to stigmer-server via gRPC (Connect protocol).

#### 2. Client Applications

- **CLI** (Go, Cobra) — The primary user interface. Commands include: `stigmer apply` (deploy agents/workflows), `stigmer run` (execute agents/workflows), `stigmer server` (start the server stack), `stigmer workflow list/get/validate/diff/logs/trace/cancel/resume`.
- **Web Console** (React, Next.js/Vite) — Browser-based UI with workflow editor (YAML + visual canvas), execution viewer, settings.
- **Desktop App** (Tauri v2 + React) — Native desktop app wrapping the same React UI.

#### 3. SDKs

- **Go SDK** — Proto-generated stubs + client libraries for the gRPC API.
- **TypeScript SDK** (`@stigmer/sdk`) — Connect-Web client for browser/Node.js.
- **React SDK** (`@stigmer/react`) — React hooks and components for the web/desktop consoles.
- **Python SDK** — Proto-generated stubs for Python agent-runner.
- **Java SDK** — Proto-generated stubs for Java consumers.

#### 4. Protobuf API Surface

The API is defined in protocol buffers organized by domain:
- `ai.stigmer.agentic.agent.v1` — Agent resources (CRUD + query)
- `ai.stigmer.agentic.agentexecution.v1` — Agent execution lifecycle
- `ai.stigmer.agentic.agentinstance.v1` — Agent instance management
- `ai.stigmer.agentic.workflow.v1` — Workflow template resources
- `ai.stigmer.agentic.workflowexecution.v1` — Workflow execution lifecycle (commands: create, cancel, signal, retry; queries: get, list, stream events)
- `ai.stigmer.agentic.workflowinstance.v1` — Workflow instance management
- `ai.stigmer.agentic.mcpserver.v1` — MCP server resources
- `ai.stigmer.tenancy.project.v1` — Multi-tenancy / project management
- `ai.stigmer.platform.v1` — Platform-level services (server info)

#### 5. Build System

- **Bazel** — Top-level build system (BUILD.bazel, MODULE.bazel)
- **Make** — Developer-facing targets (`make test`, `make lint`, `make check`, `make build`, `make local`)
- **npm workspaces** — For TypeScript packages (sdk/react, sdk/typescript, sdk/ink, client-apps/web, client-apps/desktop, cursor-runner)
- **Poetry** — For Python packages (agent-runner)
- **Go workspaces** — `go.work` for multi-module Go development

### Existing Test Infrastructure

#### What We Have Today

1. **E2E Test Suite** (`test/e2e/`, Go, testify/suite):
   - **Phase 1 (complete)**: 15 tests covering deployment (`stigmer apply`) and execution creation (`stigmer run`) for agents and workflows.
   - **Phase 2 (planned, not implemented)**: Full execution tests (actual agent/workflow execution with phase progression, outputs, log streaming).
   - **Test harness**: Connects to a running `stigmer server` instance. Requires Stigmer server + Temporal + Ollama (local LLM).
   - **Fixtures**: Automatically synced from SDK examples (19 SDK examples → testdata/).
   - **Build tag**: `go:build e2e` — tests are excluded from `make test`.
   - **Test helpers**: gRPC client wrappers for querying agents, workflows, executions, instances, projects via API.
   - **Limitation**: Uses the same local database as manual development (`~/.stigmer/stigmer.db`). No test isolation.

2. **Cursor Runner Unit Tests** (`backend/services/cursor-runner/src/__tests__/`):
   - `config.test.ts` — Configuration validation tests.
   - One integration test file was deleted: `cursor-usage-probe.integration.test.ts`.

3. **Workflow Runner Tests** (`backend/services/workflow-runner/test/`):
   - Golden test files for workflow execution.
   - Manual test YAML files (test-simple-fetch.yaml, test-context-variables.yaml).

4. **No Integration Tests for**:
   - Full workflow execution lifecycle (PENDING → RUNNING → task execution → COMPLETED/FAILED)
   - Cross-service communication (stigmer-server ↔ workflow-runner ↔ agent-runner/cursor-runner)
   - Cursor SDK agent execution through the full stack
   - Workflow task kinds (19 kinds, none tested end-to-end)
   - Human-in-the-loop approval flows
   - Multi-agent workflows (workflow calling agents)
   - Error handling, retry, timeout, and cancellation flows
   - Budget/cost tracking
   - Workflow execution event streaming
   - Environment variable injection and secrets

| `cursor.yaml` | Cursor API key (`prod.api-key`) | Yes — needed for Cursor harness integration tests |
| `anthropic.yaml` | Anthropic API key | Yes — needed for LangGraph harness tests with Claude |

```bash
planton secret get --org stigmer --name cursor --entry prod.api-key
```

### How We Want to Use Cursor Runner for Testing

The Cursor Runner (`@cursor/sdk`) can be used to programmatically trigger AI agent executions. The idea is:

1. **Cursor Runner as test executor**: Instead of manually running agents or relying on simple mocked tests, use the Cursor SDK to actually execute agent tasks as part of integration tests.
2. **The runner connects to Cursor's backend**: Uses a Cursor API key (from `cursor.yaml` secret group) to authenticate.
3. **The runner reports back**: Sends execution status, usage data, and results back to stigmer-server via gRPC.
4. **This tests the real stack**: stigmer-server → Temporal → workflow-runner → cursor-runner → Cursor SDK → results back through the entire pipeline.

## What We Need to Understand

### 1. Integration Test Architecture for Multi-Service AI Platforms

How should we architect an integration test suite for a platform with this many moving parts?

- **Service dependency graph for testing**: What's the right order/strategy for testing services that depend on each other? (stigmer-server depends on Temporal, workflow-runner depends on both, agent-runner depends on stigmer-server + LLM providers, cursor-runner depends on stigmer-server + Cursor API)
- **Test isolation strategies**: How do platforms like Temporal, Airflow, Prefect, n8n, Dagster, and other workflow orchestration tools handle test isolation? Do they use separate databases per test? Test namespaces? Ephemeral environments?
- **Mocking vs. real services**: When should we use real external services (Cursor API, Anthropic API, Ollama) vs. mocks? What's the industry standard for testing LLM-dependent workflows?
- **Container-based test environments**: Should we use Docker Compose, Testcontainers, or similar for spinning up isolated test environments? How do Temporal's own integration tests work?

### 2. Testing Workflow Orchestration Specifically

What are the proven patterns for testing workflow execution engines?

- **Temporal test patterns**: Temporal has its own test framework (`go.temporal.io/sdk/testsuite`). How should we combine Temporal's test utilities with our own integration tests? Should workflow activities be tested in isolation vs. integrated?
- **Task kind testing**: We have 19 task kinds. What's the strategy for testing each kind? A matrix approach? Golden file testing? Contract testing?
- **Execution lifecycle testing**: How to test async execution lifecycles (PENDING → RUNNING → COMPLETED/FAILED) without flaky timeouts? Polling vs. event-driven test assertions?
- **HITL testing**: How to test human-in-the-loop approval flows in automated tests? How do other platforms (Temporal, Airflow) handle this?
- **Workflow composition testing**: How to test workflows that call agents (`agent_call` task)? How to test workflows that call other workflows? How to test fork/join, conditional branching, error handling paths?
- **Non-determinism**: AI agent outputs are non-deterministic. How do you write assertions for tests that involve LLM calls? Fuzzy matching? Schema validation? Behavioral assertions instead of exact output matching?

### 3. Using AI Coding Agents (Cursor SDK) as Test Executors

This is a novel pattern — using AI agents themselves to drive integration tests. What are the considerations?

- **Reproducibility**: Cursor agent executions are non-deterministic. How do we make tests meaningful when the agent might take different paths each time?
- **Cost control**: Each Cursor agent execution costs real money (LLM tokens). How do we budget for CI runs? How do other platforms handle cost-sensitive testing?
- **Timeouts and reliability**: Cursor agent executions can take seconds to minutes. How do we handle flaky tests due to external service latency?
- **Minimal agent tasks for testing**: What are the simplest possible Cursor agent tasks we can use for integration testing that still exercise the full stack? (e.g., "write hello to a file" instead of complex multi-step tasks)
- **Verification strategy**: How do we verify that the agent actually did what we expected? File system checks? Output validation? State assertions?

### 4. Test Infrastructure and CI/CD

How should we set up the test infrastructure?

- **CI runner requirements**: Our tests need Temporal, stigmer-server, possibly Ollama, and access to external APIs (Cursor, Anthropic, OpenAI). How do CI platforms (GitHub Actions, etc.) handle this?
- **Secrets injection for CI**: We have secrets in Planton. How should these be injected into CI environments? GitHub Secrets? Vault? Planton CLI in CI?
- **Test environment provisioning**: Should we use ephemeral environments per PR? Per merge to main? Scheduled nightly? What's the cost/benefit?
- **Parallel test execution**: Can we run workflow integration tests in parallel? What isolation mechanisms are needed?
- **Test data management**: Workflow tests create state in the database and Temporal. How do we clean up? Namespace per test? Database reset?

### 5. Test Reporting and Observability

How should we report on and observe integration test results?

- **Test report formats**: JUnit XML? Custom dashboards? GitHub Actions annotations?
- **Execution traces**: How to capture and display full execution traces (workflow → task → agent → LLM call) for debugging failed tests?
- **Flakiness detection**: What tools/patterns exist for detecting and managing flaky integration tests in workflow platforms?
- **Cost reporting**: How to track and report the cost of each test run (LLM tokens consumed)?
- **Historical trends**: How to track test reliability, execution times, and costs over time?

### 6. Comparable Platforms and Their Testing Strategies

What can we learn from similar platforms?

- **Temporal** — How does Temporal Cloud itself test its workflow execution engine? What does their test suite look like?
- **Airflow** — How does Apache Airflow test DAG execution? They have 4000+ tests. What's their architecture?
- **Prefect** — How does Prefect test flow execution?
- **n8n** — n8n is open-source and has visual workflow editing (similar to our canvas). How do they test node execution?

- **LangGraph** — How does LangGraph itself test agent graph execution?

## Context

This is for a production platform with early adopters. We need to move from "tests that verify deployment" to "tests that verify the entire workflow execution pipeline works." The immediate priority is building confidence that workflow changes don't break the execution engine. The secondary priority is having a repeatable, automated test suite that runs in CI. We'd rather have a small number of high-confidence integration tests than a large number of shallow tests.
