# Deep Research: Bringing the AI Workflow Orchestration Domain to the Foreground

## Research Objective

We are building **Stigmer** — a platform for deploying, running, and orchestrating AI agents. We have a fully modeled but not-yet-surfaced **Workflow domain** that orchestrates multi-step tasks involving AI agent calls, API calls, conditional branching, parallel execution, error handling, and more. The workflow domain has been implemented at the data model / proto level and wired to a Temporal-based execution backend, but it has **not been brought to the UI or end-user experience yet**. We are currently focused on single agent execution and agent instances in the foreground.

We need comprehensive research on three areas:

1. **Validation of our architectural choices** (serverless workflow DSL + Temporal durability)
2. **Strategy for surfacing workflows in the UI/UX** (how to bring it to the foreground)
3. **Completeness of our workflow task modeling** (especially around decision-making after agent calls, understanding agent output, routing, and what other task types we need)

## What We Have Built (Current State)

### Domain Model (Template → Instance → Execution pattern)

We follow a three-layer pattern, identical to our agent domain:

- **Workflow** (Template): The reusable orchestration blueprint. Contains an ordered list of `WorkflowTask` items. Each task has a `kind` (enum) and a `task_config` (google.protobuf.Struct that gets unmarshaled to the appropriate typed config based on `kind`).

- **WorkflowInstance**: A configured deployment of a Workflow template. Binds Environment references (env vars, secrets, credentials) to a Workflow. Allows the same Workflow to be deployed multiple times with different configurations (dev/prod, different cloud accounts, different teams).

- **WorkflowExecution**: A single runtime invocation. Contains trigger_message, trigger_metadata, runtime_env overrides, and a callback_token for Temporal async activity completion.

### Workflow Task Types (13 defined)

We use a **"kind + Struct" discriminated union** pattern where `WorkflowTask.kind` determines the type and `WorkflowTask.task_config` (google.protobuf.Struct) holds the configuration. Each kind has a corresponding typed proto message:

| Kind | Proto Config | Purpose |
|------|-------------|---------|
| `set_vars` | SetTaskConfig | Assign variables in workflow state |
| `http_call` | HttpCallTaskConfig | Make HTTP requests (GET/POST/PUT/DELETE/PATCH) |
| `grpc_call` | GrpcCallTaskConfig | Make gRPC requests |
| `activity_call` | CallActivityTaskConfig | Execute Temporal activities |
| `switch_case` | SwitchTaskConfig | Conditional branching with cases evaluated in order |
| `for_each` | ForTaskConfig | Iterate over collections |
| `fork` | ForkTaskConfig | Parallel execution with optional race mode |
| `try_catch` | TryTaskConfig | Error handling with try/catch blocks |
| `listen` | ListenTaskConfig | Wait for external signals (via Temporal signals) |
| `wait` | WaitTaskConfig | Pause for duration or until timestamp (via Temporal timers) |
| `raise_error` | RaiseTaskConfig | Raise errors to terminate or trigger error handling |
| `run_workflow` | RunTaskConfig | Execute sub-workflows (via Temporal child workflows) |
| `agent_call` | AgentCallTaskConfig | Invoke an AI agent with message, env, and config overrides |

### Workflow DSL

The workflow definition uses a YAML DSL influenced by the CNCF Serverless Workflow specification (and internally called "Zigflow DSL"). A WorkflowDocument has dsl version, namespace, name, version, and description. Tasks are defined as an ordered list. Expression syntax uses `${ ... }` (JQ-style expressions). Export blocks let you save task output to context. FlowControl blocks let you jump to specific tasks or end the workflow.

### Execution Engine

- **Temporal** is used for durability, long-running execution, retries, and signal handling
- Workflow validation generates CNCF Serverless Workflow DSL 1.0.0 YAML and validates it asynchronously
- Agent calls use an async activity completion pattern: the workflow activity extracts its Temporal task token, passes it to the AgentExecution, and returns `activity.ErrResultPending`. When the agent completes, it calls `ActivityCompletionClient.complete(token, result)` to resume the workflow.
- ExecutionPhase lifecycle: PENDING → IN_PROGRESS → COMPLETED/FAILED/CANCELLED/TERMINATED, with a PAUSED state that supports resume

### What's NOT Built Yet

- No workflow UI (no builder, no execution viewer, no monitoring dashboard)
- No visual workflow editor or canvas
- No way for users to create, browse, or trigger workflows from the UI
- No visualization of workflow execution progress (task-by-task)
- Limited decision-making after agent calls — the switch_case task uses expression evaluation but doesn't have built-in understanding of agent output structure
- No explicit "transform" or "extract" task for parsing agent outputs into structured data
- No "human input" or "approval gate" task type within the workflow itself (though agent executions have HITL approval)

## Research Questions

### Area 1: Architecture Validation — Serverless Workflow DSL + Temporal

1. **Is our choice of CNCF Serverless Workflow DSL (v1.0.0) + Temporal the right foundation?** Compare against alternatives:
   - AWS Step Functions (States Language)
   - Apache Airflow / Prefect / Dagster
   - LangGraph / LangChain for AI orchestration
   - Inngest / Trigger.dev for serverless workflows
   - Orkes (Conductor) for Temporal alternatives
   - n8n / Windmill for visual workflow builders
   - Custom DSL from scratch

2. **Is the "kind + Struct" discriminated union the right modeling pattern** for workflow tasks? Compare with:
   - Protobuf `oneof` for task configs
   - Separate proto messages per task type (no shared WorkflowTask)
   - JSON Schema-based validation instead of proto
   - How do other workflow engines model their task/step definitions?

3. **Is Temporal the right durability layer** for AI agent workflows specifically? Consider:
   - Agent calls can take minutes to hours (long-running activities)
   - Human-in-the-loop approval pauses
   - Cost implications of Temporal for many concurrent workflows
   - Does Temporal's activity model map well to AI agent invocations?
   - Temporal vs. Restate vs. Durable Execution alternatives

4. **How well does the CNCF Serverless Workflow spec align with AI/agentic use cases?** The spec was designed for cloud-native microservice orchestration. Does it naturally support:
   - Streaming agent output
   - Agent-to-agent communication during execution
   - Dynamic task generation (agent decides what to do next)
   - Context/memory passing between agent calls
   - Cost tracking and budget enforcement per workflow

### Area 2: UI/UX Strategy — Bringing Workflows to the Foreground

5. **What are the best UI/UX patterns for workflow builders in 2025-2026?** Research and compare:
   - Visual canvas/node-based editors (like n8n, Retool Workflows, Zapier)
   - Code-first with visual preview (like GitHub Actions, Temporal Cloud UI)
   - Hybrid approaches (visual + YAML/code toggle)
   - AI-assisted workflow creation (describe what you want, AI builds the workflow)
   - How do Relevance AI, Wordware, Langflow, Flowise, and similar AI workflow tools handle their UX?

6. **How should workflow execution be visualized?** Research:
   - Real-time execution progress (task-by-task status updates)
   - Agent call output streaming within a workflow context
   - Error visualization and debugging UX
   - Timeline view vs. DAG view vs. log-centric view
   - How do Temporal Cloud UI, Inngest dashboard, and AWS Step Functions console show execution state?

7. **What's the right workflow creation experience for an AI-first platform?** Consider:
   - Should users be able to describe workflows in natural language and have them generated?
   - Should there be a library/marketplace of pre-built workflow templates?
   - How much should the YAML DSL be hidden vs. exposed?
   - What's the right balance between power-user features and approachability?

8. **How should workflows integrate with the existing agent experience?** Currently users interact with agents directly. How should workflows appear alongside:
   - Agent sessions (chat interface)
   - Agent marketplace/discovery
   - Dashboard and monitoring
   - CLI experience (we have `stigmer run agent` — what's the workflow equivalent?)

### Area 3: Workflow Task Modeling — Completeness and Agent Output Handling

9. **How should agent output be understood and used for routing decisions?** Our current model:
   - Agent produces unstructured text output
   - switch_case evaluates JQ expressions on the output
   - But agent output is freeform text, not structured data

   Research how to bridge this gap:
   - Should we have an explicit "parse agent output" / "extract structured data" task?
   - Should agents be required/encouraged to output structured JSON alongside natural language?
   - How do other platforms handle decision-making based on LLM output? (e.g., LangGraph conditional edges, Semantic Kernel plans)
   - Should there be an "LLM judge" / "classifier" task that takes agent output and produces a structured decision?
   - Tool like Instructor / Outlines / Guardrails for structured output extraction

10. **What additional task types do we need?** Evaluate whether we should add:
    - `human_input` / `approval_gate` — explicit HITL task within workflow (not just agent-level)
    - `llm_call` — direct LLM call without a full agent (for simple classification, extraction, summarization)
    - `transform` / `map` — data transformation between tasks (JQ/JSONPath/template-based)
    - `webhook_trigger` — receive external events mid-workflow
    - `notification` — send Slack/email/Discord notifications
    - `data_store` — read/write from a database or key-value store
    - `code_execution` — run arbitrary code (Python/JavaScript sandbox)
    - `delay_until_condition` — wait until a dynamic condition is met (polling)
    - `batch` — process items in batches with concurrency control
    - `cache` — cache results of expensive operations
    - `assert` / `validate` — validate data meets schema before proceeding

11. **How should the workflow handle agent "autonomy" vs. "orchestration"?** Two models:
    - **Orchestrated**: Workflow strictly controls which agent runs when, with what input
    - **Autonomous**: Agent decides what to do next, workflow provides guardrails
    - Hybrid: Workflow provides structure but agents can request additional steps
    - How do platforms like CrewAI, AutoGen, OpenAI Swarm handle this spectrum?

12. **How should context/state flow between tasks?** Our current model:
    - Export block saves task output to context (`export.as = "${.}"`)
    - Tasks reference context via `${ $context.taskName.field }`
    - Is this sufficient? Research:
      - Scoped vs. global context
      - Context size limits (agent outputs can be large)
      - Context summarization between tasks
      - Type safety for context references
      - How do workflow engines handle large intermediate results?

13. **How should error handling work for AI-specific failures?** Beyond try/catch:
    - Agent hallucination detection and retry
    - Output quality validation (did the agent actually answer the question?)
    - Cost-aware retry (don't retry expensive operations blindly)
    - Graceful degradation (fall back to simpler model, shorter prompt)
    - Human escalation when AI fails
    - Timeout strategies for agent calls (how long is too long?)

## Context About Our Platform

- **Stigmer** is an AI agent platform. Think of it as "Kubernetes for AI agents" — you define agents declaratively (model, tools/MCP servers, system prompt, skills) and the platform handles execution, scaling, context management, and tool orchestration.
- The platform supports **multiple LLM providers** (OpenAI, Anthropic, Google, etc.) via a model registry.
- Agents can use **MCP servers** (Model Context Protocol) for tool access.
- The execution runtime uses **LangGraph** for the agent execution graph and **Temporal** for workflow durability.
- We follow a **Template → Instance → Execution** pattern for both agents and workflows.
- The CLI (`stigmer`) is the primary interface today. A web UI exists for agent interaction but workflows are not surfaced.
- Target users: developers and teams who want to build and deploy AI agent workflows for automation, internal tools, and customer-facing applications.
