# Bringing the AI Workflow Orchestration Domain to the Foreground

## Executive assessment

Stigmer’s underlying direction is fundamentally sound. A declarative workflow layer on top of a durable execution engine is exactly where the wider market is moving for production AI systems: Temporal explicitly positions durable execution as a strong fit for AI agents; Prefect now markets orchestration for “AI Teams” with state machines and human-in-the-loop; Apache Airflow has added a Common AI Provider; Conductor now pitches itself as durable execution for workflows and agents; and AWS Step Functions has added Bedrock AgentCore integrations. That is a strong validation of the core architectural bet: **AI workflows need orchestration that is durable, inspectable, resumable, and policy-aware**. citeturn7search0turn15search2turn15search13turn6search4turn8search3

The biggest weakness in the current Stigmer design is not the backend foundation. It is the gap between a powerful orchestration model and what users can actually see, edit, debug, and trust. The strongest workflow products in 2025–2026 all emphasise one of three things in the foreground: **a builder**, **a runtime inspector**, or ideally both. n8n, Zapier Canvas, Langflow, Flowise, Windmill, Trigger.dev, Inngest, Step Functions, and Temporal all make execution state highly visible, and several now use AI assistance or natural language to generate flows. If Stigmer keeps workflows hidden behind single-agent UX for too long, the platform risks looking like “agents plus some internal plumbing” instead of “an AI automation platform with reliable orchestration”. citeturn35search1turn30search0turn28search2turn3search1turn11search1turn34search3turn34search17turn9search0turn9search1

The second major weakness is the modelling gap around **AI outputs as control signals**. Free-form text is a poor primitive for routing, retries, approvals, and downstream integrations. The market has moved decisively towards schema-constrained outputs, typed extraction, validators, and guardrails. OpenAI and Anthropic both support structured outputs, Instructor and Guardrails add typed extraction plus retries and validation, and Outlines offers schema- and grammar-constrained generation. In other words: **agent output needs a structured side channel** if workflows are going to branch on it reliably. citeturn12search0turn12search1turn12search2turn12search3turn13search0turn13search4

My overall recommendation is therefore: **keep the architectural foundation, do not replace it, but change the product strategy and task model before investing heavily in a full visual canvas**. Specifically, bring workflows to the foreground first through a run viewer, template library, trigger surface, and YAML-plus-graph editor; then close the modelling gaps with structured AI outputs, approval gates, transform/extract, validation, and event emission. citeturn9search0turn9search1turn28search2turn35search1turn31view1

## Architecture foundation

### Why the current foundation is strong

Temporal is a strong durability layer for AI workflows because its core primitives map unusually well onto long-running, failure-prone, human-interrupted agent systems. Temporal supports child workflows, signals, timers, queries, and durable event histories; it is explicitly designed for workflow executions that can survive crashes, deployments, and long waits; and its AI-facing material now frames durable execution as a natural fit for production agents. This lines up closely with your current Async Activity Completion pattern for agent calls and with pause/resume semantics for approvals and external waits. citeturn7search13turn7search17turn7search2turn7search0turn25search2

The Temporal-specific caveat is cost and history growth. Temporal Cloud bills on Actions and Storage, where starts, signals, heartbeats, timers, retries, and related operations are billable; active and retained histories also count towards storage. Temporal’s own limits documentation warns that a workflow execution’s history is capped at 51,200 events or 50 MB, with warnings at 10,240 events or 10 MB, and recommends patterns such as Continue-As-New and workload partitioning with child workflows when histories become large. That is acceptable for AI orchestration, but it means Stigmer needs explicit policies for large outputs, high signal volume, retries, and heartbeat usage from day one. citeturn24view0turn24view2turn25search0turn22view0turn22view3turn26view0

The CNCF Serverless Workflow choice is also more defensible than it may first appear. The project remains vendor-neutral under CNCF; its task model already covers set, call, fork, for, listen, raise, run, switch, try, and wait; and the current mainline DSL reference has already expanded the default call family to include A2A and MCP, signalling that the ecosystem is trying to adapt the spec to agent-native use cases rather than staying purely in microservice-land. That makes it a better starting point than inventing a fully custom DSL from scratch. citeturn36search6turn31view0turn31view1turn32view0turn32view2turn32view3

### Where alternatives are stronger

AWS Step Functions is the strongest “managed alternative” when teams are all-in on AWS. It offers a mature console, graph-oriented execution views, long-running Standard workflows, Distributed Map for very large fan-out, JSONata-based data transformation, and new Bedrock AgentCore integrations. But its hard quotas remain meaningful: Standard execution history is capped at 25,000 events, task and state input/output are capped at 256 KiB, and it is structurally AWS-centric. For Stigmer’s multi-provider, multi-agent positioning, that lock-in is a real drawback even though Step Functions is an excellent benchmark for UX and execution inspection. citeturn23view3turn23view0turn23view1turn8search8turn9search0turn8search3

Airflow, Prefect, and Dagster are not the right primary benchmark for Stigmer’s user-facing workflow product. Airflow and Dagster still come from data orchestration first; Dagster explicitly frames itself as a data orchestrator for data engineers, and Airflow’s new AI provider shows adaptation rather than original design for agentic systems. Prefect is closer to your problem space, especially with interactive workflows and AI-team positioning, but its centre of gravity is still Python-native flows rather than a portable declarative workflow DSL. These tools are highly relevant reference points for reliability, retries, and observability, but not a clean substitute for a first-class AI workflow product surface. citeturn15search3turn15search13turn16search0turn15search2turn2search2

LangGraph, OpenAI Agents SDK, CrewAI, and AutoGen are also not substitutes for your workflow layer; they are complements. LangGraph gives stateful agent graphs with persistence, interrupts, streaming, and conditional edges; OpenAI Agents SDK gives handoffs, guardrails, approvals, and streaming; CrewAI explicitly distinguishes deterministic Flows from autonomous Crews; and AutoGen supports human-in-the-loop and multi-agent conversation patterns. These frameworks are best treated as **runtime components inside steps** or as execution engines for specialised nodes, not as the outer durable orchestration layer that owns deployment, external signals, retries, cost policy, and auditability. citeturn27view1turn13search2turn28search0turn14search7turn17search1turn14search0turn14search8turn14search1

Inngest and Trigger.dev are closer competitors in spirit because they position themselves around durable, long-running background workflows and AI tasks. Inngest offers concurrency controls, traces, replay, and step durability; Trigger.dev offers checkpoint/resume, waiting for events, real-time monitoring, and LLM streaming support. Their advantage is simplicity and strong developer ergonomics. Their relative weakness for your roadmap is that they are code-first runtimes rather than a portable, explicit workflow domain model that could be surfaced consistently across UI, CLI, and APIs. citeturn34search0turn34search2turn34search17turn34search12turn34search16turn34search3turn34search5

n8n, Windmill, Retool Workflows, Langflow, Flowise, Wordware, Zapier Canvas, and Relevance AI are the best **product UX** benchmarks, not the best backend architecture benchmarks. They show how builders, templates, playgrounds, approvals, AI-assisted generation, webhook triggers, and execution inspection are being exposed to users. They validate the need to bring the workflow domain to the foreground, but they do not invalidate your Temporal-centric backend. citeturn11search0turn11search1turn35search3turn28search2turn3search1turn4search0turn30search0turn10search0

### Verdict on the overall architecture

The right conclusion is not “replace Serverless Workflow and Temporal”. The right conclusion is: **keep the foundation, but make it more AI-native at the edges**. Concretely, that means adding structured output, budget and policy controls, artifact references, transform and validation steps, and richer execution surfaces on top of a durable core that is already broadly validated by market direction. citeturn7search0turn15search2turn6search4turn31view1turn12search0turn18search0

## Modelling and schema design

### The right answer on `kind + Struct`

Your current `kind + Struct` discriminated-union pattern is a good **storage and compatibility** choice, but a poor **developer and product ergonomics** choice if left untyped. `google.protobuf.Struct` is explicitly a dynamically typed JSON-like object, and the protobuf documentation says a custom typed message should be preferred if you do not intend to parse arbitrary JSON. By contrast, protobuf `oneof` gives generated discriminated-union APIs and presence checks, but protobuf’s own guide highlights backward-compatibility hazards when adding or removing oneof fields, and oneofs cannot directly contain repeated or map fields without wrapper messages. citeturn21view0turn21view1turn20view0turn20view1turn20view2

That leads to a clear recommendation: **keep `kind + Struct` as the persisted/publicly extensible envelope, but add a first-class schema registry and typed projections for each task kind**. In practice, each `kind` should have all of the following: a canonical typed proto, a JSON Schema for UI generation and validation, example payloads, a renderer/editor descriptor, and a server-side validator. This gives you forward extensibility like n8n/Conductor-style node registries, while avoiding the “opaque blob” problem that kills editor quality and runtime safety. The envelope stays flexible; the per-kind contract becomes strict. This is an inference from protobuf’s typed-vs-dynamic guidance and from how node-based workflow systems expose task metadata and editor schemas. citeturn21view0turn21view1turn20view0turn36search1turn11search8

If you were designing only an internal SDK for a single language and a closed set of tasks, I would lean harder towards `oneof`. But for a workflow domain that needs to round-trip through YAML, APIs, CLI, a future UI builder, and likely third-party extensions, `kind + Struct` is the more future-proof public model. The missing piece is not a different union primitive; it is **typed validation, schema-aware editing, and static reference checking layered on top of the current envelope**. citeturn20view0turn20view2turn21view0

### What to add to the modelling layer immediately

Every task should declare, not merely imply, its input and output contract. The Serverless Workflow DSL itself already has `input`, `output`, `export`, and `then` concepts, and Step Functions now uses JSONata for explicit transformation over state data. Stigmer should copy that spirit more aggressively into the proto model: make `input_schema`, `output_schema`, and `export_schema` normal parts of task definition, and make the builder validate `${...}` references against those schemas rather than only at runtime. citeturn31view1turn8search8

I would also introduce a **task descriptor registry** rather than hard-coding behaviour in many places. Conductor’s system-task model is a useful precedent here: the engine knows which tasks are HTTP, event, human, wait, transform, and LLM-related, and its runtime/UI can treat them differently. Stigmer needs the same pattern so the future UI can render task forms, docs, diff views, examples, and execution inspectors from a single metadata source. citeturn36search1turn36search21

## Foreground UX strategy

### Start with a hybrid product, not a canvas-first product

The strongest recommendation in this report is that Stigmer should **not** make “full visual builder” the first workflow milestone. The best first foregrounding move is a **hybrid workflow experience**: a library/index, a YAML or structured-form editor, a generated graph preview, and a first-class execution viewer. This is closer to GitHub Actions and Temporal in spirit than to pure no-code products, and it suits your developer-heavy audience far better than rushing into a visually editable DAG canvas before you have stable schemas, references, and runtime debugging. GitHub Actions shows the value of a real-time graph for code-defined workflows; Temporal Web UI shows the value of execution history, pending work, relationships, and metadata even without a builder-first experience. citeturn11search2turn11search14turn9search1

That does not mean avoiding visual affordances. It means using them where they deliver the highest leverage first: **previewing topology, showing current branch, showing retries and waits, and surfacing task outputs and errors**. Visual editing can come later, once the task schemas and runtime inspection model are stable. Windmill is a useful directional reference because it mixes code-first surfaces with a flow editor and treats scripts as the base unit under the graph. citeturn11search1turn35search18turn35search6

### The creation experience I would ship

The best workflow creation experience for Stigmer is a **three-lane builder**:

A **template lane**, where users start from prebuilt workflow templates, because template galleries and marketplaces are now standard in tools such as Relevance AI, Langflow, and Flowise. This is especially important because many users do not want to compose orchestration primitives from scratch; they want a starting point for support triage, research, lead qualification, content review, or escalation workflows. citeturn10search0turn10search1turn10search6

A **describe-it lane**, where users can generate a draft workflow from natural language. n8n’s AI Workflow Builder asks users to describe requirements in natural language and then generates and refines a workflow; Zapier Canvas similarly uses AI to generate workflows and suggest next steps; Wordware demonstrates the appeal of a document-like, plain-English authoring surface. The right Stigmer approach is not to hide the DSL, but to let AI generate it and immediately open it into a schema-aware editor. citeturn35search1turn30search0turn4search5turn4search0

A **power-user lane**, where users can edit the YAML or a typed form directly. For Stigmer’s audience, this matters more than in mainstream no-code tools. You already have a declarative domain model and a CLI-first culture. That is an asset. Preserve it. The visual surface should be additive, not substitutive. citeturn11search2turn35search18turn35search14

### The execution experience I would ship

Your execution viewer should combine three synchronized views in a single page: **graph**, **timeline**, and **details/logs**. Step Functions is the best reference for graph plus per-state input/output inspection; Temporal is the best reference for raw execution history and relationships; Inngest is the best reference for waterfall-style traces with timing, retries, and queue phases; Trigger.dev is the best reference for a run log made of logs, spans, and traces. Taken together, they point to a concrete design: a left rail with the workflow map, a centre timeline of task attempts and waits, and a right pane with inputs, outputs, streamed tokens, structured results, retry metadata, and trace links. citeturn9search0turn9search1turn34search17turn9search3

For AI-specific runs, agent-call nodes need more than a green/red status. Langflow’s Playground and OpenAI Agents streaming both underline the value of monitoring partial output, tool calls, and intermediate logic while a run is in progress. For Stigmer, each `agent_call` node should expose live token streaming, tool/MCP calls, model/provider metadata, usage and cost, validator results, and the final structured decision object if one exists. Without that, debugging AI branches will remain guesswork. citeturn28search2turn28search14turn28search9turn18search0

### How workflows should appear alongside agents

The cleanest product model is to make workflows the **automation layer above agents**, not a separate exotic product. Relevance AI’s split between a builder platform and a chat/workbench experience is instructive: creators build agents, tools, and workforces on one side, while users interact through a conversational surface on the other. Stigmer should do something similar: agents remain the interactive specialists; workflows become the repeatable, governable automations that coordinate those specialists. citeturn10search0turn10search8

That means surfacing workflows in four obvious places. In the catalogue, alongside agents, as reusable templates. In the chat UI, as “run this as an automation” or “promote this session to a workflow draft”. In monitoring, as a workflow run list with drill-down into child agent runs. And in the CLI, as a peer to agents: `stigmer run workflow`, `stigmer workflows list`, `stigmer workflows watch`, and `stigmer workflow logs`. This is partly a product inference, but it is grounded in how competing platforms separate creation from execution while keeping them adjacent. citeturn10search0turn16search13turn9search1

## Task model gap analysis

### Fix the agent-output problem first

Today, your branching model depends on evaluating expressions over outputs that may be free-form natural language. That is the most important modelling flaw to fix before broad UI exposure. The industry answer is now clear: **give models a structured-output path whenever their output is intended to drive control flow**. OpenAI and Anthropic both support schema-constrained structured outputs; Instructor provides typed extraction with validation and retries; Guardrails layers output guards and corrective re-asks; and Outlines enforces schema or grammar constraints during generation rather than cleaning up after the fact. citeturn12search0turn12search1turn12search2turn12search3turn13search0turn13search4

The right design for Stigmer is therefore a **dual-channel `agent_call` output model**:

- `final_text`: the human-readable answer.  
- `structured`: a typed JSON object validated against an optional schema.  
- `artifacts`: files, URLs, or object-store references.  
- `tool_trace`: optional tool/MCP/A2A call trace.  
- `usage`: tokens, latency, provider, and cost metadata.  
- `quality`: optional confidence, validator result, or judge verdict.  

That allows `switch_case` to route on `structured.decision`, `quality.confidence`, or validator results instead of parsing prose. This recommendation is directly supported by the structured-output and validation ecosystem above. citeturn12search0turn12search1turn12search2turn12search3

When a provider or agent cannot natively emit typed output, use a separate **extract/transform/validate chain** rather than relying on JQ over raw prose. Flowise’s structured-output tutorial explicitly frames this as necessary whenever model output needs to be passed into HTTP requests or databases. That same principle applies to branching. citeturn29search2turn29search6

### The task types Stigmer should add

The highest-priority new task types are these.

A **`transform`** task. This is the most obvious missing primitive. Step Functions now exposes JSONata transforms, and Conductor ships JSON JQ Transform as a built-in system task. In Stigmer, `transform` should handle JSON reshaping, projections, joins, field extraction, templating, and “claim-check” conversion from large inline payloads to artifact references. This should be a cheap, deterministic task, not something that requires an agent call. citeturn8search8turn36search13turn36search1

An **`approval_gate`** or **`human_input`** task. LangGraph interrupts, Prefect’s interactive workflows, OpenAI Agents human review, Flowise human-in-the-loop, Windmill approvals, n8n human approval for tool calls, and Conductor Human tasks all converge on the same pattern: workflows need a first-class way to stop, collect typed input or approval, and resume safely. This should not be hidden inside agent-level HITL only. It belongs in the workflow domain. citeturn2search0turn27view1turn16search0turn16search6turn17search1turn28search3turn35search2turn35search0turn6search0

A direct **`llm_call`** task. Many workflow decisions are too small to justify a full agent runtime: classification, extraction, moderation, summarisation, scoring, or cheap routing. Conductor already includes LLM-oriented system tasks, and modern structured-output support makes direct model calls reliable enough for these narrow uses. This task should support response schemas, bounded prompts, budgets, and fallback models. citeturn36search1turn12search0turn12search1

A **`validate`** or **`assert`** task. Dagster’s asset checks are a good analogy: workflows benefit from explicit validation nodes that verify properties before downstream actions occur. For AI runs, validation should cover both structural conformance and task-specific expectations. This is how you distinguish “the API call succeeded” from “the model answer is safe and complete enough to continue”. citeturn36search0turn36search8turn13search3turn12search3

An **`emit_event`** task. This is notable because Serverless Workflow itself includes `Emit`, while Stigmer currently has `listen` but no matching event-emission primitive in the task list you described. Adding `emit_event` closes the loop for event-driven orchestration and aligns better with the reference spec. Notifications can be implemented either as a specialised convenience wrapper over `emit_event` or as a thin provider-specific task if you decide that email/Slack/Discord deserve a more approachable UX. citeturn31view0turn31view1

A stronger **batching/concurrency extension** to `for_each`. You likely do not need a separate `batch` task if `for_each` can express `max_parallelism`, `batch_size`, `continue_on_error`, and result aggregation. Large parallel fan-out is common in both Step Functions’ Map state and Inngest’s concurrency controls, so this should be a first-class config in Stigmer even if it stays under the existing task type. citeturn8search12turn23view0turn34search0

### What not to prioritise as first-class tasks

A **mid-workflow `webhook_trigger`** is probably the wrong abstraction. Entry triggers belong at the execution boundary, while mid-flow webhooks are better modelled as a bridge that converts inbound HTTP events into `listen` resumptions or signals. Retool’s webhook triggers are useful precedent for the entry-point side, but internally you already have the more general `listen` concept. citeturn36search3turn31view1

A generic **`cache`** task is also lower priority than it sounds. Caching is usually better modelled as an execution policy on `llm_call`, `agent_call`, `http_call`, or `activity_call`, not as a visible step that users drag into a workflow. Observability platforms such as Langfuse and gateways such as Helicone show that cost, rate, and spend control are increasingly cross-cutting concerns rather than individual steps. citeturn18search0turn18search1

A broad **`data_store`** task should also wait unless your demand clusters around a small number of backends. In the near term, HTTP, gRPC, MCP, and activities already cover most integration patterns. If you later see repeated patterns around SQL, KV, or object storage, you can promote those into typed first-class tasks. citeturn31view1turn32view0

A **`code_execution`** task should be treated as late-stage and high-risk. Wordware exposes code execution because it unlocks flexibility, but it also illustrates why this feature tends to become a gravity well: once users have arbitrary Python/JavaScript execution, they use it for transforms, API glue, unplanned integrations, and logic that should arguably live elsewhere. If Stigmer adds this, it should be explicitly sandboxed, permissioned, and governance-heavy rather than part of the first workflow foregrounding release. citeturn4search7turn11search1

### The autonomy versus orchestration question

The right answer for Stigmer is **hybrid**, but with strong boundaries. CrewAI’s own distinction is helpful here: Flows are deterministic and event-driven, while Crews are more autonomous and collaborative. OpenAI Agents SDK similarly separates orchestration/handoffs from guardrails and human review. That maps well to a platform like Stigmer: the **outer workflow** should remain deterministic, auditable, and policy-driven, while **inner agent steps** can remain adaptive and tool-using within a budgeted envelope. citeturn14search0turn14search8turn14search18turn17search1

In practical terms, I would avoid “dynamic task generation by agents” as a default top-level capability. Instead, let agents choose among tools, sub-agents, or bounded sub-workflows inside an `agent_call`, `llm_call`, or `run_workflow` step, but require the outer workflow to decide when a human must approve, when costs are capped, what fallback path exists, and how final outputs are validated. That is how you preserve enterprise trust while still allowing agentic behaviour where it is useful. citeturn14search18turn14search3turn27view1

### State and context flow

Your current export-based context passing is directionally correct, but it needs stricter scoping and size discipline. Step Functions’ tight payload limits and Temporal’s event-history/storage warnings both show the danger of letting large intermediates accumulate in orchestration state. LangGraph’s checkpointing model also makes clear that state growth affects persistence and replay behaviour. citeturn23view3turn22view0turn27view1

I recommend four state classes in the workflow engine:

- **Control state**: small, typed values used for routing, branching, and policies.  
- **Artifact references**: URIs and metadata for large outputs, transcripts, documents, and files.  
- **Conversation state**: agent/session memory stored externally and referenced, not inlined everywhere.  
- **Observability state**: trace IDs, usage, and run metadata for debugging and cost reporting.  

This is an inference from the limits and persistence models above, but it is the cleanest way to avoid payload bloat while preserving replayability. Wordware’s subflow design is also a useful UX reminder that intermediate data should sometimes be intentionally hidden from parent context to control prompt size and complexity. citeturn23view3turn22view0turn27view1turn4search1

### AI-specific error handling

AI workflows need at least three distinct classes of failure, not one generic “task failed” outcome.

**Operational failures**: timeouts, provider errors, network faults, rate limits. These should use ordinary retry/backoff semantics and possibly model/provider fallback. Trigger.dev, Inngest, Temporal, and Prefect all treat retries and replay as first-class; your engine should too. citeturn34search12turn34search17turn26view0turn16search4

**Structural failures**: malformed JSON, schema mismatch, missing fields, invalid tool arguments. These should trigger structured-output repair, re-ask, or extraction fallback rather than the same generic retry used for provider outages. Guardrails, Instructor, Outlines, and vendor structured-output support all exist precisely for this layer. citeturn12search0turn12search1turn12search2turn12search3turn13search0

**Quality or policy failures**: the model answered, but badly; it hallucinated; it omitted required evidence; it chose an unsafe action; or confidence is too low. This is where explicit validators, LLM-judge patterns, or human escalation belong. OpenAI’s eval guidance, the OpenAI Evals framework, and recent literature on LLM-as-a-Judge all support the idea that evaluation needs its own stage rather than being conflated with execution success. citeturn13search3turn13search7turn13search11

## Prioritised roadmap

### What to build first

First, **ship workflow visibility before workflow authoring**. Add a workflow list, searchable executions table, per-run graph/timeline/log view, trigger/run actions, and links from child agent runs back to the parent workflow. This is the shortest path to making the workflow domain real in the product and mirrors what Step Functions, Temporal, Inngest, and Trigger.dev all treat as core. citeturn9search0turn9search1turn34search17turn34search3

Second, **fix the control-plane semantics of AI outputs**. Add structured outputs to `agent_call`, plus `transform`, `llm_call`, `approval_gate`, and `validate`. Without these, a builder will only magnify the current runtime ambiguity. The industry evidence here is overwhelming: structured outputs, prompt/tool schemas, and human-review checkpoints are now standard expectations rather than advanced extras. citeturn12search0turn12search1turn12search2turn16search0turn17search1

Third, **ship a hybrid editor**, not a full no-code canvas. Start with YAML plus typed side panels generated from task schemas, a live topology preview, and inline validation of expressions and references. Add “generate from prompt” and template cloning into that experience. This is the best fit for your current DSL, your developer audience, and the patterns visible in n8n, Zapier Canvas, Windmill, and GitHub Actions. citeturn35search1turn30search0turn11search1turn11search2

### What to build next

Add **workflow templates and a marketplace-style library**. Relevance AI, Langflow, and Flowise all show that discoverability and reuse matter. In enterprise products, most workflow adoption comes from cloning and adapting a small number of trusted patterns rather than greenfield design. citeturn10search0turn10search1turn10search6

Add **entry triggers and event symmetry**. Expose schedule/webhook/manual triggers clearly in the UI and CLI, and add `emit_event` so users can both wait for and publish workflow-relevant events. This closes an important conceptual gap in the current task set. citeturn36search3turn31view0turn31view1

## 1.4 Temporal is the right durability layer for AI workflows

Temporal maps particularly well to AI-agent workflows because AI agents are long-running, failure-prone, externally asynchronous, and often blocked on humans, tools, or providers.

Your current pattern is correct: the workflow activity extracts a Temporal activity task token, passes it to an external agent execution, returns pending, and later completes the activity by token. Temporal’s Go docs describe this exact async completion pattern: get the activity task token, send it to an external service, return `ErrResultPending`, and then have the external process call `CompleteActivity` with result or error. Temporal is also a good match for:

* **Minutes-to-hours agent calls:** use async activities, heartbeats, timeouts, and cancellation.
* **Human approvals:** use signals/updates plus external approval records.
* **Long waits:** use Temporal timers instead of sleeping workers.
* **Sub-workflows:** use child workflows for agent subruns, batches, or nested workflows.
* **Durable orchestration:** workflow state recovers after worker failure. ([Temporal][7])

### Important Temporal caveats

Temporal is not a free dumping ground for all agent state. Agent transcripts, streaming tokens, tool logs, files, large outputs, and embeddings can blow up payload/history size and make replay/visibility expensive. Temporal community guidance repeatedly recommends storing large payloads externally and passing keys/references, and using `ContinueAsNew` or child workflows when histories grow large. ([Temporal Community Forum][10])

For Stigmer, Temporal should store or coordinate:

* task scheduling decisions
* activity state
* timers
* signals
* child workflow IDs
* compact task results
* artifact references
* summaries/checkpoints

Temporal should not store:

* raw token streams
* full multi-hour transcripts
* large documents
* screenshots
* tool result blobs
* vector data
* unbounded loop state

## 1.5 The `kind + Struct` modeling pattern is understandable, but should not remain the only internal representation

A `kind + config` discriminated-union style is common in workflow DSLs. AWS ASL uses `Type` plus state-specific fields; Conductor tasks use task type plus task parameters; n8n nodes use node type plus parameters; Serverless Workflow uses task shapes in YAML/JSON. So the pattern is not wrong.

The problem is specifically **`google.protobuf.Struct` as the main internal config envelope**.

`Struct` represents arbitrary JSON-like objects; that is useful for DSL ingestion and unknown extension fields, but it removes compile-time guarantees. Protobuf `oneof`, by contrast, is built for “many possible fields, at most one set,” gives generated accessors, and enforces mutual exclusivity. `google.protobuf.Any` gives another extension path by storing an arbitrary serialized message with a type URL. ([Protocol Buffers][4])

### Recommended hybrid model

Use three layers:

1. **Authoring DSL layer**

   * YAML/JSON
   * `kind`
   * JSON Schema validation
   * good error messages
   * UI schema/form generation

2. **Compiled workflow IR**

   * immutable
   * versioned
   * typed
   * validated
   * task graph normalized
   * output schemas resolved
   * environment refs checked
   * budget/retry/timeout policies attached

3. **Proto/API layer**

   * core tasks represented as typed configs, preferably `oneof`
   * extension/custom tasks represented via `Any` or a constrained `Struct`
   * `Struct` allowed only at extension boundaries, not as the internal default

Example shape:

```protobuf
message WorkflowTask {
  string id = 1;
  string name = 2;
  WorkflowTaskKind kind = 3;

  oneof config {
    SetTaskConfig set_vars = 10;
    HttpCallTaskConfig http_call = 11;
    GrpcCallTaskConfig grpc_call = 12;
    AgentCallTaskConfig agent_call = 13;
    LlmCallTaskConfig llm_call = 14;
    ExtractTaskConfig extract = 15;
    ValidateTaskConfig validate = 16;
    HumanInputTaskConfig human_input = 17;
    TransformTaskConfig transform = 18;
    google.protobuf.Any extension_config = 99;
  }

  RetryPolicy retry_policy = 100;
  TimeoutPolicy timeout_policy = 101;
  BudgetPolicy budget_policy = 102;
  string output_schema_ref = 103;
}
```

You can keep YAML compatibility by compiling from `kind + task_config` into this typed representation.

# 3. Task model gap analysis

## 3.1 The central gap: routing on unstructured agent output

Your current model:

* `agent_call` produces unstructured text
* `switch_case` uses expression evaluation
* expressions expect data structure
* agent output is often prose

That means routing will be unreliable unless users manually prompt agents to output JSON and hope it parses.

This is the wrong default.

The industry is moving toward **schema-constrained or schema-validated LLM outputs**. OpenAI Structured Outputs uses JSON Schema and constrained decoding; Instructor wraps multiple providers with Pydantic validation and automatic retries; Guardrails provides validation plus actions like reask, fix, filter, refrain, or exception. ([OpenAI][3])

### Recommended output model for `agent_call`

Add an output contract:

```yaml
- triage_ticket:
    agent_call:
      agent: support_triage_agent
      message: ${ .ticket.description }
      output:
        mode: structured
        schema:
          type: object
          required: [severity, category, customer_impact, rationale]
          properties:
            severity:
              type: string
              enum: [low, medium, high, critical]
            category:
              type: string
            customer_impact:
              type: boolean
            rationale:
              type: string
        on_invalid:
          retry: 1
          then: human_review
```

Then routing becomes:

```yaml
- route:
    switch_case:
      cases:
        - when: ${ .triage_ticket.customer_impact == true and .triage_ticket.severity in ["high", "critical"] }
          then: manager_approval
        - when: ${ .triage_ticket.severity == "low" }
          then: auto_reply
      default: support_review
```

### Recommended decisioning tasks

You need four distinct concepts:

| Concept                        | Purpose                                                       | Why separate                                                     |
| ------------------------------ | ------------------------------------------------------------- | ---------------------------------------------------------------- |
| `llm_call`                     | Simple direct model call for classify/extract/summarize/judge | Cheaper and simpler than full agent                              |
| `extract` / `structure`        | Convert text/artifact into typed JSON                         | Makes routing deterministic                                      |
| `validate` / `assert`          | Check schema/business invariants                              | Prevents bad data from flowing                                   |
| `semantic_switch` / `classify` | Use an LLM to choose a route with structured enum output      | Useful when routing condition is semantic, not purely JSON logic |

Do not make `switch_case` responsible for understanding prose. `switch_case` should evaluate structured state only. If users want semantic routing, make that explicit.

## 3.2 Structured outputs are necessary but not sufficient

Structured output guarantees format, not truth. OpenAI’s Structured Outputs improve schema adherence, but schema adherence does not prove the value is correct. Instructor’s own guidance notes that schema adherence does not eliminate validation/retry needs for useful content, and Guardrails separates validation failures from remediation behavior. ([OpenAI][3])

Therefore, Stigmer should distinguish:

1. **Parse validity** — is it valid JSON?
2. **Schema validity** — does it match schema?
3. **Business validity** — do fields satisfy constraints?
4. **Semantic validity** — is it actually correct?
5. **Safety validity** — is it allowed to continue?
6. **Confidence** — does the system trust the result enough to route?

Add fields like:

```yaml
confidence_threshold: 0.8
on_low_confidence: human_review
on_refusal: fallback_agent
on_invalid_schema: retry_then_extract
on_policy_violation: terminate
```

## 3.3 LLM judge/classifier should exist, but with guardrails

An `llm_judge` or `classify` task is useful for:

* output quality checks
* deciding whether an agent answered the question
* comparing candidate outputs
* deciding escalation
* labeling severity/category
* evaluating hallucination risk
* deciding whether to ask a human

But LLM judges have known reliability/bias issues. 2024–2025 research on LLM-as-judge identifies biases such as position bias, inconsistent evaluation, prompt sensitivity, and reliability gaps. ([Hugging Face][18])

So Stigmer should model judge output as evidence, not absolute truth:

```yaml
llm_judge:
  rubric: ...
  output_schema:
    decision: enum[pass, revise, escalate]
    confidence: number
    rationale: string
  sampling:
    samples: 3
    aggregate: majority
  on_low_confidence: human_input
```

For high-risk workflows, require:

* explicit rubric
* model/version recording
* confidence
* rationale
* optional multi-sample/ensemble
* human escalation threshold
* audit trail

## 3.4 Recommended new task types

### P0: add before serious UI launch

| Task kind                       | Why needed                                                                                        | Maps to current proto pattern                                         |
| ------------------------------- | ------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `llm_call`                      | Direct model call for classification/extraction/summarization/judging without full agent overhead | `LlmCallTaskConfig` with model, prompt, schema, budget, retry         |
| `extract` / `structure`         | Parse agent/tool/text/artifact output into structured JSON                                        | `ExtractTaskConfig` with source expr, schema, method, repair policy   |
| `validate` / `assert`           | Check schema, business rules, required fields, confidence thresholds                              | `ValidateTaskConfig` with schema/rules/on_fail                        |
| `human_input` / `approval_gate` | Workflow-level HITL, not only agent-level approval                                                | `HumanInputTaskConfig` with approvers, form schema, timeout, outcomes |
| `transform` / `map`             | JQ/JSONPath/template transformations between tasks                                                | `TransformTaskConfig` with engine/expression/target                   |
| `notification`                  | Slack/email/Discord/Teams notifications, operational workflows                                    | `NotificationTaskConfig` with channel, template, recipients           |
| `artifact_store`                | Persist large agent outputs, documents, files, traces outside Temporal                            | `ArtifactStoreTaskConfig` or built-in export policy                   |
| `budget_guard`                  | Stop or branch on token/cost/tool budget                                                          | `BudgetGuardTaskConfig` with scope and policy                         |

Orkes Conductor’s system tasks include Human, JSON JQ Transform, Wait, Event, HTTP, Kafka Publish, and Inline JS; Windmill exposes branches, loops, retries, approvals, concurrency, cache, and code; Trigger.dev exposes structured inputs/outputs, HITL, streaming, and Python execution. These are strong signals that your task catalog is missing common production primitives. ([docs.conductor-oss.org][19])

### P1: add after MVP

| Task kind                              | Why needed                                            | Notes                                                                 |
| -------------------------------------- | ----------------------------------------------------- | --------------------------------------------------------------------- |
| `batch`                                | Process items with batch size and concurrency control | Needed for enrichment, extraction, scraping, evals                    |
| `poll_until` / `delay_until_condition` | Wait for external condition with timeout/backoff      | Prefer event/signal when possible; polling as fallback                |
| `cache`                                | Avoid repeated expensive LLM/API calls                | Must include key, TTL, scope, invalidation                            |
| `code_execution`                       | Python/JS sandbox for transformations/custom logic    | High security risk; require sandbox, network policy, secret isolation |
| `data_store`                           | Read/write KV/database records                        | Start with managed Stigmer KV/artifact metadata                       |
| `webhook_event` / `await_webhook`      | Mid-workflow callback/correlation                     | Distinguish from workflow trigger                                     |
| `rate_limit`                           | Respect provider/API concurrency and rate limits      | Important for forks/batches                                           |
| `compensate`                           | Saga-style undo for side effects                      | Needed for real business workflows                                    |

Windmill and Wordware both support code execution, but Wordware explicitly warns about prompt injection risk when code interacts with LLM-controlled variables, which is why this should be P1/P2 with sandboxing rather than MVP. ([Wordware][20])

| Task kind                         | Why needed                                                         |
| --------------------------------- | ------------------------------------------------------------------ |
| `plan_and_execute`                | Let an agent propose a bounded sub-plan, validate it, then execute |
| `agent_handoff`                   | Let one agent hand off to another with structured context          |

| `memory_write`                    | Persist facts/summaries to memory store                            |
| `stream_emit`                     | Emit progress/events/artifacts to UI or downstream systems         |
| `tool_policy_check`               | Decide whether a tool call/action is allowed                       |
| `redact`                          | Remove PII/secrets before passing data to model or UI              |

## 3.6 Agent autonomy vs workflow orchestration

There are four useful modes:

### Mode A: strict orchestration

The workflow decides everything. Agents are called as bounded tasks.

Best for:

* enterprise automation
* compliance
* side effects
* customer-facing workflows
* deterministic approvals

### Mode B: semantic routing

The workflow owns the graph, but an LLM classifier or agent output chooses a branch.

Best for:

* triage
* prioritization
* escalation
* content classification

LangGraph conditional edges are the reference pattern: a routing function reads current state and returns the next node(s). ([LangChain Docs][23])

### Mode C: agent-planned, workflow-executed

An agent proposes a structured plan, Stigmer validates it against schemas, policies, budgets, and allowed task types, then the workflow executes it.

Best for:

* flexible research workflows
* support investigations
* ops runbooks
* semi-structured automations

### Mode D: autonomous inner agent loop

The workflow calls a LangGraph/CrewAI/AutoGen-style agent loop as a child run, with max steps, budget, timeout, tool permissions, and HITL policies.

Best for:

* exploratory tasks
* multi-agent collaboration
* tool-heavy reasoning
* tasks where rigid orchestration is premature

CrewAI explicitly separates **Flows** for structured event-driven control and state from **Crews** for autonomous collaborating agents; AutoGen AgentChat uses teams/group chats with termination conditions such as max messages, token usage, timeout, text mentions, and handoff; OpenAI Swarm used agents and handoffs but is now described by OpenAI as educational and replaced by the production Agents SDK. ([CrewAI Documentation][24])

### Recommendation for Stigmer

Make **Mode A and B the default**. Support Mode C behind a `plan_and_execute` task. Allow Mode D by running an agent graph as an `agent_call` child workflow/subtrace with strict limits.

The workflow should own:

* durability
* state boundaries
* approvals
* budgets
* retries
* side-effect policy
* execution trace
* RBAC/audit
* external triggers

Agents should own:

* local reasoning
* tool selection within permissions
* summarization
* extraction/classification when explicitly requested
* proposing plans, not silently mutating the workflow graph

Academic evidence supports caution: 2024–2025 surveys show rapid progress in LLM agents and multi-agent systems, but a 2025 failure-taxonomy study found multi-agent systems fail through specification issues, inter-agent misalignment, and task verification problems. ([Springer][25])

## 3.7 Context/state flow

Your current export model is good for simple workflows:

```yaml
export:
  as: ${ . }
```

and:

```yaml
${ $context.taskName.field }
```

But it is not sufficient for production AI workflows because agent outputs can be large, sensitive, unstructured, streaming, and semantically reusable.

### Recommended state model

Use four layers:

1. **Workflow context**

   * small typed JSON
   * branch decisions
   * IDs
   * structured task outputs
   * summaries
   * artifact references

2. **Task-local state**

   * raw input/output
   * prompt/rendered variables
   * retry attempts
   * validation errors

3. **Artifact store**

   * large text
   * documents
   * transcripts
   * screenshots
   * CSVs
   * tool blobs
   * model streams
   * logs

4. **Memory/index layer**

   * vectorized facts
   * cross-run memory
   * summarized context
   * agent memory

Temporal community guidance around payload/history size strongly supports this: store large payloads outside Temporal and pass references. ([Temporal Community Forum][10])

### Type safety

Add:

* declared workflow input schema
* declared workflow output schema
* each task output schema
* schema-aware expression editor
* autocomplete for `$context`
* compile-time validation of context references
* UI warnings when referencing raw text in `switch_case`
* data lineage from task output to downstream input

CrewAI Flows support both unstructured state and structured Pydantic state; LangGraph checkpoints preserve state snapshots, next nodes, metadata, writes, and tasks; these are useful references for Stigmer’s state model. ([CrewAI Documentation][21])

## 3.8 AI-specific error handling

Generic `try_catch` is necessary but not enough. AI workflows need classified failures.

Recommended failure taxonomy:

| Failure class           | Example                         | Default handling                     |
| ----------------------- | ------------------------------- | ------------------------------------ |
| `provider_rate_limit`   | model API 429                   | backoff, fallback provider           |
| `provider_error`        | 5xx from model provider         | retry with cap                       |
| `timeout`               | agent exceeds wall time         | cancel, summarize partial, escalate  |
| `tool_error`            | MCP tool fails                  | retry idempotently or alternate tool |
| `schema_invalid`        | output not valid JSON/schema    | repair/reask/extract                 |
| `low_confidence`        | classifier unsure               | human review                         |
| `model_refusal`         | safety refusal                  | branch/refine/human                  |
| `budget_exceeded`       | token/cost cap reached          | stop, cheaper model, human           |
| `quality_failed`        | judge says answer insufficient  | revise/retry/escalate                |
| `human_rejected`        | approval denied                 | branch/rework/terminate              |
| `side_effect_uncertain` | API may have partially executed | compensate/reconcile                 |
| `policy_violation`      | tool/secret/action not allowed  | terminate/audit                      |

Guardrails’ remediation taxonomy—reask, fix, filter, refrain, exception—is a useful model for `schema_invalid` and `quality_failed` outputs. ([Guardrails AI][26])

### Cost-aware retry

Do not blindly retry expensive `agent_call` tasks.

Each task should have:

* `max_attempts`
* `max_cost`
* `max_tokens`
* `retry_on`
* `do_not_retry_on`
* `fallback_model`
* `fallback_agent`
* `on_exhausted`

AutoGen’s termination conditions include max messages, token usage, timeout, text mention, and handoff; these are useful guardrails for autonomous agents inside workflows. ([Microsoft GitHub][27])

# 4. Architecture risks and mitigations

## Risk 1: routing on freeform text

**Severity:** Critical
**What can go wrong:** workflows take wrong branches because prose changes, JSON is malformed, or agent output is ambiguous.
**Mitigation:** add `output_schema` to `agent_call`, plus `extract`, `validate`, `llm_call`, and `semantic_switch`.

## Risk 2: `Struct` everywhere weakens safety

**Severity:** High
**What can go wrong:** runtime config errors, weak SDKs, poor UI forms, migration ambiguity, inconsistent task config validation.
**Mitigation:** use typed configs internally; generate JSON Schema/UI Schema for authoring; constrain `Struct` to extension boundaries.

## Risk 3: Temporal history/payload bloat

**Severity:** High
**What can go wrong:** replay latency, large histories, storage costs, failures from oversized payloads, slow UI.
**Mitigation:** external artifact store, summaries in context, child workflows for large subruns, Continue-as-New for loops/batches. ([Temporal Community Forum][10])

## Risk 4: agent call is a black box

**Severity:** High
**What can go wrong:** users cannot debug why an agent failed, which tool was called, where cost went, or why output changed.
**Mitigation:** nested agent subtraces with model calls, tool calls, MCP events, streams, approvals, artifacts, costs.

## Risk 5: HITL modeled only inside agents

**Severity:** High
**What can go wrong:** workflows need approvals at non-agent steps: before API calls, publishing, customer messages, transactions, or retries.
**Mitigation:** add workflow-level `human_input` / `approval_gate`. Use external approval records and Temporal signals/updates, not only long-lived activity tokens. Temporal community discussion on human tasks warns about modeling issues with task tokens alone and points toward signal/update patterns. ([Temporal Community Forum][28])

## Risk 6: visual builder becomes a spaghetti canvas

**Severity:** Medium
**What can go wrong:** complex workflows become unreadable.
**Mitigation:** support subworkflows, collapsible groups, swimlanes, templates, auto-layout, YAML/code view, and execution-first debugging.

## Risk 7: dynamic task generation breaks governance

**Severity:** High
**What can go wrong:** agent generates arbitrary steps, calls unauthorized tools, exceeds budget, or creates nondeterministic execution.
**Mitigation:** only allow dynamic plans through `plan_and_execute` with schema validation, allowlisted task kinds, budget, RBAC, and optional approval.

## Risk 8: code execution opens security holes

**Severity:** High
**What can go wrong:** prompt injection, data exfiltration, secrets leakage, arbitrary network access.
**Mitigation:** delay to P1/P2; sandbox; disable network by default; explicit secret mounts; deterministic packages; audit logs. Wordware’s code execution docs explicitly warn about prompt injection risk. ([Wordware][20])

## Risk 9: Serverless Workflow maturity

**Severity:** Medium
**What can go wrong:** spec changes, incomplete runtime semantics, mismatch with AI needs.
**Mitigation:** use CNCF SWF as authoring/interchange influence; keep Stigmer IR as your stable internal contract. CNCF classifies Sandbox as early-stage/experimental relative to Incubating/Graduated maturity. ([CNCF][29])

## Risk 10: cost explosions from forks, retries, and agent loops

**Severity:** High
**What can go wrong:** a parallel workflow fans out to many expensive model/tool calls.
**Mitigation:** workflow-level and task-level budgets, concurrency caps, rate limits, cache, max agent steps, token caps, live cost meter.

## Risk 11: UI generated workflows leak secrets or sensitive context to builder LLM

**Severity:** High
**What can go wrong:** AI workflow generator sees credentials, private data, or past execution secrets.
**Mitigation:** follow n8n’s pattern: send node/workflow structure and mock execution data, not credentials or sensitive prior executions. ([n8n Docs][12])

## Risk 12: workflow DSL uses ordered task list where graph semantics are needed

**Severity:** Medium
**What can go wrong:** branching, fork, jump, and flow-control become hard to visualize and validate.
**Mitigation:** compile ordered list to an explicit graph IR with stable task IDs, edges, branch labels, and layout metadata.

# 6. Specific recommendations for Stigmer

## 6.1 Keep the architecture, but reposition it

Position Stigmer Workflows as:

> Durable, observable, deployable agent applications.

Not merely:

> YAML automation workflows.

That framing makes workflows the natural next layer above agents.

## 6.2 Add task output contracts everywhere

Every task should have:

* declared output schema
* actual output preview
* export path
* validation result
* artifact references
* cost/timing metadata

For `agent_call`, make structured output optional but strongly encouraged. For `switch_case`, warn if routing on raw text.

## 6.3 Make `human_input` first-class

Agent-level HITL is not enough. Workflows need approval gates at any point.

Use Temporal signals/updates or a signal-backed external approval record. Avoid treating a long-lived human approval purely as an activity token problem; Temporal community discussion around human tasks points toward signal/update/external-task modeling. ([Temporal Community Forum][28])

## 6.4 Build a real execution trace model

A Stigmer execution trace should contain:

* workflow events
* Temporal IDs
* task events
* agent events
* model calls
* tool calls
* MCP calls
* streaming deltas
* artifacts
* approvals
* cost
* retries
* validation failures

Do not expose raw Temporal history as the main UX. It is too low-level.

## 6.5 Move toward typed task configs

Do not break current DSL immediately. Instead:

1. keep YAML `kind + task_config`
2. validate via JSON Schema
3. compile to typed configs
4. store compiled spec
5. expose typed configs via API/SDK
6. reserve `Struct` for unknown extensions

## 6.6 Treat workflows and agents as mutually composable

Support:

* workflow calls agent
* agent invokes workflow as a tool
* workflow calls subworkflow
* workflow can be published as “agent app”
* agent chat can become workflow draft
* workflow run can open agent session trace

## 6.7 Add budget as a core primitive

At minimum:

```yaml
budget:
  max_cost_usd: 5.00
  max_tokens: 250000
  max_agent_steps: 20
  max_parallelism: 10
  on_exceeded: human_input
```

Budget should be visible in UI and enforced in runtime.

## 6.8 Add “workflow templates” before a marketplace

Start with curated internal templates. Later add marketplace/community sharing. Relevance AI, Langflow, and OpenAI Agent Builder all use templates as onboarding accelerators. ([Relevance AI][34])

# 7. Final answer to the three research areas

## Area 1: architecture validation

**Validated with caveats.** Serverless Workflow + Temporal is a defensible and strong foundation. Temporal is especially well suited to AI-agent workflows because of long-running async activities, timers, signals, child workflows, retries, and durable recovery. CNCF Serverless Workflow gives you portable DSL vocabulary, but it should not constrain the Stigmer AI-specific task model.

The major architecture changes I would make before building a big UI are:

* introduce compiled typed Workflow IR
* add task schema registry
* move core configs away from raw `Struct`
* add structured output contracts
* add artifact store
* add domain execution event stream
* add workflow-level HITL and budget primitives

## Area 2: UI/UX strategy

Start with:

1. workflow list/detail
2. YAML editor with graph preview
3. execution viewer
4. run workflow from UI
5. agent-chat-to-workflow conversion
6. templates

Then build the visual canvas.

The execution viewer should be the hero feature: graph, timeline, task IO, agent stream, cost, artifacts, approvals, errors, retries, and debug controls.

## Area 3: task model completeness

Your 13 tasks cover classic workflow control flow reasonably well. The missing AI-first tasks are:

* `llm_call`
* `extract` / `structure`
* `validate` / `assert`
* `human_input` / `approval_gate`
* `transform`
* `notification`
* `artifact_store`
* `budget_guard`
* `batch`
* `cache`
* `poll_until`
* `code_execution`
* `semantic_switch` / `classify`
* eventually `plan_and_execute`, `memory_recall`, `memory_write`, `eval`, and `agent_handoff`

The highest-priority fix is not adding every task. It is making **agent output typed, validated, and routable**.

# Bottom line

Stigmer should not pivot away from its current architecture. It should **complete the missing AI orchestration layer** on top of it.

The winning product shape is:

> Temporal-backed durable workflows, authored visually or as YAML, deployed as WorkflowInstances, executed with full agent-aware traces, with structured LLM outputs, human approvals, budgets, artifacts, and typed routing.

The most important immediate build order is:

1. typed workflow IR and task schema registry
2. structured agent/LLM output handling
3. artifact store and execution event stream
4. workflow execution viewer
5. workflow-level human input/approval
6. YAML editor with graph preview
7. visual builder
8. AI-assisted workflow generation

This path gets workflows into the foreground with the least architectural regret.
