## Design Decision

**Option B (Minimal, Honest)** was selected after architectural analysis of three options:

- **Option A (Full pass-through)**: Extend `ExecuteCursorActivity` to receive `SessionContext`. Rejected because the cursor-runner already needs `getSession()` for blueprint resolution -- passing memory through Temporal would duplicate data the runner already has via the same gRPC call.
- **Option B (Observability + Forward-compat)**: Replace `readSessionThreadId` with `readSessionContext` in the workflow. The activity signature stays unchanged. Memory and cursorMode are logged for observability and available for Task 4 (cloud mode dispatch).
- **Option C (Hybrid)**: Add optional sessionMemoryJson parameter. Rejected as unnecessary complexity given the runner's existing data access pattern.

The honest engineering assessment: the original plan assumed the cursor-runner would NOT have its own `getSession()` call for memory, but it does (and must, for blueprint resolution). Option B acknowledges this reality.

## Observations

- The existing `InvokeAgentExecutionWorkflowSignalTest.java` only tests the Graphton flow and passes `AgentExecution` to a workflow expecting `InvokeAgentExecutionWorkflowInput`. This type mismatch suggests the test may rely on Temporal's lenient deserialization or may not be actively running in CI. Left untouched since the Graphton flow is unaffected by this change.
- The `readSessionThreadId` method on the activity interface is already marked `@Deprecated` (done in Task 6). It remains callable for in-flight workflow replay via the version guard.
- The TS cursor-runner activity signature (`ExecuteCursor: async (executionId, threadId)`) only declares 2 params while the Java interface has 3 (`executionId, threadId, invokerIdentityAccountId`). The third param is sent by Java but silently dropped by the TS activity registration. This pre-existing mismatch is noted but not addressed in this task.
