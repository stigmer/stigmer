# Safely Resuming AI Agent Tool Execution After Long Human-in-the-Loop Idle Periods

## Executive summary

For your specific scenario, the safest and most robust answer is **not** to treat a month-late approval as permission to blindly execute the original tool call. Across the frameworks I reviewed, the strongest durable-resume models all preserve **explicit workflow state** rather than some opaque “live LLM mind”. LangGraph checkpoints graph state and resumes with the same `thread_id`; Temporal keeps Workflow state durably and waits for Signals for hours, days, or indefinitely; CrewAI Flows can pause for human feedback and persist or checkpoint state; AutoGen can save and load team or agent state between runs; and the Cursor SDK can reattach to an existing agent by ID, but its documented primitives do **not** include a first-class “approve and execute this exact previously blocked tool call” API. OpenAI’s old Assistants API is now deprecated, and its `requires_action` model is about submitting tool outputs into a run that can also expire, which makes it a poor foundation for month-long pending approvals. citeturn27view0turn27view1turn27view2turn38view0turn38view1turn41view0turn43view0turn47view0turn15view0turn17view0turn31search20turn34search0turn35search4

The practical implication is that **Pattern C: hybrid execution** is the right default for your architecture: use **blind execution only for tightly scoped, idempotent, low-risk operations with strong preconditions and a short time-to-live**, and use **re-derivation with pre-flight validation** for destructive or externally stateful operations such as `git push`, database migrations, file deletion, network writes, or any action whose safety depends on current workspace state. Even checkpoint-first systems do not eliminate stale-world risk: they restore control state, but the outside world may have changed, which is exactly why LangGraph stresses determinism, replay discipline, and isolation of side effects into tasks, and why Temporal models approvals as external signals into durable workflows rather than as an invitation to replay side effects blindly. citeturn27view2turn28view0turn28view4turn47view0turn47view1turn47view2

For **Cursor SDK + Temporal + MongoDB + Daytona**, my recommendation is to make **Temporal the source of truth for approval state**, **MongoDB the source of truth for evidence and replay bundles**, and **Cursor an execution harness rather than the durable memory layer**. When an approval arrives after a long idle, the workflow should first run **drift checks** in the sandbox, classify the tool by risk, and then either execute directly or spin up a fresh agent with a tightly structured continuation prompt that asks it to confirm, revise, or refuse the action based on the **current** workspace. That design aligns with the strongest documented capabilities of the surveyed frameworks and avoids depending on undocumented Cursor semantics. citeturn47view0turn15view0turn17view0turn21view0turn22view3turn43view0turn43view2

## Framework-by-framework findings

**Cursor SDK.** The official SDK defines an **Agent** as a durable container for conversation state, workspace config, and settings, and documents `Agent.resume(agentId)` for reattaching to an existing agent. It also exposes `run.conversation()` for structured run history, a `"request"` stream event for “awaiting user input or approval”, and `"tool_call"` events for tool lifecycle updates. However, the same docs also note that tool-call payload schemas are **not stable**, that resumed agents do not automatically restore everything such as `model` or inline `mcpServers`, and I did **not** find any documented SDK API that says “execute the previously denied tool call with `call_id=X`”. That means Cursor’s documented story is **reattach if the agent still exists**, not **resurrect an evicted approval point from database state**. citeturn16view0turn17view0

Cursor’s hooks are important here. `preToolUse` can return `allow`, `deny`, `user_message`, `agent_message`, and `updated_input`, but the docs explicitly say that `"ask"` is **accepted by the schema but not enforced for `preToolUse` today**. By contrast, `beforeShellExecution` and `beforeMCPExecution` do support `allow | deny | ask`. So if you want a real first-party approval gate in Cursor today, the documented place to enforce it is **before shell or MCP execution**, not `preToolUse`. That is a subtle but critical finding for your architecture, because it means a generic pre-tool approval abstraction may not map cleanly to Cursor’s current enforced semantics. citeturn22view0turn22view2turn22view3

Cursor’s runtime choice also matters. The docs describe local agents as running **inline in your Node process**, whereas cloud agents run in an isolated VM and are explicitly positioned for runs that should **survive the caller disconnecting**. The CLI docs similarly describe a “Cloud Agent handoff” so work can keep running while you are away. That suggests cloud/self-hosted Cursor runtimes are the closest first-party path to native session continuity, but even there, the public SDK docs still do not document an approval-specific, exact-tool replay primitive. citeturn15view0turn15view2turn15view3

**LangGraph.** LangGraph has the cleanest documented long-delay HITL semantics of the frameworks reviewed. Its `interrupt()` API pauses execution, saves graph state through the persistence layer, and “waits indefinitely” until resumed. Resumption is explicit: you call the graph again with `Command(resume=...)` and the **same `thread_id`**, and execution continues from the checkpointed thread. LangGraph’s docs also make clear that its checkpoint is a `StateSnapshot` containing explicit state values, metadata, next nodes, and tasks/interrupts—not hidden model activations. That is exactly the capability you want for month-late approval **if** your approval boundary lives inside the LangGraph runtime. citeturn27view0turn27view1turn28view0turn28view3turn45search0

LangGraph’s advanced HITL middleware goes further than a simple approve/reject gate. It supports `approve`, `edit`, `reject`, and `respond`, so a human can approve the tool call as-is, modify it before execution, reject it with feedback, or answer an “ask user” style tool directly. That is a materially richer model than most other frameworks. Its production guidance also stresses that durable execution depends on determinism and idempotency, and that side effects must be wrapped in tasks because resumption **replays** from a safe restart point rather than resuming from a raw CPU instruction pointer. That means LangGraph solves “how do I restore my workflow state?” better than almost anyone, but it still does **not** make stale side effects safe on its own. citeturn27view3turn27view2turn45search1turn45search3

**OpenAI Assistants and Responses.** The Assistants API is now officially deprecated and scheduled for removal in **August 2026**, with OpenAI recommending the **Responses API** instead. In the old Assistants model, `requires_action` means the run is waiting for tool outputs via `submit_tool_outputs`, and the streaming docs include both `thread.run.requires_action` and `thread.run.expired` events. In other words, Assistants’ tool-calling pause is fundamentally about the application submitting tool results back into the run, and the run lifecycle itself can expire. That makes Assistants unsuitable as the durable, month-long approval substrate for your use case. citeturn31search20turn30search0turn32search5turn34search0

The Responses API is the modern equivalent, and its docs describe a multi-step function-calling loop where the application sends tools, receives a tool call, executes code on the application side, and then makes a second request with the tool output. OpenAI also now provides **Conversations** for storing and retrieving conversation state across Response API calls, and the migration guide notes that Responses lets you manage conversations rather than passing `previous_response_id` around. That is useful for state management, but it still leaves **approval durability** in the application layer. Put bluntly: with OpenAI APIs, the durable HITL logic belongs in your orchestration tier, not in the API provider’s run object. citeturn35search3turn35search4turn36search7turn35search0turn35search2

**AutoGen.** AutoGen has two distinct patterns. During a run, `UserProxyAgent` can provide feedback, but the docs warn that this blocks execution and leaves the team in an **unstable state that cannot be saved or resumed**; they recommend using that only for short interactions needing immediate feedback. For asynchronous human input, the documented pattern is different: let the team **terminate**, save its state, put it in persistent storage, and resume later when feedback arrives by starting the next run with the preserved team state. Assistant state is explicitly documented as the model context, and team state includes message threads and agent states. That means AutoGen supports **stateful continuation across runs**, but not a native, durable mid-tool approval checkpoint comparable to LangGraph interrupts. citeturn38view0turn38view1turn39view1turn39view2

**CrewAI.** CrewAI’s production direction is clearly **Flow-first**. Its docs recommend wrapping crews inside flows because flows provide state management, control, and observability. For HITL, the `@human_feedback` decorator pauses a flow, shows output to a human, collects feedback, and can route to different listeners. CrewAI also documents explicit persistence with `@persist()` and early-release checkpointing that can resume from the last completed task or method without rerunning completed work. In AMP, `/resume` accepts an `execution_id`, `task_id`, human feedback, and approval flag, and that human feedback is incorporated as **additional context for subsequent task executions** rather than being framed as “execute this exact stale tool call verbatim”. That is a strong signal that CrewAI’s production design leans towards **resume with refreshed context**, not blind replay. citeturn41view3turn41view0turn41view1turn43view0turn43view1turn43view2

CrewAI also provides one of the clearest public production examples of long-delay HITL mechanics. Its enterprise “Flow HITL Management” is email-first, can notify external responders, can pause at review points, supports dashboard/API/email responses, and can auto-respond after a timeout. It even documents that response tokens in email replies expire after **7 days**. That is not your exact stack, but it is a concrete example of a production product treating HITL as a durable orchestration problem with explicit timeout and routing rules rather than as a latent LLM memory problem. citeturn44view0

**Temporal.** Temporal is the strongest orchestration substrate in your stack for bridging long idle periods. Its AI cookbook HITL example models approvals as **Signals** into a waiting workflow, emphasising that the workflow can wait for hours, days, or indefinitely while consuming no compute, that timers are durable, and that the workflow retains a complete audit trail. Temporal’s general message-passing docs add an important engineering constraint: Signals, Updates, and Queries operate against the workflow’s **current state**, and handlers must be written to be robust, re-entrant, and idempotent. This is exactly the right place to own the “pending approval” state machine for your platform. citeturn47view0turn47view1turn47view2

**Public production examples.** The clearest public examples I found are mostly vendor or framework documentation rather than independent postmortems: LangGraph Deep Agents explicitly market “indefinite interrupts” and safe audit/recovery around sensitive operations; CrewAI Enterprise documents email-first HITL review and auto-response policies; and Temporal ships a cookbook for agent approval via signals that can pause for days or indefinitely. I did **not** find many public, independent case studies specifically about “a coding agent waited a month for approval and then resumed”, so some of the design guidance below is necessarily a synthesis of framework mechanics plus well-established workflow-safety practice rather than a large body of public incident literature. citeturn45search1turn45search3turn44view0turn47view0

## What actually breaks after long idle periods

The central failure mode is not only “lost context”; it is **stale justification**. A month later, the workspace, branch tip, file contents, credentials, reviewer intent, surrounding tickets, deployed environment, and even tool semantics may all have changed. The surveyed frameworks reinforce that point indirectly. LangGraph’s docs repeatedly frame durable execution around reproducibility, checkpoint state, and idempotent handling of side effects. CrewAI’s checkpointing resumes from the last completed unit of work. Temporal’s workflow waits efficiently and receives a fresh signal into current workflow state. None of these frameworks claim that restoring workflow state also restores the external world that made the action safe in the first place. citeturn27view2turn28view0turn28view4turn43view0turn47view0turn47view1

That is why the HITL case is harder than a normal “user sent a new message” continuation. In a normal continuation, the new user input gives the fresh agent an updated objective. In a delayed approval case, the new input is often only **“approved”**, which contains almost no semantic guidance. If you resume naively, the fresh agent must infer not only *what* to do, but *why the original call was correct*, *which assumptions still need to hold*, and *whether the human meant to approve the original tool call exactly as proposed or merely the underlying intent*. The more destructive the tool, the less acceptable it is to resolve those ambiguities by approximation. That inference is consistent with the stronger frameworks’ bias towards explicit state, explicit resume inputs, and explicit human decisions such as `approve`, `edit`, `reject`, and `respond`. citeturn27view3turn45search0turn43view1

There is also a subtle but important distinction between **checkpoint fidelity** and **world fidelity**. LangGraph can checkpoint the exact graph state. AutoGen can save model context and message threads. Cursor can persist conversation state while the agent still exists. But if the repository HEAD changed, a DB schema advanced, or credentials rotated, an exact checkpoint may be **more dangerous**, not less, because it can recreate the original decision boundary while hiding that the world has moved on. That is why even checkpoint-capable systems must run **pre-flight validation** before any delayed, stateful side effect. citeturn28view0turn39view2turn15view0turn17view0turn27view2

## Recommended architecture for Cursor plus Temporal plus MongoDB plus Daytona

The right mental model is that **Temporal owns lifecycle**, **MongoDB owns evidence**, **Daytona owns the resumable workspace**, and **Cursor owns reasoning/execution within a bounded session**. Do not make Cursor the source of truth for approval continuity. Its docs support reattachment to an existing agent, but not reconstruction of a semantically exact pending approval point after the agent has disappeared. Temporal, by contrast, is explicitly built to preserve workflow state across days or longer and to accept eventual approval signals safely and durably. citeturn17view0turn47view0turn47view1turn47view2

A good production state machine for each sensitive action is:

1. **Proposal phase.** Agent proposes a tool call. The platform captures an **approval bundle** in MongoDB: tool name, normalised args, workspace identity, repo URL, branch, HEAD SHA, dirty-tree fingerprint, relevant changed files, recent transcript excerpt, session summary, explicit agent-visible justification, and a risk class.  
2. **Pause phase.** Temporal workflow enters `PENDING_APPROVAL` and sets an approval TTL plus optional escalation timer.  
3. **Approval phase.** Human responds via UI. Temporal records approver identity, timestamp, and decision.  
4. **Pre-flight phase.** Before anything else, a Temporal activity runs a fresh drift check in Daytona: verify repo identity, branch/head drift, diff since proposal, relevant file existence, migration state, credential scope, and any domain preconditions.  
5. **Decision phase.** A deterministic policy decides:  
   - if risk is low and all preconditions still match, execute directly;  
   - otherwise start a fresh Cursor/agent session with a continuation prompt and ask it to **confirm, revise, or decline** the action.  
6. **Execution phase.** Perform the tool call through an app-owned activity or through the agent, then persist outputs and audit data.  
7. **Closure phase.** Mark approval as consumed so a replay or duplicate click cannot execute the side effect twice.  

That design borrows the strongest parts of Temporal’s signal-driven waiting, LangGraph’s checkpoint-minded explicit state, and CrewAI’s persisted pause/resume model, while working around Cursor’s current lack of a documented exact-tool approval replay primitive. citeturn47view0turn47view1turn27view1turn27view3turn43view0turn43view1

For **tool classification**, I would use three classes. **Class green**: pure reads and deterministic local computations, or writes that are demonstrably idempotent and reversible. **Class amber**: workspace-mutating operations whose correctness depends on current repo state, such as code generation into files, branch creation, or local refactors. **Class red**: irreversible or externally visible actions such as `git push`, database migrations, secret rotation, deletions, payments, emails, production shell commands, or destructive MCP actions. Green may blind-execute with tight checks and short TTLs; amber should usually re-derive after meaningful drift; red should **always** re-derive after any non-trivial delay and often require a second explicit confirmation if drift is detected. This is a platform policy recommendation, but it is squarely aligned with the way LangGraph, CrewAI, and Temporal all frame human approval around sensitive operations rather than trying to hide risk behind full-state resumption. citeturn27view3turn47view0turn44view0

One further recommendation: where possible, refactor “dangerous tool calls” into **app-owned canonical tools** rather than letting the coding agent emit raw shell for everything. For example, prefer `push_branch(repo, expected_head, remote, force=false)` over arbitrary `git push ...`, and `run_migration(migration_id, expected_schema_version)` over free-form database shell access. Cursor’s hooks can still gate raw shell or MCP use, but your long-idle resumption story becomes much safer when the operation itself carries typed preconditions that your platform can validate without an LLM. This recommendation is consistent with Temporal’s agent cookbook, which explicitly frames the real action as an activity invoked by the workflow after approval. citeturn47view0turn21view0turn22view3

## Safety rules and implementation templates

The most important safety rule is simple: **approval should authorise intent, not stale execution**. An approval recorded on 9 April should not automatically authorise a force-push on 9 May unless your platform has independently verified that the preconditions captured on 9 April are still true on 9 May. The stronger the side effect, the more your workflow should treat approval as permission to **re-check and proceed if still valid**, not as a standing order to replay bytes. That principle follows directly from the state-orchestration emphasis across LangGraph, CrewAI, and Temporal, and from the lack of any surveyed framework that claims to make delayed world-state drift disappear. citeturn27view2turn43view0turn47view0

You should therefore store an **approval memo** rather than attempt to store or replay hidden chain-of-thought. None of the surveyed systems restore opaque model activations. What they persist are explicit artefacts such as graph state, message histories, model context, or workflow state. Your memo should therefore contain: the proposed action; why it was needed; what evidence the agent observed; which assumptions had to hold; what objects would be touched; whether the action is idempotent; what rollback exists; and what freshness TTL applies. That memo is stable, reviewable, auditable, and model-agnostic. citeturn28view0turn39view2turn17view0turn35search3

A practical **continuation prompt** for re-derivation after approval looks like this:

```text
System:
You are resuming a previously paused agent task after delayed human approval.
Your job is NOT to blindly execute the prior action.
Your job is to determine whether the approved action is still appropriate and safe in the CURRENT workspace.

You must:
- inspect current workspace and git state first
- compare current state against the captured preconditions
- only execute the action if the original rationale still holds
- if drift is material, either propose a revised action or refuse execution
- explain your decision briefly and concretely
- do not assume any hidden memory beyond the material below

Captured approval bundle:
- Original user intent: {{user_intent}}
- Proposed tool/action: {{tool_name}} {{tool_args}}
- Risk class: {{risk_class}}
- Captured rationale: {{approval_memo}}
- Captured workspace fingerprint:
  - repo: {{repo_url}}
  - branch: {{branch}}
  - head_sha: {{head_sha}}
  - changed_files: {{changed_files}}
  - dirty_tree_hash: {{dirty_hash}}
- Relevant transcript excerpt:
{{recent_transcript}}
- Session summary:
{{session_summary}}

Current validation results:
{{drift_report}}

Required output:
Return one of:
1. CONFIRM_EXECUTE with the exact action to run
2. REVISE_ACTION with an updated action and justification
3. REFUSE with a concise explanation of what changed
```

The right **token budget** for this continuation is a product decision, not something the docs prescribe, but a good operational target is **4,000–8,000 tokens** total, with a hard ceiling around **12,000** for rare complex resumes. Keep the bundle small and high-signal: summary, approval memo, last relevant turns, and a machine-generated drift report are more valuable than replaying an entire month-old transcript. This recommendation is consistent with LangGraph’s explicit guidance to manage short-term memory through trimming, deletion, summaries, and checkpoint retrieval rather than indiscriminately replaying everything. citeturn29view0

A minimal **Temporal-driven policy skeleton** would look like this:

```python
class ApprovalDecision(Enum):
    BLIND_EXECUTE = "blind_execute"
    RERUN_AGENT = "rerun_agent"
    REJECT_AS_STALE = "reject_as_stale"

def decide_resume(policy, approval_bundle, drift_report):
    if approval_bundle.approval_expired:
        return ApprovalDecision.REJECT_AS_STALE

    if drift_report.material_drift:
        return ApprovalDecision.RERUN_AGENT

    if policy.is_green(approval_bundle.tool_name) and approval_bundle.is_idempotent:
        return ApprovalDecision.BLIND_EXECUTE

    return ApprovalDecision.RERUN_AGENT
```

And the corresponding **pre-flight checks** should include, at minimum: same repo and sandbox identity; branch and HEAD match policy; diff against captured fingerprint; files still exist where expected; secrets and credentials are still scoped appropriately; remote actions still target the same remote/environment; and the approval has not already been consumed. Those checks should be deterministic activities, not model judgements. Temporal’s docs on signals, current workflow state, durable timers, and idempotent handler design are the right foundation for that layer. citeturn47view0turn47view1turn47view2

## Open questions and limitations

The main limitation in the public evidence is that there are **few public, independent case studies** about month-delayed approval specifically in coding-agent platforms. Most of the strongest evidence is from official framework documentation and product examples rather than operator postmortems. I therefore have high confidence in the documented mechanics of each framework, but lower confidence in claims about what is “most common in production” beyond the patterns those docs encourage. citeturn45search1turn44view0turn47view0

The most important unresolved Cursor-specific question is whether there are private or newly added APIs beyond the public beta docs for acknowledging a `"request"` event or replaying a previously blocked approval point. In the public material I reviewed, that capability was **not documented**. Unless you verify otherwise from a newer Cursor release or direct vendor guidance, the safest assumption is that **Cursor native resumption is opportunistic reattachment, not durable HITL replay**. citeturn17view0turn15view0

If you follow only one rule from this report, it should be this: **after a long idle, approval should wake a workflow, not fire a tool**. The workflow can then decide—using drift checks, typed policy, and optionally a fresh agent pass—whether the tool should still run. That is the design that best matches the documented state of the art today. citeturn47view0turn27view0turn43view0

# Runner Management UX & Architecture Research Report

Fair criticism. The right answer here is not “copy GitHub Actions.” GitHub Actions, GitLab Runner, and Buildkite are mostly **operator/admin tools**. Stigmer Desktop is a **developer product**, so the UX contract should be closer to Cursor, Windsurf, Devin, Gitpod Desktop, or Coord: the user starts work, not infrastructure.

My strongest recommendation:

> **Stigmer Desktop should treat a local runner as a reconciled desired state, not as a user-created process. “Start Runner” should become an idempotent “ensure local execution is available” operation. If a runner is already running, that is success, not an error.**

The current bug is not really that the process is still alive. That is actually good. The bug is that the desktop UX exposes a CI-runner mental model to someone who simply wants to use Stigmer.

## 1. Executive conclusion

The best-in-class pattern across modern developer-agent products is:

1. **Hide runner lifecycle in the happy path.**
   The user should see “Local execution: Ready / Working / Reconnecting / Needs attention,” not “Start Runner” plus a modal full of name, endpoint, and token fields.

2. **Make runner startup idempotent.**
   Clicking the control when a runner is already running should return success: “This computer is already connected.” The CLI should also exit `0` for the already-running same-runner case.

3. **Separate machine identity from display name.**
   Hostname-derived slugs are useful display defaults, but they should not be the primary uniqueness key. Use a stable generated `machine_id` plus `org_id` plus `endpoint`.

4. **Desktop should auto-adopt existing local runners.**
   If a CLI-started runner is already active, Desktop should detect it, classify it, and show it as available. The user should not have to know whether it was launched by Desktop, CLI, launchd, or systemd.

5. **Default to one runner per machine per org.**
   Multiple runners on one machine are valid for CI/fleet scenarios, but for a developer desktop, the default should be “this computer is available for Stigmer runs.” Additional runners should be an advanced/admin path.

6. **Move name, endpoint, and token out of the happy path.**
   Those belong in Settings or Advanced. A blank optional form is misleading because it creates the impression that the user is creating something new, when the desired operation is usually “use my existing local capability.”

7. **Auto-start on app launch; optionally run at login.**
   Desktop should silently ensure the runner after authentication. A separate “Run at login” toggle can install a login item / LaunchAgent / systemd user service.

8. **Treat duplicate-active as a state transition, not an exception.**
   “Runner already running” should become:

   * Desktop: adopt and show Ready/Busy.
   * CLI interactive: print “Runner already active; using existing runner PID 9730” and exit `0`.
   * CLI advanced: use explicit `--new`, `--replace`, or `--name` for power users.

## 2. The key product mismatch

Your current desktop flow says:

> “Start Runner”

But the user intent is:

> “Use this computer for Stigmer.”

That distinction matters. “Start Runner” implies there is no existing runner and that a new resource is being created. So when the system replies “runner already running,” it sounds like a failure. In reality, it means the user’s intent is already satisfied.

This is the same distinction Gitpod Desktop appears to make: it automatically starts a macOS runner for the current organization, has only one active runner at a time in that local-desktop mode, stops/starts it when switching organizations, and starts it again when Gitpod Desktop restarts. The user does not manually fill out a runner-name form in the normal path. ([Gitpod][1])

Coord, which is especially close to Stigmer’s model, also treats the runner as part of the desktop product: a lightweight desktop app connects to a workspace, watches for jobs, runs local agent sessions, streams progress, and gives the user Status, Logs, and History. Coord explicitly says each machine runs one runner instance, while the workspace can have many runners across machines. ([Coord Docs][2])

That is the product category Stigmer Desktop should copy more than GitHub Actions.

# 3. Comparative platform findings

## 3.1 GitHub Actions self-hosted runners

GitHub Actions is a good reference for **admin-runner lifecycle**, not necessarily for Desktop UX.

### Registration and service model

GitHub’s self-hosted runner flow is explicit: add/configure a runner, then optionally configure it as a service. On Linux, GitHub documents `svc.sh install`, `start`, `status`, `stop`, and `uninstall` after the runner has already been added. It also documents service customization through systemd. On macOS, GitHub points to launchd plist customization. ([GitHub Docs][3])

GitHub’s UI shows runners in repository/organization/enterprise settings with statuses such as **Idle**, **Active**, and **Offline**. “Offline” means the runner application is not connected, the machine is off, or it cannot communicate with GitHub. ([GitHub Docs][4])

### Auto-start and persistence

GitHub explicitly supports running the runner app as a service so it can start automatically when the machine starts. That is the right pattern for headless or infrastructure-like deployments. ([GitHub Docs][3])

GitHub also auto-updates self-hosted runners by default when a new version is available, and documents disabling that with `--disableupdate`, with the caveat that runners must be updated within a set window or they stop receiving jobs. ([GitHub Docs][5])

### Ephemeral and just-in-time runners

GitHub’s more modern pattern for autoscaling is **ephemeral** runners: one runner gets one job and then is automatically de-registered. GitHub recommends ephemeral runners for autoscaling because persistent self-hosted runners can receive jobs while being shut down or recycled. ([GitHub Docs][5])

GitHub also has just-in-time runner registration APIs for single-use runners without time-limited registration tokens, again aimed at autoscaling infrastructure. ([The GitHub Blog][6])

### Duplicate/active runner implication

GitHub’s model is fundamentally admin-facing: duplicate registration is handled through runner names, replacement flags, or separate runner instances. Active-session duplication is treated as a runner/session conflict, not a friendly “already ready” desktop state. Community reports show that trying to run a second session for the same configured runner can result in an active-session conflict and retry loop. ([Stack Overflow][7])

### Lesson for Stigmer

Copy GitHub’s **status vocabulary**, **service install path**, and **auto-update discipline**. Do not copy its user-facing “configure a runner” posture for the desktop happy path.

For Stigmer Desktop, the equivalent of GitHub’s “runner is Idle” should be a success state: **Local execution ready**.

## 3.2 GitLab Runner

GitLab Runner has a cleaner conceptual separation than many platforms:

* `gitlab-runner register` adds runner configuration.
* `gitlab-runner run` runs the multi-runner service.
* Service commands install/start/stop/restart/status the service.
* Multiple runner configurations can live in one `config.toml`.

GitLab’s docs say registration stores configuration in `config.toml`, and registering multiple runners on the same host means repeating `gitlab-runner register`. The command list includes `register`, `run`, `install`, `start`, `stop`, `restart`, `status`, `unregister`, and `verify`. ([GitLab Documentation][8])

A particularly important identity lesson: in GitLab Runner’s advanced config, the runner `name` is described as informational. The real runner identity is the runner configuration/token, not the display name. GitLab also supports multiple `[[runners]]` sections in a single config. ([GitLab Documentation][9])

On macOS, GitLab Runner is documented as a user-mode LaunchAgent, not a system LaunchDaemon. It runs when the user logs in and stops when the user logs out. GitLab explicitly notes this mode gives access to user-mode resources such as UI elements and keychain material, which is highly relevant for developer tools that need Git credentials, SSH keys, editors, and local dev environments. ([GitLab Documentation][10])

GitLab also documents service support across Windows, Linux systemd/Upstart/System V, and macOS launchd. ([GitLab Documentation][11])

### Lesson for Stigmer

GitLab’s most important lesson is: **registration and running are different operations**.

Stigmer’s Desktop happy path should not “register a runner” every time. It should call an idempotent operation like:

```bash
stigmer runner ensure --managed-by desktop --json
```

That operation may register, resume, reconnect, adopt, or start. The user does not care which one happened.

Also, Stigmer should copy GitLab’s identity separation: human-readable runner name should be informational and mutable; uniqueness should come from an internal ID.

## 3.3 Buildkite Agent

Buildkite is a strong reference for **agent session design**, naming templates, heartbeat/lost detection, and dashboard status.

Buildkite’s agent is a small cross-platform build runner that polls Buildkite, runs jobs, reports status/output, and uploads artifacts. ([Buildkite][12])

### Naming

Buildkite’s config supports optional agent names and name templates such as hostname, spawn number, random value, and process ID. This is important because it avoids pretending that a user-chosen name is necessarily the true identity. Buildkite also supports tags and queue routing. ([Buildkite][13])

### Lifecycle

`buildkite-agent start` manually starts and registers an agent connection. Buildkite supports lifecycle options such as disconnecting after a job, disconnecting after idle timeout, disconnecting after uptime, and acquiring a specific job. ([Buildkite][14])

Buildkite’s agent lifecycle docs describe graceful disconnect behavior: the agent can finish a current job before disconnecting. The docs also describe heartbeat/lost behavior: after registration, the agent sends regular heartbeats; if Buildkite misses heartbeats for consecutive minutes, the agent is marked lost and no more jobs are assigned. ([Buildkite][12])

Buildkite’s GraphQL Agent object exposes fields such as connection state, heartbeat time, hostname, IP address, whether the agent is running a job, whether it is paused, and lost/disconnected timestamps. ([Buildkite][15])

Buildkite also has queue metrics and an Agents panel that shows connected agents and busy-vs-idle utilization. ([Buildkite][16])

### Lesson for Stigmer

Buildkite’s best ideas for Stigmer are:

* Use **templateable display names**, not display names as identity.
* Treat the runner connection as a **session** with heartbeat, lost time, connected time, and current job state.
* Support graceful drain/stop.
* Expose enough status for debugging, but do not make the normal user configure all of it.

Stigmer should model:

```text
machine identity   stable across restarts
runner record      stable per org/machine/endpoint
runner session     ephemeral per process start
task assignment    bound to current live session
display name       user-facing, mutable, non-unique
```

## 3.4 Cursor Background Agents

Cursor is the opposite end of the spectrum from GitHub Actions. It does not ask users to manage local runners for Background Agents. Cursor’s Background Agents are remote agents that edit and run code in isolated Ubuntu-based machines. Users start agents from the UI, view status, send follow-ups, and take over the machine. ([Cursor Documentation][17])

Cursor exposes agent management through an Agents sidebar: users can view all agents associated with their account, inspect background agents, and jump into remote machines. Cursor’s changelog also describes a unified sidebar for foreground and background agents. ([Cursor][18])

Cursor’s setup surface is repository/environment-centric: environment files, install commands, startup commands, secrets, terminals, and repo cloning. The user configures the environment, not a runner process. ([Cursor Documentation][19])

### Lesson for Stigmer

Cursor’s key lesson is task-centric UX:

> The primary object is the agent/session/task, not the runner.

For Stigmer Desktop, runner status should be supporting infrastructure. The main UX should answer:

* Can Stigmer use this computer?
* What is currently running?
* Does it need my attention?
* Can I view logs or take over?

Not:

* What runner name do I want?
* What endpoint should this runner use?
* What token should I paste?
* Why is a PID from five hours ago blocking me?

## 3.5 Windsurf / Codeium

Windsurf’s Cascade is presented as an editor-integrated agent, not a user-managed local runner. Users interact through Cascade, which can use terminal/tool execution, detect packages, maintain plans/todos, continue work with context, and support auto-execution modes. ([Windsurf Docs][20])

Windsurf 2.0’s Agent Command Center is particularly relevant: it manages local and cloud agents from a Kanban-style view, with statuses like in-flight, blocked, and ready for review. It unifies local Cascade sessions and cloud/Devin sessions as work items. ([Windsurf Docs][21])

### Lesson for Stigmer

The UX object should be **work state**, not process state.

A good Stigmer equivalent would be:

```text
Local execution
Ready on Swarup’s MacBook Pro

Current work
- Agent run #123: Running tests
- Agent run #124: Waiting for approval

Controls
Pause new work | View logs | Restart local runner | Advanced
```

The runner remains observable, but it is not the center of the product.

## 3.6 Devin

Devin largely avoids local runner UX by using cloud dev environments. Devin’s environment is a Linux-based VM workspace, configured once and saved as a snapshot. Each session boots from a fresh copy of the snapshot. ([Cognition AI][22])

Devin’s declarative environment model uses concepts similar to Blueprint, Build, and Snapshot; builds run when saving the blueprint and periodically. Every session starts from the snapshot rather than from a user-managed local daemon. ([Cognition AI][23])

Repository setup is framed as project/environment setup, not runner setup. Devin can boot a session from the latest snapshot, run `git pull`, run maintenance commands, and then execute work. ([Devin Docs][24])

### Lesson for Stigmer

Devin’s lesson is not “use cloud VMs.” Stigmer explicitly wants local execution. The lesson is:

> The agent product should make execution substrate feel like part of the environment, not a thing the user starts repeatedly.

For Stigmer, the analog is: configure local environment once, then keep it available.

## 3.7 Coord

Coord is one of the closest public analogs to Stigmer’s local-runner model.

Coord’s desktop runner executes agentic jobs on the user’s local machine. It connects to a workspace, watches for ready jobs, picks them up, clones code, starts AI agents like Claude Code/Codex/Gemini CLI, streams progress, and packages results. Its interface includes Status, Logs, and History. ([Coord Docs][2])

Coord also says credentials stay on the user’s machine, each runner becomes part of the team execution network, users can run runners on as many machines as they want, and each machine runs one runner instance. ([Coord][25])

Coord supports automatic retries for crashes, timeouts, and network hiccups, and a graceful stop that lets the agent finish the current operation. ([Coord Docs][2])

### Lesson for Stigmer

Coord validates the likely best product stance for Stigmer:

* Runner is a desktop subsystem.
* One runner per machine by default.
* Status/logs/history are exposed.
* Start/stop exist, but not as “fill out a name/token/endpoint form.”
* Recovery is automatic.

## 3.8 Gitpod Desktop

Gitpod Desktop is another highly relevant example because it has a local runner but makes it app-managed.

Gitpod Desktop’s docs describe local environments as being backed by a runner that Gitpod Desktop automatically starts for the current organization. The older docs explicitly say only one runner is active at a time, stopping the runner stops local environments, quitting Gitpod Desktop stops the runner, switching orgs stops the current org runner and starts the new org runner, and restarting Gitpod Desktop starts the runner again. ([Gitpod][1])

### Lesson for Stigmer

This is probably the closest UX pattern for your immediate desktop problem:

> Desktop owns the local runner for the current org. It auto-starts, auto-stops, and auto-switches. The user does not create duplicate runners by clicking “Start.”

# 5. Best-in-class UX patterns to adopt

## Pattern 1: Replace “Start Runner” with “Local execution availability”

The primary control should be something like:

```text
Local execution
Ready on Swarup’s MacBook Pro

[Pause new work] [View logs] [Restart] [Advanced]
```

Not:

```text
Start Runner
Name: _______
Endpoint: _______
Token: _______
```

The modal should disappear from the happy path. Endpoint and token should be derived from logged-in Desktop auth. Name should default automatically and be editable later.

Recommended UI states:

| User-facing state | Meaning                                                |
| ----------------- | ------------------------------------------------------ |
| Ready             | Runner connected and idle                              |
| Working           | Runner connected and running a task                    |
| Reconnecting      | Runner process exists but cloud stream is reconnecting |
| Needs attention   | Auth, permission, version, or environment issue        |
| Paused            | Runner exists but will not accept new work             |
| Disabled          | User has turned off local execution                    |
| Updating          | Desktop/runner is updating                             |
| Offline           | No local runner is reachable                           |

The key is that **already running maps to Ready or Working**, never to Error.

---

## Pattern 2: Make “start” an idempotent ensure operation

Implement a new semantic operation:

```bash
stigmer runner ensure --managed-by desktop --json
```

Expected results:

```json
{
  "ok": true,
  "status": "ready",
  "runner_id": "runr_...",
  "machine_id": "mach_...",
  "session_id": "sess_...",
  "adopted_existing": true,
  "pid": 9730,
  "started_at": "2026-05-09T06:12:00Z"
}
```

The operation should be allowed to do any of these:

* Detect existing Desktop-managed runner and return success.
* Detect existing CLI-managed runner and adopt/display it.
* Detect stale state and clean it up.
* Reconnect a disconnected runner.
* Register/resume a server-side runner record.
* Start a new process only when no compatible runner exists.

The user-facing verb should be **Connect**, **Enable local execution**, or simply an automatic background action. Internally, the verb is **ensure**.

---

## Pattern 3: Treat “already running” as success

Current behavior:

```text
runner "swarups-macbook-pro-local" is already running
```

Recommended Desktop behavior:

```text
This computer is already connected.
Using runner started 5 hours ago.
```

Recommended CLI behavior:

```text
Runner already active: swarups-macbook-pro-local
PID: 9730
Status: ready
Use `stigmer runner status` to inspect, or `stigmer runner restart` to restart.
```

Exit code should be `0` for the same org/endpoint/machine case.

Only true conflicts should be errors, for example:

* Existing runner belongs to a different org and cannot be adopted.
* Existing runner uses a different endpoint.
* Existing process is unresponsive and cannot be stopped.
* Credentials are invalid.
* Local state is corrupt and automatic repair failed.

Even then, the CTA should be “Reconnect,” “Restart runner,” or “Run diagnostics,” not “try another `--name`.”

---

## Pattern 4: Separate stable identity from display name

Your current key is effectively:

```text
runner name = sanitized hostname = uniqueness key = local state filename
```

That is fragile.

Problems:

* Hostnames can change.
* Hostnames collide.
* `.local` suffixes leak into names.
* Two orgs on the same machine need distinct runner records.
* A user changing display name should not create a new runner identity.
* “Use `--name`” tells the user to create a duplicate when they actually want to reuse the current machine.

Recommended identity model:

```text
machine_id:
  Stable generated UUID for this local Stigmer installation.
  Stored in ~/.stigmer/machine.json or OS keychain.
  Not user-facing.

runner_id:
  Stable server-side runner record.
  Scoped to org_id + endpoint + machine_id.
  Reused across process restarts.

session_id:
  Ephemeral process connection/session.
  New on every runner process start.

display_name:
  Human-readable default from hostname.
  Mutable.
  Not unique.
  Not used as the lock key.

task_queue:
  Stable per runner_id, e.g. runner:{runner_id}.
```

Recommended local path:

```text
~/.stigmer/
  machine.json
  runners/
    <endpoint_hash>/
      <org_id>/
        <machine_id>.json
        <machine_id>.lock
        <machine_id>.sock
```

The server should enforce uniqueness on:

```text
(org_id, endpoint, machine_id)
```

not on display name.

---

## Pattern 5: Introduce a local runner control plane

Relying only on a PID file is not enough. `signal 0` answers “does a process with this PID exist?” It does not prove:

* It is the Stigmer runner.
* It is the same runner instance.
* It belongs to the same org/endpoint.
* It is healthy.
* It is accepting or rejecting work.
* The PID has not been reused.

Add a local control socket:

```text
~/.stigmer/runners/<endpoint>/<org>/<machine_id>.sock
```

Supported RPCs:

```text
status
stop
restart
pause
resume
logs
health
adopt
```

The Desktop app should use this socket to adopt CLI-started runners. The CLI should use it to avoid starting duplicates.

State file should include:

```json
{
  "runner_id": "runr_...",
  "machine_id": "mach_...",
  "session_id": "sess_...",
  "org_id": "org_...",
  "endpoint": "api.stigmer.ai:443",
  "pid": 9730,
  "process_start_time": "...",
  "executable_path": "...",
  "executable_hash": "...",
  "control_socket": "...",
  "started_at": "...",
  "managed_by": "cli|desktop|service",
  "version": "...",
  "capabilities": [...]
}
```

Duplicate detection should check, in order:

1. File lock.
2. State file.
3. PID exists.
4. PID start time matches.
5. Executable/cmdline matches.
6. Control socket responds.
7. Server says current session is alive.

Only then classify it as active. If socket fails but PID exists, classify as **Unhealthy** and offer Restart/Repair.

# 6. Recommended Stigmer architecture

## 6.1 New command model

Keep `stigmer up runner` for compatibility, but make the underlying model more explicit.

Recommended commands:

```bash
stigmer runner ensure --json
stigmer runner status --json
stigmer runner stop
stigmer runner restart
stigmer runner pause
stigmer runner resume
stigmer runner logs
stigmer runner doctor
stigmer runner service install --user
stigmer runner service uninstall
```

Compatibility:

```bash
stigmer up runner
```

should become equivalent to:

```bash
stigmer runner ensure
```

unless the user explicitly requests foreground mode or a new named runner.

Power-user flags:

```bash
--new                 # intentionally create another runner
--replace             # gracefully stop/preempt existing runner
--name <display-name> # set display name, not identity
--foreground          # run in foreground
--service             # run as service/supervisor mode
--org <org-id>
--endpoint <endpoint>
```

Important default:

```text
same org + same endpoint + same machine_id + already active = success
```

## 6.2 Desktop app lifecycle

On Desktop launch:

1. Authenticate user.
2. Resolve active org/workspace.
3. Call `runner ensure --managed-by desktop --json`.
4. If existing local runner is found, adopt it.
5. If no runner exists, start one silently.
6. Display compact status.

Desktop should not show a runner form unless:

* The user is unauthenticated.
* There is no token/config available.
* Endpoint is non-default and not configured.
* The user opens Advanced settings.
* The org requires a special runner policy.

Recommended Desktop card:

```text
Local execution

Ready
This computer can run Stigmer agents.

Machine: Swarup’s MacBook Pro
Current task: None
Last connected: just now

[Pause new work] [View logs] [Restart] [Advanced]
```

If already running from CLI:

```text
Local execution

Ready
Connected to an existing local runner started from Terminal 5 hours ago.

[Manage here] [View logs] [Restart] [Advanced]
```

If busy:

```text
Local execution

Working
Running Agent Execution #8421

[View task] [View logs] [Pause new work after current task]
```

If reconnecting:

```text
Local execution

Reconnecting
Your runner is still running locally. We are reconnecting to Stigmer Cloud.

[View logs] [Restart]
```

## 6.3 Server-side runner/session model

Current:

```text
runner.apply()
runner_id
task_queue runner:{runner_id}
connect stream
heartbeats every 30s
phases PENDING -> STARTING -> READY -> BUSY -> STOPPED
```

Recommended extension:

```text
Runner:
  runner_id
  org_id
  endpoint
  machine_id
  display_name
  created_at
  last_seen_at
  desired_state: enabled|paused|disabled
  observed_state: offline|starting|ready|busy|reconnecting|stopping|stopped|error
  capabilities
  version
  managed_by_last: desktop|cli|service
  current_session_id

RunnerSession:
  session_id
  runner_id
  process_id_optional
  process_start_time_optional
  started_at
  connected_at
  last_heartbeat_at
  disconnected_at
  status
  version
  management_mode
```

`runner.apply()` should behave like Kubernetes-style apply/reconcile:

```text
Given org_id + endpoint + machine_id:
  if runner exists:
    update mutable fields and return existing runner_id
  else:
    create runner and return new runner_id
```

The connect stream should include:

```text
runner_id
session_id
machine_id
version
capabilities
resume_token / nonce
```

If a second session connects for the same `runner_id`, the server should not return a generic failure. It should return structured information:

```json
{
  "code": "ALREADY_CONNECTED",
  "runner_id": "runr_...",
  "active_session_id": "sess_...",
  "last_heartbeat_at": "...",
  "policy": "reject_without_replace"
}
```

The client then maps this to:

* Desktop: adopt existing if local; otherwise show “Runner active elsewhere.”
* CLI: exit `0` if it is the same local process; otherwise print clear conflict.
* Explicit `--replace`: request graceful preemption.

## 6.4 Task queue implications

Your current Temporal queue pattern, `runner:{runner_id}`, is directionally right because it gives a stable routing address. Temporal workers poll task queues, and Temporal task queues can have multiple workers; Temporal worker poller metadata includes worker identity and last access time. ([Temporal API Docs][27])

For Stigmer, keep:

```text
task_queue = runner:{runner_id}
```

But avoid binding logical runner identity to process lifetime. The process session should be replaceable.

Recommended policy:

```text
runner_id stable
session_id ephemeral
task_queue stable
worker identity includes session_id + version
```

This lets you show:

```text
Runner: Swarup’s MacBook Pro
Current session: started 5 hours ago
Current task queue: runner:runr_123
```

without forcing the user to understand any of it.

# 8. Recommended decision on your four options

You listed:

* Option A: Auto-adopt the existing runner.
* Option B: Show “Runner is already active” as success.
* Option C: Transparent reconnect / stop old and start new.
* Option D: Remove the “Start Runner” button when one is already running.

Recommended answer:

```text
Primary: A + B + D
Avoid as default: C
```

### Option A: Auto-adopt existing runner

Yes. This should be the core behavior.

Adoption should work across:

* Desktop-started runner.
* CLI-started runner.
* Service-started runner.
* Login-item-started runner.

### Option B: Already active as success

Yes. This is the minimum fix.

Already running means the user’s intent is satisfied.

### Option C: Stop old, start new

Only for explicit **Restart** or **Replace**.

Transparent replacement can kill in-flight work, lose logs, interrupt local tool state, or produce surprising behavior after laptop sleep/wake. Buildkite’s lifecycle distinction between graceful disconnect and forced disconnect is a useful reminder: stopping a runner is operationally meaningful and should not be hidden when work may be active. ([Buildkite][12])

### Option D: Remove Start button when active

Yes, but it is not enough alone.

The deeper fix is that the button should not represent “create process.” It should represent desired availability.

# 9. Background process management recommendations

## 9.1 macOS

For developer machines, prefer:

```text
Desktop app / LaunchAgent / login item
```

not a root LaunchDaemon.

Reason: developer runners often need user-session resources: SSH agent, Git credentials, keychain, editor integrations, filesystem permissions, and sometimes UI-adjacent tools. GitLab Runner’s macOS docs make this same point by supporting only user-mode LaunchAgent on macOS and noting access to user resources like keychain and UI elements. ([GitLab Documentation][10])

Apple’s launchd model uses property lists with keys such as `Label`, `ProgramArguments`, and `KeepAlive`; Apple also recommends designing daemons to run on demand where possible. ([Apple Developer][28])

For Tauri, the autostart plugin supports launching the app at system startup across macOS, Linux, and Windows, and supports macOS LaunchAgent mode. ([Tauri][29])

Recommended macOS modes:

| Mode               | Use case                                | Mechanism                                                       |
| ------------------ | --------------------------------------- | --------------------------------------------------------------- |
| Desktop default    | User opens Stigmer                      | Tauri app spawns/supervises runner                              |
| Run at login       | User wants always-ready local execution | LaunchAgent/login item starts Stigmer or lightweight supervisor |
| Headless machine   | Shared build/dev machine                | Explicit service install with service account                   |
| Enterprise managed | Admin-controlled fleet                  | MDM-installed LaunchAgent/Daemon depending on credential model  |

Do not make LaunchDaemon the default for ordinary developers.

---

## 9.2 Linux

For Linux developer desktops:

```text
systemd --user service
```

For headless servers:

```text
systemd system service
```

systemd’s `Restart=` policy can restart services on failure, and `Restart=on-failure` is the recommended pattern for long-running services. `RestartSec` controls delay before restart, and watchdog settings can mark a service failed if it stops pinging. ([freedesktop.org][30])

Recommended user service:

```ini
[Unit]
Description=Stigmer Runner
After=network-online.target

[Service]
ExecStart=/usr/local/bin/stigmer runner supervise --managed-by service
Restart=on-failure
RestartSec=5s
KillSignal=SIGTERM
TimeoutStopSec=300
WatchdogSec=90

[Install]
WantedBy=default.target
```

Recommended behavior on SIGTERM:

1. Stop accepting new tasks.
2. If idle, exit immediately.
3. If busy, mark draining and finish current safe checkpoint.
4. After grace period, terminate child process if necessary.
5. Report final status.

---

## 9.3 Desktop app versus service

Recommended default:

```text
Desktop app supervises the runner while the user is logged in.
```

Recommended optional setting:

```text
[ ] Run Stigmer at login
```

Recommended advanced setting:

```text
Install as background service...
```

Avoid forcing users into service setup during onboarding. That is CI-runner UX, not local-agent UX.

# 10. Sleep, wake, and network reconnection

Laptops sleep. Networks change. VPNs disconnect. The runner UX should assume this.

Recommended state handling:

```text
Heartbeat every 30s
Missed 1-2 heartbeats: reconnecting / degraded
Missed longer grace window: offline, no new tasks
Reconnect with same runner_id and new or resumed session_id
Do not create a new runner record
Do not show an error unless user action is required
```

Buildkite’s heartbeat/lost model is a useful precedent: agents send regular heartbeats, and the platform marks agents lost after missed heartbeat windows so no more jobs are assigned. ([Buildkite][31])

For Stigmer:

* On sleep: local runner may pause; cloud should show **Reconnecting** or **Offline**, not **Stopped**.
* On wake: runner reconnects using the same `runner_id`.
* If a task was running: use task heartbeat/checkpoint semantics and mark the execution **Recovering**, **Retrying**, or **Needs attention** depending on tool state.
* Do not ask the user to start a new runner after wake.

Suggested statuses:

```text
READY          connected and idle
BUSY           connected and working
RECONNECTING   process exists, stream reconnecting
OFFLINE        no recent heartbeat, not eligible for new work
DRAINING       finishing current task, no new tasks
PAUSED         user/admin paused new work
UNHEALTHY      local process exists but health check failed
STOPPED        intentionally stopped
```

Avoid using `STOPPED` for sleep/network loss unless the process actually exited intentionally.

# 11. Multi-runner versus single-runner

## CI platforms

GitHub, GitLab, and Buildkite all support multiple runners/agents per machine or per fleet because their primary use case includes CI capacity management, parallelism, queues, labels, executors, and autoscaling. GitLab explicitly supports multiple registered runner configs in one `config.toml`, and Buildkite supports spawn/name templates and multiple agent sessions. ([GitLab Documentation][26])

## Developer-agent platforms

For local AI coding agents, the default should be different:

```text
One machine = one local execution capability per org/endpoint.
```

Coord says each machine runs one runner instance, while users can run runners on many machines. ([Coord][25])

Gitpod Desktop’s local runner model similarly centers on one active local runner for the current organization in the desktop context. ([Gitpod][32])

## Recommendation for Stigmer

Default:

```text
one runner per machine per org per endpoint
```

Advanced:

```text
multiple named runners on same machine
```

Use cases for advanced multi-runner:

* CI/testing.
* Benchmarking.
* Multiple sandboxes.
* Different capability profiles.
* Different credentials.
* Different concurrency limits.
* One runner per repository/worktree.
* Enterprise fleet machines.

UX distinction:

```text
Happy path:
  “Use this computer for Stigmer.”

Advanced path:
  “Add another runner on this computer.”
```

These should not be the same button.

# 12. Anti-patterns to avoid

## Anti-pattern 1: Optional blank fields in the happy path

A modal with blank optional fields creates cognitive load. The user thinks:

* Do I need a name?
* What endpoint should I use?
* Which token?
* What happens if I leave these blank?

Then leaving them blank triggers a duplicate-name error. This feels like the user did something wrong.

Move these fields to Advanced.

---

## Anti-pattern 2: Hostname slug as identity

Hostname is a good display default, not a stable identity.

Bad:

```text
identity = sanitize(os.Hostname())
```

Better:

```text
display_name = pretty_hostname()
identity = generated_machine_id
```

Even better:

```text
runner uniqueness = org_id + endpoint + machine_id
```

---

## Anti-pattern 3: “Already running” as a red error

This is the precise problem. Already running is normally success.

Only error if:

* It is running for the wrong org.
* It is running against the wrong backend.
* It is unresponsive.
* The user explicitly requested a second runner and the name conflicts.

---

## Anti-pattern 4: Suggesting `--name` to normal desktop users

The current suggestion tells the user to create another runner. But their intent is to use the existing one.

Better:

```text
This computer is already connected.
```

Then advanced help:

```text
To intentionally create another runner, use --new --name <name>.
```

---

## Anti-pattern 5: PID-only liveness

`signal 0` is insufficient.

Use:

* PID.
* Process start time.
* Executable path/hash.
* State nonce.
* Lock file.
* Control socket health.
* Server heartbeat/session state.

---

## Anti-pattern 6: Mixing “stop runner” with “stop current work”

Stopping a runner may interrupt agent execution. The UI should distinguish:

```text
Pause new work
Stop after current task
Restart now
Force stop
```

Buildkite’s lifecycle distinction between graceful and forceful disconnect is a good model here. ([Buildkite][12])

# 14. Stale state and crash recovery

Current stale cleanup is directionally right but too weak.

Recommended stale cleanup decision tree:

```text
Read state file.
Acquire lock.
If lock unavailable:
  query control socket.
  if healthy -> active, return success.
  if unhealthy -> mark needs attention.

If lock available:
  check PID.
  if PID absent -> stale, clean.
  if PID present:
    compare process start time.
    compare executable path/cmdline.
    query control socket.
    if healthy -> active.
    if not healthy -> unhealthy, offer restart.
```

Server-side:

```text
If no heartbeat within grace window:
  observed_state = offline
  eligible_for_new_tasks = false

If runner reconnects with same machine_id:
  same runner_id
  new session_id or resumed session
```

State files should not be removed only on clean exit. They should be repaired continuously.

# 15. Auto-update pattern

GitHub auto-updates self-hosted runners by default and documents a manual opt-out with operational consequences. ([GitHub Docs][5])

For Stigmer Desktop:

* Desktop app update should update bundled CLI/runner.
* Runner should support graceful drain before update.
* If idle: restart immediately.
* If busy: mark update pending; update after current task.
* If security-critical: pause new work and force update after a clear grace period.

Recommended states:

```text
READY
UPDATE_AVAILABLE
UPDATING
UPDATE_PENDING_AFTER_TASK
UPDATE_FAILED
```

Do not make users manually update a sidecar unless they are in service/headless mode.

# 18. Direct answers to your research questions

## 1. Comparable platform runner UX patterns

CI platforms expose runner lifecycle because their users are admins/operators. GitHub, GitLab, and Buildkite expect explicit registration, service installation, status inspection, and sometimes multiple runner instances. GitHub and GitLab have service modes; Buildkite has strong heartbeat/session/status concepts. ([GitHub Docs][3])

AI coding tools mostly hide runner lifecycle. Cursor, Windsurf, and Devin expose agents, sessions, environments, and work status, not “start a runner process.” ([Cursor Documentation][17])

Closest local-runner analogs are Coord and Gitpod Desktop. Coord exposes a desktop runner with Status/Logs/History and one runner per machine. Gitpod Desktop automatically manages a current-org local runner. ([Coord Docs][2])

---

## 2. “Start and forget” patterns

The strongest patterns are:

* idempotent ensure
* auto-adopt existing local process
* auto-start on app launch
* run-at-login option
* graceful reconnect after sleep/wake
* status-first UI
* move configuration to Advanced

Already-running should be success.

---

## 3. Identity and naming patterns

GitLab explicitly treats runner `name` as informational; Buildkite supports generated/template names; GitHub often defaults toward machine names but also has replacement/ephemeral infrastructure patterns. ([GitLab Documentation][33])

For Stigmer:

```text
machine_id + org_id + endpoint = identity
hostname = display name
session_id = process instance
```

---

## 4. Desktop / GUI patterns

Cursor and Windsurf show agent/session status in sidebars and command centers. Coord shows Status/Logs/History in a desktop runner. Gitpod Desktop automatically starts/stops the current local runner. ([Cursor][18])

For Stigmer:

* remove the normal Start Runner dialog
* show Local Execution card
* show tray/menu-bar status
* add Advanced settings for runner internals

---

## 5. Error prevention and recovery

Best answer:

```text
Auto-adopt existing runner.
Treat active runner as success.
Use Restart only when explicit.
Hide Start when already active.
```

Stale state should be repaired with lock + PID + process birth time + executable check + control socket + server heartbeat.

Sleep/wake should be reconnect, not re-register.

---

## 6. Background process management

macOS developer mode should use Desktop-managed process or LaunchAgent/login item, not default LaunchDaemon. GitLab’s macOS runner design supports this user-mode approach because of user session/keychain/UI needs. ([GitLab Documentation][10])

Linux desktop should use systemd user service. Headless/server should use system-level systemd service with restart-on-failure and watchdog options. ([freedesktop.org][30])

---

## 7. Multi-runner versus single-runner

CI/admin tools support multiple runners per machine. Developer desktop tools should default to one local runner per machine per org. Coord explicitly says each machine runs one runner instance, while many machines can join the workspace. ([Coord][25])

For Stigmer:

```text
Default: one runner per machine/org/endpoint
Advanced: additional runners
```

# 19. Final recommendation

Stigmer should not ask desktop users to “start a runner” as though they are administering CI infrastructure.

The target product contract should be:

> **When Stigmer Desktop is open and the user is signed in, this computer is available for Stigmer runs unless the user disables it.**

The target technical contract should be:

> **`ensureRunner(org, endpoint, machine_id)` reconciles local and server state until a compatible runner is active, adopted, reconnected, or clearly needs attention.**

The target behavior for your screenshot scenario should be:

```text
User clicks local execution control.
Existing runner PID 9730 is alive.
Desktop adopts it.
UI shows: “Ready — this computer is already connected.”
No error.
No modal.
No `--name` suggestion.
```

The most important architectural shift is separating these concepts:

```text
display name ≠ identity
runner record ≠ process session
start command ≠ create new runner
already running ≠ error
desktop user ≠ CI administrator
```

Once those are separated, the UX becomes straightforward: Stigmer simply keeps local execution available, and runner management fades into the background where it belongs.
