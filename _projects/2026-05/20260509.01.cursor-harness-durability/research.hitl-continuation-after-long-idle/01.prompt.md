# Deep Research: Safely Resuming AI Agent Tool Execution After Long Human-in-the-Loop Idle Periods

## Research Objective

We are building an AI agent orchestration platform where agents can request tool/command approval from humans before executing sensitive operations (human-in-the-loop / HITL). The problem: the agent's execution context may be **completely lost** between the moment it requested approval and the moment the human responds — which could be minutes, days, or even a month later.

We need to understand the state of the art for safely resuming tool execution in this scenario, across both the Cursor SDK specifically and the broader AI agent ecosystem (LangGraph, CrewAI, AutoGen, OpenAI Assistants, etc.).

## The Specific Scenario

```
1. User sends message to AI coding agent
2. Agent analyzes the request, reads files, runs commands
3. Agent decides it needs to run a sensitive tool (e.g., git push, database migration, file deletion)
4. Platform pauses agent and asks human: "The agent wants to run: git push --force origin main. Approve?"
5. Human walks away for 1 month
6. Human comes back and clicks "Approve"
```

**At step 6, the original agent context is completely gone:**
- The AI agent process has exited
- The conversation context has been garbage-collected by the AI provider
- The LLM that generated the tool call no longer has any memory of why it wanted to run that command
- Only our database has: the tool name, parameters, the conversation transcript, and a session summary

**The core question: How should the platform handle step 6 safely and correctly?**

## What We Know So Far

### Our Current Architecture
- **Cursor SDK** (`@cursor/sdk`) as one execution harness, using local agents
- **Temporal** for durable workflow orchestration (the workflow itself survives indefinitely)
- **MongoDB** stores: full conversation messages, pending approval details (tool name, parameters, tool call ID), session memory summaries
- On reinvocation after approval, we currently try `Agent.resume(agentId)` — which fails if the agent has been evicted
- We're building a **replay/continuation layer** where a fresh agent gets session memory + continuation prompt instead of native context

### The HITL-Specific Challenge
Unlike a normal "user sends next message" continuation, the HITL case has a critical difference:

- **Normal continuation**: User provides new intent. The fresh agent reads memory, understands the workspace, and proceeds with the new task. Even with some context loss, the user's new message drives the direction.
- **HITL continuation**: The user's "message" is just "approved" or "rejected." The agent must reconstruct not just WHAT tool to run, but WHY it wanted to run it, whether the conditions still apply, and whether it's still safe to execute — all from stored context alone.

- **OpenAI Assistants API**: How does the Assistants API handle `requires_action` (tool approval) state? What happens if you wait a long time before submitting tool outputs?

### 3. Safety and Quality Concerns for Delayed Tool Execution
- **Stale context problem**: If the agent decided to run `git push` based on the state of the codebase 1 month ago, is it safe to execute that push now? The codebase may have changed completely.
- **Re-derivation vs blind execution**: Should the platform blindly execute the approved tool call with the original parameters, or should it create a new agent that re-derives whether the tool call is still appropriate?
- **What do experts / papers say about time-delayed tool execution in AI agent systems?**
- Are there known failure modes when agents execute stale tool calls?

### 4. Architectural Patterns for HITL Continuation
- **Pattern A: Blind execution** — Store the exact tool call, execute it verbatim after approval. No LLM involved at step 6. Fastest, cheapest, but potentially unsafe if context changed.
- **Pattern B: Re-derivation** — Create a new agent, give it the session memory + "you previously decided to run X because Y, the user approved. Re-examine the current state and proceed if still appropriate." Slower, costs tokens, but safer.
- **Pattern C: Hybrid** — For idempotent/safe tools, execute blindly. For destructive tools, re-derive. Classification could be based on tool metadata.
- **Pattern D: Checkpoint-based** — If the framework supports it (LangGraph), restore the agent to the exact checkpoint just before the tool call, with full LLM state, and let it proceed naturally.
- Which of these patterns are actually used in production AI agent systems?

### 5. LangGraph Checkpoint Model (Comparison)

- When a LangGraph graph resumes from a checkpoint after days, does it reload the full LLM context?

### 6. Context Window Budget for HITL Replay
- If we go with Pattern B (re-derivation), we need to include in the prompt:
  - Session memory summary (~2-4k tokens)
  - The specific tool call that was approved (name, parameters, the agent's reasoning)
  - Current workspace state (changed files, git status)
  - Recent conversation turns leading up to the tool call
- What is the recommended token budget for HITL continuation prompts?
- How should tool call reasoning be captured for later replay? Just the tool name/params? Or also the agent's internal reasoning chain?

### 7. Workspace Drift Detection
- After a month, the workspace may have changed (other commits, file modifications, etc.)
- Should the platform detect workspace drift before executing an approved tool?
- Are there patterns for "pre-flight checks" that validate whether a stale tool call is still safe?
- What metadata should be captured at tool-call time to enable drift detection later?
