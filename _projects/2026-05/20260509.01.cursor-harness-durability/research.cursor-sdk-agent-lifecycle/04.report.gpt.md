# Cursor SDK Agent Lifecycle, Durability, and Multi-Turn Conversation Architecture

## Bottom line

For the use case you described — durable, multi-turn conversations that may sit idle for hours or days while still needing access to a real local filesystem — **standard Cursor local agents are not a safe primary durability primitive**. Cursor’s own SDK references say local agents are the right fit for dev-loop tooling against a checked-out workspace, but also explicitly say local is **not** the runtime to choose when work needs to outlive the caller process; by contrast, the new Cloud Agents API is described as being built around **durable agents** with explicit lifecycle controls. citeturn12view0turn51view0turn51view2

The strongest architecture recommendation for Stigmer is therefore:

- **Use Cloud Agents whenever you can** for durable, resumable threads.
- **Treat standard local `agent-...` agents as best-effort only**, even if you store `agentId`.
- **Build a first-class replay/checkpoint layer** for any workflow that must survive long idle periods on local workspaces.
- **Pilot Cursor self-hosted cloud agents / My Machines** as the medium-term path to combine durable cloud-style sessions with execution on infrastructure you control. Cursor now publicly supports self-hosted cloud agents that keep code and tool execution inside your own network, and the docs advertise “My Machines” for running Cloud Agents on a laptop, devbox, or remote VM. citeturn35view0turn34search0turn34search1turn34search2

In other words, among your options, **Option C is the right immediate posture**, but with an important refinement: **make self-hosted cloud agents your strategic destination**, and make **local+replay** your tactical fallback for non-git or otherwise unsupported workspaces. citeturn12view0turn35view0turn51view0

## What Cursor says is durable and what it does not

Cursor’s public SDK material draws a very clear distinction between **local** and **cloud** runtimes. In the official runtime-choice reference, cloud is the runtime to use when the agent must “run longer than the caller’s process can stay alive”, and the capability matrix states that cloud **outlives the caller process** while local does not. The same document says cloud requires a GitHub repo URL, whereas local works directly against `cwd`. citeturn12view0

At the same time, the official advanced SDK reference says `Agent.resume(agentId, ...)` exists for both runtimes, and that what persists includes **conversation history and agent state**; for cloud, it also says “the whole agent” persists, including clone/branch/PR state. It additionally says local agents are discovered under a workspace via `Agent.list({ runtime: "local", cwd })`, and that persisted messages can be listed per agent with `Agent.messages.list(...)`. citeturn12view1

Taken together, the official material supports a more nuanced conclusion:

- **Cloud durability is a first-class product contract.** Cursor’s changelog and announcement explicitly describe the Cloud Agents API as being reworked around **durable agents and per-prompt runs**, with explicit lifecycle operations such as archive, unarchive, and permanent delete. citeturn51view0turn51view2
- **Local persistence exists, but it is not presented as a production-grade durability contract.** Cursor documents local persistence in terms of workspace-scoped state under the workspace’s Cursor data directory and resumption within that context, but simultaneously tells you not to rely on local when the agent must survive beyond the lifetime of the caller process. citeturn12view0turn12view1

That distinction matters for your architecture. The docs support the idea that a local agent may be resumable in favourable conditions; they do **not** support treating a local `agent-...` ID as equivalent to a durable, long-lived cloud thread. citeturn12view0turn12view1

One more important operational point: even “local” Cursor execution is **not offline**. A Cursor staff reply explains that requests are first sent from the user’s machine to Cursor’s servers, where final prompt construction and other preprocessing occur, and that this step cannot currently be bypassed. That is not SDK-specific language, but it is highly relevant to understanding why local mode can still depend on Cursor-side state or routing. citeturn38view0

What Cursor **does not publicly document**, in the material reviewed here, is just as important: I did **not** find a published TTL, heartbeat contract, keepalive guarantee, or garbage-collection policy for standard local `agent-...` state. The public docs describe *how to resume* and *where local state is anchored* (`cwd`), but they do not publish a retention SLA for local server-side/session-side state. citeturn12view0turn12view1

## Why `Agent.resume` is failing in practice

The public docs describe `Agent.resume` as working when you have the right runtime options and, for local, the right workspace path. The advanced reference is explicit that on resume you must re-pass **inline MCP servers**, that local resumption depends on the `cwd` still existing, and that local ambient settings are reloaded from the environment rather than being fully persisted. The runtime-choice reference adds that local agents are scoped to the workspace’s data directory and that, unlike cloud agents, they are not meant to outlive the caller process. citeturn12view0turn12view1

So, in documented terms, `Agent.resume("agent-...")` is most likely to succeed when all of the following are true:

- you are resuming as **local** rather than accidentally treating the ID like a cloud `bc-...` agent;
- you pass the same essential runtime options again;
- the **same `cwd` still exists** and still maps to the same Cursor data directory;
- any required **inline MCP config** is supplied again. citeturn12view1turn12view0

However, the empirical evidence is much weaker for local mode than for cloud mode.

A fresh community bug report from late April 2026 shows that local agents in `@cursor/sdk` versions 1.0.7 through 1.0.12 were failing to retain conversation context across repeated `agent.send()` calls **even on the same SDKAgent instance**, while cloud agents behaved correctly. A Cursor staff member acknowledged that this did **not** match the SDK docs, filed it internally as a separate bug, and noted a possible issue involving `sdk-agent-store/` being keyed by `process.cwd()` rather than `local.cwd()`. The same thread explicitly says the current workaround is either to use `cloud: { repos }` or to manually include prior turns in the prompt. citeturn22view0

That thread does not prove that your exact “Agent not found after days” failure is the same bug. But it does prove something operationally important: **local-agent continuity is currently unreliable enough that Cursor staff are openly recommending cloud or manual replay as the workaround**. citeturn22view0

By contrast, cloud durability is reinforced repeatedly in official material. Cursor’s changelog says the Cloud Agents API is now run-scoped around **durable agents**; the announcement says cloud agents keep running when your laptop sleeps; the runtime-choice reference says cloud agents can be resumed anywhere by `bc-...` ID. citeturn51view0turn51view2turn12view0

On transport and long-lived connections, Cursor’s public material points to **SSE and HTTPS**, not a documented WebSocket durability contract. The 2026 changelog explicitly mentions SSE streaming with reconnect via `Last-Event-ID`, and the self-hosted cloud-agent blog says workers connect outbound via HTTPS to Cursor’s cloud. Community logs from self-hosted worker mode show heartbeat frames arriving every 30 seconds, but that is worker-bridge behaviour, not a documented keepalive contract for standard local SDK agents. citeturn51view0turn35view0turn50view0

The practical conclusion is straightforward: **cloud resume is a supported product path; local resume is a convenience feature whose current real-world reliability is not strong enough for hours-or-days-later orchestration**. citeturn12view0turn22view0turn51view0

## Cloud agents, self-hosted workers, and workspace constraints

For **standard cloud runtime**, the constraints are clear. Cursor documents cloud agent creation in terms of:

```ts
cloud: {
  repos: [{ url: "https://github.com/your-org/your-repo", startingRef: "main" }]
}
```

The runtime-choice reference says cloud **requires a GitHub repo URL**, clones from `startingRef`, provisions a VM, and can push a branch or open a PR. It also explicitly says cloud cannot see uncommitted local changes and that if you are trying to emulate local by using `workOnCurrentBranch`, you should usually use local instead. citeturn12view0

So the definitive answer for your “arbitrary filesystem paths” question is:

- **No public standard-cloud API path is documented for “point this cloud agent at an arbitrary local filesystem path”.**
- The documented standard-cloud abstraction is **repo-based**, not path-based. citeturn12view0

Where the picture changes materially is **self-hosted cloud agents**.

Cursor’s March 2026 launch post says self-hosted cloud agents keep **code and tool execution entirely in your own network**, that a worker connects outbound to Cursor over HTTPS, and that Cursor’s cloud handles inference and planning while sending tool calls to the worker for execution **on your machine**. The post says each agent session gets its own dedicated worker started via `agent worker start`, and that workers may be **long-lived or single-use**. It also says Cursor provides a Helm chart and Kubernetes operator for large-scale worker fleets. citeturn35view0

The accompanying public docs/search snippets reinforce that there are now multiple official self-hosted deployment surfaces:

- **Self-Hosted Pool** for operating a pool of self-hosted Cloud Agent workers. citeturn34search1
- **Self-Hosted on Kubernetes** via a Cursor operator and Helm chart. citeturn34search2
- **My Machines**, described as running Cloud Agents on a machine you already use, such as a laptop, devbox, or remote VM. citeturn34search0

This is the clearest official path toward “local-agent-like filesystem access with cloud-agent-like durability”. Cursor is now explicitly supporting **cloud agent sessions whose execution happens on your infrastructure** rather than Cursor-hosted VMs. citeturn35view0turn34search0turn34search1turn34search2

There are still constraints, though. Public evidence suggests self-hosted cloud agents are **still repo-oriented in practice**:

- Cursor’s public Cloud Run worker guide clones a `REPO_URL` into `/workspace/repo` and says the worker requires the current working directory to be **the git repo**. citeturn23view0
- Community self-hosted worker logs show the worker deriving a **repo label from git origin** and binding the workspace path to a local checked-out repository. citeturn50view1

So the best current answer is:

- **Self-hosted cloud agents absolutely help if your real need is “durable sessions on infra I control”.**
- **They do not, from the public material reviewed here, eliminate the repo assumption in the same way that `local: { cwd }` does.**
- If you need truly arbitrary non-git filesystem paths, **public documentation is not yet sufficient to say self-hosted cloud agents solve that cleanly**. citeturn35view0turn23view0turn50view1

That said, for a platform like Stigmer that already provisions isolated sandboxes, **self-hosted cloud agents are the most plausible long-term bridge** between durability and private execution. citeturn35view0turn34search0turn34search1

## Context continuity, summarisation, and replay quality

Cursor’s SDK references expose several useful facts about conversation continuity.

First, on the happy path, the SDK’s model is that an **agent** owns multi-run history and state. The advanced reference says conversation history and agent state persist, `run.conversation()` gives you conversation turns for a run, and `Agent.messages.list(agentId, ...)` gives you the full persisted conversation across runs. citeturn12view1

Second, Cursor explicitly warns that persisted/replayed history is not always as rich as the live stream. The advanced reference says replayed runs may be **sparser** than live local runs if the originating runtime did not capture all tool arguments/results, and the streaming reference says tool-call payloads may be **trimmed server-side** using `truncated` flags. citeturn12view1turn28view3

Third, Cursor’s broader agent documentation confirms that **internal summarisation is real**. In Cursor’s January 2026 best-practices post, the company says long conversations can make the agent lose focus and explicitly describes quality degradation “after many turns and summarizations”. The same article recommends starting a fresh conversation when you switch tasks or the agent grows confused, and using `@Past Chats` to let the agent **selectively** read prior history instead of copy-pasting whole transcripts. citeturn45view0turn45view1

That gives you the most reliable answer currently possible to the “native resume vs replay quality” question:

- **Yes, Cursor appears to do internal context management beyond naive raw replay.**
- The public evidence for that is the company’s own language about accumulated noise after “many turns and summarizations”, plus its recommendation to selectively rehydrate prior context instead of duplicating everything verbatim. citeturn45view0turn45view1

I would therefore make the following explicit inference for architecture design: **native `Agent.resume` should generally preserve quality better than feeding a fresh agent a giant raw transcript**, because Cursor’s own harness is summarising, selecting, and pruning context internally. That inference is well-supported by Cursor’s product guidance, but Cursor does **not** publish a formal benchmark or a numeric context-window policy for SDK agents in the material reviewed here. citeturn12view1turn45view0

For replay design, that leads to a clear best practice:

- **Do not replay full transcripts by default.**
- **Do not replay bulky raw tool outputs unless they are uniquely important.**
- **Replay a compact session memory**, then let the agent re-open the workspace and pull the rest of the context on demand. Cursor explicitly encourages keeping context lean and relying on agent search tools to fetch relevant details as needed. citeturn45view0turn12view1turn28view3

For Stigmer, the ideal replay artefact is not a transcript; it is a structured memory document containing:

- user goal and acceptance criteria;
- current status;
- decisions made and why;
- changed files / branch / commit / artefacts;
- unresolved issues and next steps;
- distilled findings from tool calls, with paths to raw artefacts if needed.

That design aligns with Cursor’s own guidance to externalise durable context into plans, rules, and other workspace artefacts, rather than letting endless chat history carry all the state. Cursor specifically recommends saving plans to the workspace because that makes it easier to resume interrupted work and gives future agents context for the same feature. citeturn45view0

## Recommendation for Stigmer

### Recommended architecture

For your current stack — Temporal activities inside Daytona sandboxes with a stored `thread_id` — I would use the following decision rule.

**When the workspace is repo-backed and supported by Cursor cloud, prefer a durable cloud thread.** That can be Cursor-hosted cloud or, ideally, self-hosted cloud agents / My Machines if you need execution on infrastructure you control. This is the path Cursor is explicitly turning into a durable product surface. citeturn51view0turn51view2turn35view0turn34search0

**When the workspace is only a local filesystem path, treat Cursor local as ephemeral execution, not durable memory.** Try `Agent.resume` for short-gap continuity, but make replay fallback the norm rather than the exception. Cursor’s own guidance and current bug reports do not justify betting your platform’s durability guarantees on local `agent-...` continuity. citeturn12view0turn22view0

**Do not choose “keep the local process alive longer” as your primary solution.** It may improve the odds for short idle periods, but it does not change Cursor’s documented runtime split, and it does not address the active local-context issues being reported in the SDK. citeturn12view0turn22view0

### Recommended resume flow

The practical flow I would implement is:

1. **Attempt native resume first** for local sessions.
2. If resume fails with “Agent not found”, if follow-up memory is clearly missing, or if the idle gap exceeds your own threshold, **create a fresh local agent**.
3. Before sending the new user message, prepend a compact “continuation pack” derived from your own checkpointed memory.
4. Ask the agent to **read a workspace memory file first** and re-orient itself from the current filesystem state. Cursor’s own best-practice guidance strongly favours letting the agent fetch context on demand rather than flooding it up front. citeturn45view0

A good Stigmer continuation prompt shape is:

```ts
function buildContinuationPrompt(memory: string, userMessage: string) {
  return [
    "You are continuing an existing coding session.",
    "First, read .stigmer/session-memory.md and inspect the current workspace state.",
    "Trust the filesystem and current branch state over stale history if they differ.",
    "",
    "Session memory:",
    memory,
    "",
    "New user message:",
    userMessage,
  ].join("\n");
}
```

This pattern is not copied from Cursor docs; it is an architectural recommendation based on Cursor’s guidance that agents should find context on demand, that long conversations accumulate noise, and that plans/workspace artefacts are a better durable memory substrate than endless chat continuation. citeturn45view0turn12view1

### Recommended checkpoint contents

After every completed run, persist a file such as `.stigmer/session-memory.md` or a DB record with:

```md
# Goal
...

# Current status
...

# Decisions taken
- ...

# Changed files
- path/to/file.ts
- ...

# Validation
- Tests run:

- Artefacts/logs:

# Open questions
- ...

```

This is the best way to avoid raw transcript bloat while preserving the state that actually matters. Cursor’s own docs say replayed streams may be sparser than live ones and that tool payloads may be truncated, which is another reason not to treat raw tool event history as your sole durable memory format. citeturn12view1turn28view3

If your customers often have local/private workspaces and durability matters, the most promising Cursor-native direction is to **map Daytona sandboxes or developer devboxes onto Cursor self-hosted cloud agents / My Machines** rather than staying on standard local SDK mode forever. ## 2. `Agent.resume` behavior and limitations

### Local resume

For local IDs, `Agent.resume("agent-...")` should be considered a **local store reattachment**. It succeeds only if the local SDK store can find the agent record. It can fail even when:

```text
the Daytona sandbox is alive
the workspace files still exist
the Node process is still alive
the agentId is stored correctly in Stigmer DB
```

because the lookup can still point at a different local SDK state root.

A key public bug report says local context loss reproduces across `Agent.create()` + multiple `send()` calls and across `Agent.resume()` patterns, in the same process and across separate processes. It also reports `Agent.messages.list(agentId, { runtime: "local", cwd })` returning `[]` after a successful run, while the SQLite store contains run data. ([Cursor - Community Forum][1])

### Cloud resume

Cloud agents are the more reliable native multi-turn path. Cursor staff stated that cloud agents handle prior conversation state server-side and work correctly, and recommended either switching to `cloud: { repos }` or manually injecting history for local use cases until the local bug is fixed. ([Cursor - Community Forum][4])

Cursor’s SDK announcement also explicitly says cloud agents keep going when the laptop sleeps or the network drops, and that you can stream the conversation and reconnect later. ([Cursor][2])

The updated Cloud Agents API was reworked around **durable agents and per-prompt runs**, with run-scoped follow-ups/status/streaming/cancellation, SSE streaming with reconnect via `Last-Event-ID`, and explicit lifecycle controls like archive, unarchive, and permanent delete. ([Cursor][5])

### WebSocket / long-lived connection

For cloud, the public changelog specifically mentions SSE streaming and reconnect support via `Last-Event-ID`. I did not find a local-agent heartbeat or “keep this local agent alive” mechanism in public docs. ([Cursor][5])

For Stigmer, this means **keeping the Temporal activity worker process warm may help active runs**, but it should not be treated as a durability strategy for multi-day conversations.

## 3. Cloud agents and workspace constraints

Cloud/background agents are repo-centric. The Background Agent API launch endpoint requires `source.repository`, described as the GitHub repository URL, with optional `source.ref`. Its response examples use `bc_abc123` background-agent IDs. ([Cursor Documentation][6])

The official SDK announcement’s cloud example likewise uses:

```ts
cloud: {
  repos: [{ url: "https://github.com/cursor/cookbook", startingRef: "main" }],
  autoCreatePR: true,
}
```

and says each cloud agent gets a clone of the repo in a dedicated VM. ([Cursor][2])

I found no documented mechanism to point a cloud agent at an arbitrary already-mounted Daytona filesystem path. The documented cloud source model is GitHub repo/ref, not `LocalPathSource`.

Self-hosted cloud agents improve security and network locality, but they do not appear to remove the repo-centric model. Cursor’s self-hosted cloud-agent announcement says code and tool execution stay in your infrastructure, while Cursor handles orchestration/model access/user experience; the worker receives tool calls for execution. ([Cursor][7])

A Cursor staff forum answer says API-created self-hosted agents are supported by passing `"usePrivateWorker": true` to `POST /v0/agents`, but the example still uses `source.repository` and `source.ref`. It also says self-hosted Cloud Agents are Team/Enterprise, not personal Pro. ([Cursor - Community Forum][8])

So:

```text
Cloud agents = durable native agent/session behavior, but GitHub-repo shaped.
Local agents = arbitrary filesystem path, but local durability/context behavior is currently not reliable.
Self-hosted cloud = cloud-agent lifecycle with execution in your infra, still repo/API shaped.
```

## 4. Cloud lifecycle: not “indefinite”

Your belief that cloud agents persist indefinitely until archived/deleted is too strong.

The older Background Agent docs say background agents require data retention “on the order of a few days.” ([Cursor Documentation][9])

The Background Agent status API includes an `EXPIRED` status in its status enum, which is direct evidence that cloud/background agents can expire. ([Cursor Documentation][10])

The API also provides a delete endpoint that permanently deletes a background agent and associated resources, and the updated Cloud Agents API added explicit archive/unarchive/permanent delete controls. ([Cursor Documentation][11])

So the correct phrasing is:

**Cloud agents are the native durable/reconnectable Cursor agent mode, but public docs do not guarantee indefinite retention. Design Stigmer as the long-term system of record.**

## 5. Context window and conversation continuity

### What Cursor publicly promises

Cursor’s SDK announcement says SDK-launched agents use the full Cursor harness, including “intelligent context management” via codebase indexing, semantic search, and grep. ([Cursor][2])

Cursor’s general context docs say Cursor automatically pulls in relevant parts of the codebase, including current file, semantically similar patterns, and other session information. They also distinguish intent context from state context, which is useful for replay design. ([Cursor Documentation][12])

The Background Agent API has a conversation endpoint that retrieves background-agent conversation history, ordered chronologically, and says conversation is inaccessible if the background agent has been deleted. ([Cursor Documentation][13])

### What is not publicly specified

I did not find a public Cursor SDK guarantee for:

```text
exact context window size
exact summarization algorithm
whether all prior tool calls are restored verbatim
whether local Agent.resume restores the same context as cloud Agent.resume
whether native cloud context uses hidden summaries, retrieval, tool-output compression, or pruning
a configurable TTL / eviction policy for local SDK agents
a supported checkpoint export/import mechanism for local agents
```

Cursor’s CLI docs do mention `/compress` to free up context-window space and `--resume [thread id]` / `cursor-agent resume` to continue a prior thread, which shows Cursor has user-facing context compression/resume concepts in the CLI. But that is CLI documentation, not a formal SDK guarantee for local agents. ([Cursor Documentation][14])

### Quality implication

Native cloud resume likely has a quality advantage over raw replay because cloud agents are explicitly said to use Cursor’s full harness and server-side conversation handling. But for **local SDK agents today**, the observed behavior is worse than replay: local agents may not load prior context at all. Cursor staff currently recommends manual history injection as the workaround. ([Cursor - Community Forum][4])

So the quality concern is real, but the current local baseline is not “native Cursor context management.” The current local baseline, per public bug reports, is often **no prior conversation context loaded**.

## 6. Architecture recommendation for Stigmer

### Recommended decision

Adopt **Option C**, but implement it like this:

```text
1. Cloud/self-hosted cloud agents when a GitHub repo/ref is available
   and the user expects durable native Cursor conversation behavior.

2. Local agents for arbitrary Daytona filesystem paths,
   but with Stigmer-owned durable memory/replay as the correctness layer.

3. Local Agent.resume remains an optimization, not the source of truth.

4. Stigmer DB stores:
   - Cursor agentId / run IDs
   - full user/assistant transcript
   - compacted running summary
   - file changes / workspace facts
   - tool-result summaries
   - current task state
   - resume failure diagnostics
   - SDK version, process cwd, local cwd, platform stateRoot/workspaceRef

5. Temporal remains the orchestration/durability boundary.
   Cursor’s agentId is not the durability boundary.
```

This fits your own architecture: Temporal already gives you durable workflows/activities, and your session DB already stores `session.spec.thread_id`. The change is to stop treating `thread_id = cursor agentId` as sufficient. Make `thread_id` either a Stigmer session/thread ID, or store Cursor’s agentId as a provider-specific execution handle under the session.

### What to do immediately

For local mode, pass an explicit stable SDK platform state root and workspace reference on both create and resume. Based on the SDK package types, `AgentOptions` accepts `platform?: CursorAgentPlatformOptions`; package code recognizes `platform.workspaceRef` and `platform.stateRoot`.

```ts
import { Agent } from "@cursor/sdk";
import path from "node:path";

type CursorSessionConfig = {
  apiKey: string;
  sessionId: string;
  workspacePath: string;      // e.g. /workspace/customer-project
  sandboxRoot: string;        // e.g. /workspace
  modelId: string;
  existingAgentId?: string | null;
};

function localCursorOptions(cfg: CursorSessionConfig) {
  const stateRoot = path.join(
    cfg.sandboxRoot,
    ".stigmer",
    "cursor-sdk-state",
    cfg.sessionId,
  );

  return {
    apiKey: cfg.apiKey,
    model: { id: cfg.modelId },
    local: {
      cwd: cfg.workspacePath,
      settingSources: ["project"] as const,
    },
    platform: {
      // Do not let process.cwd() decide the local SDK store identity.
      workspaceRef: `stigmer-session:${cfg.sessionId}`,
      stateRoot,
    },
  };
}

export async function createOrResumeLocalCursorAgent(cfg: CursorSessionConfig) {
  const options = localCursorOptions(cfg);

  if (cfg.existingAgentId?.startsWith("agent-")) {
    try {
      const agent = await Agent.resume(cfg.existingAgentId, options);
      return { agent, resumed: true, reason: "native-local-resume" as const };
    } catch (err) {
      if (!isCursorAgentNotFound(err)) throw err;

      // Do not fail the user turn. Fall through to a fresh local agent
      // and use Stigmer replay/summary as the continuity layer.
    }
  }

  const agent = await Agent.create(options);
  return { agent, resumed: false, reason: "fresh-local-agent" as const };
}

function isCursorAgentNotFound(err: unknown): boolean {
  const msg = err instanceof Error ? err.message : String(err);
  return /Agent .* not found/i.test(msg);
}
```

This may not fix the confirmed local context-loading bug, but it should reduce avoidable `Agent not found` caused by state-root drift.

### Do not rely on local native context even after successful resume

Until Cursor ships and confirms a fix, send a compact continuation prompt in local mode even when `Agent.resume()` succeeds. That prevents “successful resume but no memory” from silently degrading user experience.

```ts
const continuationPrompt = buildCursorContinuationPrompt({
  userMessage,
  durableSummary: await db.getSessionSummary(sessionId),
  recentTurns: await db.getRecentTurns(sessionId, 8),
  workspaceDigest: await collectWorkspaceDigest(workspacePath),
  openTasks: await db.getOpenTasks(sessionId),
  changedFiles: await db.getChangedFiles(sessionId),
  lastKnownCommands: await db.getCommandSummaries(sessionId),
});

const run = await agent.send(continuationPrompt);
```

## 7. Replay design: how to reduce quality loss

The replay prompt should not be a raw transcript dump. Treat it as a **state restoration packet**.

Use this structure:

```text
<stigmer_continuation>
  <session_identity>
    Stigmer session ID
    Cursor provider/session handle if any
    Workspace path
    Current date/time
  </session_identity>

  <standing_instructions>
    Agent identity, coding style, user preferences, safety/tool policies.
  </standing_instructions>

  <durable_summary>
    Compressed summary of the conversation so far.
    Focus on decisions, requirements, constraints, unresolved questions.
  </durable_summary>

  <workspace_state>
    Current git branch / commit if available.
    Dirty files.
    Files created/modified/deleted by prior runs.
    Important paths.
    Known tests/build commands.
  </workspace_state>

  <recent_turns>
    Last N user/assistant turns verbatim, usually 4-10 turns.
  </recent_turns>

  <tool_observations>
    Summaries of important command outputs, errors, test failures, logs.
    Include paths and exit codes. Avoid huge raw stdout/stderr.
  </tool_observations>

  <current_user_message>
    The new user message.
  </current_user_message>

  <operating_rules>
    Re-read files before editing.
    Treat filesystem as source of truth.
    Do not assume old tool outputs are still current.
    Ask for clarification only when blocked.
  </operating_rules>
</stigmer_continuation>
```

Example:

```ts
function buildCursorContinuationPrompt(input: {
  userMessage: string;
  durableSummary: string;
  recentTurns: Array<{ role: "user" | "assistant"; text: string }>;
  workspaceDigest: string;
  openTasks: string[];
  changedFiles: string[];
  lastKnownCommands: Array<{
    command: string;
    cwd: string;
    exitCode: number;
    summary: string;
  }>;
}) {
  return `
You are continuing an existing Stigmer coding-agent session.

<continuation_contract>
Use the context below as durable session memory. The live filesystem is the source of truth.
Before editing a file that matters, inspect it again. Do not assume old command output is still current.
</continuation_contract>

<durable_summary>
${input.durableSummary || "(No prior summary.)"}
</durable_summary>

<workspace_state>
${input.workspaceDigest}
Changed files from prior turns:
${input.changedFiles.map((f) => `- ${f}`).join("\n") || "- None recorded"}
</workspace_state>

<open_tasks>
${input.openTasks.map((t) => `- ${t}`).join("\n") || "- None recorded"}
</open_tasks>

<recent_turns>
${input.recentTurns
  .map((t) => `<turn role="${t.role}">\n${t.text}\n</turn>`)
  .join("\n\n")}
</recent_turns>

<important_tool_observations>
${input.lastKnownCommands
  .map(
    (c) => `- cwd=${c.cwd}
  command=${c.command}
  exit=${c.exitCode}
  summary=${c.summary}`,
  )
  .join("\n")}
</important_tool_observations>

<current_user_message>
${input.userMessage}
</current_user_message>
`.trim();
}
```

### Tool-call replay policy

Do **not** replay full raw tool logs by default. For coding agents, huge tool output is usually lower value than:

```text
command
working directory
exit code
short failure summary
top 20-50 relevant lines
artifact/file paths
test names
stack trace frames
timestamps
hashes/checksums if relevant
```

Let the agent re-run commands or re-read files when it needs current state. Cursor’s own context docs emphasize that context should describe both intent and current state; insufficient or irrelevant context can push the agent toward hallucination or unnecessary exploration. ([Cursor Documentation][12])

### Summary policy

Maintain two memories:

```text
1. Running durable summary
   Updated after each turn.
   Target: 1k-4k tokens.

2. Recent-turn window
   Verbatim last N turns.
   Target: 4-10 turns depending on size.
```

For long sessions, store structured facts separately:

```json
{
  "decisions": [],
  "constraints": [],
  "files_changed": [],
  "commands_run": [],
  "open_questions": [],
  "failed_attempts": [],
  "successful_tests": [],
  "user_preferences": [],
  "current_plan": []
}
```

This gives you a stable continuation layer that survives local Cursor SDK bugs, Daytona restarts, and cloud-agent expiry.

## 9. Direct answers to your seven investigation areas

### 1. Cursor local agent server-side lifecycle

I found no public documentation for a local-agent server-side TTL, heartbeat, or server-side GC. The available evidence says local SDK agent metadata/runs are stored locally, and `Agent.resume("agent-...")` uses the local store path. The public local-context bug report found persisted SQLite run data under `sdk-agent-store`, not reliable server-side context restore. ([Cursor - Community Forum][1])

### 2. `Agent.resume` behavior and limitations

Local resume can fail when the local store cannot find the agent. In `@cursor/sdk@1.0.12`, direct package inspection shows `Agent.resume("agent-...")` routes through `createAgentPlatform(options?.platform).resumeAgent(...)`, while cloud IDs/options route through `resumeCloudAgent`. Public reports show local resume/multi-send patterns currently fail to load previous context even when persisted data exists. ([Cursor - Community Forum][1])

### 3. Cloud agents and workspace constraints

Cloud/background agents are documented as repository-based. The API launch endpoint starts an agent “to work on your repository” and requires `source.repository`; the SDK cloud example passes `cloud.repos`. I found no public mechanism to point cloud agents at arbitrary Daytona paths. ([Cursor Documentation][6])

### 4. Context window and conversation continuity

Cloud agents have API-visible conversation history and server-side handling; local agents currently have a confirmed bug where prior conversation state is not loaded. Cursor exposes intelligent context management generally, but no public SDK-level contract for exact context window, summarization algorithm, or tool-output compression. ([Cursor Documentation][13])

### 5. Alternative patterns

There is no separate public “session” abstraction I found that solves this for local SDK agents. The model is Agent + Runs; the Cloud Agents API is being reworked around durable agents and per-prompt runs. I found no public local TTL configuration or supported local checkpoint restore API. ([Cursor][5])

### 6. Hybrid architecture

For both local filesystem access and durable conversations, the best pattern is **not** “force everything into cloud.” It is:

```text
Cloud/self-hosted cloud for repo-backed workspaces.
Local + Stigmer replay for arbitrary filesystem workspaces.
```

Self-hosted cloud helps with code/tool execution staying inside your infrastructure, but public docs/examples still describe repo cloning and API creation with `source.repository`, not attaching to arbitrary pre-existing filesystems. ([Cursor][7])

### 7. Context replay vs native resume quality

Cloud native resume is probably higher quality when available because it uses Cursor’s server-side cloud-agent state and full harness. But local native resume is not currently trustworthy for continuity. Cursor staff’s current workaround is manual history injection or cloud mode. ([Cursor - Community Forum][4])

## Final recommendation

Make **Stigmer the durable conversation system**, not Cursor local agents.

Use Cursor as an execution harness with two modes:

```text
Repo-backed durable mode:
  Cursor cloud / self-hosted cloud agent
  Native Cursor context
  Stigmer mirrors transcript + summaries because cloud can expire

Arbitrary-path mode:
  Cursor local agent
  Explicit platform stateRoot/workspaceRef
  Best-effort native resume
  Always include Stigmer replay/summary until Cursor fixes local context
```

This gives you the product behavior you need: users can come back hours or days later and continue the same Stigmer session, regardless of whether the underlying Cursor local agent ID is still resumable.
