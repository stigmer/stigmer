# Deep Research: Cursor SDK Agent Lifecycle, Durability, and Multi-Turn Conversation Architecture

## Research Objective

We are building an AI agent orchestration platform (Stigmer) that uses the **Cursor SDK (`@cursor/sdk`)** as one of its execution harnesses. We need a thorough understanding of how Cursor SDK agents persist (or don't), what happens to agent state across disconnections, and what the correct architectural pattern is for building durable multi-turn conversations that may span hours or days of idle time.

## Context and Known Information

### Our Architecture
- We run agents inside **Daytona sandboxes** (ephemeral Linux containers with persistent disk)
- A **cursor-runner** (TypeScript/Node.js) process runs inside the sandbox as a **Temporal activity worker**
- Each user message triggers a new Temporal activity (`ExecuteCursor`) that either creates or resumes a Cursor agent
- The Cursor `agentId` is stored in our database as `session.spec.thread_id`
- We use **local runtime** (`Agent.create({ local: { cwd: "/workspace/..." } })`) because users pass arbitrary local filesystem paths as workspaces

### The Problem We Observed
1. User sends first message -> `Agent.create({ local: { cwd } })` succeeds, returns `agent-<uuid>` ID
2. We store the agentId in our DB
3. User sends second message (seconds to days later) -> `Agent.resume("agent-<uuid>")` -> **"Agent not found"**
4. The sandbox was still alive, the Node process was still running, but Cursor's backend no longer knew about the agent

### What We Believe (Needs Verification)
- Local agents (`agent-` prefix) have server-side state that gets garbage-collected after the SDK client disconnects or after some TTL
- Cloud agents (`bc-` prefix) persist indefinitely until explicitly archived/deleted
- The SDK docs say `Agent.resume` works for "continuing after the local process restarted" but don't specify a TTL or eviction policy

## Specific Areas to Investigate

### 1. Cursor Local Agent Server-Side Lifecycle
- What exactly happens server-side when you call `Agent.create({ local })` vs `Agent.create({ cloud })`?
- Is there a documented or empirically known TTL for local agent state on Cursor's servers?
- Does the agent state persist across SDK client disconnections? For how long?
- Is there a heartbeat mechanism that keeps local agents alive?
- What triggers garbage collection of a local agent on Cursor's side?

### 2. Agent.resume Behavior and Limitations
- Under what conditions does `Agent.resume("agent-...")` succeed vs fail?
- Is there a difference in resume reliability between local and cloud agents?
- Does the Cursor SDK maintain a WebSocket/long-lived connection that keeps agents alive?
- If the SDK process exits and restarts, can it always resume a local agent? Is there a time limit?

### 3. Cloud Agents and Workspace Constraints
- Cloud agents require `cloud: { repos: [...] }` — can you pass arbitrary filesystem paths?
- Is there any mechanism to use cloud agents with a pre-provisioned filesystem (not git clone)?
- Can cloud agents be pointed at a self-hosted runner's filesystem somehow?
- What is the documented lifecycle of cloud agents? Do they ever expire without explicit deletion?

### 4. Context Window and Conversation Continuity
- When you `Agent.resume`, does Cursor restore the full conversation context?
- Is there a context window limit after which earlier messages are summarized or dropped?
- Does Cursor handle context summarization internally, or does the caller need to manage it?
- If we replay messages manually (passing prior conversation as a long prompt to a new agent), how does that compare quality-wise to native `Agent.resume` with Cursor's internal context management?

### 5. Alternative Patterns for Durable Conversations
- How do other platforms building on the Cursor SDK handle multi-turn conversations that span long idle periods?
- Is there a "session" concept in Cursor separate from agents?
- Can you configure agent TTL or eviction policies?
- Is there a way to "warm up" or "restore" a local agent from a checkpoint/snapshot?

### 6. Hybrid Architecture Patterns
- For a platform that needs BOTH local filesystem access AND durable conversations:
  - Is the recommended pattern to always use cloud agents + git repos?
  - Or is there a way to get local-agent-like filesystem access with cloud-agent-like durability?
  - What about the "self-hosted pool" mentioned in Cursor docs — does that help?

### 7. Context Replay vs Native Resume (Quality Impact)
- If we accept that local agents are ephemeral and build a "replay" mechanism:
  - How should we structure the replayed context? (full messages vs summarized?)
  - Tool call results can be very large — should they be summarized or omitted?
  - Does Cursor's internal context management do something smarter than raw message replay?
  - What is the maximum effective context size before quality degrades?
  - Are there best practices for "conversation continuation" prompts that preserve agent behavior?

## Why This Matters

We need to make an architectural decision between:
- **Option A**: Accept local agents are ephemeral; build context replay when resume fails (concern: context window bloat from tool calls, quality degradation vs native Cursor context management)
- **Option B**: Use cloud agents for all cloud executions (concern: loses LocalPathSource support for users who don't have git repos)
- **Option C**: Hybrid — cloud agents when git repos available, local agents with "best-effort resume" and clear user expectations about durability
- **Option D**: Keep local runner processes alive longer to extend agent lifetime (concern: resource cost, doesn't solve the "days later" case)

The quality concern is real: if Cursor internally does sophisticated context management (summarization, attention-based pruning, tool-call compression) that we lose by replaying raw messages to a fresh agent, that's a significant quality regression.
