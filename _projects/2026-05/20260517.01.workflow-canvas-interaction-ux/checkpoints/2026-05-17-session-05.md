# Session Notes: 2026-05-17 (Session 05)

## Accomplishments

- Fixed stale-closure bug in `addSuccessorTask` and `insertTaskOnEdge` — task picker selections now correctly add new nodes to the canvas
- Fixed Tauri desktop app blocking HTML5 drag-and-drop from the palette via `dragDropEnabled: false`
- Replaced naive `getBoundingClientRect` subtraction with React Flow's `screenToFlowPosition` for viewport-aware drop positioning

## Decisions Made

- **Stale closure fix**: Capture `dispatch()` return value and pass it into the `requestAnimationFrame` callback, matching the existing correct pattern in `onDrop`. Do NOT re-read `history.currentModel` in rAF closures — it points to the pre-dispatch model.
- **Tauri drag-drop**: Set `dragDropEnabled: false` in `tauri.conf.json`. Trade-off: loses Tauri's native file-drop-with-paths capability, but the app has no file-drop feature. Tauri team is working on a non-breaking alternative (tauri-apps/tauri#14373).
- **Drop position**: `screenToFlowPosition` is the correct API for converting screen coordinates to flow coordinates — it accounts for viewport zoom and pan offset.

## Key Code Changes

- `sdk/react/src/workflow/useWorkflowCanvas.ts`: Fixed `addSuccessorTask` and `insertTaskOnEdge` rAF closures; replaced manual drop position math with `screenToFlowPosition`; added `useReactFlow()` call
- `client-apps/desktop/src-tauri/tauri.conf.json`: Added `dragDropEnabled: false` to window config

## Learnings

- Tauri v2's built-in drag-drop system and HTML5 drag-and-drop are mutually exclusive — when `dragDropEnabled` is `true` (default), all DOM `dragover` and `drop` events are suppressed
- Tauri config changes (`tauri.conf.json`) require a full Rust recompile, not just Vite HMR
- When using `requestAnimationFrame` inside `useCallback` hooks that read from React state-derived objects, the rAF closure captures the stale pre-update value — always pass computed data into the rAF via local variables
