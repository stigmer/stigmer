# State-of-the-Art Workflow UX for Stigmer

## Strategic conclusion

The strongest pattern across the best-documented workflow products is not “show more logs”; it is “keep the user anchored in the workflow structure they designed, then layer execution, timing, and diagnostics on top”. AWS Step Functions gives users graph, table, and events views from the same execution; Azure Logic Apps lets users switch between workflow, code, and run history in the same designer surface; Airflow combines Graph, Grid, Gantt-style views, and run tabs; Inngest now uses an interactive waterfall timeline plus a details pane; LangSmith Studio exposes graph mode with nodes traversed and intermediate state; and Temporal’s Web UI leans heavily into searchable visibility, history, and metadata rather than a graphical execution canvas. Taken together, the lesson is that Stigmer should treat **design-time graph**, **run-time state overlay**, **time-based trace**, and **raw event/log detail** as four coordinated views of the same underlying execution, not as separate experiences that drift apart. citeturn2view0turn16view3turn27view0turn33view1turn18search0turn32view0

For Stigmer specifically, that implies three big moves. First, replace the current log-centric execution page with a **read-only execution canvas** that reuses the exact node positions and shapes from the editor, adds live status overlays, and opens an inspector with inputs, outputs, tokens/cost, retries, and errors when a node is clicked. Second, replace the current “everything is a rectangular card” visual grammar with a small, disciplined set of shapes grounded in BPMN/UML semantics so users can scan conditionals, waits, parallelism, human steps, and AI work at a glance. Third, replace dagre as the primary layout engine with **ELK Layered** configured for ports, model order, and incremental stability. Those three changes will move the product much closer to the quality bar set by Step Functions, Airflow, Azure Logic Apps, Inngest, and the better AI-native tools. citeturn2view0turn21search1turn27view0turn33view1turn9search8turn9search13turn10search0turn10search6

The practical recommendation is **not** a full platform rewrite. Keep React Flow as the canvas foundation, keep the command/history pattern, keep YAML as the source language, and keep Temporal as the execution engine. What should be thrown away is the current node grammar, the current broken add-task interactions, the current mini overview diagram, and the current dagre-only layout approach. In other words: preserve the architecture, rewrite the workflow UX. React Flow remains a strong fit for this because it is MIT-licensed, heavily customisable, already supports custom nodes and edges as React components, supports multiple handles, and ships official examples for shapes, interactivity control, ELK integration, multi-handle layout, and save/restore. Alternatives each introduce trade-offs: GoJS is commercial; JointJS core is MPL but its richer low-code plugins are commercial; Rete is powerful but some advanced plugins have non-commercial licensing today; Cytoscape is excellent for graph analysis but weaker as a polished workflow editor foundation. citeturn31search2turn9search3turn9search7turn9search15turn10search2turn10search6turn30search3turn31search1turn31search0turn31search8turn31search3turn24search2

## Execution visualisation

The best direct benchmark is AWS Step Functions. Its execution details page explicitly offers **Graph view**, **Table view**, and **Events**, with a shared selection model between graph and table. In Graph view users can zoom, fit, go full-screen, click any state to open step details, see a legend for execution status, inspect inputs/outputs for the selected step, and browse `Map` iterations and `Parallel` branches. Failed steps are highlighted from the error banner, retries surface in the step details pane, and redrive lets an unsuccessful run continue from the failed, timed-out, or aborted step while preserving successful prior steps. That is very close to the interaction model Stigmer needs. citeturn2view0turn2view1turn21search3turn21search9turn21search13

Azure Logic Apps reaches a similar goal from a different angle. In the Standard designer, Microsoft exposes **Workflow**, **Code**, and **Run history** as top-level views in the same surface. For failed runs, the docs describe selecting the failed run, expanding each step in the run, and reviewing inputs, outputs, and errors per step. Microsoft also pairs run history with alerts and Azure Monitor diagnostics for richer debugging. The design implication is important: the run experience is not a separate “logs product”; it is an alternate mode of the same workflow artefact. Stigmer should copy that principle. citeturn16view3turn16view1turn16view0turn15search16

Airflow and Inngest show the other half of the puzzle: **time matters**. Airflow’s Graph View shows dependencies and run-specific task states, while Grid View is the primary interface for monitoring runs over time, and Gantt charts/task-duration views reveal bottlenecks. Inngest’s redesigned traces view goes even further: an interactive two-panel layout with a waterfall timeline on the left and contextual step or run details on the right, explicit bar types for queue delay, waits, invokes, execution time, and finalisation, compound bars to separate waiting from execution, zoom for long-running functions, and retry-attempt detail. For Stigmer, the lesson is that a graph alone is not enough for long-running AI work. You need a **structural canvas** and a **temporal trace view**, and users must be able to move between them without losing context. citeturn27view0turn27view1turn33view1turn33view2turn33view0

Retool Workflows and n8n are useful cautionary references. Retool’s docs describe a Run history panel with recent runs, run status, per-block status, log filtering, JSON download, and aggregate analytics for run counts, failure rates, latency, and resource consumption. Its Branch block can highlight the condition that evaluated `true` in green during testing. n8n’s current documentation is much more editor-centric: the Executions list, node-level data inspection, partial execution of selected steps, pinned execution data for development, and “Debug in editor” / “Copy to editor” for replaying past runs back into the canvas. Those patterns are helpful, but they still fall short of the Step Functions/Azure/Inngest bar for a first-class, live execution canvas. citeturn34view0turn34view1turn4search1turn4search3turn4search12turn1search10

Temporal’s official UI docs are revealing in a different way. The Web UI focuses on visibility and debugging: workflow lists, Saved Views, filters over status and search attributes, and a detailed execution page with History, Workers, Relationships, pending Activities, Queries, and Metadata. Temporal’s observability docs emphasise real-time monitoring, visibility, metrics, tracing, and logging, but the official documentation does **not** present the kind of structural, state-machine graph overlay that Step Functions does. I would treat Temporal as the backend execution truth and source of searchable history, not as the UX model for Stigmer’s front-end execution visualisation. citeturn32view0turn32view2

AI-native tools add one more useful ingredient. LangSmith Studio’s graph mode is explicitly for nodes traversed and intermediate states, Langflow exposes a Playground for real-time testing and built-in traces for latency/token usage, CrewAI AMP positions tracing around task timelines, tool usage, and LLM calls, and Flowise documents streaming through server-sent events for predictions. Public docs for Relevance AI and Wordware are much thinner on concrete run-view UX, so I would not use them as primary execution-view references. The most defensible Stigmer execution design is therefore: **graph-first canvas + temporal waterfall + event/log tab + rich inspector**. citeturn18search0turn18search17turn19search7turn19search3turn20search1turn20search3turn19search14turn19search4turn19search1

For implementation, I would make the execution page a read-only React Flow scene that reuses the exact saved layout for the workflow version being executed. Each node gets a runtime overlay with one status from `{pending, running, completed, failed, skipped, waiting-human, retrying}` plus optional badges for attempt count, elapsed time, stream activity, and cost. The active node should use a restrained pulse or travelling border, completed nodes should get clear success/failure glyphs, skipped branches should dim, and taken branches should retain full opacity. Clicking a node should open a dedicated runtime inspector with inputs, outputs, streamed text, logs, token/cost counters, start/end times, retries, and raw event history for that node. In parallel sections, multiple nodes can pulse simultaneously; in switch/case sections, taken edges stay bright and untaken edges fade. This is an inference from the strongest elements of Step Functions, Airflow, Inngest, Azure Logic Apps, and LangSmith rather than a direct copy of any single tool. citeturn2view0turn27view0turn33view1turn16view1turn18search0

Long-running agent output needs special treatment. Flowise shows that SSE-style token streaming is a common fit for AI output; Prefect’s artifact model explicitly includes progress indicators, Markdown, tables, images, and links rendered in the UI; and Langflow traces record latency and token usage. For Stigmer, streamed output should **not** be shoved into the node card itself beyond perhaps a one-line tail preview and a “streaming” indicator. The full stream belongs in the inspector and optionally in a bottom “Transcript / Trace” drawer keyed to the selected node. On the canvas, show progress compactly: currently streaming, elapsed time, recent token rate, and whether the stream is still open. This keeps the graph legible even when an agent runs for minutes or hours. citeturn19search14turn28search1turn19search3

## Visual grammar for nodes and overviews

Stigmer’s current “same rectangle, different stripe” approach is below the accessibility and comprehension bar. W3C’s guidance on WCAG 1.4.1 is explicit that colour must not be the only means of conveying information; users need another visual cue such as shape or text. That principle applies doubly in workflow editors, where users scan for control-flow structure, not just labels. BPMN and UML both reinforce the same idea: business/process notation uses shape as part of semantics, not decoration. BPMN is explicitly a graphical notation for business processes; gateways route tokens, activities represent work, and events represent things that happen. UML activity diagrams likewise use diamonds for decision/merge and thick bars for fork/join. citeturn9search2turn9search14turn9search8turn9search16turn9search13turn9search1

Modern tools only partially follow formal standards, but most still differentiate meaningfully. Step Functions distinguishes actions from flow states and gives Choice, Parallel, Map, Wait, Success, and Fail distinct semantics in the studio. n8n differentiates trigger operations from actions and marks triggers with a bolt icon. Node-RED organises nodes by category, supports per-node icons and colours, supports status icons under nodes, and lets switch-like nodes label ports with rule information. Unreal Blueprints and Unity’s visual tools are also instructive: they separate execution flow from data values, use strong iconography and typed ports, and lean hard on category distinctions so graphs remain scannable as they grow. citeturn21search1turn21search7turn21search12turn8search0turn12search13turn22search1turn22search0turn23search4turn23search10

For Stigmer, I would recommend a **small, opinionated shape vocabulary** rather than a unique body shape for every task kind. Too many shapes become kitsch; too few become ambiguous. A good middle ground is:

| Task family | Recommended shape | Notes |
|---|---|---|
| Start / End | pill / circle-terminal | Keep as the only fully terminal-specific shapes |
| Agent Call / LLM Call / Evaluate | rounded rectangle | Same base work shape, different icon and accent |
| HTTP / gRPC / Activity / Run Workflow | rectangle with service header or strong left icon bay | “External/service invocation” family |
| Set Variables / Transform / Validate | rectangle with data icon and lighter density | “Data operation” family |
| Switch Case | diamond | Standard decision semantics |
| Fork / Join | thick horizontal bar | UML/BPMN-consistent for parallel split/join |
| For Each | rounded rectangle with loop marker | Prefer marker over exotic body shape |
| Human Input / Approval | octagon or gate-style rounded hexagon | Distinctly non-automatic step |
| Wait | rounded rectangle with clock marker or paused state pill | Emphasise temporal pause |
| Try / Catch | container rectangle with shield marker and fallback edge | Error-handling semantics matter more than shape novelty |
| Listen / Raise Error | event circle or compact event badge shape | Only for true event semantics |

This mapping is a synthesis of BPMN/UML semantics and the scannability patterns used by Step Functions, Node-RED, and modern visual programming systems. The key is consistency: use shape for **control-flow class**, icon for **operation type**, and colour only as a tertiary cue. citeturn9search8turn9search16turn9search13turn9search1turn21search12turn22search1turn12search13

The overview page should also stop pretending to be a minimap. A tiny thumbnail with unreadable labels is neither an overview nor an editor. Airflow is a useful analogue here: it does not rely on a miniature DAG alone; it pairs overview/status information with Graph, Grid, Runs, Tasks, and Events tabs. Temporal similarly treats the list/search view and execution details page as core entry points. Stigmer’s overview should become a **full-width, read-only structural view** with click-to-inspect nodes, sensible zoom-to-fit, and optional collapse of branch internals, paired with summary cards for budget, environment, success rate, recent failures, and mean duration. On narrow screens or very dense graphs, offer a second representation: a collapsible tree or lane list rather than shrinking the canvas into uselessness. citeturn27view0turn32view0

Technically, React Flow is capable of this. Its official docs show that custom nodes are just React components, handles are regular elements that can be positioned and styled arbitrarily, and the shapes example demonstrates SVG-based diamonds, circles, and hexagons. Custom edges are also React components, which means your execution edges can carry labels, status markers, and inline insertion affordances. For Stigmer, I would use a central `<ShapeShell>` component that renders the SVG outline based on a semantic `visualClass`, then overlays HTML labels, icons, status badges, and handles. That gives you formal shapes without giving up rich text, chips, streaming indicators, or Tailwind/CSS-variable theming. citeturn9search3turn9search7turn9search15turn9search19

## Auto-layout

The research strongly favours moving from dagre to **ELK Layered** as Stigmer’s default auto-layout engine. Dagre is still a good lightweight choice for simple DAGs, but React Flow itself documents layouting as something you bring in separately, and now ships official examples for both dagre and ELK. ELK Layered supports layered/Sugiyama layouts, orthogonal routing, port constraints, hierarchy handling, model-order preservation, and semi-interactive crossing minimisation. React Flow’s official ELK examples also explicitly show multi-handle/port configuration, which matters directly for your switch/case, human-input, and fork-like nodes. citeturn10search3turn10search14turn10search2turn10search6turn11search6turn10search0turn26search1turn26search2turn11search1

ELK’s advantages map almost one-to-one to your problem cases. `org.eclipse.elk.portConstraints` and fixed port order let you keep branch outputs stable and reduce crossings; `considerModelOrder` helps preserve user intent and incremental stability; semi-interactive crossing minimisation preserves desired in-layer order while still reducing some crossings; and hierarchy handling lets grouped or nested structures be laid out with children included when needed. By contrast, d3-dag is appealing because it is lighter and TypeScript-first, and its Sugiyama implementation exposes layering, decross, and coordinate stages directly, but it does not advertise the same depth of port and hierarchy control. For Stigmer’s 10–50 task workflows with conditionals, parallelism, and multiple handles, ELK is the safer primary engine; d3-dag is a credible secondary option if bundle size or server-side layout becomes more important than routing sophistication. citeturn26search1turn26search2turn11search1turn26search3turn10search9turn10search1

The right implementation is not “run ELK on everything all the time”. It is a staged layout pipeline. Represent the workflow semantically first: identify linear sequences, switch groups, parallel groups, loop scopes, and error paths. Assign stable port identities for each outgoing branch. Measure actual node sizes after render. Then run ELK Layered with top-to-bottom direction, orthogonal or polyline routing, fixed port order, and model order informed by the workflow definition order. Cache the resulting layout per workflow version so the execution viewer can reuse it exactly. This is how you get from “algorithmic” layout to “designed” layout. The recommendation is an inference, but it is supported by ELK’s model-order and port-order capabilities and React Flow’s own layout examples. citeturn10search0turn10search6turn26search2turn26search12turn11search6

Incremental or partial relayout is worth doing from the start. ELK has options aimed at interactive and semi-interactive behaviour, specifically to preserve relative order or use existing positions as hints. For Stigmer, the practical rule should be: when a user inserts a node between two existing nodes, relayout only the local chain or affected branch cluster; when they add a new case to a switch or a new branch to a fork, relayout that control-flow group and its immediate downstream join region; reserve whole-canvas relayout for explicit “Auto-layout all” actions. This avoids the jarring “everything jumps” feeling that makes users distrust automatic layout. citeturn11search1turn26search0turn26search9turn26search10

My concrete recommendation is: keep dagre only as a fallback for server-side or emergency simple layout paths; move the main editor and overview layout to ELK; and run ELK in a worker for large graphs so UI interactions stay smooth. Since ELK is famously configurable and therefore easy to misconfigure, take the React Flow multi-handle ELK example as the baseline and build a thin Stigmer-specific layout adapter around it rather than scattering layout options throughout the editor. citeturn10search6turn10search10turn11search6turn26search7

## Editor interactions and inspector

The current “+ button does nothing / or inserts a hardcoded agent call” pattern is a high-friction bug because it violates one of the most important promises of visual editors: the canvas must feel direct and trustworthy. Other tools solve this by making insertion context-aware. n8n has an “Add node connector” on nodes and connections; Node-RED supports quick-add and even splicing a node into a wire by dropping onto its midpoint; React Flow’s own examples show adding a node on edge drop; Retool exposes an Add block flow and gives branch connectors for separate outcomes; and Step Functions uses drag/drop state insertion with a dedicated Inspector for configuration, not a muddled side panel that also tries to be the add-step picker. citeturn12search0turn12search4turn12search1turn30search16turn12search2turn12search3

For Stigmer, every add interaction should open a single, consistent **anchored command menu**. Clicking `+` on an edge should open a small searchable picker at the midpoint with scope-specific options: “Insert step”, “Insert condition”, “Insert parallel”, “Insert approval”, plus recently used types. Clicking `+` at the bottom of a node should mean “Add after”. Clicking `+` on a switch node should mean “Add case”. Clicking `+` on a fork should mean “Add branch”. The user should never wonder whether `+` means append, insert, or configure; the control itself must encode that. This recommendation is an inference from the common patterns above rather than a direct copy from one vendor. citeturn12search0turn12search1turn12search2turn30search16

Branching needs special UX rather than generic edges. Retool’s Branch block documentation is unusually clear here: you can add multiple `Else if` branches, each branch has its own connector, and the true condition is highlighted in green during testing. Node-RED also shows the value of labelled ports for switch-like logic. Stigmer should therefore model branch outputs as named, visible ports with inline labels and stable order. A switch node should render its cases explicitly on the node body or on attached lane stubs, allow reordering by drag handle, allow a default case, and expose “Add case” inline. In execution mode, the taken case edge should stay bright, the untaken ones should dim, and skipped downstream nodes should be visibly marked as skipped rather than merely uncoloured. citeturn34view1turn12search13

The inspector panel should become single-purpose: **configure the selected thing**. Step Functions uses an Inspector to edit the selected state, including input/output configuration; Node-RED uses an edit dialog with properties, description, and appearance; Figma’s Design tab is similarly selection-based and property-centric. Stigmer should follow that model. When nothing is selected, the right side should show workflow-level settings. When a node is selected, it should show a typed form with a stable structure: summary header, primary config, data mapping, runtime policies, error handling, advanced options. Node actions like delete, duplicate, disable, and convert should live in a compact header or context menu, not mixed into the primary config form. Adding new tasks should be handled elsewhere, not in the inspector. citeturn21search15turn22search4turn23search7

Because task types differ sharply, the inspector should be schema-driven per node family. An Agent Call needs model, system prompt, tools, message template, timeout, retry, streaming policy, and cost estimate fields. A Switch Case needs branch conditions and default behaviour. HTTP/gRPC nodes need request builders and test/send facilities. Human approval needs assignee, SLA, timeout, and approval payload mapping. Wait needs deadline or duration with clear relative/absolute time semantics. Try/Catch needs explicit retry policy, caught error classes, and fallback target. The visual editor should not hide these differences under one generic card; the forms should educate the user about the semantics of each step. This is again a synthesis, but it follows the typed-block philosophies of Step Functions, Retool, n8n, and Logic Apps. citeturn21search15turn34view1turn8search11turn16view2

## Workflow creation journey

The best onboarding flows today give users three obvious starts: **blank**, **template**, or **describe it with AI**. Step Functions supports starter templates alongside blank design/code creation. Azure Logic Apps exposes template starts as one workflow type. n8n now has both a huge workflow template library and an AI Workflow Builder that can create, refine, and debug workflows from natural-language goals. Retool documents “Generate a workflow using Retool AI”, and Zapier Canvas positions AI-assisted generation and next-step suggestions as core workflow-planning features. Make similarly markets visual, code, and prompt-based automation entry points. That is the current state of the art. citeturn21search5turn16view3turn13search8turn13search16turn13search1turn13search2turn13search3turn13search7

For Stigmer, the creation journey should start with a high-level choice screen: “Start from template”, “Describe a workflow”, or “Build from scratch”. Templates are not just marketing assets; they are onboarding tools and design-system enforcers. n8n’s library shows how much value users get from starting from community examples. I would seed Stigmer with a small first-party gallery focused on AI-agent orchestration patterns rather than generic business automations: agent with tools, retrieval-and-judge, human approval loop, multi-agent research, branch-on-evaluation, long-running external activity, retryable API orchestration, and workflow chaining. citeturn13search8turn13search4turn13search12

Code-vs-visual should be treated as **two editors over one lossless model**, not as an import/export trick. Step Functions explicitly supports Design and Code modes; Azure Logic Apps lets users switch between Workflow, Code, and Run history; React Flow’s save/restore model is straightforward enough to derive visual scenes from a serialisable graph; and your own YAML DSL is already a powerful source language. The non-negotiable requirement is that visual edits and YAML edits both round-trip through a shared workflow AST/IR, with stable node IDs and layout metadata stored separately but linked to the workflow version. That is what will let you show the exact same graph in Overview, Editor, and Execution. citeturn12search11turn16view3turn30search2turn30search18

AI assistance should generate drafts, not magic. n8n’s AI Workflow Builder claims to handle node selection, placement, and configuration; Retool’s generator can assemble complete workflows from a prompt. That is useful, but the common failure mode of AI-generated workflows is hidden assumptions. Stigmer should therefore make AI-generated graphs auditable: show assumptions, missing credentials, unresolved expressions, and a “why this structure?” explanation. A generated workflow should open straight into the visual editor with validation chips, placeholder variables, and a diffable YAML view rather than pretending it is production-ready. citeturn13search16turn13search1turn13search5

## Monitoring, architecture, and technology choices

Operationally, the strongest pattern is a layered monitoring model: list/search at the top, per-run details in the middle, and fleet-level metrics above all of it. Temporal Web UI gives you workflow lists, search attributes, saved views, and execution metadata; n8n gives workflow-level and all-executions lists with filters over status, times, and custom execution data; Airflow’s Dag List and Runs tabs summarise recent runs and trends; Retool adds run history and workflow analytics; Dagster+ Insights surfaces run duration, failures, and cost metrics; Inngest added environment-level dashboards, backlog/concurrency/failure metrics, and queryable Insights; and Azure Logic Apps exposes run history plus alerts and diagnostics. Stigmer should mirror that stack. citeturn32view0turn14search3turn14search7turn27view0turn34view0turn14search2turn33view2turn16view0

The workflow-level operations page should therefore include: a run table with saved filters, version, status, current node, duration, queue time, cost, and trigger source; a health strip with success rate, failure rate, average and p95 duration, approval backlog, and spend; and a recent-failure panel that groups by failing task kind or task name rather than just by run. Temporal’s Saved Views are a particularly good model for reusable filters, and Airflow’s separation of Graph/Grid/Run tabs is a good model for moving between structure and time. citeturn32view0turn27view0

On the client technology question, my recommendation is to stay with **@xyflow/react** for this launch cycle. The reasons are practical: you already use it; it is open source under MIT; it has the custom node/edge primitives you need; it integrates cleanly with Zustand-style state; and the official examples now cover much of the complexity you care about, including shapes, interactivity controls, ELK, multiple handles, expansion/collapse, and save/restore. GoJS and JointJS are both more batteries-included in some enterprise-diagramming areas, but they push you toward licensing and integration trade-offs that are hard to justify for an open-source-first Stigmer workflow editor. Rete is attractive if you want a more processing-oriented visual-programming framework, but its licensing around some advanced plugins is a real caveat. citeturn31search2turn9search3turn9search7turn9search15turn10search2turn10search6turn30search3turn11search3turn31search1turn31search0turn31search3

For state management, keep your existing domain-first command/history model, but separate it more clearly from view state. The durable source of truth should be a workflow AST/IR plus layout snapshot. Use the command/history layer for structural mutations and undo/redo. Put ephemeral editor state such as viewport, hover, selection, open toolbars, insertion-menu state, and execution playback controls in a lightweight store; React Flow itself explicitly documents using a state-management library such as Zustand, Redux, Recoil, or Jotai, and its `useStore` hook is re-exported from Zustand. I would not introduce CRDTs until you truly need concurrent multi-user editing. citeturn30search3turn30search14turn30search8

For real-time execution updates, the browser-facing transport should probably **not** be your raw Temporal gRPC stream. Browsers are naturally comfortable with SSE for server-to-client one-way event push and with WebSockets for two-way communication. MDN is explicit that SSE is one-way and WebSocket is two-way. If you want browser-native protobuf/RPC semantics, grpc-web typically requires a proxy, whereas Connect servers can handle gRPC-Web natively and browser support is strongest for server streaming rather than client streaming. Given that Stigmer’s execution view primarily consumes append-only server events, I would expose a **normalised execution-event stream** from your backend over SSE for single-run viewers and use WebSockets only where you need bi-directional control or multi-subscription dashboards. That keeps the front end simple while letting the backend remain close to Temporal’s event model. citeturn25search0turn25search4turn25search1turn25search5turn25search2turn25search11turn25search15

Architecturally, the cleanest design is to treat the graph as shared but projected differently in each surface. The editor uses interactive nodes and editable edges. The overview uses the same graph in read-only mode with collapsed detail and optional summary chips. The execution viewer uses the same graph plus a run-state overlay keyed by stable node IDs. React Flow’s interaction props make read-only scenes straightforward, and save/restore of a serialisable flow or your own graph model makes version-aligned layout reuse straightforward. This “one graph, many views” architecture is exactly what eliminates the current disconnect between design and execution. citeturn30search11turn30search2turn31search18

## Roadmap, risks, and open questions

If the goal is maximum UX impact before launch, build in this order. First, ship the **read-only execution canvas** with node overlays, clickable runtime inspector, branch dimming/highlighting, parallel-state support, and a linked trace/log drawer. This is the most visible gap and the most strategically important because it fixes the current design/run-time disconnect. Second, ship the **new node grammar** and **repaired add-flow interactions** together, because users will feel the difference immediately during authoring. Third, replace dagre with **ELK-based layout** and persist versioned layout snapshots. # Section 1: Execution Visualization — State of the Art

## 1.1 Comparative analysis

### AWS Step Functions

AWS Step Functions has one of the strongest execution visualizations for workflow state machines. Its execution detail page includes a graph view, table view, and event view. The graph view displays the workflow visually with zoom/fullscreen controls, and selecting a state shows its details. The graph and table are synchronized, so selecting a row in the table highlights the corresponding graph state. ([AWS Documentation][1])

Important execution patterns from Step Functions:

| Pattern                        | What AWS does                                                                                                                       | Why Stigmer should copy it                                                                       |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| **Graph/table/event triad**    | Execution can be inspected as graph, table, or raw event history. ([AWS Documentation][1])                                          | Stigmer needs graph for comprehension, timeline/table for performance, raw events for debugging. |
| **Step details panel**         | Step details include input, output, definition, retry attempts, duration, and resource links. ([AWS Documentation][1])              | Each Stigmer node click should reveal runtime data, not just static config.                      |
| **Failure highlighting**       | Failed executions show error/cause and link to the failing step, highlighting it in the graph/table views. ([AWS Documentation][1]) | Users should land directly on the failing node.                                                  |
| **Retries/backoff visible**    | The table timeline visualizes retries as red segments and backoff as gray segments. ([AWS Documentation][1])                        | Retries should not be hidden inside logs.                                                        |
| **Map/parallel awareness**     | Map and Parallel states have dedicated display affordances, including failed/aborted iteration filtering. ([AWS Documentation][1])  | Stigmer’s `for_each` and `fork` need special execution visualization.                            |
| **Graph export / orientation** | Graph can be exported as SVG/PNG and shown horizontally or vertically. ([AWS Documentation][1])                                     | Useful for debugging reports, docs, and support tickets.                                         |

AWS Workflow Studio also separates **Design**, **Code**, and **Config** modes; the visual canvas, state browser, inspector, and contextual help are first-class parts of the authoring experience. It also synchronizes code and visual selection, highlighting the ASL definition corresponding to a selected visual state. ([AWS Documentation][9])

### Azure Logic Apps

Azure Logic Apps has a clear separation between **designer** and **run history**. In run history, users can inspect past/current/waiting runs, see status for each step, and open individual step details for inputs, outputs, and errors. Azure documents statuses including `Running`, `Succeeded`, `Failed`, `Skipped`, `Waiting`, `Timed out`, `Cancelled`, and `Aborted`. ([Microsoft Learn][2])

A particularly strong pattern is **rerun from a specific action**. When rerunning from a step, Azure visually distinguishes operations whose inputs/outputs are reused from the action that is actually resubmitted. ([Microsoft Learn][2])

Stigmer should adopt this distinction:

```text
Original upstream nodes: completed, muted, reused
Selected rerun node: active, emphasized
Downstream nodes: pending / will rerun
```

This is especially important for expensive AI workflows where rerunning an entire agent chain may be wasteful.

### n8n

n8n’s execution history allows users to inspect previous workflow runs, filter by status, load previous executions into the editor, debug failed production runs, and rerun workflows. ([n8n Docs][3])

n8n’s strongest lesson for Stigmer is not only the canvas itself; it is the **debugging loop**:

```text
Production run fails
→ Open execution
→ Copy execution data into editor
→ Inspect node data
→ Modify workflow
→ Rerun/debug
```

For AI workflows, n8n also supports streaming responses from AI Agent nodes, allowing data to be sent while the agent is generating rather than only after completion. ([n8n Docs][10])

Stigmer should explicitly support:

```text
Open failed run → Debug in editor with pinned runtime data
Open successful run → Copy sample data into editor fixtures
Open running agent step → Stream tokens/tool calls in inspector
```

### Retool Workflows

Retool Workflows are composed of connected blocks that interact with resources, transform data, run logic, branch conditionally, and run multiple paths in parallel. The Retool IDE automatically connects blocks and displays connection lines. Retool also has versioned publishing and a run history panel showing successful/failed runs and per-block status. ([Retool Docs][11])

Retool’s useful lessons:

1. **Versioned publishing matters.** Execution should be associated with the workflow version that actually ran.
2. **Per-block run status belongs inside the workflow IDE.**
3. **Error handling is both local and global.** Retool supports local `On Error` connectors and global error handlers. ([Retool Docs][11])

For Stigmer, this implies every execution must render against a **workflow version snapshot**, not the latest editable graph.

### Temporal Cloud / Temporal Web UI

Temporal’s native UI is not primarily a visual workflow canvas. It is an execution-history and debugging UI. It exposes workflow execution tables, filters by status/type/time/search attributes, and an execution detail view with History, Workers, Relationships, Pending Activities, Queries, Metadata, Timeline, All, Compact, and JSON views. ([Temporal Docs][4])

Temporal’s most important UX lesson for Stigmer is that **durable execution is an event-sourced system**, and the UI must allow escape hatches to the underlying event history. Temporal’s event history is persisted and used for replay and crash recovery. ([Temporal Docs][12])

Stigmer should not expose Temporal history as the primary interface for normal users, but it should provide:

```text
User view:
  Graph + timeline + task inspector

Developer/debug view:
  Raw Temporal event ID
  Attempt number
  Activity/workflow IDs
  Worker/task queue
  Retry/backoff details
  Event history download
```

Temporal also emphasizes metrics, tracing, logging, and visibility as core observability dimensions. ([Temporal Docs][13])

### Apache Airflow

Airflow is mature in multi-run monitoring. Its UI includes a system health overview, DAG list with recent runs, DAG details with Overview/Grid/Graph/Runs/Tasks/Events/Code/Details tabs, grid views showing task status across runs, graph views showing logical structure and run-specific task states, and Gantt/log/task-instance details. ([Apache Airflow][5])

Airflow’s lesson: one view is not enough.

For Stigmer:

| User question                        | Best view                           |
| ------------------------------------ | ----------------------------------- |
| “Where is the current run?”          | Execution graph                     |
| “Why is it slow?”                    | Timeline / waterfall                |
| “Which node failed often this week?” | Health dashboard                    |
| “Which runs failed after deploy?”    | Execution table filtered by version |
| “What changed in the workflow?”      | Version diff                        |
| “What exactly happened internally?”  | Raw event history                   |

### Prefect

Prefect emphasizes runtime state tracking, failure handling, real-time monitoring, dynamic dependency graphs, human intervention, and UI visualization of dependency graphs/DAGs. ([Prefect][14])

Its state model is useful for Stigmer because it includes more than simple pending/running/succeeded/failed. Prefect states include `Scheduled`, `Late`, `AwaitingRetry`, `AwaitingConcurrency`, `Pending`, `Running`, `Retrying`, `Paused`, `Suspended`, `Cancelling`, `Cancelled`, `Completed`, `Cached`, `RolledBack`, `Failed`, `TimedOut`, and `Crashed`. ([Prefect][15])

Stigmer should not expose all of these as top-level UI colors, but it should support the semantic distinction between:

```text
queued
waiting for concurrency
waiting for human
running
streaming
retrying
awaiting retry
completed
cached/reused
skipped/untaken
failed
timed out
cancelled
```

Prefect Automations also support triggers, state changes, absence of expected events, custom events, notifications, and actions such as canceling, pausing, resuming, or launching flow runs. ([Prefect][16])

### Dagster

Dagster’s UI is strong for data/asset orchestration. It provides overview dashboards, asset catalogs, lineage, run filtering, timing/errors/logs, Gantt charts, structured/raw logs, and re-execution. ([Dagster Docs][17])

Dagster+ Insights tracks success rate, failure counts, time to resolution, execution time, run duration, step failures, credits, and cost metrics. ([Dagster Docs][18])

For Stigmer, Dagster’s operational lesson is that once workflows are in production, the unit of UX shifts from “one pretty graph” to:

```text
workflow fleet health
version-level regressions
node-level failure hotspots
cost trends
duration trends
time-to-resolution
```

### Inngest

Inngest is highly relevant because it models durable functions as step-based execution. Its run details show root cause, timings, local reproduction, filters by status/app/time, searchable errors, event payloads, attributes, step timelines, retries, and failed-step expansion. ([inngest.com][19])

Inngest’s trace UI uses a two-panel layout: a left waterfall timeline and a right contextual detail panel. The timeline shows step timing, queue delays, execution time, retries, I/O, and a time brush for zooming. ([inngest.com][6])

This is one of the strongest references for Stigmer’s execution view. The best execution UI is not only a graph. It is:

```text
top: run summary
center: graph / selected step
bottom: waterfall timeline
right: contextual runtime detail
```

### LangGraph Studio / LangSmith

LangGraph Studio is especially relevant for Stigmer because it targets agentic systems. It provides graph visualization, graph mode and chat mode, node traversal details, intermediate states, assistants/threads/prompts/experiments/memory, and debugging features like time travel. ([LangChain Docs][7])

LangGraph’s streaming model is directly applicable to Stigmer. It supports stream modes from full graph state snapshots after each step to token-by-token LLM output, with resumability through last-event IDs. It can stream state values, state updates, LLM tokens with metadata by graph node, debug events, custom events, and raw events. ([LangChain Docs][20])

LangSmith traces expose inputs, outputs, timing, token counts, errors, metadata, tool calls, model usage, parallel tool-call grouping, latency, and cost. ([LangChain Docs][21])

Stigmer should treat AI-agent execution as a combination of:

```text
workflow graph execution
LLM token stream
tool-call trace
state mutation stream
cost/token accounting
human-readable transcript
machine-readable event history
```

# Section 2: Visual Node Differentiation — Shapes, Icons, and Visual Grammar

## 2.1 What standards say

### BPMN

BPMN differentiates semantic categories visually:

| BPMN concept                   | Meaning                                                                              | Relevant Stigmer mapping                             |
| ------------------------------ | ------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| **Task**                       | Atomic unit of work; token waits until the job completes. ([Camunda 8 Docs][23])     | Agent call, LLM call, HTTP call, transform, validate |
| **User task**                  | Human work item. ([Camunda 8 Docs][23])                                              | Human input / approval                               |
| **Service task**               | Work performed by service/software. ([Camunda 8 Docs][23])                           | HTTP/gRPC/activity/agent/LLM                         |
| **Event**                      | Something that happens; catch events wait, throw events emit. ([Camunda 8 Docs][24]) | Listen, wait, raise error                            |
| **Exclusive gateway**          | Chooses one outgoing path based on conditions/default. ([Camunda 8 Docs][25])        | Switch case                                          |
| **Parallel gateway**           | Splits into all outgoing paths or joins all incoming paths. ([Camunda 8 Docs][26])   | Fork/join                                            |
| **Subprocess / call activity** | Encapsulated reusable flow.                                                          | Run workflow, grouped foreach/try blocks             |

BPMN’s key lesson: **branching is not just another task rectangle**. Gateways and events deserve distinct shapes.

### UML / flowchart conventions

Classic flowchart notation uses rounded terminals for start/end, rectangles for processing, diamonds for decisions, and arrows for flow. ([Wikipedia][27])

Stigmer should not become a strict BPMN editor, but it should borrow the vocabulary users already understand:

```text
rounded pill  = start/end
rectangle     = action/task
diamond       = decision
bar           = fork/join
circle/timer  = event/wait
double border = subworkflow
```

| **For Each**             | Rounded container/subprocess                                     | Loop                  | Collapsible group with iteration semantics        |
| **TryCatch**             | Shielded container or rounded rectangle with catch port          | Shield                | Normal output + error/catch output                |
| **Wait**                 | Circle or rounded timer node                                     | Clock/hourglass       | Duration/deadline chip                            |
| **Human Input**          | User-task rounded rectangle                                      | Person/hand           | Approver/channel/SLA chip                         |
| **Set Variables**        | Data card                                                        | `{}` / variable       | Key count chip                                    |
| **Transform**            | Data card                                                        | `fx` / transform      | Language chip: JS/JQ/JSONata/etc.                 |
| **Validate**             | Data card                                                        | Check/funnel/shield   | Schema chip                                       |
| **Listen**               | Event circle                                                     | Antenna/ear           | Trigger/event name chip                           |
| **Raise Error**          | Terminal/error octagon or red end pill                           | Alert/stop            | Error code chip                                   |

### Do not overdo custom geometry

A shape system can become noisy. Use three levels of differentiation:

```text
Level 1: macro shape
  task / decision / event / fork / container / terminal

Level 2: icon
  agent / llm / api / human / transform / wait / error

Level 3: chips
  model, method, branch count, approver, timeout, cost, status
```

This gives scanability without making every node a unique illustration.

### Branch port design

For `switch_case`, output handles should be semantically labeled:

```text
        ┌───────────────┐
        │ classify_user │
        │ switch_case   │
        └──────◇────────┘
             /  |   \
       enterprise free default
```

In React Flow terms:

```ts
ports = [
  { id: "case_enterprise", side: "bottom", label: "enterprise" },
  { id: "case_free", side: "bottom", label: "free" },
  { id: "default", side: "bottom", label: "default" }
];
```

For `try_catch`:

```text
normal output: solid
catch output: dashed/error-styled
finally output: optional
```

For `fork`:

```text
parallel outputs:
  branch_1, branch_2, branch_3
join:
  visual join bar or implicit merge node
```

## 2.4 Accessibility

Current “thin colored left stripe” differentiation is insufficient. WCAG guidance explicitly says color should not be the only means of conveying information, and meaningful UI indicators need adequate contrast. ([W3C][22])

Implementation requirements:

```text
- shape + icon + text, not color alone
- status badges with text labels
- 3:1 contrast for non-text state indicators
- visible focus rings
- keyboard selection and traversal
- ARIA labels: "Switch Case node classify_user, 3 branches"
- reduced-motion support for execution animations
- high-contrast theme test
- color-blind palette test
```

## 2.5 Implementation in `@xyflow/react`

React Flow supports custom nodes as React components, and custom nodes can render arbitrary content with multiple source/target handles. ([React Flow][31]) It also supports custom edges as React components, with built-in path helpers and fully custom SVG paths. ([React Flow][32])

Recommended approach:

```ts
interface TaskTypeVisualSpec {
  kind: WorkflowTaskKind;
  category: "ai" | "control" | "invocation" | "data" | "governance" | "event";

  shape:
    | "task-card"
    | "decision-diamond"
    | "parallel-bar"
    | "event-circle"
    | "terminal-pill"
    | "subworkflow-card"
    | "container";

  icon: React.ComponentType;
  defaultSize: { width: number; height: number };

  ports: (task: WorkflowTask) => PortSpec[];
  layoutHints?: LayoutHints;

  renderBody: React.ComponentType<TaskNodeRenderProps>;
  renderInspector: React.ComponentType<TaskInspectorProps>;
  renderExecutionOverlay: React.ComponentType<TaskExecutionOverlayProps>;
}
```

Example node rendering strategy:

```tsx
function WorkflowNode({ data, selected }: NodeProps<WorkflowNodeData>) {
  const spec = taskTypeRegistry[data.task.kind];

  return (
    <NodeShell
      shape={spec.shape}
      selected={selected}
      status={data.execution?.status}
      validation={data.validation}
      ariaLabel={buildNodeAriaLabel(data)}
    >
      <NodeHeader
        icon={spec.icon}
        name={data.task.name}
        kind={data.task.kind}
        chips={buildTaskChips(data.task)}
      />

      <spec.renderBody task={data.task} />

      {data.execution && (
        <spec.renderExecutionOverlay execution={data.execution} />
      )}

      {spec.ports(data.task).map((port) => (
        <Handle
          key={port.id}
          id={port.id}
          type={port.direction === "in" ? "target" : "source"}
          position={toReactFlowPosition(port.side)}
          aria-label={port.label}
        />
      ))}
    </NodeShell>
  );
}
```

For diamonds and bars, prefer SVG/HTML hybrid:

```text
- outer SVG shape for visual geometry
- transparent rectangular hitbox for selection
- handles positioned on fixed sides
- label area centered
- branch labels rendered outside shape if needed
```

# Section 3: Auto-Layout — Achieving Design-Quality Layout

## 3.1 Why current dagre layout is not enough

Dagre-style layered layout is fine for simple DAGs, but Stigmer workflows contain semantics that generic DAG layout does not understand:

```text
- switch branches with labels and default paths
- fork/join parallelism
- foreach/map iteration containers
- try/catch error paths
- human wait gates
- long-running AI nodes with expanded runtime overlays
- manual user positioning
- old execution graph snapshots
```

A layout algorithm that sees only anonymous rectangles and edges will produce technically valid but visually poor diagrams.

## 3.2 Layout library comparison

| Option                   | Strengths                                                                                                                                                                                | Weaknesses                                                                       | Recommendation                                               |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| **dagre**                | Simple, common, easy with React Flow                                                                                                                                                     | Limited control over ports, compound nodes, advanced routing, workflow semantics | Keep only as fallback for tiny graphs                        |
| **ELK / elkjs**          | Professional layout engine; supports layered layout, ports, hierarchical/compound nodes, labels, orthogonal routing, port constraints, crossing minimization. ([Eclipse Foundation][33]) | More complex config; needs measurement; best run in worker                       | **Primary recommendation**                                   |
| **d3-dag**               | Lightweight TypeScript DAG layout, React Flow compatible, multiple layout algorithms, quality/speed presets. ([Erik Brinkman][34])                                                       | Less complete for compound workflow diagrams than ELK                            | Good secondary option for simple browser-only layout         |
| **Cytoscape.js layouts** | Strong graph/network visualization, layouts, algorithms, extensibility. ([Cytoscape.js][35])                                                                                             | More network-analysis oriented; less React-component-native                      | Not primary for Stigmer editor                               |
| **GoJS**                 | Rich diagramming framework with automatic layouts, templates, undo/redo, subgraphs, context menus, many samples. ([GoJS][36])                                                            | Commercial/licensing and migration cost                                          | Consider only if leaving React Flow                          |
| **JointJS**              | SVG diagramming, workflow/BPMN demos, high customizability. ([JointJS][37])                                                                                                              | Advanced product features often commercial; migration cost                       | Consider for enterprise diagram editor rewrite               |
| **Rete.js**              | Visual programming framework, TypeScript-first, processing-oriented node editors, plugins, codegen. ([Rete.js][38])                                                                      | More node-programming-engine oriented than orchestration monitoring              | Consider only if editor becomes dataflow-programming-centric |

## 3.3 Recommended: ELK layered layout with workflow-aware preprocessing

React Flow has official examples showing how to integrate `elkjs` with React Flow and use options such as layered algorithm, spacing, and vertical/horizontal direction. ([React Flow][39])

Recommended ELK baseline:

```ts
const elkOptions = {
  "elk.algorithm": "layered",
  "elk.direction": "DOWN",
  "elk.edgeRouting": "ORTHOGONAL",

  "elk.spacing.nodeNode": "56",
  "elk.layered.spacing.nodeNodeBetweenLayers": "96",

  "elk.layered.crossingMinimization.strategy": "LAYER_SWEEP",
  "elk.layered.nodePlacement.strategy": "NETWORK_SIMPLEX",

  "elk.portConstraints": "FIXED_SIDE"
};
```

Exact option names should be validated against the chosen `elkjs` version, but the conceptual direction is clear:

```text
layered
top-to-bottom
orthogonal edges
fixed-side ports
larger branch spacing
compound containers for foreach/try/subworkflow
```

## 3.4 Workflow-aware layout pipeline

Do not send raw nodes directly to ELK. Build a semantic layout model first.

```text
WorkflowSemanticModel
  → identify structures:
      linear chains
      switch groups
      fork/join groups
      foreach containers
      try/catch regions
      subworkflow call nodes
  → assign ports:
      input top
      normal output bottom
      branch outputs ordered left-to-right
      catch/error output right
  → add layout hints:
      branch spacing
      container padding
      fixed port side
      manual pins
  → run ELK
  → map ELK coordinates to React Flow positions
  → animate viewport/position changes
```

### Switch layout

```text
              switch
        ┌───────┼────────┐
      case A  case B   default
        │       │        │
        └───────┴────────┘
              merge
```

Rules:

```text
- preserve case order from YAML
- default branch always rightmost or visually marked
- edge labels must not overlap
- untaken branches in execution dim without collapsing
```

### Fork layout

```text
              fork
     ┌─────────┼─────────┐
   branch 1  branch 2  branch 3
     └─────────┼─────────┘
              join
```

Rules:

```text
- fork and join horizontally centered
- branches get equal lane spacing
- long branch does not drag all branches into disorder
- join status can show N/M completed
```

### Try/catch layout

```text
        risky task
          │
      normal path
          │
        next step

catch path drawn to the right, dashed/error-styled:
        risky task ───catch──▶ handler
```

Rules:

```text
- error edges route to the right or side lane
- catch path should never be confused with normal path
- retries shown in runtime overlay/timeline, not as extra design edges
```

## 3.5 Incremental layout

Full re-layout after every edit causes user disorientation. Implement three layout scopes:

```text
Auto-layout all
Auto-layout selected
Tidy branch / tidy downstream
```

Command pattern integration:

```ts
interface GraphCommand {
  apply(model: WorkflowGraphModel): WorkflowGraphModel;
  affectedNodeIds?: string[];
  layoutPolicy?: "none" | "affected-subgraph" | "downstream" | "whole-graph";
}
```

Examples:

```text
InsertNodeOnEdgeCommand:
  layout affected edge neighborhood

AddSwitchCaseCommand:
  layout switch group and downstream merge region

AddParallelBranchCommand:
  layout fork group

MoveNodeCommand:
  layout none; mark node as manually pinned

DeleteNodeCommand:
  if reconnecting, layout affected predecessor/successor neighborhood
```

Store layout metadata separately:

```yaml
x-stigmer-ui:
  layout:
    orientation: vertical
    nodes:
      run_analyst:
        x: 240
        y: 360
        pinned: true
      approve_report:
        x: 240
        y: 520
```

## 3.6 Layout quality gates

Add automated layout tests using representative workflow fixtures:

```text
- linear 10-node workflow
- switch with 5 branches
- fork with 4 branches and uneven branch lengths
- foreach with inner switch
- try/catch with retry and error handler
- 50-node mixed workflow
```

Check:

```text
- no node overlap
- no label overlap above threshold
- edge crossings below threshold
- branch order stable
- start-to-end flow mostly monotonic
- port side correctness
- layout deterministic for same graph
- manual pins preserved
```

Use screenshot regression tests for visual quality.

# Section 7: Technology Recommendations

## 7.1 Keep `@xyflow/react`, but rewrite the graph architecture

React Flow already supports the capabilities Stigmer needs: custom nodes, arbitrary React-rendered node bodies, multiple handles, custom edges, and integration with layout libraries like ELK. ([React Flow][31])

For 10–50+ tasks, React Flow is a reasonable foundation. The issue is not the renderer; it is the current graph semantics, node visual system, layout pipeline, and execution projection.

### Recommended decision

```text
Keep:
  @xyflow/react v12
  React/Next.js
  Tailwind + --stgm-* tokens
  command/history pattern
  YAML DSL
  Temporal runtime

Rewrite:
  node renderer
  edge renderer
  task visual registry
  execution viewer
  overview diagram
  plus-button insertion UX
  layout pipeline
  inspector architecture
```

## 7.2 When to consider alternatives

| Library                 | Consider if                                                                                                                             | Not ideal because                                                              |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| **GoJS**                | You want a full commercial diagramming stack with built-in layouts, templates, undo/redo, subgraphs, samples, and support. ([GoJS][36]) | Licensing/migration cost; less aligned with existing React Flow investment     |
| **JointJS**             | You want a specialized SVG diagramming toolkit with workflow/BPMN-style demos and commercial support options. ([JointJS][37])           | Migration cost; advanced features may require commercial product               |
| **Cytoscape.js**        | You need large graph/network analysis, graph algorithms, and many layout extensions. ([Cytoscape.js][35])                               | Less natural for form-heavy React workflow editors                             |
| **Rete.js**             | You want a visual programming engine with codegen and node-processing semantics. ([Rete.js][38])                                        | Stigmer is orchestration/operations-heavy, not just local dataflow programming |
| **Custom Canvas/WebGL** | You need thousands of nodes or fully custom rendering performance                                                                       | Overkill; weak accessibility and form integration risks                        |

## 7.3 Shared graph model architecture

Recommended architecture:

```text
YAML DSL
  ↓ parse
Workflow AST
  ↓ normalize
WorkflowSemanticModel
  - tasks
  - control-flow semantics
  - ports
  - branches
  - validation
  - version metadata

  ↓ project
GraphViewModel
  - React Flow nodes
  - React Flow edges
  - layout metadata
  - visual specs
  - viewport hints

  ↑ commands
GraphCommand history

Execution events
  ↓ normalize
ExecutionProjection
  - node runtime states
  - edge runtime states
  - attempts
  - streaming chunks
  - costs
  - branch decisions
  - iteration states
```

### Renderer modes

Use one renderer with mode-specific capabilities:

```ts
type WorkflowGraphMode = "design" | "overview" | "execution";

interface WorkflowGraphProps {
  mode: WorkflowGraphMode;
  graph: GraphViewModel;
  execution?: ExecutionProjection;
  editable?: boolean;
  onCommand?: (command: GraphCommand) => void;
  onSelectNode?: (nodeId: string) => void;
}
```

| Mode          | Behavior                                                           |
| ------------- | ------------------------------------------------------------------ |
| **Design**    | draggable, connectable, editable, plus buttons, inspector config   |
| **Overview**  | pannable/zoomable, task summary popovers, recent health badges     |
| **Execution** | read-only, status overlays, branch highlighting, runtime inspector |

## 7.4 State management

Keep the command/history pattern for structural mutations. Add a clear separation between durable graph state and ephemeral UI state.

```text
Durable:
  YAML
  semantic graph
  layout metadata
  workflow version

Undoable:
  graph commands
  config edits
  layout changes

Ephemeral:
  selection
  viewport
  open panels
  task picker state
  hover state
  temporary connection
  execution follow mode
```

A practical setup:

```text
Zustand or Jotai:
  editor view state
  selection
  viewport
  panels
  task picker

Command history:
  graph mutations
  YAML patches
  undo/redo

React Query / TanStack Query:
  workflow data
  execution snapshots
  execution history
  templates

Streaming store:
  append-only run events
  coalesced execution projection
```

CRDT collaboration can wait. The command log is a good foundation, but collaborative editing is not the first UX bottleneck.

## 7.5 Real-time execution updates

Because Stigmer receives execution events via Temporal/gRPC streaming, the browser-facing protocol should be designed for resiliency.

Recommended:

```text
Server:
  Temporal/gRPC stream
    → normalize events
    → persist append-only execution event log
    → maintain projection snapshot

Browser:
  GET projection snapshot
  subscribe to events after seq
```

Transport:

| Transport     | Use                                                                                          |
| ------------- | -------------------------------------------------------------------------------------------- |
| **SSE**       | Best default for one-way execution updates; simple reconnect and `Last-Event-ID`             |
| **WebSocket** | Use if you need bidirectional controls, collaborative cursors, or rich interactive debugging |
| **gRPC-web**  | Use only if your stack already supports it cleanly                                           |
| **Polling**   | Fallback for self-hosted environments with restrictive infra                                 |

LangGraph’s resumable streaming with last-event ID is a strong reference for long-running AI graph execution. ([LangChain Docs][20])

## 7.6 Layout engine

Use `elkjs` in a Web Worker.

```text
main thread:
  measure nodes
  send graph + layout hints to worker

worker:
  run ELK
  return positions and bend points

main thread:
  apply positions
  animate if appropriate
```

React Flow’s ELK example shows the core mapping: build an ELK graph with child dimensions, run layout, then map ELK `x/y` back to React Flow node positions. ([React Flow][39])

## 7.7 Task type registry

Centralize all type-specific behavior:

```ts
interface TaskTypeDefinition<TConfig = unknown> {
  kind: string;
  category: string;
  label: string;
  description: string;

  visual: TaskTypeVisualSpec;
  ports: (config: TConfig) => PortSpec[];
  defaultConfig: () => TConfig;

  inspector: React.ComponentType<InspectorProps<TConfig>>;
  validate: (config: TConfig) => ValidationIssue[];
  toYaml: (task: Task<TConfig>) => YamlNode;
  fromYaml: (node: YamlNode) => Task<TConfig>;

  execution?: {
    summarize: (events: WorkflowExecutionEvent[]) => NodeExecutionSummary;
    renderOverlay: React.ComponentType<ExecutionOverlayProps>;
  };

  layoutHints?: LayoutHints;
}
```

This prevents scattered logic like “switch cases have special handles” living in random canvas components.

# Section 9: Risk Assessment

## 9.1 Biggest UX risks

### Risk 1: Execution graph becomes decorative

If the graph only shows status but real debugging still requires logs, users will not trust it.

Mitigation:

```text
- graph, timeline, and inspector must be synchronized
- every node click exposes input/output/error/duration/cost
- failure opens the failed node automatically
- raw logs remain available but secondary
```

### Risk 2: Rendering old runs on the latest graph

This creates misleading execution views when workflows change after a run.

Mitigation:

```text
- persist workflow version snapshot with every run
- execution view defaults to executed version
- show banner if viewing against latest draft:
  "This run used version 12. You are viewing draft version 14."
```

### Risk 3: Color-only status semantics

Color-only state indicators fail accessibility and reduce scanability.

Mitigation:

```text
- shape, icon, text, and contrast
- status badges
- reduced-motion mode
- color-blind checks
```

WCAG explicitly warns against relying only on color and requires sufficient contrast for meaningful non-text indicators. ([W3C][22])

### Risk 4: Streaming output overwhelms the graph

Long agent output inside nodes will destroy readability.

Mitigation:

```text
- node shows only status and 1-line preview
- inspector owns full transcript
- timeline owns events/tool calls
- chunk/coalesce token streams
- virtualize long transcripts
```

### Risk 5: Auto-layout causes disorientation

Full re-layout after every edit makes users feel the canvas is unstable.

Mitigation:

```text
- preserve manual positions
- layout only affected subgraph when possible
- animate moderately
- provide "Auto-layout selected" and "Tidy branch"
- never re-layout while user is dragging
```

### Risk 6: Branch semantics remain opaque

Users must understand not only that a branch exists, but why a path was taken.

Mitigation:

```text
- edge labels for cases
- decision inspector shows evaluated expression
- taken/untaken branch states
- default branch visibly marked
- test condition tool in editor
```

### Risk 7: YAML and visual editor diverge

This is a common failure mode for dual code/visual tools.

Mitigation:

```text
- one semantic model
- visual commands produce YAML patches
- YAML parses into graph model
- unsupported YAML rendered as advanced/code-owned blocks
- round-trip tests
```

### Risk 8: Retry visualization lies

Duplicating nodes for attempts can make the workflow look structurally different from what was designed.

Mitigation:

```text
- keep graph structural
- show attempts in timeline/inspector
- optional "expand attempts" mode
```

### Risk 9: Prototype only works for happy-path demos

Workflow UX often looks good with 6 nodes and fails at 40.

Mitigation: test with fixtures before committing:

```text
1. 12-node linear workflow
2. switch with 6 branches
3. fork/join with uneven branch lengths
4. foreach with 100 iterations
5. try/catch with retries
6. long-running streaming agent with tool calls
7. 50-node mixed production-like graph
```

### Risk 10: Sensitive execution data leaks

Workflow runs may include secrets, prompts, user data, API responses, or internal documents.

Mitigation:

```text
- artifact references instead of inline payloads
- redaction policies
- role-based payload access
- audit log for viewing sensitive inputs/outputs
- environment-level retention policy
```

## 9.2 What to prototype before full implementation

Prototype these in order:

### Prototype A: Execution graph overlay

Goal:

```text
Can users answer "where is the run and what happened?"
```

Test tasks:

```text
- identify current running node
- identify failed node
- explain which switch branch ran
- inspect node output
- find retry attempts
```

### Prototype B: Streaming agent execution

Goal:

```text
Can users monitor a 20-minute agent call without losing context?
```

Test tasks:

```text
- see live progress
- inspect tool calls
- find partial output
- cancel safely
- understand cost so far
```

### Prototype C: Branch creation

Goal:

```text
Can users add a switch case or parallel branch without reading docs?
```

Test tasks:

```text
- add approval branch
- add default branch handling
- add parallel enrichment path
- reconnect branch to downstream node
```

### Prototype D: ELK layout quality

Goal:

```text
Does auto-layout produce diagrams users would accept as designed, not merely valid?
```

Test:

```text
- 10, 25, 50-node graphs
- branches
- forks
- try/catch
- foreach
- manual pin preservation
```

### Prototype E: YAML/visual round-trip

Goal:

```text
Can power users trust both modes?
```

Test:

```text
- edit YAML, see graph update
- edit graph, see YAML patch
- unsupported YAML does not disappear
- validation maps to graph nodes and YAML lines
```

# Final recommendation

Stigmer’s best path is:

```text
Do not replace React Flow yet.
Do replace the workflow UX model.
```

The winning architecture is:

```text
one semantic workflow model
one task visual registry
one graph renderer with design/overview/execution modes
ELK layout
Temporal event projection
graph + timeline + inspector execution cockpit
contextual command-based editing
```

The first launch-quality milestone should be:

```text
1. Execution graph with live node states
2. Runtime inspector with input/output/error/stream
3. Branch/parallel highlighting
4. Shape/icon node vocabulary
5. Contextual task insertion picker
6. ELK layout for complex flows
```

That combination would move Stigmer from “workflow editor plus log viewer” to a cohesive orchestration product that can credibly compete with n8n, Retool Workflows, AWS Step Functions, and AI-native agent workflow tools.
