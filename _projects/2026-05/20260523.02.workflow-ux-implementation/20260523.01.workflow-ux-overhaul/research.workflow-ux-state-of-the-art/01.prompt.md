# Deep Research: State-of-the-Art Workflow UX — Execution Visualization, Visual Editor Node Differentiation, and End-to-End Workflow Experience

## Research Objective

We are building **Stigmer** (https://stigmer.ai) — an open-source AI agent platform with a **workflow orchestration engine**. The workflow system allows users to compose multi-step AI agent workflows involving agent calls, LLM calls, conditional branching, parallel execution, human approval gates, HTTP/gRPC calls, data transformations, and more.

We have a working implementation of the **workflow visual editor**, **workflow overview page**, and **workflow execution viewer**, but the UX across all three has significant gaps. We are willing to **completely rewrite** the UI if necessary — no customers are using workflows in production yet, so this is our chance to build a **state-of-the-art solution** before launch.

We need comprehensive research on **how leading workflow, orchestration, and visual programming platforms handle these UX challenges**, so we can redesign our workflow experience to be best-in-class.

## What Is Stigmer?

Stigmer is an **open-source AI agent platform**. Users define AI agents declaratively (model, tools/MCP servers, system prompt, knowledge) and deploy them with a single command. The platform handles execution, scaling, context management, and tool orchestration.

**Workflows** are a core feature: users define multi-step orchestration pipelines where each step is a "task" — an agent call, an LLM call, a data transformation, an HTTP request, a conditional branch, a human approval gate, etc. Workflows are defined in a YAML DSL (influenced by CNCF Serverless Workflow spec) and execute as durable Temporal workflows.

The web UI has four tabs for each workflow:
- **Overview**: Description, budget, environment variables, and a mini task-flow diagram
- **Instances**: Deployed instances of the workflow
- **Executions**: List of past and running executions
- **Editor**: Code (YAML) and Visual (canvas) editing modes

## Our Current Implementation — Technology Stack

- **React** (Next.js app) with **Tailwind CSS** + custom CSS variables (`--stgm-*` design tokens)
- **@xyflow/react v12** (formerly React Flow) — the core canvas rendering library
- **@dagrejs/dagre** — for automatic graph layout (top-to-bottom DAG)
- **@stigmer/react SDK** — internal React component library containing the canvas editor

### Architecture Overview

The workflow UI has these layers:

1. **`WorkflowEditorView`** — Top-level component that toggles between "Code" (YAML) and "Visual" (canvas) editing modes. Provides toolbar with validation summary, save, undo/redo, auto-layout, and a "Refine with AI" panel.

2. **`WorkflowCanvasEditor`** (Visual mode):
   - **`WorkflowTaskPalette`** (left sidebar) — categorized, searchable list of available task types that users drag onto the canvas
   - **`WorkflowCanvasInner`** (center) — the actual `<ReactFlow>` canvas component
   - **`WorkflowInspectorPanel`** (right sidebar) — property editor for the selected node/edge

3. **`useWorkflowCanvas`** hook — orchestrates the graph model through a **command/history pattern** (undo/redo). All structural mutations go through `GraphCommand` objects dispatched to history.

4. **`WorkflowGraphModel`** — source-of-truth data model with `nodes` (task name, kind, category, config, position) and `edges` (source, target, optional source handle for branching). Sentinel nodes `__start__` and `__end__` represent workflow entry/exit points.

### Current Task Type Categories and Types

The visual editor palette organizes tasks into categories:

| Category | Task Types |
|----------|-----------|
| **AI** | Agent Call, LLM Call, Evaluate (LLM Judge) |
| **CONTROL FLOW** | Switch Case, For Each, Fork, TryCatch, Wait |
| **INVOCATION** | HTTP Call, gRPC Call, Activity Call, Run Workflow |
| **DATA** | Set Variables, Transform, Validate |
| **GOVERNANCE** | Human Input |
| **EVENT** | Listen, Raise Error |

### Current Node Rendering

**All task nodes look essentially identical** — they are rectangular cards with:
- A category-colored left border stripe
- Task name (text)
- Kind badge (e.g., "agent call", "switch case")
- Connection handles (top = input, bottom = output)
- Multi-port outputs for `switch_case` and `human_input` tasks

There is **no visual differentiation by shape** — a Switch Case node looks the same as an Agent Call node, which looks the same as a Fork node. The only difference is the color of the left border stripe (by category) and the text label.

### Current Auto-Layout

Uses `@dagrejs/dagre` for top-to-bottom automatic layout. **The auto-layout frequently produces suboptimal results** — nodes overlap, are not properly spaced, or the graph doesn't look "clean." The layout quality degrades as workflow complexity increases.

## Problem Areas We Need Researched

### Problem 1: Workflow Execution Visualization (CRITICAL)

**Current state**: When a workflow execution is running, we show a **log-based event stream**:
- A header: "Execution started - 11 tasks"
- Sequential log entries: "run_analyst — agent_call" with timestamps
- "Streaming events..." indicator
- A side panel showing "TASKS" with the task name and type, and a counter (0/11)

**What's wrong**: This is basically a log viewer. It does not leverage the workflow's visual structure at all. Users defined their workflow as a visual flow diagram, but when it runs, they see a flat list of timestamped events. This is a **major disconnect** between the design experience and the execution experience.

**What we think it should be**: The execution view should show the **same flow diagram** that the user designed, but with **live task status overlays**:
- Each node in the flow should show its execution status (pending, running, completed, failed, skipped)
- The "current execution point" should be visually highlighted (e.g., a glowing border, animation, or progress indicator on the actively running task)
- Completed tasks should show success/failure state (green checkmark, red X)
- Clicking a task node in the execution view should show its output, duration, cost, and error details
- The flow should animate or transition as execution progresses
- For parallel tasks (Fork), multiple branches should show running simultaneously
- For conditional tasks (Switch Case), the taken branch should be highlighted while untaken branches are dimmed

**Research needed**:
1. How do state-of-the-art workflow execution tools visualize running workflows?
2. How does **AWS Step Functions** console show execution progress on a state machine diagram?
3. How does **Temporal Cloud UI** show workflow execution with its visual graph?
4. How does **n8n** show execution progress in its canvas view?
5. How does **Prefect** / **Dagster** show DAG execution with real-time task status?
6. How does **Apache Airflow** show DAG run progress visually?
7. How does **Inngest** show function execution steps?
8. How does **Retool Workflows** show execution results on its canvas?
9. How do **LangGraph Studio** and **LangSmith** visualize agent execution graphs?
10. How does **Azure Logic Apps** designer show run history on the visual canvas?
11. What are the best practices for **real-time execution visualization** on flow diagrams?
12. How should we handle **streaming agent output** within the execution visualization? (Agent calls can produce streaming text output that takes minutes)
13. What animation/transition patterns work best for showing execution progression?
14. How should error states and retries be visualized on the flow diagram?

### Problem 2: Task Flow Overview Diagram (HIGH)

**Current state**: The workflow Overview page shows a small, static "TASK FLOW" diagram at the bottom. It's a miniaturized version of the visual flow with tiny, barely readable node labels. It has zoom controls (+/-) and an "Expand" button. It feels like a thumbnail preview rather than a usable visualization.

**What's wrong**:
- The diagram is too small to be useful without expanding
- Node labels are barely readable
- It's not interactive — you can't click on a task to see its details
- The visual representation uses the same generic rectangular cards as the editor (no shape differentiation)
- Scrolling and panning are limited

**What we think it should be**: The overview should have a richer, more interactive task flow visualization:
- Either a properly sized, pannable/zoomable flow diagram, or a different representation (timeline, swimlane, tree)
- Clicking a task should show a summary popover with key configuration
- Clear visual distinction between task types using shapes/icons
- Status badges if any recent execution data is available

**Research needed**:
1. How do workflow tools present workflow overviews/summaries?
2. What alternative visualizations work better than a minimap for showing workflow structure? (Timeline view, swimlane diagram, collapsible tree, etc.)
3. How much interactivity should an overview diagram have vs. the full editor?

### Problem 3: Visual Node Differentiation by Shape (HIGH)

**Current state**: Every task type renders as the **same rectangular card shape**. The only visual differentiation is:
- A thin colored left border (by category — AI, Control Flow, Invocation, etc.)
- A text badge with the kind name (e.g., "agent call", "switch case")

**What's wrong**: Users cannot quickly scan the workflow and understand its structure at a glance. A Switch Case (conditional branching) should look visually different from an Agent Call (AI invocation), which should look different from a Fork (parallel execution). The visual grammar of the flow diagram is flat — it's just a chain of identical-looking boxes.

**What we think it should be**: Different task types should have **distinct visual shapes and iconography**, following conventions from flowchart standards (BPMN, UML Activity Diagrams) and modern visual programming:
- **Agent Call / LLM Call**: Standard rectangle or rounded rectangle with an AI/brain icon
- **Switch Case**: Diamond shape (traditional decision/branch symbol) or a hexagon
- **Fork / Parallel**: A wide "split" bar or a node with multiple parallel output arrows, possibly using a different shape
- **For Each**: A loop icon or a rounded shape with a cycle indicator
- **Human Input / Approval**: A person icon shape, or a distinctly colored gate/shield shape
- **HTTP Call / gRPC Call**: An API icon, or a different rectangle with a communication symbol
- **Start / End**: Rounded pills (already implemented as sentinels)
- **Try/Catch**: A shield or safety icon
- **Wait**: An hourglass or clock icon
- **Listen**: An ear/antenna icon
- **Set Variables / Transform**: A data/gear icon

**Research needed**:
1. How do **BPMN** (Business Process Model and Notation) diagrams differentiate node types? What shapes map to what semantics?
2. How do **UML Activity Diagrams** represent decisions, forks/joins, actions, and swim lanes?
3. How does **n8n** visually differentiate trigger nodes, action nodes, conditional nodes, and loop nodes?
4. How does **Zapier Canvas** differentiate step types visually?
5. How does **ComfyUI** differentiate node types (it's a node-based AI tool)?
6. How do **Unreal Engine Blueprints** differentiate event nodes, function nodes, variable nodes, flow control nodes?
7. How does **Unity Visual Scripting** (Bolt) differentiate node types?
8. How does **Node-RED** differentiate node types visually?
9. How does **Apache NiFi** differentiate processors, controllers, and funnels?
10. How does **Retool Workflows** differentiate block types?
11. How does **AWS Step Functions Workflow Studio** differentiate state types (Task, Choice, Parallel, Wait, etc.)?
12. What are the **accessibility implications** of using shapes vs. colors alone for differentiation?
13. How do you implement custom node shapes in **@xyflow/react v12**? What are the technical approaches (SVG shapes, CSS clip-path, custom HTML, Canvas rendering)?
14. What **iconography** works best for representing AI/ML operations, conditional logic, parallel execution, human approval, data transformation, and external service calls?

### Problem 4: Auto-Layout Quality (MEDIUM)

**Current state**: Auto-layout uses `@dagrejs/dagre` for top-to-bottom DAG layout. Results are often messy — nodes overlap, spacing is inconsistent, and the graph doesn't look visually polished after auto-layout.

**What's wrong**: Dagre is a basic graph layout algorithm. It doesn't handle complex workflow patterns (multiple branches, parallel paths, loops) elegantly. The layout looks "algorithmic" rather than "designed."

**Research needed**:
1. What are the best graph layout libraries/algorithms for workflow DAGs in 2025-2026?
2. How does **ELK (Eclipse Layout Kernel)** compare to dagre for workflow layouts? (ELK is used by many professional tools)
3. How does **d3-dag** compare for DAG-specific layouts?
4. How do **AWS Step Functions Workflow Studio** and **Azure Logic Apps** achieve clean layouts for their visual workflows?
5. What layout algorithms work best for workflows with conditional branches, parallel forks, loops, and error-handling paths?
6. How do you achieve "design-quality" auto-layout (consistent spacing, alignment, minimal edge crossings, aesthetic proportions)?
7. How does **@xyflow/react** integrate with ELK for auto-layout? Are there official examples or community packages?
8. What about **incremental/partial layout** — re-laying out only the affected portion when a node is added/removed, rather than re-laying out the entire graph?

### Problem 5: Visual Editor — Adding Tasks / Plus Buttons Not Working (MEDIUM)

**Current state**: The visual editor has plus buttons (+) that appear on edges and nodes, but clicking them **does not work reliably** or does not produce the expected result:
- The edge "+" button inserts a hardcoded `agent_call` node — there's no type picker
- Some "+" buttons appear non-functional (clicking them does nothing)
- Adding branches to a Switch Case or Fork via the visual editor is not intuitive
- The overall "add task" experience in the visual editor is broken/incomplete

**What's wrong**: Users clicking "+" expect to choose what to add. The experience is broken for key workflows like "add a new branch to this Switch Case" or "add a parallel path to this Fork."

**Research needed**:
1. How do other visual editors handle "add branch" for conditional (switch/case) nodes?
2. How do other editors handle "add parallel path" for fork/join patterns?
3. What task picker UX patterns work best when inserting between existing nodes?
4. Should the "+" trigger a popover, a dropdown, a command palette, or a mini-sidebar?
5. How should we handle "add task at the end" vs "insert task between" vs "add branch"?

### Problem 6: Right Panel / Inspector Panel UX (LOW-MEDIUM)

**Current state**: The right panel shows a property editor for the selected node. It also has task type options that appear to be for adding tasks, but the interaction is not clear.

**What's wrong**: The panel may be trying to serve too many purposes (node configuration, node actions, and task type selection). The UX for configuring a selected task and for adding new tasks should be clearly separated.

**Research needed**:
1. How do production visual editors design their inspector/properties panels?
2. How do they separate "node configuration" from "node actions" (delete, duplicate, etc.)?
3. What are the best patterns for a form-based task configuration panel alongside a visual canvas?
4. How should different task types present their configuration options? (e.g., an Agent Call needs model selection and message template; a Switch Case needs condition expressions; an HTTP Call needs URL, method, headers, body)

## Cross-Cutting Research Areas

### Area A: Workflow Creation Experience

Beyond the visual editor, research the overall **workflow creation** UX:
1. How do modern platforms balance **code-first (YAML/DSL)** vs. **visual-first** workflow creation?
2. What is the state-of-the-art for **AI-assisted workflow creation** ("describe what you want, AI builds the workflow")?
3. How do platforms handle **workflow templates/marketplace** for starting points?
4. How does the **onboarding experience** work for first-time workflow creators in platforms like n8n, Retool, Zapier, and Make?

Beyond individual execution views:
1. How do platforms show **workflow health dashboards** (success rate, average duration, cost, error trends)?
2. How do **Temporal Cloud**, **Prefect Cloud**, and **Dagster Cloud** show workflow monitoring at scale?
3. What alerting and notification patterns are standard for workflow failures?
4. How should workflow execution history be browsable, filterable, and searchable?

### Area C: Technology Recommendations for a Rewrite

Since we are open to a complete rewrite:
1. Should we stick with **@xyflow/react v12** or consider alternatives? (e.g., JointJS, GoJS, Cytoscape.js, vis-network, Rete.js, custom Canvas/SVG)
2. If staying with @xyflow/react, what is the best architecture for combining a **read-only execution view** and an **editable design view** from the same underlying graph model?
3. What state management patterns work best for complex visual editors? (Zustand, Jotai, custom command/history, CRDT-based?)
4. How should we handle **real-time execution updates** in the execution view? (WebSocket, SSE, polling, gRPC streaming?)
5. What graph rendering libraries provide the best **custom shape support** for workflow DAGs?

## Context Constraints

- We use **@xyflow/react v12** currently but are open to alternatives if the research recommends it
- We use a **command/history pattern** for undo/redo — all mutations go through `GraphCommand` objects
- We use **Temporal** for durable workflow execution — execution events come via gRPC streaming
- We use **CSS variables** (`--stgm-*`) and Tailwind CSS for theming
- The workflow DSL is YAML-based, influenced by CNCF Serverless Workflow spec
- We support **10-50+ tasks** in a single workflow
- Agent calls can take **minutes to hours** and produce **streaming text output**
- The editor runs in both **self-hosted (open-source)** and **cloud** environments
- We have no legacy UX to preserve — we can redesign from scratch
- Our goal is to build a **state-of-the-art** workflow UX that can compete with or exceed n8n, Retool Workflows, and AWS Step Functions
