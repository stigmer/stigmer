# Deep Research: State-of-the-Art UX for AI Agent Platform Resource Management Screens

## Research Objective

We are building **Stigmer** — an AI agent orchestration platform (platform-for-platforms) where teams build, manage, and run AI agents. The web console at `app.stigmer.ai` and an embeddable React SDK (`@stigmer/react`) are the primary interaction surfaces.

We need a comprehensive UX research report on how to design **world-class resource management screens** — the views where users browse, inspect, configure, edit, and delete platform resources like Agents, Skills, MCP Servers, Runners, and Settings entities. Our current screens are functional but basic compared to state-of-the-art developer platforms. A customer of ours built a richer experience (file-explorer-style skill browser, visual MCP server configuration) using our SDK than what we ourselves provide in our own console.

The research should cover **UX philosophy, interaction patterns, visual design systems, and concrete screen-by-screen recommendations** for every resource management surface in the platform.

---

## Our Platform and Architecture

### What Stigmer Does

Stigmer is a **managed AI agent execution platform**. Platform builders (our customers) use Stigmer to:

1. **Define Agents** — AI agents with system instructions, model configuration, MCP server integrations, skills (knowledge packages), sub-agents, and environment variables
2. **Attach Skills** — Markdown-based knowledge packages (SKILL.md files) that agents reference for domain expertise
3. **Configure MCP Servers** — Model Context Protocol servers that provide tools (functions) agents can call, with OAuth flows, tool approval policies, and per-agent tool filtering
4. **Run Sessions** — Conversational execution sessions where users interact with agents via real-time streaming
5. **Manage Runners** — Execution environments (local desktop, cloud-provisioned) that actually run agent code
6. **Administer Organizations** — Members, invitations, identity providers, API keys, billing, environments, OAuth apps, platform clients, usage tracking

### The Two UI Surfaces

1. **Stigmer Console** (`client-apps/web`) — A Next.js app that serves as the primary admin interface at `app.stigmer.ai`. Used by platform builders to manage their Stigmer organization.

2. **@stigmer/react SDK** — A framework-agnostic React component library that platform builders embed in their own products. Every major UI component (ResourceListView, AgentDetailView, SkillDetailView, McpServerDetailView, RunnerListPanel, MembersSection, ApiKeysSection, BillingSection, etc.) lives in the SDK, not the Console. The Console pages are thin wrappers around SDK components.

This dual-surface architecture means UX improvements must work both as standalone SDK components (embeddable, themeable, self-contained) and as first-party Console pages (with navigation, breadcrumbs, settings layout).

### Technology Stack

- **React 19**, TypeScript
- **Tailwind CSS v4** with `--stgm-*` CSS custom properties and `@layer stgm` isolation
- **@connectrpc/connect** — gRPC-Web / Connect protocol for all data fetching
- **@bufbuild/protobuf** — Protobuf message types
- **Lucide React** icons (Console only; SDK uses inline SVGs)
- **No component library** — all UI primitives are built from scratch (buttons, inputs, dropdowns, tooltips, scroll areas, separators, toasts via Sonner)
- **No state management library** — plain React hooks

## Current Screen Inventory and Gaps

### 1. Library — Resource List Pages

**Current state:** All three resource types (Skills, Agents, MCP Servers) share a single `ResourceListView` SDK component that supports:
- Grid or list layout with responsive columns
- Search with debounce
- Scope toggle (org-only vs. all/marketplace)
- Pagination (page-based, not infinite scroll)
- Skeleton loading states
- Empty states with icons
- Keyboard navigation (arrow keys, Enter/Space)
- Per-item action slots (e.g., "Connect" button on MCP servers)

**What's missing / subpar:**
- **No sorting** — Cannot sort by name, date created, date updated, status
- **No filtering** — Cannot filter by status (Ready/Failed/Uploading), visibility (Public/Private), tags
- **No bulk operations** — Cannot select multiple items to delete, change visibility, or export
- **No inline actions** — No quick-action menu (kebab/three-dot) on items for delete, duplicate, share, copy ID
- **No view persistence** — Grid vs. list preference not persisted; page size not configurable
- **Cards are information-sparse** — Grid cards show only name, org, description, and public badge. No status indicator, no last-updated time, no usage stats, no connected agents count
- **No drag-and-drop** — Cannot reorder or organize resources
- **Monotone visual language** — All three resource types look identical except for the icon. No visual differentiation based on resource status or type
- **No onboarding guidance** — Empty states just say "No X found" — no "Get Started" tutorial, no quick-create wizard

### 2. Library — Resource Detail Pages

**Current state:** Each resource type has a dedicated detail view:

- **SkillDetailView**: Header (name, org, tag, state badge, visibility, dates), Skill Content (rendered markdown), Version info (hash, git provenance)
- **AgentDetailView**: Header (name, org, icon, visibility, dates, description), Instructions (collapsible pre-formatted text), MCP Servers list (clickable), Skills list (clickable), Sub-Agents (expandable), Environment Variables (key-value list)
- **McpServerDetailView**: Similar pattern

**What's missing / subpar:**
- **Entirely read-only** — No inline editing of any field. To edit an agent, you navigate to a separate "edit session" (a conversational AI flow). Skills and MCP Servers have no edit flow at all from the detail page
- **No delete action** — Cannot delete a resource from its detail page
- **No version history** — No ability to see previous versions, diffs, or rollback
- **No usage analytics** — No "which sessions used this agent/skill" view, no execution count, no last-used timestamp
- **No relationship graph** — An agent references MCP servers, skills, and sub-agents, but there's no visual graph or dependency view
- **Instructions shown as raw pre-formatted text** — Not syntax-highlighted, not in a code editor, not editable
- **No copy actions** — Cannot copy agent instructions, skill content, environment variable names, or configuration as YAML/JSON
- **No duplication** — Cannot clone a resource to create a variant
- **Flat layout** — All sections are stacked vertically. No tabs, no sidebar-within-detail, no split-pane for large content
- **No diff view for skills** — Skills are markdown documents, but there's no diff view against previous versions or git changes

### 3. Resource Creation/Edit Flows

**Current state:** Resources are created and edited exclusively through an AI-powered conversational flow. The user clicks "Add Agent" / "Add Skill" / "Add MCP Server", which navigates to a new session page where they describe what they want in natural language, and the AI creates the resource. For agent editing, an "Edit" link navigates to another conversational session pre-loaded with the agent's current configuration.

**What's missing / subpar:**
- **No form-based creation** — Users who know exactly what they want cannot fill out a structured form. They must go through a conversation
- **No visual editor** — No WYSIWYG or structured editor for agent instructions, skill markdown, or MCP server configuration
- **No import/export** — Cannot import an agent definition from YAML/JSON/CLI output, cannot export a resource's configuration
- **No template gallery** — No pre-built agent/skill templates to start from
- **AI-only editing is a single path** — Power users who want precise control over every field (model selection, tool approval policies, environment variable validation) are forced through a conversational interface
- **No live preview** — When editing via AI, there's no side-by-side preview of the resource as it will appear

### 4. Runners Page

**Current state:** Runners are shown in a sidebar panel (`RunnerListPanel` from SDK). The panel shows a compact list with status indicators, hostname, and actions (stop, delete). A "Launch Local Runner" button triggers a desktop app deep link flow with polling and timeout handling. There's also a "Stigmer Desktop" download promo card.

**What's missing / subpar:**
- **No runner detail view** — Cannot inspect a runner's capabilities, active sessions, resource utilization, logs
- **No runner configuration** — Cannot configure runner settings (max concurrent sessions, allowed models, etc.)
- **Sidebar-only listing** — Runners deserve a full-page management view, not just a sidebar panel
- **No runner health monitoring** — No CPU/memory/disk usage, no connection latency, no uptime metrics
- **No runner grouping** — Cannot organize runners into pools or tag them for routing rules
- **No cloud runner management** — Cloud-provisioned runners are opaque — no visibility into auto-scaling, regions, or costs

### 5. Settings Pages

**Current state:** The settings section has a sidebar navigation with these pages:
- **Organization Profile** (`OrgProfileSection`) — Org name, slug display
- **Members** (`MembersSection`) — Member list with roles
- **Invitations** (`InvitationsSection`) — Pending invitation list
- **Identity Providers** (`IdentityProvidersSection`) — SSO configuration
- **API Keys** (`ApiKeysSection`) — Create/list/delete API keys
- **OAuth Apps** (`OAuthAppsSection`) — OAuth application management
- **Platform Clients** (`PlatformClientsSection`) — Platform client credentials
- **Environments** (`EnvironmentsSection`) — Environment variable management
- **Runners** — Runner management (settings context)
- **Billing** (`BillingSection`) — Credit balance, payment methods, credit packs, auto-recharge, ledger
- **Usage** (`UsageSection`) — Usage reports with export

**What's missing / subpar:**
- **No profile editing UX** — Org profile is display-only or minimal edit
- **No audit log** — No visibility into who changed what, when
- **No role management** — Cannot create custom roles or fine-grained permissions
- **No notification preferences** — No per-user notification settings
- **No danger zone** — No clearly delineated destructive actions section (delete org, transfer ownership)
- **Billing is credit-only** — No subscription plan visualization, no cost projections, no spend alerts
- **Usage has no visualizations** — No charts, graphs, or trends — just tables and numbers

### 6. Session / Conversation Views

**Current state:** Already undergoing improvement via the "react-sdk-streaming-ux" project. This research is NOT about sessions/conversations — that's covered separately.

### 7. Cross-Cutting Gaps

- **No command palette** — No Cmd+K / Ctrl+K for quick navigation, search, and actions across all resources
- **No breadcrumb interactivity** — Breadcrumbs exist but are plain navigation; not contextual
- **No toast/notification system for mutations** — Some mutations show toasts, others are silent
- **No optimistic UI** — All mutations wait for server response before updating the UI
- **No keyboard shortcuts** — No shortcuts for common actions (new session, search, navigate)
- **No dark/light mode toggle** — Theme is controlled by system preference, no manual override in the UI
- **No responsive mobile experience** — Layout breaks or is unusable on small screens for management pages
- **No accessibility audit** — Screen readers, keyboard navigation, ARIA labels exist in some components but not consistently

## What We Need From This Research

### Part 1: UX Philosophy for Developer Platforms

1. **What makes a developer platform's management UI feel "state of the art"?** Analyze what separates excellent developer tools (Vercel, Supabase, Linear, Retool, Clerk, WorkOS, Neon, PlanetScale, Railway, Render, Fly.io) from average ones. What design principles, interaction patterns, and visual languages do they share?

2. **Information density vs. clarity tradeoff** — Developer users want dense information but also scanability. How do the best platforms balance these? When should you use data tables vs. card grids vs. list views? What are the guidelines for choosing between them?

3. **The "AI-first + manual control" paradigm** — We have a unique situation where resource creation is AI-driven (conversational), but users also need traditional CRUD control. How should a platform blend AI-powered workflows with direct manipulation? What's the right balance? Are there precedents in the industry?

4. **SDK component design for embedding** — Our components are SDK-first (embeddable by customers in their products). How do the best embeddable component libraries (Stripe Elements, Auth0 Lock, Stream Chat, Sendbird) handle the tension between feature-richness and embeddability? How do they handle theming, layout adaptation, and feature toggles?

### Part 2: Resource List View Patterns

1. **Best-in-class resource list experiences** — How do Vercel (projects), Supabase (tables/databases), Linear (issues), Clerk (users), GitHub (repositories), Stripe (payments/customers), Datadog (monitors), Retool (apps), Notion (pages), and other developer platforms display resource lists? What interaction patterns do they use?

2. **Filtering, sorting, and search** — What are the best patterns for:
   - Faceted filtering (status, visibility, tags, date ranges)
   - Multi-column sorting
   - Full-text search with type-ahead suggestions
   - Saved/bookmarked filter presets
   - URL-synced filter state (shareable URLs)

3. **Grid vs. List vs. Table** — When should each be used? How do platforms let users switch between them? Should the preference be persisted? How does each layout handle different content densities?

4. **Bulk operations and multi-select** — How do the best platforms handle selecting multiple resources and performing batch operations (delete, change visibility, tag, export)? Checkbox selection patterns, floating action bars, keyboard shortcuts.

5. **Empty states and onboarding** — How do the best platforms handle empty resource lists? What makes a great empty state that guides users to their first action? Examples of effective "Get Started" patterns.

6. **Pagination vs. infinite scroll vs. virtual scrolling** — For resource lists with potentially hundreds of items, what's the best approach? How do platforms handle very long lists without performance degradation?

7. **Real-time list updates** — When a resource changes (e.g., a runner comes online, a skill finishes uploading), how should the list update? Optimistic updates, polling, WebSocket/SSE push, animation for new items appearing?

### Part 3: Resource Detail View Patterns

1. **Best-in-class resource detail pages** — How do developer platforms display complex resource configurations? Analyze detail pages in:
   - Vercel (project settings, deployment details)
   - Supabase (table editor, function details)
   - GitHub (repository settings, action run details)
   - Clerk (user details, organization settings)
   - Stripe (payment details, subscription details)
   - Linear (issue detail, project settings)
   - AWS Console (resource detail pages)
   - Datadog (monitor detail, dashboard)

2. **Inline editing vs. modal editing vs. page-level editing** — When should fields be editable inline (click to edit)? When should editing open a modal/sheet/drawer? When should it navigate to a separate edit page? What are the patterns for:
   - Single-field inline edit with save/cancel
   - Section-level edit mode (toggle a section into edit mode)
   - Full-page edit with autosave
   - Sheet/drawer-based editors for complex sub-objects

3. **Code/text content display** — For resources that contain code or markdown (agent instructions, skill SKILL.md content):
   - How should they be displayed? Syntax highlighting, line numbers, copy buttons?
   - How should they be edited? Code editor (Monaco, CodeMirror), rich text editor, or raw textarea?
   - How should diffs between versions be shown?

4. **Relationship visualization** — An agent has MCP servers, skills, sub-agents, environment variables. How should these relationships be displayed?
   - Flat section lists (current approach)
   - Interactive dependency graph
   - Tab-based navigation between related resources
   - Linked breadcrumbs and cross-navigation

5. **Resource metadata and status** — How should the following be displayed?
   - Created/updated timestamps
   - Version history and change log
   - Status indicators (Ready, Failed, Uploading, Pending)
   - Usage statistics (execution count, last used, connected agents)
   - Ownership and sharing info

6. **Destructive actions** — How should delete, disable, and other destructive actions be presented? Confirmation dialogs, type-to-confirm, undo periods, archival vs. permanent deletion.

7. **Activity feeds and audit trails** — Should detail pages include an activity feed showing recent events (created, updated, used in session X, error in execution Y)? How do the best platforms present this?

### Part 4: Resource Creation and Edit Flows

1. **Form-based vs. conversational creation** — How should we blend our AI-driven creation flow with traditional form-based creation? Options:
   - AI chat as the only path (current)
   - Form-first with AI assist (AI fills fields, user reviews)
   - Dual path (user chooses AI or manual)
   - AI overlay on form (form exists, AI button can auto-populate)

2. **Multi-step creation wizards** — For complex resources like agents (which have instructions, MCP servers, skills, sub-agents, env vars), what's the best creation UX?
   - Step-by-step wizard with validation
   - Single long form with sections
   - Progressive disclosure (start simple, add complexity)

3. **Template / starter galleries** — How do the best platforms offer resource templates?
   - Vercel templates, Supabase starters, GitHub template repos, Retool templates
   - How are templates browsed, previewed, and customized?

4. **Import/export** — How should resources be importable/exportable?
   - YAML/JSON configuration files
   - CLI-generated definitions
   - Cross-org cloning / forking
   - Version-controlled definitions (GitOps)

5. **Live preview during editing** — How should the user see the effect of their changes in real-time? Split-pane preview, side-by-side rendering, inline preview.

### Part 5: Settings and Admin UX Patterns

1. **Settings page organization** — How do the best platforms organize settings?
   - Sidebar navigation with categories
   - Tab-based navigation
   - Single scrollable page with jump-to-section
   - How deep should nesting go?

2. **Member and team management** — Best patterns for:
   - Inviting members (email input, role selection, bulk invite)
   - Role management and permissions display
   - Member list with search, filter, status
   - Removing members (confirmation, grace period)

3. **API key and credential management** — How do platforms handle:
   - Key creation (naming, permissions/scopes, expiration)
   - Key display (show-once patterns, copy buttons, regeneration)
   - Key rotation and revocation
   - Usage tracking per key

4. **Billing and usage dashboards** — What makes a great billing experience?
   - Credit/balance visualization
   - Usage charts and trends
   - Cost breakdowns by resource/agent/model
   - Spending alerts and budgets
   - Invoice history

5. **Environment / secrets management** — How do platforms handle:
   - Secret input (masked fields, reveal toggles)
   - Environment groups/inheritance
   - Secret rotation
   - Audit trails for secret access

### Part 6: Interaction Patterns and Micro-UX

1. **Command palette (Cmd+K)** — How do the best developer tools implement command palettes?
   - Search across all resources, actions, navigation, settings
   - Recent items, fuzzy search, keyboard-first design
   - Action execution from the palette (create, delete, navigate)

2. **Toast notifications and mutation feedback** — How should the UI communicate success/failure of operations?
   - Undo-able toasts for destructive actions
   - Progress toasts for long operations
   - Inline validation vs. toast-based error reporting

3. **Keyboard shortcuts** — What shortcuts do developer platforms commonly implement? How are they discoverable (shortcut overlay, tooltip hints)?

4. **Drag-and-drop** — Where is drag-and-drop valuable in a platform management UI? File explorer for skills? Reordering MCP server priority? Kanban for workflow stages?

5. **Context menus and right-click** — Should resource items have right-click context menus? How do platforms handle this alongside kebab menus?

6. **Optimistic UI** — How should mutations be displayed before server confirmation? Which operations are safe for optimistic updates? How to handle rollback on failure?

7. **Loading states and transitions** — Best patterns for:
   - Skeleton loading (content-aware shapes)
   - Shimmer effects
   - Suspense boundaries in React
   - Page transition animations
   - Route-level loading bars (NProgress-style)

### Part 7: File Explorer and Tree View Patterns

1. **File explorer for skills** — One of our customers built a file-explorer-style view for browsing skills. Research:
   - File tree patterns in web UIs (VS Code-style, Figma-style, Notion-style)
   - How to represent a flat list of skills as a hierarchical tree (by org, by tag, by status?)
   - Expand/collapse, drag-and-drop organization, multi-select
   - Preview pane alongside tree navigation

2. **Tree views for agent composition** — An agent has MCP servers, sub-agents (which have their own MCP servers and skills), forming a tree. How should this be visualized?
   - Collapsible tree views
   - Graph/network visualizations
   - Interactive dependency diagrams

### Part 8: Visual Design and Theming

1. **Dark-mode-first design** — Our platform uses a dark theme. What are the best practices for:
   - Color palette choices for status indicators, interactive elements, hierarchy
   - Contrast ratios for readability
   - Surface layering (card-on-background-on-page)
   - Border vs. shadow vs. gradient for depth

2. **Information hierarchy through typography** — How to use font size, weight, spacing, and color to create clear visual hierarchy in resource views

3. **Status indication patterns** — Color coding, icons, badges, pulsing indicators for different resource states (Ready, Failed, Running, Pending, Degraded)

4. **Responsive design for management UIs** — How should complex management screens adapt to different viewport sizes? Is a separate mobile experience needed, or should desktop-first suffice for B2B developer platforms?

## Constraints and Requirements

- **React 19, TypeScript, Tailwind CSS v4** — All recommendations must be implementable with this stack
- **SDK-first architecture** — Components must be embeddable in customer products, not just work in our Console. They must be self-contained, themeable via CSS custom properties, and not depend on Next.js or any framework
- **Dark theme** — Primary theme is dark. Light mode is secondary
- **No heavy UI library dependency** — We build our own primitives. Recommendations for specific headless UI libraries (Radix, Ariakit, React Aria) are welcome, but we won't adopt a full design system like Material UI or Chakra
- **Accessibility (WCAG 2.1 AA)** — All patterns must be accessible: keyboard navigable, screen reader friendly, sufficient contrast ratios
- **Performance** — Resource lists may contain hundreds of items. Detail pages may have large markdown content. Solutions must be performant
- **Protobuf data model** — All data comes from protobuf-generated types via gRPC. Field names follow proto conventions. The data model has metadata (name, slug, org, visibility, id), spec (configuration), and status (computed state)
- **Multi-tenant** — Resources belong to organizations. Scope toggle switches between "my org" and "all orgs" (marketplace)
