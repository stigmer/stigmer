# Deep Research: Runner Management UX & Architecture

## Research Objective

Stigmer is an AI agent platform. A "runner" is a local process that users start on their machine — it connects to the Stigmer cloud backend (api.stigmer.ai:443), registers itself, receives work (agent executions), and runs them locally. Think of it like a GitHub Actions self-hosted runner or a Kubernetes Node: it heartbeats, picks up tasks from a queue, and reports status.

**The core question:** How do comparable platforms (GitHub Actions, GitLab Runner, Buildkite Agent, Cursor Background Agents, Codeium Windsurf, Devin, etc.) handle the UX of local runner/agent management — specifically the "just start it and use it" experience? What are the best-in-class patterns for making runner management invisible to the user?

We're experiencing user friction: users open the desktop app, click "Start Runner" (with empty form fields), and get errors like "runner already running" because a previous session from 5 hours ago is still active. The system works correctly but the UX fails — users shouldn't need to think about runner lifecycle at all.

## Context: Current Architecture

### What a Runner Is
- A local process (Python-based agent-runner + optional Cursor harness in Node.js)
- Connects to `api.stigmer.ai:443` via gRPC
- Registers with `runner.apply()` (create-or-update semantics)
- Opens a bidirectional connect stream for heartbeats (every 30s) and commands
- Gets assigned a Temporal task queue (`runner:{runner_id}`) for work routing
- Reports phase transitions: PENDING → STARTING → READY → BUSY → STOPPED

### How Users Start a Runner Today

**From CLI:**
```bash
stigmer up runner
# Uses hostname as name, config file for token/endpoint
# Or with explicit options:
stigmer up runner --name my-runner --token sk-... --endpoint api.stigmer.ai:443
```

**From Desktop App (Tauri):**
- User clicks "Start Runner" button
- A dialog appears with 3 optional fields: Name, Endpoint, Token/API Key
- All fields show placeholders like "my-macbook (default: hostname)"
- If left empty, defaults are used (hostname for name, config for creds)
- The desktop app spawns the CLI sidecar: `stigmer-cli up runner --standalone --token ... --endpoint ...`

### The Problem Scenario (from screenshots)
1. User's machine hostname: "Swarups-MacBook-Pro.local"
2. Gets sanitized to slug: "swarups-macbook-pro-local"
3. User already has a runner from 5 hours ago still running (PID 9730)
4. User clicks "Start Runner" without entering anything
5. Gets error: `runner "swarups-macbook-pro-local" is already running`
6. Error shows PID, Backend, Started time, and suggests `--name <name>`
7. User is confused — they just wanted to use Stigmer

### Current Name Resolution Logic
```
1. If --name flag provided → use it (must be valid slug)
2. Else → os.Hostname() → sanitizeToSlug() → lowercase, replace non-alphanumeric with hyphens
```

### Current Conflict Detection
```
1. Load state from ~/.stigmer/runners/<name>.json
2. If state exists AND process is still alive (signal 0) → error
3. If state exists but process is dead → clean up stale state, proceed
```

### State Persistence
- Runner state stored at `~/.stigmer/runners/<name>.json`
- Contains: runner_id, slug, org, backend_endpoint, PID, task_queue, started_at
- Removed when runner stops cleanly
- Stale files cleaned on next `stigmer up runner` (ReapStaleRunners)

### Desktop App Architecture
- Tauri (Rust) shell spawns CLI binary as sidecar
- ProcessManager tracks desktop-managed runner processes
- Events: runner:started, runner:stopped, runner:error, runner:log
- UI shows runners from server API (all org runners) + local state (on-disk JSON)
- Topology classification: desktop-managed, local-cli, local-daemon, remote, stopped-local

## Specific Research Questions

### 1. Comparable Platform Runner UX Patterns

**GitHub Actions Self-Hosted Runners:**
- How does GitHub handle the "runner already registered" case?
- What happens when a user tries to start a second runner instance?
- How does the runner token/registration flow work?
- Is there an "auto-start on boot" pattern?

**GitLab Runner:**
- How does `gitlab-runner register` vs `gitlab-runner run` work?
- Multiple runner instances on same machine?
- Service mode vs foreground mode?

**Buildkite Agent:**
- How do they handle agent naming/uniqueness?
- What's the agent lifecycle on a developer machine?
- How does the Buildkite dashboard show agent status?

**Cursor Background Agents:**
- How does Cursor expose its background agent runners?
- Is there a runner concept at all, or is it invisible?
- How do they handle "machine already has an agent running"?

**Devin / Codeium Windsurf / Similar:**
- How do AI coding agent platforms handle local execution?
- Is runner management exposed at all to users?
- What's the "zero-config" experience?

### 2. "Start and Forget" Patterns

- What patterns exist for ensuring a runner "just works" without user intervention?
- How do platforms handle the case where a runner is already running? (reconnect vs error vs silent skip)
- What's the UX for "I already have a runner, I just want to use it"?
- Should the UI auto-detect and surface existing runners without requiring a start action?
- How do platforms handle runner persistence across reboots (launchd, systemd, Windows services)?

### 3. Identity & Naming Patterns

- How do comparable platforms generate stable runner identities?
- Should a machine have exactly one runner identity that persists forever?
- How do multi-org scenarios work (same machine, different orgs)?
- What's the naming convention (hostname-based, UUID-based, user-chosen)?
- Should re-registration be completely implicit (detect, resume, done)?

### 4. Desktop App / GUI Patterns for Runner Management

- Which platforms have GUI/desktop apps for runner management?
- What's the optimal UX when a runner is already running?
- Should the "Start Runner" button be replaced with "Connect" or "Resume"?
- How do platforms show runner status in system tray / menu bar?
- What's the pattern for "always-on" runners managed by the desktop app?

### 5. Error Prevention & Recovery

- How should the system handle the "already running" case gracefully?
  - Option A: Auto-adopt the existing runner (detect it, show it, done)
  - Option B: Show "Runner is already active" as a success state, not an error
  - Option C: Transparent reconnect (stop old, start new)
  - Option D: Remove the "Start Runner" button entirely when one is already running
- How do platforms handle stale runner state (PID file exists, process died)?
- What happens when the machine sleeps/wakes?
- What about network reconnection after laptop lid close/open?

### 6. Background Process Management Patterns

- How do comparable platforms keep runners alive in the background?
- macOS: launchd plist vs login item vs background app?
- Linux: systemd service vs user service?
- Should the desktop app auto-start a runner on launch?
- How do platforms handle runner auto-updates without user intervention?

### 7. Multi-Runner vs Single-Runner per Machine

- Is there ever a need for multiple runners on the same machine?
- How do platforms distinguish "I want another runner" from "I want to use my existing runner"?
- Should the default UX assume one-runner-per-machine?
- How do CI/testing scenarios (many runners on one machine) differ from developer scenarios?

## What I Want from This Research

1. **Best-in-class examples** of "invisible" runner management UX — platforms where users never think about runner lifecycle
2. **Concrete patterns** we could adopt to make "Start a runner and use it" truly that simple
3. **Anti-patterns** to avoid — what causes confusion in comparable platforms
4. **Recommended architecture** for making the desktop app experience zero-friction:
   - Should the desktop app auto-start a runner silently on launch?
   - Should the "Start Runner" dialog even exist?
   - What should happen when clicking "Start Runner" and one already exists?
5. **Production patterns** for background process management on macOS/Linux (the primary dev platforms)
6. **Comparison table** of how 5+ platforms handle: registration, naming, duplicate detection, auto-start, status display, stopping
