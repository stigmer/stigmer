# Deep Research: Tamper-Resistant Usage Reporting from Untrusted Runners

## Research Objective

We need to understand what techniques, patterns, and industry precedents exist for making usage/telemetry data reported by untrusted client-side processes trustworthy enough for billing purposes — specifically in the context of an AI agent platform where open-source runners execute on user-controlled machines and must report LLM token usage back to a central billing server.

## Our Specific Situation

### Platform Architecture

Stigmer is an infrastructure platform for AI agents. It has two execution engines ("harnesses"):

1. **Native harness (LangGraph):** The runner talks directly to LLM providers (Anthropic, OpenAI). Our server-side proxy sits between the runner and the provider, observes every byte of the HTTP response, and extracts token usage from the provider's SSE stream. This is tamper-proof because the proxy is server-side and the runner cannot bypass it (the runner doesn't have the provider API key — the proxy injects it).

2. **Cursor harness:** The runner uses the Cursor SDK (`@cursor/sdk`), which manages its own communication with Cursor's backend. We discovered through empirical testing that the Cursor SDK does NOT use `globalThis.fetch` for its main agent streaming — it uses an internal transport (likely WebSockets or native HTTP/2) that bypasses our fetch interceptor entirely. Our server-side proxy only sees sidecar calls (auth, model listing, analytics) but NOT the main agent turns that contain the LLM usage data.

### The Problem

The Cursor SDK provides per-turn usage data via an `onDelta` callback inside the runner process:

```json
{
  "type": "turn-ended",
  "usage": {
    "inputTokens": 10043,
    "outputTokens": 49,
    "cacheReadTokens": 2048,
    "cacheWriteTokens": 0
  }
}
```

This data is available ONLY inside the runner process. Our server-side proxy cannot observe it. The runner code is open-source (Apache 2.0), so any user can inspect and modify it.

### The Constraint

We need this usage data for billing (debiting credits from user accounts). If we trust runner-reported data at face value, a user could fork the runner, modify it to report zero usage, and consume LLM resources for free while Stigmer pays Cursor for the actual usage.

### What We Already Know

- **Cursor's Admin API** (`/teams/filtered-usage-events`) provides team-level usage data, but does NOT include `runId` or `agentId` fields, making per-execution attribution non-deterministic (fuzzy matching by email + time window + model + token proximity, with confidence scoring).
- **The runner runs inside Daytona sandboxes** (container-based) in cloud mode, but could also run locally in OSS mode.
- **We already have a trust level enum** in our proto: `BILLING_AUTHORITY` (proxy-reported), `SERVER_OBSERVED`, `DISPLAY_ONLY` (runner-reported).

## What We Need to Understand

### 1. Industry Patterns for Untrusted Client Telemetry

How do other platforms handle billing based on data reported by untrusted clients? Specifically:

- **Cloud gaming platforms** (e.g., GeForce Now, Xbox Cloud Gaming) — how do they meter GPU time when the client reports session duration?
- **CDN/bandwidth billing** (e.g., Cloudflare, Fastly) — how do they handle usage reported by edge nodes that could be compromised?
- **Metered SaaS billing** (e.g., Twilio, Stripe, AWS) — how do they ensure API call counts are accurate when the client SDK reports usage?
- **Cryptocurrency mining pools** — how do they verify work submitted by untrusted miners?
- **Mobile ad networks** — how do they detect fraudulent impression/click reporting from untrusted apps?

### 2. Cryptographic and Attestation Approaches

- **Signed usage receipts:** Could the Cursor SDK be asked (via feature request) to sign usage data with a key that Stigmer can verify? What would this look like?
- **Trusted execution environments (TEEs):** Could the runner process run inside a TEE (e.g., AWS Nitro Enclaves, Intel SGX) so that even if the user controls the host machine, they can't tamper with the runner's usage reporting?
- **Remote attestation:** Could the server verify that the runner binary is unmodified before trusting its usage reports?
- **Commitment schemes:** Could the runner commit to usage data (hash) before the server reveals the billing rate, preventing retroactive modification?

### 3. Statistical and Behavioral Detection

- **Anomaly detection:** What statistical methods can detect tampered usage (e.g., a user whose reported token counts are consistently 50% lower than users with similar workloads)?
- **Honeypot turns:** Could the server inject known-cost operations (e.g., a calibration prompt) into the runner's workload to verify that reported usage matches expected usage?
- **Cross-referencing:** Beyond the Admin API, what other signals could be used to cross-validate runner-reported data? (e.g., response latency correlating with token count, message length correlating with output tokens)

### 4. Practical Hybrid Approaches

- **Provisional billing with reconciliation windows:** How do credit card networks and payment processors handle provisional charges that are settled later? What's the UX pattern for "estimated" vs "settled" amounts?
- **Trust-but-verify with consequences:** How do platforms like AWS spot instances handle the trust problem — trust the client but audit asynchronously, with account penalties for detected fraud?
- **Rate-limited trust:** Could we trust runner-reported data up to a threshold (e.g., first $100/month) and require server-side verification beyond that?

### 5. The Cursor SDK Specifically

- Does the Cursor SDK or any similar agent SDK (e.g., OpenAI Agents SDK, Anthropic Claude Code SDK) provide any mechanism for server-side usage verification that doesn't depend on the client?
- Are there any Cursor SDK features (planned or existing) that would allow a third party to independently verify usage — such as a usage webhook, a run completion callback to a configured URL, or a signed usage receipt?
- How do other platforms that wrap third-party SDKs (e.g., LangSmith wrapping LangChain, Vercel AI SDK wrapping provider SDKs) handle the trust gap when the SDK controls its own transport?

## Output Format

Please provide:
1. A structured comparison of approaches (table format) with: approach name, trust level achieved, implementation complexity, latency impact, limitations
2. Specific recommendations for our situation (Cursor SDK + open-source runner + Daytona sandboxes)
3. Industry precedents with citations — what do real companies actually do?
4. A recommended phased approach: what to do now (simple), what to do next (moderate), what to do eventually (sophisticated)

## Context

This is for a production platform with early adopters. We currently show $0.00 for all Cursor sessions because no usage data reaches the billing pipeline. The immediate priority is showing accurate usage data. The secondary priority is making it tamper-resistant for billing. We'd rather show estimated-but-honest data today and add tamper resistance incrementally than block the UX fix waiting for a perfect solution.
