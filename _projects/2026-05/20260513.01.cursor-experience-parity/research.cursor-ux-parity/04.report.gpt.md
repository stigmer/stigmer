# Achieving Cursor-Quality UX in Stigmer

## Executive findings

The Cursor SDK, announced in public beta on **29 April 2026**, gives Stigmer access to the same underlying agent runtime, harness, and models that power Cursor’s desktop app, CLI, and web app. That is a strong foundation for parity, but it does **not** mean the full Cursor IDE experience is automatically available through the SDK. In practice, the SDK is best treated as an **execution substrate**; Stigmer still needs its own **session controller, event model, context manager, queue, checkpointing layer, and UI projections** to match the product experience users associate with Cursor. citeturn0search1turn2search5turn3search9

The clearest conclusion from the public documentation is that Cursor’s most distinctive UX advantages fall into two buckets. The first bucket is **runtime-native features that the SDK can partially expose**: streaming tool calls, agent modes, MCP-backed tool access, cloud agents, browser/computer-use artefacts, and durable agent execution. The second bucket is **IDE/product affordances that are either undocumented in the SDK or explicitly local/UI-scoped**: checkpoints, context-usage breakdowns, message queue UX, and user-visible summarisation controls. Those second-bucket items are the ones Stigmer should plan to implement natively rather than waiting for SDK parity. citeturn6search0turn21search1turn0search2turn0search0turn6search4

The most important strategic decision is therefore this: **do not try to mirror Cursor internals one-to-one**. Instead, define a **Stigmer-native UX contract** that works across both Cursor SDK runs and LangGraph runs: a common timeline, common queue semantics, common summary objects, common checkpoints, common approval cards, and common observability panels. That will let Stigmer deliver “Cursor-quality” UX across web, API, and SDK surfaces instead of merely reproducing the editor sidebar. This is also where Stigmer can surpass Cursor: especially on **web-native checkpoints, cross-harness observability, and shareable session artefacts**. citeturn0search1turn18search2turn11search4turn12search0

### What this means in practice

Stigmer can reach **high UX parity** on the features users notice most, but not by relying on undocumented Cursor SDK behaviour. The safe rule is: **if a feature is visible in Cursor’s editor but not explicitly described as an SDK capability, assume Stigmer must own it** until proved otherwise in real runtime tests. The only exception should be features where the SDK clearly streams enough raw information to let Stigmer project a very similar UI, such as tool-call cards, thinking panels, and step timelines. citeturn0search1turn2search2turn2search1

## Priority and roadmap

### Highest value for least effort

The best first tranche is **read-only planning mode, rich tool-call rendering, queued messaging, context telemetry, and inline approvals**. Those features solve obvious “this feels worse than Cursor” gaps, require limited back-end invention compared with full checkpointing, and mostly consume data Stigmer can already derive from streams, tool metadata, and session policies. Cursor’s own docs show that mode selection, tool visibility, todo/planning visibility, queueing, and context breakdown all materially shape the day-to-day UX. citeturn6search0turn6search4turn21search1turn1search5

**Live summarisation** should ship early as well, even though it is not the absolute lowest-effort item, because it is the feature users are already explicitly comparing against Cursor. The key is to start with a **minimal but robust summarisation system** rather than an overly clever one: token-threshold trigger, structured running summary, inline “conversation compacted” card, and a separate canonical transcript that remains fully visible to the user. LangGraph’s memory guidance explicitly recommends separate state for full message history versus summarised context, and Cursor’s own research shows why summary quality matters for long-horizon coding tasks. citeturn18search7turn18search0turn20search0

**Checkpoints and restore** should come after those foundations. They are valuable, but they introduce real storage, recovery, and workspace-consistency complexity. Replit’s documentation is instructive here: once a platform supports checkpoint restore properly, users expect not just code rollback but conversation continuity, configuration continuity, and sometimes database continuity as well. Cursor’s own checkpoints are intentionally narrower and local-only. citeturn12search0turn12search3turn0search2

## Recommended architecture

### Treat the SDK as the execution engine, not the UX state machine

Stigmer should ingest raw Cursor stream events into an **append-only run ledger** and then build multiple derived views on top of that ledger: transcript, tool timeline, plan list, queue, context meter, approval state, summary chain, modified-files view, and observability metrics. This separation is important because Cursor’s public SDK surface is still maturing; even Cursor staff have already confirmed a streaming bug where some synchronously executed tools fail to emit clean completion/error updates. A derived-state architecture lets you patch around those imperfections without corrupting your canonical history. citeturn2search1turn2search0

That same architecture should power **both Cursor SDK runs and LangGraph runs**. LangGraph already thinks in terms of persisted state, short-term thread memory, summarisation, and checkpoints. If Stigmer defines its own canonical event schema now, the UI can stay stable even when the underlying harness changes. citeturn18search2turn18search0

### Keep two conversation representations

For long sessions, Stigmer should store:

- a **canonical transcript** for user-visible history, auditing, replay, export, and debugging;
- a **model context window representation** containing recent messages, tool references, and structured summary state.

This split is not just convenient; it is the right safety/performance boundary. LangMem’s guidance recommends rendering the full unmodified history to users while storing summarisation results separately, and Cursor’s dynamic-context work shows why long tool outputs and chat history should often be referenced as files rather than injected wholesale into the prompt. citeturn18search7turn10search0

A good summary object for coding tasks should include: **user goal, current plan state, what changed, key files, tool findings, failed approaches, open blockers, next actions, and references to artefacts/history files**. That mirrors the kind of structured information Cursor’s self-summarisation training is optimising for, while also fitting the LangGraph pattern of extending an existing running summary. citeturn20search0turn18search0

### Implement a native session controller

The **session controller** should be a Stigmer-owned service that decides:

- which mode the run is in;
- which tools are allowed;
- when queued messages can be injected;
- when a summary should be created;
- when a checkpoint should be taken;
- when a tool requires HITL approval.

This controller lets Stigmer emulate Cursor’s Ask-versus-Agent distinction regardless of harness: in Cursor SDK by gating tools and instructions; in LangGraph by routing through planner/executor subgraphs. It also creates one place to enforce approval and safety policies. Cursor’s secure-sandbox write-up is a useful warning here: repeated approval prompts create approval fatigue, so the controller should support policy presets and safe defaults rather than a naive “popup for everything” flow. citeturn6search0turn1search1turn9search4

### Build a checkpoint service independent of Cursor

Because Cursor checkpoints are a local editor feature, Stigmer should build its own checkpoint abstraction. The lowest-risk starting point is:

- **tracked files**: synthetic Git commits or hidden worktree refs before each material edit batch;
- **untracked files and artefacts**: content-addressed blob storage keyed to the checkpoint;
- **conversation continuity**: store the summary object, queued messages, approvals, and run position alongside the file snapshot.

That will not be as deep as Replit’s “entire environment plus optional database” restore, but it will cover the use cases most users actually hit during coding-agent sessions: “show me what changed”, “restore the last good state”, and “continue from there”. citeturn12search0turn12search3turn0search2

## UX implementation patterns and libraries

### Summarisation, planning, queueing, and approvals

For **summarisation**, use a **token-budget trigger rather than message count**. LangGraph explicitly frames token thresholds as the right mechanism for trimming or summarising, and Cursor’s self-summarisation research uses a fixed token-length trigger inside the agent loop. A practical Stigmer policy would be a **soft warning** before the threshold, an **automatic summary** at the threshold, and an **emergency compact** only if the model window is at risk. Cursor’s default context window is typically 200k tokens, with Max Mode extending that on selected models, so token-aware behaviour matters even when a model supports large windows. citeturn18search0turn20search0turn21search9

For **what model should summarise**, the best cost/performance default is a **smaller, cheaper model** unless the runtime provides a high-quality built-in summary. LangGraph’s own examples use smaller models such as `gpt-4.1-mini` or `claude-haiku` in summarisation middleware while leaving the main task to a stronger model. That is a sensible pattern for Stigmer too. citeturn18search8turn18search0

For **display**, use an **inline compacted-history card** in the transcript plus a **side-panel view of active model context**. Do not hide or replace the user’s original chat history. LangMem explicitly recommends showing the full history in the UI and, optionally, the summary/context passed to the LLM as an additional view. citeturn18search7

For **planning mode**, match the workflow users already know from Cursor, Devin, and Copilot: a visible **Plan/Ask toggle**, a **read-only tool policy**, a **structured plan output**, and a single **Approve & Execute** transition into full agent mode. Cursor’s Ask mode is the closest current analogue, Devin explicitly recommends starting in Ask and then switching to Agent, and Copilot’s plan mode requires user review before implementation. citeturn6search0turn13search7turn14search0

For **message queueing**, Stigmer should support two semantics:

- **Queue**: FIFO follow-ups that run after the current task reaches a safe point.
- **Steer**: a high-priority message delivered at the next safe point, not necessarily a hard interruption.

That design matches Cursor’s “queue” versus “send as fast as possible” UX and mirrors GitHub Copilot SDK’s explicit distinction between **queueing** and **steering** during active turns. Until Cursor documents true active-turn injection in the SDK, safe-point steering is the correct implementation target. citeturn6search4turn5search6

For **HITL approvals**, prefer **inline approval cards in the activity timeline** or a sticky side rail, not modal dialogs. Cursor’s sandboxing article argues that approvals become unreliable when they force constant context switches. Inline approvals keep the user in the same narrative thread as the action being approved. citeturn9search4

### Rich rendering for diffs, terminals, trees, and charts

The best React stack for a Cursor-quality web UI is:

| UI problem | Recommended approach | Libraries / references |
|---|---|---|
| File diffs and review | Use Monaco for full-fidelity code diffs; optionally use a Git-style diff component for compact review cards | Monaco’s `IDiffEditor`, diff view model, and diff options support an IDE-like experience. citeturn23search0turn23search1turn23search3turn23search8 |
| Terminal replay and live stdout | Use a real terminal emulator, not plain `<pre>` blocks | `xterm.js` is the obvious choice; it is used by major IDE and cloud-console products and supports parser hooks and stable terminal APIs. citeturn22search6turn22search0turn22search10 |
| File tree, checkpoint tree, artefact tree | Use a virtualised tree component | `react-arborist` is designed for VS Code/Finder-style tree interfaces and supports drag/drop, filtering, keyboard navigation, and virtualisation. citeturn26search2turn26search5 |
| Multi-pane IDE layout | Persist panel proportions and support drag resizing | `react-resizable-panels` supports persistent panel groups, conditional panels, and SSR layout persistence. citeturn27search3turn27search0 |
| Large chat logs and large tool results | Virtualise aggressively | TanStack Virtual provides React virtualisers for element and window scrolling. citeturn22search1 |

A few implementation details matter more than the specific library choice. First, **batch high-frequency deltas** such as text, thinking, token counts, and shell output into short rendering windows so React is updating at human cadence rather than token cadence. Second, **persist large tool results as references** and lazy-load the body; Cursor itself moved toward file-backed long outputs rather than prompt truncation for shell and MCP responses. Third, **keep thinking collapsed by default** unless the user opts in; it is useful for debugging and trust, but it should not dominate the primary transcript. citeturn10search0turn2search2

## Risks and open questions

### Main risks

| Risk | Why it matters | Mitigation |
|---|---|---|
| **SDK beta instability** | Cursor SDK is still in public beta, and at least one event-stream bug is already acknowledged publicly | Put a strict adapter layer between Cursor SDK and Stigmer’s internal event schema; never let the UI depend on raw SDK completeness. citeturn0search1turn2search1 |

# 2. Hard truth by feature

## 2.1 Chat summarization

### What Cursor is doing

Cursor has two relevant mechanisms:

First, **automatic context summarization**. Cursor docs say it automatically summarizes and manages context as conversations grow, and it condenses older messages to make room. ([Cursor Documentation][3])

Second, **Composer was trained with compaction-in-the-loop**. Cursor’s March 2026 writeup describes training Composer so that, at fixed token triggers, a synthetic summarization query is inserted; the model gets scratch space and emits a condensed context that includes the conversation state, plan state, remaining tasks, and number of prior summarizations. Cursor says the old baseline compaction prompt was thousands of tokens and often produced >5k-token outputs, while Composer’s trained summaries average around ~1,000 tokens after a short summarization prompt. ([Cursor][15])

Third, Cursor’s **dynamic context discovery** means summarization is not the only source of retained memory. Cursor turns long tool outputs into files, references chat history during summarization, syncs MCP descriptions into files, stores terminal sessions as files, and lets the agent search those files later. ([Cursor][11])

### Can Stigmer detect Cursor self-summarization through SDK events?

**Maybe, but do not design around it.**

Your starting information says low-level `InteractionUpdate` events include “summary and shell-output deltas.” That is useful and should be instrumented. But I did not find a public SDK contract saying there is a stable `SDKMessage` type like `summary`, nor a documented `run.compact()` / `agent.summarize()` API.

Recommended implementation:

```ts
type CursorSummarySignal =
  | { source: "sdk-delta"; confidence: "medium"; text: string; rawEvent: unknown }
  | { source: "assistant-text-detection"; confidence: "low"; text: string; rawEvent: unknown }
  | { source: "stigmer-native"; confidence: "high"; summaryId: string };
```

Stigmer should:

1. Log all raw `summary`-like deltas if present.
2. Display Cursor-originated summary cards when confidently detected.
3. Still run Stigmer-native active summarization, because Cursor-originated compaction may be opaque, automatic, or unavailable in LangGraph/local SDK paths.

### Can Stigmer trigger Cursor’s built-in summarization?

**I found no public SDK evidence that it can.**

Cursor CLI-like products have slash commands such as compacting/summarization in other tools, and Cursor IDE has automatic summarization. But the public Cursor SDK examples and release notes focus on `agent.send`, streaming, cloud/local execution, cancellation, conversation state, MCP, artifacts, and run lifecycle—not manual compaction control. ([Cursor][1])

### The Stigmer-native summarization design

Stigmer should split session history into two streams:

| Stream                        | Purpose                                                                                   | Retention                           |
| ----------------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------- |
| **Display transcript**        | What the user sees; full chronological history, all tool calls, all approvals, all diffs. | Immutable / durable.                |
| **Model context view**        | What gets passed to the model for the next step/run.                                      | Actively compacted.                 |
| **Context files / artifacts** | Long outputs, terminal logs, screenshots, raw files, previous summaries.                  | Searchable, referenceable.          |
| **Durable memory**            | Cross-session lessons, preferences, repo facts, decisions.                                | Extracted post-run or periodically. |

This mirrors LangGraph/LangMem guidance: keep full message history for UI while using a summarized context state for the LLM. LangMem’s summarization docs explicitly recommend rendering the full unmodified message history while separately passing summarized context to the LLM. ([LangChain AI][16])

### Summarization trigger

Use multiple triggers, not just one:

| Trigger                  | Recommended threshold                                                                                                                                                                                                                                |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Token budget**         | Summarize when estimated input context reaches **70–80%** of target budget. Cursor’s training writeup mentions fixed token triggers in the 40k/80k region for their experiments, but Stigmer should make this model-window dependent. ([Cursor][15]) |
| **Tool-output pressure** | Summarize or externalize when one tool result exceeds a configured token/byte threshold.                                                                                                                                                             |
| **Turn boundary**        | Summarize only after `turn-ended`, `step-completed`, or tool completion—not mid-tool.                                                                                                                                                                |
| **Before follow-up**     | Especially important for local Cursor SDK because current forum reports confirm a local conversation-state bug. ([Cursor - Community Forum][2])                                                                                                      |
| **Manual**               | `/summarize`, “compact context,” or “save current state.”                                                                                                                                                                                            |
| **Checkpoint boundary**  | Summarize after meaningful file changes and tests.                                                                                                                                                                                                   |

### Summary schema

Use a typed summary, not freeform prose:

```ts
type CodingSessionSummary = {
  userGoal: string;
  currentPlan: Array<{
    id: string;
    title: string;
    status: "todo" | "in_progress" | "done" | "blocked";
    dependencies?: string[];
  }>;
  implementedChanges: Array<{
    file: string;
    description: string;
    checkpointId?: string;
  }>;
  decisions: Array<{
    decision: string;
    rationale: string;
    alternativesRejected?: string[];
  }>;
  errorsAndFixes: Array<{
    symptom: string;
    rootCause?: string;
    fix?: string;
    stillRelevant: boolean;
  }>;
  testsAndValidation: Array<{
    commandOrCheck: string;
    result: "passed" | "failed" | "not_run" | "partial";
    notes?: string;
  }>;
  importantContext: Array<{
    kind: "file" | "symbol" | "api" | "constraint" | "user_preference";
    value: string;
    reason: string;
  }>;
  artifacts: Array<{
    artifactId: string;
    type: "terminal_log" | "diff" | "screenshot" | "browser_video" | "long_tool_output";
    summary: string;
  }>;
  openQuestions: string[];
  nextBestActions: string[];
};
```

### Same model or cheaper model?

Use a **tiered policy**:

| Case                                         | Model choice                                                                       |
| -------------------------------------------- | ---------------------------------------------------------------------------------- |
| **Active compaction that will guide coding** | Use a strong coding-capable model. Summary omissions can cause expensive mistakes. |
| **Post-run memory extraction**               | Use cheaper model, then optionally validate against changed files/tool logs.       |
| **Large terminal/log compression**           | Use cheap model or deterministic extraction first.                                 |
| **Critical/security-sensitive code changes** | Use two-pass: extractor → synthesizer → verifier.                                  |

OpenAI’s current API ecosystem is moving toward explicit compaction and memory separation: the Responses API has a `/responses/compact` endpoint for long-running conversations, while the Agents SDK memory system distills longer-term lessons into memory files using progressive disclosure. ([OpenAI Platform][17])

Anthropic’s public docs are more about **thinking summarization** than conversation compaction: Claude can return summarized thinking while charging for full thinking tokens, and thinking behavior around tool use has provider-specific handling. That is relevant to Stigmer’s “reasoning display” policy, but it is not a replacement for Stigmer’s own conversation summarization. ([Claude API Docs][18])

### User-facing summarization UX

Do this:

> **Context compacted**
> Stigmer summarized earlier conversation to keep the agent focused. Full history is still available.

Render as a collapsible card with:

* Summary version.
* Trigger reason: “context reached 76%,” “large terminal output,” “manual compact.”
* What was retained.
* What was moved to artifacts.
* Link to full transcript.
* “Edit summary” or “pin correction” for power users.

Do **not** impersonate Cursor with “I have summarized the conversation” unless the Cursor model actually emitted that text. Stigmer should own the UX language.

## 2.2 Planning / mode switching

### What Cursor exposes in the IDE

Cursor docs distinguish modes: Agent mode has full tool access; Ask mode is read-only exploration; Custom modes let users configure behavior. Cursor also documents planning/todos and queued messages, and its changelog notes Plan Mode as a way for Cursor to write detailed plans before complex tasks. ([Cursor Documentation][4])

### Does Cursor SDK expose mode switching?

I did not find public SDK docs for:

```ts
agent.setMode("plan")
agent.send(prompt, { mode: "ask" })
agent.send(prompt, { toolPolicy: "read_only" })
```

So Stigmer should model this itself.

### Recommended Stigmer modes

| Mode           | Purpose                            | Allowed capabilities                                         | Output style                      |
| -------------- | ---------------------------------- | ------------------------------------------------------------ | --------------------------------- |
| **Ask**        | Understand repo, answer questions. | Read/search only. No edits, no shell unless explicitly safe. | Answer with citations/snippets.   |
| **Plan**       | Produce implementation plan.       | Read/search, optionally dry-run commands. No writes.         | Markdown plan + typed task graph. |
| **Agent**      | Implement approved plan.           | Edits, tests, shell, browser, MCP subject to policy.         | Execution timeline.               |
| **Autonomous** | Long-running execution.            | Broader tools, bounded by approvals/guardrails.              | Progress dashboard + checkpoints. |
| **Review**     | Inspect diff/results.              | Read diff, run tests, comment.                               | Findings, risks, suggested fixes. |

### Critical design point

**Planning mode must be enforced by capability policy, not only prompt.**

Prompt-only planning fails because the model can still call write tools if those tools are available. For LangGraph this is straightforward: route to a planner node with a read-only tool registry. For Cursor SDK it is harder if first-party edit/shell tools cannot be selectively disabled. In that case, use one of these strategies:

1. Use LangGraph / Stigmer-native code search for Ask/Plan.
2. Use Cursor SDK only after user clicks **Implement**.
3. Use MCP/tool proxying to expose only read-only tools when possible.
4. If using Cursor full agent for Plan, run in a throwaway read-only clone or reject filesystem mutations via sandbox policy.

Windsurf’s model is a good benchmark: Code mode executes, Plan mode explores and presents a Markdown plan, and Ask mode is search-only/read-only. Replit also has Plan mode for brainstorming and ordered task lists before code/data changes. ([Windsurf Docs][19])

## 2.4 Checkpoints / restore

Cursor checkpoints are local snapshots created automatically for Agent changes; Cursor says they are not version control, are stored locally separate from Git, and track Agent changes rather than manual edits. ([Cursor Documentation][6])

The SDK does not appear to expose Cursor IDE checkpoint objects. Stigmer should build its own.

### Recommended checkpoint implementation: hidden Git refs first

Use Git because Stigmer already tracks branches/SHAs and because users understand diffs. Avoid polluting user-visible branch history by using hidden refs.

Checkpoint creation pattern:

```bash
# In the isolated workspace/worktree:
git add -A

tree="$(git write-tree)"
parent="$(git rev-parse HEAD)"

commit="$(
  printf "stigmer checkpoint: session=%s seq=%s\n\n%s\n" "$SESSION_ID" "$SEQ" "$SUMMARY" |
  git commit-tree "$tree" -p "$parent"
)"

git update-ref "refs/stigmer/checkpoints/$SESSION_ID/$SEQ" "$commit"
```

Checkpoint metadata:

```ts
type Checkpoint = {
  id: string;
  sessionId: string;
  runId: string;
  seq: number;
  commitSha: string;
  baseSha: string;
  createdAt: string;
  createdBy: "agent" | "user" | "system";
  reason:
    | "before_first_write"
    | "after_edit_batch"
    | "before_risky_command"
    | "after_tests_passed"
    | "manual";
  fileStats: {
    filesChanged: number;
    insertions: number;
    deletions: number;
  };
  relatedToolCallIds: string[];
  summary: string;
};
```

Restore pattern:

1. Create a safety checkpoint of current state.
2. Show diff from current → target checkpoint.
3. Ask for confirmation if user changes exist.
4. Restore in isolated workspace:

```bash
git reset --hard "$CHECKPOINT_COMMIT"
git clean -fd
```

5. Emit a restore event.
6. Recompute session context summary.

### When to checkpoint

| Moment                           | Why                                  |
| -------------------------------- | ------------------------------------ |
| Before first file write          | Undo “agent went wrong immediately.” |
| Before destructive shell command | Safety.                              |
| After each edit batch            | User can return to meaningful steps. |
| After tests pass                 | Stable restore point.                |
| Before HITL-denied operation     | Preserve reviewed state.             |
| Before applying queued message   | Separate user intents.               |

### Why this can exceed Cursor

Replit’s checkpoint docs describe complete snapshots that can include project files, conversation context, environment config, agent memory, and database contents; rollback restores not only files but context and config. That is a useful north star. ([Replit Docs][20])

Stigmer can go beyond Cursor’s local-only checkpoints by storing:

* Workspace diff.
* Agent event position.
* Summary version.
* Queue state.
* Tool artifacts.
* Test status.
* Browser screenshots.
* Approval history.

## 2.5 Rich tool call rendering

Cursor’s rich UX is mostly a **renderer problem**, not just an SDK problem.

Cursor docs list built-in tools for search, file read/list, codebase search, grep, web, edit/reapply, delete file, terminal, and MCP. MCP tool responses appear in chat with expandable arguments/responses, and MCP can return images as base64. ([Cursor Documentation][7])

The Cursor SDK can stream tool calls and deltas, but the stable public guarantee for every first-party tool schema is weaker than what a web UI needs. Cursor CLI output docs explicitly tell clients to ignore unknown fields and use tool call IDs to correlate starts/completions. ([Cursor Documentation][8])

### Recommended architecture: tool renderer registry

```ts
type ToolRendererAdapter = {
  match(event: NormalizedToolCall): boolean;
  normalize(raw: unknown): NormalizedToolCall;
  enrich?(ctx: EnrichmentContext): Promise<NormalizedToolCall>;

    | "file_diff"
    | "terminal"
    | "search_results"
    | "browser_artifact"

```

Adapters:

| Tool family | Do not rely only on SDK result               | Enrich with                                          |
| ----------- | -------------------------------------------- | ---------------------------------------------------- |
| File edit   | Edit args may not contain full before/after. | Git diff before/after tool call or edit batch.       |
| Terminal    | Result may be partial/large.                 | Streaming stdout/stderr chunks, exit code, duration. |
| Search      | Results may be unstructured.                 | File/line/snippet parser; lazy open.                 |
| Browser     | Screenshot may be artifact/base64.           | Store screenshot/video/console/network logs.         |
| MCP         | Arbitrary JSON/images.                       | Schema inference + generic expandable viewer.        |
| Long output | May be truncated.                            | Artifact file with preview.                          |

### Large result handling

Cursor’s dynamic context discovery writeup says Cursor turns long tool responses into files instead of simply truncating, then lets the agent search those files when needed. Stigmer should copy this pattern. ([Cursor][11])

UX:

* Show first 200 lines or first/last chunks.
* “Open full artifact.”
* “Ask agent about this output.”
* “Pin into context.”
* “Exclude from future context.”

## 2.6 Message queuing and immediate messaging

Cursor docs say users can queue messages while the Agent works; queued messages appear below the active task, can be reordered, and are processed sequentially. The same docs also say `Ctrl+Enter` queues a message, while default sending can append the user message to the most recent user message after a tool call. ([Cursor Documentation][9])

This is subtly different from the common user perception of “Cmd+Enter sends immediately.” Stigmer should make the semantics explicit in its own product.

### Stigmer queue semantics

Use server-side queueing, not client-only queueing.

```ts
type QueueItem = {
  id: string;
  sessionId: string;
  targetRunId?: string;
  authorId: string;
  content: MessageContent[];
  order: number;
  status:
    | "draft"
    | "queued"
    | "eligible_for_delivery"
    | "delivered"
    | "executing"
    | "completed"
    | "canceled"
    | "failed";
  deliveryMode:
    | "after_current_turn"
    | "after_current_tool"
    | "interrupt_if_supported"
    | "cancel_and_restart"
    | "manual_release";
  createdAt: string;
};
```

### Why native queueing is necessary

Cursor cloud/API docs and changelogs indicate support for follow-ups/run-scoped controls, but local Cursor SDK has a confirmed forum issue where `agent.send()` can start fresh context rather than carrying prior conversation state. ([Cursor][10])

So the safe rule is:

| Harness        | Recommended behavior                                                                                                        |
| -------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Cursor cloud   | Use run-scoped follow-up if available; otherwise queue next run.                                                            |
| Cursor local   | Do not assume `agent.send()` during/after stream preserves context. Inject compacted history explicitly until bug is fixed. |
| LangGraph      | Native queue is straightforward: route next item after current graph interrupt/turn.                                        |
| Browser/client | Optimistic queue UI only; backend remains source of truth.                                                                  |

## 2.7 Streaming UX optimization

### Event processing

Normalize all Cursor and LangGraph events into a common model:

```ts
type AgentEvent =
  | { type: "message.delta"; messageId: string; text: string; ts: number }
  | { type: "thinking.delta"; messageId: string; text: string; ts: number }
  | { type: "tool.started"; toolCallId: string; name: string; args: unknown; ts: number }
  | { type: "tool.delta"; toolCallId: string; stream: "stdout" | "stderr" | "json"; chunk: string; ts: number }
  | { type: "tool.completed"; toolCallId: string; result: unknown; exitCode?: number; ts: number }
  | { type: "step.started"; stepId: string; label?: string; ts: number }
  | { type: "step.completed"; stepId: string; ts: number }
  | { type: "token.sample"; input?: number; output?: number; total?: number; ts: number }
  | { type: "checkpoint.created"; checkpointId: string; ts: number }
  | { type: "summary.created"; summaryId: string; ts: number }
  | { type: "approval.requested"; approvalId: string; ts: number }
  | { type: "run.status"; status: RunStatus; ts: number };
```

### React batching

Do not re-render per token. Batch by message/tool ID and flush on animation frame or every 50–100 ms.

```ts
const pending = new Map<string, AgentEvent[]>();

function onIncomingEvent(event: AgentEvent) {
  const key = eventKey(event);
  pending.set(key, [...(pending.get(key) ?? []), event]);
  scheduleFlush();
}

let flushScheduled = false;

function scheduleFlush() {
  if (flushScheduled) return;
  flushScheduled = true;

  requestAnimationFrame(() => {
    const batch = [...pending.values()].flat();
    pending.clear();
    flushScheduled = false;
    sessionStore.apply(batch);
  });
}
```

### Thinking / reasoning display

Use a policy-driven renderer:

| Policy                | UX                                                |
| --------------------- | ------------------------------------------------- |
| Hidden                | Show “Thinking…” spinner only.                    |
| Summarized            | Show collapsible “Reasoning summary.”             |
| Raw provider thinking | Show only if provider terms and org policy allow. |
| Admin/debug           | Show raw deltas behind permission gate.           |

Anthropic’s docs are a reminder that “thinking” is provider-specific and may be summarized/charged differently than visible text, so Stigmer should not treat all thinking streams as equivalent. ([Claude API Docs][18])

### Long-running tool calls

Render progressive state:

* Queued.
* Running.
* Streaming output.
* Waiting for approval.
* Retrying.
* Completed.
* Failed.
* Timed out.
* Canceled.

Cursor SDK/forum bugs around missing tool completion status make it important to synthesize timeouts and fallback state transitions from later events. ([Cursor - Community Forum][21])

## P0 — ship first

### 1. Active summarization + visible “context compacted” card

**Effort:** Medium.

**Implementation path:**

* Add summary trigger.
* Add summary artifact table.
* Add summary card in React timeline.

LangGraph/LangMem already has native patterns for summarizing older messages before the LLM call while keeping full UI history separate. ([LangChain AI][16])

### 2. Rich file diff + terminal renderer

**Why:** Users judge agent quality by what changed and what commands ran.

**Effort:** Low-medium.

**Implementation path:**

* Create tool-call adapter registry.

* Render terminal chunks.
* Store long outputs as artifacts.

Recommended libraries: `react-diff-view` for unified/split diffs, Monaco Diff Editor for editor-like review, xterm.js for terminal rendering, and TanStack Virtual for long timelines/logs. ([npm][22])

### 3. Server-side queued messages

**Why:** Cursor and Windsurf users expect to keep interacting while the agent works.

# 6. Code patterns and libraries

## 6.1 Diff rendering

Use two levels:

| Use case                           | Library                                       |
| ---------------------------------- | --------------------------------------------- |
| Review-style diff cards            | `react-diff-view`                             |
| Editor-grade diff / inline editing | Monaco Diff Editor via `@monaco-editor/react` |
| Very large diffs                   | Virtualized chunks + lazy loading             |

`react-diff-view` supports unified/split Git diffs and large-diff lazy loading; Monaco provides a VS Code-like diff editor experience. ([npm][22])

Pattern:

```tsx
function FileDiffCard({ diff, filePath }: { diff: string; filePath: string }) {
  const files = parseGitDiff(diff);

  return (
    <Card>
      <CardHeader>{filePath}</CardHeader>
      <DiffView files={files} viewType="split" />
    </Card>
  );
}
```

## 6.2 Terminal rendering

Use xterm.js for replayable terminal sessions. xterm.js is the same class of terminal component used by VS Code-like tools and supports addons for fitting, search, serialization, web links, and WebGL acceleration. ([GitHub][24])

Pattern:

```tsx
function TerminalCard({ chunks }: { chunks: TerminalChunk[] }) {
  const ref = useRef<HTMLDivElement>(null);

  useEffect(() => {
    const term = new Terminal({ convertEol: true });
    const fit = new FitAddon();

    term.loadAddon(fit);
    term.open(ref.current!);
    fit.fit();

    for (const chunk of chunks) {
      term.write(chunk.data);
    }

    return () => term.dispose();
  }, [chunks]);

  return <div ref={ref} className="terminal-card" />;
}
```

## 6.3 Virtualized agent timeline

Use TanStack Virtual for long sessions with thousands of tool/log/message rows. It is designed as a headless virtualizer for large scrollable lists. ([TanStack][25])

Pattern:

```tsx
function AgentTimeline({ items }: { items: TimelineItem[] }) {
  const parentRef = useRef<HTMLDivElement>(null);

  const virtualizer = useVirtualizer({
    count: items.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 96,
    overscan: 12,
  });

  return (
    <div ref={parentRef} className="timeline-scroll">
      <div style={{ height: virtualizer.getTotalSize(), position: "relative" }}>
        {virtualizer.getVirtualItems().map((row) => (
          <div
            key={row.key}
            style={{
              position: "absolute",
              transform: `translateY(${row.start}px)`,
              width: "100%",
            }}
          >
            <TimelineRow item={items[row.index]} />
          </div>
        ))}
      </div>
    </div>
  );
}
```

## 6.4 Summarization in LangGraph

LangMem’s `SummarizationNode` is the closest ready-made pattern: it summarizes older messages when a threshold is exceeded, keeps a running summary, and returns summary + recent messages for the next LLM call. ([LangChain AI][16])

Graph shape:

```text
user input
   |
context_manager / summarization_node
   |
planner_or_agent_llm
   |
tool execution
   |
checkpoint/diff/artifact projection
   |
context_manager
   |
next turn
```

## 6.5 Cursor SDK stream normalization

Keep raw event storage separate from projections.

```ts
async function runCursorAgent(run: CursorRun, ctx: IngestContext) {
  for await (const sdkMessage of run.stream()) {
    await rawEventStore.append({
      sessionId: ctx.sessionId,
      runId: ctx.runId,
      harness: "cursor_sdk",
      sourceEventType: sdkMessage.type,
      rawJson: sdkMessage,
      sequence: await nextSequence(ctx.runId),
      eventTime: new Date().toISOString(),
      schemaVersion: 1,
    });

    const events = normalizeCursorMessage(sdkMessage);

    for (const event of events) {
      await normalizedEventStore.append(event);
      await projectors.apply(event);
    }
  }
}
```

## 6.6 Large tool output externalization

```ts
async function maybeExternalizeToolResult(result: ToolResult) {
  const tokenEstimate = estimateTokens(JSON.stringify(result));

  if (tokenEstimate < 4_000) {
    return { inline: result };
  }

  const artifact = await artifactStore.write({
    type: "long_tool_output",
    content: JSON.stringify(result, null, 2),
    preview: makePreview(result),
  });

  return {
    inline: {
      notice: "Large tool output stored as artifact",
      artifactId: artifact.id,
      preview: artifact.preview,
    },
  };
}
```

This mirrors Cursor’s dynamic-context approach of storing long responses as files/artifacts rather than truncating them away. ([Cursor][11])

# 11. What Stigmer can offer beyond Cursor parity

Cursor parity is the floor. Stigmer can differentiate with:

1. **Harness-neutral UX**
   Same timeline whether the execution engine is Cursor SDK, LangGraph, OpenAI Agents, or custom MCP graph.

2. **Auditable enterprise event store**
   Cursor IDE is a productivity surface; Stigmer can be an audit/control plane.

3. **Checkpoint + summary coupling**
   Restore not just files, but model context, queue state, artifacts, and plan state.

4. **Policy-first modes**
   Plan/Ask/Agent backed by real capability enforcement, not just prompts.

5. **Team-level observability**
   Cost, token, error, approval, and quality metrics across agents/projects.

6. **Dynamic context as product primitive**
   Context manifest, searchable artifacts, summary versions, skill/rule materialization.

7. **Cross-run memory with governance**
   Memory extraction is useful only if users can inspect, edit, delete, and scope it.

8. **Queue orchestration across agents**
   Queued messages, child agents, parallel tasks, dependencies, and approval gates.

Replit’s full-state checkpoints, Devin’s session tools/search/summarizer direction, Windsurf’s modes and checkpoints, Cody’s source-aware context, and v0’s version/deployment loop all point to the same emerging standard: users expect agents to be **inspectable, interruptible, reversible, and stateful**. ([Replit Docs][20])

# 12. Final recommendation

Build Stigmer’s Cursor-quality UX around **native Stigmer state**, not Cursor IDE state.

The product architecture should be:

```text
Cursor SDK / LangGraph
  = execution engines

Stigmer Event Store
  = source of truth

Stigmer Context Manager
  = summaries, context budget, dynamic files

Stigmer Mode Policy
  = Ask / Plan / Agent enforcement

Stigmer Checkpoint Service
  = reversible workspace state

Stigmer Artifact Store
  = long outputs, terminal logs, screenshots, videos

Stigmer React Timeline
  = Cursor-quality rendering

Stigmer Observability
  = enterprise-grade agent dashboard
```

The immediate implementation order should be:

1. **Active summarization with visible compacted-context cards.**
2. **Rich tool rendering using native diffs and terminal streaming.**
3. **Server-side queued messages.**
4. **Plan/Ask/Agent modes with enforced policies.**
5. **Git-based checkpoints and restore.**
6. **Context meter and context manifest.**
7. **Dynamic context files / skills / artifact search.**
8. **Browser artifact rendering.**
