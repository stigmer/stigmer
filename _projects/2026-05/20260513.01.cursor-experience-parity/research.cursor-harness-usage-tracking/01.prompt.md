# Deep Research: Usage & Billing Tracking for SDK-Proxied AI Agent Platforms

## Research Objective

We are building **Stigmer**, an AI agent orchestration platform that wraps the **Cursor TypeScript SDK** (`@cursor/sdk`, public beta since April 29, 2026) as one of its execution harnesses. Users create "sessions" in Stigmer that dispatch work to Cursor agents via the SDK. The other execution harness is **LangGraph** (Python), which calls LLM providers (Anthropic, OpenAI) directly.

**The core problem**: Our Planton-based usage dashboard shows $0.00 cost and zero tokens for sessions that use the Cursor harness, even though those sessions clearly performed substantial work. The only usage that appears is from direct Anthropic calls (e.g., subject generation). We need to understand how to properly capture, attribute, and display usage metrics when the LLM calls are proxied through the Cursor SDK rather than made directly.

## Known Information (Starting Points)

### What We Know About Cursor SDK Usage Data

1. **`TurnEndedUpdate` event** — The Cursor SDK's `InteractionUpdate` stream includes a `turn-ended` event with an optional `usage` object:
   ```typescript
   interface TurnEndedUpdate {
     type: "turn-ended";
     usage?: {
       inputTokens: number;
       outputTokens: number;
       cacheReadTokens: number;
       cacheWriteTokens: number;
     };
   }
   ```

2. **`TokenDeltaUpdate` event** — A `token-delta` event with a cumulative `tokens: number` field, emitted during streaming.

3. **Cursor Admin API endpoints** that expose team-level usage:
   - `GET /teams/daily-usage-data` — Daily aggregated metrics (lines added/deleted, requests by type, models used)
   - `POST /teams/spend` — Spending per user with `spendCents`, `overallSpendCents`, `chargedCents`
   - `POST /teams/filtered-usage-events` — Granular per-event data including:
     - `tokenUsage.inputTokens`, `outputTokens`, `cacheWriteTokens`, `cacheReadTokens`, `totalCents`
     - `chargedCents` (model cost + Cursor Token Rate)
     - `cursorTokenFee` (the $0.25/M token Cursor surcharge)
     - `isHeadless` boolean (background/SDK agents)
     - `model`, `kind`, `maxMode`, `isTokenBasedCall`

4. **Cursor billing model**: SDK runs follow the same pricing as IDE runs. $0.25/M token Cursor Token Rate applies. Spend appears in Cursor's dashboard under "SDK" tag.

### Our Current Architecture

- **cursor-runner** (TypeScript, Temporal activity worker) wraps the Cursor SDK. It calls `Agent.create()` / `Agent.resume()` + `agent.send()` and consumes the stream via `run.stream()` and `onDelta`/`onStep` callbacks.
- **agent-runner** (Go, Temporal activity worker) wraps LangGraph. It calls LLM providers directly and receives token usage in the standard LLM response metadata.
- **stigmer-service** (Java) orchestrates sessions/executions via Temporal workflows.
- **Planton** is our infrastructure/billing platform. The usage dashboard (see screenshot context) shows Total Cost, LLM Calls, Tokens, Executions, Agents, Sessions over time. It currently captures usage from direct LLM calls only.

### The Gap

The cursor-runner processes `TurnEndedUpdate.usage` data during streaming but does NOT:
- Persist per-turn token counts to the execution status
- Forward usage data to Planton's metering system
- Aggregate usage across turns within an execution
- Map Cursor's billing data to Stigmer's cost model

For the LangGraph harness, usage tracking works because the agent-runner intercepts LLM response metadata (tokens, cost) directly from provider callbacks and writes them to execution status.

## Specific Areas to Investigate

### 1. SDK-Level Usage Capture Patterns
- What is the best practice for capturing and aggregating token usage from `@cursor/sdk` stream events?
- Is `TurnEndedUpdate.usage` reliable (it's optional — when is it absent)?
- Should we accumulate `TokenDeltaUpdate.tokens` as a fallback or cross-check?
- Are there other SDK events or APIs that expose per-run cost/token data beyond stream events?
- Does `run.wait()` or `RunResult` contain any usage summary?

### 2. Cursor Admin API as a Reconciliation Source
- Can we use the `/teams/filtered-usage-events` endpoint to backfill or reconcile usage for SDK runs?
- How do we correlate a specific Cursor agent/run ID with a Stigmer session/execution for billing reconciliation?
- What is the latency between an SDK run completing and the usage event appearing in the Admin API?
- Is there an `agentId` or `runId` field in usage events that would allow per-execution attribution?

### 3. Dual-Billing Architecture (Cursor + Direct LLM)
- How do other platforms that proxy through Cursor SDK handle the "double accounting" problem (Cursor bills their team, but the platform also needs to bill its own users)?
- What are common patterns for passing through or marking up SDK-proxied costs?
- How should we handle the Cursor Token Rate ($0.25/M) in our own cost model — absorb it, pass it through, or treat it as infrastructure cost?

### 4. LangGraph Usage Tracking for Comparison
- How does LangGraph Python track token usage across a graph execution?
- LangGraph has known issues with `UsageMetadataCallbackHandler` conflicting with streaming (`stream_mode="messages"`) — what are the current workarounds?
- Does LangSmith provide reliable token tracking that LangGraph can't get locally?
- What observability tools (LangWatch, LangSmith, Phoenix) provide the best token/cost tracking for LangGraph?

### 5. Unified Metering Architecture
- What are best practices for building a unified usage/metering system that tracks costs across heterogeneous backends (direct LLM calls vs SDK-proxied calls)?
- How do platforms like Vercel AI SDK, LangChain, or CrewAI handle unified billing when they support multiple providers/runtimes?
- What database schema / event format is recommended for storing per-execution usage data that covers both direct and proxied LLM calls?

## Why This Matters

Our early adopters are seeing $0.00 cost on their Stigmer usage dashboards despite running extensive Cursor-harness sessions. This makes the platform look broken and prevents proper cost attribution. We need a robust solution that works for both Cursor SDK and LangGraph harnesses to maintain user trust and enable proper billing/budgeting.
