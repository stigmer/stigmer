# Usage and Billing Tracking for SDK-Proxied AI Agent Platforms

## Core findings

The most robust answer for Stigmer is a **hybrid metering model**: use the Cursor harness for **real-time, per-execution provisional usage**, and use the Cursor Admin API for **delayed reconciliation against the team bill**. Cursor’s public SDK launch materials make clear that SDK runs are billed with Cursor’s standard token-based consumption model, and the Admin API exposes team-level usage and spend data for custom dashboards. At the same time, the published Admin API schema is oriented around **team usage events** rather than an SDK run ledger, while the public SDK examples focus on streaming run events and `run.wait()`/`getRun()` workflows rather than a documented “final usage summary” object. That combination strongly suggests you should not wait for Cursor’s Admin API before showing usage in Stigmer, but you also should not treat the initial stream alone as your final bill of record. citeturn35search0turn25search1turn30search3turn29search0

That recommendation also fits how other multi-provider AI platforms solve the problem. Vercel AI Gateway, for example, returns a generation identifier immediately and then exposes a later lookup endpoint with authoritative cost and token fields “shortly after” completion; LangSmith similarly supports a split between automatically captured token usage and manually supplied custom costs, then aggregates them at trace, project, and thread level. In other words, the pattern used by mature gateways and observability platforms is **immediate provisional attribution plus later authoritative enrichment**, not a single source that is perfect for both UX and finance. citeturn39search1turn10search0

For Stigmer specifically, the reason the current Planton dashboard shows `$0.00` for Cursor-backed executions is structural, not cosmetic. Your LangGraph harness talks to providers directly and can intercept provider-native token metadata at the model boundary. The Cursor harness does not: it hands work to Cursor’s runtime and billing surface, which is why Cursor documentation describes SDK runs as using the same runtime and pricing model as Cursor’s own agent surfaces. If Planton only meters direct provider callbacks today, Cursor sessions will keep looking “free” until you add a Cursor-specific usage ingestion path. citeturn35search0turn27search1turn25search1

A second important finding is that **run-to-bill correlation is weaker in the Admin API than in the SDK runtime**. Public Cursor examples show SDK/cloud-run identifiers such as `run.id` and `run.agentId`, and the Background Agents API is explicitly keyed by agent IDs like `bc_abc123`. By contrast, the public Admin API schema for filtered usage events documents fields like `timestamp`, `model`, `kind`, `requestsCosts`, `isTokenBasedCall`, `tokenUsage`, `maxMode`, `isFreeBugbot`, and `userEmail`, but it does **not** document any `runId` or `agentId` field. That means the best place to create a durable Stigmer correlation key is **at dispatch time**, inside your own runner, not during later reconciliation. citeturn35search0turn32search2turn30search1turn25search1

## Recommended metering architecture

The cleanest design is to treat usage as an **immutable ledger of per-call or per-turn usage events**, with execution summaries and dashboard totals computed from that ledger.

```text
Stigmer session / execution
        |
        +-----------------------------+
        |                             |
        v                             v
cursor-runner                   agent-runner
(@cursor/sdk)                   (LangGraph + direct providers)
        |                             |
        | stream events               | provider response metadata
        |                             |
        v                             v
Normalised usage event producer
        |
        v
Usage ledger table / event stream
(provisional + reconciled records)
        |
        +-----------------------------+
        |                             |
        v                             v
Execution summary projector     Reconciliation worker
(for dashboards / Planton)      (Cursor Admin API, async)
        |                             |
        +-------------<---------------+
                      enrich / correct
```

In this design, `cursor-runner` emits **provisional usage events** as soon as the Cursor stream yields a turn-level usage signal, while `agent-runner` emits **direct/provider usage events** from LangGraph model responses. Both are normalised into the same schema before they ever reach Planton. A separate reconciliation worker then consults Cursor’s Admin API with a short delay and updates provisional Cursor events into reconciled ones where possible. This keeps dashboards responsive while still giving finance, limits, and invoices a path to authoritative correction. Cursor’s own ecosystem supports both halves of this design: the SDK is explicitly built around streamed run execution and resumable runs, while the Admin API is designed for team usage dashboards and spend tooling. citeturn35search0turn25search1turn30search3

The user-facing billing model should also reflect Cursor’s pricing reality. Cursor’s Team and Enterprise pricing documentation says included and on-demand usage are based on **public API prices plus the Cursor Token Fee**, and that non-Auto agent requests carry a **$0.25 per million token fee** applied to **input, output, and cached tokens**. That means a Stigmer dashboard that shows only “underlying model spend” will understate the real cost of Cursor-backed work. For trust and explainability, the safest product choice is to show either a single “actual billed cost” that already includes Cursor’s surcharge, or a split line item such as **Underlying model cost** + **Cursor platform fee**. Vercel AI Gateway’s published pricing is a useful contrast here: Vercel explicitly advertises zero markup, while Cursor explicitly documents an added token fee for team plans. citeturn27search1turn39search2turn39search0

A good operational rule is:

- **Show provisional usage immediately.**
- **Show cost as estimated until reconciled** if it depends on local rate cards rather than a provider- or gateway-returned billed amount.
- **Promote to authoritative cost** only after either direct provider metadata or a reconciliation source confirms it.

That rule is consistent with how LangSmith and Phoenix model costs: both platforms can compute costs from token data when prices are known, and both also support sending custom costs when the caller already knows the true billable amount. citeturn10search0turn18search0turn22search0

## Concrete implementation patterns

### Cursor stream ingestion

For the Cursor harness, the right primitive is **a per-turn usage record**, not a single execution-level counter. The reportable unit should be “one Cursor turn ended with these token counts”, tagged with the Stigmer execution, tenant, session, and the Cursor run identifiers that are available at dispatch time. Cursor’s public SDK examples show a streamed `run` object plus `run.id` and, for cloud runs, `run.agentId`, which is enough to seed that correlation early. Public CLI output documentation also shows Cursor’s general execution model using stable per-execution `session_id` values and terminal result events, which reinforces the idea that each execution should be treated as a correlated stream rather than as a single opaque output blob. citeturn35search0turn29search0

A good TypeScript pattern in `cursor-runner` looks like this:

```typescript
type UsageProvenance = "provisional" | "reconciled" | "gap";
type UsageSource = "cursor_sdk_stream" | "cursor_admin_api" | "provider_direct";

interface NormalizedUsageEvent {
  eventId: string;
  tenantId: string;
  sessionId: string;
  executionId: string;
  harness: "cursor_sdk" | "langgraph";
  source: UsageSource;
  provenance: UsageProvenance;

  cursorRunId?: string;
  cursorAgentId?: string;

  modelName?: string;
  providerName?: string;

  turnIndex?: number;
  startedAt?: string;
  endedAt: string;
  observedAt: string;

  inputTokens?: number;
  outputTokens?: number;
  cacheReadTokens?: number;
  cacheWriteTokens?: number;
  reasoningTokens?: number;

  inputCostUsd?: number;
  outputCostUsd?: number;
  infraFeeUsd?: number;
  totalCostUsd?: number;

  metadata?: Record<string, unknown>;
}

async function meterCursorRun(run: any, ctx: {
  tenantId: string;
  sessionId: string;
  executionId: string;
  modelName?: string;
}) {
  let turnIndex = 0;

  for await (const event of run.stream()) {
    if (event.type === "token-delta") {
      // UI progress only. Do not settle billing from this.
      await emitProgress({
        executionId: ctx.executionId,
        cursorRunId: run.id,
        streamedTokensCumulative: event.tokens,
        observedAt: new Date().toISOString(),
      });
      continue;
    }

    if (event.type === "turn-ended") {
      const now = new Date().toISOString();

      if (!event.usage) {
        await insertUsageLedger({
          eventId: crypto.randomUUID(),
          tenantId: ctx.tenantId,
          sessionId: ctx.sessionId,
          executionId: ctx.executionId,
          harness: "cursor_sdk",
          source: "cursor_sdk_stream",
          provenance: "gap",
          cursorRunId: run.id,
          cursorAgentId: run.agentId,
          modelName: ctx.modelName,
          turnIndex: turnIndex++,
          endedAt: now,
          observedAt: now,
          metadata: { reason: "turn-ended-without-usage" },
        } satisfies NormalizedUsageEvent);

        continue;
      }

      const usage = event.usage;
      const estimate = estimateCursorCost(ctx.modelName, usage);

      const usageEvent: NormalizedUsageEvent = {
        eventId: crypto.randomUUID(),
        tenantId: ctx.tenantId,
        sessionId: ctx.sessionId,
        executionId: ctx.executionId,
        harness: "cursor_sdk",
        source: "cursor_sdk_stream",
        provenance: "provisional",
        cursorRunId: run.id,
        cursorAgentId: run.agentId,
        modelName: ctx.modelName,
        turnIndex: turnIndex++,
        endedAt: now,
        observedAt: now,
        inputTokens: usage.inputTokens,
        outputTokens: usage.outputTokens,
        cacheReadTokens: usage.cacheReadTokens,
        cacheWriteTokens: usage.cacheWriteTokens,
        inputCostUsd: estimate.inputCostUsd,
        outputCostUsd: estimate.outputCostUsd,
        infraFeeUsd: estimate.infraFeeUsd,
        totalCostUsd: estimate.totalCostUsd,
      };

      await insertUsageLedger(usageEvent);
      await projectExecutionSummary(ctx.executionId);
      await forwardToPlanton(usageEvent);
    }
  }

  // Async reconciliation can happen after completion.
  await enqueueCursorReconciliation({
    executionId: ctx.executionId,
    cursorRunId: run.id,
    cursorAgentId: run.agentId,
    completedAt: new Date().toISOString(),
  });
}
```

The key design decision here is that `token-delta` is used only for **UX progress**, not settlement. That is because it is useful for “tokens so far” displays but does not itself express the billing breakdown Stigmer needs across input, output, and cache classes. By contrast, your turn-end signal already carries the shape you actually need for billing attribution. That separation matches the broader observability guidance in OpenTelemetry and OpenInference: when token counts are streamed, they are excellent for live telemetry, but final usage and cost should be attached to the operation record that represents the completed model interaction. citeturn23search4turn22search0turn22search1

### Reconciliation worker

Cursor’s Admin API should then be treated as a **settlement and audit plane**, not your primary meter. The worker should query `/teams/filtered-usage-events` after a short delay and try to match unreconciled Cursor events using a coarse key such as **service account email**, **time window**, **model**, **token tuple**, and, if available in your observed payloads, any undocumented fields you already see in practice. Public docs only guarantee fields such as `timestamp`, `model`, `kind`, `requestsCosts`, `isTokenBasedCall`, `tokenUsage`, `maxMode`, `isFreeBugbot`, and `userEmail`, so any stronger matching key should be treated as tenant-specific rather than schema-guaranteed. citeturn25search1

A simple matching algorithm is:

```text
Find provisional Cursor events where provenance = provisional
  and reconciled_at is null
  and completed_at < now - 2 minutes

Query Cursor Admin API for the service account / date window

For each usage event returned:
  if userEmail, model, tokenUsage tuple, and time window match exactly once:
      mark ledger row reconciled
      overwrite estimated cost with authoritative cost if available
      store raw admin payload in metadata
  else:
      keep provisional and flag for manual/automatic retry
```

This is also where Stigmer should handle **gaps**. If a `turn-ended` arrives without usage, do not fabricate a billable number from deltas; instead, write a gap record and let reconciliation attempt to fill it later. That protects trust better than silently showing a false exact cost. The absence semantics of `usage` are not publicly documented in the sources I found, so a conservative fallback policy is preferable. citeturn25search1turn35search0

## Cursor and LangGraph comparison

### Cursor

For Cursor, there are three important public surfaces.

The first is the **SDK/runtime surface**. The public SDK announcement shows local and cloud execution via `Agent.create()`, `agent.send()`, streamed run output, `run.id`, `run.agentId`, and resumable `Agent.getRun(...).wait()` flows. This is the surface you own inside `cursor-runner`, and therefore the only place where Stigmer has perfect awareness of which internal session/execution triggered the work. citeturn35search0

The second is the **team-admin surface**. Cursor’s Admin API is meant to “build custom dashboards, monitoring tools, or integrate with existing workflows”, and its filtered usage endpoint documents token usage on a per-event basis when `isTokenBasedCall` is true. That makes it a good reconciliation source. But the public schema is team-oriented: it does not document run IDs or agent IDs, and it requires an org-level admin key. That makes it well suited to back-office reconciliation and finance controls, and poorly suited to instant customer-facing attribution inside a live execution. citeturn25search1

The third is the **pricing surface**. Cursor’s Team pricing documentation says included and on-demand team usage follows public API pricing plus the Cursor Token Fee, and that the fee applies to all non-Auto agent requests across input, output, and cached tokens. Cursor’s SDK launch post also says the SDK is billed on standard token-based consumption pricing. Together, those two sources are enough to justify treating Cursor runs as a real cost centre in Stigmer even when the underlying model call never touches your own Anthropic or OpenAI client libraries directly. citeturn27search1turn35search0

### LangGraph

LangGraph is a different situation because you **do** own the provider boundary. Current LangChain and LangGraph documentation says token usage, when available, is standardised on `AIMessage.usage_metadata`, and LangChain provides `UsageMetadataCallbackHandler` and `get_usage_metadata_callback()` to aggregate usage across chat model calls. The LangGraph Python streaming docs say `stream_mode="messages"` yields `(message_chunk, metadata)` from LLM calls and that the metadata includes `langgraph_node`, with the streaming API still marked “in preview”. citeturn40search2turn40search4turn12search0turn12search3turn17search0

However, the GitHub issue history shows that relying on graph-level streaming for billing has been fragile in some releases. One closed issue shows that `usage_metadata` disappeared from final `AIMessage` objects when `stream_mode=["values", "messages"]` was used; another reports that adding `UsageMetadataCallbackHandler` removed the message-stream handler in a LangGraph 1.0.2 setup; a third shows usage missing when `stream_mode` included `"messages"` in 0.5.3 and 0.6.4. Those reports are version-specific bug evidence, not proof that the current release is still broken, but they are strong evidence that **settlement should happen at the provider/model wrapper boundary, not at the graph stream boundary**. citeturn13view0turn15view0turn15view1

In practice, the LangGraph recommendation is:

- use provider-native usage metadata on the underlying model client whenever possible;
- use `UsageMetadataCallbackHandler` as an aggregator, not as the sole bill-of-record;
- mirror those same counts into LangSmith or OTLP if you want external observability;
- keep `messages` streaming for UX, not for authoritative cost settlement. citeturn40search2turn12search0turn10search0turn17search0

### Observability choices

If you want one observability plane across Java, Go, TypeScript, and Python, **Phoenix/OpenTelemetry/OpenInference** is the cleanest standards-first path. Phoenix computes costs from token counts and model metadata, supports session-, trace-, and project-level cost views, and is built on OpenTelemetry/OpenInference. OpenInference gives you a rich vendor-neutral schema for token counts and costs, while the newer OpenTelemetry GenAI conventions standardise conversation IDs and usage counters. citeturn18search0turn18search2turn18search6turn22search0turn22search1turn23search0

If you want the smoothest LangGraph-native experience, **LangSmith** is stronger. It can automatically record token usage and costs for major providers, accepts custom costs for non-LLM runs, and aggregates spend at trace and project level. It also explicitly notes that thread metadata such as `session_id` or `thread_id` needs to be attached to child runs if you want thread-level cost aggregation to work properly, which maps neatly to Stigmer’s need to aggregate by session and execution. citeturn10search0

**LangWatch** is a viable third option when you want model-cost dashboards and OTEL compatibility, but its own troubleshooting guide effectively confirms the same general lesson: cost goes to zero if spans are missing model identifiers or token metrics. That makes it a useful dashboard layer, but not a substitute for building a proper first-party usage ledger in Stigmer. citeturn19search0turn19search2turn19search3

CrewAI’s published tracing story is also telling: CrewAI emphasises tracing, LLM calls, token usage, and costs in AMP or external observability integrations, rather than presenting a framework-native billing ledger. That again points toward the same architectural norm: frameworks emit traces and usage signals, while applications that need tenant billing usually build a separate normalised metering layer. citeturn21search0

## Approach comparison and risk assessment

| Approach | What it gives you | Latency | Correlation quality | Best use | Main risk |
|---|---|---:|---|---|---|
| SDK events only | Immediate per-execution attribution inside Stigmer | Real-time | High | Live dashboards, budgets, user trust | Cost is estimated unless you have an authoritative billed-cost field |
| Admin API only | Team-level usage and spend aligned to Cursor billing surfaces | Delayed | Medium to low | Finance review, audits, post-hoc correction | Weak per-run attribution; poor UX; rate-limit and performance sensitivity |
| Hybrid | Immediate usage with later correction | Real-time + delayed reconciliation | High overall | Recommended production model | More moving parts; needs idempotent reconciliation logic |

The table above follows directly from the public Cursor surfaces. SDK/cloud examples are stream-first and identifier-rich at the point of execution; the Admin API is team-dashboard-oriented and token-aware but does not publicly document run IDs or agent IDs; community reports also show rate limits and query-performance sensitivity on Admin API usage endpoints. That makes the hybrid approach the most balanced across reliability, latency, and accuracy. citeturn35search0turn25search1turn37search0

The risk profile of each route is different.

**SDK-only** is the best answer for user trust because it eliminates the “$0.00 while work is happening” problem immediately. Its weakness is financial exactness: without a documented authoritative billed-cost field in the SDK examples I found, you are computing a local estimate from model rates and Cursor’s team pricing rules. That is good enough for real-time product UX, but not ideal as the last word for invoices or spend disputes. citeturn35search0turn27search1turn29search0

**Admin-only** is tempting because it is closer to the team bill, but it is the wrong primary source for an interactive product. Cursor’s docs position the Admin API for custom dashboards and team metrics, not for inline per-run settlement; the schema is missing documented run identifiers; and forum reports show endpoint throttling and slow retrieval behaviour for token-heavy data collection. citeturn25search1turn37search0

**Hybrid** requires more engineering, but it is the only option that solves both sides of the problem: it restores real-time credibility for Stigmer users while giving operations and finance a way to reconcile back to Cursor’s team-billed reality. This is also the design that most closely resembles the patterns already used by Vercel AI Gateway, LangSmith, and Phoenix. citeturn39search1turn10search0turn18search0

## Open questions and limitations

Several details remain undocumented in the public material I found, and you should treat them as **implementation unknowns to validate in staging** rather than as guaranteed platform behaviour. citeturn25search1turn35search0

The most important unknown is **when Cursor omits turn-end usage**. Public examples and launch materials demonstrate streamed runs and resumable runs, but I did not find a published specification for the absence semantics of the turn-level usage object. The safe operational posture is therefore to persist a gap marker and reconcile later, rather than to infer a billable total from stream deltas. citeturn35search0turn29search0

The second unknown is **whether your tenant receives richer Admin API fields than the public docs show**. Your starting notes mention fields such as `isHeadless`, `chargedCents`, and `cursorTokenFee`. Those are not present in the public response schema I found for `/teams/filtered-usage-events`, which means they may be undocumented, rollout-specific, or surfaced only in some environments. They are worth using if they are truly present in your payloads, but you should avoid schema-locking around them until you have captured them consistently in production samples. citeturn25search1

The third unknown is **reconciliation latency and SLA**. Vercel explicitly documents that generation lookups are available shortly after completion, but Cursor’s public Admin API docs do not publish an equivalent latency promise for usage-event appearance. Given the reported Admin API throttling and performance sensitivity, you should design reconciliation as an eventually consistent background task rather than as a blocking step in session completion. citeturn39search1turn37search0

The concise implementation recommendation is therefore:

Build a **normalised usage ledger** now; emit **Cursor provisional usage from stream events immediately**; project that into Planton so users stop seeing `$0.00`; then add a **Cursor Admin API reconciliation worker** that upgrades those provisional rows when back-office data appears. For LangGraph, keep **billing at the provider/model boundary** and use LangSmith or OTLP/Phoenix as an observability layer, not as the only source of truth for billing. That architecture is the best fit for the evidence available today and the least risky way to restore user trust quickly without losing financial accuracy later. citeturn25search1turn35search0turn40search2turn10search0turn18search0

# Comprehensive Report: Usage & Billing Tracking for Cursor-SDK-Proxied Agent Runs in Stigmer

## Executive recommendation

Stigmer should implement **hybrid metering**:

1. **Primary real-time metering:** Capture `TurnEndedUpdate.usage` inside `cursor-runner` during every Cursor SDK run, aggregate it per turn/run/execution/session, persist it to execution status, and emit normalized usage events to Planton immediately.

2. **Fallback telemetry:** Track `TokenDeltaUpdate.tokens` only as a diagnostic and “estimated/observed stream tokens” fallback when `turn-ended.usage` is missing. Do **not** use token deltas as final billable usage because they do not give input/output/cache token breakdown.

3. **Financial reconciliation:** Poll Cursor Admin API `/teams/filtered-usage-events` after completion to reconcile SDK-provisional events against Cursor’s eventual billing records. Treat the Admin API as a **settlement/backfill source**, not the source for live dashboard updates.

4. **Unified ledger:** Route Cursor SDK usage, LangGraph direct provider usage, provider Admin API usage, and reconciliation adjustments into the same append-only `usage_event` ledger. Planton should read from that normalized ledger rather than separate provider-specific paths.

The immediate bug is straightforward: **Cursor usage is not entering Stigmer’s usage pipeline at all**. The robust fix is not just “parse one more field”; it is to make Cursor a first-class metered backend whose costs are provisional during execution and settled later.

# 1. What is actually happening in Stigmer today

For LangGraph sessions, `agent-runner` directly observes provider responses or LangChain/LangGraph callback metadata. That means usage metadata enters your execution status and Planton path.

For Cursor sessions, the real LLM calls are hidden behind Cursor. Stigmer sees Cursor SDK stream events, but unless `cursor-runner` converts those events into Stigmer usage records, Planton has no LLM call to meter. From Planton’s perspective, no OpenAI/Anthropic request happened, so it shows `$0.00`, `0 tokens`, and `0 LLM calls`.

That is not a Planton dashboard problem. It is a **metering ingestion boundary problem**.

The fix is to define Cursor SDK as a proxied LLM backend:

```text
Direct LangGraph call:
Stigmer -> Anthropic/OpenAI -> usage metadata -> Stigmer meter

Cursor SDK call:
Stigmer -> Cursor SDK -> Cursor-managed model/provider -> Cursor stream/Admin API -> Stigmer meter
```

The second path requires explicit translation.

# 2. Cursor SDK usage capture

## 2.1 What the SDK appears to expose

The best public, implementation-level type summary I found for the current SDK shape shows:

```ts
interface TokenDeltaUpdate {
  type: "token-delta";
  tokens: number;
}

interface TurnEndedUpdate {
  type: "turn-ended";
  usage?: {
    inputTokens: number;
    outputTokens: number;
    cacheReadTokens: number;
    cacheWriteTokens: number;
  };
}
```

The same source describes `Run` / `RunResult` fields such as `id`, `agentId`, `status`, `result`, `model`, `durationMs`, `git`, `createdAt`, plus methods `stream()`, `wait()`, `cancel()`, and `conversation()`. It does **not** show a usage summary on `RunResult`. It also notes that stream events include `agent_id` and `run_id`, and that low-level interaction updates include `token-delta` and `turn-ended`. ([Zenn][3])

That means the practical SDK-level source of token accounting is the stream callback / interaction update path, not `run.wait()`.

## 2.2 Best practice for Cursor SDK capture

Use `TurnEndedUpdate.usage` as the **primary SDK metering signal**.

Why:

* It has the token categories needed for billing: input, output, cache read, cache write.
* It is turn-scoped, which maps cleanly to a Stigmer execution/session timeline.
* It can be emitted immediately, so dashboards no longer show `$0.00` while work is happening.
* It is closer to actual model billing than `TokenDeltaUpdate.tokens`.

`usage` is optional, so the implementation must not treat absence as zero. An absent usage object should produce a `usage_missing` diagnostic event and trigger reconciliation.

Recommended interpretation:

```text
turn-ended.usage present:
  billable provisional token event

turn-ended.usage absent:
  non-billable diagnostic event
  mark execution usage as incomplete
  attempt Admin API reconciliation

token-delta:
  streaming progress / sanity check only
```

## 2.3 Should `TokenDeltaUpdate.tokens` be accumulated?

Yes, but only as a fallback/cross-check.

Do **not** use token deltas as final billing because the public type only exposes a single cumulative `tokens` number. It does not distinguish input/output/cache tokens, and it is not documented as the authoritative billing unit. Treat it as:

```text
observed_stream_tokens
confidence = low
billable = false
```

Good uses:

* Prove the run was non-empty even if `turn-ended.usage` is missing.
* Alert when `token-delta` is large but `usage` is absent.
* Display “estimated activity” before final usage arrives.
* Detect regressions after SDK upgrades.

Bad uses:

* Customer invoice totals.
* Cursor fee calculation.
* Provider model cost calculation.

## 2.4 Does `run.wait()` or `RunResult` contain usage?

I did not find a reliable public source showing usage on `RunResult`. The visible SDK type summary shows run identity, status, model, duration, result, and git metadata, but no usage field. ([Zenn][3])

Engineering recommendation: **do not depend on `run.wait()` for usage**. Capture usage during streaming, then use `wait()` only for terminal run result/status.

# 3. Cursor Admin API as reconciliation source

## 3.1 What the Admin API exposes

Cursor’s Admin API is intended for team data, usage metrics, and spending. The official docs describe endpoints for daily usage data, monthly team spend, and filtered usage events. `/teams/filtered-usage-events` is documented as a granular source for individual API calls, model usage, token consumption, and costs. ([Cursor Documentation][4])

The documented filtered usage event response includes fields such as:

* `timestamp`
* `model`
* `kind`
* `maxMode`
* `requestsCosts`
* `isTokenBasedCall`
* `tokenUsage.inputTokens`
* `tokenUsage.outputTokens`
* `tokenUsage.cacheWriteTokens`
* `tokenUsage.cacheReadTokens`
* `tokenUsage.totalCents`
* `userEmail`

([Cursor Documentation][4])

The request supports filtering/pagination fields such as `userId`, `email`, `page`, and `pageSize`. ([Cursor Documentation][5])

Your starting notes mention newer/additional fields such as `chargedCents`, `cursorTokenFee`, `isHeadless`, and SDK/headless classification. I would preserve those fields if present in raw payloads, but the public documentation snippet I could verify does **not** show `agentId` or `runId`.

## 3.2 Can it backfill/reconcile SDK runs?

Yes. Use it for:

* Nightly settlement
* Backfill for historical Cursor runs
* Detecting SDK usage capture gaps
* Replacing provisional estimated cost with Cursor-billed cost
* Reconciling Cursor dashboard spend against Stigmer ledger totals

Do **not** use it as the only source for the user-facing dashboard because:

* It is delayed.
* It appears to be team/user/event oriented, not Stigmer execution oriented.
* It does not publicly document `runId`, `agentId`, or custom metadata fields for exact attribution.
* Cursor Admin API docs do not publish a clear event availability latency SLA.

## 3.3 How to correlate Cursor Admin usage to Stigmer executions

Since the public Admin API schema does not show a run ID or agent ID, exact correlation is not guaranteed. Record as much SDK context as possible during execution, then match later.

At Cursor SDK time, persist:

```text
stigmer_org_id
stigmer_workspace_id
stigmer_project_id
stigmer_session_id
stigmer_execution_id
temporal_workflow_id
temporal_activity_id
temporal_attempt
cursor_agent_id
cursor_run_id
cursor_user_email / API key owner
model
run_started_at
run_ended_at
turn_index
turn_started_at
turn_ended_at
turn token counts
```

At reconciliation time, query Cursor usage events filtered by user/email and time window:

```text
event.timestamp between run_started_at - 2 minutes and run_ended_at + 15 minutes
event.userEmail == cursor_user_email
event.model == sdk_model, when available
event.isTokenBasedCall == true
token distance is small
```

Use a scoring function:

```text
score =
  time_distance_weight
+ token_distance_weight
+ model_mismatch_penalty
+ overlapping_runs_penalty
+ kind/headless/sdk_tag_bonus
```

Classify matches:

```text
confidence >= 0.95:
  settle exact execution event

0.70 <= confidence < 0.95:
  settle with warning / admin review flag

confidence < 0.70 or multiple close candidates:
  keep as aggregate team/user reconciliation only
```

Product/SDK request for Cursor:

```text
Please include one of:
- runId in /teams/filtered-usage-events
- agentId in /teams/filtered-usage-events
- client-supplied metadata/tags on Agent.create/send that propagate to usage events
- SDK RunResult.usage and RunResult.cost
```

Without one of those, per-execution settlement will always have an attribution-risk edge case when several SDK runs overlap for the same Cursor team member/model.

## 3.4 Reconciliation latency

I did not find a published Cursor Admin API latency guarantee. For an analogous provider-side usage/cost API, Anthropic states that Admin API usage/cost data typically appears within about five minutes and recommends polling no more than once per minute. ([Claude API Docs][6])

Use that only as a design reference, not as a Cursor guarantee. For Cursor, implement empirical measurement:

```text
on Cursor run end:
  record ended_at

poll after:
  +2 min
  +5 min
  +15 min
  +1 hour
  +24 hours

record:
  first_seen_at
  match_confidence
  settlement_delta
```

After a week of production data, you will know Cursor’s real delay distribution.

# 4. Cursor billing model and cost mapping

Cursor’s pricing policy defines model API fees as total tokens multiplied by model pricing rates, and Cursor token fees as total tokens multiplied by the Cursor Token Rate. ([Cursor][7]) Cursor team pricing documentation states that non-Auto agent requests include a `$0.25 / 1M token` Cursor fee and that it applies to input, output, and cached tokens. ([Cursor Documentation][8]) A Cursor community answer adds that fee applicability can vary by plan and Auto/non-Auto model usage, so Stigmer should make fee rules plan/config driven rather than hard-coded globally. ([Cursor - Community Forum][9])

## 4.1 Provisional cost formula

For a Cursor SDK turn:

```ts
const totalCursorTokens =
  inputTokens +
  outputTokens +
  cacheReadTokens +
  cacheWriteTokens;

const modelCostUsd =
  (inputTokens / 1_000_000) * rate.inputPerMTokUsd +
  (outputTokens / 1_000_000) * rate.outputPerMTokUsd +
  (cacheReadTokens / 1_000_000) * rate.cacheReadPerMTokUsd +
  (cacheWriteTokens / 1_000_000) * rate.cacheWritePerMTokUsd;

const cursorTokenFeeUsd =
  cursorTokenFeeApplies
    ? (totalCursorTokens / 1_000_000) * 0.25
    : 0;

const upstreamCostUsd = modelCostUsd + cursorTokenFeeUsd;

const stigmerChargeUsd =
  upstreamCostUsd +
  platformMarkupUsd +
  orchestrationFeeUsd;
```

Important: This is only provisional unless Cursor returns authoritative `totalCents`, `chargedCents`, or equivalent in Admin API.

## 4.2 How to present this to users

Recommended dashboard labels:

```text
Current run:
  Estimated Cursor harness cost: $X.XX
  Tokens: N input, N output, N cache read, N cache write
  Status: estimated

After reconciliation:
  Final Cursor harness cost: $Y.YY
  Settlement delta: +$Z.ZZ / -$Z.ZZ
  Status: settled
```

For admins/export:

```text

  Cursor-managed model cost
  Cursor token fee
  Stigmer orchestration/platform fee
  Total charge
```

For regular users, keep it simpler:

```text

LangGraph/provider cost
Stigmer platform cost
Total
```

## 4.3 Absorb or pass through Cursor Token Rate?

Recommendation: **pass it through as part of Cursor harness cost**, at least initially.

Reasons:

* It is a real upstream cost of using the Cursor harness.
* Absorbing it hides margin risk from heavy users.
* It varies with token volume, so it should participate in budgets.
* It is easier to discount later than to introduce later.

Product framing:

```text
“Cursor harness usage is billed based on Cursor-managed model usage plus Cursor’s token processing fee. Stigmer displays this as a single Cursor harness cost, with detailed export available to admins.”
```

# 5. Dual-billing architecture: avoiding double counting

The key is to distinguish **who makes the provider call** from **who bills the Stigmer customer**.

For LangGraph:

```text
backend = langgraph
vendor = anthropic/openai
provider_invoice_owner = Stigmer or customer BYOK
usage_source = provider_response / callback
```

For Cursor:

```text
backend = cursor_sdk
vendor = cursor
underlying_model_provider = cursor_managed
provider_invoice_owner = Stigmer Cursor team
usage_source = cursor_sdk_stream + cursor_admin_api
```

Do **not** try to book Cursor SDK usage as OpenAI/Anthropic usage unless Cursor explicitly exposes the underlying provider and billing unit. From Stigmer’s ledger perspective, Cursor is the upstream vendor.

This also matches the broader AI spend-management pattern: unified AI cost tools increasingly normalize spend across direct API providers and AI SaaS platforms, with tagging by team/customer/feature and reconciliation against provider billing sources. ([zelaros.com][10])

# 6. LangGraph usage tracking comparison

## 6.1 Local usage capture

LangChain provides `UsageMetadataCallbackHandler`, which tracks `AIMessage.usage_metadata` across model calls and can aggregate usage by model, including input/output totals and token details such as cache reads and reasoning tokens where available. ([LangChain Reference Docs][11])

LangGraph streaming supports several stream modes, including `messages`, which emits token-by-token message chunks with metadata, and `updates`, which emits node-level state updates. ([LangChain Docs][12])

## 6.2 Known streaming issue

There are known community and GitHub reports around token usage not being included as expected when `stream_mode` includes `messages`. One LangGraph issue specifically reports usage metadata being present for `stream_mode=["updates"]` but missing when `stream_mode=["updates", "messages"]`. ([GitHub][13]) There are also community questions about combining `UsageMetadataCallbackHandler` with LangGraph streaming. ([LangChain Forum][14])

## 6.3 Recommended LangGraph pattern

Use a two-layer approach:

1. **Primary local usage:** provider response metadata / LangChain usage metadata callback / custom `on_llm_end` callback.
2. **Trace reconciliation:** LangSmith, Langfuse, Phoenix, or provider Admin APIs.

LangSmith’s current cost tracking supports automatic token/cost tracking for major providers and custom cost data for other components. It recognizes fields such as `input_tokens`, `output_tokens`, `total_tokens`, token details, and explicit cost fields, with provider/model metadata used for price-map lookup. ([LangChain Docs][15]) LangChain’s changelog also describes unified cost tracking across LLMs, tools, retrieval, automatic cost derivation, manual cost inputs, and custom price maps. ([changelog.langchain.com][16])

For direct providers, Anthropic’s Messages API responses expose usage fields such as input and output tokens, while Anthropic’s Admin Usage and Cost API provides historical reconciliation with filtering by API key, workspace, and model. ([Claude API Docs][17]) OpenAI Responses usage includes input/output tokens, cached token details, reasoning token details, and total tokens; OpenAI also provides Usage and Costs APIs for dashboard/export-style reconciliation. ([OpenAI Platform][18])

Billing systems need auditability. A Cursor SDK event may be provisional, then later an Admin API event settles it. Do not overwrite the original event. Add a settlement event or update only a materialized aggregate with a pointer to both records.


## 7.4 Align with OpenTelemetry GenAI conventions

Recommendation:

* Use OpenTelemetry spans/metrics for observability.
* Use the Stigmer usage ledger for billing.
* Keep field names compatible where possible.

Also note that observability systems such as Langfuse and Phoenix already support normalized token/cost tracking with cache-read/cache-write/reasoning details, custom model pricing, and rollups to trace/session/project. ([langfuse.com][20]) LangWatch similarly calculates cost from captured model names and prompt/completion tokens or estimates, with explicit model-cost configuration. ([langwatch.ai][21])

# 8. Concrete implementation recommendations

## 8.1 Immediate Cursor SDK instrumentation

Add a `CursorUsageAccumulator` in `cursor-runner`.

```ts
type CursorTurnUsage = {
  inputTokens: number;
  outputTokens: number;
  cacheReadTokens: number;
  cacheWriteTokens: number;
};

type CursorUsageTotals = {
  inputTokens: number;
  outputTokens: number;
  cacheReadTokens: number;
  cacheWriteTokens: number;
  observedStreamTokens?: number;
  turnsWithUsage: number;
  turnsMissingUsage: number;
};

function emptyCursorUsageTotals(): CursorUsageTotals {
  return {
    inputTokens: 0,
    outputTokens: 0,
    cacheReadTokens: 0,
    cacheWriteTokens: 0,
    turnsWithUsage: 0,
    turnsMissingUsage: 0,
  };
}

function addCursorTurnUsage(
  totals: CursorUsageTotals,
  usage: CursorTurnUsage,
): CursorUsageTotals {
  return {
    ...totals,
    inputTokens: totals.inputTokens + usage.inputTokens,
    outputTokens: totals.outputTokens + usage.outputTokens,
    cacheReadTokens: totals.cacheReadTokens + usage.cacheReadTokens,
    cacheWriteTokens: totals.cacheWriteTokens + usage.cacheWriteTokens,
    turnsWithUsage: totals.turnsWithUsage + 1,
  };
}
```

Then instrument `agent.send`.

```ts
type MeteringClient = {
  emitUsageEvent(event: Record<string, unknown>): Promise<void>;
};

type ExecutionContext = {
  orgId: string;
  workspaceId: string;
  sessionId: string;
  executionId: string;
  userId: string;
  userEmail?: string;
  model?: string;
  temporalWorkflowId: string;
  temporalActivityId: string;
  temporalAttempt: number;
};

async function executeCursorMessage(params: {
  ctx: ExecutionContext;
  agent: any;
  message: string;
  metering: MeteringClient;
  executionStatus: {
    patchUsage(usage: CursorUsageTotals): Promise<void>;
    patchDiagnostics(diagnostics: Record<string, unknown>): Promise<void>;
  };
}) {
  const { ctx, agent, message, metering, executionStatus } = params;

  let cursorRunId: string | undefined;
  let cursorAgentId: string | undefined;
  let turnIndex = 0;
  let lastObservedStreamTokens: number | undefined;
  let totals = emptyCursorUsageTotals();

  const emitted = new Set<string>();
  const pendingEvents: Array<() => Promise<void>> = [];

  const emitOrBuffer = async (fn: () => Promise<void>) => {
    if (cursorRunId) {
      await fn();
    } else {
      pendingEvents.push(fn);
    }
  };

  const run = await agent.send(message, {
    onDelta: async (delta: any) => {
      const update = delta.update ?? delta;

      if (update.type === "token-delta") {
        lastObservedStreamTokens = update.tokens;
        totals.observedStreamTokens = update.tokens;

        await executionStatus.patchDiagnostics({
          cursorObservedStreamTokens: update.tokens,
        });

        return;
      }

      if (update.type !== "turn-ended") {
        return;
      }

      const currentTurnIndex = turnIndex++;
      const usage = update.usage as CursorTurnUsage | undefined;

      await emitOrBuffer(async () => {
        const key = [
          "cursor",
          ctx.executionId,
          cursorRunId ?? "unknown-run",
          currentTurnIndex,
        ].join(":");

        if (emitted.has(key)) return;
        emitted.add(key);

        if (!usage) {
          totals = {
            ...totals,
            turnsMissingUsage: totals.turnsMissingUsage + 1,
          };

          await executionStatus.patchUsage(totals);

          await metering.emitUsageEvent({
            schemaVersion: "usage_event.v1",
            idempotencyKey: key,
            orgId: ctx.orgId,
            workspaceId: ctx.workspaceId,
            sessionId: ctx.sessionId,
            executionId: ctx.executionId,
            userId: ctx.userId,
            userEmail: ctx.userEmail,

            temporalWorkflowId: ctx.temporalWorkflowId,
            temporalActivityId: ctx.temporalActivityId,
            temporalAttempt: ctx.temporalAttempt,

            harness: "cursor_sdk",
            source: "cursor_sdk_turn_ended",
            status: "missing_usage",
            upstreamVendor: "cursor",
            providerInvoiceOwner: "cursor_team",
            isProxied: true,

            model: ctx.model,
            cursorAgentId,
            cursorRunId,
            turnIndex: currentTurnIndex,

            tokens: {
              observedStream: lastObservedStreamTokens,
            },

            cost: {
              currency: "USD",
              pricingVersion: "cursor-2026-05",
              confidence: "low",
            },

            missingUsage: true,
            observedAt: new Date().toISOString(),
          });

          return;
        }

        totals = addCursorTurnUsage(totals, usage);
        totals.observedStreamTokens = lastObservedStreamTokens;

        await executionStatus.patchUsage(totals);

        await metering.emitUsageEvent({
          schemaVersion: "usage_event.v1",
          idempotencyKey: key,
          orgId: ctx.orgId,
          workspaceId: ctx.workspaceId,
          sessionId: ctx.sessionId,
          executionId: ctx.executionId,
          userId: ctx.userId,
          userEmail: ctx.userEmail,

          temporalWorkflowId: ctx.temporalWorkflowId,
          temporalActivityId: ctx.temporalActivityId,
          temporalAttempt: ctx.temporalAttempt,

          harness: "cursor_sdk",
          source: "cursor_sdk_turn_ended",
          status: "provisional",
          upstreamVendor: "cursor",
          providerInvoiceOwner: "cursor_team",
          isProxied: true,

          model: ctx.model,
          cursorAgentId,
          cursorRunId,
          turnIndex: currentTurnIndex,

          tokens: {
            input: usage.inputTokens,
            output: usage.outputTokens,
            cacheRead: usage.cacheReadTokens,
            cacheWrite: usage.cacheWriteTokens,
            total:
              usage.inputTokens +
              usage.outputTokens +
              usage.cacheReadTokens +
              usage.cacheWriteTokens,
            observedStream: lastObservedStreamTokens,
          },

          cost: {
            currency: "USD",
            pricingVersion: "cursor-2026-05",
            confidence: "medium",
          },

          observedAt: new Date().toISOString(),
          rawPayloadRedacted: true,
        });
      });
    },
  });

  cursorRunId = run.id;
  cursorAgentId = run.agentId;

  for (const flush of pendingEvents.splice(0)) {
    await flush();
  }

  for await (const event of run.stream()) {
    // Existing UI/message streaming stays here.
    // Do not rely on this path alone for billing unless usage events appear here too.
  }

  const result = await run.wait();

  await executionStatus.patchUsage(totals);

  return {
    result,
    usage: totals,
    cursorRunId,
    cursorAgentId,
  };
}
```

Implementation notes:

* The callback buffers usage events until `run.id` is available.
* The idempotency key includes execution ID, Cursor run ID, and turn index.
* Missing usage emits a real diagnostic record.
* Execution status is patched as usage arrives.
* Planton receives usage immediately.

## 8.2 Provisional cost calculator

```ts
type RateCard = {
  provider: "cursor";
  model: string;
  effectiveFrom: string;
  inputPerMTokUsd: number;
  outputPerMTokUsd: number;
  cacheReadPerMTokUsd: number;
  cacheWritePerMTokUsd: number;
  cursorTokenFeePerMTokUsd: number;
  cursorTokenFeeApplies: boolean;
};

function calculateCursorProvisionalCost(args: {
  usage: {
    input: number;
    output: number;
    cacheRead: number;
    cacheWrite: number;
  };
  rate: RateCard;
  platformMarkupPct?: number;
}) {
  const { usage, rate } = args;

  const modelCostUsd =
    (usage.input / 1_000_000) * rate.inputPerMTokUsd +
    (usage.output / 1_000_000) * rate.outputPerMTokUsd +
    (usage.cacheRead / 1_000_000) * rate.cacheReadPerMTokUsd +
    (usage.cacheWrite / 1_000_000) * rate.cacheWritePerMTokUsd;

  const totalTokens =
    usage.input + usage.output + usage.cacheRead + usage.cacheWrite;

  const proxyFeeUsd = rate.cursorTokenFeeApplies
    ? (totalTokens / 1_000_000) * rate.cursorTokenFeePerMTokUsd
    : 0;

  const upstreamCostUsd = modelCostUsd + proxyFeeUsd;
  const platformFeeUsd =
    upstreamCostUsd * ((args.platformMarkupPct ?? 0) / 100);

  return {
    modelCostUsd,
    proxyFeeUsd,
    platformFeeUsd,
    totalCostUsd: upstreamCostUsd + platformFeeUsd,
  };
}
```

## 8.3 Cursor Admin API reconciliation job

```ts

async function reconcileCursorUsageWindow(args: {
  cursorAdminClient: {
    filteredUsageEvents(input: {
      email?: string;
      startDate: string;
      endDate: string;
      page: number;
      pageSize: number;
    }): Promise<{ usageEvents: CursorUsageEvent[]; totalPages?: number }>;
  };
  ledger: {
    findCursorProvisionalCandidates(input: {
      userEmail?: string;
      model?: string;
      timestamp: string;
      windowMinutes: number;
    }): Promise<any[]>;
    settleUsageEvent(input: {
      provisionalEventId: string;
      adminEvent: CursorUsageEvent;
      matchConfidence: number;
      settlementCostUsd?: number;
    }): Promise<void>;
    recordUnmatchedAdminEvent(event: CursorUsageEvent): Promise<void>;
  };
  startDate: string;
  endDate: string;
  email?: string;
}) {
  const pageSize = 100;
  let page = 1;

  while (true) {
    const response = await args.cursorAdminClient.filteredUsageEvents({
      email: args.email,
      startDate: args.startDate,
      endDate: args.endDate,
      page,
      pageSize,
    });

    for (const adminEvent of response.usageEvents ?? []) {
      if (!adminEvent.isTokenBasedCall || !adminEvent.tokenUsage) {
        continue;
      }

      const candidates = await args.ledger.findCursorProvisionalCandidates({
        userEmail: adminEvent.userEmail,
        model: adminEvent.model,
        timestamp: adminEvent.timestamp,
        windowMinutes: 20,
      });

      const scored = candidates
        .map((candidate) => ({
          candidate,
          confidence: scoreCursorMatch(candidate, adminEvent),
        }))
        .sort((a, b) => b.confidence - a.confidence);

      const best = scored[0];

      if (!best || best.confidence < 0.7) {
        await args.ledger.recordUnmatchedAdminEvent(adminEvent);
        continue;
      }

      if (best.confidence >= 0.95) {
        await args.ledger.settleUsageEvent({
          provisionalEventId: best.candidate.id,
          adminEvent,
          matchConfidence: best.confidence,
          settlementCostUsd: centsToUsd(
            adminEvent.chargedCents ??
              adminEvent.tokenUsage.totalCents ??
              undefined,
          ),
        });
      } else {
        await args.ledger.settleUsageEvent({
          provisionalEventId: best.candidate.id,
          adminEvent,
          matchConfidence: best.confidence,
          settlementCostUsd: centsToUsd(
            adminEvent.chargedCents ??
              adminEvent.tokenUsage.totalCents ??
              undefined,
          ),
        });
      }
    }

    if (response.totalPages && page >= response.totalPages) break;
    if (!response.usageEvents || response.usageEvents.length < pageSize) break;

    page += 1;
  }
}

function scoreCursorMatch(candidate: any, adminEvent: CursorUsageEvent): number {
  let score = 1.0;

  if (candidate.model && adminEvent.model && candidate.model !== adminEvent.model) {
    score -= 0.25;
  }

  const candidateTokens =
    (candidate.tokens?.input ?? 0) +
    (candidate.tokens?.output ?? 0) +
    (candidate.tokens?.cacheRead ?? 0) +
    (candidate.tokens?.cacheWrite ?? 0);

  const adminTokens =
    (adminEvent.tokenUsage?.inputTokens ?? 0) +
    (adminEvent.tokenUsage?.outputTokens ?? 0) +
    (adminEvent.tokenUsage?.cacheReadTokens ?? 0) +
    (adminEvent.tokenUsage?.cacheWriteTokens ?? 0);

  if (candidateTokens > 0 && adminTokens > 0) {
    const delta = Math.abs(candidateTokens - adminTokens);
    const ratio = delta / Math.max(candidateTokens, adminTokens);
    score -= Math.min(0.4, ratio);
  }

  const candidateTime = new Date(candidate.eventEndedAt ?? candidate.observedAt).getTime();
  const adminTime = new Date(adminEvent.timestamp).getTime();
  const minutes = Math.abs(candidateTime - adminTime) / 60_000;

  score -= Math.min(0.3, minutes / 60);

  return Math.max(0, score);
}

function centsToUsd(cents?: number): number | undefined {
  return typeof cents === "number" ? cents / 100 : undefined;
}
```

## 8.4 LangGraph callback implementation

Use a custom callback that emits one normalized event per LLM call, and keep `UsageMetadataCallbackHandler` as an aggregate sanity check.

```py
from uuid import UUID
from typing import Any, Dict, Optional
from langchain_core.callbacks import BaseCallbackHandler
from langchain_core.outputs import LLMResult

class StigmerMeteringCallback(BaseCallbackHandler):
    def __init__(self, metering_client, context: Dict[str, Any]):
        self.metering_client = metering_client
        self.context = context
        self.call_index = 0

    def on_llm_end(
        self,
        response: LLMResult,
        *,
        run_id: UUID,
        parent_run_id: Optional[UUID] = None,
        **kwargs: Any,
    ) -> None:
        self.call_index += 1

        usage = None
        model = None

        if response.llm_output:
            usage = response.llm_output.get("token_usage") or response.llm_output.get("usage")
            model = response.llm_output.get("model_name") or response.llm_output.get("model")

        # Some chat models attach usage_metadata to the AIMessage.
        for generations in response.generations:
            for generation in generations:
                message = getattr(generation, "message", None)
                if message is not None:
                    usage = usage or getattr(message, "usage_metadata", None)
                    response_metadata = getattr(message, "response_metadata", None) or {}
                    model = model or response_metadata.get("model_name") or response_metadata.get("model")

        if not usage:
            self.metering_client.emit_usage_event({
                "schemaVersion": "usage_event.v1",
                "idempotencyKey": f"langgraph:{self.context['execution_id']}:{run_id}",
                "orgId": self.context["org_id"],
                "sessionId": self.context["session_id"],
                "executionId": self.context["execution_id"],
                "harness": "langgraph",
                "source": "langgraph_callback",
                "status": "missing_usage",
                "upstreamVendor": self.context.get("provider", "unknown"),
                "isProxied": False,
                "providerRequestId": str(run_id),
                "llmCallIndex": self.call_index,
                "missingUsage": True,
            })
            return

        input_tokens = (
            usage.get("input_tokens")
            or usage.get("prompt_tokens")
            or usage.get("inputTokens")
            or 0
        )
        output_tokens = (
            usage.get("output_tokens")
            or usage.get("completion_tokens")
            or usage.get("outputTokens")
            or 0
        )
        total_tokens = (
            usage.get("total_tokens")
            or usage.get("totalTokens")
            or input_tokens + output_tokens
        )

        self.metering_client.emit_usage_event({
            "schemaVersion": "usage_event.v1",
            "idempotencyKey": f"langgraph:{self.context['execution_id']}:{run_id}",
            "orgId": self.context["org_id"],
            "workspaceId": self.context.get("workspace_id"),
            "sessionId": self.context["session_id"],
            "executionId": self.context["execution_id"],
            "userId": self.context.get("user_id"),

            "harness": "langgraph",
            "source": "langgraph_callback",
            "status": "provisional",
            "upstreamVendor": self.context.get("provider", "unknown"),
            "providerInvoiceOwner": self.context.get("provider_invoice_owner", "stigmer"),
            "isProxied": False,

            "model": model,
            "providerRequestId": str(run_id),
            "llmCallIndex": self.call_index,

            "tokens": {
                "input": input_tokens,
                "output": output_tokens,
                "total": total_tokens,
                "cacheRead": (
                    usage.get("input_token_details", {}).get("cache_read")
                    if isinstance(usage.get("input_token_details"), dict)
                    else None
                ),
                "reasoning": (
                    usage.get("output_token_details", {}).get("reasoning")
                    if isinstance(usage.get("output_token_details"), dict)
                    else None
                ),
            },

            "cost": {
                "currency": "USD",
                "pricingVersion": self.context.get("pricing_version", "default"),
                "confidence": "medium",
            },
        })
```

# 10. Risk assessment and mitigations

| Risk                                            | Severity | Where it appears      | Why it matters                                               | Mitigation                                                                            |
| ----------------------------------------------- | -------: | --------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| `TurnEndedUpdate.usage` absent                  |     High | Cursor SDK            | Missing token/cost for run                                   | Emit `missing_usage`, track `token-delta`, reconcile Admin API, alert                 |

| Cursor Admin API latency unknown                |   Medium | Reconciliation        | Dashboard may stay provisional longer                        | Poll with backoff, measure `first_seen_at`, show estimated/settled status             |
| Cursor pricing changes                          |     High | Cost model            | Incorrect customer charges                                   | Versioned rate card by effective date; settle with Admin API actuals                  |
| Cursor Token Fee plan differences               |   Medium | Cost model            | Overcharging/undercharging                                   | Make fee rules plan/model configurable; reconcile against Cursor charges              |
| Duplicate Temporal retries                      |     High | All harnesses         | Double billing                                               | Idempotency key per execution/run/turn/call                                           |
| Direct/proxied double counting                  |     High | Unified billing       | Inflated costs                                               | `harness`, `upstreamVendor`, `isProxied`, `providerInvoiceOwner` fields               |
| LangGraph streaming callback gaps               |   Medium | LangGraph             | Direct runs may miss usage                                   | Use `on_llm_end`, provider response metadata, LangSmith/provider Admin reconciliation |
| Raw payload privacy                             |     High | Ledger storage        | Tool args/prompts may contain secrets                        | Store redacted raw payloads or object refs; avoid prompt bodies in billing DB         |

| Provider dashboard vs invoice mismatch          |   Medium | Finance               | Usage endpoint may not equal invoice                         | Use provider Costs/Billing endpoints for settlement when available                    |

# 11. Backfill plan for existing `$0.00` Cursor sessions

## 11.1 What can be recovered

For past Cursor runs where Stigmer did **not** persist `turn-ended.usage`, you may still recover approximate/settled cost from Cursor Admin API, but per-execution attribution depends on overlap.

Use available Stigmer records:

```text
session_id
execution_id
started_at
ended_at
runner_id
user_id
Cursor user/API key owner
model, if stored
agent_id/run_id, if stored
```

Then query Cursor Admin API by user/email and time window. Match usage events into buckets:

```text
exact match:
  one Stigmer execution overlaps one Cursor usage event

probable match:
  several events, but one close token/time/model match

ambiguous:
  multiple concurrent Stigmer executions for same Cursor user/model

unmatched:
  Cursor usage exists but no Stigmer session window
```

For ambiguous cases, do not invent precision. Attribute to user/day/team aggregate and mark execution-level cost as “unattributed Cursor usage”.

## 11.2 Backfill algorithm

```text
for each historical Cursor execution with zero usage:
  window = [started_at - 5m, ended_at + 30m]
  events = Cursor Admin API filtered by user/email/window
  candidates = events where isTokenBasedCall == true
  score candidates by overlap/model/token hints
  if exactly one high-confidence match:
     create settled usage_event linked to execution
  elif multiple medium-confidence matches:
     create provisional allocation with confidence flag
  else:
     create org/user/day aggregate usage only
```

# 14. Answers to your specific investigation questions

## SDK-level usage capture patterns

Use `TurnEndedUpdate.usage` from `onDelta` / interaction updates as the source for provisional token usage. Aggregate per turn, persist per execution, and emit to Planton immediately.

`usage` is optional, so absence should be treated as “unknown”, not zero. Public sources confirm the optional shape but do not document every absence condition. ([Zenn][3])

Use `TokenDeltaUpdate.tokens` only for progress, diagnostics, and missing-usage detection.

I did not find a public `RunResult.usage` field. Treat `run.wait()` as terminal status/result, not metering.

## Cursor Admin API reconciliation

Yes, use `/teams/filtered-usage-events` for backfill and reconciliation. Official docs describe it as granular usage event data with token usage and cost fields. ([Cursor Documentation][4])

I did not find a documented `agentId` or `runId` in the public Admin API response. Use time/email/model/token matching and ask Cursor for metadata propagation.

No Cursor latency SLA was found. Implement empirical polling and track first-seen latency.

## Dual billing

Do not double count underlying LLM providers for Cursor runs. For Stigmer, Cursor is the upstream vendor. Bill customers based on Cursor harness cost plus Stigmer fee. Pass through the Cursor Token Rate as part of Cursor harness COGS unless you intentionally bundle it.

## LangGraph usage tracking

Continue local capture through provider metadata / LangChain callbacks, but harden streaming edge cases. Use LangSmith/Langfuse/Phoenix/provider Admin APIs for reconciliation and observability. LangSmith supports automatic and custom cost tracking, while Phoenix/Langfuse support custom price maps and token categories. ([LangChain Docs][15])

## Unified metering

Create a single normalized usage ledger across all harnesses. Use SDK/provider callbacks for real-time provisional events and Admin APIs for settlement. Use OpenTelemetry GenAI conventions for observability fields, but keep a billing-specific append-only ledger for financial correctness. ([OpenTelemetry][19])
