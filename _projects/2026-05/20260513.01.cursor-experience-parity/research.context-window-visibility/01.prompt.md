# Deep Research: Context Window Visibility for AI Agent Orchestration Platforms

## Research Objective

We are building **Stigmer**, an AI agent orchestration platform that supports two execution harnesses: **Cursor SDK** (`@cursor/sdk`) and **LangGraph** (Python). Our early adopters are requesting context window visibility similar to what the Cursor IDE provides natively — specifically the circular gauge that shows context consumption broken down by category (System Prompt, Tools, Rules, Skills, MCP, Subagents, Conversation).

**The core problem**: Users can see in Cursor IDE exactly how much of the context window is consumed and by what (rules, tools, conversation history, etc.), but when using Stigmer's interface they have no visibility into context window state. We need to understand how to extract, calculate, and display this information for both the Cursor SDK harness and the LangGraph harness.

## Known Information (Starting Points)

### How Cursor IDE Shows Context

1. **Context gauge** — A circular visualization in the prompt input area showing percentage of context window used (e.g., "10% Full", "~104.7K / 1M Tokens").
2. **Category breakdown** — Context consumption is split into:
   - System prompt (e.g., 3.3K tokens)
   - Tools (e.g., 16.3K tokens)
   - Rules (e.g., 1.8K tokens)
   - Skills (e.g., 1.2K tokens)
   - MCP (e.g., 2.8K tokens)
   - Subagents (e.g., 731 tokens)
   - Conversation (e.g., 78.4K tokens)
3. **Model context window** — Most models operate with ~200K token context windows; Cursor shows the max and current.
4. **Cursor 3.3** introduced "Context Telemetry" specifically to help users diagnose why agents ignore instructions or hallucinate during long sessions.

### Cursor's Context Management Techniques

1. **Dynamic context discovery** — Instead of static context, Cursor pulls context on-demand:
   - Long tool responses are written to files instead of truncated
   - Chat history is referenced as files during summarization
   - MCP tool descriptions are synced to folders (46.9% token reduction in A/B tests)
   - Terminal sessions are treated as files
2. **Self-summarization** — When context window fills, Cursor's Composer model generates a condensed summary:
   - Trained via reinforcement learning with "compaction-in-the-loop"
   - Uses ~1,000 tokens for summary vs ~5,000 for prompted summarization
   - Chat history available as files for recovery of lost details
   - Structured format: user goal, what was implemented, errors/fixes, next steps

### Cursor SDK Available Data

From the `@cursor/sdk` streaming events:
- **`TokenDeltaUpdate`**: `{ type: "token-delta", tokens: number }` — cumulative token count per delta
- **`TurnEndedUpdate`**: `{ type: "turn-ended", usage?: { inputTokens, outputTokens, cacheReadTokens, cacheWriteTokens } }` — per-turn aggregate
- **`SDKMessage` events**: `assistant`, `tool_call`, `thinking`, `system`, `user`, `status`, `task`, `request` — message-level events
- **`onDelta` callbacks**: `text-delta`, `thinking-delta`, `tool-call-started`, `tool-call-completed`, `step-started`, `step-completed`
- **No explicit "context window state" API** — The SDK does not appear to expose the context breakdown that the IDE shows.

### LangGraph Context Tracking

- **Known issues**: `UsageMetadataCallbackHandler` conflicts with streaming. `get_openai_callback()` returns zero during message streaming.
- **LangSmith**: Can capture token usage externally but adds latency.
- **No built-in context window visualization** — LangGraph does not natively provide context window state or category breakdowns.

### Our Current State

- **React SDK** shows some token info at the widget level (per-message tokens) but not the aggregate context window state.
- **cursor-runner** processes stream events but doesn't aggregate/expose context utilization data.
- **agent-runner** (LangGraph) doesn't track context window state at all.
- Proto messages exist for `TokenUsage` in execution status but are not populated for Cursor harness runs.

## Specific Areas to Investigate

### 1. Extracting Context Window State from Cursor SDK
- Is there any undocumented or planned API in `@cursor/sdk` that exposes context window utilization?
- Can we reconstruct context window state from the stream events (accumulating `inputTokens` from `TurnEndedUpdate`)?
- Does the `run.conversation()` method return enough data to estimate context size?
- Can we use the `onDelta` callback's `StepStartedUpdate`/`StepCompletedUpdate` to track context per step?
- Is there a way to query the underlying Cursor local/cloud agent for its current context state?

### 2. Calculating Context Window Breakdown by Category
- How does Cursor IDE calculate the breakdown (system prompt, tools, rules, skills, MCP, conversation)?
- Can we approximate this for SDK runs by:
  - Knowing the system prompt size (from our own prompt builder)?
  - Tracking tool call input/output sizes from stream events?
  - Measuring MCP tool descriptions we pass to the agent?
  - Tracking conversation turn sizes from `SDKMessage` events?
- What token estimation approach is accurate enough? (`tiktoken`, character-based ~4 chars/token, model-specific tokenizers)?
- How frequently should we recalculate context state (per message, per turn, per step)?

### 3. Context Tracking for LangGraph Harness
- How can LangGraph Python expose context window state to the orchestrating platform?
- Does LangGraph's `StateGraph` maintain any internal context/token accounting?
- Can we use LangChain's `BaseCallbackHandler` to intercept all LLM calls and accumulate token usage?
- How do we handle LangGraph's graph structure (nodes, edges) and map it to context categories?
- What about LangGraph's checkpointing — can we extract context state from checkpoints?
- Are there community solutions (LangWatch, Langtrace, Phoenix) that provide this?

### 4. Real-Time vs Post-Hoc Context Visibility
- Should context window state be calculated in real-time (during streaming) or post-hoc (after execution)?
- What are the performance implications of real-time token counting during streaming?
- Can we use a "lazy" approach — calculate context breakdown only when the user opens the context panel?
- How does Cursor IDE handle this — is the circle updated in real-time or computed when the panel is opened?

### 5. UI/UX Patterns for Context Visualization
- What are the best UI patterns for showing context window utilization in a web-based AI chat interface?
- Beyond the circular gauge, what other visualizations help users understand context consumption?
- How should we handle the "summarization happened" event — should we show a visual indicator?
- What accessibility considerations apply to context window visualizations?
- How do other AI platforms (ChatGPT, Claude, Cody, Windsurf) display context information?

### 6. Cross-Harness Unified Context Model
- Can we define a common context state proto/schema that works for both Cursor and LangGraph?
- What fields should this include (total tokens, max tokens, category breakdown, summarization count, etc.)?
- How do we handle the fact that Cursor manages its own context window internally while LangGraph gives us full control?
- Should the context model be per-execution, per-turn, or per-message?

## Why This Matters

Context window visibility is becoming table-stakes for AI agent interfaces. Cursor has set the bar with their context telemetry feature. Our early adopters explicitly said they "want to understand what is the context size recurrently" like what Cursor provides. Without this, users can't diagnose why agents hallucinate, ignore instructions, or degrade over long sessions — and they'll blame Stigmer's interface rather than the underlying context management.
