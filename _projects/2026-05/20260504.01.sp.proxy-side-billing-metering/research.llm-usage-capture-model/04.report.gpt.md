# LLM Usage Capture Model for a Proxy Metered AI Agent Platform

## Executive synthesis

The strongest pattern across providers and gateways is not a single all-purpose “usage” record. It is a **layered model**:

- an **authoritative per-request usage fact** sourced from the provider or trusted proxy, used for billing and reconciliation;
- a **separate aggregate/reporting layer** for dashboards, finance, and chargeback;
- an **observability layer** for latency, traces, logs, retries, and debugging. citeturn38view0turn38view1turn9view0turn39view3turn2view2turn18view1turn27search3turn31search0

For Stigmer, that argues for **three message families**, not one:

1. **Authoritative per-call record** written by the proxy after each LLM call completes.
2. **Execution aggregate** derived server-side from authoritative per-call records.
3. **Runtime observability record** written by the runner, clearly marked non-billing and lower trust.

That design lines up with how OpenAI separates per-call `usage` from org-level Usage and Costs APIs, how Anthropic separates response `usage` from its Usage & Cost Admin API, how AWS/Azure/Vertex separate invocation usage from monitoring dashboards/logs, and how gateways such as Vercel, LiteLLM, Helicone, and Portkey expose both request logs and rollups. citeturn37view2turn38view0turn38view1turn4view1turn9view0turn39view0turn39view3turn2view2turn18view0turn18view1turn27search6turn27search3turn29search0turn29search1turn30search0turn31search0

The most important implementation recommendation is this: **do not embed billing-authoritative per-call records inside hot execution status or message documents**. Store per-call records in a dedicated collection keyed by execution and call ID, then materialize a lightweight execution summary onto the execution document. That mirrors the “request log + summary dashboard” pattern used by the strongest gateway products and avoids repeated rewrites of large execution documents at 3–50 calls per run. citeturn27search3turn27search0turn31search0turn31search1turn39view3

## Design patterns that emerge from the survey

The survey points to a repeatable pattern:

**Inline provider usage** is the closest thing to token truth. OpenAI, Anthropic, Bedrock, and Vertex all expose token usage directly in the response object returned for an individual call. The richness varies by provider, but the pattern is consistent: post-response usage is the canonical source for token-based charging. citeturn37view2turn4view1turn39view0turn18view0

**Billing and finance views are aggregate layers, not the per-request ledger itself.** OpenAI’s Usage and Costs APIs are bucketed. Anthropic’s Usage & Cost Admin API is historical and grouped. Cloud providers push monitoring into CloudWatch, Azure Monitor, and Cloud Monitoring. Gateways add grouped reporting APIs and dashboards. citeturn38view0turn38view1turn9view0turn39view3turn2view2turn18view1turn27search0

**Operational timing belongs to observability.** AWS publishes `InvocationLatency` and `TimeToFirstToken`; Azure publishes time-to-response, time-between-tokens, TTFLB/TTFB metrics; Vertex publishes first-token latency and token throughput; Vercel reports P75 TTFT and duration. None of the surveyed systems bill LLM text generation by duration. citeturn2view4turn2view2turn18view1turn27search3

**Per-request logs and grouped rollups coexist.** Vercel, Portkey, Helicone, LiteLLM, and AWS all use some form of “request detail + aggregate dashboard/report” design. That is the scalable shape Stigmer should mirror. citeturn27search3turn27search0turn31search0turn31search1turn30search1turn29search1turn39view3

**OpenTelemetry is becoming an observability substrate, not a billing standard.** Vercel AI SDK uses OpenTelemetry, Vertex can emit OTEL-formatted logs, and Portkey exposes OTEL-based observability and export. But billing fields and authoritative token usage are still provider- and product-specific. citeturn28search3turn18view2turn19view3turn31search9turn31search13

## Recommended Stigmer data model

### Use separate record types

Stigmer should not use one message type “everywhere.” The cleanest design is:

- **`LlmCallUsageRecord`**: authoritative, per call, written by proxy in cloud mode and by runner in OSS mode with an explicit downgraded trust marker.
- **`ExecutionUsageSummary`**: server-derived aggregate for the execution, materialized from authoritative per-call records.
- **`ExecutionRuntimeMetrics`** or **`LlmCallRuntimeObservation`**: runner-reported observability data, display-only, never used for billing.

That is the closest match to the market pattern and the least confusing trust boundary. citeturn38view0turn38view1turn9view0turn39view3turn27search3turn31search1

### Recommended execution aggregate

The execution aggregate should be **derived** from authoritative per-call records, not independently written by the runner.

| Field | Derivation |
|---|---|
| `llm_call_count` | Count of authoritative call records |
| `input_tokens`, `output_tokens`, `total_tokens` | Sum across authoritative calls |
| `cache_read_input_tokens`, `cache_write_input_tokens`, optional `reasoning_tokens`, optional audio tokens | Sum across authoritative calls |
| `provider_cost_micros_total`, `billable_cost_micros_total` | Sum across authoritative calls |
| `currency`, `latest_pricing_version`, `latest_markup_version` | Derived / last-seen from stamped pricing |
| `model_breakdown[]` | Group authoritative calls by `{provider, model, service_tier}` and sum counts/tokens/cost |
| `failed_call_count`, `partial_usage_call_count`, `last_usage_update_at` | Derived state for UI and reconciliation |

Two deliberate recommendations follow from the survey:

- **Do not make `primary_model` or `primary_provider` a source-of-truth field.** Multi-model activity is normal in every surveyed system. If you keep a convenience field, compute it on read or materialize it as a clearly-derived display hint such as “dominant model by billable cost.” citeturn38view1turn9view0turn2view2turn18view1turn27search0
- **Do not store per-call detail as a repeated field on the hot execution status document.** Keep the per-call fact table separate and put only the summary on the execution document. Products that show both logs and dashboards almost always operate this way conceptually, even if the internal schema is not public. citeturn27search3turn31search0turn31search1turn39view3

### Keep runner observability out of billing usage

`tool_result_chars_truncated`, `tool_duration_ms`, `approval_wait_duration_ms`, local retry counts, context-window utilization, and “thinking time” are all valuable, but they should live in a **runner-reported observability message**, not the authoritative usage ledger. Anthropic even separates code-execution cost from token-usage reporting, and cloud providers put timing and operational metrics in monitoring systems rather than the billing record. citeturn9view0turn2view4turn2view2turn18view1

## Trust boundary and duration guidance

### Trust boundary matrix

| Field group | Proxy authoritative | Runner authoritative | Recommended handling |
|---|---|---|---|
| Provider/model/service tier/upstream request id | Yes | Sometimes knows a local alias only | Store on authoritative per-call record |
| Provider token counts and cache token counts | Yes in cloud mode; provider response is the source of truth | No | Billing-authoritative on per-call record |
| Provider cost and billable cost | Yes, if server computes from pricing registry and markup policy | No | Stamp on per-call record and aggregate |
| Proxy TTFT / proxy stream duration / status code / response bytes | Yes | No | Store on per-call record as observability fields, not billing |
| Client-perceived LLM round-trip | No | Yes | Store in runner observability sidecar |
| Tool execution duration, approval wait, truncation, context utilization | No | Yes | Store on execution runtime metrics, never in billing summary |
| Trace/span/subagent join info | Often runner supplied | Yes | Store as join metadata; do not trust for billing |
| Execution aggregate tokens/cost | Derived server-side | No | Materialize from authoritative per-call facts |

### Duration recommendation

Stigmer **should** capture proxy-side duration, but should name it precisely:

- `proxy_time_to_first_byte_ms`
- `proxy_stream_duration_ms`
- optionally `proxy_request_duration_ms` if you want request-start to stream-end

That is useful because AWS, Azure, Vertex, and Vercel all expose operational latency metrics, including TTFT-like measurements and total generation time. citeturn2view4turn2view2turn18view1turn27search6turn27search3

But Stigmer should **not** label proxy duration as “LLM call duration” without qualification. A proxy can measure **provider-facing** latency and stream timing. It cannot measure the client’s total waiting experience once network path, client buffering, downstream processing, tool orchestration, and local rendering are included. Azure’s distinct TTFB/TBT/TTLB metrics and Vercel’s separate `latency` and `generation_time` fields are good models here. citeturn2view2turn27search6

The right answer is therefore:

- **Billing:** duration is not a billing concern for LLM text calls in the surveyed products.
- **Observability:** store both proxy-side and runner-side duration, but in different fields and with different trust labels. citeturn2view4turn18view1turn27search3

### Handling missing or conflicting token counts

When the provider delivers a final usage object, use it. If the stream ends without authoritative usage, mark the call `PARTIAL` or `UNAVAILABLE` and do **not** replace it with a billing-authoritative estimate. Many platforms expose preflight counting APIs separately from post-response usage, which reinforces the distinction between pre-request counting and post-request billing truth. citeturn35search10turn13search12turn17search7

For Stigmer, the simplest safe rule is:

- **Provider-reported post-call usage present:** bill from it.
- **No provider-reported final usage:** record incomplete usage, do not debit token-based spend from an estimate, and reconcile later only if you obtain provider-authoritative data.

That protects the “tamper-proof billing” requirement more than trying to be clever.

## Handoff pattern from usage write to billing debit

The safest design is **write usage first, then debit via an idempotent outbox pattern**.

### Recommended flow

1. Proxy finishes parsing the stream and builds the authoritative `LlmCallUsageRecord`.
2. In one database transaction:
   - upsert the per-call usage record by its idempotency key;
   - update the execution aggregate;
   - insert an outbox/debit-intent record if billing has not yet been applied.
3. After commit, process the debit-intent synchronously or asynchronously.
4. Billing uses the **same idempotency key** and records `billing_event_id`.
5. On success, mark `billing_state=APPLIED`. On failure, leave `billing_state=PENDING` or `FAILED_RETRYABLE` and retry.

This is much safer than calling billing first, because it ensures “billing happened” is never the only durable fact. Vercel’s Stripe metering docs describe the same essential properties for a metering pipeline: non-blocking response flow, idempotent meter events, conditional emission after successful responses, and observable failures. citeturn27search8

### Same transaction or separate

If the usage fact store and billing ledger are in the **same transactional database boundary**, then yes, same transaction is ideal.

If billing is a **separate service**—which seems closer to your current `reportLlmCallUsage(...)` shape—do **not** attempt distributed 2PC. Use the outbox pattern above. That gives you consistency without coupling proxy completion to a remote debit call.

### Idempotency key

`(execution_id, sequence)` is acceptable **only if sequence identifies one logical billable provider attempt**.

If a single sequence can generate multiple genuine provider attempts that each consumed tokens, then you need a more precise key, such as:

- `call_id` = stable unique id for the logical provider attempt
- `sequence` = ordering hint within the execution
- optional `attempt` = retry number

My recommendation is:

- keep `sequence` for ordering and UI;
- use `call_id` for idempotency and joins;
- enforce uniqueness on `(execution_id, call_id)`.

That avoids the common failure mode where a transport retry is accidentally treated as the same billable event, or a duplicate proxy callback is treated as a second billable event.

## Final recommendations for the questions you called out

**One usage message type or multiple?**  
Use multiple types. At minimum: authoritative per-call, derived execution aggregate, runner observability. Reusing one message across all contexts will blur trust boundaries and lifecycle semantics. citeturn38view0turn9view0turn39view3turn27search3

**Is duration a billing concern?**  
No for LLM text calls in the surveyed systems. It is an observability concern. Platforms measure TTFT, total generation time, or latency, but do not use it as the billing unit for text generation. citeturn2view4turn2view2turn18view1turn27search6

**Should the proxy-written record be the single source of truth?**  
Yes for cloud mode billing-safe fields. In OSS mode, use the same schema but mark the source as self-reported so downstream systems can distinguish trust level.

**Is there a standard for proxy request records?**  
There is an emerging observability influence from OpenTelemetry, but not a universal billing-usage standard. Token and cost schemas remain provider- and gateway-specific. citeturn28search3turn18view2turn31search9

**Should cost be stored or computed at read time?**  
Store it at write time, with pricing and markup versions, and store both provider cost and billable cost. Read-time recomputation is bad for auditability and invoice reproducibility. Gateway products that expose per-request cost effectively follow this pattern. citeturn27search6turn29search0turn29search1turn31search7

**Where should `estimated_cost_usd` live?**  
Ideally nowhere as a primary persisted field. Persist integer micros for authoritative provider and billable cost, and derive a display-friendly decimal on read if needed for compatibility.

**Should tool truncation and runtime timing live in usage?**  
No. Keep them in execution runtime metrics or a runner observability sidecar.

## Open questions and limitations

Some public docs are much stronger than others. OpenAI, Anthropic, AWS, Azure, Vertex, and Vercel publish substantial official usage and observability detail; Cursor’s public docs are more product-facing and do not expose a stable request schema; Azure’s public docs describe monitoring categories and metrics clearly but are less explicit about a per-request billing ledger API; Helicone and Portkey are strong on observability and cost tooling, but the exact internal storage model is not fully public. The design recommendations above therefore lean most heavily on the provider docs and the best-documented gateway patterns.

# Executive recommendation

Stigmer should **not** keep evolving the current `UsageMetrics / ModelUsage / LlmCallMetrics` shape as one mixed “usage” blob. The clean design is:

**1. An immutable, proxy-written per-call metering record**
This is the billing-authoritative event for a single LLM provider call. It contains provider-reported tokens, normalized token buckets, pricing snapshot, provider cost, customer billable amount, proxy-observed timings, provider response metadata, and billing debit status.

**2. A derived execution-level usage aggregate**
This is a projection over the per-call records, grouped by provider/model/pricing version/service tier. It powers dashboard summaries, cost reports, and execution status display. It can be denormalized onto `AgentExecutionStatus`, but it should be derived from per-call records, not separately trusted.

**3. A separate runner-provided observability record**
Runner timings, tool duration, approval wait, context-window utilization, truncation counts, and “thinking time” belong in an execution observability model, not in billing usage. These are useful and should be displayed, but they should be marked `DISPLAY_ONLY` or kept in a separate proto.

**4. Cost must be stamped at write time**
Store both `provider_cost_micros` and `customer_billable_amount_micros`, plus the exact pricing registry version and markup policy version used. Do not store only `estimated_cost_usd` as a float.

**5. Duration is useful, but not billing usage**
The proxy should measure `time_to_first_byte`, `time_to_first_token`, `time_to_last_byte`, and stream duration. These are trusted proxy telemetry. They are not the same as client-perceived latency and should not be called plain `duration_ms`.

**6. Use insert-only idempotent metering + outbox/ledger debit**
The safest pattern is: insert immutable usage record → enqueue/debit billing idempotently → mark usage record debited. If the billing debit and usage write can be in one DB transaction, do it. If not, use a transactional outbox and require billing ledger entries to reference an existing usage record ID.

The market pattern is consistent: **providers expose token usage; cloud platforms expose observability metrics separately; billing/cost records are separate or explicitly caveated; gateways combine logs for UX but distinguish exact gateway-observed costs from estimated/direct-integration costs.** OpenAI is especially explicit that Usage API data may not reconcile exactly with Costs and that the Costs endpoint/Costs tab is the financial source of truth. ([OpenAI Platform][1])

## Competitive-analysis synthesis

The market shows four recurring patterns.

First, **provider responses expose usage tokens, not a complete billing ledger**. OpenAI, Anthropic, Bedrock, Azure, and Vertex all expose token usage in responses or monitoring APIs, but billing/cost reporting is separate or has different aggregation semantics. OpenAI is the clearest warning: Usage API data may not reconcile exactly with Costs, and financial reporting should use Costs. ([OpenAI Platform][1])

Second, **latency/duration is observability, not core LLM usage**. Bedrock, Azure, Vercel Gateway, Portkey, Helicone, and Cloudflare all expose latency/TTFT/duration as monitoring/log fields. They do not treat these as token-billing fields for normal on-demand inference. Azure explicitly says service-side latency does not include client-side latency. ([Microsoft Learn][13])

Third, **estimated usage must be labeled**. Vertex says preflight Count Tokens can differ from actual consumed tokens and that accurate billing usage is in post-execution `usage_metadata`. Cloudflare says gateway costs are estimates unless backed by provider data, and Helicone explicitly distinguishes exact gateway costs from best-effort direct integrations. ([Google Cloud Documentation][16])

Fourth, **OpenTelemetry GenAI is emerging, but it is not a billing schema**. OTel GenAI semantic conventions include token usage, provider/model attributes, and operation duration, and they say to report billable tokens when both used and billable token counts exist. But the GenAI conventions are still marked Development, so they are excellent for export/tracing names, not sufficient as Stigmer’s ledger model. ([OpenTelemetry][36])

# 2. Recommended per-call record

## Core principle

The per-call record should answer this question:

> “What exactly did Stigmer’s trusted metering layer observe for this provider call, what price schedule did we apply at that moment, and what billing ledger event did it produce?”

It should **not** try to answer:

> “How long did the whole agent step feel to the runner?”
> “How much time was spent executing tools?”
> “How full was the context window?”
> “How long was the human approval wait?”

Those belong in observability records.

## Boundary rule

In cloud mode:

> **Only `PROXY_PROVIDER_REPORTED` or `PROVIDER_ADMIN_RECONCILED` records can create billing debits.**

# 5. Duration recommendation

## Should proxy track duration?

Yes. The proxy should track duration, but with precise names:

* `proxy_total_duration_ms`
* `upstream_ttfb_ms`
* `upstream_time_to_first_token_ms`
* `upstream_ttlb_ms`
* `stream_duration_ms`

These are valuable for:

* provider latency dashboards,
* detecting degraded models/providers,
* separating provider slowness from runner/tool slowness,
* debugging SSE streaming behavior,
* SLA/SLO metrics,
* choosing routing/fallbacks.

Bedrock, Azure, Vercel Gateway, Portkey, Helicone, and Cloudflare all treat latency/TTFT/duration as important observability dimensions. ([AWS Documentation][10])

## Is proxy duration the same as runner-perceived LLM latency?

No.

Azure’s monitoring docs explicitly state that service-side “Time to Response” does not account for client-side latency between the client and the API endpoint, and they recommend client-side logging for optimal latency tracking. ([Microsoft Learn][13])

For Stigmer, that means:

| Metric                        |                      Source | Meaning                                                                                                                    |
| ----------------------------- | --------------------------: | -------------------------------------------------------------------------------------------------------------------------- |
| `proxy_ttfb_ms`               |                       Proxy | Provider/proxy path until first byte.                                                                                      |
| `proxy_ttlb_ms`               |                       Proxy | Provider/proxy path until last byte.                                                                                       |
| `stream_duration_ms`          |                       Proxy | Provider stream length.                                                                                                    |
| `runner_llm_wait_duration_ms` |                      Runner | What the runner experienced around the LLM call. Includes client/proxy network, SDK overhead, buffering, possibly retries. |
| `execution_total_duration_ms` | Runner/server orchestration | Whole task duration.                                                                                                       |
| `tool_duration_ms`            |                      Runner | Tool execution, not LLM usage.                                                                                             |

## Is duration a billing concern?

For normal on-demand LLM APIs, no: billing is token-based, sometimes with extra dimensions such as cached tokens, service tier, provisioned throughput, fine-tuned hosting, or hourly capacity. OpenAI/Anthropic/Vertex/Vercel Gateway pricing is primarily token-based for inference; Bedrock also has provisioned throughput that is billed hourly as a separate capacity product. ([OpenAI][39])

So for Stigmer:

> Store duration. Show duration. Alert on duration. Do not debit credits based on duration unless Stigmer later introduces a separate compute/runtime billing product.

# 6. Usage record design patterns

## Pattern A: Single unified record

This is common in lightweight SDKs and gateway dashboards: one log row contains model, tokens, cost, latency, status, metadata. Vercel Gateway, Portkey, Cloudflare AI Gateway, LiteLLM, and Helicone all expose request logs that combine usage, cost, latency, and metadata. ([Vercel][20])

This is good for dashboards. It is risky for billing if fields from different trust domains are mixed without source labels.

## Pattern B: Billing record + observability record

This is more appropriate for Stigmer.

OpenAI separates Usage API from Costs API and says Costs is the financial source of truth. Anthropic separates usage and cost report endpoints. Cloud platforms separate runtime response usage, monitoring metrics, invocation logs, and cost management. ([OpenAI Platform][1])

For Stigmer, separation is warranted because:

* the proxy is trusted and billing-authoritative,
* the runner is open-source and forkable,
* runner telemetry is still valuable,
* prepaid credit debit must be auditable,
* missing final usage / retries / conflicts require ledger-like handling.

Recommended pattern:

```text
LlmCallUsageRecord        immutable billing-authoritative metering event
BillingLedgerEntry        immutable financial debit/credit entry
ExecutionUsageAggregate   derived projection for dashboards/status
ExecutionObservability    runner/proxy telemetry, display-only
AgentMessage.llm_metrics  legacy/display pointer, not source of truth
```

## Pattern C: Immutable core + enrichable telemetry

Use this hybrid:

* **Immutable core:** tokens, provider, model, price snapshot, costs, billing debit link.
* **Enrichable separate telemetry:** runner-perceived duration, context utilization, tool truncation, trace/span annotations.

Do **not** let runner updates mutate billable fields on the proxy record.

## Pattern D: Aggregate + per-call storage

Use both.

Per-call records are necessary for:

* idempotent billing,
* auditability,
* debugging a specific expensive call,
* sub-agent tracing,
* reconciliation against provider usage/cost reports,
* multi-model executions.

Aggregates are necessary for:

* fast dashboard reads,
* execution status display,
* project/user/day cost charts,
* “stop/warning” billing signals,
* avoiding expensive scans on every UI load.

For MongoDB, I would store per-call records in a separate append-only collection and denormalize the aggregate onto the execution document. Since Stigmer executions usually have 3–50 LLM calls, embedding a small recent call list for UI is fine, but the authoritative source should be a separately indexed collection.

# 7. Recommended handoff pattern: proxy write → billing debit

## Preferred if usage store and billing ledger are in the same database

Use one transaction:

1. Validate execution is active and belongs to tenant.
2. Normalize provider usage.
3. Compute provider cost from pricing registry.
4. Compute customer billable amount from markup policy.
5. Insert immutable `LlmCallUsageRecord`.
6. Insert idempotent `BillingLedgerEntry`.
7. Update execution aggregate.
8. Return billing signal if needed.

This gives the strongest consistency.

## Preferred if usage and billing are separate services/databases

Use a transactional outbox.

```text
Proxy observes final provider usage
    ↓
Usage service inserts immutable LlmCallUsageRecord with billing_debit_status=PENDING
    ↓
Same DB transaction inserts BillingDebitRequested outbox event
    ↓
Billing worker consumes outbox event
    ↓
Billing service idempotently debits credits using usage_record_id/idempotency_key
    ↓
Usage record marked DEBITED with ledger_transaction_id
    ↓
Execution aggregate updated
```

This avoids the dangerous state where billing succeeds but no usage record exists.

## Failure handling

| Failure case                                                                     | Recommended behavior                                                                                                                                                                                                                       |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Usage write succeeds, billing debit fails retryably                              | Keep usage record as `PENDING` or `FAILED_RETRYABLE`; retry via outbox. Do not delete usage.                                                                                                                                               |
| Usage write succeeds, billing debit fails terminally due to insufficient credits | Mark `FAILED_TERMINAL` or `DEBIT_REJECTED_INSUFFICIENT_CREDITS`; send STOP/WARNING through existing billing signal path; finalize according to policy.                                                                                     |
| Billing succeeds, usage write fails                                              | Avoid this ordering. Ledger debit should require a pre-existing `usage_record_id`.                                                                                                                                                         |
| Proxy retries same `(execution_id, sequence)` with same payload                  | Return existing record and existing debit result. Idempotent success.                                                                                                                                                                      |
| Proxy retries same key with different token/cost payload                         | Do not overwrite. Mark conflict, alert, and block duplicate debit.                                                                                                                                                                         |
| Stream completed but final provider usage missing                                | Insert `usage_status=STREAM_INTERRUPTED_MISSING_FINAL_USAGE`, `is_billable=false` or `PENDING_RECONCILIATION`, depending on policy. OpenAI warns final streaming usage may not arrive if the stream is interrupted. ([OpenAI Platform][3]) |
| Provider returns error with usage                                                | Store usage with `PROVIDER_ERROR_WITH_USAGE`; bill only if provider-reported billable usage and Stigmer policy says to pass it through.                                                                                                    |
| Runner reports usage in cloud mode                                               | Store only as display telemetry or ignore for billing. Never debit from it.                                                                                                                                                                |
| OSS mode runner reports usage                                                    | Store in same schema with `metering_source=RUNNER_PROVIDER_REPORTED_OSS`; mark trust appropriately.                                                                                                                                        |

## Insert-only or upsert?

Use **insert-only immutable records** with idempotent replay semantics.

Technically the operation can be implemented as “insert if absent; if duplicate, compare payload hash and return existing if identical.” But conceptually it should not be an upsert that mutates token or cost fields.

Recommended unique indexes:

```text
unique(execution_id, execution_attempt, sequence, metering_source)
unique(usage_record_id)
unique(idempotency_key)
index(tenant_id, created_at)
index(project_id, created_at)
index(execution_id, sequence)
index(root_execution_id, created_at)
index(provider, resolved_model, created_at)
index(billing_debit_status, created_at)
```

Use a `canonical_payload_hash` over normalized provider/model/tokens/status fields. If a retry has the same key but different hash, create a conflict event, not a new charge.

# 9. What to change in the new `updateUsage` RPC

Your current `updateUsage` input is:

```text
execution_id, sequence, model, provider,
input_tokens, output_tokens,
cache_creation_tokens, cache_read_tokens
```

That is enough for a first debit, but not enough for an audit-grade metering record.

Recommended request shape:

```proto
message UpdateUsageRequest {
  string execution_id = 1;
  int32 execution_attempt = 2;
  int32 sequence = 3;
  string idempotency_key = 4;

  string provider = 10;
  string requested_model = 11;
  string resolved_model = 12;
  string provider_model_version = 13;
  string endpoint = 14;
  bool streaming = 15;
  string service_tier = 16;
  string provider_request_id = 17;

  int32 http_status_code = 20;
  string finish_reason = 21;
  string raw_finish_reason = 22;
  string error_code = 23;
  string error_type = 24;

  TokenUsage tokens = 30;
  ProxyTiming proxy_timing = 40;

  UsageCompletionStatus usage_status = 50;
  string provider_usage_json = 60;

  string trace_id = 70;
  string span_id = 71;
  string parent_span_id = 72;
}
```

Server-side handler should:

1. Validate execution and sequence.
2. Normalize model/provider.
3. Look up pricing registry by provider + resolved model + service tier + timestamp.
4. Compute `provider_cost_micros`.
5. Apply markup policy to compute `customer_billable_amount_micros`.
6. Insert immutable `LlmCallUsageRecord`.
7. Trigger idempotent billing debit.
8. Update aggregate projection.
9. Return current billing signal.

Do **not** accept `providerCostMicros` from runner or proxy as authoritative input unless the proxy itself is the trusted server component and the pricing code is server-owned. Even then, prefer computing cost in one server-side metering service so pricing logic is centralized.

# 11. Handling provider usage edge cases

## A. OpenAI streaming final usage missing

OpenAI’s streaming `include_usage` sends usage in a final chunk before `[DONE]`, but if the stream is interrupted, that final usage chunk may not arrive. ([OpenAI Platform][3])

Recommended Stigmer behavior:

```text
usage_status = STREAM_INTERRUPTED_MISSING_FINAL_USAGE
token_source = NONE or PARTIAL_PROVIDER_STREAM
is_billable = false, or pending reconciliation
billing_debit_status = NOT_APPLICABLE or PENDING_RECONCILIATION
```

Do not silently estimate and debit.

## B. Anthropic stream partial usage

Anthropic streaming provides usage in events, including cumulative output token counts in `message_delta`, but error events can occur in a stream. ([Claude API Docs][40])

Recommended behavior:

* If final/complete usage is available, bill normally.
* If only partial cumulative usage is available, mark `PROVIDER_ERROR_WITH_USAGE` or `STREAM_INTERRUPTED_MISSING_FINAL_USAGE`.
* Decide policy explicitly: either bill provider-reported partial usage or wait for reconciliation.

## C. Preflight count does not match final count

Vertex explicitly says Count Tokens estimates may not match final consumed tokens and that accurate usage for billing is available after execution. ([Google Cloud Documentation][16])

Recommended behavior:

* Preflight estimates can be stored as `USAGE_METERING_SOURCE_ESTIMATED`.
* They can drive warnings, context planning, or UI estimates.
* They must not create cloud billing debits.

## D. Provider model alias changes

Store both:

* `requested_model`
* `resolved_model`
* `provider_model_version`
* `pricing_registry_version`
* `pricing_effective_at`

Do not rely on `primary_model` or a mutable model alias for historical billing.

## E. Cache token pricing

OpenAI, Anthropic, Bedrock, and Vertex all have provider-specific cache token concepts. ([OpenAI Platform][2])

Normalize common fields, but preserve raw provider usage JSON because cache semantics differ.

# 12. Direct answers to your key questions

## 1. Should Stigmer have one usage message type or separate types?

Use separate types.

Recommended:

```text
LlmCallUsageRecord          billing-authoritative per-call event
ExecutionUsageAggregate     derived usage/cost summary
ExecutionObservability       runner/proxy timing and context metrics
BillingLedgerEntry           financial debit/credit record
```

You can expose a unified UI object, but the stored data model should preserve source/trust boundaries.

## 2. Is duration a billing concern?

For normal LLM calls, no. It is observability. Token usage, cache tokens, service tier, and sometimes provisioned capacity/hosting are billing concerns. Bedrock provisioned throughput is hourly, but that is a separate capacity product, not per-call LLM duration billing. ([AWS Documentation][9])

## 3. Should the proxy-written per-call record be the source of truth?

Yes, in cloud mode:

```text
PROXY_PROVIDER_REPORTED LlmCallUsageRecord
= source of truth for provider/model/tokens/cost/debit
```

Runner data can enrich display telemetry but must not mutate billable fields.

In OSS mode, use the same schema but mark the source as runner-reported or estimated.

## 4. Is there an emerging OpenTelemetry standard?

Yes, OpenTelemetry GenAI semantic conventions exist for gen-AI spans and metrics, including token usage, provider/model attributes, and operation duration. They are currently marked Development, and they say to report billable tokens when both used and billable token counts are available. ([OpenTelemetry][36])

Use OTel naming and trace concepts, but do not use OTel as your billing ledger schema.

## 5. How should token mismatches/errors be handled?

Use explicit statuses:

```text
COMPLETE
STREAM_INTERRUPTED_MISSING_FINAL_USAGE
PROVIDER_ERROR_WITH_USAGE
PROVIDER_ERROR_NO_USAGE
ESTIMATED_ONLY
RECONCILED
CONFLICT
```

Provider-reported final usage wins. Estimates are display-only. Missing final usage should be nonbillable or pending reconciliation, not silently debited.

## 6. Should cost be stored as provider cost, customer cost, or both?

Both.

Per call:

```text
provider_cost_micros
customer_billable_amount_micros
pricing_registry_version
markup_policy_version
price rates used
```

Aggregate:

```text
sum(provider_cost_micros)
sum(customer_billable_amount_micros)
```

Ledger:

```text
actual debit/credit entries
```

Avoid authoritative `estimated_cost_usd` floats.

## 7. Are there platforms that explicitly model billing-authoritative vs display-only?

Public docs rarely expose internal field names like that, but the pattern is visible:

* OpenAI separates Usage API from Costs and says Costs is the financial source. ([OpenAI Platform][1])
* Anthropic separates usage reports from cost reports. ([Claude API Docs][5])
* Helicone explicitly says gateway cost calculation is accurate due to complete visibility, while direct integrations are best-effort estimates. ([Helicone][27])
* Cloudflare AI Gateway says its costs are estimates and accurate cost details should be checked with the provider dashboard. ([Cloudflare Docs][33])

For Stigmer, make that distinction explicit in the proto.

# 13. Final Stigmer design decision

I would implement this:

```text
Cloud mode:
  Proxy writes LlmCallUsageRecord:
    metering_source = PROXY_PROVIDER_REPORTED
    trust_level = BILLING_AUTHORITY
    usage_status = COMPLETE only if final provider usage was observed

  Server computes:
    provider_cost_micros
    customer_billable_amount_micros
    pricing snapshot
    markup policy version

  Billing debits:
    idempotently by usage_record_id / execution_id+attempt+sequence

  Runner writes:
    ExecutionObservabilityMetrics
    RunnerLlmCallTelemetry
    never billing fields

OSS mode:
  Runner may write LlmCallUsageRecord:
    metering_source = RUNNER_PROVIDER_REPORTED_OSS or ESTIMATED
    trust_level = DISPLAY_ONLY unless explicitly configured otherwise
```

And I would make these immediate proto/API changes:

1. Add top-level `usage_summary: ExecutionUsageAggregate` to `AgentExecutionStatus`.
2. Add top-level `observability: ExecutionObservabilityMetrics` to `AgentExecutionStatus`.
3. Stop treating `AgentMessage.llm_metrics` as authoritative. Keep it as display/legacy or replace with a reference to `usage_record_id`.
4. Store authoritative per-call usage in a separate `llm_usage_records` collection.
5. Make `updateUsage` create an immutable `LlmCallUsageRecord`, not just update an execution blob.
6. Rename `estimated_cost_usd` to integer cost fields:

   * `provider_cost_micros`
   * `customer_billable_amount_micros`
   * `estimated_provider_cost_micros` only for estimates/OSS display.
7. Split ambiguous `duration_ms` into:

   * proxy timing fields,
   * runner timing fields,
   * execution observability fields.

The shortest version of the architecture is:

```text
Billing truth:
  LlmCallUsageRecord  →  BillingLedgerEntry

Display truth:
  ExecutionUsageAggregate + ExecutionObservabilityMetrics

Debug truth:
  Trace/span records + optional request/response logs

Never mix:
  trusted token/cost fields with untrusted runner timing/context fields
  unless the source/trust level is explicit
```
