# Deep Research: LLM Usage Capture Model for a Proxy-Metered AI Agent Platform

## Research Objective

We are building the usage capture and billing metering layer for **Stigmer** — an infrastructure platform for AI agents. Stigmer routes all LLM API calls through a server-side proxy (the platform controls the API keys). We need to understand **how best-in-class platforms capture, store, and expose LLM usage data** when usage is observed at a proxy layer, and how they separate billing-authoritative usage from observability/display metrics.

The core challenge: we have **two observers** of each LLM call, with different visibility into different aspects:

| Observer | What it sees | Trust level |
|----------|-------------|-------------|
| **Proxy** (server-side, tamper-proof) | Token counts (from SSE stream), model, provider, response bytes | HIGH — billing-authoritative |
| **Runner** (client-side, open-source, forkable) | Duration, tool execution time, approval wait time, tool result truncation, thinking time, context window utilization | LOW — display-only, not billing-safe |

We want a **state-of-the-art** design for the usage data model that:
1. Enables tamper-proof billing (credits debited based on proxy-observed tokens)
2. Provides rich observability for users (execution cost, duration breakdown, per-call detail)
3. Is clean, maintainable, and doesn't mix trust levels in confusing ways
4. Scales to millions of executions with per-call granularity

## Our Architecture

### Platform Overview

Stigmer deploys AI agents that execute multi-step tasks using LLMs and tools. Each execution makes 3-50 LLM API calls. The platform has two execution engines ("harnesses"):

- **Native Harness**: Python/LangGraph agent calling Anthropic, OpenAI, etc. directly through Stigmer's proxy
- **Cursor Harness**: Using Cursor SDK where Cursor makes the LLM calls (proxied through Stigmer)

### The Proxy Layer

All cloud-mode LLM calls route through the proxy:
```
Runner → Stigmer Proxy → LLM Provider (Anthropic/OpenAI)
```

The proxy:
- Injects the platform's API key (runner never sees it)
- Tees the SSE response stream to both the runner AND an SSE parser
- Extracts token usage from the final SSE events (OpenAI `usage` object, Anthropic `message_start`/`message_delta`)
- Has access to: model name, provider, input/output/cache tokens

The proxy does NOT see:
- How long the runner waited for the response (it could measure first-byte-to-last-byte on the proxy side)
- Tool execution duration
- Total execution wall-clock time
- Context window utilization
- Tool result truncation

### Current Data Structures

We currently have three proto messages for usage (designed before the proxy metering project):

**UsageMetrics** (execution-level aggregate):
```
prompt_tokens, completion_tokens, total_tokens, llm_call_count,
primary_model, cache_creation_tokens, cache_read_tokens,
model_breakdown (repeated ModelUsage),
estimated_cost_usd,
tool_result_chars_truncated,
llm_calls (repeated LlmCallMetrics),
total_duration_ms, llm_duration_ms, tool_duration_ms, approval_wait_duration_ms,
primary_provider
```

**ModelUsage** (per-model aggregate within an execution):
```
model, provider, input_tokens, output_tokens, cache_creation_tokens, cache_read_tokens,
call_count, input_price_per_million, output_price_per_million,
cache_creation_price_per_million, cache_read_price_per_million, estimated_cost_usd
```

**LlmCallMetrics** (per-individual-LLM-call):
```
sequence, model, provider, input_tokens, output_tokens,
cache_creation_tokens, cache_read_tokens, estimated_cost_usd,
duration_ms, timestamp, total_tokens
```

**Where these live today**: NOT on `AgentExecutionStatus` as a top-level field. Instead, `LlmCallMetrics` is embedded per-message as `llm_metrics` on `AgentMessage`. The execution-level `UsageMetrics` aggregate is referenced in comments but never added to the status proto.

### Billing System (Already Built)

We have a working prepaid credit billing system with:
- Credit reservation at execution start
- Per-LLM-call debit via `reportLlmCallUsage(executionId, sequence, model, harness, costTier, providerCostMicros, inputTokens, outputTokens)`
- Finalization (release unused reservation) at execution end
- Billing signals (STOP/WARNING) delivered to runner via `updateStatus` response

The billing system takes `providerCostMicros` as input and applies a versioned markup policy to compute the customer-facing `billableAmountMicros`. Today the runner computes `providerCostMicros` (untrusted). We're moving this computation to the server using a model pricing registry.

### The New `updateUsage` RPC (Just Built, Design Under Review)

We just implemented an `updateUsage` RPC that the proxy calls after each LLM stream completes:
- Input: execution_id, sequence, model, provider, input_tokens, output_tokens, cache_creation_tokens, cache_read_tokens
- Handler: looks up model pricing → computes providerCostMicros → writes to execution → calls billing

**The open question**: What exactly should be written to the execution, and in what shape?

## What We Need From This Research

### Part 1: How Do Comparable Platforms Model LLM Usage?

Research how these platforms capture, store, and expose LLM usage data:

1. **OpenAI Platform** — How do they track usage per API call? What fields do they expose in usage records? How do they separate billing-relevant usage from observability?
2. **Anthropic Console** — Same questions. What does their usage API return?
3. **AWS Bedrock** — How do they track per-invocation usage? What goes into their CloudWatch metrics vs. billing records?
4. **Azure OpenAI** — What's in their usage logs? How is it structured for billing vs. monitoring?
5. **Google Vertex AI** — Usage tracking model for Gemini calls.
6. **Cursor** (as a platform that proxies LLM calls for its users) — How do they track usage per-request? What's exposed to the user?
7. **Vercel AI SDK** — Their telemetry/usage model for AI gateway calls.
8. **LiteLLM / Helicone / Portkey** (LLM proxy/gateway products) — How do dedicated LLM gateways model usage records? What fields do they store?

For each platform, I want to understand:
- What is the "usage record" data model? (token counts, cost, duration, model, etc.)
- Is billing data separate from observability/display data, or unified?
- Do they distinguish "provider-reported" tokens from "estimated" tokens?
- How is duration tracked (if at all)?
- What's the granularity? (per-request? per-session? per-day?)
- How do they handle multi-model scenarios (one session uses multiple models)?

### Part 2: Trusted vs. Untrusted Usage Data

In systems where a **proxy/gateway** observes LLM calls on behalf of a downstream client:

1. **What data does the proxy authoritatively know?** (tokens from provider response, model, response code, latency on proxy side)
2. **What data does only the client know?** (end-to-end latency from client's perspective, retry behavior, tool execution context, thinking/reasoning time within the client)
3. **How do platforms separate these?** Is it one record with annotations about source, or separate records entirely?
4. **The duration question specifically**: Can a proxy meaningfully measure "LLM call duration"? (It can measure time-to-first-byte and time-from-first-to-last-byte of the SSE stream. Is that the same as what the client perceives as latency?)

### Part 3: Usage Record Design Patterns

What are the recognized design patterns for usage records in proxy-metered systems?

1. **Single unified record vs. billing record + observability record**: Which pattern do platforms use? When is separation warranted?
2. **Immutable vs. enrichable records**: Should a usage record be written once (at proxy time) and never modified? Or should it be enrichable (proxy writes core fields, client can add duration/context later)?
3. **Aggregate vs. per-call storage**: Should the execution store a flat list of per-call records? Or an aggregate + per-call detail? What are the trade-offs for query patterns (dashboards, cost reports, debugging)?
4. **Cost stamping**: Should cost be stored on the usage record, or computed at read time from a separate pricing table? Platforms that store cost at write time — do they store provider cost, customer cost, or both?

### Part 4: Recommended Data Model

Given our constraints (proxy observer + untrusted runner, prepaid billing, per-call debit, multi-model executions, sub-agent hierarchies), what should our usage data model look like?

Specifically:
1. What fields should be on the **per-call** record (written by proxy after each LLM stream)?
2. What fields should be on the **execution-level aggregate** (derived from per-call records)?
3. Should duration be captured at the proxy layer (SSE stream duration) or only at the runner (client-perceived latency)?
4. Should we have a separate "billing usage" record vs. "display usage" record, or one unified record with clear field ownership?
5. Where does `estimated_cost_usd` belong — on the per-call record, the aggregate, or both?
6. How should pricing rates be stamped (at write time for historical accuracy)?
7. Should tool_result_chars_truncated, tool_duration_ms, approval_wait_duration_ms be part of the usage model at all, or should they be separate observability fields on the execution status?

### Part 5: The Handoff — Proxy Write to Billing Debit

The flow is: proxy observes tokens → writes usage record → billing debits credits. Questions:

1. Should the usage write and billing debit be in the same transaction, or separate?
2. If separate: what happens if usage is written but billing debit fails? Or billing succeeds but usage write fails?
3. How do other platforms ensure consistency between "usage recorded" and "credits debited"?
4. Idempotency: when the dedup key is (execution_id, sequence), what happens if the proxy retries? Should the usage record be upserted or insert-only?

## Constraints

- **Proto-first**: Our data model is protobuf. Any usage message must be expressible as a proto and storable in MongoDB (via JSON serialization).
- **Two repos**: Proto definitions live in the OSS repo. Java/Python implementations in the cloud repo.
- **Existing billing works**: The billing debit pipeline (reserve → report → finalize) is already built and tested. We're only changing WHO computes providerCostMicros and WHERE usage is written.
- **Runner still reports observability data**: Even after proxy metering, the runner continues to send `updateStatus` with messages, phase, tool calls. The question is whether it also sends duration/timing data that enriches the usage record.
- **OSS edition has no proxy**: In OSS mode, the runner reports usage directly (no proxy). The data model should support both paths.

## Key Questions to Answer

1. Should we have ONE usage message type (used everywhere) or separate types for different contexts (billing, display, per-call, aggregate)?
2. Is duration a billing concern or purely an observability concern? Does any platform charge based on duration for LLM calls?
3. Should the proxy-written per-call record be the "single source of truth" for an LLM call's usage, or should it be one of several signals that get reconciled?
4. Is there a standard for how LLM gateways/proxies model their per-request records? (Is there an emerging "OpenTelemetry for LLM" standard?)
5. How do platforms handle the case where token counts from the provider response don't match what was sent? (Provider error, truncated response, timeout)
6. Should cost be stored as provider cost, customer cost, or both? At per-call level, aggregate level, or both?
7. Are there platforms that explicitly model "billing-authoritative" vs. "display-only" usage and how do they do it?
