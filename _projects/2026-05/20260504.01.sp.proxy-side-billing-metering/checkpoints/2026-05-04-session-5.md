## Decisions Made

- **Don't strip `llm_metrics`**: Trust boundary is already at the collection level (`LlmCallUsageRecord`). Stripping would break `UsageAggregationService` (3 report RPCs) without adding billing trust. Migrating those reports is tracked as a separate follow-up.
- **`querySignal` over cached signal**: Read-only query of reservation + account on each heartbeat. Simpler than caching the last signal from the proxy path. The runner calls `updateStatus` every 2-3 seconds — one extra reservation + account read per heartbeat is acceptable given these are indexed MongoDB reads.
- **No reservation = continue**: OSS mode and billing-not-configured executions should never be interrupted by billing. When no reservation exists, `querySignal` returns `continue_execution`.
- **"DEPRECATED" is wrong**: Proto comments on `UsageMetrics`/`ModelUsage`/`LlmCallMetrics` say "DEPRECATED" but these types have no external consumers. They're legacy types to be removed, not deprecated. Tracked in parent follow-up.

## Learnings

- The original T05 plan said "detect new llm_metrics on messages, call billing service, map signal." After proxy-side billing was built (T01-T04), this approach became unnecessary — billing debits happen in the proxy, not in `updateStatus`. The right design is a read-only signal query.
- The existing codebase has no `StigmerMode` or cloud-vs-OSS deployment flag. The "cloud mode" concept from the plan was descriptive, not a runtime toggle. The `querySignal` design naturally handles this by returning `continue` when no reservation exists.
