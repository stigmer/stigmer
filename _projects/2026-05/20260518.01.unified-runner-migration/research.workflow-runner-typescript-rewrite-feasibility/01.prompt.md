# Deep Research: Feasibility of Rewriting Go Workflow Runner (Zigflow/CNCF Serverless Workflows) in TypeScript

## Research Objective

We are evaluating whether to **eliminate our Go-based workflow-runner service** and rewrite it entirely in TypeScript, merging it into a unified TypeScript runner that already handles AI agent execution (LangGraph/deepagents) and Cursor SDK harnesses.

The workflow-runner is a ~19,000-line Go service that implements the **CNCF Serverless Workflow specification** (v0.9/1.0) on top of **Temporal**. It dynamically interprets YAML workflow definitions at runtime — no code deployment is needed for new workflows.

The core question: **Can we achieve production-equivalent CNCF Serverless Workflow execution in TypeScript on Temporal, and is the effort justified given that all code will be AI-generated through Cursor sessions (not hand-written)?**

## Context: Why This Pivot Is Being Considered

1. **We are already unifying Python agent-runner + TypeScript cursor-runner into a single TypeScript runner** (unified-runner-migration project, in progress). Adding the Go workflow-runner to this unification would mean ONE service, ONE language, ONE deployment.

2. **All code is written through AI/Cursor sessions** — not manually. The "effort to rewrite 19K lines of Go" is NOT the same as a human manually porting it. With structured project management (task breakdown, checkpoints, design decisions), AI-authored TypeScript rewrites are tractable.

3. **Go is the ONLY remaining non-TypeScript language** in the runner execution path after the unified migration completes. Eliminating it removes:
   - Go build toolchain (Bazel rules_go)
   - Go dependency management (go.mod separate from pnpm workspace)
   - Separate Docker build stages for Go binary
   - Cognitive overhead of maintaining two languages in the same architectural tier

4. **TypeScript Temporal SDK is production-ready** — Temporal's TypeScript SDK is first-class and used in production by many organizations.

## Current Go Workflow Runner Architecture

### Core Engine: Zigflow (~9,657 lines in 66 Go files)
Based on [mrsimonemms/zigflow](https://github.com/mrsimonemms/zigflow), implementing CNCF Serverless Workflow specification.

**Task types implemented:**
- `call_http` — HTTP requests with response handling
- `call_llm` — LLM calls (OpenAI, Anthropic) with structured config
- `call_agent` — Agent execution delegation (triggers deep agent runs)
- `call_grpc` — gRPC service invocation
- `switch` — Conditional branching
- `foreach` / `for` — Loop iteration
- `parallel` / `fork` — Concurrent execution
- `set` — Variable assignment
- `transform` — Data transformation (jq expressions)
- `eval` — Expression evaluation
- `validate` — JSON Schema validation
- `wait` / `listen` — Event waiting / signal handling
- `emit_event` — Event emission
- `notification` — Webhook notifications
- `try` — Error handling with retries and compensation
- `human_input` — Human-in-the-loop approval within workflows
- `raise` — Error raising
- `do` — Sequential task execution (the root container)
- `run` — Run sub-activities

### Supporting Packages (~9,610 lines)
- `budget` — Execution budget tracking
- `claimcheck` — Large payload offloading to R2/S3 (Claim Check pattern)
- `config` — LLM and Stigmer platform configuration
- `converter` — Proto-to-YAML conversion (WorkflowSpec proto → CNCF YAML)
- `dotenv` — Environment variable loading
- `env` — Runtime environment management
- `events` — Workflow event system
- `executor` — Temporal workflow function (the generic "execute any YAML" workflow)
- `grpc_client` — Platform API clients (workflow execution, instances, contexts)

- `notification` — Webhook delivery

- `temporal` — Search attribute setup
- `types` — Shared type definitions
- `utils` — Runtime expressions (jq), state management, helpers
- `validation` — Workflow validation logic
- `workflows` — Validate workflow Temporal workflow

### Key Dependencies

### Architecture Pattern
```
Java Temporal Workflow (orchestrator)
  → ExecuteWorkflow activity (Go, on workflow_execution queue)
    → hydrates context via gRPC
    → converts proto to YAML
    → starts ExecuteServerlessWorkflow (Go Temporal workflow, on zigflow_execution queue)
      → parses YAML into Serverless Workflow model
      → dynamically builds task graph using Zigflow builders
      → executes tasks as Temporal activities
      → reports progress via interceptor
      → returns results
```

## Specific Areas to Investigate

### 1. CNCF Serverless Workflow SDK in JavaScript/TypeScript
- **Does a `serverlessworkflow/sdk-js` or `serverlessworkflow/sdk-ts` exist?** What version? Is it actively maintained?
- **Model parity**: Does it support the same workflow model (Document, Do, Tasks, CallHTTP, CallFunction, Switch, ForEach, etc.)?
- **YAML parsing**: Can it parse the same YAML format that the Go SDK produces/consumes?
- **Validation**: Does it include workflow validation capabilities?
- If no official SDK exists, what would it take to implement YAML→model parsing in TypeScript? (The CNCF spec is well-documented with JSON Schema)

### 2. Temporal TypeScript SDK Capabilities
- **Workflow determinism**: Can TypeScript Temporal workflows handle the same patterns used in zigflow (dynamic activity registration, recursive task building, state passing between tasks)?
- **Activity patterns**: Does the TS SDK support the same activity patterns — heartbeats, retry policies, local activities, child workflows?
- **Interceptors**: Does the TS SDK have worker interceptors equivalent to Go's `interceptor.WorkerInterceptor`?
- **Search attributes**: Can TypeScript workers upsert search attributes?
- **Performance**: How does TypeScript Temporal worker performance compare to Go for CPU-bound workflow orchestration (parsing, jq evaluation, JSON manipulation)?

### 3. jq Expression Evaluation in JavaScript/TypeScript
- **Is there a production-ready jq implementation for Node.js?** (e.g., `jq-web`, `node-jq`, `@aspect-build/rules_jq`?)
- **Feature parity**: Does it support the full jq language (path expressions, string interpolation, conditionals, try-catch, reduce, custom functions)?
- **Performance**: Can it handle frequent expression evaluation in a hot loop (workflows evaluate expressions on every task)?
- This is CRITICAL — zigflow uses jq pervasively for:
  - Runtime expression evaluation (`${ .context.variable }`)
  - Data transformation between steps
  - Conditional evaluation in switch statements
  - Filtering and mapping in foreach loops

### 4. JSON Schema Validation in TypeScript
- What are the best JSON Schema validation libraries for Node.js? (ajv, @cfworker/json-schema, zod-to-json-schema?)
- Do they support Draft 2020-12 (which CNCF Serverless Workflow uses)?

### 5. Dynamic gRPC Invocation in TypeScript
- The Go workflow-runner uses `grpcurl` library for dynamic gRPC calls (no pre-compiled stubs). Is there an equivalent in TypeScript?
- Can `@grpc/grpc-js` + `@grpc/proto-loader` handle dynamic service invocation from runtime-provided proto definitions?

### 6. Existing TypeScript Serverless Workflow Implementations
- Has anyone implemented CNCF Serverless Workflow spec in TypeScript/JavaScript?
- Are there any TypeScript workflow engines we could build on or learn from?
- What about the official CNCF community — any TypeScript reference implementations?

### 7. Migration Effort Assessment
- Given 19K lines of Go, what is a realistic TypeScript line count for equivalent functionality?
- Which components are straightforward ports vs. require significant rearchitecting?
- What is the testing strategy — can we reuse the 12 golden test YAML files as integration tests?

### 8. Alternative Approaches
- **Keep Go workflow-runner as-is, only unify agent+cursor runners in TS** — what's the long-term cost?
- **Use Go↔TypeScript interop** (e.g., WASM compilation of zigflow, or keep as separate deployment) — viable?
- **Replace CNCF Serverless Workflow with a TypeScript-native workflow DSL** — would this simplify or complicate things?

## The "All Code Is AI-Generated" Factor

This is a crucial consideration. The effort calculation is different when:
- Code is generated in structured Cursor sessions with project management
- Each task is broken down into small, testable units
- Golden tests provide regression safety
- The existing Go code serves as a specification/reference

**Question for research**: Are there documented examples of large Go→TypeScript ports done through AI-assisted coding? What were the success rates, pitfalls, and timelines?

## What Success Looks Like

After this rewrite, the unified TypeScript runner would handle ALL three execution types:
1. **ExecuteDeepAgent** — AI agent execution (LangGraph + deepagents JS)
2. **ExecuteCursor** — Cursor SDK code editing harness
3. **ExecuteServerlessWorkflow** — CNCF Serverless Workflow interpretation (formerly Go zigflow)

Single service, single language, single Docker image, single CI pipeline.

## Context for Why This Matters

This is a **strategic pivot decision**. The unified-runner-migration is already in progress (Phase 0 complete, proceeding to Phase 1). If we decide NOW to also absorb workflow-runner into the unified TypeScript runner, we can:
- Plan the architecture to accommodate all three execution types from the start
- Avoid building infrastructure in TS that later needs to be refactored when workflow-runner joins
- Potentially share more infrastructure (Temporal workers, health reporting, OTel, claim check)

If we DON'T decide now, we'll have:
- A unified TS runner for agents + cursor
- A separate Go service for workflows
- Two deployment targets, two CI pipelines, two Dockerfiles, two languages to maintain

The cost of deferring this decision increases as the unified runner's architecture solidifies.
