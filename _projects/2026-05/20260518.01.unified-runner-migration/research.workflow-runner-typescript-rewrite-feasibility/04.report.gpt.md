# Executive Summary  
TypeScript’s ecosystem today makes a full TS-based Serverless Workflow runner *feasible*, but with caveats. An official **Serverless Workflow TypeScript SDK** exists and is actively maintained【4†L462-L470】【17†L203-L211】, and the **Temporal TypeScript SDK** supports all needed features (activities, child workflows, interceptors, search attributes) with parity to Go【29†L41-L44】【25†L142-L149】. Key dependencies (JSON Schema via **Ajv**, dynamic gRPC via `@grpc/proto-loader`, and jq) are available. However, the **jq expression support** is the biggest unknown: native JS implementations (like [@jq-tools/jq](32)) are incomplete【32†L49-L58】, so most likely one must invoke the real `jq` binary via a wrapper (e.g. **node-jq**【35†L338-L347】). With careful AI-assisted development and extensive testing, a TS runner can reach production parity, but mitigating risks around jq and dynamic gRPC is crucial. Overall, we judge a TS rewrite to be *doable* with **moderate confidence** – roughly **70%** – provided structured AI-driven sprints and reusing the Go runner as a specification.

# Ecosystem Readiness  
- **Serverless Workflow SDK (TS)**: *Ready*. CNCF provides an official TS SDK (`@serverlessworkflow/sdk`) that can parse YAML/JSON, build the model, and validate workflows【4†L462-L470】. It covers spec v1.0* and is actively maintained (frequent commits as of May 2026【17†L203-L211】), matching Go’s model (Document, Tasks, Do, Switch, ForEach, CallHttp, CallFunction/CallFunction, etc.).  
- **JSON Schema Validation (TS)**: *Ready*. Libraries like **Ajv** fully support JSON Schema draft-2020-12 (used by SW spec)【65†L319-L323】. Ajv is high-performance and widely used in Node apps. Other libraries (ajv-cli, Zod→JSON) are available too.  
- **Temporal TypeScript SDK**: *Ready*. The TS SDK supports all workflow/activity patterns needed: deterministic workflows, dynamic activity scheduling, child workflows, heartbeats, retries, interceptors, and search-attribute upsert【25†L142-L149】【60†L648-L654】. There is no known feature in Go’s SDK that TS lacks for this use-case【29†L41-L44】. Performance is comparable for I/O-heavy orchestration; Go only significantly outperforms TS on purely CPU-bound work【29†L44-L52】. TS also has robust testing (mock workflows) and is used in production at many companies.  
- **jq Expression Evaluation (TS)**: *Partial*. No complete, battle-tested jq library for Node exists. **@jq-tools/jq** provides a JS parser/interpreter but admits missing modules and many built-in filters【32†L49-L58】. A safer approach is **node-jq**, which bundles the official jq binary via a post-install step【35†L338-L347】, allowing full jq syntax. This implies shelling out for each query, which adds overhead. Mitigation: preloading data or batching expressions can help. Thorough benchmarking (e.g. comparing node-jq vs gojq) will be needed.  
- **Dynamic gRPC Invocation (TS)**: *Ready*. Node can load and use .proto definitions at runtime via `@grpc/proto-loader` and `@grpc/grpc-js`. The official tutorial shows loading a proto with `protoLoader.loadSync()` and creating service stubs dynamically【51†L316-L324】【51†L328-L333】. Thus TS can replicate Go’s grpcurl-like behavior by reading YAML’s `proto` path, loading it, and invoking `client[method](args)`. No blocking limitation is known.  
- **LLM/Agent Integration**: *Feasible*. TS has ample libraries for OpenAI/Anthropic, and the existing unified runner already handles LLM/agent activities in TS. The workflow-runner’s `call_llm` and `call_agent` tasks can reuse that code.

# Effort Estimate (AI-Assisted Rewrite)  
Given ~19,000 Go LOC (roughly ~10K engine + 10K support), an AI-assisted port can proceed in structured phases. Key steps: design data models (use SDK classes), map each task/activity to a TS module, and implement integration (YAML parsing → TS model → workflow graph execution). Leveraging Cursor, we’d break work into small issues (one task type at a time, plus utilities). 

- **Scoping & Setup (2–4 weeks)**: Bootstrap a new TS project (monorepo with pnpm), integrate Temporal TS, and import the CNCF TS SDK. Define core types and CI pipeline. Reuse Go code and tests as requirements.  
- **Core Task Implementation (8–12 weeks)**: For each Go task type (HTTP, GRPC, LLM, Agent, Switch, Loop, Set, Transform, Eval, Validate, Wait, Emit, Notify, Try/Catch, HumanInput, etc.), implement a TS equivalent activity or workflow logic. Many tasks can reuse existing code (HTTP, JSON, LLM). The largest is `transform/jq`, which requires wrapping node-jq. Each task ~1–2 weeks (with AI help), so ~12–16 weeks total.  
- **Support Components (4–6 weeks)**: Port support packages (config, env, claimcheck, telemetry, validation logic). Many utilities (JSON handling, state mgmt) have TS analogues. Some wiring (heartbeat/health, interceptors) is mostly library-config.  
- **Integration & Workflow Engine (4–6 weeks)**: Build the `executeServerlessWorkflow` TS workflow: parse YAML via SDK, construct task graph (builders), and schedule activities accordingly. This is the port of the Zigflow engine logic. AI can generate scaffolds, but careful testing is needed.  
- **Testing & Hardening (4–6 weeks)**: Reuse the 12 golden YAML test cases from Go. Validate round-trip behavior. Debug determinism issues (e.g. random seeds, timeouts). Fix edge cases.  
- **Total**: Roughly **4–6 months** of calendar time. The AI-assisted process may double throughput vs. hand-coding, but coordination, spec quirks, and debugging still require human oversight. A small team (2–3 developers coordinating via Cursor) could feasibly complete this in ~6 months from kickoff, assuming parallel tasks (one person scaffolds tasks while another tests, etc.). 

# Risk Assessment and Mitigation  
1. **jq Support Incompleteness** – The biggest risk is replicating Go’s full jq usage. TS libraries lack full jq semantics【32†L49-L58】. *Mitigation:* Use **node-jq** or similar to call the C binary (ensuring 100% compatibility)【35†L338-L347】. Cache/join outputs to reduce subprocess overhead. Fallback: simplify workflows to avoid need for obscure jq, or pre-compile expressions.  
2. **Temporal Determinism Issues** – Dynamic work graph building must follow Temporal’s determinism rules. *Mitigation:* Rely on structured scheduling (no random or non-deterministic code in workflows). Use the official Temporal best practices guide; add interceptors for progress (as in Go)【25†L142-L149】.  
3. **Performance Overhead** – TS (Node) workers have higher memory overhead and may be slower for CPU work than Go. *Mitigation:* Offload heavy processing to Activities (possibly using `worker_threads`), and ensure TypeScript workflows do minimal synchronous computation. Real-time performance should be acceptable (Go won’t be drastically faster for our I/O-heavy tasks)【29†L44-L52】.  
4. **AI-Generated Code Quality** – Auto-generated code may contain subtle bugs or style issues. *Mitigation:* Enforce rigorous testing. Use the 12 golden workflows as unit tests and add CI linting. Consider human reviews of critical modules. Automated code review tools and type-safe TypeScript will catch many errors.  
5. **Maintenance of Dual Systems** – If kept separate (Option B/C), complexity grows. *Mitigation:* If undecided, containerize the Go service and share API contracts carefully. But this risk is more about architecture choice than TS feasibility.  
6. **Dependency Gaps** – If any Go-specific feature (e.g. certain Temporal SDK calls, or claim check to R2/S3) lacks TS analog. *Mitigation:* Most libraries (AWS SDK, gRPC, JSONSchema, OpenTelemetry) exist in JS. For any gap, consider writing a thin Node binding or microservice.  
7. **Timeline Overruns** – Underestimating integration challenges or AI limitations. *Mitigation:* Schedule interim demos (Cursor-generated commits) to validate approach early. Maintain the Go runner in parallel until TS is proven.  

# Comparison of Approaches  

- **Option A – Full TypeScript Rewrite (Unified Runner)**:  
  - *Pros:* Single language/service for all runners; simplified CI/CD; sharing code (authentication, telemetry, etc.) between agent, cursor, and workflow execution; no Go toolchain. This aligns with strategic goal of **“ONE service, ONE language”**. The TS SDKs for workflows and Temporal are mature enough, and AI generation lowers the *perceived* effort.  
  - *Cons:* Upfront effort to build the entire engine in TS. Risk of missing subtle behaviors (esp. jq, dynamic GRPC). Requires dedicating time now (the unified-runner architecture may need adjustment). However, given AI support and the reference Go implementation, this is feasible.  

- **Option B – Keep Go Runner Separate**:  
  - *Pros:* No migration risk to production-critical engine. Faster to focus on agent+cursor runner (current priority). The Go runner continues to work as-is.  
  - *Cons:* Two languages/services persist. Ongoing maintenance cost: separate CI/CD, Docker layers, and cognitive load. Future improvements to unified runner (e.g. shared telemetry) remain siloed. Technology stack heterogeneity goes against the unification goal.  

- **Option C – Hybrid (Partial Rewrite)**:  
  - *Pros:* For example, port easier tasks to TS (HTTP, Set, Evaluate) and keep complex parts (the core executor or jq transformer) in Go behind a thin interface (e.g. a child workflow or external activity). This reduces immediate TS effort and risk.  
  - *Cons:* Increases runtime complexity (cross-language calls). Loses most benefits of unification. Ultimately still maintains two runtimes. Might be harder to debug interactions. Benefits are limited unless only a small portion is offloaded.  

# Critical Path and Riskiest Components  
- **Expression Evaluation (`transform`, `switch`, `foreach`)** – Heavily reliant on jq. Ensuring complete jq semantics (filters, interpolation, reduce, try/catch in filters) is the hardest port. Lack of test coverage here could cause silent bugs.  
- **YAML→Model Conversion & Validation** – The TS SDK handles this, but mismatches between what Go’s protobuf conversion expects and what TS produces must be validated. Ensuring every field (extensions, metadata) carries over identically is critical.  
- **Dynamic Workflow Graph Construction** – Recreating Zigflow’s logic in TS: building nested branches, loops, forks at runtime via Temporal APIs. Care must be taken to maintain promise chains and ensure deterministic ordering.  
- **gRPC Invocation** – Parsing `service.name` (e.g. “GreeterApi.Greeter”), loading proto definitions, and invoking methods with correct payload shapes. Edge cases (multiple files, repeated fields, streaming RPCs if ever needed) need careful handling.  
- **AI/Agent Integration** – Less risky (since this logic exists in TS already) but ensure the call_agent flow in TS matches the Go behavior (e.g. reporting, timeouts).  
- **Testing & Iteration** – Ensuring the 12 golden workflows (and any new ones) pass exactly as in Go is the ultimate check. Achieving feature-parity might expose minor spec differences that need adjustment.  

# Conclusion  
A full TypeScript rewrite of the workflow-runner is technically viable and aligns with unification goals. All critical features have TS equivalents or workaround solutions. The effort, while non-trivial, is tractable with AI-assisted development and rigorous testing. We recommend **pursuing the rewrite (Option A)**, with a pilot phase to validate jq and gRPC approaches. Alternatively, if immediate unification risk is too high, one could delay the TS port (Option B) but at the cost of keeping a multi-language deployment. Given the strategic benefits and that AI tools have successfully automated similarly complex migrations (e.g. Java→TypeScript【72†L113-L121】【72†L124-L131】), the rewrite’s effort is justified provided the team enforces strict design, testing, and risk mitigation.

# Inventory of Go Runner Features (Zigflow) 

The Go workflow-runner (Zigflow, ~9.7K lines) implements CNCF SW v0.9/1.0 on Temporal with no pre-compile of workflows. It supports the following task types (from the Go code and spec):

- **`call_http`** – Makes HTTP requests with configurable method, headers, etc., and stores the response.  
- **`call_llm`** – Calls LLM providers (OpenAI, Anthropic) using JSON prompt templates, retrieves model output.  
- **`call_agent`** – Invokes a DeepAgent (AI agent) execution as part of the workflow (delegating to LangGraph/deepagents code).  
- **`call_grpc`** – Calls a gRPC service dynamically (loads .proto, connects, invokes method).  
- **`switch`** – Conditional branching: evaluate an expression (e.g. JSONata or jq filter) to choose a branch.  
- **`foreach` / `for`** – Loop constructs: iterate over an array or index range.  
- **`parallel` / `fork`** – Concurrent flows: execute tasks in parallel (fan-out) and then join.  
- **`set`** – Assign a variable (literal or from an expression).  
- **`transform`** – Data transformation via jq expressions: take input JSON and run jq filter to produce new JSON.  
- **`eval`** – Evaluate a one-off expression (e.g. JSONata or jq) and maybe store result.  
- **`validate`** – Validate data against a JSON Schema.  
- **`wait` / `listen`** – Pause workflow until a timer or external event/signal arrives.  
- **`emit_event`** – Emit an event to a specified channel (Temporal signals/alarms or pubsub).  
- **`notification`** – Send webhook or email notifications.  
- **`try` (Error handling)** – `try/catch` blocks with retry/compensation capabilities.  
- **`human_input`** – Human-in-the-loop approval step (send task to UI, wait for manual response).  
- **`raise`** – Intentionally throw an error to abort or handle.  
- **Root `do` container** – A sequential list of tasks.  
- **`run`** – Execute a sub-workflow (invoke another CNCF SW definition by name/version).

**Supporting packages (Go)** include:
- **`validation`** – JSON Schema validation (`github.com/santhosh-tekuri/jsonschema/v6`).  
- **`gojq`** – jq interpreter (github.com/itchyny/gojq) for expressions.  
- **`grpcurl`** – for dynamic gRPC calls.  
- **HTTP client** – standard Go `net/http` (wrapped).  
- **LLM clients** – `go-openai` (OpenAI), `go-anthropic`.  
- **Temporal SDK** – worker, activities, workflows (`go.temporal.io/sdk`).  
- **`claimcheck`** – offload large payloads to R2/S3.  
- **`otel`** – OpenTelemetry (Go SDK).  
- **`PostHog`** – analytics.

**Architecture Pattern:** A Java/Go “host” workflow (ExecuteWorkflow) invokes a Go activity which translates a stored WorkflowSpec (proto) to YAML and then starts the Zigflow orchestration workflow. Zigflow workflow then parses the YAML, builds a task graph, and schedules each task as a Temporal activity (on its own task queue). Progress is tracked via worker interceptors and gRPC callbacks. 

Each Go task maps to one or more Temporal activities. For example, `call_http` runs an activity that does the HTTP call. `parallel`/`fork` spawn multiple child activities or child workflows concurrently.

# TypeScript Equivalents for Go Runner Features

Mapping each feature to a TS counterpart:

- **YAML Parsing / Workflow Model:** Use `@serverlessworkflow/sdk` to parse YAML at runtime. Example:  
  ```ts
  import { Classes } from '@serverlessworkflow/sdk';
  const wf = Classes.Workflow.deserialize(yamlText);  // parses YAML to object model【82†L462-L470】 
  wf.validate();  // throws if invalid【82†L615-L622】
  ```
  The TS model has classes for every task type (`Classes.SetTask`, etc.), so we can navigate the workflow graph similarly to Go’s Zigflow.

- **Task Execution:** Implement each CNCF task as a TS workflow or activity:  
  - *Activities:* Many tasks (HTTP, LLM, gRPC, notifications) will be **activities** implemented in Node. Temporal TS defines activities using `@temporalio/activity`. These can use npm libraries (e.g. `axios` for HTTP, `openai` for LLM).  
  - *Workflows:* Control-flow tasks (`switch`, `foreach`, `parallel`) and sequential composition (`do`) are done inside a **workflow** using `@temporalio/workflow` APIs (which are just async functions + helpers). Conditionals/loops are natural in TS (with `if` and `for`). For parallel forks, use `Promise.all` or `yield parallel()` patterns.  
  - *Set:* Map directly to a JS assignment on the workflow’s in-memory variables or we maintain a workflow state object. The TS code can just do `const x = <value>`.  
  - *Transform/Eval:* For jq expressions in e.g. `${ ... }`, use `node-jq` (see below) from an activity or within a workflow (if needed in decision logic). Alternatively use a JS expression evaluator for simple cases.  
  - *Validate:* Use a JSON Schema library (Ajv) in an activity to validate data; throw error on failure.  
  - *Wait/Listen:* Use `workflow.sleep()` for delays; for waiting on signals, use `workflow.await()` on a channel. The TS SDK supports `workflow.signal()` and `workflow.condition()`.  
  - *Emit Event:* Implement by signaling other workflows or sending external events (e.g. Pub/Sub via an activity).  
  - *Notification:* Activities to send HTTP webhooks or emails (using Node HTTP/email libs).  
  - *Human Input:* Likely a client front-end integration, not core TS runner code. The workflow can pause for signal (like `workflow.await()` for a specific event) that the UI triggers.  
  - *Raise:* `throw new Error(...)` in a workflow.  
  - *Try/Catch:* In TS workflow code, use `try { ... } catch (ex) { ... }`. Temporal’s interceptor can implement retry according to spec.  
  - *Run (sub-workflow):* TS can call `startChild()` on a workflow to invoke another workflow definition (which could be the same TS engine on a child queue) with arguments.

For each activity, a helper function can convert the CNCF task spec to TS parameters. For example, a `CallHTTP` TS activity might take `{ url, method, headers, bodyExpr }`, evaluate `bodyExpr` if needed, make the fetch, and return response. The Go code’s logic (timeouts, error handling) should be replicated.

**Interceptors/Telemetry:** Temporal TS supports interceptors for workflows and activities. We can register logging/metrics interceptors in the worker (analogous to Go interceptors)【87†L142-L151】. OpenTelemetry JS can be integrated via these interceptors.

**State Management:** The Go runner has a `state` object tracking variables. In TS workflow code, local variables or a JS object can track state. Because TS workflows run in a single-threaded event-loop, concurrency control is inherent (with async/await). Complex state can be JSON, which TS handles natively.

Any custom extensions in Go’s YAML (like `call_llm`) may need bespoke handling or extension of the model. But since YAML parsing is flexible, adding new types is possible (e.g. supporting a `call_llm` key).  

# Temporal TypeScript SDK Capabilities

- **Determinism Constraints:** Temporal requires workflow code to be deterministic. The TS SDK enforces this by forbidding certain operations (no use of Math.random(), Date.now(), or platform I/O directly). All calls to Temporal APIs (`sleep`, `query`, `signal`, `continueAsNew`, etc.) must come from `@temporalio/workflow`. Dynamic control flow (if/for) is fine as long as it’s based on workflow state. Using dynamic activity names is allowed (the TS client has `scheduleActivity` where activity types are strings). The Go Zigflow uses dynamic graphs too, so TS must carefully ensure the same graph is created on replay. In practice, constructing a workflow graph from the fixed YAML spec (with no external randomness) should be deterministic.  
- **Activity Patterns:** The TS SDK supports all standard patterns: activity heartbeats (`extendSession()` or heartbeat calls in activities), retry policies (defined via `ActivityOptions`), local activities (by annotation or within workflows), child workflows (`Client.startChild()`), and continuing-as-new. The worker can be configured with task queues like in Go.  
- **Interceptors:** Yes – as shown, TS has Worker and Workflow interceptors【87†L142-L151】. We can use these for logging, metrics (OTel) and progress reporting. The Node examples show interceptors for scheduling activities. Worker-wide interceptors (such as for heartbeats) can wrap activity execution similarly.  
- **Search Attributes:** The TS SDK allows upserting search attributes on Workflow start or within a workflow (via `workflow.upsertSearchAttributes({ ... })`). The samples explicitly list “upsert and read Search Attributes”【60†L648-L654】. These APIs mirror Go’s `workflow.UpsertSearchAttributes`. So yes, custom search attributes are fully supported.  
- **Performance:** The TS SDK is interpreted (JavaScript) rather than compiled, so raw CPU tasks are slower than Go. However, Temporal workloads are typically I/O-bound (waiting on external calls) and involve JSON manipulation. In those cases, the performance difference is modest【84†L41-L48】. The forum suggests use of `worker_threads` for heavy compute in Node. For our use case, the overhead will mostly be in HTTP/LLM calls anyway. As a sanity check, one should benchmark a few representative workflows (e.g. large transforms, many parallel tasks) in Go vs TS. But the community consensus is that TS performance is acceptable for most workloads【84†L44-L48】. TS memory usage is higher, but given cloud resources, this is likely fine.  
- **Deterministic Workflows with Dynamic Schedules:** Zigflow built the graph dynamically based on the YAML. In TS, we would read the YAML, then use it to schedule activities one by one (or in parallel). As long as the logic is coded deterministically (e.g. process tasks in the order given), this will replay correctly. Care must be taken if using any `random()` or unsupported libs.  

# jq Expression Evaluation in Node

Zigflow uses [jq](https://stedolan.github.io/jq) for variable interpolation and data transforms. In TS:

- **Node-jq:** The `node-jq` NPM package is a JS wrapper around the actual jq binary【89†L346-L352】. It **downloads jq** (via a postinstall script) into `node_modules/node-jq/bin/jq`【89†L346-L352】. Usage is `jq.run(filter, input, options)` returning a Promise of JSON string or object. This provides 100% compatibility with jq filters at cost of spawning a process. Benchmarks should measure the latency (e.g. <10ms for small JSON? possibly higher for big data). Using it in hot loops (per record in a large array) may be slow; consider batching or using `.split('--stream')`.  
- **jq-web:** A pure JS/WebAssembly port exists (called `jq-web`), but it’s largely unmaintained and was slower in tests; we did not find a robust recent project.  
- **@jq-tools/jq:** A native TypeScript implementation. It can parse jq code (`parse()`) and evaluate (`evaluate()`), but as noted, many jq features (modules, complex built-ins) are missing【90†L49-L58】. For simple filters it may work. However, since Zigflow uses jq extensively (set, transform, filter in loops, etc.), relying on an incomplete interpreter is risky. It may be usable for limited expressions, but not all.  
- **Conclusion:** Likely approach is to **use node-jq** for full coverage. We should benchmark: e.g. run thousands of filters (simple and complex) on sample JSON to quantify overhead. If performance is an issue, an alternative is to run one long-running jq subprocess and feed multiple queries (not typical usage) or implement frequently-used patterns in native JS (e.g. simple attribute access in TS). But for correctness, using the real jq is safest.  

# JSON Schema Validation in TypeScript

- **Libraries:** The de facto choice is **Ajv** (Another JSON Schema Validator)【65†L319-L323】. It is extremely fast (generates optimized code), supports all keywords of Draft 2020-12 and beyond【65†L319-L323】, and is widely used. AJV can compile schemas to validator functions. Other options: `z-schema` (less active now), `@cfworker/json-schema`, or using zod / JTD. But Ajv is best-in-class for JSON Schema.  
- **Draft Support:** Ajv v8+ supports up to Draft 2020-12 out of the box【65†L319-L323】. Since SW spec uses that, Ajv can validate any workflow definition or task input.  
- **Performance:** Ajv generates fast JS code; it's comparable to Go’s JSON schema libs. Validating a workflow schema or payload (hundreds of fields) should be sub-10ms. For large payloads, it might take more time, but use cases (validation) are infrequent. We should reuse/compile schemas (CNCF publishes them) and avoid recompiling each time.  
- **Pitfalls:** Ajv has “allErrors” and “coerceTypes” options that change behavior; we should carefully configure (likely allErrors = false, fail-fast on first error). Also watch out for `patternProperties` in the spec if any (some older JSON validators struggled). In practice, Ajv is reliable for standard SW schemas.  

# Dynamic gRPC Invocation in TypeScript

TypeScript can dynamically call gRPC services using the `@grpc/proto-loader` and `@grpc/grpc-js` packages:

- **Loading Protos:** Use `protoLoader.loadSync(protoPath)` to load a `.proto` file at runtime (the Go YAML likely gives a file path or URL). Then `grpc.loadPackageDefinition(...)` returns the service descriptors【51†L316-L324】. E.g. after loading, if the service is `GreeterApi.Greeter`, you can do:  
  ```js
  const packageDef = protoLoader.loadSync('greet.proto', {/*options*/});
  const grpcObject = grpc.loadPackageDefinition(packageDef);
  const Greeter = grpcObject.GreeterApi.Greeter;
  const client = new Greeter(host+':'+port, grpc.credentials.createInsecure());
  ```
- **Calling Methods:** Given a client instance, you can call methods dynamically: `client.sayHello({ name: "Alice" }, callback)` or use the promise API (`client.sayHello().then(...)`) if promisified. Methods and message types come from the loaded descriptors.  
- **Streaming:** The TS gRPC client supports unary, client-streaming, server-streaming, and bidi. If a workflow spec requires streaming RPCs, TS can handle them by writing to or reading from the returned stream object.  
- **Edge Cases:** 
  - *Service Names:* Ensure the YAML’s `service.name` (e.g. `"GreeterApi.Greeter"`) matches how `grpc.loadPackageDefinition` exposes it. If nested packages exist, traverse `grpcObj.Package.Subpackage.Service`.  
  - *Imports:* If `.proto` imports others, `protoLoader` resolves them if given include paths. 
  - *Reflection:* As an alternative, there is [grpc-reflection-js](https://www.npmjs.com/package/grpc-reflection-js) which can discover services from a running server, but since Zigflow already fetches `.proto`, not needed.  
- **Feasibility:** Highly feasible; Node’s gRPC ecosystem is mature. The example in docs【51†L316-L324】【51†L328-L333】 shows exactly this approach.  

# Other Dependencies

- **OpenAI/Anthropic Clients:** As mentioned, use official TS packages (`openai` npm and `@anthropic-ai/sdk`【92†L1-L3】). These are production-ready. E.g. `const openai = new OpenAI(...); const resp = await openai.chat.completions.create(...)`. They support streaming and retry.  
- **S3/R2 (Claim Check):** Use AWS SDK v3 for Node (`@aws-sdk/client-s3`) to upload/download payloads. For R2, same S3 APIs work. The SDK is TypeScript and maintained. If Go code splits large data into S3, replicate logic.  
- **OpenTelemetry:** Use `@opentelemetry/api` and exporters (OTLP, Jaeger, etc.). There are TS examples for integrating with Temporal via interceptors【87†L142-L151】.  
- **PostHog Analytics:** Use `posthog-node` to send events. The Go runner uses PostHog for telemetry; the TS port can do similarly in activities.  

# Existing TypeScript Workflow Implementations

We found **no prior open-source TS engine for CNCF Serverless Workflow**. The CNCF project lists SDKs in many languages, but only Java, Go, Python, .NET, Rust, TS. There’s no reference TS runtime. Zigflow itself is the de-facto Go reference. Some community demos (e.g. a NestJS or AWS Step Functions connector) exist, but for our needs the official TS SDK plus a custom executor is the path. (If CNCF incubates a TS engine in future, we could reuse it, but none exists now.)

  2. **Implement Simple Tasks (4–6 weeks):** `set`, `switch`, `foreach`, `parallel`, `notification` – straightforward logic. Parallel tasks can reuse Promise patterns.

  5. **gRPC Task (2–3 weeks):** Use `@grpc/proto-loader` logic above.

  7. **Validation (1 week):** Set up Ajv with CNCF JSON Schemas.

- **TS LOC Estimate:** Possibly ~25K including comments. Many utility functions (env, config, converters) will be re-implemented.  
- **Testing Strategy:** Reuse the 12 canonical workflow YAMLs as end-to-end tests, comparing the final state/responses. Also write unit tests for each activity. Use Temporal’s test framework for unit-testing workflows (TypeScript sample code exists). Include CI workflow to run these before merge.  

# AI-Generated Code Factor

There are **case studies** of AI (LLM) assisted migrations. For example, Aviator’s report on migrating a large Java codebase to TypeScript via LLM agents shows success by *decomposing tasks, planning steps, and using CI-based validation*【72†L113-L121】【72†L124-L131】. This suggests the approach is promising: let the AI break down each Go file into TypeScript tasks, use automated tests (the golden workflows) to catch regressions, and iterate.

**Pitfalls:** AI may hallucinate or produce non-idiomatic code. We must enforce **strict review gates**. The plan:
1. **Break tasks into small chunks** (Cursor issues). 
2. For each chunk, use the existing Go code + spec to prompt the LLM and generate TS code.
3. Immediately test the output (unit tests from golden examples).
4. Use the 12 golden workflows as regression tests after every major commit.
5. Conduct pair-programmer style review of AI output for correctness.

No known public data on “AI rewriting a Go codebase” specifically, but the above case study confirms multi-LLM agents can handle similarly complex work. Timeline for that Java→TS migration was a few weeks for thousands of files【72†L113-L121】【72†L124-L131】. We should proceed iteratively.
