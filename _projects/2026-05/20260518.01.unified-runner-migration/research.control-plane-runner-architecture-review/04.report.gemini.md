# **Architectural Diagnostics and Strategic Realignment: Control Plane and Runner Dynamics in AI Agent Platforms**

The architecture of distributed execution platforms requires a delicate and precise equilibrium between control plane orchestration and data plane execution. In the context of modern AI agent platforms—specifically those leveraging durable execution backbones such as Temporal—the design of the execution environment (the "Runner" or "Worker") dictates not only system scalability and fault tolerance but also developer experience and third-party adoption rates.  
This exhaustive research report investigates a critical architectural crossroad observed in the Stigmer AI platform: determining whether the current implementation of a highly stateful, API-managed, bi-directionally streaming runner is fundamentally overengineered. This inquiry is catalyzed by a highly significant diagnostic signal: the explicit friction and subsequent abandonment of the runner integration by an early-adopter customer. In platform engineering, when an early adopter struggles to embed an execution engine, the failure rarely stems from inadequate documentation; it almost universally indicates a misaligned abstraction layer that forces the consumer to manage infrastructural complexity rather than business logic.  
The ensuing analysis provides an evidence-based assessment of the control-plane-to-runner separation, evaluates comparative industry architectures, dissects the specific overengineering signals within the current design, and proposes a strategic realignment toward an anonymous, per-session worker model distributed via a lightweight NPM package.

## **1\. Comparative Analysis of Control Plane and Worker Architectures**

To establish a definitive baseline for industry standards regarding distributed execution, an exhaustive analysis of leading Continuous Integration/Continuous Deployment (CI/CD) systems, workflow orchestrators, and AI agent execution sandboxes was conducted. The objective is to map the architectural spectrum from "anonymous worker pools" to "fully managed nodes," specifically isolating how mature systems handle registration, state management, heartbeat protocols, and user visibility.

### **1.2 Macro-Architectural Trends and Deductions**

The comparative data reveals several macro-architectural trends that directly contradict the "Kubernetes Node" pattern currently implemented in the Stigmer architecture. The prevailing logic across highly scalable, distributed systems heavily favors simplicity at the edge and complexity at the core.

#### **1.2.1 The "Dumb Poller" Paradigm**

Across Temporal, Prefect, Windmill, n8n, and various CI/CD runners, the execution agent is fundamentally designed as a stateless, ignorant consumer. It does not possess a Create, Read, Update, Delete (CRUD) API, nor does it maintain or report complex lifecycle states to a central authority. Its entire operational directive consists of booting, authenticating against a queue, pulling a payload, executing it, and reporting the result. Windmill provides a striking example of this: its workers simply poll a PostgreSQL database every 50 milliseconds using a SELECT FOR UPDATE SKIP LOCKED query.39 This architecture effortlessly scales to thousands of requests per second without requiring a dedicated worker management API, because the database transaction itself manages the concurrency and state.40 Prefect's evolution is equally telling; the platform deliberately migrated from an "Agent" model (which required complex, localized infrastructure management) to a "Worker" model that simply polls predefined "Work Pools," shifting the configuration burden away from the execution process and back to the control plane.28

#### **1.2.2 The Egress-Only Communication Imperative**

Modern hybrid architectures—most notably Dagster Cloud, GitHub Actions, and GitLab Runners—explicitly prohibit bi-directional streams or inbound command channels originating from the control plane.3 They rely entirely on outbound long-polling or gRPC streams initiated by the worker.5 This design choice is not accidental; it systematically eliminates firewall ingress rules, Network Address Translation (NAT) traversal complexities, and the need for convoluted launch token handshakes. By ensuring that the worker is always the client and the control plane is always the server, these systems guarantee that workers can be deployed in highly restrictive corporate Virtual Private Clouds (VPCs) or ephemeral container environments without network friction.35

#### **1.2.3 Delegation of State to the Durable Backbone**

In systems backed by Temporal, the worker process is deliberately amnesiac. It never tracks "current executions," calculates "idle since" metrics, or exposes a custom status API. Temporal's internal Visibility and Event History subsystems natively handle all state tracking.22 The Temporal cluster maintains the definitive source of truth regarding which workflow is running on which task queue, and which activities have timed out. Attempting to duplicate this state management at the runner level introduces distributed system anti-patterns, specifically the dual-write problem and state divergence.

#### **1.2.4 SDKs Override Custom Protocols**

For platforms designed to be embedded by third-party developers—such as E2B, Modal, and LangGraph—the integration interface is invariably an SDK, never a standalone service requiring protocol implementation.47 Developers invoke a programmatic class (e.g., Sandbox.create() in E2B, or new Worker() in Temporal).24 This encapsulates the complex orchestration logic, allowing the consuming developer to focus entirely on passing their specific business logic (or AI agent prompts) into the execution environment. The current Stigmer approach, which forces a third-party developer to interface with a managed service protocol, fundamentally violates this SDK-first expectation.

## **2\. Architectural Diagnostics: The Overengineering Verdict**

The customer adoption failure serves as the most critical diagnostic signal in this entire analysis. When an early-adopter software engineer struggles to integrate an execution runner, the failure is rarely due to a lack of documentation. It is almost always indicative of a mismatched abstraction layer. The developer wishes to execute an AI agent, but the platform demands that they first manage a distributed node.  
The central inquiry—*Have I overengineered the runner concept?*—can be answered definitively and supported by extensive evidence: **Yes. The architecture is severely overengineered for its current and medium-term requirements.** The design has erroneously conflated the responsibilities of a multi-tenant cluster orchestrator (analogous to a Kubernetes Control Plane) with the responsibilities of a single-tenant task executor.  
The following sections dissect the specific components of the current Stigmer architecture, separating the justified functionality from the fundamentally overbuilt abstractions.

### **2.1 The Formal Runner API Resource (Overbuilt)**

The decision to model the Runner as a formal platform resource (ai.stigmer.agentic.runner.v1) featuring a rich status object, complete CRUD operations, and a rigid 6-phase lifecycle (PENDING → STARTING → READY ↔ BUSY → STOPPED / FAILED) is a profound instance of architectural overengineering.  
The fundamental flaw lies in the application of the "Kubernetes Node" pattern. A Kubernetes Node runs the kubelet daemon, which must monitor disk pressure, calculate memory utilization, manage the container runtime interface, and orchestrate hundreds of isolated, disparate Pods for various tenants. Conversely, the Stigmer runner handles one to three concurrent function executions inside a V8 JavaScript isolate or a CNCF workflow engine. Applying a node-level API to what is essentially a single application process introduces massive protocol overhead without delivering corresponding utility.  
Furthermore, this custom lifecycle creates a direct state machine conflict. Temporal is inherently designed as a highly robust, fault-tolerant state machine.25 Temporal activities possess native heartbeats, highly configurable timeouts, and sophisticated retry policies.59 By overlaying a custom 6-phase lifecycle on top of Temporal workers, the Stigmer architecture introduces race conditions. If Temporal determines a worker is healthy and actively processing a long-running AI generation task, but the Stigmer Control Plane marks it STOPPED because a custom 30-second heartbeat packet was dropped by the network, the system experiences split-brain state inconsistencies.  
**Verdict:** The entire RunnerQueryController and RunnerCommandController gRPC services are redundant and harmful to system stability. The concept of a "Runner" as a persistent, mutable database entity managed by the control plane should be eliminated entirely.

### **2.2 The Bi-directional Command Stream (Overbuilt and Anti-Pattern)**

The bi-directional gRPC command stream, specifically designed to push commands such as ListDirectory to the runner, violates the core software engineering principle of separation of concerns.  
The architectural mismatch occurs by mixing the control plane (task orchestration) with the data plane (filesystem interaction). Orchestrating the start and stop of AI agent tasks is a control plane function properly handled by Temporal. Filesystem browsing is a synchronous data plane function. Routing a ListDirectory command through the durable execution orchestrator's connection stream is highly inefficient.  
When evaluating alternatives, the constraints of the deployment models must dictate the solution. For the local desktop application, the Electron main process already possesses native, unrestricted Node.js filesystem access. The user interface should communicate directly with Electron via standard inter-process communication (IPC) channels for file browsing, completely bypassing the runner protocol. For the cloud deployment (the Daytona sandbox), the industry standard approach—utilized by platforms like E2B—is to deploy a lightweight, dedicated HTTP server or SDK sidecar that exposes precise filesystem APIs (read, write, list) independent of the execution engine.49  
**Verdict:** The bi-directional command stream is an anti-pattern. Eliminating it removes the necessity for complex heartbeat parsing, stream authentication logic, and custom timeout management, vastly simplifying the runner's codebase.

### **2.3 The Launch Token Handshake (Unnecessary Friction)**

The browser-to-CLI credential flow, utilizing a stigmer:// URL scheme for a "Launch Local Runner" action, is an elegant technical solution to a problem that should not exist. Because the Stigmer architecture erroneously treated the runner as a standalone daemon requiring persistent, authenticated registration with the control plane, it forced the creation of a complex handshake mechanism.  
If the runner transitions to an embedded NPM package running implicitly within the Electron application's lifecycle, the Electron application itself already holds the user's authentication context. It can simply pass this context to the embedded library. Similarly, in the cloud environment, the control plane provisions the sandbox and securely injects the necessary environment variables prior to boot.  
**Verdict:** Launch tokens are a manifestation of incidental complexity. By embedding the runner, the necessity for explicit user-driven authentication handshakes evaporates.

### **2.4 Multi-Process Tracking (Premature Abstraction)**

Maintaining an internal process\_executions map with distinct keys for "agent," "cursor," and "workflow" inside the runner adds significant internal complexity. Given the ongoing migration to a unified TypeScript runner, the underlying execution medium—whether it is a LangGraph agent involving a 10-module middleware stack, a Cursor SDK harness, or a CNCF Serverless Workflow engine—is ultimately just a different Temporal Activity type mapped to the same underlying Task Queue.  
Temporal inherently tracks which activities are executing, how long they have been running, and their current state.22 Building custom concurrency tracking logic inside the runner duplicates Temporal's native visibility and event history features.25  
**Verdict:** The runner should not introspect its own diverse workloads for reporting purposes. It should simply execute the function invoked by Temporal and allow the Temporal cluster to maintain the ledger of active processes.

## **3\. Evaluating the "Anonymous Worker" Paradigm**

The counter-proposal to the current architecture involves stripping the runner of its API entirely, treating it as an anonymous Temporal worker that simply polls a task queue. This is not merely a theoretical alternative; it is the correct, proven architectural pattern for any system built upon Temporal's durable execution backbone.

### **3.1 The Mechanics of the Anonymous Worker**

In this streamlined paradigm, the @stigmer/runner NPM package acts as a highly specialized, opinionated wrapper around the core @temporalio/worker library.

1. **Absence of Registration:** The worker completely ceases to announce itself to the Stigmer control plane. It does not exist in a relational database table. Upon instantiation, it simply opens a standard gRPC long-poll to the Temporal cluster, targeting a specific Task Queue.23  
2. **Implicit Liveness Management:** The platform relies entirely on Temporal to maintain worker liveness. If a worker process crashes, is terminated by an out-of-memory error, or loses network connectivity, the long-polling connection drops. Temporal instantly recognizes this disconnection and automatically re-routes pending and retriable tasks to other available workers polling that exact queue.22  
3. **Stateless Compute:** The runner becomes entirely disposable compute. It holds no state other than the active memory required for the currently executing task.

### **3.2 Strategic Trade-offs: Gains Versus Losses**

Transitioning to an anonymous worker model introduces profound simplifications, though it requires abandoning certain platform-centric features.  
**Primary Gains:**

* **Massive Codebase Reduction:** The architectural shift allows for the deletion of two distinct gRPC controllers, complex database schemas, heartbeat parsing logic, stale-runner cron jobs, and launch token exchange flows. This directly translates to lower maintenance overhead and fewer potential points of failure.  
* **Superior Developer Experience (DX):** Third-party integration effort plummets. Instead of spending days implementing a complex protocol with bidirectional streaming and state reporting, a developer spends minutes configuring a standard NPM package.  
* **System Resilience:** Eliminates the split-brain risk between Temporal's immutable event history and Stigmer's custom runner state, ensuring strict consistency.

**Acknowledged Losses and Mitigations:**

* *Loss:* The platform loses the ability to present a real-time UI dashboard showing hardware metrics (OS, architecture, runner version) of idle worker machines.  
  * *Mitigation:* This is fundamentally a vanity metric. Users care about the state of their *Session* or *Execution*, not the hardware running it. If a Temporal workflow transitions to Running, the UI updates to reflect that the AI agent is thinking. Hardware observability, if strictly required by enterprise customers, should be handled by standard OpenTelemetry (OTel) sidecars emitting to dedicated observability backends like Datadog, rather than shoehorned into a transactional application database.48  
* *Loss:* The ability to push a ListDirectory command over the gRPC stream.  
  * *Mitigation:* As previously established, this data-plane operation must be decoupled. In the desktop environment, use IPC. In the cloud environment, deploy a secondary, lightweight HTTP container alongside the runner specifically for filesystem APIs.

## **4\. The Per-Session Runner Model: Ephemeral over Persistent**

The most elegant and scalable solution to routing and compute isolation in an AI agent platform is the "Per-Session Runner Model," which directly leverages Temporal's capability to dynamically generate task queues.

### **4.1 Concept and Routing Mechanics**

The current model relies on persistent runners sitting idle, waiting for active sessions to be bound to them via a session.spec.runner\_id mapping. The per-session model inverts this routing logic entirely: **The unique Session ID becomes the Temporal Task Queue name.**  
Temporal Task Queues are lightweight, dynamically allocated strings.23 They do not require explicit creation, pre-registration, or provisioning via an API.23 When a workflow execution or an activity is invoked with the parameter task\_queue="session-xyz-123", the Temporal cluster instantly creates the queue in memory.23

* **Initialization Flow:** When a user opens the desktop application and starts a new conversation (Session A), the embedded Stigmer library instantiates a Temporal Worker configured to listen to taskQueue: "session-A".  
* **Execution Flow:** The user submits a prompt. The Stigmer Control Plane receives the API call and determines it belongs to Session A. The control plane dispatches a Temporal Workflow representing the agent execution, explicitly targeting taskQueue: "session-A".  
* **Routing Resolution:** The Temporal cluster seamlessly routes the workflow directly to the user's local application process, which is the sole consumer polling that specific queue.

### **4.2 Unifying Disparate Deployment Modes**

This dynamic routing model elegantly and completely unifies the two radically different deployment paths (Local Desktop and Cloud Sandbox):

1. **Local Desktop (Implicit Background Worker):** The Electron app manages the lifecycle of the @stigmer/runner instance entirely in the background. It derives the task queue name from the active session context. If the user has multiple concurrent sessions open, the application can either spawn multiple lightweight Temporal Workers within the same Node.js process, or configure a single worker to poll multiple distinct queues. The user is never exposed to the concept of a "runner."  
2. **Cloud Sandbox (Ephemeral Provisioning):** When a web user initiates a session, the control plane orchestrates the provisioning of a Daytona sandbox. As part of its automated boot script, the sandbox executes the @stigmer/runner, injecting the specific session-ID to dictate the task queue. The runner pulls work, executes the agent, and upon session termination, the entire sandbox is destroyed. The control plane orchestrates the *sandbox infrastructure*, but it never manages a conceptual *Runner* object.

### **4.3 Industry Precedents: Temporal Worker Sessions**

This specific pattern is highly documented and utilized within the Temporal ecosystem. Temporal provides a "Worker Sessions" API designed explicitly for use cases—such as file processing, machine learning model training, or AI agent state accumulation—where an Activity Task must be guaranteed to route to a specific Worker Process to ensure data locality.62  
While the Go SDK features a built-in API for Worker Sessions 65, TypeScript implementations achieve the exact same functionality manually by generating unique, dynamic Task Queue names for specific worker instances or sessions.64 By adopting this pattern, Stigmer aligns perfectly with established Temporal best practices for affinity routing, eliminating the need for a custom runner API to handle execution assignments.

## **5\. Blueprint: Runner as an Embeddable Library (SDK Pattern)**

The strategic shift of the runner into an NPM package (@stigmer/runner) dictates that its architecture must behave strictly like a library, not a managed service daemon. Third-party developers tasked with orchestrating AI agents inside their own proprietary infrastructure will swiftly reject any SDK that forces them to integrate with a heavy, external orchestration control plane.

### **5.1 The Target Programmatic API Surface**

The integration surface must be trivially simple, mirroring the frictionless developer experience provided by tools like the Vercel AI SDK or the core Temporal SDK itself. The target user-facing TypeScript API should encapsulate all complexity, exposing only what is necessary to connect to the durable backbone and define the execution environment.

TypeScript  
import { createStigmerRunner } from '@stigmer/runner';  
import { myCustomEnterpriseTools } from './tools';  
import { customAuthMiddleware } from './middleware';

/\*\*  
 \* The third-party developer instantiates the runner with their specific context.  
 \* They do not need to register this runner via a REST API.   
 \*/  
const runner \= createStigmerRunner({  
  // Connection to the durable execution backbone  
  temporalAddress: process.env.TEMPORAL\_ADDRESS || 'localhost:7233',  
  temporalNamespace: 'default',  
    
  // Connection to Stigmer only for artifact storage and artifact retrieval  
  stigmerEndpoint: 'https://api.stigmer.ai',   
  stigmerToken: process.env.STIGMER\_AUTH\_TOKEN,

  // The dynamic queue defining where this runner receives work  
  sessionTaskQueue: process.env.SESSION\_ID,  
    
  // Pluggable execution environments (LangGraph, workflows, etc.)  
  agentMiddlewares: \[customAuthMiddleware,...defaultMiddlewares\],  
  customTools: myCustomEnterpriseTools,  
});

// Start the underlying Temporal worker polling mechanism  
await runner.start();  
console.log(\`Runner actively polling for session: ${process.env.SESSION\_ID}\`);

// Ensure graceful shutdown to allow Temporal to re-route pending tasks  
process.on('SIGTERM', async () \=\> {  
  await runner.stop();  
  process.exit(0);  
});

### **5.2 Control Plane Knowledge and Ignorance**

A critical aspect of this architecture is what the control plane *does not* know. The Stigmer control plane requires **absolutely no knowledge about the runner's hardware, its operating system, or its internal process state.**  
The control plane's sole concern is the state of the *Workflow Executions*. If a third-party developer utilizes the SDK to spin up 50 instances of @stigmer/runner within their own Kubernetes cluster to handle massive concurrency, the Stigmer control plane remains blissfully unaware. It simply pushes AI execution payloads to the agreed-upon Temporal Task Queues. The developer assumes responsibility for scaling their own compute resources, utilizing standard Kubernetes metrics (like CPU usage or Temporal queue backlog) rather than relying on custom Stigmer API metrics. This is identical to how Dagster Cloud offloads compute management to the user's local hybrid agent.35

### **5.3 Abstraction of the Execution Engines**

The runner remains a highly sophisticated piece of software internally. It continues to house the complex LangGraph middleware stack (including loop-detection, HITL approval gates, and multi-provider proxies), the Cursor IDE harness, and the CNCF Serverless Workflow engine.  
However, these disparate execution modalities are implemented simply as a robust set of distinct Temporal Activities. The complexity is encapsulated entirely *behind* the runner.start() method. The end-user does not manually manage the transitions between these engines; the incoming Temporal workflow payload intrinsically dictates which activity function is invoked by the worker. The user perceives a unified execution sandbox, completely shielded from the orchestration mechanics.

## **6\. Risk Assessment and Strategic Trade-offs**

Simplifying an architecture by aggressively excising the control plane's runner management protocols carries specific risks. A robust engineering assessment must address what capabilities are lost when reducing the runner to an anonymous polling mechanism.

### **6.1 The Loss of Global Hardware Observability**

**Risk:** By treating runners as anonymous workers, the platform loses the ability to present an administrative dashboard displaying a global fleet of "Active Runner Machines" indicating OS variants, system architecture, and local memory usage. **Mitigation:** This metric is largely a vanity metric for the platform provider and is wholly irrelevant to the end user. If hardware observability is strictly required for debugging or enterprise compliance, the platform should leverage standard OpenTelemetry (OTel) tracing. The @stigmer/runner SDK can emit OTel spans directly to a dedicated observability backend (e.g., Datadog, Prometheus).48 Building hardware telemetry into the application's transactional control plane database is an anti-pattern that creates unnecessary scaling bottlenecks.

### **6.2 Decoupling Filesystem Operations in the Cloud**

**Risk:** Stripping the bidirectional command stream removes the web UI's inherent ability to browse the filesystem of a remote cloud sandbox (e.g., for workspace selection or artifact inspection). **Mitigation:** The architecture must enforce a strict decoupling of execution orchestration from workspace management. In the cloud sandbox environment (Daytona), deploy a secondary, highly focused container—or run a lightweight Node.js Express server on a different port within the same sandbox—alongside the runner. This dedicated server exposes a standard REST or GraphQL API strictly for filesystem operations (List, Read, Write). The Web UI communicates directly with this file server via standard HTTP requests. This maintains rigorous architectural hygiene: Temporal handles durable execution and workflow orchestration, while HTTP handles synchronous data-plane file manipulation. This mirrors the approach taken by advanced sandboxing platforms like E2B, which utilize specific API gateways to interact with the sandbox filesystem.49

### **6.3 Proliferation of Zombie Queues**

**Risk:** If every unique session generates a dynamic Temporal task queue, abandoning a session or encountering a hard crash leaves a "dangling" or "zombie" queue in the Temporal cluster. **Mitigation:** This is a solved problem within the Temporal ecosystem. Temporal automatically garbage collects unused, empty task queues after a specified period of inactivity.23 Because the queues are lightweight and dynamically allocated, thousands of abandoned session queues pose no threat to cluster stability and require zero explicit cleanup engineering effort from the Stigmer team.23

## **7\. Conclusions and Final Verdict**

The current Stigmer Runner architecture—characterized by comprehensive protobuf API definitions, custom CRUD operations, a rigid 6-phase lifecycle, bi-directional streaming, and complex launch token handshakes—is **critically overengineered** relative to the platform's current scale, intended deployment models, and commercial strategy as an embeddable open-source tool.  
The customer rejection signal is highly accurate and indicative of a broader architectural flaw: the architecture demands a level of integration complexity suited for replacing an enterprise container orchestrator like Amazon ECS, rather than simply embedding an AI execution engine. The reliance on the Kubernetes Node analogy, while perhaps intellectually appealing during the design phase, represents a fundamental category error that has driven the platform to redundantly reinvent orchestration primitives that Temporal already provides natively and more robustly.  
**Strategic Recommendations:**

1. **Abolish the Runner API Resource:** Immediately deprecate and delete the Runner protobuf models, the associated relational database tables, and the gRPC command/query controllers. Cease all engineering efforts aimed at treating the runner as a managed infrastructure resource.  
2. **Adopt the Anonymous Worker Pattern:** Refactor the @stigmer/runner package to act as a pure, highly opinionated extension of @temporalio/worker. The runner's only external communication should consist of long-polling the Temporal cluster for tasks and making standard REST calls to the Stigmer API solely for artifact storage and retrieval.  
3. **Implement Per-Session Routing:** Transition entirely to dynamic Temporal Task Queues derived directly from the Session ID. This architectural shift cleanly unifies the local desktop application and cloud sandbox paradigms while explicitly solving worker affinity and data locality requirements without custom routing logic.  
4. **Decouple Data Plane Operations:** Remove the ListDirectory command and all filesystem access from the orchestration layer. Utilize local Node.js IPC for the desktop application, and deploy a dedicated, lightweight HTTP file server for cloud sandboxes to manage workspace files synchronously.  
5. **Optimize the SDK Developer Experience:** Ensure that third-party customers can integrate the runner with no more than three lines of code: import the package, instantiate the configuration object, and start the polling mechanism. The internal complexity of LangGraph middlewares, Cursor harnesses, and workflow engines must remain entirely abstracted behind this simple interface.

By shedding the immense technical burden of managing infrastructure lifecycles, maintaining bidirectional streams, and reconciling divergent state machines, the Stigmer platform can refocus its engineering budget on its core value proposition: delivering highly reliable, multi-engine AI agent execution and sophisticated workflow orchestration. The path forward is not building a superior control plane to micromanage runners, but rather recognizing that the runner never required a custom control plane to begin with.
