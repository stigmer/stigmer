# Deep Research: Control Plane + Runner Architecture — Is This Overengineered?

## Research Objective

I'm building an open-source AI agent platform called **Stigmer** (stigmer.ai). It has a **control plane** (Java Spring Boot server, "stigmer-service") and a **runner** (TypeScript process that actually executes AI agents, CNCF Serverless Workflows, and Cursor IDE harnesses). I'm in the middle of two large migration projects to unify everything into a single TypeScript runner, and I'm having a crisis of confidence about the architecture.

**The core question**: Have I overengineered the runner concept? Specifically:

1. **Was creating a formal Runner API resource (with its own protobuf service, CRUD, lifecycle phases, heartbeat protocol, bidi command stream) the right call?** Or should the runner just be an anonymous Temporal worker that polls a queue — no API, no resource, no lifecycle management?

2. **Is the control-plane-to-runner separation itself overengineered?** Should the runner be a thinner process? How much logic should live in the runner vs. the control plane?

3. **How do comparable systems handle this?** I want to understand the spectrum from "anonymous worker pool" to "fully managed node with its own API" and where mature platforms land.

## What I've Built (Current Architecture)

### The Runner API Resource

I've defined a full protobuf API for the Runner as a first-class platform resource:

**Runner resource** (`ai.stigmer.agentic.runner.v1`):
- `Runner` message with `api_version`, `kind`, `metadata` (org, labels, name), thin `spec` (just a description), and rich `status`
- Follows the **Kubernetes Node pattern**: thin spec (user declares intent), rich status (runner self-reports everything)
- `RunnerStatus`: phase (PENDING → STARTING → READY ↔ BUSY → STOPPED / FAILED), task_queue, last_heartbeat_at, started_at, stopped_at, current_executions, connection_info (hostname, OS, arch, runner_version, machine_id), process_executions map, idle_since
- `RunnerPhase` enum with 6 states and documented transitions

**Two gRPC services**:
- `RunnerQueryController`: get, getByReference, list (for session composer dropdown)
- `RunnerCommandController`: apply, create, update, delete, sendCommand, stop, connect (bidi stream), createLaunchToken, exchangeLaunchToken

**Bidi command stream** (`connect` RPC):
- Runner → Server: heartbeats every 30s (phase, executions, connection_info, process_type)
- Server → Runner: commands (ListDirectory for filesystem browsing, StopRunner)
- First message must be a heartbeat (authenticates the stream)
- Server detects stale runners via heartbeat timeout (90s → STOPPED)

**Launch token handshake**: Browser-to-CLI credential flow via `stigmer://` URL scheme for "Launch Local Runner" from web console.

**Two runner creation patterns**:
- User-created (persistent): `stigmer runner start` from CLI, appears in session composer
- System-managed (ephemeral): platform auto-creates for cloud executions, labeled `stigmer.ai/system-managed: "true"`, torn down after execution

### What the Runner Actually Executes

The runner is a Temporal worker that handles three types of execution:

1. **ExecuteDeepAgent**: LangGraph-based AI agents with:
   - Full middleware stack (10 modules: think-tool, tool-truncation, error-hints, loop-detection, graceful-stop, execution-budget, cost-cap, otel-spans, approval-gate, plus a subagent gate)
   - MCP server management (stdio + HTTP, multi-server, discovery, connect backfill)
   - HITL (human-in-the-loop) approval gates
   - Streaming status updates via gRPC
   - Artifact storage (local + R2 proxy)
   - Writeback (incremental git, GitHub PRs)
   - Subagent orchestration (transform proto → compiled subagent, skill injection, model validation)
   - Multi-provider model support (Anthropic + OpenAI via proxy)
   - Session memory, checkpointing, platform mount routing

2. **ExecuteCursor**: Cursor IDE agent harness (SDK-based, already production)

3. **ExecuteServerlessWorkflow**: CNCF Serverless Workflow engine (rewritten from Go) that runs YAML-defined workflows with set, switch, for, call:http, call:grpc, call:llm, call:agent tasks

**Total codebase**: 1,057 tests passing, ~50+ modules across shared infrastructure, activities, middleware, and workflow engine.

### The Broader Platform

Beyond the runner, the control plane manages:
- **Sessions**: bind to a runner via `session.spec.runner_id`
- **Agent Executions**: record which runner handled them via `execution.status.runner_id`
- **Workflow Executions**: similar binding
- **Agents, Skills, MCP Servers, Environments, Artifacts**: all first-class API resources
- **Temporal** as the durable execution backbone (all long-running work is Temporal workflows)

### Critical Recent Shift: Runner Is Now an NPM Package

The unified TypeScript runner is being built as an **NPM package** (`@stigmer/runner` or similar). This fundamentally changes the deployment model:

- **Current state**: The runner is a CLI command (`stigmer runner start`). In the desktop app, it runs as a **sidecar process** spawned by Electron. All the registration, heartbeat, bidi stream, and lifecycle management complexity exists to make this sidecar-to-server relationship work.
- **New reality**: Since the runner is "just an NPM package," customers should be able to `npm install` it and embed it in their own applications. The runner should be an **embeddable library**, not a standalone service with its own management protocol.

### Customer Adoption Signal (Critical)

**One of our customers is not incorporating the runner integration.** This is the strongest signal that the current runner architecture is too complex. If an early adopter finds it unintuitive to integrate, the API surface is wrong. The runner needs to be something a developer can understand in 5 minutes and wire into their system in an hour, not a Kubernetes-style resource with CRUD APIs, bidi streams, and launch tokens.

### Deployment Model Rethink

The two deployment paths are now clearer:

1. **Browser/Web → Always cloud path**: When a user is in the web console, executions always go through a cloud-provisioned sandbox. The runner is invisible infrastructure — the user never thinks about runners.

2. **Desktop app → Automatic local runner**: When using the Stigmer desktop app (Electron), a runner starts automatically as part of the app lifecycle. There's no separate "start a runner" step. The runner is embedded in the desktop app process. The user never explicitly manages it.

3. **Customer integration → Embeddable NPM package**: Customers `npm install @stigmer/runner` and call something like `createRunner({ temporalAddress, stigmerEndpoint })` in their code. It should be that simple.

In all three cases, the user should **never have to think about runners**. They think about **sessions** and **executions**. The runner is an implementation detail.

### Per-Session Runner Model (Proposed Alternative)

Instead of the current model (persistent runner resource → sessions bind to it), consider:

- **Runners are per-session, not per-machine**. When a conversation/session starts, a runner is spun up (or an existing idle one is reused).
- **The runner identity IS the session ID.** The Temporal task queue is derived from the session ID, not a runner ID.
- **No Runner API resource at all.** The session IS the unit of routing. When the control plane starts a Temporal workflow for an execution, it targets the task queue that the session's runner is polling.
- **Local desktop**: The embedded runner polls a task queue derived from the desktop's session context. The desktop app manages runner lifecycle automatically.
- **Cloud**: The platform provisions a sandbox, starts a runner inside it, and the runner polls the session's task queue. Identical to today's ephemeral runner but without the Runner resource indirection.

### What's Driving My Doubt

1. The runner API is **a lot of surface area** (2 gRPC services, 12+ RPCs, bidi stream, launch tokens, filesystem browsing) for what is essentially "a process that polls a Temporal queue and executes activities"
2. The heartbeat/phase/lifecycle machinery **duplicates what Temporal already provides** — Temporal workers inherently have liveness detection, and activities have heartbeats
3. The `ListDirectory` command over bidi stream feels like **feature creep** — should filesystem browsing be in the runner protocol at all?
4. Multi-process tracking (`process_executions` map with "agent"/"cursor"/"workflow" keys) adds complexity for what might be a temporary migration artifact
5. The Kubernetes Node analogy might be **flattering but misleading** — K8s nodes run hundreds of pods and need rich status; my runner handles 1-3 concurrent executions
6. **The runner is now an NPM package** — the entire "runner as a managed service with its own API" model may be wrong. It should be an embeddable library with a clean programmatic API, not a protocol-heavy managed resource.
7. **A customer is struggling to integrate** — the current design is not intuitive for third-party developers. This is a product-level failure signal.
8. **Desktop users should never manage runners** — the desktop app should handle it automatically. The current `stigmer runner start` CLI flow adds unnecessary friction.
9. **Web users already don't see runners** — they go through cloud. So the runner is only visible to desktop/CLI users and embedding customers. Is the management API justified for just those audiences?

## Known Context

- **Stigmer is early-stage** — likely tens of users, not thousands. The runner doesn't need to handle hundreds of concurrent executions.
- **Temporal is the backbone** — all durable execution is Temporal workflows. The runner is a Temporal worker.
- **Two deployment modes**: local (user's laptop via desktop app, automatic) and cloud (Daytona sandbox, ephemeral, for web users). This dual mode drives some of the complexity.
- **The runner is not just a worker** — it also provides filesystem access to the web UI (directory browsing for workspace selection). This is the main reason for the bidi stream. BUT: with the desktop-only local runner model, filesystem browsing could be handled by the desktop app itself (Electron has full FS access) rather than the runner protocol.
- **Three execution types** in one process is the target end state (currently being migrated from 3 separate processes/languages).
- **The runner is now an NPM package** — customers need to be able to embed it. The current CLI/sidecar model with registration APIs is a barrier.
- **Customer signal**: An early adopter customer is not integrating the runner despite having been given the current implementation. This suggests the integration surface is too complex or unintuitive.
- **Desktop app manages the runner automatically** — users on the desktop app should never see or think about runners. The app starts/stops them as needed.
- **Web/browser users always go through cloud** — they never interact with runners directly. The platform handles it.
- **The only users who "see" runners today are CLI/power users** — and even they probably shouldn't have to manage them explicitly.
