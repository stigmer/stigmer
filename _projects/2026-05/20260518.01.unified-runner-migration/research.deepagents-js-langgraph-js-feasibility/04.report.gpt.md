# DeepAgents JS + LangGraph JS Migration Feasibility

**Executive Summary:** DeepAgents JS (v1.10.2 as of May 2026) and LangGraph JS (v1.2.0) are actively maintained and largely match their Python counterparts【17†L460-L464】【58†L195-L203】. The core agent factory (`createDeepAgent`) supports middleware, subagents, streaming, and checkpointers in JS【29†L610-L618】【41†L179-L187】. Key features like human-in-the-loop interrupts (via `interrupt()`/`Command({resume})`) and persistent memory (in-memory and MongoDB savers) are available【41†L179-L187】【48†L894-L900】. MCP (Model Context Protocol) tool loading is supported via the `@langchain/mcp-adapters` package (using `loadMcpTools`) for both STDIO and HTTP/SSE transports【38†L293-L302】. However, certain advanced capabilities from our Python stack — such as loop detection, execution budgeting, token-level cost caps, signal-based stop handling, and custom telemetry – have no direct equivalents and would require custom implementation. Overall, **DeepAgents JS and LangGraph JS appear capable of replacing the Python agent runner with moderate effort (confidence: medium–high)**, provided we fill a few gaps.

## Risk Assessment

The biggest gaps (and engineering risks) are in **non-LLM utilities** that the Python stack provided via custom middleware. Key concerns:

- **Control flow & safety:** Features like *loop detection*, *execution budgets*, *cost caps*, and *stop-on-signal* are **not natively supported** in LangChain.js. Implementing these will require significant custom middleware or external management. For example, there’s no out-of-box “stop agent” handler or USD spending tracker, so these must be coded by us. This is moderate effort but technically straightforward.  
- **Token accounting:** The Python code relied on `tiktoken` for accurate token counts. In JS, we lack a bundled token counting, so any budget/cost logic must either use a JS tokenizer library or rely on provider callbacks. Risk: subtle differences in token logic could affect budgeting.
- **Persistent MCP connections:** Python’s `MultiServerMCPClient` convenience is absent in JS. Managing multiple MCP servers (especially for large tool sets) may require custom aggregation of `MCPClient` instances. Slight risk of extra work but doable.  
- **Message format parity:** There are some small serialization differences (e.g. LangChain JS labels message chunks differently【50†L179-L187】). If our system depends on specific message types (e.g. for streaming UIs), this may require adaptation.  
- **Community maturity:** While both repos are active, Python is still more battle-tested and has a larger userbase【50†L119-L124】【51†L1-L4】. LangChain maintainers claim ~95% API parity【51†L1-L4】, but subtle bugs or undocumented behaviors may surface in edge cases. We should plan for iterative testing and possibly contributing fixes.  
- **Monitoring/telemetry:** No built-in observability (apart from LangSmith). If we rely on OpenTelemetry or custom monitoring, that must be added. This is a risk if our ops rely on it heavily.
  
Overall, none of these gaps are insurmountable, but **loop/cost/stop controls and telemetry will be the highest-effort gaps to bridge**. Core agent orchestration (tools, streams, subagents, HITL) is largely ready.

## Alternative Approaches

If these gaps prove too high, we can consider:

- **Delay or Partial Migration:** Postpone the migration until LangChain.js implements needed features, or keep core Python runner and only migrate supporting code.  
- **Contribute Upstream:** Invest in adding missing middleware to DeepAgents/ LangGraph JS (they welcome contributions) to close parity gaps.  
- **Other JS Agent Frameworks:** Explore **Vercel AI SDK** or **Mastra**. The Vercel AI SDK is a popular TS toolkit for building agents with Next.js/React【62†L363-L372】, and Mastra is a TS-first agent framework (open-source, 24K stars) that offers observability, memory management, etc.【59†L9-L12】【60†L83-L91】. Both can host complex agents, though migrating our Python logic into their paradigms would also require work.  
- **Hybrid or RPC:** If critical, run the Python agent-runner in a separate service (or container) and invoke it via RPC from our TypeScript system as an interim solution.  
- **Lower-Level API:** Instead of DeepAgents, use lower-level LangChain.js/ LangGraph.js primitives to rebuild only the needed pieces, though this sacrifices the “batteries-included” convenience.

Each alternative has trade-offs. Given that LangChain.js is designed for this use-case and is under active development, the most direct path is **migrating to DeepAgents JS and filling the gaps**, while considering contributions or partial fallbacks as needed.

# The biggest correction to the previous report

The earlier report said JS lacked a direct `MultiServerMCPClient` equivalent. That was wrong or at least outdated.

The LangChain JS MCP docs explicitly show:

```ts
import { MultiServerMCPClient } from "@langchain/mcp-adapters";
```

and then configure multiple MCP servers, one stdio and one HTTP, followed by `client.getTools()`. The same page says `MultiServerMCPClient` is stateless by default, creating a fresh MCP `ClientSession` per tool invocation. ([LangChain Docs][5])

So the more precise conclusion is:

**MCP multi-server loading exists. Persistent connection semantics are the risk.**

For your production runner, the question is not “can JS load tools from multiple MCP servers?” It can. The question is whether the SDK mode you use gives you the same long-lived process/session semantics as your Python `MultiServerMCPClient` context manager. DeepAgents Code docs say stdio servers are kept alive between tool calls in the CLI, but the generic LangChain MCP adapter docs say the multi-server client is stateless by default. ([LangChain Docs][6])

That is exactly the kind of thing that needs a spike, not a doc-only decision.

# Risk assessment, ranked by migration effort

## 1. Rebuilding graphton’s production middleware layer

This is the largest real cost. The JS stack gives you the substrate; it does not give you your policy layer.

The following are not demonstrated as built-ins in the JS docs I reviewed: loop detection, step budgets, wrap-up nudges, cost caps, stop signals, exact token accounting, truncation policy, OpenTelemetry integration, and your exact HITL approval wrapper semantics.

This is likely **2–5 weeks of engineering** depending on test coverage and how much graphton behavior is implicit.

Mitigation: build a `graphton-js` harness with explicit middleware contracts before migrating the runner.

## 2. MCP lifecycle and security model

Basic MCP is supported well. The danger is production lifecycle: long-lived stdio servers, auth refresh, reconnection, per-tenant isolation, project trust, env interpolation, SSRF controls, and partial server failure.

DeepAgents Code has thought through some of this: it supports server statuses, partial startup failure, project-level trust, OAuth, tool filtering, and system-prompt awareness of connected MCP servers. ([LangChain Docs][6])

But those docs are for **Deep Agents Code**, not necessarily the SDK service runtime. You should not assume all CLI lifecycle behavior drops into your server.

Mitigation: define your own MCP manager abstraction around `MultiServerMCPClient`.

## 3. Interrupt/resume semantic parity

LangGraph JS has the primitives. The concern is not existence; it is exact behavior under your production cases: multiple interrupts, nested subagents, replay, checkpoint restore, pending writes, tool-level interrupts, and crashed/resumed workers.

JS docs explicitly state that the node restarts from the beginning when resumed, and any code before `interrupt()` runs again. That means side effects before interrupts must be idempotent. ([LangChain Docs][7])

Mitigation: build HITL golden tests that mirror Python traces.

## 4. Custom HTTP checkpointer complexity

An HTTP checkpointer is feasible because JS checkpointers implement `.put`, `.putWrites`, `.getTuple`, and `.list`. ([LangChain Docs][8]) But implementing this incorrectly can corrupt resume semantics, pending writes, state history, or interrupt recovery.

Mitigation: initially use `MongoDBSaver` or `PostgresSaver` unless platform constraints force HTTP. Build the HTTP saver only after proving the rest of the runner.

## 5. Security / dependency maturity

LangChain/LangGraph is active and production-used, but security hygiene matters. Public reporting in 2026 mentioned vulnerabilities involving LangChain/LangGraph components, including checkpoint-related SQL injection in SQLite checkpointing, with fixes requiring patched versions. ([TechRadar][10])

Mitigation: pin versions, run SCA, avoid SQLite in production unless patched and audited, and treat LLM outputs/tool metadata as untrusted input.

# Migration architecture I would recommend

## Option A — best path: DeepAgents JS + graphton-js compatibility layer

Use DeepAgents JS as the runtime, but do **not** wire app code directly to `createDeepAgent`. Instead, create your own `createStigmerAgentRunner()` that wraps:

```ts
createDeepAgent({
  model,
  tools: wrappedTools,
  subagents,
  middleware: [
    loopDetectionMiddleware(),
    executionBudgetMiddleware(),
    toolTruncationMiddleware(),
    costCapMiddleware(),
    hitlApprovalMiddleware(),
    gracefulStopMiddleware(),
    telemetryMiddleware(),
    ...deepagentsMiddleware,
  ],
  checkpointer,
  store,
  interruptOn,
  backend,
  streamTransformers,
})
```

This gives you a stable internal contract and prevents upstream API churn from leaking into the rest of your service.

## Option B — LangGraph JS directly, no DeepAgents

Use LangGraph JS primitives directly and rebuild the agent loop yourself. This gives maximum control over budgets, approvals, checkpoint layout, and streaming. But you lose DeepAgents’ built-in planning/filesystem/subagent harness.

This is only attractive if DeepAgents JS middleware hooks are insufficient for graphton parity.

## Option C — keep Python runner behind RPC

Keep the Python runner as an RPC service while migrating the surrounding TypeScript service. This preserves production behavior while reducing some operational complexity. It does not eliminate Python from the execution path, but it buys time.

Best as a fallback if the JS spike reveals semantic gaps in interrupts, checkpointing, or MCP lifecycle.

## Option D — alternate TS frameworks

Vercel AI SDK and Mastra are worth evaluating for UI/tooling/app-agent ergonomics, but they are not obvious replacements for LangGraph’s durable execution + checkpoint + interrupt model. LangGraph JS is closer to your Python architecture. The LangGraph JS README explicitly positions it as a low-level orchestration framework with persistence, streaming, long-term memory, and HITL; that maps more directly to your current stack than most app-layer TS agent frameworks. ([GitHub][4])

# Hard-gate test plan

Before approving migration, I would require these tests to pass:

## 1. DeepAgents API compatibility spike

Build one representative agent with:

* tools
* `subagents`
* custom middleware
* `interruptOn`
* `MemorySaver`
* persistent checkpointer
* streaming
* filesystem backend

Acceptance: every Python runner feature has a JS extension point.

## 2. HITL parity suite

Scenarios:

* approve tool call
* reject tool call
* edit tool call
* interrupt inside a tool
* interrupt inside a subagent
* resume after process restart
* multiple simultaneous interrupts
* replay from checkpoint

Acceptance: same externally visible state machine as Python.

## 3. MCP lifecycle suite

Scenarios:

* stdio MCP server stays alive or is intentionally stateless
* SSE server disconnect/reconnect
* HTTP server auth headers
* OAuth if needed
* one MCP server fails while others load
* tool filtering
* malicious project config cannot run arbitrary commands
* per-tenant isolation

Acceptance: explicit lifecycle behavior, not accidental behavior.

## 4. graphton-js middleware suite

Port or reimplement:

* loop detection
* execution budget
* cost cap
* tool result truncation
* graceful stop
* summarization policy
* token counting
* OTel spans
* approval wrappers

Acceptance: golden traces match Python behavior for representative production runs.

## 5. Persistence durability test

Run the same workflow with:

* MemorySaver
* MongoDBSaver or PostgresSaver
* proposed custom HTTP saver

Kill the worker at:

* before model call
* after model call before checkpoint
* during tool call
* after interrupt
* after resume

Acceptance: no duplicated non-idempotent side effects; resume works with correct state.

# Final go/no-go

## My actual recommendation

**Do not approve a full production migration yet. Approve a focused TypeScript feasibility spike.**

The JS ecosystem is likely ready enough for your migration **if** you are willing to rebuild graphton as a TypeScript production harness. It is **not** ready as a drop-in replacement for your Python service.

I would classify the decision as:

**Conditional Go — 70% confidence for feasibility, 45–55% confidence for production parity without a substantial internal compatibility layer.**

The core runtime is there. The hard work is not DeepAgents JS; it is faithfully porting the operational controls your Python system accumulated around it.
