# Deep Research: Optimizing LLM Cost & Latency — Cursor SDK vs Native Anthropic API

## Research Objective

We operate **Stigmer**, an open-source agentic AI platform that executes LLM-powered agents on behalf of users. Agents can run through two "harnesses":

1. **Native harness** — our Python agent-runner calls the Anthropic API directly (using LangGraph + `langchain_anthropic`). We have full control over prompts, caching strategy, and token management.
2. **Cursor harness** — our TypeScript cursor-runner uses the **Cursor SDK** (`@cursor/sdk`) to delegate execution to Cursor's cloud agents. The Cursor SDK wraps the underlying LLM provider and adds its own system prompt, tool infrastructure, and context management.

We just built and ran our first cost benchmark comparing these two harnesses on identical prompts. The results reveal structural differences in how tokens are used and priced, and we need expert-level research to understand and act on these findings.

## Benchmark Data (from our integration test suite)

|--------|--------|--------|-------|

### Key Observations from the Data

1. **Native's first call is expensive** (Simple Reply: $0.04 for a trivial prompt) because it writes ~10.8k tokens to Anthropic's prompt cache at $3.75/M. Subsequent calls in the same session then read from cache at $0.30/M — a 12.5x discount.

2. **Cursor's input token overhead is ~10k tokens per call** — this is the Cursor system prompt/rules/context that gets prepended. This overhead is roughly constant regardless of the user's prompt size.

3. **Cursor's cache read is small (1,536 tokens)** compared to native's cache reads. This suggests Cursor manages its own caching strategy that we have no visibility into or control over.

4. **Multi-turn token divergence**: Over 3 turns, Cursor uses nearly 2x the tokens as native. This suggests native benefits significantly from Anthropic's conversation caching, while Cursor may re-send full context on each turn.

5. **Latency gap is consistent (2-3x)**: This appears to be structural SDK/proxy overhead, not LLM response time.

## What We Need Researched

### Area 1: Cursor SDK Token Economics

- What is the Cursor SDK's system prompt overhead? Is the ~10k token baseline documented or observed by other users?
- Does the Cursor SDK support Anthropic prompt caching, and if so, how does it manage cache keys? Can we influence it?
- When using `Agent.send()` and streaming via `run.stream()`, does the SDK re-send the full conversation on each turn, or does it use incremental context?
- Is there a way to inspect or reduce the Cursor-injected system context (rules, tool definitions, file context)?
- What is Cursor's pricing model for API access vs direct Anthropic API access? Is there a markup, or do they pass through Anthropic pricing?

### Area 2: Anthropic Prompt Caching Optimization for the Native Harness

- Best practices for Anthropic's prompt caching with multi-turn agents (cache_control breakpoints, system prompt caching, tool definition caching).
- How to structure long-running sessions so that the initial cache-write cost ($3.75/M) amortizes well across many turns. What's the break-even point?
- How cache TTL works (currently 5 minutes, extended with "cache breakpoints") and strategies for keeping caches warm across executions within the same session.
- Any gotchas with caching when tool definitions change between calls (e.g., MCP server tools being dynamically resolved)?

### Area 3: Reducing the Latency Gap

- What contributes to the Cursor SDK's 2-3x latency overhead? Is it:
  - SDK initialization / agent creation time?
  - Additional round-trips for tool discovery?
  - Server-side processing before the LLM call?
  - Response post-processing (tool call extraction, safety filters)?
- Are there configuration options in the Cursor SDK to reduce latency (pre-warming, connection pooling, local mode vs cloud mode)?
- How does the Cursor SDK handle streaming — is there buffering that adds latency?

### Area 4: Hybrid Cost Optimization Strategies

- For a platform like ours where we offer both harnesses, what's the optimal strategy for routing prompts?
  - Simple prompts → native (lower overhead)?
  - Complex multi-tool prompts → Cursor (better tool use, IDE integration)?
  - Long sessions → native (caching amortizes)?
- Are there other agentic platforms that have published cost comparisons between native LLM access and Cursor/Copilot/Windsurf SDK access?
- What's the current state of "Cursor for Agents" or "Cursor API" pricing and terms of service for platform embedding?

### Area 5: Billing Architecture for Multi-Source Usage

- Best practices for billing pipelines that ingest usage from multiple sources (proxy-observed vs runner-reported vs admin-reconciled) with different trust levels.
- How do other AI platforms (Vercel AI, LangSmith, Helicone, Braintrust) handle cost tracking for LLM calls that go through intermediary SDKs where the platform doesn't control the LLM call directly?
- Idempotency and deduplication patterns for usage records when the same execution might be reported by both a proxy and a runner.

## Known Context (Starting Points)

- **Cursor SDK**: `@cursor/sdk` npm package. Agent-based API. `Agent.create()`, `Agent.send()`, `run.stream()`. Supports `onDelta` callbacks with `turn-ended` events that include token usage.
- **Anthropic Caching**: Anthropic's prompt caching feature (beta) — `cache_control` breakpoints on messages, $3.75/M write, $0.30/M read, 5-min TTL, extended by cache hits.
- **Our Billing Pipeline**: Usage records flow into a MongoDB collection (`llm_call_usage_record`) via a `recordLlmCallUsage` gRPC RPC. Records are deduplicated by `(execution_id, sequence, metering_source)`. The billing handler computes cost from a model registry (JSON file with per-model pricing).
- **Models in Use**: `claude-sonnet-4-6` (Anthropic Sonnet 4.6) — $3/$15 per million input/output tokens, with cache write at $3.75/M and cache read at $0.30/M.
