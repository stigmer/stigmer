## Anthropic caching optimisation for the native harness

Anthropic’s current guidance is highly favourable to your native architecture. The platform now supports both **automatic caching** and **explicit cache breakpoints**. Automatic caching is the recommended starting point for most multi-turn conversations: you add a single top-level `cache_control`, and Anthropic automatically moves the breakpoint forward as the conversation grows. Explicit breakpoints are for cases where you want fine-grained control over which parts of the request are cached independently. citeturn1view2turn1view3

The core implementation rule is simple and important: **put static content first**. Anthropic says prompt caching works over the request prefix in the order **`tools` → `system` → `messages`**, and recommends placing static content such as tool definitions, system instructions, background context, and examples at the beginning of the prompt. This fits your native harness extremely well, because you already control prompt construction, tool schemas, and conversation state explicitly. citeturn1view2turn26view2

Best practice for long-running agents is to combine **one explicit breakpoint for stable setup** with **automatic caching for the moving conversation frontier**. Anthropic explicitly documents that pattern: cache the stable system prompt or tools explicitly, then let automatic caching handle the growing conversation. You can use up to **four** breakpoints total, which is especially helpful if some sections change at very different cadences or if a growing conversation pushes the active breakpoint too far beyond the last cache write. citeturn1view2turn26view1turn26view2

Your specific benchmark makes the economic case very clearly. Anthropic’s own pricing docs state that prompt caching pays off after **one cache read** at the 5-minute TTL and after **two cache reads** at the 1-hour TTL. Using your benchmark’s ~10,878-token cached prefix and Sonnet 4.6 pricing, that prefix costs about **$0.0408** to write once, **$0.0326** to send uncached, and only **$0.00326** to read from cache thereafter. Over ten sends of the same prefix, the repeated-prefix portion would cost about **$0.0702** with one write plus nine reads, versus **$0.3263** if resent uncached on every turn, a savings of about **78.5%** on that repeated portion. citeturn1view3turn41calculator0turn41calculator1turn41calculator2turn42calculator0turn42calculator1turn42calculator2

TTL management is also more flexible than your “5 minutes only” starting point suggests. Anthropic’s default cache TTL is **5 minutes**, refreshed at no extra charge each time the cache is used; Anthropic also offers a **1-hour cache** at a higher write multiplier. Mixed TTLs are allowed, but Anthropic requires the **longer-lived cache entries to appear before shorter-lived ones** in the prompt. That means a very practical pattern for Stigmer is to keep your most stable, expensive prefixes—core system scaffolding and stable tool definitions—on the 1-hour tier, while letting the active conversation growth stay on the default 5-minute tier. citeturn1view2turn26view4

For latency-sensitive flows, Anthropic now explicitly supports **cache pre-warming** with `max_tokens: 0`. Anthropic says this runs the full prefill phase, writes the cache, and returns immediately without generating output. The key implementation detail is that the breakpoint must be placed on the **last block shared with the follow-up request**—typically the system prompt or tool definitions—not on the placeholder warm-up user message. This is the cleanest way to remove first-turn cache-miss latency from high-volume, session-based workloads. citeturn27view1turn27view0turn27view4

There are two important gotchas for dynamic agent loops. The first is **minimum cacheable size**: for Claude Sonnet 4.6, Anthropic’s minimum cacheable prompt length is **1,024 tokens**. If your static prefix is shorter, caching is silently skipped. The second is **cache invalidation**. Anthropic states that changes to **tool definitions**—names, descriptions, or parameters—invalidate the **entire cache**. Changes to web-search, citations, or fast-mode toggles invalidate system and messages caches; changes to `tool_choice`, images, or thinking settings invalidate messages cache. So, if your native harness resolves MCP tools dynamically or regenerates tool schemas on each call, you can easily destroy the cache benefit unless you stabilise those schemas. citeturn26view0turn26view3turn29view0

The most robust mitigation is to **separate stable and volatile tools**. Anthropic’s tool-caching docs say to place `cache_control` on the **last tool** in the `tools` array, which caches the full tool-definition prefix, and note that **deferred tools** loaded through tool search do not enter the system-prompt prefix and therefore preserve cache hits. Even if you do not adopt Anthropic’s tool-search machinery directly, the design lesson is clear: keep the “always-on” part of your toolset stable and cacheable, and load or synthesise volatile tools later in the execution path rather than rebuilding the whole tool prefix on every call. citeturn29view0

Finally, note Anthropic’s newer **workspace-level cache isolation**. As of February 2026, the Claude API uses workspace-level cache isolation rather than organisation-level isolation. If Stigmer issues native Anthropic requests from multiple workspaces or API keys tied to different workspaces, shared-prefix reuse could be lower than expected. citeturn27view2turn27view3

## Closing the latency gap

The public evidence points to the latency gap being mostly **harness overhead**, not just model inference. Cursor’s agent architecture bundles system instructions, rules, tool infra, codebase search, MCP servers, hooks, skills, and subagents into the run. Cursor Cloud Agents also run in isolated environments with repository access and additional capabilities such as terminal, browser/computer use, and PR artefacts. That is a much heavier path than a single direct Messages API call through your native Python runner. citeturn4search9turn7view2turn23view0turn35search5

Because your Cursor harness specifically delegates to **Cursor cloud agents**, one public design choice is especially relevant: **Cloud Agents always run in Max Mode, and there is no toggle to turn Max Mode off**. Larger context budgets can improve result quality on complex coding tasks, but they also make it harder to achieve low, deterministic latency on simple prompts. If you want a more controlled benchmark, the best public alternative is to benchmark the Cursor SDK in **local runtime** against the same repository on disk, with the same selected model, and with as little extra configuration loaded as possible. citeturn7view2turn23view0turn30search2

There are also run-level mechanics that can add delay. Cursor’s changelog and SDK docs describe **SSE streaming**, reconnect support through `Last-Event-ID`, and raw delta callbacks. The SDK explicitly warns that `onDelta` callbacks are **awaited before the next update is processed**, which means your own stream handlers can create backpressure if they do slow work. That will not explain your entire 2–3x gap, but it is one avoidable source of additional latency in benchmarks. citeturn1view0turn3view0turn43search1

On cloud-specific startup overhead, the public documentation is incomplete, but community material is informative. Cursor staff say codebase indexing is a normal part of starting a Cloud Agent, and users report first-response delays of several minutes on larger repositories when snapshots are not used. That does not map directly to your 11-second results, but it reinforces the broader point that Cloud Agent startup and environment/indexing work are real latency contributors separate from model time. citeturn36view0

For runs originating from India or other regions far from Cursor’s streaming edge, there is a second-order network effect worth noting. In a Cursor staff forum reply, Cursor states that `api2.cursor.sh` traffic in **India and China** can go directly to AWS US without a Cloudflare edge, causing apparently buffered or slow streaming. I would not treat that as the primary explanation for your benchmark unless your benchmark runner is actually in one of those regions, but it is a plausible confounder in operational use. citeturn36view1

The practical levers available publicly are limited but real. Reuse a **durable `Agent`** instead of the one-shot `Agent.prompt()` helper when the conversation continues; prefer **local runtime** when the caller already has the repo and does not need a long-lived cloud VM; trim always-on rules and MCP servers; and, where cloud is necessary, consider **self-hosted pools** or “My Machines” style execution to keep compute and repository access closer to your environment. What I did *not* find in public Cursor documentation was any equivalent of Anthropic cache pre-warming, any documented connection-pooling knob, or any official way to reduce or override Cursor’s internal system prompt. citeturn23view0turn30search2turn34search9

## Billing architecture and competitive landscape

### Billing architecture

For Stigmer’s billing system, the most defensible pattern is a **three-layer pipeline**: raw observations, canonical reconciliation, and invoice-grade billing. Raw observations should be append-only and source-specific: one record each from the native provider response, any proxy or network tap, the runner’s own report, and any later vendor-admin export or dashboard pull. Canonical reconciliation should then choose a single billable truth by source precedence, while preserving all raw records for audit. Invoice-grade billing should only ever read from that reconciled layer. This mirrors how the better observability vendors handle mixed trust: they preserve raw traces and then aggregate costs/views from them rather than trying to turn every incoming event into an immediate bill. citeturn15view0turn15view1turn15view2turn20view0

For **trust ordering**, I would use a simple rule: **provider-admin or vendor-admin export first, proxy-observed second, runner-reported third**. Native Anthropic is relatively simple because the response usage block is provider truth. Cursor is different: the SDK gives you operationally useful usage, but actual billing can depend on Cursor plan type, plan pool, resolved model, and, on Teams, the Cursor Token Rate. Vercel’s AI Gateway and Helicone illustrate the same distinction clearly: Vercel exposes request-level cost and token logs directly at the gateway, while Helicone explicitly says cost is **100% accurate** when you use its gateway and only **best effort** when you integrate directly without it. citeturn15view0turn15view2turn12view1turn25view0

The most important schema change for Stigmer is to store **two cost fields** for intermediary platforms: `estimated_provider_equivalent_cost` and `vendor_billed_cost`. For Cursor, the first is useful for internal optimisation and model selection, but the second is what finance should care about. This is especially important because Cursor’s cloud harness may not map one-to-one onto a direct Anthropic request, and because SDK runs surface in Cursor’s own usage dashboard with an SDK tag. Cursor’s Analytics API also exposes team-level model usage and other productivity metrics on Enterprise, while Teams docs point to admin-side spending data. citeturn23view0turn24search3turn25view0

For **idempotency and deduplication**, copy payment-grade patterns rather than ad-hoc logging patterns. Stripe’s API docs recommend explicit **idempotency keys** for safe retries, and Stripe’s usage-based billing stack centres on event ingestion into a real-time metering system. Concretely, every Stigmer usage observation should carry a stable idempotency key, ideally a natural one such as `provider_request_id`, `run.id`, `generation_id`, or `span_id`; when none exists, synthesise one deterministically from `(execution_id, harness, source, sequence, turn, model, attempt, usage_hash)`. Upsert into a dedupe table on that key and keep status fields such as `provisional`, `reconciled`, and `corrected`. ## Executive Summary

Your benchmark shows that **the native Anthropic path** vastly outperforms the Cursor path for raw cost and latency on simple and multi-turn interactions. Native Anthropic lets you fully exploit prompt caching (saving up to 12.5× on repeated prefixes) and avoids Cursor’s extra system instructions and tooling. ## 1. Cursor SDK Token Economics

Cursor’s official docs make it clear that the SDK *isn’t* a thin API wrapper but the **full Cursor agent stack**. A Cursor [Agent](https://cursor.com/docs/sdk/typescript.md) holds durable conversation state, rules, tools, file context, and hooks across prompts. Cloud agents even clone your repo and load all team/project configurations. Those service features come at a token cost: community reports show simple prompts consuming ~13k–18.5k tokens on Cursor, attributable to system rules, tool definitions, and MCP context added to every request. For example, a user noted Cursor spent **8,400 tokens** just to rename a function, reflecting the bulky built-in prompt. 

**System Prompt Overhead:** Cursor’s docs do not publish a token count for its system prompt. However, Cursor staff and users consistently report a large baseline. The [rules doc](https://cursor.com/docs/rules.md) says rules are **"always applied"** at the front of the context. Cloud agents automatically load *all* project/team plugins and MCP servers, whereas local agents load only inline servers (unless you override `local.settingSources`). Disabling a rule or MCP server stops it from appearing, but any enabled rule text or tool schema *will* be sent. In practice, this means ~10k tokens of instructions and tool schemas are sent before your message. This aligns with forum posts like _“I asked Cursor to rename a function. It sent 8400 tokens.”_ (dev.to) and reports of 18.5k by January 2026. 

**Prompt Caching:** Cursor *does* support Anthropic’s cache control under the hood. The SDK’s `turn-ended` usage events include **cache_write_tokens** and **cache_read_tokens**, and Cursor’s pricing page includes separate cache write/read rates for Anthropic models. In other words, when you `Agent.send()` under the hood it uses Anthropic’s caching. What isn’t exposed is *how* cache keys are chosen. There is no SDK parameter like `cache_control` or user-visible cache ID; the behavior is managed by Cursor’s infrastructure. We also found no public documentation of cache invalidation or TTL policy. In practice, Cursor’s cache may be keyed by the full conversation so far or by some service-managed session ID. You cannot directly insert explicit breakpoints or inspect cache content from the SDK. The net effect: **native harness gives you full cache control; Cursor’s caching is automatic and opaque**.

**Incremental Context:** Likewise, Cursor’s docs say nothing about incremental context versus full re-sending. The agent is durable, but likely at the networking layer each user message is sent as a fresh prompt (with the entire enabled context). The evidence is the high token counts per turn. We did not find confirmation of any “conversation handle” API where Cursor retains history server-side. The SDK does stream back the full updated conversation object each turn, but likely only for your information, not to avoid sending tokens. Thus each turn in Cursor appears to re-send *all* enabled rules, tools, and any cached conversation prefix – then benefit from Anthropic’s cache reads under the hood. 

**Reducing Cursor Context:** You have limited levers. In a local agent, you can restrict which MCP servers to load (or none), and remove team/project hooks/rules if allowed by your configuration. For example, delete or disable any unneeded Rule .md files, or pass an empty `cloud.repos` to let it skip repo cloning. However, **Cursor’s own internal system prompt cannot be changed or removed** – that’s proprietary. The closest you get is running a local agent, which only loads *inline* hooks and servers. Even so, Cursor will prepend its curated rulebase and default tools. In short: you can trim *your own* configuration, but not the built-in context.

**Pricing Model:** Cursor’s billing is mostly pass-through of Anthropic pricing (per-token rates). On Individual plans, “Cursor 2.0” requests use the selected model at the model’s published API rate. Cloud Agents always run Max Mode at the same per-token rates. On Team plans, Cursor **adds** a flat $0.25 per million tokens to every request (including cached tokens and BYOK usage). So if you used Sonnet 4.6 under a Team plan, your $3.00 input/$15 output rates would effectively become $3.25/$15.25 respectively on actual invoice. In our benchmark, the Cursor “Provider Cost” in your table (~$0.0130) is **much lower than Sonnet 4.6’s list price for 11,500 tokens** ($~0.035). This mismatch implies your numbers are “provider-equivalent” estimates, not actual billed tokens. To be safe, always reconcile Cursor usage with its analytics or billing API – it may be using a different model (e.g. an *Auto* route) or just reporting only certain categories. The SDK does let you see the resolved model (`run.model`), so log that and cross-check.

## 2. Anthropic Prompt Caching Optimisation

Anthropic’s prompt caching is a powerful lever for the native harness. Their documentation is detailed about breakpoints and costs. The key rules are:

- **Cache Structure:** Anthropic caches the prefix of `tools → system → messages`. Always put static information (tool definitions, system instructions, fixed context) first. For an agentic task, that often means your function/tool schemas and any repository index context at the top of the prompt. This prefix will be the cacheable part.

- **Breakpoints:** Use either one explicit `cache_control` or multiple. If you have blocks that change infrequently (e.g. your stable rules or toolset) and others that change more often (conversation history), put a `cache_control: 1h` on the end of the stable block and let the rest auto-cache. Up to **4 breakpoints** can be used. For example, you might cache the tool block, then the system prompt, then the agent’s previous summary, in separate segments. 

- **Pre-warm:** Anthropic now supports prewarming with `max_tokens: 0`. To do this, issue a prompt with `max_tokens:0` and a `cache_control` at the end of your stable prefix. This writes the cache and returns immediately. On subsequent real calls, the initial latency (cache write cost and waiting for first token) is eliminated. Anthropic’s docs specifically warn to put the breakpoint *after* your static content, not on the warm-up placeholder message.  

- **TTL Management:** The default TTL is 5 minutes (at $0.30/miss read). A hit refreshes the TTL. They offer a 1-hour TTL option at a higher “cache write” cost ($3.75/M vs. $0.30/M) – it breaks even after 2 hits. If your agent runs continually, use the 1h TTL for the parts of the prompt you plan to reuse heavily (like core tools or system instructions).

- **Cacheable Size:** Claude Sonnet 4.6 needs at least **1,024 tokens** of stable content to cache anything. If your prefix is smaller, caching will silently skip. For example, an 800-token system message won’t be cached. So ensure your static block comfortably exceeds this.

- **Invalidation:** Changing tool names/descriptions or system text invalidates the cache. If your system prompt or tools evolve during a session, the whole cache flushes. Likewise toggling search/citation modes flushes some levels of cache. Therefore, design your session so that the core toolset and instructions are stable, and if you must update them, consider finishing the session or using a new Agent instance.

**Cost Break-even Example:** Using your Scenario 1 numbers, the native agent wrote ~10,878 tokens ($0.0408) on first use. Without caching, sending that prefix each turn would cost 10,878 * $3/M = $0.0326 each time. With caching, each subsequent turn costs only 10,878 * $0.30/M = $0.00326. Over **10 total uses**, the savings on that prefix alone is ~$0.256 (from $0.326 total uncached down to $0.070 cached), an ~78.5% reduction. In fact, even one reuse pays off: $0.0408 + $0.0033 = $0.0441 for two uses vs $0.0652 uncached (a 32% reduction). These back-of-envelope math match Anthropic’s guidance that a single cache read for Sonnet 4.6 (at 5-min TTL) recoups the extra write cost.

## 3. Closing the Latency Gap

The Cursor harness is inherently heavier, so latency overhead is expected. The likely contributors include:

- **Agent Startup:** Cursor Cloud Agents spin up a fresh VM, clone the repo, and **index the codebase** before the first response. Staff confirm this indexing is “normal” and can take minutes on large repos. Using Snapshots can mitigate this on repeat runs, but in your test each invocation likely did a fresh start. Native runs skip all this – there is no indexing step unless you do it manually.

- **System Prompt & Planning:** Once running, the Cursor agent still needs to process its system instructions and rules. That adds some processing time before the model call. If the model is run in Max Mode, there’s also extra preparation (even though they claim it’s just enabling a parameter).

- **Tool Infrastructure:** Cursor’s agent may choose tools via MCP or built-in skills. Even if none are used, the environment for them exists (like a local DB or web search API hook). The SDK stream events include `tool-call-started` etc., hinting at overhead between planning and execution.

- **Networking and API Calls:** The Cursor SDK uses **SSE streaming**. Each partial message or event is HTTP/1.1 chunked (and Cursor warns you might need to disable HTTP/2 to avoid buffering). If you had any VPN/proxy on your test machine, that could have delayed the stream. On a clean network, SSE should be roughly as fast as the underlying model’s response, but it does mean *multiple* HTTP transfers per turn rather than one block.

- **Model Throughput:** We also note your use of Sonnet 4.6 (27k context). If Cursor Cloud forced Max Mode on (rather than a lighter composer model you used natively), the model throughput could differ. Cloud Agents always use Max Mode, so in effect Cursor was likely running at 100k context even if you asked for 20k – not slower per token, but it could influence token flow (e.g. generating in bigger chunks).

To reduce these:

- **Reuse the same Agent:** In the SDK, create one `Agent.create(...)` and call `agent.send()` for each turn. This keeps the index loaded and context warm, unlike using `Agent.prompt()` which creates new agents each time.

- **Prefer Local Runtime:** If your runner has the repo locally, use `local: {cwd: ...}` instead of `cloud:`. A local agent avoids any network overhead and repo cloning. It will still load Cursor’s stack, but at least it runs in-process. 

- **Self-hosted Agents:** Cursor supports “My Machines” or self-hosted cloud pools. If you can run an agent on your own hardware, that should cut latency similarly to using the local runtime. 

- **Minimise Tools/Rules:** Reduce the number of enabled rules and MCP servers, as discussed above. Fewer tokens usually means slightly faster generation. Also, remove any unused heavy hooks (like remote execution).

- **Stream Optimisation:** Ensure your callback (`run.stream()`) is high-performance. The Cursor docs show an example with `await for` on `run.stream()`. Don’t do any expensive work in that loop (like heavy DOM updates). It should simply append to a buffer.

In practice, even with those, Cursor Cloud will likely remain ~2× slower. But you can narrow the gap. A head-to-head comparison using the **same model** in local mode (e.g. use the SDK’s local agent with the `claude-4-6-sonnet` model) would tell you how much is network vs how much is model. The **Cursor forum** acknowledges this problem: in China/India traffic they even suggested workarounds like disabling HTTP/2 or using Cloudflare WARP, calling it a known streaming-edge issue. If your CI runs in India, you might try those or simply run it from a closer region.

## 4. Hybrid Cost Optimization Strategies

Given the strong trade-offs, the optimal harness is **task-dependent**:

- **Simple QA or Chat:** If you are just asking factual or context-free questions, **native** is better. Cursor’s extra context adds latency and cost without benefit. 
- **Codebase Query/Refactoring:** If the task needs to search or edit your code (via GitHub, local files, MCP), Cursor shines. For example, generating a new function in context of the repo, or running CLI commands via the Cursor agent, is only possible in Cursor. 
- **Long Conversations:** For very long, interactive sessions that only use Text I/O, native will save a fortune with prompt caching. Cursor has no additional effect here beyond what a chat UI might offer; its biggest advantage is tools, which you may not need. 
- **Hybrid Flows:** You can mix: run the initial agentic logic in Cursor (to leverage code search or terminal), then switch to native Anthropic for follow-up dialogue and summarisation, or vice versa.

A decision table (heavily simplified) might look like:

| Scenario                | Model / Tools Needed         | Best Harness | Rationale                                   |
|-------------------------|-----------------------------|--------------|---------------------------------------------|
| Quick factual answer    | Claudes available           | Native       | Avoid 10k-token overhead, use cache         |
| Code migration / PR     | Repo code, file edits       | Cursor       | Agent has repo clone, terminals, PR output |
| Multi-turn support chat | Chat context, minor tools   | Native       | Better caching, faster responses           |
| Complex coding session  | Semantic search, CLI tools  | Cursor       | Full agent environment                    |
| Many short tasks        | Various models & tools      | Native (most)| Cheap per-call, only use Cursor when needed|

These guidelines align with competitor patterns: GitHub Copilot is moving from flat-rate to token-based billing on *both* code completion and agentic sessions, implying heavy sessions should pay more. Windsurf offers an “Adaptive” routing that picks smaller models for simpler requests to stretch quota, which is analogous to using native vs cloud. For Stigmer, the rule of thumb is “*less harness = cheaper & faster*,” so carve out simple chat for the native path. 

Prioritisation of changes (following your benchmark and cost figures):
1. **Default routing rule** (native vs Cursor) – highest payoff: by sending simple/medium prompts to native, you get ~50% lower tokens/latency immediately.
2. **Anthropic cache optimisations** – high payoff, easy win: enabling auto-caching and breakpoints can save ~30–80% of repeated-prefix cost.
3. **Use local agent for Cursor tasks** – moderate payoff: avoids cloud startup, likely shaves seconds.
4. **Reduce Cursor context** – uncertain payoff (depends on your config), but worth trimming unneeded rules/servers.

## 5. Billing Architecture & Competitive Landscape

### Billing Architecture

Mixing multiple LLM sources requires a robust cost pipeline. Best practice is **immutable ingestion + canonical reconciliation**. In practice:

- **Ingest Raw Usage:** Record every call attempt *with metadata* before any processing. Include fields like `harness (native/cursor)`, `model_name`, `request_id`, `execution_id`, `user_id`, `tokens_in/out`, `timestamp`, and **source**. Track separate fields for `cache_read_tokens` and `cache_write_tokens` too. This creates an unambiguous audit trail of what each component sent or received.
- **Canonical Records:** Periodically (e.g. at end of run or via background job) combine raw events into a single “billable record” for each LLM call. Use a priority order to resolve duplicates or overlaps (e.g. the runner’s record might say 110 tokens, but if we also captured the network response with 108 tokens, align them). Tools like Stripe’s usage-based billing (Metronome) use precisely this two-layer approach. 
- **Idempotency & Dedup:** Use natural keys if possible. For native Anthropic calls, the `response_id` (or a hash of conversation+prompt) can be an idempotency key. For Cursor, use the unique `run.id` or SDK session ID plus turn number. If not available, synthesize `md5(execution_id + harness + timestamp + tokens)`; any retry must use the same key. This avoids double-charging on retries.
- **Two Cost Dimensions:** Store `estimated_provider_cost` (what *would* be charged by Claude) and `platform_cost` (what Cursor actually bills, if different). This is like LangSmith’s model, where you might emit a custom usage metric for your platform’s overhead. Vercel’s AI Gateway design shows this explicitly: each request log includes *“token count”* and *“total cost”*, and BYOK usage is billed at the provider price with no hidden fees. Braintrust’s proxy does the same by capturing raw span costs; similarly, Stigmer’s billing handler can multiply token counts by per-token prices (from a config) for an “estimated cost”, then compare to actual charges.
- **Trust Tiers:** Consider the source’s trust level. Pure API calls we trust fully; third-party proxies (like Helicone if used) might be best-effort. Usually one source (like your runner) is primary, and others (proxy, SDK telemetry, admin exports) are cross-checks. 
- **Monitoring & Alerts:** Just as Stripe suggests event-driven monitoring, set up alerts for unusual usage spikes or mismatches between estimated vs invoiced spending. For Cursor, you might pull the Analytics API or usage dashboard to reconcile daily; Vercel-like dashboards allow slicing by model/user/tag.

**Industry Practices:**  
- **Vercel AI Gateway** provides every token category and cost in its logs, and an API to query usage by tags/models. Emulate this by tagging your API keys or requests with user/project IDs.  
- **LangSmith** logs provider usage and can accept custom fields; use it or a similar tool to unify multi-source logs.  
- **Helicone** distinguishes between accurate gateway logs and best-effort otherwise, recommending tagging by session ID to group calls.  
- **Braintrust** captures usage in OpenTelemetry spans, including cached tokens for Anthropic. If possible, instrument your native runner to emit similar spans.  

A simple sample schema addition might be:

```json
{
  "execution_id": "abc123",
  "harness": "cursor",
  "user_id": "XYZ",
  "metri_source": "sdk", 
  "request_id": "run-456",
  "model": "claude-4-6-sonnet",
  "tokens_input": 9934,
  "tokens_output": 32,
  "tokens_cache_read": 1536,
  "cost_estimated": 0.0130,
  "cost_billed": 0.0135,
  "timestamp": "2026-05-16T10:00:00Z"
}
```

and use a de-dup key on `(execution_id, source, request_id)`. Always preserve the raw ingestion row for auditing; do not overwrite it. When processing, mark a record as “reconciled” once matched to an invoice. Stripe’s documentation on usage-based billing and idempotency provides a good reference for the general approach.

### Competitive Landscape

Cursor is far from the only AI-IDE platform wrestling with this trade-off. Most others (Copilot, Windsurf, etc.) are adopting similar token-metering models:

- **GitHub Copilot:** As of June 2026 it has switched to pure token-based billing (AI Credits) across all interaction types. Notably, Copilot now counts *input, output, and cached tokens* exactly like an API would, and even code reviews incur GitHub Actions time charges. This matches the move away from fixed-price plans and signals that heavy agentic usage will cost more, aligning with our observation that Cursor (and Copilot) should be treated as “advanced mode” that should cost extra.  
- **Windsurf:** Windsurf’s new pricing (Mar 2026) uses quotas based on model token cost and **refreshing daily/weekly budgets**. They too acknowledge in their blog that prompt caching is critical, and have even exposed a “cache timer” to users. While Windsurf mostly bill by total tokens, they offer an analytics API for enterprise teams and configurable credit caps per user. The takeaway: Windsurf expects high-volume users to monitor tokens closely, similar to Stigmer’s approach.  
- **Vercel AI Gateway:** Vercel’s AI logs and billing are fully usage-based, with zero markup on BYOK. They provide a custom-reporting API (by model, user, tag, provider) and show how to pass through full metadata. This is a leading example of how to build a unified multi-provider billing view.  
- **LangSmith/Weights & Biases:** LangSmith automatically tracks OpenAI/Anthropic usage and even lets you define custom usage categories (e.g. token types or tool calls) for cost. For Stigmer, using a tool like this could give a unified dashboard.  
- **Helicone:** If you used the Helicone proxy, note it has two modes: a gateway mode (100% accurate usage count) or SDK mode (best-effort). They recommend sending a `session_id` to group calls.  
- **Braintrust:** Their open-source documentation shows they capture model, tokens, and custom labels via spans. They already expose Anthropic cache reads as separate fields in their tracing. Adopting a similar span model (e.g. OpenTelemetry) for Stigmer could simplify cost attribution.  

The common theme is that **token-based billing is now standard**, even for IDE agents, and platforms complement it with monitoring. Stigmer should adopt the same: usage-based records plus dashboards and budgets. Your custom billing handler (with JSON model registry for rates) is a good start; just ensure it integrates with upstream data sources like Cursor’s team analytics and, once Copilot has usage APIs, GitHub’s new reporting.
