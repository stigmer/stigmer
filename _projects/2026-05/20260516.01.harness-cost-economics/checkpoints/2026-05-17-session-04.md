## Decisions Made

- **Session-level CursorMode override (Option A)** chosen over separate cursor-runner instances (Option B) — the proto field already exists, cursor-runner already branches on it, and same-process comparison eliminates confounding variables
- **Cloud sessions use stigmer repo as workspace entry** — provides a real git repo for Cursor to clone, avoids needing external test fixture repos
- **6-minute timeout for cloud executions** (vs 4 minutes for existing benchmarks) — cloud VM provisioning adds 10-60s overhead
- **Separate report directory** (`cursor-mode-results/`) rather than mixing into existing `benchmark-results/` — different comparison dimensions should not pollute each other's trend analysis

## Learnings

- The stigmer-server uses `proto.Clone` on the full request for session creation, then applies targeted mutations (ID, slug, defaults). This means ANY spec field set by the client is persisted — no allowlist/denylist filtering. Good for extensibility, but means the server trusts client-set values on creation.
- `CursorMode` enum values use `CURSOR_MODE_` prefix (`CURSOR_MODE_LOCAL`, `CURSOR_MODE_CLOUD`), not bare `LOCAL`/`CLOUD`
- The cursor-runner's mode selection already has the right priority: explicit session `cursor_mode` > auto-detection from workspace entries + feature flag. No cursor-runner changes needed for WI-5.
