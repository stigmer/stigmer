# Deep Research: Building a State-of-the-Art React SDK for Real-Time Streaming AI Agent Conversations

## Research Objective

We are building **@stigmer/react** — a public React SDK that platform builders embed into their own products to display real-time AI agent conversations. The SDK provides a **MessageThread** component (renders the conversation), a **SessionComposer** component (message input), and underlying data/behavior hooks.

We are experiencing **visual flickering and jank** in the MessageThread during real-time gRPC streaming of agent execution updates. We need a comprehensive research report on how to build a **state-of-the-art, flicker-free, production-quality** streaming message thread and composer experience in React — comparable to or exceeding the quality of ChatGPT, Claude, Cursor, Linear, and other best-in-class streaming UIs.

The research should cover both **diagnosing common flickering causes** in React streaming UIs and **prescriptive architectural patterns** for building the best possible experience.

## Our Context and Architecture

### What We Are Building

Stigmer is a **platform for platforms** — teams building software products integrate Stigmer to add AI agent capabilities. The React SDK (`@stigmer/react`) is the primary integration surface. Platform builders do:

```tsx
import { StigmerProvider, MessageThread, SessionComposer, useSessionConversation } from '@stigmer/react';

function Chat({ sessionId, org }) {
  const conv = useSessionConversation(sessionId, org);
  return (
    <>
      <MessageThread
        executions={conv.completedExecutions}
        activeStreamExecution={conv.activeStreamExecution}
        pendingUserMessage={conv.pendingUserMessage}
        onApprovalSubmit={conv.submitApproval}
      />
      <SessionComposer
        onSubmit={(msg, model) => conv.sendFollowUp(msg, { modelName: model })}
        disabled={!conv.canSendFollowUp}
        isSubmitting={conv.isSending}
      />
    </>
  );
}
```

### The Data Flow

1. **Backend streams full execution snapshots** via gRPC server-streaming (using Connect protocol / `@connectrpc/connect`). Each stream message is the **entire AgentExecution object** — not deltas. This means every stream event replaces the full message list, tool call list, sub-agent list, etc.

2. **`useExecutionStream` hook** subscribes to the gRPC stream via `stigmer.agentExecution.subscribe(executionId)`. On each stream event, it calls `setExecution(snapshot)` — replacing the entire React state with the new snapshot object.

3. **`useSessionConversation` hook** orchestrates the lifecycle. It composes:
   - `useSession(sessionId)` — fetches session data
   - `useSessionExecutions(sessionId)` — fetches completed executions list
   - `useExecutionStream(activeExecutionId)` — streams the live execution
   - Multiple `useState` variables for pending messages, pending IDs, etc.
   - Multiple `useEffect` hooks that react to state changes (clearing pending messages when stream delivers, refetching when terminal phase is reached)

4. **`MessageThread` component** receives `executions` (completed, from list fetch) and `activeStreamExecution` (from stream). It uses `useMemo` to flatten all executions into a flat `ThreadItem[]` array (discriminated union of message, tool-group, sub-agent, phase-badge, approval-request, setup-progress, pending-message). Items are rendered via `.map()` with a `switch` on `item.kind`.

5. **`MessageEntry` component** renders individual messages. AI messages use `react-markdown` (with `remark-gfm`) to render markdown content. Human messages render plain text. Thinking messages are collapsible.

### The Streaming Pattern (Full Snapshot Replacement)

The gRPC stream sends the complete `AgentExecution` proto on every update. This means:
- When token 50 arrives, the stream message contains all 50 tokens in `messages[n].content`
- When token 51 arrives, the stream message contains all 51 tokens — the entire execution state from scratch
- Tool calls, sub-agent executions, pending approvals — all are included in every snapshot
- There is no delta/patch protocol — each snapshot is self-contained

This is intentional for simplicity and correctness (no client-side merge logic), but it means every stream event creates an entirely new object graph that React sees as "changed."

### Data Fetching Layer (`useFetch`)

All non-streaming data is fetched via a custom `useFetch` hook with stale-while-revalidate semantics:
- First load: `isLoading=true`, shows skeleton
- Subsequent fetches (dep change, manual `refetch()`): `isRefetching=true`, stale data stays visible
- When `fetchFn` becomes `null`: full state wipe — `setData(initialData)`, `hasDataRef.current = false`
- Optional `refetchInterval` for polling (used only by runner lists, not by session/execution hooks)
- No shared cache — each hook instance is independent

When `sessionId` changes (navigation), the hook does NOT clear stale data — it keeps the old session's data visible while the new session loads. This causes the "flash of wrong content" problem.

### Session Navigation Pattern

The Console is a Next.js app with a sidebar listing recent sessions (`useSessionList()`). Clicking a session navigates to `/sessions/[id]`, which renders `SessionPage`:

1. `useStaticRouteParam("id")` reads the route param
2. `useSessionPageFlow({ sessionId, org })` orchestrates everything
3. Inside: `useSessionConversation(sessionId, org)` composes `useSession`, `useSessionExecutions`, `useExecutionStream`
4. All three data sources fire new requests when `sessionId` changes
5. They resolve independently — the page may render partially updated state (new session object + old execution list, or vice versa)

The sidebar also refetches the session list on navigation (plus staggered 8s/18s timeouts for LLM subject generation), which can cause the sidebar to shift while the user is reading the session page.

## Observed Problems

### 1. Message Thread Flickering

During active streaming, the message thread exhibits a visual flickering effect. We suspect this is caused by one or more of:

- **Full snapshot replacement** — Every stream event creates a new `AgentExecution` object with new `messages` array, causing `useMemo` to rebuild all `ThreadItem[]` entries, which causes React to diff and potentially re-render every item even though most haven't changed.
- **No memoization on child components** — `MessageEntry`, `ToolCallGroup`, `SubAgentSection`, etc. are not wrapped in `React.memo`. Every parent re-render re-renders all children.
- **react-markdown re-parsing** — The `Markdown` component from `react-markdown` re-parses the full content string on every render. During streaming, AI message content grows with each token — but the entire string is re-parsed, not just the appended content.
- **Multiple sequential state updates** — `useExecutionStream` calls `setExecution(snapshot)`, `setIsConnecting(false)`, and `setIsStreaming(!isTerminal)` as separate state updates. Even with React 18+ automatic batching in async contexts, the `for await...of` loop may not batch all three updates.
- **Cascading effects** — `useSessionConversation` has `useEffect` hooks that react to `stream.execution` (clearing pending message) and `stream.phase` (refetching), causing additional render cycles.
- **Key instability** — Thread items use index-based keys like `e${ei}-m${mi}`. If the execution list order changes (e.g., when `pendingExecutionId` is cleared and it appears in the fetched list), items may get new keys, causing unmount/remount.

### 2. Composer Interaction Jank

The SessionComposer is a complex component with many hooks (`useAgentSetup`, `useMcpServerSetup`, `useAttachments`, `useRunnerList`, etc.). During streaming, the parent page re-renders frequently (due to stream updates), and the composer may re-render unnecessarily even though its own state hasn't changed.

### 3. Session-to-Session Navigation Flash

When the user navigates from one session to another (e.g., clicking a different session in the sidebar), the entire session page "flashes":

- **Stale-while-revalidate shows wrong data briefly** — Our `useFetch` hook preserves old data during refetch (stale-while-revalidate). When switching from Session A (20 messages) to Session B (3 messages), the user briefly sees Session A's 20 messages, then a flash to Session B's 3 messages. This is disorienting.
- **`useExecutionStream` resets to null** — When `executionId` changes (new session has a different active execution or none), the hook calls `setExecution(null)`, `setIsConnecting(true)`. This creates a gap where `activeStreamExecution` goes: old execution → `null` → new execution. The thread briefly loses its streaming content.
- **Cascading state resets** — When `sessionId` changes, `useSession`, `useSessionExecutions`, and `useExecutionStream` all fire new requests simultaneously. Multiple state updates cascade through the tree: loading states, execution lists, stream state. The page may render 3-4 intermediate states before settling.
- **`useFetch` full wipe when fetch function becomes null** — If `sessionId` briefly becomes null during a route transition, `useFetch` resets everything: `setData(initialData)`, `hasDataRef.current = false`, `setIsFetching(false)`. The next fetch starts from scratch (showing skeleton/loading instead of stale-while-revalidate).

**Sidebar session list additional concerns:**
- The sidebar calls `useSessionList()` and does staggered refetches (8s, 18s timeouts) after `activeSessionId` changes to pick up LLM-generated session subjects. Each refetch updates the session list, potentially causing sidebar reflows (items shifting, subjects appearing).
- When navigating to a newly created session, the sidebar refetch may cause the session list order to shift as the new session gets a subject.

### 4. Long Conversation Degradation

As conversations grow (100+ messages, many tool calls), performance degrades because:
- All items are rendered in the DOM (no virtualization)
- `buildThreadItems` iterates all executions on every stream event
- Each tool call and sub-agent section has collapsible panels with their own state

### 5. Data Fetching / Polling Concerns

Our generic `useFetch` hook has polling support (`refetchInterval`) but even without polling, the interaction between multiple `useFetch` instances on the same page causes issues:
- `useSession(sessionId)`, `useSessionExecutions(sessionId)`, and `useExecutionStream(activeId)` all operate independently. When one resolves and triggers a state update, the parent re-renders, which can cause the others to re-evaluate their derived state.
- `useSessionConversation` has a `refetch()` call triggered when the stream hits a terminal phase. This refetches the execution list, which changes `executions`, which changes `completedExecutions` and `listActiveId`, which can ripple into `activeExecutionId`, which can cause `useExecutionStream` to resubscribe.
- There is no request deduplication or shared cache — if two components both call `useSession(sameId)`, they make two independent network requests.

   - Component hierarchy and memoization strategy

   - How to handle the "growing last message" pattern (streaming token by token) without re-rendering stable earlier messages
3. **Virtualized scrolling for message threads** — When and how to implement virtualization for long conversations. ## Constraints and Requirements

- **React 19** — We are on React 19. The research should account for React 19's concurrent features, automatic batching, and any new APIs.
- **No framework dependency in SDK** — The SDK (`@stigmer/react`) cannot depend on Next.js, Remix, or any framework. It must work in any React 19 environment.
- **Protobuf messages** — Our data comes from `@bufbuild/protobuf` v2 generated classes, which are not plain JavaScript objects. This affects how structural comparison and shallow equality checks work.
- **gRPC/Connect transport** — Server streaming uses `@connectrpc/connect` which provides `AsyncIterable<T>`. We cannot easily switch to SSE or WebSockets at the transport layer.
- **Accessibility** — The message thread uses `role="log"`, `aria-live="polite"`, and `aria-relevant="additions"`. Any architectural changes must preserve accessibility. Screen readers must announce new messages.
- **Theme isolation** — Components render inside a `.stgm` container with `@layer stgm` CSS isolation and `--stgm-*` custom properties. Animation/layout solutions must work within this scoping.
- **Bundle size** — The SDK is a peer dependency. We want to minimize the size of additional libraries we bring in.
