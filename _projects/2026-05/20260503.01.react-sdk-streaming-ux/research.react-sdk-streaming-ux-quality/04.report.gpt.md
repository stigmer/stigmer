# Building a State-of-the-Art React SDK for Real-Time Streaming AI Agent Conversations

## Executive Summary

The dominant cause of your thread flicker is not gRPC itself and not React 19 by itself. It is the combination of **full-snapshot replacement**, **parent-driven rendering**, and **expensive leaf work**. Every streamed snapshot currently gives React a fresh object graph for messages, tool calls, approvals, and sub-agents, which defeats shallow prop equality, invalidates memoization, and forces the thread to reconcile much more UI than the user actually changed. React’s own guidance on `memo`, list keys, and Performance Tracks all point in the same direction: keep rendering pure, keep props stable, and stop cascading updates before they spread through the tree. citeturn12view0turn13search1turn12view1turn17view0

The single highest-impact change is to insert a **normalization and structural-sharing layer between the gRPC stream and React rendering**. Keep the server protocol as full snapshots if you want its correctness and simplicity, but do **client-side ingestion-time diffing by stable entity ID**, preserve references for unchanged messages and tool groups, and expose thread rows through **selector-based subscriptions** rather than passing the whole `AgentExecution` object through props. That is the pattern React formalized with `useSyncExternalStore`, and it is the same family of optimization used by TanStack Query’s structural sharing, Zustand selectors, Jotai atom splitting, and Valtio’s copy-on-write snapshots. citeturn11view2turn17view0turn21search3turn22view0turn22view1turn23view1

The top five actions I would take, in order, are these:

- **Add a stream ingestion store with structural sharing and per-item selectors.** Do not store the live execution as one parent `useState(snapshot)` object; normalize it by stable IDs and update only changed entities. citeturn11view2turn17view0turn23view1
- **Render the thread as stable item IDs plus memoized leaf rows.** The list should re-render only when item order changes or the last streaming item changes; earlier messages should keep the same object reference and the same key. citeturn12view0turn13search1
- **Treat the actively growing assistant message as a special rendering path.** Keep `react-markdown` for completed messages if you like, but use a streaming-aware renderer such as Streamdown, or a stable-prefix-plus-live-tail strategy, for the currently streaming block. citeturn33view1turn33view2turn33view3
- **Replace identity-blind stale-while-revalidate with key-based caching semantics.** Session A data must never remain visible under Session B’s route key. Use per-session cache entries, abort stale requests, and switch to cached new-session data or a placeholder immediately on key change. citeturn17view1turn17view2turn19view0turn19view1turn15search0
- **Adopt virtualization once thread size is no longer small.** For variable-height, bottom-anchored chat UIs, `react-virtuoso` core is the best default choice in open source; TanStack Virtual is the best headless choice if you want full control; `react-window` is the least suitable of the three for streaming chat with variable heights. citeturn27search1turn27search7turn25view2turn26view0turn34view2

My overall recommendation is: **do not chase the flicker with scattered `useMemo`, ad hoc throttles, or one-off `React.memo` wrappers first**. Start by changing the **shape of the data flow** so unchanged UI keeps the same identity. After that, add targeted memo boundaries, streaming-aware markdown, route-keyed caching, and virtualization. That sequence matches how high-quality realtime UIs are built and is much more likely to get you to a ChatGPT/Claude/Cursor-grade feel than micro-optimizing the current full-tree render path. citeturn11view2turn12view0turn17view0turn34view0turn33view2

## Diagnosing Flicker in React Streaming UIs

### What is likely causing the current flicker

Your current pattern turns each stream tick into a large React update because the top-level execution object and its nested arrays are replaced wholesale. `React.memo` only helps when props are shallowly equal, and React’s list reconciliation only remains stable when keys are stable. If every tick creates new arrays and object references, many children will still be reconsidered even when their visible content did not change. In other words, your current rendering model is optimized for correctness, but not for referential stability. citeturn12view0turn13search1turn17view0

The most common causes of flicker and jank in streaming chat UIs are these: unstable keys; parent re-renders that force all rows to be reevaluated; effects that schedule more updates after a render; layout-affecting scroll logic; and expensive per-row rendering such as Markdown parsing, syntax highlighting, image measurement, or collapsible panel recalculation. React’s Performance Tracks explicitly call out **cascading updates** as a regression pattern, and the memo documentation explicitly warns that “always new” objects or functions will break memoization. citeturn12view0turn12view1

Your suspected causes line up with these known patterns almost point-for-point. Index-based keys are especially risky when items can move from “pending” to “fetched,” because React uses keys to match list items across renders. If the same semantic item gets a new key after a refetch or reorder, React will unmount and remount it, which is exactly the kind of behavior users experience as visual flashing, collapsed-panel resets, or scroll jolts. citeturn13search1turn13search0

There is also an accessibility angle here. A `role="log"` live region is intended for sequential additions, and assistive technology works best when the log container remains stable and new content is appended in order. MDN’s live-region guidance also notes that the live region should exist before the changes occur. Replacing or remounting the entire message log subtree on each stream tick is therefore bad for both performance and announcement quality. citeturn29search0turn29search3turn29search12turn29search13

### React 19 changes the tools, not the core rule

React 19 gives you better primitives for async work, but it does not make render-surface identity problems disappear. `startTransition` marks updates as non-blocking, and React 19 allows async functions inside transitions, but the official docs still note an important caveat: **state updates after an `await` currently need another `startTransition`** if you want those updates to remain part of a transition. In a `for await...of` stream, every yielded snapshot effectively arrives after an `await`, so you should assume each streamed commit needs its own explicit transition wrapper if you want thread updates to stay lower priority than typing. citeturn11view3turn11view4

React 19 also does not let transitions control text inputs. That matters directly for your composer. The thread should be allowed to lag slightly under load; the text area must not. So the correct React-19-era split is: **input state stays local and urgent**, while thread repaint work becomes non-urgent and optionally throttled. citeturn11view3turn12view0turn34view0

React Compiler is also not the answer to this specific problem. The React docs explain that the compiler can eliminate some manual memoization when props are stable, but your current stream model is producing “always new” props for many descendants. So even if some host apps eventually compile your SDK, you should not rely on that to solve full-snapshot churn. For a published SDK, design for stable runtime semantics first; treat Compiler gains as optional upside, not architecture. citeturn12view0turn10search4

### gRPC server streaming with React without causing a repaint storm

Connect’s browser client returns server streams as an `AsyncIterable`, so `for await...of` is a first-class pattern, and Connect also supports cancellation through `AbortSignal`. Their web docs recommend memoizing clients and transports, and their cancellation docs recommend aborting calls you no longer care about. That means your `useExecutionStream` hook should always do three things: reuse a memoized client, attach an `AbortController`, and stop the old stream as soon as the execution or session identity changes. citeturn11view0turn15search0

The critical rendering rule inside that loop is simple: **do not call several independent React `setState` functions per chunk**. Instead, gather everything the UI needs from that chunk — normalized entities, stream phase, connectivity state, pending approval state, first-token flag, terminal flag — and commit it through one store transaction or one reducer dispatch. If that update is thread-only work, wrap it in `startTransition`. If you also want to cap render frequency, buffer the latest snapshot and commit at most once per animation frame with `requestAnimationFrame`. citeturn11view3turn5search3turn11view2

### Full snapshots are acceptable if you fix identity at the boundary

You do **not** need to switch the backend to deltas to eliminate flicker. Deltas are excellent for bandwidth and can simplify some client work, but full snapshots are perfectly viable if the client ingests them into a store that preserves references for unchanged entities. This is exactly the insight behind structural sharing in TanStack Query: even when a network fetch returns a brand new JSON object, the cache keeps old references for unchanged parts so downstream components do not re-render unnecessarily. Valtio’s snapshot model makes the same point from a different angle: deep snapshots can still reuse unchanged children when only one leaf changed. citeturn17view0turn23view1

So the right answer to “should we add a client-side diffing layer?” is **yes, but not a generic deep diff in render code**. Add an **ingestion-time normalization and structural-sharing layer keyed by stable message/tool/sub-agent IDs**. Compute equivalence once per arriving snapshot, preserve references for unchanged records, and let render consume stable slices. That gives you most of the UX benefit of delta streaming without changing the transport contract. citeturn11view2turn17view0turn21search1turn22view1

## State-of-the-Art Streaming Message Thread Architecture

### What best-in-class AI chat UIs are doing differently

There is limited public documentation on the exact React internals of ChatGPT, Claude, or Cursor, but the public APIs around them are revealing. OpenAI’s current Responses API streams **typed semantic events** over SSE, and Anthropic’s streaming Messages API likewise emits event sequences such as `message_start`, `content_block_delta`, and `message_stop`. That is an incremental event model, not “replace the whole conversation object every token.” Vercel’s AI SDK similarly centers its `useChat` hook on streaming message updates and a transport abstraction rather than input state living inside a giant component. citeturn34view6turn8search1turn34view0turn34view1

That does not prove how ChatGPT or Claude implement their browsers internally, but it strongly suggests the UI pattern you want: **append a new assistant turn once, then update only the last in-progress part of that turn as text arrives**. That is the core difference between a polished AI chat UI and a naive React implementation. The best products are almost certainly not rebuilding a whole heterogeneous thread tree on every token if they can avoid it; they are isolating a very small mutable tail. citeturn34view6turn8search1turn34view0turn33view2

### The right component architecture for your thread

The thread should render from a **stable ordered list of item IDs**, not from nested execution snapshots. The list itself should be cheap to compute and should usually change in only two ways: a new item ID is appended, or the metadata for the current in-progress last item changes. Every actual row component should then subscribe to its own item by ID. That turns “one stream snapshot arrived” into “maybe only the last row rerendered.” citeturn11view2turn12view0turn17view0

A practical target structure looks like this:

```txt
<StigmerProvider>
  <ConversationCacheProvider>
    <SessionPane key={sessionId}>
      <MessageThreadShell>
        <ThreadViewport role="log" aria-live="polite" aria-relevant="additions text">
          <VirtualList itemIds={visibleItemIds}>
            <ThreadRow itemId="msg_1" />
            <ThreadRow itemId="toolgrp_2" />
            <ThreadRow itemId="msg_3_streaming" />
          </VirtualList>
        </ThreadViewport>
      </MessageThreadShell>

      <ComposerShell>
        <SessionComposer />
      </ComposerShell>
    </SessionPane>
  </ConversationCacheProvider>
</StigmerProvider>
```

This design keeps the log container stable for accessibility, keeps route-local state resettable by `sessionId`, and ensures the hot path is the row identified by the streamed item ID rather than the full thread. citeturn29search0turn29search12turn13search0turn11view2

`ThreadRow` should be a small `memo`ized switch component that receives only an `itemId`, pulls the item from the store, and then renders `MessageEntry`, `ToolGroupEntry`, `SubAgentEntry`, `ApprovalEntry`, or `PhaseBadgeEntry`. Those leaf components should receive primitives or narrow slices, not the whole execution or whole thread item union object if you can avoid it. React’s memo docs are explicit: keep prop changes minimal, avoid passing fresh objects and inline functions, and prefer local/transient state where possible. citeturn12view0

### Where memoization boundaries should live

Put memo boundaries at **row and leaf level**, not only at the top-level thread. A memoized thread that receives a brand new array and brand new item objects every tick will still blow through memoization. A memoized row that looks up its own stable entity by ID from an external store is far more effective. This is why selector-driven stores outperform “pass the full list downward” patterns for high-frequency updates. citeturn12view0turn11view2turn21search0turn21search3

Two specific patterns matter here. First, use **semantic keys** derived from stable server IDs, never indexes. Second, if you create derived arrays such as `visibleItemIds`, make sure unchanged regions preserve reference when possible. If nothing earlier in the thread changed, the first 99 IDs should remain the same references and in the same order while token 100 is still growing. citeturn13search1turn17view0

### Markdown rendering during streaming

For completed messages, `react-markdown` remains a reasonable default because the unified/remark ecosystem is mature and flexible. But for the **actively streaming last message**, the unified-style Markdown pipeline is not incremental by default; it transforms Markdown into a syntax tree, and when the string changes, that parse/transform/render cycle must run again. Vercel introduced Streamdown specifically because standard Markdown packages are unreliable with incomplete or unterminated streaming chunks, and Streamdown advertises memoized, streaming-optimized rendering for that exact case. citeturn33view1turn33view2turn33view3

The best production pattern is therefore split-path rendering:

- Completed assistant messages: parse once with your standard renderer.
- Streaming assistant message: use Streamdown **or** a custom renderer that freezes the stable prefix and reparses only the trailing unstable block.
- On terminal completion: replace the streaming renderer with the finalized full Markdown render if needed. citeturn33view2turn33view3

If you want the lowest engineering risk now, use **Streamdown only for the active streaming row** and keep `react-markdown` for historical rows. That gives you better incomplete-Markdown behavior without forcing a broad renderer rewrite across your entire SDK surface. citeturn33view2turn33view3

### Virtualized scrolling and bottom-follow behavior

For chat UIs with variable-height content, the comparison is fairly clear. `react-virtuoso` core is purpose-built for variable-sized items, auto-resizes when content changes, and supports `alignToBottom` plus `followOutput` for chat-like append behavior. Its commercial `VirtuosoMessageList` goes even further and is explicitly built for human/AI conversations with automatic scroll control and streaming examples. TanStack Virtual is very capable and headless, but you have to build more of the chat behavior yourself. `react-window` is solid for general list virtualization, but its own docs note that dynamic row heights are less efficient, which makes it a worse fit for long, variable-height AI threads with Markdown, code blocks, and collapsible tools. citeturn27search1turn27search7turn25view0turn25view1turn25view2turn26view0

For your SDK, I would recommend this policy:

- **Under roughly 150 rendered thread blocks** and modest tool richness, non-virtualized rendering is acceptable if the ingestion layer preserves identity.
- **Above that**, or as soon as profiler data shows commits becoming noticeable on mid-tier hardware, turn on virtualization.
- Prefer **`react-virtuoso` core** for the default SDK implementation because it handles variable-height chat content with less custom engineering.
- Prefer **TanStack Virtual** only if you want maximal control and can afford to build the scroll model yourself.
- Avoid `react-window` as the default for this specific problem class. citeturn27search1turn27search7turn25view2turn26view0turn34view2

Auto-scroll should use a **follow-the-tail state machine**, not unconditional `scrollIntoView` on every update. The robust pattern is: track whether the user is “near bottom” with a bottom sentinel and `IntersectionObserver`; stay pinned when near bottom; disengage follow mode when the user scrolls away; and re-engage when the sentinel becomes visible again. If you are manually controlling scroll anchoring, set `overflow-anchor: none` on the controlled scroller to prevent the browser from fighting your own anchoring logic. When you do scroll imperatively, do it in `requestAnimationFrame` so layout and paint stay aligned. citeturn28search2turn28search0turn28search1turn5search3

## State Management and Data Fetching for High-Frequency Streams

### React-only hooks are not enough for the hot path

Could you solve this with plain React hooks only? Yes — but not with the current “parent owns full execution state” shape. The correct React-native primitive for this kind of problem is `useSyncExternalStore`, which exists specifically to connect React safely to state that lives outside React’s own component state. That lets you keep a tiny, framework-agnostic internal store in your SDK and subscribe rows to precise slices of data without forcing the whole `MessageThread` tree to rerender from the top. citeturn11view2

That means the best answer to “should we adopt Zustand, Jotai, or Valtio?” is nuanced:

- **You do not need an external library** to solve this; a small internal store built on `useSyncExternalStore` is enough and keeps your SDK surface clean. citeturn11view2
- **If you want the best ergonomics with minimal conceptual overhead**, Zustand’s vanilla store plus selectors is the closest fit. It is explicitly designed to use a vanilla store in React and offers selector/equality controls for granular rerendering. citeturn21search3turn21search0turn21search1
- **Jotai** is excellent if you want atom-per-item or atom-per-slice patterns; its own performance docs emphasize small components, heavy work outside render, and utilities such as `splitAtom` for dynamic lists. citeturn22view0turn22view1
- **Valtio** is attractive when you want access tracking and copy-on-write snapshots, but its proxy model is a stronger opinion to bake into a public SDK. citeturn23view0turn23view1

For a public SDK with bundle-size sensitivity, my recommendation is: **build a tiny internal store on `useSyncExternalStore`, and keep Zustand as an implementation reference, not a required public dependency**. citeturn11view2turn21search3turn21search0

### Structural sharing is more important than immutable purity slogans

The winning pattern for your full-snapshot stream is:

1. ingest snapshot,
2. normalize entities by ID,
3. compare field-level changes only where needed,
4. preserve old object references for unchanged entities,
5. update the ordered list of thread item IDs separately. citeturn17view0turn23view1

That is better than deep-cloning immutable trees every tick, and it is usually better than running a generic deep-equality function on the whole protobuf object graph every tick. TanStack Query’s docs are helpful here because they say the quiet part out loud: network responses tend to arrive as new references, so structural sharing is what preserves referential stability downstream. citeturn17view0

If you choose to use Immer internally for ergonomics, use it only as a way to express updates to your **normalized store**, not as a way to replace the root execution object with every snapshot. Replacing the root draft with a fresh full snapshot defeats the whole point. The optimization is not “immutability”; the optimization is **unchanged references remaining unchanged**. citeturn17view0turn23view1

### Debouncing and throttling the stream

You should usually **throttle renders, not network ingestion**. Keep reading every stream event so client state stays logically current, but commit visible UI updates at most once per frame or roughly 30–60 times per second. Browsers already synchronize paint with `requestAnimationFrame`, and using rAF as your commit gate is the simplest way to stop a high-frequency token stream from outpacing the screen refresh rate. citeturn5search3

A good default policy is:

- first token: commit immediately;
- mid-stream tokens: coalesce to once per animation frame;
- terminal event: commit immediately and finalize markdown;
- connectivity/status changes: commit in the same transaction as content if they refer to the same snapshot. citeturn11view3turn5search3

This is one of the largest practical differences between polished AI chat UIs and naive ones. The user perceives “constant motion,” but the screen is not actually repainting for every raw token event. citeturn5search3turn33view2

### Optimistic user messages and the no-stream gap

React 19’s `useOptimistic` and TanStack Query’s optimistic update patterns both support the message flow you want: show the user message immediately, keep it visible while the mutation is pending, and then reconcile with the true server state. That is the foundation for eliminating the awkward “I clicked send, then nothing happened until the stream appeared” gap. citeturn11view5turn17view4

The ideal state machine is:

- `draft`
- `submitted`
- `queued`
- `connecting`
- `streaming`
- `complete`
- `error` citeturn11view5turn17view4

The UI mapping should be equally explicit. On submit, append the optimistic user bubble immediately. While waiting for the execution and first stream chunk, insert a placeholder assistant row in the correct position — not `null`, not a disappearing thread. When the first streamed content arrives, hydrate that same row with content. On completion, swap it to finalized render state and invalidate the execution list cache. That removes the visual glitch between “send” and “stream start” without pretending the server has already completed the assistant turn. citeturn11view5turn17view4turn15search0

## Navigation, Sidebar Stability, and Composer UX

### Fixing the flash of wrong content on session switches

Your current `useFetch` behavior is correct for “refetch the same identity,” but incorrect for “switch to a different identity.” SWR’s own docs distinguish key-change behavior from ordinary fetch/revalidate behavior, and both SWR and TanStack Query are built around **query keys**. When the key changes, the new data source is a different cache entry. Whether you choose to keep previous data is an explicit policy choice, not the default truth of the UI. citeturn17view2turn17view1turn19view2

For chat session navigation, the correct policy is: **do not show Session A’s transcript under Session B’s route key**. On `sessionId` change, either show cached Session B content instantly or show a neutral Session B placeholder or skeleton immediately. Old-session data can remain in cache for instant back-navigation, but it should not remain visible in the active pane once the identity changed. citeturn17view1turn17view2turn19view1

React’s state-preservation docs are relevant here too. State is associated with position in the UI tree, and changing keys is the standard way to reset subtree-local state. That means your route-local session pane should be keyed by `sessionId`, so composer drafts, pending placeholders, scroll flags, and local disclosure state belong to the correct session. Cache belongs outside that boundary; ephemeral UI state belongs inside it. citeturn13search0

### Request coordination across session, executions, and stream

When a session switch triggers `getSession`, `listExecutions`, and `subscribe`, those requests should be coordinated through one **session controller** or one cache-backed view model, not through three unrelated hooks racing to paint partial data. TanStack Query is stronger than SWR for your specific requirements because it provides key-based caching, structural sharing, selectors, invalidation, and request-dedup-friendly semantics that line up well with a multi-resource screen. SWR is lighter and very good at cache/revalidate and deduplication, but it is less opinionated about orchestrating several interdependent resources into one route-level state machine. citeturn17view0turn17view1turn19view0turn19view2turn20view0

If you do not want to ship TanStack Query inside the SDK, then copy its semantics internally: key-based cache entries; request deduplication; structural sharing; `enabled`/conditional loading instead of `fetchFn = null` wipes; placeholder policy that depends on whether the key is the same or different; and explicit invalidation on stream terminal events rather than effect-chains that refetch and resubscribe in surprising order. citeturn17view0turn17view1turn19view0turn20view0

Also, always cancel the old stream as soon as the identity changes. Connect’s web client supports cancellation with `AbortSignal`, and gRPC guidance in general is clear that cancellation should stop unnecessary work when the client is no longer interested in the result. That matters for correctness, server cost, and preventing late chunks from Session A leaking into Session B’s store. citeturn15search0turn15search15

### Using transitions without showing the wrong conversation

`startTransition` is valuable here, but only for the right purpose. Use it to keep the app responsive while a route swap and cache hydration happen in the background. Do **not** use it as an excuse to leave the old transcript in place under the new route key. The old shell can remain interactive while the new session prepares, but the content pane itself should switch either to cached new-session content or to a placeholder as soon as the identity changes. citeturn11view3turn11view4

If you want a visual polish layer on top of that, the browser’s View Transition API is now baseline across latest browsers for same-document transitions, and the browser API is preferable to any React-experimental wrapper in an SDK context. React’s `<ViewTransition>` API is still experimental/canary, whereas `document.startViewTransition()` itself is a standard browser API with a fallback path. That makes view transitions a good **host-app enhancement**, not a core dependency of `@stigmer/react`. citeturn32view1turn32view2turn32view0

### Keeping the sidebar stable when subjects arrive later

The sidebar should not reorder because a session title changed from “Untitled” to an LLM-generated subject. The simplest rule is: **sort by a stable timestamp or stable server-side rank, not by mutable subject text**, and reserve fixed vertical space for each row so late-arriving titles do not change row height. If you do need to reorder after a true ranking change, animate that reorder rather than letting the list jump. React’s key guidance applies here as well: keep keys stable so the same row is updated in place instead of remounted. citeturn13search1turn32view2

For long sidebars or heavy session rows, `content-visibility: auto` can reduce offscreen rendering work, and native or View-Transition-based animations can soften the remaining UI movement. But the biggest win is policy: mutable metadata should update **within** the row, not reshuffle the row unless the sort key itself truly changed. citeturn5search0turn32view2

### Composer isolation and input responsiveness

The composer should be in a sibling subtree with its own local state, not a child that is casually rerendered by every streaming update. React’s docs explicitly recommend keeping transient form state local and not lifting it higher than necessary, and `startTransition` explicitly cannot be used to control text inputs. This gives you a very strong architectural rule: store the draft text, selection, and input adornment state inside the composer subtree, and let the thread update on a different priority path. citeturn12view0turn11view3

Vercel’s current `useChat` design is a useful reference point here because its React hook now uses a transport architecture and no longer manages input state internally. That separation is a clue: transport state and input state should not be tightly coupled. For Stigmer, `SessionComposer` should own its draft locally, accept a stable `onSubmit`, and subscribe only to the narrow booleans it truly needs, such as `canSendFollowUp`, `isSubmitting`, or `runner availability`. citeturn34view0turn34view1

For self-resizing textareas, the most production-safe answer today is still JavaScript measurement with a max height and inner scrolling after the limit. The new `field-sizing` CSS property is promising because it lets form controls size to fit content, but it should be treated as progressive enhancement rather than the only implementation path. If the composer’s size changes affect the thread viewport, use `ResizeObserver` to adjust bottom padding or scroll math without continuous polling. citeturn30search0turn30search13turn5search2

### Animation and perceived performance

You do not need a large animation library to make this feel premium. For message enter animations, use CSS transforms and opacity, and leverage `@starting-style` for clean entry transitions when elements first appear. For navigation transitions, prefer the browser View Transition API where the host app wants it. Use Motion only if you later need complex layout choreography, exit animations, or gesture-heavy interactions that are painful to implement with CSS alone. citeturn6search0turn32view1turn32view2turn6search2turn6search12

Perceived performance wins also come from showing the right placeholder at the right time. A cold session switch should show a neutral skeleton. A submitted follow-up should show the optimistic user bubble instantly. A stream that exists but has not yielded content yet should show a lightweight “agent is responding” placeholder in the exact row where the answer will land. And once lists become long, either virtualize or at least use `content-visibility: auto` for offscreen regions rather than paying full layout and paint costs for everything. citeturn11view5turn17view4turn5search0

## Recommended Architecture and Implementation Roadmap

### The proposed architecture

I would re-architect your stack around four internal layers:

1. **Cache layer** for `session`, `executionList`, and per-session metadata, keyed by identity.
2. **Stream ingestion layer** that accepts full execution snapshots and normalizes them into stable entity maps with structural sharing.
3. **Selector layer** that exposes `useThreadItem(id)`, `useThreadOrder(sessionId)`, `useStreamStatus(sessionId)`, and narrow booleans for the composer.
4. **UI layer** with a virtualized or non-virtualized ordered list of item IDs and memoized rows. citeturn11view2turn17view1turn17view0turn12view0

In concrete terms:

```txt
Connect stream
    -> stream controller
        -> normalize by ID
        -> preserve unchanged refs
        -> commit once per frame
            -> external session/thread store
                -> selector hooks
                    -> MessageThread rows
                    -> SessionComposer booleans
```

That architecture is simultaneously more React-idiomatic, more transport-agnostic, and more SDK-friendly than the current “stream snapshot becomes component state” approach. citeturn11view2turn17view0turn15search0

### What the ideal `useExecutionStream` should do

The ideal hook does not return a huge evolving execution object. It should be a **controller hook** whose job is to connect, cancel, coalesce, and ingest. A sketch looks like this:

```ts
import { startTransition, useEffect, useMemo } from 'react';

export function useExecutionStream(executionId: string | null, sessionId: string) {
  const client = useStigmerClient();           // memoized once per provider
  const store = useConversationStore();        // external store

  useEffect(() => {
    if (!executionId) {
      store.setStreamState(sessionId, { stage: 'idle' });
      return;
    }

    const abort = new AbortController();
    let latest: AgentExecution | null = null;
    let raf = 0;
    let firstChunk = true;

    store.setStreamState(sessionId, { stage: 'connecting', executionId });

    (async () => {
      try {
        for await (const snapshot of client.subscribe({ executionId }, { signal: abort.signal })) {
          latest = snapshot;
          if (raf) continue;

          raf = requestAnimationFrame(() => {
            raf = 0;
            const next = latest;
            if (!next) return;

            const commit = () => {
              store.ingestExecutionSnapshot(sessionId, next, {
                firstChunk,
                receivedAt: performance.now(),
              });
              firstChunk = false;
            };

            startTransition(commit);
          });
        }
      } catch (err) {
        if (!isCanceled(err)) {
          store.setStreamState(sessionId, { stage: 'error', executionId, error: err });
        }
      } finally {
        store.finishStream(sessionId, executionId);
      }
    })();

    return () => {
      if (raf) cancelAnimationFrame(raf);
      abort.abort();
    };
  }, [client, executionId, sessionId, store]);
}
```

This hook uses Connect’s `AsyncIterable` stream model and cancellation support, uses one commit path per buffered frame, and puts transition semantics exactly where React says non-urgent async UI work belongs. citeturn11view0turn15search0turn11view3turn5search3

# 1. Executive Summary

## The diagnosis

Your flicker is probably not one bug. It is a stack of compounding problems:

1. **Every stream event replaces the whole execution object graph.**
2. **That invalidates `useMemo` dependencies and child props**, because React compares dependencies and memoized props by reference / `Object.is`.
3. **Index-derived keys cause remounts when ordering changes**, which is the most direct path to visible flicker, lost collapse state, and re-triggered animations.
4. **`react-markdown` reparses a growing full string repeatedly**, which is especially bad for long streamed assistant messages.
5. **Session navigation uses stale-while-revalidate across identity changes**, so Session A’s data can render under Session B’s route.
6. **Composer and thread live under the same frequently updating parent**, so the input is exposed to stream-driven render pressure.

React gives you tools—`memo`, `useMemo`, `useSyncExternalStore`, `useTransition`, `useDeferredValue`, `useOptimistic`—but they only help if the data model has stable identities. React’s docs are explicit that `memo` only skips rendering when props are unchanged, `useSyncExternalStore` re-renders when the snapshot changes by `Object.is`, and `getSnapshot` must return a cached immutable snapshot when nothing changed. ([React][1])

## Top 5 recommendations

### 1. Add a **client-side snapshot-ingestion layer** that normalizes full `AgentExecution` snapshots into a structurally shared conversation store.

This is the single highest-impact change.

Do **not** pass the latest full protobuf snapshot directly into the React tree. Keep the backend’s full-snapshot protocol if you like, but translate each snapshot into a normalized client view model:

```ts
ConversationStore
  sessionById
  executionById
  messageById
  toolCallById
  subAgentById
  threadItemIds
  streamStatusByExecutionId
```

On every snapshot, update only entities whose semantic fields actually changed. Reuse object references for everything else. Earlier messages must keep the same `messageView` object and the same `threadItemId` across stream updates. This gives React, memoized rows, virtualizers, markdown caches, and collapse state something stable to hold onto.

### 2. Replace index keys with durable semantic keys everywhere.

Keys like `e${ei}-m${mi}` are unsafe for streaming conversations because a refetch, pending-message reconciliation, or execution insertion can shift indexes. React’s list docs warn that index keys become problematic when items can be inserted, deleted, or reordered, and that changing keys recreates components and DOM. ([React][2])

Use keys like:

```ts
message:${executionId}:${message.id ?? message.clientId ?? message.createdAt}:${role}
tool-group:${executionId}:${toolCallGroupId}
approval:${executionId}:${approvalId}
phase:${executionId}:${phaseName}:${phaseStartedAt}
pending:${clientMessageId}
```

Then reconcile pending user messages into server messages **without remove+insert**.

### 3. Move streaming state into an external store or stable reducer, and subscribe at row/message granularity.

The `MessageThread` should subscribe to ordered item IDs. Each `ThreadRow` should subscribe to its own item. Each `MessageEntry` should subscribe to its own message. The active streaming message should be the only row that changes on token updates.

You can implement this with a tiny custom store plus `useSyncExternalStore`, or with Zustand selectors. Zustand’s docs recommend selectors to prevent rerenders, and `useShallow` when computed selector output is shallow-equal even if a new object/array would otherwise cause a rerender. ([Zustand Documentation][3])

### 4. Treat streaming markdown differently from completed markdown.

`react-markdown` is safe and extensible, but it is a general Markdown-to-React pipeline: parse Markdown to mdast, transform through remark, convert to hast, transform through rehype, then render React elements. That is good for static/completed content; it is not ideal for token-by-token rendering of an incomplete, growing Markdown string. ([unified][4])

For the active assistant message, either adopt **Streamdown** or implement a block-level streaming renderer. Streamdown is explicitly positioned as a drop-in replacement for `react-markdown` for AI streaming, with handling for incomplete Markdown blocks, unterminated syntax, GFM, code blocks, math, and efficient reconciliation of full accumulated strings. ([Vercel][5])

### 5. Fix navigation by keying data by `sessionId` and never showing old-session data under a new session identity.

Stale-while-revalidate is good for “same key, fresh data.” It is bad when the identity changes from Session A to Session B. TanStack Query and SWR both model this around keys; TanStack Query also exposes `placeholderData`, cache lifetimes, stale times, refetch behavior, and structural sharing. ([TanStack][6])

For your Console, replacing the custom `useFetch` with TanStack Query or SWR is strongly recommended. For the public SDK, keep the core framework-agnostic and light, but provide an optional adapter such as `@stigmer/react-query`.

# 2. Detailed Findings

## Part 1 — Diagnosing flickering in React streaming UIs

### Common flicker causes in your current architecture

#### A. Full snapshot replacement invalidates everything upstream

Your stream sends full `AgentExecution` snapshots. That is fine at the transport boundary, but it is toxic if directly used as React render input.

This line is the root pattern to eliminate:

```ts
setExecution(snapshot);
```

Why it flickers:

```tsx
const items = useMemo(
  () => buildThreadItems(executions, activeStreamExecution, pendingUserMessage),
  [executions, activeStreamExecution, pendingUserMessage]
);
```

If `activeStreamExecution` is a new object on every stream message, `useMemo` runs on every stream message. If `buildThreadItems` returns new `ThreadItem` objects for every row, every row receives new props. `React.memo` cannot help unless the props are referentially stable or custom-compared. React’s `useMemo` and `memo` docs both depend on stable dependencies / props; new object references defeat them. ([React][7])

#### B. Index keys cause remounts

Keys such as `e${ei}-m${mi}` are likely causing direct unmount/remount flicker when:

* a pending execution becomes part of fetched executions,
* the execution list refetches in a different order,
* pending user message is removed and server message inserted,
* phase/tool/approval items appear before messages,
* a terminal refetch moves active execution into completed executions.

A re-render is usually not visible. A remount often is: animations replay, scroll anchoring changes, local collapse state resets, markdown components rebuild, images/code blocks refetch/recalculate, and focus can be disturbed.

#### C. Markdown parsing cost grows with every token

The expensive part is not just “rendering text.” It is repeatedly parsing the entire accumulated assistant message. `react-markdown` is built on unified/remark/rehype and turns the Markdown string into syntax trees before producing React elements. That architecture is correct for normal Markdown, but token streaming keeps feeding it a new incomplete document. ([unified][4])

For example, if a 6,000-character assistant response arrives in 300 chunks, a naive renderer can parse roughly:

```txt
20 chars
40 chars
60 chars
...
6000 chars
```

That is much more work than rendering 6,000 characters once.

#### D. Cascading state effects create extra intermediate UI states

This pattern is visually dangerous:

```ts
setExecution(snapshot);
setIsConnecting(false);
setIsStreaming(!isTerminal);
```

React 18+ automatically batches updates from promises, timeouts, native events, and other contexts when using `createRoot`; React 19 inherits that model. But batching several `setState` calls in the same callback does not solve the core problem: each stream event is still a new render opportunity, and separate effects that react to stream state can produce additional render cycles. ([React][8])

The better pattern is one store publication per frame, with a single state-machine transition:

```ts
store.ingestSnapshot(snapshot);
```

#### E. “Old → null → new” stream gaps create visual disappearance

When `executionId` changes, setting stream execution to `null` is a blunt reset. The UI sees:

```txt
old active execution
→ no active execution
→ new active execution
```

That produces a gap even if the user should conceptually see “connecting to the next execution.” Use a stream state machine and keep a stable placeholder row instead.

#### F. Scroll anchoring and layout effects can amplify flicker

Auto-scroll implementations often flicker when they:

* call `scrollToBottom()` after every token,
* read `scrollHeight` and set `scrollTop` repeatedly in layout effects,
* ignore whether the user scrolled away,
* do not account for expanding tool panels,
* allow images/code blocks to change height after render,
* combine virtualization with manual scroll code.

The best chat virtualizers expose “at bottom” and scroll modifiers rather than forcing you to manually inspect and mutate scroll metrics on every update. Virtuoso’s message-list docs, for example, describe conditional auto-scroll only when the list is at bottom or already scrolling. ([Virtuoso][9])

## React 19-specific considerations

React 19 does not remove the need for stable identity. It gives you better primitives for prioritization and optimistic updates.

### What helps

React 19 supports async functions in transitions, pending states, error handling, forms, and optimistic updates. Transitions keep the current UI responsive while data changes. ([React][10])

Use this for:

* session navigation transitions,
* non-urgent thread updates,
* expensive markdown/background formatting,
* replacing skeleton with loaded conversation,
* completing optimistic message reconciliation.

Use `useOptimistic` for pending user messages if the flow maps cleanly to a React Action; it shows temporary UI while an action is in progress and then returns to canonical state. ([React][11])

### What does not help

Do **not** put controlled textarea input updates in a transition. React’s transition docs explicitly distinguish urgent updates like typing from non-urgent UI transitions. ([React][12])

Do **not** expect React Compiler or `memo` to rescue unstable data. Compiler/memo optimizations help when props and state are stable. They do not make full object graph replacement cheap.

Do **not** suspend based on `useSyncExternalStore` stream state. React’s docs warn that external-store mutations cannot be marked as non-blocking transitions in the same way, and suspending from external-store values can replace already-rendered content with fallbacks, which is usually poor UX. ([React][1])

## gRPC / Connect streaming + React best practices

Connect is a good transport fit. Connect’s TypeScript implementation is designed for browser and Node use, works with gRPC/gRPC-Web/Connect protocols, and is type-safe end-to-end. ([npm][13])

The issue is not Connect. The issue is how stream messages enter React.

### Recommended stream-consumption pattern

```ts
type ExecutionStreamStatus =
  | { state: "idle" }
  | { state: "connecting"; executionId: string }
  | { state: "awaiting-first-snapshot"; executionId: string }
  | { state: "streaming"; executionId: string }
  | { state: "terminal"; executionId: string; phase: Phase }
  | { state: "error"; executionId: string; error: unknown };

function useExecutionStreamController(args: {
  sessionId: string | null;
  executionId: string | null;
  client: StigmerClient;
  store: ConversationStore;
}) {
  const { sessionId, executionId, client, store } = args;
  const runIdRef = useRef(0);

  useEffect(() => {
    if (!sessionId || !executionId) {
      store.setStreamStatus({ state: "idle" });
      return;
    }

    const abort = new AbortController();
    const runId = ++runIdRef.current;

    let latest: AgentExecution | undefined;
    let raf = 0;

    const flush = () => {
      raf = 0;
      const snapshot = latest;
      latest = undefined;

      if (!snapshot || runId !== runIdRef.current) return;

      store.ingestExecutionSnapshot(snapshot, {
        sessionId,
        executionId,
        receivedAt: performance.now(),
      });
    };

    store.setStreamStatus({ state: "connecting", executionId });

    void (async () => {
      try {
        store.setStreamStatus({ state: "awaiting-first-snapshot", executionId });

        for await (const snapshot of client.agentExecution.subscribe(
          { executionId },
          { signal: abort.signal }
        )) {
          if (runId !== runIdRef.current) break;

          latest = snapshot;

          if (isTerminal(snapshot.phase)) {
            if (raf) cancelAnimationFrame(raf);
            raf = 0;
            flush(); // terminal state should not wait for the next frame
            store.setStreamStatus({
              state: "terminal",
              executionId,
              phase: snapshot.phase,
            });
            continue;
          }

          if (!raf) {
            raf = requestAnimationFrame(flush);
          }
        }
      } catch (error) {
        if (!abort.signal.aborted && runId === runIdRef.current) {
          store.setStreamStatus({ state: "error", executionId, error });
        }
      }
    })();

    return () => {
      abort.abort();
      runIdRef.current++;
      if (raf) cancelAnimationFrame(raf);
    };
  }, [sessionId, executionId, client, store]);
}
```

Key properties:

* one stream run has one `runId`;
* stale stream events are ignored;
* snapshots are coalesced to animation frames;
* terminal snapshots flush immediately;
* stream state is a single finite state machine;
* React tree receives normalized store updates, not raw full snapshots;
* no old → null → new flicker unless session identity truly changes.

`requestAnimationFrame` is the right default coalescing primitive because it schedules work before the next repaint and generally tracks the display refresh rate; browser implementations pause it in background tabs, which is also desirable for stream UI battery/performance. ([MDN Web Docs][14])

## Full snapshot vs. delta updates

Public AI APIs generally expose **delta or semantic event streams**, not repeated full message snapshots. OpenAI’s Responses streaming uses server-sent events with semantic event types such as `response.output_text.delta`, and Chat Completions streaming sends chunks with a `delta` field. Anthropic’s Messages streaming uses SSE events such as `content_block_delta`, including `text_delta`, `input_json_delta`, and `thinking_delta`. ([OpenAI Platform][15])

That does **not** mean you must change Stigmer’s backend protocol immediately. Full snapshots have advantages:

* self-contained correctness,
* easy reconnect semantics,
* no client-side patch replay bugs,
* easier late subscriber behavior,
* simpler server implementation.

But the React boundary should still be delta-like. The client can derive semantic changes from full snapshots.

### Recommendation

Implement **semantic client-side diffing**, not generic deep diffing.

Bad:

```ts
const diff = deepDiff(oldSnapshot, newSnapshot);
apply(diff);
```

Better:

```ts
ingestExecutionSnapshot(snapshot) {
  upsertExecutionMetadata(snapshot);
  upsertMessages(snapshot.messages);
  upsertToolCalls(snapshot.toolCalls);
  upsertSubAgents(snapshot.subAgents);
  recomputeThreadOrderOnlyIfIdsChanged();
}
```

Use entity IDs, phase values, content string equality, status fields, and sequence numbers. Avoid deep-equaling whole protobuf trees.

# 3. Part 2 — State-of-the-Art Streaming Message Thread Architecture

## What best-in-class AI chat UIs do differently

The public evidence points to four architectural differences between a polished streaming chat UI and a naive React implementation:

1. **They stream semantic units or deltas, not full UI trees.** Public OpenAI and Anthropic streaming APIs are event/delta-oriented. ([OpenAI Platform][15])
2. **They maintain stable message identity.** A message is created, then updated in place until completion.
3. **They render only the active tail frequently.** Older rows are inert.
4. **They use streaming-aware Markdown and scroll behavior.** Vercel’s AI Elements and Streamdown are built around streaming states, message parts, tool displays, and streaming markdown rather than generic static document rendering. ([Vercel][16])

## Recommended component hierarchy

### Memo boundaries

### Preferred row pattern

## Virtualized scrolling

### When to introduce virtualization

Do not wait for thousands of messages. Your rows are not simple text rows; they contain Markdown, code blocks, tool panels, sub-agent panels, approval cards, collapsible state, and possibly attachments.

Introduce virtualization when any of these are true:

* **100+ thread rows**, especially with tool calls;
* **300–500+ DOM nodes** in the thread;
* React Profiler shows thread commits regularly above **16 ms** during streaming;
* markdown/code/tool panels visibly delay input;
* mobile or low-end laptops show scroll jank;
* long conversations are a core SDK use case.

### Recommended library

Use **React Virtuoso** as the default recommendation. The core `react-virtuoso` package is MIT-licensed and handles variable-sized items automatically; its commercial `VirtuosoMessageList` is purpose-built for human/AI chat with streaming responses, auto-scroll, and virtualized rendering. ([Virtuoso][18])

For a polished SDK:

* default non-virtualized list for small threads,
* optional `virtualized` mode,
* optional peer adapter for Virtuoso,
* later: dedicated `@stigmer/react-virtuoso` export.

### Library comparison

| Library                              |                  Fit for Stigmer | Why                                                                                                                                                                                                        |
| ------------------------------------ | -------------------------------: | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `react-virtuoso`                     |                     Best default | Variable heights, chat-friendly APIs, bottom alignment, at-bottom callbacks.                                                                                                                               |
| `@virtuoso.dev/message-list`         |    Best UX if license acceptable | Built specifically for chat/AI, declarative scroll modifiers, streaming examples.                                                                                                                          |
| `@tanstack/react-virtual`            |     Best headless/control option | Small, powerful, framework-agnostic engine, but you implement more chat behavior yourself. TanStack describes it as headless virtualization for massive scrollable DOM nodes at 60 FPS. ([TanStack][19])   |
| `react-window`                       |                         Weak fit | Excellent for simple fixed/known-size lists; less ergonomic for dynamic-height, bottom-anchored chat with streaming rows.                                                                                  |
| Stream Chat `VirtualizedMessageList` | Good reference, not a dependency | Shows best practice: virtualization keeps DOM small and smooth in high-traffic channels; docs recommend lightweight custom renderers and setting default item height to avoid scroll jumps. ([Stream][20]) |

### Auto-scroll with virtualization

The state machine should be:

```txt
atBottom = true
  new token/new row -> follow tail

user scrolls up
  atBottom = false
  new token/new row -> preserve scroll position, show "New messages"

user clicks button or scrolls bottom
  atBottom = true
  catch up to latest
```

Virtuoso exposes `atBottomStateChange`, `atBottomThreshold`, `alignToBottom`, and message-list scroll modifiers for controlling this declaratively. ([Virtuoso][21])

## Markdown rendering during streaming

### Keep `react-markdown` for completed messages

`react-markdown` remains a reasonable choice for completed/static messages because it is safe by default, supports plugins, and follows CommonMark/GFM with plugins. ([unified][4])

### Do not use naive `react-markdown` for the active stream tail

For active streaming content, use one of these options.

#### Option A — Streamdown

Best immediate upgrade. It is designed for AI-powered streaming, incomplete Markdown, and full accumulated content updates. ([Streamdown][22])

```tsx
import { Streamdown } from "streamdown";

function AssistantMarkdown({ content, isStreaming }: Props) {
  return (
    <Streamdown mode={isStreaming ? "streaming" : "static"} isAnimating={isStreaming}>
      {content}
    </Streamdown>
  );
}
```

#### Option B — Block-stabilized renderer

If you want to avoid a new dependency:

```ts
type MarkdownBlock = {
  id: string;
  text: string;
  complete: boolean;
  rendered?: ReactNode;
};
```

Algorithm:

1. Split content into stable blocks at safe boundaries:

   * blank line,
   * closed code fence,
   * closed list block,
   * completed table,
   * completed paragraph.
2. Render completed blocks once and cache their React tree.
3. Render only the active incomplete block on each token.
4. When a block becomes complete, freeze it.
5. On message completion, render all blocks in static mode.

This gives most of the benefit without requiring true incremental Markdown parsing.

## Auto-scroll best practices

Use a hook like:

```ts
function useTailFollow(scrollerRef: RefObject<HTMLElement>) {
  const atBottomRef = useRef(true);

  const onScroll = useCallback(() => {
    const el = scrollerRef.current;
    if (!el) return;

    const distance = el.scrollHeight - el.scrollTop - el.clientHeight;
    atBottomRef.current = distance < 96;
  }, []);

  const afterContentChange = useCallback((reason: "token" | "new-row" | "resize") => {
    if (!atBottomRef.current) return;

    requestAnimationFrame(() => {
      const el = scrollerRef.current;
      if (!el) return;
      el.scrollTop = el.scrollHeight;
    });
  }, []);

  return { onScroll, afterContentChange, isAtBottom: () => atBottomRef.current };
}
```

But prefer virtualizer-native APIs when virtualized.

Rules:

* never auto-scroll if user scrolled up;
* always preserve user scroll position during historical load;
* use a threshold, not exact bottom equality;
* batch scroll writes in `requestAnimationFrame`;
* avoid measuring layout multiple times per token;
* call scroll correction when tool panels expand/collapse;
* do not animate every token scroll;
* show “Jump to latest” / “New messages” button.

## Snapshot ingestion with structural sharing

```ts
function ingestExecutionSnapshot(
  prev: ConversationState,
  snapshot: AgentExecution
): ConversationState {
  let next = prev;

  next = upsertExecutionMetadata(next, snapshot);
  next = upsertMessages(next, snapshot);
  next = upsertToolGroups(next, snapshot);
  next = upsertSubAgents(next, snapshot);
  next = upsertApprovals(next, snapshot);
  next = reconcilePendingUserMessages(next, snapshot);
  next = updateThreadOrderIfNeeded(next, snapshot);

  return next;
}
```

Example for messages:

```ts
function upsertMessages(
  state: ConversationState,
  snapshot: AgentExecution
): ConversationState {
  let messagesById = state.messagesById;
  let changed = false;

  for (const proto of snapshot.messages) {
    const id = stableMessageId(snapshot.id, proto);
    const old = messagesById.get(id);

    const nextMessage: MessageView = {
      id,
      executionId: snapshot.id,
      role: proto.role,
      content: proto.content,
      status: deriveMessageStatus(proto, snapshot),
      createdAt: proto.createdAt,
      updatedAt: proto.updatedAt,
    };

    if (
      old &&
      old.content === nextMessage.content &&
      old.status === nextMessage.status &&
      old.role === nextMessage.role &&
      old.updatedAt === nextMessage.updatedAt
    ) {
      continue;
    }

    if (messagesById === state.messagesById) {
      messagesById = new Map(messagesById);
    }

    messagesById.set(id, old ? { ...old, ...nextMessage } : nextMessage);
    changed = true;
  }

  return changed ? { ...state, messagesById } : state;
}
```

## Protobuf-specific note

Your prompt says `@bufbuild/protobuf` v2 generated values are “generated classes.” Double-check this. Buf’s Protobuf-ES v2 docs say v2 no longer generates classes; it generates schema objects and TypeScript types, and generated messages are plain objects. If your objects are still class-like, you may be on old generated output, a wrapper layer, or a different generator. ([Buf][23])

This matters because TanStack Query’s built-in structural sharing only works automatically for JSON-compatible values; for non-JSON-compatible values you need a custom structural-sharing function. ([TanStack][6])

## Should you adopt Zustand, Jotai, or Valtio?

### My recommendation

For `@stigmer/react` core:

* Build a tiny custom store around `useSyncExternalStore`, **or**
* Use Zustand’s vanilla store internally if you are comfortable with a small dependency.

For the Console app:

* Use TanStack Query / Connect Query for fetch/cache/request dedupe.
* Use the same conversation store for streaming state.

### Zustand

Best pragmatic fit. It gives selectors, shallow equality, external store ergonomics, and low conceptual overhead. Zustand’s docs directly address preventing rerenders with selectors and shallow comparisons. ([Zustand Documentation][3])

### Jotai

Good if you want atomized state by message/tool/sub-agent. It can work well, but dynamic atom management for hundreds of ephemeral conversation entities can become its own architecture.

### Valtio

Good for proxy-based fine-grained tracking, but less explicit. For a public SDK where users need predictable behavior, explicit selectors are easier to reason about than implicit property tracking.

### Plain React hooks

Plain hooks can work only if you avoid storing the full snapshot as one state object. A reducer with normalized structural sharing can be acceptable, but it still causes the parent provider component to re-render unless subscriptions are granular.

## Throttling and debouncing stream updates

Use **latest-wins `requestAnimationFrame` coalescing**.

```ts
let latestSnapshot: AgentExecution | null = null;
let frame = 0;

function onSnapshot(snapshot: AgentExecution) {
  latestSnapshot = snapshot;

  if (isTerminal(snapshot.phase)) {
    flushNow();
    return;
  }

  if (!frame) {
    frame = requestAnimationFrame(flushNow);
  }
}

function flushNow() {
  if (frame) cancelAnimationFrame(frame);
  frame = 0;

  const snapshot = latestSnapshot;
  latestSnapshot = null;
  if (!snapshot) return;

  store.ingestExecutionSnapshot(snapshot);
}
```

This caps visual updates at display refresh rate while preserving correctness because each snapshot is self-contained. You can also cap expensive Markdown rendering to 30 fps while still storing the latest raw content.

## Optimistic UI

Use stable optimistic IDs.

```ts
const clientMessageId = crypto.randomUUID();

store.addPendingUserMessage({
  clientMessageId,
  sessionId,
  content,
  createdAt: Date.now(),
});
```

When the stream or list fetch returns the corresponding server message:

```ts
store.reconcilePendingMessage({
  clientMessageId,
  serverMessageId,
  executionId,
});
```

Do not remove the pending row and insert a new server row. Update the row in place.

Ideal visual sequence:

```txt
User submits
→ user message appears immediately with clientMessageId
→ assistant placeholder appears: "Connecting…"
→ first snapshot arrives: same assistant row becomes "Thinking…"
→ text starts streaming in same row
→ tool call appears as stable child row/card
→ terminal phase freezes markdown and status
→ completed execution cache is updated without remount
```

# 5. Part 4 — Navigation Transitions and Data Fetching

## The core rule

**Stale-while-revalidate is correct for the same identity. It is wrong across identity changes unless the UI clearly marks the previous data as a placeholder and keeps the old identity visible.**

When route changes from `/sessions/A` to `/sessions/B`, do not render A’s messages under B’s URL/header.

## Recommended session data state machine

```ts
type SessionResource<T> =
  | { status: "idle"; key: null; data: null }
  | { status: "loading"; key: SessionId; data: null }
  | { status: "ready"; key: SessionId; data: T; stale: false }
  | { status: "refreshing"; key: SessionId; data: T; stale: true }
  | { status: "placeholder"; key: SessionId; data: T; placeholderFor: SessionId }
  | { status: "error"; key: SessionId; data: T | null; error: unknown };
```

Your current `useFetch` collapses two very different cases:

1. “Same key refetching” → keep old data.
2. “New key loading” → old data is wrong unless explicitly used as placeholder.

Separate them.

## Atomic conversation bundle

Instead of three independent page-level states resolving separately:

```txt
useSession(sessionId)
useSessionExecutions(sessionId)
useExecutionStream(activeExecutionId)
```

create a single session conversation resource:

```ts
type ConversationBundle = {
  session: Session;
  completedExecutions: AgentExecution[];
  activeExecutionId: string | null;
  initialActiveExecution?: AgentExecution;
};
```

Load critical data together:

```ts
async function loadConversationBundle(sessionId: string) {
  const [session, executions] = await Promise.all([
    client.session.get({ sessionId }),
    client.execution.list({ sessionId }),
  ]);

  const activeExecutionId = deriveActiveExecutionId(session, executions);

  return {
    session,
    completedExecutions: executions.filter(isCompleted),
    activeExecutionId,
  };
}
```

Then mount/subscribe the stream after the bundle identity is coherent.

## React `startTransition` for navigation

React 19 transitions can keep the current UI responsive and interactive while data changes. That helps route/page transitions, but the SDK cannot depend on Next.js/Remix/router features. ([React][10])

Expose framework-agnostic primitives:

```ts
preloadSession(sessionId)
useSessionConversation(sessionId, {
  cacheTimeMs,
  staleTimeMs,
  placeholder: "skeleton" | "cached-only" | "keep-previous-with-overlay",
})
```

Then the host app can wrap navigation in its router’s transition mechanism.

## Should you replace `useFetch`?

### For the Console app: yes

Use TanStack Query or SWR. Since you are already on Connect, evaluate **Connect Query**, which is a TypeScript-first expansion pack for TanStack Query for Connect. ([GitHub][24])

TanStack Query gives you:

* key-based cache,
* request deduplication,
* stale times,
* garbage collection,
* retries,
* refetch-on-focus control,
* placeholder data,
* structural sharing. ([TanStack][6])

### For the public SDK: not as a hard dependency

Do not force every SDK consumer to adopt TanStack Query. Instead:

* core SDK includes minimal keyed cache and stream store;
* optional package integrates with TanStack Query;
* allow consumers to bring their own data source.

```txt
@stigmer/react              // core hooks + styled components
@stigmer/react-query        // optional TanStack Query integration
@stigmer/react-virtuoso     // optional virtualized MessageThread
@stigmer/react-streamdown   // optional streaming markdown renderer
```

## Preventing flash of wrong content

Use this rule in `useFetch` replacement:

```ts
if (newKey !== previousKey) {
  const cached = cache.get(newKey);

  if (cached) {
    return { status: "ready", key: newKey, data: cached, stale: true };
  }

  return { status: "loading", key: newKey, data: null };
}
```

Never do:

```ts
return { status: "loading", key: newKey, data: previousKeyData };
```

unless the UI visibly keeps the old route/session shell.

## Sidebar list stability

Your sidebar should optimize for spatial stability:

* fixed row height;
* stable keys by `sessionId`;
* reserve space for generated subject;
* show `"Untitled conversation"` placeholder with same typography;
* update subject text in place;
* avoid reordering while active session is being read;
* if a new subject changes sort order, defer reorder until next open, next manual refresh, or after a quiet period;
* pin active session row;
* cross-fade title text, not whole row;
* do not shift row heights when subject arrives.

For the 8s/18s subject refetches, merge data into existing rows by ID. Do not replace the full list array with new row objects if the order and most fields did not change.

# 6. Part 5 — Composer UX Best Practices

## Composer isolation

The composer must not subscribe to token-level stream state.

Bad:

```tsx
function ChatPage() {
  const conv = useSessionConversation(sessionId);

  return (
    <>
      <MessageThread {...conv} />
      <SessionComposer
        disabled={!conv.canSendFollowUp}
        isSubmitting={conv.isSending}
        onSubmit={(msg) => conv.sendFollowUp(msg)}
      />
    </>
  );
}
```

If `conv` is a new object every token, composer props may change every token.

Better:

```tsx
function ChatPage({ sessionId, org }: Props) {
  return (
    <SessionConversationProvider sessionId={sessionId} org={org}>
      <MessageThreadContainer />
      <ComposerContainer />
    </SessionConversationProvider>
  );
}

const ComposerContainer = memo(function ComposerContainer() {
  const canSend = useConversationSelector((s) => s.composer.canSend);
  const isSending = useConversationSelector((s) => s.composer.isSending);
  const sendFollowUp = useConversationAction((a) => a.sendFollowUp);

  return (
    <SessionComposer
      disabled={!canSend}
      isSubmitting={isSending}
      onSubmit={sendFollowUp}
    />
  );
});
```

## Self-resizing textarea

Use either a tiny internal hook or `react-textarea-autosize`. The package is purpose-built for a textarea that grows with content and supports `minRows`, `maxRows`, and cached measurements. ([jsDocs.io][25])

Manual implementation:

```tsx
function useAutosizeTextarea(
  ref: RefObject<HTMLTextAreaElement>,
  value: string,
  maxHeight = 240
) {
  useLayoutEffect(() => {
    const el = ref.current;
    if (!el) return;

    el.style.height = "0px";
    const next = Math.min(el.scrollHeight, maxHeight);

    el.style.height = `${next}px`;
    el.style.overflowY = el.scrollHeight > maxHeight ? "auto" : "hidden";
  }, [ref, value, maxHeight]);
}
```

`useLayoutEffect` is appropriate here because the browser should measure and apply the height before repaint, but use it sparingly because layout effects can hurt performance if overused. ([React][26])

CSS:

```css
.stgm .stgm-composer-textarea {
  resize: none;
  overflow-y: hidden;
  max-height: 240px;
}
```

The CSS `resize` property controls whether the user can manually resize textareas, and `scrollHeight` gives the content height including overflowed content. ([MDN Web Docs][27])

## Input responsiveness during streaming

Rules:

* composer state is local;
* controlled textarea updates are urgent;
* do not wrap keystroke state in transitions;
* do not pass stream content through composer parent;
* memoize toolbar subcomponents;
* avoid measuring layout outside the textarea;
* load runner/model lists in their own cache;
* defer expensive thread work, not input work.

If thread rendering is still heavy, use `useDeferredValue` for the rendered message content or markdown blocks. React’s docs describe `useDeferredValue` as letting a slower part of the UI lag behind while urgent input stays responsive. ([React][28])

## Submission UX

Recommended sequence:

```txt
User presses Enter
→ composer clears immediately
→ pending user message appears
→ composer remains usable or disabled according to product policy
→ assistant placeholder appears
→ stream connects
→ first content updates placeholder in place
→ on error, pending message gets retry affordance
```

Use `useOptimistic` when the submission is modeled as an action; otherwise keep optimistic state in the conversation store. ([React][11])

# 7. Part 6 — SDK / Library Design Considerations

## Patterns from best-in-class SDKs

### Vercel AI SDK / AI Elements

Vercel’s `useChat` handles conversational UI state and streaming messages, while AI Elements offers production-ready components for messages, conversation, markdown response, prompt input, tool displays, and streaming states. ([AI SDK][29])

Key lesson: separate **transport/state hooks** from **composable UI parts**.

### Stream Chat React

Stream Chat’s React SDK uses provider/context architecture, message lists, message inputs, and virtualized message lists. Its virtualized list reads from channel contexts and renders only visible messages to keep DOM small and scrolling smooth. ([Stream][20])

Key lesson: heavy chat SDKs expose context-driven defaults plus customization points.

### Sendbird UIKit

Sendbird’s UIKit uses a top-level provider plus modules and UI components. It supports render props/custom rendering such as custom message renderers and input renderers. ([Sendbird Docs][30])

Key lesson: public SDKs need slots and override points, not just monolithic components.

### CometChat

CometChat’s Messages component is a composite of header, list, and composer; the list handles real-time operations and the composer is its own component. ([CometChat][31])

Key lesson: keep message list and composer as independently replaceable modules.

### TalkJS

TalkJS wraps chat UI in a session component that manages auth/connection and hosts chatbox/inbox/popup components. ([TalkJS][32])

Key lesson: connection/session lifetime should be explicit and stable.

# 8. Part 7 — Animation and Perceived Performance

## Animation recommendation

Do **not** add Framer Motion to core SDK yet.

Use CSS for core:

* new message row fade/slide;
* tool call expand/collapse with height/opacity carefully;
* streaming caret;
* skeleton shimmer;
* respect `prefers-reduced-motion`;
* no per-token animation.

CSS `@starting-style` is useful for entry transitions when an element is first added to the DOM; MDN describes it as defining starting styles for first-render/display transitions. ([MDN Web Docs][33])

Example:

```css
.stgm .stgm-thread-row[data-new="true"] {
  opacity: 1;
  transform: translateY(0);
  transition:
    opacity 160ms ease,
    transform 160ms ease;

  @starting-style {
    opacity: 0;
    transform: translateY(6px);
  }
}

@media (prefers-reduced-motion: reduce) {
  .stgm .stgm-thread-row[data-new="true"] {
    transition: none;
    transform: none;
  }
}
```

## Skeletons

Use skeletons for:

* first session load,
* no cached session bundle,
* connecting to first stream snapshot,
* tool call pending result,
* subject generation in sidebar.

Do not skeletonize the whole thread on background refetch.

## Perceived performance

Use:

```css
.stgm .stgm-thread-row {
  contain: layout paint;
}

.stgm .stgm-thread-row--offscreen-eligible {
  content-visibility: auto;
  contain-intrinsic-size: auto 160px;
}
```

`content-visibility: auto` lets the browser skip layout/painting work for offscreen content, and `contain-intrinsic-size` provides a placeholder size to reduce reflow/scroll jumps. Use this carefully with dynamic chat rows and test accessibility/scrolling; MDN notes that offscreen content with `content-visibility: auto` remains in the DOM and accessibility tree. ([MDN Web Docs][34])

For route-level polish, the View Transition API can reduce cognitive load during view changes, but it is browser/platform-level and should be a host-app enhancement, not a core SDK dependency. ([MDN Web Docs][35])

# 9. Competitive Analysis

## ChatGPT / OpenAI

Public OpenAI streaming uses SSE and semantic/delta events. Responses streaming includes typed events such as `response.created`, `response.output_text.delta`, `response.completed`, and `error`; Chat Completions streaming sends chunks with a `delta` field rather than full final messages. ([OpenAI Platform][15])

Implication for Stigmer: even if your backend keeps full snapshots, the client UI should behave as if it receives semantic deltas.

## Claude / Anthropic

Anthropic streams event sequences: `message_start`, content block starts, `content_block_delta`, content block stops, `message_delta`, and `message_stop`. Tool input can stream as partial JSON strings, while text streams as `text_delta`. ([Claude API Docs][36])

Implication for Stigmer: model the UI around content blocks/tool blocks/status transitions, not around whole execution replacement.

## Cursor / Linear-like UI quality

Public internal implementation is not available. Observable pattern: they prioritize stable layouts, minimal row movement, persistent input responsiveness, careful skeletons, and local updates over whole-page changes. For Stigmer, this translates into:

* stable row IDs,
* no old-session flash,
* no remounts,
* streamed row updates only,
* delayed/controlled sidebar reordering,
* composer isolation.

## Vercel AI SDK / AI Elements

Vercel’s public AI stack explicitly addresses the missing pieces in a naive chatbot: conversation components, streaming response handling, markdown rendering, message parts, tool displays, and prompt input. Streamdown exists specifically because traditional markdown renderers are not optimized for incomplete AI-streamed Markdown. ([Vercel][16])

Implication for Stigmer: your SDK should not just expose hooks; it should encode production chat behavior.

## Stream / Sendbird / CometChat / TalkJS

Mature chat SDKs converge on:

* provider/session component,
* composable message list,
* independent composer,
* context-based state,
* render overrides,
* virtualized list for high-volume channels,
* stable message identity. ([Stream][20])

Implication for Stigmer: offer both plug-and-play and headless APIs, and avoid making developers fork the whole component just to customize one row.

# 10. Recommended Architecture

## High-level architecture

```txt
Connect/gRPC full snapshots
        │
        ▼
useExecutionStreamController
  - AbortController
  - runId stale-event guard
  - rAF coalescing
  - terminal immediate flush
        │
        ▼
ConversationSnapshotIngestor
  - normalize protobuf snapshot
  - semantic diff by IDs/status/content
  - structural sharing
  - pending reconciliation
        │
        ▼
ConversationStore
  - stable external store object
  - selector subscriptions
  - item/message/tool entity maps
        │
        ├───────────────► MessageThread
        │                   subscribes to itemIds only
        │
        ├───────────────► ThreadRow(id)
        │                   subscribes to one item
        │
        ├───────────────► MessageEntry(messageId)
        │                   subscribes to one message
        │
        └───────────────► SessionComposer
                            subscribes only to composer-relevant state
```

## Store interface

```ts
type Listener = () => void;

interface ConversationStore {
  getSnapshot(): ConversationState;
  subscribe(listener: Listener): () => void;

  ingestExecutionSnapshot(
    snapshot: AgentExecution,
    meta: { sessionId: string; executionId: string; receivedAt: number }
  ): void;

  setStreamStatus(status: ExecutionStreamStatus): void;

  addPendingUserMessage(message: PendingUserMessage): void;
  reconcilePendingMessage(args: ReconcilePendingArgs): void;
}
```

## Selector hook

React core does not include `useSyncExternalStoreWithSelector`, but you can use the shim or build a small selector cache. Conceptually:

```ts
function useConversationSelector<T>(
  selector: (state: ConversationState) => T,
  isEqual: (a: T, b: T) => boolean = Object.is
): T {
  const store = useContext(ConversationStoreContext);

  return useSyncExternalStoreWithSelector(
    store.subscribe,
    store.getSnapshot,
    store.getSnapshot,
    selector,
    isEqual
  );
}
```

If you do not want the shim dependency, expose narrower hooks that return cached snapshots from the store:

```ts
useThreadItemIds()
useThreadItem(id)
useMessageField(id, selector)
```

## Data fetching

```txt
SessionConversationProvider(sessionId)
  ├─ get cached bundle by sessionId
  ├─ if cached: render immediately, refresh in background
  ├─ if uncached: render neutral skeleton
  ├─ load session + executions atomically
  ├─ ingest completed executions into store
  ├─ derive activeExecutionId
  └─ start stream controller
```

## Navigation policy

```txt
Target session cached?
  yes → switch immediately to cached target; background refresh
  no  → show target skeleton OR keep old route UI during transition
        but never show old messages under new session identity
```

## Animation policy

```txt
New row inserted → CSS opacity/translate transition
Token appended → no row animation; optional caret
Tool starts → stable card appears
Tool completes → card updates in place
Markdown completes → freeze static renderer
Session changes → skeleton/cross-fade at shell level only
```

# 11. Implementation Roadmap

## Phase 0 — Instrument first

**Complexity:** S
**Impact:** High

Add:

* React Profiler traces around `MessageThread`, `MessageEntry`, `SessionComposer`;
* render count dev helper;
* why-did-you-render in dev;
* stream event rate logging;
* commit duration logging;
* count of DOM nodes in thread;
* key stability assertions;
* “row mounted” debug logging.

Success criteria:

```txt
During token streaming:
- only active assistant row re-renders frequently
- completed rows do not remount
- composer does not re-render per token
```

## Phase 1 — Fix keys and pending reconciliation

**Complexity:** S–M
**Impact:** Very high

* Replace all index keys.
* Preserve pending user message row ID.
* Reconcile pending → server in place.
* Preserve collapse state keyed by semantic ID.

This alone may eliminate the visible flicker if remounting is the main culprit.

## Phase 2 — Introduce structural-sharing snapshot ingestion

**Complexity:** M–L
**Impact:** Highest

* Build `ConversationStore`.
* Normalize snapshots into entity maps.
* Reuse unchanged references.
* Update only changed entities.
* Make `threadItemIds` stable.
* Stop passing full `activeStreamExecution` to the thread.

This is the architectural foundation.

## Phase 3 — Row-level subscriptions and memoization

**Complexity:** M
**Impact:** High

* `MessageThread` subscribes to IDs.
* `ThreadRow` subscribes to one item.
* `MessageEntry` subscribes to one message.
* `ToolCallGroup` subscribes to one group.
* `SessionComposer` only subscribes to composer state.

## Phase 4 — Stream controller state machine and rAF batching

**Complexity:** M
**Impact:** High

* Replace multiple `setState` calls with store transitions.
* Add `AbortController`.
* Add runId stale event guard.
* Add latest-wins rAF coalescing.
* Flush terminal snapshots immediately.
* Eliminate old → null → new gap.

## Phase 5 — Streaming markdown upgrade

**Complexity:** S if Streamdown, M–L if custom
**Impact:** High for long AI messages

* Use Streamdown for active assistant messages.
* Keep `react-markdown` for completed messages, or use Streamdown static mode everywhere.
* Freeze completed markdown.

## Phase 6 — Data fetching/cache fix

**Complexity:** M
**Impact:** Very high for navigation

Console:

* Replace `useFetch` with TanStack Query or Connect Query.
* Key all queries by sessionId/org.
* Set appropriate `staleTime` and `gcTime`.
* Do not keep previous session data on key change unless explicitly using placeholder UI.
* Load session bundle atomically.

SDK:

* Implement minimal keyed conversation cache.
* Add optional TanStack Query adapter.

## Phase 7 — Composer isolation

**Complexity:** S–M
**Impact:** High for perceived quality

* Move composer container out of stream-rendering path.
* Memoize `SessionComposer`.
* Stabilize callbacks.
* Keep textarea local.
* Use autosize hook or `react-textarea-autosize`.

## Phase 8 — Auto-scroll state machine

**Complexity:** M
**Impact:** High

* Track at-bottom.
* Stop following when user scrolls up.
* Add “Jump to latest.”
* Use rAF scroll writes.
* Integrate tool expansion height changes.

## Phase 9 — Virtualization

**Complexity:** M–L
**Impact:** High for long conversations

* Add `virtualized` prop.
* Use Virtuoso adapter.
* Start virtualizing around 100+ rows or profiler threshold.
* Test dynamic tool panels, code blocks, and streaming tail.

## Phase 10 — Animation/perceived polish

**Complexity:** S–M
**Impact:** Medium

* CSS row entry transitions with `@starting-style`.
* Skeletons for target session load and stream connect.
* Respect reduced motion.
* Optional Framer Motion adapter later.

# 12. Direct Answers to the 14 Key Questions

## 1. What is the single highest-impact change?

Add a **client-side normalized conversation store with structural sharing** between gRPC snapshots and React rendering. Keep old rows referentially stable; update only the active message/tool entity that changed.

## 2. Should you add client-side diffing?

Yes, but not generic deep diffing. Add a semantic ingestion layer that maps full snapshots into stable entities and reuses references for unchanged messages/tool calls/sub-agents. Keep full snapshots at the transport boundary; expose delta-like updates to React.

## 3. Is `react-markdown` right for streaming AI content?

For completed messages, yes. For active streaming messages, no—not by itself. Use Streamdown or a custom block-stabilized renderer. `react-markdown` is a full unified Markdown pipeline; Streamdown is specifically designed for AI streaming and incomplete Markdown. ([unified][4])

## 4. When should virtualization be introduced, and which library?

Introduce it around **100+ thread rows**, **300–500 DOM nodes**, or when profiler commits exceed **16 ms** during streaming. Prefer React Virtuoso / Virtuoso Message List for variable-height, bottom-anchored chat. Use TanStack Virtual if you want maximum headless control and are willing to implement chat behavior yourself. ([Virtuoso][18])

## 5. Should you adopt Zustand/Jotai?

For SDK core, either build a tiny `useSyncExternalStore` store or use Zustand’s vanilla store. Zustand is the most pragmatic external option. Jotai and Valtio can work but are less directly suited to a normalized streaming entity graph.

## 6. What should ideal `useExecutionStream` look like?

It should be a controller, not a `useState(snapshot)` hook:

* abortable;
* guarded by run ID;
* latest-wins rAF batching;
* terminal immediate flush;
* single finite state machine;
* publishes to normalized store;
* never emits old → null → new gaps unless identity truly changed.

## 7. How to handle no stream → connecting → first token → streaming → complete?

Represent those as explicit states on a stable assistant/execution row:

```txt
idle
connecting
awaiting-first-snapshot
thinking/setup
streaming
terminal-merging
complete
error
```

The row should update in place. Do not remove it between states.

## 8. What animation library should you adopt?

None in core. Use CSS transitions, `@starting-style`, and a streaming caret. Add Framer Motion only as an optional adapter later. Core SDK bundle size and virtualization compatibility matter more than animation richness.

## 9. How to ensure composer never lags?

Keep composer state local, memoize composer, pass stable callbacks, do not subscribe composer to token-level stream state, and keep thread updates non-urgent/coalesced. Controlled input updates should remain urgent.

## 10. Critical difference between ChatGPT/Claude-style rendering and naive React?

Best-in-class UIs update stable semantic entities in place. Naive React rebuilds a full tree from a full snapshot every token. Public OpenAI/Anthropic streams are semantic/delta-based; your UI should emulate that even if transport snapshots are full. ([OpenAI Platform][15])

## 11. How should UI transition between sessions?

Use per-session cache. If target session is cached, render it immediately and refresh. If not cached, show a neutral skeleton or keep the previous route visible during a transition—but never show Session A messages under Session B identity.

## 12. Should you replace custom `useFetch`?

For the Console app, yes: use TanStack Query, SWR, or Connect Query. For public SDK core, avoid a hard dependency; provide optional adapters. TanStack Query’s key-based caching, structural sharing, placeholder data, stale-time, refetch, and garbage-collection controls directly address your current issues. ([TanStack][6])

## 13. How to prevent flash of wrong content?

Make `useFetch` key-aware. On `sessionId` change:

```txt
cached target exists → show cached target
no cached target → show target skeleton
```

Never carry old-key data into new-key UI unless it is explicitly marked as placeholder and the old identity remains visible.

## 14. How should sidebar subject updates avoid shifting?

Keep row height and order stable. Reserve title space. Update text in place. Defer reorder. Pin active row. Merge refetch results by ID. Cross-fade subject text only, not the row.
