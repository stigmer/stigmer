## Decisions Made

1. **Execution-level structural sharing over entity maps**: The original plan proposed `Map<string, AgentMessage>` normalization. Rejected because `AgentMessage` has no stable ID, tool calls are owned by parent messages, and the proto structure is the domain model. Execution-level sharing walks the tree and preserves unchanged references — simpler, more maintainable, same optimization.

2. **`useExecutionStream` unchanged for T04**: Modifying it would break tests that use `toBe(snapshot)` reference equality. rAF coalescing and the stream controller rewrite belong to T06. Structural sharing is applied downstream in `useSessionConversation` where it flows to `MessageThread`.

3. **Message comparison strategy**: Messages are compared by array index (append-only slots confirmed by runner code). Within each message: `content`, `type`, `isStreaming`, `timestamp`, `toolCalls.length`. Tool calls compared by `id` field. Sub-agents compared by `id` field with recursive message sharing.

## Learnings

- **Runner message semantics from code**: The Graphton runner only `append()`s new `AgentMessage` objects. Content at a given index mutates during streaming (`content +=`, tool call field updates, `isStreaming` flag). Summarization only affects `context_info`, not `messages`. This was confirmed by reading `status_builder.py`, `chat_model.py`, and `tool_event.py`.
- **Backend replacement semantics**: Each `updateStatus` RPC does `clearMessages().addAllMessages()` — full array replacement, not incremental. But the runner maintains stable ordering, so index-based comparison is safe.
- **`Object.create + Object.assign` pattern**: Used for creating hybrid structurally-shared objects. Preserves protobuf prototype chain while mixing old and new references.
