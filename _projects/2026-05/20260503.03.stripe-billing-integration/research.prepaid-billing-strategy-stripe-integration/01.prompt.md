# Deep Research: Prepaid Credit Billing Strategy & Stripe Integration for an AI Agent Platform

## Research Objective

We are building the billing system for **Stigmer** — an infrastructure platform for AI agents and automation workflows (think "Heroku for AI agents"). Teams deploy AI agents on Stigmer and those agents consume LLM tokens (Anthropic, OpenAI, Google, local Ollama, etc.) and Cursor SDK requests during execution.

We want a **prepaid credit-based billing model** (similar to Daytona, Replit, Vercel, and other usage-based platforms) where customers purchase credits upfront and consume them as their agents execute. We need a comprehensive strategy covering: how our existing usage tracking feeds into billing, where and how to apply a margin/markup on provider costs, Stripe integration for prepaid credit purchases, and the full end-to-end billing pipeline.

The research should produce an actionable blueprint we can implement — not abstract theory.

## Our Context and Architecture

### What Stigmer Is

Stigmer is a **platform for platforms** — B2B SaaS where teams integrate AI agent capabilities into their own products. A customer (an "Organization" in Stigmer) deploys Agents, creates Sessions, runs AgentExecutions, and each execution consumes LLM tokens that cost real money.

### Two-Repo Architecture

| Concern | **stigmer** (OSS) | **stigmer-cloud** (Cloud) |
|---------|-------------------|--------------------------|
| **Control plane** | `stigmer-server` — Go, gRPC + Connect, SQLite | `stigmer-service` — Java 21, Spring Boot, gRPC, MongoDB, Redis, OpenFGA |
| **Agent runner** | Python, LangGraph, Temporal Python SDK | Python (shared implementation, deployed differently) |
| **Billing scope** | None (self-hosted, user pays provider directly) | **This is where billing lives** — multi-tenant, we pay providers, we bill customers |

**Billing is a cloud-only feature.** The OSS edition has no billing — users bring their own API keys and pay providers directly. In the cloud edition, Stigmer pays the LLM providers and bills customers.

### Two Execution Harnesses

Stigmer supports two execution engines ("harnesses"), each with different cost structures:

#### 1. Native Harness (HARNESS_NATIVE)
- Stigmer's own execution engine — Python, LangGraph, Temporal
- Stigmer calls LLM provider APIs **directly** (Anthropic, OpenAI, Google, Ollama)
- **Cost is transparent**: we know the exact provider token prices (stored in our model registry)
- Models range from $0/MTok (Ollama/local) to $75/MTok output (Claude Opus 4)

#### 2. Cursor Harness (HARNESS_CURSOR)
- Uses the Cursor SDK to execute agent tasks
- Cursor calls the LLM on our behalf — we pay Cursor, not the LLM provider directly
- **Cost is Cursor's pricing** which is different from raw provider pricing
- Cursor has its own models (Composer 2, Composer 1.5) and proxied versions of Anthropic/OpenAI/Google models at their own price points

### Current Usage Tracking (Already Built)

We already have comprehensive usage tracking at the execution level. This is the data we will bill on.

#### UsageMetrics (per execution)
```protobuf
message UsageMetrics {
  int32 prompt_tokens = 1;           // Total input tokens
  int32 completion_tokens = 2;       // Total output tokens
  int32 total_tokens = 3;            // prompt + completion
  int32 llm_call_count = 4;          // Number of LLM API calls
  string primary_model = 5;          // e.g., "claude-sonnet-4-6"
  int32 cache_creation_tokens = 6;   // Tokens written to cache
  int32 cache_read_tokens = 7;       // Tokens read from cache
  repeated ModelUsage model_breakdown = 8;  // Per-model detail
  double estimated_cost_usd = 9;     // Total cost at provider rates
  // ... duration fields, tool tracking
}
```

#### ModelUsage (per model within an execution)
```protobuf
message ModelUsage {
  string model = 1;                           // "claude-sonnet-4-6"
  string provider = 2;                        // "anthropic"
  int32 input_tokens = 3;                     // Regular (non-cached) input
  int32 output_tokens = 4;
  int32 cache_creation_tokens = 5;
  int32 cache_read_tokens = 6;
  int32 call_count = 7;
  double input_price_per_million = 8;         // Rate stamped at execution time
  double output_price_per_million = 9;
  double cache_creation_price_per_million = 10;
  double cache_read_price_per_million = 11;
  double estimated_cost_usd = 12;             // Computed cost for this model
}
```

#### LlmCallMetrics (per individual LLM call)
```protobuf
message LlmCallMetrics {
  int32 sequence = 1;                // Call sequence number (1-based)
  string model = 2;
  string provider = 3;
  int32 input_tokens = 4;
  int32 output_tokens = 5;
  int32 cache_creation_tokens = 6;
  int32 cache_read_tokens = 7;
  double estimated_cost_usd = 8;     // Cost for this single call
  int32 duration_ms = 9;
  string timestamp = 10;
}
```

#### Usage Reports (already implemented)
- **Session-level**: `GetSessionUsageReport` — aggregates across all executions in a session
- **Agent-level**: `GetAgentUsageReport` — aggregates across all sessions for an agent, with time-range filtering and pagination
- **Org-level**: `GetOrgUsageReport` — aggregates across all agents in an org, includes daily cost trends and top agents by cost

#### Cost Computation Pipeline
The `UsageTracker` (Python, in the agent runner) computes cost at execution time:
1. On each `on_chat_model_end` event from LangGraph, it extracts token counts
2. Looks up the model in `model-registry.json` to get pricing rates
3. Computes per-call cost using the disjoint token bucket formula:
   ```
   cost = (input_tokens × input_price + output_tokens × output_price
           + cache_creation_tokens × cache_write_price
           + cache_read_tokens × cache_read_price) / 1,000,000
   ```
4. Stamps the pricing rates and computed cost onto the `LlmCallMetrics` proto
5. Pricing is frozen at execution time — historical data is self-contained

#### Cost Cap (already implemented)
We have a `CostCapMiddleware` that enforces per-execution budget limits:
- Warning at 80% of budget (injects SystemMessage asking model to wrap up)
- Hard stop at 100% (blocks all tool calls, asks for summary)
- Sub-agents share the parent's cost cap

### Current Billing State

The billing page in our web console is a **"Coming Soon" placeholder**:
```tsx
export default function BillingPage() {
  return <ComingSoon title="Billing" icon={CreditCard} />;
}
```

No Stripe integration exists. No prepaid credit system exists. No margin/markup is applied anywhere — the `estimated_cost_usd` in usage metrics currently reflects **raw provider cost** (what we pay Anthropic/OpenAI/Cursor).

### The Prepaid Model We Want (Inspired by Daytona)

We want customers to:
1. **Purchase credits upfront** (e.g., $50, $100, $500 credit packs)
2. **Credits are consumed** as their agents run, based on actual LLM token usage
3. **When credits run low**, they get warnings
4. **When credits are exhausted**, executions are blocked (with grace period for in-flight executions)
5. **Auto-recharge option** — automatically purchase more credits when balance drops below a threshold
6. **Usage dashboard** — see real-time credit balance, consumption history, per-agent breakdown

### Part 2: Margin & Markup Strategy

This is a critical question for us. Currently, our model-registry.json contains **raw provider costs** (what Anthropic/OpenAI charges us). We need to add a margin so we can run a business. The question is: **where and how?**

1. **Where should the margin be applied?**

   **Option A — Markup in the Model Registry**: Modify `model-registry.json` to store **customer-facing prices** instead of (or in addition to) provider costs. Apply a fixed percentage markup (e.g., 30%) to all provider prices.
   
   **Option B — Margin at the Billing Layer**: Keep model-registry.json as provider costs. Apply the markup when converting usage (which is stamped at provider cost) to credit deductions. The billing service multiplies `estimated_cost_usd × margin_multiplier`.
   
   **Option C — Per-Harness / Per-Tier Margin**: Different margin rates for different harnesses or cost tiers. E.g., higher margin on economy models (where absolute cost is low so customers are less price-sensitive) and lower margin on premium models.
   
   **Option D — Credit Conversion Rate**: Don't change dollar prices at all. Instead, make credits worth less than their purchase price. E.g., $1 purchase buys 0.80 credits, and 1 credit = $1 of provider cost. The margin is embedded in the purchase-to-credit conversion.
   
   What do industry leaders do? What are the tradeoffs of each approach?

2. **What margin percentage is typical for AI infrastructure platforms?**
   - What does Cursor charge vs. what they pay providers? (Their Sonnet 4.6 at $3/$15 per MTok is same as Anthropic's price — are they subsidizing or making margin elsewhere?)
   - What does AWS Bedrock charge vs. raw provider pricing?
   - What does Azure OpenAI charge vs. OpenAI direct?
   - What margin do cloud infrastructure platforms (Vercel, Railway, Render) typically take?
   - What's the standard markup range in the AI platform space?

3. **Margin visibility and transparency**:
   - Should customers see the raw provider cost and our margin separately?
   - Or should they only see the final price (like most SaaS)?
   - How do platforms like Cursor handle pricing transparency?
   - What does Stigmer's positioning (developer-focused, open-source core) imply for pricing transparency?

4. **Margin on Cursor Harness vs. Native Harness**:
   - For Native Harness, we call providers directly — our cost is the provider's published price
   - For Cursor Harness, we pay Cursor (which may already include their margin) — should we add margin on top of Cursor's price?
   - How do platforms that resell other platforms' services handle double-margin?
   - Should the Cursor Harness have a different (lower?) margin than Native?

5. **Free/local model handling**:
   - Ollama models cost $0 (local execution). Do we still charge for platform overhead?
   - If so, how? A fixed fee per execution? A per-minute compute charge?
   - How do platforms like Replit handle free-tier compute?

## Constraints and Requirements

- **Cloud-only**: Billing is exclusively a stigmer-cloud feature. The OSS edition has no billing.
- **Stripe**: We are committed to using Stripe as the payment processor. No other payment providers.
- **MongoDB**: Billing data storage in the cloud edition uses MongoDB.
- **Temporal**: Execution orchestration uses Temporal — billing events should integrate with or flow through Temporal if appropriate.
- **gRPC/Connect**: All APIs are gRPC with Connect protocol. Billing APIs will follow the same pattern.
- **Multi-tenant**: Organizations are the billing entity. Each org has its own credit balance.
- **Both harnesses**: Billing must support both Native and Cursor harness executions from day one.
- **Existing usage data**: We already have detailed per-execution, per-model, per-call usage data. Billing should build on top of this, not replace it.
- **Real-time**: Credit balance must be queryable in near-real-time. Usage dashboards can be eventually consistent.
- **International**: Customers are global. Must handle multiple currencies, tax jurisdictions.
