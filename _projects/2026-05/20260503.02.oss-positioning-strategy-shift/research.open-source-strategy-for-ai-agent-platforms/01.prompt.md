# Deep Research: Optimal Open-Source Strategy for an AI Agent Platform Company

## Research Objective

We are building **Stigmer** — an AI agent platform that lets engineering teams define agents, teach them domain knowledge, connect them to tools, set rules for human approval, and call those agents from any application via API. The platform handles the hard infrastructure: durable execution, tool sandboxing, conversation memory, human-in-the-loop approval flows, and multi-step workflow automation.

We need a comprehensive research report on **which open-source strategy best suits a product like ours** — an infrastructure platform for AI agents — to maximize adoption, community engagement, commercial viability, and long-term defensibility.

We are questioning whether our current approach is optimal and want to understand what the landscape of successful open-source infrastructure companies tells us about the right model for our kind of product.

---

## Our Current Situation

### What Stigmer Does

Stigmer is an **AI agent platform** (the emerging market category recognized by Forrester and Gartner). Teams building software products use Stigmer to add AI agent capabilities without building agent infrastructure from scratch.

**Core capabilities:**

1. **Domain Knowledge** — Upload business-specific knowledge (Skills) so agents give domain-expert answers, not generic ones. No vector databases or embedding pipelines required.
2. **Tool Access** — Agents interact with external systems (databases, APIs, ticketing systems) through the Model Context Protocol (MCP), an open standard.
3. **Human Approval Flows** — Configurable human-in-the-loop: define which actions require human approval before the agent proceeds. Durable execution means the agent waits indefinitely without losing state.
4. **Multi-Step Workflows** — Structured automation using CNCF Serverless Workflow DSL, executed on Temporal for durability and reliability.
5. **Declarative Resource Model** — Kubernetes-inspired: agents, skills, MCP servers, sessions, environments are all YAML resources with `apiVersion`, `kind`, `metadata`, `spec`, `status`.
6. **Real API Contracts** — gRPC services with public protobuf definitions. Type-safe client generation in Go, Python, Java, TypeScript, Dart. The CLI, SDKs, and web console are all API consumers.

**Target audience:**
- **Primary:** Technical founders and engineering leads choosing agent infrastructure for their product
- **Secondary:** Developers on those teams who implement the integration (write YAML, use CLI, call API, embed SDK)

**Anti-personas:** Hobbyists, no-code users, data scientists doing model training, chatbot widget seekers.

### Our Architecture (Two-Repo Model)

| Concern | **stigmer** (OSS repo) | **stigmer-cloud** (Private repo) |
|---------|------------------------|----------------------------------|
| **Control plane** | `stigmer-server` — Go, gRPC + Connect, SQLite | `stigmer-service` — Java 21, Spring Boot, gRPC, MongoDB, Redis, OpenFGA |
| **Workflow runner** | Go, Temporal Go SDK | Go, Temporal Go SDK (shared implementation) |
| **Agent runner** | Python, LangGraph, Temporal Python SDK | Python (shared implementation, deployed differently) |
| **API contracts** | `apis/` — Protobuf source of truth, published Buf module | `apis/stubs/` — Generated from OSS protos |
| **Storage** | SQLite (single-file, zero-config, local-first) | MongoDB + Redis + S3-compatible object storage |
| **IAM** | Lightweight local identity (single implicit user) | Auth0, OpenFGA for fine-grained authorization |
| **Build system** | Go modules, `go.work`, Bazel (Gazelle) | Bazel (Gazelle + Maven for Java) |
| **Web console** | Next.js (included in OSS repo) | Same console, different backend config |
| **CLI** | Go CLI (`stigmer` command) | Same CLI, connects to cloud backend |
| **SDKs** | Go, TypeScript, Python, React, Ink (terminal) | Same SDKs |
| **License** | Apache 2.0 | Proprietary / not published |

### Our Current Open-Source Strategy

Our current positioning document (internal) states:

> **Decision 3: Cloud-Primary, Open Source as Trust Signal**
>
> - **Sales site**: Leads with cloud. "Sign up. Get an API key. Build your first agent in 5 minutes."
> - **Open-source story**: Appears as a trust section — "Inspect every line of code. Self-host if you need to. No vendor lock-in." Not the primary CTA.
> - **README**: Stays developer-first (`brew install`, `stigmer server`, local-first). The README lives on GitHub where the audience is already technical.

The sales website has an "Open Source" section that says: *"Inspect every line of code. Stigmer is Apache 2.0. Public protobuf contracts. Self-host if you need to. No vendor lock-in. The fastest path is cloud, but you always have the option to run everything yourself."*

**What's open source (Apache 2.0):**
- The entire `stigmer` OSS repo: control plane (Go), agent runner (Python), workflow runner (Go), CLI, SDKs, web console, all protobuf definitions, documentation
- This is a fully functional, self-hostable product with SQLite storage

**What's proprietary:**
- The cloud service implementation (`stigmer-cloud`): Java control plane, MongoDB/Redis storage, multi-tenant IAM (Auth0, OpenFGA), billing, SSO/SAML, advanced RBAC, organization federation
- Managed infrastructure, SLA, support

### Our Concern

We believe people will be **more interested** in our solution if open source is positioned more prominently — not just as a trust signal but as a core part of the value proposition. We're worried that by treating open source as secondary to cloud, we might be:

1. **Missing developer adoption** — Developers discover and evaluate infrastructure through GitHub, not sales pages
2. **Undervaluing our differentiator** — In the AI agent platform space, being genuinely open source (Apache 2.0, fully functional self-hosted) is rare and valuable
3. **Misreading the market** — Infrastructure platforms that succeeded (Kubernetes, Terraform, Temporal, Supabase, PostHog, Sentry, GitLab) often led with open source
4. **Limiting community contributions** — A "trust signal" framing doesn't invite contributions the way an "open-source-first" framing does
5. **Making the wrong revenue assumption** — Maybe the cloud conversion funnel works better when the OSS product is the hero, not a footnote

But we also have legitimate concerns about:
- Giving away too much value (the OSS product is already fully functional)
- Cloud competitors copying our work
- Revenue cannibalization from self-hosting
- The right license choice (Apache 2.0 vs BSL vs AGPL vs SSPL vs FSL vs other)
