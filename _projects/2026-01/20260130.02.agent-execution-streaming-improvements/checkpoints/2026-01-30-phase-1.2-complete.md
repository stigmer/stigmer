## Key Implementation Details

### Hybrid Scheduling Algorithm

The scheduler triggers updates based on three conditions (any true = send update):

```python
should_send_update = (
    # Primary: Time-based with event guard
    (time_since_last >= 500ms AND events_since_last >= 1)
    OR
    # Secondary: Burst protection
    (events_since_last >= 50)
    OR
    # Tertiary: Keepalive
    (time_since_last >= 5000ms)
)
```

### Configuration

All thresholds are configurable via environment variables:

| Variable | Default | Purpose |
|----------|---------|---------|
| `STREAMING_MIN_INTERVAL_MS` | 500 | Rate limiting (max 2 updates/sec) |
| `STREAMING_MAX_INTERVAL_MS` | 5000 | Keepalive (reassure user during long ops) |
| `STREAMING_BURST_THRESHOLD` | 50 | Burst protection (prevent memory issues) |

### Architecture Decisions

1. **Dedicated scheduler class** instead of inline logic
   - Testable in isolation
   - Reusable for future streaming components
   - Clean separation of concerns

2. **Monotonic time** (`time.monotonic()`)
   - Immune to system clock adjustments
   - Reliable for duration measurements
   - Standard practice for timers

3. **Frozen dataclass** for configuration
   - Immutable = thread-safe
   - Clear validation at construction
   - Follows existing codebase patterns

4. **UpdateReason enum** for observability
   - Clear logging of why updates are sent
   - Debugging and monitoring support
   - Production observability

## Technical Decisions

### 1. Heartbeat vs Status Update Separation

**Decision**: Keep heartbeat (Temporal timeout prevention) separate from status updates (UX)

**Rationale**:
- Different purposes and requirements
- Heartbeat: Prevent Temporal activity timeout (independent of UX)
- Status update: User experience (optimized by scheduler)
- Heartbeat now time-based (2 seconds) instead of event-count

### 2. Mark Update on Failure

**Decision**: Still mark update as sent even if gRPC call fails

**Rationale**:
- Prevents retry storm on persistent failures
- Logs error for debugging
- Next natural trigger will retry
- Avoids cascading failures

### 3. First Update Immediate

**Decision**: Send first update immediately (with first event)

**Rationale**:
- Establishes baseline state quickly
- User sees activity started
- Subsequent updates follow hybrid schedule

### 4. Structured Logging Format

**Decision**: Use `[STREAM]` prefix with key=value pairs

**Format**:
```
[STREAM] execution=<id> update_sent=true reason=<reason> 
         events_total=N events_since_last=M time_since_last_ms=T
         messages=X tool_calls=Y
```

**Rationale**:
- Parseable by log aggregators
- Consistent with existing `[USAGE]` pattern
- Easy to filter and analyze
- Production observability

## Learnings

### 1. Monotonic Time is Essential

**Discovery**: Using `time.monotonic()` instead of `time.time()` prevents issues with:
- NTP clock adjustments
- Daylight saving time changes
- Manual clock changes
- System suspend/resume

**Impact**: Reliable duration measurements for production systems

### 2. Configuration Validation at Construction

**Discovery**: Dataclass `__post_init__` validation provides immediate feedback

**Benefit**:
- Fail fast on invalid configuration
- Clear error messages at startup
- No silent failures during runtime

### 3. Frozen Dataclasses for Config

**Discovery**: Immutable config prevents accidental modification

**Benefit**:
- Thread-safe by default
- Clear ownership and lifecycle
- Easier to reason about

### 4. Enum for Logging is Powerful

**Discovery**: `UpdateReason` enum provides type-safe reason codes

**Benefit**:
- No magic strings in code
- Autocomplete support
- Easy to extend with new reasons
- Clear documentation
