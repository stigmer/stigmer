## Session Summary

Successfully implemented Phase 2.2, which changes tool status from `PENDING` to `RUNNING` when tools start executing. This provides semantically correct status representation and better UX in the CLI/UI.

## Accomplishments

### 1. Changed Tool Initial Status

**Change**: Modified `_handle_tool_start_event` to set `TOOL_CALL_RUNNING` instead of `TOOL_CALL_PENDING`

**Rationale**: 
- In LangGraph, `on_tool_start` fires when execution **begins**, not when queued
- `PENDING` implies "waiting to execute" (misleading)
- `RUNNING` correctly reflects "currently executing" (tool is doing work)

**File**: `backend/services/agent-runner/worker/activities/graphton/status_builder.py`

### 2. Added Tool Execution Duration Tracking

**Implementation**:
- Added `_tool_start_times: Dict[str, datetime]` to StatusBuilder `__init__`
- Record start time on `on_tool_start` (keyed by `run_id`)
- Calculate and log duration on `on_tool_end`
- Clean up start time dict on completion

**Pattern**: Follows same approach as message duration tracking from Phase 1.1

**File**: `backend/services/agent-runner/worker/activities/graphton/status_builder.py`

### 3. Added Structured Logging

**Format**: `[TOOL]` prefix for tool lifecycle events

**On tool start**:
```
[TOOL] execution={id} tool={name} run_id={id} status=RUNNING
```

**On tool end**:
```
[TOOL] execution={id} tool={name} run_id={id} status=COMPLETED duration_ms={ms}
```

**Benefits**:
- Consistent with existing patterns (`[USAGE]`, `[STREAM]`, `[RETRY]`)
- Enables filtering and analysis of tool execution logs
- Provides visibility into tool performance

## Decisions Made

### 1. No Proto Changes Required

**Decision**: Don't add `duration_ms` field to ToolCall proto

**Rationale**:
- ToolCall already has `started_at` and `completed_at` timestamps
- Frontend can calculate duration: `completed_at - started_at`
- Adding field would require proto change + stub regeneration
- Current approach provides observability via logs without API changes

**Trade-off**: Accepted - duration in logs is sufficient for now

### 2. Duration Tracking Pattern

**Decision**: Use same pattern as message duration (Phase 1.1)

**Rationale**:
- Consistent with existing code
- Proven approach (already tested)
- Clean dictionary-based tracking

**Implementation**: `Dict[str, datetime]` keyed by `run_id`

### 3. Structured Logging Prefix

**Decision**: Use `[TOOL]` prefix (not `[TOOLCALL]` or other variations)

**Rationale**:
- Concise and clear
- Consistent with `[USAGE]`, `[STREAM]`, `[RETRY]` pattern
- Easy to grep/filter
