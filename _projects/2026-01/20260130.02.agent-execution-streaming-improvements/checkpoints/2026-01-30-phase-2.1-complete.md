## Decisions Made

### Proto Design
**Decision**: Use `int32` instead of `int64` for token counts and duration  
**Rationale**: Token counts and durations (in milliseconds) easily fit in 32-bit integers. Saves space and matches industry patterns.

**Decision**: Use proto3 default values (0, false) as "unset" indicators  
**Rationale**: Simpler than `optional`, clear semantics: zero/false means either "not applicable" or "not yet finalized"

**Decision**: Place fields on AgentMessage rather than separate message  
**Rationale**: Keeps related data together, simpler API surface. Fields are zero-cost for non-AI messages.

### Implementation Pattern
**Decision**: Set `is_streaming=True` immediately when creating message  
**Rationale**: Message is actively streaming from the moment it's created. UI can immediately show typing indicator.

**Decision**: Finalize all fields in `on_chat_model_end` (not incrementally)  
**Rationale**: Token usage and final duration are only available when generation completes. Clean state transition.

## Learnings

### What Worked Well
1. **Leveraging Phase 1.1 infrastructure**: Token tracking and timing infrastructure from Phase 1.1 made implementation straightforward
2. **Proto3 defaults**: Using 0/false as "unset" is clean and idiomatic
3. **Test-first mindset**: Writing tests first helped clarify exact field semantics
4. **Comprehensive documentation**: Clear proto comments prevent future confusion

### What to Remember
1. **Proto field numbers are permanent**: Once assigned, field numbers cannot be reused (protobuf compatibility)
2. **Stubs must be regenerated**: Proto changes require regenerating all language stubs (Python, Go, Java, TypeScript)
3. **Test coverage is critical**: Edge cases (missing metadata) are important to test
4. **Monotonic time matters**: Duration tracking must use `time.monotonic()` not `time.time()`
