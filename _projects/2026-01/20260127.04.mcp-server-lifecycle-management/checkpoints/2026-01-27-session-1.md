## Accomplishments

### 1. Deep Research into MCP Protocol
- Investigated MCP transport types (stdio, HTTP, Docker)
- Discovered stdio: Client spawns subprocess, manages lifecycle
- Discovered HTTP: Just HTTP calls to already-running server
- Found that Docker is NOT a standard MCP transport

### 2. LangGraph Integration Discovery
- Researched LangGraph's `langchain-mcp-adapters` package
- Found `MultiServerMCPClient` already provides:
  - Subprocess spawning/termination (stdio)
  - HTTP client sessions with connection pooling (HTTP)
  - Graceful shutdown
  - Multi-server management
- **Result**: We don't need to build custom lifecycle managers!

### 3. Implementation Plan Overhaul
**Before**: 18-25 days
- Custom `StdioServerManager`
- Custom `HttpServerManager`
- Custom `DockerServerManager`
- Custom `McpServerRegistry`
- Custom `HealthMonitor`
- Custom `ShutdownCoordinator`

**After**: 2.5-4.5 days
- Config transformer (Stigmer proto → LangGraph format)
- LangGraph integration
- Dockerfile update (add Node.js)

**Savings**: 15-20 days of development time

### 4. Proto Spec Cleanup
- Removed `DockerServerConfig` message (58 lines)
- Removed `VolumeMount` message (19 lines)
- Removed `PortMapping` message (27 lines)
- Removed Docker from `server_type` oneof
- **Total**: -102 lines from proto spec
- **Result**: Clean, simple API with stdio and HTTP only

## Decisions Made

### DD01: Use LangGraph's Built-in Lifecycle Management
**Rationale**:
- LangGraph already does everything we planned to build
- Less code to maintain
- Battle-tested library
- Stays aligned with LangGraph ecosystem

**Trade-offs**:
- Dependency on LangGraph's implementation
- Less fine-grained control
- Inherit any LangGraph bugs

**Outcome**: Accepted - benefits far outweigh risks

### DD02: Docker Transport Removed from Proto
**Rationale**:
- YAGNI (You Aren't Gonna Need It)
- Not a standard MCP transport
- LangGraph doesn't support it
- Users can work around: run container + use HTTP

**Trade-offs**:
- Can't run containers automatically
- Less "magic" for users

**Outcome**: Accepted - can add later if needed

## Learnings

### About MCP Protocol
1. **stdio transport**: Client is responsible for spawning subprocess
2. **HTTP transport**: Server is already running, client just makes HTTP calls
3. **Docker is not standard**: Custom addition, not in MCP spec

### About LangGraph
1. `MultiServerMCPClient` is production-ready for MCP integration
2. Handles subprocess lifecycle automatically
3. Supports stdio and HTTP (not Docker)
4. Known issue: May restart server on each tool call (being tracked)

### About Agent Runner Docker Image
- Currently based on `python:3.11-slim`
- Has: Python, git, curl, ca-certificates
- **Missing**: Node.js/npm/npx
- **Impact**: Can't run npm-based MCP servers (most common type!)
- **Solution**: Add Node.js 20.x to Dockerfile
