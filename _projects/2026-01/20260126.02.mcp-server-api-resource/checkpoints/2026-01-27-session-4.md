## Technical Decisions

### 1. Tri-Scope Operator Pattern

**Challenge**: McpServer is the first resource needing operator access from all three scopes.

**Solution**:
```fga
define operator: operator from platform or operator from organization or operator from identity_account
```

**Rationale**: 
- Platform operators manage marketplace servers
- Org operators troubleshoot org-scoped servers  
- Identity account operators derive from user's org membership
- Provides complete troubleshooting coverage

### 2. Marketplace Visibility Pattern

**Challenge**: Platform-scoped servers need to be discoverable by all users.

**Solution**:
```fga
define can_view: viewer or platform
define can_use: viewer or platform
```

**Rationale**:
- The `or platform` clause allows any user to view/use marketplace items
- Enables public marketplace while maintaining private org/user servers
- Follows the "if you can see it, you can use it" principle

### 3. Org Admin Ownership

**Challenge**: Organization-scoped servers need manageable by org admins.

**Solution**:
```fga
define owner: [identity_account] or admin from organization or operator
```

**Rationale**:
- Follows `environment.fga` pattern
- Enables org admins to manage team resources
- Balances creator ownership with org governance

### 4. Clone Permission for Learning

**Challenge**: Enable users to learn from marketplace configurations.

**Solution**:
```fga
define can_clone: viewer or platform
```

**Rationale**:
- Users can create personal copies of marketplace servers
- Enables experimentation without affecting originals
- Promotes knowledge sharing and learning
- Supports marketplace ecosystem growth

## Learnings

### 1. Tri-Scope Pattern Complexity

**Observation**: McpServer is more complex than existing 2-scope resources (skill, agent).

**Insight**: The tri-scope pattern requires careful consideration of:
- Operator access propagation from all scopes
- Visibility rules that work correctly for each scope
- Permission inheritance across three different ownership models
- Public marketplace vs private team vs personal visibility

**Application**: This pattern can be reused for future marketplace-enabled resources.

### 2. Marketplace Visibility Pattern

**Observation**: The `or platform` clause is a powerful pattern for public resources.

**Insight**: By adding `or platform` to permissions:
- Platform-scoped resources become publicly discoverable
- Org-scoped and user-scoped resources remain private
- Single permission definition handles all three scopes elegantly
- No need for complex conditional logic

**Application**: This pattern should be documented as a standard for marketplace resources.

### 3. FGA Model Quality Matters

**Observation**: The user emphasized foundation-quality code with no technical debt.

**Insight**: FGA models are critical infrastructure that's hard to change later:
- Comprehensive documentation pays off during implementation
- Clear examples prevent misunderstandings
- Validation catches issues early
- Following established patterns reduces bugs

**Application**: Never rush FGA models - they're worth the investment in quality.
