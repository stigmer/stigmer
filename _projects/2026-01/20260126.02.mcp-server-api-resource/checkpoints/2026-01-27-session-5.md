## Key Technical Decisions

### 1. Identity-Account-Scoped Query Pattern

**Problem**: How to query identity-account-scoped resources when user ID isn't stored in metadata?

**Solution**: 
- Store only `metadata.ownerScope = identity_account` in MongoDB
- Query by `ownerScope + slug` (no user ID in query)
- Rely on FGA authorization to filter to owner's resources
- This matches the platform pattern where ownership is determined via FGA tuples

**Implementation**:
```java
// Repository method (simplified)
public Optional<McpServer> findByIdentityAccountAndSlug(String slug) {
    Query query = Query.query(
        Criteria.where("metadata.ownerScope").is(ApiResourceOwnerScope.identity_account_VALUE)
                .and("metadata.slug").is(slug)
    );
    // FGA authorization ensures caller can only access their own resources
}
```

**Why this works:**
- GetByReference handler calls FGA authorization after loading
- FGA checks `can_view` permission via owner relation
- If user doesn't own it, FGA denies access
- Result: Only the owner can successfully retrieve their resources

### 2. Server Config Validation Strategy

**Decision**: Implement validation as a reusable pipeline step shared by Create and Update handlers

**Implementation**:
- `ValidateServerConfig` as a `@Component` class
- Validates exactly one server type (stdio/http/docker)
- Type-specific validation: command, URL, image, volume mounts
- Used by both CreateHandler and UpdateHandler

**Benefits:**
- DRY (don't repeat yourself)
- Consistent validation across operations
- Easy to extend with new server types

### 3. FGA Tuple Creation Pattern

**Pattern**: Three-tuple model for tri-scope resources

**Tuples created on McpServer creation:**
1. **Scope link** (exactly one):
   - Platform: `mcp_server:{id}#platform@platform:stigmer`
   - Org: `mcp_server:{id}#organization@organization:{org_id}`
   - Identity: `mcp_server:{id}#identity_account@identity_account:{user_id}`

2. **Owner link** (always):
   - `mcp_server:{id}#owner@identity_account:{creator_id}`

**Why this pattern:**
- Scope link enables scope-based visibility rules in FGA model
- Owner link establishes who can edit/delete
- Org admins get edit/delete via FGA model's `define owner: [identity_account] or admin from organization`
- Clean, minimal tuple set

### Challenge 2: Determining Identity-Account Query Strategy

**Investigation**: Examined WorkflowInstance and Skill repos

**Finding**: 
- Skill only supports platform/org (no identity_account)
- WorkflowInstance supports identity_account but doesn't query by it (uses IAM filtering)
- Identity ownership is via FGA, not metadata fields

**Resolution**: 
- Query by `ownerScope + slug` for identity-account
- FGA authorization filters to owner during `can_view` check
- Matches platform's FGA-centric authorization model

## Learnings

### 1. Tri-Scope Repository Pattern

**Pattern identified**: Two approaches for user-scoped queries:
- **Approach A** (used): Query by ownerScope + slug, FGA filters access
- **Approach B** (alternative): Store userId in metadata, query directly

**Why Approach A is better:**
- Consistent with platform's FGA-first philosophy
- Avoids denormalizing user ID into metadata
- Single source of truth (FGA) for ownership
- Cleaner metadata structure

### 2. Handler Base Classes Provide Significant Leverage

**Observation**: Standard handlers (Get, Update, Delete) are ~60-80 lines

**Why so compact:**
- Base classes provide pipeline scaffolding
- Common steps injected (`commonSteps.validateFieldConstraints`, etc.)
- Operation-specific steps (`createSteps.buildNewState`, etc.)
- Framework handles: validation, authorization (proto-level), persistence, events

**Implication**: Custom logic only needed for:
- Business-specific validation (ValidateServerConfig)
- Custom authorization (AuthorizeCreation for tri-scope)
- Custom operations (FGA tuple creation)

### 3. Proto Stub Generation Timing

**Learned**: Always generate stubs before creating handlers

**Process followed:**
1. Generated Java stubs: `cd apis && make java-stubs`
2. Verified McpServer proto classes exist: 29 files generated
3. Then created handlers with correct import paths

**Why this matters:**
- IDEs can validate imports during development
- Catch proto issues early (missing types, wrong package names)
- Ensures consistency between proto definitions and Java code
