## Decisions Made

### 1. Separate McpToolsLoader per Subagent
**Rationale**: Complete isolation of MCP access, preventing access to parent's full tool set

**Implementation**: Each subagent gets filtered `mcp_servers` and `mcp_tools` dicts passed to its own McpToolsLoader instance

### 2. Permission Intersection Model
**Formula**: `subagent_tools = parent_enabled_tools ∩ subagent_requested_tools`

**Rules**:
- SubAgent can only access MCP servers explicitly listed in `mcp_access`
- SubAgent tools must be subset of parent's enabled tools
- Empty `enabled_tools` in McpAccess = inherit all parent tools
- Invalid server references are logged and skipped

### 3. Batch Skill Resolution
**Optimization**: Collect all unique skill refs across all subagents, fetch in single gRPC call

**Benefits**:
- Reduces gRPC overhead (N calls → 1 call)
- Simplifies skill distribution logic
- Better error handling (one failure point)

### 4. Graceful Degradation
**Philosophy**: Invalid configs should not crash the system

**Implementation**:
- MCP access errors → log warning, skip that server
- Skill fetch failures → log error, continue without skills
- Tool creation failures → log error, subagent created without tools
- All failures logged for debugging

## Learnings

### 1. Graphton API Design
**Discovery**: Graphton's subagent parameter expects simple dicts with `name`, `description`, `system_prompt`, and optional `tools` list

**Impact**: No need to create complex wrappers, direct dict construction works perfectly

### 2. McpToolsLoader Lifecycle
**Finding**: McpToolsLoader handles deferred loading in async contexts automatically

**Implementation**: Must check `_deferred_loading` flag and call `_load_tools_async()` if needed

### 3. Permission Model Complexity
**Challenge**: Tool intersection logic required careful validation

**Solution**: Build slug → usage mapping upfront for O(1) lookups during filtering

### 4. Test Mocking Strategy
**Approach**: 
- Mock `McpToolsLoader` to avoid actual MCP connections
- Use real `SkillWriter` for integration tests
- Mock gRPC clients but verify correct filtered configs passed

## Open Questions

### 1. Caching Strategy
**Question**: Should we cache transformed subagents if AgentSpec hasn't changed?

**Considerations**:
- Performance benefit if same agent used multiple times
- Cache invalidation complexity when skills or MCP servers update
- Memory usage for cached transformations

**Decision**: Defer to production usage patterns - implement if needed

### 2. Nested Subagents
**Question**: Should subagents be able to have their own subagents?

**Current**: Proto doesn't define recursive SubAgent structure
**Future**: Could add if use cases emerge (hierarchical task delegation)

### 3. Metrics Collection
**Question**: What metrics should we track for subagent usage?

**Candidates**:
- Delegation frequency (which subagents used most)
- Permission denials (MCP access attempts)
- Failure rates (subagent vs parent success)
- Performance impact (overhead of delegation)

**Decision**: Start with basic usage tracking, expand based on needs
