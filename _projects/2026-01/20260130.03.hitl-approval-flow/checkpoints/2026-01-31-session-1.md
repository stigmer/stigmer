### 5. AgentExecution.SubmitApproval (Most Complex)
- **Purpose**: User submits approval decision (APPROVE/SKIP/REJECT) for pending tool call
- **Preconditions**:
  - Phase must be `EXECUTION_WAITING_FOR_APPROVAL`
  - `tool_call_id` must match `status.pending_approval.tool_call_id`
  - Action must be APPROVE, SKIP, or REJECT (not UNSPECIFIED)
- **Idempotency**: If tool call already has matching approval action, treat as no-op
- **Temporal Integration**:
  - Sends `submitApproval` signal to running workflow
  - Workflow ID: `stigmer/agent-execution/invoke/{execution-id}`
  - Untyped signal: `workflowClient.SignalWorkflow(ctx, workflowId, "", signalName, input)`
- **Workflow Changes**:
  - Added approval loop: executes Python activity → waits for signal → re-executes with decision
  - Max 100 approval cycles to prevent infinite loops
  - Uses `workflow.GetSignalChannel(ctx, "submitApproval")` to receive signals
  - Embeds approval decision in `ToolCall.approval_action` and `approval_decided_at`
  - Re-invokes `ExecuteGraphton` activity with updated execution proto
- **Error Handling**:
  - `NOT_FOUND`: Execution doesn't exist
  - `FAILED_PRECONDITION`: Wrong phase or tool_call_id mismatch
  - `UNAVAILABLE`: Temporal signal failed (workflow not running)

### 6. WorkflowExecution.SubmitApproval
- **Purpose**: Delegate approval from workflow level to child agent execution
- **Pattern**: Load workflow → extract `child_agent_execution_id` from `pending_approval` → forward to `AgentExecution.SubmitApproval`
- **Validation**:
  - `status.pending_approval` must be populated
  - `tool_call_id` must match
  - `child_agent_execution_id` must not be empty
- **Delegation**: Calls `AgentExecutionController.SubmitApproval()` directly (in-process)
- **Use Case**: User approves from workflow UI, approval propagates to child agent

## Decisions Made

### 1. Store Query Strategy
**Decision**: Use protobuf reflection instead of JSON extraction

**Rationale**:
- Data stored as binary protobuf BLOBs in SQLite
- Converting to JSON for querying would be expensive
- Protobuf reflection allows direct field access
- Maintains type safety
- Acceptable performance for local OSS usage (single user, low volume)

**Trade-off**: Full table scan instead of indexed query (ok for OSS, would need optimization for Cloud)

### 2. Temporal Signal Pattern
**Decision**: Use `workflow.GetSignalChannel()` for receiving signals

**Rationale**:
- Recommended pattern in Temporal Go SDK documentation
- Type-safe with proto message deserialization
- Blocks workflow execution until signal received
- Integrates cleanly with workflow logic

**Alternative Considered**: `workflow.SetSignalHandler()` - more complex, less idiomatic for this use case

### 3. Approval Loop Design
**Decision**: Embed approval decision in `ToolCall.approval_action` field

**Rationale**:
- Matches Java implementation pattern
- Python activity can read decision from proto
- No need for separate signal payload or state management
- Clear audit trail (decision + timestamp in proto)

**Implementation**:
```go
// Workflow receives signal with SubmitApprovalInput
// → Finds tool call by ID
// → Sets approval_action = input.action
// → Sets approval_decided_at = workflow.Now()
// → Re-invokes Python activity with updated execution proto
// → Python reads approval_action and handles accordingly
```

### 4. Max Approval Cycles
**Decision**: Hard limit of 100 approval cycles per execution

**Rationale**:
- Prevents infinite loops (bug in approval logic)
- 100 is generous for realistic scenarios (most agents need 1-5 approvals)
- Workflow fails fast if limit reached
- Easy to debug (clear error message)

**Alternative Considered**: No limit - risky, could cause workflow to run indefinitely

### 5. Idempotency Strategy
**Decision**: Treat duplicate approvals as no-op (return success)

**Rationale**:
- User might click "Approve" multiple times (network lag, UI bug)
- Prevents confusing errors ("already approved")
- Audit trail preserved (first approval timestamp)
- Workflow state unchanged

**Validation**: Only allow duplicate if action matches (can't change APPROVE → REJECT)

## Learnings

### 1. Temporal Signal Workflow Pattern
- Signals enable external events to unblock running workflows
- `workflow.GetSignalChannel()` provides clean blocking semantics
- Workflow context must be used for all time operations (`workflow.Now()`)
- Signal payload can be any proto message (type-safe deserialization)

### 2. Protobuf Reflection in Go
- `msg.ProtoReflect()` provides access to message descriptor
- Field names in Go proto: camelCase (e.g., `executionId`)
- Field names in JSON proto: snake_case (e.g., `execution_id`)
- Need to handle both naming conventions for field path queries
- `protoreflect.Name(toSnakeCase(fieldName))` for fallback lookup

### 3. Pipeline Pattern Benefits
- Each step has single responsibility
- Easy to test individual steps in isolation
- Clear error handling per step
- Context passing enables inter-step communication
- Reusable steps across handlers (ValidateProto, LoadTarget)

### 4. gRPC Error Codes Matter
- `NOT_FOUND`: Resource doesn't exist (e.g., execution not found)
- `FAILED_PRECONDITION`: Resource exists but in wrong state (e.g., not waiting for approval)
- `INVALID_ARGUMENT`: Input is malformed (e.g., empty tool_call_id)
- `UNAVAILABLE`: Transient failure (e.g., Temporal not available)
- Proper codes enable client retry logic and user-friendly error messages
