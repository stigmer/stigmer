# Eliminating Docker Dependency for a Python Agent-Runner via Native Process Distribution

## Executive summary and recommendations

Stigmer’s goal—run **agent-runner** like a “normal daemon process” on macOS/Linux/Windows without Docker—collides with two hard realities in the current Python packaging ecosystem:

1. **Frozen-binary tools (PyInstaller, Nuitka, cx_Freeze)** still fundamentally depend on static import analysis + per-project configuration for “non-standard” import patterns; they have improved, but they have **not** eliminated the core failure mode you hit in January 2026 (dynamic imports and import-system tricks). PyInstaller explicitly documents that packages using unusual import mechanisms can require hooks/hidden imports, because PyInstaller cannot reliably find everything automatically. citeturn12search1turn0search25  
2. Your dependency stack (Temporal Python SDK + gRPC + MCP subprocess orchestration) strongly favors shipping a **real CPython runtime + site-packages** (a hermetic environment), not a fully “frozen” executable, because that’s the closest analogue to what Docker gives you: normal `import` semantics, native wheels working as designed, and easy debugging.

Based on 2025–2026 state-of-the-art tooling, the three most viable approaches (in descending order of practical feasibility for your exact constraints) are:

**Recommended approach (best overall): Hermetic CPython runtime bundle (python-build-standalone) + wheelhouse/venv, installed and managed by the Go CLI**  
Use a relocatable CPython distribution (the same family of builds used by uv) and install your pinned dependencies into an app-managed environment directory the CLI controls. This keeps agent-runner a native process, eliminates Docker Desktop entirely for the core product, and avoids the brittle “frozen import graph” problem because everything runs under standard CPython. python-build-standalone explicitly targets “self-contained, highly-portable Python distributions” with bundled/linked stdlib extension dependencies. citeturn1search1turn15search9  

**Second-best: PEX/zipapp-style artifact plus bundled interpreter (PEX “scie” or equivalent)**
Traditional zipapps (shiv/zipapp) still require a Python interpreter on the target machine; shiv’s docs describe bundling dependencies but relying on Python to run, with extraction into a cache directory. citeturn17view0turn16search3turn16search10  
However, PEX is specifically designed to create executable Python environments and can include multiple platform-specific Python distributions in a single PEX (and newer “self-contained interpreter executable” patterns exist in the PEX ecosystem). citeturn0search20turn0search4  
This can get you closer to a **single-file** experience, but you’ll still produce per-platform artifacts for native extensions and you’ll still want an installation/cache strategy.

**Third-best: uv-bootstrap on first run (download CPython + install deps)**
uv can install Python versions automatically (using python-build-standalone) and then create environments/install dependencies without the user pre-installing Python. citeturn1search0turn1search24  
This is operationally elegant and reduces CI artifact bloat, but it introduces network/proxy failure modes and can harm first-run experience unless you also ship a wheelhouse/offline cache.

Recommendation: **Implement the hermetic CPython runtime bundle managed by the Go CLI** and treat “PEX/SCIE” as an optional future refinement for single-file packaging once the basics are stable.

## Constraints and requirements that dominate the design

Your stack is unusually packaging-hostile in ways that matter more than any single tool choice:

**Native extensions are unavoidable.**  
The Temporal Python SDK is built on a Rust “SDK Core,” and Temporal’s own materials explicitly describe using PyO3 + bridge code so the Python SDK can leverage the Rust core. citeturn2search0turn2search24  
Similarly, gRPC’s Python distribution is a binary-heavy package with wheels for major platforms. citeturn2search5turn2search37  
This means any viable distribution must handle platform-specific `.so`/`.dylib`/`.pyd` artifacts correctly.

**Alternative runtimes (e.g., GraalPy) are not credible for Temporalio today.**  
Temporal community guidance indicates CPython-only support; GraalPy support is not a goal because of C-extension interactions via Rust/PyO3. citeturn2search4  
GraalPy’s own documentation notes that native C extensions have limitations and that CPython-built extensions are not binary-compatible. citeturn5search2turn5search6  

**Your observed `multipart` breakage may be “dynamic imports” and/or “namespace conflicts,” not just PyInstaller quality.**  
There is a well-documented naming conflict around `multipart` vs `python-multipart`. python-multipart explicitly notes historical `import multipart` behavior and cautions that conflicts arise if the `multipart` package is also installed. citeturn13search25turn13search7  
This matters because it shows that “missing multipart at runtime” can arise from packaging *and* from dependency name collisions, especially when tools stage dependencies in unusual ways.

**MCP subprocess spawning makes “what ships” extend beyond Python.**  
The MCP specification states that the stdio transport works by the **client launching the MCP server as a subprocess** and then exchanging JSON-RPC over stdin/stdout. citeturn8view0  
So if your agent-runner must launch Node or Go-based MCP servers locally, you either (a) ship those runtimes, (b) force-install them, or (c) redesign to prefer remote HTTP transport or prebuilt server binaries.

**Docker Desktop friction is structurally real on macOS.**  
Docker’s own docs describe Docker Desktop on macOS as running containers inside a Linux VM using selectable VMM backends (HyperKit/Apple Virtualization Framework/etc.). citeturn4search1turn4search13  
Docker also documents that Docker Desktop is only free for “small businesses” under specific thresholds; larger org use requires paid subscription. citeturn4search0turn4search23  

These constraints are why “package as a single binary” is a high-risk bet, while “ship a real Python runtime” is a low-risk bet.

## Viable approaches and what 2026 tooling actually enables

This section answers your numbered research questions, but consolidates them into approach families that map to implementation decisions.

### Frozen executables

**PyInstaller (revisited)**  
PyInstaller’s core model remains: analyze imports, then compensate for edge cases with **hooks** and **hidden imports**. PyInstaller’s own documentation states that packages that “make unusual uses of the Python import mechanism” or change imports at runtime may not be reliably detected, and that hooks exist to specify additional imports/data/binaries. citeturn12search1turn13search0  
The hooks ecosystem is active (including community-maintained hooks). citeturn13search33turn13search12  

Key implications for Stigmer:

- **Dynamic imports are not “solved.”** The mechanism is “documented workaround,” not “automatic success.” citeturn12search1turn0search25  
- **Onefile mode has inherent extraction overhead and operational hazards.** PyInstaller documents that onefile bundles extract into a temporary `_MEIxxxxxx` directory at startup, and that temp directory placement has OS/security implications (e.g., `noexec` mounts). citeturn14search12turn14search4  
- **Cross-compilation remains non-native.** Community guidance consistently indicates PyInstaller doesn’t cross-compile OS targets; you build on each target OS/arch. citeturn0search30turn0search26  
- **Native extensions generally work when the correct wheels/binaries are staged**, but you inherit the debugging burden of “did the freezer collect the right shared libs?”—exactly the class of problem Docker avoids. PyInstaller hooks explicitly support collecting binaries and metadata for packages. citeturn12search1  

Bottom line: PyInstaller can be made to work for complex apps, but it is a **maintenance-heavy** approach for a Temporal/AI stack with dynamic imports and transitive conflicts. It also pushes you toward onedir packaging (less startup penalty) rather than onefile.

**Nuitka (Python-to-C compiler)**  
Nuitka is fundamentally different from PyInstaller (compile to C, then build a native executable), but it still must decide what to include for “standalone” distributions, and it sees similar dependency-graph explosion issues. Nuitka’s docs explicitly call out “dependency creep” leading to substantial compilation times. citeturn0search23  
Cross-platform story:

- Nuitka maintainers and community guidance indicate you should generally build on the target platform; cross-compilation is not the default path. citeturn14search23turn14search13  
- Nuitka offers many inclusion options; recent releases focus on correctness of `--include-package` behavior (including extension submodules). citeturn0search38  
- Nuitka’s onefile has cache/extraction behavior and real-world complexities; issues around onefile cache modes exist, indicating the complexity is still actively evolving. citeturn14search2turn14search18  

Licensing is nuanced. Nuitka’s repository license file is AGPLv3 text, and Nuitka’s own overview states AGPLv3 with an exception for created binaries, with a separate proprietary “Nuitka Commercial.” citeturn11view0turn9search33turn9search1  

Bottom line: Nuitka can sometimes reduce runtime “import missing” issues relative to PyInstaller in specific projects, but it is still a **complex native build pipeline** with long builds and per-platform compilation. For your stack, Nuitka is plausible, but not the lowest operational risk.

**cx_Freeze**  
cx_Freeze is a more explicit-config freezer. Documentation emphasizes specifying modules/packages and explicitly including compiled libraries. citeturn2search6turn9search23  
Dynamic import issues are not unique to PyInstaller; cx_Freeze has open issues where runtime-determined imports cause missing modules unless explicitly handled. citeturn2search18turn2search38  
Licensing is PSF-derived. citeturn9search3turn9search7  

Bottom line: cx_Freeze is unlikely to magically solve the class of problems you already saw; it shifts the burden toward “explicitly list everything” and works best when import behavior is conventional.

**PyOxidizer (not in your list, but materially viable)**  
PyOxidizer builds executables embedding Python. It advertises cross-platform support and can produce a single executable embedding interpreter + stdlib + app resources. citeturn15search5turn2search27  
But it explicitly documents **restrictions and partial support** for extension modules and notes that limitations often stem from the underlying Python distribution and extension module behavior. citeturn15search0turn15search18  
It also ties closely to python-build-standalone distributions. citeturn15search1turn15search9  

Bottom line: PyOxidizer can be powerful, but for heavy native-extension stacks it often becomes a specialized build engineering project in its own right; this is less appealing when your goal is “be boring and robust like Docker, but without Docker.”

### Zipapp-style applications: shiv and PEX

**Shiv**  
Shiv builds a zipapp with dependencies included, but it still relies on the system’s Python to run. Packaging guidance broadly classifies shiv/zipapp as approaches that “require Python.” citeturn16search10turn16search16  
Shiv’s own docs explain that it unpacks dependencies to a cache directory (`~/.shiv`) and then adds them to `sys.path`. This extraction exists specifically because binary dependencies and filesystem expectations break pure zipimport. citeturn17view0  

For Stigmer, shiv alone violates the “cannot require users to install Python” constraint. But it’s conceptually relevant because it demonstrates a stable pattern: **ship deps, extract to cache, run with normal CPython import semantics.**

**PEX (and “bundle interpreter” options)**  
PEX is designed to produce executable Python environments (zipapp-like) and explicitly references PEP 441 concepts. citeturn0search20turn0search32  
Crucially, PEX can include multiple platform-specific Python distributions inside a single PEX in some modes. citeturn0search20  

For Stigmer, PEX becomes truly interesting when combined with a shipped interpreter (e.g., “scie”/self-contained interpreter executable patterns). That turns PEX into a realistic contender for “single artifact per platform” without the freezer-style import breakage, because it’s still just CPython running packages.

Bottom line: PEX-style packaging is **more reliable for dynamic imports than freezing**, but by itself it still doesn’t solve the “no system Python” constraint unless you ship an interpreter via a companion mechanism.

### Shipping a real CPython runtime and environment

**uv-managed environments**  
uv explicitly supports installing and managing Python versions (and auto-installing missing versions), and it states that because Python does not publish official distributable binaries, uv uses python-build-standalone distributions. citeturn1search0turn1search24  
uv itself is shipped as a standalone tool and is dual-licensed MIT/Apache-2.0. citeturn1search8turn9search2  

This makes uv a strong candidate for your Go CLI to orchestrate:

- download correct CPython for OS/arch  
- create venv inside a Stigmer-controlled directory  
- install pinned dependencies (ideally from a local wheelhouse)

The key design choice: **online bootstrap vs offline bundle**. Online-only bootstrap reduces releases but can be brittle behind enterprise proxies; offline wheelhouse improves UX predictability.

**python-build-standalone as a first-class distribution primitive**  
python-build-standalone produces “self-contained, highly-portable Python distributions,” meant to be downloaded/unzipped and run. citeturn1search1turn15search9  
This project is now under Astral stewardship and is widely used across the ecosystem; Astral’s own post emphasizes it underpinning Python installation workflows and highlights eliminating runtime dependencies as a goal. citeturn15search9  

A key nuance for your native-extension stack: musl-based Python builds can be incompatible with extension modules, and Astral explicitly calls that out as a limitation they want to remove. This strongly suggests you should prefer **glibc-based Linux builds** for your gRPC/Temporal wheels. citeturn15search9turn15search4  

Bottom line: python-build-standalone + “install dependencies normally” is the closest non-Docker analogue to your current container runtime. It’s also the approach uv uses and documents, which reduces your risk.

### Conda-based environment shipping: conda-pack and micromamba

**conda-pack**  
conda-pack creates archives of conda environments for installation where Python/conda may not be present. citeturn1search2turn1search10  
But conda-pack is explicitly **platform/OS-specific**; environments must match platform and OS between source and target. citeturn1search18  

**micromamba**  
micromamba is a small standalone package manager that doesn’t come with a default Python; it can be used to create environments. citeturn1search3turn1search27  

For Stigmer, conda-based approaches can work, but they tend to increase:

- artifact size (conda libs + solver metadata + non-Py deps)  
- operational complexity (conda channels, pinning, security review)  
- platform-specific build pipelines anyway

Bottom line: Conda approaches are viable if you need heavy non-Python system dependencies. Your agent-runner stack is primarily Python + native wheels, making python-build-standalone/uv the more direct fit.

### Embedding Python in the Go CLI binary

Embedding CPython is real and documented by Python itself (the official docs explicitly cover embedding the interpreter in another application). citeturn5search0turn5search4  
But for your case, “embed CPython inside the Go BusyBox binary” has major disadvantages:

- It pushes you into **CGO** and platform toolchains; cross-compilation becomes substantially harder. Go build tooling becomes “not zero effort” when CGO is involved; GoReleaser explicitly calls out CGO as tricky, especially for cross-compiling. citeturn5search39turn5search11  
- The mature Go bindings story is weak for Python 3.11+; e.g., Datadog’s go-python3 bindings were archived, and community successors often lag modern CPython versions (one successor notes “currently supports python-3.7 only”). citeturn6search0turn6search1  
- Even organizations that embed CPython (Datadog) treat it as a specialized engineering effort; it’s a proof that embedding is possible, not that it’s cheap. citeturn6search3  

A pragmatic middle ground exists: **don’t embed in-process; ship a Python distribution and spawn it as a subprocess**. Some Go libraries already implement exactly that pattern—embedding a Python distribution but executing Python in another process without CGO. citeturn6search10turn6search13  
This essentially converges back to the recommended approach (hermetic Python runtime managed by the CLI), just with different implementation details.

Bottom line: In-process embedding is high complexity with little upside versus “ship CPython + run it as a daemon.”

## MCP server runtime and sandboxing: solving the “Node/Go/Docker” dependency spiral

Your Docker image is huge largely because it is doing **two jobs**:

- provide a Python runtime + dependencies for agent-runner  
- provide toolchains/runtimes to spawn a variety of MCP servers (`npx`, `uvx`, `go run`, `docker run`)

The MCP spec makes clear that **stdio transport implies local subprocess execution**. That means local runtime availability is non-negotiable for stdio-based servers. citeturn8view0  
However, the MCP spec also defines **Streamable HTTP** transport, where the server can be “an independent process” handling multiple client connections, rather than being launched as a subprocess. citeturn8view0  
So you have a fundamental architectural option:

### Shift MCP from “local subprocess by default” to “remote or managed local servers”
If Stigmer treats MCP servers as:

- **remote HTTP endpoints** (hosted elsewhere or locally as a separate daemon), or  
- **prebuilt native binaries** (instead of scripts requiring Go/Node toolchains),

you can dramatically reduce what agent-runner needs to ship.

This is not hypothetical: vendors explicitly distribute MCP servers as standalone binaries in some cases (e.g., Apollo MCP server docs mention a standalone binary option; pgEdge describes deployment as a standalone binary under systemd or Docker). citeturn3search6turn3search23  

### A pragmatic “tiered” MCP runtime policy
A viable product strategy in 2026 is to formalize MCP server execution into tiers:

- **Tier A (works out of the box): Python MCP servers**  
  Agent-runner already ships a CPython runtime; stdio-launched Python MCP servers become easy. (This aligns with MCP ecosystem docs describing Python servers as first-class.) citeturn3search8turn3search2  

- **Tier B (auto-installed on demand): Node runtime for `npx` MCP servers**  
  Only download/install Node when user config references a Node-based server. This mirrors your Temporal “download binary on first run” pattern and keeps default installs small.

- **Tier C (user-provided or deprecated): Go toolchain for `go run` MCP servers**  
  “go run” implies the full Go toolchain; the Go toolchain footprint is substantial and creates additional supply-chain and update burden. Prefer “download prebuilt MCP server binaries” over `go run`. (This is consistent with the existence of real MCP servers shipped as binaries.) citeturn3search23turn3search6  

- **Tier D (optional isolation): Docker-based MCP servers**  
  Keep Docker as an *optional* integration for isolation, not a core runtime dependency.

### If you genuinely need sandboxing without Docker
The non-Docker sandbox landscape is fragmented:

- **gVisor** sandboxes containers by interposing between workload and the host **Linux kernel**, i.e., it’s a Linux container runtime hardening layer. citeturn4search2turn4search6  
- **Firecracker** is Linux/KVM microVM-based; it requires KVM and is Linux-centric. citeturn4search3turn4search15  
- **bubblewrap** is a Linux namespace-based sandbox builder; it is explicitly a tool for constructing sandbox environments and is Linux-specific in practice. citeturn18search1turn18search8  

On macOS and Windows, equivalents exist (VMs, OS sandboxes), but there is no single cross-platform “drop-in Docker replacement” that preserves Docker’s UX while being lightweight.

### WebAssembly as a future direction for MCP tool sandboxing
WebAssembly runtimes like Wasmtime position sandboxed execution of untrusted code as a primary goal. citeturn18search3  
There is already research (2026) explicitly motivated by MCP that uses WASM/WASI sandboxes to safely execute tools and audit external input exposure. citeturn18academia39  

Practical limitation: most MCP servers today are not delivered as WASM components, and compiling arbitrary Node/Python tooling into WASM with full syscalls is non-trivial. WASI Preview 2 improves the “component model,” but it is still an ecosystem transition. citeturn18search30turn8view0  

Bottom line: WASM is promising for the *future* of safer tool execution, but not a near-term replacement for the runtime sprawl of today’s MCP server ecosystem.

## Recommended implementation roadmap and migration plan

This roadmap assumes the recommended approach: **CLI-managed hermetic CPython runtime bundle** for agent-runner, with MCP runtime dependencies handled separately and lazily.

### Roadmap for the filesystem layout and lifecycle

**Runtime layout proposal (conceptual)**  
Install everything under a Stigmer-managed directory, versioned independently of the CLI binary, e.g.:

- `~/.stigmer/runtimes/agent-runner/<agentRunnerVersion>/<platform>/python/` (python-build-standalone extracted)  
- `~/.stigmer/runtimes/agent-runner/<agentRunnerVersion>/<platform>/venv/` (app venv)  
- `~/.stigmer/cache/wheels/<lockHash>/<platform>/` (optional offline wheelhouse)  

This is analogous to how uv manages multiple Python versions and how python-build-standalone distributions are intended to be downloaded/unpacked and executed. citeturn1search0turn1search1  

### Build pipeline design

**Pin and lock dependencies**
- Commit a lock file for the agent-runner environment. If you move from Poetry to uv, use uv’s lock + hash discipline. uv is explicitly designed for fast, deterministic dependency workflows. citeturn9search6turn1search4  

**Produce a per-platform wheelhouse**
- For each target (macOS arm64/amd64, Linux amd64/arm64, Windows amd64), build a wheelhouse containing:
  - all third-party wheels  
  - your monorepo-local wheels for `graphton` and `stigmer-stubs`  
- This leverages the main advantage of wheels: native extension packages install without compilers when wheels exist. citeturn2search17turn2search5  

**Avoid musl builds for Linux**
- Because the ecosystem still has known incompatibilities between musl-based Python distributions and binary extension modules, prefer glibc-based distributions for agent-runner. citeturn15search9turn15search4  

**Fix `deepagents-cli` namespace collision during build**
- Treat this as an environment construction step, not a runtime hack:
  - install dependencies in a controlled order  
  - apply the known `deepagents` repair step (or, ideally, fork/patch upstream packaging so the collision cannot occur)
- Even if you later adopt a zipapp (shiv/PEX), shiv exposes a “preamble” mechanism to run sanity/cleanup code during bootstrap, which illustrates a general pattern: controlled pre-run fixups can be part of the artifact. citeturn17view0  

### Go CLI integration

**Bootstrap logic (first run)**
1. Detect OS/arch and desired agent-runner version.
2. Download the python-build-standalone distribution (or ship it as a sidecar artifact) and extract. uv explicitly uses python-build-standalone because CPython doesn’t publish official distributable binaries. citeturn1search0turn15search9  
3. Create a venv using the extracted python (or equivalent) and install dependencies from the wheelhouse.
4. Start the agent-runner process as a daemon with PID management like your Go components.

**Steady-state**
- Subsequent starts are “just run python,” with no Docker and minimal overhead.

### Migration plan from Docker

A safe migration minimizes user-impact risk:

**Phase one: dual-path execution**
- Keep Docker-based runner available behind a config flag (or automatic fallback) while introducing native runner.
- Default to native runner for macOS arm64 (primary), but fall back to Docker if environment bootstrap fails or if user explicitly requests.

**Phase two: decouple MCP runtime dependencies**
- Ship only Python runtime + deps in the core agent-runner bundle.  
- Add “runtime managers” for Node/Docker/Go, installing on demand based on configured MCP servers.  
- Prefer MCP Streamable HTTP servers or prebuilt binaries where possible, because the MCP spec supports this transport and it reduces local runtime coupling. citeturn8view0turn3search23  

**Phase three: remove Docker from core path**
- Keep Docker integration only as an optional MCP isolation backend or legacy compatibility.

## Risk assessment and fallback strategy

### Key risks of the recommended approach

**Platform-native wheel gaps and glibc compatibility**
- If any dependency lacks wheels for Linux arm64 or macOS variants, you’ll fall back to source builds (requiring compilers) unless you build wheels yourselves. gRPC tooling docs explicitly warn that wheel coverage may not include every system and that building from source may require extra tooling like Cython. citeturn2search13turn2search37  

Mitigation: maintain your own wheel build pipeline for the small set of packages that ever fall back to sdist.

**Supply-chain and security posture of “downloaded runtimes”**
- The CLI becomes a runtime installer/downloader. This demands signature verification and careful caching. (This is not unique—Docker Desktop itself is a large dependency with licensing and VM semantics; you’re trading one supply-chain for another.) citeturn4search0turn4search1  

Mitigation: publish checksums/signatures, enforce hash pinning (lockfile hashes), and validate on install.

**macOS code signing/quarantine edge cases**
- Downloaded binaries may behave differently than Homebrew-installed ones depending on quarantine attributes. This is operational, not conceptual.

Mitigation: distribute runtime artifacts through trusted channels and ensure consistent file permissions; offer a “diagnostics” command to print runtime paths and environment integrity.

**`deepagents-cli` collision remains a long-term maintenance hazard**
- If upstream continues shipping conflicting namespace layouts, every packaging approach must address it (including Docker, if you ever move away from pip-based installs inside the container).

Mitigation: fork or vendor with a patched namespace; treat upstream fix as a product reliability task.

### Fallback strategy if the recommended approach fails

If the hermetic runtime bundle runs into unexpected blockers on a subset of platforms:

1. **Fallback A: uv bootstrap without offline wheelhouse**  
   This reduces artifact building pressures and leans on uv’s runtime Python install behavior. citeturn1search0turn1search24  

2. **Fallback B: PEX/SCIE-style executable packaging**  
   Still CPython semantics, still normal imports, but potentially improved UX via “single artifact.” citeturn0search20turn0search4  

3. **Fallback C: retain Docker for “MCP isolation mode only”**  
   Keep Docker as an optional sandbox backend while agent-runner remains native; this addresses your users’ primary pain (Docker Desktop warnings + prerequisite) for the core product, while still allowing advanced users to run containerized MCP servers.

### What not to rely on as fallback

- **GraalPy** as a drop-in runtime for agent-runner is not aligned with Temporal Python SDK realities; Temporal support statements and GraalPy’s own native-extension limitations make this a high-risk “rewrite the world” option. citeturn2search4turn5search6  
- **Linux-only sandbox tech** (gVisor, Firecracker, bubblewrap) will not solve macOS-first UX. citeturn4search2turn4search3turn18search1
