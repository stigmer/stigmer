# Deep Research: Eliminating Docker Dependency for Python Agent-Runner — Native Binary/Process Distribution

## Research Objective

We need a comprehensive analysis of all viable approaches to distribute and run a **complex Python service as a native process** on macOS, Linux, and Windows — eliminating the current Docker container dependency. The goal is to make the Python agent-runner start as a daemon process (similar to how our Go-based components run), so users never see Docker-related warnings or need Docker installed.

## Context & Background

### What We're Building

**Stigmer** is a developer tool (CLI + local backend) that runs AI agents. The architecture has three daemon components managed by a Go CLI:

1. **stigmer-server** (Go) — gRPC API server. Runs as a native binary/daemon. ✅
2. **workflow-runner** (Go) — Temporal worker. Runs as a native binary/daemon. ✅
3. **agent-runner** (Python) — Temporal worker that executes AI agents using LangGraph. **Currently runs in Docker.** ❌

The Go components use a "BusyBox pattern" — the CLI binary itself contains the server and workflow-runner code, spawned via hidden subcommands (`stigmer internal-server`, `stigmer internal-workflow-runner`). They start as native OS processes with PID files, just like any system daemon.

### Why We Moved to Docker (January 2026)

We originally tried **PyInstaller** to package agent-runner as a standalone binary. After **7+ hours of debugging**, we abandoned it because:

- The `multipart` package uses **dynamic imports** that PyInstaller's static analysis cannot detect
- Even with hidden imports, runtime hooks, and sys.path hacks, multipart failed at runtime
- Builds succeeded but execution crashed with `ModuleNotFoundError: No module named 'multipart'`
- The `deepagents` package has a **namespace collision** with `deepagents-cli` that corrupts imports

Docker solved all of these problems by providing a real Python runtime with all packages installed normally.

### Why Docker Is Now a Problem

1. **Alarming UX**: When the Docker container mounts `$HOME:$HOME` (needed for local workspace paths), Docker Desktop shows: *"You have opted to share your home directory with a container. This can affect your system performance."* — This is scary for users who just downloaded our product.

2. **Docker as a prerequisite**: Users must install Docker Desktop (which itself requires a license for companies >250 employees), adding friction to onboarding.

3. **2GB image size**: The Docker image is ~2GB due to bundled runtimes (Node.js, Go, Docker CLI, uv/uvx for MCP server support).

4. **Architectural mismatch**: Two Go components run as simple daemon processes; one Python component requires a full container runtime. This asymmetry creates complexity in lifecycle management, log aggregation, health monitoring, and debugging.

5. **macOS Docker Desktop overhead**: Docker Desktop on macOS runs a Linux VM, consuming significant memory (~2-4GB) even when idle.

### What We Want

**Ideal end state**: `stigmer server start` spawns all three components as native OS processes. No Docker required for the core product. Agent-runner runs as a process with a PID file, just like workflow-runner.

### Key Characteristics

- **Native extensions**: `temporalio` uses Rust via pyo3, `grpcio` has C extensions — these are platform-specific compiled code.
- **Dynamic imports**: `multipart` package (transitive dependency) and `deepagents` use patterns that break static analysis tools.
- **Namespace collision**: `deepagents-cli` writes files into the `deepagents/` namespace directory, corrupting the clean `deepagents` package. Requires post-install `pip install --force-reinstall --no-deps deepagents==0.4.0` to fix.
- **Local library dependencies**: Two monorepo-local packages (`graphton`, `stigmer-stubs`) are referenced by relative path.
- **MCP server spawning**: At runtime, agent-runner spawns MCP (Model Context Protocol) servers as STDIO subprocesses. These servers can be: `npx` (Node.js), `uvx` (Python), `go run` (Go), or `docker run` (containers). This is why the Docker image includes Node.js, Go, Docker CLI, and uv/uvx.

### Entry Point

Simple: `python main.py` — starts a Temporal worker that listens for agent execution tasks.

### Target Platforms

- **macOS** (arm64, amd64) — Primary platform, most users are on Mac
- **Linux** (amd64, arm64) — Servers and CI
- **Windows** (amd64) — Future, lower priority

## Research Questions

### 1. PyInstaller (Revisited)

PyInstaller has been updated significantly since early 2026. Research:

- Has PyInstaller v6.x resolved dynamic import detection? Specifically for packages like `multipart` that use `importlib` at runtime.
- Are there new mechanisms (e.g., improved hooks ecosystem, better `collect_all`, `collect_submodules`) that handle our failure modes?
- How does PyInstaller handle packages with Rust extensions (pyo3) like `temporalio`?
- How does PyInstaller handle the `deepagents`/`deepagents-cli` namespace collision?
- What is the current state of cross-compilation (build on macOS for Linux)?
- What are the resulting binary sizes for complex ML/AI Python stacks?
- Are there known success stories of PyInstaller packaging LangChain/LangGraph applications?

### 2. Nuitka (Python to C Compiler)

- How does Nuitka handle dynamic imports compared to PyInstaller?
- Does Nuitka's compilation approach avoid the `ModuleNotFoundError` issues we hit?
- How does it handle native extensions (Rust via pyo3, C extensions)?
- What is the compilation time for a project of our dependency size?
- Cross-compilation support (build on macOS for Linux)?
- Resulting binary size and startup time?
- Licensing implications (MIT vs commercial)?

### 3. cx_Freeze

- How does cx_Freeze compare to PyInstaller for dynamic imports?
- Cross-platform support status in 2026?
- How does it handle namespace package collisions?

### 4. Shiv / PEX (Python Zip Applications)

- Can Shiv or PEX create self-contained Python applications that include all dependencies?
- Do they require a system Python installation on the target machine, or can they bundle the interpreter?
- How do they handle native extensions (compiled .so/.dylib files)?
- Would this solve the dynamic import problem (since it's a real Python environment, not a frozen one)?
- How does `uv` relate to this approach? Can `uv tool` package and distribute Python apps?

### 5. Embedded Python in Go Binary

Since our CLI is Go, could we embed a Python interpreter?

- **cgo + CPython embedding**: What is the state of embedding CPython in Go via cgo? How complex is it?
- **go-python3**: Are there mature Go bindings for Python 3.11+?
- **GraalPy / GraalVM polyglot**: Can GraalPy run our Python code with native extensions? What about Rust pyo3 extensions?
- How would this interact with packages that have C/Rust native extensions?
- What are the binary size implications?

### 6. `uv`-based Self-Contained Distribution

`uv` (by Astral) can install Python interpreters and manage virtual environments:

- Can `uv` install a specific Python version + all dependencies into a self-contained directory?
- Could we ship a "bootstrap" script that runs `uv python install 3.11` + `uv pip install` on first run?
- This would be similar to how we manage Temporal (download binary on first run).
- How reliable is `uv`'s Python installation across macOS/Linux/Windows?
- Could this be integrated into the Go CLI (CLI downloads uv, uv sets up Python environment)?
- Does this approach handle native extensions correctly across platforms?

### 7. Conda-Pack / Micromamba

- Can conda-pack create relocatable conda environments that include the Python interpreter?
- How does this work with pip-only packages (e.g., packages not on conda-forge)?
- Cross-platform distribution: can you package on macOS and run on Linux?

### 8. Python Standalone Builds (python-build-standalone / Gregory Szorc)

- The `python-build-standalone` project provides relocatable Python builds. Can these be bundled with our app?
- How do these interact with pip-installed packages that have native extensions?
- Could we bundle python-build-standalone + a pre-built venv as a distributable artifact?

### 9. The MCP Server Runtime Problem

Beyond packaging Python itself, we need Node.js, Go, and Docker CLI in the runtime for MCP server spawning. Research:

- Could MCP servers be required to be installed separately by the user (shift the dependency)?
- Could we lazy-install runtimes (install Node.js only when a Node-based MCP server is first configured)?
- Are there universal MCP server runners that don't require multiple runtimes?
- Could we use WebAssembly (WASM) to sandbox MCP servers without Docker?

### 10. Hybrid Approaches

- **Docker only for MCP sandbox, not for agent-runner**: Keep agent-runner as native process, only use Docker for MCP server isolation if needed.
- **Process isolation without Docker**: Are there lightweight process isolation tools (Firecracker, gVisor, Bubblewrap) that could replace Docker for the sandbox use case?

## Evaluation Criteria

For each approach, please evaluate:

| Criterion | Description |
|-----------|-------------|
| **Feasibility** | Can this actually work with our dependency stack (pyo3 Rust extensions, dynamic imports, namespace collisions)? |
| **User Experience** | Does the user need to install anything? Is it zero-config? |
| **Binary/Package Size** | What is the distributable size? (Current Docker image: ~2GB, target: <200MB) |
| **Startup Time** | Cold start time? (Current Docker: ~3s, target: <1s) |
| **Cross-Platform** | macOS (arm64, amd64), Linux (amd64, arm64), Windows? |
| **Build Complexity** | How complex is the CI/CD pipeline? Cross-compilation? |
| **Maintenance Burden** | Ongoing effort to keep the packaging working as dependencies change? |
| **Runtime Debugging** | Can developers inspect/debug issues easily? |
| **MCP Server Support** | Does this approach support spawning Node.js/Go/Python MCP servers? |

## Known Constraints

- The Go CLI is the distribution mechanism (installed via `brew install stigmer`). Any Python packaging must integrate into or be managed by the Go CLI.
- We cannot require users to install Python manually. The solution must be self-contained or auto-bootstrapping.
- Native extensions (Rust pyo3 in temporalio, C in grpcio) mean pure-Python solutions won't work — we need platform-specific compiled code.
- The `deepagents-cli` namespace collision is a hard constraint that any packaging solution must handle.
- We ship for macOS (arm64 primary, amd64) and Linux (amd64, arm64). Windows is future.
