## Decisions Made

- **Extend `ProvisionResult` instead of creating `EntryProvisionResult`**: The original plan proposed a separate dataclass, but this would duplicate all fields. Adding `entry_name: str = ""` at the end of the existing frozen dataclass is DRY, backward-compatible, and follows the principle of not introducing unnecessary types.
- **`entry_name` at end of dataclass with default**: Existing construction sites (in `empty.py`, `local_path.py`, `git.py`, tests) use keyword arguments, so adding a new defaulted field at the end is safe. Avoids positional argument breakage.
- **`dataclasses.replace()` for stamping `entry_name`**: Respects the frozen invariant. The entry name comes from the `WorkspaceEntry` proto, not the source handler, so it's stamped after provisioning.
- **Duck-typing for `WorkspaceEntry` protos**: `provision_all()` accepts `Sequence[object]` and accesses `.name` and `.source` via duck-typing with `# type: ignore[attr-defined]`. Avoids importing generated proto stubs into the domain layer.
- **Single-entry format preserved exactly**: When `len(provision_results) == 1`, the output is identical to the pre-change format. No regressions for existing single-workspace sessions.
- **File tree heading adjustment**: In multi-entry mode, `### Project Structure` is replaced with `#### Project Structure` to avoid conflicting with per-entry `###` headings. Tested via line-level assertion to handle substring matching (`"###"` is a substring of `"####"`).
- **Primary workspace for relevance and file refs**: Both `build_relevance_prompt_section` and `build_referenced_files_prompt_section` use `provision_results[0].root_dir` — acknowledged MVP limitation.

## Learnings

- When adding fields to a frozen dataclass, placement matters. Fields with defaults must come after fields without defaults. Adding at the end with a default is the safest strategy.
- `"### Project Structure"` is a substring of `"#### Project Structure"` (starting at index 1). String containment checks for Markdown heading levels need to be line-boundary-aware, not simple `in` checks.
- The `provision_all()` pattern of iterating entries and delegating to the per-source `provision()` method is clean enough that Phase 4 (git repos) should require zero changes to `provision_all()` itself — only the git source handler needs multi-repo awareness.
