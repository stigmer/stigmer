## Decisions Made

- **No "Apply" button (DD-R12)**: EnvVarForm already has its own "Save"/"Use once" submit button. Tool selection changes are local state with no API call. Batch "Apply" would fight EnvVarForm's component contract and add complexity for zero benefit. UX justification: Nielsen #7 — two immediate actions are faster than one batched action.
- **Decomposed props (DD-R13)**: Component accepts flat, decomposed props rather than `McpServerSetupEntry`. The `credentials?` sub-object controls whether the credentials form is shown — no status string inspection needed. Platform builders can use any state management, not just our reducer.
- **Tool selector disabled during setup (DD-R14)**: Progressive disclosure — complete step 1 (credentials) before step 2 (tools). Tools are still visible as a preview of what the server provides.
- **`SUBMIT_FAIL` action (DD-R11)**: On credential submission failure, transitions `submitting → needsSetup` with error preserved. Enables retry. The hook's catch block uses `SUBMIT_FAIL` instead of `SET_ERROR`.
- **`submitting` carries `missingVariables` (DD-R10)**: Required so the credentials form stays visible (disabled/loading) during submission instead of flash-unmounting.

## Learnings

- The `submitting` phase variant was designed without considering that the UI needs the `missingVariables` data to keep the form visible during async operations. This is a general pattern worth remembering: transient states should carry forward the data the UI needs from the previous state, even if the reducer doesn't "use" it for logic.
- The master plan's "Apply" button wireframe conflicted with EnvVarForm's existing component contract. When composing existing components, the composition should respect each child's interaction model rather than fighting it.
- `EnvVarForm` hardcodes `w-72` which is fine for standalone use but needs overriding in panel composition. `tailwind-merge` via `cn()` handles this cleanly.
