## Decisions Made

### DD-R1: Merge `ready` and `ready-default` into single `ready` status
- **Rationale**: Fewer union variants, simpler pattern matching for consumers, one code path in `toUsageInputs()`. The UI derives "using defaults?" by comparing `enabledTools` against `discoveredTools`.

### DD-R2: Remove `configuring` from the reducer
- **Rationale**: This is UI navigation state (which server's config panel is open), not data state. The agent pattern has no "user opened the form" status. McpServerPicker manages drill-in navigation via local `useState`.

### DD-R3: Add `submitting` status
- **Rationale**: The master plan omitted this, but `EnvVarForm` accepts `isSubmitting` prop. Without a `submitting` phase, there's no way to show a loading spinner during credential save. Matches `agentSetupReducer`.

### DD-R4: Error orthogonal to phase
- **Rationale**: Making `error` a separate status (as in the master plan) loses phase context — if submission fails, the form state is gone. The `agentSetupReducer` pattern (`phase & { error: Error | null }`) preserves context for inline error display and retry.

### Additional decisions:
- `Record<string, Entry>` over `Map` — idiomatic React spreading, easier serialization
- `McpServerUsageInput` NOT stored in reducer state — derived by hook in `toUsageInputs()` (derive, don't store)
- Full `McpServer` protobuf message carried in entry state — pragmatic, avoids re-fetch for config panel
- `discoveredTools` and `toolApprovals` pre-extracted alongside `mcpServer` — convenience and null safety over raw protobuf path traversal

## Learnings

- The `agentSetupReducer` pattern (error orthogonal to phase, guard transitions, readonly fields) translates well to a multi-entry map-based reducer. The main structural difference is the `Record<string, Entry>` wrapping.
- The master plan's state model had 6 statuses; the refined reducer has 4. Simpler is better when the removed distinctions can be derived from data or belong in the UI layer.
