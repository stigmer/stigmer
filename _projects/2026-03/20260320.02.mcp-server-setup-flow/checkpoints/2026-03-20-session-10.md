## Design Decisions

### DD-T03.10: Submit Context for runtimeEnv Aggregation

**Problem**: SessionComposer owns all three runtimeEnv sources (agent one-time, MCP one-time, manual secrets), but it fires `onSubmit(message, modelId)` — the consumer creates executions and needs the merged runtimeEnv. MCP `pendingRuntimeEnv` was trapped inside SessionComposer with no way for the consumer to access it.

**Options evaluated**:
1. Expand `onSubmit` with a context parameter (recommended)
2. Add a new callback `onMcpPendingRuntimeEnvChange` (rejected — consumer must merge 3 sources manually)
3. Other patterns (ref, render callback, external hook — all more complex)

**Decision**: Expand `onSubmit` to `(message, modelName?, context?) => void` where context carries the merged `runtimeEnv`.

**Rationale**:
- **Architect**: SessionComposer is the aggregate that owns all setup flows — it should aggregate what it owns. Pushing merge logic to the consumer violates cohesion.
- **UX Designer**: SDK APIs are user interfaces. One merged object at submit time is strictly better DX than three separate reactive streams that the consumer must track and merge.
- **Web UX/UI**: The three-branch `switch` on `resolution.mode` in SessionLauncher collapsed to a two-branch `if`. Consumer code got simpler.
- **Backward compatible**: Adding an optional third parameter is non-breaking. Existing `(message, model) => void` handlers ignore it.

**Merge order** (last-write-wins): Agent → MCP → Manual secrets. Manual wins because the user explicitly typed them.
