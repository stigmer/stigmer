## Decisions Made

### DD-R5: `entries` as `Record`, not `Map`
- **Rationale**: Reducer already produces `Record<string, Entry>`. Wrapping in Map adds conversion cost and breaks useMemo stability (new Map instance every render).

### DD-R6: `usageInputs` as derived `useMemo` value, not `toUsageInputs()` function
- **Rationale**: Pure derivation from entries — `useMemo` is more React-idiomatic, always current, referentially stable, no stale closure risk.

### DD-R7: `pendingRuntimeEnv` via flat `useRef` accumulation
- **Rationale**: Keeps runtime env values out of reducer state (stays pure) and out of React state (no unnecessary re-renders). Consumed imperatively at session creation time. On `removeServer`, not cleaned per-server — env var keys are shared across servers and extra keys are harmless.

### DD-R8: Error handling — dispatch `SET_ERROR` without re-throwing
- **Rationale**: Unlike `useAgentSetup` (re-throws for imperative callers), multi-server orchestration benefits from reactive error reading via `entries[key].error`. Multiple servers may error independently — re-throw would surface only one.

### DD-R9: `clearError(ref)` per-server
- **Rationale**: Agent flow has global `clearError()` (single agent). Multi-server needs per-entry error clearing.

### Additional decisions:
- `computeDefaultEnabledTools` helper: uses `spec.defaultEnabledTools` if non-empty, otherwise all discovered tool names
- `usageInputs` derivation: when enabledTools matches all discovered tools, passes `undefined` (API convention for "all tools"); org/slug parsed from server key (inverse of `toServerKey`)
- `allReady` is vacuously true when no entries exist (empty = nothing blocking)
- `needsSetupCount` counts only `needsSetup` entries (not `loading` or `submitting`)
- Known edge case accepted: personal environment loading race (same as `useAgentSetup.resolveAgent`)

## Learnings

- The multi-server hook is structurally simpler than `useAgentSetup` because there's no AgentInstance concept — MCP servers share the personal environment directly for secrets. No instance creation, no instance lookup.
- The "swallow error + dispatch" pattern (DD-R8) is cleaner for multi-entry hooks than the "dispatch + re-throw" pattern used in single-entry hooks. Callers read entries reactively rather than using try-catch.
- Deriving `usageInputs` via `useMemo` with a for-loop and `Object.entries` is cleaner than `.filter().map()` chains because TypeScript narrows the entry type inside the `if (status !== "ready") continue` guard.
