## Decisions Made

### DD-T03.1: Always-on setup mode (not opt-in)

When `showMcp` is true, the setup flow is always active. No new prop to enable/disable.

**Rationale**: The setup flow is strictly better UX — catches missing credentials proactively. Platform builders who want simple toggle can use `McpServerPicker` directly.

### DD-T03.2: Popover close does NOT reset entries

Unlike agent popover (resets on close), MCP entries persist across popover open/close cycles.

**Rationale**: MCP is multi-select. Each entry represents an independent committed selection. Resetting on close would discard credential work.

### DD-T03.3: useEffect sync for `usageInputs` to consumer

Hook's `usageInputs` pushed to consumer via `onMcpServerUsagesChange` through a `useEffect`, not imperative handlers.

**Rationale**: MCP `usageInputs` is derived from all entries and changes asynchronously. Agent uses imperative push (single-select, result available immediately). MCP requires reactive derivation.

## Learnings

- The `useEffect` sync pattern is the right approach for multi-entry derived state propagation. Agent's imperative push works for single-select but doesn't generalize to N-entry flows where the derived output changes asynchronously.
- `mcpServerUsages` prop becoming output-only is a clean behavioral shift — the prop interface stays the same but the data flow inverts (hook → consumer instead of consumer → picker).
- No React rules-of-hooks issues because `showMcp` is computed before the hook call and the hook handles `null` org as a no-op.
