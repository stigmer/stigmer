## Decisions Made

1. **Full identity override** over dual-identity: Follows Kubernetes Impersonate-User, AWS STS AssumeRole, and Microsoft OBO industry standards. The effective caller becomes the target user entirely -- no split between "auth identity" and "owner identity." `RequestCallerIdentity` stays clean with no new fields.

2. **FGA-based impersonation gate**: Defined `can_impersonate: operator` on the `platform` FGA type. Only principals with `can_impersonate` permission can use the `x-on-behalf-of` header. Machine account inherits this through its existing `operator` tuple -- no new migration needed.

3. **Silent rejection**: When an unauthorized caller or non-machine-account sends `x-on-behalf-of`, the header is silently discarded. No error response, no information leakage about the feature's existence.

4. **Sequential provisioning assumption validated**: User confirmed that the identity account provisioning flow completes (granting platform-level FGA permissions) before on-behalf-of operations run. This means a newly provisioned user will always pass authorization when resources are created on their behalf.

5. **`@Lazy` injection for circular dependency avoidance**: `OnBehalfOfAuthorizationGuard` uses `@Lazy IamPolicyGrpcRepo` to prevent circular dependency during Spring bean initialization, mirroring the established pattern from `RequestAuthorizationService`.

## Key Code Changes

### New Files (stigmer-cloud)

- **`OnBehalfOfMetadata.java`** (api-authentication): Constants class holding `Metadata.Key<String> ON_BEHALF_OF_KEY` for `x-on-behalf-of`. Shared by client and server interceptors.

- **`OnBehalfOfClientInterceptor.java`** (api-authentication): `ClientInterceptor` that attaches `x-on-behalf-of: identityAccountId` to outgoing gRPC metadata. One instance per target user, not Spring-managed.

- **`ImpersonatedChannelFactory.java`** (api-authentication): Spring `@Component` with `forIdentity(String identityAccountId)` method. Wraps `inProcessChannelAsSystem` with `OnBehalfOfClientInterceptor`. Resulting channel stack: machine account token injection + on-behalf-of header.

- **`OnBehalfOfAuthorizationGuard.java`** (api-authorization): Spring `@Component` that checks FGA tuple `identity_account:<callerId> can_impersonate platform:stigmer`. Fails closed -- returns `false` on exception.

- **`OrganizationGrpcRepo.java` + `OrganizationGrpcRepoImpl.java`** (stigmer-service/downstream): New downstream repo with `createAsSystem()` and `createOnBehalfOf()` methods.

### Modified Files (stigmer-cloud)

- **`platform.fga`**: Added `can_impersonate: operator` permission under new "IMPERSONATION" section.

- **`GrpcRequestContextBuilderInterceptor.java`**: Removed `@RequiredArgsConstructor`, added explicit constructor with `@Lazy OnBehalfOfAuthorizationGuard`. Added `applyOnBehalfOfOverride()` method that reads `x-on-behalf-of` header, validates machine account + FGA permission, and rebuilds `RequestCallerIdentity` with full override.

- **`AgentInstanceGrpcRepo.java` + `AgentInstanceGrpcRepoImpl.java`**: Added `createOnBehalfOf(AgentInstance, String)` interface method and implementation using `ImpersonatedChannelFactory`.

- **`ExecutionContextGrpcRepo.java` + `ExecutionContextGrpcRepoImpl.java`**: Same pattern for execution contexts.

## Learnings

- The `grpc-request` BUILD.bazel already depends on both `api-authentication` and `api-authorization`, so no dependency changes were needed for the interceptor modifications.
- Machine account is bootstrapped as `platform:stigmer#operator` via `U20250102_InsertBootstrapIdentityAccounts` migration, which means defining `can_impersonate: operator` automatically grants it impersonation rights with zero migration work.
- The in-process FGA call from the interceptor does NOT carry `x-on-behalf-of` header, naturally preventing infinite recursion.
