## Decisions Made

1. **Extend in place, not new hooks**: Adding `getOrCreate`, `addVariables`, `removeVariables`, `isMutating` to existing return types is backward compatible. Avoids duplicate "personal" exports in the SDK.

2. **SDK client directly for mutations, Layer 1 hooks for reading**: The plan said "composes Layer 1 hooks" but composing multiple React mutation hooks creates confusing multi-state (two independent `isLoading`, two independent `error`). Using `useStigmer()` directly for mutations provides unified `isMutating` / `error` state. Layer 1 data hook (`useEnvironmentList`) still used for reading.

3. **`useRef` for stable environment/instance reference**: Mutation callbacks (`getOrCreate`, `addVariables`, `removeVariables`) access the current environment/instance via `useRef` so they don't recreate on every list query response. This avoids unnecessary re-renders for consumers that destructure mutation functions.

4. **Unified error state**: `error = mutationError ?? listError`. Mutation errors take precedence (more actionable). Both are surfaced through the same field — consumers don't need to check two separate error states.

5. **`getOrCreate` with optional `initialData`**: Saves a round-trip for first-time users (create with data in one call vs. create empty + addVariables).

6. **`agentSlug` as `getOrCreate` param, not hook param**: The hook fetches by `agentId` (stable server ID). The slug is only needed at creation time for the naming convention. Avoids requiring both `agentId` AND `agentSlug` at hook initialization.

## Learnings

- Composing React mutation hooks at the orchestration layer is impractical — unified state management via `useStigmer()` is cleaner than juggling multiple independent loading/error states from composed hooks.
- `useRef` for "latest value without triggering callback recreation" is the right pattern for orchestration hooks that have both declarative reading (auto-refresh) and imperative mutations (user-triggered).
