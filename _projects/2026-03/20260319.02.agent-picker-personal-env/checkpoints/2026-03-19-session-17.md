## Decisions Made

- **Two orthogonal dimensions**: Secret delivery flow (Environment vs Execution) and orchestration level (Layer 1 vs Layer 2) are independent — any user can use any combination
- **`runtimeEnv` on `CreateAgentExecutionInput`**: Directly passes through to the TypeScript SDK's `AgentExecutionInput.runtimeEnv`, which already converts to the proto `ExecutionValue` map
- **`runtimeEnv` on `SendFollowUpOptions`**: Forwarded to `useCreateAgentExecution.create()` so conversation-based UIs can inject per-execution secrets
- **No Layer 2 for Execution Flow**: Passing `runtimeEnv` at call time doesn't require multi-step orchestration, so no orchestration hook is needed — Layer 1 is sufficient
- **Standalone environment components (from Session 16) confirmed as Environment Flow coverage**: `EnvironmentVariableEditor`, `EnvironmentListPanel`, `CreateEnvironmentForm` complete the Environment Flow's UI surface

## Learnings

- The original "two profiles" framing was a conflation of two independent concerns — recognizing orthogonality led to a cleaner architecture model
- `runtimeEnv` was fully wired through proto -> TypeScript SDK -> Go/Java backend but had a single gap: the React SDK hooks didn't expose it
- The Execution Flow doesn't need a Layer 2 orchestration hook — it's inherently simple (pass secrets at call time), unlike the Environment Flow which requires multi-step provisioning
