## Decisions Made
- **Split output strategy**: AI content stays on stdout (direct write), status on stderr through Bubbletea. `tea.Println` is line-based (`\r\n` appended), so it cannot support token-by-token AI streaming.
- **tea.WithInput(nil)**: Bubbletea does not own stdin. The existing approval flow reads raw terminal input directly; moving it into Bubbletea's event-driven Update cycle is deferred to Phase 4.
- **inApprovalFlow sentinel**: During approval, `statusf()` bypasses `program.Println()` and writes directly to stderr. This avoids races between Bubbletea's 60fps async renderer and the time-sensitive approval UI which uses `termctl.EraseLines` for cursor manipulation.
- **Nil program = fallback**: When `cfg.program` is nil (tests, CI, piped output), `statusf()` does a direct `fmt.Fprint` -- existing tests pass unchanged without any modification.

## Learnings
- Bubbletea v1.2.4 `Program.Println` queues lines in `queuedMessageLines` and flushes them on the next renderer tick (60fps). This means output through Println is not synchronous -- critical for understanding why approval writes must bypass it.
- `tea.WithInput(nil)` works cleanly: the program simply never reads from stdin.
- The existing two-lane output design (dataW=stdout, statusW=stderr) maps naturally to the Bubbletea boundary.

## Open Questions

- Phase 4 complexity: Moving `handleApproval` (blocking, raw terminal reads) into Bubbletea's async `Update` cycle will be the most complex phase. May need a dedicated planning session.
