# Task T01: Usage Metrics, Cost Tracking & Usage Optimization — Full Design

**Created**: 2026-03-13
**Status**: PENDING REVIEW
**Type**: Feature Development

> **This plan requires your review before execution.**

---

## Context & Motivation

Today, `UsageMetrics` captures **volume** (how many tokens, how many LLM calls, which model) but has **zero cost/financial data**. You can say "this execution consumed 50K tokens" but you can never answer "this execution cost $0.37." There is also no visibility into whether prompt caching is happening, what the cache hit rate is, or how much money caching is saving. On the optimization side, the only cost-reduction mechanism today is context summarization; techniques like prompt caching, tool result truncation, and model routing — which platforms like Cursor use aggressively — are entirely absent.

This project addresses both sides:
1. **Measurement**: Enrich the data model so every execution carries accurate, self-contained cost data with cache token differentiation.
2. **Optimization**: Implement runtime techniques that reduce actual token consumption and cost.
3. **Visibility**: Build CLI-level usage reports and the RPCs to power them, so users can see cost at execution, session, agent, and org levels.

## Part 1: Usage Metrics Enrichment (Schema + Runtime)

### 1.1 — Cache Token Differentiation

**Problem**: The current `UsageMetrics` has a single `prompt_tokens` field that lumps together tokens costing $3/MTok with tokens costing $0.30/MTok (Anthropic cache reads). This makes any cost calculation fundamentally wrong.

**What providers actually return**:

| Token Bucket | Anthropic Field | OpenAI Field | Price Impact |
|---|---|---|---|
| Regular input | `input_tokens` | `prompt_tokens - cached_tokens` | Full price |
| Cache write | `cache_creation_input_tokens` | N/A (automatic) | 1.25x (Anthropic) |
| Cache read | `cache_read_input_tokens` | `prompt_tokens_details.cached_tokens` | 0.1x (Anthro) / 0.5x (OpenAI) |
| Output | `output_tokens` | `completion_tokens` | 3-5x input price |

**Schema change — `UsageMetrics` (api.proto)**:

Add cache-aware token fields alongside the existing ones (backward compatible):

```protobuf
message UsageMetrics {
  // --- Existing fields (unchanged) ---
  int32 prompt_tokens = 1;
  int32 completion_tokens = 2;
  int32 total_tokens = 3;
  int32 llm_call_count = 4;
  string primary_model = 5;

  // --- New: Cache token differentiation ---
  // Tokens written to provider prompt cache.
  // Anthropic: cache_creation_input_tokens (billed at 1.25x input rate)
  // OpenAI: N/A (caching is automatic, no separate write metric)
  // Zero if prompt caching is not active or not supported by provider.
  int32 cache_creation_tokens = 6;

  // Tokens read from provider prompt cache (cache hits).
  // Anthropic: cache_read_input_tokens (billed at 0.1x input rate)
  // OpenAI: prompt_tokens_details.cached_tokens (billed at 0.5x input rate)
  // Zero if no cache hits occurred.
  int32 cache_read_tokens = 7;

  // --- New: Per-model breakdown ---
  // Breakdown of token usage and cost per model.
  // Enables accurate cost calculation when multiple models are used
  // (e.g., main model + summarization model, or sub-agents on different models).
  repeated ModelUsage model_breakdown = 8;

  // --- New: Computed cost ---
  // Total estimated cost in USD for this execution context.
  // Computed at execution time using the pricing rates in effect.
  // Sum of all model_breakdown[].estimated_cost_usd.
  // Captured at write time because pricing changes over time — storing
  // the computed cost makes historical data self-contained.
  double estimated_cost_usd = 9;
}
```

### 1.2 — Per-Model Usage Breakdown

**Problem**: `primary_model` is a single string. In practice, the main agent might use `claude-sonnet-4`, summarization uses `claude-haiku-4`, and a sub-agent could use `gpt-4o`. There is no way to apply different rates to different models within one execution.

**New message — `ModelUsage`**:

```protobuf
message ModelUsage {
  // Model identifier as returned by the provider.
  // Example: "claude-sonnet-4-20250514", "gpt-4o-2024-08-06"
  string model = 1;

  // Provider identifier. Determines which pricing table to use.
  // Examples: "anthropic", "openai", "google", "ollama", "aws-bedrock"
  string provider = 2;

  // Regular input tokens (non-cached).
  int32 input_tokens = 3;

  // Output tokens generated by the model.
  int32 output_tokens = 4;

  // Tokens written to prompt cache during this execution.
  int32 cache_creation_tokens = 5;

  // Tokens read from prompt cache (cache hits).
  int32 cache_read_tokens = 6;

  // Number of LLM API calls made with this model.
  int32 call_count = 7;

  // --- Pricing rates at execution time ---
  // Captured at execution time so historical data remains accurate
  // even when provider pricing changes.

  // Input token price per million tokens (USD) at execution time.
  double input_price_per_million = 8;

  // Output token price per million tokens (USD) at execution time.
  double output_price_per_million = 9;

  // Cache write token price per million tokens (USD) at execution time.
  // Anthropic: 1.25x of input_price. OpenAI: same as input.
  double cache_creation_price_per_million = 10;

  // Cache read token price per million tokens (USD) at execution time.
  // Anthropic: 0.1x of input_price. OpenAI: 0.5x of input_price.
  double cache_read_price_per_million = 11;

  // Computed cost in USD for this model's usage in this execution.
  // = (input_tokens * input_price / 1M)
  //   + (output_tokens * output_price / 1M)
  //   + (cache_creation_tokens * cache_creation_price / 1M)
  //   + (cache_read_tokens * cache_read_price / 1M)
  double estimated_cost_usd = 12;
}
```

### 1.3 — Summarization Cost Tracking

**Problem**: `SummarizationEvent` records `summarization_model` and `duration_ms`, but does NOT record how many tokens the summarization LLM call consumed or its cost. This is a hidden cost — multiple summarization events using `claude-haiku-4` consume tokens and incur charges that are invisible.

**Schema change — `SummarizationEvent` (api.proto)**:

```protobuf
message SummarizationEvent {
  // --- Existing fields (unchanged) ---
  string timestamp = 1;
  int32 tokens_before = 2;
  int32 tokens_after = 3;
  float compression_ratio = 4;
  int32 duration_ms = 5;
  string summarization_model = 6;
  int32 messages_before = 7;
  int32 messages_after = 8;
  SummarizationSource source = 9;

  // --- New: Summarization LLM call usage ---
  // Input tokens consumed by the summarization LLM call.
  // This is the context sent to the summarization model for compression.
  int32 summarization_input_tokens = 10;

  // Output tokens generated by the summarization model (the summary).
  int32 summarization_output_tokens = 11;

  // Cost in USD of this summarization call.
  // Computed using the summarization model's pricing rates.
  double summarization_cost_usd = 12;
}
```

### 1.4 — Model Pricing Registry

**Problem**: To compute `estimated_cost_usd` at execution time, the agent-runner needs to look up the current pricing rates for the model being used. No such data source exists today.

**Approach**:

This does NOT need a new proto resource. The Model Registry (which already exists for context window limits and summarization thresholds) should be extended with pricing data. This is a configuration/data concern, not an API concern.

**What the registry needs per model entry**:

```
model_id: "claude-sonnet-4-20250514"
provider: "anthropic"
input_price_per_million_tokens: 3.00
output_price_per_million_tokens: 15.00
cache_creation_price_per_million_tokens: 3.75   # 1.25x input
cache_read_price_per_million_tokens: 0.30        # 0.1x input
```

**Implementation detail**: This could be a YAML/JSON config file loaded by the agent-runner at startup, or fields on the existing model registry entries. The key requirement is that the agent-runner can look up `(provider, model) → pricing rates` at execution time and stamp those rates onto `ModelUsage`.

**Historical accuracy**: Because pricing changes over time, we stamp the rate onto each execution record at write time. This means an execution from January 2026 carries the January 2026 rates even if prices dropped in March 2026. Reports built on this data are always historically accurate without needing a "pricing history" table.

### 1.5 — Per-LLM-Call Breakdown

**Problem**: The current `UsageMetrics` is a single **aggregate** across all LLM calls in a context. There is no `repeated` structure that tracks each individual LLM call. This means:

- You can't distinguish "one big call of 40K tokens" from "ten calls of 4K tokens each"
- You can't see when models changed mid-execution (e.g., fallback from Claude to GPT on a rate-limit retry)
- You can't attribute cost to specific reasoning steps ("the 8th LLM call was the expensive one because it had a huge tool result in context")
- You can't compute metrics like "average tokens per call" or "token growth rate across calls" for optimization tuning

Today, `AgentMessage.token_count` (field 7) captures total tokens per message, but that field is a single `int32` — it doesn't differentiate input vs output tokens, has no cache awareness, and doesn't record which model generated it. So even at the message level, you can't compute accurate costs.

**New message — `LlmCallMetrics`**:

```protobuf
// Metrics for a single LLM API call during execution.
// Provides per-call granularity for debugging, optimization, and cost attribution.
//
// One entry is created for each on_chat_model_end event.
// Ordered chronologically — the Nth entry corresponds to the Nth LLM call.
message LlmCallMetrics {
  // Sequence number of this LLM call within the execution (1-based).
  // The first LLM call is 1, the second is 2, etc.
  int32 sequence = 1;

  // Model used for this specific call.
  // May differ from primary_model if model fallback or routing occurred.
  string model = 2;

  // Provider for this call.
  string provider = 3;

  // Input tokens for this call (total prompt size sent to the model).
  int32 input_tokens = 4;

  // Output tokens generated by the model in this call.
  int32 output_tokens = 5;

  // Cache tokens written during this call.
  int32 cache_creation_tokens = 6;

  // Cache tokens read (cache hits) during this call.
  int32 cache_read_tokens = 7;

  // Computed cost in USD for this single call.
  double estimated_cost_usd = 8;

  // Wall-clock duration of this LLM call in milliseconds.
  // From request sent to response complete.
  int32 duration_ms = 9;

  // ISO 8601 timestamp when this LLM call started.
  string timestamp = 10;
}
```

**Schema change — `UsageMetrics`**:

```protobuf
message UsageMetrics {
  // ... existing and new fields from 1.1 ...

  // Per-call breakdown of every LLM API call in this context.
  // Ordered chronologically (call 1, call 2, ...).
  // Enables debugging expensive calls, tracking token growth across calls,
  // and verifying cache hit patterns (call 1 = cache miss, calls 2+ = cache hits).
  //
  // This is the detailed view — model_breakdown is the per-model aggregate.
  // Both are populated: model_breakdown for reports, llm_calls for debugging.
  repeated LlmCallMetrics llm_calls = 11;
}
```

**Why both `model_breakdown` AND `llm_calls`?**
- `model_breakdown` (section 1.2) is the **aggregate** view: "claude-sonnet-4 used 50K input tokens total across 8 calls = $0.15." This is what the CLI cost report uses.
- `llm_calls` is the **detailed** view: "call 1: 20K input (cache miss, $0.06), call 2: 20K input (18K cached, $0.006), call 3: 22K input (20K cached, $0.006)...". This is what you use for debugging and optimization tuning.

The detailed view is especially valuable for verifying prompt caching: you expect call 1 to be a cache miss (or cache write), and calls 2+ to have high `cache_read_tokens`. If they don't, something is wrong with the cache breakpoint placement.

**Size consideration**: A typical execution has 3-15 LLM calls. Each `LlmCallMetrics` is ~10 fields / ~80 bytes. Even a 50-call execution adds only ~4KB. This is negligible compared to the `messages[]` and `tool_calls[]` arrays which carry full content strings.

### 1.6 — Execution Duration Breakdown

**Problem**: The current schema has `started_at` and `completed_at` timestamps (from which you can compute total wall-clock duration), but there's no breakdown of *where* the time was spent. In a typical execution:

- **LLM time**: Time waiting for the model to respond (this is the "thinking" time)
- **Tool time**: Time executing tools (shell commands, file reads, MCP calls)
- **Approval wait time**: Time blocked waiting for user approval (HITL)
- **Overhead time**: Time in the platform (event processing, state persistence, etc.)

This matters because:
- LLM time correlates with token costs — slower responses usually mean more output tokens
- Tool time is "free" from an LLM perspective but costs compute resources (sandbox runtime)
- Approval wait time inflates wall-clock duration but shouldn't be counted as execution cost
- For billing models that charge by execution duration (not just tokens), you need this breakdown

**Schema change — `UsageMetrics`**:

```protobuf
message UsageMetrics {
  // ... existing and new fields ...

  // Total wall-clock duration of the execution in milliseconds.
  // Convenience field equivalent to (completed_at - started_at).
  // Includes all time: LLM calls, tool execution, approval waits, overhead.
  int32 total_duration_ms = 12;

  // Time spent waiting for LLM responses in milliseconds.
  // Sum of all LLM call durations (llm_calls[].duration_ms).
  // This is the "thinking" time — directly correlates with token generation.
  int32 llm_duration_ms = 13;

  // Time spent executing tools in milliseconds.
  // Sum of all tool execution durations (tool start to tool complete).
  // Represents compute resource usage in the sandbox.
  int32 tool_duration_ms = 14;

  // Time spent waiting for user approval in milliseconds.
  // Sum of all approval wait times (approval_requested_at to approval_decided_at).
  // This is idle time — no LLM or compute resources consumed.
  // Useful for excluding from "active execution cost" calculations.
  int32 approval_wait_duration_ms = 15;
}
```

This enables reports like:
```
Duration: 45.2s total
  LLM thinking:     12.3s (27%)
  Tool execution:   28.1s (62%)
  Approval wait:     0.0s (0%)
  Overhead:          4.8s (11%)
```

### 1.7 — Provider on Top-Level UsageMetrics

**Problem**: The top-level `UsageMetrics` has `primary_model` but no `provider`. The `ModelUsage` breakdown inside carries `provider`, but if a consumer reads only the top-level fields (which is the common case for simple displays), they don't know which provider served the request.

**Schema change — `UsageMetrics`**:

```protobuf
message UsageMetrics {
  // ... existing fields ...
  string primary_model = 5;

  // Provider that served the primary model.
  // Examples: "anthropic", "openai", "google", "ollama", "aws-bedrock"
  // Matches the provider field in model_breakdown for the primary model.
  // Useful for quick display without diving into model_breakdown.
  string primary_provider = 16;
}
```

### 1.8 — AgentMessage Token Enrichment

**Problem**: The existing `AgentMessage.token_count` (field 7) is a single `int32` described as "total tokens consumed to generate this message." This has several limitations:

- Doesn't differentiate input vs output tokens (both have very different prices)
- Doesn't know about cache tokens
- Doesn't record which model generated the message
- Can't be used for per-message cost calculation

For the purpose of the cost report, per-message cost isn't strictly required (the aggregate `UsageMetrics` and the per-call `LlmCallMetrics` cover it). However, enriching `AgentMessage` would enable per-message cost display in the UI/CLI (e.g., showing the cost next to each AI response, like Cursor does).

**Schema change — `AgentMessage` (api.proto)**:

```protobuf
message AgentMessage {
  // --- Existing fields (unchanged) ---
  MessageType type = 1;
  string content = 2;
  string timestamp = 3;
  repeated ToolCall tool_calls = 4;
  google.protobuf.Struct metadata = 5;
  bool is_streaming = 6;
  int32 token_count = 7;         // Keep for backward compat
  int32 generation_duration_ms = 8;

  // --- New: Enriched per-message usage ---
  // Input tokens consumed by the LLM call that generated this message.
  // Only meaningful for type == MESSAGE_AI.
  // Enables per-message cost display: "This response cost $0.02"
  int32 input_tokens = 9;

  // Output tokens generated for this message.
  // Only meaningful for type == MESSAGE_AI.
  int32 output_tokens = 10;

  // Cache read tokens for the LLM call that generated this message.
  // Non-zero indicates the prompt hit the provider cache.
  int32 cache_read_tokens = 11;

  // Estimated cost in USD for this message's LLM call.
  // Only meaningful for type == MESSAGE_AI.
  double estimated_cost_usd = 12;

  // Model that generated this message.
  // Only meaningful for type == MESSAGE_AI.
  // Useful when model routing is active and different messages
  // may come from different models.
  string model = 13;
}
```

This enables the CLI to show:
```
Assistant: Here's the implementation for the auth middleware...
  [claude-sonnet-4 · 1,830 output tokens · $0.027 · 82% cached]
```

### 2.1 — Prompt Caching

**What it is**: Structure LLM calls so that the system prompt + tool definitions + skill instructions form a stable prefix, then mark it with Anthropic's `cache_control: {"type": "ephemeral"}` breakpoints. On subsequent LLM calls within the same conversation, this prefix hits the provider's cache and costs 90% less (Anthropic) or 50% less (OpenAI).

**Why it's the highest-impact optimization**: In a typical agentic loop with 10 LLM calls, the system prompt + tool definitions might be 15-20K tokens. Without caching, you pay full price 10 times = 150-200K input tokens at full rate. With caching, you pay full price once + 9 cache reads at 10% rate = roughly 80-90% savings on the prompt portion.

**What Cursor does**: Structures prompts so static content (system prompt, tool schemas, file context) forms a cacheable prefix. Uses explicit `cache_control` breakpoints on Anthropic. Benefits from automatic caching on OpenAI.

**What Stigmer needs**:

1. **Agent-runner change**: In the LangGraph model call construction, structure the messages so that the system prompt (instructions + skills + tool schemas) is placed at the beginning as a stable prefix. For Anthropic, add `cache_control: {"type": "ephemeral"}` breakpoints at the boundary between static and dynamic content.

2. **Cache breakpoint placement strategy**:
   - Breakpoint 1: After system prompt + instructions + skills (these rarely change within a session)
   - Breakpoint 2: After tool definitions (these are fixed per agent configuration)
   - Dynamic content (conversation history, user message) goes after the breakpoints

3. **Provider handling**:
   - Anthropic: Explicit `cache_control` breakpoints required. Cache lasts 5 minutes, extended on each hit. Cache writes cost 1.25x, cache reads cost 0.1x.
   - OpenAI: Automatic caching (no client-side opt-in needed). 50% discount on cached tokens. Requires prompt prefix >= 1024 tokens.
   - Google: Context caching with explicit `CreateCache` API. Configurable TTL.
   - Ollama/local: No caching (skip).

4. **Tracking**: The cache token fields in `UsageMetrics` (section 1.1) capture the results. Additionally, a `cache_hit_rate` can be computed from `cache_read_tokens / prompt_tokens` to monitor effectiveness.

5. **Schema change — `UsageMetrics`**: Already covered in section 1.1. No additional fields needed beyond `cache_creation_tokens` and `cache_read_tokens`.

### 2.2 — Tool Result Truncation

**What it is**: When a tool returns a massive output (e.g., `cat` of a 3000-line file, or `shell` command that outputs 500 lines), truncate the result to a configurable limit before injecting it back into the conversation.

**Why it matters**: A single uncapped tool result can inject 50-100K tokens of context in one shot. This accelerates context window fill-up (triggering more summarization events, each with their own cost), and makes every subsequent LLM call more expensive (bigger prompt = more input tokens). It's a compounding problem.

**What Cursor does**: Truncates tool results to configurable limits. Appends a marker like "output truncated, request specific sections for more detail." Uses line-range reads instead of full file reads.

**What Stigmer needs**:

1. **Schema change — `ExecutionConfig` (spec.proto)**:

```protobuf
message ExecutionConfig {
  // --- Existing fields ---
  string model_name = 1;
  ContextManagementConfig context_management = 2;
  int32 max_tool_rounds = 3;

  // --- New: Tool result truncation ---
  // Maximum number of characters for a single tool result before truncation.
  // When a tool result exceeds this limit, it is truncated and a marker is
  // appended: "[truncated — result exceeded {limit} chars, ask for specific sections]"
  //
  // 0 = use platform default (recommended: 30,000 chars ≈ ~7,500 tokens).
  // Set higher for agents that work with large files/outputs.
  //
  // Applies to all tool results (shell, read, write, MCP tools).
  // Does not apply to built-in tools that already manage their output size.
  int32 max_tool_result_chars = 4;
}
```

2. **Agent-runner change**: In the tool result processing pipeline (after tool execution, before injecting result into conversation), apply truncation if `len(result) > max_tool_result_chars`. Append a truncation marker so the LLM knows the result was cut and can ask for specific sections.

3. **Tracking — `UsageMetrics`**: Optionally track how many characters were truncated across the execution:

```protobuf
message UsageMetrics {
  // ... existing and new fields ...

  // Total characters truncated from tool results during this execution.
  // Non-zero indicates the agent received tool outputs that exceeded limits.
  // Useful for: tuning truncation limits, identifying verbose tools.
  int64 tool_result_chars_truncated = 10;
}
```

### 2.3 — Model Routing for Sub-Agents

**What it is**: Allow sub-agents to use a different (cheaper) model than the parent agent. A sub-agent doing a simple file search doesn't need `claude-sonnet-4` at $3/$15 per MTok when `claude-haiku-4` at $0.25/$1.25 would work.

**What Cursor does**: Uses 4 tiers — fast/cheap for Tab completion, mid-tier for Chat, top-tier for Agent mode, and cheap for "fast apply" (diff application).

**What Stigmer needs**:

1. **Schema change — `SubAgentDefinition` (agent/v1/spec.proto)**:

```protobuf
message SubAgentDefinition {
  // --- Existing fields ---
  string name = 1;
  string description = 2;
  string instructions = 3;
  repeated McpAccess mcp_access = 4;

  // --- New: Model override for this sub-agent ---
  // When set, this sub-agent uses this model instead of the parent's model.
  // Enables cost optimization by routing simple sub-agent tasks to cheaper models.
  //
  // Examples:
  //   - Parent uses "claude-sonnet-4" ($3/$15 per MTok)
  //   - File search sub-agent overrides to "claude-haiku-4" ($0.25/$1.25)
  //   - Code review sub-agent keeps parent model (leave empty)
  //
  // When empty: inherits the parent agent's model (current behavior).
  string model_override = 5;
}
```

2. **Agent-runner change**: When constructing the sub-agent's LLM, check `sub_agent_definition.model_override`. If set, use that model instead of the parent's `ExecutionConfig.model_name`.

3. **Tracking**: Already handled — `SubAgentExecution.usage` is isolated per sub-agent, and `ModelUsage.model` in the breakdown captures which model was actually used.

### 2.4 — Token Budgeting / Cost Caps

**What it is**: Allow setting a maximum cost or token budget per execution, so runaway agents don't drain API credits.

**What Stigmer has today**: `max_tool_rounds` limits iterations but doesn't cap actual token spend. An agent with `max_tool_rounds: 10` could spend $0.05 or $5.00 depending on context size.

**What Stigmer needs**:

1. **Schema change — `ExecutionConfig` (spec.proto)**:

```protobuf
message ExecutionConfig {
  // --- Existing fields ---
  // ... model_name, context_management, max_tool_rounds, max_tool_result_chars ...

  // --- New: Cost cap ---
  // Maximum estimated cost in USD for this execution.
  // When the running cost exceeds this limit, the agent receives a
  // "budget exhausted" message and the execution transitions to TERMINATED.
  //
  // 0.0 = no cost cap (default, unlimited).
  // Recommended: 1.00-5.00 for interactive sessions, 10.00+ for batch workflows.
  //
  // Cost is checked after each LLM call using the running total from
  // UsageMetrics.estimated_cost_usd. When approaching the cap (>80%),
  // a budget warning is injected into the conversation.
  double max_cost_usd = 5;
}
```

2. **Agent-runner change**: After each `on_chat_model_end` event, check the running `estimated_cost_usd` against `max_cost_usd`. At 80%, inject a warning. At 100%, terminate gracefully.

### 2.5 — Diff-Based / Compact Output Formats

**What it is**: Instead of having the model output an entire file when making an edit, use a structured diff format where the model outputs only the old and new snippets. Pair this with a "fast apply" pipeline where an expensive model decides *what* to change, and a cheap model applies the change to the actual file.

**Why it matters**: Output tokens are the most expensive token type across all providers — typically 3-5x more expensive than input tokens ($15/MTok for Claude Sonnet output vs $3/MTok input). If a model needs to edit 3 lines in a 500-line file, without a diff format it regenerates all 500 lines as output tokens. With a diff format (search-and-replace blocks), those 500 output lines shrink to ~10-15 lines. On a typical coding session with 20 file edits, this can save 50-80% on output token costs.

**What Cursor does**:
- Uses a "search and replace" output format — the model outputs `<<<< SEARCH ... ==== ... REPLACE >>>>` blocks containing only the changed snippet and enough surrounding context to locate it
- Uses a "fast apply" pipeline: the expensive model (Claude Sonnet/Opus) decides *what* to change and outputs the diff, then a cheap model (GPT-4o-mini or Haiku) applies the diff to the actual file content
- Falls back to full file output only when the model can't express the change as a diff (e.g., new file creation)

**What Stigmer needs**:

1. **Instruction-level change (system prompt)**: Add instructions to the agent's system prompt that encourage using structured diff output when editing files. This is the lowest-effort change — no schema or runtime changes needed, just prompt engineering. The agent's built-in `write` / `edit` tools already accept targeted edits; the optimization is getting the LLM to consistently use them instead of rewriting entire files.

2. **Tool design consideration**: Evaluate whether the existing sandbox tools (`read`, `write`, `shell`) encourage efficient output. For example:
   - Does the `read` tool support line-range reads (e.g., "read lines 50-80 of file.py")? If not, the model is forced to read full files, which then leads to full-file rewrites.
   - Does the `write`/`edit` tool accept a search-and-replace style input? If so, the prompt should encourage that pattern over full-file writes.

3. **Fast-apply pipeline (future, P2)**: For agents that do heavy file editing, introduce a two-model pipeline:
   - Main model: Decides what to edit, outputs a structured diff (search/replace blocks)
   - Apply model: A cheap model (claude-haiku-4) takes the diff + original file and produces the final file
   - This is a deeper architectural change and can be deferred to a later phase

4. **Tracking**: Track output token efficiency:

```protobuf
message UsageMetrics {
  // ... existing and new fields ...

  // Average output tokens per LLM call.
  // Computed as: completion_tokens / llm_call_count.
  // Useful for detecting inefficient output patterns (e.g., full-file rewrites).
  // High values (>2000 tokens/call average) may indicate the model is not
  // using diff-based output and could benefit from prompt tuning.
  // This is a derived/convenience field — not strictly required.
  // Can be computed client-side from completion_tokens and llm_call_count.
}
```

Note: The main savings from diff-based output are captured by the existing `completion_tokens` field — if the optimization works, `completion_tokens` goes down, `estimated_cost_usd` goes down. No new schema field is strictly needed; the metric is implicit in lower output tokens.

### 2.6 — Smart Context / Selective File Inclusion

**What it is**: Instead of including all configured skills and context in every LLM call regardless of relevance, dynamically select which context to include based on the current conversation state, and enforce a "context budget" that ranks inclusions by relevance.

**Why it matters**: Today, `ResolvedExecutionContext.skill_names` shows that every configured skill's full `SKILL.md` content is appended to the system prompt. If an agent has 5 skills and each is 2K tokens, that's 10K tokens in the system prompt on every single LLM call. On a 10-call execution, that's 100K extra input tokens — even if only 1 of those 5 skills was relevant to the current conversation. At $3/MTok, that's $0.30 of waste (or $0.03 with caching, but still non-zero).

This problem compounds with:
- **MCP tool schemas**: Each MCP server contributes tool definitions. An agent with 3 MCP servers might have 50+ tool definitions, each with parameter schemas. These are all included in every LLM call.
- **Conversation history**: Without smart selection, every past message (including large tool results) stays in context until summarization kicks in at 90% utilization.

**What Cursor does**:
- Pre-indexes the codebase (embeddings + AST analysis) and uses semantic search to find relevant code chunks
- Sends only relevant line ranges to the model, not entire files
- Maintains a "context budget" — each file inclusion costs tokens, so they rank by relevance and cut off at a threshold
- Uses a "codebase context" section that's dynamically populated per query, not statically dumped

**What Stigmer needs**:

1. **Skill relevance filtering (medium effort)**:
   - Before constructing the system prompt, evaluate which skills are relevant to the current user message
   - Simple approach: keyword matching between user message and skill names/descriptions
   - Better approach: use a cheap model (haiku) or embedding similarity to score skill relevance
   - Only include skills above a relevance threshold in the system prompt
   - Schema consideration — `ResolvedExecutionContext` already tracks `skill_names`; add a field to distinguish included vs. available:

```protobuf
message ResolvedExecutionContext {
  // --- Existing fields ---
  repeated string environment_keys = 1;
  map<string, McpServerResolutionStatus> mcp_servers = 2;
  repeated string skill_names = 3;

  // --- New: Skill inclusion tracking ---
  // Skills that were available but not included in the system prompt
  // because they were not relevant to the current execution context.
  // Enables visibility into the filtering decision.
  repeated string excluded_skill_names = 4;
}
```

2. **Tool schema pruning (medium effort)**:
   - If an agent has 50+ MCP tools but the current conversation is about Kubernetes, only include k8s-related tool schemas in the prompt
   - This requires tool categorization or relevance scoring
   - Significant token savings when agents have many MCP servers configured

3. **Context budget / token allocation (lower priority)**:
   - Define a maximum token budget for context (e.g., 40K tokens for context, leaving 160K for conversation + output on a 200K model)
   - Rank context items by relevance: skills > recent tool results > older history
   - Trim low-relevance items when approaching the budget
   - This overlaps with the existing summarization mechanism but works proactively rather than reactively

4. **Line-range reads in tool design**:
   - Ensure the `read` tool supports and encourages line-range reads (e.g., `read(file, start_line=50, end_line=80)`) so the model doesn't need to read entire files to find relevant sections
   - Add instructions in the system prompt encouraging targeted reads over full file reads

## Risks & Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| LangChain `usage_metadata` may not expose all cache fields | Cache tokens reported as 0, cost calculations under/overestimate | Test with raw provider SDK to verify fields; fallback to provider-specific extraction if LangChain is incomplete |
| Provider pricing changes | Historical cost data becomes inaccurate if not stamped at write time | Already addressed: stamp rates on each execution record at write time |
| Backward compatibility of `UsageMetrics` | Existing consumers break | All new fields are additive (new field numbers); zero defaults are safe |
| Prompt caching TTL (5 min Anthropic) | Cache misses if executions are infrequent | Cache effectiveness tracking (cache_hit_rate) will reveal this; consider warm-up strategies for batch scenarios |
| Tool result truncation loses important data | Model makes wrong decisions due to missing context | Append clear truncation marker; make limit configurable per-agent; default conservative (30K chars) |
| Diff-based output may reduce edit accuracy | Model misidentifies the search block, applies edit to wrong location | Keep full-file write as fallback; only enforce diff style for files > N lines; validate search block uniqueness before applying |
| Skill filtering removes relevant skills | Model loses capabilities it needs for the task | Start conservative (include skill if relevance score > low threshold); log excluded skills for debugging; always include skills explicitly referenced in user message |
| Tool schema pruning hides available tools | Model can't use a tool it needs because the schema was pruned | Only prune when tool count exceeds a threshold (e.g., 30+); keep a "request additional tools" meta-tool so the model can ask for pruned tools |
