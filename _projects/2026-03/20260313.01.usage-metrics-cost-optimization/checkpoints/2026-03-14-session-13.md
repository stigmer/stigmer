## Decisions Made

- **BM25-style scoring over alternatives**: Chose BM25-inspired relevance scoring (stateless, zero-cost, fast) over keyword overlap (too brittle), embedding similarity (over-engineering), or LLM calls (adds latency + cost). Can upgrade later if insufficient.
- **Defer `tool_count` proto field**: Used structured logging only for tool count observability instead of adding a new proto field. Avoids schema churn for a diagnostic-only signal.
- **Safety floor for skill filtering**: Always keep at least half the skills regardless of relevance score. Prevents aggressive filtering from removing skills the BM25 scorer undervalues.
- **Skill count threshold of 8**: Below 8 skills, the noise cost is minimal and filtering could only hurt. The threshold is high enough to avoid unnecessary processing for typical agents.
- **Description truncation at 500 chars**: Conservative limit that preserves meaningful description content while capping the long tail of verbose MCP tool descriptions.

## Learnings

- **Progressive disclosure matters**: The skill system's design of injecting only metadata (~50-70 tokens) into the prompt while keeping full content on disk meant that filtering could never achieve the "30% system prompt reduction" originally estimated. Always verify assumptions against actual architecture.
- **Tool schemas live in API payload, not system prompt**: `bind_tools()` sends schemas as part of the API tool-calling payload. This means tool pruning removes capabilities, not just tokens — a fundamentally different tradeoff than prompt optimization.
- **BM25 works well for short-text matching**: Even with skill names and descriptions being very short documents, BM25's term frequency saturation and document length normalization produce useful relevance rankings.
