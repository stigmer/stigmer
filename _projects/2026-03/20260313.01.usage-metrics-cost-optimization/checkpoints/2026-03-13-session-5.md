## Decisions Made

1. **Architecture correction**: Task file specified StatusBuilder for both features. After investigation, determined StatusBuilder is an observer (cannot modify LLM state). Implemented as graphton middleware instead — matching ExecutionBudgetMiddleware and LoopDetectionMiddleware patterns.

2. **Truncation strategy**: Prefix-only for the middleware (30K context budget layer). Existing `tool_wrappers.py` handles head+tail at 120K (smart formatting layer). Two complementary layers.

3. **Sub-agent cost scope**: Main agent only. Matches per-graph middleware pattern. Total-cost tracking deferred.

4. **Tool truncation activation**: Always active with 30K default. `max_tool_result_chars=0` = "use platform default", not "disable". Protects against uncapped MCP tools.

5. **Cost cap termination**: Graceful — SystemMessage + block tools → one final model call to summarize.

6. **Independent cost tracking**: CostCapMiddleware tracks its own running cost, separate from UsageTracker. Different timing (middleware fires before event stream), layer (graphton vs agent-runner), and precision needs (rough estimate vs exact per-model accounting).

## Learnings

- The `awrap_tool_call` hook signature does NOT include `runtime` (unlike `aafter_model` and `abefore_agent`). Only `request` and `handler`.
- `ToolMessage.content` can be a string or a list (multimodal content blocks). Must check `isinstance(content, str)` before truncation.
- Handler return type is `ToolMessage | Command`. Must check for `Command` passthrough.
- `request.tool_call` is a dict with `id`, `name`, `args` keys (not attributes).
