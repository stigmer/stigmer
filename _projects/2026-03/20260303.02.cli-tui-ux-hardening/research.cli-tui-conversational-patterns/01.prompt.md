# Deep Research: Industry Patterns for Conversational Agent CLI/TUI Interfaces

## Research Objective

I'm building a CLI tool (Go, Cobra, Bubbletea) that executes AI agents and presents their streaming output in the terminal. The tool has two key commands:

- **`stigmer draft <resource-type>`** — invokes a system AI agent that generates configuration files (YAML, Markdown). The agent runs server-side, streams its thinking/tool-calls/output back to the CLI over gRPC, and the CLI renders a real-time conversational TUI. The agent may pause to request approval before executing dangerous tools (e.g., writing files, running shell commands).

- **`stigmer run agent <name>`** — executes any user-defined AI agent with the same streaming TUI. After the agent completes, the user can send follow-up messages to continue the conversation within the same session (multi-turn).

The TUI currently uses Bubbletea (Charm ecosystem) in alt-screen mode. It renders:
- A scrollable viewport of content blocks (human messages, AI messages, tool call blocks with expand/collapse, sub-agent delegation blocks, todo/planning blocks)
- Inline approval prompts (a/s/r keys) when the agent wants to run a tool
- A footer with context-sensitive key hints
- A header with session subject and phase indicator
- An input composer at the bottom for follow-up messages after completion

**The current implementation works but feels "AI-generated" — it's functional but not crafted.** I want to understand how the best CLI tools in this space approach these problems so I can make ours feel native, polished, and professional.

## What I Already Know

1. **Our architecture**: gRPC stream → goroutine converts proto updates to TUI events → Bubbletea model receives events and renders content blocks in a viewport. Approval is handled via a channel between the stream goroutine and the TUI.

2. **Our current issues**: Approval prompts can get lost on session resume; error messages leak gRPC internals; no graceful fallback for non-TTY environments; no connection health monitoring; the TUI can feel sluggish during rapid tool call bursts.

3. **Charm ecosystem**: We use bubbles/viewport, bubbles/spinner, bubbles/textarea, lipgloss for styling. We're committed to the Charm stack.

## Specific Areas to Investigate

### Area 1: How Do Leading AI CLI Tools Handle Streaming Conversations?

Research the following tools and document their exact UX patterns for the streaming agent conversation experience:

- **Claude Code (Anthropic)** — The `claude` CLI tool. How does it render streaming AI output? How does it handle tool calls (file edits, shell commands)? What does the approval flow look like? How does it handle the transition from "agent is working" to "agent is done, your turn"? Does it use alt-screen or inline rendering?

- **GitHub Copilot CLI** — The `gh copilot` experience. How does it present suggestions and confirmations? What approval patterns does it use for executing shell commands?

- **Aider** — The AI pair programming CLI. How does it handle the conversational flow? How does it display file diffs, tool calls, and agent thinking? How does it handle multi-turn conversations?

- **Cursor CLI / Codex CLI (OpenAI)** — If they have terminal-based interfaces, how do they work?

- **Warp Terminal** — How does Warp's AI integration handle inline agent output and command suggestions?

- **Open Interpreter** — How does it render code execution, streaming output, and approval for running code?

- **Cody CLI (Sourcegraph)** — If it has a terminal mode, how does it handle streaming and tool use?

For each tool, I need:
- Screenshot descriptions or detailed UX flow descriptions
- Whether they use alt-screen TUI vs inline rendering
- How they visually separate "agent is thinking" vs "agent output" vs "tool execution"
- How they handle the approval/confirmation step for dangerous actions
- How they signal "agent is done, it's your turn now"
- How they handle errors and connection issues
- Whether they support session resume / re-attach

### Area 2: The "Conversational TUI" Design Pattern

This is a relatively new UI pattern — a terminal interface that looks and feels like a chat conversation but with rich elements (code blocks, diffs, collapsible sections, progress indicators). Research:

- **What are the established design principles** for conversational TUIs vs traditional command output?
- **Progressive disclosure** in the terminal: how do the best tools decide what to show collapsed vs expanded? What heuristics do they use for tool call output (show a summary line, let user expand for full output)?
- **Visual hierarchy**: How do leading tools differentiate between agent text, tool calls, system messages, and user input in a single scrolling view? What color schemes, icons, indentation, and spacing patterns are considered best practice?
- **Streaming text rendering**: Character-by-character, word-by-word, or chunk-by-chunk? What feels natural in a terminal? How do tools handle the cursor/caret during streaming?
- **The "agent is thinking" indicator**: Spinner? Animated dots? Pulsing block? What do users prefer and what's been tested?

### Area 3: Approval / Human-in-the-Loop Patterns in CLI Tools

Our tool pauses agent execution to ask the user whether to approve, skip, or reject a tool call (e.g., "The agent wants to run `rm -rf /tmp/build`"). Research:

- **How do other tools present approval requests?** Inline prompt, modal overlay, separate panel?
- **What information do they show?** Just the command? A risk assessment? The full arguments? A diff preview?
- **Auto-approve patterns**: How do tools handle `--yes` or `--auto-approve` flags safely? Do any tools have tiered approval (auto-approve reads, prompt for writes, block for deletes)?
- **Batch approval**: When an agent wants to run 5 tool calls, do tools prompt for each one individually or offer "approve all"?
- **Timeout behavior**: What happens if the user doesn't respond to an approval prompt? Do tools time out, skip, or wait forever?
- **The "approval fatigue" problem**: How do mature tools reduce unnecessary prompts without sacrificing safety? Research any approval policy frameworks.

### Area 4: Session Resume and Detach/Re-attach

Our tool supports detaching from a running execution (`q` to quit) and re-attaching later (`stigmer run ses-XXX`). Research:

- **Do other AI CLI tools support detach/re-attach?** Which ones, and how?
- **How do they restore the conversation state?** Full replay? Summary of what happened? Just show the latest state?
- **The "pending approval on resume" problem**: If the agent was waiting for approval when the user detached, how do other tools surface the pending approval when the user re-attaches?
- **tmux/screen parallels**: Are there UX lessons from terminal multiplexer session management that apply?

### Area 5: Alt-Screen TUI vs Inline Rendering

This is a fundamental architectural choice. Research:

- **Which AI CLI tools use alt-screen** (full TUI, takes over terminal) **vs inline** (renders below the command, scrolls with terminal history)?
- **What are the tradeoffs?** Alt-screen provides better layout control but loses terminal history. Inline preserves history but has limited layout options.
- **Hybrid approaches**: Do any tools start inline and switch to alt-screen when content exceeds a threshold? Do any use alt-screen during execution and print a summary inline after?
- **The "I want to see what happened after I close the TUI" problem**: Our tool currently prints a one-line summary after the alt-screen closes. Is this sufficient? What do other tools do?
- **Non-TTY / CI/CD fallback**: How do tools that primarily use a TUI degrade gracefully when stdout is piped or the terminal is dumb?

### Area 6: What Makes a CLI Feel "Crafted" vs "AI-Generated"?

This is subjective but important. Research:

- **Micro-interactions**: Subtle animations, transition effects, easing on scrolling — what small details separate a professional TUI from a functional one?
- **Typography and spacing**: How do the best terminal tools use whitespace, horizontal rules, box-drawing characters, and padding to create visual rhythm?
- **Color discipline**: How many colors is too many? What are established terminal color palettes that work across light/dark themes? How do tools handle 256-color vs true-color vs 16-color terminals?
- **Sound and haptics**: Do any CLI tools use terminal bell or system notifications for attention events (e.g., approval needed)?
- **Error presentation**: How do tools like `rustc`, `elm`, or `deno` present errors in a way that's both beautiful and actionable? What can we learn from compiler error UX for agent error UX?
- **Loading/progress states**: Beyond spinners — what creative progress indicators exist in the terminal space? Research Charm's `harmonicá` and similar.

### Area 7: The Sub-Agent / Nested Execution Pattern

Our tool supports agents that delegate to sub-agents (e.g., a "draft" agent spawns a "researcher" sub-agent and a "code-editor" sub-agent). Research:

- **How do other tools visualize nested/hierarchical agent execution?** Tree view? Indented blocks? Tabs?
- **Collapse/expand patterns for nested content**: What's the standard for showing a sub-agent's work as a collapsible section?
- **Progress rollup**: How do tools show aggregate progress when multiple sub-tasks are running in parallel?

## Output Format Expectations

For each area, I want:
1. **Concrete examples** from real tools (with version numbers and dates if possible)
2. **Screenshots or detailed visual descriptions** of the UX patterns
3. **Source links** to documentation, blog posts, or open-source code where these patterns are implemented
4. **"Best in class" recommendations** — which tool does each thing the best, and why
5. **Anti-patterns** — what NOT to do, with examples of tools that got it wrong

## Why This Research Matters

We're building a developer tool that will be used daily by engineers running AI agents from their terminal. The streaming conversation TUI is the primary interface — if it feels clunky, unreliable, or generic, developers will avoid it. The terminal is an intimate environment for developers; they notice every pixel, every millisecond of lag, every unnecessary line of output. We need to meet the bar set by tools like Claude Code, ripgrep, and the Charm ecosystem itself.

The goal is not to copy any single tool but to understand the design space deeply enough to make informed, opinionated choices that make our TUI feel like it was built by someone who lives in the terminal.
