## Decisions Made

- **`stigmer fix` over `stigmer reset-terminal`**: User chose bare `stigmer fix` — shortest to type blind, auto-detects what to fix. Avoids confusion with existing `stigmer server reset`.
- **`p.Kill()` over `p.Quit()` for signals**: `Quit()` goes through the event loop which may be stuck. `Kill()` cancels the internal context immediately.
- **`stty sane` over `term.MakeRaw+Restore`**: When the terminal is already in raw mode, MakeRaw saves the broken state and Restore re-applies it. `stty sane` unconditionally resets to cooked mode.
- **Nested `recover()` around `p.RestoreTerminal()`**: Bubbletea's RestoreTerminal panics if the program was never fully initialized. The nested recover ensures restoreTerminal never panics regardless of program state.
- **Per-TUI signal registration**: Signal handlers active only while TUI runs. No global state, no interference with daemon/MCP handlers.

## Learnings

- Bubbletea v1.2.4 has its own `recoverFromPanic` deferred in `eventLoop()` that catches panics from Init/Update/View, restores the terminal, and returns nil error from `Run()`. This means our wrapper's `recover()` never fires for event-loop panics — it's defense-in-depth for panics in `Run()`'s terminal setup/teardown path.
- `p.RestoreTerminal()` accesses internal fields that are only initialized during `Run()`. Calling it on an unstarted program panics with nil pointer dereference. Must be guarded.
- The `term.MakeRaw(fd)` function returns the *previous* state. If the terminal is already in raw mode, it saves the raw state and restoring that state re-applies raw mode — useless for fixing a broken terminal. `stty sane` is the correct approach.
