## Decisions Made

- **No buffer increase**: Kept events channel at 16. With cancellable operations, buffer size is irrelevant to safety. The 256 buffer in `run_session.go` is intentional for replay (different workload).
- **No arbitrary timeout on approval response**: A 30-second timeout would punish users who take time to review approvals. Context cancellation (TUI exit) is the correct exit mechanism.
- **`trySendEvent` as a reusable primitive**: Rather than scattering `select` blocks, introduced a helper that will be reused in Phase 1.3 (dead stream detection).
- **`streamCancel()` before error check**: Placed `streamCancel()` immediately after `p.Run()` returns, before the error check, so goroutines are cleaned up even if Run() returns an error.
- **Fresh context for final fetch**: `fetchFinalExecution` uses `context.Background()` because `streamCtx` is now cancelled. This is intentional — the fetch needs a live context.

## Learnings

- The original "deadlock" diagnosis was inaccurate. True deadlocks require both goroutines permanently blocked on each other. The TUI continuously drains the events channel via `listenForEvents`. The actual problem was goroutine lifecycle management — no way for the goroutine to know the TUI was gone.
- `context.Background()` in goroutine-spawning code is a code smell. Always use a cancellable context when the goroutine's lifecycle is bounded by an outer scope.

- Should `sendApprovalResponse` in the TUI also be context-aware? Low priority — it runs in Bubbletea's Cmd goroutine pool and the leak is bounded to process lifetime.
