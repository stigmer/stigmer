## Decisions Made

- **Separation of concerns**: `Classify` (pure classification), `formatError` (output formatting), and `Handle` (exit orchestrator) are separated into independently testable functions. No `os.Exit` mocking needed for tests.
- **`CLIError` type over enhanced switch**: Introduced a structured `CLIError` with `ExitCode`, `Message`, `Hints`, and `Cause` fields. This enables testing classification logic without side effects and makes the error contract explicit.
- **Error chain unwrapping via `extractGRPCStatus`**: Walks `errors.Unwrap()` chain to find gRPC status. This fixes the pre-existing bug where `status.FromError()` couldn't detect gRPC errors wrapped with `errors.Wrap()`.
- **Exit code scheme**: 0=success, 1=general, 2=usage, 3=connection, 4=auth, 5=not-found. Follows BSD sysexits.h convention adapted to the Stigmer domain.
- **`classifyStreamError` remains separate**: Stream errors (mid-operation TUI display) and command errors (CLI exit) serve fundamentally different audiences. Not unified.
- **`SetDebug(bool)` package-level setter**: Called from `PersistentPreRun` in root.go. Simpler than parameter passing; the debug flag is already set before any command runs.
- **`main.go` routes through `clierr.Handle`**: Cobra-level errors now get the same classification and formatting treatment as command-level errors.

## Learnings

- `status.FromError()` does NOT walk the error chain. It only checks the outermost error via a `GRPCStatus()` interface type assertion. When `github.com/pkg/errors.Wrap()` wraps a gRPC error, the wrapper does not implement that interface, so classification silently falls through to the generic handler. This was happening at 25+ call sites across the command layer.
- `github.com/pkg/errors` v0.9.1 supports `Unwrap()` (Go 1.13 error wrapping compatibility), so `errors.Unwrap()` from the standard library can walk through `pkg/errors` wrappers.
- The existing `--debug` flag only controlled zerolog output level. Extending it to also show the raw error chain in `clierr.Handle` was a natural addition that required no new flags or user-facing changes.
- Pre-existing Bazel module resolution issues (`chroma_v2`, `glamour`, `charmbracelet_x_ansi` repos) prevent full CLI binary builds but do not affect the `clierr` package or its tests.
