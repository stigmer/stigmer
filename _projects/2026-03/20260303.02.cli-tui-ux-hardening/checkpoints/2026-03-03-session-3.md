## Decisions Made

- **No keepalive changes**: The existing 30s/10s configuration is correct and working. The original plan's 10s/5s would be too aggressive for slow networks.
- **No application-level recv timeout**: This is the same anti-pattern documented in `backend/client.go` — it falsely triggers during normal LLM thinking pauses. Transport-level keepalive is the correct approach.
- **No stale-connection TUI warning**: Showing "connection may be stale" after 30s contradicts the existing "Thinking..." indicator. LLM inference routinely exceeds 30s.
- **Error translation at stream layer, not TUI layer**: The streaming layer knows the gRPC context (codes, transport errors), so it creates the `streamError`. The TUI just displays `e.Err.Error()` which is now the actionable message.
- **`streamError` type over enriching `StreamErrorEvent`**: Used idiomatic Go error wrapping instead of adding fields to the event type. Keeps the event interface simple; the error carries its own display message.
- **No blanket `trySendEvent` migration**: The helper functions (`emitMessageEvents`, etc.) run inside the recv loop and are bounded by the cancellable stream context. Migrating them would add complexity for a near-zero probability scenario. User agreed with this recommendation.

## Learnings

- The codebase already had a documented history of application-level connection heuristics that were replaced by transport-level keepalive. The comment in `backend/client.go` was the key evidence.
- Go's `select` is non-deterministic when multiple cases are ready. A test using a buffered channel with a cancelled context is inherently flaky — only unbuffered channels or single-ready-case selects produce deterministic behavior in tests.
- `status.FromError()` from `google.golang.org/grpc/status` cleanly extracts gRPC status codes, enabling error classification without string matching.
