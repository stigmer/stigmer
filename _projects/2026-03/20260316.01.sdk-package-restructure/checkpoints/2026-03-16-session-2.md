## Decisions Made

- **`Object.assign(create(Schema), { data })` for builders**: The `create(Schema, init)` pattern causes TypeScript errors because SDK input types (e.g., `EnvSpecInput`) don't match protobuf-es v2's `MessageInit<T>` structural types. `Object.assign` avoids this type-checking entirely while producing correct proto messages at runtime. No `any` types needed.
- **Enum imports always from `enum_pb`**: The initial heuristic derived the file from the package name's second-to-last component (yielding `v1_pb` which doesn't exist). All enums in this codebase consistently live in `enum_pb.ts`.
- **`Date | string` for Timestamp fields**: The Go SDK uses `string` (RFC3339). In TypeScript, allowing both `Date` and `string` gives consumers flexibility. The `Object.assign` builder pattern means we don't need to convert at build time.
- **`JsonObject` from `@bufbuild/protobuf` for Struct**: protobuf-es v2 uses `JsonObject` (not `Record<string, unknown>`) for `google.protobuf.Struct` fields. Using the correct type ensures compatibility with the proto runtime.
- **Cross-package type resolution via `tsImportMethodType`**: Centralized function that handles all cases: commons types (with file mapping for `status_pb`, `metadata_pb`), spec-defined types (using `TypeSchema.ProtoFile`), and standard IO types.

## Learnings

- protobuf-es v2's `MessageInit<T>` is stricter than expected — it recursively requires nested fields to match the proto message shape exactly. SDK input types intentionally differ (simpler, more ergonomic), so direct `create(Schema, init)` doesn't work for nested messages. The `Object.assign` pattern is the correct TypeScript workaround.
- The `TypeSchema.ProtoFile` field from the spec schemas is essential for correct import resolution. Without it, the generator can't distinguish between types in `spec_pb` vs `io_pb` within the same package.
- Some resources have unusual patterns: IamPolicy's Create/Delete take `IamPolicySpec` (not `IamPolicy`), Environment/McpServer/IdentityProvider use the commons `ApiResourceId` (not a resource-specific ID). The generator handles both patterns.
- The initial codegen run produced 25+ TypeScript errors across 6 categories. Systematic debugging required examining actual `@stigmer/protos` exports, proto stub file structure, and protobuf-es v2's type system.
