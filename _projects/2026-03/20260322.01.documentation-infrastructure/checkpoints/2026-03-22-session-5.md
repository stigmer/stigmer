## Decisions Made

- **Single workflow over two files**: Original plan called for `docs-lint.yml`
  and `docs-build.yml`. Chose a single `ci.docs.yaml` with parallel jobs — same
  performance (jobs run concurrently), less duplication, easier maintenance.
- **Vale manual install over `errata-ai/vale-action`**: Uses direct binary
  download + `make lint-docs` for exact parity with local development. Trade-off
  is no inline PR annotations, but consistency was prioritized.
- **Lychee action for links**: Used `lycheeverse/lychee-action@v2` instead of
  manual install + `make check-links`. Pragmatic choice since this is a
  non-blocking advisory check.
- **Non-blocking link checks**: `continue-on-error: true` on the links job.
  Lychee does not understand Fumadocs slug-style links (e.g., `./skills` without
  `.mdx` extension) and external links are flaky in CI. Will tighten after adding
  a `.lychee.toml` config.
- **Vale style packages are gitignored**: Google, Microsoft, and alex packages
  are downloaded by `vale sync`, not checked into the repo. The CI workflow runs
  `vale sync` explicitly before `make lint-docs`.

## Learnings

- The repo had zero PR-triggered workflows. All seven existing workflows are
  release/deploy pipelines. This is the first PR quality gate.
- Vale style packages (Google, Microsoft, alex) are NOT in git — they live in
  `vale/styles/` but are gitignored. `vale sync` must run in CI to download
  them.
- Lychee link checking fails on Fumadocs-style relative links (`./skills`
  instead of `./skills.mdx`) because it looks for files literally on disk. A
  custom link checker or `.lychee.toml` config may be needed for internal links.
- The `release.website.yaml` was only watching `site/**`, not `docs/**`. This
  meant docs-only changes merged to main would NOT trigger a site rebuild — a
  silent deployment gap since Fumadocs sources content from `../docs`.
