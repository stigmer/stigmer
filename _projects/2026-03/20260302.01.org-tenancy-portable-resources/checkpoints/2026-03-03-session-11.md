# Session Notes: 2026-03-03 (Session 11) — T01.8: CLI Org Global Flag, Runtime Injection, and Cleanup

## Accomplishments

- Removed speculative `ContextConfig.Environment` field (YAGNI — no domain semantics)
- Promoted `--org` to root persistent flag, eliminating duplication across 11+ commands
- Injected `STIGMER_ORG_ID` into agent execution runtime (`prepareAgentExec`) and SDK synthesis env (`synthesize.go`)
- Updated all seedpack skill docs (agent-creator, mcp-server-creator) to use `STIGMER_ORG_ID` instead of asking user or hardcoding `org: local`
- Fixed all test references to removed `Environment` field
- Updated `next-task.md` with T01.9 documentation scope

## Decisions Made

- **STIGMER_ORG_ID is outbound-only**: Injected by CLI into agent runtime, not read by CLI from user's shell. CLI's own org resolution chain remains: `--org flag > stigmer.yaml metadata.org > context.organization > Backend.Cloud.OrgID > error`
- **OrgOverride kept as data field in agentExecFlags**: Removed the flag registration but kept the struct field. Run handlers set it from `GetOrgFlag(cmd)` in their closures — minimal invasiveness
- **Restructured executeProjectApply**: Moved org resolution before synthesis so `STIGMER_ORG_ID` is available in SDK env. Replaced `establishBackendConnection` with `connectAndEnsureDaemon`
- **Skill docs eliminate "local vs cloud" org distinction**: Agents always use `STIGMER_ORG_ID`. Backend type is a connectivity concern, not an org identity concern
- **CLI docs deferred to T01.9**: configuration.md, configuration-cascade.md, and new "what-is" docs are scope-creep for this task

- `config.go`: Removed `Environment` field from `ContextConfig`
