# Session Notes: 2026-03-03 (Session 15) — Seedpack Bootstrap and Organization Hierarchy Fix

## Accomplishments

- Diagnosed and fixed the seedpack bootstrap chicken-and-egg problem that caused `stigmer draft skill` and `stigmer list agents` to fail after the org-tenancy migration
- Established a clear architectural boundary: Organization is not a project resource — it sits above Project in the hierarchy and must be applied independently
- Implemented two-phase seedpack bootstrap: organizations first, then project members
- Made `stigmer apply -f` work for Organization resources without requiring an org context
- Improved draft command error diagnostics with actionable troubleshooting steps

## Decisions Made

- **Organization removed from declarative project apply**: A project should never create its parent. Organization → Project → Members is the hierarchy. This eliminates the chicken-and-egg problem and simplifies the mental model.
- **Manual cleanup via `stigmer server reset`**: No automatic migration of old `local` resources. The reset command already clears the data directory and re-bootstraps fresh. Clean, explicit, user-controlled.
- **Conditional org resolution**: `stigmer apply -f` no longer requires org context when all items are Organization kind. This is essential for Phase 1 of seedpack bootstrap (the org doesn't exist yet).
- **Two-phase bootstrap in daemon.go**: Phase 1 applies organizations via `apply -f`, Phase 2 applies the project via `apply --config`. Organization YAMLs in Phase 2 are harmlessly skipped by the declarative flow.

## Key Code Changes

- `apply_declarative.go`: `detectResourceItems` skips Organization kind with warning message guiding to `stigmer apply -f`
- `apply_file.go`: Added `requiresOrgContext()` helper; `resolveOrganization` call is now conditional on non-Organization items being present
- `daemon.go`: `EnsureSeedpackBootstrapped` now runs two phases — organizations dir via `apply -f`, then project via `apply --config`
- `draft_handler.go`: `displayDraftAgentNotFoundError` now accepts `orgID`, shows searched org, and provides 3 troubleshooting steps

## Learnings

- The OSS server does not validate org existence when creating resources — it treats `metadata.org` as a string, not a foreign key. This means the chicken-and-egg ordering was not causing server-side errors, but the CLI's org context resolution was the real issue.
- Organization resources are self-identifying by slug on the server (slug-based lookup in `LoadForApplyStep`). The `OrgID` passed from the CLI is only used to fill `metadata.org` when empty — safe to omit for Organization resources.
- The seedpack bootstrap runs `stigmer apply` as a child process with `STIGMER_SKIP_SEEDPACK_BOOTSTRAP=1` recursion guard. The child's `EnsureRunning` → `EnsureSeedpackBootstrapped` is safely no-op'd.

## Open Questions

- Should we add an explicit org existence check on the server side in the future? Currently, resources can be created under non-existent orgs in OSS.
- Should the seedpack's `organizations/` directory convention be documented as a pattern for user projects?
