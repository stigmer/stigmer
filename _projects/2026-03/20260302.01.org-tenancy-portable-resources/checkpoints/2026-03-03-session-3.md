## Decisions Made

- **ResourceChangeRecord → ApiResourceReference**: The new tenancy proto removed `ResourceChangeRecord` entirely. Adapted Java code to use `ApiResourceReference` directly, mapping the former `resource_id` field to `org`, since `ApiResourceReference` carries `(org, kind, slug, version)` semantics.
- **Pause on reconciliation rearchitecture**: The ProjectSpec fundamentally changed — it no longer embeds full resource definitions (agents, workflows, etc.) but uses lightweight `ApiResourceReference` members. This invalidates the entire cloud reconciliation subsystem. Decided to document and defer rather than brute-force a broken solution.
- **Document for future session**: Created a detailed migration document capturing completed work, remaining challenges, and recommended approach for the reconciliation rearchitecture.

## Discoveries

1. **ResourceChangeRecord was removed from the proto** — Not called out in the T01.1 OSS plan since it was a proto design simplification, but it required adapting 3 Java files in the cloud repo.
2. **ProjectSpec fundamentally redesigned** — The biggest surprise. The new `tenancy/project/v1/spec.proto` replaces embedded resource definitions (agents, workflows, mcp_servers, skills) with a flat `repeated ApiResourceReference members` field. The `runtime` field was also removed. This means:
   - `DesiredState` / `ActualState` extractors that iterate resource-specific lists are broken
   - `DependencyGraph*` components that analyze inter-resource dependencies need rethinking
   - `ReconciliationPlan` builder that generates per-kind change sets needs adapting
   - The entire reconciliation model shifts from "Project manages resources" to "Project tracks membership references"

## Blockers

- **Cloud build fails**: `ProjectReconciliationService` calls methods (`getWorkflowsList()`, `getMcpServersList()`, etc.) that no longer exist on the new `ProjectSpec`. Requires rearchitecting the reconciliation subsystem.
- **Pre-existing cloud build failures**: Several unrelated build errors exist in `SkillPushHandler.java`, `CreateExecutionContextStep.java`, `WorkflowExecutionSendSignalHandler.java`.

## Open Questions

- Should the cloud reconciliation service be simplified to only track membership (add/remove references) rather than manage resource lifecycle?
- Does the reference-based ProjectSpec mean that resource CRUD moves out of Project reconciliation entirely?
- What replaces `runtime` in the new model?
