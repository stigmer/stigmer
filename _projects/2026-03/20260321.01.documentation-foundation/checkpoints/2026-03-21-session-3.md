## Decisions Made

- **Three rules, not five** — The original Phase 3 plan called for 5 rules (`write-documentation`, `review-documentation`, `write-quickstart`, `write-sdk-guide`, plus standards). Consolidated to 1 auto-apply + 2 action rules. Content-type-specific template enforcement lives inside the write rule via path detection. Mirrors the CLI pattern (`coding-guidelines.mdc` + `implement-stigmer-cli-features.mdc`).
- **Rule directory `.cursor/rules/docs/`** — Follows the existing convention of `.cursor/rules/client-apps/cli/` for domain-scoped rules.
- **Role as process, rules as enforcement** — The role file (`_roles/002_document_writer.md`) was duplicating ~60% of `docs/standards/documentation-standards.md` verbatim. Rewrote to focus on behavior and process, referencing standards docs for actual rules. Zero maintenance debt.
- **Auto-apply rule stays lean** — 110 lines. Fires on every doc edit, so it must be concise — guardrails, not handbook. Heavy lifting in the action rules.

## Learnings

- Auto-apply rules should be lean because they inject into context on every file edit. Verbose rules waste context window on every interaction.
- Separating "what the rules are" (standards doc) from "who enforces them" (cursor rules) from "how to behave" (role file) eliminates maintenance debt. Single source of truth.
- The CLI rules pattern (`coding-guidelines.mdc` + `implement-stigmer-cli-features.mdc`) is a good model for other domain-specific rule sets.
