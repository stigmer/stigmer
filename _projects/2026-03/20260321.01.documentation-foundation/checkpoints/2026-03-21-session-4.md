## Decisions Made

- **Multi-word terminology enforcement only** — Single-word prohibited terms ("server", "token", "module", "pipeline", etc.) generate massive false positives because they have broad contextual exceptions. The automated linter only flags multi-word prohibited terms ("agent run", "tool connector", "chat session", etc.) which are unambiguously wrong. Single-word enforcement stays with the Cursor auto-apply rule which has full document context.
- **MDX-only strict mode** — `make lint-docs` targets `docs/**/*.mdx` only (2 files today). Pre-existing `.md` files predate the standards and would fail ~377 checks. The content migration project uses `make lint-docs-audit` to get the full picture.
- **MD025 front_matter_title workaround** — markdownlint's MD025 (single-h1) was counting the YAML frontmatter `title:` as an H1, creating false positives. Fixed by setting `front_matter_title: ""` in the config.
- **Linter script at repo root** — `scripts/lint-docs.mjs` lives alongside existing `scripts/` files. Dependencies are root devDeps, not a separate workspace.
- **No site/ changes** — Linting is a repo-wide concern. All tooling lives at repo root, not inside `site/`.

## Learnings

- markdownlint-cli2 treats frontmatter `title:` as an H1 by default — need `front_matter_title: ""` to disable this. Not documented prominently.
- Single-word terminology enforcement is impractical for automated linting when the prohibited terms overlap with general programming vocabulary. Human review (Cursor rules) is the right enforcement layer for contextual terms.
- `find -path` does not support `**` globs the way shell globbing does — needed a recursive directory walker in Node.js instead.
