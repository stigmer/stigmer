## Decisions Made

- **Surgical `NewDisconnectedContext` (Option A over Option B)**: Applied cancellation safety only to the new EC cleanup call. Comprehensive cancellation safety for all cleanup operations (Option B) was deferred to T05 because `completeExternalActivity` has mixed failure semantics (must-succeed on success path, best-effort on failure path). A naive `defer` restructuring would cause a behavioral regression on the success path.
- **Store-direct pattern**: Activity uses the store directly (not downstream gRPC client), consistent with all existing local activities (`LoadAgentExecution`, `UpdateExecutionStatus`).
- **Shared activity in `executioncontext` domain**: Activity placed in `executioncontext/temporal/activities/` rather than duplicated in AE and WE, matching the Java codebase structure.
- **Explicit calls at exit points (not `defer`)**: The `deleteExecutionContext` call is placed explicitly before each `return` in `Run()`, not in a `defer` block. This is consistent with the existing cleanup pattern and avoids the complexity of consolidating all cleanup into a single deferred block.

## Learnings

- Java Cloud's `DeleteExecutionContextActivity` was defined (interface, impl, workflow `finally` calls) but never registered in either worker config. This is a silent failure pattern in Temporal: if an activity implementation isn't registered on the worker, the activity call just fails without a clear "not registered" error from the workflow's perspective. This is worth watching for in future activity additions.
- The `LoadAgentExecution` activity added in T03 was also missing from its BUILD.bazel srcs -- another silent issue that only surfaces during Bazel builds (not `go build`).
