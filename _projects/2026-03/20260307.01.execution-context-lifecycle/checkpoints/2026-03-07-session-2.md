- Both pipelines now create a fully-merged ExecutionContext before persisting the execution

## Decisions Made

- **Shared merge in `libs/go/envmerge/`**: Extracted the three-layer merge logic into a pure, reusable function rather than duplicating it in both pipeline steps. This keeps domain steps thin and the merge logic testable independently.
- **AE uses gRPC clients, WE uses store directly for Workflow lookup**: Preserved each domain's existing data access pattern. The AE controller already used downstream gRPC clients for cross-domain lookups; the WE controller loaded Workflows from the store directly.
- **Empty EnvironmentValue entries are filtered**: The proto `EnvironmentValue.value` can be empty (used as schema declarations with only a `description`), but `ExecutionValue.value` has `min_len=1`. Empty values are silently filtered during the merge.
- **ExecutionContext always created**: Even if all layers produce an empty data map, the ExecutionContext is still created. This provides a consistent contract for downstream consumers (agent-runner always has a context to query).

## Key Code Changes

- `backend/libs/go/envmerge/merge.go`: New file. Pure function `MergeEnvironmentLayers(templateData, environments, runtimeEnv) -> map[string]*ExecutionValue`. Three-layer precedence: template defaults < environment_refs < runtime_env.
- `backend/services/stigmer-server/pkg/domain/agentexecution/controller/create_execution_context_step.go`: New file. Resolves agent_instance_id from pipeline context or session lookup, loads AgentInstance + Agent, resolves environments by reference, merges, creates ExecutionContext via downstream client.
- `backend/services/stigmer-server/pkg/domain/workflowexecution/controller/create_execution_context_step.go`: New file. Resolves workflow_instance_id from execution spec, loads WorkflowInstance (via downstream client) and Workflow (via store), resolves environments by reference, merges, creates ExecutionContext.
- `downstream/session/client.go`, `downstream/agentinstance/client.go`, `downstream/workflowinstance/client.go`: Added `Get(ctx, id)` methods (and `queryClient` fields where needed).
- `agentexecution_controller.go`, `workflowexecution_controller.go`: Added `environmentClient` and `executionContextClient` fields and updated setter methods.
- `create.go` (both AE and WE): Inserted the new step into the pipeline after `setInitialPhaseStep` and before persist/attachments.
- `server.go`: Created environment and executioncontext client instances, injected into both controllers.

## Learnings

- The WE and AE domains have subtly different data access patterns despite nearly identical functional needs. WE loads Workflow from the store directly because it's in the same service boundary; AE loads Agent via a downstream gRPC client. Respecting these existing patterns avoids coupling surprises.
- The `EnvironmentValue` -> `ExecutionValue` conversion requires careful handling: EnvironmentValue has a `description` field and allows empty `value`; ExecutionValue has neither.
