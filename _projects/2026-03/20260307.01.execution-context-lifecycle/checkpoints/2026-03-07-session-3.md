## Decisions Made

1. **Native types over proto for workflow input**: The workflow input never crosses a language boundary (Go starts Go workflows, Java starts Java workflows). Proto would add build friction (protoc + stub generation) for no interoperability benefit. Activity inputs that DO cross the polyglot boundary already use proto correctly.

2. **WE workflow input unchanged**: Keep full `WorkflowExecution` proto for WE workflows (minus cleared `runtime_env`). The `ExecuteWorkflow` activity is implemented by `workflow-runner` and expects the full proto. Changing it would require cross-service changes for no additional security benefit (the field is already empty).

3. **LoadAgentExecution as local activity (not regular activity)**: Runs in-process on the same worker, avoids task queue routing overhead. Follows the established `UpdateExecutionStatus` local activity pattern.

## Learnings

- The Java cloud `completeExternalActivity` already used a string summary (not the full proto), so the stale-data bug only existed in the Go OSS version. Always verify assumptions across both codebases before planning.
- Proto messages are immutable in Java. Clearing runtime_env requires `execution.toBuilder().setSpec(spec.toBuilder().clearRuntimeEnv().build()).build()` + `context.setNewState()`.
- The cloud Bazel build has pre-existing strict dependency errors in unrelated files. These are not caused by our changes.
