## Decisions Made

### Use proto types directly (no custom data interfaces)
Every existing hook in `@stigmer/react` returns proto types as-is, wrapped only with React-specific metadata. This hook follows that pattern: the aggregated result is a `UsageMetrics` proto object via `create(UsageMetricsSchema)`, not a custom interface. Zero field duplication.

### Extract `aggregateUsage()` as a pure function
Separating the aggregation logic from the React hook makes it independently testable without React, and reusable by non-React consumers if needed.

### Naming: `UseExecutionUsageReturn` not `ExecutionUsageSummary`
A proto message named `ExecutionUsageSummary` already exists in `io.proto` for session-level usage reports — a different concept. The hook return type is named `UseExecutionUsageReturn` to avoid collision and follow the `Use*Return` convention.

### `llmCalls` sorted by `timestamp` not `sequence`
`LlmCallMetrics.sequence` is 1-based within each agent's scope. When concatenating across main + sub-agents, sequence numbers overlap. Sorting by ISO 8601 `timestamp` gives a globally meaningful order.

### Short-circuit when no sub-agent usage exists
When no sub-agents have usage data, the main agent's `UsageMetrics` object is returned directly — no new object allocation, no unnecessary computation.

## Learnings

- The `toolResultCharsTruncated` field is `bigint` (from proto `int64`), not `number`. Aggregation must use `BigInt` arithmetic (`0n`, `+=`).
- The `create()` function from `@bufbuild/protobuf` is the established pattern for constructing proto message instances — used by `useSubmitApproval` and `useCreateAgentExecution`.
- The codebase convention is clear: hooks return proto types wrapped with React-specific state, never parallel data interfaces.
