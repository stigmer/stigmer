## Decisions Made

- **Cloud-only credential setup**: In local mode, the user's own git config is untouched. Credential helper is only configured when `is_local_mode=False` and a GitHub token is present.

- **`GitMetadata` over `ProvisionResult`**: The `git_credentials_configured` field lives on `GitMetadata` (not `ProvisionResult`) because it's git-specific metadata. Phase 2 will access it via `result.git_metadata.git_credentials_configured`.

- **Non-fatal failures**: Credential setup failure (any of the three steps) logs a warning and returns `False`. The clone still succeeds and the workspace is usable — the agent just can't push. Consistent with the existing `_setup_git_excludes` pattern.

- **Remote URL cleanup**: After clone, `git remote set-url origin <clean_url>` removes the embedded token. This prevents accidental token leakage if the agent runs `git remote -v` and includes the output in responses.

- **Credential file location**: `/home/daytona/.git-credentials` on the local sandbox FS. Does not survive sandbox restarts, but neither does the separated git dir — re-provisioning handles both.

## Learnings

- **Token-in-URL persists in git config**: When you `git clone https://x-access-token:TOKEN@github.com/...`, git stores the full URL (with token) as `remote.origin.url`. AD-05 env var stripping doesn't affect this. The original plan's assumption that stripping `GITHUB_TOKEN` from env vars "kills push capability" was wrong — push works via the URL.

- **Response key collision in test fakes**: The `_GitBackend` substring-matching response system can cause collisions. The credential file write command contains both `.git-credentials` and `printf`. Filtering by `".git-credentials"` alone matches the `credential.helper` config command first (since it also contains `.git-credentials` in the file path). Fixed by adding `">" in c` to distinguish writes from config commands.
