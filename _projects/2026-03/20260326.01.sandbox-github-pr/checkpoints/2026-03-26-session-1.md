## Decisions Made

- **`is_local_mode` parameter** (not type-checking or path detection): The provisioner already tracks deployment mode via `is_local_mode`. Passing this to `git_source.provision()` is explicit, testable, and avoids coupling `git.py` to sandbox internals.

- **Global git config** (not per-repo): `safe.directory='*'` and `core.fileMode=false` are set globally before any git operations. In a Daytona sandbox, all repos share the same volume constraints, so global config is appropriate and simpler than per-repo.

- **Stale pointer = re-clone** (not repair): When a `.git` pointer file exists but the target git dir is gone (sandbox restart), we re-clone rather than trying to reconstruct the git state. This is acceptable because agents push all commits to the remote before execution ends.

- **`git rev-parse --absolute-git-dir`** for excludes: Instead of hardcoding `.git/info/exclude`, we resolve the actual git directory path. This works transparently for both normal clones (`.git` directory) and separated clones (`.git` pointer file).

- **Removed `_scoped_path` helper**: Dead code after the excludes mechanism changed from `backend.read_file`/`write_file` to shell-based operations.

## Learnings

- **Daytona volumes use `mountpoint-s3`** (AWS S3 FUSE mount). The key missing operation is `rename()` (ENOSYS, errno 38), not `flock()` as initially hypothesized. `flock()` actually works on these volumes.

- **Git's "dubious ownership" check** (CVE-2022-24765) triggers because FUSE volumes show files owned by `nobody:nogroup` while git runs as `daytona`. This is a separate issue from the `rename()` failure.

- **`chmod()` fails silently** (EPERM) on the volume. Git's `core.fileMode` must be set to `false` to prevent false-positive status changes from permission tracking.

- **`git clone --separate-git-dir` expects to create the target directory itself**. Pre-creating the exact target path (not just the parent) causes git to refuse.
