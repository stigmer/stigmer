## Decisions Made

1. **Only design tokens extracted from `globals.css`** — the `:root` and `.dark` CSS variable blocks. The `@theme inline` bridge, `@custom-variant dark`, framework imports, and body styles stay in the app's CSS.

2. **`@theme inline` stays in `globals.css`** — it maps CSS variables to Tailwind utility classes and references Next.js-specific font variables (`--font-geist-sans`, `--font-geist-mono`). Moving it would couple the theme package to Next.js font loader infrastructure.

3. **No React theme context created** — Planton needed `PlantonThemeContext` for MUI mode bridging (`{ mode: 'light' | 'dark' }`). Stigmer uses Tailwind's CSS-class-based dark mode (`.dark` on document root), so JavaScript mode detection is unnecessary.

4. **No `cva`/`VariantProps` re-export** — these are component authoring tools from `class-variance-authority`, not theme concerns. Components import CVA directly.

5. **`ClassValue` re-exported** — allows downstream packages to type `className?: ClassValue` props without declaring a direct `clsx` peer dependency.

## Learnings

- CSS `@import` of workspace packages through Tailwind v4's `@tailwindcss/postcss` plugin works correctly. The technical risk identified in the plan (whether PostCSS would resolve workspace symlinks) did not materialize.
- Tailwind v4's CSS-first configuration model creates tight coupling between design tokens, the `@theme inline` bridge, and framework-specific font variables. Clean separation requires thoughtful boundaries.
