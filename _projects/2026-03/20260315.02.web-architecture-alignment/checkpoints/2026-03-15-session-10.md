### Phase 7 (Revised): Domain UI Components + List/Detail View Enhancement — COMPLETED

Implemented the full revised Phase 7 plan: enriched `@stigmer/agent-ui` with embeddable card and overview components, replaced the generic resource card system with domain-aware rendering, improved all three detail views, and cleaned up the last deprecated code.

## Decisions Made

1. **Agent gets full domain library treatment; Skill and MCP Server stay Console-only** — Agent has clear embedding cases (agent picker, marketplace, admin dashboards). Skill and MCP Server are developer/infrastructure-focused with no external consumer yet. They will be promoted to domain libraries when marketplace work begins.

2. **Separate card types for separate data contexts** — Domain card (`AgentCard`) accepts full `Agent` proto for embedding. Console search card (`AgentSearchCard`) accepts `SearchResult` for list pages. Not duplication — fundamentally different data access patterns.

3. **Card grid for agents, list for skills/MCP servers** — Agents are browse/discover resources (like npm, Docker Hub). Skills and MCP servers are operational, text-heavy resources better served by list layout.

4. **Internal primitives duplicated, not shared** — `agent-ui` has its own `badge.tsx`, `collapsible.tsx`, `section.tsx` separate from `agent-execution-ui`. Duplication is acceptable for small surface area, avoids coupling between packages.

5. **OrgProvider migrated to context-based transport** — This was the last consumer of the deprecated singleton transport pattern, enabling full deletion of `transport.ts` and `org-service.ts`.
