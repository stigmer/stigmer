## Decisions Made

1. **Session table stays Console-only** — `@stigmer/session-ui` keeps Layer 1 + Layer 2 (service factory + hook). Rationale: a sessions table is Console-specific admin UI, not an embeddable component. Platform builders want session replay viewers, not admin tables. The table requires too much configurability (columns, filters, pagination style) to be a clean embeddable. Embeddable session components (replay viewer) are a separate future task.

2. **Scoped to API surface** — the `SessionQueryController` only supports `list(pageSize, pageToken, tags[])` and `listByAgent(agentId, pageSize, pageToken)`. No server-side text search, sorting, date range, or status filter. Built what the API supports, documented the gaps.

3. **No status column** — Session has no lifecycle status field; it's derived from the latest `AgentExecution`. Showing it requires N+1 queries. Deferred until server adds a denormalized `lifecycle_status` field.

4. **`useSessionPage` uses `useQuery`** (not `useInfiniteQuery`) — tables use page-based navigation, not "load more". `useSessionList` (infinite) remains untouched for `RecentSessions` and `AgentSessionHistory`.

5. **Agent filter via search API** — uses `useAgentQueryService().search()` with empty query to populate the dropdown. When an agent is selected, `useSessionPage` switches from `service.list()` to `service.listByAgent()`. Filter change resets page to 1.

## Learnings

- The Session proto has no lifecycle status — it's a conversation context, not a stateful resource. Status lives on AgentExecution. This is a correct domain boundary (Session IS just a container), but it creates a UX gap in list views.
- `agentInstanceId` on Session is a runtime reference, not a user-friendly display name. Showing it as monospace text is functional but not ideal — server needs to denormalize agent display info.
- The existing `useSessionList` (infinite query) and `useSessionPage` (page-based query) can coexist cleanly because TanStack Query's key hierarchy (`sessionKeys.lists()` vs `sessionKeys.pages()`) keeps them independent.

## Server API Gaps Identified

- `ListSessionsRequest` needs: `sort_by`, `sort_order`, `search_text`, `created_after`/`created_before`
- Session response needs denormalized `agent_display_name` or `agent_slug`
- Session needs derived `lifecycle_status` field (from latest AgentExecution)
- These block: text search, column sorting, date range filtering, status filtering, agent name display
