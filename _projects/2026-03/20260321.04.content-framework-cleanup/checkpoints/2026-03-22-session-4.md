## Decisions Made

| Decision | Rationale |
|---|---|
| Visual container (Option A), not sub-components (Option C) or focused list (Option B) | All 5 concept pages share identical problem section structure. Content authors already follow it organically. A wrapper provides the visual signal without fighting MDX composition. |
| `children` only, no other props | Simplest API. Heading stays in MDX (TOC constraint). Content inside is standard markdown. |
| `<section>` not `<aside>` | Content section, not supplementary info. DefinitionBanner uses `<aside role="note">` for supplementary thesis statement. |
| `fd-muted-foreground` left bar, `bg-fd-muted/30` background | Differentiates from DefinitionBanner (`accent` bar, `bg-fd-card`, `shadow-md`). ProblemStatement is less prominent. |
| No `not-prose` | ProblemStatement wraps prose content (paragraphs, code blocks, lists). Prose styling must be inherited. |
| Departed from plan's `<Problem>` sub-component sketch | Actual content includes code blocks, narrative paragraphs, rich bullet text — awkward as structured child components. MDX composition with JSX sub-components is the most fragile pattern. |

## Learnings

- MDX 3 (Fumadocs 15.x) supports markdown content inside JSX components when there's a blank line after the opening tag — this is what makes the visual container pattern work.
- The "visual container for children" pattern is simpler and more maintainable than structured sub-components when the internal structure is already consistent across pages.
