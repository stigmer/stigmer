# Deep Research: AI Agent Execution UI — Library Landscape, Adapter Patterns, and Gap Analysis

## Research Objective

We are building **Stigmer**, an infrastructure platform for AI agents and automation workflows. Stigmer runs agents **on the server** (Python/LangGraph/Temporal) and streams execution data to a browser-based web console via **gRPC-Web** (Connect-RPC, Protobuf).

We need to build a **web UI for monitoring agent executions in real-time**. This is NOT a simple chatbot — our agent executions include:

- **Streaming messages** (token-by-token from the server)
- **Tool calls** with arguments, results, and multiple statuses (pending, running, completed, failed, waiting for approval, skipped)
- **Human-in-the-loop (HITL) approval gates** — the execution pauses, shows the user what the agent wants to do, and waits for approve/skip/reject
- **Sub-agent delegation** — a parent agent spawns child agents, each with their own message streams and tool calls (nested execution trees)
- **Execution lifecycle phases** — PENDING → IN_PROGRESS → WAITING_FOR_APPROVAL → COMPLETED/FAILED/CANCELLED
- **Thinking/reasoning blocks** — extended thinking content that should be collapsible
- **Artifacts** — files, code, diffs produced by the agent
- **Token usage and cost tracking** per message and per execution
- **Session management** — browsing past sessions and replaying their execution history

Our current tech stack is: **React 19, Next.js 16, TailwindCSS v4, shadcn-ui, Connect-RPC (gRPC-Web), Protobuf**.

We have a working web console with hand-built execution monitoring components. But we are exploring whether we should **replace our custom components with a popular AI chat UI library** and build a thin **adapter layer** that converts our gRPC/Protobuf data into the library's expected format.

The motivation is twofold:
1. **For our own web console**: Use battle-tested, accessible, well-maintained components instead of building everything from scratch
2. **For our consumers**: Ship a library (e.g., `@stigmer/assistant-ui-adapter`) so developers can embed Stigmer execution views in their own apps with minimal code

### 2. The "Adapter Pattern" — Is This the Right Architecture?

We're considering this architecture:

```
Stigmer Server (gRPC) → Adapter Layer → Popular UI Library → User's Browser
```

Where the adapter converts our Protobuf types into the library's expected format (e.g., `ThreadMessageLike` for assistant-ui, or the data format expected by Vercel AI SDK's `useChat`).

Research questions:
- **Is this adapter pattern used by other companies/products?** Find real-world examples of products that wrap a popular UI library with their own data source adapter.
- **What are the tradeoffs?** Coupling to a third-party component library vs. building your own.
- **When does this pattern break down?** At what level of customization does the adapter become more complex than building from scratch?
- **How do other agent platforms handle their UI?** (LangSmith, LangGraph Studio, Autogen Studio, CrewAI, AgentOps, Langfuse, Helicone, Arize Phoenix, etc.) — do they use existing UI libraries or build their own?

## Known Information (Starting Points)

- **assistant-ui**: Uses `ExternalStoreRuntime` for custom backends. Has `makeAssistantToolUI` for custom tool renderers. Uses shadcn-ui styling conventions. MIT licensed. React-only.
- **Vercel AI SDK**: `useChat` hook with transport abstraction. More low-level (hooks, not full components). Good for simple chat, unclear for complex agent execution.
- **PI mono** (https://github.com/badlogic/pi-mono): An open-source agent platform that built their own web-ui using **Lit Web Components** + Tailwind. They run agents in the browser (client-side). Good UX patterns (tool renderer registry, streaming container split, thinking blocks, artifact system) but incompatible framework (Lit vs React) and architecture (client-side vs server-side agents).
- **Stigmer's current execution UI**: React 19 + Next.js 16, with hand-built components for ExecutionStream, MessageEntry, ToolCallCard, SubAgentCard, ApprovalControls. Works but maintenance-heavy and not shippable as a library.
