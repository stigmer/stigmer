# AI Agent Execution UI: Library Landscape, Adapter Patterns, and Gap Analysis for Stigmer

## Context and requirements for Stigmer’s execution UI

**Stigmer** (server-run agents; browser console via gRPC-Web/Connect-RPC + Protobuf) is implementing a *real-time execution monitor* that is materially broader than a “chat UI.” The UI requirements you listed align more closely with an **event-sourced execution timeline + nested run tree** than with a linear chat transcript:

- **Incremental/streaming output** (token-by-token deltas, in-progress message parts, typing indicators).
- **Tool calls as first-class entities** with rich lifecycle states (pending/running/completed/failed/waiting-for-approval/skipped) and structured inputs/outputs.
- **Human-in-the-loop approval gates** where the run pauses and must resume from a user action.
- **Sub-agent delegation** producing nested execution trees (parent run → child runs), each with their own streams and tool calls.
- **Run lifecycle phases** beyond chat status (PENDING → IN_PROGRESS → WAITING_FOR_APPROVAL → COMPLETED/FAILED/CANCELLED).
- **Collapsible “thinking/reasoning” blocks**, plus **artifacts** (files/code/diffs) and **token+cost accounting**.
- **Session browsing + replay** (persisted event logs and deterministic re-render).

This shape matches what multiple “agent UI protocols” and “agent run UIs” have converged on: **typed event streams** (message deltas, tool start/end, state patches, handoffs) rather than “array of chat messages.” For example, **AG-UI** explicitly positions itself as an event-based protocol connecting agent backends to frontends across transports like SSE/WebSockets/webhooks. citeturn6view4turn5search17

## Landscape overview and comparison table

A key finding from the 2024–2026 ecosystem: most widely adopted projects fall into one of four buckets:

1) **Composable React chat toolkits** (strong UI primitives, tool-call rendering, theming)  
2) **Headless hook/tooling SDKs** (transport + streaming + tool invocation types, but minimal UI)  
3) **Agent “apps” and templates** (excellent UX references; not designed to embed as a library)  
4) **Legacy bot/messaging web clients** (rich activity/event rendering; often coupled to a specific protocol or license)

## Leading library deep dives

### assistant-ui

assistant-ui is the clearest “library-first” match to your current **React 19 + shadcn-ui conventions** and to the idea of distributing `@stigmer/assistant-ui-adapter`. The project positions itself as composable primitives (Radix-style) with built-in streaming, scrolling, attachments, keyboard shortcuts, and accessibility. citeturn16search14turn27search24

It also explicitly frames itself as compatible with multiple backends (including **AI SDK**, **LangGraph**, and custom protocols), which aligns with your desire to adapt **gRPC/Protobuf** events into a UI runtime. citeturn16search14turn27search24

Most importantly for Stigmer: assistant-ui explicitly targets “generative UI” and tool visualization, including inline approvals. citeturn16search14turn5search3

**Where it’s less obviously aligned** is the “agent execution monitor” aspect: nested run trees, multi-phase execution banners, replay controls, and lifecycle semantics are not described as first-class UI widgets in the primary docs you provided; they appear to be something you would layer on top via custom message parts/tool UIs and out-of-thread panels. citeturn27search3turn27search0

### CopilotKit and AG-UI

CopilotKit’s differentiator is that it treats “agent ↔ frontend interaction” as a **protocol + SDK ecosystem** problem rather than only a “chat components” problem. AG-UI describes itself as an open, event-based protocol with ~16 event types that can work over many transports (SSE/WebSockets/etc.), and is explicitly intended to connect “any agentic backend” to “user-facing applications.” citeturn6view4turn5search17turn5search26

For Stigmer—already streaming structured execution events—the protocol framing is attractive: instead of coercing your execution model into a chat-message array, you could map your Protobuf messages into AG-UI event types (message deltas, tool call start/end, state deltas, handoffs). citeturn6view4turn5search17turn5search26

However, adopting CopilotKit/AG-UI as a UI layer is a **bigger architecture bet** than “thin adapter to a chat library,” because it implies either:
- exposing AG-UI semantics as a first-class frontend contract, or
- maintaining a translation layer from Stigmer events to AG-UI events (and keeping up with protocol evolution). citeturn6view4turn5search17

### Vercel AI SDK UI

The AI SDK’s UI module (e.g., `useChat` in `@ai-sdk/react`) is ubiquitous and well supported, but it is intentionally **low-level** in UI terms: it gives you state, streaming, transports, and typed “parts,” and expects you to implement the UI. It documents that `useChat` was significantly updated in AI SDK 5.0 to a transport-based architecture. citeturn16search11

This is a good fit if Stigmer wants a **headless core** and is comfortable owning most UI. It is a weaker fit if you explicitly want to “replace custom components with a popular UI library,” because the AI SDK is not that UI library—it’s the substrate. citeturn26view0turn16search11

That said, the AI SDK’s “agent UI messages” and “tool invocation parts” patterns are directly relevant to your model: the official repo example shows branching on `invocation.state` for tool UI rendering. citeturn26view0

### LangChain agent-chat-ui

LangChain’s agent-chat-ui is valuable as a **reference implementation** for connecting to a graph-based agent runtime. It is explicitly a Next.js app that chats with a LangGraph server, and it documents configuration patterns (deployment URL, assistant/graph ID, auth). citeturn6view3turn8view2

It also calls out how to extend streaming hooks with authentication headers (via `useTypedStream`). citeturn8view2

For Stigmer, this is less a drop-in component library and more a **benchmark for UX and architecture** (streaming transcript + run controls + server connectivity), because its primary distribution is as an app/template (`npx create-agent-chat-app`). citeturn6view3turn8view2

### Bot Framework Web Chat

Bot Framework Web Chat is an outlier: it is older in the “LLM agent UI” sense, but it has a mature model for **message-like activities with intermediate streaming/livestreaming** and strong accessibility investments. It explicitly added “livestreaming response” and documents handling “contentless” interim streaming activities using typing indicators. citeturn24view0turn23search5

If Stigmer ever wanted a “universal event transcript renderer,” the “activity” model plus Adaptive Cards can represent approvals and interactive steps. citeturn24view0turn25view0turn23search1

The downside is strategic: it strongly assumes a Bot Framework integration path and terminology (Direct Line, bot secrets, activities). citeturn24view0turn25view0

## Adapter pattern analysis

### Is “Stigmer server → adapter → UI library” used elsewhere?

Yes—multiple projects in this space encode the same pattern, even if they don’t label it “adapter pattern.”

- **assistant-ui ExternalStoreRuntime** is explicitly described as a bridge between your own state management (Redux/Zustand/TanStack Query/etc.) and assistant-ui’s UI components, where you “own the state” and wire callbacks. citeturn27search0  
- assistant-ui’s **AI SDK integration** (`@assistant-ui/react-ai-sdk`) is itself an adapter: it advertises forwarding system messages and “frontend tools” to your backend via `AssistantChatTransport`, and contrasts that to the AI SDK’s default transport. citeturn27search19turn27search22  
- **NLUX** is built around adapters (`useAdapter`) and ships multiple adapter packages (e.g., LangChain adapter) to let the same UI connect to different backends. citeturn9view1turn11search5  
- **AG-UI** is a protocol-level version of the same idea: standardize the event stream and allow multiple transports and framework clients. citeturn6view4turn5search17  
- Even LangChain’s agent-chat-ui highlights a “passthrough/proxy” package approach for productionizing connectivity/auth, which is a deployment-side adapter. citeturn6view3turn8view2

### Tradeoffs for Stigmer

The adapter approach is attractive when:
- Your execution model can be represented as the library’s model with **bounded translation complexity** (e.g., message parts + tool calls).
- The library provides **high-value UI primitives** you don’t want to rebuild (scroll anchoring, streaming text behavior, accessibility and keyboard shortcuts, attachments pipeline). assistant-ui explicitly markets those “handled for you.” citeturn16search14
- You can expose your own extension points without forking (e.g., “tool renderer registry” / message-part renderers / supplemental panels).

The adapter approach becomes fragile when:
- Your domain model introduces **orthogonal axes** that the library doesn’t model: for Stigmer, that’s nested run trees, multi-phase run status banners, replay/timelining, and approval gating as a state machine independent of chat input.
- You must emulate features the library implements differently. A concrete assistant-ui example: issues indicate that some multi-thread/backing-store hooks are marked `unstable_*`, and users have experienced race conditions around thread initialization vs append. citeturn5search18turn27search5
- You need semantics the library can’t represent without invasive changes. Another concrete assistant-ui example: a reported incompatibility between ExternalStoreRuntime and branching because `ThreadMessageLike` lacks a `parentId` field in that model. citeturn27search13

### How other agent platforms approach UI

In practice, **agent observability and execution platforms mostly build bespoke UIs** rather than embedding generic chat libraries, because they need heavy timeline/tree visualization and rich filtering. For example:
- **Langfuse** is positioned as an “LLM engineering platform” for monitoring/debugging AI applications and is shipped as a complete platform (not a component kit). citeturn18search24  
- LangChain’s ecosystem provides application UIs like agent-chat-ui to interact with agent servers (again: an app/template). citeturn6view3turn8view2  
- assistant-ui explicitly states “optional chat history and analytics via Assistant Cloud,” implying a cloud+UI product pairing rather than purely a UI library. citeturn16search14turn27search24

This strengthens a pragmatic inference for Stigmer: **you will likely keep some custom execution-monitor UI** even if you adopt a chat toolkit for the transcript/composer portion.

## assistant-ui deep dive

### Runtime architecture and what it implies for server-pushed gRPC streams

assistant-ui frames its architecture as three pillars: frontend components, a runtime layer (state management connecting UI to LLMs/backends), and an optional cloud service for persistence. citeturn27search24

For Stigmer, the key question is whether the runtime can be driven by **server-pushed** events (gRPC streaming) rather than only request/response chat. The docs for **ExternalStoreRuntime** explicitly describe it as a bridge where “you own the state,” integrate any state library, and support “real-time streaming” and “progressive updates.” citeturn27search0

That is compatible with your model: you can treat the gRPC event stream as the source of truth and update the external store accordingly.

### Tool rendering and per-tool UI control

assistant-ui’s **tool UI** documentation describes a tool execution UI with loading states, progress tracking, user interaction, and error feedback, and emphasizes that tool UIs are an extension mechanism for “generative UI.” citeturn5search3turn27search18

This is the closest built-in concept to Stigmer’s “tool call card” requirement. In particular:
- It explicitly supports rendering tool invocations and handling intermediate states, which maps to your `pending/running/completed/failed` set (with nuance described below). citeturn5search3turn26view0
- It also explicitly mentions inline **human approvals**. citeturn16search14turn5search3

### Thread composition and customization

assistant-ui’s `Thread` component is described as a complete chat container combining message rendering, auto-scroll, composer input, attachments, and conditional UI states—and as “fully customizable and composable.” citeturn27search3turn16search14

This supports a Stigmer design where the “chat transcript” is rendered inside assistant-ui, while **execution-phase banners**, “run is waiting for approval,” token usage, and nested sub-agent panels are provided adjacent to (or injected around) the Thread container via composition.

### Token usage and cost tracking

assistant-ui’s AI SDK v6 integration docs explicitly call out rendering token usage on the client via `useThreadTokenUsage`, including an example of showing `usage.totalTokens`. citeturn27search22

That is directly aligned with your requirement for token/cost tracking, at least at the “thread level.” If you need token usage per message/tool/sub-agent, you would still need your own attribution model and UI.

### Maturity and breaking-change risk signals

assistant-ui is active and fast-moving, and there are concrete indicators of API churn and “unstable” surfaces:
- There are hooks and packages explicitly labeled `unstable_*` in public issues (e.g., `unstable_useRemoteThreadListRuntime`). citeturn5search18turn27search6
- Users have raised runtime edge cases (race conditions) around thread initialization vs append for remote thread list runtimes. citeturn5search18
- There are reported breaking changes around “Tools() API” between versions in 2025. citeturn5search14

This isn’t a condemnation—fast iteration is common in this space—but it does imply Stigmer should treat assistant-ui as a **semver-sensitive dependency** and invest in adapter-level integration tests and a pinned version strategy.

## Stigmer-specific gap analysis for assistant-ui

This gap analysis assumes you would drive assistant-ui using **ExternalStoreRuntime** (or a comparable custom runtime) while retaining Stigmer’s event log as the canonical data model. citeturn27search0

### What assistant-ui can likely handle natively with minimal custom code

**Streaming transcript UX (auto-scroll, progressive updates, “ChatGPT-like” message rendering)** is an explicit goal of the library. citeturn16search14turn27search3

**Tool call rendering as UI components** is explicitly supported, with documentation describing loading/progress/user interaction/error handling. citeturn5search3turn27search18

**Inline human approvals** are explicitly mentioned as a capability (“collect human approvals inline”). citeturn16search14turn5search3

**Attachments/artifacts as chat-adjacent items** have first-class mention as built-in “attachments” features (though Stigmer’s “diffs/files/artifacts” may exceed standard attachments). citeturn16search14turn5search6

**Thread-level token usage** is documented via `useThreadTokenUsage` (AI SDK integration). citeturn27search22

### What requires custom components on top of assistant-ui

**Execution lifecycle phases (PENDING → IN_PROGRESS → WAITING_FOR_APPROVAL → …)**  
assistant-ui has “status” concepts for chat sending/idle and thread states, but Stigmer’s lifecycle phases are richer and independent of simple request/response flows. You will likely implement:
- a run header/status banner outside Thread, and
- mapping to disable composer input when WAITING_FOR_APPROVAL (except for approval actions).  
This is best treated as **(b) a custom component outside Thread**, driven by your run state.

**Tool call multi-status model beyond “running vs finished”**  
assistant-ui’s tool UI focuses on execution UI with loading/progress/error, and AI SDK tool parts show example states like `input-available` / `output-available`. citeturn5search3turn26view0  
Stigmer’s additional statuses (skipped, waiting for approval) require a richer state machine and will likely be **(a) solvable via custom tool renderers** for those tool names, plus **(b) higher-level run gating UI**.

**Sub-agent delegation / nested execution trees**  
There is no primary-source evidence of a first-class “nested run tree” widget in assistant-ui docs; Thread is fundamentally a transcript container. citeturn27search3  
You will almost certainly need a **run tree panel** (collapsible tree of agents, each node showing message/tool timeline) as **(b) a custom component outside Thread**, possibly with deep-linking to the relevant message/tool segments.

**Session browsing + replay**  
assistant-ui has patterns for multi-thread and persistence (Assistant Cloud, custom thread list runtimes), but replaying historical runs as time-series playback is not described as a core capability. citeturn27search5turn27search24  
This is **(b) custom outside Thread**, likely requiring Stigmer’s own event storage + deterministic reducer.

**Thinking/reasoning blocks (collapsible)**  
assistant-ui can render markdown, tool outputs, and custom parts; but there is no primary-source description of “reasoning blocks” as a built-in UI primitive. citeturn16search14turn5search6  
This is likely **(a) solvable** by treating “thinking” as a special message/part type that your adapter maps into a custom renderer (collapsible panel), or **(b)** as a transcript decoration outside the core message bubble.

### Potential incompatibilities or “fork risk” areas

**Branching / parent-child message relationships with external stores**  
If Stigmer expects to support “what-if” branches or replays with forks, note that an assistant-ui issue reports ExternalStoreRuntime being incompatible with branching because `ThreadMessageLike` lacks a `parentId` field. citeturn27search13  
This is not an immediate deal-breaker (you said branching is not required now), but it is a **future-risk signal**: implementing full DAG message ancestry in assistant-ui may require upstream changes, extension patterns, or forking.

**Unstable surfaces in thread list runtimes**  
If your embedding library must include session browsing and custom persistence, assistant-ui’s multi-thread hooks include “remote thread list” patterns and are referenced in issues with `unstable_*` APIs and lifecycle race conditions. citeturn5search18turn27search5  
This is not necessarily incompatible, but it is a **maintenance risk** for an adapter library you ship to customers.

## Recommendations

### Best-fit ranking for Stigmer’s needs

**Top choice: assistant-ui**  
It is the closest match to your **React + shadcn** aesthetic and “ship as a library” goal, and it explicitly supports streaming, tool rendering, and inline approvals—features that are non-negotiable for Stigmer. citeturn16search14turn5search3turn27search0  
The recommended approach is to adopt assistant-ui for the “transcript + tool cards + composer” surface, while keeping Stigmer-native panels for run lifecycle, run trees, replay, and artifacts.

**Second choice: CopilotKit / AG-UI ecosystem**  
If Stigmer’s execution model is truly event-sourced and you want an industry-aligned compatibility layer, AG-UI’s typed event stream posture is conceptually aligned with your gRPC execution stream. citeturn6view4turn5search17  
This is most compelling if Stigmer plans to **standardize its frontend contract** around event types (and perhaps support multiple frontend frameworks). It is less compelling if you primarily want a React component kit and minimal ecosystem lock-in.

**Third choice: Vercel AI SDK UI as the headless base**  
If you decide the adapter complexity is too high (because execution trees + approvals + statuses overwhelm a transcript library), falling back to a headless SDK with maximal control is the safest long-term option. The AI SDK sets the standard for transports and tool invocation parts, but you must build nearly all UI yourself. citeturn16search11turn26view0

### Recommended architecture

A **hybrid** architecture minimizes lock-in and keeps your UI aligned with Stigmer’s execution semantics:

- **Canonical model:** Stigmer stores a typed **execution event log** (your Protobuf events), and the web console reduces that log into a view model (messages, tool calls, approvals, artifacts, run tree nodes).
- **UI composition:** Use a library (assistant-ui) for the transcript surface, but render:
  - Run lifecycle header / phase banners
  - Sub-agent tree navigator
  - Approval gate modal/panel with “approve/skip/reject”
  - Artifact browser + diff viewer
  - Replay scrubber/timeline  
  as Stigmer-owned components outside the library’s Thread. citeturn27search3turn27search0
- **Adapter layer:** `@stigmer/assistant-ui-adapter` should be a **mapping library + runtime implementation** (e.g., ExternalStoreRuntime) rather than “just data conversion,” because the runtime controls how streaming updates reconcile. citeturn27search0

### Custom components Stigmer will likely need regardless of library choice

Even with assistant-ui, primary sources suggest `Thread` is a chat container and not a full execution-monitor shell. citeturn27search3turn27search24  
Given your requirements, Stigmer will almost certainly own:

- **Execution tree UI** (nested runs, expandable/collapsible).
- **Run-phase orchestration UI** (phase banners, cancellation controls, “waiting for approval” gating).
- **Approval gate UX** that can resume or branch execution deterministically.
- **Artifact viewers** (diffs, code viewers, file download/preview), beyond basic attachments.
- **Replay controls** (time-based playback from stored events).
- **Cost model attribution UI** (per tool/per message/per sub-agent), unless you accept thread-level only. citeturn27search22

### Risk profile

- **Dependency and upgrade risk (assistant-ui):** High velocity, with evidence of unstable APIs and breaking changes around tools/thread runtime surfaces. citeturn5search14turn5search18turn27search13  
  Mitigation: pin versions, add adapter conformance tests (golden event logs → expected UI model), and avoid depending on `unstable_*` APIs in your public adapter if possible.

- **Strategic coupling (CopilotKit/AG-UI):** Strong benefit if you want protocol standardization; risk if you want minimal coupling and total control over UX semantics. citeturn6view4turn5search17

- **Build-vs-buy (AI SDK):** Lowest external UI dependency risk; highest internal UI maintenance burden. citeturn16search11turn26view0

### Emerging patterns worth tracking

- **Event protocol standardization (AG-UI):** The “agent ↔ frontend” contract is trending toward typed event streams, matching Stigmer’s execution event model. citeturn6view4turn5search17turn5search26  
- **Library-provided runtime bridges (assistant-ui ExternalStoreRuntime):** UI kits are increasingly shipping *runtime adapters* rather than only components, acknowledging that state management and streaming reconciliation are the hard part. citeturn27search0turn27search24  
- **Tool UI as first-class UI parts (AI SDK Agent UI messages):** The “message parts + tool invocation states” pattern is becoming the baseline for rendering tool calls and intermediate states. citeturn26view0turn16search11  
- **License tightening in popular “Open” apps (Open WebUI branding clause):** This is a cautionary signal when choosing dependencies intended for redistribution/embedding. citeturn22view0
