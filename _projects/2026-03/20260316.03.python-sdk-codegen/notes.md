## 2026-03-16 — Project Context and Design Notes

### Relationship to Codegen Pipeline

This is the fourth SDK language using the same codegen pipeline:

```
Proto files (apis/)
    ↓
proto2schema (Stage 1) → JSON service schemas + spec schemas
    ↓
sdk_client.go (Stage 2, Go)         → sdk/go/internal/gen/
sdk_client_ts.go (Stage 2, TS)      → sdk/typescript/src/gen/
sdk_client_java.go (Stage 2, Java)  → sdk/java/.../internal/gen/
sdk_client_python.go (Stage 2, Py)  → sdk/python/src/stigmer/_gen/   ← NEW
```

Stage 1 is shared. Only Stage 2 is new for Python.

### Existing Infrastructure: Python Proto Stubs

Python proto stubs already exist and are generated by `make python-stubs` in `apis/Makefile`:
- Location: `apis/stubs/python/stigmer/`
- Package: `stigmer-stubs` (has its own `pyproject.toml`)
- Dependencies: `protobuf ^6.32.0`, `grpcio *`
- Python: `>=3.11,<4.0`
- Buf config: `apis/buf.gen.python.yaml` (protobuf-python + grpc-python + pyi plugins)

The SDK will depend on `stigmer-stubs` for the generated proto types.

### Key Design Decisions (carry forward from Go SDK)

- **Domain naming**: `client.agent_executions` not `client.executions` — respect ubiquitous language
- **Attribute-style access**: Python convention is `client.agents` (property), not `client.agents()` (method call like Java)
- **Input type naming**: `AgentInput` (not `CreateAgentInput`) — same input for Create, Update, Apply
- **Dataclasses for inputs**: Python has `@dataclass` — perfect for input types, no builder pattern needed
- **Hybrid types**: Proto types for responses, dataclass types for inputs (ergonomic + clean)
- **Type hints**: Fully typed SDK, `py.typed` marker for PEP 561 compliance

### Python SDK API Surface Comparison

| Go SDK | TypeScript SDK | Java SDK | Python SDK |
|--------|---------------|----------|------------|
| `stigmer.NewClient(key)` | `new StigmerClient(key)` | `StigmerClient.builder(key).build()` | `StigmerClient(key)` |
| `client.Agent.Create(ctx, input)` | `client.agent.create(input)` | `client.agents().create(input)` | `client.agents.create(input)` |
| `client.AgentExecution.Subscribe(ctx, id)` | `client.agentExecution.subscribe(id)` | `client.agentExecutions().subscribe(id)` | `client.agent_executions.subscribe(id)` |
| `*stigmer.Error` | `StigmerError` | `StigmerException` | `StigmerError` |
| `stigmer.IsNotFound(err)` | `isNotFound(err)` | `StigmerException.isNotFound(e)` | `e.is_not_found()` or `is_not_found(e)` |

### Python Naming Conventions

- **Sub-client properties**: snake_case — `client.agents`, `client.agent_executions`, `client.mcp_servers`
- **Methods**: snake_case — `create()`, `get()`, `get_by_reference()`, `update()`, `apply()`, `delete()`, `list()`
- **Input classes**: PascalCase — `AgentInput`, `SkillInput`, `McpServerInput`
- **Error class**: `StigmerError(Exception)`
- **Internal modules**: underscore prefix — `_client.py`, `_transport.py`, `_gen/`

### PyPI Publishing — Simpler Than Maven Central

PyPI publishing is significantly simpler than Maven Central:
- **No GPG signing required**
- **No source/javadoc archives required**
- **No namespace verification** — first-come-first-served
- **Trusted Publishing** (OIDC) — zero secrets, zero API tokens
- **One GitHub Actions step** — `pypa/gh-action-pypi-publish`

Owner setup:
1. Create account at https://pypi.org
2. Register Trusted Publisher (GitHub repo + workflow file)
3. Done. No keys, no tokens, no secrets.

### Async Consideration

Python gRPC supports both sync and async:
- Sync: `grpc.insecure_channel()` + stubs
- Async: `grpc.aio.insecure_channel()` + same stubs

**Decision**: Start with sync-only. Add async as a follow-up (can be a separate `StigmerAsyncClient` or `AsyncAgentClient`). Most Python gRPC SDKs start sync.
