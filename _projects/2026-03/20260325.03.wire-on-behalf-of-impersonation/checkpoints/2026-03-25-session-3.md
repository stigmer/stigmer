## Decisions Made

- **ExecutionContext FGA**: Derived auth from parent execution, not a dedicated FGA model. ExecutionContext is ephemeral (1:1 with parent, created/deleted within execution lifecycle). Full FGA model would be over-engineering. Handler-level custom auth checks `can_view` on parent `agent_execution` or `workflow_execution`.
- **Dual-channel pattern (Python)**: System channel for operator-only operations (`updateStatus`), OBO channel for user-scoped reads. Clean separation of system vs user identity.
- **`can_update_status` permission**: New FGA permission restricts `updateStatus` to operators only. Status updates are machine/system operations, not user operations. Prevents accidental user-level access to status mutation.
- **Pipeline reorder**: `createAuthorizationTuples → createExecutionContext → persist` ensures FGA tuples exist before ExecutionContext creation (enabling derived auth) and `runtime_env` is cleared before persist (preventing secret leakage to MongoDB).
- **`buildAuthenticatedContext` in Go task builder**: Discovered missing auth headers on `task_builder_call_agent_activities.go` gRPC clients. Fixed with helper that injects both `authorization` and `x-on-behalf-of` headers.

## Learnings

- FGA authorization should be proportional to resource lifecycle. Ephemeral resources with 1:1 parent relationships can use derived auth instead of dedicated models — simpler, no tuple management overhead
- Go gRPC clients in the task builder were missing auth headers entirely. The `initGrpcConnection` created raw connections without interceptors. This was a latent bug masked by operator-level access
- Pipeline step ordering matters for security: FGA tuples must exist before any resource that depends on them for authorization, and secrets must be cleared before persistence
