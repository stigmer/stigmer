## Decisions Made

1. **Pre-render in renderer, not model**: The renderer owns both history and rendering. The Bubbletea model is a thin command relay (`ClearScreen` + `Println`). This is cleaner separation of concerns than the previous approach where the model received raw history items and rendered them.

2. **Single Println replaces N Println calls**: Traced Bubbletea v1.2.4's `tea.Sequence` implementation (`tea.go:420-446`) — each command goes through a blocking `p.Send()` round-trip. N individual `tea.Println` calls produce N separate stderr writes with visible flicker. Batching into one write eliminates this.

3. **Snapshot copy removed**: Pre-rendering to an immutable string eliminates the need for `make([]committedItem, len(r.history)); copy(...)`. Cleaner and avoids shared-pointer questions.

4. **Terminal resize re-commit deferred**: Mode-invariant items (AI messages, human messages, system messages) store pre-rendered text at the original terminal width. A resize-triggered re-commit would only reflow mode-variable items (tools, headers), creating an inconsistent visual. Proper resize support requires storing raw content for ALL items — a larger architectural change.

## Learnings

- Bubbletea's `tea.Sequence` spawns a goroutine that calls `p.Send()` for each command — blocking round-trips, not concurrent dispatch. This makes N-item sequences linearly slower than batched approaches.
- For mode-invariant text items, `renderCommittedItem` returns in ~3ns with zero allocs (just returning the stored string). The expensive items are headers (~40us, panel rendering) and tools (~6.5us, lipgloss styling).
- The rendering cost (1-2ms for 500 items) is negligible compared to the previous event-loop overhead.
