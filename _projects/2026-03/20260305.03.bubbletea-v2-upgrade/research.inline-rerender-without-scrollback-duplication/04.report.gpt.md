# Inline Terminal Re-rendering Without Scrollback Duplication

## Constraints that make “editing committed history” intrinsically hard

Modern terminal emulators conceptually maintain a *screen grid* (what’s currently visible) plus a *scrollback history* (lines that have scrolled off the top of the screen). In classic xterm-derived behavior, the *alternate screen buffer* is a separate screen grid that is exactly the size of the display and “contains no additional saved lines,” meaning you generally can’t scroll back through history while an application is on the alternate screen. citeturn21view9turn23search14

Once text has moved into scrollback history, most terminals do **not** provide a general-purpose mechanism for an application to “seek back” into scrollback and edit it in place. This limitation shows up in Q&A discussions as “there is no way” to mark a scrollback position and programmatically return to it as an addressable editing target. citeturn23search2

That constraint is the core reason your current “clear screen + replay entire transcript” approach duplicates scrollback:

- `CSI 2 J` (*Erase in Display, “Erase All”*) clears the **visible** screen grid, but it is not specified as “delete scrollback history,” and xterm documents a separate parameter `Ps=3` (*Erase Saved Lines*) for that behavior. citeturn21view0  
- When you replay the full transcript, you are producing new output lines. The old transcript remains in scrollback history, so users now see multiple copies when they scroll up.

So the key architectural truth for “inline mode, preserve scrollback” is:

If content must remain editable (expand/collapse, header late-resolution, approval collapse), it must remain in an area you can still rewrite (the current screen grid), **not** in scrollback. Once lines are “committed” and then scrolled off, treat them as immutable. citeturn23search2turn21view9

## How Ink re-renders and why it usually avoids scrollback duplication

### Ink’s render pipeline: “virtual output” + line-aware terminal updates

Ink builds a layout tree (Yoga-based) and renders it into a **virtual output buffer** before writing to stdout. In Ink’s source, the renderer creates an `Output` grid (width/height), draws nodes into it (`renderNodeToOutput`), and returns both:

- `output` (interactive/dynamic output)
- `staticOutput` (from `<Static>`, rendered separately)
- `outputHeight` (for cursor management and clearing decisions) citeturn10view1turn10view0

This is already an important design point for your use case: Ink keeps “what is currently on-screen” as a *model-owned render result*, rather than letting arbitrary stdout writes become untracked history. citeturn10view1turn10view0

Ink’s terminal updating loop is implemented in its `log-update` module. In its “standard” mode, Ink rewrites by:

1. returning to the bottom of the previous output (if it had moved the cursor for input),
2. erasing the number of lines it previously rendered, and
3. writing the new frame. citeturn12view1turn13view0

Concretely (paraphrased from the code), Ink writes sequences like:

- `ansiEscapes.eraseLines(previousLineCount)` (erase prior output region),
- then emits the new `str`,
- then emits a cursor suffix that moves the cursor back to the intended input location and shows it. citeturn12view1turn13view0

Ink also has an “incremental” mode that compares line-by-line and only rewrites lines that changed, using cursor movement, erase-to-end-of-line, and next-line operations to reduce flicker. citeturn12view1

**Why this matters for scrollback:** This update style largely does **not** append new lines to the terminal; it rewrites an existing region in place. That means the terminal’s scrollback doesn’t accumulate duplicates per frame in the way a “clear + reprint everything” approach does. citeturn12view1

### `<Static>` in Ink: explicitly “commit once, never update”

Ink’s `<Static>` component is explicitly designed for “write-once logs.” The docs describe it as “append-only” output: once a `<Static>` item is rendered, it won’t be re-rendered or removed; only *new* items appear below it. citeturn3view1

This maps almost one-to-one to Bubble Tea’s inline split:

- `<Static>` ≈ “committed region” (your `tea.Println` area)
- non-static components ≈ “active view” (your `View()` region)

and it implies the same constraint: you *avoid* editing committed history by **not committing content that may change**. citeturn3view1

### How Ink handles output that reaches or exceeds the viewport

Ink detects “fullscreen” frames by comparing `outputHeight` to terminal row count. When `outputHeight >= viewportRows`, Ink treats it as fullscreen and changes its render strategy. citeturn7view4

Ink also has logic to decide whether it must perform a full-terminal clear for a frame (notably, “overflowing frames still need full clear fallback,” and “clear when shrinking from fullscreen to non-fullscreen output”). When it decides to clear, Ink writes `ansiEscapes.clearTerminal + staticOutput + output`. citeturn7view4

This reveals two practical takeaways:

- Ink’s “no-duplicate scrollback” properties mainly hold while it can keep rewrites within a manageable region (i.e., it can cursor-up and erase prior lines). citeturn12view1turn7view4  
- Once output height becomes comparable to viewport height, Ink may fall back to a “clear terminal + redraw” strategy that can reprint content and thus can create scrollback artifacts depending on how the application uses `<Static>` vs dynamic output. citeturn7view4turn21view0

### What Ink’s use tells you about Claude Code and Copilot CLI-like apps

A GitHub engineering post about Copilot CLI’s animated banner explicitly notes that Ink “re-renders on every state change” and does not manage frame deltas or paint synchronization by itself. citeturn32search13

Separately, a public bug report for Claude Code shows it displays tool results as a collapsed summary with a “ctrl+o to expand” affordance (i.e., a toggle-based transcript expansion). citeturn32search0

These two signals align with the “mutable region vs committed region” insight:

- They can safely offer expand/collapse *for content that is still in their managed render region*.
- For older content that has been truly committed into scrollback, they would need either (a) not to commit it until stable, or (b) treat expansion as showing detail in a separate, currently-rendered region rather than “editing history inside scrollback.” citeturn3view1turn23search2turn32search0

## Terminal primitives for targeted replacement and their scrollback implications

### Clearing and erasing: `CSI J` / `CSI K` and why `2J` isn’t a “scrollback-safe reset”

xterm documents `CSI Ps J` (*Erase in Display*), including:

- `Ps=2` → “Erase All” (the whole visible display),
- `Ps=3` → “Erase Saved Lines” (xterm’s notion of saved/scrollback lines). citeturn21view0

It also documents `CSI Ps K` (*Erase in Line*) including `Ps=2` → “Erase All” (entire current line). citeturn21view0

Your observation (“clear + replay duplicates scrollback”) is consistent with these semantics: `2J` does not imply “delete history,” and terminals often treat the pre-clear content as scrollback-visible history unless explicitly erased via a terminal-specific “erase saved lines” feature (like `3J`, where supported) or a vendor extension. citeturn21view0turn23search11

### Cursor-relative rewriting works—until the content scrolls away

The core building blocks for targeted replacement are:

- Cursor move up/down (`CSI Ps A` / `CSI Ps B`) and “cursor to column” (`CSI Ps G` / `CSI row;col H`) citeturn21view0  
- Erase line (`CSI 2 K` per xterm’s EL “Erase All”) citeturn21view0  
- Insert/Delete lines (`CSI Ps L` / `CSI Ps M`) citeturn21view0  

Ink’s incremental renderer is a concrete example of using cursor positioning plus erase-to-end-of-line to update only changed lines, which is exactly the “cursor up + clear line + rewrite” technique you’re exploring. citeturn12view1

But this strategy only works for regions that are still within the terminal’s current screen grid. Once lines have scrolled off the top into scrollback, you generally can’t address them as “lines N above the cursor” anymore in a stable way, and you can’t “bookmark” an arbitrary scrollback point as a writable location. citeturn23search2turn21view9

### Scrolling primitives and scroll regions: `CSI S/T` and `CSI top;bottom r`

xterm documents:

- `CSI Ps S` → “Scroll up Ps lines (SU)”
- `CSI Ps T` → “Scroll down Ps lines (SD)” citeturn22view0

It also documents `CSI top;bottom r` → `DECSTBM` (*Set Scrolling Region*), which sets top/bottom margins for scrolling. citeturn21view3

Microsoft’s Windows Terminal documentation calls out that scrolling margins are useful for keeping a non-scrolling area (like a title bar) while the rest of the screen scrolls. citeturn23search9

However, scroll regions have a major scrollback implication that matters for your “inline + preserve scrollback” constraint:

- If the scroll region does **not** include the top line of the screen, lines that “scroll off” within that region may **not** be appended to scrollback history in some terminals. This behavior is reported as a bug/limitation in kitty, where setting a scroll region smaller than full height prevents top lines from appearing in scrollback after they leave the visible area. citeturn23search3turn23search7

In other words, DECSTBM can help you isolate a “managed sub-viewport,” but you must treat it as a tradeoff: it can reduce scrollback pollution, yet it can also break the expectation that users can scrollback through all prior content (because “scrolled out of region” is not necessarily “saved to scrollback”). citeturn23search3turn23search7turn23search9

### “Bookmarking” cursor positions: `ESC 7/8`, `CSI s/u`, and alt-screen save/restore

xterm documents multiple save/restore concepts:

- `ESC 7` / `ESC 8` → DECSC / DECRC (Save/Restore Cursor) citeturn21view5turn21view6  
- `CSI s` / `CSI u` are also listed as save/restore cursor sequences (notably as “ANSI.SYS” behavior in the xterm reference). citeturn21view5  
- Private modes `1047/1048/1049` relate alternate screen buffer switching and cursor save/restore. For example, xterm’s list includes `1049` as “save cursor and use alternate screen buffer, clearing it first,” and xterm describes the normal vs alternate screen buffers and their scrollback capabilities. citeturn21view9turn23search14

These mechanisms help restore cursor position within the current buffer state. They do **not** solve “go back and rewrite scrollback history” for the same reason: scrollback is not a generally addressable edit surface. citeturn23search2turn21view9

### Terminal differences that matter in practice

Two “modern terminal” features are especially relevant to reducing flicker and tearing during frequent rewrites:

- **Synchronized output / synchronized rendering** via DECSET mode `2026` (“batch rendering until reset to flush queued screen data”) is explicitly supported by WezTerm. citeturn24search2  
- Contour’s documentation describes the same feature using `CSI ? 2026 h` (begin) and `CSI ? 2026 l` (end), with the goal of atomic screen updates. citeturn24search9  

But terminal behavior around scrollback in alt-screen or with scroll regions differs:

- iTerm2 has an explicit setting about whether “lines that scroll off the top of the screen” in alternate screen mode are saved to scrollback, implying this is configurable and not universally consistent. citeturn23search26  
- An iTerm2 issue thread discusses “scrollback buffer weirdness” in scenarios involving alternate screen and scroll regions, illustrating that even in widely used terminals, these interactions can be subtle. citeturn23search5  

## Bubble Tea v2 Cursed Renderer in inline mode

### What v2 changes at a high level

Bubble Tea v2 introduces the “Cursed Renderer,” described as “built from the ground up” and “based on the ncurses rendering algorithm,” optimized for speed and accuracy. citeturn14search1turn14search2

Under the hood, Bubble Tea v2 uses Charm’s Ultraviolet primitives. Ultraviolet’s documentation explicitly describes:

- a “cell-based rendering model” inspired by ncurses,
- support for both full-window and inline use cases, and
- a “powerful cell-based diffing algorithm” that minimizes terminal writes. citeturn19view0

This matters for your app because it significantly improves the I/O cost of re-rendering the active area (especially over slower terminals/SSH). It does **not**, by itself, make “editing scrollback history” possible. citeturn19view0turn23search2

### Evidence of differential rendering and overflow behavior in Bubble Tea v2

In `cursed_renderer.go`, the renderer maintains:

- a `uv.TerminalRenderer` (`scr`)
- a `uv.ScreenBuffer` (`cellbuf`)
- `lastView` for change detection. citeturn16view0turn17view4

It explicitly skips work when there are no changes (“No changes, nothing to do”). citeturn25view0

The render flow clears and redraws into the screen buffer (`cellbuf.Clear()` then `content.Draw(...)`). citeturn26view0

When the view’s frame is taller than the physical screen, Bubble Tea v2 **drops lines from the top** of the buffer:

> “If the frame height is greater than the screen height, we drop the lines from the top of the buffer.” citeturn26view0

That is critical for your “500+ lines” scenario:

- It means a “put everything in `View()` and let the renderer handle it” approach will not automatically give you terminal scrollback; instead, the renderer shows the bottom portion (like a constantly-updated screen), and older lines may never be emitted as scrollback history unless you explicitly print them as unmanaged output. citeturn26view0turn29view1

Finally, the renderer calls `s.scr.Render(s.cellbuf.RenderBuffer)` to “render and queue changes,” implying it uses the underlying cell-based buffer and renderer to compute minimal updates. citeturn25view3turn19view0

### Inline vs alt-screen handling is explicit

Bubble Tea v2’s renderer initializes Ultraviolet with:

- `SetRelativeCursor(true)` and `SetFullscreen(false)` (“Always start in inline mode”). citeturn16view5

It also implements alt-screen transitions by writing sequences like `ansi.SetModeAltScreenSaveCursor` and `ansi.ResetModeAltScreenSaveCursor`, and it intentionally sequences cursor visibility updates around alt-screen switching. citeturn16view5turn26view0

### `tea.Println` / `tea.Printf` semantics are intentionally “unmanaged”

Bubble Tea v2’s own documentation states:

- `Printf` / `Println` “print above the Program,”
- the output is “unmanaged by the program” and “will persist across renders,”
- and “the message will be print on its own line,”
- and “if the altscreen is active no output will be printed.” citeturn29view1

That is almost exactly the same conceptual split Ink makes with `<Static>`: unmanaged output is append-only, outside the re-render pipeline, and therefore should be treated as immutable with respect to later UI toggles. citeturn3view1turn29view1

### How Cursed Renderer inserts “unmanaged lines” above the view

The renderer interface includes an `insertAbove(string)` capability, and the Cursed Renderer’s `insertAbove` implementation uses a combination of:

- moving down to the bottom,
- writing newline repeats to “scroll the screen up by the offset to make room,”
- using `CursorUp` and `InsertLine(offset)`,
- and clearing the right side of each inserted line. citeturn17view3turn25view8

This is strong evidence that Bubble Tea’s inline “Println above the view” feature is, internally, a controlled insertion into the visible screen grid (and thus into terminal history as the screen scrolls). It is not a mechanism for later editing those inserted lines once they’ve been committed and potentially scrolled into history. citeturn25view8turn29view1turn23search2

### Synchronized updates exist in Bubble Tea v2

Bubble Tea v2 includes logic to wrap updates in synchronized output mode (“wrap all updates … in synchronized output mode … rendering the updates atomically”) when supported. citeturn26view6turn24search2turn24search9

That can improve UX for frequent re-renders (less flicker), but it does not change scrollback immutability. citeturn26view6turn23search2

## Architectures that can meet your “success” criteria

### All-in-View approach

Bubble Tea’s design goal is that the view “describes the entire UI” so you “don’t have to worry about redrawing logic.” citeturn32search3turn14search1

However, the Cursed Renderer’s overflow handling (“drop lines from the top of the buffer” when the frame exceeds screen height) means an all-in-View transcript behaves like a continuously updated screen, not like persistent terminal history. citeturn26view0turn23search14

So an all-in-View approach is feasible if **you are willing to implement your own scrollback inside the app** (a viewport/pager model), but it conflicts with your explicit constraint: users expect to use *terminal scrollback* in inline mode. citeturn26view0turn23search14

### Partial-commit approach: “mutable window” + “immutable transcript”

Both Ink and Bubble Tea v2 effectively endorse a split model:

- **Mutable region**: whatever is managed by the renderer (Ink’s interactive output, Bubble Tea’s `View()` region) and can be rewritten in place. citeturn12view1turn19view0  
- **Immutable region**: append-only output (Ink `<Static>`, Bubble Tea `Println/Printf`) that persists and shows up in terminal scrollback. citeturn3view1turn29view1  

This model naturally avoids scrollback duplication because you stop reprinting historical lines: once printed as unmanaged output, you never redraw them via “clear + replay.” citeturn29view1turn21view0

### DECSTBM / scrolling region approach: powerful but risky for “native scrollback”

Using a scrolling region (`CSI top;bottom r`) can create a “managed pane” where you can insert/delete/scroll without disturbing other parts of the screen. citeturn21view3turn23search9

But multiple sources show that scroll regions can interact unpredictably with scrollback recording:

- some behavior reports indicate that if the scroll region doesn’t include the top of the screen, lines may not be added to scrollback (kitty issue, and related troubleshooting commentary for Terminal.app-like behavior). citeturn23search3turn23search7  
- iTerm2’s own configuration implies alternate-screen scrollback behavior is a setting, reinforcing that scrollback behavior is terminal-dependent. citeturn23search26turn23search5  

So DECSTBM is best treated as a specialized tool for *multi-pane screen layouts*, not as a universal mechanism to “edit committed history without scrollback duplication.” citeturn23search9turn23search3turn23search2

### Alt-screen toggling as a “temporary redraw space”

xterm describes `1049` mode as saving cursor state and switching to alternate screen, and describes that alternate screen typically contains no saved lines. citeturn21view9turn23search14

This implies a tempting idea: render in alt-screen, then “return” to normal. But the normal buffer’s scrollback is not automatically replaced by what you drew in alt-screen, and in real terminals the interaction between alt-screen and scrollback can be configurable and surprising (e.g., iTerm2’s settings and issues). citeturn23search14turn23search26turn23search5

Given your requirement to preserve normal scrollback and avoid duplication, alt-screen-as-a-redraw-sandbox is high risk and unlikely to produce consistent results across the terminals you listed. citeturn23search14turn23search26turn23search5

## Recommended blueprint for Bubble Tea v2 inline conversational UIs

### Principle: decide what is allowed to change before you print it

Both Ink’s `<Static>` and Bubble Tea’s `Println/Printf` are explicit “append-only” constructs. Once you use them, you should assume that output is immutable and may soon be in scrollback. citeturn3view1turn29view1

So, reframe your UI requirements into two categories:

- **Mutable items** (must support expand/collapse, approval collapse, header late-resolution): keep them renderer-managed (in `View()`) until they become stable. citeturn12view1turn19view0turn29view1  
- **Immutable items** (finalized transcript lines): only then “commit” them with `tea.Println`/`tea.Printf` so they enter normal terminal scrollback exactly once. citeturn29view1turn21view0  

This is the only robust way to meet both:
1) “updates on screen,” and  
2) “no duplicated scrollback,”  
because it eliminates the need for “clear + replay.” citeturn21view0turn23search2

### Concrete approach: a “mutable window” above the input, flush-to-scrollback on stabilization

Implement a transcript model as a sequence of blocks (messages, tool calls, approvals, headers), each with:

- `state`: pending (mutable) vs finalized (immutable)
- `renderMode`: collapsed/expanded plus any resolved header fields

Render **only mutable blocks** + the input area in `View()`.

When a block becomes immutable (e.g., approval resolved, tool output finalized, header subject resolved), do two steps:

1. Emit one final immutable line(s) for that block via `tea.Println` (or a single `tea.Printf` call knowing it will still be “on its own line”). citeturn29view1turn27search3  
2. Remove that block from the mutable set so it is never redrawn again.

This pattern matches Bubble Tea’s documented “unmanaged output persists across renders” intent. citeturn29view1turn32search3

### How this addresses your three core use cases

**Session header update (subject resolves 3–6 seconds later)**  
Keep the header in the mutable `View()` area initially (with placeholder subject). When the subject resolves, you update the model and the renderer rewrites the current region using its cell-diff algorithm. Once the header is “done,” print it once as unmanaged output and remove it from the mutable view. citeturn19view0turn26view6turn29view1

**Approval collapse**  
Keep approval context (expanded file snippet, prompt, controls) in the mutable area. On accept/reject, update the model to the collapsed one-line summary and render it (still mutable for a moment), then commit that one-line summary via `tea.Println` and remove the approval block from the mutable region. citeturn29view1turn19view0

**Expand/collapse toggle for tool results**  
Only guarantee “inline toggling” for tool results that are still in the mutable window. This aligns with the general terminal reality: once output is truly in scrollback, you can’t reliably rewrite it. citeturn23search2turn3view1turn29view1

This is also consistent with how “ctrl+o to expand” is conceptualized in Claude Code’s UI: it’s an interactive affordance tied to tool transcript lines, but it is not evidence that scrollback history is being edited—only that the app can switch what it renders while the content is still in its managed surface. citeturn32search0

### Practical performance notes for 500+ line sessions in Bubble Tea v2

Bubble Tea v2 + Ultraviolet is optimized to reduce terminal I/O by diffing at the cell level. citeturn19view0turn14search1

But CPU and allocation costs still depend on what you choose to render each frame. The Cursed Renderer’s overflow behavior (dropping top lines when the frame exceeds screen height) strongly suggests that extremely tall “all history in view” frames are not meant to be your scrollback mechanism. citeturn26view0

Therefore, the “mutable window + commit older content” design is not just about scrollback correctness—it is also aligned with the renderer’s strengths: keep the managed region bounded, let the diff algorithm update it efficiently, and use unmanaged printing for true scrollback. citeturn19view0turn26view0turn29view1

### Terminal compatibility knobs you should use, and ones you should avoid

- Enable synchronized updates when supported (DECSET `2026`) to reduce tearing during frequent redraws; Bubble Tea v2 has explicit support for synchronized output wrapping, and WezTerm documents support for it. citeturn26view6turn24search2turn24search9  
- Avoid “clear + replay” patterns (`CSI 2 J` + redraw) because `Erase All` does not imply “erase scrollback history,” and replay necessarily creates duplicates in scrollback. citeturn21view0turn23search11  
- Treat DECSTBM (scroll regions) as advanced: it can help implement multi-region layouts, but it can also disrupt scrollback recording in some terminals and may behave inconsistently. citeturn23search9turn23search3turn23search5turn23search26  

### Why Warp “solves” this differently (and why it’s not directly transferable to ANSI TUIs)

Warp’s architecture is not “ANSI text stream + scrollback,” but a higher-level UI model. Warp explicitly organizes sessions into “Blocks” (a command and its output), with documentation emphasizing block selection, copying, and navigation rather than raw scrollback behavior. citeturn32search6turn32search10

Warp’s engineering posts describe internal grid-based data structures and a “block” model where each block has separate grids for prompt, input, and output. citeturn32search18turn32search2

That’s essentially a “virtual terminal + structured history” approach built into the terminal itself. It’s powerful, but it’s not something an ordinary CLI app can assume in iTerm2/Terminal.app/Kitty/Alacritty/WezTerm. citeturn32search18turn21view9
