# Research: Inline Terminal Re-rendering Without Scrollback Duplication

## Research Objective

We are building a CLI application (Go, using charmbracelet/bubbletea) that renders interactive content in **inline mode** (not alt-screen). We need to understand the best techniques for re-rendering already-committed terminal content without polluting the terminal's scrollback buffer.

## Context

Our CLI application renders a conversational AI session in the terminal. Content includes:
- A session header panel (rendered at the top of the session)
- AI messages, tool call results, approval prompts
- An interactive input area at the bottom

We use **Bubbletea's inline mode** (no alt-screen), which has two rendering regions:
1. **Committed region**: Content written via `tea.Println()` -- pushed above the active view, enters terminal scrollback. Bubbletea "forgets" this content after committing.
2. **Active view**: Content rendered by `View()` at the bottom -- Bubbletea re-renders this in place on every frame using cursor-up + clear + rewrite.

We have several use cases that require modifying already-committed content:
- **Expand/collapse toggle** (like Claude Code's Ctrl+Shift+O): User toggles between compact and expanded views of tool call results
- **Approval collapse**: After user approves/rejects, expanded file content collapses to a one-line summary
- **Session header update**: A "subject" field in the header resolves 3-6 seconds after session start and needs to be shown

## Current Approach (Problem)

We currently use `tea.ClearScreen` (`\033[2J\033[1;1H`) followed by replaying all content from an in-memory history. This works visually on the active screen, but `\033[2J` in modern terminals (iTerm2, macOS Terminal, Ghostty, etc.) **moves visible content to the scrollback buffer** rather than erasing it. Result: every re-commit duplicates all previous content in scrollback.

For a session with 50 tool calls that does 3 approval re-commits, the full history appears 4 times in scrollback. This is bad UX.

## Specific Research Questions

### 1. How does Ink (React for terminals) handle re-rendering?

Ink is the Node.js framework used by Claude Code. Specifically:
- How does Ink's renderer track and re-render content that has been written to the terminal?
- Does Ink use `tea.Println`-equivalent committed content, or does it keep everything in its active render area?
- How does Ink handle content that exceeds the terminal viewport height?
- Does Ink have scrollback duplication issues when re-rendering? If not, how does it avoid them?
- How does Ink's `<Static>` component work, and can Static content be modified after rendering?
- What ANSI escape sequences does Ink use for its re-rendering cycle?

### 2. Terminal escape sequences for targeted content replacement

- Is `\033[2J` (Erase in Display) the only way to clear the screen, or are there alternatives that don't push content to scrollback?
- Can we use `\033[<n>A` (Cursor Up) + `\033[2K` (Erase Line) to selectively rewrite specific lines without affecting scrollback?
- What is the behavior of `\033[<n>S` (Scroll Up) and `\033[<n>T` (Scroll Down) -- do these affect scrollback?
- Is there a reliable way to "bookmark" a cursor position at the start of a session and return to it later?
- What are the differences between `\033[s`/`\033[u` (DECSC/DECRC), `\033 7`/`\033 8` (Save/Restore), and `\033[?1048s`/`\033[?1048u`?
- How do modern terminals (iTerm2, Ghostty, Kitty, Alacritty, WezTerm, macOS Terminal.app) differ in their handling of these sequences?

### 3. Bubbletea v2 Cursed Renderer capabilities

Bubbletea v2 (released Feb 24, 2026) ships with the "Cursed Renderer" based on ncurses algorithms:
- Does the Cursed Renderer do differential/incremental rendering (only rewriting lines that changed)?
- In inline mode, how does the Cursed Renderer track committed content height?
- Can the Cursed Renderer handle a View() that grows over time (new content appended each frame)?
- What happens when View() content exceeds the terminal viewport -- does the Cursed Renderer handle the overflow gracefully?
- Is there a way to keep ALL content in View() (no Println) and let the Cursed Renderer manage everything, including scrollback?
- How does `tea.Println` interact with the Cursed Renderer's line tracking?

### 4. Alternative rendering architectures for inline mode

- **All-in-View approach**: Keep all session content in View() instead of committing via Println. What are the performance implications? Does diff-based rendering make this feasible for sessions with 500+ lines of content?
- **Partial-commit approach**: Keep only recent content in View() and commit older content via Println when it's unlikely to change. How do frameworks like Ink handle this boundary?
- **Virtual terminal / pseudo-terminal approach**: Render to an in-memory buffer and only sync the visible portion to the real terminal. Are there Go libraries for this?
- **Alt-screen with scrollback preservation**: Some terminals support `\033[?1049h` (alt-screen) which saves and restores the normal screen buffer. Could we use alt-screen during re-rendering and exit back to inline mode? What are the risks?

### 5. How do other CLI tools handle this?

- **Claude Code** (Ink): How does it handle expand/collapse (Ctrl+Shift+O) without scrollback duplication?
- **GitHub Copilot CLI**: Does it use inline or alt-screen rendering?
- **Warp terminal**: How does Warp's block-based rendering model work? (Warp treats each command as a block)
- **Charm's own tools** (mods, gum, vhs, soft-serve): Do any of them do inline re-rendering of committed content?

### 6. The DECRST/Scrolling Region approach

- Can `\033[<top>;<bottom>r` (Set Scrolling Region / DECSTBM) be used to constrain scrolling to a specific region of the screen?
- If we set a scrolling region that covers our session content, could we clear and rewrite within that region without affecting scrollback above?
- Is this approach used by any major CLI framework?
- What are the terminal compatibility implications?

## Known Constraints

- We are committed to **inline mode** (not alt-screen) for the primary rendering. Users expect to scroll back through session history in their normal terminal scrollback.
- The application is written in **Go** using **charmbracelet/bubbletea v2**.
- We need to support: iTerm2, macOS Terminal.app, Ghostty, Kitty, Alacritty, WezTerm, and standard xterm-compatible terminals.
- The solution must handle sessions ranging from 5 lines to 500+ lines.

## What "Success" Looks Like

An approach where:
1. Content re-rendering (expand/collapse, approval collapse, header update) works correctly on the visible screen
2. When the user scrolls up in their terminal, they do NOT see duplicated content
3. Works across major modern terminals
4. Performance is acceptable for sessions with hundreds of lines
