# Session Notes: 2026-03-17 (Session 14)

## Accomplishments

- Investigated security implications of `LocalPathSource` workspace entries reaching the cloud backend
- Confirmed existing defense layers: frontend hides local folder UI in cloud mode, agent runner rejects `LocalPathSource` when `is_local_mode=False`, Daytona sandbox isolates filesystem
- Identified UX gap: API callers (SDK, curl, platform builders) can bypass the frontend and submit `LocalPathSource` entries directly, causing a late failure during agent runner provisioning
- Implemented `RejectLocalPathWorkspaceStep` in `SessionCreateHandler.java` (stigmer-cloud) for fail-fast API-level validation

## Decisions Made

- **Validation in cloud backend only** — The Go backend serves both local and cloud modes; `LocalPathSource` is valid in local mode. Cloud-specific validation belongs in the cloud-specific backend.
- **Placement after validateFieldConstraints, before authorize** — Proto structure must be valid before semantic checks; no point authorizing a request that will be rejected.
- **`INVALID_ARGUMENT` status** — Consistent with other validation failures in the pipeline.
- **Error message matches agent runner** — "LocalPathSource workspace entries are not supported in cloud mode. Use git_repo for cloud deployments." Consistency per Nielsen heuristic #4.

## Key Code Changes

- `SessionCreateHandler.java` (stigmer-cloud): Added `RejectLocalPathWorkspaceStep` inner class (pure validation, no dependencies), added field + pipeline wiring, updated step numbering and Javadoc. +47/-10 lines.

## Learnings

- The defense-in-depth model has four layers: frontend UI hiding, Java backend validation (new), agent runner `is_local_mode` check, Daytona sandbox isolation.
- The agent runner already had a guard (`WorkspaceProvisionError` for non-local-mode), but it fires late — after session creation, persistence, and execution start. The API-level guard gives immediate feedback.
