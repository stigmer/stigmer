## Decisions Made

- **No emoji badges in compact format** — Structure communicates state: result summary line = done, error line = failed, dim `…` suffix = running. Emoji badges (`⏳`, `✓`) make the app look unprofessional. This was a deliberate departure from the legacy format, agreed with the user after analyzing Claude Code's approach.
- **Running events kept for writes/edits** — User confirmed from real Cursor usage that writes have observable latency. Suppressing would create "is it stuck?" anxiety. Reads (<100ms) remain suppressed.
- **Waiting-approval state untouched** — The verbose gutter-bordered preview is intentionally preserved for approval decisions where users NEED to see content. Richer approval UX (more preview lines, `[v] View full content` key) is Phase 3 scope.
- **`hasCompactRenderer` graduated registry** — Single source of truth for which tools have compact renderers. As Phases 2.3-2.4 add more, they register here and running events automatically get compact formatting.

## Learnings

- `countLines` counts `strings.Count(s, "\n") + 1`, so trailing newlines add an extra line. Must account for this in test expectations.
- `resolveDisplayContent` correctly handles the write/edit content source — it respects `contentSourceInput` so write tools get line count from args content, not the result confirmation message. Reusing existing infrastructure avoids duplication.
- The graduated pattern (register in `hasCompactRenderer`, compact running format auto-applies) eliminates per-tool-type changes in the inline renderer for future phases.
