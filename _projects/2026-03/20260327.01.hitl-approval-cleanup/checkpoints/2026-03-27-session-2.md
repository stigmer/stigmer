## Decisions Made

- **Merged schema approach for MCP wrappers**: When `args_schema` from an MCP tool is copied onto the approval wrapper, it destroys `InjectedToolCallId` metadata. Solution: `_build_merged_schema()` creates a Pydantic model containing both the MCP tool's fields (LLM-visible) and `InjectedToolCallId` (hidden from LLM, injected at runtime).
- **Args unwrapping refactored**: The old `len(kwargs) == 1` check for `input`/`kwargs` shells broke when `InjectedToolCallId` added `tool_call_id` alongside model args. New helper `_approval_tool_kwargs_to_actual_args()` strips injected keys first, then unwraps in a loop.
- **ToolCall-format invocation required**: With `InjectedToolCallId`, `BaseTool.ainvoke()` requires ToolCall-format input (`{name, args, id, type}`) and returns `ToolMessage` instead of plain strings. All tests updated accordingly.

## Surprises / Learnings

- **`args_schema` copy + `InjectedToolCallId` conflict**: Not anticipated in planning. The `@tool` decorator generates a schema with `InjectedToolCallId` metadata; overwriting `args_schema` destroys it. This is a subtle LangChain implementation detail that required a merged schema approach.
- **ToolCall-format invocation changes return type**: When `BaseTool.ainvoke()` receives ToolCall-format input, it wraps the return value in a `ToolMessage` object. This affected every test assertion that compared results against plain strings.
- **`**kwargs` + `InjectedToolCallId` schema**: LangChain's generated schema exposes a single `kwargs` bucket when no Pydantic model is provided. Tool arguments arrive wrapped in `{"kwargs": {...}}`, requiring unwrapping logic.
