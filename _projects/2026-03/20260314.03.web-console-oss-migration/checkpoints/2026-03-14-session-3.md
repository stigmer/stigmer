## Decisions Made

- **`src/auth/` as bounded module**: Auth is a cross-cutting concern with its own types, config, context, providers, hooks, and guard. Colocating them makes the auth system easy to reason about and maintain.
- **`useAuth()` as sole public API**: No component outside `src/auth/` imports mode-specific providers, checks auth config, or accesses the token store. This is the Strategy pattern applied to React context.
- **Token store as auth-transport bridge**: Module-level variable (`getAuthToken`/`setAuthToken`). Auth providers write, transport interceptor reads. No React context in the transport layer — Connect-RPC clients are module-level singletons.
- **`user: null` in disabled mode**: No synthetic "Local User". Components handle `user === null` gracefully.
- **OIDC deferred**: Interface defined (`OidcConfig`), but implementation waits for T04 to determine whether OIDC must be client-side PKCE (static export) or can use server-side approach.
- **OrgProvider unchanged**: Makes real gRPC calls in disabled mode. Server has no auth middleware, returns orgs without tokens. Error/retry state handles "server not running" case.
- **Auth mode via env var**: `NEXT_PUBLIC_AUTH_MODE` (default `"disabled"`). Build-time in Next.js, runtime in dev mode. Extendable to runtime config via `/api/config` in T05.

## Learnings

- `src/lib/` files (including `auth-token.ts`) were never committed to git in T02 — they existed on disk but were untracked. The delete operation removed them from disk but didn't create a git diff.
- The provider nesting order matters: `AuthProvider` must be outermost (provides context), then `AuthGuard` (blocks until auth resolves), then `OrgProvider` (needs auth to be settled before fetching orgs).
- `context.tsx` separated from providers prevents circular imports: both provider implementations and `useAuth()` hook import from `context.tsx`, but neither imports the other.
