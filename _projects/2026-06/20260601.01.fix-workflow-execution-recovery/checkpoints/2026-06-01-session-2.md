## Decisions Made

- **Read from status.tasks[] instead of event log**: task_completed events don't carry output (output_summary field exists but is never populated). status.tasks[].output has 64KB truncation but is acceptable for >99% of workflows. Improvement deferred to T08.
- **Recovery flag on RunWorkflowEngineOptions, not ExecuteServerlessWorkflowInput**: Recovery mode is an engine concern (how to execute), not a workflow model concern (what to execute). Keeps the input type clean.
- **Top-level task skip only**: Composite tasks (for, fork, try) that partially completed are re-executed entirely. Sub-task recovery adds significant complexity for marginal benefit.
- **Deactivate recovery after first non-skipped task**: Nulling the context prevents accidental late skipping and eliminates unnecessary Map lookups.
- **T06 must NOT clear status.tasks[]**: Identified a data race — if T06 clears status.tasks[] before the engine reads them, recovery context is empty. Engine's own event emission naturally replaces stale entries.

## Learnings

- The Temporal serialization boundary requires converting proto Struct to plain objects in the activity. RecoveryContext (with Map) must be built inside the sandbox, not returned from the activity.
- Recursive `executeDoTasks` calls (from for.ts, fork.ts, try.ts) naturally don't receive the recovery context because it's an optional 7th parameter. This is the correct behavior — no special handling needed.
- Version pinning via `workflowVersionHash` eliminates YAML drift concerns for recovery — the same execution ID preserves the hash, ensuring identical task lists.
- The `processTaskOutput` and `processTaskExport` functions use the raw full output during normal execution, but the cached output from status.tasks[] during recovery. If the output was >64KB and truncated, the recovered $context may differ from the original. Documented as a known limitation.
