## Key Architecture

**Package Structure**:
```
pkg/
├── panel/         # Lipgloss panel renderer (domain-agnostic)
├── approval/      # Bubbletea prompts + formatter (reusable)
├── spinner/       # ANSI spinner (lightweight, non-blocking)
├── toolrender/    # Category-aware tool display (proto-free)
└── display/       # Terminal detection + width

cmd/stigmer/root/
├── run.go                    # Command definition + flags
├── run_handlers.go           # Orchestration
├── run_stream.go             # Streaming core
├── run_stream_approval.go    # Approval handling
├── run_display.go            # Ongoing message rendering
├── run_display_approval.go   # Approval panel rendering
├── run_display_summary.go    # Completion panel rendering
└── run_display_tools.go      # Proto-to-primitive conversion
```

**Key Patterns**:
1. **Proto-to-primitive conversion** — Keeps packages reusable by converting gRPC types to simple Go structs
2. **Domain-agnostic pkg/** — No business logic in utilities, all testable in isolation
3. **SRP enforcement** — All files under 250 lines, extracted helpers when needed
4. **Comprehensive testing** — 115 new tests, 100% coverage on new packages
5. **Terminal coexistence** — Spinner (ANSI) and Bubbletea work together without conflicts

## Decisions Made

### Architectural

1. **Streaming by default** — Removed flag confusion, real-time updates are the happy path
2. **Bubbletea for prompts** — Better than Survey for multi-phase interaction and testing
3. **ANSI spinner** — Lightweight goroutine solution avoids Bubbletea contention
4. **Both new packages in pkg/** — panel, approval, spinner, toolrender are all domain-agnostic
5. **Panel-based UI** — Consistent visual language across approval, summaries, and future features

### Scope Adjustments (T05)

1. **Deferred JSON streaming output** — Requires NDJSON schema design, deserves separate task
2. **Skipped content truncation** — Not a terminal pattern, wait for user feedback
3. **Scoped error handling** — Global handler sufficient, execution errors from backend
4. **Skipped phase animations** — Spinner provides motion, animations fragile in terminals
5. **100-column panel cap** — Consistent with approval UI, maintains readability

## Lessons Learned

### What Worked Well

1. **Incremental task breakdown** — T02-T05 each built on previous work cleanly
2. **Package-first approach** — Building reusable utilities (panel, spinner, toolrender) first enabled rapid integration
3. **Comprehensive testing** — 100% coverage caught issues early, gave confidence to refactor
4. **SRP enforcement** — 250-line limit forced good separation, made code easier to reason about
5. **Proto-to-primitive pattern** — Clean boundary between gRPC and UI layers
6. **Scope discipline** — Pushing back on T05 over-scope kept work focused and high-quality

### Challenges

1. **Bazel dependency resolution** — Hit pre-existing `com_github_atotto_clipboard` issue, fell back to `go build`
2. **Pre-existing test failures** — `TestAllVerbs` count mismatch from earlier work, isolated and ignored
3. **Go version warnings** — go.work requires 1.25.6 but 1.23.12 running, pre-existing issue
4. **Linter warnings** — Some pre-existing issues in modified files, addressed only what was new

### Patterns to Replicate

1. **Proto-to-primitive conversion** — Always introduce a boundary layer between gRPC and domain/UI
2. **Domain-agnostic pkg/** — Build utilities with zero business logic for maximum reuse
3. **Extract helpers early** — Don't wait until file hits 250 lines, extract at 200
4. **Test first for packages** — New packages should have test files created alongside source
5. **Panel-based UI** — Consistent visual language makes CLI feel cohesive
