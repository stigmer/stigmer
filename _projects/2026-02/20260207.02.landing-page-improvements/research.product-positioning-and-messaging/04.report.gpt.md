## 1. Executive Summary

### Recommended positioning

**Position Stigmer as: *“Open-source Durable Agentic Workflows”*** — an **AI-native automation platform** where **agents are first-class**, but **durable workflow orchestration is the differentiator**.

Why this works now:

* “Agentic workflows” is becoming a recognized frame for **multi-step, tool-using agent processes** (not just chatbots). IBM describes agentic workflows as AI-driven processes where agents make decisions, take actions, and coordinate tasks with minimal human intervention. ([IBM][1])
* The market splits into two camps:

  * Agent frameworks emphasize **shipping reliable agents** + guardrails/observability (e.g., LangChain’s “Ship reliable agents” + observability/eval/deploy). ([LangChain][2])
  * Workflow engines emphasize **durability + state + retries** (e.g., Temporal’s “What if your code never failed?” and “never lose state”). ([Temporal][3])
* Stigmer’s uncommon advantage: **you’re natively in the “durable execution” world** (via Temporal), while most agent platforms are still “best effort” unless you bolt on a workflow engine later. Temporal explicitly frames the core value as durable execution that guarantees code runs to completion despite failures. ([Temporal][4])

### Top 3 messaging priorities (for the new landing page)

1. **Outcome-first reliability:** “Your AI automation survives failures, retries safely, and never loses state.” (Translate “Temporal orchestration” into value.) ([Temporal Docs][5])
2. **Agents + workflows as one product:** “Start with an agent. Ship as a workflow.” (No “pick a framework now, add orchestration later”.) This matches how hybrid players are starting to message (e.g., Prefect: “Orchestrate workflows. Build AI applications.”). ([Prefect][6])
3. **Open + local-first by default:** open-source + standard integrations (MCP) + laptop-first dev loop; avoid lock-in.

### Key differentiation points to highlight everywhere

* **Durable execution for agentic automation:** workflows keep state/progress through failures (Temporal’s core promise). ([Temporal Docs][5])
* **Local-first dev loop, production-grade runtime:** “prototype locally → ship the same workflow in production.”
* **Standard tool integration via MCP:** MCP is positioned as an open protocol to integrate LLM apps with external tools/data sources. ([GitHub][7])
* **Open-source Apache 2.0** (trust + extensibility + no lock-in).

## 2.1 Product Positioning Strategy

You gave four options. Here’s how they play out in today’s market reality.

### Option A: “Agent platform” (workflows are a feature)

**Pros**

* Meets existing demand: “AI agents” is the keyword people search.
* Easier mental model if audience is app developers prototyping agents.

**Cons**

* You end up in the most crowded category: LangChain, CrewAI, AutoGen, Semantic Kernel all frame themselves around building agents/multi-agent apps. ([LangChain][2])
* Your biggest “moat” (durable orchestration via Temporal) becomes a footnote—despite being the thing that helps users **ship**.

**Target audience implications**

* Pulls you toward “AI engineers building agent apps” (and their evaluation/observability concerns).

**Competitive implications**

* You’ll be compared primarily on: memory, tool calling, model support, templates, eval tooling.
* Harder to win vs incumbents who already own mindshare on “agent framework”.

**Examples of this positioning**

* **LangChain**: “Ship reliable agents” + platform around observability/eval/deploy. ([LangChain][2])
* **AutoGen**: multi-agent AI applications acting autonomously or alongside humans. ([GitHub][8])
* **Semantic Kernel**: dev kit to build AI agents + integrate models into C#/Python/Java (enterprise-ready framing). ([Microsoft Learn][9])
* **CrewAI**: “collaborative AI agents, crews, and flows — production ready from day one.” ([CrewAI Docs][10])

---

### Option B: “Workflow orchestration platform” (agents are a task type)

**Pros**

* Strong differentiation with platform engineers: you’re speaking the language of reliability and long-running processes.
* Natural comparison set includes serious systems like Temporal, Airflow, Prefect, Dagster—where durability, retries, state, visibility matter. ([Temporal][3])

**Cons**

* Risks sounding like “yet another orchestrator,” unless you lead with what’s different: **AI agents as first-class steps** + MCP integration + sandboxes.
* Might under-serve users who do want to “just build an agent quickly.”

**Target audience implications**

* Pulls you toward **platform engineers, DevOps, infra/tooling teams**.
* Great if that’s the primary buyer/user.

**Competitive implications**

* You’ll be compared on: reliability guarantees, scaling, observability, deployment.
* If you can clearly say “Temporal-grade durability without Temporal-level setup,” that’s compelling.

**Examples**

* **Temporal**: makes failures irrelevant; don’t lose state. ([Temporal][3])
* **Airflow**: programmatically author/schedule/monitor workflows (batch-oriented). ([Apache Airflow][11])
* **Dagster**: “data (and AI) pipelines” framing, with local testing + observability emphasis. ([Dagster][12])

---

### Option C: Dual-pillar (equal emphasis on agents + workflows)

**Pros**

* Honest + accurate.
* Lets you show “start small (agent), scale up (workflow)” progression.

**Cons**

* Dual-pillar often reads like two products stapled together unless you unify them with one sentence:

  * “Agents are how you do work. Workflows are how you ship work.”

**Audience implications**

* Broadest reach, but requires tight messaging hierarchy.

**Competitive implications**

* You’ll fight on two fronts; must be crystal-clear where you win.

### Example 2: Workflow “PR Review Pipeline” (your differentiator)

```yaml
apiVersion: agentic.stigmer.ai/v1
kind: Workflow
metadata:
  name: pr-review-pipeline
spec:
  inputs:
    pr_url: string
  tasks:
    - name: fetch-pr
      agent: github-analyst
      inputs:
        pr_url: "${workflow.inputs.pr_url}"

    - name: review-code
      agent: code-reviewer
      inputs:
        code: "${tasks.fetch-pr.output.diff}"

    - name: post-comment
      agent: github-commenter
      inputs:
        pr_url: "${workflow.inputs.pr_url}"
        review: "${tasks.review-code.output}"
```
