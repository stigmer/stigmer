## Best practices that emerge across ecosystems

### 1) Ship a minimal “SYSTEM layer” that can create/enable more capabilities

* Codex bundles system skills like `$skill-creator` so skill creation is possible immediately. ([OpenAI Developers][1])
* K3s bundles packaged components and applies them automatically on startup. ([K3s][8])
  Pattern: **bootstrap must not depend on the network or on user-authored content**.

### 2) Use progressive disclosure to keep context small and predictable

This is now a standard expectation in agent skill systems:

* Codex: injects *only name/description/path*; instructions load only on explicit invocation. ([OpenAI Developers][2])
* Claude skills: metadata always loaded; instructions loaded when triggered. ([Claude][9])
  Pattern: Stigmer’s “metadata always loaded, instructions/resources on demand” aligns strongly with industry direction.

### 3) Separate “installation/init” from “execution”

The reliable tools don’t mix “start the daemon” with “download and trust new third‑party bits”:

* Terraform installs dependencies during `terraform init`, updates lockfiles, and expects code review of lockfile changes. ([HashiCorp Developer][10])
* Pulumi installs required providers when running `pulumi up/preview`, caches them locally, and documents manual preload for air‑gapped scenarios. ([pulumi][11])
* Ollama starts the server; models are pulled/loaded when needed. ([Ollama Documentation][7])
  Pattern: **make bootstrap explicit or lazy**, and keep the “server start” path fast and resilient.

### 4) Treat extensions as immutable artifacts + metadata, not just “git HEAD”

For reproducibility and offline:

* Terraform uses a dependency lock file and verifies installed packages match recorded checksums (TOFU) and can rely on signed checksums. ([HashiCorp Developer][10])
* LocalAI’s gallery supports downloading model files with `sha256` verification. ([LocalAI][12])
  Pattern: store **(artifact bytes + digest)** locally; keep **source reference** only as metadata.

### 5) Make provenance & permissions first-class

* Terraform providers from registry are cryptographically signed; Terraform verifies signatures during installation. ([HashiCorp Developer][13])
* Claude skills can specify `allowed-tools` in frontmatter, making permissions auditable and reviewable. ([Claude Code][3])
* Sigstore/cosign provides a standard way to verify artifact signatures (including digest-binding). ([Sigstore][14])
  Pattern: provenance isn’t “nice to have” once the system self-bootstraps.

## Specific recommendations to improve your seedpack bootstrap

### Recommendation A: Don’t “git clone on server start” as the primary happy path

Auto-cloning from GitHub at `stigmer server start` creates two avoidable failure modes:

1. **network unavailability** breaks first-run setup (violates your offline-first goal), and
2. **supply-chain exposure** at the most privileged moment (first-time bootstrap).

**Instead:**

* **Vendor** a known-good snapshot of `skill-creator` into the seedpack (as content bytes), **pinned to an upstream commit SHA**, and embed it in the binary.
* Keep the upstream URL + commit SHA as provenance metadata, but the bootstrap uses embedded bytes first.

This is consistent with how K3s treats packaged manifests (managed by the system, rewritten for integrity). ([K3s][8])

Then add an explicit (opt-in) update path:

* `stigmer seed update` (or `stigmer skill sync --upstream`) to fetch upstream changes when online.

### Recommendation B: Make bootstrap versioned and idempotent like DB migrations

Adopt a “seedpack schema version” concept:

* `seedpack_version` stored in Stigmer’s DB/registry state
* Each Stigmer release ships `seedpack vN`
* Server startup runs **(N+1..current)** steps idempotently

This mirrors “init/lockfile” expectations in dependency managers: deterministic steps, resumable, reviewable. ([HashiCorp Developer][10])

### Recommendation C: Make skills immutable artifacts, with a lock/selection mechanism

Your current “ZIP artifact” approach is directionally right. Improve it with:

* **content-addressed identity**: `sha256` of the ZIP contents as the canonical version
* optional human version tags (`v1.2.3`) mapped to a digest
* store source metadata (`git url`, `ref`, `commit sha`, `subdir`) separately from the artifact

This matches:

* Terraform’s checksums/lockfile verification model. ([HashiCorp Developer][10])
* LocalAI’s sha256-verified downloads. ([LocalAI][12])

Practical UX:

* `stigmer pull skill stigmer/skill-creator@sha256:...`
* `stigmer lock` generates `stigmer.lock` with digests (like `.terraform.lock.hcl`) ([HashiCorp Developer][10])

### Recommendation D: Add an explicit “disable/override” mechanism for system skills

Codex supports disabling skills via config, even when they exist on disk. ([OpenAI Developers][1])
K3s supports disabling packaged components and `.skip` files. ([K3s][8])

For Stigmer:

* allow `stigmer config set skill stigmer/skill-creator enabled=false`
* allow user override precedence **without mutation** of the system copy:

  * system: `stigmer/system/skill-creator`
  * user: `me/skill-creator` or `org/skill-creator`
* the resolver chooses a version based on precedence rules and “enabled” status

This prevents “bootstrap edits” from becoming an implicit fork with unknown provenance.

### Recommendation E: Bring “tool permissions” into the SKILL.md contract

Claude’s skills frontmatter supports `allowed-tools`. ([Claude Code][3])
Codex separately distinguishes metadata always injected vs full instructions on invocation. ([OpenAI Developers][2])

For Stigmer, you can unify these ideas:

* Put **capability requirements** in skill metadata (or adjacent manifest), not buried in prose.
* Make the agent-runner enforce tool allowlists at runtime (deny by default).

This is the single biggest guardrail against “promptware supply chain” risks.

### Recommendation F: Move “bootstrap” closer to where it’s needed (lazy bootstrap)

Ollama’s server starts without forcing downloads; artifacts are pulled lazily. ([Ollama Documentation][7])
Continue seeds config quickly and then users add. ([Continue][5])

A good hybrid for Stigmer:

* **Server start** applies only embedded seedpack (no network).
* `stigmer draft *` performs a **capability check** and if missing, offers:

  * “Install from embedded seedpack” (offline)
  * “Update from upstream” (online)

This keeps the “daemon path” reliable and pushes optional networking into user-invoked commands.

## Skill import best practices

### Git import is fine, but treat it as a *build step* that produces a pinned artifact

Codex explicitly separates “system bundled” skills from installed skills, and provides an installer that can download from other repositories. ([OpenAI Developers][1])
Terraform treats registries specially because signature verification is supported there. ([HashiCorp Developer][13])

For Stigmer:

* `skill.FromGit(...)` should **always resolve to**:

  * `repo url`
  * `commit sha` (resolved, not symbolic like `main`)
  * `subdir`
  * artifact digest (zip hash)

Then store the resolved artifact in your registry/cache.

* Avoid “live references” at runtime (“always use main”). That undermines reproducibility.

### Version pinning & updates

Borrow Terraform’s mental model:

* The lock file records selected versions/checksums and makes upgrades explicit (`-upgrade`). ([HashiCorp Developer][10])
  For Stigmer:
* `stigmer pull --upgrade` updates to latest allowed range
* otherwise keep using the pinned digest from lockfile

### Artifact format choice

Your “ZIP with content” approach is consistent with:

* Pulumi plugins cached locally and installable manually for air-gapped environments. ([pulumi][11])
  If you want an industry-standard container:
* store skills as **OCI artifacts** (registry + digest semantics), then optionally sign them with cosign. ([Sigstore][14])

## Server bootstrap patterns and guidance

### Should bootstrap block startup or run in background?

Evidence points to: **don’t block on anything that might need the network**.

* Ollama’s model storage is separate and configurable; server can start without pulling new content. ([Ollama Documentation][7])
* Continue’s initial bootstrap is just generating a local config file—cheap. ([Continue][5])
* K3s does auto-apply manifests on startup, but those manifests are local and integrity-managed. ([K3s][8])

So for Stigmer:

* Bootstrapping **embedded** seedpack content can block startup (it’s local and deterministic).
* Bootstrapping that requires network (git clone, registry pull) should be:

  * lazy (triggered by `draft`), or
  * explicit (`stigmer bootstrap --online`), or
  * asynchronous but clearly reported (server starts in “degraded” mode).

### Handling bootstrap failures gracefully

Steal K3s’s error surfacing pattern:

* errors show up in the AddOn object / events; i.e., the system persists the failure for inspection. ([K3s][8])

For Stigmer:

* persist bootstrap step status per step:

  * `seedpack.apply.embedded: ok`
  * `seedpack.fetch.upstream: skipped (offline)`
  * `seedpack.verify.signature: failed (reason)`
* expose `stigmer bootstrap status` to show actionable remediation.

## Trust, provenance, and attestation

### What you should track for `skill-creator`

Minimum provenance fields to store *with the skill version*:

* `source.type`: `embedded | git | registry | localpath`
* `source.url` (if git/registry)
* `source.ref` and resolved `source.commit_sha`
* `artifact.digest` (sha256)
* `retrieved_at`
* `verified.signatures`: list of verifications performed

This directly supports a Terraform-style “trust on first use” model, where the initial selection is reviewed, then future installations must match recorded checksums. ([HashiCorp Developer][10])

### Signing options

* **Terraform model**: registry-installed providers are cryptographically signed; Terraform verifies signatures during install. ([HashiCorp Developer][13])
* **Sigstore model**: sign/verify OCI artifacts (digest-binding is part of verification). ([Sigstore][14])

Recommended Stigmer path:

1. Treat your skill ZIPs as OCI artifacts (optional but powerful).
2. Sign seedpack and skill artifacts (cosign keyless or key-based).
3. Verify signatures during install and record verification result.

### User override of system skills

Yes—**but** do it safely:

* allow overrides by namespace/priority, not by mutating system artifacts
* allow disabling built-ins (Codex does). ([OpenAI Developers][1])
* keep system versions always addressable (for support/debug).

## Risk assessment and mitigations

### Risk 1: Supply-chain + promptware risk from auto-cloning on startup

**Failure mode:** first-run bootstrap pulls arbitrary upstream content at a privileged moment (server initialization).
**Mitigations:**

* Use embedded snapshot by default; network updates are opt-in.
* Pin to commit SHA, record digest.
* Require signature verification for “system” updates (cosign / signing pipeline). ([Sigstore][14])

### Risk 2: Upstream breaking changes (Anthropic skill format / content changes)

**Failure mode:** `main` changes break your bootstrapped drafter behavior.
**Mitigations:**

* never track `main`; track commit digest
* run a compatibility test suite as part of Stigmer release CI:

  * parse SKILL.md frontmatter
  * validate required fields, size limits, etc.
* provide migration adapters if format evolves.

### Risk 3: Network unavailable on first run

**Failure mode:** user can’t start the server (bad local-first UX).
**Mitigations:**

* server startup uses only embedded seedpack
* draft commands can offer “install from embedded” or “update online”
* persist “bootstrap status” and show remediation steps (K3s-style inspectability). ([K3s][8])

### Risk 4: Privilege escalation through skills

**Failure mode:** a malicious/buggy skill uses powerful tools (shell, filesystem, network) to exfiltrate secrets.
**Mitigations:**

* adopt explicit tool allowlists at the skill/agent boundary (Claude pattern). ([Claude Code][3])
* deny-by-default tool access
* require user confirmation for high-risk tools for non-system skills.

### Risk 5: “Silent drift” of system skills

**Failure mode:** system skills change and behavior shifts unexpectedly.
**Mitigations:**

* treat system seedpack updates like “dependency upgrades”:

  * update creates a diff
  * user (or CI) reviews and approves
* Terraform-style lock + checksum verification is the right mental model. ([HashiCorp Developer][10])

## Implementation considerations for Stigmer

### 1) Make seedpack a first-class “release artifact,” not a project

Instead of embedding a Go SDK project and running synthesis that may require external fetches, consider embedding:

* the **final** serialized resources (agents/skills/workflows) as an internal “system bundle”
* plus a `seedpack.manifest.json` describing:

  * bundle version
  * included digests
  * upstream provenance

Then “apply” is a pure local operation.

### 2) Bootstrap as a state machine with step-level durability

Model steps like:

1. `extract_bundle`
2. `apply_bundle_to_registry`
3. `register_system_agents`
4. `verify_integrity`
5. `mark_complete`

Store step completion in DB (or even a file) so it’s resumable.

### 3) Add a “skill lockfile” to Stigmer projects

A `stigmer.lock` that pins:

* `stigmer/skill-creator = sha256:...`
* `stigmer/yaml-validator = sha256:...`

This mirrors `.terraform.lock.hcl` expectations around code review for dependency changes. ([HashiCorp Developer][10])

### 4) Prefer “artifact registry” semantics over “git semantics”

If you keep `skill.FromGit`, make it compile to an immutable artifact:

* shallow clone (or use GitHub tarball), extract subdir, zip, hash, store
* always store the resolved commit sha

### 5) Expose “system vs user” scopes explicitly

Codex has system/user/repo/admin scopes, and calls out that SYSTEM is bundled. ([OpenAI Developers][1])
Stigmer should similarly make “system seeded” resources easy to reason about:

* `stigmer system list`
* `stigmer system diff --against upstream`
* `stigmer system disable <name>`

### 6) Treat schema validation as part of the drafting loop

Your “yaml-validator skill” idea is correct; make it:

* deterministic (actual schema check, not just LLM “looks right”)
* automatically invoked by the drafter workflow before output is accepted

This aligns with the general “prefer determinism/scripts for validation” guidance present in Codex skills docs. ([OpenAI Developers][2])

## Bottom line: Is your architecture sound?

Yes—the **seedpack bootstrap** idea is aligned with real-world patterns, especially the **K3s packaged components** style of “bundled content applied on startup with integrity and disable controls.” ([K3s][8])
And the “meta-skill to create skills” approach is strongly validated by **OpenAI Codex**, which explicitly bundles a built-in **skill creator** as a SYSTEM capability. ([OpenAI Developers][2])

The main change I’d make to your proposal is:

**Do not auto-clone upstream repos during server startup in the happy path.**
Embed a pinned snapshot, make online updates explicit, and add artifact digests + (ideally) signatures.
