# Deep Research: Platform Capabilities & Draft Commands Implementation Strategy

## Research Objective

Investigate the optimal implementation strategy for "Platform Capabilities" in a CLI tool—specifically, AI-powered `draft` commands that help users interactively author YAML configurations for various resource types. The core question is: **where should these platform-provided AI skills/capabilities live, and how should they be distributed?**

## Background Context

### What We're Building

**Stigmer CLI** is a command-line tool for managing AI agent resources. It follows a YAML-first approach where users define resources (agents, workflows, skills, MCP servers) in YAML files and apply them to a backend platform.

We're implementing `draft` subcommands for each resource type that provide **agent-assisted authoring**:

```
stigmer draft agent      # AI helps create agent YAML
stigmer draft workflow   # AI helps create workflow YAML  
stigmer draft skill      # AI helps create skill YAML
stigmer draft mcpserver  # AI helps create MCP server YAML
```

### How Draft Commands Work

When a user runs `stigmer draft agent`:
1. An AI agent asks questions about what they want to build
2. Based on responses, it generates a valid YAML configuration
3. The generated YAML follows the schema and includes best practices
4. User can iterate and refine the draft

### Critical Constraint: Skills Are Foundational

**Skills are the foundation of everything in Stigmer.** A skill defines what an AI agent can do. Before any agent, workflow, or MCP server can be created, the relevant skills must exist first.

This means:
- `stigmer draft agent` internally uses skills to provide the drafting capability
- `stigmer draft skill` uses skills to help create new skills
- These are **platform-provided skills**, not user-created skills
- They're essential for the CLI to function but shouldn't appear in `stigmer skill list` (user's skill inventory)

### The Implementation Question

We need platform-provided "drafting skills" that power these commands. The key question is: **where do these skills live and how are they distributed?**

## Known Information & Current Thinking

### Option A: Embed Skills in CLI Binary (go:embed)

The current project notes mention:
> "Platform Capabilities embedded in CLI - Drafting capabilities are platform functions, not user skills - Embedded via `go:embed` (~100KB, works offline)"

**Pros:**
- Works offline
- No network dependency at runtime
- Version-locked with CLI (consistency)
- Simple deployment

**Cons:**
- CLI binary size increases
- Updating skills requires CLI update
- No dynamic updates

### Option B: Host Skills in Public Repository

Similar to how Anthropic provides default prompts/skills publicly:
- Skills live in a public GitHub repository
- CLI fetches them on first run or periodically syncs
- Could be in Stigmer's own open-source monorepo or a dedicated repository

**Pros:**
- Skills can be updated independently of CLI
- Community can contribute/fork
- Smaller CLI binary

**Cons:**
- Requires network access (at least initially)
- Version compatibility concerns
- More complex distribution

### Option C: Hybrid - Bootstrap/Migrate on Install

When CLI is installed:
1. CLI checks if platform skills exist in user's environment
2. If not, syncs them from a known source (repository or embedded fallback)
3. Skills are stored locally but can be updated

Similar to how package managers sync their registries.

**Pros:**
- Balance of offline capability and updatability
- Skills can be customized by advanced users
- Clear separation of concerns

**Cons:**
- More complex implementation
- Migration/sync logic needed
- Potential state management issues
