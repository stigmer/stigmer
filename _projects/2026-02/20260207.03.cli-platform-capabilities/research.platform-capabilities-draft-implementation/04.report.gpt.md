## Executive Summary

**Recommendation: implement “Platform Capabilities” as a versioned *Capabilities Bundle* with a hybrid distribution model:**

1. **Embed a minimal, known-good baseline bundle in the Go CLI binary** (via `//go:embed`) so `stigmer draft *` always works without any extra network fetches and remains consistent with the CLI version.
2. **Allow optional, signed, versioned updates pulled from a public “capabilities registry”** (GitHub releases or a dedicated repo), cached locally, and only used when the bundle declares itself compatible with the installed CLI.
3. **Keep these drafting capabilities out of the user’s skill inventory** by treating them as **system/internal capabilities**, not user-managed “skills,” and exposing them only via a separate namespace and commands (e.g., `stigmer capabilities …`).

This is the most common “best of both worlds” pattern across modern agentic CLIs: ship a built-in system layer, allow local/workspace overrides, and provide a curated/updatable registry—while making compatibility and security explicit. You can see this clearly in:

* **OpenAI Codex “Agent Skills”**: system skills are built-in, additional skills can be installed, and skills exist in multiple scopes (system/admin/user/repo). ([OpenAI Developers][1])
* **GitHub Copilot CLI**: ships defaults (agents + MCP server) and supports user/repo/org scoped customization with precedence rules. ([GitHub Docs][2])
* **Kiro CLI (Amazon Q successor)**: maintains prompts/agents in user + workspace locations, supports MCP-provided prompts, and migrates/maintains backward compatibility between directory layouts. ([Kiro][3])

## Industry Research

### 1. What major AI-capable CLIs do

#### GitHub Copilot CLI

Copilot CLI is a strong reference model because it distinguishes between:

* **Built-in defaults** (it “includes a default group of custom agents” for common tasks). ([GitHub Docs][2])
* **User- and repo-scoped extensibility**:

  * Custom instructions from repository Markdown files (e.g., `.github/copilot-instructions.md`, `.github/instructions/**/*.instructions.md`, and agent files like `AGENTS.md`). ([GitHub Docs][2])
  * Custom agents loaded from **multiple locations** (user `~/.copilot/agents`, repo `.github/agents`, org/enterprise locations), with documented override precedence. ([GitHub Docs][2])
* **MCP integration with a shipped default**:

  * “Copilot CLI comes with the GitHub MCP server already configured,” and additional servers can be added interactively and stored locally (default `~/.copilot/mcp-config.json`, respecting `XDG_CONFIG_HOME`). ([GitHub Docs][2])

**Takeaway for Stigmer:** Copilot CLI treats “system capabilities” (defaults) as part of the product, while allowing layered overrides and configuration—without forcing those defaults into the user’s “inventory.”

#### OpenAI Codex CLI / Codex App: “Agent Skills”

Codex is directly relevant because it uses the word “skills” in a way very similar to your “platform skills” concept:

* **Skill packaging & structure:** skills are **folder-based bundles** with a required `SKILL.md` and optional scripts/resources/assets. ([OpenAI Developers][1])
* **Progressive disclosure:** Codex initially loads only metadata (`name`, `description`, file path, optional metadata) and loads full instructions only when needed. ([OpenAI Developers][1])
* **Multi-scope loading:** Codex reads skills from **repository, user, admin, and system** locations. ([OpenAI Developers][1])
* **Built-in system skills + installable curated/experimental skills:**

  * Codex “ships with a few built-in system skills… including `$skill-creator` and `$skill-installer`.” ([OpenAI Developers][4])
  * The public `openai/skills` catalog explains that skills in `.system` are automatically installed, while curated/experimental skills can be installed by name or URL via `$skill-installer`. ([GitHub][5])

**Takeaway for Stigmer:** this is almost exactly your desired split:

* a built-in/system set (non-user-inventory),
* plus curated community-updatable content,
* plus optional experimental channels.

#### Amazon Q Developer CLI → Kiro CLI

Kiro’s docs show a mature “prompt capability management” design:

* **Prompts are managed via a command system** (`/prompts …`) with clear types: local (workspace), global (user), and MCP prompts. ([Kiro][3])
* **Prompts are stored on disk** (e.g., workspace prompts saved to `.kiro/prompts/`). ([Kiro][3])
* **Migration strategy:** when migrating from Amazon Q Developer CLI, prompts/agents and MCP config are copied from `~/.aws/amazonq` to `~/.kiro` and Kiro maintains backward compatibility by continuing to read old folders. ([Kiro][6])
* **Offline/enterprise constraints are explicitly handled:** e.g., Kiro’s `introspect` tool downloads embedding models by default but supports a “progressive mode” for environments where downloads are blocked. ([Kiro][7])

**Takeaway for Stigmer:** treat drafting capabilities as disk-managed artifacts with explicit migration and offline-friendly modes.

#### Anthropic Claude Code

Claude Code’s CLI reference shows explicit support for supplying a system prompt from a file (`--system-prompt-file`)—a clear “embedded defaults + file override” pattern. ([Claude Code][8])
Anthropic also documents sandboxing and security considerations for agentic tooling, reinforcing that “capabilities” can become a security boundary. ([Anthropic][9])

### 2. Skill/prompt registries in AI platforms

Two strong “prompt registry” references:

#### LangSmith / LangChain Hub

LangSmith supports:

* **Commit tags** to reference stable versions in code (e.g., `:prod`) without changing code when you retarget the tag. ([LangChain Docs][10])
* **Pulling specific versions** by commit hash/tag. ([LangChain Docs][11])
* **Stale-while-revalidate caching** to reduce latency and keep prompts fresh. ([LangChain Docs][11])
  LangChain Hub provides `hub.pull` / `hub.push` for centralized artifacts. ([LangChain Docs][12])

#### PromptLayer Prompt Registry

PromptLayer’s API explicitly supports:

* retrieving templates by name/id,
* selecting **version or label (e.g., “prod”)**,
* and warns about provider-specific schema drift, recommending stable prompt data fields. ([PromptLayer][13])

**Takeaway for Stigmer:** versioned prompt artifacts + stable labels (“stable”, “beta”) + caching is a common, solved pattern.

### 3. Offline-first patterns from mainstream CLIs

Even beyond AI tooling, the “offline + updateable” problem is well-trodden:

* **Terraform provider mirroring**: `terraform providers mirror` downloads required provider plugins into a local filesystem directory for offline/air-gapped environments. ([HashiCorp Developer][14])
* **Terraform plugin cache**: `plugin_cache_dir` improves performance and reduces repeated downloads. ([HashiCorp Developer][15])
* **Terraform disables network checks**: `disable_checkpoint` disables upgrade/security checks that require network access. ([HashiCorp Developer][15])
* **Krew plugin index model**: a default plugin index plus custom indexes; “update” is explicit (`kubectl krew update`) before installing plugins. ([Krew][16])

**Takeaway for Stigmer:** “explicit update command + local cache + optional mirrors + disable network checks” is the standard offline-friendly UX.

## Pattern Analysis

### Pattern 1: System layer + override scopes (system → user → repo → org)

This is the most important pattern to adopt for Stigmer.

Examples:

* Copilot CLI custom agents come from multiple locations with precedence rules (system overrides repo overrides org, etc.). ([GitHub Docs][2])
* Codex skills load from multiple scopes including system/admin/user/repo. ([OpenAI Developers][1])
* Kiro prompts are global/user + workspace + MCP-provided. ([Kiro][3])

**Stigmer mapping:** your “drafting skills” should be a **system scope** capability bundle, with optional:

* user overrides (power users),
* repo/workspace overrides (project conventions),
* org-managed overrides (teams).

### Pattern 2: Registry + versioning + caching

Examples:

* LangSmith commit tags and stale-while-revalidate caching. ([LangChain Docs][10])
* PromptLayer version/label retrieval and provider-schema warnings. ([PromptLayer][13])
* Terraform mirrors/caches for offline. ([HashiCorp Developer][14])

**Stigmer mapping:** if you decouple capability updates from CLI releases, you need:

* **a versioned artifact**
* **compatibility metadata**
* **a cache**
* **explicit update UX**
* **a rollback/pin mechanism**

### Pattern 3: Security boundary: prompts and “skills” are supply-chain inputs

Two risks matter:

1. **Supply-chain tampering** (malicious bundle delivered via network).
2. **Prompt injection** (malicious instructions inside a repo or dependency that the agent consumes).

A real-world cautionary example: reporting on **prompt injection vulnerabilities impacting Amazon Q tooling** illustrates how “instructions as data” can become an exploit path. ([Tom's Hardware][17])

**Stigmer mapping:** treat remotely fetched drafting capabilities as “code”:

* signed,
* pinned,
* validated,
* and ideally not executable.

## Recommended Architecture for Stigmer

### High-level architecture

```
                 ┌───────────────────────────┐
                 │ Stigmer CLI binary         │
                 │  - embedded baseline bundle│
                 └─────────────┬─────────────┘
                               │ bootstrap
                               v
┌────────────────────────────────────────────────────┐
│ Local capability cache (XDG data dir)              │
│  capabilities/                                     │
│   ├─ bundles/<version>/...                         │
│   ├─ manifest.json                                 │
│   └─ pinned.lock (optional)                        │
└─────────────┬──────────────────────────────────────┘
              │ load best compatible bundle
              v
┌────────────────────────────────────────────────────┐
│ Draft engine (stigmer agent|workflow|skill|mcp draft)│
│  - Q&A flow + YAML generation                       │
│  - deterministic validation in CLI                  │
└─────────────┬──────────────────────────────────────┘
              │ optional explicit update
              v
┌────────────────────────────────────────────────────┐
│ Capabilities registry (GitHub releases / repo)     │
│  - signed bundle tarballs                           │
│  - compatibility metadata                           │
└────────────────────────────────────────────────────┘
```

This mirrors:

* Codex’s system + installable skills model ([GitHub][5])
* Terraform’s cache/mirror/offline approach ([HashiCorp Developer][14])
* Krew’s explicit update/install UX ([Ray][18])

### Where the capabilities should live

#### In code: embed a baseline bundle

Use `//go:embed` to ship a baseline set of drafting skills in the CLI so:

* first-run works without a separate download,
* `stigmer draft skill` has a bootstrap path,
* behavior is version-locked to the CLI release.

Go supports embedding entire directory trees via `embed.FS`. ([Go Packages][19])

**Practical size guidance:**
Your estimate (~100KB) is nowhere near problematic. Total embedded size limits are platform-dependent (32-bit systems can be constrained around ~2GB total), and there’s historically a ~2GB per-file constraint reported in the Go toolchain. ([Google Groups][20])

#### In source control: store the authored skills as first-class artifacts

For collaboration, CI testing, and community contributions, keep the source of truth in git.

A proven structure is “one folder per capability,” similar to Codex skills being directories with a required instructions file plus optional assets. ([OpenAI Developers][1])

**Suggested repo layout (monorepo-friendly):**

* `capabilities/draft/agent/...`
* `capabilities/draft/workflow/...`
* `capabilities/draft/skill/...`
* `capabilities/draft/mcpserver/...`
* `capabilities/manifest.yaml`

**If you want community contribution + independent release cadence:** consider a **separate** `stigmer/capabilities` repo, analogous to how ecosystems separate “indexes/catalogs” from core binaries (Krew’s default index is in a dedicated repo). ([Krew][16])

My recommendation in practice:

* **Start in the main monorepo** for tight coordination.
* **Publish bundles as GitHub release assets** (so you get immutable versioned artifacts).
* Optionally split into a separate repo later once the format stabilizes.

### How updates should work

#### Commands and UX

1. **Non-blocking on normal use**

* `stigmer draft agent` uses whatever compatible bundle is installed locally.
* If no cache exists, bootstrap from embedded bundle.

2. **Explicit update command**

* Provide:

  * `stigmer capabilities status`
  * `stigmer capabilities update`
  * `stigmer capabilities pin <version>` / `unpin`
  * `stigmer capabilities list` (system-only; not part of user skills)

This matches the “explicit update” convention from Krew (`kubectl krew update`). ([Ray][18])

3. **Optional lightweight update notification**

* Once per day/week: fetch only a small manifest, compare versions, print:

  * “New drafting bundle available (vX.Y). Run `stigmer capabilities update`.”

Also provide an “offline / enterprise” switch akin to Terraform’s `disable_checkpoint` (disable network checks). ([HashiCorp Developer][15])

#### Cache & refresh mechanics

Adopt a stale-while-revalidate mental model:

* Always run off the local cache.
* Only refresh in update workflows (or optional background checks).
  LangSmith explicitly recommends stale-while-revalidate caching for prompts. ([LangChain Docs][11])

---

### Version compatibility strategy

This is the part that prevents “skills updated independently of CLI” from becoming a footgun.

#### 1. Bundle manifest with compatibility ranges

Every capabilities bundle should include:

* `bundleVersion` (semver)
* `minCliVersion` / `maxCliVersion` (or a semver range)
* `skillSchemaVersion`
* `resourceSchemaVersion` (for your YAML schemas)
* optional: `channels: [stable|beta|experimental]`
* a file hash list

Then:

* CLI selects the **highest installed bundle that matches** its compatibility constraints.
* If a newer downloaded bundle is incompatible, it is kept but ignored.

This is conceptually identical to:

* LangSmith letting you pin by commit hash/tag ([LangChain Docs][10])
* PromptLayer letting you pull a specific version/label ([PromptLayer][13])
* “plugin version compatibility” warnings in real plugin ecosystems (example: a kubectl plugin warning about compatibility with older controllers). ([Ray][18])

#### 2. Channels for stability

Borrow the Codex idea of `.system` vs curated vs experimental. ([GitHub][5])

For Stigmer, define:

* `system` (embedded baseline, always present)
* `stable` (default update channel)
* `experimental` (opt-in)

---

### Handling skill schema evolution

When the **format of “skills”** changes:

1. **Version the schema explicitly** (`skillSchemaVersion: 1|2|…`).
2. **Support at least N previous schema versions** in the CLI (especially within a major CLI version line).
3. **Publish bundles per schema version** rather than forcing immediate migrations.
4. Offer `stigmer capabilities doctor`:

   * validates cache integrity,
   * flags incompatible bundles,
   * can “cleanup older bundles.”

Kiro demonstrates a pragmatic approach: it migrates configuration directories and still reads legacy locations to maintain backward compatibility. ([Kiro][6])

---

### Security considerations

#### Embedding vs fetching

* **Embedding** ties capability content to the signed CLI release artifact.
* **Fetching** introduces a supply-chain and tampering risk.

If you fetch:

* use **signed bundles** (cosign/sigstore, GPG, etc),
* verify checksums,
* allow only trusted registries by default.

#### Prompt-injection and untrusted repositories

Even if your platform skills are trusted, your draft flows may load **project context** (readme, existing YAML, comments). Prompt injection attacks against agentic tools are not hypothetical; public reporting around Amazon Q prompt injection underscores the need to treat “instructions in repos” as an attack surface. ([Tom's Hardware][17])

#### Executable capability content

If your “skills” can include scripts/tools, avoid executing remotely fetched code. Prefer:

* **instruction-only** skills in bundles,
* deterministic validation implemented in Go,
* and explicit user confirmation for any file writes.

This parallels best practices discussed for agentic tool safety and sandboxing. ([Anthropic][9])

## Implementation Considerations for a Go CLI

### 1. Embedding and loading

* Use `embed.FS` to embed a directory of capability definitions. Go’s embed directive supports embedding into `embed.FS`, `[]byte`, or `string`. ([Go Packages][19])
* Recommended: embed a single directory like `internal/capabilities/baseline/` containing:

  * `manifest.json`
  * `skills/**/*.yaml`
  * `examples/…`

### 2. Local storage paths

Follow the pattern used by other CLIs:

* Support XDG locations (Copilot CLI notes config in `~/.copilot` and allows overriding with `XDG_CONFIG_HOME`). ([GitHub Docs][2])
* You can store capabilities under `XDG_DATA_HOME` (not config), e.g.:

  * Linux/macOS: `$XDG_DATA_HOME/stigmer/capabilities/…` (fallback `~/.local/share/...`)
  * Windows: `%LOCALAPPDATA%\Stigmer\capabilities\…`

### 3. Sync and concurrency

* Ensure updates are atomic:

  * download to temp dir,
  * verify signature + checksums,
  * then rename into `bundles/<version>/`.
* Use a file lock for concurrent CLI invocations.

### 4. Validation pipeline

In CI for the capabilities repo/dir:

* parse YAML,
* validate against your proto-derived JSON schema,
* run “golden tests” for draft outputs.

OpenAI explicitly recommends treating skills as testable artifacts using eval-like workflows to prevent regressions. ([OpenAI Developers][21])

### 5. UX behaviors inside `draft`

* Always validate generated YAML locally before writing.
* Consider a “plan-like” UX: show YAML, ask confirmation to write, then save.
* Support iterative refine loops.

### 6. Don’t mix user skills and system capabilities

Internally:

* define `CapabilityBundle` type separate from `SkillResource`.
* `stigmer skill list` only lists user resources.
* `stigmer capabilities list` lists internal “draft packs.”

This mirrors the “system vs user vs repo scopes” separation seen in Codex and Copilot CLI. ([OpenAI Developers][1])

## Direct answers to your specific questions

1. **What do major AI CLIs do—embed, fetch, or hybrid?**
   Predominantly **hybrid**:

   * Built-in defaults + file-based overrides + optional ecosystem/registry content (Copilot CLI, Codex skills, Kiro prompts). ([GitHub Docs][2])

2. **Is there a standard pattern for platform capabilities that aren’t user-visible?**
   Yes: a **system scope layer** (built-in) plus layered overrides. Copilot CLI has system-provided agents and precedence across locations. ([GitHub Docs][2])
   Codex explicitly has built-in system skills and multiple scopes. ([OpenAI Developers][1])

3. **Practical `go:embed` size limit? Is ~100KB fine?**
   ~100KB is extremely safe. Go embed supports embedding files into the binary via `embed.FS`. ([Go Packages][19])
   Total embedded size is platform dependent (32-bit platforms often can’t support totals above ~2GB). ([Google Groups][20])
   There’s also a documented “file too large” issue around ~2GB per file in the toolchain. ([GitHub][22])

4. **If hosted in a public repo: monorepo or separate repo? structure?**

   * **Monorepo first** for tight coupling and testing; publish bundles as release artifacts.
   * **Separate repo later** if you want faster iteration independent of CLI and community contributions, similar to catalog/index models. ([Krew][16])
   * Structure: **one folder per capability/skill** + top-level manifest, like the Codex skills folder standard. ([OpenAI Developers][1])

5. **Recommended sync/migration pattern?**

   * Explicit update command (Krew-style). ([Ray][18])
   * Local caching + optional mirrors for offline (Terraform-style). ([HashiCorp Developer][14])
   * If you ever change on-disk layouts, copy forward and keep reading legacy paths (Kiro migration-style). ([Kiro][6])

6. **How to handle skill schema evolution?**

   * Put `skillSchemaVersion` in the bundle manifest.
   * Publish multiple bundles per schema version as needed.
   * CLI selects compatible bundle; fallback to embedded baseline.
   * Offer a `capabilities doctor` / `migrate` command.
     (Kiro’s backward compatibility approach is a good model.) ([Kiro][6])

7. **Security considerations for dynamic fetching vs embedding?**

   * Embedding reduces supply-chain risk.
   * Fetching requires signatures/checksums and trust policy.
   * Prompt-injection is a real risk in agentic tools; treat repository text as untrusted input. ([Tom's Hardware][17])

8. **UX pattern for “updates available”?**

   * Non-blocking notification + explicit update command is common (e.g., update the index, then install). ([Ray][18])
   * Provide an opt-out/disable flag for network checks (Terraform-style). ([HashiCorp Developer][15])
