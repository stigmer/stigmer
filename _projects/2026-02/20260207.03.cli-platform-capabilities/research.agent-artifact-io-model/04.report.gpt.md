# Agent Artifact Input/Output Model for Sandboxed Agentic Platforms

## Executive summary and design goals

A production-grade artifact lifecycle for sandboxed agents usually converges on one core idea: **separate “conversation” from “artifacts.”** Conversations are lightweight, durable logs of intent and results; artifacts are **durable, addressable blobs and trees** (files/directories) stored outside the sandbox, with explicit lifecycle policies (retention, versioning, quotas, access control). citeturn18view1turn18view0turn25view2

The most resilient model for your architecture is a **two-layer persistence strategy**:

- **Durable artifact store (required):** store all user-uploaded inputs and agent-produced outputs in object storage (you already have Cloudflare R2 / S3-compatible storage). This layer survives sandbox failures and session boundaries. citeturn20search8turn20search0  
- **Durable sandbox workspace (optional but powerful):** mount persistent storage into the sandbox so the “working directory” survives sandbox recreation. In Daytona, this is directly supported via **Volumes**, which are FUSE mounts backed by an S3-compatible object store and can be mounted across sandboxes (including with per-user subpaths for isolation). citeturn17view0turn8view0

This dual approach matches what high-scale platforms do in practice: **work happens in an ephemeral execution environment, state is checkpointed into durable storage, and deliverables are exported via a first-class “artifact download” mechanism** rather than relying on the sandbox’s lifespan. citeturn22view1turn22view0turn18view1

## Survey of approaches in leading platforms

### Conversation-style assistants: attachments in, downloadable artifacts out

Modern chat assistants that support files generally separate “chat text” from “uploaded files” and “generated files,” each with their own limits and retention behaviors.

- In ChatGPT, users can upload multiple file types (documents, spreadsheets, PDFs, etc.) with explicit per-file limits (e.g., 512MB hard limit; spreadsheets effectively lower) and per-user/org caps; files are retained according to plan and chat retention policies. citeturn4view1turn4view0  
- ChatGPT’s “data analysis” experience provides **UI-native downloads** (e.g., table download button, chart downloads) and can generate downloadable files when the code execution tool is enabled; there are explicit file download size limits (512MB is referenced for downloadable files in the custom GPT context). citeturn24view0turn24view1  
- Claude’s “Artifacts” emphasize a **separate artifact surface** (sidebar window) for substantial, reusable content and include explicit “View and export” affordances including “Download files to use outside the conversation.” citeturn24view2  
- Claude’s artifact feature also highlights an important product lesson: **persistence for artifact state has explicit scoping and quotas** (personal vs shared storage; size limits; deletion behaviors when artifacts are unpublished). Even though Claude’s persistent storage is text-only for that feature, the governing concept—explicit store, explicit quota, explicit deletion semantics—maps well to your platform’s needs. citeturn24view2

A parallel pattern exists in Claude’s API-level “Files API”: a **create-once, use-many-times** design where files are uploaded to secure storage, referenced by an ID in subsequent requests, and managed via list/retrieve/delete. This is essentially the same pattern you want for agent inputs (reference materials) and in many cases for outputs (deliverables). citeturn6view0

**Key takeaway:** user experience improves when file inputs/outputs are first-class objects with IDs, metadata, and a dedicated download/export surface—not when they are embedded as raw bytes in chat messages. citeturn24view2turn6view0turn24view0

### IDE agents: multi-file context in, edits and reviewable changes out

IDE agents emphasize two things you can reuse in your platform design:

1) **Users attach or select context at file/folder granularity**, not just paste text.  
2) **Outputs are often presented as structured “changes”** (diffs, file edits, PRs), not as raw text blobs.

Examples from major IDE ecosystems:

- JetBrains’ AI Assistant UI explicitly supports attaching **files and folders** (and other structured context) to requests; and in agent mode it can propose **multi-file changes** that users review before applying. citeturn25view0  
- VS Code’s Copilot workspace context system builds a “workspace index” from indexable files and directory structure, and uses strategies like remote indexing and semantic search to ground responses in the codebase. This is effectively a formalized “artifact ingestion” pipeline: the system continuously transforms workspace files into a searchable context store rather than requiring manual copy/paste. citeturn25view1  
- In the Devin ecosystem, one primary “deliverable surface” is the **pull request / branch**: Cognition’s product update describes Devin responding to comments “on its PRs,” a timeline/checkpoint system that can roll back files and memory, and MultiDevin merging changes “into one branch or pull request.” citeturn26view0

**Key takeaway:** for code- and file-producing agents, the most usable “output model” is not “a long text response,” but **(a) reviewable changes to a file tree** and/or **(b) an exportable artifact package** (e.g., a zip, a repo branch/PR, or a registry push). citeturn25view0turn26view0turn18view3

### CI/CD and orchestration: artifacts as durable outputs, references passed through workflows

Two mature families of systems are particularly informative for your problem: CI/CD artifact systems and workflow orchestrators.

- GitHub Actions treats artifacts as **named, uploaded directories/files** that can be shared between jobs and persisted after runs. Workflows upload artifacts, optionally set retention, and later download them (either within a workflow run or externally). This aligns very closely with “agent runs create output directories.” citeturn18view3  
- GitHub also makes retention a first-class control. For organizations, default retention for Actions artifacts/logs is 90 days (with configurable ranges depending on repo type). citeturn25view2  
- Temporal documentation strongly cautions against passing large blobs through workflow/activity payloads because **payload sizes are limited** (default 2MB per payload, 4MB hard limit per gRPC message/history transaction) and large histories degrade performance. Their troubleshooting guidance explicitly recommends **offloading large payloads to object stores and passing references instead**. citeturn18view1turn18view0  
- The existence of community solutions like Datadog’s “temporal-large-payload-codec” reinforces the pattern: even when you can technically encode large payloads, the preferred operational approach is to store blobs externally and keep workflow history small. (Notably, that repo itself warns it is not production-ready and is meant to further discussion.) citeturn18view2

**Key takeaway:** because you run on Temporal and gRPC, you should assume that **artifact bytes do not belong in workflow history**; they belong in external blob storage with IDs/URLs referenced by workflow state. citeturn18view1turn18view0

## Persistence and sandbox survivability patterns

### What “persistence” means in practice

Real systems distinguish at least four persistence tiers:

- **Ephemeral execution filesystem:** fast scratch space; safe to lose.  
- **Persistent workspace filesystem:** survives restarts/recreates; used for iterative work.  
- **Durable artifact store:** immutable or versioned deliverables and checkpoints in object storage.  
- **Source-of-truth repository/registry:** the long-term distribution channel (Git repo, skill registry), where “publishing” happens.

This layered model appears repeatedly:

- Gitpod’s lifecycle explains this explicitly: workspaces are ephemeral containers, but content in `/workspace` is backed up on stop and restored on restart; only that directory is preserved across transitions. citeturn22view1  
- GitHub Codespaces similarly emphasizes that stopping/restarting a codespace does not lose saved changes; but deleting it does delete the work, and persistence ultimately depends on pushing commits (or otherwise exporting). It also distinguishes preserved paths across rebuilds (e.g., `/workspaces` preserved; changes outside cleared). citeturn22view0  
- Replit’s docs/blog ecosystem describes durable storage concepts such as “Object Storage” as a durable place for unstructured data, and differentiates workspace-development files from deployment/runtime and storage choices. citeturn3search8turn3search12turn3search19

### Daytona-specific capabilities that directly address your “ephemeral sandbox” gap

Your current assessment (“sandbox filesystem is ephemeral and there’s no download API”) is partially outdated relative to Daytona’s documented SDK capabilities. Daytona provides three critical building blocks:

**Sandbox file retrieval exists.** The Daytona SDK `fs` supports downloading single files and multiple files (`download_file`, `download_files`), and directory listings (`list_files`) to build a tree/manifest. citeturn6view1turn6view2  

**Persisted storage is supported via Volumes.** Daytona Volumes are FUSE-based mounts backed by an **S3-compatible object store**, mountable into one or multiple sandboxes, and explicitly designed to “persist files beyond the lifecycle of any individual sandbox.” The docs also support mounting a **subpath** (useful for tenant isolation under a single volume) and list limitations (slower than local filesystem; not suitable for block-storage-like DB workloads). citeturn17view2turn17view0turn8view0  

**Whole-sandbox persistence exists via stop/archive states.** Daytona’s sandbox lifecycle includes distinct states:  
- a **stopped** sandbox “maintain[s] filesystem persistence while their memory state is cleared,” with cost implications;  
- an **archived** sandbox moves the “entire filesystem state” to “very cost-effective object storage,” trading slower start times for lower cost. citeturn16view2turn8view1  

Daytona also provides operational lifecycle controls you should factor into your reliability design:

- Auto-stop can trigger even if internal processes are still running; only certain external interactions reset the inactivity timer. This matters if you run long agent jobs without continuous SDK interaction. citeturn23view0  
- Sandboxes can be “recoverable” in certain error states, and recovery is explicit rather than automatic. citeturn23view0  
- Daytona supports webhooks for sandbox/snapshot/volume lifecycle event categories, with a consistent payload envelope, enabling you to react to lifecycle transitions in your platform (e.g., trigger a checkpoint or update platform metadata on “sandbox.archived”). citeturn16view0

### Mapping Daytona persistence to your platform’s requirements

Your requirements (“user-created artifacts must survive sandbox failures and session boundaries”) can be satisfied in Daytona in two non-exclusive ways:

- **Workspace persistence:** Put user work under a mounted Volume path (example: `/workspace` or `/home/daytona/workspace`), so that sandbox recreation does not destroy work. The docs explicitly state files written to the volume persist even after the sandbox is deleted. citeturn17view0turn17view2  
- **Artifact persistence:** Export deliverables via `fs.download_*` or by zipping inside the sandbox and uploading to object storage; then treat the sandbox as disposable. citeturn6view1turn6view2  

Because you already have Cloudflare R2 and because R2 provides an S3-compatible API, it is plausible (and strategically aligned) to unify durability on “S3-compatible blob storage” across both your existing artifact store and Daytona’s volume-backed persistence model. citeturn20search8turn17view0  

## Recommended end-to-end artifact lifecycle architecture for your platform

### A reference lifecycle that matches your stages

Below is an end-to-end lifecycle design mapped to your seven stages, using the **durable artifact store + persistent workspace** model.

**Stage: Input / Upload**  
Implement an `ArtifactService` that supports “create upload → upload bytes → finalize,” returning an immutable `artifact_id` plus metadata (size, hashes, content type, logical paths). This mirrors Claude’s “upload once → reference file_id later” API design. citeturn6view0  

**Stage: Inject into sandbox**  
When an agent execution begins, your runner:

- Ensures a sandbox exists.  
- Mounts (or re-mounts) the appropriate persistent workspace Volume.  
- Downloads referenced input artifacts from the durable store and injects them into **predictable mount points** (e.g., `/inputs/<artifact_id>/...`) or copies them into the Volume-backed workspace path. citeturn17view0turn6view2  

**Stage: Process**  
Agent reads/writes under:

- `/workspace` (Volume-backed) for “project state,” and  
- `/tmp` (ephemeral) for caches / intermediate / re-derivable outputs.

This is directly aligned with Daytona’s warning that Volumes are slower than local FS; you want to reserve the Volume for critical state. citeturn17view2turn17view0  

**Stage: Persist**  
Two ways to persist “important outputs,” both supported:

- **Explicit publish:** agent calls a tool like `publish_artifact(path=/workspace/my-skill, kind=skill_dir)` which causes the runner to package the directory (zip/tar), generate a manifest, and upload to R2.  
- **Automatic checkpointing:** runner auto-publishes checkpoints on state transitions (e.g., on sandbox stop/archive, or on workflow step completion), with retention policies and quotas. Daytona’s lifecycle controls and webhooks make event-driven checkpointing feasible. citeturn16view0turn23view0turn18view3  

**Stage: Output / Retrieve**  
Expose artifacts to users as durable objects:

- Web UI: artifact browser (tree view + download zip button), similar in spirit to Claude artifacts’ “dedicated window” and export controls. citeturn24view2  
- CLI: `stigmer artifacts get <artifact_id> --out ./` downloads and unpacks.  
- API: `GetArtifactManifest`, `DownloadArtifact` (signed URL or streaming).

This matches how CI systems present workflow outputs as downloadable artifacts, with retention. citeturn18view3turn25view2  

**Stage: Cleanup**  
Your cleanup activity should delete or archive sandboxes **only after** outputs are persisted. Alternatively, prefer archiving over deletion for a grace period, since Daytona supports archiving to object storage to preserve filesystem state for extended periods. citeturn16view2turn8view1  

### Unit of persistence: session vs project vs user

Based on patterns from workspace-based platforms, a **project-scoped workspace** is usually the most stable unit of persistence:

- Gitpod preserves `/workspace` across restarts even though containers are disposable. citeturn22view1  
- Codespaces preserves saved changes across stops/restarts and deletes after policy thresholds; the lifecycle is “codespace” (project-like) rather than “chat session.” citeturn22view0  

For your platform, a practical mapping is:

- **User**: principal for auth/quota.  
- **Project**: durable “workspace root” (Volume subpath).  
- **Session**: conversational execution context (may come and go).  
- **Execution**: one run within a session (produces outputs and/or checkpoints).

Daytona volumes support subpaths specifically “for isolating data or implementing multi-tenancy,” which fits a `volume/<org>/<user>/<project>` layout inside one or many volumes. citeturn17view0  

## API and workflow design suggestions

### gRPC design for artifact input

You have two viable gRPC-compatible ways to handle file inputs; in practice most platforms implement both.

**Option: Out-of-band upload with references (recommended default)**  
1. Client calls `CreateArtifactUpload` and receives signed upload parameters (or an upload token).  
2. Client uploads directly to object storage (reduces load on your control plane).  
3. Client calls `FinalizeArtifactUpload` to register metadata and receive `artifact_id`.  
4. Agent execution spec references `artifact_id` and desired mount target.

This matches the general “upload once, reference by ID” pattern used in Claude’s Files API and in CI artifact systems. citeturn6view0turn18view3  

**Option: gRPC streaming uploads (useful for CLI and small/medium artifacts)**  
Be careful with message sizing: gRPC implementations commonly enforce per-message limits (4MB is a commonly referenced default in server/client implementations), and streaming is the recommended approach for long-lived flows. citeturn19search14turn19search7  

If you do gRPC streaming, use a “metadata first, then chunks” protocol (client-streaming) and store chunks into object storage as they arrive. Also note that streaming RPCs are constrained to one message type per direction; if you need mixed message types, you’ll likely use `oneof`/`Any` patterns. citeturn19search3  

### gRPC design for artifact output

For outputs (like skill directories), you want both:

- **Artifact listing & metadata:** cheap unary RPC, returns manifest summaries and artifact IDs.  
- **Artifact download:** either server-streaming (bytes chunks) for CLI/programmatic use, or signed URL download for browsers.

GitHub Actions’ model—upload directories, name them, download later, manage retention—maps closely to your output requirements and provides users a familiar mental model. citeturn18view3turn25view2  

### Response schema: representing directory structures

Your `AgentExecutionStatus` should grow artifact-aware fields (conceptually):

- `repeated OutputArtifact artifacts`
- `OutputArtifact { artifact_id, kind, root_path, manifest_id, size_bytes, created_at, retention_policy, preview }`
- `ArtifactPreview` could contain a tree listing for small outputs: `[{path, is_dir, size, sha256, mime}]`

Daytona’s SDK already has the primitives you’d use to create this manifest (`list_files`, `get_file_info`, and downloads). citeturn6view1turn6view2  

### Temporal workflow integration: avoid “artifact bytes in workflow history”

Temporal’s docs make the constraints and the correct design direction explicit:

- Activity and workflow payloads are limited (2MB per request payload; 4MB per event-history transaction/gRPC message). citeturn18view1turn18view0  
- Large payloads hurt workflow performance because history is transferred for recovery; the recommended mitigation includes offloading to object stores and passing references. citeturn18view0turn18view1  

Therefore:

- Your workflows should pass **artifact references** (IDs/URIs) between activities, not the bytes.  
- Artifact upload/download should be its own activity layer (or service) that is idempotent and retryable; the workflow stores only metadata and IDs.  
- If you ever need transparent large-payload handling, treat it as an advanced feature; even prominent community implementations caution against production use without upstream support. citeturn18view2

A minimal production-safe MVP (that closes your three critical gaps) can be staged as:

- Add “output artifact references” to execution status; runner packages output directories to zip and uploads to R2, returning artifact IDs. Use GitHub Actions’ artifact semantics as a UX guide (named artifacts, retention policy). citeturn18view3turn25view2

**Second milestone: Persistent workspace to prevent “mid-work” loss**  
- Adopt Daytona Volumes for workspace directories, using volume subpaths per project/user to isolate tenants. citeturn17view0turn17view2  
- Change your “session → sandbox” model to “project → volume subpath” and treat sandboxes as disposable compute that mounts the project workspace.  
- Continue exporting deliverables as artifacts (zip) for explicit downloads and for “push to registry” flows.

This milestone reduces operational risk for iterative workflows (skill creation sessions), where users expect their in-progress edits to survive crashes. citeturn17view2turn22view1turn22view0  

**Third milestone: Lifecycle automation and policy**  
- Enforce retention/quotas at the artifact store layer (default retention, user/org quotas), similar to GitHub’s explicit artifact/log retention policy controls. citeturn25view2

### Trade-offs that matter most

**Mount vs checkpoint sync**  
- Mounting (Daytona Volumes) gives near-real-time persistence and supports sandbox replacement without copying the whole workspace, but volumes are FUSE-based and “generally slower” than local sandbox file systems; also not suitable for block-storage workloads (databases). citeturn17view2turn17view0  
- Checkpoint sync (zip + upload to object store) is simpler to reason about for outputs and versioning but can lose data if the sandbox dies before a checkpoint and can be expensive for frequent large trees. citeturn18view1turn18view3  

A hybrid is usually best: **Volumes for active workspace state, artifact exports for deliverables and versioned checkpoints.** citeturn17view2turn25view2  

**Embedded response vs external download**  
- Conversation-embedded downloads (download buttons, artifact panels) are a strong UX pattern: ChatGPT uses download controls for generated tables/charts; Claude explicitly separates “artifact content” into a dedicated pane with export/download controls. citeturn24view0turn24view2  
- For large outputs, external downloads (artifact store URLs, CLI download) scale better and avoid putting bytes into chat history or workflow payloads (critical with Temporal’s payload limits). citeturn18view1turn18view0  

**Ephemeral-only vs persistent-by-default**  
- Ephemeral-only can work for “one-shot” executions if every deliverable is exported immediately, but it is fragile for iterative tasks (skill authoring) and makes “return to session” unreliable. citeturn22view0turn22view1  
- Persistent-by-default (workspace volume + artifact exports) matches established developer workflows and reduces user trust failures.

### Failure mode handling

**Sandbox dies mid-execution**  
Mitigations should target both “compute continuity” and “data continuity”:

- Store all important in-progress work in a Volume-backed workspace path, so a sandbox crash does not delete the working directory. Daytona explicitly states volume-written files persist beyond the lifecycle of individual sandboxes. citeturn17view2turn17view0  
- Be aware auto-stop can happen even while internal processes run, unless there is qualifying external interaction; if you rely on long-running tasks, your runner should keep the sandbox “active” via periodic SDK calls, or configure auto-stop appropriately. citeturn23view0turn8view1  
- Use explicit “publish” steps to export deliverables into the artifact store, ensuring durable outputs even if the workspace later changes. citeturn18view3turn25view2  

**User returns to a dead session**  
Design for rehydration:

- Recreate a sandbox and mount the same project subpath within the volume; your state returns. Daytona volume subpaths are explicitly supported for multi-tenancy/isolation. citeturn17view0  
- If you do not use volumes initially, rehydrate by pulling the most recent checkpoint artifact (zip) from R2 and injecting into the new sandbox (still workable; just slower). citeturn6view2turn18view3  

**Storage backend unavailable**  
This is the hardest failure because it affects both inputs and outputs:

- For inputs: fail fast before starting agent execution if required input artifacts cannot be fetched; store clear error state in session/execution.  
- For outputs: if object storage is down, keep outputs in the persistent volume/workspace and mark the execution as “completed but not published,” allowing later publish retries. (This is one reason Volumes are valuable as a second persistence tier.) citeturn17view2turn18view1  
- For workflow orchestration: never attempt to buffer artifact bytes inside Temporal to “get around” storage outages; it risks payload limit failures and non-recoverable workflow termination. citeturn18view1turn18view0

## Closing recommendation

To build a production-grade artifact lifecycle for sandboxed agents, treat **artifacts as first-class durable objects** (IDs + metadata + retention + ACL + download surface), and treat sandboxes as compute that is **safe to lose** because state lives either in a mounted persistent workspace (Daytona Volumes) or in the durable artifact store (R2). This approach aligns with documented patterns from workflow orchestrators (Temporal’s explicit payload limits and object-store offloading guidance), CI artifact systems (upload/download + retention), workspace platforms (ephemeral compute + preserved workspace path), and modern assistant UX patterns (artifact panes and download affordances). citeturn18view1turn18view3turn25view2turn22view1turn17view2turn24view2
