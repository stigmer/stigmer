# Research: Agent Artifact Input/Output Model for Agentic Platforms

## Research Objective

Design the artifact input/output model for an agentic AI platform where:
1. Users need to provide files/artifacts as input to agents (not just text messages)
2. Agents operate in sandboxed environments and create file-based outputs (directories, not just single files)
3. Users need to download/retrieve these outputs from the sandbox

## Context: Current Architecture

We have an agentic platform with this architecture:

### Agent Execution Flow
```
User → CLI/Web → gRPC API → Temporal Workflow → Python Agent Runner → LangGraph Agent
                                                        ↓
                                                   Sandbox (Daytona)
```

### Current Input Model (Limited)
```protobuf
message AgentExecutionSpec {
  string message = 1;           // Text-only input
  string session_id = 2;        // Session tracking
  map<string, ExecutionValue> runtime_env = 3;  // Environment variables
  // NO file/artifact input fields
}
```

### Current Output Model (Limited)
```protobuf
message AgentExecutionStatus {
  repeated AgentMessage messages = 1;  // Text responses
  repeated ToolCall tool_calls = 2;    // Tool results (string only)
  // NO file/artifact output fields
}
```

### Sandbox Environment
- Agent runs in isolated sandbox (Daytona in cloud, local filesystem in dev)
- Agent can read/write files within sandbox via tools
- Files persist within a session
- **No API to download files from sandbox to client**

## Specific Use Case: Skill Creation

A "skill" in our platform is a **directory** structure:
```
my-skill/
├── SKILL.md           # Main skill definition (required)
├── scripts/           # Optional executable scripts
│   ├── validate.py
│   └── generate.sh
├── references/        # Optional reference documents
│   └── api-spec.yaml
└── assets/            # Optional assets
    └── template.json
```

### User Journey for Creating a Skill

1. **User wants to create a skill** for validating Kubernetes manifests
2. **User has reference materials**:
   - Kubernetes API spec document
   - Example manifests (valid and invalid)
   - Existing validation scripts to learn from
3. **User invokes skill-creator-agent**:
   - Needs to provide reference materials as INPUT
   - Agent analyzes materials and creates skill directory in sandbox
4. **Agent creates skill in sandbox**:
   - Creates directory structure with SKILL.md and scripts
   - Files exist in sandbox filesystem
5. **User wants to download the skill**:
   - How does user get the directory OUT of the sandbox?
   - Push directly to registry? Download to local? Both?

## Research Questions

### Q1: Input Model for Artifacts

How do modern agentic platforms and AI assistants handle file/artifact inputs?

**Specific questions:**
- How does ChatGPT handle file uploads (PDFs, code, images)?
- How does Claude handle file attachments in conversations?
- How does GitHub Copilot Workspace handle multi-file context?
- How do orchestration platforms (Temporal, Prefect) pass artifacts between activities?
- What are the patterns for file input in gRPC APIs? (streaming, chunked upload, reference URLs)

**Design considerations:**
- Should files be uploaded directly in the API call, or uploaded separately and referenced?
- How to handle large files (multi-MB)?
- How to handle multiple files/directories?
- Streaming vs. complete upload?

### Q2: Output Model for Artifacts

How do agentic platforms deliver file/artifact outputs?

**Specific questions:**
- How does Cursor Agent return code changes? (edits vs. new files)
- How does Replit Agent handle file creation/modification?
- How does Devin return deliverables?
- How do build systems (Bazel, Gradle) expose artifacts?
- How do CI/CD platforms (GitHub Actions, GitLab) handle artifact downloads?

**Design considerations:**
- Should files be embedded in response, or available for download?
- How to represent directory structures in responses?
- How to handle large outputs?
- Incremental streaming of files as they're created?

### Q3: Sandbox Artifact Retrieval

How do sandboxed execution environments expose artifacts to clients?

**Specific questions:**
- How does Daytona SDK handle file downloads?
- How does Docker handle `docker cp` for container files?
- How do cloud functions (Lambda, Cloud Functions) return file outputs?
- How do notebook environments (Jupyter, Colab) handle file downloads?
- How do remote development environments (GitHub Codespaces, Gitpod) sync files?

**Design considerations:**
- Pull (client requests specific files) vs. Push (agent publishes artifacts)?
- Streaming vs. batch download?
- How to handle directory trees?
- Compression (ZIP) vs. individual files?

### Q4: Conversation-Embedded vs. External Downloads

Should artifact downloads be part of the conversation or external?

**Patterns to investigate:**
- ChatGPT's file generation (code interpreter outputs)
- Claude's artifact panel
- Notion AI's inline file generation
- IDE agents that write directly to filesystem

**Considerations:**
- User experience: inline download buttons vs. separate artifact viewer?
- Mobile vs. desktop differences?
- CLI vs. Web UI differences?

### Q5: Workflow Integration

How should artifact I/O integrate with our Temporal workflow system?

**Questions:**
- Should artifact upload/download be a separate activity?
- How do Temporal workflows pass large artifacts between activities?
- Should artifacts be stored in workflow history or external storage?

## Known Information

### What We Have
- Skill push already works: `stigmer push skill ./my-skill/` packages directory to ZIP and uploads
- Artifact storage exists: R2/S3 for storing ZIPs
- Sandbox file access: Agent can read/write files in sandbox via tools
- Session persistence: Files persist across executions in a session

### What We Don't Have
- File input in agent execution API
- File output in agent execution response
- Download API for sandbox files
- Directory representation in responses
