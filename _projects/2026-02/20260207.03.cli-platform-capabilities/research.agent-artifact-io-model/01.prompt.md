# Research: Agent Artifact Input/Output Model for Agentic Platforms

## TL;DR - The Core Problems

We're building an agentic platform where agents run in sandboxes and create files (like skill directories). We have THREE critical gaps:

| Gap | Problem | Impact |
|-----|---------|--------|
| **No File Input** | Users can only send text messages to agents | Can't provide reference materials for skill creation |
| **No File Output** | Agent responses are text-only | Can't deliver created skills to users |
| **Ephemeral Sandbox** | Files lost when sandbox dies | User's work can vanish without warning |

**The fundamental question**: How do we build a production-grade artifact lifecycle for an agentic platform with sandboxed execution?

## Research Objective

Design the artifact input/output model for an agentic AI platform where:
1. Users need to provide files/artifacts as input to agents (not just text messages)
2. Agents operate in sandboxed environments and create file-based outputs (directories, not just single files)
3. Users need to download/retrieve these outputs from the sandbox
4. **User-created artifacts must survive sandbox failures and session boundaries**

## Context: Current Architecture

We have an agentic platform with this architecture:

### Agent Execution Flow
```
User → CLI/Web → gRPC API → Temporal Workflow → Python Agent Runner → LangGraph Agent
                                                        ↓
                                                   Sandbox (Daytona)
```

### Current Input Model (Limited)
```protobuf
message AgentExecutionSpec {
  string message = 1;           // Text-only input
  string session_id = 2;        // Session tracking
  map<string, ExecutionValue> runtime_env = 3;  // Environment variables
  // NO file/artifact input fields
}
```

### Current Output Model (Limited)
```protobuf
message AgentExecutionStatus {
  repeated AgentMessage messages = 1;  // Text responses
  repeated ToolCall tool_calls = 2;    // Tool results (string only)
  // NO file/artifact output fields
}
```

### Sandbox Environment (Daytona)

**Current Implementation Details:**

```
Session → Sandbox (1:1 relationship)
   ↓
sandbox_id stored in session.spec.sandbox_id
   ↓
Sandbox reused across executions in same session
```

**Lifecycle:**
1. **Creation**: `daytona.create()` or `daytona.create(snapshot=snapshot_id)`
2. **Reuse**: If `session_id` exists, try to get existing sandbox via `daytona.get(sandbox_id)`
3. **Health check**: `sandbox.process.exec("echo alive")` before reuse
4. **Deletion**: `sandbox.delete()` via cleanup activity (best-effort)

**File Operations:**
- Write: `sandbox.fs.upload_files(file_uploads)` 
- Execute: `sandbox.process.exec(command)`
- Read: No explicit download API found

**Critical Limitation: Files are EPHEMERAL**
- Files exist ONLY within sandbox filesystem
- No external storage attachment
- No volume mounts
- When sandbox is deleted → ALL FILES LOST
- Skills are re-injected on every execution (not persisted)

**Failure Scenarios:**
| Scenario | Current Behavior | Data Loss? |
|----------|-----------------|------------|
| Sandbox deleted externally | New sandbox created | YES - all user files lost |
| Sandbox unresponsive | New sandbox created | YES - all user files lost |
| Session timeout | Sandbox may be cleaned up | YES - all user files lost |
| User returns to old session | New sandbox, old files gone | YES |

**No API to download files from sandbox to client**

## Specific Use Case: Skill Creation

A "skill" in our platform is a **directory** structure:
```
my-skill/
├── SKILL.md           # Main skill definition (required)
├── scripts/           # Optional executable scripts
│   ├── validate.py
│   └── generate.sh
├── references/        # Optional reference documents
│   └── api-spec.yaml
└── assets/            # Optional assets
    └── template.json
```

### User Journey for Creating a Skill

1. **User wants to create a skill** for validating Kubernetes manifests
2. **User has reference materials**:
   - Kubernetes API spec document
   - Example manifests (valid and invalid)
   - Existing validation scripts to learn from
3. **User invokes skill-creator-agent**:
   - Needs to provide reference materials as INPUT
   - Agent analyzes materials and creates skill directory in sandbox
4. **Agent creates skill in sandbox**:
   - Creates directory structure with SKILL.md and scripts
   - Files exist in sandbox filesystem
5. **User wants to download the skill**:
   - How does user get the directory OUT of the sandbox?
   - Push directly to registry? Download to local? Both?

### Q6: Sandbox Filesystem Management (Critical)

Our sandboxes are ephemeral - files are lost when sandbox dies. How do other platforms handle this?

**Current Pain Points:**
1. User creates skill in sandbox → sandbox deleted → skill LOST forever
2. User returns to old session → new sandbox created → old files GONE
3. No persistence layer for user-created artifacts
4. Skills are re-injected on every execution (expensive, redundant)

**Specific questions:**

**Persistence Models:**
- How does Daytona support persistent volumes or storage mounts?
- How do GitHub Codespaces persist workspaces across sessions?
- How does Gitpod handle workspace persistence?
- How does Replit persist project files?
- How do Jupyter Hub / Colab handle notebook/file persistence?

**Storage Attachment Patterns:**
- Can we attach an S3/R2 bucket to sandbox as mounted volume?
- Can we use Daytona's workspace persistence features?
- Should we have a separate "project workspace" that survives sandbox lifecycle?
- FUSE mounts? Network filesystems?

**Sync vs. Mount:**
- Mount: Real-time access to external storage (like NFS, EFS)
- Sync: Copy files to/from external storage at checkpoints
- Which is better for our use case?

**Snapshot-Based Persistence:**
- Can we snapshot sandbox state before deletion?
- Restore from snapshot when user returns?
- How do Daytona snapshots work?

**Design considerations:**
- What's the "unit of persistence"? Per-session? Per-user? Per-project?
- How do we handle the case where sandbox dies mid-execution?
- Should important artifacts be automatically synced to durable storage?
- What's the cost/performance tradeoff of persistent storage?

### Q7: End-to-End Artifact Lifecycle

Design the complete lifecycle for user artifacts in agent execution.

**Artifact Lifecycle Stages:**
```
1. INPUT: User provides files to agent
   ↓
2. UPLOAD: Files uploaded to... where?
   ↓
3. INJECT: Files made available to sandbox
   ↓
4. PROCESS: Agent reads/writes files in sandbox
   ↓
5. PERSIST: Important outputs saved to... where?
   ↓
6. OUTPUT: User can access/download results
   ↓
7. CLEANUP: Sandbox deleted, but artifacts preserved
```

**Questions for each stage:**

**Stage 1-2 (Input/Upload):**
- Where do input files go? Directly to sandbox? To intermediate storage?
- What if sandbox doesn't exist yet when user uploads?
- File size limits? Streaming for large files?

**Stage 3 (Inject):**
- When are files copied into sandbox?
- What if sandbox is recreated mid-session?
- How to handle files the agent hasn't seen yet?

**Stage 4 (Process):**
- How does agent signal "this file is important, persist it"?
- Real-time sync vs. explicit save?
- Directory watching for automatic persistence?

**Stage 5 (Persist):**
- What storage backend? S3/R2? Database?
- How to track what was persisted? Manifest?
- Versioning? Can user revert to previous versions?

**Stage 6 (Output):**
- Download API? Push to registry? Both?
- How does user discover what artifacts exist?
- Preview vs. full download?

**Stage 7 (Cleanup):**
- What survives sandbox deletion?
- How long do artifacts persist?
- User quota/storage limits?

## Known Information

### What We Have
- Skill push already works: `stigmer push skill ./my-skill/` packages directory to ZIP and uploads
- Artifact storage exists: R2/S3 for storing ZIPs (used for skill artifacts)
- Sandbox file operations: `sandbox.fs.upload_files()` and `sandbox.process.exec()`
- Session-sandbox relationship: 1:1 mapping stored in `session.spec.sandbox_id`
- Sandbox reuse: Same sandbox reused across executions in same session
- Graceful degradation: New sandbox created if old one dies

### What We Don't Have
- File input in agent execution API
- File output in agent execution response
- Download API for sandbox files (Daytona SDK has upload but not download?)
- Directory representation in responses
- Persistent storage for user-created artifacts
- Storage bucket attachment to sandbox
- Artifact lifecycle management
- Multi-client artifact access

### Critical Architecture Gap
**User-created files in sandbox are completely ephemeral.** If sandbox dies (timeout, crash, external deletion), all work is lost. This is unacceptable for a production platform where users invest time creating skills, scripts, and other artifacts.
