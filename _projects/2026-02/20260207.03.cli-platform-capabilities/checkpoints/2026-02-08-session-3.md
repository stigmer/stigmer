## Key Decisions Made

### Pre-built Artifacts (User-Initiated Design Challenge)

**Challenge**: User questioned why we were manually creating ZIPs and proto structs when SDKs exist.

**Investigation**: Analyzed SDK functions (`skill.FromDir()`, `agent.New()`) and found they:
- Require filesystem paths (not suitable for embedded content)
- Involve synthesis step that writes `.pb` files to disk
- Are designed for CLI workflows, not server-side bootstrap

**Resolution**: Adopted build-time pre-packaging approach:
1. `vendor_skill.sh` creates ZIP artifacts at vendor time
2. Agents stored as human-readable YAML, parsed at runtime
3. Bootstrap directly calls existing gRPC APIs (Push, Apply)

This aligns with research report recommendation: "embed final serialized resources"

### Content-Addressed Idempotency

Bootstrap uses content digests for change detection:
- Skills: `artifact_digest` (SHA256 of ZIP)
- Agents: Content hash of spec fields

Skips already-applied resources, enabling safe restarts.

### Graceful Degradation

Bootstrap failures don't prevent server startup:
- Logs warnings and sets status to "failed"
- Server continues in degraded mode
- Manual re-bootstrap possible via clearing state

## Learnings

1. **SDK functions aren't universal** - They're designed for specific workflows (CLI) and may not fit server-side patterns.

2. **Research reports are valuable** - The "embed final serialized resources" recommendation directly informed the solution.

3. **Existing patterns guide design** - CLI's YAML parsing pattern (`yaml.Unmarshal` → `protojson.Unmarshal` → `protovalidate.Validate`) was reused for server-side agent loading.

4. **Content digests enable idempotency** - Using artifact/content hashes avoids re-applying unchanged resources.
