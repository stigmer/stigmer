# Deep Research Report (ChatGPT)

## 1. Executive Summary

**Recommendation:** Build Stigmer’s self-bootstrapping system as a **hybrid, versioned “capability supply chain”**:

* **Adopt the Agent Skills model as a runtime mechanism**, not just a documentation format: **load only skill metadata up-front** and **progressively load** the full `SKILL.md` (and any bundled resources/scripts) only when needed. This matches how Claude Skills and Codex Skills are designed to work. ([Claude][1])
* **Treat “skill creation” and “agent drafting” as controlled build pipelines** (draft → validate → evaluate → review → publish), **not** as automatic self-modification. OpenAI explicitly frames skill iteration as something you should evaluate systematically (like prompts) and capture traces/artifacts for regression detection. ([OpenAI Developers][2])
* **Use a hybrid distribution model**:

  * Ship an **embedded seed pack** of core system agents/skills (offline bootstrap),
  * Then **sync / override from your DB registry when available** (online evolution).
    This mirrors real-world patterns: OpenAI has “system” skills bundled and also supports installing additional skills; they even note syncing system skills from a public repo in their changelog. ([GitHub][3])
* **Implement explicit trust/permission boundaries**:

  * Default executions to **read-only / least privilege**,
  * Require user approval for risky tools or expanded sandbox/network access,
  * Keep AI-generated skills in a **non-active “Draft/Quarantined” state** until reviewed.
    This aligns with how Copilot CLI and Codex handle trusted directories and tool approvals. ([GitHub Docs][4])

If you do the above, you get a system that is:

* **Self-bootstrapping** (agents can draft skills/agents/workflows),
* **Self-improving** (through measurable iteration + versioning),
* **Maintainable** (clear separation of control plane vs runtime plane),
* **Safe** (gated publishing + sandbox/approval model),
* **Portable** (compatible with the emerging open “Agent Skills” conventions). ([OpenAI Developers][5])

## 2. Architecture Recommendation

### 2.1 Two-plane design: Control plane vs Runtime plane

**Control plane (your DB-backed registry + CLI/API):**

* CRUD + versioning for:

  * `Agent` (YAML)
  * `Skill` (SKILL.md + file bundle)
  * `Workflow` (YAML)
  * `MCPServer` (YAML)
* Publishing workflow (Draft → Published → Deprecated)
* Provenance + audit trail

**Runtime plane (execution engine):**

* Runs an **Agent invocation** with:

  * Model config
  * Toolset (MCP + built-ins)
  * Available skill metadata (progressive disclosure)
  * Sandbox / permissions profile
  * Event stream + trace persistence

This matches how production tools separate “configuration artifacts” from “execution traces” (Codex `codex exec` emits a machine-readable event stream and can be resumed later). ([OpenAI Developers][6])

---

### 2.2 Store skills as first-class, versioned packages (not just “prompt blobs”)

Industry implementations treat a skill as a **directory**:

* `SKILL.md` (YAML frontmatter + markdown instructions)
* Optional `scripts/`, `references/`, `assets/`
* Optional extra metadata file (Codex mentions `agents/openai.yaml` for dependencies/appearance) ([OpenAI Developers][7])

**Key design choice for Stigmer:** replicate the “directory skill” concept in your DB as a **package**.

A strong DB representation is:

* `skills` (logical identity)

  * `id`, `slug`, `owner_scope` (`SYSTEM|ORG|PROJECT|USER`), `created_at`, `status`
* `skill_versions` (immutable)

  * `skill_id`, `version`, `name`, `description`, `license`, `content_hash`, `created_by_execution_id`, `created_by_agent_version_id`, `created_at`
* `skill_files` (manifest)

  * `skill_version_id`, `path`, `blob_id`, `sha256`, `size`, `mime`
* `blobs` (content-addressed storage)

  * `sha256`, `bytes`, optionally external object-store pointer

This gives you:

* **Reproducible executions** (pin exact skill versions),
* **Safe rollbacks**,
* **Deduped storage**,
* **Provenance** (“this version was generated by execution X”).

---

### 2.3 Progressive disclosure: model it explicitly in your runtime

Both Anthropic and OpenAI describe **progressive disclosure** as foundational:

* **Level 1: metadata** (`name`, `description`) is always loaded and used for discovery/triggering. ([Claude][1])
* **Level 2: instructions** (body of `SKILL.md`) are loaded only when the agent decides to use the skill. ([Claude][1])
* **Level 3: resources/scripts** are accessed “as needed”; scripts can be executed without injecting their source into the LLM context (token-efficient + deterministic). ([Claude][1])

**Stigmer runtime implication:** don’t inject full skills into prompts at invocation start. Instead, implement:

* **SkillIndex injection:** a compact list of `{name, description, skill_id/version, paths}` in the system prompt.
* **Tools for skill access:**

  * `skills.read(skill_id, path="SKILL.md")`
  * `skills.read(skill_id, path="references/...")`
  * `skills.run_script(skill_id, path="scripts/validate.py", args=...)` (sandboxed)

This directly mirrors Claude’s documented behavior (“read SKILL.md via bash”; run scripts via bash; only output consumes tokens). ([Claude][1])

---

### 2.4 Agents “use” skills via three coupling modes

You should support all three, because different products do:

1. **Explicit invocation** (user or system references a skill by name)
   Codex explicitly supports this (`$skill-name` / `/skills`). ([OpenAI Developers][5])

2. **Implicit invocation** (agent chooses based on `description`)
   Codex and Copilot both describe this behavior. ([OpenAI Developers][5])

3. **Policy-driven allowlist** (agent config pins a set of skills)
   This is your enterprise safety lever: “this agent may only use these skills (and versions)”.

**Design recommendation:**

* Make **allowlist** the default for “platform/system agents” (skill-creator-agent, drafter agents).
* Allow broader discovery for “user agents” if desired, but still bounded by scope + permissions.

## 3. Bootstrapping Workflow

This is a pragmatic “no technical debt” bootstrapping flow that matches your phases but adds production-grade gates.

### Phase 0: Build the runtime primitives first

Before any self-bootstrapping, implement:

* Skill package loading + metadata indexing (progressive disclosure)
* Tool permission / sandbox profile system
* Execution tracing + artifact storage (streaming events)
* YAML/schema validation tooling hooks (deterministic)

This aligns with how Codex emphasizes reproducible runs with captured traces/artifacts and permission presets in automation. ([OpenAI Developers][6])

---

### Phase 1: Seed a minimal “System Pack” (embedded in the CLI)

Embed a **small, stable** set of resources (Go `embed`) so you can run even when the Stigmer backend DB is unreachable:

* **Skills**

  * `skill-creator` (meta-skill)
  * `yaml-validator` (deterministic schema checks)
  * `resource-packager` (turn skill folder ↔ DB package)
* **Agents**

  * `skill-creator-agent` (allowlisted: `skill-creator`, `yaml-validator`)
  * `bootstrap-admin-agent` (for init/sync ops; extremely restricted)

This follows the “bundled system skills” pattern used elsewhere. ([OpenAI Developers][5])

---

### Phase 2: “Import to DB” bootstrap (idempotent)

Implement a command like:

* `stigmer system sync` (or `stigmer init`)

  * Reads embedded pack
  * Upserts into DB as **SYSTEM scope**
  * Records “installed system pack version”
  * Does **not** overwrite DB-modified versions unless `--force` (critical for evolvability)

OpenAI’s changelog explicitly mentions “sync system skills from public repo,” which is essentially the same idea: a canonical baseline that can be synced forward. ([OpenAI Developers][8])

---

### Phase 3: Use `skill-creator-agent` to create “Drafter Skills”

For each resource type you want to draft (agent/workflow/skill/mcpserver):

* Invoke `skill-creator-agent`
* Provide artifacts:

  * JSON schema / protobuf schema
  * examples
  * lint rules (naming, required keys)
* Output: a new Skill package (e.g., `agent-drafter`)

**Important gate:** the output is saved as `status=DRAFT` and is not globally available until validated and promoted.

---

### Phase 4: Create Drafter Agents (allowlisted + pinned versions)

For each drafter skill:

* Create an agent that has **only**:

  * That drafter skill
  * Validation tools (schema validator)
  * Minimal file tools (if needed)
* Pin **exact skill versions** for reproducibility.

---

### Phase 5: Wire CLI “draft” commands to drafter agents

`stigmer draft agent` becomes:

1. Create an execution session
2. Invoke `agent-drafter-agent`
3. Stream Q&A to user
4. Run deterministic validators
5. Return a final YAML
6. Optionally auto-save as **DRAFT agent resource**

For CI/non-interactive support, mimic `codex exec` ergonomics:

* streaming progress vs final output separation
* optional JSON event stream
* optional schema-constrained output ([OpenAI Developers][6])

## 4. Agent + Skill Coupling Patterns

### 4.1 Progressive disclosure is the “industry default”

* **Codex:** starts with skill metadata and loads full `SKILL.md` only when needed; the body stays on disk until invoked. ([OpenAI Developers][5])
* **Claude:** explicitly documents 3 loading levels and emphasizes that scripts can run without injecting code into context. ([Claude][1])
* **Copilot:** decides when to use skills based on prompt + `description`, and injects `SKILL.md` into context when used. ([GitHub Docs][9])

**Pattern to copy into Stigmer:**

* Always inject a compact metadata list.
* Never inject full skill bodies unless selected.
* Provide “read skill file” and “run script” as tools.

---

### 4.2 Scopes and precedence: don’t reinvent—adopt known hierarchies

Multiple ecosystems use layered scopes:

* **Codex skills:** repo/user/admin/system scopes. ([OpenAI Developers][5])
* **Copilot custom agents:** user/repo/org/enterprise with precedence rules (system overrides repo, repo overrides org). ([GitHub Docs][4])
* **Copilot skills:** project skills and personal skills directories. ([GitHub Docs][9])

**Stigmer recommendation:** implement a precedence chain like:

`Invocation overrides` → `Project` → `Org/Tenant` → `System pack (embedded + DB)`
…and make it explicit in both your runtime resolver and your CLI UX (`stigmer resolve agent foo --explain`).

---

### 4.3 Skill metadata quality is a first-order reliability concern

OpenAI calls out that `description` is agent-facing metadata used for implicit invocation; vague descriptions cause over-triggering and unreliability. ([OpenAI Developers][7])
Anthropic similarly emphasizes that name/description drive whether a skill triggers. ([Anthropic][10])

**Recommendation:** treat skill metadata as a separately validated contract:

* Lint for “when to use / when not to use” phrasing
* Enforce length/format constraints (Codex documents max lengths and single-line constraints) ([OpenAI Developers][7])
* Track trigger quality (under/over-triggering) in telemetry

## 5. Skill Creation Lifecycle

A robust lifecycle for agent-created skills:

### 5.1 States

* `DRAFT` (untrusted, not auto-loadable)
* `REVIEW_PENDING` (ready for approval)
* `PUBLISHED` (loadable by other agents)
* `DEPRECATED` (available but discouraged)
* `REVOKED` (blocked)

### 5.2 Automated checks (pre-publish)

1. **Format validation**

   * Required frontmatter keys (at least `name`, `description`)
   * Enforce constraints for compatibility (Codex documents length limits and that extra keys are ignored). ([OpenAI Developers][7])
2. **Deterministic output validation**

   * If the skill is meant to produce YAML/JSON, validate with schema validators.
3. **Security scan**

   * Disallow network access unless explicitly required
   * Block dangerous commands or scripts by policy tier

### 5.3 Evals + regression testing (the “self-improvement” loop)

OpenAI’s guidance: treat skills like prompts; the reliable way to improve them is to run evals that capture a prompt → trace/artifacts → checks → score over time. ([OpenAI Developers][2])

**Stigmer implementation idea:**

* A `SkillEvalSuite` resource type:

  * test prompts
  * expected behaviors (tool calls, file outputs)
  * rubric checks (LLM judge) + deterministic checks
* Tie every published version to eval results.

### 5.4 Promotion and distribution

* Promote only after:

  * must-pass checks
  * at least one evaluation run
  * (optionally) human review
* Distribute via:

  * DB registry
  * optional export to filesystem/git for portability (aligns with skills-as-folders across ecosystems) ([Claude][1])

## 6. Embedded vs Database Analysis

### Scenario A: Embedded skills only

**Pros**

* Works without DB/backend connectivity
* Easy reproducibility per CLI release

**Cons**

* Painful updates
* Slow iteration (every improvement = release)
* Doesn’t match how skills evolve in real products

### Scenario B: Database-driven only

**Pros**

* Fast evolution, centralized governance
* Great for multi-tenant and enterprise rollout

**Cons**

* Cold start depends on connectivity
* Harder to guarantee reproducibility unless you pin versions carefully

### Scenario C: Hybrid (recommended)

**Pros**

* Offline bootstrap + online evolution
* Natural fit to the “system scope + user/repo scope” patterns in Codex/Copilot
* Lets you support a “system pack sync” model

**Cons**

* Requires resolver logic + conflict strategy
* Requires provenance and signing to avoid supply-chain issues

**Why hybrid is the industry direction:**

* Codex has system skills + multiple other skill locations (repo/user/admin/system). ([OpenAI Developers][5])
* The OpenAI skills catalog describes `.system` skills as auto-installed and mentions installing additional skills with a skill installer. ([GitHub][3])
* Codex changelog explicitly references syncing system skills and adding APIs/events to list/download remote skills—clear evidence of a baseline + updates distribution approach. ([OpenAI Developers][8])
* Copilot CLI similarly comes with an MCP server preconfigured and allows adding more servers—baseline + extend. ([GitHub Docs][4])

**Concrete Stigmer policy recommendation:**

* CLI embedded pack is **authoritative only until** DB is reachable.
* When DB is reachable:

  * Prefer **DB-published SYSTEM** over embedded if:

    * signed by your org key (or explicitly trusted)
    * passes compatibility checks
* Provide `stigmer system sync --dry-run` to show diffs.

## 7. Licensing Guidance

Not legal advice—treat this as engineering guidance to bring to counsel.

### 7.1 Anthropic skills licensing (what you must handle)

Anthropic’s repository states that skills are generally Apache 2.0, but it also notes **exceptions**: certain document-oriented skills are “source-available (not open source).” ([GitHub][11])

**Implication for Stigmer:**

* Do not assume “the repo = Apache 2.0 blanket.”
* Track license **per imported skill/version** in your DB and surface it in CLI (`stigmer show skill --license`).
* If you embed anything in your CLI binary, embed only content you’re confident you can redistribute under its license.

### 7.2 OpenAI skills licensing

OpenAI’s skills catalog states that the license is found **per individual skill directory** (in `LICENSE.txt`). ([GitHub][3])

**Implication:**

* Same approach: store license metadata per skill/version, don’t assume uniform licensing.

### 7.3 Are AI-generated skills “derivative works” of skill-creator?

Practically:

* If your generated skill **copies text** (substantial portions) from the upstream skill-creator instructions, that output may be a derivative work of that text and must comply with the upstream license (e.g., Apache 2.0 attribution/notice requirements).
* If the generated skill is **original** and only follows the *ideas/structure* (not copying expressive text), it’s much less likely to be considered derivative.

**Engineering-safe policy:**

* Store provenance: `generated_by_skill_id`, `generated_by_skill_version`, `generated_by_model`, `generation_prompt_hash`
* Encourage generation to be “structure-inspired, text-original”
* Optionally include an attribution note in metadata (not required in all cases, but often a good compliance posture)

Also note: GitHub’s Agent Skills docs explicitly allow a `license` field in frontmatter. That’s a useful convention to adopt inside Stigmer for clarity, even if you also store license in DB fields. ([GitHub Docs][9])

## 8. Security Considerations

### 8.1 Treat “skill creation” as a supply-chain event

Anthropic explicitly warns that malicious skills can introduce vulnerabilities and recommends installing only from trusted sources and auditing bundled files/scripts and any instructions that connect to untrusted external sources. ([Anthropic][10])

**Stigmer controls to add:**

* Trust tiers: `SYSTEM_SIGNED`, `ORG_SIGNED`, `USER_LOCAL`, `UNTRUSTED_IMPORTED`
* Mandatory review for any skill that:

  * ships scripts
  * requests network
  * adds MCP servers/tools
* Static scanning for disallowed patterns + dependency allowlists

### 8.2 Tool permissions and sandboxing

Real agent CLIs gate dangerous actions:

* Copilot CLI asks users to trust the folder and approves tools that can modify/execute files; it warns about approving broad commands like `rm`. ([GitHub Docs][4])
* Codex runs read-only by default in automation and recommends least permissions; it distinguishes safer vs “danger-full-access” execution. ([OpenAI Developers][6])
* Codex also keeps network access off by default in its sandbox and discusses controlling web search behavior, noting that even cached web results should be treated as untrusted. ([OpenAI Developers][12])

**Stigmer pattern to implement:**

* Permission profiles on every invocation:

  * `READ_ONLY`
  * `WORKSPACE_WRITE`
  * `NET_ALLOWED`
  * `DANGER_FULL_ACCESS` (rare; gated)
* Per-tool / per-MCP-server allowlists
* Interactive approval hooks in CLI (with “approve for this session” options similar to Copilot) ([GitHub Docs][4])

### 8.3 Event-streamed auditability (non-negotiable for self-bootstrapping)

Codex documents a JSONL event stream for automation (`thread.started`, `turn.*`, tool calls, file changes, etc.). ([OpenAI Developers][6])

**Stigmer should store:**

* Full event trace (append-only)
* Tool call inputs/outputs
* Artifacts produced (files, YAML, skill packages)
* The resolved versions of agents/skills/tools used

This makes “agent-created capability” reviewable and reproducible.

## 9. Technical Debt Risks

### Risk 1: Treating skills as “prompts you paste”

If you load all skill bodies into the prompt up front, you’ll lose the main scalability benefit and create context bloat. Progressive disclosure is a core design principle in both Claude and Codex skills. ([Claude][1])

**Mitigation:** implement metadata index + on-demand `skills.read()` tooling from day one.

---

### Risk 2: No provenance → no reproducibility → no safe self-improvement

Without immutable versions + traces, you cannot answer “what changed?” or roll back.

**Mitigation:** content-addressed storage, immutable versions, and execution traces (JSONL-like event log).

---

### Risk 3: Auto-activating AI-generated skills

This becomes a prompt-injection/supply-chain vector.

**Mitigation:** quarantine states + human/CI promotion gates + signatures.

---

### Risk 4: Mixing system and user capability scopes

You’ll either over-constrain users or accidentally grant system powers to untrusted content.

**Mitigation:** explicit scopes + precedence + permission tiers (system pack separate from user pack). Scope hierarchies are common across tools (Codex skills scopes; Copilot agent precedence). ([OpenAI Developers][5])

---

### Risk 5: No evaluation harness → silent regressions

OpenAI explicitly frames evals as the way to improve skills over time rather than relying on “vibes.” ([OpenAI Developers][2])

**Mitigation:** bake eval suites into skill versioning and require at least baseline eval success before publish.
