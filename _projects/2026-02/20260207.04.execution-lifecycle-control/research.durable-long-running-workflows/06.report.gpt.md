# 1) Internal “Durable Execution” Checklist

## Definition

A Stigmer workflow execution is **Durable (Long‑Running)** if it can run for **weeks/months** and reliably make progress despite worker restarts, deployments, duplicate external events, and long waits—**without being terminated by Temporal history limits**—and with enough visibility for operators to understand and intervene.

This checklist is written as **pass/fail**. If you want to claim “durable long-running workflows,” you should require **all MUST items**.

---

## MUST: Core durability (required for an honest “weeks/months” claim)

### A. History safety (won’t die at month-scale)

* [ ] **Automatic Continue‑As‑New** is implemented and enabled for long-running workflows to prevent history overflow. Continue‑As‑New creates a new run with fresh history while keeping the same Workflow ID chain. ([Temporal Docs][1])
* [ ] Continue‑As‑New triggers **before** the warn threshold (10,240 events / 10MB) with headroom (e.g., trigger at ~7–8k events or earlier), and never approaches the hard cap (51,200 events / 50MB). ([Temporal Docs][2])
* [ ] No workflow design uses **unbounded polling loops** (e.g., “check every minute for months”) unless the polling is chunked by Continue‑As‑New and explicitly bounded.

**Acceptance test:** run a synthetic workflow that generates high event volume (fan-out + many steps) and verify it continues-as-new repeatedly and never hits warn/error limits.

---

### B. Durable waiting (sleeping for months works)

* [ ] `wait` supports **long durations** (days/months) and not only `int32 seconds`. Temporal timers are persisted, reliable, and worker-resource-light even at huge scale. ([Temporal Docs][3])
* [ ] `wait_until` exists (or equivalent), and uses **workflow time** / deterministic time semantics (not system wall-clock calls inside workflow logic).
* [ ] Waiting does **not** require any active worker “holding a thread”; the workflow can be resumed after worker restarts.

**Acceptance test:** start workflow → wait for a timer → kill worker(s) → bring worker back → verify workflow resumes after timer fires.

---

### C. External events are safe (idempotent + correlatable)

* [ ] Every inbound event has:

  * **correlation key** (which workflow instance/entity does this belong to?)
  * **event id** (unique id for dedupe)
* [ ] Event delivery uses a safe pattern where duplicates won’t cause duplicate progress. Temporal guidance explicitly calls out using the Update ID or Signal-provided key as an idempotency key in message handlers. ([Temporal Docs][4])
* [ ] You have a **race-proof delivery** option for “workflow may not exist yet” (Signal-With-Start / Update-With-Start). ([Temporal Docs][5])
* [ ] You have guardrails for message-volume limits: workflows do not accumulate beyond Temporal’s per-run message constraints (e.g., signals/updates caps), or they use Continue‑As‑New to reset. ([Temporal Docs][6])

**Acceptance test:** send the same event 2–10 times (same eventId) and confirm the workflow processes it once.

---

### D. Side effects are replay-safe (determinism boundary is enforced)

* [ ] **No external I/O inside workflow code** (network, DB writes, random, system time). All side effects happen in Activities / connector workers.
* [ ] Every side-effecting Activity/connector action is **idempotent** using an idempotency key strategy (Temporal also recommends idempotency keys for Activities). ([Temporal Docs][7])
* [ ] Activity timeouts and retry policies are always set (no “infinite wait” without timeouts).

**Acceptance test:** force activity retries (simulate transient failures) and confirm no duplicate external side effects.

---

### E. Minimal operator visibility exists

* [ ] Every workflow execution writes standard **Search Attributes** (or equivalent visibility fields) such as:

  * `definitionVersion` / `definitionHash`
  * `phase` (current state)
  * `businessKey` (correlation)
  * `nextDueAt` (when it wakes up next)
* [ ] Operators can answer: “Where is it stuck?” without reading raw Temporal history logs.

*(Search Attributes themselves are a Temporal feature; the checklist here is “Stigmer consistently sets them.”)*

---

## SHOULD: Operational durability (recommended for MVP, required for “production-ready” positioning)

### F. Intervention controls

* [ ] A workflow can be **paused/resumed** safely (operator can stop progress without terminating).
* [ ] There is a supported, auditable path for “retry this step” / “skip with reason” using Updates (not manual DB edits).

### G. Payload & event growth hygiene

* [ ] Guardrails exist for large payloads (store blobs externally; keep workflow history small).
* [ ] Fan-out (`for_each` / `fork`) has **concurrency limits** and/or chunking boundaries.

### H. Upgrade safety (basic)

* [ ] Workflow definition is treated as **immutable per execution**; new versions apply to new executions by default.
* [ ] Migration (if supported) happens via **Continue‑As‑New at a checkpoint boundary** so it’s explicit and controlled.

---

## NICE-TO-HAVE: “Enterprise durable”

* [ ] Business calendar waits (weekends/holidays)
* [ ] First-class compensation/saga abstraction
* [ ] Worker versioning / deployment routing policies
* [ ] Full audit-grade state projection and reporting

---

## A simple internal grading rule

* **“Durable (Long‑Running)”** = all MUST items pass.
* **“Production Durable”** = MUST + SHOULD items pass.
* **“Enterprise Durable”** = MUST + SHOULD + selected NICE-TO-HAVE items.

# 2) Minimal Connector Contract Spec

This spec is intentionally **general-purpose** and designed to work with your existing `activity_call` approach (connectors implemented as **Temporal Activities**). The goal is: “any external system can be integrated” without Stigmer hardcoding Jira/ServiceNow/etc.

## Concepts

* **Connector**: a deployable unit (usually its own worker service) that registers one or more **Actions** as Temporal Activities.
* **Action**: a named operation (e.g., `ticket.create`, `crm.upsertContact`) with a stable schema and retry/idempotency semantics.
* **Connection**: stored auth/config (OAuth token, API key, base URL), referenced by ID—never embedded in workflow history.

---

## 2.1 Connector Manifest (minimal)

A connector ships a `connector.yaml` (or JSON) so Stigmer can discover capabilities.

```yaml
apiVersion: stigmer.dev/v1
kind: Connector
metadata:
  id: com.stigmer.connector.example
  name: Example Connector
  version: 0.1.0

runtime:
  # Connector runs as a Temporal Worker that registers Activities
  type: temporal-activity-worker
  taskQueue: connector.example

actions:
  - id: example.echo
    activityType: Example_Echo
    description: "Echo input (demo action)."

    # Required: schemas so workflows can validate inputs/outputs
    inputSchema:
      type: object
      required: [connectionId, idempotencyKey, message]
      properties:
        connectionId: { type: string }
        idempotencyKey: { type: string }
        message: { type: string }

    outputSchema:
      type: object
      required: [echoed]
      properties:
        echoed: { type: string }

    # Required: safe retry semantics
    timeouts:
      startToClose: 30s
      scheduleToClose: 2m

    retries:
      maxAttempts: 5
      backoff: exponential
      initialInterval: 2s
      maxInterval: 2m

    # Required: idempotency contract
    idempotency:
      strategy: caller-provided-key
      keyField: idempotencyKey

    # Optional but recommended: rate limit hints for operators
    rateLimitHints:
      maxRps: 10
```

### Notes / requirements

* **`activityType` is the Temporal Activity name** the connector worker registers.
* **`taskQueue` isolates connector workloads** and lets you scale or rate-limit connector workers independently.
* Schemas should be JSON Schema-ish (enough for validation + UI).

---

## 2.2 Invocation Envelope (what Stigmer sends to a connector action)

Even if you keep the input schema action-specific, you should standardize a thin envelope so connectors can implement consistent logging/metrics and multi-tenant separation.

**Recommended envelope (minimal):**

```json
{
  "connectionId": "string",
  "idempotencyKey": "string",

  "context": {
    "tenantId": "string",
    "workflowId": "string",
    "runId": "string",
    "executionKey": "string",
    "taskId": "string",
    "attempt": 1
  },

  "input": { }
}
```

### Required semantics

* **`idempotencyKey` must be stable across retries and Continue‑As‑New.**

  * DO NOT include Temporal `runId` in the key.
  * Good default: `executionKey + taskId` (where `executionKey` is stable for the whole chain).
* Connector actions must be safe under **at-least-once execution**; retries can happen. ([Temporal Docs][7])

---

## 2.3 Result Envelope (what the connector returns)

```json
{
  "ok": true,
  "output": {},
  "externalIds": {
    "primary": "string"
  },
  "meta": {
    "requestId": "string",
    "rateLimited": false
  }
}
```

On failure:

```json
{
  "ok": false,
  "error": {
    "code": "TEMPORARY | PERMANENT | AUTH | RATE_LIMITED | INVALID_INPUT | NOT_FOUND",
    "message": "string (safe to log)",
    "retryAfterSeconds": 120,
    "details": {}
  }
}
```

### Required semantics

* **Retry classification is explicit**:

  * `TEMPORARY` / `RATE_LIMITED` → retryable
  * `INVALID_INPUT` / `AUTH` / `PERMANENT` → not retryable (fail fast)
* For rate limits, return `retryAfterSeconds` when available.

## 2.4 Connection Model (minimal)

Stigmer stores connections (credentials + config) outside workflow history:

```json
{
  "connectionId": "jira-prod",
  "connectorId": "com.stigmer.connector.jira",
  "tenantId": "acme",
  "config": {
    "baseUrl": "https://...",
    "authType": "oauth2|apiKey|basic"
  },
  "secretsRef": "vault://path/or/k8s-secret"
}
```

**Contract requirement:** connectors receive only `connectionId` and must fetch secrets/config via the Stigmer connection service (or a standardized secret provider). This prevents secrets from landing in Temporal history.

## 2.5 How this maps to your current DSL (MVP-friendly)

Since you already have `activity_call`, you can invoke connectors like this (conceptually):

* `taskQueue = connector.<id>`
* `activityType = <manifest.actions[i].activityType>`
* `input = invocation envelope`

Example (pseudo-DSL):

```yaml
- name: create_ticket
  type: activity_call
  activity:
    taskQueue: connector.jira
    activityType: Jira_CreateIssue
    input:
      connectionId: jira-prod
      idempotencyKey: "${executionKey}/create_ticket"
      context:
        tenantId: "${tenantId}"
        workflowId: "${temporal.workflowId}"
        runId: "${temporal.runId}"
        executionKey: "${executionKey}"
        taskId: "create_ticket"
        attempt: "${temporal.attempt}"
      input:
        projectKey: "ENG"
        summary: "Onboard laptop"
```

This keeps Stigmer general-purpose: you’re not adding “Jira support,” you’re adding a **connector execution model**.

## Minimal “MVP-ready” connector requirements (summary)

A connector qualifies as “Stigmer-compatible” if:

1. Registers actions as **Temporal Activities** on its own task queue.
2. Accepts `connectionId` + `idempotencyKey`.
3. Implements clear retryability classification.
4. Never requires secrets in workflow inputs.
5. Logs/metrics include `(tenantId, workflowId, actionId)`.
