No—you can absolutely evolve. But there’s a trap: some things are “nice-to-have product breadth,” and some things are **foundational durability correctness**. If you postpone the foundations, you risk shipping an MVP that *looks* durable but fails under real long-running workloads.

## What’s foundational vs optional (for a truthful “durable long-running” MVP)

### A. Non-negotiables if you want to claim “durable for weeks/months”

These are the pieces that prevent “month-long workflows” from breaking:

1. **History growth control (Continue-As-New + checkpointing)**

* Temporal workflow histories have a hard cap: **51,200 events or 50MB**; warnings at **10,240 events or 10MB**. ([Temporal Docs][1])
* Continue-As-New is the standard mechanism to “checkpoint and reset history” while keeping the same Workflow ID chain. ([Temporal Docs][2])
  **If you don’t add this early**, you’ll eventually hit limits in any non-trivial months-long flow (especially with loops, fan-out, frequent signals).

2. **Long-duration waiting beyond int32 seconds**

* Temporal timers support sleeps “days, months, or even years,” and they’re persisted and don’t consume worker resources while waiting. ([Temporal Docs][3])
  So Stigmer’s `wait` needs to support:
* duration (not just seconds int32)
* “wait until timestamp”
  Even if you defer business calendars, you should at least support “until date/time” and long durations.

3. **Inbound event delivery: correlation + idempotency + (optionally) Signal-With-Start**

* Temporal supports signals/updates, but **idempotency** is on you: Temporal can dedupe Updates if you supply a stable Update ID / idempotency key. ([Temporal Docs][4])
* Temporal explicitly documents “Signal-With-Start” as a way to deliver an event and start the workflow if it’s not running yet (race-proof). ([Temporal Docs][5])
  Without a consistent inbound pattern, long-running flows get brittle (duplicates, missing events, ordering issues).

4. **Minimal visibility model (Search Attributes + “where am I?” state)**

* Search Attributes are the indexed metadata used for filtering workflow lists. ([Temporal Docs][6])
  Even if you don’t build a full UI dashboard on day one, you need *some* consistent fields (phase/state, definition version/hash, correlation keys, next due time) so operators can find and understand long-running cases.

These four are the “durability MVP core.” If you ship only one phase, ship this phase.

---

### B. Powerful, but you can defer (without breaking “durability”)

These are the “make it broadly useful in enterprise ops” items. They can come after you’ve proven durable execution:

5. **Business calendars (skip weekends/holidays)**
   Helpful, but not required to prove durability. Many teams start with “wait until timestamp” and push calendar logic into an activity/service.

6. **Full human task management (assignment, escalation, reassignment)**
   This is *generic*, not HR-specific. But it’s still a product layer that can be vNext. For MVP you can keep your approval gate and recommend “human tasks via external system + callback signal.”

7. **Prebuilt connectors (Jira/ServiceNow/Slack/etc.)**
   Not needed for MVP. What you want is a **connector framework** and 1–2 reference implementations.

8. **First-class Saga/compensation DSL**
   You can ship MVP with guidance (“model compensations explicitly via activities + try/catch”) and add a real compensation stack abstraction later.

9. **Worker versioning productization**
   Worker Versioning is how Temporal supports safe deployment changes without breaking running executions. ([Temporal Docs][7])
   But you can start with a simpler stance in MVP: “definition immutability per run + continue-as-new migrations.” Then add full worker versioning controls once you need zero-downtime upgrades at scale.

## How to talk about “connectors” in a general-purpose way

When I said “Jira/ServiceNow connectors,” the generic platform version is:

### 1) Outbound integrations: “Connector Actions” as Activities

You already have:

* `http_call`
* `grpc_call`
* `activity_call`

For general-purpose extensibility, make `activity_call` the official extension point:

* Stigmer defines a **Connector Action contract**:

  * action name (`jira.createIssue`, `servicenow.createIncident`, `smtp.sendMail`, etc.)
  * input/output JSON schema
  * retry/timeout defaults
  * idempotency key strategy (how to avoid duplicates)
  * auth/secrets mapping

* Implementations live as:

  * separate worker services (recommended for self-hosted)
  * or plugin packages loaded by a worker

This gives you “infinite integrations” without Stigmer owning them all.

### 2) Inbound integrations: a generic Event Gateway

Instead of building “HR callback support,” build:

* `POST /events` (webhook ingress)
* Normalize to `{source, eventType, eventId, correlationKey, payload}`
* Dedupe by `(source,eventId)`
* Deliver via Signal/Update (or Signal-With-Start)

That’s general-purpose and supports HR, payments, logistics, compliance, etc.

## A practical rule of thumb for what to build now

If the feature answers **“Will this break after 3 months?”**, build it early.

* History management → yes (hard limits) ([Temporal Docs][1])
* Long timers → yes (you literally need this to span months) ([Temporal Docs][3])
* Event correlation/dedupe → yes (real systems retry and duplicate) ([Temporal Docs][4])
* Everything else (connectors catalog, full human task suite, business calendars) → can evolve.
