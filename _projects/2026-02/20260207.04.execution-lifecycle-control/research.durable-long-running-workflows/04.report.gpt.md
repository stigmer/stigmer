Below is a **Temporal-first** (and Stigmer-compatible) deep research write‑up for what it takes to make **“durable execution” real for workflows that run weeks/months**—with concrete patterns, Temporal best practices, a Stigmer gap analysis, and a roadmap.

---

## What “durable execution” means for month-long workflows

In the context of workflow engines like Temporal/Cadence, “durable execution” is **not** just “the process doesn’t crash.” It means:

### Durable execution guarantees you want

1. **Progress is persisted**: If workers restart, pods get rescheduled, or deployments roll, the workflow **resumes from the last known step** without you rebuilding state machines in your DB.
2. **Waiting is durable and cheap**: A workflow can wait days/months on timers or external events without holding worker resources.
3. **Retries are safe**: Workflows and activities are executed under at-least-once delivery, so your system must be safe under retries (idempotency + dedupe).
4. **External side effects are controlled**: All nondeterministic work (network, DB writes, etc.) is isolated into Activities (or equivalent) with clear timeouts and retries.
5. **Full auditability**: You can reconstruct what happened (history) and expose operator-friendly visibility (search attributes / projections).
6. **Long-running evolution**: You can deploy new code or new workflow definitions without breaking in-flight runs (versioning).

Temporal explicitly supports “workflows that sleep for months/years” with **persisted timers** and **no worker resource consumption while waiting**. ([Temporal Docs][1])

However, **durability at month-scale is not automatic** unless you design for the known constraints—especially **event history limits** and **versioning**.

---

## The core Temporal constraint that breaks month-long workflows: Event History

Temporal’s Workflow Execution history is a durable log of what happened. That log is replayed to rebuild workflow state.

### Hard limits (and what happens when you hit them)

Temporal enforces a hard limit on Event History size:

* **51,200 events or 50 MB** per Workflow Execution history (hard cap)
* Warnings start after **10,240 events or 10 MB** ([Temporal Docs][2])

If you exceed the hard limit, **the Workflow Execution is terminated**. ([Temporal Docs][3])

There are also limits on message volume:

* Workflow is terminated if it contains **more than 10,000 Signals** or **more than 2,000 Updates** (per execution) ([Temporal Docs][3])

And limits on “incomplete operations” (mutable state pressure), like maximum number of incomplete Activities/Child Workflows/Signals/Cancellation requests (commonly **2,000** for each type by default). ([Temporal Docs][2])

### Why month-long workflows hit history limits in practice

Even “simple” task orchestration generates multiple events per step (schedule activity, start, complete, etc.). Fan-out patterns (`for_each`, `fork`) and polling loops are especially dangerous.

Temporal’s own guidance is effectively:

* **Design so each execution stays comfortably under ~10k events / 10MB**
* Use **Continue‑As‑New** to “checkpoint and roll history forward” ([Temporal Docs][4])

## Architecture patterns for truly durable long-running workflows

These are the patterns you’ll want Stigmer to standardize on, because they’re the difference between “runs for 2 hours” and “runs for 3 months reliably”.

### Pattern A: Execution Chain via Continue‑As‑New (the “history reset”)

**Goal:** Keep a logical workflow running for months while keeping each individual Temporal execution history small.

* Use Temporal **Continue‑As‑New** to:

  * finish the current run
  * start a new run with the **same Workflow ID** and a **fresh history**
  * pass forward only the minimal state needed (checkpoint) ([Temporal Docs][4])

Temporal SDKs expose a “should I continue-as-new?” indicator (e.g., `continueAsNewSuggested`). ([Temporal Docs][5])

**Stigmer implication:** your workflow runner/compiler needs a **first-class checkpoint boundary** concept (e.g., after each task, after each phase, or after N events).

---

### Pattern B: Entity Workflows (Actor-like, event-driven, “runs forever”)

Temporal itself calls out the **Entity Workflow** pattern for workflows that represent a long-lived “thing” (customer lifecycle, subscription, onboarding case file, etc.). ([Temporal][6])

**How it works:**

* One workflow per entity (e.g., `employeeId`)
* External events arrive as **Signals/Updates**
* Workflow maintains compact state, responds, sleeps, and continues-as-new periodically

This pattern is extremely relevant to onboarding/hiring pipelines: “employee onboarding case” is an entity.

---

### Pattern C: Phase/Child Workflow decomposition (limit blast radius)

Instead of one monolith workflow with 60+ steps over 3 months:

* Use a parent “orchestrator” workflow that:

  * starts child workflows for **Week 1**, **Week 2**, **Start Date**, **30/60/90-day check-ins**
  * waits on child completion / signals
* Each child has bounded history and bounded responsibility

This also makes retries, compensation, and human task modeling cleaner.

---

### Pattern D: Externalized Human Task Service (workflow is not the inbox)

Temporal doesn’t give you a full “human task inbox” product out of the box; Temporal gives you primitives (signals, updates, queries, timers). Temporal explicitly positions “Human in the Loop” as an event-driven use case with schedules/timers for prompting input. ([Temporal Docs][7])

The durable pattern in most Temporal production systems is:

1. Workflow creates a human task record in an external system (DB / Jira / ServiceNow / internal task service)
2. Workflow **waits** on a signal/update (“task completed”, “reassigned”, “comment added”)
3. Workflow sets timers for **deadline + escalation**
4. Operators interact with the external task system; it signals the workflow

This avoids “poll Temporal API to find pending tasks” anti-patterns and scales better (you can index tasks by user/team/etc. outside Temporal). Community discussions also warn that relying on “pending activities” as a user’s queue is inefficient at scale. ([Temporal Community Forum][8])

---

### Pattern E: CQRS State Projection (“Temporal is source of truth, Mongo is the read model”)

Temporal’s durable source of truth is the Workflow Execution history (and mutable state internally). ([Temporal Docs][3])

But for month-long workflows you almost always want an external read model for:

* dashboards
* reporting
* “show me all onboarding cases stuck in background check”
* SLA monitoring

Temporal supports **Visibility and Search Attributes** so you can filter/list workflows by custom metadata (status, employeeId, phase, dueDate, etc.). ([Temporal Docs][9])

**Best practice:**

* Put *small*, queryable workflow metadata into Search Attributes
* Maintain a richer projection in MongoDB/Postgres via events/updates
* Treat the projection as **derived** (rebuildable), not authoritative

---

### Pattern F: Event Ingestion Gateway + Idempotency

External events (webhooks, email replies, HR system callbacks) are at-least-once in the real world. Durable execution requires **idempotency**.

Temporal has guidance on ensuring message handlers behave “exactly once” from the workflow’s perspective, but you still need application-level idempotency for duplicates/races. ([Temporal Docs][10])

A pragmatic production pattern:

* Ingest external events through a gateway service
* Normalize them into `{correlationKey, eventId, payload, occurredAt}`
* Deduplicate by `(eventSource, eventId)` in a DB table
* Then deliver to the workflow (Signal/Update), keyed by correlationKey

This is the same core idea Stripe documents for safe retries: use idempotency keys so repeated requests don’t create duplicates. ([Stripe Docs][11])

---

### Pattern G: Saga / Compensations for long-running transactions

For “step 47 fails after 3 weeks” cases, you need:

* retries for transient failures
* compensation for irreversible sequences

Temporal provides explicit guidance on implementing **compensating actions** (saga building block). ([Temporal][12])
And Cadence positions saga orchestration as a core use case. ([Cadence][13])

Key idea: you register compensations as you go, and on failure run them in reverse order.

---

### Pattern H: Workflow Versioning + Worker Versioning (so deployments don’t break month-long runs)

Temporal workflow code must remain deterministic across replays. For long-running workflows, Temporal recommends explicit versioning approaches so you can change code safely. ([Temporal Docs][14])

Additionally, Temporal provides **Worker Versioning** using Build IDs/Worker Deployments so you can route workflow tasks to the correct worker build and avoid breaking in-flight runs. ([Temporal Docs][15])

For Stigmer, this matters even more because:

* you compile/interpret a DSL into workflow behavior
* any runner change can affect determinism
* you need a disciplined versioning model for both the runner and workflow definitions

## Temporal best practices you should implement in Stigmer

### 1. Continue‑As‑New strategy

#### What to implement

* **Automatic Continue‑As‑New support** in the Stigmer workflow runner
* Trigger when:

  * Temporal indicates `continueAsNewSuggested` (SDK-supported) ([Temporal Docs][5])
  * or you cross a Stigmer-defined threshold (e.g., step count / events estimate)
  * or you finish a logical phase boundary (recommended)

#### Practical thresholds

* Hard limit is **51,200 events / 50MB**, but best practice is to keep runs under the warn thresholds (≈10k events / 10MB). ([Temporal Docs][2])

#### State to carry forward

Carry only minimal deterministic state:

* current node/task pointer
* workflow variables needed for branching
* outstanding human tasks (IDs)
* pending “wait until” times
* correlation IDs / dedupe windows
* workflow definition version/hash

Avoid carrying large payloads; large payloads bloat history (inputs/outputs). (Temporal’s limit is on events and history size; large inputs/outputs contribute directly.)

---

### 2. Timer patterns for weeks/months

Temporal timers are explicitly:

* persisted
* reliable (survive worker/service downtime)
* resource-light (workers consume no resources while waiting)
* suitable for sleeping “months or even years” ([Temporal Docs][1])

#### What Stigmer should support

1. **Wait by duration** (ISO 8601 duration string, not int32 seconds)
2. **Wait until timestamp** (RFC3339 / ISO timestamp with timezone support)
3. **Wait with business calendar** (business day logic, holidays)

#### Implementation guidance

* For “wait until date/time”, compute `duration = targetTime - workflowNow` using the workflow’s deterministic clock (not system clock). Community guidance: use workflow time APIs (e.g., `Workflow.currentTimeMillis()` in Java) and do timezone-sensitive conversion outside the workflow if needed. ([Temporal Community Forum][16])
* For business calendars, prefer:

  * an Activity that computes the next business timestamp given a **calendar version**
  * then sleep until it
  * so changes in holiday calendars don’t break determinism (the calendar version becomes part of inputs)

#### When *not* to use short polling timers

Temporal best practices warn against frequent polling timers; prefer external systems signaling the workflow and consolidating timers. ([Temporal Docs][17])

---

### 3. Message handling patterns for external events

#### Use Signals/Updates (not polling)

Temporal’s messaging docs explicitly discuss ensuring messages are processed exactly once / idempotently. ([Temporal Docs][10])

#### Provide “SignalWithStart” wrapper at Stigmer ingress

A common operational issue is delivering an external event when you’re not sure the workflow exists yet. Temporal provides “Signal with Start” as a pattern (often invoked from an Activity). Community guidance supports calling signal-with-start from an activity owned by the team that knows how to start the workflow. ([Temporal Community Forum][18])

**Stigmer feature idea:** a standard ingress endpoint:

* receives event
* computes workflow ID from correlation key
* calls “signal with start” so you never lose the event

#### Dedupe strategy

* Add `eventId` to every inbound event
* In-workflow: track last N processed event IDs (bounded) **or** track “latest version per external system” (e.g., background_check_status_version)
* Or do dedupe in ingress DB before signaling

---

### 4. Child workflow patterns

Use child workflows to:

* isolate history growth
* isolate retries
* isolate ownership boundaries (IT provisioning subworkflow, background check subworkflow, equipment ordering subworkflow)

Child workflows also make it easier to “resume from checkpoint” by restarting a failed phase without re-running the whole onboarding.

---

### 5. Saga / compensation best practices

Temporal has explicit saga/compensation guidance and examples. ([Temporal][12])

Key practices to encode into Stigmer:

* **Register compensation before executing** the forward step (so timeouts/cancellations don’t skip compensation registration). ([Temporal][12])
* Run compensations in **reverse order**
* Support “manual intervention” mode:

  * pause workflow
  * let operator decide: retry, skip, compensate, or reroute
* If cancellation is involved, ensure compensations can run in a cancellation-safe scope (Temporal SDKs support “detached cancellation scope” concepts; Stigmer should provide a safe abstraction here).

---

### 6. Versioning + migrations

#### Two dimensions you must version

1. **Stigmer runner code** (Temporal workflow code determinism)
2. **Workflow definitions** (CNCF Serverless Workflow DSL)

Temporal’s docs explicitly: workflows can run for months/years, and changes require versioning methods to avoid nondeterminism. ([Temporal Docs][14])

Temporal also provides **Worker Versioning** so you can keep old workers to run old code and roll out new versions safely. ([Temporal Docs][15])

#### Recommended Stigmer approach

* Treat workflow definitions as immutable per execution:

  * store `definition_hash` and `definition_version` in workflow input + Search Attributes
  * new deployments can publish new definitions without affecting running instances
* Provide an explicit “migrate running workflow” operation:

  * implemented as “continue-as-new into new definition version at next checkpoint boundary”
  * optionally gate migrations behind human approval (for compliance)

---

### 7. Visibility & monitoring best practices

Temporal’s Visibility features and Search Attributes are designed for listing/filtering workflows. ([Temporal Docs][9])

**What you want for hundreds of month-long workflows:**

* Search Attributes like:

  * `employeeId`, `tenantId`
  * `workflowDefinitionVersion`
  * `phase` / `state` (e.g., BACKGROUND_CHECK, OFFER_PENDING, IT_PROVISIONING)
  * `nextDueAt` (Datetime)
  * `slaStatus` (Keyword)
  * `assignedTo` / `assignedTeam`
* A projection store (Mongo) for UI aggregation, but Search Attributes for fast filtering.

Also note: advanced visibility support depends on backend (SQL vs Elasticsearch) and Temporal server versions. ([Temporal Docs][19])

## Gap analysis: Stigmer today vs. what you need for month-scale durability

### High-level: you already have the right core engine

Because you’re built on Temporal, you already inherit:

* durable timers (in principle)
* durable state (event history)
* event-driven gating via signals
* replay-based recovery

But **Stigmer’s current abstractions** still leave major durability gaps.

### Gap table

| Capability                     | What you have now                                 | What’s missing for 3-month workflows                                                             | Why it matters                                                                                                   |
| ------------------------------ | ------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| **Event history management**   | No explicit mention of continue-as-new automation | Auto Continue‑As‑New (threshold + safe boundaries); history-aware compilation for loops/fan-out  | Temporal will terminate executions at 51,200 events / 50MB; warnings start at 10,240 / 10MB ([Temporal Docs][2]) |
| **Wait semantics**             | `wait` only seconds-based (int32)                 | ISO 8601 duration; wait-until timestamp; timezone; business calendar waits                       | Month workflows need date-based scheduling; Temporal timers support months/years ([Temporal Docs][20])           |
| **Human tasks**                | Single approval gate                              | Assignments, deadlines, escalations, reassignment, parallel tasks; external inbox integration    | Real onboarding requires task management, not just approvals ([Temporal Docs][7])                                |
| **External event ingestion**   | `listen` supports signals/queries/updates         | Ingress gateway, correlation strategy, dedupe/idempotency, signal-with-start support             | Webhooks & emails are at-least-once and out-of-order; signals also have limits ([Temporal Docs][3])              |
| **State visibility**           | Some phase tracking (WAITING_FOR_APPROVAL)        | Search Attributes model; state projection store; operator-friendly dashboards                    | Hundreds of long workflows require filtering, SLA views, alerting ([Temporal Docs][19])                          |
| **Checkpointing / resumption** | Implicit via Temporal history                     | Explicit checkpoints; resume boundaries; “operator fix then resume”                              | Month workflows inevitably hit “pause for manual fix”                                                            |
| **Saga / compensation**        | `try_catch` exists                                | Compensation stack semantics; deterministic rollback orchestration; manual compensation triggers | Needed when late-stage failure requires rollback ([Temporal][12])                                                |
| **Workflow versioning**        | Unclear in Stigmer layer                          | Definition versioning + runner determinism strategy + worker versioning                          | Long-running workflows will survive deployments only if versioning is handled ([Temporal Docs][14])              |
| **Scalability controls**       | Fork/for_each implemented                         | Concurrency limits, batching, child workflow fan-out controls                                    | Avoid event explosions and mutable-state limits ([Temporal Docs][2])                                             |

## Implementation roadmap (prioritized)

This ordering is based on “what will break a 3‑month onboarding workflow first” and “what blocks truthful durability claims.”

### Phase 1: Make month-long execution *possible* (core durability)

1. **Add Continue‑As‑New support to the runner**

   * Use Temporal’s `continueAsNewSuggested` where available + your own thresholds ([Temporal Docs][5])
   * Create safe checkpoint boundaries (after each task / after each phase)
2. **Upgrade `wait`**

   * Support `duration` strings and `until` timestamps
   * Implement deterministic “wait until date” via workflow time APIs and safe time handling ([Temporal Docs][20])
3. **Introduce Search Attributes mapping**

   * Standard attributes for workflow definition version, phase, nextDueAt, assignee
   * This is the backbone for ops visibility ([Temporal Docs][19])
4. **Define an event ingestion contract**

   * Correlation ID strategy
   * Idempotency strategy (dedupe keys)
   * “signal with start” option for race-free delivery ([Temporal Community Forum][18])

### Phase 2: Make it usable for real HR/compliance workflows

5. **Human Task subsystem**

   * Task creation Activity + task DB schema
   * Signals/Updates for completion, reassignment, comments
   * Deadline timers + escalation activities
6. **External task system connectors**

   * Jira/ServiceNow integration via Activities
   * Prefer webhook→signal patterns over polling (Temporal APS best practices) ([Temporal Docs][17])
7. **Operator controls**

   * Pause/resume
   * “retry step”, “skip step”, “rerun activity”, “trigger compensation”
   * Requires safe workflow Updates + authorization model

### Phase 3: Make it enterprise-grade durable

8. **Saga/compensation as a first-class DSL concept**

   * Standard “compensation stack” library and DSL syntax
   * Support manual compensation triggers ([Temporal][12])
9. **Versioning & migration**

   * Workflow definition immutability per execution
   * “migrate via continue-as-new” capability
   * Worker Versioning strategy for self-hosted + local dev ([Temporal Docs][15])
10. **Fleet-level monitoring & alerting**

* SLA alerts (dueDate missed)
* “stuck in state” alerts
* “high history growth” alerts (warn threshold)
* “high signal volume” alerts (approaching 10k signal limit) ([Temporal Docs][3])

## How other platforms handle long-running durability (and what to learn from them)

### Temporal: Continue‑As‑New + entity workflows

Temporal explicitly documents “very long-running workflows” and the **Entity Workflow** pattern, with Continue‑As‑New as the mechanism to run indefinitely while resetting history. ([Temporal][6])

### AWS Step Functions: hard history quota + “start a new execution”

Step Functions has a hard quota of **25,000 events in execution history**, and AWS recommends starting new executions to avoid reaching the quota. ([AWS Documentation][21])
This mirrors Temporal’s Continue‑As‑New concept, but implemented at the “new execution” level instead of a first-class workflow primitive.

### Uber (Cadence): massive scale + long-running orchestration + sagas

Uber’s Cadence announcement describes it powering **long-running workflows** at massive scale, with billions of executions. ([Uber][22])
Cadence documentation explicitly highlights sagas/compensation as a common orchestration use case. ([Cadence][13])

### Netflix Conductor: durable workflow state for months/years

Netflix’s Conductor is explicitly designed as an orchestration engine for microservices. ([Tech Blog][23])
Conductor vendors emphasize “workflows waiting for months/years” and being able to upgrade workers/services while workflows are in-flight (conceptually similar to Temporal’s durability goals). ([Orkes][24])
(Implementation details differ—Temporal’s replay model is a big differentiator.)

### Stripe: idempotency as the foundation for safe retries

Even if Stripe isn’t “a workflow engine example,” their reliability lessons are directly relevant: **idempotency keys** allow safe retries without duplicating effects. ([Stripe Docs][11])
That’s exactly the discipline Stigmer needs for `http_call`, `grpc_call`, and external webhook ingestion.

### Temporal production case studies relevant to your onboarding use case

Temporal has documented customer cases where long-running onboarding-like processes span months and benefit from timers, durable execution, and visibility (e.g., Mollie’s onboarding processes). ([Temporal][25])
Maersk highlights long-running workflows (days to weeks) and human-in-the-loop steps implemented as child workflows. ([Temporal][26])

## What you can legitimately claim today vs. after closing gaps

### What you can claim *today* (based on your description)

* “Built on Temporal durable execution”
* “Supports event-driven human approval gates”
* “Supports signal-driven waits and timer-based delays (seconds)”
* “Supports retries/error handling via Temporal + try/catch semantics”

### What you should **not** claim yet (unless implemented)

* “Runs onboarding/compliance workflows for months reliably”
  Because without Continue‑As‑New + history controls, long runs can be terminated at history limits. ([Temporal Docs][3])
* “Full human task management”
  You have approvals, not assignment/deadlines/escalations.
* “Durable calendars / business-day scheduling”
  Your wait primitive is currently seconds-based.

### What you *can* claim after Phase 1

* “Durable long-running workflows (weeks/months) with automatic history management (Continue‑As‑New)”
* “Calendar-based waits”
* “Production-grade event ingestion patterns (correlation + idempotency)”
* “Operational visibility via Search Attributes”

## Practical translation into Stigmer features (concrete)

If you want this to land cleanly in your DSL→Temporal compilation pipeline, the most leverage comes from adding these **first-class concepts**:

1. **Runner-managed checkpoint boundary**

   * `checkpoint()` implicit after each task OR configurable every N tasks
   * implements Continue‑As‑New safely
2. **Expanded wait**

   * `wait: { duration: "P30D" }`
   * `wait: { until: "2026-04-01T09:00:00-05:00" }`
   * `wait: { businessDays: 5, calendarId: "US_NYSE_HOLIDAYS_v3" }`
3. **Human task**

   * `human_task: { formSchema, assignee, dueAt, escalationPolicy }`
   * built on external task service + signal/update
4. **Event ingestion contract**

   * standardized `correlationKey` + `eventId`
   * built-in dedupe strategy
5. **Compensation block**

   * `try`/`catch` exists; add “compensation stack” semantics aligned to saga guidance ([Temporal][12])
6. **Version tags**

   * `workflowDefinitionVersion` stored and indexed
   * migration via continue-as-new
