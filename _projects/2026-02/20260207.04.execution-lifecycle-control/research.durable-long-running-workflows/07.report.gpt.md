## Recommendation for MVP: **Option C (Minimal Viable Both)**

If I had to pick one option for an MVP that you can *honestly* position as “durable workflows” **and** not walk back “retry and resume,” I’d choose **Option C**:

### Ship in MVP

1. **User-facing Cancel** (and ideally Terminate)

* Expose cancel via API/CLI as a first-class Stigmer control-plane action (not “go use Temporal UI”).
* Cancel is a core Temporal lifecycle operation (`temporal workflow cancel`). ([Temporal Docs][1])
* Terminate is the “hard stop” counterpart (`temporal workflow terminate`), and Temporal explicitly notes workflow code can’t respond to termination (so it’s for “stuck” cases). ([Temporal Docs][1])

2. **User-facing Retry/Resume** (implemented as **Reset**)

* Implement “retry/resume” as a wrapper around Temporal’s **Reset**, which is explicitly designed to “resume from a point in history without losing progress up to that point.” ([Temporal Docs][1])
* This aligns with what “retry and resume” means in durable workflow engines (you don’t just start a brand-new execution).

3. **Fix/upgrade `wait` at the API boundary**

* Even if your executor supports days/hours internally, the **platform contract** should support:

  * long durations cleanly
  * “wait until timestamp”
* Otherwise users will hit paper cuts immediately when they try to model real processes (start dates, SLAs, deadlines).

### Defer (post-MVP)

* **Pause/Resume** as an operator feature (nice, but not universally “baseline” across engines)
* Full event ingestion gateway productization

**But:** I would not defer idempotency forever—see the caveat under “Durable claim integrity” below.

---

## Why Option C is the best MVP tradeoff (industry meaning of “durable”)

In industry practice, “durable workflow” has two layers:

### Layer 1: Execution durability (engine guarantees)

* State persists across crashes/deployments
* Timers are durable
* Progress resumes automatically

You’re already strong here: Continue-as-New, claim check, deterministic boundaries, etc.

### Layer 2: Operational durability (control-plane guarantees)

Operators/users can:

* stop something safely
* restart/resume after fixing an issue
* recover without rebuilding state by hand

This layer is what separates “we run on Temporal” from “we are a workflow platform.”

**Competitors all expose control-plane operations as baseline** (stop/cancel + restart/resume). If Stigmer does not, then users will perceive Stigmer as “an SDK wrapper” rather than “a durable workflow product.”

Option C gives you just enough operational durability to match market expectations **without** derailing the foundational correctness work.

## Q1) Is user-facing lifecycle control MVP-critical for a “durable workflow” claim?

### For “durable workflows” (generic)

**Not strictly MVP-critical** *if* you define “durable” narrowly as “execution survives crashes and can wait.” That’s engine-level durability.

### For **your landing page claim**: “workflows that retry and resume”

**Yes—at least Cancel + Retry/Resume is MVP-critical.**

Why:

* “Retry and resume” is widely interpreted as: *I can fix a problem and continue without starting over.*
* If your only answer is “go to Temporal UI” or “start a new execution manually,” users will feel the claim is misleading (even if Temporal underneath can do it).

Temporal itself treats cancel/terminate/reset as first-class workflow operations in the CLI and docs (these are not exotic features). ([Temporal Docs][1])

---

## Q2) If a workflow fails and users cannot retry via API/CLI, does that break the “durable” promise?

It breaks the **“retry and resume”** promise in the way most customers will understand it.

Starting a *new* execution with the same inputs is **not** “resume”:

* you lose “already completed step results” unless you rebuild that logic
* you risk duplicating side effects (emails sent twice, tickets created twice, money moved twice)

Compare to what durable platforms provide:

* **Temporal**: `reset` explicitly supports resuming from a point in history. ([Temporal Docs][1])
* **AWS Step Functions**: `RedriveExecution` continues from the unsuccessful step and preserves successful step results (Standard workflows; time-limited eligibility). ([AWS Documentation][2])
* **Cadence**: `workflow reset` is explicitly described as rerunning a failed workflow “from the failing point without losing achieved progress (history).” ([Cadence][3])
* **Conductor**: exposes `/retry`, `/rerun`, `/restart` endpoints. ([Conductor][4])

So: if Stigmer wants to claim “retry and resume,” it needs an equivalent (Temporal Reset wrapper is the most direct).

---

## Q3) If a workflow is stuck and users cannot cancel via API/CLI, does that break the “durable” promise?

It doesn’t break **execution durability** (Temporal is still durable).
But it **does break operational durability** and will be perceived as a product gap.

Every major platform exposes “stop” operations:

* **Temporal**: `workflow cancel` and `workflow terminate` are core commands. ([Temporal Docs][1])
* **AWS Step Functions**: `StopExecution` exists as a core API operation (Standard only). ([AWS Documentation][5])
* **Cadence**: `workflow cancel` and `workflow terminate` exist in the core CLI docs. ([Cadence][3])
* **Conductor**: `DELETE /workflow/{workflowId}` terminates, and it also supports pause/resume. ([Conductor][4])

If Stigmer forces users to go to Temporal UI for stopping executions, the experience is: “Stigmer is not the control plane.” That’s a strategic product weakness.

**Practical MVP note:** expose both:

* **Cancel** (graceful cleanup path) ([Temporal Docs][1])
* **Terminate** (hard stop for stuck workflows) — and Temporal explicitly notes termination can’t be handled in workflow code. ([Temporal Docs][1])

## Q4) What competitors ship as baseline lifecycle controls (core vs premium/enterprise)?

### Temporal (OSS + Temporal Cloud)

Baseline controls are part of the platform/CLI:

* Cancel: `temporal workflow cancel` ([Temporal Docs][1])
* Terminate: `temporal workflow terminate` ([Temporal Docs][1])
* Reset (resume/retry): `temporal workflow reset` ([Temporal Docs][1])
* Signal-with-start exists as a core capability: `temporal workflow signal-with-start` ([Temporal Docs][1])

These are not “enterprise-only lifecycle features”; they’re fundamental workflow operations.

### AWS Step Functions

Baseline controls (no premium tiers; feature differences are Standard vs Express):

* Stop: `StopExecution` (not supported by Express) ([AWS Documentation][5])
* Redrive: `RedriveExecution` (Standard only; continues from failed step; preserves successful steps; eligibility constraints like 14-day period) ([AWS Documentation][2])
* Built-in Retry/Catch inside definitions (state-level error handling). ([AWS Documentation][6])

Also notable: redrive API uses a `clientToken` for idempotency. ([AWS Documentation][2])

### Cadence

Baseline controls in core CLI/docs:

* Signal/cancel/terminate in CLI ([Cadence][3])
* Reset semantics explicitly include rerunning from failing point without losing progress ([Cadence][3])
* Workflow retry policies exist as a concept too ([Cadence][7])

### Netflix Conductor (OSS) / Orkes Conductor

Baseline controls in core REST API:

* Pause/resume endpoints ([Conductor][4])
* Retry last failed task, restart, rerun from task ([Conductor][4])
* Terminate workflow via DELETE ([Conductor][4])

So in Conductor, “pause/resume/retry/restart/terminate” are *explicitly* part of core operational control, not a premium add-on.

## Q5) For “workflows that retry and resume,” what’s the **minimum** to ship honestly?

### Minimum feature set (product-facing)

1. **Cancel + Terminate** exposed via Stigmer API/CLI

* Because “stuck workflow” handling is table stakes. ([Temporal Docs][1])

2. **Retry/Resume** exposed as **Reset**

* Provide a Stigmer command/API that maps to Temporal Reset semantics. ([Temporal Docs][1])
* UX detail that matters: support “reset to last safe checkpoint” (not raw event IDs in the public API).

3. Make `retry` semantics explicit in docs:

* “Retry failed step” vs “restart workflow” vs “resume from checkpoint”
* Conductor splits these concepts (retry/rerun/restart). ([Conductor][4])
* Step Functions splits “Retry in-definition” vs “Redrive execution after failure.” ([AWS Documentation][6])

### Durability claim integrity caveat (important)

If you ship “retry/resume” but **don’t** enforce idempotency at integration boundaries, users will “resume” and accidentally duplicate side effects.

You can still ship MVP honestly if you:

* require connectors/actions to accept an **idempotency key** (your connector contract spec already points here)
* document that retries/resets require idempotent side effects
* (ideally) bake an idempotency key into every outbound call envelope

AWS Step Functions explicitly bakes idempotency into RedriveExecution requests via `clientToken`. ([AWS Documentation][2])
That’s a strong signal that “resume” features and idempotency are tightly linked in real platforms.

## What you can honestly claim on the landing page under each option

### Option A: Lifecycle Control First

**You can claim**

* “Cancel / pause / resume workflows”
* “Retry / restart workflows”

**You must NOT strongly claim**

* “durable integrations / safe external event ingestion” (without idempotency/correlation)
* “handles real-world long waits cleanly” (if wait-until remains awkward)

**Risk:** looks good in demos, but fails in real distributed, event-driven use cases.

---

### Option B: Durability Core First

**You can claim**

* “Durable long-running execution (timers, event-driven waits, survives restarts)”
* “Safe external events (idempotent/correlatable)”
* “Automatic retries at the activity/task level”

**You must change/qualify**

* “retry and resume” phrasing, because users can’t *do* it from Stigmer’s control plane.

If you keep Option B, I’d recommend landing page wording like:

* “Automatic retries and crash-safe resumption (powered by Temporal)”
  …but avoid implying operator actions like “retry a failed workflow from CLI.”

---

### Option C: Minimal Viable Both (recommended)

**You can claim (honestly)**

* “Workflows that retry and resume” **if** retry/resume = Stigmer reset/resume and you document semantics
* “Users can cancel stuck workflows” (and ideally terminate)
* “Long waits / deadlines” once wait is upgraded

**You should qualify**

* event ingestion story if correlation/idempotency is still missing (or treat it as “advanced / beta”).

---

## Bottom line

* If your landing page will continue to say **“retry and resume”**, then **Option B is not enough** without rewriting the claim.
* **Option A** optimizes for marketing and operator UX but risks shipping a “durable control plane” on top of brittle integration semantics.
* **Option C** is the smallest set that matches what durable workflow platforms ship by default: **stop + resume/retry**, plus the practical ability to model long waits.
