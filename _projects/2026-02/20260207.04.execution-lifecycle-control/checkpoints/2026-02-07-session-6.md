## Decisions Made

### 1. Generic Type Constraints
**Decision**: Used Go generics with `LifecycleInput` and `LifecycleInputWithReason` interfaces  
**Rationale**: Makes pipeline steps reusable across different input types while maintaining type safety  
**Impact**: Reduced code duplication, improved maintainability

### 2. Direct Temporal Client Injection
**Decision**: Inject Temporal client directly into controller (Option A from plan)  
**Rationale**: Simpler than creating a separate facade service, aligned with existing patterns  
**Impact**: Clean, straightforward implementation with clear dependencies

### 3. Idempotency-First Design
**Decision**: All handlers check if execution is already in target state before calling Temporal  
**Rationale**: Temporal operations are not free - avoid unnecessary API calls  
**Impact**: Better performance, clearer intent, safer error handling

### 4. Test Strategy Without Live Temporal
**Decision**: Focus unit tests on validation logic, accept "Temporal not available" for non-idempotent cases  
**Rationale**: Unit tests should not require external dependencies  
**Impact**: Fast, reliable tests that focus on business logic

### 5. Workflow ID Format
**Decision**: Use existing format `stigmer/workflow-execution/invoke/{execution-id}`  
**Rationale**: Already established in codebase, no reason to change  
**Impact**: Consistency with existing code

## Learnings

### Technical Insights

1. **Go Generics for Pipeline Steps**: Using interfaces as type constraints allows creating truly reusable pipeline steps without sacrificing type safety

2. **UpdateStatus vs Update**: For test helpers, use `UpdateStatus` to update execution phases (not `Update`, which only handles spec changes)

3. **Idempotency Patterns**: Checking target state first is cleaner and more efficient than trying the operation and catching already-done errors

4. **Test Data Uniqueness**: Using timestamps in test resource names prevents slug conflicts when tests create workflow/instance/execution entities

### Process Insights

1. **Feature Parity Strategy**: Implementing the same feature in two different languages (Java and Go) provided valuable comparison insights about patterns and approaches

2. **Test-Driven Development**: Writing tests exposed edge cases early (like the UpdateStatus issue) that would have been harder to debug later

3. **Documentation-First**: Creating the plan upfront and following it strictly resulted in a clean, well-structured implementation
