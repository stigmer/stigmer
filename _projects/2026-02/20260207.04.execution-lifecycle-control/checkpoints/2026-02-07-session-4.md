## Decisions Made

### Technical Decisions

1. **Pipeline Pattern**: All handlers follow the established `CustomOperationHandlerV2` pattern
   - Rationale: Consistency with existing handlers, composable steps, clear error handling
   - Impact: Handlers integrate seamlessly with existing infrastructure

2. **Phase Validation**: Dedicated validation steps for each operation
   - Cancel: Only PENDING/IN_PROGRESS → CANCELLED
   - Terminate: Only PENDING/IN_PROGRESS → TERMINATED
   - Recover: Only FAILED → IN_PROGRESS
   - Rationale: Enforce preconditions, prevent invalid state transitions
   - Impact: Clear error messages, predictable behavior

3. **Idempotency Strategy**: Detect and handle already-processed states
   - Cancel/Terminate: Return success if already in target state
   - Recover: Return error if already recovered (not in FAILED state)
   - Rationale: Safe retries, no duplicate operations
   - Impact: Resilient to network retries and duplicate requests

4. **Temporal Integration Approach**:
   - Cancel/Terminate: Use `WorkflowClient` with workflow stubs
   - Recover: Use `WorkflowServiceStubs` for lower-level reset API
   - Rationale: Reset requires history querying and advanced parameters
   - Impact: Recover handler is more complex but correctly implements Temporal's reset pattern

5. **Audit Logging**: All handlers include structured audit logs
   - Fields: traceId, userId, workflowExecutionId, operation, timestamp
   - Rationale: Compliance, debugging, operational visibility
   - Impact: Complete audit trail for all lifecycle operations

### Architectural Insights

1. **Temporal Reset Complexity**: 
   - Reset requires querying workflow history to find the last `WorkflowTaskCompleted` event
   - Must extract both `runId` and `eventId` for reset operation
   - More complex than simple cancel/terminate operations
   - Lesson: "Recover from failure" is not a simple "restart" - it's a sophisticated rollback

2. **Annotation Processor as Critical Infrastructure**:
   - Auto-generated controller classes are core to the gRPC routing system
   - Annotation processor failures block the entire compilation pipeline
   - Pre-existing issues can be hard to distinguish from new bugs
   - Lesson: Always test on clean branch when encountering mysterious build failures

## Learnings

### Technical Learnings

1. **Temporal Reset API is Complex**:
   - Requires history querying via `getWorkflowExecutionHistory()`
   - Must find the last successful `WorkflowTaskCompleted` event
   - Needs both `runId` and `eventId` for reset operation
   - Different from simple cancel/terminate which only need `workflowId`

2. **Java Import Aliasing**:
   - Java does not support `import ... as ...` syntax (unlike Python)
   - Must use fully qualified names to disambiguate (e.g., `io.temporal.api.common.v1.WorkflowExecution`)
   - Alternative: Use different variable names to avoid conflicts

3. **Annotation Processor Debugging**:
   - Stash all changes and test on clean branch to isolate pre-existing issues
   - `bazel clean --expunge` removes all caches and worker processes
   - ClassCastException in annotation processor often indicates JDK version incompatibility

4. **Proto Stub Generation**:
   - User ran `buf generate` to create Java stubs for new input messages
   - Stubs appear as untracked files in git status
   - Build depends on these stubs being generated before compilation

### Process Learnings

1. **Collaboration on Surprises**:
   - When proto stubs were missing, presented as "surprise" per user instructions
   - User resolved externally (ran `buf generate`)
   - Good pattern: Identify blocker, present clearly, let user decide resolution

2. **Pre-existing Issues vs. New Bugs**:
   - Always verify issue exists on clean branch before extensive debugging
   - Saved time by quickly proving annotation processor issue was pre-existing
   - Clear communication: "This blocks your work, but isn't your fault"

3. **Quality Over Speed**:
   - User emphasized: "bring your best work," "don't get complacent," "world-class platform"
   - Implemented comprehensive pipelines, not shortcuts
   - Extensive unit tests, proper error handling, audit logging
   - Result: Production-ready code that follows established patterns
