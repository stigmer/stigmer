## Decisions Made

### 1. Complete Deletion vs Gradual Deprecation

**Context**: The WorkflowRunner gRPC interface had three execution modes:
- `grpc`: Local testing/debugging only
- `temporal`: Production mode (via Temporal worker)
- `dual`: Both gRPC server and Temporal worker

**Question**: Should we deprecate gradually or delete completely?

**Decision**: Complete deletion

**Rationale**:
- gRPC mode had no active production users
- gRPC mode was theoretically for "local development" but rarely used
- Production always uses Temporal - local dev should mirror production
- Temporal provides superior debugging tools (Temporal UI, tctl CLI)
- Having multiple modes creates maintenance burden
- Clean break eliminates architectural ambiguity

**User Confirmation**: After presenting the usage analysis, user confirmed "Delete everything as planned"

### 2. Local Development Workflow

**Context**: User asked for clarification on "local development" - Stigmer server vs isolated workflow-runner testing

**Clarification Provided**:
- `grpc` mode in `workflow-runner/main.go` was for **isolated workflow-runner testing only**
- NOT for the `stigmer server` command
- `stigmer server` orchestrates multiple components including workflow-runner (in `temporal` mode)

**Migration Impact**:
- Developers must run local Temporal for workflow testing
- This mirrors production behavior (good practice)
- No user-facing functionality affected

### 3. Single Control Plane Architecture

**Architectural Principle Established**:

```
Before (Dual Control Plane):
User → WorkflowRunner gRPC (cancelExecution, pauseExecution, resumeExecution)
User → Stigmer Service (future: cancel, terminate, recover)

After (Single Control Plane):
User → Stigmer Service → Temporal API → WorkflowRunner (pure worker)
```

**Benefits**:
- Clear responsibility boundaries
- WorkflowRunner is executor only, not a controller
- Aligns with Temporal's architectural patterns
- Simpler mental model
- Foundation for user-facing lifecycle controls (T1-T7)
