## Decisions Made

- **One attempt per state, no retry loops**: Keep it simple. If recovery fails, fall through to creation. Volume guarantees file survival.
- **STARTED still gets health check**: Defense-in-depth for edge case where SDK state is stale.
- **Transitional states fall through to creation**: STARTING, STOPPING, CREATING, etc. are rare edge cases that don't warrant complex wait/retry logic.
- **`auto_delete_interval=-1` at creation time**: Explicit defense-in-depth even though SDK default is disabled.
- **`DaytonaNotFoundError` instead of bare `Exception`**: Typed error for the "sandbox gone" case.

## Learnings

- Daytona SDK `SandboxState` has 16 members, not 4-5 as public docs suggest: STARTED, STOPPED, ARCHIVED, ERROR, DESTROYED, CREATING, RESTORING, STARTING, STOPPING, DESTROYING, ARCHIVING, BUILD_FAILED, PENDING_BUILD, BUILDING_SNAPSHOT, PULLING_SNAPSHOT, UNKNOWN
- There is NO `DELETED` state — it's `DESTROYED` instead. The plan referenced DELETED but the real SDK uses DESTROYED.
- `SandboxState` is imported from `daytona` top-level (re-exported from `daytona_api_client`)
- `DaytonaNotFoundError` is also importable from `daytona` top-level
- `sandbox.start()` works on both STOPPED and ARCHIVED states (confirmed by SDK docs: "starting an archived sandbox takes more time")
- `auto_delete_interval` default is already disabled (-1), but being explicit is correct for critical invariants
