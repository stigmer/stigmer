# Session 5 Notes: Fix Premature Execution Completion

**Date**: 2026-02-15 (Saturday evening)
**Duration**: ~2 hours
**Focus**: Diagnose and fix `stigmer draft skill` premature completion issue

## Problem Statement

User reported that `stigmer draft skill` executions were completing prematurely:
1. Agent read input files correctly
2. Agent wrote skill files to sandbox
3. Execution completed immediately (no artifacts published)
4. No final AI message summarizing what was created
5. Write tool showed as "pending" (⏳) even after completion
6. User had no downloadable output

## Investigation Approach

Created detailed plan (`diagnose_premature_execution_387cbe0e.plan.md`) with 4 investigation tasks and 3 implementation tasks. Used parallel explore subagents to investigate CLI, backend, and graph structure simultaneously.

## Root Causes Found

### Cause 1: Agent Prompt Gap (Primary Issue)
The `skill-creator-agent.yaml` system prompt had:
- ✅ Access to `publish_artifact` tool (registered as builtin in `execute_graphton.py`)
- ❌ Zero mention of the tool in instructions
- ❌ No instruction to provide completion summaries
- ❌ No principle emphasizing these are mandatory

**Result**: Agent completed after writing files, unaware it should publish them.

### Cause 2: CLI Tool State Not Finalized
When `DoneEvent`, `StreamErrorEvent`, or `handleStreamClosed` fired, running tools tracked in `m.runningTools` stayed in "pending" state (⏳ indicator).

**Result**: Confusing final display showed tools as "in progress" after completion.

### Cause 3: No Backend Observability
When event stream ended naturally, no validation checked:
- Whether last message was a tool message (missing AI follow-up)
- Whether any artifacts were published

**Result**: Silent completions had no diagnostic path.

## Solutions Implemented

### Fix 1: skill-creator-agent.yaml Updates (+29 lines)

Added two workflow steps:
- **Step 5 - Publish Artifacts**: Explicit requirement with emphasis on user download needs
- **Step 6 - Summarize**: Explicit requirement with structure (name, files, decisions, suggestions)

Added two key principles:
- **Always Publish**: "Never finish without calling `publish_artifact`"
- **Always Summarize**: "Never finish silently"

Also mentioned `publish_artifact` in "Your Capabilities" section for early awareness.

### Fix 2: CLI Tool Finalization (+37 lines in 2 files)

**`render_blocks.go`**: Added `renderToolFinalized()` helper
- Replaces `⏳` with `✓` for clean visual closure

**`handle_events.go`**: Updated three terminal handlers
- `DoneEvent` handler
- `StreamErrorEvent` handler  
- `handleStreamClosed` handler

Each now iterates `m.runningTools` and calls `renderToolFinalized()` on the block content, then clears the map.

### Fix 3: Backend Post-Stream Validation (+34 lines)

In `execute_graphton.py` after stream ends (line 2150+):
- **Check last message type**: If `MESSAGE_TOOL`, log WARNING with context
- **Check artifact count**: If empty, log INFO (not error — some executions are legit artifact-free)

Both logs use `[POST_STREAM]` prefix for easy observability monitoring.

## Key Findings During Investigation

### CLI Changes Were NOT the Cause
Recent addition of `HeartbeatEvent` and thinking indicator (session 4) were initially suspected. Exhaustive trace of all 7 modified files confirmed:
- No new path sets `done = true`
- No timer/tick triggers completion
- Heartbeats early-return without state mutation
- All completion paths (`DoneEvent`, `StreamErrorEvent`, `handleStreamClosed`) unchanged

The CLI faithfully displays whatever the backend reports. Backend sent `EXECUTION_COMPLETED`, CLI showed it.

### Graph Structure Is Correct
The `deepagents` library creates a standard ReAct loop:
```
LLM → (tool calls?) → Tool Node → (back to LLM) → END (if no tool calls)
```

There is NO path to terminate after a tool without returning to the LLM. The "missing AI message" was because the agent's system prompt didn't instruct it to provide one, not a graph routing bug.

### Bootstrap Auto-Reapplication Works Seamlessly
The seedpack bootstrap:
- Runs automatically on server startup
- Computes content hash from agent definition
- Compares against stored hash
- If different: calls `agentClient.Apply()` which updates existing agent
- If same: skips

No manual CLI command needed — just restart the server.

## Decisions Made

**Decision**: Agent instruction enhancement over code enforcement
- **Rationale**: Fix at source (agent knows what to do) rather than backend validation (detect and block)
- **Trade-off**: Requires agent cooperation, not enforced by platform
- **Justification**: LangGraph graphs should be flexible; enforcement would add complexity

**Decision**: Observability warnings, not errors
- **Rationale**: Some executions legitimately have no artifacts (research, analysis)
- **Trade-off**: Agents can still complete without artifacts if they ignore instructions
- **Justification**: Logs provide diagnostic path without false-positive errors

**Decision**: No automatic artifact fallback collection
- **Rationale**: Explicit `publish_artifact` is the contract; implicit collection adds magic
- **Trade-off**: If agent forgets, user gets nothing (but now agent won't forget)
- **Justification**: Clear contract is better than implicit behavior

## Learnings

**Diagnostic Discipline Pays Off**
Creating the plan file forced structured thinking. Parallel subagent exploration was highly efficient — covered CLI, backend, and graph structure simultaneously in ~5 minutes.

**Don't Assume Recent Changes Are the Cause**
The thinking indicator work (session 4) was the obvious suspect due to timing, but exhaustive trace proved it innocent. Always verify assumptions with code evidence.

**System Prompts Are Critical Infrastructure**
The agent had the tool but not the knowledge to use it. System agent definitions are as important as code — they define agent behavior and user experience.

**Bootstrap Is Well-Designed**
Content-hash-based idempotent bootstrap "just works" — no manual steps, no version bumping needed. Restart and it auto-detects changes.

**Observability Over Enforcement**
Warnings in logs provide diagnostic value without restricting flexibility. The right level for catching edge cases without breaking valid patterns.
