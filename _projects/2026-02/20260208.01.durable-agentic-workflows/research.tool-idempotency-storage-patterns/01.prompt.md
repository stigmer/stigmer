# Deep Research Request: Tool Idempotency Storage Patterns for Durable Agentic Workflows

## Research Objective

We are building a durable agentic workflow platform (similar to Temporal + LangGraph) and need to implement **tool call idempotency** to prevent duplicate side effects when agent executions retry after crashes. We need guidance on the best storage and durability patterns for this "tool ledger" component.

## Context

### What We're Building

- **Platform**: Agentic workflow orchestration using Temporal (Java) + LangGraph (Python)
- **Problem**: When an agent crashes mid-execution and Temporal retries the activity, tools that already executed (e.g., send_email, create_pr, charge_payment) may run again, causing duplicates
- **Solution**: A "tool ledger" that records completed tool calls and returns cached results on retry

### Current Architecture

- **Temporal**: Orchestrates workflow execution with activity retries
- **LangGraph**: Manages agent state with checkpointing (MongoDB/SQLite)
- **Available Storage**: Redis (already initialized), MongoDB (used for LangGraph checkpoints)
- **Scale**: Targeting 1000s of concurrent agent executions

### Idempotency Key Design

Each tool call has a unique identifier from the LLM:
```
Key: {execution_id}:{tool_call_id}
Example: exec-abc123:call_001
```

### What the Ledger Stores

```json
{
  "result": "email sent successfully",
  "tool_name": "send_email",
  "args_hash": "sha256...",
  "timestamp": "2026-02-08T12:00:00Z"
}
```

## Specific Questions We Need Answered

### 1. Storage Backend Selection

**Options we're considering:**
- **Redis with TTL**: Fast, simple, but not durable if Redis crashes
- **MongoDB**: Durable, already have it, but slower than Redis
- **Redis + MongoDB dual-write**: Fast reads, durable writes, but complex
- **PostgreSQL**: ACID guarantees, but adds another dependency

**Questions:**
- What do production systems (Temporal, Airflow, Step Functions) use for similar idempotency tracking?
- Is Redis-only acceptable if we configure persistence (AOF/RDB)?
- What's the industry standard for this pattern?

### 2. Durability vs Performance Tradeoffs

**Scenario**: Redis loses data after a crash
- **Impact**: Some tool calls may re-execute on retry
- **Question**: Is this acceptable risk, or should we prioritize durability over speed?

**Considerations:**
- Most tool calls are read-only (low risk)
- Critical operations (payments) often have API-level idempotency anyway
- The ledger is "defense in depth", not the only protection

### 3. TTL and Storage Management

**Current thinking:**
- TTL = execution timeout + retry buffer (~15 minutes)
- Auto-expire entries to prevent unbounded growth

**Questions:**
- What TTL strategies do production systems use?
- Should TTL be configurable per-tool or per-execution?
- Are there patterns for archiving ledger entries for audit trails?

### 4. Concurrency and Race Conditions

**Scenario**: Multiple workers retry the same execution simultaneously
- Need to prevent both from executing the same tool call

**Questions:**
- Is Redis `SET NX` (set-if-not-exists) sufficient for claiming tool execution rights?
- What distributed locking patterns are recommended?
- How do Temporal and similar systems handle this?

### 5. Large Results Handling

**Problem**: Some tool results can be large (file contents, API responses)
- Don't want to bloat the ledger

**Questions:**
- Should we use a "claim check" pattern (store large results in blob storage, ledger stores reference)?
- What's the threshold for "large" (1KB? 10KB? 100KB?)?
- How do similar systems handle this?

### 6. Failure Modes and Recovery

**Questions:**
- What happens if ledger write succeeds but tool execution fails?
- Should we implement two-phase commit patterns?
- How do we handle partial failures gracefully?

### 7. Alternative Approaches

**Questions:**
- Are there better patterns than a separate ledger?
- Could we leverage Temporal's built-in features (side effects, memoization)?
- Does LangGraph have any undocumented features for this?

## What We Already Know

1. **LangGraph checkpointing** saves conversation state but does NOT prevent tool re-execution
2. **LangGraph documentation** explicitly recommends "use idempotency keys" as the solution
3. **Temporal activities** can access heartbeat details on retry, which we'll use for checkpoint resume
4. **Redis** is already initialized in our Python agent-runner for cloud deployments
