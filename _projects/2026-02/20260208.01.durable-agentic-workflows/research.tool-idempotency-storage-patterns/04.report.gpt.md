# Tool Idempotency Storage Patterns for Durable Agentic Workflows

## Why retries create duplicate side effects

Durable orchestration systems deliberately trade “exactly-once side effects” for fault tolerance by using retries and at-least-once task delivery. The consequence is fundamental: if a worker crashes after performing an external side effect (send email, create PR, charge card) but before the orchestrator records completion, the orchestrator can legitimately retry the step, and the side effect can happen twice unless you add idempotency at (or below) the tool boundary. citeturn0search4turn0search0turn7search6

In Temporal specifically, durable execution is achieved by persisting an append-only event history and replaying workflow code from that history to reconstruct state after failures. Workflow code is replayed deterministically and therefore does not “re-run” previously completed workflow steps; but Activities are separate, failure-prone units of work and can be re-executed under retries, timeouts, and worker crashes—hence Temporal’s strong guidance that Activities be idempotent. citeturn7search6turn0search0turn6search7

LangGraph’s durability has a similar boundary: it checkpoints state so a run can be resumed, but resumption may replay from a node boundary (not the exact line of code), and if a task with side effects “started but did not complete successfully,” LangGraph can re-run it. LangGraph documentation explicitly recommends designing side effects to be idempotent and using idempotency keys (or verifying existing results) to avoid duplication. citeturn11view0turn6search1

The “tool ledger” you described is therefore best understood as a defense-in-depth *idempotency store* that compensates for an unavoidable ambiguity in distributed systems: “Did the external system receive and apply the request, even though we didn’t record success?” That ambiguity is discussed explicitly in Temporal community guidance on idempotency concerns with external systems. citeturn0search16turn6search7

## What production orchestrators do instead of a general-purpose tool ledger

Temporal, Airflow, and Step Functions do not ship a single universal “side-effect ledger” for *your* external calls. Instead, they (a) persist their own internal execution state durably, and (b) push idempotency responsibilities down to user code and/or the called services.

Temporal’s durability is rooted in its persistence store (a database) which stores workflow execution mutable state plus an append-only history table; this is the mechanism that allows replay after failures. That persistence store is a required dependency for Temporal Server operation and supports multiple databases. citeturn7search0turn7search11

However, Temporal still recommends Activities be idempotent, precisely because Activity execution can be retried and re-executed; Temporal documentation and official blog guidance repeatedly emphasize idempotency as the primary strategy for safe retries. citeturn0search0turn6search7

AWS Step Functions documentation is explicit that workflows can conform to an at-least-once execution model where each step may run more than once; it also notes “idempotency is not automatically managed” in the general case of repeated executions and state logic. Step Functions provides idempotency-like behavior around *starting* an execution with the same name in a specific situation, but it does not automatically dedupe arbitrary task side effects. citeturn0search2turn0search14

Apache Airflow similarly treats retries as normal and instructs users to design tasks so reruns produce the same outcome; its best-practices documentation frames tasks like database transactions and highlights that retries imply tasks should produce the same outcome on every rerun. citeturn1search0

Prefect is notable because it offers built-in *task result caching* and describes caching as a way to “reuse results of tasks” and “ensure that your pipelines are idempotent when retrying them,” i.e., it provides a first-class “ledger-like” mechanism for *task results* (not necessarily for arbitrary external side effects unless your side effect is modeled as a task with persisted result). citeturn1search2turn1search13

Across these systems, a common best practice emerges: retain durable orchestration state in the orchestrator’s database, but treat external side effects as at-least-once unless you enforce idempotency (via stable keys and/or server-side idempotency) at the API/tool layer. This is the same principle emphasized in the AWS Builders Library guidance on making retries safe with idempotent APIs. citeturn7search6turn0search30

## Recommended storage architecture for your tool ledger

For your stack (Temporal Java Activities + LangGraph Python runner, Redis and MongoDB already available, 1000s of concurrent executions), the most robust pattern is:

A *durable system-of-record tool ledger* in MongoDB (single-write), optionally fronted by Redis as a cache and/or short-lived lock, with a “claim-check” path for large results into object storage.

This recommendation is driven by two constraints that show up repeatedly in production-grade durable execution systems:

- Internal orchestration state is durable because it is persisted in a database (Temporal’s persistence store, LangGraph checkpointers). citeturn7search0turn11view0  
- External side effects are still subject to ambiguous completion (request may have been applied even if the worker crashed before recording success), so you need durable idempotency keys and/or server-side idempotency at the tool boundary. citeturn0search16turn0search30turn4search2

### Why MongoDB as the ledger system of record

A ledger whose purpose is “prevent duplicate side effects during retries after crashes” should be durable under process restarts and typical infrastructure failures. MongoDB can provide this durability with appropriate write concern settings (ack policies) and is already in your architecture for LangGraph checkpointing. citeturn3search2turn3search23turn11view0

MongoDB also gives you two crucial primitives for the ledger:

- **Uniqueness for dedupe/claiming:** a unique index on the idempotency key ensures only one record exists for `{execution_id}:{tool_call_id}` (or `_id = key`). citeturn3search15turn9view0  
- **Atomic single-document updates:** MongoDB documents can be updated atomically (e.g., via `findAndModify`/`updateOne`), which supports safe state transitions like `STARTED → COMPLETED` without requiring distributed locks for most cases. citeturn9view0

### Where Redis fits and where it does not

Redis is excellent for performance because it serves data from memory and provides low-latency primitives like `SET ... NX PX ...` for lock-like behavior. citeturn2search30turn2search2

But Redis-only is risky for a ledger whose job is to prevent duplicate side effects after crashes, unless you explicitly accept some probability of data loss and thus some probability of re-execution. Even with persistence (AOF), Redis documentation states that with `appendfsync everysec` you may lose about a second of data in disasters, and `appendfsync always` is “very very slow” (durability over performance). citeturn2search0

More importantly, in common high-availability Redis deployments with asynchronous replication, Redis documentation warns that “acknowledged writes are [not guaranteed] retained during failures.” This directly undermines Redis as the *sole* system of record for an idempotency ledger meant to survive failures. citeturn3search10turn3search13

Therefore, Redis fits best as:

- a **read-through cache** of *completed* tool results (fast path), and/or  
- a **short-lived coordination primitive** to reduce thundering-herd concurrency (optimization),  

while MongoDB remains the authoritative ledger. citeturn11view0turn2search2turn3search10

### When PostgreSQL would be “industry standard”

If you did not already have MongoDB, an ACID SQL database is a very common “industry standard” idempotency store because it naturally supports unique constraints and atomic upserts (`INSERT ... ON CONFLICT ...`). PostgreSQL documentation explicitly describes `ON CONFLICT DO NOTHING` behavior with unique constraints/indexes, which directly implements idempotent “insert-once” semantics. citeturn3search0turn3search17

Given you already run MongoDB for LangGraph checkpoints, adding PostgreSQL *purely* for the tool ledger is likely unnecessary operational complexity unless you have additional requirements (strong relational constraints across multiple tables, transactional joins with other business data, or organizational standardization on Postgres). citeturn11view0turn3search0

### What this implies for your “single vs dual-write” question

A Redis+MongoDB dual-write where Redis is “fast reads” and MongoDB is “durable writes” can be safe if the design is explicitly **Mongo-first** for correctness, and Redis is a cache that can be rebuilt (or simply tolerated as miss-on-restart). A true dual-write that requires consistency across two stores recreates the “dual write problem” that distributed-systems literature warns about; the transactional outbox pattern exists specifically because multi-system atomic commits (2PC) are often not viable or desirable. citeturn4search0turn0search30

## Ledger record design, TTL strategy, and large results

### A practical record state machine

Your current schema stores only “completed tool calls.” In real failure scenarios you also need at least a notion of “in progress” (claim) to handle concurrency and to avoid two workers executing the same tool call at the same time.

A production-robust ledger record generally benefits from these fields:

- `key` (or `_id`) = `{execution_id}:{tool_call_id}`  
- `tool_name`, `args_hash`  
- `status`: `STARTED | COMPLETED | FAILED`  
- `owner_id` and `lease_expires_at` (optional but recommended for recovery)  
- `result_inline` or `result_ref`  
- `error` (structured, if needed)  
- `created_at`, `updated_at`, `expires_at` (TTL)  

The “lease” concept exists because without it, a worker that crashes after writing `STARTED` can block all future retries (or cause indefinite waiting). This is a standard response to the at-least-once/retry ambiguity discussed in durable execution guidance. citeturn0search16turn11view0turn6search1

### TTL that matches Temporal retry reality

Your proposed TTL (“execution timeout + retry buffer ~ 15 minutes”) can be correct *only if it is derived from the maximum retry window in your Temporal Activity configuration*.

Temporal distinguishes timeouts, and the Schedule-To-Close timeout explicitly controls the overall time allowed for an Activity execution **including all retries**. Temporal’s official material also notes that retries can extend very far if unconstrained. citeturn10search0turn10search2turn10search1

So a more production-stable TTL rule is:

> **TTL ≥ (Activity Schedule-To-Close timeout) + buffer**  
> and if you rely on workflow-level timeouts instead, TTL is derived from that broader window.

This aligns TTL with the actual retry envelope rather than an assumed 15 minutes. citeturn10search0turn10search1turn10search2

If you also have LangGraph durability set to `"async"` (which allows a “small risk” of lost checkpoints on crash), you should assume that retries after crashes are plausible even when checkpoints exist, which increases the importance of the ledger TTL covering the full retry envelope. citeturn11view0turn6search1

### TTL per tool vs per execution

Configurable TTL per tool is a practical strategy because different tools have different “duplication blast radii.” LangGraph explicitly calls out that redundancy risk is most important for operations that result in data writes. citeturn11view0turn6search2

A defensible policy many teams adopt (and which matches external API idempotency practices) is:

- **Low-risk / read-only tools:** short TTL, or no ledger at all if side effects are truly absent. citeturn11view0  
- **Medium-risk write tools with inherent idempotency:** TTL covers retry envelope. citeturn0search30  
- **High-risk tools (payments):** TTL covers retry envelope *and* aligns with external provider idempotency retention.

For example, Stripe documents that idempotency keys expire out of their system after a fixed retention window (commonly described as 24 hours for idempotency-key safety for retries), and that the same idempotency key returns the same result (including errors) once recorded. This suggests your ledger TTL for payment-like operations often benefits from being at least on the order of the provider’s idempotency window (or longer if you want additional internal protection). citeturn4search2turn4search28turn4search5

### Implementing TTL in MongoDB

MongoDB TTL indexes are explicitly designed for expiring time-bounded data (sessions, logs, ephemeral records). TTL expiration is performed by a background thread that removes expired documents; it is not an instantaneous “hard delete at exact timestamp,” which is usually acceptable for ledgers whose main purpose is dedupe during the retry window. citeturn2search3turn2search7turn2search33

### Archiving for audit trails

If you have audit/compliance needs, TTL deletion is at odds with long-term audit retention. Production workflows often separate:

- a **short-lived idempotency cache/ledger** (fast dedupe, TTL), from  
- an **append-only audit log** (long retention, immutable).

This mirrors how durable systems preserve internal execution history for debugging/compliance while also having quotas and limits around payload sizes, encouraging externalization of large or long-lived artifacts. citeturn7search6turn5search12turn8view0

### Large result handling and the claim-check pattern

Your tool ledger should avoid storing large blobs for two reasons:

1. **Hard limits exist in common components.** Temporal payloads have strict limits (e.g., 2 MB max payload per request and 4 MB per event-history transaction in Temporal Cloud), and Temporal itself recommends offloading large payloads to object storage and passing references. citeturn5search1turn8view0  
2. **MongoDB documents have a maximum BSON document size of 16 MiB**, and MongoDB documentation recommends using GridFS for larger objects. citeturn5search7

Step Functions provides an additional industry datapoint: it enforces a 256 KiB maximum input/output size for task/state/execution payloads, and AWS documentation and blog examples show patterns where large data is placed in S3 and only references are passed through the workflow. citeturn5search6turn5search36turn5search9

These constraints strongly support a **claim-check pattern** for your ledger:

- Store `result_inline` only up to a defined threshold.  
- If above threshold, store `result_ref` (e.g., an R2 object key) plus metadata (size, hash, content-type).  
- Optionally compress inline results, but treat compression as a mitigation, not a strategy for unbounded growth (matching Temporal guidance on compression vs offloading). citeturn8view0turn5search7

#### What threshold is “large”?

There is no single universal number, but multiple production systems cluster around “hundreds of KB” as a meaningful boundary:

- Temporal emits warnings at 256 KB and errors at 2 MB for payload blobs by default, and recommends offloading large payloads to object storage. citeturn8view1turn8view0  
- Step Functions’ payload quota is 256 KiB. citeturn5search6turn5search2  

Given those widely-used limits, a pragmatic internal threshold is often **32–256 KiB**, with a strong preference toward the lower end if the ledger is on hot paths and you want predictable latency and storage growth. The key is consistency and explicit enforcement, not the exact number. citeturn5search6turn8view1turn8view0

## Concurrency control and race conditions

### Use the ledger itself as the concurrency primitive

For your scenario (multiple workers potentially retrying the same execution simultaneously), the simplest “no distributed lock service” design is:

1. **Claim** the tool call by inserting a `STARTED` record with a unique key.  
2. If insert fails (duplicate key), load the existing record:
   - if `COMPLETED`, return cached result  
   - if `STARTED` and lease valid, wait/backoff/poll  
   - if `STARTED` and lease expired, attempt takeover with a conditional update  
3. Execute tool, then update record to `COMPLETED` (or `FAILED`).

MongoDB documentation explicitly warns that to avoid multiple upserts you should ensure the query fields are uniquely indexed; using `_id = key` is the strongest version of that practice. citeturn9view0

MongoDB also documents that single-document updates (e.g., `findAndModify`/`updateOne`) are atomic, which is the foundation that makes “claim and transition state” safe without a separate consensus lock system. citeturn9view0

In PostgreSQL, the same pattern is implemented using unique constraints plus `INSERT ... ON CONFLICT DO NOTHING` for claiming, with a subsequent `SELECT` to retrieve the winning record. This is the canonical relational idempotency-table pattern. citeturn3search0turn3search17

### Is Redis `SET NX` sufficient?

Redis documents the single-instance locking primitive pattern using `SET resource_name my_random_value NX PX <ttl>` and provides a safe-release Lua script that deletes the lock only if the stored value matches the expected token. This is the standard Redis-documented approach for mutual exclusion on a single Redis deployment. citeturn2search2turn2search5

However, there are two reasons it is usually better to avoid Redis locks as the *primary correctness mechanism* for your tool ledger:

- Redis HA deployments can lose acknowledged writes due to asynchronous replication (Redis Sentinel docs and multiple managed-Redis docs explicitly warn about this). citeturn3search10turn3search24  
- Distributed locking algorithms such as Redlock are debated; entity["people","Martin Kleppmann","distributed systems researcher"] provides a widely-cited critique highlighting failure modes and assumptions (clock accuracy, crash recovery) that are easy to get wrong. citeturn2search9turn2search2

Therefore, Redis locking is best treated as an optimization for load-smoothing, while the durable ledger store (MongoDB/Postgres) remains the system that definitively decides “has this tool_call_id been executed and committed?” citeturn3search10turn9view0

### Temporal-specific concurrency nuance

Even if you “expect” a single retry at a time, concurrency can still appear in practice when timeouts trigger a retry while a previous attempt is still running (for example, because heartbeats were not received). Temporal’s heartbeat and timeout model is explicitly designed to detect worker crashes and schedule retries, and heartbeat details can be read by a retried Activity. That makes “two attempts exist” a realistic operational mode your ledger should tolerate. citeturn10search2turn10search5turn0search9

## Failure modes, recovery, and alternatives to a separate ledger

### The hard truth: you can’t two-phase-commit most tool calls

If a tool call is “write to database A” + “call external API B,” you are facing the classic dual-write problem. Distributed transactions (2PC) across a database and an external service are often not available and frequently undesirable even when possible, due to coupling and operational impact. The transactional outbox pattern exists precisely to avoid that by writing an “intent/outbox record” in the same local transaction as your system-of-record update, then performing the external send asynchronously. citeturn4search0turn4search23

For your tool ledger, this implies: **don’t attempt 2PC** between “tool execution” and “ledger update” unless your tool is itself a local DB write inside the same database that hosts the ledger. Instead, treat the ledger as one layer in a defense-in-depth stack and rely heavily on external idempotency keys and/or domain-level idempotency. citeturn0search30turn4search2turn11view0

### What happens if the ledger write succeeds but tool execution fails?

This is why a `STARTED/COMPLETED/FAILED` state machine (plus leases) matters. A `STARTED` record should not be interpreted as “side effect definitely happened,” only as “someone is attempting it.” If the attempt fails before the external side effect, it should be safe to retry and eventually transition to `COMPLETED`. citeturn11view0turn0search16

If the attempt fails *after* the external side effect but before returning success (the worst case), you are back to ambiguity. This is exactly the scenario server-side idempotency keys are designed to address: the external service remembers the first outcome and returns the same outcome for retries. Stripe’s documentation is explicit that for a given idempotency key it saves and replays the first response (status code and body), even if the first response was an error. citeturn4search2turn4search28

### What happens if tool execution succeeds but ledger write fails?

This is another “ambiguous completion” scenario. A durable ledger reduces your exposure, but it cannot eliminate ambiguity if the write to the ledger fails after the side effect has occurred. This again motivates “idempotency keys at the external system boundary” as the most load-bearing protection for critical operations like payments. citeturn0search30turn4search2

### Can Temporal features replace the ledger?

Temporal’s `SideEffect` is frequently misunderstood in this context. Side effects in Temporal workflows are for *non-deterministic computations* inside workflow code (e.g., generating a UUID) while maintaining determinism by recording the result in workflow history; they do not magically make external API side effects exactly-once. Temporal docs describe `SideEffect` as storing results in workflow history and not re-executing on replay, which is valuable for determinism, not for external I/O that happens outside the workflow thread. citeturn4search6turn4search3turn4search10

Temporal does provide tools to reduce rework (for example, heartbeating progress and reading heartbeat details on retry), which helps you resume long-running Activities without repeating internal computation. But it does not eliminate the need for idempotency around external side effects if an Activity crashes after performing the side effect. citeturn0search1turn10search5turn0search9

A legitimately different Temporal-centric alternative is architectural: model each tool call as its own Activity (or child workflow) with narrowly-scoped retries and explicit idempotency keys, rather than executing “many tools” inside a single large Activity that Temporal retries as a unit. This reduces the blast radius of a retry and aligns retry semantics with tool boundaries, but it can increase orchestration overhead and still requires idempotent tool execution. citeturn0search0turn10search4turn7search6

### Can LangGraph features replace the ledger?

LangGraph can avoid repeating *completed tasks* when resuming a run if side effects are encapsulated inside tasks and durability is configured appropriately; yet LangGraph explicitly warns that in `"async"` durability mode there is a small risk of not writing checkpoints if the process crashes, and that if a task starts but does not complete successfully it can be re-run on resumption. LangGraph documentation therefore still recommends idempotent operations and idempotency keys for side effects. citeturn11view0turn6search2

In other words: LangGraph reduces duplication when the framework successfully records outcomes, but it does not eliminate the window where a side effect happened and a crash prevented the outcome from being recorded. Your tool ledger is specifically designed to narrow or close that window. citeturn11view0turn6search1

## Implementation patterns with concrete code sketches

### MongoDB-first ledger with lease-based claiming (Python)

The following sketch illustrates the “insert-to-claim” approach with a takeover lease. It relies on MongoDB’s atomic single-document updates and unique keys for correctness. citeturn9view0turn5search7turn2search7

```python
import hashlib
import json
import os
import time
from dataclasses import dataclass
from datetime import datetime, timedelta, timezone
from typing import Any, Optional, Tuple

from pymongo import MongoClient, ReturnDocument
from pymongo.collection import Collection
from pymongo.errors import DuplicateKeyError

UTC = timezone.utc

def sha256_json(obj: Any) -> str:
    payload = json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=False)
    return hashlib.sha256(payload.encode("utf-8")).hexdigest()

@dataclass(frozen=True)
class ClaimResult:
    status: str                     # "EXECUTE" | "CACHED" | "WAIT"
    cached_result: Optional[Any] = None
    conflict: Optional[str] = None  # diagnostic reason

class ToolLedger:
    """
    MongoDB-backed tool ledger.

    Collection design:
      - _id = "{execution_id}:{tool_call_id}" (unique by definition)
      - status: STARTED/COMPLETED/FAILED
      - lease_expires_at: used to recover from crashed workers
      - expires_at: TTL index target datetime
    """

    def __init__(self, collection: Collection, *, worker_id: str):
        self.col = collection
        self.worker_id = worker_id

    def claim_or_get(
        self,
        key: str,
        tool_name: str,
        args: Any,
        *,
        ttl: timedelta,
        lease: timedelta = timedelta(seconds=60),
        now: Optional[datetime] = None,
    ) -> ClaimResult:
        now = now or datetime.now(UTC)
        args_hash = sha256_json(args)

        # 1) Fast path: completed record exists
        doc = self.col.find_one({"_id": key}, projection={"status": 1, "args_hash": 1, "result_inline": 1})
        if doc and doc.get("status") == "COMPLETED":
            if doc.get("args_hash") != args_hash:
                return ClaimResult(status="WAIT", conflict="args_hash_mismatch_completed")
            return ClaimResult(status="CACHED", cached_result=doc.get("result_inline"))

        # 2) Try to claim by insert (atomic via unique _id)
        expires_at = now + ttl
        lease_expires_at = now + lease
        record = {
            "_id": key,
            "tool_name": tool_name,
            "args_hash": args_hash,
            "status": "STARTED",
            "owner_id": self.worker_id,
            "lease_expires_at": lease_expires_at,
            "created_at": now,
            "updated_at": now,
            "expires_at": expires_at,  # TTL index should be built on this field
        }
        try:
            self.col.insert_one(record)
            return ClaimResult(status="EXECUTE")
        except DuplicateKeyError:
            pass  # someone else won the claim

        # 3) Someone else has the record: check whether we should wait or take over
        doc = self.col.find_one({"_id": key})
        if not doc:
            # Extremely rare: deleted between operations (TTL thread) or transient read issue.
            return ClaimResult(status="WAIT", conflict="missing_after_duplicate")

        if doc.get("args_hash") != args_hash:
            return ClaimResult(status="WAIT", conflict="args_hash_mismatch_existing")

        if doc.get("status") == "COMPLETED":
            return ClaimResult(status="CACHED", cached_result=doc.get("result_inline"))

        # 4) Lease takeover if stale
        if doc.get("lease_expires_at") and doc["lease_expires_at"] < now:
            taken = self.col.find_one_and_update(
                {"_id": key, "status": "STARTED", "lease_expires_at": {"$lt": now}},
                {"$set": {"owner_id": self.worker_id, "lease_expires_at": now + lease, "updated_at": now}},
                return_document=ReturnDocument.AFTER,
            )
            if taken and taken.get("owner_id") == self.worker_id:
                return ClaimResult(status="EXECUTE")

        # Otherwise: someone else is in progress
        return ClaimResult(status="WAIT", conflict="in_progress_other_worker")

    def complete(
        self,
        key: str,
        result_inline: Any,
        *,
        now: Optional[datetime] = None,
    ) -> None:
        now = now or datetime.now(UTC)
        updated = self.col.update_one(
            {"_id": key, "status": "STARTED", "owner_id": self.worker_id},
            {"$set": {"status": "COMPLETED", "result_inline": result_inline, "updated_at": now, "completed_at": now}},
        )
        if updated.matched_count != 1:
            raise RuntimeError(f"Failed to mark COMPLETED for key={key} (lost claim?)")
```

This pattern uses MongoDB as both the dedupe ledger and the concurrency control mechanism (via unique key claims and atomic updates). MongoDB documentation highlights the importance of unique indexing to avoid multiple upserts and confirms atomic single-document updates, which are the key correctness properties used above. citeturn9view0turn3search9

### Redis lock as an optional optimization (Python)

If you want to reduce DB contention during bursts, you can layer a short lock using Redis’ documented `SET ... NX PX` pattern, but keep MongoDB as the source of truth. Redis documentation provides the safe-release script pattern using a unique random token. citeturn2search2

```python
import uuid
import redis

def try_lock(r: redis.Redis, lock_key: str, ttl_ms: int) -> tuple[bool, str]:
    token = str(uuid.uuid4())
    ok = r.set(lock_key, token, nx=True, px=ttl_ms)
```

## Key pitfalls to avoid

A ledger keyed only by `{execution_id}:{tool_call_id}` is only correct if `tool_call_id` is stable across retries/resumes. If a retry path can re-prompt the model and generate *new* tool_call_ids, then idempotency must be anchored to a stable business key (or to a stable tool invocation ID persisted in state) rather than an ephemeral model output. This is a direct consequence of LangGraph’s replay model and its warning that resumption may replay code from a starting point, combined with its recommendation to use idempotency keys to prevent duplication. citeturn11view0turn6search2

Using Redis-only as the ledger store for critical side effects is a common failure mode: even with AOF, Redis’ documented durability settings permit data loss under some policies, and Redis HA deployments can lose acknowledged writes because replication is asynchronous. If your ledger disappears, your system will behave as if the tool call never happened. citeturn2search0turn3search10turn3search24

Storing large results inline will eventually collide with platform limits (Temporal payload limits, Step Functions 256 KiB quota, MongoDB 16 MiB document limit). Industry patterns strongly favor storing large payloads externally and passing references, and Temporal documentation explicitly recommends offloading large payloads to an object store. citeturn8view0turn5search6turn5search7

Finally, avoid designing around “2PC between tool and ledger” for external APIs. Distributed transactions across heterogeneous systems are often not viable; patterns like transactional outbox and sagas exist precisely because atomic multi-system commits are unreliable and operationally expensive. citeturn4search0turn4search1turn4search12
