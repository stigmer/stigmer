Below is a “builder’s map” for honestly positioning **Stigmer as a Durable Agentic Workflow platform** (and for actually earning that claim technically). I’m going to be very specific about *what durability means once you add agents*, where the real failure modes hide, what Stigmer already has, and what you still need to build so the “set it and forget it” promise holds for **weeks/months** workflows that include **agent tasks**.

## 1) What “durable” means for agentic systems

Temporal’s definition of durability is basically: *the workflow always makes forward progress to completion (or a terminal state), surviving restarts, crashes, and time*. That works great for “normal” workflows.

For **agentic** workflows, the word “durable” needs to expand from “workflow state survives” into **a multi-layer contract**, because agents are (a) non-deterministic, (b) long-running, (c) tool-and-event heavy, and (d) extremely side-effect prone.

### A practical definition you can claim as “Durable Agentic Workflows”

A platform deserves the label **durable agentic workflows** when it can guarantee all of the following:

1. **Durable orchestration (workflow-level)**

   * The workflow’s control flow and state survive crashes/deployments and can wait months without consuming worker resources.
   * This is Temporal’s core promise.

2. **Durable agent sessions (agent-level)**

   * An agent task can be **resumed** after a crash *without losing progress*, including after long idle periods (e.g., “pause for approval, resume two weeks later”).
   * This is *not automatically true* just because you run LangGraph inside an Activity. You need a resume strategy.

   LangGraph’s docs explicitly frame durable execution as “save progress at key points so you can pause and later resume exactly where you left off,” and note that using a checkpointer enables pause/resume even after long delays (like a week). They also warn you to design for determinism/idempotency and wrap side effects inside tasks. ([LangChain Docs][1])

3. **Durable side effects (tool-level)**

   * If an agent calls tools that mutate the world (create ticket, send email, write DB, deploy code), retries *must not cause duplicate business effects*.
   * Temporal strongly recommends Activities be idempotent because they may execute more than once; idempotency keys are a core practice. ([Temporal Docs][2])

4. **Durable event intake (ingress-level)**

   * External events (webhooks, human decisions, upstream systems) must be correlated, deduped, and race-proof.
   * Use primitives like **Signal-With-Start** (atomic “start if missing + signal”) to avoid “workflow not found yet” races. ([Temporal Docs][3])
   * Also: Signals can be duplicated in rare cases, so handlers must be idempotent. ([Temporal][4])

5. **Durable operations over time (ops-level)**

   * Safe deploys and upgrades while workflows are running for months.
   * Temporal’s newer Worker Versioning is explicitly about deploying changes “without breaking running workflows” and includes **workflow pinning** so an execution stays on the worker version it started on. ([Temporal Docs][5])

If you only have (1) (Temporal) + “agents run somewhere,” you’re *durable orchestration with agent steps*. To claim the **category**, you want all five layers.

## 2) State of the art: how production systems do long-running agentic workflows

There are a few “winning” patterns emerging in production.

### Pattern A: “Workflows orchestrate; agents run as Activities”

This is the most common: Temporal runs the durable workflow, and each agent invocation happens inside an Activity.

Temporal and OpenAI’s Agents SDK integration is literally built around this idea: *each agent invocation is executed through a Temporal Activity*, and the orchestration runs as a Workflow, giving durability and retries “under the covers.” ([Temporal][6])

**Why teams do it:**

* Temporal Workflows stay deterministic and don’t call the model directly.
* Activities can be non-deterministic and retried safely.
* Scaling is easier because Activities are just tasks on a queue.

**What’s missing unless you add it:** “resume mid-agent-run,” “pause agent for weeks,” and “no duplicate tool side effects.”

---

### Pattern B: “Agents as long-running workflows” (actor model)

Another production pattern: implement each agent as a long-running Workflow that holds state and reacts to Signals/Queries—very actor-like.

Temporal’s “ambient agents” writeup uses this pattern:

* Each major agent is implemented as a long-running Workflow that maintains state and waits for Signals (actor model).
* Temporal Schedules can “nudge” agents periodically.
* Signals/queries become the inter-agent communication fabric. ([Temporal][7])

**Why teams do it:**

* Great for always-on agents, inbox-style behavior, or anything that looks like “a durable service with memory.”

**Cost/tradeoff:**

* You need clear boundaries for what runs as workflow vs activity.
* You still need idempotency and history management.

---

### Pattern C: “Durable tools” (make tool execution durable, not just the agent)

Temporal’s AI Cookbook shows the “Durable MCP tool” pattern:

* MCP tools are thin wrappers that start a Temporal Workflow.
* Business logic runs in Temporal workflows, and external API calls happen in Activities. ([Temporal Docs][8])

This approach is also highlighted as a way to make MCP tools durable and scalable (thin stateless MCP server, Temporal does the hard parts). ([Temporal][9])

**Why this matters for Stigmer:**
If Stigmer agents call MCP tools directly and an agent Activity retries, you can get duplicated tool calls unless you build idempotency. Durable tools is one clean way to solve that.

---

### Real-world “why Temporal” story: Grid Dynamics

Temporal published a case study where Grid Dynamics built a deep research agent with LangGraph, ran into production issues (error handling/retries, state lifecycle, scaling costs, and human-in-the-loop waiting), and migrated to Temporal. They specifically call out brittleness around manual state and “exactly-once” challenges when using Kafka/executors. ([Temporal][10])

This is basically your positioning thesis in the wild: “agents in prod need durable systems discipline.”

---

### Competitive durable-execution engines now targeting agents

Besides Temporal, there’s a cluster of “durable execution” engines positioning directly at AI agents:

* **Restate**: markets “durable agents and workflows,” claiming it persists steps (LLM calls/tools), recovers progress, and suspends long-running agents when idle. ([docs.restate.dev][11])
* **Trigger.dev**: has a checkpoint/resume system (“durable execution”) for long-running tasks in TS/JS. ([trigger.dev][12])
* **Inngest**: frames “durable execution” for background jobs/steps, including AI flows. ([inngest.com][13])
* **DBOS**: “durable execution” built on Postgres; shows patterns for crashproof AI agents with LangGraph. ([dbos.dev][14])
* **Hatchet**: markets orchestration/durable execution for agentic pipelines. ([github.com][15])

The key: lots of folks are claiming durability for agents now — which means **your bar for “truthful category ownership” is rising**. You’ll want very crisp guarantees and a concrete technical story.

## 3) Temporal + LangGraph integration patterns that actually hold up for weeks/months

You’re already using the right base architecture. The durability gap is almost entirely in the **boundary** between “Temporal durable workflow” and “LangGraph agent run.”

Here are the practical patterns you’ll want to standardize in Stigmer.

---

### Pattern 1: Treat agent execution as an Activity, but heartbeat + resume from checkpoint

If an agent run can take minutes/hours, you need Temporal **Activity heartbeats**.

Temporal recommends:

* Always set Start-To-Close (or Schedule-To-Close) timeouts.
* For long-running Activities, also use Heartbeats + Heartbeat Timeout. ([Temporal Docs][16])

Crucially: heartbeats can include **custom progress info** that you can read on retry. ([Temporal Docs][16])

**Concrete Stigmer design:**

* Each Agent Task Activity should heartbeat after each LangGraph “super-step” or after each tool call with:

  * `thread_id`
  * `checkpoint_id` (or last checkpoint timestamp/version)
  * current node / step index
  * optional “tool call dedupe keys seen so far”
* On retry, Activity reads last heartbeat detail and resumes LangGraph from that checkpoint (instead of restarting).

This is the cleanest way to make “multi-hour agent tasks” *actually durable* and cheaper (no re-burning tokens).

---

### Pattern 2: Don’t let an Activity “wait weeks”

Temporal’s “no resources while waiting” promise is a Workflow-level feature (timers, signals). If you keep an Activity running while “waiting for approval,” you break the promise.

So if LangGraph hits an interrupt / needs human input:

**Recommended Stigmer pattern:**

1. Agent Activity runs LangGraph until it reaches a “needs input” interrupt.
2. Activity returns a structured result like:

   * `status: NEEDS_INPUT`
   * `thread_id`
   * `checkpoint_id`
   * `prompt_for_human`
   * a schema for expected human response
3. Temporal Workflow transitions into a durable wait (`Listen` task / approval task).
4. When input arrives (Signal/Update), Workflow calls Agent Activity again with `(thread_id, checkpoint_id, human_input)`.

This is where LangGraph’s persistence model (threads + checkpoints) is perfect: you keep state in a durable store and resume later. ([LangChain Docs][17])

**This one adapter is the difference between:**

* “Durable workflow that calls agents”
* and “Durable agentic workflows you can leave running for months”

---

### Pattern 3: Decide your retry boundary intentionally

A tricky production choice: **what is the unit of retry**?

Some teams retry the entire agent run as one atomic unit (simpler coherence). Others retry per step.

Anup Jadhav’s Jan 2026 writeup (very aligned with your architecture) recommends running the whole LangGraph execution inside a single Temporal Activity and using heartbeats/timeouts, noting that partial retries can create inconsistent mixed outputs. ([anup.io][18])

**Stigmer takeaway:** support both modes:

* **Atomic agent run** (simple): good when agent output must be coherent as one attempt.
* **Checkpoint-resumable agent session** (durable + pause/resume): required for long runs and human-in-loop pauses.

Make it a per-agent-task policy:

* `retry_mode: atomic | resumable`
* `max_runtime_per_slice: 5m | 30m | 2h` (for resumable “timeslicing”)

---

### Pattern 4: Never pass huge agent state through Temporal payloads

Temporal persists Activity args/results in workflow history. That creates strict limits and performance issues.

* Workflow history has hard limits; it warns after **10,240 events / 10MB** and errors at **51,200 events / 50MB**. ([Temporal Docs][19])
* Payload/blob size has its own limits; self-hosted defaults warn at **256KB** and error at **2MB**. ([Temporal Docs][20])

Your **Claim Check** implementation is exactly the right move here.

**But for agent sessions specifically:**

* Don’t serialize full LangGraph state into Temporal workflow state if it grows.
* Prefer storing agent state in LangGraph checkpointer store (thread checkpoints) and passing only `thread_id`/refs in Temporal history.

This keeps Temporal history small while still being “durable.”

---

### Pattern 5: Idempotency is non-negotiable for tools

Temporal Activities are “at least once” by default, so tool calls can repeat unless you design for idempotency. Temporal docs explicitly recommend Activities be idempotent. ([Temporal Docs][2])

Temporal’s own idempotency guidance calls out idempotency keys as a key practice. ([Temporal][21])

**For agentic systems this is extra important** because retries + nondeterminism can otherwise produce “double actions” (duplicate tickets, duplicate emails, duplicated DB writes).

Stigmer needs a first-class story here (more in the gap analysis).

## 4) Long-running workflow patterns for weeks/months with many agent invocations

Here’s how “durable for months” typically breaks, and the patterns to prevent it.

---

### A. History growth management (you already did most of it)

You already implemented:

* Continue-as-new automation near ~10k events.
* Claim check for large payloads.

That’s precisely aligned with Temporal’s own history limits/warnings. ([Temporal Docs][19])

**One nuance for agentic workloads:**

* If you start emitting “fine-grained agent events” into workflow history (every tool call, every thought), you’ll blow history fast.
* Prefer: store rich agent traces in your own datastore (or external trace system), and store only *summary references* in workflow history.

---

### B. Multi-agent across long waits: make “handoff context” explicit

Example: Agent A completes → workflow waits 2 weeks → Agent B starts.

To make this durable:

* Store Agent A output as an immutable artifact:

  * either in claim-check storage (R2/filesystem) or your own artifact store
  * include stable IDs + content hashes
* In workflow state, keep only small refs to those artifacts.
* When Agent B starts, it loads refs, not huge payload blobs.

**Bonus:**

* This enables audit and “replay in a new run” without dragging huge state through Temporal.

---

### C. Human-in-the-loop: use workflow waits, not agent waits

Between agents, human tasks are best modeled as:

* Create a `HumanTask` record (assignment, due date, escalation policy)
* Workflow waits on signal/update for completion
* Timers enforce deadlines/escalations
* Continue-as-new trims history periodically if the inbox is noisy

Your current “approval gate” is the simplest version. To be durable for months in real orgs, you’ll want the full “task lifecycle” (below).

---

### D. External events: “Signal-With-Start + dedupe”

If workflows are driven by webhooks/CDC/events, you need:

* race-proof delivery (start workflow if not exists, and signal it atomically) → Signal-With-Start ([Temporal Docs][3])
* dedupe / idempotency for repeated events (Temporal itself notes signals can be duplicated rarely) ([Temporal][4])
* correlation keys to route events to the correct workflow instance

This is one of the biggest “durability gaps” for automation systems at scale.

---

### E. Safe deploys for month-long workflows: worker versioning/pinning

If you deploy weekly but workflows last months, you need a compatibility strategy.

Temporal Worker Versioning exists for this exact problem and introduces **workflow pinning** (each execution completes on the worker deployment version where it started). ([Temporal Docs][5])

For Stigmer specifically (because your workflows are declared and interpreted):

* you still need to guarantee replay safety of the workflow engine and task semantics
* and you need a way to ensure old workflows keep running even as the interpreter evolves

This is a major “real durability” requirement that many agent platforms skip.

## 5) Gap analysis for Stigmer: what you still need beyond Temporal + LangGraph

You already have a strong durability base:

* Continue-as-new automation
* Claim check
* Search attributes
* Signal/update waiting semantics

Now, the remaining gaps fall into two buckets:

1. **Platform durability basics** you listed (human tasks, signal-with-start, lifecycle controls, etc.)
2. **Agent-specific durability gaps at the Temporal↔LangGraph boundary** (the critical category-defining ones)

### A. Agent-specific durability gaps (high priority)

#### Gap A1: “Durable agent session” semantics across crashes and long pauses

If your agent task is just “Temporal Activity → run LangGraph → return output” then:

* If worker crashes at minute 29 of a 30-minute agent run:

  * Temporal will retry the activity (good),
  * but unless you resume LangGraph from checkpoint, you redo work and may duplicate side effects.

What you need:

* Heartbeat + checkpoint resume mapping (Temporal heartbeat details → LangGraph checkpoint resume). ([Temporal Docs][16])
* And the “agent interrupt → workflow wait → agent resume” adapter (so the system can wait weeks without an activity running). ([LangChain Docs][1])

This is the **single most important feature** for truthfully claiming “durable agentic workflows,” because it’s where “set it and forget it” usually breaks in agent systems.

---

#### Gap A2: Tool idempotency / durable tools

Temporal recommends Activities be idempotent because they can execute multiple times. ([Temporal Docs][2])

Agentic systems call tools constantly, and many tools have side effects. So you need one of:

* **Idempotency keys + tool call ledger**

  * Every tool call gets a deterministic idempotency key derived from:

    * `(workflow_execution_id, agent_task_id, tool_name, tool_call_index)`
  * Store tool call outcomes in a durable ledger
  * On retry, return the stored result instead of executing again

or

* **Durable tools pattern (MCP tools as Temporal workflows)**

  * Temporal’s MCP cookbook shows tools as thin wrappers that start workflows, with external calls in Activities. ([Temporal Docs][8])

Stigmer already leans into MCP; “durable MCP tools” is a very on-brand extension.

---

#### Gap A3: Cancellation / pause propagation into agent runs

To be a workflow platform (not just a runner), Stigmer needs:

* pause/resume/cancel at the workflow level
* and *propagation* into agent execution (stop tool calls, stop LLM loops, persist checkpoint, exit cleanly)

This becomes critical for month-long workflows where humans will pause/cancel as org context changes.

---

### B. Platform durability gaps (many you already identified)

#### Gap B1: Signal-With-Start

This is your “race-proof delivery” primitive for event-driven workflows. ([Temporal Docs][3])
Without it, you’ll get the classic bug: *webhook arrives, tries to signal workflow, workflow isn’t started yet, event is lost or needs weird retries.*

---

#### Gap B2: Event correlation + dedupe infrastructure

This is bigger than it sounds:

* you need an ingress gateway strategy
* correlation IDs
* dedupe store
* replay safety when duplicates occur

Temporal notes that signals can be duplicated in rare cases, which reinforces that you can’t ignore idempotency at the messaging layer. ([Temporal][4])

---

#### Gap B3: Human task management beyond “approval”

Real long-running workflows need:

* assignments (user/team)
* SLAs (due date)
* escalation paths
* reassignment
* “inbox” views + integrations (Slack/Email/Jira)

Durability isn’t just “wait”; it’s “wait *with governance*.”

---

#### Gap B4: Workflow versioning + safe upgrades

You called this out, and I’d underline it: if you want credibility with platform engineers, you need a story for “workflows survive deploys.”

Temporal’s Worker Versioning + pinning is designed for this. ([Temporal Docs][5])

At the Stigmer layer you likely also need:

* pin workflow definition version per execution
* pin agent definition versions per execution
* explicit “migrate” controls

---

#### Gap B5: Saga/compensation semantics

Temporal publishes saga/compensation guidance and patterns. ([Temporal][22])
In agentic workflows, compensations matter a lot because agents perform side effects earlier (create resources) then fail later (compliance rejection, human disapproval).

Your try/catch exists; what’s missing is:

* a compensation stack with deterministic rollback order
* clear “what gets compensated” semantics
* idempotent compensations

---

#### Gap B6: Wait semantics in your proto

Temporal can wait months; your executor supports richer durations; but your proto caps to int32 seconds.

To claim “weeks/months,” your API surface needs:

* ISO 8601 durations
* “wait until timestamp”
* optional business calendars

Otherwise users can *technically* do it but your product surface contradicts your positioning.

## 6) Implementation roadmap: what to build (prioritized)

Here’s a pragmatic roadmap focused on making the “durable agentic workflow” claim *true* as fast as possible.

### Phase 0: Make agent steps genuinely durable (category-defining)

1. **Agent Session Runtime**

   * Introduce a stable `agent_session_id` (LangGraph `thread_id`) per agent invocation.
   * Store it in workflow state and search attributes.

2. **Agent Activity heartbeats + resume**

   * Heartbeat each super-step/tool-call with `{thread_id, checkpoint_id, step}`.
   * On retry, resume from heartbeat details. ([Temporal Docs][16])

3. **Agent interrupt → Workflow wait → Agent resume**

   * Translate LangGraph “needs human input / external event” into a workflow-level wait.
   * Resume agent after signal/update using the same thread/checkpoint.

4. **Tool idempotency policy**

   * Either:

     * implement a tool-call ledger + idempotency key standard (recommended baseline), or
     * implement “durable tools” for MCP for side-effect-heavy tools. ([Temporal Docs][8])

**What you can claim after Phase 0:**
“Agent tasks resume after crashes and long pauses without losing progress; tool side effects are protected from retries.”

That’s *the* durable agentic leap.

---

### Phase 1: Make “set it and forget it” real for end users

5. **User-facing lifecycle APIs/CLI**

   * cancel, terminate
   * pause/resume (and explicit `EXECUTION_PAUSED`)
   * retry last failed step
   * inspect current phase + last agent session

6. **Signal-With-Start**

   * Implement it in your ingress layer. ([Temporal Docs][3])

7. **Event correlation + dedupe service**

   * Ingress gateway that:

     * normalizes events
     * attaches correlation keys
     * dedupes by `(source,event_id)`
     * routes via Signal-With-Start
   * Keep workflow handler idempotent. ([Temporal][4])

8. **Wait semantics upgrade in proto**

   * ISO 8601 durations, timestamps, optional calendars.

---

### Phase 2: Enterprise-grade durability patterns

9. **Human task system**

   * assignments, due dates, escalations, reassignment
   * inbox integration hooks (Slack/Email/Jira)

10. **Compensation stack / Saga semantics**

* Build “register compensation” and “execute compensations on failure/cancel” primitives.
* Follow Temporal saga guidance (compensating actions). ([Temporal][22])

11. **Workflow + agent definition version pinning**

* Every workflow run stores:

  * workflow definition version/hash
  * agent spec versions used
  * tool versions (or MCP server version)
* Add “migrate run to new version” controls.

12. **Worker versioning strategy**

* Integrate or document how Stigmer users safely deploy updates for long-running workflows.
* Use Temporal Worker Versioning / pinning where appropriate. ([Temporal Docs][5])

---

### Phase 3: Differentiators that reinforce the category

13. **Durable MCP tools as a first-class mode**

* Provide a “tool execution mode” toggle:

  * `inline` (inside agent activity with idempotency ledger)
  * `durable` (tool call starts Temporal workflow; full audit trail) ([Temporal Docs][8])

14. **Proactive schedules**

* If you want “ambient” / always-on workflows, consider exposing Temporal schedules patterns. ([Temporal][7])

15. **First-class audit + trace UX**

* Unified view: workflow timeline + agent sessions + tool calls + human tasks
* Keep Temporal history lean; store rich traces externally.

## 7) Messaging: how to communicate “durable agentic workflows” credibly

Here’s how to message this to platform engineers without over-claiming.

### The core narrative (platform engineer-friendly)

* **“Agents are distributed systems.”**
  They call flaky APIs, hit rate limits, wait on humans, and run for a long time. Production reliability isn’t optional.

* **“Temporal gives you durable orchestration; LangGraph gives you agent logic.”**
  Stigmer makes them work together as one product.

You can even point to industry evidence:

* Temporal + OpenAI Agents SDK integration explicitly positions “Durable Execution for agents” by executing agent invocations as Activities. ([Temporal][6])
* Grid Dynamics’ case study shows why LangGraph-only approaches ran into durability/lifecycle issues and why they moved to Temporal. ([Temporal][10])

### What “durable” means in your product language

Avoid vague marketing. Use concrete, testable claims:

* “Workflows survive restarts, deploys, and long waits.”
* “Agent tasks heartbeat and resume from checkpoints after failure.”
* “Tool calls are protected with idempotency keys (no duplicate tickets/emails).”
* “External events are deduped and delivered race-free via Signal-With-Start.”
* “Full audit trail: every agent run + tool call + human decision is traceable.”

### Your hero statement, tightened

Your existing hero line is strong:

> **AI automations fail. Stigmer makes them durable.**

Add a second sentence that makes it *real*:

> “Start an agentic workflow, walk away for weeks, and it resumes exactly where it left off—even after crashes or deploys.”

(Once Phase 0 is done, that’s an honest statement.)

### Category boundary: how you’re different from “agent frameworks” and “workflow engines”

* **Agent frameworks** (CrewAI/AutoGen/etc): great at reasoning/tool calling, weak at months-long durability + retries + ops.
* **Workflow engines** (Temporal alone): durable, but agents are just generic activities—no agent spec, MCP integration, agent session UX.
* **Stigmer**: **agent-native + workflow-durable**, with explicit durability guarantees at the boundary (resume, idempotency, event dedupe).

---

## The bottom line

You already have the right foundation (Temporal durability + LangGraph execution + Continue-as-new + claim check).

To **legitimately own “Durable Agentic Workflows”** as a category, the key missing work is not more orchestration primitives—it’s making the **Temporal ↔ LangGraph boundary** durable in the way users actually experience:

* **resume agent progress after crashes** (heartbeats + checkpoint resume)
* **pause agent sessions for weeks** (interrupt → workflow wait → resume)
* **prevent duplicate tool side effects** (idempotency keys / durable tools)
* **race-proof, deduped event delivery** (Signal-With-Start + correlation)
