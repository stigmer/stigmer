## Decisions Made

### Architecture: `FollowUpFn` callback over state enum

The revised plan proposed three named states (Streaming/WaitingForInput/UserTyping). During implementation, a single `inputActive bool` flag proved cleaner and more Bubble Tea-idiomatic — the textarea component manages its own focus state internally. This keeps the new code minimal and avoids a state enum that would require changes in every dispatch function.

### Key routing: `inputActive` as priority gate

When `inputActive`, the textarea captures all keys except Ctrl+C (which always quits). This is a narrow, clean addition to `handleKeyPress` — the existing handlers (cancel, help, approval, navigation) are completely untouched when `inputActive` is false. The `q` quit key is separated from Ctrl+C specifically so the textarea can type `q` without accidentally quitting.

### All terminal phases activate input

The plan said "activate input on completion." Decision: apply to failed/cancelled too. This matches how tools like Claude Code work — a failed execution doesn't mean the session is over. The user can say "that failed because X, try Y instead." StreamErrorEvent (infrastructure failure) remains terminal — the user can't fix a disconnected stream by sending a message.

### Artifact download stays single-execution for MVP

`draft_skill_handler.go` downloads artifacts from the first execution only. Session-level artifact tracking (which execution produced what?) would require deciding whether to merge, replace, or present all artifacts — a product design question deferred to a future iteration.

### `FollowUpFn` only when `sessionID != ""`

Conversational mode is gated on having a valid session ID. This prevents the follow-up path from activating in edge cases where the backend didn't return a session ID (the defensive `log.Warn()` path in Phase 1).

### Mutable channel layer (`activeEvents`, `activeApprovals`, `activeCancelFn`)

The immutable `cfg` holds the initial execution's channels. Follow-ups swap these mutable fields. The `approval.go` change (`m.activeApprovals` instead of `m.cfg.ApprovalResponses`) was the one subtle correctness fix needed — without it, an approval response after a follow-up would go to the original execution's channel, which no one is reading.

## Learnings

- Bubble Tea's value types (not pointers) mean all state must be returned by value — the mutable channel swap requires explicit field assignment, not pointer mutation
- The `textarea` component in `bubbles` needs `SetWidth` called explicitly; it doesn't inherit width from the parent layout automatically
- `streamClosedMsg` arriving after `DoneEvent` is expected and correct — the gRPC goroutine closes the events channel after sending `DoneEvent`, which triggers `streamClosedMsg`. The `inputActive` guard prevents this from being treated as an error
- The `handleWindowSize` path runs before the first frame and on every resize — all height calculations must account for `hasInputArea()` consistently

## Open Questions for Phase 3

1. **Bidirectional gRPC vs separate `RespondToQuestion` RPC** — this is the first decision needed before starting Phase 3. The approval channel pattern (unary, separate from stream) suggests a separate RPC is idiomatic for this codebase.

2. **Input routing when both approval and ask-user are active** — if an agent asks a question AND a tool is waiting for approval at the same moment, which takes priority? The approval channel is currently a blocker (the gRPC goroutine blocks waiting for it) — this could deadlock with a concurrent AskUser.

3. **Non-interactive timeout behavior** — what does the CLI send to the backend if the user doesn't respond to an AskUser event in non-interactive mode?
