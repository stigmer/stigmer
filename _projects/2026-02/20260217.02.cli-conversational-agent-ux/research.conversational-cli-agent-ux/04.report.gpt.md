# Deep Research: Conversational Agent UX in CLI Tools

## Problem framing and terminology

A “conversational CLI agent” has two parallel realities: (1) the internal orchestration layer (“requests,” “tool calls,” “runs,” “turns,” state machines), and (2) the user’s mental model (“I’m chatting with an agent about my repo”). The best modern tools intentionally **collapse internal complexity into a single, continuous conversational surface**, while keeping recovery, auditability, and automation available via **progressive disclosure** (commands, history browsers, exports, logs, structured output). citeturn7view0turn4view0turn4view1turn9search0

Across current leading tools, the user-facing abstraction is rarely “execution.” Instead, it tends to be one of:
- **Session / conversation** (resumable chat threads, often scoped to a repo/working directory). citeturn4view1turn4view0turn4view3turn7view0  
- **Task** (a goal-scoped unit that contains conversation + tool steps + checkpoints, with history/search/resume). citeturn28view1turn12view1turn7view2  
- **Thread(s) tied to a terminal session** (multiple agent conversations can exist within a broader “terminal session” context). citeturn20view1turn20view0

This matters for **Stigmer’s** evolution, because your current model (“each CLI command = one backend execution”) is the opposite mapping: it forces the user to think in discrete runs, while the conversational tools make the user think in a **single continuity** (with sub-steps beneath). The core design question is therefore: **how to let multiple internal executions occur without rupturing the user’s “one conversation” mental model**—and without hiding critical safety controls. citeturn14view0turn7view0turn4view0turn24view0

### Claude Code CLI (conversation-first with deep recovery primitives)

**User-facing model:** Claude Code presents as an always-on conversational REPL (“interactive mode”), with user controls exposed as **slash commands** (for session control, permissions, model switching, rewind/restore, etc.) rather than as “run objects.” Its CLI also supports “print mode” for one-shot invocations (e.g., `-p`) and resume/continue flags that keep the conversation model intact. citeturn4view1turn4view0turn15view0

**Session vs. execution abstraction:** The abstraction is explicitly a **session** that can be resumed by ID or name (`/resume`, `--resume`, `--continue`), renamed (`/rename`), and forked (`--fork-session`). Importantly, these operations are framed as *conversation continuity*, not as backend job control. Claude Code does expose a **session identifier** at the CLI level (e.g., `--session-id` and resume-by-ID), but it is positioned as a *power feature for resumability*, not a primary UI element. citeturn4view0turn15view0

**Conversational flow patterns:**
- **Agent-initiated questions** and approvals are treated as first-class “needs input” events. In the underlying Agent SDK, these events can include both tool approvals and explicit “ask user” questions, routed through a callback; the UI’s job is to render a question/prompt and return the user’s decision/answer. citeturn3search25turn9search2  
- Claude Code adds a subtle “workflow coaching” layer: prompt suggestions appear in the input field, derived from the project’s recent git history and your conversation, and can be accepted inline. citeturn13view0

**Terminal UI patterns:**
- Claude Code distinguishes multiple “states” via interactive affordances: toggles for verbose output, a task list view, and embedded status interfaces. It supports **background bash commands**: when a command is backgrounded, Claude immediately returns a **background task ID**, allowing the conversation to continue while the task runs asynchronously; output can be retrieved later. This is a key example of *internal mechanics partially exposed*, but in a user-meaningful way (“this is a background task you can refer back to”), not as backend execution plumbing. citeturn13view0turn4view0

**Resumability and recovery:**
- Claude Code’s **checkpointing** is designed as “local undo with conversation continuity.” It creates a checkpoint prior to edits and supports a rewind menu (Esc Esc or `/rewind`) that can restore code + conversation, conversation-only, code-only, or summarize from a point. Checkpoints persist across sessions and are cleaned up with sessions after ~30 days (configurable). citeturn14view0  
- Notably, checkpoints **do not track bash-modified files**, which creates a boundary between “agent edits” and “shell side effects” that the UX must communicate. citeturn14view0

**Non-interactive / automation:**
- Print mode (`-p`) and options like JSON/streaming output formats enable scripting; Claude Code also includes flags to limit turns and control persistence (e.g., disabling session persistence in print mode). citeturn15view0

**Noise reduction / progressive disclosure:**
- Claude Code offers a “verbose output” toggle and keeps many internals behind explicit commands or views. It generally avoids surfacing lifecycle micro-events as “execution started/completed,” and instead makes state legible through the conversational surface plus discrete tools like `/status`, `/context`, `/cost`, and a task list. citeturn19view0turn4view0

### OpenAI Codex CLI (full-screen chat harness with explicit session IDs and a first-class resume/fork model)

**User-facing model:** Codex CLI is explicitly described as a conversational workflow in a **full-screen terminal UI**, where you can send prompts and “watch Codex explain its plan before making a change,” approving or rejecting steps inline. citeturn9search7turn18view0

**Session vs. execution abstraction:**
- Codex strongly adopts **sessions** as the user-facing object: it stores transcripts locally and supports `codex resume` with a picker (recent interactive sessions), plus `codex resume --last`, `--all`, and a direct `codex resume <SESSION_ID>`. citeturn4view3turn2search5  
- It also supports **forking** a previous session (`codex fork` and `/fork`), which is an explicit acknowledgment that “multiple internal executions” can be branches of the same user-facing thread. citeturn2search5turn2search21  
- Codex does expose a **session UUID** as a resumability handle; critically, the UX “softens” this by letting users primarily interact through a picker and only use the UUID when needed (copied from picker, `/status`, or session files). citeturn4view3turn9search16

**Approvals and permissions as a UX layer:**
- Codex documents a structured model of **sandbox levels + approval policies** (e.g., auto presets, read-only, workspace-write, “ask for approval” modes, plus a high-risk YOLO/bypass flag). This is a clear example of a tool treating “internal execution mechanics” (what tools can run, where, with what approvals) as an explicit UX dimension—but exposed as *policy*, not as a stream of low-level lifecycle events. citeturn9search1  
- The docs also emphasize that `/status` can show the active model, approval policy, writable roots, and token usage—again, a “state snapshot” pattern rather than verbose lifecycle spam. citeturn9search16

**Non-interactive / CI mode:**
- Codex has a dedicated **non-interactive mode** via `codex exec` for scripts/CI, meant to avoid opening the interactive TUI and to run with explicit sandbox/approval settings. citeturn9search0  
- Crucially, Codex supports resuming sessions even in automation flows (e.g., `codex exec resume --last ...`), which is directly relevant to Stigmer’s desire to treat multiple internal “executions” as a single user-facing continuity. citeturn4view3

**UI cues (from official screenshot):**
- The Codex splash screenshot shows a top “header” area with model + directory and a conversation body with a visible “Updated Plan” and checklist-style items, reinforcing the “plan-first, then execute” mental model. citeturn18view0

### GitHub Copilot CLI (session continuity, resumability, and queueing while thinking)

**User-facing model:** Copilot CLI explicitly supports an **interactive session** where you can “have a conversation,” steer direction with feedback, and perform one or more tasks; it also supports a programmatic one-shot mode with `-p/--prompt` that exits after completion. citeturn5view0turn6search1

**Session abstraction and persistence (not “executions”):**
- Copilot CLI supports resuming and continuing sessions via `--resume`, `/resume`, and `--continue` (most recently closed local session). citeturn6search1turn7view1  
- Its best-practices documentation describes “infinite sessions” with **automatic compaction** (summarization) and provides an explicit session storage layout in `~/.copilot/session-state/{session-id}/` (events JSONL, plan file, checkpoints, artifacts). This is a notable design: it hides internal API calls but makes the session “inspectable” for power users and tooling. citeturn7view0

**Agent-initiated questions and user steering while running:**
- Copilot CLI’s interactive interface includes **plan mode**: in plan mode it asks clarifying questions and builds an implementation plan before writing code. citeturn5view0turn6search1  
- Copilot CLI explicitly supports **steering while the agent is thinking**: you can send follow-ups mid-think, or queue additional instructions for after the current response completes. This is one of the clearest published examples of “streaming output alongside user input readiness.” citeturn5view1

**Tool approval UX and safety:**
- Copilot CLI offers layered approval controls: allow/deny specific shell commands, allow write tools, allow MCP server tools, and allow-all-tools. It explicitly warns that auto-approval increases risk, and recommends mitigation via restricted environments (VM/container) for headless operation. citeturn5view0  
- The CLI also has a `--no-ask-user` flag to disable the “ask_user” tool, which is a direct answer to the “agent asks a question in non-interactive mode” problem: one approach is to make interactive elicitation optionally unavailable in automation contexts. citeturn7view1

**UI cues (from official screenshot):**
- The Copilot CLI “welcome” screenshot shows a full-screen terminal UI with a **folder trust confirmation dialog** offering “Yes,” “Yes, and remember,” and “No (Esc).” This exemplifies a pattern: safety-critical gating is rendered as a dedicated modal-like interaction rather than interleaved in the transcript. citeturn16view0turn6search35

**Progressive disclosure for session internals:**
- Instead of surfacing low-level lifecycle states, Copilot CLI provides `/session` and `/session checkpoints` to view metadata and compaction checkpoints, and a `--silent` flag for scripting that outputs only the agent response. citeturn7view0turn7view1  
- Copilot CLI also supports sharing transcripts to Markdown or a secret gist, positioning session history as an artifact rather than a backend log. citeturn7view1

### Aider (classic terminal REPL, explicit file-scoping, and transcript-as-history)

**User-facing model:** Aider is a terminal-first pair-programmer with a conversational prompt loop and **in-chat slash commands** (e.g., `/add`, `/diff`, `/clear`, `/save`, `/undo`). It leans toward an “inline REPL” feel rather than a heavy full-screen multi-pane UI. citeturn8view2turn2search4

**Session abstraction:** Aider’s persistence model is closer to “transcript files” than “session objects.” It can write chat history to a Markdown file (`--chat-history-file`, default `.aider.chat.history.md`) and can optionally restore previous history (`--restore-chat-history`). This is an explicit example of a tool that *externalizes* the session abstraction into user-visible files rather than a hidden session database. citeturn8view0

**Conversational flow and questions:** Aider’s interaction model is heavily user-driven (you prompt; it proposes diffs; you accept). It supports multi-line input mechanisms and numerous in-chat commands, but it does not appear to emphasize agent-driven elicitation UI primitives the way plan-mode tools do; instead, it focuses on controlling context (add/drop files), diffs, and iterative edits. citeturn8view2turn2search23

**Non-interactive / CI usage:**
- Aider has a dedicated scripting mode: `--message` runs one instruction, applies edits, and exits; `--yes` can auto-confirm prompts in scripting contexts. citeturn8view1  
This maps neatly to Stigmer’s current “single-shot command” mode, and highlights the design challenge of adding conversational turns without breaking automation ergonomics. citeturn8view1

**Noise reduction and context control:**
- Aider provides explicit `/clear`, `/reset`, and token/context commands. Community feedback shows that “too much history in context” can become messy and costly, motivating finer-grained controls beyond “clear everything.” citeturn2search26turn8view2

### Cline CLI (task-based abstraction, explicit headless mode detection, and checkpoint-driven risk reduction)

**User-facing model:** Cline CLI provides two distinct experiences: an **interactive mode** (conversational, “feels like chatting,” with keyboard shortcuts and slash commands) and a **headless mode** (non-interactive, clean text/JSON output, designed for automation/CI). The mode can be auto-detected by whether stdin/stdout are TTYs or by flags. citeturn7view3turn7view2turn12view1

**Session vs. execution abstraction:**
- Cline’s dominant abstraction is the **task**: “self-contained sessions that capture your conversations, code changes, command executions, and decisions,” each with a unique identifier and storage directory, resumable across sessions. citeturn28view1turn27search3  
- This is unusually aligned with Stigmer’s orchestration worldview: a “task” cleanly represents “multiple internal executions” under one user-facing goal, without forcing the user to track backend execution IDs. citeturn28view1turn7view2

**Conversational flow patterns:**
- Cline separates **Plan vs Act**: plan mode can explore and ask clarifying questions without modifying files; act mode executes. Auto-approve can be toggled globally (Shift+Tab) or configured granularly. citeturn12view1turn3search1turn3search3  
- A key Cline pattern for “reducing noise” is `/newtask`: it creates a fresh task context and explicitly aims to leave behind “noise of tool calls and implementation details,” packaging only what matters (overall plan, work done, next steps). citeturn3search4

**Resumability and recovery:**
- Cline checkpointing is designed as a **shadow Git repository** that creates snapshots after each tool use, enabling restores of files only, task only, or both. This is a strong “undo/correct” affordance that makes higher autonomy (auto-approve) psychologically safer. citeturn27search8turn12view1  
- Cline documents that tasks are saved locally and can be browsed, searched, and resumed from history—supporting “pause and resume across terminal sessions” at the task level. citeturn28view1turn27search3  
- The troubleshooting guide includes “Reconstruct Task History,” which is an explicit admission that local history indices can break and need recovery tooling. citeturn27search1turn27search10

**Non-interactive / CI mode:**
- Headless mode is positioned as “runs without an interactive interface,” executes tasks, produces clean text/JSON output, and exits. It also documents how headless mode activates (piped input, redirected output, `--json`, or `-y/--yolo`). citeturn7view2turn7view3  
This is a direct blueprint for Stigmer: keep a crisp batch mode that never blocks on questions, distinct from a conversational “session” interface. citeturn7view2

### Warp Terminal Agent Mode (dual-context model: terminal sessions vs agent conversations)

**User-facing model:** Warp explicitly splits the world into two contexts: a **terminal session** (traditional shell) and an **agent conversation view** for multi-turn workflows. This is a high-signal UX choice: it prevents agent UI chrome from polluting the core terminal and makes the transition between “I’m running commands” and “I’m chatting” explicit and visually distinct. citeturn20view0turn20view1

**Session abstraction and history:**
- Warp organizes agent interactions into **conversations tied to sessions**, and can run multiple conversations simultaneously. It warns that long conversations degrade quality and encourages starting fresh for unrelated tasks—a recurring pattern across tools. citeturn20view1  
- Conversation storage is local by default, with optional **cloud-synced conversations** for cross-device access, sharing, and retention across logouts/machine switches. citeturn21search1turn20view1

**Transition and streaming state cues:**
- Warp uses contextual hint bars (e.g., “send to agent,” “new agent”) and explicit mode switching, which reduces the “jarring” feeling of moving between agent and shell. citeturn20view0  
- A user request to disable persistent “new /agent conversation” text illustrates the flip side: even subtle, always-on hints can be perceived as noise if they occupy permanent terminal real estate. citeturn21search30

## Cross-tool pattern taxonomy

### The dominant abstraction patterns

**Session-as-conversation (repo-scoped by default).** This is the most common approach: users think “I’m in a conversation with an agent about this repo.” Resuming is framed as “continue the conversation,” not “restart an execution.” Claude Code (`--continue`, `/resume`), Codex (`codex resume`), Copilot CLI (`--resume`, `/resume`), and Kiro (`--resume`, `--list-sessions`) all reinforce this. citeturn15view0turn4view3turn6search1turn11view0

**Task-as-goal container (conversation + actions + checkpoints).** Cline makes “task” the first-class mental model: “one goal = one task,” with a unique ID, dedicated storage, checkpoints, and resumability. This is particularly relevant to Stigmer because it naturally supports multiple sub-executions within one user-facing unit. citeturn28view1turn27search8

**Dual-context UIs (terminal vs agent conversation).** Warp’s explicit separation (“clean terminal by default” and “dedicated conversation view”) is a strong answer to the “abstraction layer” problem: keep normal CLI usage visually calm, and make “agent mode” a distinct space with enhanced controls. citeturn20view0turn20view1

### Conversational flow primitives that feel “natural”

**Plan-first elicitation as a gate on autonomy.** Multiple tools use “plan mode” not just as a feature, but as a *conversational rhythm*:  
- Agent asks clarifying questions → proposes a plan → waits for approval → executes. citeturn5view0turn23view0turn20view3turn24view0  
This both reduces wasted execution and gives users a natural pause point to correct intent before the tool does expensive or risky actions.

**Queueing/steering while the agent is working.** Copilot CLI explicitly supports sending follow-ups while “thinking,” and Windsurf supports queued messages while Cascade is working. This reduces the “turn-taking friction” that otherwise makes agent workflows feel jarring in a terminal. citeturn5view1turn24view0

**Checkpoints and reversible actions as psychological safety.** Claude Code, Cline, and Windsurf all use checkpointing/revert patterns to make autonomy tolerable. The UX implication: when undo is strong, users accept lower friction approvals (auto-approve / YOLO / policy-based allowlists). citeturn14view0turn27search8turn24view0

### TUI layout patterns that recur

**Full-screen “chat composer” + scrollable transcript** (often in the alternate screen buffer). Codex’s full-screen UI and screenshot show this clearly, including a header (model/directory) and a transcript area that can embed structured plan items. Copilot’s UI similarly uses a full-screen-like layout with modals for trust confirmations. citeturn9search7turn18view0turn16view0

**Inline REPL with scrollback** (lighter-weight). Aider’s design emphasizes slash commands and file/diff control in a traditional terminal flow. This is simpler to implement but can struggle with rich state rendering, multi-pane previews, and modals. citeturn8view2turn8view0

**Separate conversation view from the terminal** (hybrid UX). Warp’s “agent modality” shows a different approach: don’t force a chat UI into the same surface as the terminal prompt; instead, switch modes and show “hint bars” in terminal mode. citeturn20view0turn20view1

### Progressive disclosure controls for “busy” agents

Across tools, the “calm UI” is achieved by:
- Showing only *high-level narrative* in the transcript by default, while deferring details to commands/views (e.g., `/status`, `/session`, `/context`, `/debug`). citeturn7view0turn9search16turn4view0  
- Providing **verbosity toggles** (e.g., “verbose output” toggles, `--verbose`, `--silent`). citeturn19view0turn12view2turn7view1  
- Converting long history into summaries via compaction (`/compact`), with explicit “checkpoint” records of those summaries (Copilot) or targeted “summarize from here” that preserves early context (Claude). citeturn7view0turn14view0turn10search18  

## Anti-patterns and UX failure modes

### Leaking internals in ways that don’t help the user

A repeating failure mode is surfacing internals without clear user value. For example, a Codex issue requests that CLI status metadata be available outside a session because the current output is “too little information,” showing that **where metadata appears** (inside vs outside session) can be a usability cliff. citeturn9search10

Similarly, when a UI introduces persistent hint text, users may experience it as noisy or intrusive—even if it’s “helpful.” A Warp feature request asks to disable persistent “new /agent conversation” text at the bottom of all terminal sessions, illustrating that always-on UI elements compete with terminal minimalism. citeturn21search30turn20view0

### Session persistence that is fragile or inconsistent

Modern conversational agents live or die on resumability. Failures in task/session history are disproportionately painful because they invalidate the “continuous conversation” promise:
- Cline users have reported task history corruption and inability to resume, leading to lost productivity and confidence; the project’s own docs add recovery tooling (“Reconstruct Task History”), implying this is a known risk surface. citeturn27search7turn27search1turn27search10  
- Gemini CLI issues highlight that “Always approve” not persisting across terminal sessions feels like a broken contract for users who expect stable permission behavior across restarts. citeturn26search2turn25search27

### Too many approvals, or confusing auto-approval semantics

Users frequently complain when tool approval prompts become constant friction, especially for repetitive safe actions. This is why many tools converge on a three-tier model:
- Manual prompts (default)  
- Policy-based allowlists / “auto for safe”  
- YOLO/full bypass (with warnings) citeturn9search1turn5view0turn24view1turn11view0  

But the failure mode is when the “autonomy setting” doesn’t behave consistently (bugs, unclear scope, or lack of persistence), producing both frustration and mistrust. citeturn9search6turn26search4

### Context bloat and “one endless thread” as a quality trap

Tools repeatedly warn that long conversations can reduce quality and performance, pushing users toward “start fresh” patterns and explicit “new task/new conversation” controls. Warp explicitly recommends starting a new conversation for unrelated tasks, and Cline formalizes “one task = one goal.” citeturn20view1turn28view1

Aider community discussion shows the same pain: if the tool blindly includes too much history, users either pay more tokens or see degraded results, motivating better history controls than “delete everything.” citeturn2search26turn8view2

## Recommendations for Stigmer

### Adopt a user-facing “session” container that can hold many internal executions

A strong, evidence-backed direction is to shift from “each `stigmer run` = one shot” to an explicit **session** (or “task”) abstraction as the user’s primary mental model, with internal executions treated as invisible sub-steps.

Two viable naming/UX options, aligned with the ecosystem:
- **Session / conversation** (matches Claude Code, Codex, Copilot, Kiro). citeturn15view0turn4view3turn6search1turn11view0  
- **Task** (matches Cline’s goal-scoped container; especially good if your agents represent multiple sub-runs). citeturn28view1  

For Stigmer specifically, “task” is conceptually closest to “multiple executions under one goal,” while “session” is the more broadly recognized industry term. A pragmatic approach in CLI UX is to use **session** as the top-level command name and **task** as an internal/help-term, or vice versa.

### Hide execution IDs by default; only surface stable, user-meaningful handles

The pattern across tools is:
- Don’t show internal IDs in the main transcript unless needed.  
- Provide **human-friendly naming** (`/rename`) and **pickers/history views** as primary navigation. citeturn4view0turn4view3turn7view0turn11view0  
- Allow “power” resumption by ID for scripting or deep debugging. citeturn15view0turn4view3turn7view1  

Recommendation: treat “execution IDs” as **implementation detail** and never require the user to see or manage them. If you must expose identifiers, expose **session IDs** (stable over time), not “execution IDs” (ephemeral per internal run).

### Choose a Bubble Tea layout that matches how users actually work with agentic CLIs

Given Stigmer uses Bubble Tea, you can match the dominant successful layout:

**Recommended default TUI layout (interactive):**
- **Scrollable transcript viewport** (top/center), optimized for streaming and long output. citeturn25search1turn25search4  
- **Composer/input area at bottom**, ideally multi-line (textarea), with clear “sending” vs “editing” state. citeturn25search4turn25search7  
- A **right-side or collapsible bottom panel** for “action approvals,” “diff previews,” and “session/task metadata” (mirrors how Copilot/Codex/Cline keep the transcript readable while still exposing controls). citeturn16view0turn18view0turn12view1  

Bubble Tea’s ecosystem includes “viewport” and text area components designed for exactly this style of interface. citeturn25search1turn25search4turn25search6

**Key interaction detail:** prioritize the “queue while working” pattern (Copilot CLI, Windsurf). Technically, this means allowing the input field to accept and buffer user messages while streaming continues, with a visible queue indicator. UX-wise, this is one of the most powerful ways to make the agent feel like a collaborator rather than a blocking command. citeturn5view1turn24view0

### Implement resumability as “local-first, optional sync,” and make scope explicit

The ecosystem suggests a default of **local storage** with repo/directory scoping:
- Codex stores transcripts locally and scopes resume browsing to the current working directory unless `--all` is used. citeturn4view3turn2search5  
- Copilot CLI stores sessions under `~/.copilot/session-state/{session-id}` and offers commands to view checkpoints and artifacts. citeturn7view0turn7view1  
- Cline tasks are saved locally with history/search/resume expectations. citeturn28view1turn27search3  
- Warp stores conversations locally by default, with optional cloud sync for cross-device/team use. citeturn21search1turn20view1  

Recommendation for Stigmer:
- **Local-first session store** (fast, private, works offline) with a clear directory/project scope.  
- **Optional remote sync** (team/shared sessions, multi-device continuity) as an explicit opt-in, similar to Warp’s “cloud-synced conversations.” citeturn21search1  
- Support “resume picker,” “list sessions,” and “resume last,” which are now standard in Codex/Copilot/Kiro/Gemini session management patterns. citeturn4view3turn6search1turn11view0turn26search19  

### Make the “working ↔ your turn” transition legible without lifecycle spam

The best tools don’t narrate lifecycle events as “execution started/completed.” They use:
- Streaming output and a clear “agent is thinking/working” indicator. citeturn5view1turn9search7  
- A “queue messages” model or “steer while thinking,” so the user never feels blocked. citeturn5view1turn24view0  
- A status snapshot command/view (`/status`, `/session`, `/context`) for users who want details. citeturn9search16turn7view0turn4view0  

For Stigmer, the principle is: **show state through affordances, not narration.** Lifecycle events should be discoverable (logs, debug views, `--verbose`), but not the primary conversational surface.

### Treat non-interactive mode as a separate product surface with explicit policies

Every mature tool separates interactive chat from automation:
- Copilot CLI: programmatic `--prompt` plus approval flags and `--silent`; also `--no-ask-user` to avoid agent questions in automation contexts. citeturn5view0turn7view1  
- Codex CLI: `codex exec` is explicitly positioned for scripts/CI, with sandbox/approval choices. citeturn9search0turn9search1  
- Cline: headless mode auto-detected for piped I/O and `-y/--json`, producing clean output and exiting. citeturn7view3turn7view2  
- Aider: `--message` runs a single instruction and exits. citeturn8view1  
- Kiro: `--no-interactive` and `--trust-all-tools`. citeturn11view0  

Recommendation: Stigmer should ship an explicit **batch interface contract**:
- If stdin/stdout aren’t TTY or a `--non-interactive` flag is set, the agent must never block on a question.  
- If the agent needs missing info, either (a) fail fast with a clear error explaining which variable is missing, or (b) require the user to pre-supply defaults/answers via flags/config (policy choice). citeturn7view2turn7view1turn9search0
