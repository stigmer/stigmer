# Deep Research: Conversational Agent UX in CLI Tools

## Research Objective

We are designing a conversational UX for a developer CLI tool (called **Stigmer**) that orchestrates AI agent executions. We need deep, well-sourced research on how modern CLI-based AI coding assistants handle interactive, conversational agent workflows — with a specific focus on the **abstraction layer between internal execution mechanics and the user-facing experience**.

## Context

Stigmer is a developer tool where users run commands like:
- `stigmer draft skill` — asks an AI agent to generate a skill definition
- `stigmer run <agent>` — runs an AI agent with given inputs

Currently, these commands work as **single-shot operations**: the CLI creates an "execution" (an internal backend concept), streams output in a terminal UI, handles approval prompts (approve/skip/reject for tool calls), and exits. Each command is independent — no conversation, no follow-up, no user input beyond approvals.

We want to evolve this into a **conversational experience** where:
1. Agents can ask the user questions mid-execution and receive answers
2. Users can provide follow-up instructions after an agent completes a task
3. Multiple internal "executions" can happen within a single user-facing "session"
4. The UX hides internal mechanics (execution IDs, lifecycle phases) and presents a clean, session-based experience

## Key Research Questions

### 1. Session vs. Execution Abstraction
- How do tools like **Claude Code CLI**, **GitHub Copilot CLI**, **Aider**, **OpenAI Codex CLI**, **Cline CLI**, **Amazon Q CLI**, and **Cursor's agent mode** abstract their internal execution/request mechanics from the user?
- Do any of these tools expose "execution IDs" or internal lifecycle states (started/completed/failed) to the user? Or do they hide these behind a seamless conversational flow?
- What is the user-facing mental model? Is it a "session", a "conversation", a "chat", or something else?
- How do tools handle **multiple sequential tasks within a single session** — does the user see them as separate operations or as a continuous conversation?
- Are there examples of tools that got this wrong (exposed too much internal state) and the UX consequences?

### 2. Conversational Flow Patterns
- How do these CLI tools handle **agent-initiated questions** (the agent needs information from the user to proceed)?
  - What does the UX look like? How is the input prompt presented?
  - Does the agent's output stream pause, or does it continue while waiting?
  - How is the question visually distinguished from regular agent output?
- How do tools handle **user follow-ups** after a task completes?
  - Is there a natural continuation prompt ("Anything else?" or just a waiting input)?
  - Can the user reference or modify previous outputs?
  - How is context maintained across turns?
- How do tools handle the **transition between agent working and user input**?
  - Is it jarring or seamless? What makes it feel natural?

### 3. Terminal UI Patterns for Conversational Agents
- What are the established TUI (Terminal User Interface) patterns for chat-like interactions in a terminal?
  - Split-pane (input at bottom, output above)?
  - Inline input (input appears inline after agent output)?
  - Full-screen REPL with scroll-back?
- How do tools handle **streaming output alongside user input readiness**?
  - Can the user start typing while the agent is still streaming?
  - Is there a clear visual state change when the agent finishes and is waiting for input?
- How do tools visually differentiate between:
  - Agent thinking/working
  - Agent output/results
  - Agent questions (waiting for user input)
  - System status (connecting, errors, etc.)
  - Tool call approvals
- Any research or blog posts on TUI design patterns for AI agent interactions specifically?

### 4. Session Management and Resumability
- How do CLI tools handle **session persistence**?
  - Can users resume a previous session? How? (Session ID, name, auto-resume?)
  - What state is preserved? (Conversation history? File changes? Tool approvals?)
  - Is session state stored locally, server-side, or both?
- How do tools present session history to the user?
  - List of past sessions? Searchable? Filterable?
  - Can users review what happened in a previous session?
- What is the lifecycle of a session?
  - When does it start? When does it end?
  - Can it be paused and resumed across terminal sessions?
  - Timeout behavior?

### 5. Non-Interactive / CI Mode Considerations
- How do conversational CLI tools handle **non-interactive environments** (CI/CD, piped input, scripts)?
- Is there a clean separation between "interactive conversational mode" and "batch/script mode"?
- How do tools handle the "agent asks a question" scenario in non-interactive mode?
  - Timeout and fail? Use a default? Skip the question?

### 6. Noise Reduction and Progressive Disclosure
- How do tools balance **showing enough information** vs. **being too noisy**?
  - Do they show every tool call? Every file read? Every API request?
  - Collapsible/expandable sections?
  - Verbose vs. quiet modes?
  - Progressive disclosure (summary first, details on demand)?
- How do tools handle **internal lifecycle events** (execution started, completed, failed)?
  - Are these exposed to the user or hidden?
  - If shown, how are they presented (subtle status bar? inline messages? notifications?)
- What visual patterns exist for making a busy agent output feel calm and readable?

### 7. Error Handling and Recovery in Conversational Sessions
- How do tools handle **errors mid-conversation**?
  - Agent crashes — does the session survive? Can the user retry?
  - Network disconnections — automatic reconnect? State preserved?
  - Rate limiting — how is the user informed? Is the session paused or lost?
- How do tools let users **undo or correct** the agent's work?
  - Checkpoints/snapshots?
  - "Go back" or "undo last action" commands?

## What We're Trying to Decide

Based on this research, we need to make the following design decisions for Stigmer:

1. **What user-facing abstraction should replace "execution"?** — Session? Conversation? Chat? Run?
2. **Should internal lifecycle events (execution started/completed) be visible to users at all?** — Or should they be completely hidden behind a seamless conversational flow?
3. **What TUI pattern is best for our use case?** — We already use Bubbletea (Go TUI framework); what's the best layout?
4. **How should session resumability work?** — Local state, server-side, or both?
5. **How should we handle the transition between "agent is working" and "your turn to talk"?**
