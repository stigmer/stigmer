## Decisions Made

1. **Section-builder pattern for dual-purpose functions**: Functions like `addLLMSections(result, cfg)` append sections to an existing `*CommandResult`. Enables both standalone use (`stigmer server llm status`) and embedded use (inside `handleServerStatus()`). Same pattern applied to `addComponentSection`, `addAgentRunnerSection`, `addBootstrapSection`.

2. **Raw value output preserved for config get/path**: `handleConfigGet()` and `handleConfigPath()` deliberately kept as `fmt.Println(value)` — wrapping in CommandResult would break piping (`stigmer config get llm.provider | xargs ...`).

3. **ProgressDisplay functions excluded**: `handleServerStart()` and `handleLLMPull()` use `cliprint.ProgressDisplay` (BubbleTea interactive spinner), a fundamentally different paradigm from CommandResult. These remain on cliprint and will need their own migration strategy in a future phase.

4. **server_logs.go excluded**: Log streaming is an ongoing data pipe, not a command result. Not suitable for the CommandResult model.

5. **Health symbols embedded in field values**: Per-field color differentiation from cliprint (yellow warning vs cyan info per line) is replaced by semantic symbols in values (e.g., `"Running ✓"`, `"Unhealthy ✗"`, `"3 (crash loop) ⚠"`). Consistent with the vocabulary from Phase 1.

6. **Output destination change accepted**: Server status output moves from stdout (fmt.Println) to stderr (HumanRenderer convention). This is the correct CLI convention — informational output to stderr, data to stdout.

7. **server_status.go + server_health.go split**: The initial server_status.go at 340 lines exceeded the 250-line limit. Pure utility functions (isProcessAlive, isDockerContainerRunning, createBasicHealthStatus, getStateDisplay, getHealthSymbol, formatDuration) extracted to server_health.go.
