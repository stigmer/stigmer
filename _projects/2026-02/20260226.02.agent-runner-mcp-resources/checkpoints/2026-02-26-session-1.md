## Decisions Made

- **Option C (pure tool-based)**: Two LangChain tools (`list_mcp_resources`, `read_mcp_resource`) rather than context injection or single-tool approach. Mirrors how Cursor IDE and Claude Desktop expose MCP resources.
- **Auth pattern**: Same as tools — connection config with pre-resolved auth headers. No special handling needed.
- **Resource filtering deferred**: All resources accessible since they're read-only reference data. `enabled_resources` proto field can be added later if needed.
- **Session management**: Per-call sessions (adapter default). HTTP transport is lightweight. Session pooling deferred.
- **Resource templates clarified**: `list_resource_templates()` returns 1 template definition with URI pattern, not 150 expanded entries. Agent fills in parameters from user context.

## Key Code Changes

- `mcp_manager.py`: Added `list_mcp_resources()` (queries both `list_resources()` and `list_resource_templates()` per server, skips servers that don't support resources) and `read_mcp_resource()` (reads text or binary resource by URI)
- `resource_tools.py`: New module with `create_resource_tools()` factory that creates two `@tool` decorated functions capturing server configs in closures
- `agent.py`: Added resource tool registration in MCP integration block of `create_deep_agent()`
- `test_mcp_manager.py`: 11 new tests covering list (with/without resources, connection failures, partial failures) and read (text, binary, invalid server, multiple contents)
- `test_resource_tools.py`: 10 new tests covering factory, JSON output, text content, error handling

## Learnings

- `langchain-mcp-adapters` v0.1.14 already wraps `list_resources()` and `read_resource()` but NOT `list_resource_templates()`
- `MultiServerMCPClient.session(server_name)` yields a raw `ClientSession` — can call MCP SDK methods directly for template support without bypassing the adapter
- MCP `Resource` (static) and `ResourceTemplate` (parameterized) are separate concepts; `list_resources()` and `list_resource_templates()` return different types
- The `DiscoveredCapabilities` proto already has `resource_templates` field — no proto changes needed for discovery
