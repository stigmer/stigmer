## Decisions Made

1. **Top-level scan only**: `scanResourceFiles` reads the project directory (not recursive). Files next to `stigmer.yaml` are resources. Simple mental model.
2. **Skip Project kind**: `detectResourceItems` silently skips documents with `kind: Project` — avoids re-applying the marker file.
3. **SDK track error**: `executeProjectApply` returns a clear error rather than a partial implementation. Phase 4 will properly adapt it.
4. **Extension-based validation**: `validateEntryPointExtension` validates `.go`, `.py`, `.ts`, `.js`, `.mts`, `.mjs` — runtime is inferred from extension in the new model.
5. **Dry-run reuse**: Declarative dry-run reuses the same `applyResourceItem` handlers (which render previews) rather than building a separate path.

## Learnings

- The Phase 1 proto removal cascaded much further than the plan anticipated — 7 additional files needed fixes beyond the 3 originally planned. Always audit `go build ./...` early to assess full blast radius.
- `DiscardUnknown: false` in the YAML loader means old YAML fixtures with `runtime: go` fail to parse — good for catching legacy configs, but means test fixtures must be updated alongside proto changes.
- Bazel builds are currently blocked by an unrelated `com_github_alecthomas_chroma_v2` dependency issue — `go build` and `go test` are the reliable verification path for now.

## Open Questions

- Should `scanResourceFiles` eventually support recursive scanning (subdirectories)? Current design is intentionally flat.
- Should we add a `--recursive` flag later, or is flat-only the right permanent design?
