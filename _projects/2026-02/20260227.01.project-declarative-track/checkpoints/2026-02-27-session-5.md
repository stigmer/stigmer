## Decisions Made

1. **One test file per production file** — Mirrors the convention used across `project/`, `apply/`, and other packages. Each `apply_*.go` gets a companion `apply_*_test.go`.
2. **Shared test helpers in dedicated file** — Created `apply_test_helpers_test.go` with reusable builders (`newTestProject`, `newTestMembers`, `writeResourceYAML`, etc.) to avoid proto construction duplication. Also added `requireSectionField`/`findSectionField` for inspecting `CommandResult` sections.
3. **Scope limited to pure functions** — The orchestration functions (`executeDeclarativeApply`, `executeProjectApply`, `executeFileApply`) hard-code side effects. Testing them requires either dependency injection refactoring or a running backend — deferred as a separate effort.
4. **Discovered `types.DetectMulti` behavior** — Invalid YAML (e.g., `{{not yaml`) does not cause an error; it returns empty results. Adjusted test expectations to match actual behavior rather than assumed behavior.

## Learnings

- The `scanResourceFiles` function uses `strings.ToLower(name)` for stigmer.yaml exclusion, which handles case variants (`STIGMER.YAML`, `Stigmer.Yaml`) correctly
- `resolveApplyFiles` traverses subdirectories recursively (via `filepath.Walk`), while `scanResourceFiles` deliberately does not (top-level only) — this is an intentional design difference between file mode and declarative mode
- `CommandResult` sections expose `Fields []KeyValue` and `Items []string` — the helper `findSectionField` makes assertions clean without relying on rendered string output
