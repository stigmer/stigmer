## Decisions Made

1. **ResourceDeleter is the single execution interface** — The old ExecutionEngine + ResourceControllerAdapter had Create/Update/Delete with full resource preparation, dependency ordering, and change records. The new ResourceDeleter only does `Delete(ctx, kind, resourceID)`. Create and Update are no longer the server's responsibility.

2. **Reference resolution via store.FindByField** — To delete an orphaned resource, we need its resource ID but only have kind+slug from the ApiResourceReference. The service resolves this via `store.FindByField(ctx, kind, "metadata.slug", slug, msg)` then extracts the ID via the HasMetadata interface.

3. **Stub mode with nil deleter** — When no ResourceDeleter is provided (e.g., in test setup), orphans are still tracked as "removed" in the result but no actual deletion occurs. This lets the controller work without downstream clients during initialization.

4. **Partial failure semantics** — If one orphan fails to resolve or delete, the service continues with the remaining orphans. Errors are accumulated in ReconciliationResult.errors. This prevents a single bad reference from blocking the entire reconciliation.

5. **ToProtoSummary mapping** — `added -> created`, `removed -> deleted`, `updated` stays empty (the server has no way to know if a retained member was updated by the CLI).

## Key Code Changes

- **reconciliation_service.go**: Interface simplified from `Reconcile(ctx, project, options)` to `Reconcile(ctx, previousMembers, currentMembers, options)` — pure set math, no project object needed
- **service.go**: Implementation uses `buildReferenceSet` for O(1) membership checks, `computeAdded`/`computeOrphans` for set difference, and `deleteOrphans` with continue-on-failure
- **execution_engine.go**: Reduced from ~550 LOC to ~100 LOC. Only ResourceDeleter interface + ResourceDeleterAdapter remain
- **reconciliation_result.go**: ReconciliationResult now holds `[]*apiresource.ApiResourceReference` slices instead of `[]*projectv1.ResourceChangeRecord`. ResultBuilder added for incremental construction during orphan processing
- **apply.go**: Critical change — captures previous members from `ExistingResourceKey` in the pipeline context BEFORE delegating to Create/Update, then passes both lists to Reconcile()

## Learnings

- The LoadForApplyStep already stores the existing resource in the pipeline context under `ExistingResourceKey` — we just needed to extract it as a `*projectv1.Project` and read `.GetSpec().GetMembers()` before the Create/Update overwrites it
- The `store.FindByField` approach for reference resolution is clean but requires knowing the concrete proto type for each kind (Agent, Workflow, etc.) since the store unmarshals into a proto message. The `newProtoForKind` helper handles this routing.
