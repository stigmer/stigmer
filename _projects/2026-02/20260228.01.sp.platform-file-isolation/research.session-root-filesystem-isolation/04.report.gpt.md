# Filesystem Isolation Patterns for AI Agent Workspace Platforms

## Problem framing and decision criteria

Your core constraint is that the agent must be able to **read platform-managed artifacts (skills + user-uploaded inputs)** *as if they were inside the workspace*, while ensuring those artifacts **do not “dirty” the user’s real project folder** when the workspace is a direct pointer to a local working tree (e.g., `/Users/dev/my-project`). This is fundamentally a “single filesystem view composed from multiple sources” problem: *source tree* + *platform state* + sometimes *generated/execution state*. The same architecture should behave consistently in “local mode” and in a Linux container sandbox.

In ecosystems that face similar pressures (IDEs, cloud workspaces, build systems, containers), successful solutions generally optimize across five axes:

- **View composition:** How to present multiple sources as one coherent workspace (copy, mount/union, symlink pointers, or “separate roots”).
- **Persistence boundaries:** What persists with the project vs. what persists with the user vs. what is ephemeral to a session/container.
- **Pollution control:** Whether the user’s project tree gains new paths (folders/files/symlinks) and whether those show up in `git status`.
- **Tool compatibility:** Whether common tooling (git, search tools, IDE watchers, archivers, sync tools) behaves predictably with the chosen composition method. citeturn15view0turn30view0turn14search5turn11search7turn10search2turn13search3
- **Security invariants:** Whether the mechanism that makes “extra files visible” also creates a bypass for path containment checks (most commonly via symlinks, junctions, device paths, or TOCTOU races). citeturn4search0turn5search3turn8view0turn5search8turn10search6

With that framing, your proposed “session-root + `.stigmer` symlink bridge” is recognizable prior art—but **the specific change from `Path.resolve()` to `os.path.normpath()` for containment is the biggest architectural risk**, because it tends to convert “symlink convenience” into “symlink escape hatch” unless you add compensating controls. citeturn4search0turn8view0turn5search8turn5search15

## How other systems layer platform files with user workspaces

Across mainstream platforms, there are four dominant patterns. Most real systems use hybrids.

### Container-first workspaces: mount layering instead of writing into the repo

**Key idea:** Put the user’s repo on a mounted path, and mount platform state elsewhere (or mount it *into a subpath* inside the repo mount) so the *container view* has “extra directories” without touching the *host* working tree.

- entity["company","GitHub","code hosting company"] Codespaces clones repositories into a persistent `/workspaces` directory that is mounted into the dev container; it explicitly distinguishes **`/workspaces` (persistent)** from other filesystem areas that are tied to the container lifecycle and are not preserved on rebuild. citeturn17view0
- Codespaces personalization (dotfiles) is handled as *environment state* rather than repository content: a dotfiles repo is cloned and then either runs an install script or symlinks dotfiles into `$HOME`. This is a direct example of “platform/user-state files live outside the repo tree, but are still accessible in the environment.” citeturn18view0
- Container implementations achieve layering using union filesystems and mounts. The Linux kernel’s OverlayFS combines `lowerdir` and `upperdir` into a merged directory view (with “upper hides lower” resolution rules). citeturn2search1turn2search0
- entity["company","Docker","container software company"] documents that bind mounts mount a host file/directory into a container path, and that Docker uses layered filesystems/copy-on-write strategies for container writable layers (storage drivers/snapshotters). citeturn23search7turn2search11turn2search0
- On Linux, bind mounts are a first-class primitive: the `mount(2)` API describes bind mounts as making a subtree visible at another point in the hierarchy. citeturn23search10

**Validation vs. your proposal:** This pattern strongly validates the *goal* (present platform files “inside” workspace without polluting the underlying project) but suggests that **a “mount view” is the cleanest way** when you can rely on a container or mount namespace. Your Day\-tona cloud mode fits this paradigm naturally.

**Unknown gaps:** What mount capabilities you have in the Daytona sandbox (e.g., CAP_SYS_ADMIN, availability of `/dev/fuse`, and whether user namespaces are enabled) will determine whether you can implement a clean overlay/bind overlay inside that environment without privileged escalation. (This is environment-specific and not fully inferable from public docs in the sources above.)

### Repo-contained configuration directories: accepted pollution as a trade-off

These systems accept some degree of project-tree modification, usually justified as “project configuration” rather than “tool runtime state.”

- VS Code Dev Containers expect a `devcontainer.json` file typically in a `.devcontainer/` folder in the repository (or an alternate root path). This explicitly embeds environment configuration into the project. citeturn0search8turn0search16turn0search12
- entity["company","JetBrains","software tools company"] IDEs store project settings under `.idea/` (and module `.iml` files). JetBrains documents that `.idea` contains both user-specific settings that shouldn’t be versioned and shared settings that often are. citeturn21search0turn21search4turn21search1
- **Tool-managed ignore guidance** is part of the story: Git documents three distinct ignore sources—repository `.gitignore`, per-repo `$GIT_DIR/info/exclude`, and a global ignore file configured via `core.excludesFile`—which is an established way to reduce the risk of accidentally committing “tool local state.” citeturn30view0

**Validation vs. your proposal:** This pattern *partially* validates putting a hidden directory in the repo (e.g., `.stigmer/`), because it matches long-standing conventions. However, it also demonstrates a key pain point: users routinely need conventions and automation to avoid committing generated/tool state, and it still “shows up” in the working tree unless ignored. citeturn21search4turn30view0

**Unknown gaps:** For your strongest requirement (“must not pollute”), the repo-contained pattern is usually a compromise, not a primary solution—unless your product explicitly embraces the convention and provides robust ignore workflows.

### Build-system split roots + convenience symlinks: keep outputs elsewhere, expose them via minimal pointers

Several build systems separate “execution/output roots” from source code, but often create **a few symlinks in the workspace** for discoverability.

- Bazel supports an output base separate from the workspace and documents that you can relocate outputs via `--output_base` / `--output_user_root`. citeturn1search0turn1search4
- Bazel also documents “convenience symlinks” and offers `--symlink_prefix=/` to suppress symlink creation entirely, or `--symlink_prefix=.bazel/` to reduce clutter by placing convenience links under a hidden directory. citeturn1search4turn1search7
- Buck2 (and Buck) store build artifacts under a `buck-out` directory in the root of the project. citeturn1search2turn1search5

**Validation vs. your proposal:** Your “session-root + symlink bridge” is closest in spirit to Bazel’s “outputs elsewhere + convenience links.” The key lesson, though, is that Bazel treats workspace-root symlinks as optional *convenience*, and even provides flags to suppress them when users want a pristine tree. citeturn1search4turn1search7

**Unknown gaps:** Bazel’s use case is “build artifacts,” not “security-scoped file access,” so its filesystem pattern doesn’t directly answer your path-guard question—but it strongly informs the “minimize pollution” ergonomics.

### Global immutable stores and per-user state dirs: keep platform files out of projects entirely

- Nix documents the Nix store as an abstraction for immutable data, usually backed by a filesystem store at `/nix/store`. This is explicitly outside any given project directory. citeturn1search3turn1search22
- The XDG Base Directory Specification defines standard locations like `$XDG_DATA_HOME`, `$XDG_CONFIG_HOME`, `$XDG_CACHE_HOME`, and `$XDG_STATE_HOME` for user-specific configuration/state/cache, pushing tool state out of project directories by convention. citeturn26search3

**Validation vs. your proposal:** This validates the *direction* of “platform files live in a session/user state root,” but it does not, by itself, solve your requirement that the agent’s file tools and shell commands see those files under `root_dir` unless you either (a) relax the sandbox to allow access outside the workspace, or (b) present a composed view via mount/symlink/overlay.

**Unknown gaps:** A pure XDG-like approach works best when tools can be configured to look outside the project tree; your agent tooling currently enforces “must be within root_dir,” which constrains how far you can adopt this pattern without a virtualization layer.

## Symlink-based isolation: prior art, compatibility, and pitfalls

Your proposal introduces a *single* `.stigmer` symlink into the workspace, pointing to a platform-managed directory outside the workspace. The key questions are (a) whether that still counts as “pollution,” and (b) whether toolchains behave safely and predictably.

### How common CLI tools treat symlinked directories

The most important compatibility facts (because your agent heavily uses shell tools):

- `find`:
  - Default behavior is to examine symlinks themselves; dereferencing requires explicit flags (e.g., `-L`). GNU findutils states that “By default, find examines symbolic links themselves … to dereference … specify `-L`.” citeturn14search2turn14search5
- `grep`:
  - `grep -r` follows symlinks only if they’re explicitly specified on the command line; `grep -R` follows all symlinks recursively. This distinction is explicit in the `grep(1)` man page. citeturn11search7
- `tar`:
  - `tar -h/--dereference` follows symlinks and archives target contents; the GNU tar manual warns that dereferencing can be unsafe if an untrusted user can modify directories while tar is running. citeturn10search2turn10search6
- `rsync`:
  - `rsync` has explicit symlink controls; it also has “safe links” concepts. The `rrsync` restricted wrapper rejects `--copy-links` by default specifically to prevent dereferencing a symlink to reach outside a permitted directory. citeturn13search3turn12search13

**Implication:** A `.stigmer` symlink to a directory will often not be traversed by default by `find` or `grep -r`, but *will* be traversed if users/agent call tools with dereference flags (`find -L`, `grep -R`, `tar -h`, certain rsync options). This is compatible with “the agent can access it when it asks,” but it creates a double-edged sword: **any containment model that ignores symlink targets is exposed the moment dereference happens**.

### Git behavior and the “one symlink in the project” UX

- Git’s `core.symlinks` describes how symlinks are checked out and tracked. If enabled, symlinks are symlinks; if disabled, they become small regular files containing link text (notably on filesystems without symlink support). citeturn15view0
- Git’s ignore system is explicitly layered: project `.gitignore`, repo-local `$GIT_DIR/info/exclude`, and global ignore via `core.excludesFile` (defaulting to `$XDG_CONFIG_HOME/git/ignore` or `~/.config/git/ignore`). citeturn30view0
- Git further notes it does not follow symlinks when accessing a `.gitignore` in the working tree. citeturn30view0

**Implication:** A `.stigmer` symlink created in the user’s project will:
- show up in directory listings (it is a real entry);
- appear as an untracked file unless ignored;
- be ignorable via `.git/info/exclude` (per repo), or via global excludes (per user). citeturn30view0turn15view0

This is essentially the same “minimal pointer” ergonomics that Bazel uses for convenience symlinks—with the difference that Bazel exposes official toggles to suppress them when users care about a pristine tree. citeturn1search4turn1search7

### Platform differences and Docker/cloud considerations

- On macOS, FUSE support is not native; macFUSE provides the kernel extension/userland support needed for user-space filesystems. macFUSE explicitly frames FUSE filesystems as user-space applications integrated into macOS. citeturn31search0turn31search4
- For overlay-in-userspace, fuse-overlayfs is specifically positioned as a FUSE implementation of overlayfs. However, upstream discussions indicate macOS support is “out of scope” for fuse-overlayfs due to Linux-specific assumptions. citeturn31search6turn31search10turn31search2

**Implication:** If you rely on symlinks to avoid heavier filesystem tricks, you avoid OS-specific FUSE deployment complexity. But if you need “no modifications at all,” you likely end up in mounting/FUSE territory, which is dramatically more feasible on Linux than on macOS.

### Recommendation for this area

Symlink bridging is **valid prior art for “minimal pollution”** (Bazel-style) but is hard to square with **“zero pollution”** and can become dangerous if combined with a containment check that ignores symlink targets. citeturn1search4turn14search2turn4search0turn12search13

**Unknown gaps:** IDE watcher behavior (VS Code/JetBrains file watchers, ripgrep defaults, rsync/tar flags used by various integrations) can materially affect performance and accidental traversal. The sources above establish CLI semantics, but IDE-specific watcher traversal defaults are not fully captured in the cited corpus.

## Path traversal guard: why `normpath` is not a drop-in replacement for `resolve`

Your current guard:

- resolves paths (following symlinks), then checks whether resolved path is within `root_dir` by prefix match.

Your proposed change:

- stop following symlinks for containment and rely on lexical normalization (`normpath`) to allow `.stigmer -> ../.stigmer` style access.

The difference is not cosmetic—it changes the security model.

### What `normpath` does and does not do

Python documents `os.path.normpath()` as a **string manipulation** that collapses redundant separators and `..`, and warns that “This string manipulation may change the meaning of a path that contains symbolic links.” citeturn4search0

That warning matters here because if the agent (or any process writing into the workspace) can introduce symlinks, a lexical check can be bypassed:

- Lexically, `workspace/a/b` is inside `workspace`.
- But if `workspace/a` is a symlink to `/etc`, then the real file read is `/etc/b`.

This exact class of bug (“improper link resolution before file access”) is a common and recurring security failure mode; it’s why restricted rsync wrappers explicitly reject dereference options that could traverse symlinks out of a restricted root. citeturn12search13

### What popular “safe join” libraries do—and their limits

Werkzeug’s `safe_join` is a widely-copied pattern for safely joining an untrusted path to a trusted base dir. Its current implementation:

- normalizes each untrusted segment with `posixpath.normpath`,
- rejects absolute paths, `..`, and alternate separators,
- then joins with `posixpath.join`. citeturn8view0

This is instructive for two reasons:

1. It demonstrates the *standard lexical approach* (normalize + reject `..`/absolute).
2. It shows how hard it is to get even the lexical version correct across platforms: Werkzeug has had multiple recent Windows-specific issues in `safe_join` (UNC paths, special device names like `CON`/`NUL`) that required patches and advisories. citeturn5search8turn4search5turn5search15turn3search0

Most importantly for your design: `safe_join` is not trying to defend against *symlink traversal when the attacker can write symlinks into the served directory*. Many web frameworks assume the server-controlled directory isn’t writable by the attacker, which is exactly the opposite of an agent workspace where the agent can typically write files freely. citeturn8view0turn4search1

### A critical architectural observation: shell access already breaks “chroot-like semantics” in local mode

Even if your tool APIs enforce containment, your shell tool (`execute(command)`) runs a real process with filesystem access available to the user account. Unless you add OS sandboxing (container/jail/user namespace), the agent can run commands with absolute paths (e.g., `cat /etc/passwd`) regardless of your Python-level guard.

This is why systems that truly need uniform filesystem scoping use kernel primitives (containers, chroot, mount namespaces) rather than relying only on path normalization in user space. The Linux kernel documents that absolute paths begin at the filesystem root, and `chroot(2)` changes the process’s root so that pathnames beginning with `/` resolve under the new root. citeturn25search0turn25search12

### Recommendation for this area

Switching the containment check from “resolve/realpath” to pure “normpath” **is not sufficient** if the agent can write symlinks (directly through tools or indirectly through shell). It creates a straightforward escape: create a symlink in-root pointing out-of-root, then access through the symlinked path. citeturn4search0turn12search13turn10search6

A safer direction—while still enabling your `.stigmer` bridge—is:

- Keep a **realpath-based containment check** (i.e., follow symlinks for the final resolved target) using an actual path-aware comparison (e.g., `commonpath`) rather than string-prefix matching.
- Add a **small allowlist of additional permitted roots** (e.g., `session_root/.stigmer`) so that `.stigmer/...` resolves to an allowed platform root but everything else must remain within the workspace root.
- Optionally treat `.stigmer` as a *reserved name* that must resolve to the platform directory you created (and refuse access if it resolves elsewhere). This “pinned symlink” concept is similar in spirit to restricted rsync’s refusal to dereference arbitrary symlinks beyond a boundary. citeturn12search13

**Unknown gaps:** A complete, hardened userspace “no symlink escape and no TOCTOU” file opener typically needs `openat()`-style directory file descriptors and careful avoidance of symlink traversal in intermediate path components. The provided sources establish why this is hard (tar’s warning, rsync restrictions, safe_join CVEs), but do not provide a single canonical Python recipe for your exact threat model. citeturn10search6turn12search13turn5search8turn5search15

## Overlay and union alternatives to symlinks

If “no pollution” for `local_path` is strict, then (by definition) you need the platform files to appear **without writing anything into the user directory**. That requires a *view layer*.

### Linux-native kernel mount solutions

- **Bind mounts:** Make the user directory available at a session-controlled mountpoint, then mount the platform directory at a subpath inside that mountpoint (e.g., mount platform state at `session_root/workspace/.stigmer`). Bind mounts are a well-defined kernel feature (`mount(2)` MS_BIND). citeturn23search10turn23search1
- **OverlayFS:** Combine multiple directory trees into one merged view via `lowerdir` and `upperdir`. OverlayFS is documented in the kernel docs and is a union filesystem. citeturn2search1turn2search0

**Key caveat:** OverlayFS’s writable semantics are “writes go to the upperdir,” which is excellent for ephemeral container layers but is tricky if you need edits to apply directly to the user’s original directory without introducing overlay metadata side effects. The kernel semantics (“upper hides lower,” merge rules) make this behavior explicit. citeturn2search1

### Rootless / user-space overlay options on Linux

- entity["company","Red Hat","enterprise software company"]’s Podman documentation recommends fuse-overlayfs for rootless mode and describes it as providing OverlayFS-like functionality for rootless environments via a mount program. citeturn2search2turn2search21
- `bindfs` is explicitly designed as “mount --bind in user-space,” mirroring one directory to another mountpoint (with optional permission manipulation). citeturn2search3turn2search14
- Linux kernel documentation describes FUSE as a filesystem where data/metadata are provided by a userspace process, and supports non-privileged mounts in some configurations. citeturn23search17turn23search11

**Feasibility in a container sandbox:** fuse-overlayfs requires `/dev/fuse` availability; the fuse-overlayfs project explicitly notes `/dev/fuse` requirements for build/deploy scenarios. citeturn31search10

### macOS practicality: FUSE is possible but operationally heavier

- macFUSE exists specifically to bring FUSE filesystem support to macOS. citeturn31search0turn31search4
- unionfs-fuse reports macOS support with macFUSE (formerly osxfuse). citeturn31search3
- bindfs’s installation notes explicitly mention macOS builds requiring XCode tools and MacFuse/fuse-t. citeturn31search5
- fuse-overlayfs maintainers have stated macOS support is out of scope due to Linux assumptions, even though Homebrew can ship packages (which may target Linux bottles). citeturn31search6turn31search2

**Implication:** A “no modifications to user project” approach on macOS usually means asking users to install macFUSE (a significant adoption and security/trust hurdle), or accepting a different fallback path.

### Recommendation for this area

If you can rely on mounts (cloud mode, and possibly Linux local mode), the cleanest architecture is:

- `session_root/workspace` is a **mount view** of the user project (bind mount or FUSE mirror);
- `session_root/.stigmer` holds platform files;
- `session_root/workspace/.stigmer` is a **mount** of `session_root/.stigmer` (not a symlink), ideally read-only.

This preserves your original `Path.resolve()`-style containment (everything is physically “inside” the mounted workspace view) and avoids touching the user directory.

Symlinks become a fallback for environments where mounts are unavailable.

**Unknown gaps:** Whether Daytona’s container environment permits nested mounts or FUSE mounts is unknown from the cited sources; this requires environment verification (capabilities, `/dev/fuse`, seccomp/apparmor constraints).

## Agent skill/context injection patterns in AI coding tools

There is a clear emerging convention: many AI coding tools store **workspace-scoped rules** in a hidden directory within the project/workspace, while also supporting **user-scoped** configuration in the home directory.

- Cursor documents that creating a new rule file places it in `.cursor/rules` in the workspace. citeturn22search0
- entity["company","Codeium","ai coding tools company"] Windsurf documents that rules are saved in `.windsurf/rules` in the current workspace (not necessarily the git root). citeturn22search4
- Continue documents user-level configuration stored in `~/.continue/config.yaml` on macOS/Linux (and the Windows equivalent), and also supports workspace-level directories such as `.continue/rules` and `.continue/mcpServers/`. citeturn22search2turn22search20turn22search9
- Aider documents `.aider.conf.yml` lookup including the home directory and the git repo root, establishing a dual-scope configuration model. citeturn22search3turn22search6

**Implication:** For “agent skills,” the ecosystem is converging on:
- **hidden workspace directories** for project-scoped instructions/rules; and/or
- **home-directory config** for user-scoped defaults.

This is compatible with your desire for `.stigmer` as a hidden entry point—*if* you can accept that it exists in the project tree. If you cannot, you will need a mount/view layer to eliminate on-disk pollution while still presenting `.stigmer` in the agent’s view.

**Unknown gaps:** Some proprietary agent platforms (e.g., fully hosted autonomous agents) do not publish filesystem injection details publicly; this limits how conclusively one can compare “skills injection” mechanisms beyond the local tools cited here.

## Integrated recommendation for your architecture

### What the research validates

Your proposed high-level separation—**platform files live in a managed session root, not inside the user’s repo**—aligns strongly with proven patterns:
- Codespaces’ split between `/workspaces` (repo) and other container lifecycle areas (environment state). citeturn17view0
- Nix’s “immutable global store” concept (platform artifacts exist outside the project). citeturn1search3
- Bazel’s “outputs elsewhere + convenience symlink prefix” approach to reduce repo clutter. citeturn1search4

### What the research challenges

The risky part is **changing your containment check to ignore symlink targets**. This is the same class of failure mode that security tooling actively defends against (restricted rsync disallowing dereferencing, tar warning about dereference in mutable directories, repeated safe_join hardening). citeturn12search13turn10search6turn5search8turn5search15

### A recommended decision tree by workspace type

**Managed workspaces (`git_repo`, `empty`)**
- Keep platform files under a hidden directory (e.g., `.stigmer/`) inside the managed workspace if you want maximal simplicity, or keep your session-root split to match cloud mode. This is primarily a UX choice because you control the directory anyway.

**Unmanaged `local_path` workspaces**
- If “no pollution” is strict, do *not* point `root_dir` at the user directory directly. Instead:
  - create `session_root/workspace` as a **view** (bind mount, FUSE mirror, or container mount) of the user directory; and
  - attach `session_root/.stigmer` into `session_root/workspace/.stigmer` via a mount (preferred) or a pinned symlink (fallback).
  - This keeps the real user directory unchanged while presenting `.stigmer` inside the agent’s root.

Where mounts are not feasible (notably on macOS without macFUSE), the fallback is a pragmatic compromise:
- Create exactly one entry in the user project (a `.stigmer` symlink or directory) and automatically add it to either:
  - `.git/info/exclude` (repo-local, not shared), or
  - global excludes file via `core.excludesFile` (user-wide). citeturn30view0
This mirrors the approach used by many tools that “drop one file” like `.envrc` (direnv) or `.nvmrc` (nvm) to enable project-specific behaviors. citeturn26search0turn29view0

### Containment guard guidance

- Do **not** replace `resolve()`-style containment with `normpath()` alone, because it is explicitly only string normalization and can change meaning with symlinks. citeturn4search0
- If you must allow `.stigmer` to point outside the workspace:
  - keep a realpath/resolve check but extend it to allow an explicit allowlist of platform roots; and
  - ensure `.stigmer` resolves only to that expected platform root (pin/validate the link target).
- If you cannot sandbox shell access, consider separating “workspace file tools” from “platform file tools” rather than relaxing containment globally. (This is less elegant but avoids turning every arbitrary symlink into an escape hatch.)

- Whether your Daytona environment allows bind mounts, overlayfs mounts, or FUSE mounts (capabilities and `/dev/fuse`). citeturn31search10turn2search2
- Whether you will expand support to Windows (Werkzeug’s recent `safe_join` CVEs show how Windows path semantics can break otherwise “reasonable” logic). citeturn5search8turn4search5turn5search15
- How IDE file watchers in your supported editors behave with a symlinked `.stigmer` directory at scale (performance and recursion/loop hazards are often environment-specific and not fully standardized in the referenced docs).
