# Deep Research: Filesystem Isolation Patterns for AI Agent Workspace Platforms

## Research Objective

We are building an AI agent execution platform where an LLM-based coding agent operates inside a "workspace" — a directory containing the user's project code. The platform needs to inject **platform-managed files** (skill definitions, user-uploaded input files) into the workspace so the agent can read them. The core problem: **these platform files must not pollute the user's project directory**, especially when the workspace points directly at the user's local project folder.

We need to understand how other systems solve this "platform files alongside user files without contamination" problem, and whether our proposed solution (session-root directory + symlink bridge) is the right architecture or if better patterns exist.

## System Context

### What We're Building

An AI coding agent platform with two deployment modes:

1. **Local mode**: The agent runs as a process on the user's machine. The workspace is a directory on the local filesystem — either a git clone (managed by us) or the user's actual project directory (e.g., `/Users/dev/my-project`).

2. **Cloud mode (Daytona sandbox)**: The agent runs inside a cloud-hosted Linux container. The workspace is a directory inside the sandbox (e.g., `/home/daytona/workspace/`).

### The Platform Files

Two categories of files the platform needs to inject before the agent starts:

1. **Skills** (`bin/skills/{name}/SKILL.md` + optional scripts/assets): Read-only instruction files the agent reads on demand during execution. Follows the Agent Skills specification (progressive disclosure model). Can include executable scripts.

2. **Input files** (`.stigmer-inputs/{filename}`): User-uploaded reference documents (PDFs, specs, etc.) the agent reads during execution.

### How the Agent Accesses Files

The agent has two ways to access files:

1. **Tool-based access**: `read(path)`, `write(path, content)`, `list_files(path)` — these resolve paths relative to `root_dir` using chroot-like semantics. A path-traversal guard prevents `../` escapes outside `root_dir`. Implemented via Python's `pathlib`.

2. **Shell access**: `execute(command)` — runs shell commands with `cwd=root_dir`. The agent frequently uses `cat`, `ls`, `grep`, `bash script.sh` etc. Shell commands resolve paths relative to the real filesystem.

### The Path-Traversal Guard

Both the pre-agent setup layer and the agent runtime enforce:

```python
resolved = (root_dir / clean_path).resolve()  # follows symlinks
if not str(resolved).startswith(str(root_dir)):
    raise ValueError("path escapes workspace root")
```

This means: any file the agent reads/writes through tools MUST be physically within `root_dir` (after symlink resolution). This is the core constraint.

### Three Workspace Source Types

1. **git_repo**: Platform clones a git repository into a managed directory. We fully control this directory.
2. **local_path**: User points the workspace at their existing local project directory. We do NOT control this directory — it's the user's real project.
3. **empty**: A fresh temp directory. We fully control it.

## The Problem

Currently, platform files are written directly into `root_dir`:
- `{root_dir}/bin/skills/skill-a/SKILL.md`
- `{root_dir}/.stigmer-inputs/requirements.pdf`

For `git_repo` and `empty`, this is acceptable (managed directories). For `local_path`, this is a real problem:
- `bin/skills/` and `.stigmer-inputs/` appear in the user's project
- They show up as untracked files in `git status`
- They can accidentally be committed
- They pollute the user's working tree

## Our Proposed Solution (Needs Validation)

**Session Root with Symlink Bridge:**

```
session_root/                         managed directory
├── .stigmer/                         platform files (real directory)
│   ├── skills/
│   └── inputs/
└── workspace/                        user's code
    ├── .stigmer → ../.stigmer        managed symlink
    ├── src/
    └── README.md
```

- `root_dir = session_root/workspace/`
- Platform files physically live in `session_root/.stigmer/` (outside workspace)
- A `.stigmer` symlink inside workspace bridges access
- The path-traversal guard is changed from `Path.resolve()` (follows symlinks) to `os.path.normpath()` (logical path only) for the containment check
- For `local_path`: the `.stigmer` symlink is created inside the user's project, pointing to an external session state directory
- For `git_repo`/`empty`: session_root is a managed temp directory; symlink points to sibling

## What We Need Researched

### 1. How Do Other Platforms Solve This?

Research how these systems handle "platform files alongside user workspace" isolation:

- **VS Code Dev Containers / devcontainers**: How do they inject configuration files (`.devcontainer/`) without polluting the project? Do they use overlayfs, bind mounts, or something else?
- **GitHub Codespaces**: Where do platform-managed files (extensions, settings, dotfiles) live relative to the user's repository?
- **Gitpod**: How does Gitpod inject workspace configuration and tooling without polluting the git working tree?
- **Docker / OCI containers**: How do containers layer platform files (from the image) with user-mounted volumes? Overlayfs, union mounts?
- **Cursor IDE / Windsurf / Aider / other AI coding tools**: Where do these tools store their runtime files (rules, context, caches) relative to the user's project?
- **JetBrains IDEs**: `.idea/` directory approach — is this actually a good pattern or a known pain point?
- **Bazel / Buck2**: How do build systems create an execution root that overlays source files with generated files?
- **Nix / Guix**: How do these package managers achieve isolated environments without polluting the project directory?
- **FUSE filesystems**: Are there lightweight FUSE-based solutions for overlaying directories?
- **Plan 9 / union mount patterns**: The Plan 9 bind mount concept — is it applicable here?

### 2. Symlink-Based Isolation: Prior Art and Pitfalls

- What are documented problems with using symlinks for directory bridging in development environments?
- How do common tools (git, find, grep, rsync, tar, IDE file watchers) behave with symlinked directories?
- Are there known issues with symlinks in:
  - macOS (APFS) vs Linux (ext4/btrfs)?
  - Docker volume mounts?
  - Cloud sandbox environments?
- Does `git` follow symlinks when computing `git status`, `git diff`, `git add`? What does `core.symlinks` control?
- Does `find . -type f` traverse symlinked directories?
- Does `grep -r` follow symlinks by default?

### 3. Path-Traversal Guard: normpath vs resolve

- Is `os.path.normpath()` sufficient for preventing path-traversal attacks, or are there known bypasses?
- Are there edge cases where `normpath` produces a path that appears contained but is actually dangerous?
- What do security-focused libraries (e.g., `werkzeug.utils.safe_join`, Flask's static file serving) use for path containment?
- Is there a standard "check containment without following symlinks" pattern in Python?
- How does `chroot` handle symlinks that point outside the chroot? Is there a userspace equivalent?

### 4. Overlayfs / Union Mount Alternatives

- Can `overlayfs` be used in userspace (non-root) for this kind of file layering?
- Is `fuse-overlayfs` (used by rootless Podman) a viable alternative to symlinks?
- What about `bindfs` (FUSE-based bind mount)?
- What's the overhead of FUSE-based solutions vs. symlinks?
- Are any of these available/practical on macOS?
- Would any of these work inside a Daytona cloud sandbox (Linux container)?

### 5. The "One Symlink in User's Project" Question

For `local_path` workspaces, our proposal creates a single `.stigmer` symlink inside the user's project directory. Alternatives:

- Is there a way to make files appear inside a directory WITHOUT any modification to that directory? (Overlay mount? FUSE? Something else?)
- How do tools like `direnv` (creates `.envrc`), `nvm` (creates `.nvmrc`), `asdf` (creates `.tool-versions`) justify placing files in user directories? Is there an established convention?
- Would it be acceptable to require the user to add `.stigmer` to their global gitignore (`~/.config/git/ignore`) instead of per-project exclusion?
- Are there platform-specific mechanisms (macOS extended attributes, Linux xattrs) that could hide the symlink from normal directory listings?

### 6. Agent Skill/Context Injection Patterns in AI Platforms

- How do AI coding agents (Cursor, Windsurf, Continue, Aider, Devin, Codex CLI) inject context/rules/skills into the agent's accessible filesystem?
- Do any of them use a "platform directory" pattern similar to what we're designing?
- How do they handle the boundary between "user's project files" and "platform-managed files"?
- Is there an emerging standard or convention for where AI agent platform files should live?

## Why This Matters

This is a foundational filesystem architecture decision for our platform. Getting it wrong means:
- Platform files polluting user projects (current problem)
- Agent unable to read skills/inputs (access problem)
- Different behavior across deployment modes (consistency problem)
- Security vulnerabilities in path handling (safety problem)

The user explicitly stated: "These filesystem modifications are the core, and if that is working perfectly, then I know we will make wonders." We need to get this right.
