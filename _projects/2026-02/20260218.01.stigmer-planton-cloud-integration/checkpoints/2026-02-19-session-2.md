# Session Notes: 2026-02-19 Session 2 — Integration Architecture Refinement

## Summary

Deep design session refining the Stigmer × Planton integration architecture. Started from the Phase 1 proto work (completed in session 1), explored the full authentication/authorization flow through iterative questioning, conducted external research via ChatGPT Deep Research, and arrived at a significantly simplified architecture.

## Major Design Evolution (Session 1 → Session 2)

### What Changed

| Aspect | Session 1 Design | Session 2 Final Design |
|--------|-----------------|----------------------|
| **JWT signing** | Planton generates custom RSA key pair, publishes JWKS on GitHub Pages, proxy mints custom JWTs | **No custom keys.** Planton's Auth0 JWT is forwarded as-is to Stigmer's token exchange |
| **JWKS in IdentityProvider** | Custom JWKS URL (GitHub Pages) | Auth0's public JWKS URL (`planton-prod.us.auth0.com/.well-known/jwks.json`) |
| **Token flow** | Proxy mints JWT → Stigmer validates directly on API endpoints | Proxy forwards Auth0 JWT → Stigmer token exchange endpoint → Stigmer issues native token |
| **Profile data (email, name)** | Optional, unclear source | Stigmer calls OIDC UserInfo endpoint during token exchange (standard, no Auth0 customization) |
| **Proxy design** | Docker image with env vars, zero code | **SDK/library** — integrator writes ~20 lines of Go, adds custom authz interceptors |
| **Authorization** | Auto-grant org membership (INSECURE — user could spoof org) | Integrator adds authz interceptor via SDK; platform-side authz is the gatekeeper |
| **API key support** | Needed identity resolution endpoint | **Deferred to post-MVP.** JWT-only for MVP. |
| **Proxy env vars** | 8+ env vars (private key, JWKS, UserInfo, issuer, audience, key ID...) | **1 env var** (`STIGMER_ENDPOINT`) — everything else is in SDK config or IdentityProvider |

### Why It Changed

1. **Custom JWKS eliminated**: If token exchange is the pattern (recommended by research), the exchange endpoint validates the external JWT. Auth0's JWKS is already public — no need for a separate JWKS.
2. **Token exchange added**: Research (10+ case studies, RFC 8693) showed that token exchange is the industry standard for cross-platform auth. It solves audience mismatch, gives Stigmer control over token policy, and separates trust boundaries.
3. **Proxy → SDK**: The authorization problem (user can spoof org access) killed the pure config-based proxy. Custom authz logic requires a code-based approach (SDK with interceptors).
4. **Profile data via UserInfo**: Auth0 access tokens don't contain email/name/picture by default (those are in the ID token). Rather than customizing Auth0 (fragile, maintenance burden), Stigmer calls the standard OIDC UserInfo endpoint during token exchange.

## Design Decisions Made

### DD-01: Token Exchange over Direct JWT Acceptance

**Decision**: Stigmer implements an RFC 8693-style token exchange endpoint. External JWTs are exchanged for Stigmer-native tokens. Stigmer API endpoints only accept Stigmer-issued tokens.

**Rationale**: 
- Industry standard (AWS STS, GCP Workload Identity, Auth0 CTE all use this pattern)
- Stigmer controls token TTL, audience, claims, and revocation
- Solves audience mismatch (external JWT has `aud: api.planton.ai`, Stigmer token has `aud: stigmer-api`)
- Identity resolution (JIT provisioning) happens once at exchange time, not on every API call
- External JWT never reaches Stigmer API endpoints — clean trust boundary

### DD-02: IdentityProvider Points to Auth0's Public JWKS

**Decision**: For Auth0-based integrators, the IdentityProvider's `jwks_uri` points directly to Auth0's `.well-known/jwks.json`. No custom key pairs needed.

**Rationale**:
- Auth0's JWKS is already public and managed (key rotation handled by Auth0)
- Eliminates private key generation, GitHub Pages hosting, manual key rotation
- Token exchange validates the JWT signature using these keys
- For non-Auth0 integrators (future), the custom JWKS path remains available

### DD-03: Proxy SDK with Interceptor Hooks (Not Config-Only Image)

**Decision**: Stigmer ships a Go library (`stigmer-proxy-sdk`) that integrators use to build their proxy. The SDK provides token exchange, gRPC forwarding, and user/org extraction. Integrators add custom interceptors (authz, logging, etc.).

**Rationale**:
- Authorization check is platform-specific (each platform has its own org access model)
- A config-only proxy can't handle custom authz logic
- Industry-validated pattern (Temporal SDK, gRPC-Go middleware, Connect-Go, Express.js)
- ~20 lines of integrator code for a working proxy with custom authz
- Also ship a pre-built Docker image (SDK with zero interceptors) for internal-only deployments

### DD-04: Profile Data via OIDC UserInfo Endpoint

**Decision**: During token exchange, Stigmer calls the OIDC UserInfo endpoint (configured in IdentityProvider) to fetch email, name, and picture. This data is stored on the identity_account and updated on every token exchange.

**Rationale**:
- Auth0 access tokens don't include email/name/picture by default (those are in ID tokens)
- Adding Auth0 Actions to customize access tokens creates maintenance burden
- OIDC UserInfo is a standard endpoint available on every OIDC provider (Auth0, Okta, Google, etc.)
- Profile data is essential for human-readable audit trails and UI display
- Updating on every exchange keeps data fresh without sync infrastructure

### DD-05: JWT-Only for MVP (API Keys Deferred)

**Decision**: The proxy and token exchange only support JWT bearer tokens for MVP. API key authentication through the proxy is deferred to post-MVP.

**Rationale**:
- Web console and CLI users always have Auth0 JWTs — primary use cases covered
- API keys are for programmatic/automation access — secondary for MVP
- Supporting API keys requires either an identity resolution callback or custom JWT minting — complexity for an edge case
- Can be added later without breaking changes

### DD-06: Auto-Grant Org Membership for Platform-Managed Orgs (Behind Authz Boundary)

**Decision**: When a federated user accesses a platform-managed org through token exchange, Stigmer auto-creates FGA membership (`organization:X#member@identity_account:Y`). This is safe ONLY because the request has passed through the platform's authorization layer first.

**Rationale**:
- The integrating platform is the authorization authority for its users and orgs
- If the request reaches Stigmer's token exchange, the platform has already verified org access
- The proxy SDK enforces this via interceptor hooks — platforms must implement their authz check
- Stigmer's FGA is a secondary check; primary authz lives in the platform
- Same trust model as Stripe Connect, Twilio subaccounts, AWS STS

### DD-07: IdentityProvider Stores UserInfo URI

**Decision**: Add `userinfo_uri` field to IdentityProvider spec (alongside `jwks_uri`, `allowed_issuers`, `expected_audience`).

**Rationale**:
- Token exchange endpoint needs to fetch profile data
- Each OIDC provider has its own UserInfo URL format
- Keeping it in the IdentityProvider makes it configurable per-provider

### DD-08: Federated Identity Account Must Store Profile Data

**Decision**: Identity accounts store email, display_name, and picture_url (not just idp_id). Updated on every token exchange.

**Rationale**:
- Audit trails showing `ida_98ZYXWVU` are useless to humans
- Email and name are essential for UI display and audit readability
- Profile data comes from UserInfo call during token exchange
- Updated on every interaction (user might change email) — no sync needed

### DD-09: Two Auth Flows (User-Context and System-Level)

**Decision**: 
- User-context: Token exchange (per-user identity from JWT)
- System-level: Stigmer API key / service account (org creation, sync, billing)

**Rationale**:
- User actions need per-user identity for audit and FGA
- System operations (create org, sync lifecycle) have no specific user
- Research confirms this split is universal (Vercel integration framework, AWS Marketplace, etc.)

## Key Learnings

1. **Start simple, add complexity only when forced**: We went from custom JWKS + JWT minting to "just use Auth0's public JWKS" — simpler and more secure.
2. **Token exchange is the industry standard for cross-platform auth**: Not direct JWT acceptance, not custom JWT minting — exchange.
3. **Authorization must live where the data is**: Planton knows org membership. Stigmer doesn't. Authz stays in Planton.
4. **OIDC UserInfo is free**: No need to customize Auth0 or build identity resolution endpoints. The standard UserInfo endpoint already has email/name/picture.
5. **Config-only proxies fail when custom logic is needed**: The authz requirement pushed us from Docker image to SDK. This is the right tradeoff.
6. **The proxy auth problem**: Auto-granting org membership is only safe when the request has already been authorized by the integrating platform. The SDK's interceptor hooks enforce this.
7. **MVP scoping matters**: Deferring API key support keeps the MVP simple. JWT-only covers web console and CLI (primary use cases).
