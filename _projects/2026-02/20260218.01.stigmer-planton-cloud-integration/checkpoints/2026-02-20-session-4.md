## Summary

Completed the full backend implementation of the `IdentityProvider` resource in `stigmer-cloud`.
This is Phase 1 of the Stigmer × Planton integration. The session also included a proto
cleanup (removing premature lifecycle state management) and a full multi-language stub regeneration.

- Removed `lifecycle_state` field from `IdentityProviderStatus` proto (field 1 reserved)

## Decisions Made

### Removed lifecycle_state from proto

The `active/suspended/revoked` lifecycle state enum was premature. No use case for suspension or
revocation exists in the current MVP scope. When lifecycle management is needed, it will be
re-introduced with proper semantic thought at that time. Field 1 is reserved in the proto to
prevent future field number reuse.

### Restricted FGA access model (not open like agent)

Identity providers are administrative infrastructure. Only owners, org admins, and operators can
view them. Regular org members do not need visibility into the platform trust configuration.
This differs from agents, which follow an open-access model (all org members can view).

### No Temporal for CRUD

Confirmed: all CRUD operations use the synchronous pipeline-based handler framework, consistent
with every other resource type. Temporal is only used for long-running async operations.

### CheckNoReferencingOrgs uses MongoTemplate directly

The delete guard queries the `organization` collection cross-aggregate. Using `MongoTemplate`
directly (rather than going through an OrganizationRepo) is appropriate for a data integrity
guard — it avoids unnecessary coupling between the IAM domain and the tenancy domain.

### Apply handler uses getDefault() pipeline

The `IdentityProviderApplyHandler` uses `applyOperationPipeline.getDefault()` rather than a
custom pipeline (unlike the `AgentApplyHandler` which uses a custom `toBuilder()` pipeline).
This is because the identity provider apply operation has no custom lookup requirements —
the default org+slug lookup covers all cases.

## Learnings

- The FGA access model for a resource is a meaningful design decision — "restricted" vs "open"
  reflects the sensitivity of the resource, not just its scope type.
- protobuf field reservation (`reserved 1;`) is the correct approach when removing fields,
  not just deleting them.
- The `@AutoGrpcRouterController` annotation processor generates command/query controller classes
  at compile time — no manual routing code is needed.
- The apply handler's pipeline choice (`getDefault()` vs `toBuilder()`) depends on whether
  the existence check needs custom scope-awareness.
