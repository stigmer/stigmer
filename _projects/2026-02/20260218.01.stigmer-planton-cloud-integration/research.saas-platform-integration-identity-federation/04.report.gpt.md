# SaaS-to-SaaS Embedded Execution Integration Patterns

## Executive Summary

When one SaaS becomes an **embedded execution provider** for another (your “Product B behind Product A” scenario), successful implementations converge on a small set of repeatable patterns: **(a)** strong tenant isolation primitives inside the provider (e.g., *connected accounts*, *subaccounts*, *namespaces*), **(b)** a cross-platform identity model that separates **who is calling** (the platform/service) from **who is being represented** (the end user), and **(c)** billing/audit surfaces that attribute every action to a tenant and (optionally) a user. You can see these themes in multi-party payment platforms using connected accounts and “act-on-behalf” request scoping, CPaaS providers using subaccounts with per-tenant usage partitioning, and workflow/orchestration providers using namespaces with independent authentication and rate limits. citeturn1search7turn10search0turn5search0

The most robust identity approach for your scenario is an **OAuth “on-behalf-of” style capability** where Product A obtains a **short-lived, audience-scoped token** for Product B that includes both **(1) a user subject** and **(2) a service actor** (or an equivalent representation), rather than passing long-lived API keys or unsigned “user headers.” OAuth Token Exchange (RFC 8693) formalizes this model (including *subject* and *actor* tokens), and large ecosystems implement similar flows (e.g., Microsoft’s OBO flow; Google Cloud STS implementing RFC 8693). Combined with event-driven tenant lifecycle sync and carefully bounded scopes/audiences (per OAuth/JWT BCP guidance), this yields defensible security boundaries, auditable provenance, and debuggable failure modes. citeturn0search4turn8search0turn8search5turn9search0turn9search2turn9search1

## Embedded-provider case studies

**entity["company","Stripe","payments platform"] (platform account → connected accounts; “customers often unaware”)**  
Stripe’s multi-party model centers on **a platform account** that can perform API operations **on behalf of** a specific **connected account** by scoping each request with a connected-account identifier (e.g., via the `Stripe-Account` header in server-side calls). This creates a strong default mapping of “platform tenant → many connected tenants,” and it enables per-tenant isolation and routing of actions without requiring end customers to have any direct relationship with the platform. citeturn1search7turn1search16turn1search3  
Identity-wise, the **caller** is the platform (authenticated by its credentials), while **the operational boundary** is the connected account being acted upon; Stripe also explicitly supports scenarios where “customers transact directly with a connected account, often unaware of your platform’s existence,” which is structurally similar to Product A fronting Product B. citeturn15search2turn15search5  
For attribution, Stripe commonly expects platforms to attach their own identifiers using **metadata** (key-value pairs stored on Stripe objects) rather than relying on Stripe to infer “which app user clicked the button.” This is a canonical example of a provider that supports audit/billing correlation by letting platforms carry identifiers across the boundary. citeturn15search0turn15search3  
Billing-wise, Stripe Connect monetization often involves platform-level fees (e.g., Connect pricing, application fees) and per-connected-account economics; Stripe documentation highlights collecting application fees and the relationship between charge flows and platform revenue. citeturn10search10turn10search2turn10search6  

**entity["company","Twilio","cloud communications platform"] (parent account → subaccounts; provider bills parent, partitions usage)**  
Twilio’s pattern for SaaS multi-tenancy is **subaccounts**, which “allow you to use the Twilio REST API just as you would for a single account,” while keeping phone numbers, applications, calls/messages, and other resources isolated such that managing one subaccount doesn’t affect others. citeturn1search2turn10search11  
Twilio is explicit about the **billing and authentication split** that many embedded execution providers adopt: Twilio “bills all subaccount usage directly to your main account” (the platform), and subaccount credentials can only access that subaccount (not siblings or the parent). This is a direct analogue for “Product B bills Product A, while Product A bills its end customers,” with strong per-tenant attribution at the provider boundary. citeturn10search0  
For attribution, Twilio encourages combining subaccounts with **Usage Records** APIs to build per-end-customer billing models—an example of provider-supported metering surfaces rather than forcing platforms to scrape logs. citeturn10search4  

**entity["company","Auth0","identity platform"] (organizations inside an identity tenant; org context in tokens)**  
Auth0’s B2B multi-tenancy approach illustrates the “organization within an organization” model: Auth0 can represent tenants as **Organizations**, and its docs state that **ID/access tokens include `org_id` by default**; with configuration, tokens can also include `org_name`. citeturn14search0turn14search3  
Auth0 also ties tenant context to login UX and protocol boundaries: depending on configuration, applications must provide an organization in `/authorize` or use flows that prompt users to select an organization. This shows a concrete, production-grade way to ensure a tenant context is always bound to authentication events (reducing “wrong-tenant” ambiguity). citeturn14search1turn14search4  
Auth0’s SAML guidance describes creating user profiles from incoming assertions even when a user record was not pre-created—explicitly calling this **just-in-time (JIT) provisioning**—which is relevant if Product B wants “shadow users” created upon first delegated execution. citeturn11search1  

**entity["company","Okta","identity and access management company"] (multi-tenant configurations; SCIM provisioning ecosystem)**  
Okta’s multi-tenancy documentation is valuable not because Okta is an embedded execution engine, but because it systematically enumerates **tenant modeling options** that mirror SaaS-to-SaaS embedding decisions: tenants can be modeled as **groups/users within a single org**, as **separate orgs (hub-and-spoke)**, or as mixed approaches. This maps closely to whether Product B should use “namespaces/labels,” “1:1 org objects,” or “hierarchical platform tenants.” citeturn14search2

Okta additionally documents **JIT provisioning** (create/update users on login) as an alternative to pre-provisioning, underscoring the common real-world trade: faster integration and lower ops burden vs. weaker “authoritative directory” alignment until SCIM is added. citeturn11search0turn11search4

## Identity federation patterns and recommendations

A useful mental model is to treat Product A → Product B calls as **delegation**: Product A is the *policy/identity authority* for its users, while Product B is the *resource/execution authority* that must enforce scoping, RBAC, audit, and metering. The patterns below differ mainly in where the **trust anchor** lives and how strongly tokens are bounded to tenant/user context. citeturn9search0turn9search2turn0search4  

### OAuth token exchange and on-behalf-of flows

**How it works (technical flow)**  
OAuth Token Exchange (RFC 8693) defines a way for a client to present an existing token (the **subject token**) and optionally an **actor token** to obtain a new token from an authorization server acting as a Security Token Service (STS). This directly matches “Product A has a user session/token; Product A needs a Product B token to perform an execution with tight scoping and auditability.” citeturn0search4turn0search12  

**Real-world adoption signals**  
Google Cloud’s Workforce Identity Federation states it follows OAuth 2.0 Token Exchange (RFC 8693) and exchanges external IdP credentials for short-lived Google access tokens via STS—demonstrating RFC 8693 at hyperscale. citeturn8search5turn8search17  
Keycloak documents token exchange support and positions it as solving “different audience” and related delegation needs, reflecting practical adoption in identity stacks that many SaaS providers embed. citeturn8search1turn8search4  
Microsoft’s identity platform documents an OAuth 2.0 **On-Behalf-Of** flow where a web API receives a user token and exchanges it for a new token to call a downstream API, which is conceptually equivalent to token exchange even if the wire protocol specifics differ. citeturn8search0turn8search3  

**Pros/cons and security properties**  
Token exchange cleanly supports **audience restriction** (mint a token that is only valid for Product B), clear separation of actor vs subject, and short lifetimes aligned with OAuth security best practices. Its risk profile depends on strict JWT validation (issuer, audience, signature, algorithm choices) and least-privilege scope design. citeturn9search0turn9search1turn9search2turn11search23  

**Operational complexity & latency**  
It adds at least one extra network hop (token endpoint/STS) to the request path and requires operating key rotation, client authentication, and debugging “which token did we mint and why.” The upside is that failures are generally *localized* (auth exchange fails fast) rather than producing silent authorization confusion at execution time. citeturn0search4turn9search0turn9search1  

### Direct OIDC/JWT federation between SaaS products

**How it works (technical flow)**  
Product A issues signed JWTs (either access tokens or a purpose-built “execution assertion”) and Product B validates them using Product A’s keys (JWKS), enforcing `iss`, `aud`, expiry, and custom claims (`tenant_id`, `roles`, etc.). This is a common “embedded provider trusts platform tokens” approach when you want lower latency than a token exchange hop. citeturn9search2turn9search1turn9search0  

**Real-world examples to anchor the idea**  
Auth0’s organization tokens model is an example of relying parties validating organization context claims (`org_id`, `org_name`) and validating issuer/audience semantics as part of API authorization, which is conceptually similar to Product B validating Product A’s tenant-and-user assertions. citeturn14search0turn14search11turn14search22  

**Pros/cons and security properties**  
The main pro is **simplicity and latency**: no STS call in the hot path. The main con is **tight coupling** and higher blast radius if Product A’s token semantics change or if Product B’s validation is incomplete. JWT best-practice guidance emphasizes strict validation (including issuer and audience) to prevent token substitution and confusion attacks, and security guidance on JWT algorithms highlights classes of implementation pitfalls (e.g., algorithm confusion) that become existential in cross-tenant scenarios. citeturn9search1turn9search2turn11search23  

### SCIM for user and group provisioning (plus RBAC sync)

**How it works (technical flow)**  
SCIM 2.0 defines schemas (RFC 7643) and an HTTP protocol (RFC 7644) to provision users/groups across domains—originally enterprise-to-SaaS, but applicable whenever one system needs to be the “directory of record.” In embedded execution-provider integrations, SCIM is typically used to ensure Product B has a consistent user directory and group/role assignments that match Product A (or the customer’s enterprise IdP via Product A). citeturn0search1turn0search2turn2search3  

**Real-world examples**  
Okta’s SCIM integration guides describe building SCIM endpoints and wiring them to Okta app integrations; Microsoft’s guidance also positions SCIM as a standardized way to exchange identity data in the cloud ecosystem. citeturn2search3turn0search13turn2search10  

**Pros/cons and latency**  
SCIM generally does **not** add latency to the execution request path because it’s an out-of-band provisioning channel. The trade-off is operational complexity: reconciliation, matching identities, deprovision semantics, and “stale users” cleanup are recurring challenges in real deployments. citeturn0search2turn11search6turn11search14  

### Service account + user context propagation

**How it works (technical flow)**  
Product A authenticates to Product B as a **service identity** (API key, OAuth client credentials, mTLS) and passes end-user identity and tenant context as **signed, integrity-protected metadata** (claims in a JWT, request headers that are part of a signed token, etc.). Providers often design APIs that make this natural by allowing metadata fields or explicit “end-user identifier” parameters. citeturn10search0turn15search0turn4search4  

**Real-world examples**  
Stripe’s metadata feature enables platforms to store their own user identifiers on provider-side objects; OpenAI supports passing end-user identifiers for safety monitoring; AWS STS provides SourceIdentity/session tags for binding downstream actions to upstream identities for audit. citeturn15search0turn4search4turn6search15turn6search1  

**Pros/cons**  
This is often the fastest path to production, but it is also the easiest to get wrong if user context is not cryptographically bound to the request (leading to identity spoofing) or if tenant scoping isn’t enforced in Product B. OAuth/JWT security best practices strongly discourage “implied trust” in bearer tokens and emphasize audience restriction, scope minimization, and robust validation. citeturn9search0turn9search1turn9search2turn13search0  

### Just-in-time user provisioning

**How it works (technical flow)**  
Product B creates a “shadow user” (and possibly org membership) the first time Product A calls Product B on behalf of that user, using claims from the inbound assertion. This is frequently paired with later SCIM adoption for lifecycle correctness. citeturn11search1turn11search0  

**Examples**  
Auth0 describes creating user profiles from SAML assertions when users aren’t pre-created (JIT provisioning). Okta documents enabling “Create and update users on login” as JIT provisioning. citeturn11search1turn11search0  

**Pros/cons**  
JIT reduces initial integration friction but complicates deprovisioning and “ghost user” cleanup without a lifecycle system (SCIM/HRIS/IdP). This is a common failure mode when platforms start with federation-only and later discover their directory has drifted from customers’ real access policies. citeturn11search6turn11search14  

### SPIFFE/SPIRE for service-to-service identity

**How it works (technical flow)**  
SPIFFE defines standards for issuing short-lived workload identities (SVIDs), and SPIRE is a reference implementation that can issue identities used for **mTLS** or **JWT-based** workload authentication. This is most directly relevant for **Product B’s internal service mesh / worker fleet** (and potentially for the A→B service boundary if you want mTLS-based client authentication and strong workload provenance). citeturn7search1turn7search2turn7search4  

**Relevance to your scenario**  
SPIFFE does **not** natively solve end-user federation (it solves workload identity), but it can harden the service-to-service channel that carries user-scoped assertions or exchanged tokens. citeturn7search4turn13search1  

### Practical pattern selection guidance

A compact way to choose:

- If Product B must support **multiple embedding platforms** and **direct users** long-term, token exchange / OBO style boundaries minimize coupling and preserve Product B’s autonomy. citeturn0search4turn8search0turn8search5  
- If you need fastest time-to-market and can accept tighter coupling initially, direct JWT federation can work—but only if you enforce strict JWT validation and tenant scoping, per OAuth/JWT best practices. citeturn9search0turn9search1turn9search2turn11search23  
- If customers demand enterprise-grade joiner/mover/leaver and group-to-role synchronization, SCIM is the ecosystem standard—treat it as a lifecycle channel, not a request-path auth mechanism. citeturn0search2turn2search3turn2search10  

## Tenant mapping and lifecycle synchronization

The “tenant within a tenant” problem is fundamentally about where you place the **isolation boundary** and how you make it **unambiguous** on every request.

**One-to-one mapping (A org ↔ B org)**  
This is the cleanest conceptual model: every Planton org maps to exactly one Stigmer org/workspace, and every Stigmer resource is owned by exactly one workspace. The strongest real-world analogues are “connected account per seller” or “subaccount per customer,” where the provider’s native isolation primitive is used per downstream tenant. citeturn1search16turn1search2turn10search0  

**Hierarchical tenancy (B has a platform container with child tenants)**  
This is essentially the “platform account” (parent) + “sub-tenant” model: Product B represents Product A as a parent/platform tenant, inside which each Product A org becomes a sub-tenant. Stripe and Twilio both reflect this structure, even though their domain language differs (platform/connected accounts vs parent/subaccounts). If Product B will be embedded by multiple platforms, this hierarchy lets Product B segment platform-level policies (rate limits, billing plans, support boundaries) while still isolating end tenants. citeturn1search16turn10search0turn10search11  

**Namespace/label isolation (tenant is a claim, not an object)**  
Some systems model tenancy as “all tenants share one org container; tenant is represented by groups/labels and enforced by authorization.” Okta explicitly calls out this style as hosting tenants “in a single org using Universal Directory,” where tenants are abstracted using users/groups rather than first-class tenant objects. This can reduce management overhead, but it increases the risk that a missing filter or a bug becomes a cross-tenant data exposure. citeturn14search2turn9search0  

**Event-driven sync for lifecycle (create/update/suspend/delete)**  
Providers commonly rely on **event/webhook** patterns to sync state across boundaries. Stripe, for example, has Connect webhooks that send “events on connected accounts” to platform endpoints—an illustration of how providers externalize tenant lifecycle changes and operational events. citeturn10search1turn10search9  
In your architecture, event-driven sync should cover at minimum: org created, org renamed, billing plan changed, org suspended, org deletion initiated, org deletion completed. The key pitfall is eventual consistency: execution requests may arrive before provisioning completes unless Product B can create/migrate tenants idempotently or enforce “tenant must exist to execute” with a clear error path. Stripe’s emphasis on idempotent requests provides a reliable pattern for these distributed workflows. citeturn15search1turn15search4  

**Deletion semantics (cascade, soft delete, orphan prevention)**  
Execution engines often need “soft delete” and “disable new executions” semantics before hard deletion. Temporal’s community guidance about “deprecate namespace” vs “delete namespace” illustrates why: you may need to stop new work while allowing in-flight work to complete, then enforce retention policies. citeturn5search6turn5search10  
For GDPR or contractual compliance, you’ll typically want explicit processor/controller contractual controls and defined retention windows; GDPR Article 28 emphasizes processor obligations governed by contract, and EU guidance clarifies controller vs processor roles (often, Product B becomes a sub-processor when embedded). citeturn12search1turn12search4turn12search5  

## Product architecture and positioning trade-offs

Your identity and tenancy model should follow the product positioning you choose for Stigmer (Product B): standalone, embedded, or hybrid.

**Standalone SaaS (B has its own UI/users/billing)**  
In this model, Product B is an independent destination with its own identity system and tenant model. Embedding then resembles partner integration: you either do token exchange/OBO (so Product B remains an authority over its own tokens) or you require users to authenticate into B directly (less “embedded”). Platforms like Stripe and Twilio demonstrate how providers can be fully standalone while still supporting platform-style tenant partitioning. citeturn1search16turn10search0turn10search4  

**Embedded/white-label engine (B is invisible; B is a backend substrate)**  
Here, Product B behaves more like an internal dependency: minimal direct user interaction, platform-level billing, and strong emphasis on programmatic tenant lifecycle and attribution. Stripe’s “customers often unaware of your platform’s existence” language (in reverse) captures this invisibility dynamic; Twilio’s “subaccount per end customer” and parent-billed usage is also a close analogue. citeturn15search2turn10search0  

**Hybrid platform (B serves direct users and embedding platforms)**  
This is the hardest but most strategically powerful position: you must support both “users log in directly” and “requests come from a platform on behalf of users.” Stripe, Twilio, and identity platforms (Auth0/Okta) all operate in this hybrid reality: they serve direct accounts while enabling delegation models (connected accounts/subaccounts/orgs) for platforms and enterprise customers. citeturn1search16turn10search0turn14search0turn14search2  
Engineering cost drivers include: dual onboarding flows, dual billing/reporting, more complex support/debugging (you must reason about platform-level incidents vs tenant-level incidents), and sharper compliance boundaries because you become a subservice organization whose controls impact customers’ assurance needs. SOC 2 guidance frames these concerns around controls relevant to security/availability/confidentiality/privacy, and SOC subservice organization treatment (carve-out vs inclusive) becomes a recurring sales and audit conversation as you embed deeper into customers’ critical paths. citeturn12search2turn12search6turn12search19  

**Build vs buy (when A should build its own agent execution instead)**  
A common inflection point is whether Product B’s differentiation comes from a general-purpose execution substrate (scheduling, retries, isolation, credentials brokering, audit, metering, multi-tenant controls) that would be expensive for Product A to replicate. If Product B’s value is primarily “a thin wrapper around workflows,” Product A may prefer to build. If Product B provides robust multi-tenancy isolation and independent authentication primitives (namespaces, API keys/mTLS, RBAC, rate-limits), it more closely resembles an infrastructure substrate that is rational to buy/partner on. Temporal Cloud’s positioning around namespace isolation and independent authentication is an example of the kind of substrate capabilities that typically justify “buy” or “integrate.” citeturn5search0turn5search7turn5search1  

## Security deep dive for cross-platform authentication

The core security goal is: **a compromise or misconfiguration in Product A must not become a cross-tenant compromise inside Product B**, and Product B must maintain **cryptographically defensible provenance** for every action.

**Token scoping and audience restriction**  
OAuth security best current practices emphasize least privilege and deprecate weaker modes; JWT best practices emphasize strict validation for issuer/audience and careful algorithm handling. In cross-platform delegation, always scope tokens to: *(a)* the specific Product B API audience, *(b)* the tenant/workspace identifier, and *(c)* the minimum execution permissions required. citeturn9search0turn9search1turn9search2  
Auth0’s guidance around organization-aware tokens underscores the same lesson: if an org claim is present, APIs should validate it to ensure the received value is expected/known—this is exactly the shape of the tenant-claim validation Product B must do. citeturn14search22turn14search11  

**Token lifetime, replay protection, and sender-constrained tokens**  
Short-lived tokens reduce the blast radius of leakage (JWT/ OAuth best practices). For high-risk operations (infrastructure deployment, credential minting), consider sender-constrained tokens via mTLS-bound tokens (RFC 8705) or DPoP (RFC 9449), which are explicitly designed to detect/prevent replay if a bearer token leaks. citeturn9search1turn13search1turn13search0  

**Audit trail integrity (end-to-end actor chain)**  
Keep both identities:  
- **Actor**: Product A service identity that called Product B (who is the technical caller?).  
- **Subject**: Product A end user whose intent triggered the execution (who should be attributed in audit/billing?).  

RFC 8693 explicitly supports subject/actor token semantics for delegation chains. AWS’s SourceIdentity and session tags show how major platforms operationalize this: record the originating identity in logs alongside the assumed-role identity, enabling traceability in CloudTrail. citeturn0search4turn6search15turn6search1turn6search0  

**Blast radius management and tenant isolation**  
Real-world providers reduce blast radius by isolating tenants into provider-native containers and credentials: Twilio subaccounts restrict what credentials can access and bill usage to the parent while partitioning resources; Temporal Cloud namespaces provide independent authentication and separate rate limits; Stripe scopes operations to connected accounts per request. These patterns directly reduce the probability that one tenant’s credentials or an authorization bug exposes another tenant’s resources. citeturn10search0turn5search0turn1search16  

**Secrets and trust relationship management**  
If you implement token exchange or signed assertions, you will manage signing keys, certificates, or client secrets. Standards-based approaches make rotation and validation behavior more predictable: JWT defines token structure; JWT BCP recommends validation and handling practices; OAuth BCP provides guidance on modern OAuth threats and mitigations. For service-to-service channels, SPIFFE/mTLS can replace long-lived shared secrets with attested, short-lived workload identities. citeturn9search2turn9search1turn9search0turn7search4turn13search1  

**Compliance implications (SOC 2 / GDPR)**  
Once Product B executes actions on behalf of Product A’s users and stores logs/identifiers, Product B becomes part of Product A’s control environment. SOC 2 is explicitly about controls relevant to security/availability/processing integrity/confidentiality/privacy of systems used to process customer data, which will include your cross-platform identity flows and audit logs. citeturn12search2turn12search6  
For GDPR, the controller/processor distinction is central: the EU’s guidance states the controller determines “why and how” personal data is processed, and Article 28 requires processor relationships to be governed by contract with specific obligations. In embedded-engine models, Product B frequently becomes a sub-processor for Product A (or a processor directly), which affects DPAs, breach notification paths, and deletion/retention commitments. citeturn12search4turn12search1turn12search5  

## Anti-patterns and a recommended architecture for Planton and Stigmer

### Anti-patterns and pitfalls

**Unsigned or weakly signed “user context headers”**  
Passing `X-User-Id: ...` style headers without a cryptographic binding to the caller (and without strict token audience/issuer controls) invites identity confusion and spoofing. JWT/OAuth best practices emphasize strict validation precisely to prevent token substitution and related confusion classes. citeturn9search1turn9search0turn9search2  

**Overly permissive JWT validation (“accept anything that looks like a JWT”)**  
Algorithm confusion attacks are a known JWT pitfall if libraries are misconfigured (e.g., accepting `none` or mixing symmetric/asymmetric algorithms incorrectly). In a multi-tenant provider, these errors can become cross-tenant compromise vectors. citeturn11search23turn9search1  

**Long-lived shared API keys across many tenants**  
This collapses blast radius: a leaked key can impersonate the entire platform across all downstream organizations. Providers that support subaccounts/namespaces/connected accounts demonstrate why per-tenant scoping and independent auth boundaries are so common. citeturn10search0turn5search0turn1search16  

**Directory drift: JIT provisioning without lifecycle controls**  
Starting with federation/JIT is common, but many teams later discover “ghost users” and stale access when the customer’s directory changes. Without SCIM or an equivalent lifecycle channel, deprovisioning semantics are fragile. citeturn11search6turn11search14  

**Tight coupling of auth semantics (breaking changes ripple across products)**  
If Product B directly consumes Product A’s internal RBAC model (roles, policies, permission names) without a stable contract layer, any change in Product A’s auth system can break execution authorization in Product B. OAuth token exchange or a stable “execution assertion” contract reduces this coupling by freezing the boundary into a versioned token/claims interface. citeturn0search4turn9search0turn9search2  

**Billing disputes from weak attribution**  
If you can’t prove “who (tenant/user) caused which execution,” billing becomes a trust problem. Twilio’s explicit combination of subaccounts + usage records and Stripe’s connected-account scoping + metadata patterns show how providers design for attribution-first economics. citeturn10search4turn15search0turn1search16  

### Recommended approach for Planton ↔ Stigmer

This recommendation assumes:  
- Planton is the user-facing control plane and the authoritative user identity/RBAC system.  
- Stigmer is a general-purpose execution provider that may later serve other platforms and possibly direct users.

**Choose a tenant model that matches your long-term product plan**  
Adopt a **hierarchical tenancy** in Stigmer: a “Planton platform tenant” containing one Stigmer workspace per Planton organization. This mirrors proven provider models (platform/connected accounts; parent/subaccounts) and keeps a clean mental model when Stigmer later supports additional embedding platforms. citeturn1search16turn10search0turn14search2  

**Make Product B authoritative over its own execution tokens (best for hybrid future)**  
Implement an STS endpoint in Stigmer that supports an **on-behalf-of / token exchange** flow. Concretely:  
1) Planton authenticates the user and holds a user session/token.  
2) Planton authenticates itself to Stigmer (client credentials, mTLS, or private-key JWT).  
3) Planton performs token exchange: subject = Planton user token (or a Planton-signed execution assertion), actor = Planton service identity, requested audience = Stigmer API, requested scope = minimum execution permissions.  
4) Stigmer issues a short-lived Stigmer access token that includes claims like: `tenant_id` (mapped workspace), `sub` (Planton user stable ID), `act` (Planton service principal), `scopes`, and a unique request ID for audit correlation.  

This follows RFC 8693’s model directly and aligns with real-world “delegate to downstream API” patterns used by large identity ecosystems. citeturn0search4turn8search0turn8search5  

**If you need a phase-zero implementation, do “service account + signed user assertion” (but make it upgradeable)**  
You can ship faster by having Planton call Stigmer with a service credential and include a Planton-signed JWT assertion containing user+tenant claims. However, design the JWT claims and validation rules as if it were the output of token exchange (strict `iss`/`aud`, short TTL, rotation), so migrating to full token exchange is a refactor of token minting, not a rewrite of authorization logic. citeturn9search1turn9search2turn9search0  

**Use SCIM only when you truly need directory synchronization**  
Start with **no full user sync**: Stigmer can store the Planton user ID as an external subject and optionally create internal “shadow users” on first use (JIT). Add SCIM later for enterprise customers that demand centralized deprovisioning and group-to-role sync. This maps to how many identity integrations evolve: federation/JIT first, lifecycle provisioning second. citeturn11search1turn0search2turn2search3  

**Adopt an audit model that preserves an actor chain**  
Store (and expose via APIs/log export):  
- Planton org ID + Stigmer workspace ID  
- Planton user stable ID (subject)  
- Planton service identity (actor)  
- Execution request ID, idempotency key, timestamps  
- Authorization decision inputs (effective scopes/roles)  

Use the AWS “SourceIdentity” concept as an inspiration: always keep the originating identity attached to downstream activity for later forensics and dispute resolution. citeturn6search15turn6search0turn0search4  

**Prevent replay and minimize blast radius by construction**  
Use short-lived tokens (minutes, not days), consider DPoP or mTLS binding for high-risk operations, and isolate credentials per Planton org/workspace (or at least per platform tenant + strict claim scoping). This is consistent with modern OAuth best practices and with how providers like Twilio and Temporal design independent authentication boundaries. citeturn13search0turn13search1turn10search0turn5search0turn9search0  

**Design deletion and suspension as first-class lifecycle states**  
Implement a two-phase lifecycle:  
- **Suspend / disable new executions** immediately when Planton org is suspended or deletion is initiated.  
- **Retain for a defined window** to allow recovery and handle in-flight executions, then hard-delete per contract.  

Temporal’s public “deprecate vs delete” framing illustrates why this is operationally necessary for execution engines. Align this with GDPR processor obligations and your DPA commitments. citeturn5search6turn12search1turn12search4  

**Billing model recommendation**  
Bill Planton as the parent/platform account and expose per-tenant usage rollups (per Planton org/workspace) sufficient for Planton to bill its customers and resolve disputes. This is strongly analogous to Twilio’s “bill parent, partition usage by subaccount” and to usage attribution patterns seen in embedded API providers. citeturn10search0turn10search4turn4search10
