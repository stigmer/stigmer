Across mature SaaS ecosystems, “Platform A embeds Platform B” is rarely a single technique. ## Architecture patterns that solve your core problem

Your “core problem” decomposes into two independently solvable layers:

- **Delegation / identity propagation** (how B knows *who* and *which org* this request is for, and that A is allowed to assert it).
- **Surface area minimization** (how A calls “execute agent X” without re-implementing B’s domain model).

The most reusable framework for the delegation layer is **Security Token Service (STS)** thinking: a token minted in one trust domain is exchanged or re-issued for a token usable in the next domain. This is explicit in OAuth 2.0 Token Exchange (RFC 8693), which frames the authorization server as an STS and standardizes “subject token” (end-user) and optionally “actor token” (the caller acting on behalf of the user). citeturn23view0turn14view1

## The API key problem: when the originating credential is opaque

Your key observation is correct: an opaque API key has **no portable claims**, so there is nothing meaningful to “forward.” Industry patterns strongly suggest you should **not try to propagate the original credential at all**. Instead, treat API keys as an **authentication method local to Platform A**, and then convert the resolved principal into a **short-lived, claim-bearing token** suitable for cross-domain delegation. This is exactly how “server mints something else” patterns work in multiple domains:

- In the realtime browser pattern, the developer’s server uses a long-lived secret to mint an **ephemeral** token for the browser; the browser never sees the long-lived credential. citeturn22view1  
- In the integration framework example, “user auth” is represented by a JWT identifying the user, regardless of how the user originally authenticated to the provider’s UI. citeturn9view0  
- In feature-flag evaluation, the per-user identity is a *context payload* containing a required `key` (identity-in-payload), not a provider-issued end-user login token. citeturn10search2turn10search15  

### Practical answer for your scenario

The cleanest way to solve “opaque API key → B needs identity” is:

- Platform A resolves `api_key → principal (user_id, org_id, roles, rate-limit tier)`.
- Platform A mints a **short-lived “subject token” JWT** with those claims.
- Platform B accepts that JWT either:
  - directly (A-signed JWT verification), or
  - indirectly via **token exchange** (recommended) where B issues a B-native access token.

This approach ensures Platform B’s integration layer does **not** care whether Platform A authenticated via JWT login or API key; it only cares that Platform A is a trusted issuer of the asserted subject identity (and that the assertion is bounded in time and scope). citeturn23view0turn14view1turn22view1

## Federating identity across separate Auth0 tenants

When two systems have different issuers, audiences, key material, and user stores, “just forward the JWT” fails for the same reason API-A tokens should not be accepted by API-B: audience and trust boundaries. The token-exchange family of solutions exists precisely to handle this. citeturn14view1turn23view0

### What “good” federation looks like in cloud identity systems

Large cloud identity systems provide a very consistent blueprint:

- Configure trust in an external OIDC issuer and exchange the external token for a **short-lived** token issued by the target system (an STS pattern). citeturn5search8turn5search13turn5search2  
- The target system emphasizes keyless or reduced-secret approaches and token exchange for safer operations (short-lived credentials instead of distributing long-lived secrets). citeturn5search13turn5search2  
- The model generalizes: establish trust → exchange token → use target-issued token to access protected resources. citeturn5search12turn5search1turn5search10  

This is conceptually the same shape you want between Platform A and Platform B, except the “protected resources” are Platform B’s agent/workflow APIs and the STS is your chosen identity layer (potentially Platform B’s Auth0 tenant). citeturn23view0turn14view1

### Auth0-specific insight that matters for you

Two facts are especially relevant:

- A single access token typically targets a single “audience” resource server, and the recommended fix for cross-API access is to obtain different tokens rather than overload one token with multiple audiences. citeturn5search7turn5search17  
- Auth0 has introduced **Custom Token Exchange** as an OAuth grant-type feature enabling token exchange (RFC 8693) with custom logic (Actions), including “exchange tokens for different audiences” and more complex integration scenarios where standard federation isn’t feasible. citeturn14view0turn14view2turn14view1  

Even if you do not use Auth0’s feature directly, the trendline is strong evidence that “token exchange for OBO + audience correction” is now a mainstream solution and aligns with your requirements. citeturn14view1turn23view0turn8search19

### Is JWKS-based federation “the right approach”?

Publishing JWKS and trusting an external signer is a valid building block, but on its own it answers only “can I verify signatures?” not “should I accept this token for this resource, for this scope, with this revocation and audit model?” Token exchange lets you take a verified external assertion and **re-issue** a token with:

- the correct `aud` for Platform B,
- Platform B’s own expiry/refresh policy,
- Platform B’s own custom claims, and
- a point to enforce org mapping and policy. citeturn14view1turn23view0turn14view2  

This is why modern guidance often combines JWT assertions (RFC 7523) with token exchange (RFC 8693) for identity chaining across trust domains. citeturn0search15turn23view1turn23view0  

Separately, OpenID Federation 1.0 (finalized February 17, 2026) is expressly about scaling trust establishment and metadata exchange across parties (bilateral and multilateral) using signed statements and trust chains. It’s relevant if you expect many third-party issuers or dynamic onboarding, but it is usually heavier than you need when **both platforms are under one engineering org**. citeturn24view0turn24view1

## Recommendation for your exact scenario

Your requirements are unusually favorable because **you control both platforms**. That lets you optimize for simplicity and security without external commercial constraints.

### Recommended north-star design

Adopt an **STS-style delegation boundary** between Platform A and Platform B built on:

- **User assertion** minted by Platform A (short-lived JWT, regardless of whether the user authenticated via A-JWT or A-API-key).
- **Token exchange** at Platform B to mint a Platform-B access token (`aud = platform-b-api`) that Platform B’s gRPC services accept natively.
- A parallel **machine-to-machine** flow for system tasks (org creation, entitlement sync, billing sync).

This matches (a) the “on-behalf-of” pattern described for token exchange and audience correction, and (b) the explicit separation of “user authentication” and “system authentication” seen in integration frameworks. citeturn14view1turn23view0turn9view0

### Concrete flows

#### User-context call flow

Platform A receives either:
- an Auth0 login JWT, or
- an opaque API key it resolves to user identity.

Then:

- **Step:** A mints a short-lived JWT assertion (“subject token”) with at least:
  - stable external subject: `sub = a|<user_id>` (or similar),
  - `exp` (very short TTL), `iat`,
  - external org id: `a_org_id`,
  - optional: `email` (or a privacy-preserving hash), plan, and rate-limit tier,
  - optional replay defense: `jti`.

- **Step:** A calls Platform B’s token service (STS) using OAuth 2.0 Token Exchange (grant type `urn:ietf:params:oauth:grant-type:token-exchange`). citeturn23view0turn14view1  
  - “Subject token” = the A-minted JWT.
  - Optional “actor” identity = Platform A’s own service identity (either via client authentication or explicit actor token, depending on implementation). citeturn14view1turn23view0  

- **Step:** Platform B verifies:
  - A is an allowed issuer and signature is valid (JWKS trust),
  - `aud` is correct for the exchange endpoint,
  - token hasn’t expired,
  - org mapping exists (or lazily creates B-org on first use).

- **Result:** Platform B issues a Platform B access token with correct `aud` for Platform B APIs and any claims B needs for:
  - OpenFGA authorization checks,
  - audit trails,
  - per-user/per-org rate limiting.

This is precisely the OBO “audience correction” motivation described: passing the original token to the downstream API is wrong because it is audience-bound; token exchange preserves user context while producing a properly scoped token for the downstream API. citeturn14view1turn23view0turn14view2

#### System-level call flow

Use a separate OAuth client identity for Platform A-as-a-system:

- Platform A obtains a machine token (client credentials) for system endpoints like “create org,” “sync org status,” and “billing/meters.” This follows standard “M2M” guidance for flows where there is no interactive user. citeturn8search5turn19view1  
- Platform B enforces that these tokens cannot call user-context endpoints unless explicitly allowed.

This mirrors the explicit split in real integration frameworks where system automation uses account-level credentials, while user actions use user identity tokens. citeturn9view0

### What Platform B should ship to make Platform A’s integration minimal

To meet your “Platform A writes minimal code” constraint, the provider side should package the above into one of two distributable integration surfaces (ideally both):

- **A thin SDK** (your Go library idea), whose only responsibilities are:
  - construct subject assertion from a user principal,
  - execute token exchange and cache results,
  - call the gRPC methods (generated client),
  - standard retries/backoff and structured audit headers.
  
  This mirrors the “SDK-first” embedding style used by feature-flag platforms (SDK keys + evaluation calls) and deployment APIs offering SDK usage as an option. citeturn10search8turn9view2  

- **An optional gateway/proxy container**, for teams who want “deploy image + set env vars”:
  - The proxy receives a minimal input contract from Platform A (e.g., `X-A-User-Id`, `X-A-Org-Id`, and a signed assertion or HMAC), performs token exchange, then forwards to Platform B’s gRPC/HTTP front door.
  - If you go this route, treat the proxy like the Relay Proxy example: document how to run it (Docker/Helm), how to configure it (env vars), and explicitly document resiliency requirements because proxies become critical-path infrastructure. citeturn21view1turn21view2  

This “SDK + optional proxy” dual-shipping approach is common: providers offer the simplest path first, then an infra-heavy option for scale/network constraints. citeturn21view2turn20view1

### How to map Platform A orgs/users to Platform B orgs/users without re-implementing B’s domain

Use a strict separation:

- **Provisioning interface:** Platform B exposes a small set of “tenant bootstrap” APIs (create org, link external org id, create default policy bindings). These are system-level calls.  
- **Execution interface:** Platform A calls high-level “execute agent/workflow” APIs with identifiers that Platform B owns.

You can implement “org creation” either:
- eagerly (when org created in A), or
- lazily (first time an org invokes B).

The lazy model is consistent with how embedded partner funnels create/link accounts during first use (trial account creation/linking). citeturn19view0turn18view0

For authorization, ensure Platform B’s access tokens include stable subject IDs and tenant IDs that your fine-grained authorization layer can consume; OpenFGA’s guidance emphasizes avoiding PII in authorization tuples and using stable identifiers—fit naturally with `sub`-style IDs. citeturn11search1turn11search0

### Why token exchange is usually the best “easy + correct” identity bridge

From a Platform A engineer’s perspective, RFC 8693-style exchange is attractive because it is:

- A single standardized token endpoint call (simple HTTP + JSON/form encoding). citeturn23view0turn8search19  
- The canonical way to preserve user context while producing a token valid for the downstream audience. citeturn14view1turn23view0  
- Compatible with JWT client authentication (RFC 7523) so you can avoid long-lived shared secrets between platforms if desired. citeturn23view0turn23view1  

### Security properties and risks for your recommended approach

If you implement **A assertion → B token exchange → B API call**, the key properties are:

- **Blast radius control:** If a single user assertion leaks, it should be short-lived; the exchange endpoint should also enforce that only Platform A (authenticated client) can exchange it, reducing the risk of a stolen token being “upgraded” into other tokens. RFC 8693 explicitly warns that omitting client authentication can allow a compromised token to be leveraged by anyone possessing it. citeturn23view0turn14view1  
- **Replay resistance:** Short TTL helps, but for high-risk endpoints you should also incorporate `jti` and maintain a brief replay cache window on Platform B. (This is an implementation recommendation derived from standard JWT threat models; the core need for careful validation is consistent with JWT-based auth requirements.) citeturn23view1turn9view0  
- **Audience correctness:** Token exchange exists specifically to avoid downstream services accepting upstream tokens with the wrong `aud`. citeturn14view1turn23view0  
- **Key management:** If you use signed assertions, you need rotation. The “app model” example shows a well-trodden operational path: platform-held private key signs JWTs; provider validates and issues a narrower token. citeturn2search11turn2search3turn2search7  
- **Proxy/gateway risk:** If you ship a deployable proxy for “zero code,” it becomes part of the critical path. Real proxy docs call out resiliency requirements (multiple instances, load balancer) and that poor configuration can reduce reliability compared to direct SDK usage. citeturn21view2turn21view1  
- **Avoid leaking long-lived secrets:** Multiple sources emphasize not exposing long-lived API keys client-side and instead minting ephemeral tokens or using client-safe tokens. citeturn22view0turn22view1turn20view0  

## Standards and specifications relevant to your design

This list focuses on specs that directly map to the mechanisms you’re considering (token exchange, JWT assertions, provisioning, federation).

- **OAuth 2.0 Token Exchange (RFC 8693)**: Defines the `urn:ietf:params:oauth:grant-type:token-exchange` grant; describes STS behavior, `resource` indication, and highlights the importance of client authentication to prevent misuse of compromised tokens. citeturn23view0turn8search19  
- **JWT Profile for OAuth 2.0 (RFC 7523)**: Defines JWT bearer authorization grants and JWT-based client authentication; intended to bridge trust domains using JWT semantics. citeturn23view1turn0search27  
- **OpenID Connect Core 1.0**: The primary identity layer on top of OAuth 2.0 used broadly for user authentication and claims. citeturn4search26turn4search35  
- **SCIM 2.0 (RFC 7643 + RFC 7644)**: Standard schemas and protocol for cross-domain identity provisioning; relevant if Platform A ever wants to provision/manage users in Platform B (even if invisible to the end user). citeturn4search5turn4search1  
- **OpenID Federation 1.0 (Final, Feb 2026)**: Trust establishment via signed entity statements and trust chains; relevant for scalable federation across many issuers, likely heavier than needed for two systems under one org. citeturn24view0turn24view1  
- **Workload identity federation patterns (cloud STS analogies)**: Although outside SaaS UI embedding, they validate the architectural shape: configure trust to an external issuer and exchange external tokens for short-lived access tokens/credentials. citeturn5search13turn5search12turn5search2
