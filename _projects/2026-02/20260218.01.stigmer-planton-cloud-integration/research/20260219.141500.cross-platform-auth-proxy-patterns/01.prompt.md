# Deep Research: SaaS-to-SaaS Integration — How Platform A Embeds Platform B's Capabilities

## Research Objective

We have two independent SaaS platforms:

- **Platform A** — A cloud deployment and infrastructure management platform (think Vercel, Heroku, or Render). It has its own users, organizations, Auth0-based authentication, and API key support.
- **Platform B** — An AI agent execution platform (think Temporal Cloud or LangSmith). It has its own users, organizations, Auth0-based authentication (separate Auth0 tenant from Platform A), API key support, and fine-grained authorization (OpenFGA).

**The goal**: Platform A wants to offer Platform B's capabilities (running AI agents, workflows, etc.) to its users. Platform A's users should be able to trigger Platform B operations directly from Platform A's UI and API — without ever needing to sign up for Platform B separately, without knowing Platform B exists, and without Platform A having to re-implement Platform B's domain (agents, workflows, execution engine, etc.).

**The constraint**: Platform A wants the integration to be as simple as possible. Ideally, Platform A writes minimal code. Platform B should provide whatever is needed (SDK, proxy, gateway, embedded service, or something else entirely) so that Platform A can get started quickly.

## The Core Problem

Platform A's users authenticate to Platform A (via Platform A's Auth0 or API keys). When they trigger an action that needs Platform B, **something** needs to:

1. **Carry the user's identity** from Platform A to Platform B (so Platform B knows WHO is making the request — for audit trails, per-user authorization, and per-user rate limiting)
2. **Map Platform A's organizations** to Platform B's organizations (or create them)
3. **Authenticate the cross-platform call** securely (Platform A's Auth0 tokens are not valid for Platform B — separate Auth0 tenants, separate audiences, separate signing keys)
4. **Not require Platform A to re-model Platform B's domain** — Platform A should be able to call "execute agent X" without understanding how agents work internally

Both platforms support two auth methods:
- **JWT bearer tokens** (from Auth0 login) — can be decoded to extract claims like `sub`, `email`, `iss`, `aud`
- **API keys** (opaque strings like `ptk_xxx` or `stk_xxx`) — validated by hash lookup, no embedded claims, bound to an owner identity

When Platform A's user authenticates via an API key, Platform A's backend knows the user (via database lookup of the API key owner), but there's no JWT with embedded claims to forward or transform.

## What We Need Researched

### 1. How do world-class SaaS platforms embed another SaaS platform's capabilities?

We want to understand the full spectrum of integration approaches used in production by real companies. Not just auth patterns — the **entire integration architecture**:

- **Stripe Connect** — How does a platform (like Shopify) embed Stripe's payment processing? What does Stripe provide to make this easy?
- **Twilio** — How do platforms embed Twilio's communications capabilities? What's the integration model?
- **Auth0 Organizations** — How does Auth0 enable platforms to embed identity management for their customers?
- **Temporal Cloud** — How do platforms embed Temporal's workflow execution? What does Temporal provide?
- **OpenAI API** — How do platforms like Microsoft (Copilot) or Notion embed OpenAI's capabilities? Is it just API keys, or something more?
- **Vercel / Netlify** — How do they integrate with external services (databases, CMS, etc.) on behalf of their users?
- **AWS Marketplace SaaS integration** — How does AWS enable SaaS products to be embedded into customer workflows?
- **Snowflake Partner Connect** — How does Snowflake enable partner tools to integrate?
- **LaunchDarkly / Split.io** — How do they enable platforms to embed feature flagging for their customers?
- **Datadog / New Relic** — How do observability platforms enable embedding into other platforms?

For each, identify:
- What does the provider (Platform B equivalent) ship? (SDK? Proxy? Gateway? API keys? OAuth app? Embedded iframe?)
- How is user identity carried across platform boundaries?
- How much code does the integrating platform (Platform A equivalent) need to write?
- How are organizations/tenants mapped?
- What auth mechanism is used for cross-platform calls?

### 2. What are the known integration architecture patterns?

Catalog the architectural approaches:

- **Direct API + SDK** — Platform A imports Platform B's SDK, calls it from their backend
- **Auth proxy / gateway** — Platform B ships a proxy that Platform A deploys; handles auth transformation
- **OAuth2 app model** — Platform B provides an OAuth2 "app" that Platform A authorizes (like GitHub Apps, Slack Apps)
- **API key delegation** — Platform B issues API keys scoped to Platform A's org
- **Token exchange (RFC 8693)** — Platform A's token is exchanged for Platform B's token
- **JWT assertion (RFC 7523)** — Platform A signs JWTs that Platform B trusts
- **Webhook / event-driven** — Platform A sends events, Platform B processes them
- **Embedded UI (iframe / web components)** — Platform B provides embeddable UI that runs inside Platform A
- **White-label / OEM** — Platform B runs as a white-labeled service within Platform A's infrastructure
- **Service mesh / sidecar** — Platform B runs as a sidecar alongside Platform A's services
- **Any other patterns discovered in research**

For each pattern:
- What's the integration effort for Platform A? (lines of code, infrastructure changes, ops burden)
- How is per-user identity preserved?
- How is organization mapping handled?
- Security properties (blast radius, key compromise impact, replay protection)
- Real-world examples of who uses this pattern

### 3. The API key problem specifically

When Platform A's user authenticates via an opaque API key (not JWT), the API key carries no claims. Platform A's backend can resolve the owner via database lookup, but:

- How should this identity be propagated to Platform B?
- Do any platforms solve this elegantly?
- Is there a standard for "I know who the user is, but the original auth credential was opaque"?
- Should Platform B's integration layer even care how Platform A authenticated its user? Or should it just receive a user identifier?

### 4. What makes an integration "easy" for Platform A?

From Platform A's perspective, what's the ideal integration experience? Research what developers actually prefer:

- "Deploy this image and set 5 env vars" (zero code)
- "Import this SDK and call functions" (minimal code)
- "Configure this OAuth app" (zero code, UI-based setup)
- "Add this webhook URL" (zero code)
- Something else?

What do developer experience studies, DX surveys, and integration adoption metrics say about which approaches get the highest adoption?

### 5. Identity federation across independent Auth0 tenants

Both platforms use Auth0 but on completely separate tenants (separate signing keys, separate audiences, separate user databases). Specifically:

- How do platforms with separate identity systems federate user identity?
- Is Auth0's Organization or Enterprise Connection feature relevant here?
- How do AWS IAM OIDC Identity Providers, GCP Workload Identity Federation, and Azure AD Federated Identity Credentials solve this?
- What's the simplest approach when both platforms are under the same engineering team's control?
- JWKS-based federation — is this the right approach or is there something better?

### 6. Machine-to-machine vs. user-context calls

Platform A needs to make two types of calls to Platform B:
- **On behalf of a user**: "User X wants to run agent Y" — needs per-user identity
- **System-level**: "Create an organization", "Sync org status" — no specific user, just Platform A's system

How do platforms handle both through the same integration? Is it one mechanism or two?

## Context About Our Current Thinking

In our design discussions, we've considered:

1. **A proxy/gateway** that Platform B ships as a Docker image. Platform A deploys it with env vars (private key, endpoint, etc.). It sits between Platform A's backend and Platform B's API, handling auth transformation (minting JWTs for Platform B).

2. **An SDK** (Go library) that Platform A imports. Handles JWT minting and API calls internally. Platform A writes handlers for each operation.

3. **JWT assertion (RFC 7523)** — Platform A generates its own signing key pair, publishes public keys via JWKS (even on GitHub Pages), and signs short-lived JWTs for each cross-platform call. Platform B validates these against the published JWKS.

We want the research to **validate, challenge, or improve** these ideas. Maybe there's a much better approach we haven't considered. We want to know what the industry best practice is, backed by real examples.
