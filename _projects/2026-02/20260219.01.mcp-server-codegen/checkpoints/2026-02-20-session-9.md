## Decisions Made

- **Cross-package imports over inline re-generation**: Rather than creating a parallel naming scheme (e.g., `ProjectAgentInput` vs `AgentInput`), we reuse the already-generated `*Input` types from sibling packages. This keeps a single source of truth for each resource's input type and avoids naming proliferation.
- **Resource wrapper detection via structural pattern matching**: `isResourceWrapper()` checks for the canonical 4-field pattern (`api_version`, `kind`, `metadata` with `ApiResourceMetadata`, `spec`) rather than maintaining a hardcoded list of wrapper types.
- **Exported vs unexported ToProto()**: Cross-package types use the exported `ToProto()` method; same-package types use the unexported `toProto()`. The `useExportedToProto` flag on `mcpInputField` controls this cleanly.

## Learnings

- Composite resources that embed full resource wrappers are a natural pattern in aggregate-root APIs. The cross-package import strategy generalizes well — any future composite resource will be handled automatically by the same detection logic.
- The structural pattern for resource wrappers (`api_version` + `kind` + `metadata` + `spec`) is reliable and avoids brittle naming heuristics.
