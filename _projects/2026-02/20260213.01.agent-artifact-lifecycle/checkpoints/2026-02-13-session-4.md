- Returns presigned URL + ISO 8601 expiration timestamp

## Decisions Made

### 1. Separate R2 Bucket
**Decision**: Use dedicated bucket for agent execution artifacts
**Rationale**:
- Different lifecycle policies (artifacts expire, skills are permanent)
- Independent cost tracking and scaling
- Security isolation (different IAM credentials)

### 2. Domain-Specific Storage
**Decision**: Create `AgentExecutionArtifactR2Store` separate from `SkillArtifactR2Store`
**Rationale**:
- Different storage semantics (content-addressable vs path-based)
- Different features (presigned URLs vs direct download)
- Better maintainability and separation of concerns

### 3. Environment-Based Configuration
**Decision**: R2 configs in prod overlay, not base
**Rationale**:
- Endpoints differ per environment (dev/staging/prod)
- Credentials are environment-specific
- Bucket names vary per deployment
- Base config should only have environment-agnostic settings

## Learnings

### 1. Proto-Level Authorization Simplifies Handlers
The `getArtifactDownloadUrl` RPC has authorization configured in the proto:
```proto
option (ai.stigmer.iam.iampolicy.v1.rpcauthorization.config).permission = can_view;
option (ai.stigmer.iam.iampolicy.v1.rpcauthorization.config).field_path = "execution_id";
```

This is handled by an interceptor, so the handler doesn't need explicit authorization logic. Initially implemented LoadExecution and Authorize steps, but removed them after discovering the proto configuration.

### 2. Java Pipeline Pattern is Powerful
The `RequestPipelineV2` pattern makes handlers very composable:
- Each step has single responsibility
- Easy to add/remove/reorder steps
- Step results are strongly typed
- Critical flag ensures important steps must succeed

### 3. Configuration Property Naming Matters
Using specific prefixes like `AGENT_EXECUTION_ARTIFACT_R2_*` instead of generic `R2_*` enables:
- Multiple R2 buckets per service
- Clear ownership (which bucket is for what)
- Easier debugging (grep for specific artifact type)

### 4. Bazel Dependency Management
The Java service already had AWS SDK dependencies from skill artifact storage, so no new dependencies were needed. If they weren't present, would have needed to add via buildozer:
```bash
buildozer 'add deps @maven//:software_amazon_awssdk_s3_presigner' //backend/services/stigmer-service:stigmer_service_lib
```
