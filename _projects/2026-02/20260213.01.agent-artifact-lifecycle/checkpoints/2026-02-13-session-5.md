## Decisions Made

### 1. Execution as Special Resource Type

**Decision**: Handle execution as a special case in commands rather than adding to `cliRelevantKinds` registry.

**Rationale**:
- Executions use dedicated `AgentExecutionQueryController` RPCs, not `SearchService`
- Different API patterns than other resources (agents, workflows, skills)
- Adding to registry would break SearchService assumptions

**Implementation**: Special-case checks in list.go, get.go, delete.go with dedicated handlers.

### 2. Download as New Verb

**Decision**: Introduce `VerbDownload` to the verb system, initially execution-specific.

**Rationale**:
- Follows CLI's verb-first pattern (`stigmer <verb> <resource-type>`)
- Extensible for future resource types (e.g., `download skill` for offline packages)
- More intuitive than subcommands like `stigmer execution download`

**Implementation**: Added to verb.go, verb_support.go, new download.go command.

### 3. Transparent Attachment Processing

**Decision**: Hide complexity of 4MB threshold and storage_key mechanics from users.

**Rationale**:
- Users shouldn't need to understand storage implementation details
- Size-based routing is an optimization, not a user concern
- Simpler mental model: "I attach files, they get to the agent"

**Implementation**: `AttachmentProcessor` class handles detection, upload, and proto creation automatically.

### 4. Wait-and-Download Workflow

**Decision**: Support `--download DIR` flag that implies `--wait` on run command.

**Rationale**:
- Common workflow: run agent, wait for completion, download results
- Single command better UX than separate run + poll + download
- Mirrors docker's pattern (`docker run --rm`)

**Implementation**: Flag composition (`--download` sets `waitFlag = true`), polling with exponential backoff.

### 5. Delete Maps to Cancel

**Decision**: Map `stigmer delete execution` to cancellation, not deletion.

**Rationale**:
- Executions are records of what happened (audit trail)
- "Delete" in user's mental model means "stop the running thing"
- Actual deletion would be a separate admin operation (retention policies)

**Implementation**: Special case in delete.go calling `execution.Cancel()`.

## Learnings

### 1. Proto Field Naming Matters

**Discovery**: The `AgentMessage` proto uses `Type` field, not `Role`.

**Impact**: Initial implementation used `msg.GetRole()` which didn't exist.

**Fix**: Changed to `msg.GetType()` and created `formatMessageType()` helper.

**Lesson**: Always check proto definitions before assuming field names, even for seemingly obvious fields.

### 2. Cancel Input Structure

**Discovery**: `CancelAgentExecutionInput` uses `Id` field, not `ExecutionId`.

**Impact**: Initial implementation failed to compile.

**Fix**: Checked proto definition, corrected field name to `Id`.

**Lesson**: Proto field naming can vary (Id vs ExecutionId vs execution_id), always verify.

### 3. Special Resource Handling Patterns

**Discovery**: CLI has two patterns for resource operations:
1. Registry-based (uses SearchService) - agents, workflows, skills
2. Special-cased (uses dedicated RPCs) - executions

**Impact**: Initial plan tried to add execution to registry, which would break.

**Fix**: Documented execution as special case, added early returns in command handlers.

**Lesson**: Not all resources fit the same pattern. Document exceptions clearly.

### 4. User Mental Models vs Technical Reality

**Discovery**: Users think "delete execution" means "stop running execution", not "erase from DB".

**Technical Reality**: Executions are audit records, cancellation != deletion.

**Resolution**: Map delete command to cancel operation, preserve execution record.

**Lesson**: Align CLI commands with user intent, not just technical operations.

### 5. Exponential Backoff for Polling

**Discovery**: Fixed interval polling (e.g., every 2 seconds) wastes resources for long-running executions.

**Implementation**: Start at 2s, increase to 10s max with 1.5x multiplier.

**Impact**: Better resource usage, reasonable response time for both quick and slow executions.

**Lesson**: Polling strategies should adapt to execution characteristics.

## Open Questions

### 1. Artifact Filtering

**Question**: Should `stigmer download execution` support glob patterns for artifact filtering?

**Context**: Currently supports `--artifact name` for exact match only.

**Example Use Case**: `--artifact "*.pdf"` to download all PDFs.

**Resolution**: Deferred to future enhancement. Exact match sufficient for MVP.

### 2. Progress Bars

**Question**: Should downloads show progress bars for large files?

**Context**: Currently shows start/complete messages, no real-time progress.

**Trade-off**: Progress bars add complexity, require terminal detection.

**Resolution**: Basic progress in place (file sizes shown). Enhanced progress for future iteration.

### 3. Resume Downloads

**Question**: Should interrupted downloads be resumable (HTTP Range requests)?

**Context**: Large artifact downloads could be interrupted by network issues.

**Trade-off**: Adds complexity for edge case (presigned URLs, range support).

**Resolution**: Not implemented. If download fails, user re-runs command (idempotent).

### 4. Batch Operations

**Question**: Should CLI support downloading artifacts from multiple executions at once?

**Example**: `stigmer download executions --status completed --last 5`

**Resolution**: Deferred. Single execution download sufficient for MVP. Future enhancement if needed.
