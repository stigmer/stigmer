## Decisions Made

### Storage Abstraction over Direct R2 Client
**Decision**: Create an abstraction layer instead of directly using R2

**Rationale**:
- OSS/local deployments don't have R2 access
- Allows running Stigmer entirely locally for development
- Follows existing pattern from workflow-runner
- Easy to add more backends (S3, GCS, Azure, etc.)

**Trade-off**: Slight overhead, but worth it for flexibility

### LangChain StructuredTool for publish_output
**Decision**: Use LangChain's `StructuredTool` instead of custom wrapper

**Rationale**:
- Native integration with Graphton/LangGraph
- Automatic schema validation via Pydantic
- Proper async/await support
- Consistent with other tool patterns

### Inject Attachments After Skills
**Decision**: Place attachment injection as Step 3.5 (after skill writing)

**Rationale**:
- Skills might reference input files
- Follows logical flow: setup → skills → inputs → agent
- Both use same file upload patterns

## Learnings

### 1. Protocol Pattern is Powerful
Using Python's `Protocol` for the storage abstraction provides:
- Duck typing with type hints
- Easy mocking for tests
- No inheritance required
- Runtime checkable with `@runtime_checkable`

### 2. LangChain Tool Integration
Key insights:
- Use `StructuredTool` for custom tools
- Define schema with Pydantic `BaseModel`
- Provide both `func` (sync) and `coroutine` (async)
- Tool `name` and `description` are critical for agent decision-making

### 3. Dependency Injection Pattern
The tool creation pattern works well:
1. Create wrapper class capturing dependencies
2. Define async `run()` method
3. Create factory function returning `StructuredTool`
4. Pass to agent via `tools=[]` parameter

### 4. Local Development Support
Supporting both local and cloud modes is valuable:
- Enables full OSS deployment without cloud dependencies
- Allows local development/testing
- Mode-aware defaults reduce configuration burden
