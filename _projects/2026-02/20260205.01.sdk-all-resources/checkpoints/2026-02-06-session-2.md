## Decisions Made

### Decision 1: Three-Tier Separation

**Context**: Original `SkillSource` conflated user input with stored state.

**Decision**: Establish three distinct layers:
1. SDK Layer (`SkillSynth`): User's synthesis input
2. Backend Spec (`SkillSpec`): Extracted content only
3. Backend Status (`SkillStatus`): System-observed metadata

**Rationale**: 
- DDD principle: Separate user intent from system state
- Matches patterns used by Agent/Workflow resources
- Enables intuitive SDK API without forcing users to provide git metadata

### Decision 2: Git Provenance in Status

**Context**: Git metadata (remote URL, commit SHA) was incorrectly placed in spec.

**Decision**: Move to `SkillStatus` as observed state.

**Rationale**:
- Git provenance is system-detected, not user-provided
- Spec should only contain user intent
- Status is the correct place for system observations (follows Kubernetes pattern)

### Decision 3: Dual Ref Tracking

**Context**: Need both human-friendly refs (tags/branches) and reproducible commits (SHAs).

**Decision**: Track both `ref` (original) and `commit` (resolved) in `GitProvenance`.

**Rationale**:
- `ref`: What user specified or what branch HEAD pointed to
- `commit`: Exact SHA for reproducibility
- Both are valuable for different use cases (GitHub links vs deployment reproducibility)

### Decision 4: FromDir vs FromGit Constructors

**Context**: Need simple, intuitive SDK API for both local and remote sources.

**Decision**: 
- `skill.FromDir(ctx, path, opts...)`: For local directories
- `skill.FromGit(ctx, url, opts...)`: For remote repositories

**Rationale**:
- Clear, self-documenting API
- Functional options provide flexibility without complexity
- Mirrors patterns in other Go libraries (Docker client, Kubernetes client-go)

### Decision 5: Breaking Change Acceptance

**Context**: This refactoring is a breaking change requiring coordinated updates.

**Decision**: Proceed with breaking change, document migration path.

**Rationale**:
- Current architecture is fundamentally flawed (anemic model, conflated concerns)
- Early in product lifecycle - better to fix now than carry technical debt
- Clear migration path: Backend → CLI → SDK update sequence

## Learnings

### 1. Separation of Concerns is Non-Negotiable

**Learning**: Conflating user input with stored state creates fundamental architecture problems.

**Impact**: The original `SkillSource` made the SDK API unintuitive (forcing users to provide git metadata) and violated DDD principles.

**Takeaway**: Always maintain clear boundaries:
- User intent (SDK synthesis input)
- Processing (CLI orchestration)
- Stored state (backend spec)
- Observed metadata (backend status)

### 2. CLI as Enrichment Layer

**Learning**: CLI is the perfect place to detect and enrich metadata.

**Impact**: CLI has access to local git context, can resolve refs to commits, and can detect provenance automatically.

**Takeaway**: Don't force users to provide metadata that can be automatically detected. Let the CLI do the work.

### 3. Breaking Changes Require Coordination

**Learning**: Proto changes propagate through all layers (Go, Python, Java stubs; SDK; CLI; Backend).

**Impact**: 31 files changed, requiring careful testing at each layer.

**Takeaway**: Document breaking changes clearly, provide migration path, and test each layer independently before integration.

### 4. Git Tracking Needs Both Ref and Commit

**Learning**: Tags/branches are human-friendly but mutable; commit SHAs are reproducible but cryptic.

**Impact**: Tracking both enables "view on GitHub" links (using ref) and reproducible deployments (using commit).

**Takeaway**: Don't force a choice between usability and reproducibility - capture both.

### 5. Proto Reserved Fields Prevent Future Conflicts

**Learning**: When removing proto fields, always use `reserved` to prevent accidental reuse.

**Impact**: Prevents future proto field number collisions that would break wire compatibility.

**Takeaway**: Always add `reserved N;` when removing fields from proto messages.
