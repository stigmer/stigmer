## Decisions Made

**apply_skill not implemented**: The `SkillCommandController.push` RPC requires a binary ZIP artifact (`bytes artifact`). MCP tools exchange text/JSON — there is no way to pass binary data through a tool argument. `apply_skill` is deferred until the backend adds a text-based skill mutation RPC (e.g., inline SKILL.md content with server-side ZIP wrapping).

**Delete by org+slug (fetch-then-delete)**: All delete RPCs on the backend require a system-generated UUID, not an org/slug pair. Forcing AI clients to obtain and pass UUIDs would be terrible UX. Each delete tool makes two RPCs over a single shared gRPC connection: `GetByReference(org, slug)` → extract `metadata.id` → `Delete(id)`. The extra round-trip cost (~1ms on localhost, ~5ms remote) is negligible.

**Apply accepts full resource JSON string**: Apply tools take `resource string` — the entire protobuf message as JSON. This decouples the MCP tool schema from proto field changes. AI clients can construct valid resource JSON from `get_*` output. `DiscardUnknown: true` ensures extra fields from AI clients don't cause errors.

**MCP Server delete uses `ApiResourceDeleteInput`**: Unlike agents/skills/workflows which use simple `{value: id}` ID wrappers, MCP Servers use `ApiResourceDeleteInput{resource_id, version_message, force}`. We set safe defaults (`force: false`, `version_message: ""`). These optional fields can be surfaced to the tool input later if audit messaging becomes important.

## Learnings

- Skills domain is fundamentally different from the other three for write operations: it is artifact-first (push ZIP), not resource-first (apply JSON). This is the right design for a versioned artifact system, but it creates a gap in the MCP tool surface that is not easily bridged without backend support.
- The fetch-then-delete pattern is clean and consistent. All domain mocks for delete tests embed both QueryController and CommandController servers on the same gRPC server — a practical pattern that validates the real two-RPC flow without needing integration infrastructure.
- `DiscardUnknown: true` is the right default for an AI-facing API. AI clients will inevitably generate JSON that includes fields beyond the minimum required.
