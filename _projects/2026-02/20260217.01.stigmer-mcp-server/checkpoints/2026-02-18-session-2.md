## Decisions Made

**Integration test strategy: real gRPC server with embedded Unimplemented* mocks**

The proto stubs provide `Unimplemented*Server` structs and `Register*Server` functions. We create minimal mock structs that embed the unimplemented base and override only the methods under test. A helper starts a `grpc.Server` on `localhost:0` (OS-assigned port) and returns its address. The handler under test connects to this address normally — no dependency injection, no production code changes.

This approach is better than:
- Interface injection: would require adding constructor parameters to production handlers
- In-process mocks: wouldn't catch real serialization / connection issues
- External test server: too heavy for unit-style tests

**`extractText` duplication is intentional**

Each domain test file has its own `extractText` helper. We chose not to export this from `testutil` because:
- It's 10 lines of test-only boilerplate
- Cross-package test dependencies create subtle coupling
- The duplication is exactly the kind that's acceptable in test code

**T03.7 (Makefile) was already done**

The root Makefile already had `mcp-server` in all three relevant targets (`test`, `test-all-go`, `coverage`). The plan was written from a truncated read of the file that didn't show the full target. No change needed.

## Learnings

- The MCP SDK's `go-sdk` v1.3.0 typed handler signatures (`func(ctx, req, *Input) (*Result, any, error)`) mean tool handlers are just plain Go functions — trivially testable without any SDK mocking.
- `grpc.NewClient` is lazy: it accepts any address (including empty string) without dialing. Tests for connection option assembly (TLS vs insecure) are lightweight.
- `t.Setenv` correctly restores env vars after each subtest, making config tests hermetic without `sync.Mutex` or manual cleanup.
