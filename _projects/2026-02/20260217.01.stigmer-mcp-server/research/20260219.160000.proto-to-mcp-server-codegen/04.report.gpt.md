# Automating MCP Server Generation from Protocol Buffers as of February 2026

## Executive summary

As of **February 19, 2026**, there is **real (but still early) open-source momentum** around **turning gRPC + Protobuf APIs into MCP servers automatically**, split into two broad camps: **compile-time code generation** (protoc/Buf plugins) and **runtime reflection-based proxies**. citeturn13view1turn7view0turn3view1turn6view1

In the Go ecosystem, the most prominent proto→MCP codegen project is **`protoc-gen-go-mcp`** from entity["company","Redpanda","streaming data company"], which generates `*.pb.mcp.go` handlers directly from protobuf services and can forward tool calls to **gRPC** or **ConnectRPC** clients while auto-generating **JSON Schema** inputs. citeturn13view1turn12view1 A second, newer Go option is **`grpc-mcp-gateway`** (Loschcode), explicitly inspired by **gRPC-Gateway** and designed around **protobuf annotations** that let you control MCP tool metadata (name/title/description/read-only hints) at the `.proto` layer. citeturn7view0turn25search12

If you want a **no-code** bridge, several projects proxy a live gRPC backend into MCP using **server reflection** or a **FileDescriptorSet** (e.g., `grpcmcp`, `ggRMCP`, `grpcurl-mcp`). These are useful for quick enablement but tend to expose broad surfaces unless you add allowlisting and policy gates. citeturn3view1turn6view1turn22search0turn16view0

Separately, the **most mature “schema-driven MCP generation” tooling today is OpenAPI-based**, not protobuf-based (AWS Labs OpenAPI MCP Server, emcee, openapi-mcp, openapi-mcp-codegen, etc.). That makes **proto→OpenAPI→MCP** a practical workaround when proto→MCP isn’t customizable enough. citeturn29view0turn29view1turn29view2turn29view3turn23search2turn25search12

Bottom line for your use case: **you probably don’t have to start from zero**, but you likely need either (a) adopting and extending an existing proto→MCP generator, or (b) chaining **proto→OpenAPI** and using a mature OpenAPI→MCP generator—especially if you require consistent **tool naming**, **resource URI templates**, and integration with your **custom proto options** for IAM and “resource kind” metadata. citeturn7view0turn13view1turn21view1turn29view0

## MCP constraints that shape proto-based generation

MCP’s **base protocol is JSON-RPC 2.0**, and tool discovery/execution is standardized around methods like `tools/list` and `tools/call`. citeturn21view2turn21view0 Each MCP tool includes an **`inputSchema`** that is a **JSON Schema object**; for the protocol revision **2025-11-25**, MCP defaults to **JSON Schema 2020-12** when `$schema` is not provided, and the tool schema root is currently restricted to `type: "object"`. citeturn21view1turn21view0

This means a proto→MCP generator must reliably do three things:

1. **Derive a JSON Schema input** for each RPC request message (including nested messages, `oneof`, maps, well-known types, etc.). citeturn21view1turn13view1turn19view1turn19view0  
2. **Translate JSON arguments ⇄ protobuf messages** and call the underlying gRPC method. citeturn13view1turn3view1turn6view1  
3. Provide **tool metadata** meaningful to LLMs (good names, descriptions, and safety hints like read-only vs destructive). MCP defines annotation hints (`readOnlyHint`, `destructiveHint`, `idempotentHint`) but warns they are only hints and should not be trusted from untrusted servers. citeturn21view1turn21view0

Two additional ecosystem realities are relevant:

- MCP implementers have actively discussed **full JSON Schema 2020-12 support**, including constructs like `oneOf`/`anyOf`/`allOf`, across clients/servers/inspectors, indicating that “dialect correctness” (and downstream client limitations) is a practical concern for generators. citeturn20search1turn21view1  
- There is accelerating interest in **gRPC as an MCP transport** (to avoid JSON-RPC transcoding overhead), but this is orthogonal to *mapping service methods into tools*. It signals that gRPC-heavy shops are pushing the MCP ecosystem toward deeper gRPC integration. citeturn24view0turn24view1turn5search28

## Proto→JSON Schema generation as the “half-solved” part

Because MCP tool inputs are JSON Schema objects (and default to 2020-12 unless specified), a reliable proto→JSON Schema pipeline removes a large portion of your per-tool boilerplate. citeturn21view1turn21view0 The ecosystem here is **stronger and older** than proto→MCP itself.

Notable open-source options:

- `bufbuild/protoschema-plugins` (`protoc-gen-jsonschema`) `https://github.com/bufbuild/protoschema-plugins` generates JSON Schema using **Draft 2020-12**, and the repo documentation shows it can be used either as a local protoc plugin or as a **Buf remote plugin** (`buf.build/bufbuild/protoschema-jsonschema`). citeturn19view1turn14search12  
- `pubg/protoc-gen-jsonschema` `https://github.com/pubg/protoc-gen-jsonschema` supports many JSON Schema drafts (draft-04 through draft-2020-12) and explicitly targets **ProtoJSON** and common patterns rather than “all JSON Schema features.” It also documents a practical compatibility choice around 64-bit integers and the Protobuf JSON mapping. citeturn19view0  
- `cerbos/protoc-gen-jsonschema` `https://github.com/cerbos/protoc-gen-jsonschema` focuses on generating JSON Schema from **protovalidate** rules (useful if you standardize on Buf’s validation ecosystem). citeturn19view2  

For reflection-based systems, there is a key nuance: gRPC server reflection is explicitly intended to help clients construct requests without precompiled stubs, and it can return protobuf descriptors, but **comments/source code info are not necessarily available unless you supply descriptors compiled with source info**. citeturn16view0turn26view0 The `jhump/protoreflect` ecosystem documents separate tooling (`protoc-gen-gosrcinfo`) for restoring source code information to descriptors in Go, and explains that generated Go types do not include source code information by default—relevant if you want to generate high-quality tool descriptions from proto comments. citeturn18view0

## Architecture patterns teams are using for proto→MCP today

A few patterns are emerging across open source and vendor writeups.

### Protoc/Buf codegen in the build pipeline

This is closest to your stated desire: **derive MCP tools (and sometimes more) directly from `.proto`** so adding a new RPC naturally expands the MCP surface.

- Redpanda’s `protoc-gen-go-mcp` explicitly positions itself as a **protoc plugin** that generates MCP handlers, JSON Schema inputs, and forwarding layers to gRPC/Connect clients with essentially “zero boilerplate,” integrating easily into Buf generation. citeturn13view1turn12view1  
- The `grpc-mcp-gateway` project takes a grpc-gateway-inspired stance: keep MCP tool mapping **in the proto file** via annotations, and generate glue code and JSON Schema around that. citeturn7view0turn25search12  
- entity["company","EnterpriseDB","postgres database company"] published a multi-part walkthrough explicitly advocating a **custom protoc plugin** to generate MCP servers from protobuf, reusing existing proto annotations/transcoding setup so gRPC, REST/OpenAPI, and MCP are all generated from one source. citeturn14search5turn8view1 The series also discusses turning proto comments into tool descriptions—matching the “semantic layer” problem that pure reflection does not solve. citeturn4search16  

### Sidecar / gateway adapters using gRPC reflection or descriptors

This pattern is attractive for platform engineering because you can deploy a single component in front of many services.

- `grpcmcp` and `ggRMCP` both support **reflection-driven discovery** as well as a **FileDescriptorSet** option. citeturn3view1turn26view0  
- `grpcurl-mcp` inherits `grpcurl`’s model: use reflection, proto source, or protoset files, and convert JSON payloads into protobuf wire format (and back). citeturn22search0turn17view0  
- These bridges build on the upstream gRPC reflection design goal: enable runtime request construction for tooling/clients without precompiled stubs. citeturn16view0  

A major risk here is **unbounded tool exposure** (every method becomes a tool) unless your gateway adds allowlisting and safety gates. MCP’s own tool documentation emphasizes that tools are “model-controlled” but recommends a human-in-the-loop model and clear UI indicators and confirmation prompts for safety. citeturn21view0

### Proto→OpenAPI→MCP as a pragmatic workaround

There is significantly more maturity in OpenAPI→MCP tooling, so many teams use protobuf only as the original source, then “hop” through OpenAPI.

Common proto→OpenAPI hops:

- **gRPC-Gateway** is a well-established protoc plugin that generates an HTTP reverse proxy from proto service definitions (using `google.api.http` annotations) and is widely used in production. citeturn25search12  
- `protoc-gen-connect-openapi` (`sudorandom/protoc-gen-connect-openapi`) generates **OpenAPI 3.1** from protobuf matching the Connect interface and highlights that Connect makes unary RPCs look like a normal HTTP/JSON API. citeturn23search2turn23search0  
- Connect’s protocol reference explicitly supports unary and streaming RPCs with either **binary protobuf or JSON payloads**, which makes it especially “bridge-friendly” for MCP-style JSON tooling. citeturn23search0turn23search4  

Once you have OpenAPI, open-source MCP options are abundant:

- entity["organization","AWS Labs","aws open-source org"] publishes an **OpenAPI MCP Server** that dynamically creates MCP tools and resources from OpenAPI 3.x, and it even includes thoughtful mapping rules (example: GET operations with query params mapped to tools instead of resources). citeturn29view0  
- `openapi-mcp-codegen` (cnoe-io) generates Python MCP servers as packages from OpenAPI, including per-endpoint tool modules and optional agent/eval generation. citeturn29view1  
- `emcee` (mattt) provides an MCP server for any web app with an OpenAPI spec and ships via Homebrew, positioning itself as a quick bridge when there is no bespoke MCP server. citeturn29view2  
- `openapi-mcp` (ckanthony) is a dockerized MCP server that reads OpenAPI/Swagger and generates an MCP toolset, emphasizing “no additional coding required.” citeturn29view3  

A related “config-first” generator style exists too (e.g., `gen-mcp`) that can create MCP servers from YAML and can auto-convert from OpenAPI—useful when your “real backend” is HTTP, but less directly applicable to gRPC without a prior hop. citeturn3view3

## Recommendation and a minimal viable “build” plan

### Recommendation

For a multi-product platform engineering organization with consistent protobuf conventions, the strongest practical strategy is a **two-track approach**:

**Track one: adopt an existing proto→MCP generator immediately for tool boilerplate.**  
- If you can tolerate a runtime dependency on `mcp-go` for now, start by piloting `protoc-gen-go-mcp` from Redpanda because it is the most complete end-to-end Go protoc plugin discovered in this research (Buf integration, JSON Schema generation, forwarding to gRPC/Connect clients, explicit roadmap and limitations). citeturn13view1turn12view1turn5search9  
- In parallel, evaluate `grpc-mcp-gateway` specifically for your need to control **tool naming and descriptive metadata from `.proto`** via annotations—this aligns closely with your existing use of custom proto options. citeturn7view0turn21view1  

**Track two: plan to generate MCP “resources” and URI templates yourself (or consciously drop them).**  
None of the proto→MCP projects above clearly claims mature support for **resource templates and URI handlers** comparable to what you handwrite today; most focus on tools (RPC calls). citeturn13view1turn7view0 If resources are core to how you want assistants to browse and retrieve objects (e.g., `stigmer://agents/{org}/{slug}`), you should treat “resource generation” as an extension layer you’ll likely need to implement—either by forking an existing generator or writing a thin generator that sits on top of descriptor sets and your custom “resource kind” annotations. citeturn21view0turn21view1

### Minimal viable proto→MCP generator tailored to your conventions

This plan assumes you build a small internal generator (or fork/extend an existing one) with your current Protobuf patterns (QueryController / CommandController, Resource/Spec/Status/Id messages, custom IAM and kind options).

**Inputs**
- Use `buf build` to output a **FileDescriptorSet** (the same descriptor artifact multiple runtime proxies already accept). citeturn3view1turn26view0turn16view0  
- Prefer including source info (`--include_source_info`) if you want comments to become tool parameter descriptions (as highlighted by the EDB series and by protoreflect’s source info discussion). citeturn4search16turn18view0turn26view0  

**Core generation outputs**
- For each QueryController/CommandController method that matches your conventions, generate:
  - MCP tool metadata (name/title/description + safety hints like read-only vs destructive). MCP supports these fields and defines precedence rules and hint semantics. citeturn21view1turn21view0  
  - `inputSchema` as JSON Schema **2020-12 by default**, consistent with MCP defaults. Reuse `bufbuild/protoschema-jsonschema` or `pubg/protoc-gen-jsonschema` depending on how much control you need over dialects and ProtoJSON quirks. citeturn21view1turn19view1turn19view0  
  - A handler that marshals JSON arguments to protobuf, calls your generated gRPC clients, and returns JSON. (This is the fundamental mapping every current proto→MCP project implements in some form.) citeturn13view1turn3view1turn6view1  

**Resource templates (optional but aligned to your current practice)**
- For each resource kind, generate:
  - A resource URI template (e.g., `{product}://{kind}/{org}/{id}`) based on your existing custom proto options. MCP supports resources as a first-class server feature. citeturn21view2turn21view0  
  - A `resources/read` handler that maps the URI back onto `Get` (or `GetByReference`) request messages.

If you decide resources aren’t worth the complexity, you can still provide a strong UX purely with tools, but you lose “browsable URIs” as a stable contract. MCP’s own documentation highlights tools as the primary model-controlled operation surface, while resources are a separate feature layer. citeturn21view0turn21view2

**SDK/runtime target**
- For Go, the official MCP Go SDK exists and is being adopted in notable servers (e.g., GitHub’s MCP server migration), which makes it a credible long-term target for generated servers. citeturn2search0turn2search17  
- If you need compatibility with your existing `mcp-go` servers, you can generate against `mcp-go` first and migrate later—mirroring the ecosystem trend where unofficial Go SDKs were popular before the official SDK stabilized. citeturn2search4turn2search8turn2search14  

**Packaging and multi-product reuse**
- Ship the generator as a protoc plugin runnable via Buf’s `buf generate` (local plugin) and, if you want centralized reuse, consider publishing it as a **Buf remote plugin** (containerized) so all products pin the same generator version in `buf.gen.yaml`. Buf’s docs describe remote plugin usage and its plugin publishing model. citeturn14search12turn14search15turn1search23  
- The existence of fresh “plugin request” issues for gRPC→MCP tooling in the Buf plugins repo suggests community interest but also indicates this is not yet mainstream in the BSR catalog. citeturn14search3turn14search15  

### Effort and risk (rough sizing)

A minimal generator that only does **tools** (no resources), with a narrow mapping aligned to your Query/Command controller conventions, is realistically “small enough” to build or fork-harden in a platform team—especially because:
- the EDB tutorial demonstrates a custom protoc plugin pipeline for MCP generation, and  
- multiple OSS projects already implement the descriptor→schema→tool mapping you’d reuse or adapt. citeturn14search5turn13view1turn7view0turn3view1  

The main risk is not code volume; it is **semantic quality and safety**: ensuring tool names/descriptions are stable, enforcing allowlists, and integrating your IAM/resource-kind options so that assistants see only what they should. MCP’s own specification stresses human-in-loop controls and tool safety considerations, which should directly influence your generated defaults (e.g., requiring explicit opt-in annotations for destructive tools). citeturn21view0turn21view1
