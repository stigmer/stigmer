# Deep Research: Automating MCP Server Generation from Protocol Buffers

## Research Objective

We are a platform engineering company building multiple products (Stigmer, Planton, and more in the future). Each product has a gRPC-based backend with APIs defined in Protocol Buffers, and each needs an MCP (Model Context Protocol) server to expose resources to AI coding assistants (Cursor, Claude Desktop, Windsurf, etc.).

We want to understand: **what open-source tools, frameworks, or approaches exist (as of February 2026) for automatically generating MCP server implementations from Protocol Buffer service definitions?** We do not want to build this from scratch if someone has already solved it.

## Our Current Setup

### Architecture Pattern (same across products)

1. **Proto definitions** define API resources with:
   - `QueryController` services (read: `get`, `getByReference`, `list`)
   - `CommandController` services (write: `create`, `update`, `apply`, `delete`)
   - Structured messages (`Resource`, `ResourceSpec`, `ResourceStatus`, `ResourceId`)
   - Custom proto options/annotations for IAM authorization and resource kind metadata

2. **Proto pipeline**: We use **Buf** (buf.build) to lint, format, and generate Go + Python stubs. Stubs are published to the Buf Schema Registry.

3. **MCP servers** (handwritten today): Each product has a Go MCP server that:
   - Uses the official `modelcontextprotocol/go-sdk` (Stigmer) or `mark3labs/mcp-go` (Planton)
   - Defines MCP tools (e.g., `get_agent`, `apply_agent`, `search`) with JSON input schemas
   - Defines MCP resource templates (e.g., `stigmer://agents/{org}/{slug}`)
   - Calls gRPC backends using the generated client stubs
   - Serializes proto responses to JSON via `protojson`

4. **Scale**: Stigmer currently has 4 resource domains (agents, skills, mcp_servers, workflows) growing to 12+. Planton has 6 domains (organizations, environments, cloud resources, services, pipelines, GitHub credentials) with 15+ tools. Future products will follow the same pattern.

### The Problem

Every time we add a new API resource or RPC:
- We manually write MCP tool definitions (name, description, JSON schema)
- We manually write handler functions (argument extraction, gRPC client call, response formatting)
- We manually write resource templates and URI handlers
- We manually register everything in the server wiring

This is ~120-230 lines of boilerplate per resource domain, following an identical pattern across all products. The proto service definitions already contain all the information needed to generate this code.

## Specific Questions to Research

### 1. Existing Open-Source Tools

- Are there any open-source **protoc plugins** or **Buf plugins** that generate MCP server code from proto service definitions? (e.g., `protoc-gen-mcp`, `buf plugin for MCP`)
- Are there any open-source **code generators** that take proto descriptors/FileDescriptorSets and emit MCP tool/resource handlers?
- Are there any **MCP server frameworks** that can auto-discover and expose gRPC services as MCP tools at runtime (no codegen, just proto reflection)?
- Has anyone published a **generic gRPC-to-MCP bridge/proxy** that sits in front of any gRPC server and exposes all services as MCP tools?

### 2. MCP Ecosystem Approaches

- How are other companies/projects building MCP servers for gRPC backends? Are they all hand-coding, or are there emerging patterns?
- Are there any **MCP server generator frameworks** (not proto-specific) that take an API schema (OpenAPI, GraphQL, gRPC) and produce MCP servers?
- The `modelcontextprotocol/go-sdk` and `mark3labs/mcp-go` — do either provide any codegen utilities or scaffolding?
- Are there tools in other languages (TypeScript, Python, Rust) that solve this and could be adapted?

### 3. gRPC Reflection / Generic Bridges

- **gRPC Server Reflection**: Can we build a generic MCP server that connects to any gRPC server with reflection enabled and dynamically exposes all services as MCP tools? Has anyone done this?
- **gRPCurl / grpcui patterns**: Tools like grpcurl already discover services via reflection. Has anyone built an MCP adapter on top of this pattern?
- **Connect protocol**: Since Connect (connectrpc.com) serves gRPC services over HTTP with JSON, could an MCP server be built as a thin wrapper over Connect endpoints?

### 4. Proto-to-Schema Generation

- Are there tools that convert proto message definitions to **JSON Schema** (which MCP tools require for input schemas)? This would solve half the problem.
- `protoc-gen-jsonschema` or similar — do any of these work well enough to feed into MCP tool definitions?
- Can Buf's proto reflection APIs be used at runtime to dynamically build JSON schemas for MCP tool inputs?

### 5. Related Patterns from Other Ecosystems

- **OpenAPI-to-MCP generators**: OpenAPI/Swagger is more established; are there production-quality tools that generate MCP servers from OpenAPI specs? Could we generate OpenAPI from our protos and then chain to MCP?
- **GraphQL-to-MCP**: Similar question for GraphQL schemas.
- **Terraform/Pulumi provider codegen**: These ecosystems have mature code generation from schemas. Are there lessons or tools we can adapt?
- **gRPC-Gateway pattern**: gRPC-Gateway generates REST proxies from proto annotations. Has anyone built a similar "gRPC-MCP-Gateway"?

### 6. Buf Plugin Ecosystem

- Does the Buf team or community have any MCP-related plugins planned or in development?
- Can we write a **Buf remote plugin** that generates MCP server code and publish it to the Buf Schema Registry for reuse across our products?
- What is the effort level to write a custom Buf plugin vs. a standalone Go code generator?

## Context for Evaluation

When evaluating solutions, please consider:

- **Language**: We primarily use Go for MCP servers. TypeScript solutions are acceptable as alternatives.
- **MCP SDK compatibility**: Must work with `modelcontextprotocol/go-sdk` (official SDK) or `mark3labs/mcp-go`.
- **Maturity**: We prefer battle-tested tools. If nothing mature exists, knowing what's in early stages helps.
- **Customizability**: We need control over tool names, descriptions, and URI patterns (not just generic auto-generated names).
- **Multi-product reuse**: Ideally, the solution works as a shared tool across Stigmer, Planton, and future products without per-product customization of the generator itself.
