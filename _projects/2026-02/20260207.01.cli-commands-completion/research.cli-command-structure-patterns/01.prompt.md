# Deep Research: CLI Command Structure Patterns - Resource-Specific vs Generic Commands

## Research Objective

I need authoritative research and industry analysis to make an architectural decision for a CLI tool (Stigmer CLI) that manages multiple resource types. The core question is:

**Should CLI commands be structured as resource-specific subcommands OR as generic verb-first commands with auto-detection?**

## Context

### Current State
Stigmer CLI currently uses resource-specific commands:
```
stigmer agent apply -f agent.yaml
stigmer agent get <ref>
stigmer agent list
stigmer workflow validate -f workflow.yaml
stigmer mcpserver delete <ref>
```

### Resource Types Being Managed
1. **Agent** - AI agent definitions
2. **Workflow** - Multi-step automation workflows  
3. **Skill** - Reusable capability modules
4. **MCP Server** - Model Context Protocol server configurations
5. **Project** - Project configurations
6. (Future: potentially more resource types)

### The Architectural Question

**Option A: Resource-Specific Commands (Current)**
```
stigmer <resource> <verb> [args]
stigmer agent get abc123
stigmer skill list
stigmer mcpserver validate -f server.yaml
```

**Option B: Generic Verb-First Commands**
```
stigmer <verb> [args]
stigmer apply -f agent.yaml       # Auto-detect from YAML kind/apiVersion
stigmer get agent/abc123          # Resource type in reference
stigmer list agents               # Pluralized resource name
stigmer validate -f workflow.yaml # Auto-detect from YAML
```

**Option C: Hybrid Approach**
- Generic `apply` and `validate` (auto-detect from YAML content)
- Resource-specific `get`, `list`, `delete` (need context)

### Key Considerations

1. **YAML-based operations**: For `apply` and `validate`, the YAML file contains a `kind` field indicating resource type (e.g., `kind: Agent`). Auto-detection is possible.

2. **Reference-based operations**: For `get` and `delete`, users provide a reference/ID. The reference format could encode resource type (e.g., `agent/abc123`) or require explicit specification.

3. **Scalability**: As we add more resource types (6+ in future), does one pattern scale better than the other?

4. **User Mental Model**: Which approach is more intuitive for developers managing multi-resource systems?

5. **Discoverability**: How do users discover available resources and their commands?
