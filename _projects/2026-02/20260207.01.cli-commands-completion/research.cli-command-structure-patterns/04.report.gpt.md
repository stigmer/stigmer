## 1. Executive summary

For Stigmer CLI (multiple resource “kinds” described in YAML with `apiVersion` + `kind`, plus CRUD-style operations), the strongest industry precedent is **Kubernetes’ `kubectl` model**: **generic, verb-first lifecycle commands** (apply/get/delete) that operate across many kinds, with **file-based commands auto-detecting kind from the manifest** and **reference-based commands requiring the resource type to be explicit** (either as an argument or encoded in the identifier). ([Kubernetes][1])

### Recommendation

Adopt a **hybrid that is “kubectl-like at the top level”**:

* Make **generic verbs the canonical UX** for shared lifecycle actions:

  * `stigmer apply -f …` and `stigmer validate -f …` (auto-detect kind from YAML).
  * `stigmer get <type>[/<id>]`, `stigmer list <type>`, `stigmer delete <type>/<id>` (resource type explicit).
* Keep **resource-specific command trees** for:

  1. **specialized verbs** that only make sense for one kind (e.g., `workflow run`, `agent test`), and
  2. **backward compatibility** (aliases/wrappers for existing `stigmer agent get …` etc).

This gives you the scaling benefits of Option B (generic verbs for N kinds) without forcing breaking changes away from Option A. It also follows modern CLI guidance: “two levels of subcommand (noun + verb) is common; either noun–verb or verb–noun works; keep interfaces stable and changes additive.” ([CLI Guidelines][2])

### What this says for Stigmer

* Tools that are **fundamentally “many kinds of objects with largely shared lifecycle verbs”** (Kubernetes) tend to converge on **generic verbs** + **resource types as arguments**, because it scales to new kinds without exploding the command tree. ([Kubernetes][14])
* Tools with **huge, heterogeneous APIs** (AWS, gcloud) tend to converge on **resource/service grouping**, because the verbs aren’t uniform across everything and the surface area is massive. ([AWS Documentation][5])
* Tools that must support both “common verbs” and “many subdomains” often become **hybrid** (Docker/Podman/Helm). ([Docker Documentation][11])

## 3. Design principles and best practices that apply directly

### 3.1 Two-level noun/verb patterns are common — either order can work

The Command Line Interface Guidelines (clig.dev) explicitly call out the “two levels of subcommand, one noun and one verb” pattern (example: `docker container create`) and say **either `noun verb` or `verb noun` ordering works**, though **noun–verb is more common**; the key is **consistency across subcommands and verbs across object types**. ([CLI Guidelines][2])

Implication for Stigmer:

* If you stay resource-first (Option A), keep verbs consistent across resources.
* If you go verb-first (Option B), keep noun spelling/aliases consistent across kinds.
* If you do hybrid, avoid “same verb but different semantics” surprises.

### 3.2 Discoverability depends less on ordering and more on help + grouping

clig.dev recommends:

* show concise help by default when required args are missing,
* provide extensive help for `--help`,
* **lead with examples**, and
* make help work consistently across subcommands. ([CLI Guidelines][2])

The practical takeaway: **you can make either Option A or Option B discoverable**, but you must invest in help output and examples. Verb-first doesn’t have to be less discoverable if you provide a `stigmer resources`/`stigmer kinds` index similar to `kubectl api-resources`. ([Kubernetes][3])

### 3.3 Future-proofing: treat CLI as an interface; keep changes additive

clig.dev is blunt here: subcommands/flags/config files are **interfaces you’re committing to keep working**, and changes need a “lengthy and well-documented deprecation process”; **keep changes additive where possible**. ([CLI Guidelines][2])

This strongly supports: **introduce new generic verbs as additive commands**, keep old resource-first commands as aliases, and deprecate gradually.

### 3.4 “Verb-first” can improve consistency when verbs are shared

Microsoft’s PowerShell team explicitly argues for **verb-first naming** because it encourages a high level of verb reuse and a consistent, predictable user experience (and avoids everyone inventing their own synonyms). ([Microsoft for Developers][15])

That aligns with Stigmer if (and only if) the verbs truly are consistent across kinds: `apply/get/list/delete/validate`.

## 4. User experience research that’s relevant (not just opinion)

### 4.1 Real-world user testing comparing noun-first vs verb-first

John Starich describes revamping a CLI (IBM Cloud Kubernetes Service) and explicitly notes:

* they compared **noun-first vs verb-first vs grouped** structures via a wrapper users used in daily work,
* users favored both noun- and verb-first variants over the old structure,
* some users preferred verb-first because it aligned with `kubectl`,
* and the maintainability tradeoff: if nouns always support all verbs, **verb-first scales easily**; if nouns have very different actions, **noun-first may be lower maintenance**. ([UX Collective][16])

This is close to your decision: Stigmer’s *core* verbs look shared, but you may add specialized actions later.

### 4.2 Evidence that people create shortcuts/aliases for frequent commands (impacting “brevity vs explicitness”)

Schröder & Cito’s empirical study analyzed **2.2M shell aliases** and found common alias categories including **shortcuts that abbreviate subcommands**, and they frame a core CLI usability issue as “recognition over recall” (users must remember syntax) — aliases are one way users cope. ([Springer][17])

Relevance:

* If users can (and will) alias anyway, **your job is to keep the underlying command model consistent and stable** so their aliases don’t break.
* Long command paths (many nested nouns) often get aliased; verb-first vs noun-first matters less than **predictable structure** + **backward compatibility**.

### 4.3 Accessibility research highlights the cost of unstructured CLI experiences

Google Research’s publication summary of a CHI paper on CLI accessibility highlights that CLIs have accessibility issues, “most important being CLIs are unstructured text interfaces,” and it provides recommendations for improving accessibility. ([Google Research][18])

While not directly about verb/noun order, it supports investing in:

* structured, predictable output (e.g., `--json`, `--yaml`, stable columns),
* consistent help and error messages,
* and avoiding “magic” behavior without clear feedback.

## 5. Detailed pros/cons for each option (with Stigmer-specific notes)

### Option A — Resource-specific subcommands (current): `stigmer <resource> <verb>`

**Advantages**

* **High local discoverability**: `stigmer agent --help` shows everything about agents.
* Natural fit for CLIs where each resource has **unique verbs** (like `gh pr merge`, `gh repo fork`, etc.). ([GitHub CLI][8])
* Easy to implement with Cobra: each resource is a subtree; completion is straightforward.
* Explicit: fewer ambiguous cases for `get/delete` when IDs are not typed.

**Disadvantages**

* **Command surface grows as O(resources × verbs)**. Adding 6+ kinds multiplies the CLI size; this is exactly the “overwhelming help output” failure mode Starich describes. ([UX Collective][16])
* **Redundant typing and redundancy in docs** if verbs are uniform across kinds.
* Awkward for **mixed-kind YAML**: if a file/dir contains `Agent` + `Workflow`, which resource subtree owns `apply`? (Kubernetes’ `apply -f dir/` is explicitly designed to handle mixed manifests.) ([Kubernetes][1])
* Cross-resource operations become harder to express (e.g., “apply everything in this folder”).

**Best fit**

* When each resource has **substantially different operations** and users start from the noun (“I’m working with PRs…”) more than the action.

**Anti-patterns to avoid**

* Inconsistent verbs (`remove` vs `delete` vs `rm`) across resource groups (PowerShell calls this out as a consistency problem). ([Microsoft for Developers][15])
* Deep nesting without good help structure (leads to “wall of text” help). ([UX Collective][16])

---

### Option B — Generic verb-first lifecycle commands with typed resources: `stigmer <verb> …`

**Advantages**

* **Scales extremely well** for many resource kinds when the verbs are shared:

  * add a new kind, and `apply/get/delete/list/validate` automatically work (if your backend/schema supports it).
  * This is essentially how Kubernetes’ API is modeled: a resource-based API with standard verbs (get/list/create/update/delete). ([Kubernetes][14])
* Enables **multi-resource apply/validate**:

  * Kubernetes explicitly supports applying multiple files, directories, and even multi-doc YAML via `apply -f`. ([Kubernetes][1])
* Encourages **consistent verb vocabulary** (PowerShell’s rationale). ([Microsoft for Developers][15])
* Shorter global help (fewer top-level commands).

**Disadvantages**

* You must solve **resource-type discoverability**:

  * kubectl solves it with `api-resources` and consistent `TYPE` naming. ([Kubernetes][3])
  * Without an equivalent, users will guess resource names and get frustrated.
* Auto-detection can become “magic”:

  * If YAML is missing `kind`, or contains multiple docs, errors must be very clear and ideally actionable.
* Specialized verbs become awkward:

  * If only workflows can `run`, you either (a) make `stigmer run` accept only workflows (surprising), or (b) reintroduce resource groups for specialized commands → hybrid anyway.
* Completion is more complex: `stigmer get <TAB>` should list kinds dynamically.

**Best fit**

* When 80%+ of operations are **shared lifecycle verbs** and the tool feels like a “resource API client” (kubectl-like). ([Kubernetes][3])

**Anti-patterns to avoid**

* Allowing `stigmer get abc123` without a typed reference unless you can guarantee unambiguous resolution (or you’ll create hard-to-debug accidents).
* Verb proliferation (`apply`, `create`, `upsert`, `deploy`) that overlap.

---

### Option C — Hybrid (as you proposed): generic `apply/validate`, resource-specific `get/list/delete`

**Advantages**

* Minimal disruption: keep current mental model while gaining the biggest win of YAML-kind auto-detection.
* Aligns with the reality that **file-based operations naturally carry their type in the file** (as Kubernetes demonstrates via manifests containing `kind:`). ([Kubernetes][1])
* Avoids ambiguity for ID-based operations if your IDs aren’t typed.

**Disadvantages**

* **Inconsistency**: users must remember which verbs are global and which are under resources.
* Can fragment documentation and examples.
* You may still want global `get/delete -f` equivalents later (kubectl supports file-based get/delete patterns). ([Kubernetes][3])

**Best fit**

* When you want to keep noun-first as primary UX, but you have strong mixed-kind YAML workflows that demand global `apply/validate`.

**Anti-patterns to avoid**

* Two subtly different applies: e.g., `stigmer apply` vs `stigmer agent apply` behaving differently for the same YAML kind.
* Hiding the detection: always show what kind(s) were detected and what actions were taken.

## 6. Recommendation for Stigmer: “kubectl-like core + grouped specialized commands + compatibility aliases”

Given your constraints (YAML has `apiVersion/kind`, DevOps audience, and you want to avoid breaking changes), the best fit is:

### 6.1 Make **generic verbs the canonical lifecycle interface**

A concrete target grammar:

```bash
# File-based, kind auto-detected (supports multi-doc and mixed kinds)
stigmer apply -f ./agent.yaml
stigmer validate -f ./workflow.yaml
stigmer apply -f ./manifests/          # directory: apply everything inside

# Reference-based: require explicit kind (either positional or type/id)
stigmer get agent/abc123
stigmer delete workflow/def456
stigmer list agents
stigmer list workflows
```

This matches what users already know from Kubernetes:

* `kubectl apply -f ./dir` (apply multiple manifests from a directory) ([Kubernetes][1])
* `kubectl get pods` (verb-first, resource type argument) ([Kubernetes][3])
* `kubectl delete` supports deleting “by file names, stdin, resources and names…” ([Kubernetes][19])

### 6.2 Add a **discoverability primitive** like `kubectl api-resources`

You should expect to add something like:

```bash
stigmer resources        # or: stigmer kinds
stigmer resources --wide # show kind, apiVersion, shortnames, plural, scope
```

Because kubectl explicitly points users to `api-resources` for the list of supported resources. ([Kubernetes][3])

This is what makes Option B actually usable at scale.

### 6.3 Keep resource-specific command trees for specialized verbs and backward compatibility

Example:

```bash
# Keep as aliases/wrappers (no breakage)
stigmer agent get abc123        # -> stigmer get agent/abc123
stigmer workflow validate -f w.yaml  # -> stigmer validate -f w.yaml (detects kind anyway)

# Use resource groups for “non-universal verbs”
stigmer workflow run <ref>
stigmer agent test <ref>
stigmer mcpserver ping <ref>
```

This is consistent with clig.dev’s guidance:

* two-level noun/verb structure is common,
* consistency matters more than which order you choose,
* and interfaces should evolve via additive changes + deprecation. ([CLI Guidelines][2])

### 6.4 Make auto-detection safe and non-magical

If you implement kind auto-detection:

* Print (or `--verbose` print) what you detected: kind(s), apiVersion(s), and count of docs.
* Provide an override flag for edge cases (e.g., `--kind Agent` or `--strict-kind`).
* Fail fast with clear error text (clig.dev: validate input and make errors understandable). ([CLI Guidelines][2])

## 7. Migration considerations (minimize breakage)

You can transition with **zero breaking changes** by making the new interface **additive**:

1. **Introduce new generic verbs** (`apply`, `validate`, `get`, `list`, `delete`) at top level.

   * Internally route to existing implementations (or a shared handler) so you don’t duplicate logic.

2. **Keep existing resource-first commands as aliases/wrappers**, but:

   * mark them “legacy” in help output, or
   * keep them but move primary docs/examples to the new canonical form.

3. **Add deprecation warnings gradually** (only once per session, or behind `--warnings`), following the “lengthy and well-documented deprecation process” guidance. ([CLI Guidelines][2])
   Starich also emphasizes breaking compatibility only with careful migration planning and user testing. ([UX Collective][16])

4. **Provide a mechanical migration aid** if you ever do remove old paths:

   * Starich describes building tooling to help scripts move to new commands as part of a staged migration. ([UX Collective][16])
     You may not need this now, but it’s worth keeping in mind if you plan a “v2” CLI later.

5. **Invest in help + examples + completion early**

   * clig.dev: show concise help by default, extensive help on demand, lead with examples. ([CLI Guidelines][2])
   * Kubernetes highlights shell completion as a first-class workflow. ([Kubernetes][1])
     This matters even more once you have `stigmer get <type>` because the `<type>` space grows.

* Kubernetes `kubectl apply` and manifest workflows (including multi-file/dir + multi-doc YAML examples). ([Kubernetes][1])

* Kubernetes `kubectl delete` supports deletion by file/stdin or type/name. ([Kubernetes][19])
* Kubernetes API is explicitly “resource-based” with standard verbs for retrieve/create/update/delete. ([Kubernetes][14])

### Service/platform CLI grouping precedent

* AWS CLI v2 command structure: `aws <command> <subcommand> [options]` where top-level command is typically a service. ([AWS Documentation][5])
* gcloud documented as a command “tree” and notes tab completion for commands and resources. ([Google Cloud Documentation][7])

### Hybrid and resource-grouped precedents

* Docker CLI reference shows extensive noun-grouping (`docker container …`, `docker image …`) and even a mechanism to hide legacy commands. ([Docker Documentation][11])
* Podman command list explicitly includes management groups like `container` (“Manage containers”) and `image` (“Manage images”). ([Podman Documentation][12])
* Helm command list shows both verb-first commands (`install`, `upgrade`, `list`, `uninstall`) and grouped nouns (`repo`, `plugin`, `get`). ([Helm][13])

### CLI design guidelines + UX research

* Command Line Interface Guidelines (clig.dev): subcommands, noun/verb pattern, consistency, and future-proofing + additive changes; help best practices. ([CLI Guidelines][2])
* PowerShell team rationale for verb-first naming: encourages verb reuse and consistent UX. ([Microsoft for Developers][15])
* John Starich (UX Collective): user testing comparing noun-first vs verb-first; maintenance scaling tradeoff; staged migration. ([UX Collective][16])
