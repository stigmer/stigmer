## Decisions Made

- **Streaming via `result` field**: During streaming, thinking content lives in `tc.result` (rendered by `renderStreamingTool`). After completion, content moves to `tc.args.thought` (rendered by `resolveDisplayContent` with `contentSourceInput`). The transition is natural because `ToolCompletedEvent` rebuilds the block from scratch.
- **No CLI code changes needed for streaming**: The existing CLI streaming pipeline (`emitToolCallStateEvents` → `ToolStreamDeltaEvent` → `renderStreamingTool`) handles native thinking streaming without modification. Only the `toolDisplayMap` entry was needed.
- **Defensive fallback in flush**: `_flush_thinking_buffer` falls back to creating a new COMPLETED ToolCall from scratch if no streaming ToolCall exists, ensuring thinking content is never lost even in edge cases.

## Learnings

- `completed_at` on ToolCall proto is a string field (not a Timestamp sub-message), so it uses direct assignment (`tc.completed_at = _utc_timestamp(now)`) not `CopyFrom`
- `args` is a Struct sub-message and supports `CopyFrom` for in-place updates
- The `StreamingUpdateScheduler` pushes updates every ~500ms, which for a 10,000-token thinking budget running 5-15 seconds produces 10-30 incremental updates — a visible live streaming effect
