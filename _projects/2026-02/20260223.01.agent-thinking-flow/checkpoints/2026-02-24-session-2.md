## Decisions Made

- **Thinking budget as platform default**: 10,000 tokens, not user-configurable. Follows Cursor's pattern — the platform selects the optimal budget.
- **Dual-path gating via `has_native_thinking`**: Detected at `create_deep_agent()` by checking if the model instance is `ChatAnthropic` with a `thinking` attribute set. Works for both string-parsed and pre-built model instances.
- **`claude-opus-4.6` excluded**: Anthropic deprecated manual `type: "enabled"` thinking on Opus 4.6. It requires `type: "adaptive"` with effort parameter — fundamentally different API shape. Deferred to future work. Opus 4.6 agents get the explicit think tool as fallback.
- **Temperature/top_k removal**: Anthropic's API rejects `temperature` and `top_k` when thinking is enabled. The model parser automatically strips these with a warning log when thinking is auto-enabled.
- **Synthetic think tool translation**: Rather than introducing new protobuf fields or gRPC message types, native thinking blocks are converted to standard `ToolCall(name="think")` protos in the StatusBuilder. This reuses the entire downstream pipeline (gRPC, CLI) without changes.

## Learnings

- Anthropic's extended thinking blocks arrive as `{"type": "thinking", "thinking": "..."}` in the content list, streaming BEFORE text blocks. This natural ordering means accumulating thinking and flushing on first text produces correct timeline ordering.
- `langchain-anthropic` 1.3.x handles thinking block stripping/redaction in multi-turn conversations automatically. No special handling needed in graphton.
- The `thinking` parameter on `ChatAnthropic` is exposed as an attribute, making detection straightforward via `getattr(model_instance, "thinking", None)`.
- `claude-opus-4.6` uses "adaptive thinking" (`type: "adaptive"` + `effort` parameter) which is fundamentally different from the manual `type: "enabled"` mode used by other models. This cannot be handled with the same code path.

## Open Questions

- How will native thinking interact with multi-turn tool-use conversations? Thinking blocks typically appear in the first response; subsequent responses after tool results may not include thinking. The StatusBuilder handles this naturally (empty buffer = no synthetic ToolCall), but real-world behavior needs Phase 4 validation.
- What's the actual token overhead and quality impact of 10,000 budget tokens? Needs measurement during Phase 4.
- When should adaptive thinking support for Opus 4.6 be added? It's a separate API shape but would benefit from the same synthetic ToolCall translation approach.
