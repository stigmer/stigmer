## Decisions Made

1. **Token endpoint is gRPC, not REST**: Connect protocol gives HTTP/JSON for free. Platform builders can call `mintUserToken` as a simple POST with JSON body — no gRPC tooling required. Keeps the API surface consistent.

2. **`auto_grant_on_org` is bool (like IdentityProvider)**: Grants on the PlatformClient's owning org. A string (arbitrary org ID) would enable cross-org grants but introduces security complexity — decided against it.

3. **`PlatformClientCreateResponse` wraps resource + secret**: Unlike ApiKey (which returns the resource directly), PlatformClient makes the one-time secret return explicit in the type system rather than relying on handler-level field injection.

4. **`mintUserToken` naming**: "Mint" is precise (Stigmer is issuing a new token) and avoids collision with generic CRUD "create" semantics.

5. **Stigmer signs its own JWTs**: PlatformClient tokens are signed by Stigmer's own key pair, not Auth0. This makes Stigmer a token issuer for the first time. The auth chain (T04) will need a new `PlatformClientTokenAuthenticationProvider`.

6. **Account linking is a future concern**: Discussed potential identity confusion when the same user accesses Stigmer through multiple auth paths. Concluded it's not a PlatformClient-specific problem — affects IdentityProvider equally. Flagged for future project, not a blocker.

## Codegen Fix: Token Service Role

The SDK codegen (`inferServiceRole` in `tools/codegen/proto2schema/main.go`) defaulted any service name without "command" or "query" to `"query"`. This caused `PlatformClientTokenController` to collide with `PlatformClientQueryController` (both got role "query", creating duplicate struct fields in Go). Fixed by adding `"token"` as a recognized service role. All four SDK generators (Go, TypeScript, Python, Java) now correctly produce three distinct client fields.
