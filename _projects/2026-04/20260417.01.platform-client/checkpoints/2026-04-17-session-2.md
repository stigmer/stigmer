## Decisions Made

1. **apply RPC removed**: The apply (create-or-update) pattern is fundamentally incompatible with PlatformClient because create returns `PlatformClientCreateResponse` (resource + one-time secret) while apply returns `PlatformClient`. If apply silently created a resource, the secret would be generated but never returned.

2. **Redis caching deferred to T03**: The `client_id` -> PlatformClient cache is only consumed by the token endpoint's authentication flow. Building it in T02 would create dead code.

3. **Context data map for intermediate state**: When using `CustomOperationHandlerV2<PlatformClient, PlatformClientCreateResponse>`, the context's `target` field is typed as `PlatformClientCreateResponse` (output type). Intermediate `PlatformClient` state is stored via `context.put()/get()` with `Context.Key<PlatformClient>`.

4. **PreserveCredentials step**: The framework's `clearComputedFields` step during update clears ALL fields marked `computed = true` in the proto, including credential fields. A custom step restores them from the existing resource after buildNewState runs.

## Learnings

- The SDK codegen's `inferResourceType` was fragile — it assumed the first command method's output type is the resource type. This assumption broke when `apply` (which returns the resource directly) was removed, making `create` (which returns a wrapper) the first method. Fixed by preferring `update`/`delete` output types.

- `ClearRequestComputedFieldsStepV2` + `UpdateOperationBuildNewStateStepV2` has a latent issue: computed spec fields (e.g., `key_hash`, `fingerprint` on ApiKey) are cleared during update but never restored from the existing resource. Only metadata identifiers are preserved. This is likely a framework-level bug affecting any resource with computed spec fields.

## Open Questions
