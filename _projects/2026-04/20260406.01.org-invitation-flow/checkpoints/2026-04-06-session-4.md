## Decisions Made

- **Token format: Base62 over Base64URL** — Base62 produces alphanumeric-only output, universally safe for copy-paste across Slack, email, SMS. Base64URL includes `-` and `_` which cause issues with double-click selection in some contexts.
- **Token size: 16 bytes (128 bits)** — sufficient entropy for revocable, short-lived tokens. Produces ~22-char tokens vs ~43-char for 32 bytes. Cleaner URLs improve share-ability.
- **No token prefix** — the URL path `/invite/<token>` provides context. Prefixes add length without improving security or disambiguation for this use case.
- **Plaintext token storage** — unlike API keys, invite tokens are designed to be shared openly. No benefit to hashing.
- **Deferred InvitationRedeemHandler** — cross-aggregate orchestration (creating IAM policies from invitation domain) requires focused architectural discussion. Options include direct repo calls, a shared service, or programmatic handler invocation.

## Learnings

- `StepResult` (from `ai.stigmer.utils.step`) does not expose `getErrorMessage()` — use `authConfig.getErrorMsg()` from `RpcAuthorizationConfig` for authorization failure messages (pattern from `IamPolicyCreateHandler`)
- `CustomOperationHandlerV2` is the right base class when I/O types don't match standard CRUD conventions (e.g., `InvitationId` -> `Invitation` for revoke, `InvitationTokenInput` -> `InvitationPreview` for getByToken)
- Cross-domain reads via `MongoTemplate` directly (not through domain repos) is the established pattern for avoiding coupling — see `IdentityProviderGetSsoProviderHandler.LoadSsoProvider`
- `@AutoGrpcRouterController` annotation auto-generates both command and query controller implementations from proto stubs

## Open Questions

- **RedeemHandler architecture**: How should invitation redemption create IAM policies? Direct repo + FGA writes? Shared `IamPolicyCreationService`? Programmatic `IamPolicyCreateHandler` invocation? Each has trade-offs around atomicity, coupling, and testability.
- **Idempotency in redemption**: Need to check if the caller is already an org member before creating duplicate IAM policies
- **State machine transitions**: When `max_redemptions` is reached, should the invitation auto-transition to `fully_redeemed`, or stay `active` and reject new attempts?
