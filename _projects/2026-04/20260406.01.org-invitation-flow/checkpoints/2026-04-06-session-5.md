## Decisions Made

- **`buildInviteUrl` prop** over hardcoded URL: platform builders may have `/join/` instead of `/invite/`, or different domains. Default uses `window.location.origin/invite/<token>` for browser environments.
- **`isAuthenticated` boolean** over embedded auth detection: keeps `InvitationRedemption` auth-agnostic. Defaults to `true` — platform builders who render only for authenticated users ignore it entirely.
- **`org` (slug) not `orgId`** for `InvitationManager`: mirrors the proto `ListInvitationsByOrgInput.org` parameter shape. Different from `OrgMembersPanel` which takes `orgId` (IAM policy APIs use IDs).
- **Self-contained panel pattern** (like `OrgMembersPanel`) over decomposed pieces (like API key): invitation management is always needed as a unit. A platform builder should embed it with one prop.

## Learnings

- The `OrgMembersPanel` pattern (self-contained panel) is better DX than the API key pattern (separate pieces) for features that are always used as a unit
- `InvitationState` enum is accessed as `InvitationState.active` from `@stigmer/protos/ai/stigmer/iam/invitation/v1/enum_pb`
- `IamRole` value import (not `type` import) needed for default prop values and `RoleSelector` kind prop
- `timestampDate` from `@bufbuild/protobuf/wkt` converts proto timestamps to JS Date objects
- Cross-domain imports within the SDK (e.g., `invitation/` importing from `iam-policy/RoleSelector`) are appropriate and encouraged
