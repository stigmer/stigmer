## Decisions Made

- **SDK-first**: `OrgProfilePanel` lives in `@stigmer/react`, not `client-apps/web`. Platform builders can embed `<OrgProfilePanel orgId="..." />` in their own dashboards without Console dependencies.
- **Fetch internally**: The panel takes `orgId` and fetches via `useOrganization()` rather than accepting a pre-fetched org prop. This keeps the component self-contained at the cost of one extra API call when the Console already has the org in `OrgProvider`.
- **Slug is read-only**: Changing slugs has cascading effects on all resource references. Not a v1 concern — display with copy button only.
- **Logo URL (not upload)**: Proto defines `spec.logo_url` as a string. File upload would require asset storage infrastructure. URL input is sufficient for v1.
- **Always-editable form**: Settings pages should have always-editable forms with a save button (Jakob's Law — matches GitHub/Vercel/Slack org settings patterns).
- **Dirty detection**: Form state compared against server snapshot to enable/disable save button and show discard option.

## Learnings

- All `*Input` types in the codegen'd SDK use `name/slug/org` for resource identification, not `id`. The `OrganizationClient.update()` works the same way as `IdentityProviderClient.update()` and `EnvironmentClient.update()` — consistent across all resources.
- The `OrgProvider` in the Console already has the full `Organization` proto from `findMyOrganizations()`, but for SDK embeddability, the panel must fetch its own data.
- The `refresh(slug)` callback on `OrgProvider` re-fetches all orgs and auto-selects the matching slug — this is the mechanism for syncing the sidebar after an org name change.

## Open Questions

- Should the Org Profile page eventually support slug editing? This is a complex operation with cascading effects on all resource references. Would need a dedicated server-side "rename" flow.
- Logo file upload vs URL: When/if asset storage infrastructure is built, the logo field should be upgraded to support direct upload.
