## Decisions Made

- **5 agents instead of 4**: Added data-analyst-agent (not in original plan) because Postgres pairing is a strong use case
- **Lean instructions (~15 lines each)**: Agent Runner handles skill activation (SkillWriter generates "Available Skills" section) and tool injection (LangGraph tool wrappers), so agent instructions only carry identity, behavioral guardrails, and output expectations
- **No `enabled_tools`**: MCP server defaults are used since tool discovery hasn't been run; avoids silent runtime failures from unverified tool names
- **No `env_spec` on agents**: MCP servers declare their own env vars; duplicating them on agents would violate DRY
- **Slack + Linear for support-agent**: Zendesk was dropped from MCP catalog (low quality); Slack covers communication, Linear covers issue tracking
- **Three search providers for research-agent**: Brave Search (broad web), Exa (semantic/neural), Fetch (full page retrieval) -- research genuinely benefits from multiple information sources

## Learnings

- The Agent Runner's `SkillWriter` follows a progressive disclosure model: only name + description + location injected into prompt; SKILL.md materialized on disk for the model to read on demand
- The Graphton `enhance_user_instructions` wraps the agent's instructions in a capabilities/resilience envelope -- agent instructions land under "## Your Task"
- MCP tools are registered as LangChain tool objects with descriptions from the MCP server's `tools/list` response, not from the prompt
- This means composite agents need far less instruction prose than initially estimated -- the composition happens in the YAML structure (skill_refs + mcp_server_usages), not in instructions
