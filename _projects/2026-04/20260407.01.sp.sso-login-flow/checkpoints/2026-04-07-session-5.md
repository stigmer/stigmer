## Decisions Made

- **Direct repo save for update handler**: The standard `UpdateOperationHandlerV2` authorizes with `can_edit` on the identity account, but federated account lifecycle uses `can_create_identity_account` on the organization. Using `IdentityAccountRepo.save()` directly avoids the authorization model mismatch.
- **Option A for revokeOrgAccess**: Extended the shared `IamPolicyGrpcRepo` interface (canonical cross-domain pattern) rather than ad-hoc gRPC stub usage in the handler.
- **Cache cleanup in deprovision**: Added best-effort Redis cache cleanup for the federation resolver cache entry. Small addition, prevents stale auth resolution after deprovision.
- **No audit timestamp management**: The `save()` method is a raw replaceOne — we preserve existing audit timestamps rather than adding manual timestamp management that might conflict with the standard pipeline later.

## Learnings

- Several Phase 2 items were already completed during Session 4 (Phase 1): `expectedAudience` population, `revokeOrgAccess` interface, Redis delete method. The session boundary between Phase 1 and Phase 2 was porous.
- The `CustomOperationHandlerV2` pattern with inner `@Component` step classes works well for handlers with custom authorization models that don't fit the standard CRUD pipeline.
- `Context.Key<T>` on `CustomOperationContextV2` is the established pattern for passing data between pipeline steps (used by `IamPolicyRevokeOrgAccessHandler`, now also by our handlers).
