## Decisions Made

1. **AgentRunner IS a domain resource** — not just infrastructure. The session composer, CLI, and platform-for-platforms framing all demand first-class CRUD.
2. **Kubernetes Node pattern** — thin spec (description only), rich status. Runner self-reports everything via heartbeat.
3. **No lifecycle/placement/runtime enums** — runner is a process with a name, queue, and connection info. Simplicity over expressiveness.
4. **Per-runner queues** (`agent-runner:{runner-id}`) — works for ephemeral (one execution) and persistent (many executions) alike.
5. **Both ephemeral and persistent runners are resources** — ephemeral labeled `stigmer.ai/system-managed`, hidden from session composer.
6. **Runner identity persists across restarts** — CLI stores ID in `~/.stigmer/runner.json`, calls `apply` to reactivate.
7. **`agent_runner_id` on SessionSpec and AgentExecutionStatus** — session binds to a runner, execution records which runner handled it.
8. **Dedicated `heartbeat` RPC** — lightweight, every 30s, 90s timeout for STOPPED transition.

## Learnings

- The original T01 design over-specified the domain model with lifecycle/placement/runtime enums. The brainstorm stripped it down to essentials. The runner is infrastructure that registers itself — the Kubernetes Node analogy was the breakthrough.
- "Platform for platforms" framing settled the per-runner vs per-user vs per-execution queue debate. External platforms integrating with Stigmer need addressable runners with stable queues.
- Saving ephemeral runners as resources (rather than treating them as invisible infrastructure) gives a single code path for dispatch and observability.

## Open Questions

- How will `sandbox_id` on SessionSpec interact with the new `agent_runner_id`? The runner owns the sandbox (status field), but existing code reads `session.spec.sandbox_id`. Migration path needed.
- MCP workflows currently share the runner's task queue — need to split into separate worker mode when per-runner queues are active.
