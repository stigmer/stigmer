# Session Notes: 2026-04-20 (Session 4 — Side-Channel Proxy FGA Authorization)

## Accomplishments

- Conducted comprehensive security audit of the Side-Channel Proxy — identified 7 findings across checkpoint, artifact, and LLM endpoints
- Evaluated and rejected two intermediate approaches before arriving at the right design:
  1. Execution-scoped JWTs through Temporal — rejected because credentials in Temporal history is the same leak we're trying to eliminate, and TTL is incompatible with durable executions
  2. Custom `X-Stigmer-*` context headers + MongoDB execution validation — rejected as unnecessary complexity that doesn't leverage existing FGA infrastructure
- Implemented FGA-based authorization that reuses the exact same `RequestCallerIdentityMapper` → `RequestAuthorizationService` → OpenFGA `check()` path as gRPC handlers
- Added `ProxyAuthorizationService` with 5-minute in-memory cache for hot-path optimization
- Added input validation hardening (document size limits, artifact key pattern validation, path traversal prevention)
- Runner-side: `HttpCheckpointSaver` now includes `org_id` in checkpoint documents from LangGraph `configurable.org`

## Decisions Made

1. **FGA authorization, not custom infrastructure** — The user correctly identified that building custom context headers and MongoDB validators was unnecessary complexity when we already have a full FGA authorization system. The proxy should just use it.
2. **Runner always carries user credentials** — Both user-started (CLI) and platform-started runners inject the user's token (API key or JWT), not a shared service key. This was a critical clarification that made FGA authorization viable.
3. **Checkpoint authorization derives session from thread_id** — `thread-{session_id}` convention enables FGA check on `session.can_view` / `session.can_edit` without additional context headers.
4. **Artifact authorization derives execution from key** — `artifacts/{execution_id}/...` convention enables FGA check on `agent_execution.can_view` / `agent_execution.can_edit`.
5. **LLM proxy is authentication-only** — Stateless pass-through, no data isolation concern, no FGA overhead.
6. **5-minute FGA result cache** — Eliminates hot-path latency while keeping the security model correct.

## Learnings

- The instinct to "build something new" (execution-scoped JWTs, context headers) was wrong. The right answer was to use the existing FGA infrastructure that was already designed for exactly this purpose.
- The session-as-personal-resource FGA model (`owner`, `viewer`, explicit grants, org admins excluded) was already perfectly designed for checkpoint authorization — we just weren't using it.
- FGA's built-in relation traversal (`agent_execution.can_view: viewer from session`) eliminates the need for manual session lookups when authorizing execution access.

## Open Questions

- Existing checkpoint documents lack `org_id`. When we deploy, old checkpoints will still be accessible (FGA controls access, not the document field). The `org_id` is for data quality, not security.
- Ephemeral threads (`ephemeral-{agent_id}-{uuid}`) don't follow the `thread-{session_id}` convention. These would be denied by the current session derivation. But the setup code requires `session_id` for all executions, so ephemeral threads may not exist in cloud mode.
