# Session Notes: 2026-04-05 (Session 2)

## Accomplishments

- Resolved the open question from session 1: `repeated IamRole` (type-safe enum) chosen over `repeated string`

## Decisions Made

- **`repeated IamRole` over `repeated string`**: The grantable role vocabulary is closed (owner, admin, member, viewer) and maps 1:1 to the `IamRole` enum. Type safety catches invalid values at compile time. The edge cases (`creator` on environment, `operator` on platform) are correctly excluded — `creator` is an attribution handled by `requires_creator_tuple`, and `operator` is a platform concept outside the IAM policy model.
- **Import direction**: `authorization_config.proto` (commons/apiresource) now imports `enum.proto` (iam/iampolicy). Verified no circular dependency — `enum.proto` is a leaf with zero imports.
- **Empty default for non-grantable resources**: Resources with no user-grantable roles (api_key, execution_context, agent_execution, identity_account, iam_policy, platform, api_resource_version) simply omit `grantable_roles`, relying on the empty repeated field default.

## Learnings

- The FGA model is the definitive source for which roles are directly assignable (`[identity_account]` type annotations) vs computed (expression-based definitions)
- `viewer` in FGA is a hybrid — it has both direct assignment and computed parts — but the grantable aspect is the `[identity_account]` part, so it correctly appears in `grantable_roles`
- `iam_policy.viewer` is purely computed (`admin from organization`) with no `[identity_account]` assignment, so iam_policy correctly has no grantable roles

## Open Questions
