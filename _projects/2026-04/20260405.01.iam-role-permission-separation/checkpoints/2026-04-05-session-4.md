## Decisions Made

- **Validation placement**: Added after `authorize` and before `checkIfDuplicate` in the pipeline. After authorize so unauthorized callers don't learn which roles are valid (principle of least information). Before checkIfDuplicate because there's no point checking duplicates for an invalid role.
- **Bootstrap path excluded**: `IamPolicyBootstrapPolicyHandler` is intentionally NOT validated. Bootstrap legitimately writes structural relations (`"organization"`, `"creator"`) and owner tuples that are not in `grantable_roles`. The two paths serve fundamentally different purposes: `create` is user-facing grants, `bootstrapPolicy` is system-internal tuple materialization.
- **Error message design**: Descriptive `INVALID_ARGUMENT` messages include the allowed roles list so callers can self-correct. Three cases: unknown resource kind, no grantable roles (system-managed), and role not in allowed list.
- **No new dependencies in the step**: `AuthorizationConfigResolver` is a static utility class (`@UtilityClass`), so `ValidateGrantableRole` has no injected dependencies — it calls static methods directly. This follows the existing resolver pattern.

## Key Code Changes

- **`AuthorizationConfigResolver.java`** (api-shape library): Added `hasGrantableRoles(ApiResourceKind)` and `getGrantableRoles(ApiResourceKind)`, consistent with existing methods like `requiresAuthorization`, `requiresOwnerTuple`, `hasAdditionalParents`
- **`IamPolicyCreateHandler.java`** (stigmer-service): Added `ValidateGrantableRole` inner class following `@Component @RequiredArgsConstructor static class` pattern. Wired into pipeline and constructor injection.

## Learnings

- The `create` and `bootstrapPolicy` RPC paths have clearly separated concerns: `create` requires `can_grant_access` on the target resource and is for user-facing role grants; `bootstrapPolicy` requires `can_bootstrap_iam` on `platform:stigmer` and is for system-created tuples during resource creation. This clean separation made it safe to add validation only to the user path.
- `IamPolicyCreationService.createTuples` uses `bootstrapPolicy` (not `create`) for all system-created tuples, so the new validation does not interfere with resource creation flows.
