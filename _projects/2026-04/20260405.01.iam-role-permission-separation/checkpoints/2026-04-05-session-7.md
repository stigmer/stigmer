## Decisions Made

- **Codegen over static maps**: `CLOUD_ONLY_KINDS` and `GRANTABLE_ROLES` are now generated from proto `kind_meta` options, not hand-maintained
- **useResourceAccess is generic**: Works for any resource kind (org, agent, environment), not just organizations — designed for reuse
- **useWhoAmI with caching**: Result cached per Stigmer client instance to avoid redundant whoAmI RPCs across re-renders
- **Settings page section (not new route)**: Members added as a section on the existing flat `/settings` page, matching the established pattern
- **Members section first**: Placed above API Keys and Environments in the settings page for visibility
- **Self-protection via SDK**: `OrgMembersPanel` discovers current user internally via `useWhoAmI()`, no prop needed from Console
- **V1 invite by ID**: Reuses existing `GrantAccessForm` with raw principal ID input; email-based lookup deferred

## Learnings

- `sdk_docs.go` already had the pattern for reading `kind_meta` extensions (`buildIdPrefixMap()`) — followed the same approach
- The `identityAccount.whoAmI()` RPC is essential for SDK-level self-protection in access management UIs
- `PrincipalAccess.principal` is an `ApiResourceRefView` with rich display fields (name, email, avatar) — makes the members list viable without additional lookups

## Open Questions

- **ApiResourceRefView population**: Need to verify that Track 2 backend populates `name`, `email`, `avatar` in `PrincipalAccess.principal`. If sparse, UI degrades to IDs only.
- **orgId vs orgSlug**: `ListResourceAccessInput` takes `ApiResourceRef.id` — need to verify whether this expects the org's resource ID or slug
- **Role change atomicity**: Delete + create is not atomic. If delete succeeds but create fails, user temporarily loses access.
