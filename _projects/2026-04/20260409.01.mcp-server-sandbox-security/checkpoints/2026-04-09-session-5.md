# Session Notes: 2026-04-09 (Session 5)

## Accomplishments

### Polyglot MCP Snapshot Workflow — COMPLETE

Restructured the MCP sandbox snapshot builder from a monolithic Python workflow into a polyglot Temporal workflow spanning Stigmer Service (Java) and Agent Runner (Python). Also diagnosed and fixed the root cause of zero schedules appearing in the production Temporal UI.

**1. Diagnosed "0 Schedules" production bug** — Checked Stigmer Service pod logs in `stigmer-prod` namespace. Found `McpRegistrySyncScheduleRegistrar` failing with `"ID required on workflow action"` because `WorkflowOptions.newBuilder()` was missing `.setWorkflowId(...)`. The Temporal Java SDK requires a workflow ID on `ScheduleActionStartWorkflow`.

**2. Fixed schedule registration** — Added `.setWorkflowId(SCHEDULE_ID)` to `McpRegistrySyncScheduleRegistrar.java`. This fixes both the existing `mcp-registry-sync-daily` schedule and establishes the correct pattern for new schedules.

**3. Built polyglot snapshot workflow (Java side)** — Created 11 new Java files under `mcpserver/temporal/`:
- `McpSnapshotTemporalConfig.java` — Spring config with schedule interval, runner queue, max packages per runtime, curated baseline lists
- `McpSnapshotTemporalWorkflowTypes.java` — Workflow and activity type constants
- `McpSnapshotScheduleRegistrar.java` — Registers `mcp-snapshot-build` schedule on startup with interval-based scheduling, memo-based runner queue routing
- `BuildMcpSnapshotWorkflow.java` / `BuildMcpSnapshotWorkflowImpl.java` — Polyglot workflow: local activity resolves packages, remote activity builds snapshot
- `ResolveSnapshotPackagesActivity.java` / `ResolveSnapshotPackagesActivityImpl.java` — Local activity queries `mcp_server` collection for registry-synced servers, extracts package identifiers from `spec.stdio` configs, merges with curated baseline
- `BuildMcpSnapshotActivity.java` — Remote activity stub matching Python `@activity.defn(name="BuildMcpSnapshot")`
- `SnapshotPackages.java`, `BuildMcpSnapshotInput.java`, `BuildMcpSnapshotOutput.java` — Model records with `@JsonProperty` snake_case mapping for polyglot serialization
- Updated `McpServerSyncTemporalWorkerConfig.java` to register both workflows on `mcp_server_sync` queue
- Added `temporal.mcp-snapshot` section to `application-temporal.yaml`

**4. Simplified Python side** — Removed `BuildMcpSnapshotWorkflow` class from `build_mcp_snapshot.py` and its registration from `worker.py`. The activity stays as-is — its `BuildMcpSnapshotInput` already accepts explicit package lists.

## Decisions Made

- **Workflow queue**: Reuse `mcp_server_sync` queue (same domain, already has a Java worker). No new queue infrastructure needed. The Python `BuildMcpSnapshot` activity continues to run on `agent_execution_runner`.

- **Package resolution from registry catalog**: Since no runtime usage tracking exists, V1 queries the `mcp_server` collection for registry-synced servers and extracts package identifiers from `spec.stdio` configs. This uses data the MCP Registry sync already populates and will naturally grow. A curated baseline from Spring config ensures useful snapshots even with no DB data (cold-start).

- **Memo-based runner queue routing**: Following the `InvokeAgentExecutionWorkflow` pattern, the snapshot schedule passes `runnerTaskQueue` via workflow memo. The workflow reads it to route the Python activity.

## Learnings

- The Temporal Java SDK `ScheduleProtoUtil.actionToProto` requires a workflow ID on `ScheduleActionStartWorkflow`. Without it, the entire schedule registration silently fails (caught by the outer `try/catch`). Production logs revealed this immediately.
- The `McpRegistryTransformer` already maps registry packages to `StdioServerConfig` with `command` (npx/uvx) and `args` (package identifier), making package extraction straightforward for the resolve activity.
