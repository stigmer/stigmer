## Decisions Made

- **EnsureThread skipped for Cursor**: Python's EnsureThread generates deterministic "thread-{sessionId}" which is not a valid Cursor agentId. New ReadSessionThreadId local activity reads session.spec.thread_id instead.
- **approvalDecisions removed from Graphton**: The parameter was always nil/null across all call sites. Both harnesses use DB-driven approval resolution. Removing it cleans the interface.
- **Minimal branching in workflow**: Cursor flow structurally identical to Graphton. Same HITL loop, same pause/resume CancellationScope, same signals. Only three variation points: threadId source, activity type, no GenerateSessionSubject.
- **No GenerateSessionSubject for Cursor**: Cursor generates conversation context natively. Redundant LLM call avoided.
- **invokerIdentityAccountId on Java ExecuteCursor**: Added for forward-compatibility.
- **Harness on DispatchResult (not separate load)**: Session is already loaded during dispatch for runner resolution. Extracting harness there is zero-cost.

## Learnings

- T03's "minimal branching" insight proved accurate — the Cursor flow is structurally identical to Graphton. The initial plan (which assumed a simpler Cursor flow) was corrected based on T03 findings.
- The `approvalDecisions` parameter was a remnant of an earlier design that was superseded by DB-driven resume. Removing it now prevents confusion for future harness implementations.
- ReadSessionThreadId solves a subtle problem: the workflow needs the Cursor agentId for HITL reinvocation, but the agentId is only known after the first ExecuteCursor call stores it on the session.
