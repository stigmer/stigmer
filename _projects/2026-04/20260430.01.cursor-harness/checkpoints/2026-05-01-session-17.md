# Session Notes: May 1, 2026 — Session 17

## Accomplishments

- Added `RUNNER_PHASE_STARTING = 6` to the runner lifecycle proto, giving runners a dedicated phase for the bootstrap window between process launch and readiness
- Updated server-side heartbeat processing to treat `STARTING` as an active-transition phase (sets `started_at`, clears `stopped_at`)
- Added dynamic phase management to `RunnerStreamClient` with `SetPhase()` and immediate heartbeat on phase change
- Restructured `startNativeRunner` to open the heartbeat stream (with `STARTING` phase) before Python runtime bootstrap, then transition to `READY` after the Python process starts
- Updated React SDK phase utilities (labels, sort order, transitional check, dot color) and unit tests
- Updated both Desktop and SDK `PhaseBadge` components to show a spinner for the `STARTING` phase
- Reduced `RESTART_GRACE_MS` from 30s to 10s (the explicit `STARTING` phase makes the long grace period unnecessary)
- Regenerated all protobuf stubs in both `stigmer` and `stigmer-cloud` repos

## Decisions Made

- **STARTING as a first-class phase**: Rather than using client-side timers or grace periods to infer "starting", we added a proper server-acknowledged phase to the runner lifecycle. This is architecturally clean and works across all surfaces (desktop, web console, API).
- **Heartbeat before bootstrap**: The CLI now opens the gRPC heartbeat stream immediately after the runner is registered, before any runtime bootstrap (Python venv, Node.js install). This ensures the server knows the runner is alive and bootstrapping from the very first moment.
- **Phase change triggers immediate heartbeat**: When `SetPhase()` is called, it signals `phaseChanged` which causes `streamLoop` to send an extra heartbeat immediately rather than waiting for the next tick interval. This minimizes the window between "bootstrap complete" and "server knows READY".
- **Reduced RESTART_GRACE_MS**: With the explicit `STARTING` phase in the proto, the UI no longer needs a 30-second grace period to paper over missing state. 10 seconds is sufficient for the sidecar spawn latency.

## Learnings

- The runner lifecycle benefits from explicit server-side phases rather than client-side heuristics. The `STARTING` phase eliminates an entire class of UI timing bugs.
- The `phaseChanged` channel pattern in `RunnerStreamClient` is a clean way to inject out-of-band signals into a ticker-based loop without polling.
- Codegen across two repos (`make codegen` in stigmer, `make protos` in stigmer-cloud) is required whenever proto changes span the platform boundary.
