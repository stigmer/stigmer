# Session Notes: May 1, 2026 — Session 18

## Accomplishments

- Fixed the cursor-runner runtime crash (`ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`) caused by Node.js 22 strip-only mode encountering `export enum` in raw proto `.ts` stubs

## Decisions Made

- **Fix in `sync.sh` only, not source `package.json`**: The source-of-truth `apis/stubs/ts/package.json` keeps `"exports": { "./*": "./*.ts" }`. Changing it to conditional exports would require `dist/` to exist after every proto regeneration, adding friction. Other consumers (Vite, tsx, SDK TS) handle `.ts` natively. Only the embed path needs compiled JS.
- **Channel-based bootstrap overlap**: Used a buffered channel (`cursorBootstrapOutcome`) to pass the bootstrap result from the parallel goroutine to the cursor-runner launch goroutine. This is cleaner than sharing mutable state and naturally blocks until the result is ready.
- **Daemon path deferred**: The daemon bootstrap (`daemon_process.go`) is also sequential but lower priority — it has more components and sequential startup simplifies error handling there. Parallelization can be a follow-up.

## Learnings

- Node.js 22's strip-only TypeScript mode is deceptively limited — it handles basic type annotations but fails on any non-erasable syntax (`enum`, `namespace`, parameter properties). This is an important constraint for any project shipping raw `.ts` to a Node.js runtime.
- The `publishConfig.exports` pattern in `package.json` already described the correct published shape (`dist/*.js`), but the default `exports` used during development was what caused the runtime issue. The gap between dev and production exports is a recurring source of bugs.
- Node.js conditional exports (with `types` and `import` conditions) are the standard mechanism for dual-entry packages and work cleanly with both `tsc` and `node`.
