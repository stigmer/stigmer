## What Was Done

Implemented unified cost tracking for the Cursor harness by aligning the cursor-runner's usage tracking with the established per-message `LlmCallMetrics` pattern used by the Python agent-runner. Created a Cursor model pricing registry sourced from Cursor's published API rates. The entire existing downstream pipeline (Go server aggregation, Java service aggregation, React hooks, usage UI) works for Cursor sessions with zero modifications.

### Critical Architecture Fix

T03 built a `UsageTracker` that accumulated raw token counts into an aggregate `UsageMetrics` proto. This did not match the system's actual architecture:

- The `toUsageMetrics()` method was never called -- accumulated data was discarded
- The aggregate approach was fundamentally different from how LangGraph handles usage
- The system expects per-message `LlmCallMetrics` on `AgentMessage.llm_metrics`, not aggregate data

The fix: rewrite `UsageTracker` to produce per-turn `LlmCallMetrics` protos with pricing stamped from a Cursor-specific registry, matching the Python pattern exactly.

### Research: Cursor SDK Does Not Provide Cost

Investigated the Cursor SDK thoroughly. The `TurnEndedUpdate.usage` provides only four token count fields (inputTokens, outputTokens, cacheReadTokens, cacheWriteTokens) -- no cost, no pricing rates, no `totalCents`. The `totalCents` field exists only in Cursor's Admin/Analytics API usage logs (dashboard-level data), not in the real-time SDK streaming events.

### Step 1: Cursor Model Pricing Registry

Created `model-pricing.ts` with per-token rates sourced from Cursor's published pricing page (https://cursor.com/docs/models-and-pricing). Covers Cursor own models (Composer 2, 1.5, 1), Auto pool, and models available via Cursor's API pool (Anthropic, OpenAI, Google). Default pricing uses Auto-pool rates as a conservative fallback for unknown models.

### Step 2: Refactored UsageTracker

Rewrote `usage-tracker.ts` to follow the per-message `LlmCallMetrics` pattern:
- `recordTurn()` now returns a fully-populated `LlmCallMetrics` proto
- Pricing looked up from `getCursorModelPricing()` at call time
- Cost computed via `computeTurnCost()` with disjoint token buckets
- Sequence numbering, timestamps, and cost logging for observability
- No aggregate `UsageMetrics` construction -- aggregation is a downstream concern

### Step 3: Wired LlmCallMetrics into Execute Flow

Modified `execute-cursor.ts` to stamp `LlmCallMetrics` on messages:
- `onDelta` callback collects metrics into a `pendingMetrics` queue
- Stream loop stamps each metric onto the most recent `MESSAGE_AI` message
- `stampMetricsOnLastAiMessage()` walks messages backward to find the target
- Post-stream drain handles edge case where turn-ended fires with no subsequent event

### Step 4: Added Cursor Provider to React Model Registry

- Added `"cursor"` to the `Provider` type union
- Added Cursor model entries (Composer 2, Composer 1.5, Auto) to `MODEL_REGISTRY`
- Added `"cursor"` to `DISABLED_PROVIDERS` (Cursor models only appear for Cursor harness sessions, not in the native model selector)

### Step 5: Verified Downstream Pipeline

Confirmed that the following files require zero changes for Cursor sessions:
- Go `usage_aggregation.go` -- walks messages generically, no provider filtering
- Java `UsageAggregationService.java` -- same generic pattern
- React `useSessionUsage.ts` -- sums `llmMetrics` from all messages, provider-agnostic
- React `UsageWidget.tsx` -- displays whatever model/provider strings come through
- React `OrgUsagePanel.tsx` -- server-side aggregation, provider-agnostic

## Key Decisions

- **Per-message LlmCallMetrics (not aggregate UsageMetrics)**: Matches the Python agent-runner pattern. Makes the entire downstream pipeline work with zero changes.
- **Static pricing table from Cursor's published rates**: Cursor SDK does not provide cost data. Pricing sourced from https://cursor.com/docs/models-and-pricing and stamped at execution time.
- **Provider = "cursor"**: Cursor is the billing provider from Stigmer's perspective. Distinguishes Cursor usage from direct Anthropic/OpenAI usage in reports.
- **One LlmCallMetrics per Cursor turn**: Finest granularity the SDK provides. Sufficient for cost tracking and real-time display.
