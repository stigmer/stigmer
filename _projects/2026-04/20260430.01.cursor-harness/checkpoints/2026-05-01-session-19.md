- Added `unhandledRejection` and `uncaughtException` handlers to cursor-runner main.ts
- Added structured logging to the fetch interceptor for proxy request failures
- Fixed CursorProxyController response header policy to forward `x-cursor-*` protocol headers instead of blanket `x-*` stripping

## Decisions Made

- **Keep process alive on unhandled rejections**: The Temporal worker's retry policies handle activity-level failures; crashing the process is strictly worse than a single activity timeout
- **Auth scheme is correct (Bearer)**: Investigation proved the Cursor SDK sends Bearer auth for gRPC-Connect calls, so no auth scheme change was needed
- **Targeted header blocking**: Replace blanket `x-*` deny with infrastructure-specific blocks (`x-envoy-*`, `x-cloud-trace-*`, `x-goog-*`) to preserve Cursor protocol headers

## Key Code Changes

- `backend/services/cursor-runner/src/main.ts`: Process-level error handlers
- `backend/services/cursor-runner/src/proxy/fetch-interceptor.ts`: Try/catch with structured logging around proxied fetch calls
- `stigmer-cloud: CursorProxyController.java`: Selective response header forwarding

## Learnings

- The Cursor SDK (`@cursor/sdk@1.0.11`) uses `Agent.create()` as an async call (returns a Promise, not immediate), calls `api2.cursor.sh/auth/exchange_user_api_key` to exchange the API key for a session token, and performs background token refreshes during long-running agent streams
- Background SDK promises can reject outside any try-catch in user code — process-level handlers are essential for production Node.js services wrapping third-party SDKs
- The Cursor REST API (`api.cursor.com`) uses Basic auth, but the SDK's gRPC-Connect calls (`api2.cursor.sh`) use Bearer auth — they are different protocols with different auth conventions
