## Decisions Made

- **Primary HITL mechanism**: Cursor `preToolUse` hooks — deterministic, non-bypassable, works local + cloud
- **Discarded MCP bridge**: Relies on agent cooperation (prompt compliance), bypassable
- **No proto changes needed for HITL**: The hooks bridge is entirely internal to the cursor-runner service
- **Execution interceptors (hooks-like system)**: Documented as strategic finding, NOT included in MVP — no customer demand yet
- **Built-in Cursor tool approval defaults**: Shell/Delete require approval, Read/Grep allow by default — runner-local config

## Key Findings

- Cursor's Hooks system is a first-class extensibility mechanism that intercepts ALL tool calls
- The `preToolUse` hook receives tool_name, tool_input, tool_use_id and returns permission (allow/deny)
- Hooks are synchronous and block until the script returns — compatible with Stigmer's async approval model
- `SDKRequestMessage` has only a `request_id` with no documented response API — not viable as primary mechanism
- Cursor has capabilities Stigmer lacks: updated_input (modify tool args), agent_message on deny, post-tool context injection, fail-open/fail-closed, tool-type matchers
- These are documented for future adoption, not MVP
