## Decisions Made

- **JIT-specific coverage is sufficient**: 48+ tests across `ValidateJitFieldsTest`, `FederatedAutoProvisionerImplTest`, `RequestCallerIdentityMapperTest`, and `FederatedJwtAuthenticationProviderTest` cover every code path, error scenario, and design decision. No additional JIT-specific tests needed.
- **No handler-level pipeline integration tests**: The codebase pattern is unit tests with mocked dependencies, not full handler pipeline tests. Pipeline ordering cannot cause JIT bugs since `ValidateJitFields` checks SSO separation independently. Adding a new test pattern for one handler would create precedent debt.
- **No end-to-end gRPC tests**: Would require Spring context, MongoDB, Redis, and FGA infrastructure. Not proportional to the value for this feature.
- **Remove stale pipeline construction tests**: `IdentityProviderDeleteHandlerTest.PipelineConstructionTests` used an outdated constructor signature and non-existent `getSteps()` API. These structural tests were tightly coupled to implementation details and had already drifted. Removed and kept the `CheckNoReferencingOrgs` behavioral tests.

## Learnings

- Test files that exist on disk but aren't registered as Bazel targets never run in CI. This is a silent coverage gap that compounds over time as the implementation evolves and the tests drift.
- Lombok `@Data` generates getters from field names (`grpcStatus` → `getGrpcStatus()`), not from custom method names. When tests reference `getErrorStatus()` but the field is `grpcStatus`, the test never compiles — but since it wasn't in a BUILD target, nobody noticed.
- The `RequestPipelineV2` API evolved to remove `getSteps()`, which broke the `PipelineConstructionTests` pattern. This validates the decision not to add pipeline ordering tests for the JIT feature — they're fragile and tightly coupled to implementation.
