## Decisions Made

- **API keys are server-side only**: Confirmed that `apiKey` config option exists for backends, CLI, SSR, and CI/CD — not for browser apps
- **Federation is the only secure browser path**: For client-side React apps, `getAccessToken` with identity federation is the correct and only secure approach
- **JIT provisioning is the answer to the friction concern**: Customer worried about federation setup complexity; JIT provisioning (from sessions 1-7) reduces this to a single backend API call
- **Documentation placement**: Added the browser auth guidance directly on the React SDK page (not a separate guide) so customers find it on the page they are already reading

## Key Code Changes

- `docs/sdk/react/index.mdx`: Added "Server-side and internal tools" heading for `apiKey` example; added full "Browser authentication" section with `getAccessToken` code example, security warning, and federation links; added auth method selection callout
- `docs/sdk/index.mdx`: Replaced single-method auth intro with dual-method bullet list; added error-level "Never expose API keys in client-side code" callout; updated `getAccessToken` description to reference browser apps and JIT provisioning

## Learnings

- Industry comparison: Products like Stripe, Clerk, and Firebase solve this with publishable/restricted keys that are safe to expose in browsers. Stigmer currently has only secret keys (`sk_`), so federation is the only browser-safe option.
- The JIT provisioning project was designed precisely for this scenario (DD-002 confirms this), but the SDK docs didn't connect the dots for customers
