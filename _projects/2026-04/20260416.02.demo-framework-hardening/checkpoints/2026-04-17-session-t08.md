## Decisions Made

1. **`data-cursor-target`, not `data-viewport-target`**: The T08 plan proposed a new `data-viewport-target` attribute. Rejected in favor of the unified `data-cursor-target` targeting model established by T07's precedent. The action type + field name already disambiguate purpose.

2. **`ViewportTransformLayer` as a separate engine component**: The transform layer wraps content but NOT the Cursor. This cursor isolation invariant ensures `position: absolute` coordinates work correctly — the cursor targets elements at their visual (post-transform) positions via `getBoundingClientRect()`, which correctly reflects CSS transforms.

3. **Conditional `overflow: hidden`**: Only applied when the transform is not identity (`scale !== 1 || x !== 0 || y !== 0`). At identity, overflow is unrestricted so portaled content (dropdowns, tooltips) is not clipped during normal playback.

4. **Softer spring for zoom**: `stiffness: 100, damping: 20, mass: 0.8` — intentionally softer than the cursor spring (`170, 22, 0.6`). The zoom should feel cinematic and deliberate, not snappy. Settles in ~500ms.

5. **Single-phase action**: Unlike click (2-phase), type (3-phase), hover (3-phase), and drag (4-phase), the viewport transition is single-phase. There are no secondary events to dispatch — the transform is computed and set, and Framer Motion handles the animation. This is the simplest action type in the engine.

6. **Viewport transform persists across steps**: The transform is not auto-reset on step change. The scenario author explicitly resets via `viewportReset: true`. The `onStepChange` callback should reset on step 0 (restart/loop).

7. **Framer Motion only**: Rejected "Framer Motion or CSS transition" from the original plan. Framer Motion is already used by `Cursor.tsx`, its spring simulation advances frame-by-frame in Remotion for deterministic video export, and CSS transitions would need separate video-path handling.

8. **`transformOrigin: "0 0"`**: Scale and translate compose from the top-left corner. The translate computation (`x = cw/2 - ex * scale, y = ch/2 - ey * scale`) assumes top-left origin, making the math straightforward and predictable.

## Learnings

- The single-phase model is a welcome simplification after the multi-phase complexity of click/type/hover/drag. The key insight: viewport transitions are camera movements, not user input simulations. There are no DOM events to dispatch, no attributes to toggle — just a coordinate transform computed from element geometry. The animation is entirely Framer Motion's responsibility.
- The `getBoundingClientRect()` + CSS zoom correction formula (`computeCursorPosition`) naturally handles elements inside a CSS-transformed wrapper. CSS transforms affect `getBoundingClientRect()` return values (they report visual positions), and since the cursor is positioned absolutely in the container (which is NOT transformed), the cursor lands at the correct visual position. No cursor code changes were needed.
- The `warnIfViewportTooCloseToAction` pattern is novel — it looks at sibling actions in the same step rather than checking total duration. This cross-action awareness is unique to viewport transitions because the spring settle time affects subsequent actions' positioning accuracy, not just whether they fire before the step ends.

## Open Questions

- Whether the `computeViewportTransformForTarget` math is correct under compound scenarios: DemoViewport CSS zoom (e.g., 0.7 on narrow screens) + viewport transition scale (e.g., 1.8). The formula accounts for CSS zoom via `getBoundingClientRect` + `offsetWidth` division, but the compound case needs browser verification.
- Whether the Framer Motion spring simulation advances correctly frame-by-frame in Remotion for the `ViewportTransformLayer`. The cursor spring works this way, so this should be fine, but it needs verification during video export testing.
- Whether `overflow: hidden` on the clip layer interacts with `scrollIntoView` calls inside the transformed content. The scroll-to action might behave differently when the scroll container's visual bounds are clipped.
