## Decisions Made

1. **Two-phase execution in the hook, not a Cursor callback** — All action logic stays in `useStepInteractions`. Cursor.tsx stays focused on visual rendering with no new API surface. `CLICK_DELAY_MS` is deterministic (matches spring settle), so no animation-completion callbacks are needed.
2. **`element.click()` (native method)** — Fires through React 18's event delegation. Tested to work with SDK components like `ApprovalCard` which already wire `data-cursor-target` and `onClick`.
3. **Both rendering patterns coexist** — The `click` action is additive. Existing three-step snapshot scenarios remain untouched. New scenarios can use either pattern based on what fits their rendering model.
4. **No automatic `clear-cursor` after click** — Scenario author explicitly adds `clear-cursor` if needed. No magic behavior.
5. **`click` is exclusively a mid-step action** — Lives in `StepInteractions` (useStepInteractions hook), not in the step-level `cursorTargetFor` pattern. Keeps visual-only cursor cleanly separated from actions that dispatch DOM events.
6. **Shared timing constants in `engine/timing.ts`** — Not in `tokens.ts` (which is for layout tokens). `CLICK_DELAY_MS` is an engine timing constant coordinating animation between Cursor and useStepInteractions.

## Learnings

- `HTMLElement.click()` fires through React 18's event delegation correctly — no need for `dispatchEvent(new MouseEvent(...))` or other workarounds
- The two-phase approach (cursor move at `atPercent`, click dispatch at `atPercent + CLICK_DELAY_MS`) extends naturally to both browser and video paths without any changes to Cursor.tsx
- The paradigm shift from snapshot rendering to interactive rendering is significant but manageable — scenarios that use `click` need real handlers, not `noop`, and must track local state for the post-click visual
- Pre-existing screenshot baseline mismatches in `demo-visibility.spec.ts` (28 failures across unmodified scenarios) are unrelated to T04 — functional tests all pass
