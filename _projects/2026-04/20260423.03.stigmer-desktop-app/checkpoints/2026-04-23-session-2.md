## Decisions Made

- **SDK is the sharing layer** — No `@stigmer/app` or `@stigmer/ui` package. Hooks and components are the right abstraction level. Sidebar duplication (~200 lines) is acceptable vs an over-abstracted shared navigation pattern.
- **Auth via PKCE + local callback** — Mirror CLI's Auth0 PKCE flow (not `stigmer://auth/callback`). Auth works on first launch before any URL scheme is registered. Same Auth0 client ID and audience across all three clients.
- **Full OrgGate, not simplified** — Provisioning race condition (Auth0 creates user before Stigmer server creates personal org) exists regardless of client type. Desktop has no natural delay after auth, so provisioning poll is necessary.
- **Draft/edit mode in SDK** — `CREATOR_AGENTS`, `parseDraftParams`, `useEditSessionPrep` all moved to SDK. URL building stays app-specific.
- **`usePersistedModel` extracted** — Both flows (new session + session page) share model persistence. Extracted as standalone hook.

## Learnings

- The plan's estimate of "~2 days for Phase A" was conservative — the extraction was clean because the web app's domain logic had clear boundaries (only 2-3 console-specific imports per file)
- `SearchResult` from protobuf has `org` and `slug` fields directly — no need for a `resourceRef` sub-object
- `OrgMembersPanel` and `OrgProfilePanel` take `orgId` (not slug) — need `useOrganization` to resolve
- `ApiKeyListPanel` is identity-scoped (no org prop needed)
- `ResourceCountCard` and `ResourceListView` are presentation-only — consumer provides data from separate hooks
