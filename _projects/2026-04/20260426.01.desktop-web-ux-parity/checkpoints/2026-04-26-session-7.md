## Decisions Made

- **Version footer placement**: Kept as desktop-specific element below UserMenu (not inside UserMenu's extraItems slot). Tauri auto-updater is a native desktop concern.

- **Color mode as localStorage preference**: Added `useColorModePreference()` hook that persists to `stigmer:colorMode` key. Flows through `StigmerProvider` via `App.tsx`. UserMenu radio buttons now functional.

- **SettingsLayout container vs per-page**: SettingsLayout applies `max-w-3xl` container. SettingsRunners sits outside the layout route (full-width for split-panel log viewer). SDK sections render directly in routes without wrapper files.

- **Section extraction over duplication**: Rather than duplicating web Section orchestration logic in desktop, extracted all 9 sections to SDK. Both apps now import identical components. IdentityProvidersSection accepts `ssoLoginBaseUrl` prop for SSO URL portability.

- **Library pages are thin routing wrappers, not duplication**: Audit confirmed these follow DD-004 (zero framework deps in SDK). The SDK provides the heavy lifting (ResourceListView, DetailViews, count hooks). The apps provide routing glue. Extracting further would require injecting LinkComponent/useNavigate as props — complexity not worth the gain.

## Learnings

- Desktop settings routes can reference SDK section components directly — no per-page wrapper file needed when the layout route provides the container. Only exceptions are app-specific pages (runners, billing).

- The `SettingsRunners` page (408 lines) is genuinely desktop-specific — uses Tauri hooks for local runner management, split-panel log viewer, runner start dialog. The web's RunnersSection is completely different. These cannot and should not be unified.

- The duplication audit pattern (file-by-file verdict with reasoning) is effective for making principled keep-vs-extract decisions. Not all code that looks similar is harmful duplication — routing wrappers are framework-specific by design.
