## Key Design Decisions

1. **SSO config lives on IdentityProvider, not Organization**: SSO is an attribute of the IdP, not the org. An IdP is already scoped to an org via `metadata.org`. This avoids coupling OrganizationSpec to IdP lifecycle, avoids bidirectional references, and follows the established "query by org" pattern. OrganizationSpec was NOT modified.

2. **PKCE (no client_secret)**: The web app is a public client using OIDC Authorization Code flow with PKCE. No client_secret is stored — this is the recommended approach for SPAs per OAuth 2.0 for Browser-Based Apps RFC draft.

3. **No oidc_discovery_url field**: The OIDC discovery URL is derived from `allowed_issuers[0]` + `/.well-known/openid-configuration`. No need for a redundant field.

4. **SsoProviderInfo projection (not full IdentityProvider)**: The SSO discovery endpoint is unauthenticated (called before login). Returning the full IdP resource would leak JWKS URI, rate limits, and userinfo endpoint. The projection returns only what the web app needs.

5. **Shared ValidateSsoFields step**: Typed to `ContextBase<IdentityProvider, IdentityProvider>` (the common supertype) rather than duplicating as inner classes. The pipeline's `addStep(? super T)` signature accepts this for both `CreateContextV2` and `UpdateContextV2`.

6. **Platform delegation guard only on update**: A newly created IdP cannot already be referenced by platform-managed organizations, so the guard is only needed during update (when enabling SSO on an existing IdP).

7. **isUpdate detection via metadata.id**: During create, `metadata.id` is empty (generated later by buildNewState). During update, the client sets `metadata.id` to identify the resource. This reliably distinguishes create vs update in the shared step.

## Architectural Insights

- The federated auth flow (`FederatedJwtAuthenticationProvider` -> `FederatedIdentityResolverImpl`) already works for SSO at the API level — it resolves accounts by IdP + sub, independent of the org. The Phase 4 changes add **discoverability** (how the web app finds the SSO config) and **validation** (business rules), not authentication logic.
- SSO and platform delegation are separate trust models. Mixing them on the same IdP creates ambiguous semantics. The platform-delegation guard enforces this separation.
- The `getSsoProvider` endpoint deliberately returns a projection, not the full resource. This is a security boundary — pre-login endpoints must not leak internal infrastructure config.
