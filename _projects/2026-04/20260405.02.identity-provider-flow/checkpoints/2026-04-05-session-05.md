## Key Design Decisions

1. **`idp_id` is not globally unique, but that's fine**: For direct/machine accounts, Auth0 generates globally unique IDs. For federated accounts, uniqueness is the compound `(identityProviderRef.org, identityProviderRef.slug, idpId)`. The existing partial compound unique index enforces this. No changes needed.

2. **`getByIdpId` uses direct `findByIdpId`, not Auth0 -> email indirection**: The old handler called Auth0 Management API to get the user's email, then looked up by email. With email no longer unique (Phase 1), this was broken. Direct `findByIdpId` is correct for Auth0 IDs (which are unique within the tenant) and removes an external API call.

3. **`getByEmail` scoped to direct accounts**: Added `spec.identityProviderRef.org exists(false)` filter. Federated accounts should be looked up by their IdP-scoped identifier, not by email. This prevents cross-trust-boundary leaks.

4. **`getByExternalSub` authorization reuses `can_create_identity_account`**: If a platform can create federated accounts in an org, it can also check if one already exists. No new permission needed.

5. **SDK policy — keep all RPCs in SDKs**: Access controlled via FGA authorization. Internal-only intent documented in proto comments rather than removing from SDKs.

6. **Dead cache proxies removed**: `EmailToIdentityAccountIdCacheProxy` and `EmailToIdpIdCacheProxy` had zero callers anywhere in the codebase. Removed along with their Redis methods.

## Architectural Insights

- The `getByIdpId` handler was calling Auth0 Management API on every lookup — this was unnecessary overhead added during initial implementation when email was the primary lookup key. With the direct `findByIdpId` approach, this external API call is completely eliminated.
- The `EmailTo*CacheProxy` classes were likely leftovers from an earlier architecture where email-based resolution was the primary path. The current auth flow goes through `IdpIdToIdentityAccountIdCacheProxy` (for Auth0) and `FederatedIdentityResolverImpl` (for federated), neither of which uses email.
- The `findByIdOrEmail` method in `IdentityAccountRepo` is used by `getActorInfo` — it needed the same federated exclusion to prevent actor resolution from accidentally picking up federated accounts.
