## Decisions Made

- **No data migration needed**: User confirmed no federated account data exists in production, so no migration or dual-read logic was necessary. Clean switch to new lookup pattern.
- **`Optional<String>` return type for resolver**: The resolver is a pure lookup; policy decisions (401 on not-found) belong in `RequestCallerIdentityMapper`. Keeps the resolver testable and single-responsibility.
- **`userInfoEndpoint` removed from token**: The auth token should carry only what's needed for authentication and identity resolution. Profile data fetching is a separate concern for Phase 3.
- **Redis cache key format `{org}/{slug}:{sub}`**: Uses the same fields as the MongoDB compound lookup for consistency. No internal IdP database ID needed in the key.
- **`UserInfoClient` kept but decoupled**: Not deleted — correct, self-contained component useful for future profile sync features. Just removed as a dependency of the resolver.
- **`IdentityAccountNotFoundException` reused**: For the 401 error when a federated account doesn't exist, reused the existing exception class rather than creating a new one.

## Learnings

- The `FederatedAuthenticationToken.userInfoEndpoint` was only consumed by `RequestCallerIdentityMapper` to pass to the provisioner. With provisioning removed, the field had zero consumers — clean removal with no ripple effects.
- The `RequestCallerIdentityMapper` catch block needed special handling: `IdentityAccountNotFoundException` must not be wrapped in a generic `RuntimeException`, so an explicit re-throw was added before the catch-all.
- MongoDB field names in queries use camelCase (`spec.identityProviderRef.org`) matching the protobuf JSON serialization format, not the snake_case proto field names.

## Open Questions
