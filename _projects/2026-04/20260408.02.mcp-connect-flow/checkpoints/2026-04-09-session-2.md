## Decisions Made

1. **Deleted `McpServerUpdateDiscoveredCapabilitiesHandler` entirely** instead of renaming to `McpServerObserveStatusHandler`. The `updateDiscoveredCapabilities` RPC was already deleted in T01. No `observeMcpServerStatus` RPC is needed — all status writes flow through the `connect` workflow's Temporal output. This avoids a platform-level backdoor RPC and keeps `status` as purely system-derived.

2. **No `can_update_mcp_server_status` FGA permission needed** — direct consequence of decision #1. The T02 Graphton backfill will call the `connect` RPC instead of a separate status-update RPC.

3. **Unconditional `pinned_tool_approvals` preservation in registry sync** — the old `UpsertMcpServerBatchActivityImpl` conditionally merged `default_tool_approvals`. Since `pinned_tool_approvals` are user-owned and never provided by the registry, the sync now unconditionally preserves them from the existing record.

4. **Workflow name kept as `"stigmer/mcp-server/discover"`** — the Go `connect.go` handler and Python `discover_mcp_server.py` both use this name. Renaming to `"stigmer/mcp-server/connect"` must happen in all three (Go + Java + Python) simultaneously, deferred to T02.

## Learnings

- The `McpServerCommandController.Method` constants are auto-generated at compile time by `AutoGrpcRouterControllerProcessor`. Handlers reference them via `@RequestRoute` and the routing is resolved at runtime by `RequestFactory` scanning `@RequestRoute` beans.
- Platform-level FGA auth (like `can_update_execution_status`) is checked via `commonSteps.authorize` reading proto method options. Resource-level auth (like `can_connect`) uses either proto method options or a custom `Authorize` step with explicit `RpcAuthorizationConfig`.
- The `DiscoverCapabilitiesInput` and `DiscoverySource` Java stubs were deleted by T01's codegen run, so the old handler wouldn't compile — this was expected and caught by design.
