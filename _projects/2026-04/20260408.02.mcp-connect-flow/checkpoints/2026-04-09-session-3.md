## Decisions Made

- **Additive pinned semantics**: `pinned_tool_approvals` (spec) and `status.tool_approvals` (status) both contribute approval requirements as a union. Neither can exempt a tool. Exemptions happen at the agent level via `ToolApprovalOverride.requires_approval = false`.
- **Synchronous backfill**: First execution blocks during setup while connect completes (~15-45s). Non-fatal on failure.
- **24-hour staleness threshold**: Backfill triggers not just on never-discovered servers but also when last discovery is older than 24h. Named constant `_BACKFILL_STALENESS_THRESHOLD_SECONDS` for easy adjustment.
- **`last_discovered_at` as backfill signal**: More reliable than checking empty tools list (MCP server could legitimately have zero tools).
- **Null safety in `_needs_backfill`**: `AttributeError` guard handles missing `status`, missing `discovered_capabilities`, and missing `last_discovered_at`.

## Learnings

- The `hasattr` guard on proto fields silently swallows renamed fields — the `default_tool_approvals` → `pinned_tool_approvals` rename in T01 broke server-level approval policies without any error. Proto field renames need grep-based impact analysis.
- `with_structured_output` requires a Pydantic model, not a dataclass. The Temporal activity layer uses dataclasses for serialization, while the LLM layer uses Pydantic — the boundary is clean.

## Open Questions

- **Go `connectTimeout` (45s)**: May be too tight for discover (up to 270s for cold-start MCP servers) + classify (up to 60s). May need to increase to match Java's 330s.
- **Runner queue contention**: Backfill starts a Temporal workflow whose activities run on the same queue as the Graphton activity. Works with `max_concurrent_activities > 1` but would deadlock on single-slot.
- **Deploy ordering**: All three repos must deploy the workflow name change together.
